    25.3 DMA-BUF 零拷贝实战¶

    所属章节：第25章 Camera全链路：从Sensor到屏幕

    难度：[E] | 预计阅读时间：45 分钟

    本节导读¶

    25.2 的 mmap 模式解决了"采集侧零拷贝"：帧从 ISP 经 DMA 进 buffer，应用直接映射读取，全程不拷。但这只是半程——帧的下一站是显示（25.4）、GPU 处理或编码器。如果显示侧需要帧数据，传统做法是 memcpy 或 copy_to_user 把 V4L2 的 buffer 搬进 DRM 的 buffer。算笔账：1080p NV12 一帧约 3MB，30fps 就是每秒 90MB 的纯搬运，4K60 翻八倍到约 700MB/s——DDR 带宽和 CPU 就这么被"倒数据"吃掉了。

    DMA-BUF 就是内核对这个问题的标准答案：让 buffer 的物理内存只有一份，子系统之间传递的只是一个文件描述符（fd）。本节把这条机制落到代码上，本节覆盖：

    • dma-buf 是什么：exporter/importer 角色与 fd 语义
    • Camera→Display 零拷贝的完整五步：分配、导出、导入、采集、上屏
    • 可运行的交接代码：DRM 分配 buffer，V4L2 导入采集，atomic commit 上屏
    • buffer 谁来分配：dumb buffer / GBM / dma_heap 三个来源的定位与选择
    • cache 一致性：CPU 摸过 dma-buf 之后会发生什么，为什么要 SYNC
    • 高频坑：对齐/stride、fd 生命周期、泄漏排查

    💡 "什么时候值得上零拷贝、带宽预算怎么算"的决策讨论在 22.5 已经做过，本节只做机制与实操：假设你已经决定要用，这里讲怎么用它、哪里会翻车。

    dma-buf 是什么：一个 fd 的背后¶

    先建立准确的心智模型。dma-buf 不是一种内存，它是内核里的一个"交接对象"：某个驱动（比如 DRM）分配好一块物理内存后，可以把它包装成一个 dma-buf 对象，并导出为一个文件描述符。别的驱动（比如 V4L2）拿到这个 fd，就能把它"导入"映射到自己的 DMA 地址空间。物理内存始终只有一份，fd 只是这张内存的"通行证"，可以像普通 fd 一样在进程间传递（fork、UNIX socket）。

    exporter（导出方）：分配物理内存并创建 dma-buf 的那一方。它提供一组回调（ops），告诉内核"有人要 DMA 这块内存时怎么拿 scatterlist、有人要 mmap 时怎么映射"。Camera→Display 链路里，exporter 通常是 DRM/显示侧（或用 GBM/ION 分配）。

    importer（导入方）：拿到 fd、把这块内存挂进自己 DMA 域的那一方。V4L2 驱动导入后，ISP 的 DMA 引擎就能直接往里面写帧。

    scatterlist：描述"一块内存在物理上由哪些段组成"的结构。DMA 引擎不认识虚拟地址，驱动要把 buffer 翻译成一组（物理地址，长度）对喂给硬件。importer 导入 dma-buf 的本质就是向 exporter 要到这张表。

    fd 语义带来两个直接推论：第一，fd 可以跨进程传——采集进程拿到的 dma-buf fd 可以通过 UNIX socket 交给显示进程，内存还是那一份；第二，fd 有引用计数，最后一个引用关闭时 exporter 才真正释放内存——fd 泄漏就是内存泄漏，本节末尾的排查会用到这一点。

    Camera→Display 零拷贝五步¶

    整条链路的 buffer 流转，大纲里的五步在代码层面长这样：

    ① DRM 分配 buffer（dumb buffer / GBM），得到 handle
② DRM 导出：handle → dma-buf fd（PRIME）
③ V4L2 导入：REQBUFS 声明 DMABUF 模式，QBUF 时把 fd 交给驱动
④ 采集：ISP 的 DMA 直接把帧写进这块内存（CPU 完全不参与）
⑤ 上屏：同一个 handle 直接交给 DRM atomic commit，显示控制器 scanout

    对照传统路径（V4L2 buffer → memcpy → DRM buffer），省掉的是每一步的 CPU 拷贝和中间那份额外的内存。下面逐段给代码。

    ①② DRM 侧分配并导出：

    /* 在 DRM 设备上分配一块 NV12 大小的 dumb buffer */
struct drm_mode_create_dumb creq = {0};
creq.width  = 1920;
creq.height = 1080 * 3 / 2;                 /* NV12: Y平面 + UV平面，高度1.5倍 */
creq.bpp    = 8;                            /* 按单平面8bit申请，手动算总高 */
ioctl(drm_fd, DRM_IOCTL_MODE_CREATE_DUMB, &creq);
/* creq.handle 是 DRM 内部的 buffer 句柄 */

/* 导出为 dma-buf fd，这就是可以递给 V4L2 的"通行证" */
int dmabuf_fd;
struct drm_prime_handle prime = {0};
prime.handle = creq.handle;
prime.flags  = DRM_CLOEXEC;
ioctl(drm_fd, DRM_IOCTL_PRIME_HANDLE_TO_FD, &prime);
dmabuf_fd = prime.fd;

    ③④ V4L2 侧导入并采集： 与 25.2 的 mmap 模式只差两个 ioctl 的参数——REQBUFS 声明 memory 类型为 DMABUF，QBUF 时给的是 fd 而不是 index 对应的内核偏移：

    struct v4l2_requestbuffers req = {0};
req.count  = 1;                             /* 导入外部buffer：一个fd一个buffer */
req.type   = V4L2_BUF_TYPE_VIDEO_CAPTURE;
req.memory = V4L2_MEMORY_DMABUF;            /* 关键：声明用外部dma-buf */
ioctl(v4l2_fd, VIDIOC_REQBUFS, &req);

struct v4l2_buffer buf = {0};
buf.type   = req.type;
buf.memory = V4L2_MEMORY_DMABUF;
buf.index  = 0;
buf.m.fd   = dmabuf_fd;                     /* 把DRM的buffer交给V4L2驱动 */
ioctl(v4l2_fd, VIDIOC_QBUF, &buf);

enum v4l2_buf_type type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
ioctl(v4l2_fd, VIDIOC_STREAMON, &type);     /* 开流后ISP的DMA直接写这块内存 */

/* 等一帧写完 */
struct v4l2_buffer dq = {0};
dq.type = type; dq.memory = V4L2_MEMORY_DMABUF;
ioctl(v4l2_fd, VIDIOC_DQBUF, &dq);          /* 帧已在这块物理内存里 */

    注意 DQBUF 返回后什么都没拷——帧数据已经在 DRM 那块 buffer 里了。

    ⑤ DRM 上屏： 用同一个 handle 创建 framebuffer，atomic commit 翻页（完整 atomic 流程是 25.4 的内容，这里只示意交接点）：

    /* 用同一个 handle 建 FB——注意 stride/offset 要对齐 NV12 双平面 */
uint32_t handles[2] = { creq.handle, creq.handle };
uint32_t pitches[2] = { 1920, 1920 };       /* Y平面和UV平面行字节数 */
uint32_t offsets[2] = { 0, 1920 * 1080 };   /* UV平面紧跟Y平面之后 */
uint32_t fb_id;
drmModeAddFB2(drm_fd, 1920, 1080, DRM_FORMAT_NV12,
              handles, pitches, offsets, &fb_id, 0);
drmModeSetPlane(drm_fd, plane_id, crtc_id, fb_id, 0,
                0, 0, 1920, 1080,           /* 屏幕目标区域 */
                0, 0, 1920 << 16, 1080 << 16); /* 源区域(16.16定点) */

    跑通这五步，你就拥有了一条 Camera→DDR→Display 的零拷贝通路：CPU 在数据路径上的工作量为零，只做配置和同步。实际产品里会申请 2~4 个这样的 buffer 轮转（25.2 的队列模型在这里原样适用），而不是示例里的单个。

    buffer 谁来分配：dumb buffer、GBM 与 dma_heap¶

    上面示例用 DRM dumb buffer 当 exporter，这是教学上最直接的选择，但不是唯一选择，也不总是最优。实际工程里有三个常见的分配来源，理清它们的定位能避免在错误的基础设施上开工：

    dumb buffer：DRM 自带的极简分配接口（DRM_IOCTL_MODE_CREATE_DUMB）。优点是零依赖、代码量小；缺点是它只知道"宽度×高度×位深"，不理解 NV12 这种多平面格式，也不参与格式 modifier 协商——所以上一节的示例才要手动把高度乘 1.5、手动算两个平面的 offset。适合 demo 和单平面简单场景。

    GBM（Generic Buffer Management）：Mesa 提供的通用 buffer 分配库，是现代 Linux 图形栈（Wayland/weston、kmscube）的标准选择。它按像素格式+使用标志分配（"我要一块 NV12、用于 scanout 和 camera 写入"），内部自动处理多平面、stride、modifier 协商，gbm_bo_get_fd 直接给 dma-buf fd。产品级 Camera→Display 链路的推荐选项。

    dma_heap：ION 的正统继任者（ION 从未进主线，dma_heap 在 Linux 5.6 起进入主线）。它是纯内核分配器，用户态通过 /dev/dma_heap/system（或 system-uncached、厂商 cma heap）ioctl 分配并直接拿到 dma-buf fd。不依赖 DRM，适合没有显示链路、纯做 Camera→编码器/NPU 的场景。

    选择的判断逻辑很直接：链路里有显示、且系统本来就有 Mesa，就用 GBM，让 modifier 协商替你挡掉对齐类问题；没有图形栈的采集处理产品（门铃、IPC 摄像头），用 dma_heap 分配、V4L2 和编码器各自导入；dumb buffer 留给验证和教学——你清楚它在格式协商上"什么都不管"，就不会把线上问题归咎于它。

    用 GBM 改写①②步的核心代码（其余步骤不变）：

    struct gbm_device *gbm = gbm_create_device(drm_fd);
struct gbm_bo *bo = gbm_bo_create(gbm, 1920, 1080,
        GBM_FORMAT_NV12,                       /* 直接声明像素格式 */
        GBM_BO_USE_SCANOUT | GBM_BO_USE_LINEAR); /* 声明用途：上屏+线性布局 */
int dmabuf_fd = gbm_bo_get_fd(bo);           /* 一步拿到dma-buf fd */
uint32_t stride_y  = gbm_bo_get_stride_for_plane(bo, 0);  /* Y平面stride */
uint32_t stride_uv = gbm_bo_get_stride_for_plane(bo, 1);  /* UV平面stride */
/* 后续V4L2导入、DRM建FB的流程与dumb buffer版相同，stride用上面查到的值 */

    对比 dumb buffer 版就能看出 GBM 的价值：格式是显式声明的，stride 是查询出来的，多平面偏移由库管理——"手动算高度×1.5"这类易错的手工活全部消失。

    cache 一致性：CPU 一伸手就会踩的坑¶

    零拷贝链路里 CPU 原则上不碰数据，但总有例外：比如要在画面上叠加 OSD 文字、抽帧做算法分析。CPU 一旦读写 dma-buf 映射的内存，就撞上一个体系结构层面的问题——CPU cache 和 DMA 各看各的内存视图。

    机理一句话：DMA 引擎读写的是物理内存，不经过 CPU 的 cache。如果 CPU 之前读过这块内存，cache 里可能留着旧数据（CPU 再读时读到的是旧值）；如果 CPU 写过，新数据可能还在 cache 里没刷回内存（DMA 读到的是旧值）。两个方向的典型症状：

    • DMA 写完，CPU 读：读到的是 cache 里的旧帧残影。画面像"上一帧和这一帧叠在一起"，或算法分析结果总是慢一拍；
    • CPU 写完（OSD），DMA 读（显示/编码）：屏幕上看不到叠加的内容，或者只有部分内容——没刷回内存的那部分丢了。

    修复手段分平台。内核为 dma-buf 定义了显式同步接口，CPU 访问前后各调一次：

    struct dma_buf_sync sync = { .flags = DMA_BUF_SYNC_START | DMA_BUF_SYNC_READ };
ioctl(dmabuf_fd, DMA_BUF_IOCTL_SYNC, &sync);   /* 开始CPU访问： invalidate cache */

/* …… CPU 安全地读写这块内存 …… */

sync.flags = DMA_BUF_SYNC_END | DMA_BUF_SYNC_READ;
ioctl(dmabuf_fd, DMA_BUF_IOCTL_SYNC, &sync);   /* 结束CPU访问： flush cache */

    ⚠️ DMA_BUF_IOCTL_SYNC 属于"标准里写了但驱动不一定实现"的接口——不少 ARM SoC 厂商驱动对它返回 ENOTTY，实际依赖内部隐式同步。工程上的稳妥做法：能用 GPU/硬件 OSD 叠加就别让 CPU 碰帧数据；必须碰时先小流量验证 SYNC 是否生效，不生效的平台用厂商私有接口（如 RK 的 RGA 同步）或干脆接受一次拷贝。上线前必须用真机验证 cache 行为，模拟器和开发板结论可能不同。

    高频坑位清单¶

    对齐与 stride。 DRM 显示控制器对 buffer 的行对齐有硬件要求（常见 16/64/128 字节对齐），V4L2 的 ISP 也有自己的 stride 约束。dumb buffer 的 pitch 由 DRM 驱动按它对齐规则算（creq.pitch），但 V4L2 写入时用的是它自己的 bytesperline——两者不一致时，画面整体斜切或花屏。处理：REQBUFS 前先 VIDIOC_G_FMT 拿到 V4L2 侧的 bytesperline，用它去算 DRM buffer 的大小和偏移，别自己拍脑袋。

    多平面格式。 NV12 是双平面格式，有的 V4L2 驱动把它暴露成单 planar 节点（V4L2_PIX_FMT_NV12），有的要求 multiplanar API（V4L2_BUF_TYPE_VIDEO_CAPTURE_MPLANE，Y 和 UV 各是一个 plane，可以各挂一个 dma-buf fd）。用错 API 的直接症状是 S_FMT 或 REQBUFS 报 EINVAL。先 VIDIOC_ENUM_FMT 查清楚驱动支持哪种。

    fd 生命周期。 QBUF 把 fd 交给驱动后，驱动内部已持有 dma-buf 引用，应用侧可以关掉自己的 fd 副本；但稳妥做法是采集期间一直持有，STREAMOFF 后再统一关。真正的事故形态是泄漏：循环里每次 PRIME_HANDLE_TO_FD 都拿新 fd 却从不 close，fd 耗尽（EMFILE: Too many open files）或 CMA 被撑爆。排查入口：

    cat /sys/kernel/debug/dma_buf/bufinfo      # 当前所有dma-buf：大小/属主/引用数
ls -l /proc/<pid>/fd | grep dma-buf        # 某进程持有的dma-buf fd

    bufinfo 里每个 buffer 的 count 字段是引用计数，采集程序运行期间看到它只涨不回落，就是泄漏路径。

    本节总结¶

    DMA-BUF 的本质是"物理内存一份、子系统间传 fd"：exporter 分配并导出 fd，importer 凭 fd 把内存挂进自己的 DMA 域。Camera→Display 零拷贝五步——DRM 分配、PRIME 导出、V4L2 以 DMABUF 模式导入、ISP 直写、同 handle 上屏——把 CPU 从数据路径上彻底摘出去。代价是三个新坑位：CPU 摸 buffer 引入的 cache 一致性（SYNC 接口+平台差异）、跨子系统的 stride/对齐协商、fd 引用计数管理（bufinfo 排查）。这些坑的共同特征是不改数据通路就永远不暴露，所以零拷贝链路的验收标准必须是"真机+满帧率+长时间"三件套。

    关键结论速查：

    问题 答案
    dma-buf 是什么 内核交接对象：包装一块物理内存，导出为 fd 跨子系统共享
    exporter/importer 分配内存并导出 fd 的一方 / 凭 fd 映射进自己 DMA 域的一方
    V4L2 导入方式 REQBUFS 声明 V4L2_MEMORY_DMABUF，QBUF 时 buf.m.fd 给 fd
    分配来源选择 有图形栈用 GBM，无显示用 dma_heap，dumb buffer 只做验证
    零拷贝省什么 CPU 拷贝 + 中间内存副本，4K60 约省 700MB/s 搬运
    CPU 访问 dma-buf 前后各一次 DMA_BUF_IOCTL_SYNC（START/END），平台不保证实现
    花屏/斜切 先查两侧 stride 对齐是否一致
    fd/内存泄漏排查 /sys/kernel/debug/dma_buf/bufinfo 看引用计数
