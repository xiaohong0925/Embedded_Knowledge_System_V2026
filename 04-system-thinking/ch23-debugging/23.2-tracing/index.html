    23.2 信息收集：日志、Tracing、监控¶

    所属章节：第23章 系统调试方法论

    难度：[M] ~ [E] | 预计阅读时间：35 分钟

    本节导读¶

    23.1 立了框架：偶发异常的第一动作是"预先布设观测"。本节回答布什么、怎么布。把 Linux 的观测手段按信息时效分三层：

    监控层  —— 系统长期的统计趋势（CPU/内存/IO 的分钟级曲线）
日志层  —— 系统自己说的话（内核/服务/应用的事件记录）
tracing 层 —— 你主动问系统的问题（某函数被谁调用、某进程在等什么）

    三层的分工一句话：监控告诉你"什么时候不对劲"，日志告诉你"系统说了什么"，tracing 告诉你"系统在干什么"。调试偶发问题时，监控层负责缩小时间窗，日志层负责找临终遗言，tracing 层负责解剖过程——缺任何一层，另外两层的信息会悬在半空对不上号。

    本节按层展开，每层给"管什么、怎么用、输出怎么读、嵌入式场景的裁剪"。最后回到机器人案例，给出一套完整的观测布设方案——23.3 的假设树就建立在这套方案产出的数据上。

    本节覆盖：日志层（dmesg/journald/应用日志纪律/pstore 临终捕获）、tracing 层（ftrace/perf/eBPF 的疆界与上手）、监控层（/proc 直读/系统监控工具/长期趋势方案）、崩溃现场三件套（coredump/kgdb/crash）、机器人案例的观测布设方案。

    日志层：系统自己说的话¶

    内核日志：dmesg 与环形缓冲¶

    内核日志存在一块环形缓冲里——固定大小，写满了从头覆盖。两个直接推论：系统跑久了，启动期的日志已被冲掉，调启动问题要趁早读；dmesg 看到的是"还没被覆盖的部分"，不是全量历史。时间戳默认是启动以来的秒数，-T 转成人可读时间（注意挂起时间会扭曲这个换算，精确对时用监控层的时间轴校正）。

    持久化靠 journald 或 syslog 把环形缓冲持续抽到磁盘——嵌入式上确认你的发行版真的开了这个抽取（Buildroot 默认系统往往只有环形缓冲，重启即失）。

    应用与服务日志：分级与留存纪律¶

    系统日志的公共纪律四条，每一条都对应一种真实事故：

    分级可用：DEBUG/INFO/WARN/ERROR 在运行时能调（kill -SIGUSR1、配置文件、dbus 接口任选其一）。出问题时不用重编固件就能打开详细日志——23.1 的"改动没生效三查"里，这是最便宜的一查。保留异常上下文：ERROR 行必须带上下文（哪个设备、哪个节点、什么参数），"init failed" 是日志负债。时间戳可信：日志系统依赖系统时间，而嵌入式设备 RTC 常常没电、NTP 未同步前时间是 1970——跨设备对日志前，先确认各机时钟同步状态，错乱的时钟会把事件顺序讲成另一个故事。留存有边界：logrotate 或 journald 上限配好——日志写满根分区导致系统故障，是嵌入式设备最高发的自伤事故之一。

    临终日志：pstore/ramoops 是偶发死机的命根¶

    内核 panic 时磁盘已经不可写——普通日志路径全部失效。pstore/ramoops 的机制：在内存里保留一块区域（约定地址，bootloader 不碰它），内核把 panic 前后的 dmesg 写进去；复位后这段内存内容还在，新启动的内核把它导出到 /sys/fs/pstore/。设备"死了又活"，临终遗言却留了下来。

    # 检查平台是否支持并启用（设备树里需要预留 ramoops 内存区）
ls /sys/fs/pstore/
# 典型产物：dmesg-ramoops-0（上次死亡的 dmesg 尾部）、console-ramoops-0

    启用它只需要设备树里一段保留内存加一个内核配置——对偶发死机类问题，这是投入产出比最高的单一项观测设施。23.5 会告诉你，机器人案的第一份有效线索就是它捞上来的。

    pstore 家族：ramoops（内存驻留，断电即失但扛 panic）、pstore-block（写块设备，断电不丢但要求死亡时块设备还能写）、pstore-ftrace（死亡前的函数调用轨迹）。选型按死亡形态：panic/挂死后能复位重启的用 ramoops，直接断电的才需要 block 方案。

    tracing 层：主动问系统问题¶

    日志是系统"自愿说的"，tracing 是你"审问出来的"。三个主力工具按抽象层级排开，各管一片，别用错地方：

    ftrace/trace-cmd：内核行为的显微镜¶

    内核内置的跟踪框架，回答"内核里正在发生什么"：函数被谁调用、某个事件（调度切换/中断/块 IO/系统调用）什么时候发生、延迟多久。trace-cmd 是它的标准前端：

    trace-cmd record -e sched_switch -e irq_handler_entry sleep 5   # 录 5 秒调度与中断事件
trace-cmd report | head -30                                      # 看谁在跑、被谁打断

    典型用法：延迟类问题的过程解剖——20.3 的调度延迟分析、osnoise/timerlat tracer（它们就是 ftrace 的预制 tracer）；"谁动了我的设备"——跟踪寄存器访问、GPIO 翻转的调用方。嵌入式开销可控（事件级跟踪几个百分点），可以上生产环境短期开启。

    perf：性能分析的望远镜¶

    基于硬件性能计数器（PMC）和采样，回答"时间花在哪了"：

    perf top -g                # 实时看 CPU 热点（含调用链）
perf record -a -g sleep 30 # 全系统采样 30 秒
perf report --sort=dso     # 按库/模块聚合——"CPU 100%"的五秒定性

    性能异常的黄金第一问"CPU 在跑什么"用 perf top 五秒出答案。注意内核侧需要帧指针或 dwarf 支持才能还原调用链（Buildroot 自定义内核常裁掉，perf report 里全是地址没有函数名时就是这个问题）。

    eBPF/bpftrace：可编程的观测¶

    把一段沙箱小程序挂到内核任意观测点，自定义"在什么事件上记录什么"。bpftrace 一行式的威力：

    bpftrace -e 'kprobe:do_sys_open { printf("%s opening %s\n", comm, str(args->filename)); }'
# 谁在打开什么文件——排查"配置到底被谁改了"类问题十秒出答案

bpftrace -e 'tracepoint:syscalls:sys_enter_read /pid==1234/ { @count = count(); }'
# 指定进程的 read 调用计数

    它填的空白是：ftrace 只能按预定义事件看，eBPF 能按你的问题定制。代价是内核版本要求（4.x 后期起步，功能逐年增强）和 ROOT 权限——嵌入式老内核上用不了时，ftrace 是退而求其次的全能选项。

    工具 回答的问题 开销 内核要求 典型场景
    ftrace/trace-cmd 内核事件的发生顺序与延迟 低~中 2.6+ 标配 延迟解剖、事件时序
    perf CPU 时间花在哪 低（采样） 标配，调用链需帧指针 CPU 热点定性
    eBPF/bpftrace 你自定义的任何观测问题 低 4.x+ 渐进 定制观测、生产环境长期挂点

    💡 三选一的记忆法：时间问题找 ftrace（看延迟与时序），热点问题找 perf（看 CPU 分布），行为问题找 eBPF（看"谁在做什么"）。三个都熟不如先精一个——ftrace 的适用面最宽，推荐它当第一个。

    监控层：长期趋势的统计学¶

    偶发异常和性能异常的主战场。三层结构：读数工具、采样存储、告警。

    读数工具（现场五件套，全部零安装）：vmstat 1（CPU/内存/IO 的总貌，盯 r 队列和 si/so）；mpstat -P ALL 1（逐核分解，单核 100% 是多核系统最常见的不均衡）；iostat -x 1（磁盘队列深度与 await，IO 型延迟的定性）；pidstat 1（落到具体进程）；sar（历史回放——今天凌晨三点发生了什么）。读懂它们的关键不在记住每个列名，在建立正常基线：健康系统的这些曲线长什么样，你心里有图，异常才看得见。

    判读示范——"应用说卡"时的一分钟 vmstat 1：

    procs ------memory----- --swap-- ---io---- -system-- ------cpu-----
 r  b    swpd   free    si   so    bi   bo   in    cs  us sy id wa st
 6  0       0 512000     0    0    10   50 2200  4100  45 15 40  0  0
 6  0       0 512000     0    0     0   20 2300  4200  48 14 38  0  0
 0  3       0  80000     0    0  9000  100 2500  4300  10 20 20 50  0

    前两秒：r=6 的任务队列（四核机器上 6 个任务排队=CPU 供不应求），us+sy=60%——CPU 是瓶颈候选。第三秒画风突变：r 掉到 0 但 b=3（三个任务堵在不可中断睡眠），wa=50%（一半时间等 IO），bi=9000（大量块读）——这一刻系统不是缺 CPU 是在等盘。结论：这是一个间歇性 IO 瓶颈，不是 CPU 瓶颈——加 CPU 核数毫无用处，要查的是谁在做大块读（pidstat -d 1 接着看）。如果只看 us 那一列的均值，你会得出"CPU 忙"的错误结论去优化代码——按秒看趋势形态，才能看到两种状态在交替。

    采样与存储：嵌入式裁剪版的方案是在设备上跑 node_exporter（或自己写的 cron+脚本），指标推到中心 Prometheus；资源紧张到极致就用最小集——每 10 秒采 CPU/内存/磁盘/温度四个数，写本地环形 CSV，出事再捞。长期趋势的价值在 23.1 说的"性能异常先量化基线"：没有两周前的曲线，"最近变慢了"永远无法证实或证伪。

    告警：阈值告警（磁盘>90%）防自伤，趋势告警（内存日均增长>50MB）抓泄漏——内存泄漏从不触发阈值告警，等它触发时已经漏了三周。

    温度必须进监控集：嵌入式设备的偶发异常里，温度是头号环境变量——高温让时序 marginal 的硬件现形、让电源跌落、让 CPU 降频。机器人案例的突破口"高温时段"，如果没有温度曲线和死机时间点的叠加图，就只是一句无法验证的猜想。

    崩溃现场三件套¶

    功能异常（23.1 的第一类）的固定现场手段：

    coredump：进程死亡时的内存快照。嵌入式要点：ulimit 打开、core 文件落盘路径指向有空间的分区、strip 过的固件要保留带符号的副本（分析时 gdb 应用名 core文件，符号在开发机上配对）。空间紧张就配 coredump 压缩+只留最近 N 个+异常时自动上传后删除。

    kgdb：内核源码级调试（串口/网络连开发机 GDB）。挂死类问题的最后手段——系统完全无响应时，它可能是唯一能问"内核此刻在干什么"的途径。代价：需要双机、内核带调试信息、学习曲线陡。不是日常工具，是"每月死一次的挂死"值得专门搭一次的装备。

    crash：分析内核转储（vmcore）的工具——内核死了，把它的"尸体"拿到开发机上解剖：看每个 CPU 在跑什么、每个任务的内核栈、内存使用明细。需要 kdump 机制（用小内核捕获大内核的转储），嵌入式上内存紧张时配置要斟酌，但对"偶发内核挂死"，kdump+crash 是从"猜"到"看"的分水岭。

    案例布设：给机器人装上黑匣子¶

    回到 23.1 的案例。症状：偶发挂死、日志无异常、实验室不复现。按三层观测栈布设：

    ① pstore/ramoops（临终捕获）
   设备树加保留内存，内核 CONFIG_PSTORE_RAM 打开
   → 死机重启后 /sys/fs/pstore/ 里捞上次死亡的 dmesg 尾部

② 看门狗改造（死亡检测与自动复位）
   硬件看门狗超时触发复位（挂死状态下用户态喂狗停止）
   → "死机"从"客户上门发现"变成"监控里的一次复位事件"，
     且复位前由 IRQ 线程打一份最后状态进 pstore

③ 最小监控集（环境变量采集）
   每 10 秒记录：CPU 温度/负载/内存剩余/电源电压（PMIC 寄存器）
   本地环形存 7 天，异常复位时自动上传前 1 小时数据
   → 死机时间点和环境曲线的叠加图

④ 远程日志（临终前的上下文）
   应用与内核日志实时推送到中心服务器（4G/Wi-Fi 在线时）
   → 不再依赖设备本地留存，"死前 5 分钟"的日志不再丢失

    四件套合计两天工作量，没有一行是在"调试"——全是布设。这正是 23.1 说的偶发异常打法：不等问题发生，让系统替你 7×24 盯着。布设完成后第一周，数据开始说话（23.3 会告诉你它们说了什么）：pstore 里第一次出现了内容，监控曲线第一次和死亡时刻对上了号。

    方案对比（Trade-off）¶

    维度 评价
    本地日志 vs 远程日志 本地可靠但随死机丢失上下文；远程有网络依赖——挂死类问题远程日志是刚需
    ramoops vs pstore-block 能复位重启选 ramoops（简单可靠）；直接断电场景才需要 block（实现复杂、死亡时块设备未必可写）
    全家桶监控 vs 最小监控集 四个核心数（CPU/内存/磁盘/温度）覆盖八成正因；全套方案的资源开销本身可能成为新变量
    kgdb 在线调试 vs kdump 事后分析 在线能问"现在"，事后能查"当时"；偶发挂死优先 kdump——你不可能守在 kgdb 前等它死
    eBPF vs ftrace 定制自由 vs 版本兼容；老内核项目别为了 eBPF 升级内核，ftrace 够打

    本节总结¶

    三层观测栈各司其职：监控层缩小时间窗（基线曲线+温度等环境变量），日志层找临终遗言（分级可用、时间戳可信、留存有边界、pstore 是偶发死机的命根），tracing 层解剖过程（ftrace 看时序、perf 看热点、eBPF 看行为）。崩溃现场三件套按死亡形态选：进程死用 coredump、内核挂死用 kdump+crash、需要实时审问才搭 kgdb。机器人案例的四件套布设（pstore/看门狗改造/最小监控/远程日志）演示了偶发异常的核心打法——两天布设换系统 7×24 替你值班，数据自己会开口。下一节 23.3 用这批数据建假设树：每条线索对应哪个分支、每个分支设计什么实验。

    关键结论速查：

    问题 一句话答案
    三层观测栈的分工 监控管"什么时候不对劲"，日志管"系统说了什么"，tracing 管"系统在干什么"
    偶发死机的命根设施 pstore/ramoops——panic 后 dmesg 尾部随内存驻留活下来
    工具三选一记忆法 时间找 ftrace、热点找 perf、行为找 eBPF
    perf 调用链全地址无符号 内核没编帧指针/dwarf——Buildroot 裁剪高频坑
    监控集的最小配置 CPU/内存/磁盘/温度——温度是嵌入式偶发异常头号环境变量
    内存泄漏抓法 趋势告警（日均增长）而非阈值告警
    进程死/内核挂死 coredump / kdump+crash；kgdb 只在需要实时审问时搭
    偶发问题的资源哲学 两天布设观测 > 两周守株待兔
