# 4.4.4 编译产物清单

> 所属章节：第4章 内核配置与编译 > 4.4 动手编译内核
> 
> 难度：[B] | 预计阅读时间：8分钟

## <span class="blue"> 本节导读

本节覆盖：内核编译完成后生成的各类文件（镜像、符号表、模块、设备树等）的位置、格式、用途与典型大小；区分 ARM32 与 ARM64 的路径差异；`make modules_install INSTALL_MOD_PATH=...` 的用法与输出目录结构；`.config` 作为编译产物的确认意义；以及 `ls -lh` 快速查看产物的方法。

## <span class="blue"> 核心编译产物一览 [B]

Linux 内核编译完成后，源码树中会生成十余种文件。下表按功能归类，列出对嵌入式开发最关键的产物。

| 产物名称 | 典型路径（ARM32） | 典型路径（ARM64） | 文件格式 | 用途 | 典型大小 |
|---------|------------------|------------------|---------|------|---------|
| vmlinux | 源码根目录/vmlinux | 源码根目录/vmlinux | ELF 可执行 | 调试符号源，配合 GDB 定位崩溃 | 50~200 MB |
| Image | arch/arm/boot/Image | arch/arm64/boot/Image | 纯二进制 | 引导程序直接加载（如 QEMU） | 5~20 MB |
| zImage | arch/arm/boot/zImage | 无（ARM64 不生成） | 压缩二进制+自解压头 | ARM32 开发板常用启动镜像 | 3~10 MB |
| Image.gz | 无 | arch/arm64/boot/Image.gz | gzip 压缩二进制 | ARM64 压缩启动镜像 | 3~10 MB |
| uImage | arch/arm/boot/uImage | 需手动用 mkimage 包装 | U-Boot 格式（64 字节头） | U-Boot `bootm` 命令启动 | 3~10 MB + 64 B |
| System.map | 源码根目录/System.map | 源码根目录/System.map | 纯文本 | 解析内核 panic 打印的地址 | 2~5 MB |
| Module.symvers | 源码根目录/Module.symvers | 源码根目录/Module.symvers | 纯文本 | 编译外部内核模块时必需 | 50~200 KB |
| .config | 源码根目录/.config | 源码根目录/.config | 纯文本 | 当前内核配置快照，确认编译选项 | 100~200 KB |
| *.dtb | arch/arm/boot/dts/<厂商>/ | arch/arm64/boot/dts/<厂商>/ | 二进制设备树 | 启动时由引导程序加载到内存 | 20~200 KB |
| 内核模块 .ko | 分散在各子目录（如 drivers/net/） | 分散在各子目录 | ELF（.ko） | 动态加载的驱动与功能组件 | 10~500 KB/个 |

![aa](images/Linux%20内核编译产物生成链条.png)

> 💡 `vmlinux` 是编译流程最先产生的原始镜像，后续所有启动镜像（Image、zImage、uImage）均由它经过 `objcopy`、压缩或加头等步骤派生而来。虽然 `vmlinux` 无法直接烧录到开发板，但在内核 panic 调试时，它是 GDB 加载符号的必备文件。

> ⚠️ 不要直接将 `vmlinux` 或 `Image` 交给 U-Boot 的 `bootm` 命令启动。U-Boot `bootm` 要求镜像带有 U-Boot 头信息，否则会报 `Bad Magic Number` 错误。应使用 `uImage` 格式，或在较新 U-Boot 中直接支持 `zImage`/`Image` 配合 `bootz`/`booti` 命令。

## <span class="blue"> 用 ls -lh 查看产物 [B]

编译完成后，在源码根目录执行以下命令，可快速一览关键产物的体积与权限：

```bash
cd ~/linux-stable

ls -lh vmlinux System.map Module.symvers .config
```

典型输出如下（不同配置与版本差异较大）：

```
-rwxr-xr-x 1 user user 187M Jun 15 14:32 vmlinux
-rw-r--r-- 1 user user 3.2M Jun 15 14:32 System.map
-rw-r--r-- 1 user user  62K Jun 15 14:32 Module.symvers
-rw-r--r-- 1 user user 152K Jun 15 14:25 .config
```

查看可启动镜像（以 ARM64 为例）：

```bash
ls -lh arch/arm64/boot/
```

典型输出：

```
-rw-r--r-- 1 user user  18M Jun 15 14:32 Image
-rw-r--r-- 1 user user 7.2M Jun 15 14:32 Image.gz
```

查看生成的设备树文件：

```bash
find arch/arm64/boot/dts -name "*.dtb" -exec ls -lh {} \;
```

> 💡 若启用了 `CONFIG_DEBUG_INFO`，`vmlinux` 会包含 DWARF 调试信息，体积通常突破 150 MB。正式发布时可用 `make INSTALL_MOD_STRIP=1` 或手动执行 `strip` 去除符号表以缩减体积。

## <span class="blue"> 模块安装：make modules_install [B]

执行 `make modules` 后，`.ko` 文件仍分散在各子目录中。要将模块统一安装到目标文件系统，需使用 `make modules_install`：

```bash
make modules_install INSTALL_MOD_PATH=/tmp/rootfs
```

`INSTALL_MOD_PATH` 指定安装前缀，最终模块落在：

```
/tmp/rootfs/lib/modules/$(KERNELRELEASE)/
```

目录内部结构如下：

```
lib/modules/5.15.78-custom/
├── kernel/
│   ├── drivers/net/ethernet/      <-- 按子系统分类存放 .ko
│   ├── fs/ext4/
│   └── ...
├── modules.dep                    <-- 模块依赖关系
├── modules.builtin                <-- 已编译进内核的模块列表
├── modules.order                  <-- 链接顺序
└── modules.symvers                <-- 模块符号版本
```

> ⚠️ 交叉编译时若不指定 `INSTALL_MOD_PATH`，`modules_install` 会默认写入主机系统的 `/lib/modules/$(uname -r)/`，覆盖主机内核模块，导致主机系统不稳定。务必显式指定 `INSTALL_MOD_PATH`。

> 💡 `$(KERNELRELEASE)` 的值由内核版本号与 `CONFIG_LOCALVERSION` 共同决定。执行 `make kernelversion` 或在 `.config` 中确认 `CONFIG_LOCALVERSION`，可提前知道模块目录名称。

## <span class="blue"> System.map 与 Module.symvers 的用途 [B]

### System.map

`System.map` 是纯文本文件，记录内核中每个函数与全局变量的**运行时虚拟地址**。当串口日志打印如下 panic 信息时：

```
PC is at __irq_usr+0x80/0xc0
```

在 `System.map` 中搜索 `__irq_usr`，即可定位到对应的 C 函数与文件。该文件在 4.3.1 节（调试符号与 vmlinux）中已有提及，二者配合使用：GDB 加载 `vmlinux` 解析 DWARF 符号，`System.map` 则用于无 GDB 环境下的快速地址查表。

### Module.symvers

`Module.symvers` 记录本次内核编译导出的所有符号（函数/变量）及其 CRC 校验值（当 `CONFIG_MODVERSIONS` 启用时）。编译外部内核模块（不随内核源码树一起编译的驱动）时，构建系统需要读取该文件来确认符号存在且版本一致。

> ⚠️ 忽略 `Module.symvers` 会导致外部模块编译出现 `undefined symbol` 或 `modpost: WARNING: could not find` 错误。若计划为当前内核版本编译第三方驱动，务必将该文件复制到外部模块源码目录或内核构建目录中。
