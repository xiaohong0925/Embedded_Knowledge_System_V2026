## <span class="blue"> HDR-DDR 帧结构与校验链

5.2 只讲了 DDR"双沿采样、16 位字、无 ACK"。完整的校验链有三层：

| 机制 | 位置 | 作用 |
|------|------|------|
| Preamble（前导字节） | 每 16 位字之前 | 接收方同步与流控（可请求暂停/中止） |
| Parity（2 个奇校验位） | 每 16 位字之后 | 逐字检错，替代 SDR 的 ACK |
| CRC5 | 整个数据包末尾 | 包级完整性兜底 |

```
HDR 命令字   数据字 0        数据字 1        …  CRC5
[Preamble][W15..W0][P P] [Preamble][W15..W0][P P] … [CRC5]
   同步+流控   16bit   奇校验×2                    包级校验
```

前导字节还承担流控：从设备处理不过来时借前导向主机请求暂停——这是 HDR 模式在取消 ACK 后保住的"慢设备保护"。退出 HDR 靠专用码型（HDR Exit Pattern），之后总线回到开漏状态，legacy 设备重新可见。

工程含义：DDR 的可靠性由"逐字奇校验 + 包级 CRC5"双重保证，理论上不弱于 SDR 的逐字节 ACK；但**大多数逻辑分析仪不解码 HDR**，出问题时只能靠控制器寄存器里的错误计数与状态位排查——这是采用 HDR 的主要工程成本。

## <span class="blue"> 错误类型与恢复

MIPI 规范为 SDR 阶段定义了错误类型集（非法 CCC、地址阶段错误、DAA 冲突、事务序列错误等），从设备检测到后进入已知状态并等待恢复，而不是把异常扩散到整条总线。恢复手段按力度递进：

| 手段 | 范围 | 场景 |
|------|------|------|
| 重发事务 | 单帧 | CRC/奇校验失败 |
| `RSTACT` CCC（v1.1 Target Reset） | 单从设备 | 设备状态机错乱，复位其协议层 |
| `RSTDAA` + 重新 DAA | 整条总线 | 地址分配混乱 |
| 控制器复位（软件复位 master IP） | 整条总线 | 上述全部无效的最终手段 |

设计原则与 CAN、PCIe 等成熟总线一致：**错误必须可归因、状态必须可复位**。调试 I3C 疑难问题时，优先从控制器的错误状态寄存器读出错误类型，再决定恢复力度——不要上来就复位整条总线。

## <span class="blue"> 多主与 Mastership 移交

I3C 允许总线上存在**次级主设备**（secondary master，能力在 BCR 中声明），典型动机是传感器集线器 MCU 在主 SoC 休眠时接管总线继续采集。

带内请求的三兄弟（共用一个仲裁入口，按地址字节区分）：

| 请求 | 地址字节 | 发起者意图 |
|------|----------|-----------|
| IBI | 自己的动态地址 + R | 上报事件 |
| Hot-Join | 0x02 + W | 新设备请求入总线 |
| Mastership Request | 0x02 + R | 次级主请求接管 |

当前主设备同意后，通过 v1.1 引入的 `GETACCMST` CCC 完成 mastership 移交，次级主接管总线时钟与 DAA 职责。

现实约束：**Linux 主线对多主的支持有限**——多数控制器驱动按单主实现，mastership 移交需要控制器硬件与驱动双重支持。多主架构当前主要出现在厂商私有方案（如传感器集线器固件）中，选型时按"未来能力"而非"现成特性"对待。

## <span class="blue"> I3C Hub：端口扩展与电压域转换

单条 I3C 总线受 50 pF 电容预算限制（5.1 的硬约束），设备多了挂不下；不同电压域（SoC 1.2 V、传感器 1.8 V、legacy 3.3 V）也无法直接混挂。**I3C Hub** 器件解决这两个问题——以上游一个 I3C 口接入，下游扩展多条独立端口：

- 每端口独立电容预算，设备数突破单总线限制；
- 端口间电压域转换，1.0~3.3 V 设备共存；
- 端口可独立配置 I3C / I2C / SMBus 模式；
- 下行 IBI 向上汇聚转发。

代表器件 NXP P3H2x4x 系列，其 Linux 驱动绑定（`dt-bindings: i3c: NXP P3H2x4x i3c-hub`）2025 年进入内核社区评审——说明 Hub 正在从"板上分立方案"变成主线支持的正式器件类。服务器（BMC 管理多组传感器/FRU）与域集中式汽车 E/E 架构是主要落地场景。

## <span class="blue"> I3C Basic vs Full：授权与功能

MIPI 完整版 I3C 面向会员授权；**I3C Basic** 是 MIPI 公开的免版税子集，JEDEC DDR5 SPD 采用的正是 Basic：

| 维度 | I3C Basic | I3C Full |
|------|-----------|----------|
| 授权 | 免版税、规范公开 | MIPI 会员 |
| SDR / IBI / DAA / CCC 核心集 | 有 | 有 |
| HDR-DDR | 有 | 有 |
| HDR-TSP/TSL | 无 | 有 |
| 多主 / 时序控制等 v1.1 高级特性 | 裁剪 | 完整 |

> 📌 勘误（对 5.1）：DDR5 SPD 走 I3C Basic，其高速模式是 **HDR-DDR**（25 Mbps），并非 5.1 早前版本所述的 HDR-TSP——TSP/TSL 属于完整版，Basic 不含。5.1 对应表述已同步修正。

对 SoC 与传感器选型：主流可购器件（MCU 内置控制器、IMU、SPD Hub）全部落在 Basic 能力集内；TSP/TSL 与多主属于"知道存在即可"的少数派。

## <span class="blue"> 功耗与时序控制

`ENTAS0~3` CCC 把设备切入四级活动状态，在活动性与功耗间取档（5.2 已列命令）。v1.1 进一步引入**时序控制（timing control）**：主机为周期性采样的传感器统一定时，多传感器数据在预设时刻齐发，减少逐个轮询的总线活动——对姿态融合这类要求多传感器时间对齐的场景（IMU + 磁力计 + 气压计）是直接收益。该特性属完整版可选能力，当前器件支持面窄，选型时逐项核对。

## <span class="blue"> 方案对比（Trade-off）

| 维度 | 评价 |
|------|------|
| HDR-DDR | 校验链完整（奇校验+CRC5）；代价是调试工具链弱，排查依赖控制器寄存器 |
| Target Reset | 单设备恢复不影响总线；代价是要求设备支持 v1.1 |
| 多主 | 主休眠时采集不中断；代价是 Linux 主线支持有限，现阶段基本是厂商方案 |
| I3C Hub | 突破电容与电压域限制；代价是多一层器件成本与驱动依赖（新绑定，内核版本要够新） |
| I3C Basic | 免版税、生态主流；代价是 HDR-TSP/TSL 与高级特性缺席 |

## <span class="blue"> 常见陷阱

> ⚠️ 把 HDR 当"免费带宽"：控制器与传感器有一方不支持 DDR 时协商静默回退 SDR，性能预期落空。选型时核对双方数据手册的 HDR 支持位（BCR 中有声明）。

> ⚠️ 总线异常就全总线复位：多数故障单设备 Target Reset 即可恢复，全复位打断所有在途事务，还丢掉错误现场。先读错误类型再定恢复力度。

> ⚠️ 按完整版规范选 Basic 器件：照着 TSP/TSL、多主能力写方案，采购回来的 Basic 器件不支持。方案评审先确认目标器件落在哪个能力集。

> ⚠️ 电容预算靠"挂上去试试"：设备逐个加、加到通信异常再减——问题在量产温度与电压角才暴露。设计阶段按数据手册输入电容累加核算，留 30% 余量。

## <span class="blue"> 动手练习

1. **校验链推演**：手工计算一个 16 位数据字的两个奇校验位（分字节奇校验），理解"逐字检错"与 ACK 的差异。
2. **恢复决策树**：给定四种故障现象（单帧 CRC 错、单设备无响应、DAA 后地址混乱、总线完全无波形），分别写出应采取的恢复手段与验证步骤。
3. **选型演练**：从两家传感器原厂数据手册中找出 I3C 能力声明（BCR、HDR 支持、Basic/Full），做一张兼容性核对表。
4. **无硬件后备**：阅读 NXP P3H2x4x Hub 的内核绑定补丁（2025 年 LKML），回答：Hub 下行端口在设备树中如何建模，与 5.3 的 I3C 子节点格式有何继承关系。
