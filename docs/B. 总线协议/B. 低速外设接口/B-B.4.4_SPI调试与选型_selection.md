# 速率与接口选择：怎样把调试证据用于决策

> 所属章节：第五部 B. 总线协议 > B-B.4 SPI 总线 > B-B.4.4 SPI 调试与选型
>
> 本组阅读：第 2 页，共 2 页

上一页已经撤销回环、短接和临时参数，让同一笔 JEDEC ID 读取回到正常基线。现在可以确认的是：**当前连接和配置下，这笔事务能够正确完成**；尚不能确认的是，更高速率是否仍有足够时序裕量，以及 SPI、I2C、QSPI 或 OSPI 中哪一种更适合目标操作。本页沿用这笔事务，把已有调试证据转成可复测的选择条件。

---

## <span class="blue"> 正常基线给出起点，不直接给出速率上限

恢复后的固定条件仍是 RK3568 SPI1 CS0、W25Q128JV-IQ/JQ、Mode 0、8 位、MSB-first、低有效 CS 和 1 MHz 请求速率：

```text
TX：9F 00 00 00
有效 RX：?? EF 40 18
拍数：8 拍命令 + 24 拍响应 = 32 拍
```

基线成立要求工具正常返回，并且 `RX[1]～RX[3] = EF 40 18`。SPI 没有低层 ACK（接收确认），所以 `exit=0` 不能代替身份数据检查；`RX[0]` 只是命令阶段的接收字节，不参与身份判断。

这组结果证明的是当前条件下的一次正常端到端事务。它不证明控制器实际输出了 1 MHz，也不证明更高速率、其他命令、长期运行或模拟裕量已经通过。`spidev_test` 显示的 `max speed` 是用户态读回的请求上限，不是引脚实测频率。速率选择因此要从这个已知起点继续取证，而不是直接把请求值当作已验证能力。

## <span class="blue"> 先算完整事务，再比较速率

### 32 拍对应多少纯时钟时间

一笔操作需要 `N` 个 SCLK 周期，实际时钟频率为 `f_actual`，纯时钟时间就是：

```text
T_clock = N / f_actual
```

`N` 必须包含完成该命令所需的全部时钟，而不只是有效数据。本例发送 `9F` 后还继续提供 24 拍时钟，才接收三字节的 JEDEC ID，所以 `N = 8 + 24 = 32`。若实际时钟为 1 MHz：

```text
T_clock = 32 / 1,000,000 s = 32 μs
```

这里的 1 MHz 是计算条件，不是由工具读回字段证明的实测频率。若控制器分频后的实际速率低于请求值，应把实际值代入同一公式，不能沿用 32 μs。

### 32 μs 为什么不是完整操作耗时

`T_clock` 只覆盖 CS 有效期间的移位时钟。用户发起一次读取，还可能包含 CS 建立与保持、内核和控制器处理、任务调度等时间：

```text
T_operation = T_clock + T_CS + T_software
```

这些附加项需要按实际路径测量，不能从 32 拍推出来。本例是读取 JEDEC ID，不加入页编程或擦除的内部忙时间；换成其他命令时，必须重新计算命令、地址、dummy（额外等待时钟）、数据以及需要等待的内部操作，不能把 32 拍或 32 μs 外推成所有 SPI 事务的固定成本。

因此，提高请求速率最多直接缩短其中的 `T_clock`。它已经恢复正确 ID，只能说明当前事务可工作；是否值得提速，还要看时钟时间在完整操作中所占比例，以及三层约束是否允许。

## <span class="blue"> 控制器、器件和板级条件共同约束候选速率

同一组 SCLK 信号由控制器产生，经板级连接到达 Flash，再由 Flash 驱动 MISO 返回控制器。任何一层的条件不满足，都可能让高速下的 `EF 40 18` 重新变成错位或偶发错误，所以不能只读其中一份参数表。

| 约束层 | 本例需要核对什么 | 证据能支持的决定 |
|---|---|---|
| 控制器 | RK3568 SPI1 与当前驱动支持的模式、速率范围和分频结果；请求值不等于实际值 | 排除控制器无法产生的配置，取得需要实测确认的实际 SCLK |
| 器件 | 当前 W25Q128JV 后缀、供电和 `0x9F` 命令允许的时钟条件；输出有效延迟与上电就绪时间 | 排除超出器件手册条件的候选速率，确定采样窗口的一端 |
| 板级 | 走线传播、主机输入建立时间、接收端门限、边沿、过冲和振铃 | 判断探针处是否仍有足够采样裕量，而不是仅凭数字解码成功提速 |

当前 RK3568 的 Linux v6.6 驱动在 [`spi-rockchip.c:602-607`](code/B-B.4.3/kernel-v6.6/drivers/spi/spi-rockchip.c){: data-code-viewer="true" data-code-title="spi-rockchip.c" data-code-path="Linux v6.6 · drivers/spi/spi-rockchip.c" data-code-lines="602-607"} 选择不小于理想值的偶数分频，使结果不超过请求速率。这个事实只适用于当前控制器与版本，不能推广为所有 SoC；它解释了为什么要区分请求值与实际值，却没有给出板卡已经通过的最高速率。

器件侧还要把输出有效延迟放进采样窗口。B-B.4.2 已给出 MISO 的时间预算：

```text
启动边沿到采样边沿的间隔
≥ tCLQV(max) + 走线传播 + 主机建立时间 + 设计余量
```

`tCLQV(max)` 来自器件手册，走线与接收端波形来自板级测量，主机建立时间来自控制器条件。上电阶段的 `tVSL` 则回答“何时允许拉低 CS”，它不能代替传输过程中的采样窗口检查。

**只有三层条件都满足，候选速率才值得进入复测。**若上一页曾出现“降速后恢复”，这条证据只把问题收敛到频率或时间窗口，不能单独指出控制器、Flash 或走线中的某一项就是根因，也不能直接推出一个安全的新频率。

## <span class="blue"> SPI 与 I2C：围绕当前短读取同场比较

速率约束明确后，还需要判断接口形式是否适合目标系统。SPI 用 CS 选择器件，数据收发可以在同一组时钟中进行，但协议层没有低层 ACK；I2C 用 SDA、SCL 两条信号线和器件地址组织访问，接收方按字节返回 ACK 或 NACK（未确认）。两者都要继续检查有效数据，ACK 也不等于读取内容正确。

| 当前决策条件 | 本例 SPI | 若改用 I2C 器件 |
|---|---|---|
| 引脚与器件选择 | 时钟和收发数据路径之外，用 CS 选择目标；多从机还要核对各自 CS 与 MISO 释放 | SDA、SCL 可连接多个带地址的器件；实际数量仍受地址分配和总线条件约束 |
| 完整事务成本 | 本例为 8 拍命令加 24 拍响应，共 32 拍，没有地址和 ACK 位 | 按具体器件命令计入地址、寄存器或命令、数据、ACK/NACK 及需要的传输阶段，不能沿用 32 拍 |
| 结果判据 | `exit=0` 与 `EF 40 18` 分开检查，SPI 没有低层 ACK | ACK 能表明相应字节被接收，仍须检查返回的身份或状态值 |
| 更适合当前系统的情况 | 需要较高串行带宽、独立全双工数据路径或明确片选控制 | 引脚受限、事务较短，并且希望利用器件寻址与接收确认 |
| 高速与板级限制 | 同时受控制器、Flash 命令和板级采样窗口约束 | 同时受模式、上拉和总线电容等条件约束，不能只看标称模式速率 |

I2C 的地址、ACK、上拉和总线电容机制见 B-B.3.1～B-B.3.2。这里比较它们，是因为这些差异会改变当前短读取的引脚成本、事务组成和成功判据，而不是为了建立“SPI 都快、I2C 都省”的笼统印象。

**同一组 `9F 00 00 00` 不能原样搬到 I2C 上比较。**只有选定具体 I2C 器件并读取其命令格式后，才能确定 `N` 并代入 `T_clock = N / f_actual`。若目标操作本来就需要持续搬运较多数据，还要把完整事务时间和总线占用一起比较；若只是偶发读取短状态，引脚、寻址和确认机制可能更影响选择。

## <span class="blue"> QSPI 与 OSPI 只增加当前选择所需的变量

当普通 SPI 的数据阶段成为瓶颈时，可以评估 QSPI（四线 SPI）或 OSPI（八线 SPI）。它们增加数据路径，但**数据阶段变宽，不等于整笔事务按四倍或八倍缩短**。控制器、器件、引脚和板级条件也必须共同支持所选模式。

先按命令格式逐阶段数拍：

```text
N_total = N_command + N_address + N_dummy + N_data
N_data  = 数据位数 / 该阶段实际使用的数据线数
```

命令和地址阶段是否也能使用多数据线，要由具体命令与器件手册决定，不能从数据阶段反推。dummy 是等待时钟，不含有效数据，直接按手册规定的拍数计入。得到 `N_total` 后再除以实际时钟频率，才是扩展接口的纯时钟时间。

Flash 的页编程、擦除和 BUSY（器件内部忙标志）等待属于内部过程，不能因为数据写入阶段变宽就按同样比例缩短。选择时分别计算传输与内部等待；W25Q 的正式产品接入和写路径归 B-B.4.5，本页不展开这些操作流程。

## <span class="blue"> 候选配置必须复测，失败时回到已恢复基线

三层约束和接口比较给出的是候选，不是验证结果。速率候选仍用同一笔 32 拍读取复测，才能与上一页的正常基线直接比较：

1. **固定其他条件。**保持 Mode 0、8 位、MSB-first、低有效 CS、原 CS 映射和正常 Flash 连接，一次只改请求速率，并记录实际改动。
2. **重复正常判据。**执行同一命令，核对工具正常返回和 `RX[1]～RX[3] = EF 40 18`；`RX[0]` 仍不参与判断。若取得实际 SCLK，记录测量条件，不用 `max speed` 代替。
3. **补足高速所需证据。**提高速率或已有频率相关故障时，先核对完整数字帧仍覆盖 32 拍且数据位置正确，再按三层约束检查接收端模拟波形。数字解码和模拟裕量不能互相替代。
4. **限定通过范围。**偶发故障需要有限次数、明确判据和失败记录。普通 `spidev_test -p` 不自动比较有效 ID，单纯循环命令不能得到错误率。
5. **失败就撤销候选。**出现异常时回到最后一个已确认正常的配置，重新取得 `EF 40 18`，不要同时叠加多项修改。若只是探索候选而尚未选定新配置，同样恢复 1 MHz 基线并复测。

若更换接口或器件，新对象必须先建立自己的已知正常事务，不能继续把 W25Q128JV-IQ/JQ 的 `EF 40 18` 当作它的预期答案。候选复测通过也只覆盖本次接口、速率、连接和测试次数，不自动证明其他命令、长期运行或所有产品访问均已验证。

## <span class="blue"> 本节总结 [B→I]

调试恢复出的正常基线，是选型复测的起点，不是更高速率已经可用的证明。先按完整事务计算纯时钟时间，再让控制器、器件和板级证据共同约束候选配置；SPI 与 I2C 的差别则落实到引脚、事务组成、确认机制和总线条件。QSPI／OSPI 只在各阶段格式和内部等待都算清后才有可比较的收益。最终保留哪个配置，要由同一事务的复测结果决定，失败时能够回到已知正常状态。

## <span class="blue"> 本节自查

??? details "Q1. 为什么本例在 1 MHz 下的 32 μs 不能直接当作一次读取的总耗时？"
    32 μs 只由 32 拍和实际 1 MHz 时钟计算得到。完整操作还可能包含 CS 建立与保持、内核和控制器处理及调度时间；本例的请求速率也不能代替实际频率。换命令还要重新计算各阶段拍数和可能的内部忙时间。

??? details "Q2. 为什么控制器、器件手册和板级测量都不能单独给出已验证的最高速率？"
    控制器决定可产生的模式与分频结果，器件手册给出命令和输出有效等条件，板级测量检查传播、建立时间和信号质量。只有三层共同满足，候选配置才有复测依据；其中一项通过不能抵消另一项未知或超限。

??? details "Q3. SPI 没有低层 ACK、I2C 有 ACK，会怎样改变本例的成功判据？"
    SPI 的工具正常返回与 `EF 40 18` 必须分别检查。I2C 的 ACK 只表明相应字节得到接收确认，仍不能证明身份或状态值正确。两者都不能用传输调用成功代替有效数据检查。

??? details "Q4. 为什么不能把 QSPI 或 OSPI 的整笔事务时间直接除以 4 或 8？"
    只有实际使用多数据线的阶段才按线数减少拍数。命令、地址和 dummy 要按具体格式分别计算，页编程、擦除等内部忙时间也不随数据线数按比例缩短。

??? details "Q5. 候选速率复测失败后，为什么不能继续叠加另一项修改？"
    同时改变多个条件会破坏与正常基线的可比性，无法判断哪项改动造成结果变化。应回到最后已确认正常的配置，用同一笔 32 拍读取重新取得 `EF 40 18`，再一次只改一个变量。
