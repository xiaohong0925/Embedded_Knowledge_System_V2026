# B-B.6.2 I3C 协议层与 CCC 命令

> 所属章节：第五部 B. 总线协议 > B-B.6 I3C 智能传感器总线
>
> 难度：[I] Intermediate | 预计阅读时间：35 分钟

## <span class="blue"> 本节导读

上一节解决了物理层：开漏与推挽怎么切换、速率档位有哪些。本节进入协议层——I3C 不只是"更快的 I2C"，它在两线之上建了一整套总线治理机制：统一的管理命令集（CCC）、上电自动分配地址（DAA）、从设备主动上报事件（IBI）、运行时接入新设备（热加入）。这四件事在 I2C 里要么不存在、要么靠私有方案拼凑，I3C 把它们全部标准化。

本节覆盖：SDR/HDR-DDR/HDR-TSP 三种传输模式的帧结构差异、CCC 命令格式与常用命令表、动态地址分配的仲裁流程、热加入机制、IBI 带内中断的时序与 payload 协商。

---

## <span class="blue"> 三种传输模式

### SDR：默认档位

单沿采样、8 位数据 + ACK，帧结构与 I2C 一致（START/STOP 语义相同），速率 12.5 MHz。与 I2C 的关键差异是引入**广播地址 0x7E**——所有 I3C 从设备必须识别它，CCC 命令与 DAA 都从这个地址进入。

```
SCL  ──┐  ┌──┐  ┌──┐  ┌──┐  ┌──┐  ┌──┐  ┌──┐  ┌──┐  ┌──┐  ┌──────
       └──┘  └──┘  └──┘  └──┘  └──┘  └──┘  └──┘  └──┘  └──┘
SDA  ──████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░████
       S   D7 D6 D5 D4 D3 D2 D1 D0        ACK            P
```

### HDR-DDR：双沿采样

进入 HDR 模式后，数据按 **16 位字**传输，SCL 上升沿与下降沿都采样，速率 25 Mbps。帧内**没有 ACK 位**，改用 CRC5 校验保证完整性。进入与退出靠专用码型（HDR Restart/Exit Pattern）。

```
SCL  ──┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐
       └─┘ └─┘ └─┘ └─┘ └─┘ └─┘ └─┘ └─┘ └─┘ └─┘ └─┘ └─┘
         ↑ ↓ ↑ ↓ ↑ ↓ ↑ ↓ ↑ ↓ ↑ ↓ ↑ ↓ ↑ ↓ ↑ ↓    双沿采样
SDA  ──░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░
       └── 16-bit Word（无 ACK）──┘└── CRC5 ──┘
```

### HDR-TSP：三进制符号

SDA/SCL 两线的翻转状态组合编码为三进制符号，每个时钟周期携带约 1.5 bit，速率 33.3 Mbps。复杂度高，当前多数控制器只实现 SDR 与 DDR，TSP 主要用于 DDR5 SPD 等规范强制场景。TSL 是其兼容变体，允许总线上存在 I2C legacy 设备。

| 模式 | 速率 | 采样 | 帧内校验 | I2C 设备 | 适用 |
|------|------|------|----------|----------|------|
| SDR | 12.5 MHz | 单沿 | ACK | 可识别共存 | 控制与常规读写 |
| HDR-DDR | 25 Mbps | 双沿 | CRC5 | 必须静默 | 批量传感器数据 |
| HDR-TSP/TSL | 33.3 Mbps | 符号编码 | CRC5 | 静默（TSP）/共存（TSL） | 极限带宽 |

> ⚠️ 进入 HDR 前必须确认总线上的 I2C legacy 设备处于安全状态：它们不认识 HDR 码型，可能把特殊时序误判为普通 START/数据，造成误动作或总线锁死。正确顺序是先 CCC 广播管理 legacy 状态，再 ENTHDR。

## <span class="blue"> CCC 命令集

CCC（Common Command Code）是标准化的总线管理指令，经 0x7E 广播地址下发，所有 I3C 设备都必须实现——驱动不再需要翻每家厂商的私有命令手册。

```
SDA  ──████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░████
       S  0x7E+W   ACK   CCC码   ACK   [参数/数据]    P
```

广播 CCC 作用于所有设备，定向 CCC 在 CCC 码之后跟目标动态地址：

| 命令 | 类型 | 功能 |
|------|------|------|
| `ENTDAA` | 广播 | 进入动态地址分配流程 |
| `SETDASA` | 定向 | 用静态 I2C 地址直接指配动态地址（跳过 DAA） |
| `RSTDAA` | 广播 | 清除所有动态地址 |
| `ENEC` / `DISEC` | 定向/广播 | 使能/禁用事件（IBI、热加入等） |
| `ENTAS0~3` | 定向/广播 | 切换活动状态（功耗管理） |
| `GETPID` / `GETBCR` / `GETDCR` | 定向 | 读 48 位临时 ID / 总线特性 / 设备特性寄存器 |
| `SETMWL` / `SETMRL` | 定向 | 设置最大写/读长度 |
| `ENTHDR0~7` | 广播 | 进入各 HDR 模式 |

> 💡 `SETDASA` 是 I2C 迁移的捷径：对带固定静态地址的传感器（如 0x68 的 IMU），直接按静态地址指配动态地址，跳过整个 DAA 竞争流程，初始化显著加快。

## <span class="blue"> 动态地址分配（DAA）

I3C 设备上电时没有动态地址，由主机通过 ENTDAA 流程逐个分配：

```
1. 主机:  S → 0x7E+W → ACK → ENTDAA → Repeated START → 0x7E+R
2. 从机:  逐个驱动自己的 48 位 PID + BCR + DCR（开漏仲裁）
3.        赢得仲裁的设备继续，其余自动退出本轮
4. 主机:  回写 7 位动态地址 → 该设备 ACK，获得地址
5.        重复 2~4，直到无设备再响应 → STOP 结束
```

仲裁机制与 CAN 的 ID 仲裁同源：开漏线上，发 1（释放）的设备检测到线被拉低（有设备发 0）即退出——**数值最小的 PID+BCR+DCR 永远胜出**，全过程无需主机干预。

```
Slave A: 0 0 1 0 1 ...      Slave B: 0 0 1 0 0 ...
              ↑ 第 4 位：A 发 1 释放，B 发 0 拉低
              → A 检测到线被拉低，退出；B 赢得本轮
```

## <span class="blue"> 热加入（Hot-Join）

总线运行中接入的新设备可以主动请求加入，无需重启总线：

1. 新设备上电后等待总线空闲，然后拉低 SDA（类 START 条件）；
2. 主机检测到后开始提供 SCL 时钟；
3. 新设备发送**保留地址 0x02 + 写位**——这是热加入的标识；
4. 主机随后发起 ENTDAA，仅为新设备分配动态地址。

> ⚠️ 热加入请求与 IBI 可能背靠背到达。主控制器的 IBI 队列深度不足会丢事件——驱动设计时确认控制器的 IBI 缓冲能力，必要时在软件层补队列。

---

## <span class="blue"> IBI 带内中断

IBI（In-Band Interrupt）让从设备借总线本身上报事件，省掉每设备一根的 INT 线。

| 维度 | IBI | GPIO 中断 |
|------|-----|-----------|
| 引脚 | 零额外引脚 | 每设备一根 INT |
| 延迟 | 约 10~100 µs（需总线仲裁） | 约 1~10 µs |
| 携带数据 | 1~8 字节 payload | 无，仅电平 |
| 多设备优先级 | 地址仲裁自然排序 | 需中断控制器 |
| 适用 | 传感器事件、数据就绪 | 极低延迟唤醒 |

时序流程：

1. 总线空闲时，从设备拉低 SDA（类 START）；
2. 主机检测到后输出 SCL；
3. 从设备发送**自己的动态地址 + 读位**（RnW=1）——多设备同时请求时按地址仲裁，地址小者优先；
4. 主机 ACK（接受）或 NACK（暂缓）；
5. 从设备随中断发出 payload（可选），主机一次事务即拿到事件与数据。

payload 长度由 BCR 声明能力、经 GETMRL/SETMRL 协商，典型用法：温度传感器告警时直接带 2 字节温度值——"中断 + 读寄存器"两轮事务合并为一轮，总线活动时间减半，对电池设备是直接的功耗收益。

## <span class="blue"> 方案对比（Trade-off）

| 维度 | 评价 |
|------|------|
| CCC 标准化 | 驱动统一、行为可预期；代价是设备必须实现完整 CCC 集，简单传感器固件变重 |
| DAA 动态地址 | 零冲突即插即用；代价是地址运行时可变，软件与调试记录不能写死 |
| HDR 模式 | 带宽 2~3 倍；代价是无 ACK 靠 CRC 兜底，调试工具支持少 |
| IBI vs GPIO 中断 | 省线、带数据、天然优先级；代价是延迟高一个量级，硬实时唤醒仍要 GPIO |
| 热加入 | 在线维护；代价是对控制器事件处理能力要求高 |

---

## <span class="blue"> 常见陷阱

> ⚠️ 进 HDR 前不管 legacy 设备：I2C 设备误识别 HDR 码型导致总线锁死，表现为"一进高速模式整条总线挂死"。

> ⚠️ 把 DAA 当一次性流程：RSTDAA 或总线复位后所有动态地址失效，驱动必须支持重新枚举，不能缓存地址跨复位使用。

> ⚠️ IBI 当 GPIO 中断用：对延迟敏感的唤醒场景用 IBI，100 µs 级延迟直接超标。IBI 是事件通道，不是实时中断。

> ⚠️ payload 长度没协商就发：从设备发的 payload 超过 SETMRL 设定值，主机按错误帧丢弃，事件静默丢失。初始化时先 GETMRL 再 SETMRL。

## <span class="blue"> 动手练习

1. **仲裁推演**：给定三个 PID（如 0x0123…、0x00FF…、0x0122…），手工推演 DAA 三轮仲裁的胜出顺序与最终地址分配。
2. **CCC 流程设计**：写出"枚举 2 个 I3C 传感器 + 使能 IBI + 设置 4 字节 payload"所需的 CCC 命令序列（含命令类型与参数）。
3. **对比量化**：同一告警场景，分别计算"GPIO 中断 + I3C 读寄存器"与"IBI 带 2 字节 payload"的总线事务数与时间（按 12.5 MHz 估算字节时间）。
4. **无硬件后备**：阅读内核文档 `Documentation/driver-api/i3c/protocol.rst` 的 CCC 与 DAA 章节，对照本篇流程图找出内核实现与规范描述的对应关系。

## <span class="blue"> 本节总结

| 自查项 | 确认标准 |
|--------|----------|
| 三种模式 | SDR/DDR/TSP 的速率、校验方式、legacy 共存规则 |
| CCC | 0x7E 广播入口；广播 vs 定向的格式差异；ENTDAA/SETDASA/ENEC/GETMRL 用途 |
| DAA | ENTDAA 流程五步；PID 开漏仲裁（最小值胜出） |
| 热加入 | 保留地址 0x02 + 写位的请求标识 |
| IBI | 动态地址 + 读位发起、地址仲裁定优先级、payload 经 MRL 协商 |
| 边界认知 | IBI 延迟量级；HDR 无 ACK；动态地址不可硬编码 |
