# B-B.5.2 UART 帧、采样与波特率

> 所属章节：第五部 B. 总线协议 > B-B.5 UART 串口
>
> 难度：[B→I] Beginner → Intermediate

## <span class="blue"> 本节导读

B-B.5.1 已经确认 NEO-6M 的 TxD1 能把电平送到 RK3568 的 UART4_RX_M0，但一串高、低电平还不会自动变成程序里的字节。接收端必须知道每一段电平持续多久、从哪一段开始是一个数据单位、应该在什么时刻读取它。

本节只回答一个问题：**没有共享时钟时，RK3568 怎样把 NEO-6M 发来的 RX 波形恢复成确定的 `0x24`，双方波特率误差又为什么可能使接收失败？**

全文沿用同一个最小实例：NEO-6M 发出 NMEA 文本的首字符 `$`，它的 ASCII（American Standard Code for Information Interchange，美国信息交换标准代码）编码是 `0x24`。NEO-6M 数据手册给出的 Serial Port 1 默认配置是 9600、8 个数据位、无校验、1 个停止位，简写为 **9600、8N1**。这里的默认值只是教学基线，实际模块可能被重新配置，不能把当前模块的状态也当成已经实测。

> 本节覆盖：UART 帧的位序和位时间、UART4 的 16 倍采样、时钟与分频产生的实际波特率、误差在一帧内的累积、帧／校验／溢出／Break 状态，以及 FIFO 和两类流控怎样影响正常接收。NMEA 字段解析、Linux TTY 路径和完整排障分别归后续篇目。

## <span class="blue"> 没有共享时钟，接收端怎样找到一帧的起点

UART 没有一条由发送端持续提供给接收端的时钟线。发送端按自己的时钟改变 TX 电平，接收端则按自己的时钟观察 RX。双方事先约定每个二进制位占用的时间，接收端才能判断一段电平代表一个位，还是连续几个相同的位。

> 波特率：每秒传输的符号数，单位是 baud。UART 的每个符号只表示一个二进制位，所以在本文语境中，波特率与比特率的数值相同。9600 baud 表示每秒传输 9600 个位时间。

9600 baud 对应的位时间是：

```text
位时间 = 1 / 9600 s ≈ 104.17 µs
```

线路空闲时保持高电平。发送端把线路拉低一个位时间，表示一帧的起始位；这个从高到低的边沿给接收端提供了本帧的时间起点。接收端随后按约定的位时间读取数据位，最后检查停止位是否回到高电平。

> 帧：从起始位开始，到停止位结束的一组串行位。8N1 中的一帧包含 1 个起始位、8 个数据位和 1 个停止位，共 10 个位时间。校验位和其他位宽配置会改变这个总数。

每来一个新帧，接收端都重新利用起始沿对齐。因此，双方时钟不同造成的采样偏移会在一帧内逐渐增加，却不会脱离当前帧继续累积到后面的所有帧。连续数据流能否长期正确接收，取决于每一帧内是否都能正确采样和校验，而不是一次对齐就能永久有效。

## <span class="blue"> 把 `$` 拆成 9600、8N1 的十个位时间

`0x24` 写成 8 位二进制是 `0010 0100`。这是按最高有效位（MSB）到最低有效位（LSB）阅读的习惯写法；UART 在线路上先发送最低有效位，所以实际顺序必须按 D0 到 D7 重排：

```text
数值：       0x24 = 0010 0100（MSB → LSB）
线路上：     D0  D1  D2  D3  D4  D5  D6  D7
数据位：      0   0   1   0   0   1   0   0
完整帧： 起始 0 → 0 0 1 0 0 1 0 0 → 停止 1
```

这里最容易读错的是 D2 和 D5。它们是两个为 1 的数据位，其余 6 个数据位都是 0。停止位不是额外的一个字节，也不携带 NMEA 内容，它只是本帧末尾必须为高的一个位时间。

沿折线逐段还原：起始位为低；D0、D1 为低；D2 为高；D3、D4 为低；D5 为高；D6、D7 为低；最后停止位为高。把 D7 到 D0 按通常的二进制书写顺序排回 `0010 0100`，得到 `0x24`。

**`0x24` 是一个特殊的对称位图案：正读和反读都是 `0010 0100`。**因此，只看最后的数值不能证明接收端是否真的按 LSB-first 处理，本例也不会出现“位序反转后变成另一个字节”的结果。需要跟随的是每个位在线路上的编号和时刻：第一个数据位始终是 D0，两个高电平分别位于 D2 和 D5，不能根据这个对称结果省略位序判断。

RK3568 TRM 的图 25-2 还允许 5～8 个数据位、可选校验位以及 1、1.5、2 个停止位。它们是双方必须一致的帧配置，不是接收端可以单方面猜出的属性。本篇先固定 8N1，后面只增加校验配置作对照。

## <span class="blue"> 从起始沿到停止位：接收端怎样恢复 `0x24`

只知道每位 104.17 µs，还不能回答应该在位段的哪个时刻读取。若刚好在电平跳变附近采样，旧位和新位就可能混淆。UART4 使用高于位速率的内部波特时钟，把采样点放到各位的中部。

> 过采样：用高于符号速率的时钟观察线路，再按符号边界选择判决时刻。RK3568 TRM 图 25-4 给出的 UART 接收时序是 16 倍波特时钟：起始位中点使用第 8 拍，后续相邻采样点相隔 16 拍。

沿本例可以把接收过程拆成五步：

1. 线路原来处于空闲高电平，接收端检测到进入起始位的低电平。
2. 经过 8 个波特时钟，到达起始位中部附近。以理想起点计算，这是第 `0.5` 个位时间。
3. 再经过 16 个波特时钟，到达 D0 中部，即第 `1.5` 个位时间。以后每隔 16 拍依次读取 D1 到 D7。
4. D7 的采样点是第 `8.5` 个位时间，停止位的采样点是第 `9.5` 个位时间。按前面的位序，8 次数据采样恢复为 `0x24`。
5. 停止位采样为高，当前 8N1 帧成立。接收端重新等待下一次起始沿，下一帧再从新的时间起点计算。

这些 `0.5、1.5、…、9.5` 都是从发送端起始沿开始计算的**发送端位时间坐标**。理想情况下，接收端的位时间与发送端完全相同，采样点落在每个位段中央。下一节的误差推演只改变接收端的位时间，发送端波形保持不变，就能看清偏差怎样逐位积累。

TRM 证明了 UART4 的 16 拍采样关系，但本节不把其他 UART 的可变过采样、多数表决或毛刺过滤方式写成 UART4 已经核实的细节。交互模型也只计算时钟比率造成的偏移，不模拟这些未展开的硬件行为。

## <span class="blue"> 波特率从哪里来，误差为什么会逐位积累

### UART4 的实际位时间由时钟和分频共同决定

v6.6 的 `rk356x.dtsi` 给 UART4 列出了两路时钟：`SCLK_UART4` 名为 `baudclk`，是波特率生成所用的时钟；`PCLK_UART4` 名为 `apb_pclk`，用于 APB 寄存器访问。APB（Advanced Peripheral Bus）是 SoC 内部访问外设寄存器的总线，它不是 RX 上的串行位时钟，两者不能混为一谈。

RK3568 UART4 兼容 Synopsys DesignWare APB UART。v6.6 中对应的 DesignWare 驱动在 `dw8250_set_termios()` 中按目标波特率的 16 倍请求 `baudclk`：

```text
请求时钟 = 目标波特率 × 16
```

`clk_round_rate()` 先询问时钟框架能提供的近似速率，`clk_set_rate()` 再设置时钟。随后通用 8250 路径用 `DIV_ROUND_CLOSEST(uartclk, 16 × baud)` 计算分频值，这个宏把结果舍入到最接近的整数。RK3568 TRM 把保存分频值的高、低寄存器称为 DLH（Divisor Latch High）和 DLL（Divisor Latch Low）；8250 代码把高寄存器称为 DLM，低寄存器仍称 DLL。

若时钟框架实际提供 `R`，整数分频值为 `D`，实际波特率就是：

```text
实际波特率 = R / (16 × D)
```

例如，目标为 9600 baud 时，驱动请求 `9600 × 16 = 153600 Hz`。如果时钟框架恰好提供 153600 Hz，且 `D = 1`，实际波特率就是 9600 baud。若仅作教学演算，假设实际提供的是 153000 Hz，则：

```text
实际波特率 = 153000 / (16 × 1) = 9562.5 baud
相对误差 = (9562.5 - 9600) / 9600 ≈ -0.3906%
```

第二个数值是说明误差来源的假设算例，不是当前 RK3568 板卡的时钟实测结果。实际 `R` 要由板级时钟配置确认。NEO-6M 手册给出的是 9600 的接口配置，没有给出本文所需的内部时钟和分频值，因此也不能替它编造一组分频寄存器。

### 双方速率不同时，采样点偏离各位中心

设发送端实际波特率为 `Bs`，接收端实际波特率为 `Br`，定义接收端相对偏差：

```text
e = (Br - Bs) / Bs
```

`e > 0` 表示接收端更快，采样会逐渐提前；`e < 0` 表示接收端更慢，采样会逐渐推迟。第 `k` 个位段的中心仍按 `k + 0.5` 计算，其中起始位 `k = 0`，D0 为 `k = 1`，停止位为 `k = 9`。换算到发送端的位时间坐标，采样位置为：

```text
采样位置 = (k + 0.5) / (1 + e)
```

下表保留发送端的 `$` 波形不变，只改变接收端速率。连续 NMEA 数据中，当前停止位之后还可能紧跟下一帧的低起始位，所以表中同时列出下一帧起始位。

| 接收端偏差 `e` | 停止位采样位置（发送端位时间） | 采样落点 | 对本例的含义 |
|---|---:|---|---|
| 0 | 9.500 | 当前停止位，高 | 停止位检查通过 |
| +1% | 9.406 | 当前停止位，高 | 采样略提前，但仍落在停止位内 |
| -1% | 9.596 | 当前停止位，高 | 采样略推迟，但仍落在停止位内 |
| +6% | 8.962 | D7，低 | 在本例中把停止位读成低，产生帧错误 |
| -6% | 10.106 | 下一帧起始位，低 | 连续接收时把停止位读成低，产生帧错误 |

这些数值由同一个公式算出，而不是通用容忍度表。实际结果还取决于各位的电平变化、帧配置、起始沿检测和后续是否立即发送下一帧。例如，最后一帧之后一直保持空闲高电平时，即使停止位采样偏到 10.106，读到的仍可能是高；只有紧接低起始位时才呈现表中的帧错误。

因此，**不能给 UART 写一个适用于所有情况的固定 2～3% 或 5% 容忍度**。工程核算要检查具体帧中每个采样点是否仍落在预期位段，并给真实时钟、波形和噪声留下余量。

下面的交互模型固定发送 `$`、9600、8N1，并假设下一帧紧接当前帧。调整接收端偏差后，可以对照采样位置、恢复出的数据位和停止位结果。它是本节公式的确定性教学模型，不是 RK3568 硬件仿真。

## <span class="blue"> 停止位、校验位与 Break 怎样改变帧判断

### 帧错误只能说明停止位检查失败

UART 接收端在停止位应为高电平时读到低电平，就会报告帧错误（Framing Error）。前面的 +6% 和 -6% 算例都利用了这一判定：预期读取停止位，实际却落在 D7 或下一帧起始位的低电平。

帧错误是重要的控制器证据，但不能单独证明根因就是波特率。双方数据位、校验位或停止位配置不一致，也会使预期的停止位位置错位；Break 同样会让线路在停止位仍为低。B-B.5.1 已经说明的接线、电平和电源问题，也可能改变接收端看到的波形。正确顺序是先确认它报告了哪一种异常，再结合帧配置和实际波形缩小原因，而不是直接替换波特率数值。

### 校验位增加一次奇偶检查

校验位位于最后一个数据位和停止位之间。偶校验要求数据位与校验位中 1 的总数为偶数，奇校验则要求总数为奇数。`0x24` 的 D2、D5 两个数据位为 1，已经有偶数个 1，所以本例的偶校验位为 0，奇校验位为 1。

8N1 增加偶校验后变成 8E1，其中 E 表示 even parity。帧从 10 位变成 11 位，停止位中心也从第 9.5 移到第 10.5 个位时间。若发送端使用 8E1、接收端却按 8N1，接收端会把校验位当作停止位，并把真正的停止位当作后续线路状态，双方的帧边界不再一致。

校验可以发现符合其规则的部分位错误，但不能指出哪一位出错，也不能把错误位纠正。它也不代替 NMEA 或 Modbus 上层的完整数据校验，那些语义分别归 B-B.5.5 和 B-B.5.7。

### Break 不是数据 `0x00`

`0x00` 虽然 8 个数据位全为低，但合法帧仍有高停止位。Break 则让线路持续为低，连停止位也没有恢复高电平，因此控制器把它作为另一类线路事件报告，而不是交给程序一个普通的 `0x00` 字节。

UART 的线路状态寄存器（LSR）用不同状态位区分 Break、帧错误、校验错误和溢出。v6.6 的 `serial8250_read_char()` 在 Break 指示成立时增加 `brk` 计数，并优先按 Break 处理，而不是再把它重复解释成普通帧错误或校验错误。Break 可能是对端有意发送的信令，也可能来自异常拉低，状态位本身不提供这一层意图。

## <span class="blue"> 字节来不及取走时会怎样：FIFO、溢出与流控

前面的帧错误和校验错误发生在位与帧的接收判断中。另一种问题出现在字节已经恢复之后：新字节持续到达，旧字节却没有及时被取走。

> FIFO：First-In-First-Out，先进先出缓冲。UART 的接收 FIFO 暂存已经恢复的字节，让软件不必在每个字节到达的同一瞬间都完成处理。

RK3568 的 TX 和 RX 各有 64 字节 FIFO。假设 RX FIFO 初始为空，NEO-6M 以 9600、8N1 连续发送，软件一直不读取且没有流控，那么填满 64 个字节位置所需的量级是：

```text
64 × 10 / 9600 s ≈ 66.67 ms
```

这不是“软件有 66.67 ms 一定安全”的保证。FIFO 触发阈值、驱动读取、系统中其他活动和发送端帧间隔都会改变实际条件；阈值触发也不等于 FIFO 已满。这个计算只把字节到达速率和缓冲容量放在同一个时间尺度上。

当接收缓冲已没有空间而新字节仍到达时，控制器报告溢出错误（Overrun Error）。它说明某处取字节的速度没有跟上，并不自动证明是用户程序读慢，也不说明数据一定在 TTY 缓冲区丢失。Linux 的 8250 路径会增加 `overrun` 计数；TTY 后续还有哪些缓冲和交付路径，由 B-B.5.3 展开，系统侧定位归 B-B.5.4。

### RTS／CTS 用额外信号限制发送

RTS（Request To Send）和 CTS（Clear To Send）是一对硬件流控信号，名称沿用历史术语，实际用途是传递接收能力与发送许可。RK3568 的引脚名写成 `UART4_RTSn_M0` 和 `UART4_CTSn_M0`，末尾 `n` 表示低有效。接收一侧通过 RTS 输出告知发送能力，发送一侧通过 CTS 输入判断能否继续，因此两端也是 RTS 接 CTS、CTS 接 RTS。

UART4 支持自动 RTS／CTS。TRM 图 25-6 显示，RX FIFO 达到接收阈值后，`rts_n` 变为高电平，撤销允许；但发送端可能没能及时检测到变化，当前帧 T 的下一帧 T+1 仍可能进入线路。这说明硬件流控不是“电平一变，当前所有数据瞬间消失”，接收设计必须容纳已经在途的数据。FIFO 被读取到相应恢复条件后，RTS 才重新允许对端发送。

TRM 图 25-7 显示，`cts_n` 变为高电平后，当前字符完成停止位，后续字符暂停发送。它禁止的是后续帧，不是把当前帧从中间截断。CTS 恢复低电平后，发送才可继续。

当前 NEO-6M 模块资料只给出本例使用的 TxD1／RxD1，没有给出可接入这条链路的 RTS／CTS。因此，**不能把 UART4 的自动流控能力当成 NEO-6M 已经具备的能力**。本例仍以正确读取和避免溢出为基线，不能靠在软件里打开硬件流控多出两条实际不存在的连线。

### XON／XOFF 把控制字符放进数据流

软件流控不使用额外引脚，而是让接收方发送 XON、XOFF 控制字符，请求对端恢复或暂停发送。这些字符仍走普通 UART 数据帧，不是 UART 硬件专门定义的另一种帧。N_TTY 是 Linux 默认的终端线路规程，它会按 `VSTART`、`VSTOP` 分别保存的恢复和暂停字符识别软件流控；终端参数接口 termios 的完整模型归 B-B.5.3。

若双方以常见的 `0x11` 作为 XON、`0x13` 作为 XOFF，数据流中的这些字节就可能被解释为控制信息，而不是有效载荷。使用软件流控必须同时满足：双方约定一致，并且有效数据不会与这些控制值冲突，或上层另有转义规则。NEO-6M 除 NMEA 文本外还支持 UBX 二进制协议，UBX 是 u-blox 自定义的二进制数据格式，所以不能凭“GPS 只发文本”给整条链路默认开启 XON／XOFF。

两类流控都只能处理发送方愿意并且能够响应的暂停请求。它们不修复错误的帧配置，也不能恢复已经因溢出丢失的字节。

## <span class="blue"> 回到同一帧：波形、字节与错误状态分别能证明什么

沿 `$` 的接收过程，可以取得多种证据，但每种证据只覆盖自己的位置：

| 证据 | 能说明什么 | 不能单独说明什么 |
|---|---|---|
| RX 引脚上的波形与位宽 | 电平怎样变化、实际位时间和起始／停止位置 | UART4 是否按同样配置恢复出相同字节 |
| 逻辑分析仪解码为 `0x24` | 分析仪按自身采样和 8N1 配置得到该字节 | RK3568 的控制器状态、FIFO 和用户程序是否收到 |
| LSR 的帧／校验／溢出／Break 状态 | 控制器报告了哪一类接收异常 | 异常的唯一根因，以及问题应定位到线路、驱动还是用户程序 |
| 恢复出的 `0x24` 与停止位正常 | 当前这一帧的位序和停止位检查成立 | 后续帧不会溢出，或 NMEA 内容已经通过语义校验 |

逻辑分析仪或示波器可以测量真实波形，但当前没有执行这些仪器测量，也没有取得实际板卡的时钟配置和控制器状态。本节的数值演算用于解释机制，不冒充实板结果。完整的软件观察、外部回环和分层排障由 B-B.5.4 组织。

## <span class="blue"> 本节总结

UART 接收不是看见高低电平就能直接得到字节，而是用起始沿建立本帧时间起点，再按约定的帧格式和波特率逐位采样。UART4 的 16 拍采样把判决点放在位段中部，双方速率偏差则使这些点在一帧内逐渐提前或推迟，必须按实际波形计算，不能套固定容忍度。

停止位、校验、Break 和溢出描述的是不同层面的异常，RTS／CTS 与 XON／XOFF 也只是限制后续发送的机制，不能恢复已经发生的错误。对本例最值得保留的一条主线是：`0x24` 的位序、采样位置、实际位时间和控制器状态必须指向同一帧，任何一个环节都不能用另一个环节的证据代替。

## <span class="blue"> 本节自查

??? details "Q1. `0x24` 正读和反读都是 `0010 0100`，怎样确认接收端仍按 LSB-first 恢复？"
    不能只看最终数值，因为这个字节的位图案左右对称。要逐个核对采样时刻和位编号：第一个数据位是 D0，随后依次到 D7，两个高电平落在 D2 和 D5。把采样得到的 D7 到 D0 排回通常书写顺序，才是 `0x24`；对称性不改变 UART 先发送最低有效位的规则。

??? details "Q2. 为什么接收端不需要与发送端共享一条时钟线，误差又不会跨所有帧持续累积？"
    双方事先约定波特率和帧格式。接收端利用每个起始位的高到低边沿建立新的时间起点，再用自己的 16 倍波特时钟安排采样。偏移只在本帧内累积，下一帧会重新对齐。

??? details "Q3. 若 UART4 实际得到 153000 Hz 的 `baudclk`，整数分频值为 1，目标 9600 baud 时的实际波特率和相对误差是多少？"
    实际波特率为 `153000 / 16 = 9562.5 baud`。相对误差为 `(9562.5 - 9600) / 9600 ≈ -0.3906%`。这只是说明计算方法的假设值，不是板卡实测。

??? details "Q4. 接收端比发送端快 6% 时，8N1 的停止位采样点在哪里，为什么本例会报告帧错误？"
    `e = +0.06`，停止位采样位置为 `9.5 / 1.06 ≈ 8.962`。它落在 D7 的时间范围内，而 `0x24` 的 D7 为低，所以接收端在预期停止位的位置读到低，报告帧错误。换一组数据或帧配置，具体表现可能不同。

??? details "Q5. 为什么 64 字节 RX FIFO 和 9600、8N1 算出的约 66.67 ms 不能写成软件的安全响应时间？"
    该数值只假设 FIFO 初始为空、连续满帧发送、无人读取且无流控，是填满容量的时间量级。实际触发阈值、驱动读取、帧间隔和系统调度都会改变结果，溢出风险必须结合真实运行条件判断。

??? details "Q6. 自动 RTS 已经变为高电平，为什么仍可能收到下一帧？"
    发送端检测 RTS 变化需要的时间与已经在途的数据不会消失。RK3568 TRM 图 25-6 明确给出 T+1 帧仍可能到达的情况，所以接收端要预留相应余量，不能把流控理解成即时停止。

??? details "Q7. Break 与数据 `0x00` 的波形区别是什么？"
    合法的 `0x00` 帧虽然数据位全低，但停止位必须为高。Break 在停止位仍为低，线路持续低电平，因此控制器按 Break 事件报告，而不是普通的 `0x00` 数据帧。
