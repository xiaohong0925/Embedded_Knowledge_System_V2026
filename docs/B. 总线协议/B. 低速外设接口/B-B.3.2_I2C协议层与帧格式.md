# B-B.3.2 I2C 协议层与帧格式

> 所属章节：第五部 B. 总线协议 > B-B.3 I2C 总线
>
> 难度：[B] Beginner / [I] Intermediate | 预计阅读时间：30 分钟

## <span class="blue"> 本节导读

物理层解决的是"电信号怎么在线上传"，协议层解决的是"这些电信号在说什么"。I2C 的每一笔通信都遵循固定的状态机：START 开场、地址帧点名、数据帧传输、STOP 收场，中间靠 ACK/NACK 握手确认。读懂这套帧格式，就能对着逻辑分析仪或示波器的波形，逐位还原出总线上发生的一切——这是调试任何 I2C 问题的基本功。

本节覆盖：五状态通信模型、START/STOP 条件与数据位规则、7 位/10 位地址帧格式、ACK/NACK 握手机制、时钟延展（Clock Stretching）、重复 START 与复合消息、完整读写时序、协议层故障定位与总线恢复。

## <span class="blue"> 通信状态机

I2C 总线上的每次通信严格遵循五状态模型：

```
                START 条件               STOP 条件
   ┌──────┐    ┌────────→┐    ┌────────→┐    ┌────────┐
   │ IDLE │────────────→│ ADDR │────────→│ DATA │────────→│ IDLE │
   │ 空闲 │←────────────────────────────│      │         │
   └──────┘    NACK（无设备应答）        └───┬────┘
                                             │ Repeated START
                                             └────→ 回到 ADDR（不释放总线）
```

| 状态 | 进入条件 | 总线行为 | 说明 |
|:---:|:---|:---|:---|
| IDLE | 上电或 STOP 后 | SDA、SCL 均为高（上拉） | 总线空闲，等待 START |
| ADDR | START 后 | 发送 7 位地址 + R/W 位 + ACK 位 | 共 9 个时钟 |
| DATA | 地址 ACK 后 | 逐字节传输，每字节后跟 ACK/NACK | 字节数不限 |
| STOP | 主设备发起 | SDA 在 SCL 高电平期间上升 | 释放总线，回到 IDLE |

两个边界条件定义了通信的起止，其余时间内 SDA 只在 SCL 低电平期间变化：

- **START 条件**：SCL 为高电平期间，SDA 由高变低
- **STOP 条件**：SCL 为高电平期间，SDA 由低变高

```
      START        8 位数据               ACK       STOP
        ↓                                             ↓        ↓
SDA  ───┐   ┌───┬───┬───┬───┬───┬───┬───┬───┐   ┌───┐      ┌────
        └───┘ D7│D6 │D5 │D4 │D3 │D2 │D1 │D0 └───┘   └──────┘
SCL  ─────┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌──────────
          └─┘ └─┘ └─┘ └─┘ └─┘ └─┘ └─┘ └─┘ └─┘ └─┘
```

数据在 SCL 高电平期间必须稳定——正因为正常数据只在 SCL 低电平期间翻转，SDA 在 SCL 高电平期间的边沿才能被独占用来编码 START/STOP。

## <span class="blue"> 地址帧格式

### 7 位地址 + R/W 位

START 之后的第一个字节是地址帧：高 7 位是从设备地址，最低位是读写方向。

```
地址帧（1 字节 = 8 位）：
┌─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┐
│ A6  │ A5  │ A4  │ A3  │ A2  │ A1  │ A0  │ R/W │
└─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┘
  ↑MSB 先发                                    ↑0=写，1=读
```

以 EEPROM AT24C02（7 位地址 0x50 = `1010000`）为例：

| 操作 | 线上字节 | 二进制 |
|------|----------|--------|
| 写 | 0xA0 | `10100000`（R/W=0） |
| 读 | 0xA1 | `10100001`（R/W=1） |

代码里写的是 7 位地址 0x50，线路上实际传输的是左移一位后的 8 位。

> ⚠️ 在 Linux 的 `i2c_transfer()` 或 `i2cget` 里把 0xA0 当地址传入，设备不会有任何响应——内核把它解释成 7 位地址 0x50 之外的东西。统一约定：软件和文档中用 7 位地址，R/W 位由驱动自动拼接。

### 10 位地址扩展

7 位地址可用 112 个（0x08~0x77，见 B-B.3.1），设备密集时不够用，协议定义了 10 位地址模式，用两个字节完成寻址：

```
第一字节：┌───┬───┬───┬───┬───┬────┬────┬─────┐
          │ 1 │ 1 │ 1 │ 1 │ 0 │ A9 │ A8 │ R/W │   高 5 位固定 0b11110
          └───┴───┴───┴───┴───┴────┴────┴─────┘
第二字节：┌────┬────┬────┬────┬────┬────┬────┬────┐
          │ A7 │ A6 │ A5 │ A4 │ A3 │ A2 │ A1 │ A0 │
          └────┴────┴────┴────┴────┴────┴────┴────┘

完整时序：[S][11110 A9 A8 W][ACK][A7~A0][ACK][DATA][ACK]...[P]
```

高 5 位固定 `0b11110`，落在 7 位地址的保留段（0x78 以上）内，因此 10 位设备与 7 位设备可以混挂在同一条总线上互不干扰。实际产品中 10 位设备很少见，多数工程师用不到，但调试时如果看到线上出现 0xF0 开头的地址帧，要知道这是什么。

## <span class="blue"> ACK/NACK 握手机制

I2C 没有独立的应答线，应答借用 SDA：每传完 8 位，第 9 个时钟由**接收方**控制 SDA——拉低是 ACK（"收到，继续"），保持高是 NACK（"没收到/不要了"）。

| 时刻 | 谁应答 | NACK 的含义 | 主设备应对 |
|------|--------|-------------|------------|
| 地址帧第 9 拍 | 从设备 | 该地址无设备、设备未上电或正忙 | 发 STOP，放弃本次通信 |
| 写方向数据帧第 9 拍 | 从设备 | 从设备拒绝接收（缓冲区满/寄存器非法） | 发 STOP 或 Repeated START |
| 读方向数据帧第 9 拍 | **主设备** | "这是最后一字节，别再发了" | 随后发 STOP |

读方向由主设备应答这一点容易绕反：读操作中主设备是接收方，每收一字节回 ACK 表示继续，最后一字节回 NACK 表示收尾，然后从设备释放 SDA，主设备才能发 STOP。

```
写方向（从设备 ACK）：
SDA  ──D7──D6──D5──D4──D3──D2──D1──D0──┐ ┌──
                                        └─┘ ← 从设备在第 9 拍拉低

读方向收尾（主设备 NACK）：
SDA  ──D7──D6──D5──D4──D3──D2──D1──D0─── ─── ← 主设备保持高（上拉）
```

## <span class="blue"> 时钟延展（Clock Stretching）

时钟延展是从设备主动拖慢总线的机制：从设备在处理不过来时（低速 MCU、EEPROM 内部写周期）把 **SCL 拉低**，主设备检测到 SCL 被拉低后必须等待，直到从设备释放、SCL 回升，才继续下一个时钟。

```
正常：  SCL  ┌─┐ ┌─┐ ┌─┐ ┌─┐
             └─┘ └─┘ └─┘ └─┘
延展：  SCL  ┌─┐ ┌─┐ ┌──────────┐ ┌─┐
             └─┘ └─┘            └─┘ └─┘
                       ↑            ↑
                  从设备拉低 SCL   从设备释放，主设备继续
```

对软件的直接要求：I2C 主机驱动必须回读 SCL 并设置超时。Linux 的 GPIO 模拟实现 `drivers/i2c/algos/i2c-algo-bit.c` 中有专门的 SCL 等待循环，带超时保护；超时未等到 SCL 升高即报错返回。

> ⚠️ 时钟延展死锁。从设备固件 bug 拉低 SCL 后死机，SCL 永远回不来，整条总线瘫痪。更隐蔽的是某些软件 bit-bang 实现不回读 SCL、盲目输出时钟，遇到延展直接跑飞。产品级驱动必须带超时检测，必要时配合看门狗。

> 💡 部分传感器（如 BMP280）上电后做内部校准，会主动延展时钟几百微秒。初始化阶段的 timeout 报错，先确认是设备在延展时钟，再怀疑地址或线路。

## <span class="blue"> 重复 START 与复合消息

从传感器读寄存器是两步操作：先写入寄存器地址，再读回数据。朴素做法中间发 STOP：

```
[S][Addr+W][ACK][RegAddr][ACK][P]   ← 释放总线
[S][Addr+R][ACK][Data][NACK][P]     ← 重新寻址
```

重复 START（Repeated START，记作 Sr）省去中间的 STOP，不释放总线直接换方向：

```
[S][Addr+W][ACK][RegAddr][ACK][Sr][Addr+R][ACK][Data][NACK][P]
                              ↑
                    不发 STOP，直接再次 START
```

收益有两个：

- **效率**：省掉 STOP + 总线空闲时间 + 再次 START 的开销
- **原子性**：多主环境中，START 到 STOP 之间总线归当前主设备独占；中间插入 STOP 会让出总线，可能被其他主设备抢占，读到错误数据

Linux 中 `i2c_transfer()` 天然支持复合消息：传入消息数组，内核自动在相邻消息间生成 Repeated START。

## <span class="blue"> 完整时序图

### 写单字节

主设备向 0x50 写入数据 0xAB：

```
[S][ 1 0 1 0 0 0 0 0 ][A][ 1 0 1 0 1 0 1 1 ][A][P]
    └─ 0x50<<1|0=0xA0 ┘    └─ 数据 0xAB ─┘
 ↑START      ↑从设备 ACK            ↑从设备 ACK  ↑STOP
```

### 读寄存器（Repeated START 复合消息）

从 0x50 的寄存器 0x01 读 1 字节：

```
[S][Addr+W][A][0x01][A][Sr][Addr+R][A][Data][N][P]
   第一步：写寄存器地址    ↑换方向  第二步：读数据
```

### 连续读（Burst Read）

```
[S][Addr+R][A][Data0][A][Data1][A]...[DataN-1][N][P]
                ↑中间字节全部 ACK      ↑最后一字节 NACK 收尾
```

传感器批量读、EEPROM 顺序读都是这个模式：主设备全程收数据，只在最后一字节回 NACK。

## <span class="blue"> 协议层故障定位

协议层异常的第一排查手段：**抓一笔完整波形，逐位解码 START 后的第一个地址帧**——第 9 拍有没有 ACK，直接区分三大类故障：

- **地址帧 NACK** → 设备不存在/地址错/未上电（物理层或配置问题）
- **地址 ACK 但数据异常** → 寄存器地址错、读写方向错（协议理解问题）
- **波形本身畸形**（边沿圆钝、毛刺）→ 回到物理层查电容与上拉

无仪器时的替代路径：`i2cdetect -y -r <bus>` 的扫描本质就是发地址帧看 ACK——扫不到等于地址帧 NACK，扫得到但 `i2cget` 读回 0xff/错误值，问题在数据帧。

### 高频错误对照表

| 错误类型 | 根本原因 | 波形/工具症状 | 处理 |
|:---|:---|:---|:---|
| 地址 NACK | 地址错误、设备未上电、设备损坏 | 地址帧第 9 拍为高 | 核对手册地址与硬件地址引脚；查供电 |
| 数据 NACK（写方向） | 寄存器地址非法、从设备缓冲区满 | 数据帧第 9 拍为高 | 核对寄存器表；降速重试 |
| 时钟延展死锁 | 从设备拉低 SCL 后死机 | SCL 持续为低 | 复位从设备；驱动加超时 |
| 总线卡死 | 上次通信异常终止，未发 STOP | SDA 或 SCL 持续为低 | clock out 恢复（见下） |
| 数据错乱 | 上拉/电容问题、速率过高 | 边沿圆钝、毛刺 | 回物理层按 B-B.3.1 核算 |

### 总线恢复：clock out

总线被异常通信卡死（SDA/SCL 持续为低）时，手动补 9 个时钟把从设备"推"完当前字节：

```c
/* GPIO 模拟 SCL 输出最多 9 个时钟，促使从设备释放 SDA */
for (int i = 0; i < 9; i++) {
    gpio_set_value(scl_gpio, 0);
    udelay(5);                     /* 按总线速率调整 */
    gpio_set_value(scl_gpio, 1);
    udelay(5);
    if (gpio_get_value(sda_gpio) == 1)   /* SDA 已释放 */
        break;
}
/* 补一个 STOP 条件 */
gpio_direction_output(sda_gpio, 0);
gpio_set_value(scl_gpio, 1);
udelay(5);
gpio_set_value(sda_gpio, 1);       /* SDA 上升 @ SCL=H */
```

Linux 内核在 `i2c-core` 中实现了同样的逻辑：`i2c_generic_scl_recovery()`，控制器驱动可将其挂入 `i2c_adapter` 的 bus recovery 回调，通信超时后由内核自动执行恢复。

## <span class="blue"> 方案对比（Trade-off）

| 维度 | 评价 |
|------|------|
| Repeated START | 原子性、省时间；代价是从设备必须支持（个别老器件不支持复合消息） |
| 10 位地址 | 地址空间扩 8 倍；代价是每帧多一字节开销、兼容性差、实际产品少用 |
| 容忍时钟延展 | 兼容慢速设备；代价是吞吐不确定、驱动必须加超时保护 |
| 软件 bit-bang | 不占用控制器、时序完全可控；代价是无硬件仲裁、CPU 占用、延展处理要自己写 |
| Burst Read | 吞吐高、原子性；代价是中间出错要整批重传 |

## <span class="blue"> 常见陷阱

> ⚠️ 地址帧传 8 位值。把 0xA0 当地址传给 `i2c_transfer()`，内核拼上 R/W 位后线上变成别的地址，设备不应答。统一用 7 位地址。

> ⚠️ 读方向最后一字节回了 ACK。从设备以为主设备还要读，继续占用 SDA，主设备发不出 STOP，总线挂死。最后一字节必须 NACK。

> ⚠️ 读操作中间插 STOP。多主环境中总线被抢，读回别的数据；即使单主，部分器件（如某些摄像头）也要求寄存器读写必须复合消息。用 `i2c_transfer()` 的消息数组保证 Repeated START。

> ⚠️ bit-bang 实现不回读 SCL。遇到时钟延展继续打时钟，数据全部错位且无声无息。软件模拟必须回读 SCL 并加超时。

> ⚠️ 把初始化 timeout 当地址错。部分传感器上电校准时延展时钟数百微秒，误判会引向错误排查方向。先看是不是延展。

## <span class="blue"> 动手练习

1. **手工解码**：对照本篇"写单字节"时序，把向 0x50 写 0x5A 的完整波形按位画出（含 START/STOP/ACK 位），标注每个时刻 SDA/SCL 电平。
2. **工具验证**：在开发板上执行 `i2cget -y <bus> 0x50 0x00`（读 AT24C02 的 0 地址），用逻辑分析仪或示波器抓波形，逐位核对是否符合"读寄存器"复合消息格式。
3. **NACK 复现**：对一个不存在的地址执行 `i2cget -y <bus> 0x60 0x00`，观察报错；有条件抓波形确认地址帧第 9 拍为高。
4. **无硬件后备**：阅读内核源码 `drivers/i2c/algos/i2c-algo-bit.c` 中 SCL 等待与超时逻辑，以及 `i2c-core-base.c` 中 `i2c_generic_scl_recovery()` 的恢复流程，理解时钟延展与总线恢复在软件中的落地方式。

## <span class="blue"> 本节总结

| 自查项 | 确认标准 |
|--------|----------|
| 状态机 | IDLE→ADDR→DATA→STOP；Repeated START 回 ADDR 不释放总线 |
| START/STOP | SCL 高电平期间 SDA 的下降沿/上升沿；数据位只在低电平期变化 |
| 地址帧 | 7 位地址 + R/W；软件用 7 位；10 位模式头字节 0b11110 |
| ACK/NACK | 第 9 拍接收方拉低为 ACK；读方向最后一字节主设备回 NACK |
| 时钟延展 | 从设备拉低 SCL 拖慢总线；驱动必须回读 + 超时 |
| Repeated START | 复合消息的效率与原子性收益；`i2c_transfer()` 消息数组 |
| 排查锚点 | 抓波形看地址帧第 9 拍 ACK，区分物理层/配置/协议三大类 |
