# B-C.9.1 MIPI D-PHY 物理层

> 所属章节：第五部 B. 总线协议 > C. 中高速外设与存储
>
> 难度：[I] | 预计阅读时间：50 分钟

## 本节导读

手机摄像头拍的照片、显示屏上刷的画面，在 SoC 与传感器/屏幕之间跑的都是 MIPI 接口。MIPI 不是一个协议，而是一族协议：物理层有 D-PHY / C-PHY / A-PHY，协议层有 CSI-2（摄像头进）和 DSI（显示出）。本篇讲其中最经典的物理层 D-PHY——它决定了线怎么接、电平怎么摆、速度怎么算，是调通任何一路摄像头或屏幕之前绕不开的一层。

D-PHY 的核心设计是**双模式**：同一对物理线，低速时当单端控制通道用（LP 模式，配置寄存器、状态切换），高速时当差分数据通道用（HS 模式，跑图像流）。摄像头 99% 的时间在 LP 模式省电，出图的一瞬间切 HS 突发传输。理解这套"平时省电、用时爆发"的机制，就理解了 MIPI 为什么统治了移动设备。

> 本节覆盖：D-PHY 的 Lane 构成与源同步架构、LP/HS 双模式的电气差异、HS 上跑的长包/短包结构、LP 状态机与 LP→HS 切换时序、版本速率演进、Lane 数与带宽的换算方法（含分辨率选型速算）、Linux 侧用 media-ctl/v4l2-ctl 观察链路的手段、C-PHY 与 A-PHY 的定位差异、bring-up 排障。按"线怎么连 → 电平怎么摆 → 包长什么样 → 模式怎么切 → 速率怎么算 → Linux 上怎么看 → 坏了怎么查"展开——这正是你 bring-up 一块新摄像头模组时的排查顺序。

读完你应该能独立完成三件事：按分辨率/帧率/位宽算出所需 Lane 数与速率档位并写进设备树、用 media-ctl 和 v4l2-ctl 确认链路拓扑与格式协商结果、对着 dmesg 里的 ECC/CRC 错误报告判断问题在物理层还是协议层。

## 信号构成：1 对时钟 + N 对数据

D-PHY 采用**源同步**架构——发送方随数据一起发出时钟，接收方用这根时钟采样数据，双方不需要共享全局时钟：

```
   发送端（CSI-2：摄像头 / DSI：SoC 显示侧）        接收端（SoC / 屏幕）
   ┌─────────────────────────┐                  ┌─────────────────┐
   │                         │   CLK+ ────────► │                 │
   │      数据源              │   CLK- ────────► │   D-PHY 接收器   │
   │    （Sensor/GPU）        │                  │                 │
   │                         │   D0+ ────────►  │                 │
   │                         │   D0- ────────►  │                 │
   │                         │   D1+ ────────►  │                 │
   │                         │   D1- ────────►  │                 │
   │                         │   （D2/D3 同理）   │                 │
   └─────────────────────────┘                  └─────────────────┘
       1×CLK 差分对 + 1~4×Data 差分对
```

> Lane（通道）：D-PHY 里一对差分线叫一个 Lane。时钟 Lane 必有一条，数据 Lane 1~4 条可选，具体用几条由设备树里 sensor/屏幕的 `data-lanes` 属性声明，驱动据此配置 PHY——Lane 数写错是 bring-up 阶段"链路不锁定"的高频原因。

- **CLK+/-**：一对差分时钟，HS 模式下所有 Data Lane 共用它做边沿采样
- **D0~D3+/-**：最多 4 对差分数据线。D0 特殊：LP 模式下它是双向的，支持 BTA（Bus Turn-Around，总线反转）——接收方可以借 D0 回传应答，比如 DSI 读屏幕寄存器。BTA 的切换同样走 LP 状态机：发送方发 Escape 进入请求后释放 D0，接收方接管驱动回传，完事再交还——全程在 LP 低速下完成，不涉及 HS。

源同步的工程含义值得说透：时钟和数据一起走，两者经历的走线延迟、温度漂移一致，接收端看到的相位关系天然稳定——所以 D-PHY 不需要接收端 PLL 从数据里恢复时钟（那是 SerDes 的做法，见 F.16 相关节）。代价是多一对时钟线，以及**时钟与数据的相对走线长度必须严格匹配**，失配直接吃掉采样裕量。

## 双模式：LP 与 HS 的电气差异

同一对线在两套完全不同的电气规则下工作：

| 特性 | LP 模式（Low Power） | HS 模式（High Speed） |
|------|---------------------|----------------------|
| 信号方式 | 单端（每根线独立判断电平） | 差分（两线反相摆动） |
| 电压摆幅 | 1.2V（0~1.2V） | 约 ±200mV |
| 速率 | < 10 Mbit/s | 80 Mbit/s ~ 2.5 Gbit/s/lane |
| 用途 | 控制、配置、状态切换 | 图像/显示数据传输 |
| 功耗 | 极低 | 较高 |
| 线路状态 | LP-00/01/10/11 | HS-0/HS-1 |

LP 的四状态由两根线的单端电平组合而成；HS 则是标准低压差分。摆幅从 1.2V 压到 200mV 是高速的必要条件——摆幅越小，翻转越快、功耗越低、EMI 越小，这是所有高速差分接口（USB、PCIe、SerDes 同理）的共同选择。

> ⚠️ MIPI 链路的大量现场问题出在 PCB 而不是芯片。硬约束三条：Lane 间走线等长（长度差 < 0.2mm 量级）、差分阻抗 100Ω ±10%、远离开关电源等噪声源。示波器上看到眼图闭合、消隐期错位，先量走线再怀疑配置。

## HS 线上跑的是什么：长包与短包

D-PHY 只管比特搬运，比特的组织方式由上层协议（CSI-2/DSI）定义，但物理层调试时你会在错误计数器里直接遇到这两个名字，需要先建立最小认知：

> 长包（Long Packet）：图像数据的运输单元。结构是 4 字节包头（数据标识 DI + 16 位字数 WC + ECC 纠错字节）+ 载荷 + 2 字节 CRC。一行像素就是一个长包。
>
> 短包（Short Packet）：同步信号的运输单元，只有 4 字节包头没有载荷。帧开始（FS）、帧结束（FE）、行开始（LS）、行结束（LE）各是一个短包——一帧图像的时序骨架全靠它们标定。

包头里有两个字段在排障时天天见，先认识：

- **DT（Data Type，6 位）**：载荷格式编号。RAW10 是 0x2B、RAW8 是 0x2A、YUV422 8-bit 是 0x1E——驱动报 "unsupported data type" 或抓包看到 DT 与预期不符，说明 sensor 配置输出的格式和 SoC 侧声明的不一致。
- **VC（Virtual Channel，2 位）**：虚拟通道号，0~3。多路 sensor 复用同一物理链路的场景（如双目摄像头走一组 Lane）靠 VC 区分数据归属，软件侧在 media-ctl 拓扑里能看到对应的源实体。

包头的 ECC 字节和包尾的 CRC 是两层保护：ECC 只保包头（可纠 1 位错），CRC 保整个载荷。dmesg 里 `ECC error` 和 `CRC error` 因此指向不同嫌疑区——ECC 错集中在包头窗口，多为边沿/时序问题；CRC 错在数据窗口，多为摆幅/眼图问题。排障节会用到这个区分。

## LP 状态机与 HS 切换

### LP 四状态

| 状态 | Dp | Dn | 含义 |
|------|----|----|------|
| LP-11 | 1 | 1 | Stop：空闲态，链路的默认与复位态 |
| LP-00 | 0 | 0 | HS 请求 / Escape 入口 |
| LP-01 | 0 | 1 | 中间过渡态 |
| LP-10 | 1 | 0 | 中间过渡态 |

（LP 电平：1 = 1.2V，0 = 0V，单端判断。）

### LP → HS 切换时序

每次进入高速传输都要走一遍固定序列，任何违规跳变都会被接收端拒绝：

```
CLK Lane:  LP-11 ──→ LP-00 ──→ HS-Rqst ──→ HS 差分时钟连续输出
Data Lane: LP-11 ──→ LP-01 ──→ LP-00 ──→ HS-Rqst ──→ HS 突发数据
           (Stop)    (过渡)    (请求)      (准备)     (preamble+同步字0xB8+载荷)

关键时序参数：
  T_LPX        LP 状态最短持续时间（~50ns）
  T_HS-PREPARE HS 准备时间（38~95ns + 2UI）
  T_HS-ZERO    HS 零态持续（105ns + 6UI）
  T_HS-TRAIL   结尾拖尾（最大 105ns + 12UI）
```

> UI（Unit Interval）：一个比特的时间宽度，等于速率的倒数——2.5 Gbit/s 时 1 UI = 400 ps。上面时序参数里的 "+2UI" 意味着绝对时间随速率档位变化，示波器量测前先按当前速率换算。

逐步分解：

1. **LP-11（Stop）**：链路空闲，差分驱动器关闭，功耗最低
2. **LP-11 → LP-01 → LP-00**：Data Lane 上的这个序列是"我要进 HS"的请求签名；CLK Lane 走自己的 LP-00 请求路径先行启动
3. **HS-Rqst → HS 突发**：驱动器从单端切差分，先发一串 0 的 preamble 让接收端锁定，再发同步字 0xB8 对齐字节边界，随后才是 CSI-2/DSI 的数据包
4. **HS-TRAIL → LP-11**：传完发拖尾位，关闭差分驱动，回 LP-11 继续省电

> ⚠️ HS 是**突发传输**架构：链路的典型节奏是 LP → HS → LP → HS 循环，每次切入都有几百纳秒的固定开销（唤醒序列 + preamble + 同步字）。推论是**小包传输效率极低**——MIPI 适合图像这种大包连续流，不适合稀疏的小数据包。这也是为什么传感器的寄存器配置走 LP/Escape 或干脆走 I2C，只有像素流走 HS。

## 版本演进

| 参数 | v1.1 | v1.2 | v2.x |
|------|------|------|------|
| 最高速率/lane | 1.5 Gbit/s | 2.5 Gbit/s | 4.5 Gbit/s |
| Data Lane 数 | 1~4 | 1~4 | 1~4 |
| HS 差分摆幅 | 200mV | 200mV | 200mV |
| 典型应用 | 720p 摄像头 | 1080p/4K 摄像头 | 4K/8K 显示 |

嵌入式领域目前最常见的是 v1.2：4 Lane 共 10 Gbit/s，带 4K@30fps 摄像头刚好够用。要 4K@60fps 或多路高帧率，上 v2.x 或转 C-PHY。

## 带宽速算：选型第一笔账

总带宽 = Lane 数 × 每 lane 速率。D-PHY 本身没有 8b/10b 这类重编码（这点不同于 PCIe/USB3），开销主要来自数据包头和行/帧消隐，工程估算按 85% 有效载荷率：

> 消隐（Blanking）：行与行、帧与帧之间的空闲间隔。模拟电视时代留给电子束回扫的时间，数字时代保留下来用于同步与缓冲。消隐期不传像素但占用带宽，所以"物理带宽 ≠ 像素带宽"，估算时必须乘系数。

| Lane 数（v1.2 @ 2.5G/lane） | 物理带宽 | 有效带宽估算 | 适用 |
|------|---------|------------|------|
| 1 Lane | 2.5 Gbit/s | ~260 MB/s | 小分辨率传感器 |
| 2 Lane | 5.0 Gbit/s | ~530 MB/s | 720p@60 / 1080p@30 |
| 4 Lane | 10 Gbit/s | ~1.06 GB/s | 1080p@120 / 4K@30 / 2K 屏 |

实战速算——1080p（1920×1080）摄像头、RAW10 输出、30fps：

```
像素率   = 1920 × 1080 × 30 = 62.2 Mpixel/s
数据率   = 62.2M × 10bit ≈ 622 Mbit/s
加 15% 行/帧消隐开销：622 × 1.15 ≈ 715 Mbit/s

结论：1 Lane v1.1（1.5G）理论够但裕量不足；
     2 Lane 是稳妥选择，还给 ISP 后处理留了空间。
```

同 sensor 提到 60fps，数据率翻倍到约 1.43 Gbit/s，2 Lane 起步。这个速算方法（像素率 × 位宽 × 消隐系数 → 对照 Lane 带宽）对 DSI 屏幕同样适用，把"摄像头分辨率"换成"屏幕分辨率 × 色深"即可。

## Linux 侧观察：media-ctl 与 v4l2-ctl

摄像头链路在内核里是 V4L2 子系统管理的一条流水线：sensor → MIPI CSI-2 接收器 → ISP → 采集节点。bring-up 时确认"链路物理层通了没有"靠两个工具。

第一眼看拓扑：

```text
# media-ctl -d /dev/media0 -p        （节选自一款 4 Lane sensor 平台，实体名随 SoC 不同）
- entity 23: gc5535 4-0036 (1 pad, 1 link)          ← sensor 实体，I2C 地址 0x36
  pad0: Source  [fmt:SRGGB10_1X10/2880x1620]
    -> "mipi_csi2_input":0 [ENABLED]
- entity 27: mipi_csi2_input (2 pads, 2 links)      ← CSI-2 接收器实体
  pad0: Sink    [fmt:SRGGB10_1X10/2880x1620]
    <- "gc5535 4-0036":0 [ENABLED, IMMUTABLE]       ← 链路已建立
```

读法：每个方框是一个"实体"（sensor、CSI-2 接收器、ISP 各一），pad 是接口，箭头是数据通路。重点确认三处：sensor 的 fmt（格式/分辨率）是否与预期一致、`ENABLED` 链路是否从 sensor 一路连到采集节点、中间有没有断开的 pad。拓扑里根本没有 sensor 实体，说明 I2C 侧的 probe 就失败了——问题还没到 MIPI 这一层。

第二眼看格式协商结果：

```text
# v4l2-ctl -d /dev/video0 --list-formats-ext
ioctl: VIDIOC_ENUM_FMT
    Type: Video Capture
    [0]: 'RG10' (10-bit Bayer RGRG/GBGB)
        Size: Discrete 2880x1620
            Interval: Discrete 0.033s (30.000 fps)
```

读法：`RG10` 即 RAW10 的 V4L2 四字符码（对应 CSI-2 的 DT=0x2B），分辨率与帧率档位是 sensor 驱动声明的集合。这里列出的档和 media-ctl 拓扑里的 fmt 对不上，说明驱动声明与链路配置不一致；这里根本没有期望的分辨率档，先去查 sensor 驱动的 mode 表，不要动物理层。

第三眼看错误计数。dmesg 是物理层体检报告（字段名随 SoC 驱动不同，含义相通）：

```text
[  123.451] mipi_csi2: stream ON, 4 lanes, 891 Mbps/lane
[  125.002] mipi_csi2: ERR1 0x00000010  (ECC error)      ← 包头窗口出错
[  125.002] mipi_csi2: ERR2 0x00000004  (CRC error)      ← 载荷窗口出错
```

第一行确认 Lane 数与速率档——和带宽速算的预期对不上就先改设备树。后两行是分水岭：ECC 错误指向包头接收窗口（边沿/时序/等长问题），CRC 错误指向数据窗口（摆幅/眼图/阻抗问题），两者都没有却只有帧同步丢失，则怀疑消隐配置或 sensor 输出时序。

## C-PHY 与 A-PHY：两条进化路线

D-PHY 之后 MIPI 推出了两个不同方向的 PHY：

**C-PHY——提升引脚效率。** 取消独立时钟对，三根线一组构成一个 lane，用线间电平跳变编码符号，时钟从跳变中恢复。16bit 数据映射为 7 个符号（约 2.28 bit/symbol），每 lane 等效约 5.7 Gbit/s。注意 C-PHY 的 "1 lane" 是 **3 根线**，与 D-PHY 的 2 根线不同，算总线数时别混。

**A-PHY——拉长传输距离。** 为车载设计：同轴线或屏蔽双绞线传 15 米，内置 FEC 前向纠错与重传，单链路最高 16 Gbit/s。典型拓扑是"摄像头端短距 D-PHY 接 sensor，经加串器（serializer）转 A-PHY 跑长距，到网关经解串器（deserializer）还原成 CSI-2 进 SoC"——TI 的 FPD-Link、ADI（Maxim）的 GMSL 是这一生态的主流芯片。

```
摄像头模组                          中央网关/SoC
┌────────────┐                    ┌──────────────────┐
│ CSI-2 传感器│──D-PHY(短距)──► 加串器 │══A-PHY(≤15m)══► 解串器 │──CSI-2──► SoC
└────────────┘                    └──────────────────┘
```

三者对比：

| 维度 | D-PHY | C-PHY | A-PHY |
|------|-------|-------|-------|
| 线结构 | 1 CLK 对 + 1~4 Data 对 | 3 线组，无独立 CLK | 同轴/屏蔽双绞线 |
| 每 lane 线数 | 2 | 3 | 1~2 |
| 最高速率 | 2.5 Gbit/s/lane（v1.2） | ~5.7 Gbit/s/lane | 16 Gbit/s |
| 距离 | < 30cm（板内/FPC） | < 30cm | **15m** |
| 典型应用 | 手机/嵌入式摄像头与屏 | 高像素多摄手机 | 车载 ADAS 摄像头 |

选型逻辑：板内连接、成本敏感 → D-PHY；手机 SoC 原生支持且追求高像素 → C-PHY；摄像头离主控超过一米（车载、机器人远端视觉）→ A-PHY 或 FPD-Link/GMSL 加串方案。

## 排障：摄像头 bring-up 常见故障

| 症状 | 优先怀疑 | 验证方法 |
|:---|:---|:---|
| media-ctl 拓扑里没有 sensor 实体 | I2C 侧失败（供电/复位/地址/ID 读取），还没轮到 MIPI | `i2cdetect` 确认地址，`dmesg` 看 probe 日志 |
| 链路不锁定、接收器报 LP 状态异常 | 设备树 `data-lanes` 与实际接线不符；CLK Lane 极性接反 | 对照原理图逐 Lane 核对；示波器看 LP-11 空闲态是否存在 |
| dmesg 大量 ECC error | 时钟/数据相对走线失配，采样窗口偏到包头上 | 量走线长度差；降速率档验证是否消失 |
| dmesg 大量 CRC error | 差分摆幅不足或阻抗失配，眼图闭合吃掉数据 | 示波器量 HS 摆幅（应约 ±200mV）与眼图张开度 |
| 有帧但花屏/错位 | DT 格式不匹配（sensor 出 RAW10，SoC 按 RAW8 解）；WC 与实际行长不符 | v4l2-ctl 与 sensor 模式表对照格式四字符码 |
| 帧率上不去 | 消隐配置过宽，或速率档低于带宽需求 | 按带宽速算复核；查 sensor 的 HTS/VTS 寄存器 |
| 低温/高温下偶发丢帧 | 时序参数裕量不足（T_HS-PREPARE 等边界值） | 温度箱复现，放宽时序参数验证 |

> 💡
> 排查顺序固定为"I2C → 拓扑 → 格式 → 物理层"：先用 i2cdetect 确认 sensor 活着，再 media-ctl 看链路，再 v4l2-ctl 对格式，最后才上示波器。反过来做（先量波形）是新手最常见的浪费时间姿势——大部分"MIPI 不通"死在 I2C 和设备树上。

## 本节总结

D-PHY 的统治力来自一个克制的分工：物理层只做两件事——LP 模式省电地把链路管起来，HS 模式突发地把图像推过去，其余全交给 CSI-2/DSI。围绕这个分工，本篇的主线其实只有三条：信号上，源同步架构（1 CLK 对 + N Data 对）用多一对线的代价换来免时钟恢复的简单接收端，同时把走线等长变成了硬约束；机制上，LP→HS 切换序列与突发架构决定了"小包低效、大包高效"的性格，寄存器配置走 I2C/LP、像素走 HS 因此是必然分工而不是习惯；工程上，带宽速算（像素率 × 位宽 × 消隐系数 → Lane 数与速率档）和"i2cdetect → media-ctl → v4l2-ctl → dmesg 错误计数"的排查顺序，是 bring-up 任何一路摄像头或屏幕的通用开场。C-PHY 和 A-PHY 不是替代而是补位：引脚效率和传输距离两个 D-PHY 没解的问题，各给了一条路线。

| 关键结论 | 一句话记忆 |
|:---|:---|
| 架构 | 源同步：时钟随数据走，免时钟恢复，走线等长是硬约束 |
| 双模式 | LP 单端 1.2V 管控制，HS 差分 ±200mV 管图像，同一对线两套规则 |
| 突发架构 | 每次切入 HS 有数百 ns 固定开销；小包低效，大包高效 |
| 包结构 | 长包运像素（带 ECC+CRC），短包标帧/行同步；DT 定格式、VC 分通道 |
| ECC vs CRC | ECC 错在包头窗口（查时序/等长），CRC 错在数据窗口（查摆幅/眼图） |
| 速算公式 | 像素率 × 位宽 × 1.15 消隐 → 对照 Lane 带宽，留裕量 |
| 排查顺序 | I2C → media-ctl 拓扑 → v4l2-ctl 格式 → dmesg 错误 → 示波器 |
| 选型 | 板内 D-PHY；手机高像素 C-PHY；超一米车载 A-PHY/加串方案 |
