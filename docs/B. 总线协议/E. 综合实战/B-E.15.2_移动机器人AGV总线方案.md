# B-E.15.2 移动机器人 AGV 总线方案

> 所属章节：第五部 B. 总线协议 > E. 综合实战
>
> 难度：[E] | 预计阅读时间：40 分钟

## 本节导读

AGV（自动导引车）与机械臂的总线需求相反：机械臂是多轴硬同步（EtherCAT 的地盘），AGV 是两轮差速 + 大量低速外设 + 大带宽传感器——CAN FD 的灵活寻址和抗扰性比 EtherCAT 的极致周期更对路，而激光雷达这类大数据量传感器直接走标准以太网。本篇以一台差速驱动 AGV 为对象，做与 15.1 同构的总线架构演练，重点在对比中看清"为什么同一类问题在两台机器上收敛到不同答案"。

本节覆盖：AGV 总线拓扑与选型理由、CAN FD 节点与报文 ID 规划、总线负载率核算、传感器链路（激光雷达/安全扫描仪/超声波）的分层、无线链路双备份、bring-up 与排障要点。

## 拓扑与选型

```
 ┌──────────────── AGV 主控（SoC，Linux）────────────────┐
 │                                                        │
 │  CAN FD（500k/2M）──┬─ 左轮伺服                         │
 │                     ├─ 右轮伺服                         │
 │                     ├─ 顶升机构                          │
 │                     └─ BMS（电池管理）                   │
 │                                                        │
 │  千兆以太网 ──┬─ 激光雷达（UDP 点云）                    │
 │              └─ 安全激光扫描仪（UDP，区域入侵检测）       │
 │  I2C ── 超声波阵列 ×8（近距避障）                        │
 │  MIPI DSI + I2C ── 7 寸屏 + 电容触摸（HMI）              │
 │  SDIO ── WiFi6 模块（厂内调度）                          │
 │  USB ── 4G 模块（远程备份链路）                          │
 │  RS-485 ── 辅助电机驱动器（Modbus RTU）                  │
 └────────────────────────────────────────────────────────┘
```

选型理由表：

| 功能 | 总线 | 理由 | 被排除方案 |
|:---|:---|:---|:---|
| 左右轮伺服 | CAN FD | 两轮差速无轴间硬同步需求（同步由控制算法做）；CANopen 伺服生态成熟；线缆可穿过旋转/移动部件且抗扰 | EtherCAT：ESC 成本与布线（专用线型拓扑）不划算；RS-485：带宽与实时性不足 |
| 顶升/BMS | 同上 CAN FD | 与驱动轮共网，ID 规划隔离优先级 | 独立总线：浪费控制器 |
| 激光雷达 | 千兆以太网 UDP | 点云 10+ MB/s，厂商原生 UDP 输出 | USB：点云带宽与驱动复杂度都不合适 |
| 安全扫描仪 | 以太网 UDP | 厂商标准接口；安全判定在扫描仪内部完成，总线只传结果 | 串行接入控制环路：违反安全独立原则 |
| 超声波阵列 | I2C | 低速、近距离、成本极低 | 单总线/并口：布线复杂 |
| HMI | MIPI DSI + I2C 触摸 | SoC 原生显示/触摸路径 | HDMI：转接芯片多余 |
| 无线 | SDIO（WiFi6）+ USB（4G） | 双链路异构备份：WiFi 断时 4G 接管 | 单链路：厂区漫游存在盲区 |

与 15.1 的对照是本篇最重要的认知：机械臂把同步精度放在第一位所以上 EtherCAT，AGV 把布线与成本放在第一位所以用 CAN FD——**总线选型是被系统需求约束逼出来的，不是性能参数表比出来的**。

## CAN FD 节点与 ID 规划

单条 CAN FD 挂四类节点，ID 按 11.2 的"ID=优先级"原则分配：

| 节点 | Node-ID | 周期报文 | COB-ID 段 | 周期 | 优先级理由 |
|:---|:---:|:---|:---|:---:|:---|
| 左轮伺服 | 1 | TPDO1 状态字+实际速度 | 0x181 | 4 ms | 驱动控制最实时 |
| 右轮伺服 | 2 | TPDO1 同上 | 0x182 | 4 ms | 同上 |
| 顶升机构 | 3 | TPDO1 状态 | 0x183 | 20 ms | 任务级动作 |
| BMS | 4 | 电池 SOC/温度/告警 | 0x184+ | 100 ms | 慢变量，告警走 EMCY |
| 主站下发 | — | RPDO：目标速度+控制字 | 0x201~0x203 | 4/20 ms | — |

负载率核算：左右轮各 4 ms 一帧 TPDO + 一帧 RPDO，顶升 20 ms，BMS 100 ms，加上心跳与偶发 SDO，仲裁段 500 kbps 下负载率约 45%——在 50%~70% 的工程合格线内。canbusload 实测确认，不要只信计算。

两条设计纪律：

1. **EMCY 报文（0x80+Node-ID）的接收处理必须做**。BMS 过温、伺服过流都走 EMCY 主动上报，主站收到后的动作是减速停车并上报调度，不是写日志了事。
2. **轮速反馈的时间戳**：左右轮 TPDO 到达时刻有先后（仲裁顺序），里程计融合时按 CAN 帧时间戳对齐，不能按"同一周期读到"假设同时采样——4 ms 周期下两轮采样差可达毫秒级，高速直行时会折算成航向误差。

## 传感器链路分层

```
 安全层：安全扫描仪（Sick 类，安全认证器件）
   → 区域入侵直接输出安全继电器信号切断动力（硬件路径）
   → 同时 UDP 上报区域状态供上层记录
   原则：安全判定在认证器件内完成，不依赖主控软件

 感知层：激光雷达（SLAM/避障决策输入）
   → UDP 点云 → 主控 SLAM 节点
   → 时间戳对齐：雷达内部时钟与主控 PTP/NTP 对齐，
     点云时间戳与轮速里程计（CAN 帧时间戳）进同一坐标系

 补盲层：超声波 ×8（I2C 轮询，50 ms 周期）
   → 覆盖激光雷达的近距盲区与透明/吸波材质盲区
```

三层各司其职：安全层是硬件认证路径，感知层给算法，补盲层兜物理传感器的探测盲区。感知融合的时间对齐规则与 15.1 相同——不同源的量带时间戳交给算法，不强行同节拍。

## 无线双链路

```
 主链路：WiFi6（SDIO）—— 厂内 AP 漫游，低延迟调度通信
 备份链路：4G（USB）—— 出厂区/WiFi 盲区时接管
 切换策略：链路质量监控（RSSI+丢包率）连续 N 秒低于阈值
           → 任务降级（就近停车或按最后指令完成当前段）
           → 切换 4G 上报调度
```

无线链路的总线视角只有一条：**它是不可靠链路，控制闭环不能跨无线**。调度系统下发的是任务（去 A 点），不是实时控制量（速度指令）；实时闭环永远在车载主控本地。这条原则同时适用于 AMR、无人车和远程驾驶场景。

## Bring-up 与排障

```bash
# CAN FD 初始化（/etc/network/interfaces 或 systemd 服务固化）
ip link set can0 type can bitrate 500000 sample-point 0.75 \
    dbitrate 2000000 dsample-point 0.70 fd on restart-ms 100
ip link set can0 txqueuelen 1000 up

# 健康基线（交付前建立）
canbusload can0@500000            # 记录正常运行负载率基线 ~45%
ip -details -statistics link show can0   # 错误计数基线应为 0
candump -ta can0 > baseline.log   # 录一段正常流量作对比样本
```

| 症状 | 优先怀疑 | 验证方法 |
|:---|:---|:---|
| 里程计原地打转 | 单轮 TPDO 丢失（该轮 EMCY 或掉线） | candump 核对 0x181/0x182 双通道都在 |
| 直线跑偏 | 两轮采样时间未对齐 / 轮径参数未标定 | 时间戳差统计；轮径标定流程 |
| 负载率缓慢爬升 | 某节点 PDO 周期被误改 / 错误帧重传 | canbusload 趋势 + 错误计数 |
| 避障误触发停车 | 超声波串扰（8 路同发互串） | 超声波改为分时触发，核对轮询时序 |
| 过 WiFi 漫游区后任务丢 | 漫游断链期间无降级策略 | 模拟断链测试切换路径 |
| BMS 告警主站无反应 | EMCY 接收处理缺失 | cansend 模拟 EMCY 帧验证处理链 |
