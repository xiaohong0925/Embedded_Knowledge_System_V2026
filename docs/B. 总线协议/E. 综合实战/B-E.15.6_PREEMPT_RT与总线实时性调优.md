## 本节导读

前面五篇实战反复出现同一句话："最坏延迟要压到周期的 15% 以内。"机械臂 1 ms 周期、人形机器人 250 µs DC 同步、EtherCAT 主站每周期准时发帧——它们最后都收敛到同一个系统问题：Linux 的调度延迟能不能压到微秒级，并且**最坏情况**也可控。

标准 Linux 内核做不到这件事，不是因为它慢，而是因为它内部存在三类"不可抢占区段"：高优先级的实时线程就算已经就绪，也得等内核从这些区段里出来才能运行，等待时间不可预测。PREEMPT_RT 补丁把这三类区段逐一拆掉，让实时线程几乎可以抢占一切，最坏延迟从毫秒级压到几十微秒。

但打上 RT 补丁只是入场券。BIOS 的电源管理（SMI）、CPU 深休眠（C-state）、中断亲和性、内存换页、驱动里的长临界区——每一项都能绕过内核，把实时性打回原形。所以实时性不是"装个 rt 内核"就结束的事，而是一套"rt 内核 + 系统调优 + 量化验证"的完整方法论。

> 本节覆盖：实时性的度量口径（为什么只看最坏值）、PREEMPT_RT 的三大改造及其原理、最坏延迟的四层来源清单、BIOS/内核/系统/应用四道调优工序、cyclictest 与 hwlatdetect 的输出解读、周期性抖动的归因流程、可写进测试报告的验收标准。按"度量 → 内核改造 → 来源审计 → 调优 → 验证 → 归因 → 验收"的顺序展开，这正是你在真实项目里把一个系统从"能跑"做到"敢交付"的执行顺序。

本篇被 B-D.12.5（IgH 主站实战）、B-E.15.1（机械臂）、B-E.15.3（人形机器人）反复引用，是它们的实时性地基；反过来，本篇的验收表也直接复用了那几篇的控制周期数字。

## 先统一口径：实时性度量的是什么

实时（real-time）不等于快。一个系统的平均响应可以很快，但只要偶尔一次慢得离谱，实时控制就会出事——机械臂关节多走一拍、EtherCAT 主站错过 DC 同步窗口。所以实时性度量的不是平均性能，而是**最坏情况下的调度延迟**。

> 调度延迟：从"实时线程应该被唤醒的时刻"（定时器到期、数据包到达）到"它真正开始在 CPU 上执行"之间的时间差。这段时间里线程是就绪状态，但 CPU 被别的活动占用。

> 最坏延迟（worst-case latency）：长时间运行中观测到的最大调度延迟。实时系统的所有设计预算都按最坏值做，平均值只在对比调优效果时有参考意义。一次 10 ms 的尖刺就足以否决一套方案，哪怕它 99.99% 的时间都在 30 µs 以内。

这个口径决定了后文所有工具的用法：cyclictest 看 Max 列和直方图尾部，不看 Avg；验收按 72 小时连续测试的最坏值签字，不按演示时的漂亮数字。

## PREEMPT_RT 的三大改造

标准内核里有三类代码区段，CPU 一旦进入就不能被抢占（或者抢占代价极大），它们是调度延迟的主要来源。PREEMPT_RT 对每一类都做了手术式改造。

### 改造一：自旋锁变成可睡眠锁

标准内核里，自旋锁（spinlock）持锁期间关闭抢占。内核里到处都是自旋锁——调度器、内存管理、块层、网络栈，一个驱动持锁遍历几千条链表的临界区，就能让实时线程等上几毫秒。

PREEMPT_RT 把绝大多数自旋锁替换为 rtmutex：

> rtmutex（实时互斥锁）：一种可睡眠的锁。高优先级线程试图获取一把被低优先级线程持有的 rtmutex 时，会睡眠等待，同时把锁的持有者**临时提升到自己的优先级**（优先级继承），让持有者尽快跑完临界区、释放锁。自旋锁的语义是"等我转完"，rtmutex 的语义是"我让你先跑完"。

为什么这能降低最坏延迟？因为持锁者变成了可调度实体。标准内核里持自旋锁的代码是不可抢占的"黑箱"，你只能等；RT 内核里持 rtmutex 的低优先级线程会被优先级继承拉到高优先级，立刻获得 CPU 把临界区跑完——等待时间从"不可控"变成"一次临界区的执行时间"。

> 优先级反转：高优先级线程 H 等待低优先级线程 L 持有的锁，而中优先级线程 M 又抢占了 L——H 实际上在等 M，优先级体系失效。优先级继承（把 L 临时提升到 H 的优先级）是经典解法，PREEMPT_RT 把它铺到了内核所有 rtmutex 上，应用层用 `pthread_mutexattr_setprotocol(PTHREAD_PRIO_INHERIT)` 也能获得同样保护。

少数真正不能睡眠的地方（如调度器自身的运行队列锁）仍保留 raw_spinlock，PREEMPT_RT 的全部工作之一就是把这些"真自旋锁"压缩到最小集合。

### 改造二：中断处理线程化

标准内核里，硬中断 handler 在中断上下文执行，优先级高于一切线程——一个失控的网卡中断风暴可以把整个系统打停，实时线程连被调度的机会都没有。

PREEMPT_RT 默认把几乎所有中断 handler 变成内核线程（threaded IRQ）：

> 中断线程化（threaded IRQ）：硬中断 handler 只做最少的事（确认中断、屏蔽中断线），真正的处理逻辑放到一个普通内核线程里执行。这个线程有调度优先级（默认 SCHED_FIFO 50），可以被更高优先级的实时线程抢占，也可以被绑核、被观测、被限流。10.4 节讲的 `request_threaded_irq()` 是驱动侧的显式用法；PREEMPT_RT 是在全系统范围内默认启用它。

这意味着你可以在 `ps` 里看到名为 `irq/123-enp2s0` 的内核线程，用 `chrt` 调它的优先级，用 `taskset` 绑它的核——中断从"系统里不可见的最高权力"变成了"可管理的普通任务"。EtherCAT 主站场景的典型配置：网卡中断线程和周期控制线程绑到同一个隔离核，中断线程优先级 80、控制线程 90，收包唤醒后处理完立刻让位给控制线程。

### 改造三：关抢占区段的可抢占化

`rcu_read_lock()`、显式 `preempt_disable()` 这类区段在标准内核里也不允许抢占，某些路径（如大块内存的 RCU 释放、页表批量操作）能持续数百微秒。PREEMPT_RT 引入可抢占 RCU 等一系列改造，把这些区段也变成可调度点。这一层改造对使用者透明，知道它存在、知道它是补丁体量最大的部分即可。

### 改造的效果量级

同一台 x86 工控机（i7 级、工业主板），三组数字来自公开 QA 数据与实测经验的常见量级：

| 配置 | cyclictest 最坏延迟（72 h） | 能否跑 1 ms 周期 |
|:---|:---|:---|
| 标准内核，无调优 | 1~10 ms（SMI 爆发时更高） | 不能 |
| PREEMPT_RT，无系统调优 | 100~500 µs | 勉强，抖动风险大 |
| PREEMPT_RT + 全套调优 | 20~60 µs | 能，预算余量充足 |

> ⚠️
> 表中的数字是**量级参考**而不是承诺：具体平台的 SMI 行为、网卡型号、内存拓扑都会让数字漂移，消费级主板甚至可能怎么调都压不进 100 µs。这正是后文"验收必须自己测"的原因。

## 主线化现状与内核获取

PREEMPT_RT 曾经是需要手动打补丁的外部项目。从 Linux 6.12 起，PREEMPT_RT 在全部主流架构上完成主线化，配置项就是 `CONFIG_PREEMPT_RT=y`——这是 16.1 章（内核配置）里与实时性直接相关的那一行。

实际获取路径有三条，按工作量排序：

- **发行版现成包**：Ubuntu 24.04+ 的 `linux-image-realtime`、Debian 的 `rt` 内核包、openEuler 的 rt 内核，装完重启即得。产品项目首选，内核维护责任在发行版。
- **主线内核自编译**：`.config` 里确认三项——`CONFIG_PREEMPT_RT=y`、`CONFIG_HIGH_RES_TIMERS=y`、`CONFIG_NO_HZ_FULL=y`（后两项是调优前提，下文会用到）。
- **厂商 BSP 内核**：工业 ARM 平台（TI AM64x、NXP i.MX8MP 这类带 PRU/实时核的 SoC）通常由厂商提供打好 RT 补丁的 BSP，版本往往落后主线，用之前先确认补丁基线。

> HIGH_RES_TIMERS（高精度定时器）：把内核定时器分辨率从 jiffies 滴答（毫秒级）提升到硬件时钟事件精度（纳秒级接口、实际微秒级生效）。`clock_nanosleep()` 周期任务的定时精度直接依赖它。现代主流架构上它默认开启，自编译精简内核时值得确认一眼。

## 最坏延迟的四层来源清单

PREEMPT_RT 只解决了内核层的问题。实时性调优的真正对象是一张四层清单，每一层都能独立毁掉实时性——这也是为什么"装了 rt 内核还是抖"是调试现场最常见的抱怨。

### 硬件/固件层

这一层的延迟源完全绕过操作系统，内核看不见、统计不到，是最阴险的一类。

> SMI（System Management Interrupt，系统管理中断）：x86 平台上 BIOS/固件触发的一种特殊中断，CPU 收到后进入系统管理模式（SMM）执行固件代码，**整个操作系统在此期间被冻结且毫无感知**。常见诱因：USB  legacy 仿真、BIOS 电源管理、EC（嵌入式控制器）事件、内存巡检。一次 SMI 可以冻结 CPU 几十微秒到数毫秒，而且用 `ftrace` 这类内核工具永远抓不到——只能用 `hwlatdetect`（它用一个忙等循环独占 CPU，从 TSC 时间戳的跳变反推冻结窗口）才能看见。

> C-state（CPU 休眠态）：CPU 空闲时进入的省电状态，C1 最浅、C6/C8 更深。从深休眠唤醒需要重新上电、恢复缓存状态，耗时几十到几百微秒——这段时间就加在你的调度延迟上。实时系统必须限制 C-state 深度，宁可多耗电。

超线程（两个逻辑核共享物理核的执行资源，互相拖慢最坏情况）、频率缩放（变频过渡期的抖动）也在这一层。工程惯例：实时核关闭超线程、锁频运行。

### 内核层

- 未启用 `CONFIG_PREEMPT_RT` 或缺 `CONFIG_HIGH_RES_TIMERS`——前面已讲。
- 调度器把 RT 线程搬来搬去：核间迁移本身有缓存冷启动代价，能源感知调度（EAS，多见于 ARM 大小核平台）会主动迁移任务省电，实时系统要用 isolcpus 把实时核从普通调度域里摘出来。
- 内核时钟滴答（tick）：普通核上定时器中断按 Hz 频率周期性打断任务，本身就是延迟源。

> nohz_full（全动态滴答）：对指定 CPU 关闭周期性时钟滴答——当核上只有一个可运行任务时，tick 完全停止，任务运行期间零中断打扰。配合 isolcpus 使用，是实时核的标准配置。注意它要求核上**真的只有一个 RT 任务**，多放一个任务就会退化为普通调度。

### 驱动层

- 非 RT 感知的驱动：长自旋锁临界区（在 RT 内核里变成 rtmutex 后依然占时间）、驱动里直接 `local_irq_disable()` 关本地中断。第 10、11 章讲过的中断/底半部纪律在这里有直接的实时性后果。
- GPU/NPU 驱动：页表操作、固件 mailbox 通信可能停顿数百微秒。15.3 人形机器人篇那个"GPU 推理帧时间偶发抖动"的案例，根因之一就是核显与 CPU 共享内存带宽和末级缓存——驱动层的资源争抢，cyclictest 数字上表现为与推理节奏相关的周期性尖刺。
- 网卡驱动：NAPI 轮询、中断合并（interrupt coalescing）参数会直接影响收包延迟，EtherCAT 主站场景通常要 `ethtool -C` 关掉接收合并。

### 应用层

- 页错误：实时线程访问到还没映射的内存页，触发缺页中断走内核内存分配路径，一次几十微秒起。解法三件套在 12.5 和 15.1 的代码里都出现过：`mlockall()` 锁定全部内存、启动时预触碰栈和堆、实时循环里不做任何动态内存分配。
- 优先级与绑核没配：线程跑在默认 SCHED_OTHER，和普通进程一起被 CFS 调度，实时性无从谈起。
- 日志与 IO：`printf` 到串口/文件是系统调用，可能阻塞；实时循环里打日志是新手最常见的自伤行为，正确做法是写无锁环形缓冲、由普通优先级线程落盘。

## 调优四道工序

按"BIOS → 内核命令行 → 系统服务与中断 → 应用代码"的顺序执行，每一步都有独立的验证手段，做完一步验一步，不要全部配完再测——出了问题没法归因。

### 工序一：BIOS

关掉一切电源管理相关的选项，这是消除 SMI 和 C-state 延迟的第一战场：

```text
关：C-states（或限制到 C1）、C1E、Turbo Boost（评估后）、超线程（可选）、
    ASPM、USB legacy 支持、BIOS 里的所有"绿色/省电"特性
开：高性能电源模式（High Performance）、锁定 CPU 频率（若有选项）
```

验证手段：Linux 启动后 `turbostat` 观察各核 C-state 驻留比例——调优成功的标志是实时核深 C-state 驻留为 0%；`hwlatdetect` 空跑 10 分钟，确认无超限事件（输出解读见后文）。

> 💡
> Turbo 要不要关有争议：开 Turbo 平均性能高，但变频过渡期引入抖动；锁定基频可预测性最好。1 ms 以上周期的系统可以开 Turbo 试试，250 µs 级系统建议锁频。两档都实测，用 cyclictest 最坏值裁决。

### 工序二：内核命令行

在 bootloader 的启动参数里加：

```bash
isolcpus=2,3 nohz_full=2,3 rcu_nocbs=2,3 irqaffinity=0,1 intel_idle.max_cstate=1
```

逐项含义：

| 参数 | 作用 | 配合关系 |
|:---|:---|:---|
| `isolcpus=2,3` | 把 2、3 号核从普通调度域摘除，不再自动分配任务 | 实时任务的"专用跑道"，RT 线程用 `taskset`/`sched_setaffinity` 显式放上去 |
| `nohz_full=2,3` | 这两个核在单任务时停掉周期性时钟滴答 | 必须和 isolcpus 指向同一组核 |
| `rcu_nocbs=2,3` | 把 RCU 回调处理挪离这两个核 | 漏配它是"isolcpus 配了但仍有周期抖动"的常见根因 |
| `irqaffinity=0,1` | 新注册中断默认亲和到 0、1 核 | 给 housekeeping 核兜底，个别中断再手工调整 |
| `intel_idle.max_cstate=1` | 内核层限制 C-state 深度 | BIOS 没有对应选项时的兜底；BIOS 已关可不加 |

验证：`cat /proc/cmdline` 确认参数生效；`cat /sys/devices/system/cpu/isolated` 应输出 `2-3`。

### 工序三：系统服务与中断亲和

```bash
systemctl stop irqbalance && systemctl disable irqbalance
# irqbalance 的使命是动态均衡中断分布，它会精确地打乱你刚配好的亲和性
```

NTP/chrony 必须配置为**平滑校时**（slew 模式），禁止跳变校时——EtherCAT DC 参考时钟的稳定性直接依赖系统时钟的单调平滑，一次 50 ms 的跳变校时就能让全轴位置环集体报警。

然后把 EtherCAT 网口的中断绑到规划好的核：

```bash
grep enp2s0 /proc/interrupts
#  45:   1234567   ...   PCI-MSI  enp2s0
echo 2 > /proc/irq/45/smp_affinity_list
# 中断线程化后，等价操作也可以直接对 irq/45-enp2s0 线程做 taskset
```

中断线程与 RT 控制线程的核分配有两种风格：

| 风格 | 延迟路径 | 风险 | 适用 |
|:---|:---|:---|:---|
| 同核 | 收包中断处理完立刻唤醒同核控制线程，路径最短 | 中断风暴会挤占控制线程 | EtherCAT 主站推荐起步方案 |
| 分核 | 中断在 housekeeping 核处理，跨核唤醒控制线程 | 多一次 IPI 核间中断延迟 | 中断负载重、隔离性优先的系统 |

两种都实测，用 cyclictest 和应用内周期统计的对比数据选型，不凭感觉。

### 工序四：应用代码

实时线程的启动纪律，三件套缺一不可：

```c
/* 1. 锁定全部内存，禁止换页——之后的页错误会立刻失败而不是偷偷换页 */
mlockall(MCL_CURRENT | MCL_FUTURE);

/* 2. 预触碰栈：在进入实时循环前把栈每页写一遍，让缺页在启动阶段集中发生 */
unsigned char stack_prefault[8 * 1024 * 1024];
memset(stack_prefault, 0, sizeof(stack_prefault));

/* 3. 提到 RT 优先级 */
struct sched_param sp = { .sched_priority = 90 };
sched_setscheduler(0, SCHED_FIFO, &sp);
```

实时循环内的纪律：不分配堆内存、不做文件 IO、不打日志（写无锁环形缓冲由低优先级线程落盘）、互斥锁一律带 `PTHREAD_PRIO_INHERIT`。

验证：`cat /proc/self/status` 里 `VmLck` 应等于进程全部内存、`MajFlt` 在循环运行后不再增长；`chrt -p <pid>` 确认优先级生效。

两个应用层容易踩空的地方：

- **RT 限流（RT throttling）**：内核默认给 SCHED_FIFO/RR 任务留了保护闸——每组 CPU 每 1 s 只允许 RT 任务连续占用 0.95 s（`/proc/sys/kernel/sched_rt_runtime_us`），防死循环的 RT 任务把系统锁死。调试期如果 RT 线程"跑着跑着集体停 50 ms"，先查这个。专用实时系统常把它设为 `-1` 关闭限流，但这等于撤掉保险丝——应用必须保证 RT 线程周期内一定让出 CPU（`clock_nanosleep` 到下一周期），关闭前想清楚。
- **SCHED_DEADLINE**：比 SCHED_FIFO 更现代的调度类，直接声明"周期、运行时间、截止期限"三参数，由内核的 CBS 算法保证带宽并防止超支——线程就算写错了也拖不死别人。对周期性控制任务这是理论上更优的抽象，代价是配置复杂、工具链支持不如 SCHED_FIFO 成熟。新项目值得评估，存量项目继续 SCHED_FIFO 没有对错问题。

## 量化验证：cyclictest 输出解读

实时性只认测量。cyclictest 起一组高精度定时器线程，每周期把"应唤醒时刻"与"实际唤醒时刻"做差，统计延迟分布。它是实时验收的事实标准工具。

```bash
cyclictest -m -p 99 -i 1000 -h 500 -l 10000000 --smp
```

参数含义：`-m` 内部做 mlockall；`-p 99` RT 优先级 99；`-i 1000` 周期 1000 µs（模拟 1 ms 控制周期）；`-h 500` 输出到 500 µs 为止的直方图；`-l 10000000` 跑一千万次循环（1 ms 周期下约 3 小时）；`--smp` 每个核各起一个测量线程。

典型输出（每核一行，周期性刷新）：

```text
T: 0 ( 1234) P:99 I:1000 C:  99999 Min:      3 Act:      8 Avg:      9 Max:      42
T: 1 ( 1235) P:99 I:1000 C:  99999 Min:      3 Act:     11 Avg:     10 Max:      38
```

逐列解读：

- `T: 0 (1234)`：0 号测量线程，PID 1234，通常绑在 0 号核（`--smp` 模式下线程号与核号对应）。
- `I:1000`：测量周期 1000 µs。
- `C: 99999`：已完成 99999 次循环。
- `Min / Act / Avg / Max`：历史最小 / 本次 / 历史平均 / **历史最大**延迟，单位 µs。验收只看 Max；Avg 只用于调优前后对比。上面这组数字（Max 42）就是调优成功的样子；如果 Max 栏出现 800，说明这个系统上不了 1 ms 周期，不用继续往下看了。

`-h 500` 输出的直方图在测试结束时打印，长尾形状比 Max 单值更有信息量：尾部稀疏偶发（几天一次尖刺）指向 SMI 类事件；尾部连续厚重指向系统性的驱动/调度问题。

配套的 hwlatdetect 输出长这样：

```text
hwlatdetect:  test duration 600 seconds
   detector: pulse
   samples taken: 0 exceeding threshold (15 usec)
```

`samples taken: 0` 是理想结果——600 秒内没有抓到任何固件冻结窗口。如果数字非零，每一条 sample 都对应一次 SMI/固件停顿，且这个停顿是 OS 完全无能为力的层面，只能回 BIOS 找选项或换平台。

### 必须带压测试

空闲系统的延迟数字没有意义——实时系统的敌人全在压力下现身：内存带宽争抢、cache 冲突、中断负载、调度竞争。标准压力剧本：

```bash
stress-ng --cpu 4 --io 2 --vm 2 --vm-bytes 75% &
iperf3 -c <对端> &           # 网络压力
hackbench -l 100000 &        # 调度器压力（可选）
```

压力状态下重跑 cyclictest，经验合格线：最坏值漂移不超过空闲态的 2 倍。超过就说明隔离没做好——最常见的是 rcu_nocbs 漏配、irqbalance 还活着、或内存带宽被压测打满影响实时核。

## 周期性抖动的归因流程

12.5/15.x 实战里"周期偶发超时"这类问题，按固定顺序归因，不要跳跃：

```text
第 1 步：cyclictest 空闲基线干净吗？
   不干净 → 问题在硬件/内核层，与应用无关
     hwlatdetect 查 SMI；turbostat 查 C-state 驻留
第 2 步：基线干净，压力剧本下复现吗？
   复现 → 隔离/驱动层问题
     查 /proc/interrupts 分布、驱动临界区、内存带宽争抢
第 3 步：压力也不复现，只有真实业务复现 → 抖动的相关性
   与时间相关（每 N 秒一次）→ 后台服务、cron、NTP 跳变校时
   与负载相关 → 中断亲和、驱动临界区
   与操作相关（打开文件、打印日志时）→ 应用层页错误、阻塞 IO
第 4 步：ftrace 抓现场
   trace-cmd record -e sched_switch -e irq_handler_entry \
                    -p function_graph -l <rt线程函数> sleep 60
   在唤醒链路上找耗时最长的环节
第 5 步：修复后回归——同一压力剧本重跑 cyclictest，对比直方图尾部
```

> 💡
> 这套顺序的核心思想是**分层排除**：先用与应用无关的工具（cyclictest/hwlatdetect）把硬件和内核层洗清，再怀疑驱动，最后才看应用代码。颠倒顺序是实时性调试最常见的弯路——在应用代码里翻三天，最后发现是 BIOS 的 USB legacy 支持没关。

## 验收标准模板

实时系统的交付要落纸面。下表可直接放进测试报告，合格线数字按控制周期换算（表内以 1 ms 周期系统为例）：

| 项 | 方法 | 合格线 |
|:---|:---|:---|
| 空闲最坏延迟 | cyclictest 72 h | < 150 µs（周期的 15%） |
| 压力最坏延迟 | cyclictest + stress-ng + 网络压力 24 h | < 300 µs（空闲态 2 倍以内） |
| SMI 事件 | hwlatdetect 24 h，阈值 15 µs | 0 次超限 |
| 控制周期实测 | 应用内周期时间戳统计，跑满验收时长 | max < 1.2× 周期，抖动 < 10% 周期 |
| 总线侧错误 | EtherCAT WKC / 错误计数器 | 0 |

两条签字原则：测试必须跑满时长，72 小时不是修辞——SMI 类事件可能一天才出现一次；压力剧本必须写进报告正文，"在压力状态下"的空洞描述等于没测。

## 排障：实时性故障速查

| 症状 | 优先怀疑 | 验证方法 |
|:---|:---|:---|
| 最坏延迟几百 µs 且固定间隔出现 | SMI（BIOS 电源管理） | hwlatdetect；BIOS 逐项关电源管理 |
| 最坏延迟随温度/时间劣化 | C-state 深休眠、CPU 降频 | turbostat 驻留统计 |
| 加负载后抖动恶化 10 倍 | 中断未隔离、irqbalance 在跑 | /proc/interrupts 分布、进程状态 |
| isolcpus 配了但仍有周期性抖动 | rcu_nocbs 漏配，RCU 回调还在实时核上跑 | 内核命令行核对；/proc/interrupts 看残留中断 |
| RT 线程偶发长时间不运行 | 优先级反转（普通互斥锁被低优先级线程持有） | ftrace 查阻塞链；锁换 PTHREAD_PRIO_INHERIT |
| 程序运行初期抖、后期稳定 | 缺页集中在启动后（未 mlockall/未预触碰） | /proc/self/status 看 MajFlt 增长 |
| 一切配置正确仍不达标 | 平台本身不适合（消费级主板/网卡） | 换 Intel I210 + 工业主板交叉验证 |
| GPU 推理期间周期尖刺 | 核显/独显与实时核争抢内存带宽与 cache | 15.3 篇案例；隔离内存通道或推理挪到独立核 |

## 本节总结

实时性是一套度量驱动的工程方法，不是内核补丁的代名词：先统一口径（只看最坏延迟），再用 PREEMPT_RT 拆掉内核的三类不可抢占区段（rtmutex 化、中断线程化、可抢占 RCU），然后按硬件/内核/驱动/应用四层清单逐项审计，最后以 cyclictest 72 小时最坏值和 hwlatdetect 零事件作为交付签字依据。调优四道工序（BIOS、内核命令行、服务与中断、应用三件套）每一步都有独立的验证手段，出问题能立刻归因到层。

回到 B 扩展开头的问题——"这条总线能不能扛住这个控制周期"——到这里有了完整的答案闭环：协议特性决定理论上限（D 板块），驱动与主站栈决定实现质量（12.5），系统实时性决定你能不能兑现理论值（本篇）。

| 关键结论 | 一句话记忆 |
|:---|:---|
| 度量口径 | 只看最坏值，平均值仅供调优对比 |
| PREEMPT_RT 三改造 | 锁可睡眠、中断变线程、RCU 可抢占 |
| 四层来源 | 固件 SMI 最阴险，hwlatdetect 是唯一照妖镜 |
| 调优 | BIOS 关电源管理 → isolcpus 三兄弟 → 杀 irqbalance → mlockall 三件套 |
| 验收 | 72 h 满时长 + 明写的压力剧本，两条缺一不可 |
