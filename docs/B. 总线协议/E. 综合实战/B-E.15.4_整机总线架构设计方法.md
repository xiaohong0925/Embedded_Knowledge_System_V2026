# B-E.15.4 整机总线架构设计方法

> 所属章节：第五部 B. 总线协议 > E. 综合实战
>
> 难度：[M] | 预计阅读时间：40 分钟

## 本节导读

15.1~15.3 是三个具体整机的答案，本篇把答案背后的方法抽出来：拿到任何一个新整机需求，怎样系统地推导出总线架构——而不是凭经验拍脑袋或者抄上一个项目。方法是四步流程：需求枚举 → 约束量化 → 选型矩阵收敛 → 预算验证。这套流程对机器人成立，对数通设备、仪器仪表、车载域控同样成立。

本节覆盖：总线需求枚举的六个维度、约束量化的做法（周期/带宽/距离/成本/生态/安全）、选型矩阵的构建与使用、带宽与时延预算的核算模板、架构评审的检查清单、常见架构决策失误。

## 第一步：需求枚举

把整机里**每一个需要通信的功能**列出来，逐项填六个维度。漏项是架构失败的第一来源——方法上要求按整机 BOM 和功能清单逐行过，不允许凭记忆列举。

| 维度 | 问题 | 示例（某检测设备） |
|:---|:---|:---|
| 数据内容 | 传什么 | 伺服指令 / 传感器读数 / 视频流 / 日志 |
| 周期/时延 | 多快一次、允许多大延迟与抖动 | 1 ms 周期，抖动 <100 µs |
| 数据量 | 单次多少字节 | 10 B / 帧 vs 10 MB/s 流 |
| 距离与拓扑 | 物理上隔多远、中间过什么结构 | 板内 / 穿关节 / 跨机柜 |
| 环境 | EMC、温度、振动 | 工业现场强干扰 |
| 安全等级 | 错误数据的后果 | 普通数据 / 安全相关 |

输出物是一张"通信需求清单"，每一行是一个功能，六列填满。这张表是后续所有决策的输入，也是架构评审的受审对象。

## 第二步：约束量化

把需求清单聚类成若干"流量类"，每类量化出硬指标：

```
 流量类 A：伺服闭环（8 轴）
   周期 1 ms、抖动 <50 µs、单帧 20 B、距离 <3 m、安全相关
 流量类 B：传感采集（12 路）
   周期 10 ms、抖动宽松、单帧 8 B、板内
 流量类 C：高速数据（相机/采集）
   持续 200 MB/s、无周期要求、距离 <1 m
 流量类 D：管理/日志
   无实时要求、带宽小、要走标准网络
```

量化时不许写"快一点""尽量低"这种词——每个指标必须有数字和测量方法。写不出数字的需求是没想清楚的需求，回到需求方确认。

## 第三步：选型矩阵收敛

对每个流量类，用 B 扩展各组的知识填选型矩阵。**每个候选必须能说出"排除理由"**——说不出排除理由的选型是惯性不是设计：

| 流量类 | 候选 | 收敛 | 排除理由 |
|:---|:---|:---|:---|
| A 伺服闭环 | EtherCAT / CAN FD / RS-485 | EtherCAT | CAN FD：8 轴双向带宽不够；RS-485：无同步机制 |
| B 传感采集 | SPI / I2C / CAN | SPI+I2C 按器件分 | CAN：板内芯片加收发器是浪费 |
| C 高速数据 | PCIe / USB3 / 千兆网 | PCIe | USB3：DMA 直通与延迟不如 PCIe；千兆网带宽不够 |
| D 管理 | 以太网 | 以太网 | — |

收敛的优先级顺序（高约束先收敛）：

1. **安全约束**：安全相关功能先划出去走独立路径（14.3 原则），不参与总线性价比竞争。
2. **实时约束**：周期与抖动要求最苛刻的流量类先定总线——它往往决定整机的主干网。
3. **带宽约束**：大数据量类其次，它决定是否需要第二条高速通路。
4. **成本与生态**：前两条满足后，剩下按成本、供应链、团队熟悉度收敛。

## 第四步：预算验证

架构落地前做一次书面预算，两个科目：

**带宽预算**（每条总线）：

```
 总线 X 负载率 = Σ（每节点帧长 × 频率）/ 总线有效速率
 合格线：CAN/CAN FD < 60%；EtherCAT 周期占用 < 50%；
         以太网数据面 < 70%；I2C/SPI 按最坏情况不阻塞实时读
```

**时延预算**（每条端到端控制路径）：

```
 传感采样 ─t1→ 总线传输 ─t2→ 主控计算 ─t3→ 总线下发 ─t4→ 执行器动作
 t1+t2+t3+t4 ≤ 控制周期 × 60%（留 40% 抖动与余量）
 每项给出测量或计算依据
```

预算不过就回第三步改方案——预算表的价值就是在画板子之前暴露问题。

## 架构评审检查清单

设计评审时逐条过：

- [ ] 需求清单是否按 BOM 逐项枚举，无凭记忆补的项
- [ ] 每个选型是否有书面排除理由
- [ ] 安全功能是否独立于通信总线（或有认证的安全协议）
- [ ] 实时网与非实时网是否物理/逻辑隔离
- [ ] 每条总线的负载率预算是否达标
- [ ] 每条控制路径的时延预算是否达标
- [ ] 单点故障清单：每条总线断掉的后果与降级动作是否定义
- [ ] 时钟同步策略：哪些量必须同节拍、哪些带时间戳补偿
- [ ] 可生产性：线缆长度、连接器、穿结构路径是否和机械工程师对过
- [ ] 可测试性：每条总线是否有出厂测试手段（loopback、candump 类工具）

## 常见决策失误

| 失误 | 表现 | 纠正 |
|:---|:---|:---|
| 抄旧方案 | 上一代用 CAN 就接着用，轴数翻倍后带宽崩 | 每次按四步流程重走，历史方案只是候选之一 |
| 唯参数论 | 选速率最高的总线，忽略生态与成本 | 收敛优先级：安全→实时→带宽→成本 |
| 总线种类爆炸 | 一台机器八种总线，测试维护成本失控 | 同类流量合并，总线种类 ≤5 为宜 |
| 安全后补 | 架构定稿后才加急停回路 | 安全约束第一步就划出去 |
| 预算缺失 | 没算负载率，现场高负载时才暴露丢帧 | 第四步不签字不投板 |

## 本节自查

读完本篇，你应能独立完成以下动作：

- 为一个新整机产出六维通信需求清单
- 把需求聚类成流量类并量化出周期/带宽/距离/安全指标
- 构建选型矩阵并对每个收敛写出排除理由
- 按模板核算带宽预算与时延预算，说明合格线的来源
- 主持一次总线架构评审，逐条过检查清单
- 识别"抄旧方案""唯参数论"等五类失误在自己项目中的痕迹
