# B-D.14.4 车载 SerDes：GMSL / FPD-Link / A-PHY / ASA / HSMT

> 所属章节：第五部 B. 总线协议 > D. 专用网络总线
>
> 难度：[I] | 预计阅读时间：45 分钟

## 本节导读

摄像头和显示屏是车载数据量最大的两类外设：一路 8 MP 摄像头的 RAW 数据流超过 3 Gbps（算式见下文），一块座舱大屏的显示流更在 10 Gbps 以上。这类"点对点、几米到十五米、单对同轴或差分线"的高速视频链路，走的是车载专用 SerDes——不是以太网（以太网要做包交换和全网调度，点对点视频流用它是杀鸡用牛刀还引入延迟），也不是 MIPI 直连（物理层扛不住十五米线束）。

市场上有五个标准并存：GMSL（ADI）、FPD-Link（TI）两家私有标准占据存量市场，A-PHY（MIPI 联盟）、ASA（欧系车企联盟）、HSMT（中国标准）三个后起标准试图打破私有锁定。做摄像头/显示链路设计或选型时绕不开这五家——它们决定了你的摄像模组买谁的、SoC 平台支持谁、出问题找谁。

> 本节覆盖：车载 SerDes 解决的问题与 MIPI 直连的物理边界、串行器/解串器对的管道结构、五大标准的技术与生态对比（速率/调制方式/线缆/锁定关系）、PoC 同轴供电与反向控制通道两个伴随机制、Linux 驱动接入形态（V4L2 subdev/DRM bridge/I2C 透传）、三层调试入口与链路排障。按"为什么需要 → 管道结构 → 五标准选型 → 伴随机制 → Linux 落地 → 排障"的顺序展开——这正是一个摄像头链路项目从方案到调试的实际推进顺序。

B-F.16.1 讲的 SerDes 通识（均衡、眼图、抖动、信道预算）是本篇的物理层地基：车载 SerDes 是那套通用技术在车规十五米线束上的具体形态，本篇不再重复通识，聚焦车载特有的标准格局与接入形态。

## 为什么 MIPI 不能直接上车

先算清数据量。8 MP 摄像头（3840×2160）输出 RAW10、30 fps：

```text
3840 × 2160 像素 × 10 bit × 30 fps ≈ 2.5 Gbps（纯像素）
加行场消隐与 CSI-2 协议开销 ≈ 3 Gbps 线上速率
```

3 Gbps 要从摄像模组走到域控制器，距离 3~15 米。MIPI CSI-2 的物理层 D-PHY（B-C.9 组）设计边界是**板内十几厘米**：电压摆幅小（高速模式 200 mV）、无长线均衡、无任何车规 EMC 设计。直接拉十五米，信号完整性在第一个连接器处就崩了。

> 信号完整性（Signal Integrity）：高速信号在传输线上保持波形不失真的性质。距离一长，趋肤效应和介质损耗把高频分量衰减掉（码间串扰）、连接器阻抗不连续引起反射、外部干扰耦合进来——三者叠加，接收端眼图闭合，误码率爆炸。F.16.1 有完整的机制讲解；这里只需要记住结论：**速率×距离的乘积是物理层的硬约束**，3 Gbps×15 m 远超 MIPI D-PHY 的设计包络。

车载 SerDes 的本质就是把 MIPI 流重新封装到带均衡、编码、车规 EMC 设计的高速串行链路上：

```text
 摄像模组                线束 3~15 m              域控制器
 ┌─────────┐    ┌────┐   同轴/差分对   ┌────┐    ┌─────────┐
 │ Sensor  │───▶│串行器│ ═══════════▶ │解串器│───▶│ SoC     │
 │ MIPI    │MIPI│     │   + PoC 供电  │     │MIPI│ CSI-2   │
 └─────────┘    └────┘   + 反向控制   └────┘    └─────────┘
```

> SerDes（Serializer/Deserializer，串行器/解串器）：把并行数据流（这里是 MIPI 的多 lane 数据）转成高速串行比特流发送、在远端还原的芯片对。通识见 F.16.1。车载 SerDes 的特点是**两端必须同标准、通常同厂商配对**——串行器是 ADI 的，解串器就得是 ADI 的，这就是后文"生态锁定"的物理基础。

对 SoC 来说这一切透明：解串器输出的仍是标准 CSI-2，SoC 的摄像头驱动链路不需要知道中间隔了十五米线。中间的线束问题全部由 SerDes 芯片对吃掉。

## 五大标准对比

| 标准 | 主推方 | 代表芯片 | 下行速率 | 调制 | 线缆 | 生态性质 |
|:---|:---|:---|:---|:---|:---|:---|
| GMSL2 / GMSL3 | ADI（美信） | MAX9295/96717 串、MAX9296/96724 解 | 6 / 12 Gbps | NRZ / PAM4 | 同轴或 STP | 私有，ADAS 摄像头市占最高 |
| FPD-Link III / IV | TI | DS90UB953/960 系列 | 4.16 / 13.5 Gbps | 私有编码 / PAM4 | 同轴或 STP | 私有，座舱显示与摄像头 |
| A-PHY | MIPI 联盟 | Valens VA70xx 等 | 16 Gbps（路线图 32） | PAM4/8/16 自适应 | 同轴/差分 | 开放标准 |
| ASA Motion Link | ASA 联盟（宝马等发起） | 多厂商 | ~13.5 Gbps | PAM4 | 非屏蔽双绞为主 | 联盟标准，欧系车企推动 |
| HSMT | 中国汽标委 | 国产芯片跟进中 | ~12.8 Gbps | PAM4 | 同轴/STP | 中国公开标准 |

> NRZ 与 PAM4：两种线路编码。NRZ（不归零码）一个符号携带 1 bit（高/低两电平）；PAM4 用四个电平携带 2 bit，同样波特率下速率翻倍，代价是信噪比预算恶化约 9.5 dB（眼图从一只眼变三只眼，每眼高度只剩 1/3）。12 Gbps 以上的车载 SerDes 全部转向 PAM4——细节见 F.16.1 的调制对比节。

五个标准的格局认知，三条就够：

- **存量看私有双雄**：GMSL 与 FPD-Link 上车验证里程最长（亿辆级），2026 年的在产车型摄像头链路基本是这两家。选型倾向由摄像模组供应商决定——模组厂把串行器做进了模组，你买谁的模组就用谁的标准。
- **增量看开放标准**：A-PHY/ASA/HSMT 意在打破"串行器-解串器必须同厂"的锁定，2026 年处于新标准导入期。新平台设计评审会看到它们；评估重点是生态成熟度（有没有第二家芯片供应商）与车企背书。
- **上下行全部不对称**：下行（域控→摄像头/屏）是 Gbps 级视频流；上行反向通道只有百 Mbps 级，跑 I2C/GPIO 透传。这是五个标准共同的架构特征，不是某一家的设计癖好——视频本来就单向。

> 反向通道（Back Channel）：车载 SerDes 链路上与视频流向相反的低速通道。摄像头侧 Sensor 的 I2C 初始化、触摸回传、模组固件升级都走它。实现上是在高速下行流里时分/频分嵌入低速上行数据，对应用层表现为"透过解串器访问远端 I2C 设备"。

## 五标准逐个看

表格给格局，逐个给细节——选型评审时需要的是这一层。

### GMSL（ADI）

Gigabit Multimedia Serial Link，原是美信（Maxim）产品线，随 ADI 收购美信归入 ADI。GMSL2（6 Gbps，NRZ）是 ADAS 摄像头事实上的最大存量；GMSL3（12 Gbps，PAM4）面向 8 MP 以上摄像头与多屏座舱。强项是**验证里程**——AEC-Q100 车规认证加上亿辆级装车量，车企功能安全评审对它的接受度最高。弱点是私有：串行器 MAX96717 必须配 ADI 的解串器，第二供应商不存在。Linux 支持五家里最好，`drivers/media/i2c/` 下的 max 系列驱动就是证明。

### FPD-Link（TI）

Flat Panel Display Link，历史比 GMSL 更老——出身是笔记本屏线（LVDS 时代）。FPD-Link III（4.16 Gbps）在座舱显示链路装机量巨大，IV 代（13.5 Gbps，PAM4）补齐了高分辨率摄像头能力。TI 的策略是把 SerDes 做成"全家桶"的一环：摄像头 DS90UB953 + 解串器 DS90UB960 + 配套的时钟/电源芯片一起卖。Linux 主线有 DS90UB 系列驱动，覆盖度略逊于 GMSL。

### A-PHY（MIPI 联盟）

MIPI 联盟亲自主导的开放标准，野心最直接：**既然两端都是 MIPI 接口（CSI-2/DSI），中间的远程传输也该是 MIPI 标准**——消除"私有 SerDes 夹在两个 MIPI 之间"的别扭。技术上最激进：PAM4/8/16 自适应调制（按信道质量自动选阶数）、内建重传机制（视频 SerDes 里少见），16 Gbps 起步路线图到 32 Gbps 以上。芯片供应商以 Valens 为主，2026 年仍在生态爬坡期。看点是它是唯一一个"标准组织背书+多供应商愿景"的方案，长期最可能改写格局。

### ASA Motion Link（ASA 联盟）

ASA（Automotive SerDes Alliance）由宝马等欧系车企发起，逻辑是"车企不想再被芯片厂锁定，自己组团定标准"。~13.5 Gbps，PAM4，线缆主打非屏蔽双绞（UTP）——比同轴便宜是它对车企的核心卖点。欧洲新平台开始导入。对它的评估重点是：芯片供应商名单够不够长、UTP 在你的 EMC 环境里实测余量够不够。

### HSMT（中国汽标委）

中国汽车芯片标准体系里的高速多媒体传输标准，~12.8 Gbps，同轴/STP。定位与 ASA 类似（打破私有锁定），驱动力是国产供应链安全——国产 SerDes 芯片厂（慷智、瑞发科等）跟进中。做国产平台的项目会遇到它；评估维度与 ASA 相同，另加一条：与国产 SoC 平台的配套验证状态。

**选型决策的一句话版**：量产求稳选私有双雄（跟着模组供应商走），新平台且有议价能力时评估开放标准；显示链路看 FPD-Link 装机惯性，摄像头链路看 GMSL 生态，五年后的平台设计把 A-PHY 放进观察清单。

## 伴随机制：PoC 同轴供电

摄像头模组悬在车身末端，单独拉电源线意味着多一根线束、多一个连接器。PoC（Power over Coax）把供电（典型 5~12 V）叠加在同一根同轴线上：

> PoC（Power over Coax，同轴供电）：在同轴电缆上同时传输高速数据与直流供电。原理与 PoE（以太网供电，C.7 组）相同思想、不同实现：高频数据走电容耦合通路，直流电源走电感通路，两端用"电感+电容"的分频网络把两者分开互不干扰。

PoC 的坑全在那个分频（滤波）网络：电感要在数据频段呈现高阻（不能短路数据）、在直流下低阻（不能压降过大发热），还要扛住电流不饱和。选型时要看电感的两组曲线：阻抗-频率曲线（在链路基频处阻抗要足够高，GMSL2 的 6 Gbps NRZ 基频约 3 GHz，要求该频点阻抗典型在 1 kΩ 量级）、饱和电流曲线（模组工作电流加大温度裕量下不饱和——电感饱和后阻抗崩塌，数据被短路到电源，链路瞬断）。工程实践中常把多个不同感值的电感并联/串联组合来覆盖宽频段，SerDes 厂商的参考设计里那张"PoC 电感推荐表"直接照抄是最稳的起点，自研替代料必须过全温误码验证。

滤波网络设计不良的典型症状是链路误码率升高**且**模组供电纹波超标——两个看似不相关的毛病同一个根因。摄像模组硬件评审时，PoC 滤波电感的选型曲线是必查项。

## 信道预算：十五米线束的衰减账

车载 SerDes 的"能通"不是玄学，是一笔可算的衰减账（信道预算方法详见 F.16.1，这里给一个车载实例）：

```text
发送端输出摆幅（典型）            ≈ 800 mV（差分）
15 m 同轴线缆衰减 @3 GHz          ≈ −12 dB（Leoni Dacar 级车规线典型值）
2~3 个连接器 + 线束转接           ≈ −3 dB
PCB 走线与 AC 耦合电容             ≈ −2 dB
─────────────────────────────────────────────
信道总衰减                        ≈ −17 dB（电压比 ≈ 1/7）
接收端收到                        ≈ 110 mV
接收器灵敏度（带 CTLE+DFE 均衡后）  ≈ 几十 mV 可恢复
结论：有余量，但不奢侈——这就是链路训练存在的原因
```

> 链路训练（Link Training）：链路上电后，收发两端自动协商均衡参数的过程——发送端试几档预加重，接收端调整 CTLE/DFE 抽头，用误码率反馈选出最优组合，然后进入锁定（lock）状态。GMSL/FPD-Link 的训练在毫秒级完成，对软件透明；训练失败就是排障表里的"lock 位为 0"。训练机制详解见 F.16.1，车载侧只需要知道：**换线束供应商、改走线长度后，原来锁得上的链路可能锁不上——预算变了**。

这笔账的实践推论有三条：线束和连接器的选型直接吃掉预算余量（便宜线缆在 3 GHz 处衰减可能翻倍）；同一个模组移到不同车型上要重算（线长变了）；"实验室能通、装车偶发不通"几乎总是预算余量不足在温度/老化边缘暴露。

## Linux 接入形态

对软件工程师，SerDes 芯片对的可见接口有三层：

**1. V4L2 侧（摄像头链路）**：解串器驱动（`drivers/media/i2c/max96717.c`、`max9296.c` 等已进主线）注册为 V4L2 subdev，串在 sensor 与 SoC CSI 接收端之间。视频管道变长：

```text
sensor → serializer →（GMSL 链路）→ deserializer → csi2-rx → isp → /dev/video0
```

> V4L2 subdev 与 media controller：V4L2 的子设备框架。视频管道里每个芯片（sensor、串行器、解串器、ISP）是一个 subdev，各自有自己的控制接口；media controller（`/dev/media0`）把整条管道的拓扑暴露出来，用 `media-ctl` 查看和配置各节点的格式与连接。多芯片摄像头管道（手机、车载）都靠它管理——`media-ctl -p` 打印的拓扑图是摄像头调试的第一现场。

**2. DRM 侧（显示链路）**：串行器作为 DRM bridge 注册，把 SoC 的 DSI/eDP 输出桥接到 FPD-Link/GMSL 显示链路。显示链路对软件更透明——bridge 注册后，上层看到的就是一块普通屏。

**3. I2C 透传**：SerDes 对的反向通道把 I2C 透传到远端 Sensor。设备树里 sensor 节点挂在解串器创建的 I2C 适配器下：

```dts
&i2c1 {
    max9296: deserializer@48 {              /* 域控侧解串器，本地 I2C */
        compatible = "adi,max9296a";
        reg = <0x48>;
        /* GMSL 链路配置：串行器地址映射、MIPI 速率/lane 数 */
        ports {
            /* port@0/1：GMSL 输入（接远端串行器）；
               port@2：CSI-2 输出到 SoC */
        };
        i2c-alias {                         /* 透传 I2C：远端设备挂这里 */
            ov9281: sensor@60 {
                compatible = "ovti,ov9281";
                reg = <0x60>;             /* 远端 sensor 的原始地址 */
            };
        };
    };
};
```

驱动写法上的关键认知：**sensor 驱动不知道自己在十五米外**。解串器驱动完成地址映射（远端 0x60 映射成本地别名，避免与本地总线冲突）和链路管理，sensor 驱动读写寄存器时，I2C 事务被解串器截获、打包进反向通道、送达远端串行器、在模组侧还原成真实 I2C。`i2cdetect` 扫这条透传总线能看到远端 sensor，但扫描本身会通过反向通道放大延迟——透传链路上的 I2C 超时参数通常要放宽。

### 显示链路的两个软件可见细节

显示方向（SoC→屏）与摄像头方向对称，但有两点软件工程师会直接碰到：

- **触摸回传走反向通道**：座舱触摸屏的触摸坐标数据从屏端经反向 I2C 透传回 SoC。现象是"屏亮了但触摸没反应"——十有八九是反向通道或透传地址配置问题，不是触摸驱动本身。排查顺序与摄像头链路一致：先查链路 lock，再查 I2C 透传。
- **多屏菊花链（daisy-chain）**：一颗解串器可以级联驱动多块屏（仪表+中控+副驾），视频流在 SerDes 层做复制或拆分。设备树里表现为一个 bridge 节点带多个 panel 子节点；点亮顺序和格式协商由 bridge 驱动完成，上层 DRM 看到的仍是一块逻辑屏或一组独立 CRTC，取决于驱动的拆分方式。

### GMSL 管道（pipe）概念

GMSL 解串器内部有"pipe"（管道）概念：每路 GMSL 输入可以映射到不同的 CSI-2 输出端口和虚拟通道（VC）。四路摄像头接一颗解串器时，pipe 映射决定哪路摄像头出现在哪个 CSI 口、哪个 VC 号上——设备树里 `ports` 节点的配置就是在描述这张映射表。多摄像头"图像串台"（A 摄像头的画面从 B 的节点出来）查的就是 pipe/VC 映射。

### 多摄像头帧同步

ADAS 多目视觉要求多路摄像头**同一时刻曝光**（前后视画面时间对齐，融合算法才有意义）。实现靠反向通道透传的 GPIO：解串器把一个 GPIO 信号经 SerDes 链路送到所有串行器，作为各路 sensor 的 FSYNC（帧同步）触发源。设备树/驱动里的同步配置出错时，症状不是"没图像"而是"各路图像时间戳对不上"——这类问题在单摄像头调试时完全不可见，多目联调才暴露。

## 三层调试入口

车载 SerDes 链路的调试按层进行，每层有专属工具：

```text
第 1 层 V4L2 层：    media-ctl -p              看管道拓扑与格式协商
                    v4l2-ctl --stream-mmap    验证有没有帧流出来
第 2 层 SerDes 寄存器层：i2ctransfer 读解串器的
                    链路锁定状态、误码计数、线路质量寄存器
第 3 层物理层：      解串器内建的眼图监视器/PRBS 测试模式
                    （厂商工具经 I2C 触发，误码统计直接读回）
```

分层定位原则：**先确认链路锁没锁（第 2 层），再看有没有帧（第 1 层），怀疑物理层才上第 3 层**。"链路锁不上"是线束/供电/配对问题，"锁上了没帧"是 MIPI 配置问题——两类故障的排查路径完全不同，先用锁定状态寄存器分流。

`media-ctl -p` 的输出样本（四路 GMSL 摄像头链，截取关键段）：

```text
Media controller API version 6.6.x
- entity 1: max9296 2-0048 (2 pads, 2 links)
    pad0: Sink  [fmt:UYVY8_1X16/1920x1080]
      <- "ov9281 4-0060":0 [ENABLED]     ← 远端 sensor 经透传总线出现
    pad1: Source
      -> "csi2-rx":0 [ENABLED]           ← 解串器输出接到 SoC CSI 接收端
```

判读要点：每个 entity 是管道里的一颗芯片，`[ENABLED]` 表示该链接已建立；sink pad 的 `fmt` 是协商出的数据格式——**"没帧"故障先看这条链上的格式是否逐跳一致**（sensor 输出 RAW10 而解串器 pad 显示 UYVY，就是格式协商断了）。拓扑里缺 entity 或链接未 ENABLED，说明驱动 probe 顺序或设备树端口绑定有问题。

PRBS 测试模式值得单独说：让串行器发标准伪随机码流（不经过 sensor），解串器统计误码——这等于把视频源从问题里摘出去。误码依旧 → 线束/连接器/PoC 问题；误码消失 → 问题在 sensor 或 MIPI 配置。这是"花屏"类故障的隔离手术刀。

## 排障：车载 SerDes 链路

| 症状 | 优先怀疑 | 验证方法 |
|:---|:---|:---|
| 链路锁不上（lock 位为 0） | 线缆/连接器、PoC 滤波、串行器未上电、Ser/Des 型号不配对 | 读解串器链路状态寄存器；量 PoC 电压；核对两端芯片型号 |
| 锁定但无视频帧 | MIPI 速率/lane 数两端不匹配；media 管道格式没协商通 | 核对 sensor 输出与解串器 CSI 配置；`media-ctl -p` 看格式链 |
| 图像偶发花屏 | 链路误码：线束受损、EMC、PoC 滤波不良 | 读误码计数；开 PRBS 模式隔离视频源 |
| I2C 透传超时 | 地址映射冲突、反向通道未使能、超时参数太短 | 核对 i2c-alias 映射表；放宽 I2C 超时 |
| 摄像头启动慢/偶发失败 | PoC 上电时序：电压爬升期内链路训练失败 | 示波器抓 PoC 电压爬升与 lock 时间的关系 |
| 低温下链路不稳 | 连接器接触电阻变化、线缆特性漂移 | 温箱复测+误码计数；查车规连接器批次 |
| 同型模组有的通有的不通 | 模组内串行器固件版本不一致 | 读串行器固件版本寄存器比对 |

## 本节总结

车载 SerDes 解决的是一个边界清晰的问题：MIPI 的物理包络到不了十五米，而以太网对点对点视频流太重——于是有了"串行器-解串器对"这个专用形态，把 MIPI 流扛过车规线束，对 SoC 完全透明。选型维度上，GMSL/FPD-Link 私有双雄占存量、A-PHY/ASA/HSMT 开放标准争增量，真正的选型权往往在摄像模组供应商手里；工程落地时，PoC 滤波网络和反向通道 I2C 透传是两个最常出事的伴随机制。Linux 侧接入已是主线形态：V4L2 subdev + media controller 管摄像头长管道，DRM bridge 管显示，I2C 透传让远端 sensor 对驱动透明；调试按"V4L2 → 寄存器 → 物理层 PRBS"三层递进，先用锁定状态分流故障类别。

| 关键结论 | 一句话记忆 |
|:---|:---|
| 存在理由 | MIPI 距离不够、以太网太重，SerDes 是视频链路的专用解 |
| 管道 | sensor→串行器→线束→解串器→SoC，对 SoC 透明 |
| 选型 | 存量 GMSL/FPD-Link，增量看 A-PHY/ASA/HSMT；模组厂定标准 |
| 伴随机制 | PoC 供电的坑在滤波电感；反向通道跑 I2C/GPIO 透传 |
| Linux | V4L2 subdev 长管道 + DRM bridge + I2C 透传，主线已支持 |
| 调试 | 先查 lock，再查帧，PRBS 模式隔离物理层 |
| 多目同步 | FSYNC 走反向通道 GPIO；"图像串台"查 pipe/VC 映射 |
