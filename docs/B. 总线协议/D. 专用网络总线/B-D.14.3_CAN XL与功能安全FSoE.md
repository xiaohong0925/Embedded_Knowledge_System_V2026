# B-D.14.3 CAN XL 与功能安全（FSoE）

> 所属章节：第五部 B. 总线协议 > D. 专用网络总线
>
> 难度：[E] | 预计阅读时间：35 分钟

## 本节导读

CAN 家族的第三代 CAN XL 在 2024 年完成标准化（CiA 610-1 / ISO 11898-1:2024），控制器芯片开始量产。它要回答的问题很具体：在车载区域架构里，CAN 能不能不掉队地接住 10 Mbps 级主干通信，同时保持与 CAN FD 的生态连续？本节前半段讲 CAN XL 相对 FD 的变化——帧结构、速率、与以太网的衔接；后半段讲功能安全协议这一层，以 FSoE（FailSafe over EtherCAT）为样本说明"安全协议跑在非安全总线上"的通用模式——这是机器人安全功能（STO、安全限速）落地的协议基础。

本节覆盖：CAN XL 的帧结构与速率机制、XL/FD/2.0 三代共存关系、CAN XL 与车载以太网的定位边界、功能安全通信的问题定义、黑色通道模式、FSoE 的工作机制、功能安全开发的工程纪律。

## CAN XL：FD 的短板与 XL 的补法

CAN FD 把 payload 扩到 64 字节、数据段提到 8 Mbps，但两个约束还在：帧开销比例仍然高（64 字节数据要配约 40 位帧头帧尾）；与以太网体系（区域架构主干）没有直接衔接。CAN XL 的补法：

| 维度 | CAN FD | CAN XL |
|:---|:---|:---|
| 数据段速率 | ≤8 Mbps | ≤20 Mbps（SIC XL 收发器） |
| Payload | 64 B | 2048 B |
| 帧头开销 | 固定 40+ 位 | 精简控制场，引入 SDU Type |
| 以太网衔接 | 无 | 帧可隧道承载以太网帧（L2 互通） |
| 寻址 | 11/29 位 ID | 保留 ID 仲裁 + 新增节点寻址字段 |
| 校验 | CRC-17/21 | 双 CRC（13 位头 CRC + 32 位帧 CRC） |
| 收发器 | FD 收发器 | SIC XL 收发器（PWM 编码驱动） |

机制上的两个关键变化：一是 **SIC XL 收发器**用 PWM 编码在数据段驱动总线（TxD 的占空比区分 0/1），绕开传统显性/隐性电平驱动在 10 Mbps 以上的振铃瓶颈；二是 **SDU Type 字段**标识帧内载荷的协议类型，使 CAN XL 帧能直接装以太网帧——区域架构里 CAN XL 网段与以太网网段的二层桥接由此成立。

仲裁段保持 1 Mbps 级并沿用 ID 优先级仲裁，CAN FD 帧与 CAN XL 帧能在同一总线共存（FD 控制器把 XL 帧识别为协议外帧并忽略，XL 控制器全网通吃）。这与 2.0/FD 的共存规则同构，但设计目标反过来：XL 不是 FD 的替代，是 FD 网络向区域主干演进时"向后兼容的桥"。

> 💡
> 选型坐标：新量产项目、带宽需求 ≤64 B/帧 → CAN FD 仍是稳态答案；区域架构预研、需要 CAN 生态与以太网二层互通 → 跟踪 CAN XL，2026 年控制器（英飞凌 TC4x、NXP S32K3 后续型号）与 Vector/PEAK 工具链正在成形，但收发器与网络设计规则尚未沉淀，预研可以、量产押注尚早。

## 功能安全通信的问题定义

安全关键控制（机器人 STO 安全转矩关断、安全限速 SLS、协作机器人的功率与力限制）对通信的要求与普通控制不同：数据**错了比不到更危险**。位置指令被干扰翻转一位，执行器照做就是事故。功能安全协议（safety protocol）的目标是在不改变底层总线的前提下，让端到端数据完整性可证明，满足 IEC 61508 / ISO 13849 的安全完整性等级（SIL2/SIL3、PL d/e）。

威胁清单是固定的：报文丢失、重复、乱序、延迟、篡改（位翻转）、错误寻址（A 的数据被 B 当成自己的）。安全协议的对策也是固定的一组：

| 威胁 | 对策 |
|:---|:---|
| 位翻转/篡改 | 安全 CRC（独立于底层 CRC 的第二层校验） |
| 丢失/重复/乱序 | 序列号（consecutive counter） |
| 延迟 | 时间戳/看门狗超时（数据过期即进入安全态） |
| 错误寻址 | 连接 ID（SADC：源与目的唯一标识） |
| 时钟不一致 | 双方各自独立超时判断，不依赖对端时钟 |

## 黑色通道：安全协议与非安全总线分层

功能安全通信的标准架构是**黑色通道（Black Channel）**：安全层把上述安全字段（安全 CRC、序列号、连接 ID）打进应用数据的安全容器（Safety PDU），整个容器作为普通数据交给下层总线传输。底层总线（EtherCAT、PROFINET、CANopen）不需要任何安全认证——它只负责"尽力送达"，完整性由安全层端到端保证。

```
 安全相关控制数据（如 STO 命令）
   │
   ▼ 安全层打包：+ 序列号 + 连接ID + 安全CRC
 Safety PDU
   │
   ▼ 黑色通道（任意总线，不做安全假设）
 EtherCAT 帧 / CANopen PDO / PROFINET RT 帧
   │
   ▼ 对端安全层解包：校验 CRC、序列号连续、超时未超
   ├── 全部通过 → 数据可用
   └── 任一失败 → 进入安全态（如触发 STO）
```

这个分层的关键推论：总线故障永远导向安全态而不是危险态——校验失败、超时、断链的默认动作是停机，不是继续运行。"失效安全（fail-safe）"的含义就是这个默认方向的选取。

## FSoE：EtherCAT 上的样本实现

FSoE（FailSafe over EtherCAT，ETG.5100）是黑色通道模式在 EtherCAT 上的实例：安全 PDO 作为普通过程数据在 EtherCAT 帧里跑，安全主站（Safety Master，通常在安全 PLC 里）与安全从站（伺服的 STO 输入端）之间维持安全连接。

工作机制要点：

- 安全连接建立时分配唯一连接 ID 与安全参数（看门狗时间、数据长度）。
- 每个周期双方交换安全 PDU：数据 + 序列号 + CRC。序列号必须逐周期递增，重复、跳号、超时一律触发安全态。
- 安全逻辑（STO、SLS、SOS 等安全功能）只由通过安全认证的对端数据驱动；普通 PDO 里的同名控制位不具备安全效力——**非安全数据驱动安全功能是功能安全审计的第一红灯**。

同类协议谱系：PROFIsafe（PROFINET）、CIP Safety（EtherNet/IP）、openSAFETY（POWERLINK）、CANopen Safety（EN 50325-5）。机制全部是黑色通道 + 上述威胁对策表，学会 FSoE 等于学会全部——差异只在封装格式。

## 工程纪律

功能安全开发与普通嵌入式开发的工作方式有本质区别，三条纪律必须提前知道：

1. **认证是体系不是零件**。FSoE 主站/从站协议栈需要安全认证（TÜV 等机构），自己写的实现不能直接用于安全回路；产品认证覆盖需求、设计、验证、变更管理全流程。
2. **安全相关部件选认证件**。安全 PLC、安全 IO、带 STO 的伺服都选带证书的产品，自研部分限制在非安全域。
3. **安全功能独立于标准控制路径**。急停/STO 的触发链路不走常规控制总线逻辑，安全回路设计从风险分析（ISO 12100 / ISO 10218 机器人）开始，不是从协议选型开始。

嵌入式工程师在非安全域内的价值位：理解安全 PDU 在总线上的形态（抓包能认出安全流量）、知道安全态转换对普通控制程序的影响（STO 触发后伺服的 PDO 行为变化）、在系统设计时把安全与非安全域的边界划清楚。

## 排障：安全通信相关现象

| 现象 | 机制解释 | 工程动作 |
|:---|:---|:---|
| 安全连接周期断链 | 安全看门狗超时，实际周期抖动超标 | 量化周期抖动（12.3/15.6 方法），安全看门狗留 ≥2× 最大抖动余量 |
| 上电后安全连接不建立 | 连接 ID / 安全参数两端不一致 | 核对安全组态文件的双方参数 |
| 安全态频繁误触发 | 序列号丢步：过程数据丢帧 | 查 WKC 与丢帧统计，先修基础通信质量 |
| 安全 PDU 数据正确但不被采信 | 抓包看到的是"数据"，安全效力看 CRC/序列号 | 用安全协议分析工具（TwinCAT Safety 诊断等）看连接状态 |
