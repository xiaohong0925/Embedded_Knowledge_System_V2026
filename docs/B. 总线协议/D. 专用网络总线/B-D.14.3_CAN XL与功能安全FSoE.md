# B-D.14.3 CAN XL 与功能安全（FSoE）

## 本节导读

D.11 讲的 CAN 2.0/CAN FD 是今天车上的现实，本节讲两件"正在发生"的事。

第一件是 CAN 家族的第三代——CAN XL，2024 年完成标准化（CiA 610-1 / ISO 11898-1:2024），控制器芯片开始量产。它要回答的问题很具体：在 D.14.1 讲的区域架构里，CAN 能不能不掉队地接住 10 Mbps 级的主干通信，同时保持与 CAN FD 生态的连续性？

第二件是功能安全通信。机器人安全功能（STO 安全转矩关断、安全限速）落地的协议基础，是"安全协议跑在非安全总线上"的通用模式。本节以 FSoE（FailSafe over EtherCAT）为样本把这个模式讲透——它与 D.11、D.12 的内容共同构成安全相关总线系统的完整图景。

> 本节覆盖：CAN FD 遗留的两个短板与 CAN XL 的补法、SIC XL 收发器的 PWM 编码机制、XL/FD/2.0 三代共存规则、CAN XL 与车载以太网的定位边界与选型坐标、功能安全通信的问题定义与威胁对策表、黑色通道分层模式、FSoE 的连接建立与周期交换机制、功能安全开发的工程纪律、安全通信排障。前半段（CAN XL）按"短板 → 机制 → 共存 → 选型"推进，后半段（功能安全）按"问题定义 → 通用模式 → 样本实现 → 工程纪律"推进——两段共享一个主题：**总线技术演进到最后，比的都不是速率，是可信度**。

## CAN XL：FD 的短板与 XL 的补法

CAN FD 把 payload 扩到 64 字节、数据段提到 8 Mbps，但两个约束还在：

1. **帧开销比例仍然高**：64 字节数据要配约 40 位的帧头帧尾（ID、控制场、CRC、ACK 等），短帧场景开销占比更糟——CAN FD 的有效吞吐量天花板远低于标称 8 Mbps。
2. **与以太网没有直接衔接**：区域架构的主干是车载以太网（D.14.1），CAN FD 网段要接主干必须走应用层网关做协议翻译，引入延迟和状态维护负担。

CAN XL 的补法逐项对应：

| 维度 | CAN FD | CAN XL |
|:---|:---|:---|
| 数据段速率 | ≤ 8 Mbps | ≤ 20 Mbps（SIC XL 收发器） |
| Payload | 64 B | 2048 B |
| 帧头开销 | 固定 40+ 位 | 精简控制场，引入 SDU Type |
| 以太网衔接 | 无 | 帧可隧道承载以太网帧（L2 互通） |
| 寻址 | 11/29 位 ID | 保留 ID 仲裁 + 新增节点寻址字段 |
| 校验 | CRC-17/21 | 双 CRC（13 位头 CRC + 32 位帧 CRC） |
| 收发器 | FD 收发器 | SIC XL 收发器（PWM 编码驱动） |

2048 字节 payload 配上精简控制场，开销占比从"短帧近半"压到个位数百分比——有效吞吐量的提升比标称速率（8→20 Mbps）的提升更实质。

算一笔效率账，假设都传 1500 字节数据（一个以太网帧的量）：

```text
CAN FD：1500 B ÷ 64 B/帧 = 24 帧
  每帧开销 ≈ 帧头帧尾 ~50 位 + 位填充 → 开销占比约 8%~15%（短帧更高）
  且每帧都要重新仲裁——总线利用率受 ID 优先级环境牵制

CAN XL：1 帧装下（2048 B 载荷）
  帧头帧尾开销 ~100 位 vs 载荷 12000 位 → 开销占比 < 1%
  一次仲裁解决，仲裁段只占全程约 5% 时间

有效吞吐粗算：XL 数据段 20 Mbps × ~95% 载荷效率
  ≈ 19 Mbps 有效——已是 CAN FD（8 Mbps × ~80%）的 3 倍
```

### CAN XL 帧结构一瞥

XL 帧的字段排布体现了"兼容"与"扩容"两条主线（对照 D.11 的 FD 帧读）：

```text
┌─────── 仲裁段（1 Mbps，与 FD 相同）───────┐┌──── 数据段（≤20 Mbps）────┐
 SOF | Priority ID(11位) | 控制场 | …… | SDT | 数据 1~2048B | FCRC | FDF尾
     └─ 沿用 ID 仲裁 ──┘        └ 13位HCRC ┘  └─ 32位帧CRC ─┘
```

- **Priority ID**：沿用 11 位 ID 做仲裁，仲裁行为与 FD 完全一致——共存规则的载体。
- **HCRC（13 位头 CRC）**：单独保护帧头。头错了整帧必须立刻丢弃，不能等 32 位帧 CRC 算完才发现——双 CRC 的第一枚是给"快速拒帧"用的。
- **SDT（SDU Type）**：8 位协议类型字段，见下节。
- **FCRC（32 位帧 CRC）**：2048 字节长帧的检错需求远超 FD 的 64 字节，CRC 从 17/21 位升到 32 位。

### 机制变化一：SIC XL 收发器与 PWM 编码

传统 CAN 收发器用显性/隐性电平驱动总线（D.11 已讲），这个驱动方式在 10 Mbps 以上撞墙：总线是个大电容负载，显性→隐性的切换靠上拉电阻被动放电，速率一高，边沿跟不上、振铃（ringing）吞掉采样窗口。

> 振铃（Ringing）：信号跳变后在线上往复振荡的现象。总线的寄生电感电容构成谐振回路，快速边沿激发振荡，幅度可能大到被误判为多次跳变。CAN 仲裁段限制在 1 Mbps 的根本原因之一就是给振铃留衰减时间。

SIC XL 收发器的解法是换驱动方式：数据段不再靠电平高低，而是用 PWM 编码——TxD 上以**占空比**区分 0/1（如 1/3 占空比为 0、2/3 为 1），收发器主动推拉两个方向，边沿可控、振铃窗口被编码周期吸收。代价是收发器复杂度上升、与旧收发器电气不兼容——这就是"XL 网段要换 SIC XL 收发器"这条硬件约束的来历。

### 机制变化二：SDU Type 与以太网隧道

> SDU Type（Service Data Unit Type，服务数据单元类型）：CAN XL 帧控制场里新增的协议类型标识字段，声明本帧载荷装的是什么协议——CAN FD 兼容载荷、以太网帧、或其他上层协议。它是 CAN XL 能当"多协议容器"用的机制基础。

SDU Type 标识为以太网时，CAN XL 帧的 2048 字节载荷直接装一个以太网帧（最长 1500 字节放得下）。区域架构由此获得一个新能力：**CAN XL 网段与以太网网段之间可以做二层桥接**——区域控制器收到 XL 帧，剥掉头，载荷就是以太网帧，直接转发上主干，不需要应用层协议翻译。CAN 生态的末端设备由此"不掉队"地接入以太网主干，这是 CAN XL 对 D.14.1 架构演进给出的 CAN 侧答案。

### 三代共存规则

仲裁段保持 1 Mbps 级并沿用 ID 优先级仲裁，所以 CAN FD 帧与 CAN XL 帧能在同一总线上共存：FD 控制器把 XL 帧识别为"协议外帧"并忽略，XL 控制器全网通吃。这与 2.0/FD 的共存规则同构（老节点忽略新帧），但设计目标反过来了——**XL 不是 FD 的替代，是 FD 网络向区域主干演进时"向后兼容的桥"**。

> 💡
> 选型坐标：新量产项目、带宽需求 ≤ 64 B/帧 → CAN FD 仍是稳态答案；区域架构预研、需要 CAN 生态与以太网二层互通 → 跟踪 CAN XL。2026 年的现实是控制器（英飞凌 TC4x、NXP S32K3 后续型号）与 Vector/PEAK 工具链正在成形，但 SIC XL 收发器供货与网络设计规则（拓扑限制、终端匹配新参数）尚未沉淀——预研可以，量产押注尚早。

## 功能安全通信的问题定义

安全关键控制（机器人 STO 安全转矩关断、安全限速 SLS、协作机器人的功率与力限制）对通信的要求与普通控制不同：数据**错了比不到更危险**。位置指令被干扰翻转一位，执行器照做就是事故；指令晚到一拍，最多性能下降。

> 功能安全（Functional Safety）：系统在故障/干扰下仍不导致人身伤害的属性，由 IEC 61508（通用）、ISO 13849（机械）等标准定义，按安全完整性分级（SIL1~3、PL a~e）。机器人行业常引用 ISO 10218（工业机器人）与 ISO/TS 15066（协作机器人）。分级的工程含义：等级越高，对"危险失效概率"的上限要求越严，对应的开发流程与硬件冗余要求越重。

功能安全协议（safety protocol）的目标是在**不改变底层总线**的前提下，让端到端数据完整性可证明。威胁清单是固定的六类，对策也是固定的一组：

| 威胁 | 后果样本 | 对策 |
|:---|:---|:---|
| 位翻转/篡改 | 位置指令 100 变 116 | 安全 CRC（独立于底层 CRC 的第二层校验） |
| 报文丢失 | 急停命令没送到 | 序列号 + 超时判安全态 |
| 报文重复 | 同一命令被执行两次 | 序列号连续性检查 |
| 报文乱序 | 新位置被旧位置覆盖 | 序列号单调性检查 |
| 延迟 | 数据过期被误用 | 时间戳/看门狗超时，过期即安全态 |
| 错误寻址 | A 轴的数据被 B 轴当成自己的 | 连接 ID（源与目的的唯一标识对） |

> 安全态（Safe State）：系统判定"当前数据不可信"后进入的预定义状态，典型动作是 STO（Safe Torque Off，安全转矩关断——切断电机转矩输出但保持控制电源）或安全停车。安全态的核心属性是**保守**：宁可误停机，不可误动作。

注意对策表里没有"重传"——安全协议不修复数据，只**检测**不可信并导向安全态。实时控制等不起重传周期，这是它与传统可靠性协议（TCP 式重传）的设计分野。

## 黑色通道：安全协议与非安全总线分层

功能安全通信的标准架构是**黑色通道（Black Channel）**：

> 黑色通道（Black Channel）：功能安全通信的分层模式。安全层把安全字段（安全 CRC、序列号、连接 ID）打进应用数据，构成安全容器（Safety PDU），整个容器作为普通数据交给下层总线传输。底层总线（EtherCAT、PROFINET、CANopen）**不需要任何安全认证**——它只负责尽力送达，完整性由安全层端到端保证。总线对安全层来说是一个"不可信的黑色管道"，所有信任都建立在端到端校验上。

```text
 安全相关控制数据（如 STO 命令）
   │
   ▼ 安全层打包：+ 序列号 + 连接ID + 安全CRC
 Safety PDU
   │
   ▼ 黑色通道（任意总线，不做安全假设）
 EtherCAT 帧 / CANopen PDO / PROFINET RT 帧
   │
   ▼ 对端安全层解包：校验 CRC、序列号连续、未超时
   ├── 全部通过 → 数据可用
   └── 任一失败 → 进入安全态（如触发 STO）
```

这个分层的关键推论有两条：

- **总线故障永远导向安全态而不是危险态**——校验失败、超时、断链的默认动作是停机，不是继续运行。"失效安全（fail-safe）"的含义就是这个默认方向的选取。
- **底层总线可以自由选型**：安全认证覆盖的是安全层协议栈与端点，中间的交换芯片、线缆、网关都在黑色通道内，不需要安全认证——这大幅降低了系统集成的认证负担。

## FSoE：EtherCAT 上的样本实现

FSoE（FailSafe over EtherCAT，ETG.5100 规范）是黑色通道模式在 EtherCAT 上的实例：安全 PDU 作为普通过程数据跑在 EtherCAT 帧里，安全主站（Safety Master，通常在安全 PLC 内）与安全从站（伺服的 STO 输入端）之间维持安全连接。

工作机制按时序展开：

```text
1. 组态阶段：安全工程工具定义连接对、分配唯一连接 ID、
   设定安全参数（看门狗时间、数据长度、CRC 多项式）
2. 建立阶段：主从两端交换参数并互验一致，连接进入"运行"态
3. 周期交换：每个总线周期双方互发安全 PDU（数据+序列号+CRC）
   序列号必须逐周期递增；重复、跳号、超时一律触发安全态
4. 失效响应：任一校验失败 → 该连接导向安全态，
   从站执行本地安全动作（如 STO 切断转矩）
```

工程上最常打交道的是看门狗时间的整定：安全看门狗必须大于"最坏通信延迟 + 抖动"，否则误触发；又不能大到延迟检测失去意义。经验整定线是 **≥ 2×（周期 + 最大抖动）**——D.12.3/E.15.6 的抖动测量方法在这里直接变成安全参数的输入。

> ⚠️
> 安全逻辑（STO、SLS、SOS 等）只允许由通过安全连接的数据驱动。普通 PDO 里同名的控制位**不具备安全效力**——"从普通过程数据里读 STO 状态位去控制安全功能"是功能安全审计的第一红灯。抓包能看到数据不代表数据有安全效力，这两者之间的鸿沟就是安全层的全部价值。

### 安全 PDU 的线上形态

抓包时认得出安全流量是非安全域工程师的基本功。FSoE 安全 PDU 的典型布局：

```text
┌─────────────────────────────────────────────┐
│ 安全数据（如 STO 命令位、安全位置） n 字节    │
│ 连接 ID（隐式或显式，标识本连接对）           │
│ 序列号（逐周期递增的计数器）                  │
│ 安全 CRC（覆盖以上全部字段）                  │
└─────────────────────────────────────────────┘
   整个容器作为普通 EtherCAT 过程数据传输
```

在 Wireshark/TwinCAT 抓包视图里，它混在普通 PDO 数据区中——肉眼无法与普通过程数据区分，这正是设计意图（总线不知道也不需要知道）。区分靠组态：安全工程工具里登记了哪些 PDO 区间是安全 PDU。诊断时如果看到"数据明明在更新但安全连接报序列号错误"，多半是组态映射错位——安全 PDU 被映射到了错误的 PDO 偏移，序列号字段读到的其实是数据字节。

### 一个威胁场景的完整推演

把六类威胁放进一个具体场景，看对策如何接力：安全主站每 4 ms 向伺服发一次"允许运行"安全 PDU。

- **总线丢了一帧**：从站序列号发现跳号 → 不采信该周期数据；看门狗计时继续走。
- **干扰翻转了一位**：安全 CRC 校验失败 → 该 PDU 直接丢弃，等效于丢帧。
- **交换机故障延迟 20 ms**：看门狗超时（整定值如 8 ms）→ 进入安全态，STO 切断转矩。
- **另一根轴的安全 PDU 错送到本从站**：连接 ID 不匹配 → 丢弃。
- ** attacker/故障节点重放上周期的帧**：序列号重复 → 丢弃。

任何单一故障都不导致危险动作；要骗过这套机制需要同时伪造正确的序列号、连接 ID 和 CRC——这就是"完整性可证明"的含义：不是绝对不可能出错，而是出错的概率被压到 SIL 等级要求的可计算上界之下。

同类协议谱系：PROFIsafe（PROFINET）、CIP Safety（EtherNet/IP）、openSAFETY（POWERLINK）、CANopen Safety（EN 50325-5）。机制全部是黑色通道 + 同一张威胁对策表，学会 FSoE 等于学会全部——差异只在封装格式与组态工具。

## 工程纪律：功能安全开发的边界

功能安全开发与普通嵌入式开发的工作方式有本质区别，三条纪律必须提前知道：

1. **认证是体系不是零件**：FSoE 主站/从站协议栈需要安全认证（TÜV 等机构），自己写的实现不能直接用于安全回路。产品认证覆盖需求、设计、验证、变更管理全流程——不只是代码本身。
2. **安全相关部件选认证件**：安全 PLC、安全 IO、带 STO 的伺服都选带证书的产品，自研部分限制在非安全域。
3. **安全功能独立于标准控制路径**：急停/STO 的触发链路不走常规控制总线逻辑。安全回路设计从风险分析（ISO 12100 / ISO 10218）开始，不是从协议选型开始——协议是风险分析结论的载体，不是起点。

嵌入式工程师在非安全域内的价值位：理解安全 PDU 在总线上的形态（抓包能认出安全流量）、知道安全态转换对普通控制程序的影响（STO 触发后伺服的 PDO 行为变化）、在系统设计时把安全与非安全域的边界划清楚。

> 💡
> 安全组态文件本身就是安全相关物项：连接 ID、看门狗时间、PDO 映射的任何改动都要走变更管理（重新评审、重新验证），改完组态文件要核对它的版本号/CRC 与两端实际加载的一致。"参数对不上"类故障（排障表第二行）的根源常常是有人改了组态没走变更流程——这在普通嵌入式项目里是小事，在安全项目里是事故隐患。

## 排障：安全通信相关现象

| 现象 | 机制解释 | 工程动作 |
|:---|:---|:---|
| 安全连接周期断链 | 安全看门狗超时，实际周期抖动超标 | 量化周期抖动（D.12.3/E.15.6 方法），看门狗按 ≥2× 余量整定 |
| 上电后安全连接不建立 | 连接 ID / 安全参数两端不一致 | 核对安全组态文件的双方参数版本 |
| 安全态频繁误触发 | 序列号丢步：过程数据丢帧 | 查 WKC 与丢帧统计，先修基础通信质量 |
| 安全 PDU 数据正确但不被采信 | 抓包看到"数据"，安全效力看 CRC/序列号/连接状态 | 用安全协议分析工具（TwinCAT Safety 诊断等）看连接状态机 |
| STO 触发后伺服行为"怪异" | 安全态下 PDO 被安全层接管，普通控制失效 | 这是设计行为；普通程序要正确处理安全态期间的控制空窗 |
| 组态下载后安全连接报参数错 | 组态版本与端点内加载版本不一致 | 比对组态文件 CRC/版本号，两端重新同步下载 |

## 本节总结

CAN XL 是 CAN 家族对区域架构的回答：2048 字节 payload 把帧开销占比压到个位数，SIC XL 收发器用 PWM 编码绕开显性/隐性驱动在 10 Mbps 以上的振铃墙，SDU Type 字段让 XL 帧直接隧道承载以太网帧——CAN 生态由此接入以太网主干而不掉队；三代共存规则保证它是"桥"而不是"替代"，2026 年仍处于预研可以、量产尚早的导入期。功能安全部分的主线是一个通用模式：威胁清单固定六类、对策固定一组（安全 CRC/序列号/看门狗/连接 ID），黑色通道分层让底层总线免于安全认证，所有校验失败的默认方向是停机——"失效安全"就是这四个字。FSoE 只是该模式在 EtherCAT 上的实例，谱系内所有安全协议同构。对嵌入式工程师的实践落点是：会认安全流量、会整定安全看门狗、守住"非安全数据不驱动安全功能"这条红线。

| 关键结论 | 一句话记忆 |
|:---|:---|
| CAN XL 补什么 | FD 的帧开销与以太网衔接两块短板 |
| SIC XL | PWM 占空比编码替代电平驱动，绕开振铃墙 |
| SDU Type | 让 XL 帧装下以太网帧，二层桥接由此成立 |
| 选型坐标 | FD 仍是量产稳态；XL 跟踪预研，2026 不押量产 |
| 威胁对策 | 六类威胁对四件武器：CRC、序列号、超时、连接 ID |
| 看门狗整定 | ≥ 2×（周期 + 最大抖动），输入来自 D.12.3/E.15.6 的抖动测量 |
| 红线 | 非安全数据不得驱动安全功能；抓包看到数据 ≠ 数据有安全效力 |
| 黑色通道 | 总线不可信，信任全在端到端；失败默认停机 |
