## 本节导读

上一节讲车载以太网怎么扛主干，这一节走到网络的另一端——末端那些便宜到不能再便宜的节点。车身里大量设备根本不需要 CAN：车窗升降、座椅调节、雨刷、氛围灯、方向盘按键——数据量小（几个字节）、速度无所谓（人的手速就是上限）、成本敏感（一辆车几十个这样的节点，每个省一块钱都是钱）。

LIN（Local Interconnect Network）就是为这类节点设计的：单线、UART 物理层、主从轮询、最高 20 kbps，节点成本压到 CAN 的几分之一。它的技术先进性接近于零，但工程价值在于它把"够用就好"四个字执行得极其彻底——理解 LIN 每一处设计为什么这样省，就是理解成本驱动设计的教科书案例。

> 本节覆盖：LIN 的物理层（单线电平、不对称上拉的设计目的）、帧结构（帧头/应答两段式及各字段作用）、调度表机制与确定性来源、LIN 与 CAN 的分工边界、休眠唤醒与自动波特率两个实用机制、Linux 下的三条接入路径、典型故障排查。按"物理层 → 帧 → 网络行为 → 选型边界 → 工程接入"的顺序展开——和你拿到一个 LIN 节点从接线到通信的动顺序一致。

机器人行业里 LIN 用得少，但"低成本单主子网"的设计思想——以及它与 CAN 的边界划分——值得每个做整机总线规划的工程师建立认知：B-E.15.4 的整机总线设计方法里，"末端用什么"这一问，LIN 是最常见的答案之一。

## 物理层：一根线上的 UART

LIN 用单根信号线（相对车身地），电平沿用 12 V 车规逻辑：

> 显性/隐性电平：总线型网络的通用术语。隐性（逻辑 1）是总线的"默认态"——没人驱动时由上拉电阻维持在高电平（LIN 里接近电池电压 VBAT）；显性（逻辑 0）是"驱动态"——任何节点把线拉到接近 0 V。**任何节点都能把总线从隐性压成显性，这个特性叫"线与"（wired-AND）**——CAN 用它做仲裁，LIN 用它做唤醒。这条总线术语在 D.11（CAN）里已经出现过，是车载总线的通用语言。

物理层本质就是一个带车规电平转换的 UART：19200 bps 以内（规范上限 20 kbps），8N1 格式。MCU 侧不需要任何专用外设——一个普通 UART 加一个 LIN 收发器芯片就是全部硬件。

```text
 主机节点                          从机节点 ×N（最多 16）
 ┌──────────┐                      ┌──────────┐
 │ UART_TX/RX│                     │ UART      │
 │ LIN 收发器│──── LIN 线 ─────────┤ LIN 收发器 │
 │（上拉 1kΩ）│                    │（上拉 30kΩ）│
 └──────────┘                      └──────────┘

 显性时任意节点可拉低总线 → 线与特性
```

注意上拉电阻的**不对称**：主机 1 kΩ（强上拉），从机 30 kΩ（弱上拉）。这不是随手选的——它定义了总线电平的"主导权"分配：主机端强上拉保证自己发的帧头边沿干净快速（帧头是全网时序基准），从机弱上拉降低自身功耗和成本，从机只在自己的应答时隙里短暂驱动总线。电气规范里这组数字是互操作的前提：你自制的节点接错上拉档位，轻则波形畸变，重则把整个子网的通信质量拖垮。

收发器芯片（TJA1021、MCP2003 等）做的事很单纯：UART 电平 ↔ LIN 车规电平的转换，加上 EMC 保护、休眠/唤醒检测。它的 datasheet 里最值得看的部分是唤醒检测的时序参数——休眠唤醒一节会用到。

## 帧结构：主机问，指定者答

LIN 帧固定两段：**主机发帧头（Header），指定节点回应答（Response）**。从机永远不允许主动发送——这是 LIN 与 CAN 仲裁制的根本区别，总线冲突在机制上不存在（不需要仲裁，因为永远只有一个发话人）。

```text
 一帧 = 帧头（主机发） + 应答（指定从机或主机自己发）

 帧头：  Break 场（≥13 位显性，唤醒注意力 + 帧起始标志）
         Sync 场（0x55，从机用它自动校准波特率）
         PID（保护标识符：6 位 ID + 2 位奇偶校验）

 应答：  数据 1~8 字节 + 校验和
         校验和两档：经典校验（仅数据，LIN 1.x）/
                    增强校验（数据+PID，LIN 2.x）
```

三个字段各藏一个设计意图：

- **Break 场**（≥13 位连续显性）：UART 数据帧最长连续显性也只有 9 位（起始位+8 个 0 数据位+...），13 位的"超长低电平"在正常数据流里不可能出现，所以它能被所有节点无歧义地识别为"新的一帧开始了"。用一个物理上不可能混淆的模式当分隔符，是最廉价的帧同步方案。
- **Sync 场**（固定字节 0x55 = 0101 0101b）：8 位里 5 个下降沿。廉价从机用内部 RC 振荡器当 UART 时钟，精度差（±10% 量级），温度一变就漂移——同步场就是发给从机的"标准尺"：从机量出 0x55 各位的实际宽度，反推出主机的真实波特率，自动校准自己的 UART 分频。这就是 LIN 从机可以省掉晶振的原因，**省掉的每颗晶振都是 BOM 表上的钱**。
- **PID**（Protected ID）：6 位标识符 + 2 位奇偶校验。校验不是摆设——PID 错了，从机应答的就是错的数据，错误校验位让接收方能发现"这帧的地址本身就坏了"，直接丢弃而不是误用。

校验和的两档用一个小算例看清楚。假设数据字节为 `0x12 0x34 0x56`（3 字节），PID 为 `0x22`：

```text
经典校验（LIN 1.x）：只对数据求和，带进位回卷
  0x12 + 0x34 + 0x56 = 0x9C → 取反 = 0x63（校验和字节）

增强校验（LIN 2.x）：数据 + PID 一起求和
  0x12 + 0x34 + 0x56 + 0x22 = 0xBE → 取反 = 0x41
  （和超过 0xFF 时把进位加回低位，即"1 的补码求和"）
```

混网时两档算法算出的字节不同——这就是排障表里"1.x/2.x 节点混网偶发校验错"的机理：帧本身没坏，是两端校验口径不一致。诊断帧（ID 0x3C/0x3D）是个例外：无论 LIN 版本一律用经典校验，排障时别把这条规则忘掉。

> 自动波特率（Autobaud）：接收方通过测量发送方发来的已知模式（LIN 用 0x55 的下降沿间隔）反推实际波特率，动态校准本地 UART 分频器的机制。它把时钟精度要求从"每个节点 ±2%"放松到"主机准就行"，是从机可以用片内 RC 振荡器省掉外部晶振的关键。串口类总线里通用，UART 的 `AT` 时代 Modems 也靠它。

### 示波器上认一帧

拿示波器（或逻辑分析仪）抓到的一帧 LIN 波形，按字段顺序认读：

```text
 电平
 高 ┐        ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌── 数据字节（UART 波形，LSB 先传）──┐
    │        │ │ │ │ │ │ │ │
 低 │ ───────┘ └─┘ └─┘ └─┘ └────────────────────────────────────┘
      Break    0x55 = 0101 0101b（LSB 先传 → 线上是 0,1,0,1,0,1,0,1）
      ≥13 位低   五个下降沿等距 → 从机量距校波特率
```

认读顺序：先找 Break（一段明显超长、超过任何正常字节的低电平）→ 紧跟的字节应该是 0x55（波形上五个等距下降沿，肉眼可认）→ 再一个字节是 PID → 之后是应答数据与校验和。逻辑分析仪配 LIN 解码插件（Sigrok/PicoScope 都内置）能直接显示字段分割，手工认读的价值在于：当解码器都认不出帧头时，你要能自己看出 Break 宽度不对。

### 版本简史：为什么"LIN 1.x / 2.x"的说法总在排障时出现

LIN 由车企联盟（LIN Consortium）在 1999 年前后发起，规范的几次关键演进直接对应今天的排障常识：

- **LIN 1.3**（2000 年代初）：早期量产版本，经典校验，配置基本靠手工约定。
- **LIN 2.0 / 2.1**（2003/2006）：引入增强校验、诊断帧（0x3C/0x3D）与节点自动配置（NAD 分配），从机开始标准化。
- **LIN 2.2A**（2010）： Consortium 最后一个版本，澄清了若干时序细节。
- **ISO 17987**（2016 起）：LIN 被 ISO 收编为国际标准（拆成 7 个部分：物理层、数据链路层、一致性测试等），内容等同 2.2A。

所以今天的车上跑的就是 2.2A/ISO 17987，"LIN 1.x 节点"只存在于老旧供应商件里——但只要混网存在，经典/增强校验的坑就一直在，这是版本史留给排障表的那一行。

## 调度表：确定性来自"一切都在表里"

LIN 网络里"什么时候谁说话"完全由主机的**调度表（Schedule Table）**决定：一张静态时间表，定义按什么顺序发哪些帧头、每帧占多少槽位时间。

> 调度表：LIN 主机内的静态发送时刻表。主机严格按表轮询——第 0~10 ms 发"车窗状态"帧头，第 10~20 ms 发"座椅位置"帧头……从机只在被点到名的时隙里应答。网络行为完全可预测：每一帧何时出现在总线上，看表就知道。

一个槽位时间的量化感受：19200 bps 下一位约 52 µs，一个典型帧（帧头约 34 位 + 8 字节应答约 90 位）线上时间约 6.5 ms，加上帧间间隔，一个槽位通常排 10 ms 量级。十条消息的调度表周期就是 100 ms——对车窗这种"人的反应速度"的应用绰绰有余，这也是为什么 LIN 不需要更快。

标准轮询之外有两个补充机制：

- **事件触发帧（Event-triggered Frame）**：多个从机共享一个应答时隙，平时无人应答（省带宽），谁状态变了谁抢答；万一两个从机同时抢答冲突，主机检测到后回退到逐个点名（切换到一个专门的"点名调度表"）查清是谁。这是"大概率没冲突就省着用，冲突了就退一步查"的带宽优化。
- **诊断帧**：保留 ID（0x3C/0x3D）承载诊断与节点配置（NAD 地址分配等），走独立的调度表项，不与业务帧抢时隙。

> NAD（Node Address for Diagnostics，诊断节点地址）：LIN 从机的诊断地址。出厂时同类节点的 NAD 往往相同，装车后由主机通过诊断帧逐一分配唯一地址——否则一条"读故障码"请求会被四个一样的车窗电机同时应答。新节点上线先配 NAD，是产线工艺的一环。

> LIN 与 CAN 的设计哲学对照：CAN 把智能放在每个节点（分布式仲裁），LIN 把智能集中在主机（调度表）。前者灵活、抗单点故障；后者便宜、行为完全可预测，但主机一死全子网瘫痪。总线选型里"集中 vs 分布"这条轴线，LIN 和 CAN 是两端的教科书样本——B-E.15.4 整机总线设计里遇到"末端子网要不要用主从轮询"的问题时，回想这个对照。

量产工作流里，调度表不是手工排的。OEM 以 **LDF（LIN Description File）** 发布整个子网的定义——节点清单、信号布局、帧 ID、周期、调度表全在这份文本文件里；主机侧工具链（Vector 的 LIN 工具、AUTOSAR 配置器）从 LDF 直接生成主机调度代码，从机供应商也照同一份 LDF 实现。**排查"按文档该通却不通"的问题时，第一件事是核对双方是否在用同一版本的 LDF**——版本不一致是 LIN 集成故障的隐蔽来源。

## 为什么不直接用 UART 或 RS-485

一个自然疑问：LIN 物理层就是 UART，那直接拉 UART 点对点、或者用工控常用的 RS-485 不就行了？三者的差异恰好在车载需求上：

| 维度 | 裸 UART | RS-485 | LIN |
|:---|:---|:---|:---|
| 拓扑 | 点对点 | 多节点总线 | 多节点总线（≤16） |
| 线数 | 2（TX/RX） | 2（差分） | **1** |
| 协议层 | 无（自定义） | 无（自定义，常用 Modbus） | 完整标准（帧/调度/休眠/诊断） |
| 节点寻址与冲突 | 需自定义 | 需自定义（Modbus 主从轮询） | 标准内建 |
| 休眠唤醒 | 无标准 | 无标准 | 标准内建（车规必需） |
| 车规生态 | 无 | 工业生态 | 车规收发器/LDF/AUTOSAR 全配套 |

结论：LIN 卖的不是技术先进性，是**一整套开箱即用的车规标准**——帧格式、调度、休眠、诊断、配置、文件交换格式（LDF）全都定义好了，整车厂和几十家供应商靠它互操作。自定义 RS-485 方案省下的协议成本，会在跨供应商联调时十倍奉还。

## 休眠与唤醒：车身网络的省电日常

车身网络有个独特需求：车熄火停放后，大量节点必须进入微安级休眠，否则几天就把电瓶放光；而任一节点有动作（比如用户拉车门把手）又要能唤醒整个子网。

LIN 的机制依赖那条"线与"特性：任何节点（包括从机）把总线拉成显性并维持 250 µs~5 ms，就是一个全网可识别的唤醒信号——唤醒不需要主机批准，因为"线与"保证了谁都能拉低总线。主机检测到唤醒后重启调度表，各从机的收发器收到唤醒沿后给 MCU 上电/出复位。对端流程是休眠：总线空闲超过规定时长（规范为 4~10 s 量级的超时），节点自行进入休眠。

排障表里"休眠唤不醒"是车身电子的高频故障，示波器量唤醒脉冲宽度（是否落在 250 µs~5 ms 窗口内）是第一动作。

> 💡
> 休眠电流是验收项：整车静态电流预算通常以毫安计，分摊到每个 LIN 节点只剩几十微安。开发期实测节点休眠电流（串联微安表在收发器供电脚）应纳入例行检查——一个没进休眠的节点能在停车场里把整车电瓶耗光，而且故障现象（亏电）与根因（某个节点的固件没处理休眠超时）相隔十万八千里，排查极其耗时。

## LIN 与 CAN 的分工

| 维度 | LIN | CAN / CAN FD |
|:---|:---|:---|
| 速率 | ≤ 20 kbps | 1 M / 8 Mbps |
| 线数 | 1 | 2（差分） |
| 节点成本 | 极低（UART + 便宜收发器，省晶振） | 中（控制器 + 收发器 + 精密时钟） |
| 节点数 | ≤ 16 | ~110（电气限制） |
| 冲突机制 | 无（主机轮询） | 非破坏仲裁 |
| 实时性 | 由调度表保证（静态可预测） | 由优先级仲裁保证（动态可预测） |
| 失效模式 | 主机失效 = 全子网瘫痪 | 单节点失效不影响总线 |
| 典型节点 | 车窗、座椅、雨刷、灯光、空调面板 | 动力、底盘、安全、诊断主干 |

分工规则一句话：**安全相关、跨域通信、诊断主干一律 CAN；单功能执行器、人机界面小件用 LIN**。一辆车里 LIN 子网通常有十条以上（车门一个、车顶一个、座椅一个……），各由车身域控制器或对应 ECU 当主机——回看 D.14.1 的架构图，LIN 就是挂在"区域控制器"或"车身 ECU"下面那些最末端的细线。

## Linux 下的 LIN 接入

Linux 没有原生 LIN 子系统（曾有主线化提案但未落地），工程上三条路：

1. **UART + 外部 LIN 收发器**：LIN 帧就是 UART 字节流，用 tty 直接收发。帧头里 Break 场的产生依赖 UART 的 break 控制（`TIOCSBRK` ioctl，或用"临时降波特率发 0x00"的技巧模拟长低电平）。适合主机角色的简单实现和诊断工具，时序精度一般（受 tty 层调度影响）。

   一个最小可用的"发帧头"片段（诊断工具场景）：

   ```c
   int fd = open("/dev/ttyS1", O_RDWR);
   struct termios tio;
   tcgetattr(fd, &tio);
   cfsetispeed(&tio, B19200);
   cfsetospeed(&tio, B19200);
   tio.c_cflag |= CLOCAL | CREAD;
   tio.c_iflag = 0;                         /* 关掉输入加工，原样读字节 */
   tio.c_lflag = 0;                         /* 关规范模式 */
   tio.c_oflag = 0;
   tio.c_cc[VMIN] = 0;  tio.c_cc[VTIME] = 5;  /* 读超时 0.5 s */
   tcsetattr(fd, TCSANOW, &tio);

   /* Break 场：拉低总线 ≥13 位时间（19200 bps 下约 680 µs），给足余量 */
   ioctl(fd, TIOCSBRK, 0);                  /* 开始 break（持续拉低） */
   usleep(1000);                            /* 1 ms > 680 µs 下限 */
   ioctl(fd, TIOCCBRK, 0);                  /* 结束 break */

   uint8_t header[2] = { 0x55, 0x22 };      /* Sync 场 + PID */
   write(fd, header, 2);

   uint8_t resp[9];                         /* 应答：最多 8 数据 + 1 校验 */
   int n = read(fd, resp, sizeof(resp));    /* VTIME 超时内等从机应答 */
   ```

   三个关键动作：`TIOCSBRK`/`TIOCCBRK` 包住 `usleep` 手工构造 Break 宽度；`0x55` 紧跟其后充当 Sync；发完 PID 转为读等待应答。**这套代码只适合做诊断工具和原型验证**——`usleep` 的调度抖动在毫秒级，业务调度表别这么跑。

2. **USB-LIN 适配器**：PEAK、Vector 等厂商的分析工具走 USB 接入，应用层用厂商 API 或 slcan 风格接口。开发和售后诊断场景的主流。抓包分析时这类工具通常直接按 LDF 做信号级解码，比手工解析字节流效率高得多。

3. **MCU 协处理**：实时性敏感的主机调度表放 MCU 上跑（调度表槽位精度是毫秒级要求，Linux 用户态的调度抖动难以稳定保证），Linux 通过 SPI/UART 与 MCU 交换数据。量产车身控制器的主流形态——Linux 管业务逻辑与人机界面，MCU 管总线时序，职责划分与 15.1 机械臂的"ROS 在上、实时控制在下"是同一种分层思想。

多数嵌入式工程师与 LIN 的交集是第二条或第三条——理解协议帧格式足够你做网关转发（LIN ↔ CAN ↔ 以太网的区域控制器就是干这个的）和诊断分析，不必在 Linux 里自己实现调度表。

## 排障：LIN 常见故障

| 症状 | 优先怀疑 | 验证方法 |
|:---|:---|:---|
| 从机全部无应答 | 主机 Break/Sync 场时序不对；上拉电阻档位错 | 示波器看 Break ≥13 位显性、Sync=0x55 波形 |
| 单个从机不应答 | PID 分配错；从机 NAD（节点地址）未配置 | 换已知好的从机交叉验证；诊断帧读 NAD |
| 偶发校验错 | 经典/增强校验混用（LIN 1.x 与 2.x 节点混网） | 核对各节点 LIN 版本与校验类型配置 |
| 波特率漂移丢帧 | 从机 RC 振荡器精度差，自动波特率未使能 | 查从机 Sync 场校准是否开启；全温范围复测 |
| 休眠唤不醒 | 唤醒脉冲宽度不合规（需显性 250 µs~5 ms） | 示波器量唤醒脉冲宽度 |
| 波形边沿缓慢、通信距离短 | 总线电容超限（线太长/节点太多）或上拉错误 | 示波器看上升沿；核对节点数与线长预算 |
| 总线卡死在显性 | 某节点收发器损坏持续拉低 | 逐个断开节点定位；检查收发器供电 |

## 本节总结

LIN 是成本驱动设计的极端样本：单线省一对差分线、UART 物理层省专用控制器、自动波特率省从机晶振、主从轮询省仲裁逻辑——每一处"省"都对应一个明确的机制补偿（Break 场做帧同步、Sync 场当时钟尺、调度表保证确定性）。它的确定性不靠仲裁赢来，靠"一切都在调度表里"得来；代价是主机单点失效全子网瘫痪，所以安全相关通信永远轮不到它。工程接入上，Linux 没有原生 LIN 子系统，诊断靠 USB 适配器，量产靠 MCU 协处理跑调度表——嵌入式工程师需要做到的是看懂帧、选对边界、查得了故障，而不是在 Linux 里重造一个 LIN 主机。

| 关键结论 | 一句话记忆 |
|:---|:---|
| 定位 | 末端低成本子网：车窗/座椅/雨刷/灯光，≤20 kbps 够用 |
| 物理层 | 单线 UART + 不对称上拉（主机 1kΩ 强、从机 30kΩ 弱） |
| 帧 | 主机发帧头（Break/Sync/PID），指定者回应答；从机永不主动发 |
| 确定性 | 来自静态调度表，不是仲裁；主机是单点 |
| 省电机制 | 自动波特率省晶振；线与特性支撑任意节点唤醒 |
| 与 CAN 分工 | 安全/跨域/诊断归 CAN，单功能小件归 LIN |
