# B-D.14.1 车载以太网与 TSN

> 所属章节：第五部 B. 总线协议 > D. 专用网络总线
>
> 难度：[I] | 预计阅读时间：50 分钟

## 本节导读

汽车电子架构正在从"几十个 ECU 各自挂 CAN"转向"少数几个域控制器 + 车载以太网主干"。驱动力只有一个：数据量。激光雷达点云、多路摄像头、OTA 固件包，随便哪一项都能把 CAN FD 的 8 Mbps 压垮——后面有定量算式。

但车规环境给以太网提了两个商用以太网从没遇到过的问题。第一，线束是车上最贵最重的部件之一，传统以太网 4 对双绞线太奢侈，必须压缩到 1 对；第二，车上的控制流量（刹车、转向指令）和娱乐流量（后排屏幕的视频）跑在同一张网上，控制流量绝不能被挤占——以太网"尽力而为"的本性必须改造。前者的答案是 100BASE-T1/1000BASE-T1 物理层，后者的答案是 TSN（时间敏感网络）。

> 本节覆盖：车载以太网的需求驱动力（带量化）、它相对商用以太网的物理层差异及单对线全双工原理、电子架构的三代演进（分布式→域→中央计算）及 CAN 在各阶段的位置、TSN 子标准族各自解决的确定性问题、SOME/IP 与 DoIP 应用层协议、Linux 侧的完整支持链（PHY 驱动/gPTP/tc 整形）、车载以太网项目的排障要点。按"为什么需要 → 物理层怎么实现 → 架构怎么演进 → 实时性怎么保证 → 应用层跑什么 → Linux 怎么落地"的顺序展开——这正是你在车载项目上从理解需求到动手调试的接触顺序。

本节与 D.12（工业以太网）是平行篇：TSN 是两个行业共用的底座，车载把它当标配直接上量，工业是渐进改造。读完本节再读 12.1 的 CC-Link IE TSN，会发现概念框架完全相通。

## 为什么汽车需要以太网：先算带宽账

> ECU（Electronic Control Unit，电子控制单元）：车上的嵌入式控制计算机，一个 ECU 负责一类功能（发动机管理、车窗、空调……）。传统燃油车有 30~70 个 ECU，新能源车更多。ECU 之间主要靠 CAN/LIN 互联，这是 D.11/D.14.2 的世界。

分布式 ECU 架构在数据量小的年代运转良好。但自动驾驶和智能座舱把传感器带宽拉到了 CAN 完全无法承受的量级：

| 数据源 | 原始数据带宽量级 | 说明 |
|:---|:---|:---|
| 一路 1080p30 未压缩摄像头 | 约 1.5 Gbps | 1920×1080×24bit×30fps ≈ 1.49 Gbps |
| 一路车载激光雷达 | 几十~几百 Mbps | 点云已结构化，低于原始图像 |
| OTA 固件包 | 越大越好 | 整车包可达数 GB，刷写时间=带宽 |
| CAN FD 总线 | 最高 8 Mbps | D.11 的主干，差三个数量级 |

压缩能救回一部分（H.264 把摄像头压到几 Mbps），但环视 6~8 路摄像头加雷达加地图更新，主干带宽需求仍然轻松超过 100 Mbps——CAN FD 连零头都不够。结论只有一个：主干必须换以太网。CAN 不会消失，它退到末端执行器（便宜、够用、确定性天然好），这个分工在架构演进一节展开。

## 物理层：1 对双绞线上的全双工

商用以太网 1000BASE-T 用 4 对双绞线。车规把线砍到 1 对，这就是 T1 后缀的含义：

| 维度 | 商用以太网（1000BASE-T） | 车载以太网（1000BASE-T1） |
|:---|:---|:---|
| 线缆 | 4 对双绞线 | **1 对**双绞线（T1 = single Twisted pair） |
| 重量/成本 | 高 | 低——整车线束减重以公斤计，一米都是成本 |
| EMC 要求 | 办公环境标准 | 车规 EMC（发动机舱级，点火脉冲/大电流切换的干扰场） |
| 确定性 | 无保证 | TSN 保证（后文展开） |
| 温度范围 | 商业级（0~70 °C） | 车规（−40~+105 °C，机舱件 +125 °C） |
| 连接器 | RJ45 | 车规专用（H-MTD、MATEnet 等，带锁扣抗震） |

> EMC（Electromagnetic Compatibility，电磁兼容）：设备在电磁环境中既不被干扰也不干扰别人的能力。车载是 EMC 最严苛的民用场景之一——发动机点火、电机大电流 PWM 切换都是强干扰源，而车身控制又要求零失误。单对双绞线 + 车规连接器的屏蔽/绞距设计都是围绕 EMC 做的。

1 对线怎么做到全双工？两端在同一对线上同时收发，各自收到的都是自己信号与对方信号的叠加——只要本地精确地减去自己发出的那部分（回声消除），剩下的就是对方的信号。

> 回声消除（Echo Cancellation）：单对线全双工的核心技术。发送方已知自己发出的波形，用自适应滤波器实时估计这路信号在线缆/连接器上产生的回声与畸变，从接收到的混合信号中减掉它，恢复出对方信号。电话免提不啸叫用的也是这个思想。它的代价是 PHY 芯片复杂度——车载 PHY 里的 DSP 算力主要花在这里。

标准演进线：博通的私有规范 BroadR-Reach 被 OPEN Alliance（One-Pair EtherNet，车企+芯片商的产业联盟）采纳，随后标准化为 IEEE 802.3bw（100BASE-T1，2015）与 802.3bp（1000BASE-T1，2016）。10GBASE-T1（802.3ch，2020）也已落地，面向自动驾驶域内主干。

PHY 芯片选型集中在三家：Marvell 88Q 系列、NXP TJA1100/1101/1103、TI DP83TC 系列。Linux 侧它们是标准 PHY 驱动（主线已收录），由 phylink 框架接管；MAC 侧就是 SoC 的普通千兆 MAC。**对驱动开发者来说，车载以太网的可见差异基本只有 PHY 配置**——最重要的一个配置项是主从角色：

> T1 主从角色（Master/Slave）：单对线上的两端必须一个 Master 一个 Slave，由 PHY 的 strap 电阻或寄存器配置决定。角色决定时钟与训练序列的发起方。两端角色相同是 T1 链路不通的第一检查项——这个角色问题在 4 对线的商用以太网里不存在，是从商用以太网转车载的工程师最常踩的坑。

## 架构演进：分布式 → 域 → 中央计算

```text
 分布式架构（过去）              域架构（现在）               中央计算（趋势）
 ┌────┐ ┌────┐ ┌────┐        ┌──────────┐               ┌──────────────┐
 │ECU1│ │ECU2│ │ECU3│ …×70   │动力域控制器│              │  中央计算平台  │
 └─┬──┘ └─┬──┘ └─┬──┘        │座舱域控制器│   车载以太网   │  (HPC)        │
   └──────┴──────┘ CAN       │底盘域控制器│ ════════════ │              │
        CAN/LIN 低速网        └────┬─────┘    主干        └───┬──────┬───┘
                                 │                          │      │
                            各域内 CAN/CAN FD           区域控制器  区域控制器
                            （域内不变）                  （挂 CAN/LIN 端点）
```

三代架构各自的逻辑：

- **分布式**：一个功能一个 ECU，ECU 数量随功能膨胀到 70+，线束长达数公里，跨 ECU 的功能（如自适应巡航）要靠 CAN 消息广播协调，软件分布在几十颗 MCU 上，升级困难。
- **域架构**：按功能域（动力/底盘/座舱/车身/智驾）各设一个域控制器，吞并域内 ECU 的功能；域间与主干上车载以太网，域内末端仍是 CAN/CAN FD。这是当前量产车的主流形态。
- **中央计算**：一个高性能计算平台（HPC）承担主要算力，车身按物理位置分几个区域控制器（Zone Controller），就近接入传感器/执行器——**线束按物理位置而不是按功能布线**，长度大幅缩短；区域控制器与 HPC 之间跑千兆/万兆车载以太网，末端挂 CAN/LIN。这是特斯拉、新势力与新一代传统车企平台的演进方向。

> 区域控制器（Zone Controller）：中央计算架构里按车身物理区域（左前/右后等）划分的汇聚节点。它不实现业务功能，只做三件事：就近接入末端传感器执行器、协议汇聚（CAN/LIN/以太网互转）、配电管理。它存在的全部理由是缩短线束——末端设备到区域控制器的线只要几米，主干高速网才跨车身。

注意贯穿三代的常量：**CAN/LIN 在每一代里都没消失，只是位置从主干退到末端**。末端执行器（车窗电机、温度传感器）的数据量小、实时性要求高、成本敏感，CAN FD 在这个位置几乎无可替代。D.11 的知识在车里全程有效，变的只是主干。

## TSN：给以太网装上时刻表

普通以太网是"尽力而为"：拥塞时帧在交换机里排队，延迟不可预测。娱乐流量排队无所谓，刹车指令排队是要命的。TSN（Time-Sensitive Networking，时间敏感网络）就是 IEEE 802.1 为解决这个问题定义的一组子标准——它不是单一协议，每个子标准解决一个确定性问题：

| 子标准 | 名称 | 解决的问题 | 机制要点 |
|:---|:---|:---|:---|
| 802.1AS | 时间同步（gPTP） | 全网没有共享时间基准 | PTP 的以太网定制版，µs~ns 级同步 |
| 802.1Qbv | 时间感知整形（TAS） | 实时帧被前面的大帧阻塞 | 每队列配时间门：实时窗口内只放行实时队列 |
| 802.1Qbu / 802.3br | 帧抢占 | 正在发送的大帧堵住等待的实时帧 | 允许打断大帧，先发实时帧再续传 |
| 802.1Qav | 信用整形（CBS） | 音视频流量的突发与带宽平滑 | 按信用值限速，削平突发 |
| 802.1CB | 帧复制与消除 | 安全关键帧丢包 | 双路径冗余发送，接收端去重 |
| 802.1Qci | 流过滤与监管 | 故障节点刷屏拖垮全网 | 入口按流限速/丢弃 |

挑影响最大的三个展开。

### 802.1AS：一切的时间地基

时间门调度、帧抢占时序、跨域的事件时间戳，全都建立在"全网设备共享同一个时钟"之上。

> gPTP（generalized PTP，802.1AS 定义的时间同步协议）：PTP（IEEE 1588）针对以太网的定制版。选出一个 Grandmaster（主时钟），通过 Sync/Follow_Up 报文向下游分发时间；相邻设备间用 Peer Delay 机制逐跳测量链路延迟并补偿。与通用 PTP 的主要差异：要求全网设备（包括每台交换机）都支持 802.1AS，逐跳补偿——这正是"gPTP 不同步"排障时"链路上有非 TSN 交换机"是首查项的原因。

同步的报文交换流程（每对相邻设备之间周期进行）：

```text
 发起方                                   响应方
    │ ─── Pdelay_Req（t1 时刻发出）──────▶ │
    │ ◀── Pdelay_Resp（t2 收到 / t3 发出）─ │
    │ ◀── Pdelay_Resp_Follow_Up ────────── │
    │   链路延迟 = [(t4−t1) − (t3−t2)] / 2    （假设双向对称）
    │
    │ ◀── Sync + Follow_Up ────────────── │  Grandmaster 方向逐跳分发
    │   本地时钟 = 主时钟时间 + 各跳延迟补偿之和
```

Peer Delay 测量把每一跳的链路延迟单独算出来：(t4−t1) 是往返总时间，减去对方的处理时间 (t3−t2)，除以 2 得单向延迟；同步报文经过每台支持 802.1AS 的交换机时，驻留时间被累加进修正字段——这样即使报文在交换机里排队，时间信息也不失真。全网收敛后任意两节点的时钟偏差可压到百纳秒量级，这是 Qbv 全链路对齐开门的前提。

### 802.1Qbv：时间感知整形器（TAS）

Qbv 给交换机每个出端口的每个队列装一个"时刻表"（Gate Control List）：什么时刻开哪个队列的门，只放行对应流量。

> 整形器（Shaper）：网络设备上控制流量发送节奏的机制。Qav 的信用整形按"带宽额度"放行（有信用才能发）；Qbv 的时间门按"时刻表"放行（轮到你的窗口才能发）。后者确定性强得多——实时队列的窗口是独占的。

时间门让实时帧的最坏延迟变成**可计算的定值**：实时窗口按周期开门，窗口内只有实时流量，路径上每台交换机的等待上界都能算出来，全链路累加就是端到端最坏延迟。从"延迟不可预测"到"延迟可证明"，这就是 TSN 对车载控制流量的全部意义。

一个可计算的实例：实时流周期 250 µs，路径上经过 3 台 TSN 交换机，每台为该流开的窗口宽度 30 µs，帧长 256 字节（千兆线上约 2 µs）。逐段累加最坏情况：

```text
发送端排队：     最坏等一个周期 = 250 µs（刚好错过本次窗口）
每跳交换机：     窗口内即转发 ≈ 帧长 2 µs + 内部处理 ≈ 5 µs/跳 × 3 跳 = 15 µs
链路传播：       车载线束总长 < 15 m，光速传播 ≈ 0.1 µs，可忽略
─────────────────────────────────────────
端到端最坏延迟 ≈ 265 µs——可证明的上界，写进系统设计文档
```

对比无 TSN 的普通以太网：同样的拓扑，一个 1500 字节大帧排在实时帧前面，单跳就多堵 12 µs 且不可预测何时发生，拥塞时排队深度无界——"最坏延迟"根本不存在，只有"统计上不太糟"。这就是"可证明"三个字的分量：功能安全论证（D.14.3 的 FSoE 语境）需要的是上界证明，不是统计安慰。

时间门有一个配合机制：保护带（guard band）。实时窗口开门前，要提前一段"禁发期"防止一个刚开头的大帧跨过开门时刻堵住窗口——这正是 Qbu 帧抢占要优化的浪费。

### 802.1Qbu / 802.3br：帧抢占

保护带的长度要按最大帧长预留（1500 字节约 12 µs），这段时间什么也发不了。帧抢允许把正在发送的普通帧**打断**，先发实时帧，完了再续传被打断的帧——保护带从"最大帧长"缩到"最小帧片段长"（约 123 字节），窗口利用率显著提高。被打断的帧以片段形式传输，接收端重组；eMAC（express MAC）/pMAC（preemptable MAC）的双 MAC 结构就是 802.3br 在 PHY 之上做的支撑。

### 车载与工业的用法差异

同一套 TSN 子标准，两个行业的落地节奏不同：车载把 TSN 当底座直接上量（新一代平台普遍要求 802.1AS + Qbv 起步）；工业是存量改造，渐进引入（12.1 的 CC-Link IE TSN、PROFINET over TSN 都是这条路线）。学通一套机制，两个行业通用。

## 应用层：SOME/IP 与 DoIP

物理层和 TSN 之上，车载有两套必须知道的应用协议：

> SOME/IP（Scalable service-Oriented MiddlewarE over IP）：AUTOSAR 定义的车载面向服务通信协议。把功能抽象成"服务"（如"车速服务"），提供者发布、订阅者消费，支持 RPC（请求-响应）与事件通知（发布-订阅）两种模式。配套的 SOME/IP-SD（Service Discovery）让节点上线即被全网发现，不需要静态配置。座舱域、智驾域内部的高带宽进程间通信大量用它。

> DoIP（Diagnostics over IP，ISO 13400）：把 UDS 诊断协议（ISO 14229，D.14.3 的功能安全语境里还会出现）从 CAN 搬到以太网上。诊断仪经 DoIP 直连整车，读写故障码、刷写固件。CAN 诊断刷一个大固件包要数小时，DoIP 把它压到分钟级——OTA 时代诊断带宽就是刷机速度。

> AUTOSAR（AUTomotive Open System ARchitecture）：汽车行业的基础软件标准联盟，定义 ECU 软件的分层架构与组件接口。分 Classic（MCU 上，经典控制功能）与 Adaptive（高性能 SoC 上，Linux/QNX 环境，SOME/IP 就在这里定义）两个平台。车载软件岗位的岗位描述里"熟悉 AUTOSAR"几乎是标配要求。

一次 SOME/IP 服务调用的完整生命周期，可以对照理解它的设计：

```text
1. 提供者启动 → SOME/IP-SD 组播 OfferService（服务 ID + 实例 + 端点）
2. 订阅者启动 → SD 组播 FindService；收到 Offer 即知端点
3. 订阅        → SubscribeEventgroup，提供者确认后开始推事件
4. 调用        → Request/Response（RPC）或持续 Notification（事件流）
5. 下线        → StopOfferService，订阅者超时剔除
```

这套"上线即发现"的机制让车载域内拓扑可以动态扩展（售后加装设备、冗余节点切换），与 IT 领域的 gRPC + 服务注册中心是同一思想的车规实现。报文头里的 Service ID / Method ID / Client ID 三元组是抓包分析的定位钥匙——车载以太网抓包（Wireshark 有 SOME/IP 解析器）先看这三个字段。

与 OPC UA（D.12.4）的关系：SOME/IP 是车规强实时服务通信，OPC UA 是工厂语义互操作——同一层问题在不同行业的形态。读懂一个，另一个的概念框架直接平移。

## Linux 侧支持链

车载以太网在 Linux 上的落地是完整的，逐层看：

**PHY/MAC 层**：TJA110x、88Q、DP83TCxx 等 PHY 驱动主线已收录，设备树里一个 `phy` 节点的事：

```dts
&mac0 {
    phy-mode = "sgmii";
    phy-handle = <&tja1103>;
};
/* MDIO 总线上 */
tja1103: ethernet-phy@18 {
    compatible = "ethernet-phy-id0007.bbb0";  /* 具体 ID 查数据手册 */
    reg = <0x18>;
    /* master/slave 角色通常在 strap 电阻上定，寄存器可查 */
};
```

`ethtool eth0` 输出里识别 T1 PHY 的典型特征：`Supported link modes: 1000baseT1/Full`、`Port: Twisted Pair`——看到 `baseT1` 字样就知道是单对线 PHY。主从角色可用 `ethtool` 的 PHY 私有寄存器接口或厂商工具确认，两端角色相反才能 link。

**时间同步**：linuxptp（`ptp4l`）支持 802.1AS gPTP 配置档。`ptp4l` 运行时的日志里关注 `master offset`（与主时钟的偏差，收敛后应在几十 ns 量级）与 `path delay`——offset 长期收敛不下去，就是链路上有不支持 802.1AS 的设备在引入未补偿延迟。

**流量整形**：内核 mqprio/taprio qdisc 分别对应队列映射与 Qbv 时间门，用 `tc` 配置；TSN 网卡（Intel I210/I225/I226）有硬件 offload，时间门在网卡硬件里执行，不占用 CPU：

```bash
# taprio（Qbv 时间门）配置示例：每 250 µs 一个周期，
# 前 100 µs 开队列 1（实时），后 150 µs 开队列 0（普通）
tc qdisc replace dev eth0 parent root handle 100 taprio \
    num_tc 2 map 1 0 queues 1@0 1@1 \
    base-time 0 sched-entry S 02 100000 sched-entry S 01 150000 \
    flags 0x2
```

逐参数解读：`num_tc 2` 两个流量类别；`map 1 0` 优先级到类别的映射；`base-time 0` 时刻表起点（实际项目里应填与 gPTP 对齐的绝对时间，全端口时刻表才能同步开门）；`sched-entry S 02 100000` 是门控条目——`S` 是 SetGateStates 命令，`02` 是十六进制门位图（队列 1 开门），`100000` 是该窗口持续 100000 ns；`flags 0x2` 启用硬件 offload。

> ⚠️
> taprio 只配了发送端主站的出口是不够的——实时帧路径上**每台交换机的每个出端口**都要配置对齐的时间门，全链路用同一个 gPTP 时间基准。只配一端是"TSN 配了但没效果"的最常见形态。

**帧抢占、CB 冗余**：内核与驱动支持在演进中，落地以 SoC/交换芯片厂商 BSP 为准——做车载项目选型时，把"802.1Qbu/CB 的 BSP 支持状态"列进芯片评估清单。

## 排障与认知误区

| 误区/症状 | 事实与处置 |
|:---|:---|
| 以为车载以太网要换特殊 MAC | 不需要。特殊的是 PHY（单对线）与交换机（TSN）；SoC 侧标准 MAC |
| T1 链路不通 | 第一查主从角色：两端必须一 Master 一 Slave（strap/寄存器定）；第二查线束——T1 对线缆绞距与连接器阻抗敏感，普通网线不行 |
| T1 链路通了但丢包/误码 | 车规 EMC 不达标：查线束屏蔽层接地、连接器是否车规件；`ethtool -S` 看 PHY 误码计数 |
| gPTP 不同步（offset 不收敛） | 链路有非 TSN 交换机，透传延迟未补偿；确认全网设备 802.1AS 能力，逐跳排查 |
| 实时帧仍被挤 | taprio 只配了主站出口；路径上每台交换机每个端口都要配，且时刻表要对齐同一 gPTP 基准 |
| 以为 TSN 替代 CAN | 分层关系：TSN 以太网是主干，CAN/LIN 守末端执行器，长期共存——见架构演进节 |
| 把 SOME/IP 当通用 RPC 用到车控硬实时链路 | SOME/IP 跑在 UDP/TCP 之上，本身不带实时保证；硬实时靠 TSN 底层，SOME/IP 服务的是座舱/智驾的软实时通信 |

## 本节总结

车载以太网是被传感器带宽逼出来的架构变革：一路未压缩摄像头就接近 1.5 Gbps，CAN FD 的 8 Mbps 差三个数量级，主干只能换以太网。车规化改造集中在两处——物理层用回声消除在 1 对双绞线上跑全双工（T1），确定性用 TSN 子标准族补齐（gPTP 统一时间、Qbv 时间门让最坏延迟可计算、Qbu 帧抢占提高窗口利用率）。架构演进沿"分布式→域→中央计算"推进，CAN/LIN 没有消失，而是退守末端执行器；SOME/IP 和 DoIP 则分别承载车内的服务通信与诊断刷写。Linux 侧支持链完整：PHY 驱动主线收录、linuxptp 支持 gPTP、taprio 提供时间门硬件 offload——工程上要记住的核心纪律是 TSN 必须全链路逐端口配置，只配一端等于没配。

| 关键结论 | 一句话记忆 |
|:---|:---|
| 驱动力 | 传感器带宽超 CAN FD 三个数量级，主干必换以太网 |
| T1 物理层 | 1 对线全双工靠回声消除；链路不通第一查主从角色 |
| 架构演进 | 分布式→域→中央；CAN 退守末端，不消失 |
| TSN | AS 统时间、Qbv 定上界、Qbu 提利用率、CB 做冗余 |
| 应用层 | SOME/IP 管服务通信，DoIP 管诊断刷写 |
| 工程纪律 | TSN 全链路逐端口配置，共用同一 gPTP 时间基准 |
