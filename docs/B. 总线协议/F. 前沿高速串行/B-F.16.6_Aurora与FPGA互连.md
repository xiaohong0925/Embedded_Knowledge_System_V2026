# B-F.16.6 Aurora 与 FPGA 互连

> 所属章节：第五部 B. 总线协议 > F. 前沿高速串行
>
> 难度：[M] | 预计阅读时间：45 分钟

## 本节导读

前面几篇讲的 SerDes 协议（PCIe、JESD204C、USB4）都有完整的标准组织和沉重的协议栈。但 FPGA 世界里还有一类完全不同的需求：两块 FPGA 之间、FPGA 与自定义板卡之间，只想**简单、低开销、低延迟地搬数据**——不需要枚举、不需要命令队列、不需要操作系统。AMD（Xilinx）的 Aurora 就是为这个场景设计的轻量级链路层协议，大概是 SerDes 世界里"最小可用"的协议实现。

嵌入式工程师遇到 Aurora 的典型场景：高速数据采集系统（FPGA 采集后灌给另一片做处理）、雷达/声呐前端互联、自定义背板链路，以及 Zynq/MPSoC 这类 SoC+FPGA 器件上"PL 侧数据进 Linux"的最后一公里。

> 本节覆盖：Aurora 在 SerDes 协议谱系里的定位（与 PCIe/JESD204C 的轻重对比）、8B/10B 与 64B/66B 两个版本的差异、帧定界与时钟补偿等核心机制、通道绑定（多 lane 对齐）、Vivado IP 核配置与回环验证三板斧、PL→PS 数据进 Linux 的完整路径、选型边界与跨厂商风险。按"定位 → 协议机制 → 工具链实战 → 系统整合 → 选型"展开——这正是一个 Aurora 项目从方案评估到上板调试的顺序。

先修：B-F.16.1 SerDes 通识（均衡、眼图）；B-F.16.4 JESD204C 可对照阅读。

## 定位：协议栈的"极简主义"

对比最能说明问题：

| 维度 | PCIe | JESD204C | Aurora |
|------|------|----------|--------|
| 设计目标 | 通用计算互联 | 转换器专用 | 点对点搬数据 |
| 协议层数 | 事务/数据链路/物理三层 | 链路/传输两层 | **一层链路协议** |
| 寻址与枚举 | 完整（BDF、配置空间） | 无（参数静态配置） | 无 |
| 流量控制 | 信用制 | 无 | NFC/UFC（可选） |
| 差错处理 | ACK/NAK 重传 | 无（告警） | 无（CRC 可选） |
| 实现代价 | 重（硬核或大量逻辑） | 中 | **极轻（几千 LUT）** |
| 物理层 | 各家 GT/SerDes | 同左 | 同左 |

> GT 收发器（Gigabit Transceiver）：FPGA 内集成的高速串行收发硬核（AMD 家的 GTX/GTH/GTY 等），内含 SerDes、均衡器、时钟数据恢复（CDR）。Aurora/JESD204C/PCIe 在 FPGA 上都跑在 GT 之上——协议可以换，GT 是同一块硅。GT 的参数（线速率范围、参考时钟要求）是板级设计的硬约束。

Aurora 的哲学是：把 SerDes 物理层之上的一切裁到最少，只保留"把字节流可靠地从 A 搬到 B"所必需的东西——帧定界、时钟补偿、可选的流控。适合"链路两端都是我设计"的封闭系统；需要接第三方设备或操作系统的场景，它帮不上忙。

与 PCIe 的体验差异值得强调：PCIe 驱动开发的大半复杂度来自枚举与配置空间（B-D.10 组），Aurora 全都没有——上电、链路初始化、`channel_up` 拉高，然后就是一个 AXI4-Stream 数据管道。从"点亮"到"传数据"的工作量大约是一个下午。

延迟对比也给个量级感受（同档 GT、小数据包）：Aurora 的协议处理延迟约几十~一百 ns 且逐拍确定；PCIe 要走 TLP 打包、数据链路层 ACK 信用检查，协议栈延迟在数百 ns~µs 级且有事务层排队变量。对"采样数据晚一拍就废"的前端链路，这个差是选型级的。

## 协议结构：两个版本

**Aurora 8B/10B**：经典版本，用于较低速率（≤6.6 Gbit/s/lane）的老 GT。8B/10B 编码自带丰富的控制符（K 码），协议开销 25%，但控制与定界极其简单，逻辑资源最省。

**Aurora 64B/66B**：高速版本（最高 32 Gbit/s/lane），编码开销仅 3%（66 位里 64 位是数据，2 位同步头），控制信息改用同步头与专门的控制块传递。新设计默认选它。

64B/66B 的同步头值得多看一眼：每 64 位数据前缀 2 位——`01` 表示纯数据块，`10` 表示含控制信息。接收端靠滑窗搜索这个 2 位模式完成块对齐（连续 64 个块里 01/10 规律成立才算锁定）。8B/10B 靠特殊码字"认出"控制信息，64B/66B 靠同步头"声明"控制信息——前者简单但烧 25% 带宽，后者省带宽但控制信道变窄。这条从 8B/10B 到 64B/66B+ 的编码演进线，在 PCIe Gen3、100G 以太网上是同一个故事，F.16.1 有通论。

> K 码（K-character）：8B/10B 编码中一类特殊码字，与数据码字（D 码）在电平上可区分，用于帧定界、时钟补偿等带外信令——接收端不需要额外信号线就能认出"这不是数据"。Aurora 8B/10B 用 `/A/`、`/R/` 等 K 码做空闲填充与对齐。JESD204 的 SYNC、PCIe 的 COM 字符是同族机制。

### 数据流与帧定界

Aurora 把链路抽象为**连续字节流**，帧是可选的：

```text
流模式（Streaming）：  data data data data data ...   （无帧结构，纯管道）
帧模式（Framing）：    /SCP/ data data ... /ECP/ /SCP/ data ... /ECP/
                       帧起始          帧结束
```

流模式适合"永远流不停"的场景（原始采样数据直灌）；帧模式给数据加边界，适合有报文语义的传输（一帧=一个数据包/一条指令）。帧模式下用户接口会多一个 `tlast` 信号标记帧尾——这是 AXI4-Stream 的标准语义。

### 控制元素

| 元素 | 作用 |
|------|------|
| SCP / ECP | 帧起始/结束定界（帧模式） |
| CC（Clock Compensation） | 周期插入的空闲序列，吸收两端晶振的 ppm 级频差 |
| UFC（User Flow Control） | 应用层信令通道（给对端发短消息） |
| NFC（Native Flow Control） | 接收端反压："我满了，暂停发" |

> 时钟补偿（Clock Compensation）：链路两端各用自己的参考时钟，标称同频但实际差几十 ppm——发送端略快时接收缓冲会被慢慢灌满，略慢时会被抽空。发送端周期插入 CC 空闲序列，接收端的**弹性缓冲**（elastic buffer，一个带水位线的 FIFO）按水位丢弃或重复这些空闲符号，把频差吸收掉。所有无时钟线的 SerDes 协议都有这一机制（PCIe 的 SKP、以太网的 Idle 删除），Aurora 是最简单、最适合理解的实例。

一个具体的数字场景：两端晶振各 ±50 ppm，最坏相差 100 ppm——每秒钟收发时钟累积偏移 100 µs 的数据量，约等于 10.3 Gbps 链路上 130 字节的偏差。没有弹性缓冲，缓冲器几秒内就会溢出/抽空导致链路重初始化；有了它，CC 序列的丢弃/重复把这个偏差永远消化在水位线之内。ppm 这个单位（百万分之一）在高速链路里不是细节，是决定"链路能活多久"的参数。

> UFC 与 NFC 的分工：UFC 是"捎句话过去"——在数据流里插入一条带优先级的短消息（比如参数更新、状态切换通知），不打断数据流；NFC 是"别发了"——接收端缓冲快满时通知发送端暂停，纯流量控制。数据采集系统里 UFC 常用于带内下发采集参数，NFC 用于下游处理不过来时的防溢出兜底。

UFC 在 IP 核上表现为一条独立的 AXI4-Stream 侧信道（`s_axis_ufc_*` 端口）：应用逻辑往这条口推一条短消息（带长度字段），Aurora 核把它插入数据流的下一可用间隙，对端从 `m_axis_ufc_*` 收。带内信令由此不需要另拉一根 UART——参数通道和数据通道共用一条链路，系统少一组连线、少一个同步问题。

NFC 的使用形态是对端发"暂停 X 拍"的控制消息，本端用户侧的 `tready` 随之拉低。用户逻辑必须尊重 `tready`（见 AXI4-Stream 握手规则），否则数据会在你的逻辑内部溢出——NFC 只负责把反压信号传过来，不替你存数据。

### 通道绑定（Channel Bonding）

多 lane 时，各 lane 的走线长度差（板上几毫米的差、连接器偏差）会造成 lane 间偏移（skew）——同一时刻发出的数据，各 lane 到达接收端的时刻不同。Aurora 在每个 lane 的同一时刻发一个特殊对齐序列，接收端用弹性缓冲把各 lane 重新对齐（快的等一下慢的），对外呈现一条逻辑上的宽链路。这与 PCIe 的 lane-to-lane deskew 是同一原理的轻量实现。

## Vivado 实战：IP 核配置与回环验证

Aurora 在 Vivado 里是现成 IP 核（`Aurora 8B/10B` / `Aurora 64B/66B`），典型配置项：

```text
Core:
  Lane width      : 4 bytes（数据路径宽度，影响内部时钟频率）
  Line rate       : 10.3125 Gbps
  Reference clock : 156.25 MHz（板载晶振，查原理图确认实际焊接值）
  Lanes           : 4
  Data flow       : Duplex（全双工）/ Simplex-TX / Simplex-RX
  Framing         : Streaming 或 Framing（AXI4-Stream 接口）
  Flow control    : None / UFC / NFC
  CRC             : 可选
```

三个配置决策的来由：**Lane width** 决定用户侧时钟频率（10.3125 Gbps 线速率、64B/66B、4 lane 时，内部数据路径每拍要吞吐 16 字节，位宽选大则时钟低、时序好收敛）；**Reference clock** 必须严格按原理图晶振值填——填错是最常见的"链路死活不上"原因；**Simplex** 用于单向采集链路，省一半 GT 资源。

顺带说清时钟链：板载晶振（如 156.25 MHz）进 GT 的 PLL，倍频出串行线速率时钟；GT 内部再分频出用户侧并行时钟（`user_clk`）。IP 核配置里的 Line rate 和 Reference clock 两个值必须满足 GT PLL 的合法倍频关系——Vivado 会校验并给出可选组合，校验不过多半是晶振频率与速率档位不匹配。原理图阶段就要确认晶振选型能覆盖你要的线速率。

### 用户接口：AXI4-Stream

用户侧是标准 AXI4-Stream 接口：

> AXI4-Stream：AMBA 家族里的流式接口协议，无地址、纯数据流。握手只有两个信号：`tvalid`（发送方：数据有效）与 `tready`（接收方：我能收），**同拍同时为高才完成一拍传输**。另有 `tdata`（数据）、`tlast`（帧尾）、`tkeep`（字节使能）。FPGA 逻辑之间搬数据的事实标准——Aurora、AXI DMA、大多数视频/数据 IP 的用户口都是它。

```verilog
// 发送一拍数据的握手时序：
//   tvalid 拉高后必须保持到 tready 也为高的那个时钟沿，数据才被对方收走
//   发送方不许等 tready 再拉 tvalid（死锁），接收方可以随时拉低 tready 反压
always @(posedge clk) begin
    if (s_axis_tx_tvalid && s_axis_tx_tready)
        // 本拍数据已被 Aurora 核收走，推进到下一拍
end
```

FPGA 逻辑把数据往 TX 口一推就走，门槛极低；`tready` 就是 NFC 反压到达用户逻辑的最终形态——对端说"满了"，本端 Aurora 核的 `tready` 就会拉低。

### 回环验证三板斧

1. **IP 核自带 example design**：右键 IP → Open IP Example Design，Vivado 自动生成带测试激励的完整工程，含帧发生器与校验器，上板即跑。**任何 Aurora 调试都从"example design 能不能跑通"开始**——它能跑通则 IP 配置与板级连接没问题，剩下的差异都在你自己的逻辑里。
2. **近端回环（near-end loopback）**：GT 内部把 TX 环回 RX，不经过外部信道，验证逻辑与配置正确。
3. **IBERT 眼图扫描**：换用 IBERT IP 对真实信道扫眼图、测 BER。

> IBERT（Integrated Bit Error Ratio Tester，集成误码率测试仪）：AMD FPGA 内建的物理层测试 IP，占用 GT 直接发 PRBS 码流并统计误码，配合 Vivado 的 Serial I/O Analyzer 扫出眼图。它把"信道质量"这个模拟问题变成软件里可读的数字与图形——F.16.1 的眼图知识（眼高/眼宽/模板）在这里直接用上。链路误码排查的标准动作：IBERT 扫眼 → 眼图好则问题在协议层，眼图差则问题在信道/时钟。

板内调试再补一件利器：**ILA**（Integrated Logic Analyzer，集成逻辑分析仪 IP）——把 `channel_up`、`lane_up`、AXI 握手信号挂上去，Vivado 里直接看波形。Aurora 链路"偶发掉线"类问题，用 ILA 抓掉线前后几百拍的状态信号是定位根因的最短路径。

### 状态信号排障入口

状态信号里 `channel_up`（链路就绪）和 `lane_up[n]`（各 lane 就绪）是调试入口。`channel_up` 不亮时按这个顺序查：

| 排查顺序 | 检查项 | 验证方法 |
|:---|:---|:---|
| 1 | 参考时钟有没有、频率对不对 | 示波器量 GT 参考时钟脚；核对 IP 配置与原理图晶振值 |
| 2 | GT 复位时序 | 查 `gt_reset`/`reset` 脉冲宽度与释放顺序（PG046/PG074 有明确时序要求） |
| 3 | P/N 极性是否接反 | GT 大多支持极性翻转寄存器修复；PCB 画反也能软件救 |
| 4 | 对端是否同速率/同协议版本 | 两端 IP 配置逐项比对 |
| 5 | 信道质量 | IBERT 扫眼图 |

另有一种中间态要知道：`lane_up` 部分亮（4 lane 只亮了 2 个）。这指向单 lane 级问题——对应 lane 的走线/连接器/焊点，或该 lane 的极性。用 IBERT 对各 lane 单独扫眼图，坏 lane 会现形；全部 lane 都不亮才是链路级问题（时钟/复位/配置），按上表顺序查。

CRC 选项的取舍也在这里说：Aurora 本身无重传，CRC 只能检错不能纠错，检出错帧就丢。开不开取决于下游能不能容忍丢帧——原始采样流（丢一拍补零/插值即可）通常不开，指令与参数通道（错了要重发）通常开，并在应用层加序号与确认。这个"检错后怎么办"的答案不在协议里，在你的系统需求里。

## PL 数据进 Linux：Zynq/MPSoC 的最后一公里

常见系统拓扑：Aurora 从远端板卡收高速数据进 FPGA（PL），PL 经 DMA 写入 PS（ARM 核）的 DDR，Linux 应用读走。

```text
远端板卡 ──Aurora──► FPGA(PL) ──AXI DMA──► DDR ──► Linux 应用
                        │                    ▲
                        └── 中断：帧/块完成 ──┘
```

Linux 侧的两种做法：

- **UIO 方式**（快糙猛）：设备树声明 DMA 与中断，用户态 `mmap` UIO 节点直接读写 DMA 寄存器与缓冲区。适合原型验证，不适合量产（无隔离、无并发保护）。

  UIO 的设备树骨架：

  ```dts
  aurora_dma: dma@a0000000 {
      compatible = "generic-uio";          /* 直接挂 UIO，无内核驱动 */
      reg = <0xa0000000 0x10000>;          /* DMA 寄存器窗口 */
      interrupts = <0 89 4>;               /* DMA 完成中断（GIC SPI 89，上升沿） */
      interrupt-parent = <&gic>;
  };
  /* DDR 里预留的一致性缓冲区：用 reserved-memory 防止内核占用 */
  reserved-memory {
      aurora_buf: buffer@30000000 {
          reg = <0x30000000 0x10000000>;   /* 256 MB 环形缓冲区 */
          no-map;
      };
  };
  ```

  用户态打开 `/dev/uio0`，`mmap` 两个区域（寄存器+缓冲），中断用 `read()` 阻塞等待。原型阶段这套半天能跑通；量产要换正经字符驱动的理由：UIO 没有并发访问保护、缓冲区生命周期裸奔、任何用户态 bug 都能直接写坏 DMA 寄存器。
- **正经字符驱动**：probe 里 `dma_alloc_coherent` 分配环形缓冲，中断里推生产指针，用户态 `read/poll` 取数据——结构与 B-D.10.3 的 PCIe DMA 驱动完全同构，只是数据来源从 PCIe 链路换成了 PL 侧 AXI。写法的每一步（一致性内存、中断上半部只确认不搬运、环形缓冲指针同步）在 D.10.3 和第 10 章都有对应讲解。

性能要点：算带宽账时把三段都列出来——Aurora 链路带宽（线速率 × 编码效率 × lane 数）、AXI 总线带宽（位宽 64/128bit × 频率）、DDR 控制器带宽。**瓶颈在窄的那一段**：4 lane 10.3 Gbps Aurora（≈5 GB/s 有效）配 64bit@250MHz AXI（2 GB/s），AXI 段就是短板，要么加宽位宽要么降链路速率预期。

### 一个完整算例：雷达前端采集卡

把全篇串起来看一个真实形态的系统：远端雷达前端板（ADC 采样率 2 GSPS × 14bit，打包后数据率约 3.5 GB/s）→ Aurora 64B/66B × 4 lane @ 10.3125 Gbps（有效带宽 4 × 10.3125 × 64/66 / 8 ≈ 5.0 GB/s，余量 40%）→ 处理卡 FPGA 解包 → AXI DMA（128bit @ 250 MHz ≈ 4 GB/s，瓶颈段，靠 DMA 突发与 DDR 写带宽余量硬扛）→ PS 侧 Linux 字符驱动环形缓冲 → 应用层落盘/实时显示。

每条链路决策在文中的出处：选 Aurora 因两端都是自家板卡（定位节）；4 lane 配置经通道绑定对齐（协议节）；上板先跑 example design 再切 IBERT 扫背板信道（工具链节）；Linux 侧用字符驱动而非 UIO 因产品要跑 7×24（整合节）。带宽三段账里 AXI 段最窄——这就是系统设计评审时该被追问的那一项。

## 选型：什么时候用 Aurora

| 需求 | 选择 |
|------|------|
| 两端都是自家 FPGA/板卡，纯搬数据 | **Aurora**（最省逻辑、最低延迟） |
| 接 ADC/DAC 芯片 | JESD204C（芯片只认这个） |
| 需要操作系统/驱动生态、接标准外设 | PCIe |
| 多板卡交换式互联（不常用） | Serial RapidIO |
| 标准化背板互联 | PCIe 或以太网（10G/25G 用 FPGA GT 跑） |

Aurora 的护城河就是"轻"：逻辑资源省一个数量级、延迟是确定的百纳秒级、协议简单到可以整个读懂。代价是生态为零——换家 FPGA 厂（Intel/Altera）就得换实现（Transceiver Native PHY + 自定义协议，或开源 Aurora 兼容实现）。**跨厂商互联不要用 Aurora**；产品生命周期内可能换 FPGA 供应商的，协议选型时把这条写进决策记录。

### 自己造一个行不行

FPGA 工程师常有冲动：既然 Aurora 这么简单，自己造一个极简协议行不行？行，技术上不难（GT 原语 + 自定义帧头就能跑），但先算清隐形成本：链路初始化的状态机、时钟补偿、通道绑定、误码统计，每一个"看起来简单"的机制都是你要在所有边界条件下验证的——高温、老化、线缆插拔、两端上电时序差。Aurora 这些机制经过几千万片量产验证，你的自研协议只有你的测试台。**结论：学习/论文场景造轮子值得（把 Aurora 读一遍再仿写一遍是极好的训练），产品场景用 Aurora 并把它当黑盒验证**。只有在 Aurora 的某个限制确实卡住需求时（比如要跨厂商、要接标准生态），才考虑换协议而不是造协议。

## 本节总结

Aurora 是 SerDes 协议谱系里"极简主义"的极端样本：把物理层以上裁到只剩帧定界、时钟补偿和可选流控，换来几千 LUT 的实现代价、确定的百纳秒级延迟和一个下午的点灯速度。它的机制全部是 SerDes 通识的最简实例——CC 序列吸收 ppm 频差、通道绑定吸收 lane 间 skew、K 码做带外信令，每一条在 PCIe/以太网里都有更复杂的同构体。工程落地的两个关键路径是 Vivado 的"example design 先行"验证法和 Zynq 上 PL→PS 的三段带宽账（链路/AXI/DDR，瓶颈在窄处）。选型边界清晰：两端都是自家 FPGA 的封闭系统用 Aurora，要生态要跨厂商就别用它。

| 关键结论 | 一句话记忆 |
|:---|:---|
| 定位 | 封闭系统点对点搬数据的最轻协议，一层链路无枚举 |
| 两版本 | 8B/10B 老而简单，64B/66B 新且省带宽（3% 开销） |
| 机制 | CC 吸频差、绑定吸 skew、UFC 捎话、NFC 反压 |
| 验证 | example design 先行，ILA 看状态，IBERT 扫眼图 |
| 进 Linux | UIO 做原型，字符驱动做产品；带宽瓶颈找三段最窄处 |
| 边界 | 生态为零，跨厂商禁用 |
