# 27.4 TSN：标准以太网上的确定性

> 所属章节：第27章 工业通信全链路
>
> 难度：[E] | 预计阅读时间：25分钟

## <span class="blue">本节导读

前两节买的确定性都付了"非标准"的代价：EtherCAT 用专用主站、专用帧结构、专用 MAC 驱动；CAN 干脆是另一种总线。TSN（Time-Sensitive Networking，时间敏感网络）的目标更激进：**不改以太网的任何语义——普通 IP、普通交换机芯片、普通网线——在标准以太网上买到有界延迟**。它的卖点不是替代谁，而是"一网到底"：运动控制、视觉流、日志、远程运维跑在同一张网上，各拿各的服务等级。

机械臂场景里，TSN 出现在下一代平台评估会上：视觉相机要 1Gbps 级带宽（EtherCAT 给不了），控制环要 1ms 有界（普通以太网给不了），TSN 承诺两者兼得。这一节要把这个承诺拆开验货。

> 本节覆盖：TSN 作为 IEEE 802.1 标准族的两根支柱（gPTP 全网对时 + 802.1Qbv 时间门控，含四消息对时交换的数学与 GCL 设计实例）、Linux 上的落地配置链（ethtool 查能力 → ptp4l 对时 → taprio 配门控）、2026 年内核支持现状（哪些成熟、哪些还要看驱动）、"时间门控不生效"的三类根因，以及 TSN 与 EtherCAT 的替代关系决策。

## <span class="blue">TSN 不是一个协议，是一套标准族 [E]

先破除一个常见误解：TSN 不能像 EtherCAT 那样"装上就跑"。它是 IEEE 802.1 下的一族标准，各自解决确定性的一块拼图，工程上最核心的是四块：

| 标准 | 名字 | 解决什么 | Linux 对应物 |
|:---|:---|:---|:---|
| 802.1AS | gPTP 时间同步 | 全网纳秒级对时——一切调度的地基 | `ptp4l`（linuxptp） |
| 802.1Qbv | 时间感知整形（TAS） | 关键流量的发送窗口独占化 | `taprio` qdisc |
| 802.1Qbu | 帧抢占 | 大帧被切碎让路，压缩阻塞时间 | 部分网卡支持 |
| 802.1CB | 帧复制与消除 | 双路径冗余，丢包无感切换 | 开发中 |

按 27.1 的三类失败姿势对号入座：**802.1AS 治丢同步，Qbv 治超时（关键帧延迟有界化），Qbu 压缩 spike 的一个来源（被大帧阻塞），CB 治链路级丢包**。本节集中讲前两块——它们是 TSN 的最小可用集，后两块知道存在、知道去哪查就够。

## <span class="blue">支柱一：gPTP 全网对时 [E]

Qbv 时间门控的前提是"全网所有节点共享同一个时刻"——门几点几分几秒开，必须所有人口径一致，否则门控表就是废纸。所以 TSN 部署的第一步永远是对时。

gPTP（generalized PTP，802.1AS）是 PTP（IEEE 1588）的收紧版：域内所有设备强制支持硬件时间戳、强制逐跳测量链路延迟，省掉了通用 PTP 的协商弹性，换来更快的收敛和更稳定的精度（普通 PTP 亚微秒，gPTP 目标是百纳秒级）。运行时的角色选举由 BMCA（最佳主时钟算法）自动完成：全网比时钟质量，最优者成为 grandmaster，其余节点逐级对齐。

> 硬件时间戳：网卡 MAC/PHY 层给帧打上收发的物理时刻，绕过协议栈的不确定延迟。没有它，PTP 的时间戳打在软件层，栈内排队抖动直接变成对时误差——所以 PTP 精度问题十有八九先查硬件时间戳支不支持。

Linux 侧工具是 linuxptp 套件。完整配置链：

```bash
# ① 查网卡能力：硬件时间戳是硬门槛
ethtool -T eth0
# 关注输出里 hardware-transmit / hardware-receive / hardware-raw-clock
# 如果只有 software-*，这块网卡做不了 gPTP，Qbv 也无从谈起

# ② 跑 gPTP 守护进程（802.1AS 域）
ptp4l -i eth0 -m --domainNumber 0

# ③ 把 PHC（网卡硬件时钟）同步到系统时钟，应用才能用 CLOCK_REALTIME
phc2sys -s eth0 -c CLOCK_REALTIME -m

# ④ 验证：ptp4l 日志里 offset 应稳定在百纳秒量级
# master offset   42 s2 stable ...
```

`master offset` 那行日志是 27.1 意义上的验收数：offset 持续几百纳秒内且稳定（`stable` 字样），对时才算锁住；**锁住之前配任何门控都是无的放矢**——这正是后面排查清单的第一条。

对时是怎么"对准"的？主从之间周期性地交换四条消息，算两个未知数：

```
grandmaster                     slave
    │ ── Sync(t1) ─────────────▶ │  t2 = 从钟收到时刻
    │ ── Follow_Up(t1精确值) ──▶ │  （Sync 发出时刻硬件时间戳）
    │ ◀── Delay_Req(t3) ──────── │  t4 = 主钟收到时刻
    │ ── Delay_Resp(t4) ────────▶ │
    ▼                            ▼
链路延迟 = [(t4-t1) - (t3-t2)] / 2
主从偏差 = (t2-t1) - 链路延迟
```

从站拿到四个时间戳就能解出"我的钟比主钟慢多少"和"帧在路上走了多久"——和 27.2 EtherCAT DC 的传播延迟测量是同一个数学问题，区别只在 DC 是 ESC 硬件算、gPTP 是 ptp4l 守护进程算。这也解释了对时精度的天花板在哪：**t1~t4 全部来自硬件时间戳才有百纳秒级**，任何一个退化成软件打戳，栈内排队抖动就直接进入对时结果。

## <span class="blue">支柱二：802.1Qbv 时间门控 [E]

对时锁住之后，Qbv 给每个出口队列装一扇"定时门"：网卡的 8 个优先级队列各有一个门控状态（开/关），由一张**门控表（GCL，Gate Control List）**按全网共享的时刻轮转。控制帧所在队列的门开了，其他门全关——这段时间里关键流量独占发送口，**谁也插不进队，包括已经在排队的普通流量**。

```
一个 GCL 周期 1ms（与 27.1 预算表同构）：

时刻(μs)   0        100       300                     1000
          │控制窗口 │ 保护带  │  普通窗口              │下一周期
          ▼        ▼        ▼                       ▼
控制队列   门开     门关      门关                     门开
普通队列   门关     门关      门开                     门关
          └ 控制帧独占  └ 防止大帧越界 └ 视觉/日志/运维全走这
```

注意 GCL 的结构和 27.1 的时间预算表是同一张表——**TSN 本质上是把预算表从"应用层的约定"变成了"网卡硬件的执行"**。保护带（guard band）的作用和预算表里"算法前留 100μs"相同：普通窗口最后一个帧不能越过窗口边界，网卡会阻止"装得下开头装不下结尾"的帧发出，防止它侵占下一个控制窗口。

Linux 配置走 `taprio` qdisc：

```bash
tc qdisc replace dev eth0 parent root handle 100 taprio \
    num_tc 2 \
    map 1 0 1 1 1 1 1 1 \
    queues 1@0 1@1 \
    base-time 0 \
    sched-entry S 01 300000 \
    sched-entry S 02 700000 \
    flags 0x2
```

逐参数解读：`num_tc 2` 两个流量类别；`map` 把 8 个优先级映射到类别（优先级 0 进控制类，其余进普通类）；`base-time 0` 门控表从 gPTP 时刻 0 开始对齐——**这个时刻就是全网共享的那本日历**；两条 `sched-entry` 是 GCL 本体：`S 01 300000` 开门位图 0x01（队列 0）300μs，然后 `S 02 700000` 开队列 1 七百 μs，拼成 1ms 周期；`flags 0x2` 请求网卡硬件卸载——门控由 MAC 硬件执行，不走软件队列。

发送侧应用只需给 socket 打优先级（`SO_PRIORITY` 0），帧就会被分流进控制队列；更精细的做法是 ETF qdisc + `SO_TXTIME`，让帧带"预定发射时刻"，网卡到点才发——这是 802.1Qbv 的姊妹机制，适合端站侧精确对齐周期。

## <span class="blue">GCL 设计实例：从预算表到门控表 [E]

taprio 命令里那两条 `sched-entry` 不是拍出来的，是从预算表推的。拿机械臂场景算一遍：

**输入**：控制周期 1ms；控制帧（主站到 6 轴伺服 + 回程）最坏传输 250μs；视觉相机每周期突发一帧图像约 12MB，走普通类；链路 1Gbps。

**推导**：

1. 控制窗口 = 控制帧最坏传输 + 余量 = 250μs + 50μs = **300μs**；
2. 保护带 = 一个 MTU 帧在窗口边界的最大"越界"时间：1522 字节 ÷ 1Gbps ≈ 12.2μs，取 **13μs**——网卡在普通窗口末尾会自动阻止放不进剩余时间的帧，这个宽度就是它执行阻止的依据；
3. 普通窗口 = 1000 - 300 = **700μs**（保护带已含在内由硬件处理）。

**对照 taprio 命令**：`sched-entry S 01 300000`（控制类 300μs，门位图 0x01）+ `sched-entry S 02 700000`（普通类 700μs）——前面那条命令就是这么来的。视觉流量会不会挤死？普通窗口 700μs × 1Gbps ≈ 87KB 每周期——不够相机的 12MB，所以视觉帧横跨多个周期慢慢发，这正是设计意图：**控制帧每周期必达，大流量帧延迟换吞吐**。如果视觉也要确定性（比如视觉伺服），那它就得升格进控制窗口、重新分预算——GCL 表的每一项都是预算表的一行，改一行牵动全表。

## <span class="blue">2026 年支持现状：能用到什么程度 [E]

落地前先校准预期，按成熟度分三档：

- **成熟可用**：gPTP（ptp4l 主线多年）、taprio 软件门控（内核主线）、ETF/SO_TXTIME（主线）、硬件卸载——Intel i210/i225/i226 与主流 SoC 的 stmmac 系 MAC 都支持，工控板卡选型时这是明确选项；
- **看驱动**：帧抢占（802.1Qbu/802.3br）——硬件和驱动支持仍在铺开，选型要逐型号核实；
- **开发中**：802.1CB 帧复制消除、完整的 802.1Qcc 集中配置模型——关注但暂不进产品设计。

和 EtherCAT 生态的差距也要说在明处：EtherCAT 有 ESI 文件、ETG 一致性认证、几十个伺服品牌即插即用；TSN 的配置（GCL 怎么算、窗口怎么分）目前更多是工程师自己的功课——**协议给了机制，没给配置答案**，这正是 27.1 预算表功底的价值。

## <span class="blue">门控不生效：三类根因 [E]

现场配 TSN 最高发的症状是"配完了，延迟还是老样子"。按 27.1 的三类姿势分诊：

| 症状 | 根因类别 | 验证 |
|:---|:---|:---|
| taprio 配上了但延迟无改善 | 超时（设计）类：用了软件门控 | `flags 0x2` 加上后 `tc -s qdisc` 看是否卸载成功；不支持硬件卸载的网卡，软件门控精度受调度限制，关键场景不可用 |
| 门控生效但时刻错位 | 丢同步类：gPTP 没锁住 | ptp4l 日志 offset 是否稳定；`base-time` 是否用 gPTP 时刻而非本地时钟——两本日历门控必然错位 |
| 偶发延迟毛刺 | spike 类：大帧越界/抢占缺失 | 保护带是否覆盖 MTU 帧长；Qbu 是否可用——没有帧抢占时，1500 字节大帧在 1Gbps 下能堵 12μs |

> ⚠️ 第二个根因最隐蔽：ptp4l 没起来时 taprio 照样接受配置、照样轮转——它只是按**错误的日历**轮转。症状是全链路"有规律地"错过窗口，看起来像协议问题，实际是对时没建立。排 TSN 问题先贴 ptp4l 日志，这已经是社区排障的第一条行规。

## <span class="blue">TSN vs EtherCAT：替代关系怎么判 [E]

回到评估会上的问题，直接给决策对照：

| 维度 | EtherCAT | TSN |
|:---|:---|:---|
| 确定性来源 | 专用帧结构 + 硬件 ESC | 标准以太网 + 时间门控 |
| 周期能力 | 250μs~1ms 成熟，12.5μs 极限 | 1ms 级成熟，更短看硬件 |
| 带宽 | 100M 为主（G 版在推） | 1G/2.5G/10G 原生 |
| 拓扑 | 线型/树型，主站单点 | 任意交换式拓扑，支持冗余 |
| 生态 | 伺服/IO 极其成熟 | 芯片成熟，设备生态建设中 |
| 混合流量 | 不支持（专线专用） | 设计目标（控制+视觉+运维一网） |
| 配置成本 | 低（ESI 文件描述一切） | 高（GCL/窗口自己算） |

落到结论的三句话：**今天做 6 轴伺服从站，选 EtherCAT**——生态、成本、周期能力全部现成；**做"控制 + 视觉 + 运维"一网到底的新平台，TSN 开始值得评估**——带宽和拓扑是它的主场；**两者不是二选一**——主控制器上联用 TSN 汇流、下挂 EtherCAT 段做伺服，是 2026 年机器人平台最现实的混合架构。

## <span class="blue">本节总结

TSN 在标准以太网上买确定性，靠两根支柱：gPTP 全网对时（地基，offset 稳定在百纳秒级才算锁住）和 802.1Qbv 时间门控（GCL 按共享时刻轮转门控，控制窗口独占发送口——本质是把 27.1 的预算表从应用约定变成网卡硬件执行）。Linux 配置链四步：ethtool 查硬件时间戳、ptp4l 对时、phc2sys 桥接系统时钟、taprio 配 GCL。

2026 年现状：对时、软件门控、ETF、i210/i225/i226 与 stmmac 硬件卸载成熟；帧抢收看驱动；CB 与 Qcc 开发中。门控不生效按三类分诊：软件门控冒充（查卸载）、日历错位（查 ptp4l，最隐蔽）、大帧越界（查保护带与 Qbu）。替代关系：伺服从站今天仍选 EtherCAT，一网到底的新平台开始评估 TSN，主控上联 TSN + 下挂 EtherCAT 段是现实混合架构。
