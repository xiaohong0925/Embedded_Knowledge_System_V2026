# 27.6 综合实战：CNC 运动控制 125μs 周期端到端

## <span class="blue">本节导读

## <span class="blue">需求与预算：125μs 意味着什么 [E]

五轴联动 CNC：X/Y/Z 直线轴 + A/C 旋转轴同时插补，刀具中心点要沿复杂曲面走，位置环 8kHz——控制周期 125μs。指标两个：**每 125μs 完成一次全链路（读 5 轴编码器 → 插补 → 写 5 轴指令），周期抖动最大 <5μs**（5μs 的相位误差在五轴联动时已经能在加工面上留下可测量的刀痕）。

先按 27.1 的方法画出预算表——周期从 1ms 压到 125μs，每个数字都变紧：

| 时刻 | 环节 | 预算 | 依据 |
|:---|:---|:---|:---|
| 0μs | EtherCAT 读 PDO（5 轴编码器） | ~15μs | 5 站线型拓扑，27.2 的线性规律 |
| 20μs | 数据在用户空间可用 | ~5μs | 专用驱动 + 调度唤醒（27.5 配置后） |
| 70μs | 五轴插补完成 | ~50μs | 算法实测最坏值 + 余量 |
| 95μs | 输出写入完成 | ~25μs | 回程帧 + 从站处理 |
| 125μs | 下一周期 | — | 总占用 76%，符合 70% 纪律的下沿 |

对照 27.1 的 1ms 表看区别：**125μs 周期里调度唤醒的预算只剩 5μs**——这意味着 jitter 指标的 5μs 里调度段独占大头，27.5 的每一项配置从"建议"变成"必需"，而且没有任何一项允许打折扣。

## <span class="blue">第一版：标准答案为什么不达标 [E]

按 27.5 清单完整配置：PREEMPT_RT 内核、CPU 2/3 隔离四参数、irqbalance 关闭、中断亲和、主站线程 SCHED_FIFO 99、mlockall + 栈预触碰、定频。验收：

```bash
taskset -c 2 cyclictest -p 99 -m -i 125 -l 86400000 -h 50
```

结果：99.999% 的样本 Max 在 3μs 内——漂亮。但直方图的尾巴上，**偶发出现 50~200μs 的单次 spike**。过夜跑 24 小时，spike 出现约两万次。对照指标 <5μs：不合格，而且超了一个数量级。

用 27.1 的三类姿势分诊：不是稳定超时（主体极好），不是丢同步（DC 监控干净）——是 spike 类。这类问题的难点 27.1 说过：**实验室测不出来、复现靠运气**。但这个案例里 spike 有个宝贵特征：它不是随机的。

## <span class="blue">排查链：五步猎杀 [E]

### 第一步：复现与量化——把"偶发"变成"规律"

先别猜，先测。把 cyclictest 的 spike 时间戳连续记录 24 小时，统计间隔分布——结论立刻浮出来：**spike 间隔高度集中在约 4 秒**，每次持续 50~200μs。偶发问题的第一条线索永远是统计规律：严格周期的 spike 意味着周期性的触发源，而"4 秒"这个量级不像任何软件定时器（cron 是分钟级、tick 是毫秒级）。

### 第二步：分段定位——排除总线与算法

按 27.1 的逐段测量表过一遍：

- EtherCAT 主站统计（`ethercat master`）：cycle time 分布干净，spike 时刻总线侧无异常——**总线段排除**；
- 算法内 `clock_gettime` 打点：spike 时刻算法本身耗时不变——**算法段排除**；
- cyclictest 与主站线程同核对照：两者在**同一时刻**看到延迟——问题在"线程被唤醒之前"，即调度段或更底层。

### 第三步：ftrace——发现"时间凭空消失"

上 ftrace 抓调度延迟的最大值现场：

```bash
cd /sys/kernel/debug/tracing
echo wakeup_rt > current_tracer
echo 1 > tracing_on; sleep 300; echo 0 > tracing_on
cat trace | less
```

抓到的 spike 现场出现了本案最关键的指纹：**spike 窗口内 ftrace 没有任何记录**——没有中断、没有调度、没有锁，不是"被打断"，是 CPU 在那 50~200μs 里**对内核彻底消失**了。27.5 说过，能对 OS 隐身的只有一样东西：SMI。

### 第四步：确认 SMI——指纹比对

三个证据闭环：

1. **OS 不可见**：ftrace 空白——SMI 进 SMM 模式执行固件代码，内核无从感知；
2. **严格周期 4 秒**：典型的 BIOS 定时任务特征；
3. **平台**：x86 工控主板——SMI 的唯一产地。

咨询主板厂商 + 查 BIOS 源码注释（或实测二分法：逐项关闭 BIOS 选项看 spike 是否消失），定位到 **BIOS 的 CPU 温度监控**：固件每 4 秒进 SMM 读一次温度传感器，检查风扇策略，耗时 50~200μs（取决于当时 EC 总线忙不忙——这解释了为什么 spike 时长不固定）。

### 第五步：BIOS 处置——以及它的代价

在 BIOS 里关闭温度监控 SMI。这个决定不是免费的，必须走评审：

- **失去什么**：CPU 过温的固件级保护（原来过温时 SMM 会强制降频/关机）；
- **补什么**：外部看门狗 + 独立的温度监控（EC 或直接 I2C 挂温度传感器，由 Linux 业务核轮询，过温走软件保护流程）——第 30 章会系统讲这类兜底设计；
- **为什么不能全关**：有些 SMI 源（如电源按钮、某些 EC 事件）关系安全，本案只关温度轮询一项，其余保留。

> ⚠️ 本案的教训要刻进团队知识库：**BIOS 设置是实时系统的一部分**。x86 平台上任何"OS 层面查不到的延迟"，第一嫌疑人就是 SMI；工控主板选型时"BIOS 是否允许关闭非必要 SMI 源"应该写进采购规格书。

## <span class="blue">最终架构与验收 [E]

```
┌─────────────────────────────────────────────────┐
│ CPU 0-1：Linux 非实时                            │
│   HMI / 文件管理 / 网络 / 日志 / 温度轮询(软件)   │
├─────────────────────────────────────────────────┤
│ CPU 2-3：隔离（isolcpus/nohz_full/rcu_nocbs）    │
│   核2: EtherCAT主站线程 SCHED_FIFO 99            │
│   核3: 五轴插补线程   SCHED_FIFO 98              │
│   ├── 定频（intel_pstate=disable + BIOS锁频）    │
│   ├── mlockall + 栈预触碰 + 堆预分配             │
│   └── 全部外设中断 affinity → CPU 0-1            │
├─────────────────────────────────────────────────┤
│ BIOS：温度监控SMI关闭（外部看门狗+软件温度保护）  │
└─────────────────────────────────────────────────┘
```

验收数据（27.1 的烤机三维度全做）：

| 维度 | 做法 | 结果 |
|:---|:---|:---|
| 时长 | 72 小时连续 | Max jitter 3μs，无单次超标 |
| 负载 | CPU 0-1 编译内核 + 满速网络传输 | 核 2/3 直方图纹丝不动 |
| 工况 | 实际切削铝件/钢件各 8 小时 | 加工面无刀痕恶化，三坐标测量合格 |

**125μs 周期、最大抖动 <3μs**——指标 <5μs 达成，且余量留了 40%。

## <span class="blue">评审清单：这套方法论的口袋版 [E]

CNC 案例走完，把全章收敛成一份评审清单——任何工业通信设计评审，逐条过：

**总线（27.2~27.4）**

- [ ] CAN：ID 表按迟到后果排序；bus-off 恢复策略评审过

**调度（27.5）**

**验证（27.1/27.6）**

- [ ] x86 平台：SMI 源清单与 BIOS 处置评审过，外部兜底落实

## <span class="blue">本节总结

125μs 周期把 27.1 预算表的每行都压紧一个数量级——调度段预算只剩 5μs，27.5 的每项配置从建议变必需。第一版"标准答案"不合格的原因不在配置清单里：偶发 50~200μs spike 超出指标 10~40 倍。

排查链五步是全章方法论的主刀：先统计规律把偶变变周期（4 秒）、再逐段排除（总线与算法干净）、ftrace 抓到"时间凭空消失"的指纹、三证据闭环确认 SMI、BIOS 处置并补上外部看门狗的代价。最终架构 125μs 周期 jitter <3μs 验收通过。三条刻进知识库的教训：BIOS 设置是实时系统的一部分；spike 排查靠统计规律与逐段定位，不靠猜；x86 工控选型把"SMI 可关闭性"写进采购规格书——或者，直接选 ARM。
