# 27.3 CAN/CAN-FD 链路：SocketCAN 与错误恢复

> 所属章节：第27章 工业通信全链路
>
> 难度：[E] | 预计阅读时间：25分钟

## <span class="blue">本节导读

27.2 把周期性伺服数据交给了 EtherCAT。但一台机械臂上还有很多数据不是周期的：急停按钮和 IO 模块的状态变化、电池管理板的电压上报、力控传感器的触发事件、关节驱动器的故障码——它们**事件驱动、频率不高、但一条都不能丢，而且延迟要有上界**。为它们再铺一路 EtherCAT 是杀鸡用牛刀，这个角色在工业现场几十年了都是 CAN。

> 本节覆盖：CAN 在控制链路里的分工（与 EtherCAT 是搭配不是竞争）、"ID 即优先级"的位级仲裁原理与真实机械臂 ID 分配实例、SocketCAN 把 CAN 抽象成网络设备的架构收益、CAN FD 对时间预算的实际意义（含 FD 收发代码与 BRS 标志）、错误状态机（TEC/REC 计数规则、active→passive→bus-off 迁移）与 bus-off 恢复策略、采样点计算实例，以及"错误帧激增"的链路级排查。

## <span class="blue">CAN 在链路里的分工：事件型数据的高速公路 [E]

机械臂的通信拓扑典型地长这样：

```
                  ┌─ EtherCAT ── 6×伺服驱动器（1ms 周期，位置/转矩）
  控制器 (Linux) ─┤
                  └─ CAN ── IO模块 / 电池BMS / 力传感器 / 驱动器故障上报
                            （事件触发，毫秒级上界，不周期）
```

为什么事件型数据适合 CAN 而不是也走以太网？三个硬件级特性：

1. **仲裁即优先级**：CAN 是多主总线，多个节点同时发帧时靠 ID 逐位仲裁，**ID 数值小的赢**——不需要任何调度器，优先级是协议天生的。急停帧配最小 ID，它就永远插队成功。
2. **广播天然**：一帧总线上人人收到，状态上报不需要订阅机制。
3. **错误处理硬件化**：帧校验、ACK、错误计数、故障隔离全部在 CAN 控制器硬件里，软件看到的是"收到帧"或"收到错误事件"，不用自己实现可靠性。

用 27.1 的语言总结：**EtherCAT 的确定性是"周期准时"，CAN 的确定性是"高优先级帧的等待时间有上界"**——两种确定性服务于两种数据。

## <span class="blue">ID 即调度表：CAN 确定性的核心 [E]

"ID 数值小 = 优先级高"这句话的推论经常被低估：**设计 CAN ID 分配表就是在设计一张调度表，而且它一旦烧进固件就无法动态调整**。

先把"为什么 ID 小就赢"讲到物理层，否则这张调度表立不住。CAN 总线有两个电平状态：**显性（0）压过隐性（1）**——任何一个节点输出显性位，总线就是显性。仲裁过程是：多个节点同时开始发帧，从 ID 最高位开始逐位发送，每个节点边发边听总线：

```
节点A 发 ID 0x103：0 0 1 0 0 0 0 0 0 1 1
节点B 发 ID 0x105：0 0 1 0 0 0 0 0 1 0 1
                      ↑ 前8位相同，两节点都"听到自己发的"，继续
节点A 第9位发 0（显性），节点B 第9位发 1（隐性）
                      ↓
总线呈现显性 0 —— B 听到总线与自己发的不一致，立即闭嘴转为接收
A 浑然不觉，继续发完——全程没有任何数据被破坏，没有重传
```

三个关键性质都在这个例子里：**败者无损退出**（B 的帧没发出去但也没坏，下个空档自动重试）、**胜者零感知**（A 根本不知道发生过争夺）、**结果在 ID 发完时即定**（仲裁开销 = ID 长度本身，没有额外时间）。所以"延迟上界 = 最长一帧的剩余传输时间"不是估算，是协议保证——败者最多等当前这帧传完，下一轮仲裁必胜（除非又有更小 ID 来抢）。

工程上的做法是把链路里所有帧按"迟到后果"排序，后果越重 ID 越小。一台协作机械臂的真实分配实例：

| ID（11 位） | 帧 | 发送方 | 迟到后果 |
|:---|:---|:---|:---|
| 0x001 | 急停/安全联锁 | 安全控制器 | 法定责任 |
| 0x080 | 同步帧 SYNC | 主控制器 | 全轴节拍漂移 |
| 0x181~0x186 | 六轴实际位置/状态（TPDO） | 各关节驱动器 | 控制品质下降 |
| 0x201~0x206 | 六轴目标指令（RPDO） | 主控制器 | 周期抖动 |
| 0x301 | 电池 BMS 电压/温度 | 电池板 | 续航估算偏差 |
| 0x381 | 力传感器触发事件 | 力控板 | 力控响应变慢 |
| 0x581~0x586 | 驱动器故障码（SDO 响应） | 各关节驱动器 | 故障感知延迟 |
| 0x701~0x706 | 节点心跳 | 各节点 | 掉线检测变慢 |
| 0x600~0x606 段 | 参数读写、日志 | 调试工具 | 无实时后果 |

两个设计细节值得学：**同功能帧用连续 ID**（0x181~0x186 六轴排一起，过滤器用一个掩码段就圈住，前面 SocketCAN 代码里 `0x100/0x700` 那个掩码就是这个用意）；**心跳压到接近最低优先级**——它周期固定、迟到一两个节拍无所谓，但绝不能让它抢安全帧。

这张表决定了最坏情况延迟：**一个高优先级帧最多等"当前正在传的最长一帧"传完**（CAN 仲裁在位级进行，不打断已获胜的帧）。经典 CAN 一帧最长约 130μs（1Mbps、含位填充），这就是安全帧延迟上界的计算基础——不是拍脑袋的"很快"，是可以写进安全认证文档的算术。

> ⚠️ 反过来说，ID 分配失误是架构级错误：把诊断帧放进高优先级段，一次日志风暴就能把控制帧挤出上界。评审 CAN 设计先审 ID 表，再审代码。

## <span class="blue">SocketCAN：把 CAN 变成网络设备 [E]

早期 Linux CAN 驱动是字符设备：`read/write` 一次一帧，多个应用要共享总线就得自己写分发层，过滤器各搞一套。SocketCAN（内核主线）的架构决策是把 CAN 控制器抽象成**网络设备**（`can0`），应用用标准 BSD socket 收发：

```
应用A ─┐                            ┌─ can_raw（原始帧）
应用B ─┼─ socket(PF_CAN) ── 协议层 ─┼─ can_bcm（周期发送/过滤）
应用C ─┘                            └─ can_isotp（诊断分包）
                    │
              网络设备层（can0：队列、过滤器、统计）
                    │
              CAN 控制器驱动（mcp251xfd/flexcan/...）
```

这个抽象对链路的收益是实打实的：

- **多应用共享有序**：协议栈统一排队与过滤，安全监控应用和控制应用各开一个 socket、各设各的过滤器，互不感知；
- **过滤下沉到内核**：`setsockopt(CAN_RAW_FILTER)` 让应用只收关心的 ID，用户态不被无关帧吵醒——这在 1ms 周期的机器上就是抖动预算；
- **工具链通用**：`candump can0` 抓帧、`cansend` 发帧、`cangen` 打压力、`ip -details link show can0` 看错误计数——排查不用等写代码；
- **bcm 协议代发周期帧**：`can_bcm` 可以在内核里按周期自动发帧，用户态不用自己开定时器线程。

启用与收发骨架（CAN FD，仲裁段 500kbps、数据段 2Mbps）：

```bash
ip link set can0 down
ip link set can0 type can bitrate 500000 dbitrate 2000000 fd on
ip link set can0 up
ip -details -statistics link show can0    # 错误计数在这里看
```

```c
int s = socket(PF_CAN, SOCK_RAW, CAN_RAW);

struct ifreq ifr = {0};
strcpy(ifr.ifr_name, "can0");
ioctl(s, SIOCGIFINDEX, &ifr);

struct sockaddr_can addr = {
    .can_family = AF_CAN,
    .can_ifindex = ifr.ifr_ifindex,
};
bind(s, (struct sockaddr *)&addr, sizeof(addr));

/* 只收急停帧 0x001 和故障上报 0x100~0x1FF */
struct can_filter rfilter[2] = {
    { .can_id = 0x001, .can_mask = 0x7FF },
    { .can_id = 0x100, .can_mask = 0x700 },
};
setsockopt(s, SOL_CAN_RAW, CAN_RAW_FILTER, &rfilter, sizeof(rfilter));

struct can_frame frame;
read(s, &frame, sizeof(frame));     /* 阻塞等帧；帧带硬件时间戳可选 */
```

`struct can_frame` 就是 CAN 帧的 C 语言化身（ID + 最多 8 字节数据）——协议细节见 B-D.11.1/11.2，这里只需记住：**socket 层的每个字都是标准语义，CAN 的特殊性被压缩进了帧结构和几个 sockopt 里**。

CAN FD 的收发只差两个开关：用 `canfd_frame`（数据到 64 字节）、显式声明接受 FD 帧：

```c
/* 收发 FD 帧前必须显式使能，否则 FD 帧被协议栈丢弃 */
int enable = 1;
setsockopt(s, SOL_CAN_RAW, CAN_RAW_FD_FRAMES, &enable, sizeof(enable));

/* 发送一帧 FD：ID 0x381，12 字节力传感器数据 */
struct canfd_frame fd = {
    .can_id = 0x381,
    .len    = 12,               /* FD 允许 0~8, 12, 16, ... 64 */
    .flags  = CANFD_BRS,        /* 数据段切到 2Mbps（双波特率） */
};
memcpy(fd.data, force_samples, 12);
write(s, &fd, sizeof(fd));
```

`CANFD_BRS` 这个标志位对应前面说的双波特率：**置位表示这帧的数据段用高速率发**——仲裁段所有人 500kbps 对齐，ID 比完之后数据段切 2Mbps。注意它是逐帧属性：同一条总线上可以混发带 BRS 和不带 BRS 的帧，配置波特率时 `dbitrate` 是对整条链路的全局约定，BRS 只决定单个帧用不用它。

## <span class="blue">CAN FD：预算意义上的两件事 [E]

CAN FD 相对经典 CAN 改了两处，都要翻译成预算语言：

1. **数据段 8 → 64 字节**：同样一帧能搬 8 倍数据。对事件型链路意味着原本要分包的大数据块（固件参数、波形片段）一帧搞定，占用总线的时间反而更短。
2. **双波特率**：仲裁段保持原速（多主仲裁要求所有节点同速），数据段可切到 2~5Mbps——**帧的"占线时间"大幅缩短**。

占线时间缩短直接改善 27.1 意义上的最坏延迟：高优先级帧等待上界 = 当前在传最长帧的剩余时间，帧越短上界越小。所以即使数据量没变，CAN FD 也在买确定性——这是选型时容易被"我数据不多，经典 CAN 够用"漏掉的论点。

## <span class="blue">错误帧激增：链路级排查 [E]

CAN 硬件会把物理层问题翻译成软件可见的计数与状态，排查路径是固定的。先看控制器自己的错误状态机——它由两个硬件计数器驱动：

> TEC（Transmit Error Counter，发送错误计数）/ REC（Receive Error Counter，接收错误计数）：每个 CAN 控制器里的两个 8 位计数器。规则大方向是"出错加分、成功减分"：发送出错 TEC +8，成功发送一帧 TEC -1；接收出错 REC +1（主动报错时更多），成功接收 REC -1。**加分比减分狠**，所以健康总线上计数恒在 0 附近，持续上升的计数本身就是故障证据。

两个计数器把节点推进三种状态，这就是前面说的错误状态机：

```
 TEC<128 且 REC<128        任一计数 ≥128            TEC ≥256
 ┌──────────────┐   →    ┌──────────────┐   →    ┌──────────────┐
 │ error-active │        │ error-passive│        │   bus-off    │
 │ 正常收发      │        │ 可收发，但    │        │ 脱离总线      │
 │ 主动报错      │        │ 只能被动报错  │        │ 一帧不发      │
 └──────────────┘   ←    └──────────────┘        └──────────────┘
                  两计数回落到 127 以下自动回来      只能靠恢复策略回来
```

设计意图值得体会：一个持续发错误帧的节点会先被降级（passive：报错方式从"打断总线"变成"安静标记"），再被隔离（bus-off）——**故障节点被硬件逐出总线，健康节点不受拖累**。这是 CAN 多主架构敢用在安全场合的底气，但也意味着"某节点突然沉默"可能不是死了，是被隔离了。

> bus-off 恢复策略：节点进入 bus-off 后怎么回来，是链路级设计决策而非驱动细节。两种选择：`ip link set can0 type can restart-ms 100`（内核定时自动重启，快但可能在故障未排除时反复进出——TEC 每次重上 0 又从 0 涨，表现为总线周期性"抽搐"）或应用监控 bus-off 事件后走自己的恢复流程（慢但可控，可以配合报警与降级，恢复前先查物理层）。安全相关链路通常选后者——自动恢复把"节点死了"和"节点刚回来"变得不可区分。

"错误帧激增"这个现场高发问题，按概率排序的排查表：

| 排查项 | 验证方法 | 典型根因 |
|:---|:---|:---|
| 终端电阻 | 断电量 CANH-CANL 电阻，应为约 60Ω（两个 120Ω 并联） | 漏装/多装终端、节点被摘掉后链路失配 |
| 波特率与采样点 | 示波器量位宽；核对各节点配置 | 某节点采样点不一致，高速率下边际出错 |
| 布线与接地 | 看拓扑：是否双绞、屏蔽层单端接地、支线长度 | 星型接线、支线过长反射、与动力线并行 |
| 单一节点发疯 | 逐个下电隔离，看错误计数是否消失 | 某节点收发器损坏，持续往总线上灌错误 |

表里"采样点"展开算一笔，它是波特率配置里最常被随手填的参数。CAN 的一个位时间被切成若干时间份额（tq），接收方在位内的某个份额处采样电平——**采样点 = 采样时刻占整个位时间的百分比**。500kbps 位时间 2000ns，假设控制器时钟 40MHz（tq = 25ns），一位 80 个 tq：配同步段 1tq + 相位段 1 共 69tq，则采样点在 (1+69)/80 = **87.5%**。CiA 推荐值就是 87.5%（高速）或 75%~87.5% 区间。两个节点采样点一个配 75% 一个配 87.5%，低速率下都能蒙对，速率一高、线缆一长，边沿传播延迟让"该采样的时刻"错位——表现为**偶发**位错误，正是"错误帧激增"里最难复现的那一类。所以排查第二行不是核对"波特率一不一样"，是核对"位时序参数一不一样"——`ip -details link show can0` 会把 tq、采样点全列出来，逐节点对比即可。

> 💡 `candump can0` 里看到的不只是数据帧——配置 `CAN_RAW_ERR_FILTER` 后错误帧也能抓，错误帧的类型位会直接告诉你方向（位错误/格式错误/ACK 错误）。ACK 错误高发而数据收发正常，多半是"总线上只剩一个活节点"——没有人为它应答。

## <span class="blue">本节总结

CAN 在工业链路里的角色是事件型数据：与 EtherCAT 搭配而非竞争，确定性含义是"高优先级帧等待时间有上界"。这个上界来自 ID 逐位仲裁——ID 分配表就是调度表，评审 CAN 设计先审 ID 表；上界可以算术化（最长帧占线时间），CAN FD 缩短占线时间因此也在买确定性。

SocketCAN 把 CAN 抽象成网络设备：多应用共享、过滤器下沉内核、can-utils 工具链通用——架构收益最终都落在抖动预算与排查效率上。错误处理硬件化带来独特的分诊路径：错误状态机（active→passive→bus-off）加错误帧类型位，bus-off 恢复策略（自动 restart-ms vs 应用控制）是必须评审的链路级决策；"错误帧激增"按终端电阻→采样点→布线接地→单节点隔离的顺序查，物理层永远是头号嫌疑人。
