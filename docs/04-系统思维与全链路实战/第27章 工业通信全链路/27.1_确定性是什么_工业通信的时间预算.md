# 27.1 确定性是什么：工业通信的时间预算

> 所属章节：第27章 工业通信全链路
>
> 难度：[E] | 预计阅读时间：25分钟

## <span class="blue">本节导读

先看两个真实系统的验收标准：

- 协作机械臂：EtherCAT 主站周期 1ms，要求"每个周期的实际间隔与 1ms 的偏差不超过 ±20μs"；
- 五轴 CNC 机床：控制周期 125μs，要求"最大抖动小于 5μs"——注意不是平均抖动，是**最大**抖动。

这两个标准里没有一个字提到"快"。1ms 周期不快（千兆以太网 12μs 就能传一帧），难的是**第一百万个周期和第一个周期一样准**。这就是工业通信与办公网络的本质区别，也是本章全部六节服务的对象。

> 本节覆盖：度量确定性的三个量（周期、抖动、deadline，含实测数据演算与周期来源）、办公以太网为什么天生不确定、为什么"错过 deadline 是错不是慢"、1ms 控制周期被哪些环节花掉（全链路解剖、时间预算表与超支演练）、确定性失败的三类姿势（超时、spike、丢同步）、抖动的主要来源与测量工具（cyclictest 读法、烤机设计、误读清单），以及"先定预算、再选总线、再配 RT、最后验证"的全章方法论。

## <span class="blue">确定性不是快：三个量 [E]

日常说一个系统"实时"，通常意思是"响应快"。工业上这个词有严格定义：**实时 = 结果正确 + 在 deadline 之前完成**，两条缺一不可。把定义拆开，度量一个工业通信链路只用三个量：

> 周期（cycle time）：控制循环的名义间隔。机械臂 1ms、CNC 125μs、PLC 常见 4~10ms。周期由控制算法的需求决定（采样定理、电机带宽），不是通信系统能选的——通信系统的任务是在这个周期内把该传的数据传完、该算的算完。

<!-- -->

> 抖动（jitter）：相邻周期实际间隔与名义周期的偏差。1ms 周期实测 0.98ms、1.03ms、0.99ms……偏差的最大值就是最大抖动。抖动比延迟更致命：伺服电机把周期当时间基准用，周期不稳，微分环节算出的速度就是噪声，表现为电机振动、加工表面振纹。

<!-- -->

> deadline：单次周期内各环节允许花掉的时间上限。1ms 周期不是"每 1ms 醒来一次"就完事——醒来之后，读传感器、跑算法、写输出必须在下一个周期到来前完成，且通常要求留出余量（完成的时刻不能贴着周期末尾）。

这三个量里，**平均值都没有意义，有意义的只有最坏值**。平均延迟 50μs 的系统，如果每十万次有一次 2ms，对办公网络是 99.999% 的优等生，对运动控制是每小时失控几十次的残次品。工业通信的设计、测量、验收全部围绕最坏值展开，这是与普通软件开发最大的思维差异。

把三个量放到一组实测数据上过一遍。某机械臂主站 1ms 周期，连续 6 个周期的实际唤醒间隔（μs）：

```
1001, 998, 1002, 999, 1087, 1000
```

- **周期**：名义 1000μs，控制算法定的，不改；
- **抖动**：各次偏差 +1、-2、+2、-1、**+87**、0——最大抖动 87μs。注意前四次的"优秀"不能抵消第五次的 87，验收标准卡的就是这个 87；
- **deadline**：假设预算给"读传感器 + 算法 + 写输出"共 800μs。第 5 次唤醒晚了 87μs，该周期可用时间被挤压到 713μs——要么算法在更短时间内完成，要么这一次就是错过 deadline。

周期 1ms 这个数字从哪来？从被控对象来：电机电流环带宽通常在 kHz 级，速度环几百 Hz，位置环几十到一百 Hz。控制周期要显著快于被控环路的带宽（经验值 10~20 倍），否则数字控制引入的相位滞后会让系统不稳。机械臂位置环约 100Hz → 控制周期 1ms 是十倍关系；CNC 高动态插补要求更严，所以压到 125μs。**周期是物理世界提的需求，通信系统只是满足它**——"先定预算"的第一步，其实是先和控制算法工程师对表。

最后再回答一个零基础读者最常问的问题：**办公以太网为什么做不到这些？**不是速度问题，是语义问题。办公以太网从设计那天起就是"尽力而为"：交换机缓冲队列在拥塞时排队（排队时长不可预测）、TCP 丢包重传（一次重传就是毫秒级）、网卡中断合并（攒几个包才打断 CPU，拿延迟换吞吐）。这些机制每一个都在优化平均吞吐，代价全是最坏延迟无界。工业通信的全部机制——27.2 的飞读飞写、27.4 的时间门控——本质上都是在把这些"不确定"逐个换成"有界"。

顺带把"实时"的分级说清，后面章节会反复用到：

> 硬实时（hard real-time）：错过 deadline = 系统失效，后果不可接受——运动控制、安全回路。验证方式是**证明最坏值有界**，而不是测试很多次没出问题。

<!-- -->

> 软实时（soft real-time）：错过 deadline = 品质下降，可以容忍偶发——音视频流掉一帧是杂音不是事故，HMI 刷新晚 50ms 没人受伤。

两者之间还有一类叫固实时（firm real-time）：错过即作废但不致命——机器人视觉识别的一帧，迟到就丢弃等下一帧。注意一台真实机器上三种任务几乎总是并存：控制环是硬实时、视觉是固实时、HMI 与日志是软实时。27.5 的优先级与隔离设计，本质上就是在同一颗 CPU 上给这三种任务划地盘、并且保证低等级任务永远抢不走高等级任务的资源。

## <span class="blue">错过 deadline 是"错"，不是"慢" [E]

办公系统超时，用户体验是"卡了一下"。运动控制错过 deadline，后果是物理世界的错误：

| 场景 | 错过 deadline 的物理后果 |
|:---|:---|
| 机械臂转矩控制 | 转矩指令迟到，电机实际出力与规划轨迹脱节，轻则抖动，重则触发伺服驱动器过流保护、整轴急停 |
| CNC 插补 | 位置指令迟到，刀具多走或少走一个增量，工件报废；五轴联动时可能撞刀 |
| 多轴同步（龙门双驱） | 两轴指令不同步到达，机械结构承受扭转应力，长期累积精度丧失 |
| 安全回路（STO/急停） | 安全信号迟到，法定责任问题，不是技术问题了 |

所以工业链路里"超时"的处理方式也不是重试——重试在下一个周期才完成，数据已经过期，过期指令比没有指令更危险。正确的处理是**报警、计数、进入降级或急停**。"降级"是具体的设计动作，不是口号：机械臂限速 30% 运行保持可干预、龙门轴回参考点、CNC 停主轴保留坐标系——每个产品都要在自己的 FMEA（失效模式分析）里把"哪类超时进哪种降级"写死。这个原则会贯穿 27.2（EtherCAT 从站超时）和 27.3（CAN 错误帧）的排查逻辑。

## <span class="blue">全链路解剖：1ms 被谁花掉了 [E]

把一个控制周期从"传感器锁存"到"执行器动作"拉成一条链，数据要经过七段：

```
 传感器        总线         主站/控制器接收      调度         控制算法       输出          执行器
 锁存          传输         协议栈处理           唤醒         计算           写入          响应
  │            │            │                  │            │             │             │
 编码器        EtherCAT     MAC驱动→IGH        定时器       PID/轨迹       PDO写入       伺服
 同时采样      帧逐站       ec_master收到      hrtimer到期  插补           帧发出        转矩
 (DC同步)     飞读飞写     PDO数据            RT线程       运算           (回程帧)      建立
  │            │            │                  │ 被唤醒      │             │             │
  ~1μs        ~10-30μs     ~10-50μs           2-20μs      50-500μs     ~10-30μs      ~100μs
  (硬件保证)   (拓扑决定)   (协议栈决定)       (RT配置决定)  (算法复杂度)   (拓扑决定)    (电机物理)
```

每一段的时间来源完全不同，这就是"全链路"视角存在的理由：**优化任何单独一段都可能对总预算无效**——把 EtherCAT 从 1ms 提到 250μs，调度唤醒抖动 50μs 没解决，系统仍然不合格。大纲给出的 1ms 周期时间轴就是一张预算分配表：

| 时刻 | 环节 | 预算 | 由谁保证 |
|:---|:---|:---|:---|
| 0μs | EtherCAT 读 PDO（上一周期从站锁存的传感器数据到达） | ~30μs | 主站配置（27.2） |
| 100μs | 传感器数据在用户空间可用 | ~70μs | 协议栈 + 调度唤醒（27.2/27.5） |
| 300μs | 控制算法完成（PID/插补/PLC 逻辑） | ~200μs | 算法实现 + CPU 隔离（27.5） |
| 700μs | 输出写入完成（PWM/PDO 发出） | ~400μs | 总线回程（27.2） |
| 900μs | 状态上报（OPC UA/日志，非实时） | 弹性 | 低优先级线程（27.5） |
| 1000μs | 下一周期开始 | — | 定时器精度（27.5） |

注意表里两个刻意的设计：**重活（算法）只分到 200μs，但前面留了 100μs 才动手**——这是在给抖动留吸收空间；**状态上报放在最后且允许被挤占**——非实时任务进预算表的唯一姿势就是"可被推迟"。预算表不是平均分配，是优先级分配。

每一段都有各自的测量手段——排查的第一步永远是"把超标定位到段"，没有这张对照表，"系统慢了"只能靠猜：

| 段 | 用什么量 | 量的对象 |
|:---|:---|:---|
| 传感器锁存 | 示波器 / DC 寄存器 | SYNC0 信号的实际相位 |
| 总线传输 | 主站统计 / 协议分析仪 | 帧发出到折返的时间 |
| 协议栈处理 | ftrace / 应用内时间戳 | 中断到数据可用 |
| 调度唤醒 | cyclictest / ftrace wakeup 事件 | 定时器到期到线程运行 |
| 控制算法 | 代码内 `clock_gettime` 打点 | 函数入口到出口 |
| 输出写入 | 主站统计 | 数据就绪到帧发出 |
| 执行器响应 | 电流探头 / 编码器回读 | 指令到达到物理动作 |

> 💡 预算表还有一条不成文的纪律：所有环节最坏值加起来不超过周期的 70%。剩下的 30% 不是浪费，是给"还没想到的抖动源"留的——27.6 会看到，SMI 这种东西永远存在，区别只是你有没有余量接住它。

### 预算超支演练：一个周期是怎么崩的

假设算法某次走了条慢路径，耗时从 200μs 变成 350μs。对照预算表走一遍连锁反应：

1. 算法在 300μs 时刻没完成，拖到 450μs 才交出结果；
2. 输出写入从 700μs 顺延到 850μs——侵占了状态上报段，没关系，上报本来就允许被挤占；
3. 但输出帧 850μs 才发出，从站收到指令的时刻错过了 DC 对齐点——本周期转矩指令迟到，电机感受到的就是一次"小抖动"，加工件上留下一道几乎不可见的纹；
4. 如果超支更多（比如 600μs），输出错过整个周期窗口，伺服驱动器的通信看门狗超时——进入前面说的报警/降级路径。

这个演练的价值在定位：**同样表现为"电机抖了一下"，根因在算法段、传输段还是调度段，肉眼分不出来，要靠预算表逐段对时间戳**。27.6 的排查链就是把这个演练反过来做——从症状出发，逐段对表，收敛到超支的那一段。

## <span class="blue">确定性失败的三类姿势 [E]

与第 21 章 OTA 一样，先把"会怎么死"列清楚，再谈防御。工业通信链路的失败姿势三类：

### 姿势一：周期超时——稳定地来不及

控制算法在某条路径上耗时超过预算，或者总线负载超过周期容量，**每个周期都超时或大概率超时**。这是设计错误，不是故障：预算表没算对、算法复杂度失控、PDO 映射了太多变量。排查方法是量每一段的实际耗时（ftrace、IGH 的 `ethercat master` 统计），对照预算表找到超支的段。

### 姿势二：jitter spike——偶发地来不及

系统 99.99% 的时间合格，偶发一次超标：SMI（BIOS 的系统管理中断，x86 平台特有）、page fault（没锁内存的线程触页）、中断风暴（某个外设发疯）、DVFS 频率切换、另一个核上的线程抢 L3 缓存。**这是工业现场最难缠的一类**——实验室测不出来，上量才暴露，复现靠运气。27.5 的 RT 配置和 27.6 的 SMI 排查链主要就是对付它。

### 姿势三：丢同步——时钟源漂移

EtherCAT DC 参考时钟漂移、gPTP 主时钟切换或失锁，多轴"各自准时、互相不同步"。这类失败数据上不超时、抖动也不大，但轴间相位差在变化，对龙门双驱、电子凸轮是慢性毒药。防御是时间同步本身的监控（27.2 的 DC 漂移、27.4 的 gPTP 状态）。

三类姿势对应三种完全不同的防御体系：**超时靠预算设计与容量规划，spike 靠系统配置与平台选择，丢同步靠时钟架构与监控**。把它们混为一谈、统一当作"实时性不好"去调 PREEMPT_RT 优先级，是现场最常见的误诊。

## <span class="blue">抖动从哪来，怎么量 [E]

spike 类失败既然最难缠，先把已知抖动源列成清单——这是 27.5 配置工作的总依据：

| 抖动源 | 量级 | 平台 | 对策所在节 |
|:---|:---|:---|:---|
| SMI（BIOS 温度监控等） | 50~500μs | x86 | 27.6（BIOS 层处理） |
| page fault（未锁内存） | 10~100μs | 全平台 | 27.5（mlockall） |
| 中断抢占（网卡/磁盘中断打到 RT 核） | 5~50μs | 全平台 | 27.5（irq affinity） |
| DVFS 频率切换 | 5~20μs | 全平台 | 27.5（定频） |
| tick 中断（HZ 周期打扰） | 1~10μs | 全平台 | 27.5（NO_HZ_FULL） |
| 缓存争抢（其他核跑内存密集型任务） | 1~30μs | 多核 SoC | 27.5（CPU 隔离） |

测量工具是 rt-tests 套件里的 cyclictest——它做的就是"以固定周期唤醒，记录每次实际间隔与名义值的偏差"，直接产出抖动分布。Buildroot/Yocto 里都有（Buildroot：`BR2_PACKAGE_RT_TESTS`），交叉编译后在目标板上跑：

```bash
# 周期1ms，跑10万次，SCHED_FIFO优先级99，锁内存，直方图输出
cyclictest -p 99 -m -i 1000 -l 100000 --histogram=2000 -h 100
```

关键参数：`-p 99`（实时优先级，模拟真实控制线程）、`-m`（锁内存，否则你在测量 page fault 而不是调度器）、`-i 1000`（周期 1000μs）。输出长这样：

```
# Histogram
000000 000000  000000 000000  098712 000000  000000 000000  ...
# Min Latencies: 00002 00002
# Avg Latencies: 00005 00005
# Max Latencies: 00011 00247
```

读法分三步，顺序不能乱：

1. **先看 Max 列的最大值**——直方图每个数值一列、按 CPU 分组，`098712` 出现在哪一列表示该 CPU 落在对应延迟桶里的次数。Max 列是唯一与验收标准对应的数；
2. **再看直方图的"尾巴"**：本例 98712 次集中在一个桶里、尾部零星散着几次高延迟——典型的"偶发 spike"形态。尾巴上的每一次都要追到源头，不能当噪声扔掉；
3. **最后才看分布主体**：主体紧贴理论下限，说明常态路径干净；主体本身就很宽，说明基础配置就没做对（比如没打 PREEMPT_RT）。

这例里第二个 CPU 出现过一次 247μs——平均值 5μs 毫无意义，**那个 247 就是系统的真实答卷**。

一次合格的验证不是跑一遍命令就完事，烤机设计至少覆盖三个维度：

| 维度 | 做法 | 针对的抖动源 |
|:---|:---|:---|
| 时长 | 至少数小时，关键设备过夜 | 温度漂移、定时事件（cron、日志轮转） |
| 负载 | 同时用 `stress-ng` 打满 CPU/内存/IO，模拟业务高峰 | 缓存争抢、中断压力、内存回收 |
| 工况 | 覆盖冷热机状态与真实业务（电机真的在动） | 温度降频、真实中断流量 |

三个最常见的误读，每一个都有团队踩过：

- **忘记 `-m` 就下结论**：没锁内存时量到的是 page fault 与调度器的混合体，数值偏大且不可比——先把内存锁住，量到的才是调度器本身的账；
- **只在空载系统上测**：空载 5μs 的系统满载可能 50μs，验收必须在业务压力下做；
- **拿 Avg 写报告**：平均值在工业验收里没有地位——现场的电机按最坏值抖，不按平均值抖。

> ⚠️ cyclictest 量的是调度器到用户线程这一段，不含总线。完整链路抖动要用 EtherCAT 主站自带的统计（`ethercat master` 的 cycle time 分布）和应用层打时间戳联合判断。27.6 的排查链会演示怎么把"超标"一步步定位到具体哪一段。

## <span class="blue">本章的方法论 [E]

把本节的逻辑收拢成工作顺序，后面五节严格按它走：

1. **先定预算**——从控制算法需求出发定周期与抖动指标，画出时间预算表（本节）；
2. **再选总线**——按预算里的传输段要求选 EtherCAT / CAN / TSN，协议细节指 B 扩展（27.2~27.4）；
3. **再配 RT**——按抖动源清单逐项配置 CPU 隔离、锁内存、中断亲和（27.5）；
4. **最后验证**——cyclictest + 主站统计 + 长时间烤机，超了就用排查链定位（27.6）。

## <span class="blue">本节总结

确定性用三个量度量：周期（名义间隔）、抖动（偏差的最大值）、deadline（单次完成上限）——平均值没有意义，只有最坏值算数。错过 deadline 是错误不是慢，所以工业链路的超时处理是报警与降级，不是重试。

1ms 周期被七段环节花掉：传感器锁存、总线传输、协议栈、调度唤醒、控制算法、输出写入、执行器响应——每段时间来源不同，只优化一段可能毫无效果，预算表按优先级分配且总量不超过 70%。失败姿势三类：稳定超时（设计错误，查预算）、偶发 spike（配置与平台问题，最难缠）、丢同步（时钟架构问题），误诊成"实时性不好"统一调优先级是现场大忌。测量用 cyclictest，看 Max 列不看 Avg。
