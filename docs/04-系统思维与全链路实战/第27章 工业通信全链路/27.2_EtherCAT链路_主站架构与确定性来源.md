# 27.2 EtherCAT 链路：主站架构与确定性来源

> 所属章节：第27章 工业通信全链路
>
> 难度：[E] | 预计阅读时间：25分钟

## <span class="blue">本节导读

27.1 的预算表里，"总线传输"一段只分到约 30μs——一帧数据要串过 6 个伺服驱动器加若干 IO 模块，每个站都要读走输入、写入输出。用标准以太网的玩法（每个站一问一答），6 个站就是 6 次收发往返，光协议栈处理就奔着几百微秒去了，预算当场破产。EtherCAT 能用一帧解决，靠的不是更高的波特率——它跑的就是普通 100M/1G 以太网——而是两个独特的机制：**飞读飞写**和**分布式时钟**。

> 本节覆盖：飞读飞写消灭了链路里的哪段开销（含 FMMU/SyncManager 两个硬件单元）、分布式时钟的三步校准机制消灭了 27.1 失败姿势里的哪一种、IGH 主站的架构（专用 MAC 驱动为什么绕开内核协议栈、ec_generic 折中的量化代价）、Domain/PDO/cycle time 三个核心概念、1ms 周期主站应用的完整形态（ecrt 骨架 + RT 线程 + 两个必踩的坑），以及从站偶发超时的分诊表与两个真实排查场景。

---

## <span class="blue">飞读飞写：一帧串起所有站 [E]

标准以太网通信是"存储转发"：帧到一个节点，整个收下来、校验、处理、再发出。如果主站要和 6 个从站交换数据，直观方案是 6 个帧各走一趟。EtherCAT 的做法完全不同——**一帧从主站发出，像火车一样依次经过每个从站，每个站在帧经过自己身边的瞬间，从分配给自己的车厢里取走上周期准备好的输入数据、放下本周期的输出数据，帧走到队尾自动折返，回到主站时读写已全部完成**。

```
 主站 ──▶ [站1: 读车厢1/写车厢1] ──▶ [站2: 读车厢2/写车厢2] ──▶ ... ──▶ [站N] ──┐
   ▲                                                                              │
   └────────────────────── 帧折返，读写俱毕 ◀─────────────────────────────────────┘
```

这个机制对时间预算的意义是决定性的：

- **传输时间与站数近似线性、且系数极小**。每个站引入的只是"帧经过身边"的硬件延迟（约 1μs 量级），不是一次完整的收发处理。6 个站的链路，传输段实测就是十几到三十微秒——预算表里那 30μs 是这么来的。
- **没有协议栈排队**。一个周期就一帧（或少数几帧），不存在"6 个响应包在网卡队列里排队"的不确定性。
- **从站零软件参与**。数据处理在从站的 ESC（EtherCAT Slave Controller）硬件里完成，从站 CPU 慢、忙、甚至跑的是裸机，都不影响帧的通行时间——传输段的确定性是硬件给的，不依赖任何一端的软件质量。

"车厢"在硬件里是怎么实现的？两个 ESC 内部的单元值得知道名字，排查和读从站手册时会反复遇到：

> FMMU（Fieldbus Memory Management Unit，现场总线内存管理单元）：ESC 里的地址翻译器。主站把整列车看成一个连续的"逻辑地址空间"（比如 4GB 里的一段），每个从站的 FMMU 配置成"逻辑地址 X 到 X+n 映射到本站的物理内存 Y"。帧经过时，FMMU 比对地址、命中就读写——这就是"取走自己车厢"的物理动作。主站侧 `ethercat master` 看到的 Domain 数据区，就是这段逻辑地址空间的镜像。

<!-- -->

> SyncManager（同步管理器）：ESC 里管数据一致性的缓冲控制器。它保证"主站读走的输入"和"从站应用正在写的输入"不会撞车——典型配置是三段缓冲（类似三缓冲翻页），飞读飞写读的是已完成的上一帧数据，从站应用写的是下一帧。从站手册里每个 PDO 通道都会标注挂在哪个 SyncManager 下。

这两个单元解释了飞读飞写为什么**快且不乱**：快在地址比对是硬件组合逻辑（纳秒级），不乱在缓冲一致性由 SyncManager 兜底。对应用工程师，它们是"配置项"；对排查工程师，它们是"从站手册里必须核对的两张表"。

> 💡 这也是 EtherCAT 诊断的一个反直觉点：从站应用卡死，帧照样过、其他站照样正常——所以"链路通"不代表"从站健康"，从站状态要单独监控（状态机是否在 OP、AL status code），后面排查一节会用到。

## <span class="blue">分布式时钟：消灭"各站各的时刻" [E]

27.1 失败姿势三是"丢同步"——各轴各自准时、互相不同步。没有同步机制时，6 个伺服各自用自己的本地时钟锁存编码器：哪怕每个都准到微秒级，它们的采样**时刻**互不相同，主站拿到的是 6 个不同时刻的位置快照，插补算法算出的轨迹天然带相位误差。

EtherCAT 的答案是 DC（Distributed Clock，分布式时钟）：每个从站的 ESC 里有一个硬件时钟，主站负责把它们全部校准到**同一个纳秒级时间基准**上。校准不是一次性的动作，是持续进行的三步机制：

1. **选定参考时钟**：主站把链路上第一个支持 DC 的从站的时钟设为全系统基准，其他所有站都与它对齐；
2. **测量传播延迟**：帧到站有先后，主站通过测量帧到各站的往返延迟，算出每个站与参考站之间的传输时间差，写进各站的偏移寄存器——没有这个补偿，"同时"在链路上天然不成立（站 1 和站 60 收到同一帧差着几十微秒）；
3. **持续漂移补偿**：每个从站持续比较本地时钟与（经延迟补偿后的）参考时钟，用硬件锁相环微调本地时钟速率——晶振有温漂，只校准一次的话几分钟就漂散了，所以补偿必须随帧持续进行。

对齐之后由 DC 产生 SYNC0 硬件信号，所有从站在**同一物理瞬间**锁存输入、应用输出。回到 27.1 的链路解剖表：第一行"传感器锁存 ~1μs（硬件保证）"就是 SYNC0 干的事——6 个轴的编码器在同一个微秒内采样，主站收到的 PDO 是一张"同一时刻的全家福"，而不是 6 张不同时间的单人照。多轴同步应用（龙门双驱、电子凸轮、飞剪）没有 DC 根本无从谈起。

> DC 漂移：从站时钟与参考时钟之间未被校正的残余偏差。正常系统里它应该被第三步压在百纳秒量级上下小幅波动；如果主站日志里漂移**持续单向增大**，说明补偿回路没工作——常见原因是参考站选错、某段链路传播延迟不稳定（线序、干扰、拓扑变动），属于 27.1 说的"丢同步"类失败的前兆。

## <span class="blue">IGH 主站：为什么绕开内核协议栈 [E]

Linux 上的开源主站实现是 IGH EtherCAT Master（EtherLab 项目），它的架构选择本身就是一节链路课：

```
用户空间                     内核空间                        硬件
┌──────────────┐    ┌──────────────────────┐    ┌────────────────┐
│ 控制应用      │    │ ec_master 模块        │    │ 以太网 MAC      │
│ ecrt API     │───▶│ 状态机/DC同步/PDO交换 │───▶│                │
│ ecrt 工具    │    │ ec_igc / ec_generic   │───▶│ PHY → RJ45     │
│ (扫描/诊断)  │    │ (专用MAC驱动)          │    │ 从站1...从站N   │
└──────────────┘    └──────────────────────┘    └────────────────┘
```

关键设计是 **ec_igc / ec_e1000e 这类专用 MAC 驱动**：它们接管网卡，把 EtherCAT 帧直接塞进 MAC，**完全绕开内核网络协议栈**（socket、qdisc、iptables 全不参与）。对照第 26 章的纵向链路，这相当于在"网络设备层"开了个专用岔道。绕开的理由用 27.1 的语言说：协议栈的每一层都是不确定的队列与锁，而 EtherCAT 帧根本不需要 IP、不需要路由、不需要任何"网络"语义——它要的是确定性的 MAC 直发。代价是这块网卡从此归 EtherCAT 专用，不能再配 IP 上网。

调试期可以用 `ec_generic` 驱动折中：它借用内核原生网卡驱动收发，不用为特定网卡编译专用模块。代价要量化着说：原生驱动路径带中断合并、队列调度和锁竞争，收发时序的不确定性大约增加 10~30μs 量级——对 4ms 周期的调试环境无所谓，对 1ms 以下周期的量产系统就是预算的 10% 以上。所以工程惯例是：**开发用 generic 快速迭代，量产切换到与网卡匹配的专用驱动**，切换的成本只是改主站配置里的驱动名，应用代码零改动。

主站侧的三个核心概念：

> Domain：一组需要在同一周期内同步交换的过程数据的容器。应用向 Domain 注册自己关心的 PDO 变量，主站按 Domain 组织每周期收发。大多数应用一个 Domain 就够；快慢任务分域（1ms 域管伺服、10ms 域管 IO）是进阶玩法。

<!-- -->

> PDO（Process Data Object，过程数据对象）：周期交换的数据单元——伺服的目标位置、实际位置、转矩指令、状态字。PDO 在从站上电配置阶段（SDO 通讯）就映射好，运行期只走飞读飞写，不带任何协议开销。非周期的参数读写（改伺服增益）走另一条 SDO 通道，不进实时预算。

<!-- -->

> Cycle Time：主站的收发周期，等于控制周期。IGH 本身不替你定时——定时是应用的事（hrtimer/`clock_nanosleep`），IGH 负责"被叫醒后把 PDO 交换做完"。这个分工决定了 27.5 的存在：定时与唤醒的确定性不归 EtherCAT 管，归 RT 配置管。

## <span class="blue">落到代码：1ms 周期的主站骨架 [E]

IGH 用户空间 API 是 ecrt 库。一个最小但结构完整的周期任务骨架（省略错误处理，实际工程照 IgH 官方 example 扩展）：

```c
static ec_master_t *master;
static ec_domain_t *domain;
static uint8_t *domain_pd;              /* Domain 过程数据映射区 */

static unsigned int off_actual_pos;     /* PDO 变量在映射区里的偏移 */
static unsigned int off_target_pos;

/* 上电初始化：PDO 映射在哪个从站、哪个索引，来自从站 ESI 文件 */
static ec_pdo_entry_reg_t domain_regs[] = {
    {0, 0, 0x607A, 0x00, &off_target_pos, NULL},  /* 目标位置 → 写入 */
    {0, 0, 0x6064, 0x00, &off_actual_pos, NULL},  /* 实际位置 ← 读出 */
    {}
};

void init(void)
{
    master = ecrt_request_master(0);            /* 申请 0 号主站 */
    domain = ecrt_master_create_domain(master);
    ecrt_domain_reg_pdo_entry_list(domain, domain_regs);
    ecrt_master_activate(master);               /* 配置冻结，进入周期交换 */
    domain_pd = ecrt_domain_data(domain);
}

/* 周期任务：被 27.5 的 RT 线程以 1ms 周期调用 */
void cyclic_task(void)
{
    ecrt_master_receive(master);            /* 收：取回折返帧 */
    ecrt_domain_process(domain);            /* 解包到 domain_pd */

    int32_t pos = EC_READ_S32(domain_pd + off_actual_pos);
    int32_t cmd = control_algorithm(pos);   /* 控制算法，预算表 300μs 段 */
    EC_WRITE_S32(domain_pd + off_target_pos, cmd);

    ecrt_domain_queue(domain);              /* 打包回程数据 */
    ecrt_master_send(master);               /* 发：帧再次出发 */
}
```

注意骨架里每个调用和 27.1 预算表的对应关系：`receive/process` 是"0μs 读 PDO"段，`control_algorithm` 是"300μs 算法"段，`queue/send` 是"700μs 输出"段——**时间预算表不是文档装饰品，它就是这个函数的执行时序**。EC_READ/WRITE 宏只是按偏移读写一块内存，所有总线动作集中在 `send/receive` 两次，这正是飞读飞写在 API 层的投影。

配套的问题是"谁来以 1ms 周期调它"——`cyclic_task` 不会自己跑起来。标准的驱动者是一个绝对时间定时的 RT 线程（27.5 会展开每项配置的工程理由，这里先把完整形态立住）：

```c
#define NSEC_PER_SEC 1000000000L
#define PERIOD_NS    1000000L            /* 1ms */

static void *rt_thread(void *arg)
{
    /* 三件套：RT优先级、锁内存、绝对时间定时 */
    struct sched_param param = { .sched_priority = 90 };
    sched_setscheduler(0, SCHED_FIFO, &param);
    mlockall(MCL_CURRENT | MCL_FUTURE);

    struct timespec next;
    clock_gettime(CLOCK_MONOTONIC, &next);

    while (running) {
        next.tv_nsec += PERIOD_NS;               /* 绝对时间累加 */
        while (next.tv_nsec >= NSEC_PER_SEC) {   /* 纳秒进位 */
            next.tv_nsec -= NSEC_PER_SEC;
            next.tv_sec++;
        }
        clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, &next, NULL);

        cyclic_task();                           /* 本节上面的周期函数 */
    }
    return NULL;
}
```

这段代码里藏着两个新手必踩的坑，先点名：

1. **必须用绝对时间（`TIMER_ABSTIME`）不能相对睡**。`usleep(1000)` 每次睡 1ms，加上任务本身的执行时间，实际周期是 1ms + 执行时间——每个周期都慢一点点，误差持续累积（周期漂移）。绝对时间定时是"以上次的理论到期点为基准算下次"，单次迟到不会传染给后续周期。
2. **`mlockall` 必须在进入循环前调用**，且栈要预先触碰。否则第一次 page fault 发生在周期循环里，那一个周期的延迟就是几十微秒——27.1 抖动源清单里的 page fault 就是这么进来的，cyclictest 的 `-m` 参数防的也是它。

## <span class="blue">验证与排查：主站自带的统计 [E]

预算合不合格不用猜，IGH 提供运行时观测：

```bash
ethercat master          # 主站状态：周期时间分布、最大/最小
ethercat slaves          # 各站状态机：PREOP/SAFEOP/OP
ethercat upload -p 0 0x6064 0   # SDO 读实际位置（诊断用，不走实时通道）
```

`ethercat master` 输出里的 cycle time 分布是 27.1 cyclictest 的总线侧对照：**cyclictest 告诉你线程醒得准不准，主站统计告诉你醒来之后收发花了多久**，两个数都在预算内，链路才是闭环的。

现场最高发的"从站偶发超时"，按 27.1 的三类姿势分诊：

| 症状 | 最可能类别 | 排查方向 |
|:---|:---|:---|
| 固定某站周期性地丢 | 超时（设计） | 该站 PDO 映射过大、拓扑过长、该站 ESC 处理慢 |
| 随机站、随机时刻丢 | spike | 主站周期不稳（cyclictest 对照）、物理层干扰（换线/查接地） |
| 多站同步误差缓慢变大 | 丢同步 | DC 漂移监控、主站参考时钟源、SYNC 配置 |

两个真实场景，演示分诊表怎么用：

**场景 A：固定是第 4 轴超时**。某六轴机械臂，运行中稳定地每几分钟报一次站 4 的 working counter 错误，其他站从不报错。对照分诊表第一行——固定站、规律性，属"超时（设计）"。查该站 PDO 映射：站 4 是带力控的腕部轴，调试时把力传感器原始数据（64 字节）也映射进了 1ms Domain，该站每周期要处理的数据量远超其他站。处置：力控数据挪到独立的 10ms Domain（快慢分域），1ms 域只留位置环必需变量，故障消失。教训：**PDO 映射"多映射点保险"的想法直接透支预算**，每个变量都要为它占的帧空间和处理时间辩护。

**场景 B：全随机、无规律的偶发丢站**。某产线机械臂，现场偶发随机站超时，实验室复现不了。对照第二行属 spike。先用 cyclictest 排除主站侧（结果干净），再查现场环境：发现超时时刻与隔壁工位焊接机启停强相关——焊机的电流突变通过共用地线耦合进 EtherCAT 线缆。处置：通信线与动力线分槽走线、屏蔽层单端可靠接地，超时率从每天数次降到零。教训：spike 类问题**先排物理层再排软件**，而"实验室复现不了"本身就是物理层问题的特征证词。

> ⚠️ 物理层在工业现场的权重远超办公室经验：编码器线、动力线与 EtherCAT 网线并行走线，变频器的 dv/dt 干扰足以造成偶发 CRC 错误。`ethercat slaves` 里某站的错误计数器持续增长，先怀疑线缆与接地，再怀疑软件。

## <span class="blue">本节总结

EtherCAT 的确定性来自两个硬件机制而非带宽：飞读飞写让一帧串完所有站（传输时间 ≈ 站数 × 1μs，与从站软件质量无关），分布式时钟让所有从站在同一物理瞬间锁存与输出（消灭"丢同步"类失败）。IGH 主站用专用 MAC 驱动绕开内核协议栈——协议栈的队列与锁对 EtherCAT 帧是纯负担。

三个概念落进预算：Domain 组织周期数据、PDO 是飞读飞写承载的变量、Cycle Time 由应用定时器而非主站负责——所以链路的确定性一半是 EtherCAT 给的（传输与同步），另一半要 27.5 的 RT 配置给（定时与唤醒）。验证靠 `ethercat master` 的 cycle time 分布与 cyclictest 双侧对照；从站超时按超时/spike/丢同步三类分诊，物理层干扰在分诊表里的权重要给足。
