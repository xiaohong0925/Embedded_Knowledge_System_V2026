# 25.4 DRM/KMS 显示通路实战

> 所属章节：第25章 Camera全链路：从Sensor到屏幕
>
> 难度：[E] | 预计阅读时间：45 分钟

## <span class="blue"> 本节导读

25.3 把帧数据零拷贝地送到了显示子系统手里——但"手里"是个黑盒。`drmModeSetPlane` 一调画面就上屏了，中间发生了什么？为什么有时候设 plane 报 EINVAL？为什么 camera 预览用 weston 桌面显示比直接写 plane 慢一整帧？这一节把显示这一半拆开。

DRM/KMS 的复杂度来自一个事实：现代显示控制器不是"一块 framebuffer 扫到屏幕"那么简单，它有多个硬件图层（plane）、多条显示管线（crtc）、多种输出接口（HDMI/DSI/eDP），而且这些资源的组合方式每款 SoC 都不同。内核用四个对象描述这套硬件，用 atomic commit 解决多对象更新的撕裂问题。本节覆盖：

- 显示控制器在干什么：scanout 与硬件图层
- DRM 四对象模型：plane / crtc / encoder / connector
- `modetest` 实操：读出你板子上显示资源的真实清单
- atomic commit：为什么必须"原子"，怎么用
- Direct Display vs Compositor：两条上屏路径的延迟差异与实测方法
- 显示侧高频故障：tearing、underrun、plane 能力超限

> 💡 面板侧协议（DSI 时序、eDP、LVDS）属于 B-C.9.3/9.4 的内容，本节只关心 SoC 内部"内存→显示控制器"这一段。

## <span class="blue"> 显示控制器在干什么

先建立硬件直觉。显示控制器（Display Controller，RK 平台叫 VOP，全志叫 DE，高通叫 DPU）的工作模型非常简单：**按帧率节拍（比如 60Hz），周期性地从 DDR 读出帧数据，按面板时序发出去**。这个过程叫 scanout——它不需要 CPU 参与，CPU 唯一的职责是在每帧开始前告诉它"下一帧扫哪块内存、扫多大、叠几层"。

关键在"叠几层"。现代显示控制器有多个**硬件图层**：最底下是主图层（primary plane），上面可以有若干叠加层（overlay plane），每层有独立的位置、大小、格式，硬件在 scanout 时实时合成。这就是 Camera 预览可以"零拷贝直接上屏"的硬件基础——camera 帧放 overlay plane，UI 放 primary plane，硬件合成，GPU 完全不用动。

> scanout：显示控制器从内存读像素、按面板时序（行同步/场同步/消隐期）逐行送出的过程。读速必须跟上节拍，供不上数据就是 underrun（本节末尾展开）。

<!-- -->

> vblank：两场画面之间的消隐间隔，是交换 buffer 的唯一安全时机——正在扫描中途换内存地址，屏幕上半部分是旧帧、下半部分是新帧，这就是 tearing（撕裂）。所有显示更新都必须等 vblank，这是理解 atomic commit 的前提。

## <span class="blue"> DRM 四对象模型

内核用四个对象描述上述硬件，每个对象对应显示通路的一段：

```
内存中的帧(buffer/FB)
      │
      ▼
   plane ──────► crtc ──────► encoder ──────► connector ──► 面板
  (图层：哪块内存)  (管线：合成+时序)  (接口转换：RGB→DSI)  (物理口：接的什么屏)
```

> plane：图层。绑定一块 framebuffer（25.3 的 dma-buf 就在这里挂上来），回答"显示哪块内存、缩放多少、放屏幕哪个位置"。分 primary（必有一个）、overlay（叠加）、cursor（鼠标）三类。

<!-- -->

> crtc：显示管线（CRTC 是历史命名，Cathode Ray Tube Controller）。把多个 plane 按 z-order 合成，生成像素流和扫描时序，回答"以什么分辨率、什么刷新率扫"。一个 crtc 同一时刻只驱动一路显示。

<!-- -->

> encoder：接口转换器。把 crtc 的像素流编码成具体接口信号（MIPI DSI、HDMI TMDS、eDP），通常对应用透明。

<!-- -->

> connector：物理连接器。代表 HDMI 口、DSI 面板本身，带着面板的能力信息（EDID/支持的分辨率列表）和连接状态（插拔检测）。

配置一路显示的本质就是串起一条链：plane 挂 FB → plane 绑 crtc → crtc 经 encoder 到 connector → 设置显示模式（mode）。每个对象有一组属性（property），atomic commit 做的事就是**把这条链上所有改动打包，在一个 vblank 边界一次性生效**。

## <span class="blue"> modetest 实操：读出真实资源清单

libdrm 自带的 `modetest` 是显示子系统的 media-ctl——配置之前先看清楚板子上有什么。Buildroot 开 `BR2_PACKAGE_LIBDRM_INSTALL_TESTS` 获得。

```
modetest -M rockchip
```

输出按对象分四段，下面是 RK3568 的典型形态（删减标注版）：

```
Connectors:                                    ← 物理口清单
id      encoder status          name            size (mm)   modes
157     156     connected       DSI-1           154x86      1        ← DSI屏已接
        modes: 800x1280@60 ...
163     0       disconnected    HDMI-A-1        0x0         0        ← HDMI没插

CRTCs:                                         ← 显示管线：两路输出能力
id      fb      pos     size
96      0       (0,0)   (0,0)      ← crtc 96 空闲
152     0       (0,0)   (0,0)      ← crtc 152 空闲

Planes:                                        ← 图层清单：重点看能力
id      crtc    fb      CRTC x,y      x,y     possible crtcs
71      0       0       0,0           0,0     0x00000003
  formats: XR24 AR24 RG24 NV12 NV16 NV21      ← 支持的像素格式
  props: type=Overlay, zpos, alpha ...         ← 叠加层，带混叠属性
86      0       0       0,0           0,0     0x00000003
  formats: XR24 AR24 ...
  props: type=Primary ...
```

读这张表抓三个要点：

1. **plane 的格式支持是硬约束**。列表里没有 NV12 的 plane 不能直接显示 camera 帧（要么换 plane，要么先格式转换）——25.3 的零拷贝链路在选 plane 时就得对着这张表查。
2. **possible crtcs 是位掩码**。`0x00000003` 表示这个 plane 能绑到 crtc 0 或 1；有些 SoC 的叠加层只能绑特定 crtc，双屏异显时这是规划资源的核心依据。
3. **crtc 数量决定异显路数**。两个 crtc = 最多两路独立显示（比如 DSI 主屏 + HDMI 副屏）。

顺手验证一下通路是否真的活着——modetest 自带彩条测试：

```
modetest -M rockchip -s 157@96:800x1280
```

`-s` 参数是 `connector@crtc:模式`，成功的话 DSI 屏上会出渐变彩条。这一步不依赖任何应用代码，显示链路硬件+驱动是否正常，一条命令见分晓。

## <span class="blue"> atomic commit：为什么必须"原子"

理解了四对象，就能理解 atomic 要解决什么。移动一个 camera 预览窗口，至少要改三组属性：plane 的 FB（新帧）、plane 的位置（x/y）、可能还有 crtc 的 mode。如果分三次 ioctl 下发，vblank 可能插在任意两次之间——屏幕上就出现"帧换了但位置还是旧的"这类半成品画面。

早期 DRM 用 page-flip + SetPlane 等一串独立 ioctl，无法避免这个问题。atomic commit 的思路：**攒一批改动 → 一次 ioctl → 内核校验全部合法后，在下一个 vblank 一起生效**；任何一项不合法则整批拒绝，硬件状态不变。

代码形态是"构建 property set → 一次提交"：

```c
drmModeAtomicReq *req = drmModeAtomicAlloc();

/* 攒改动：plane 绑定新 FB（25.3 的 camera 帧）+ 摆位置 */
add_prop(req, plane_id, "FB_ID",   fb_id);
add_prop(req, plane_id, "CRTC_ID", crtc_id);
add_prop(req, plane_id, "CRTC_X",  100);      /* 窗口在屏幕上的位置 */
add_prop(req, plane_id, "CRTC_Y",  50);
add_prop(req, plane_id, "CRTC_W",  1280);     /* 显示尺寸（可缩放） */
add_prop(req, plane_id, "CRTC_H",  720);
add_prop(req, plane_id, "SRC_X",   0);        /* 源区域，16.16 定点数 */
add_prop(req, plane_id, "SRC_Y",   0);
add_prop(req, plane_id, "SRC_W",   1920 << 16);
add_prop(req, plane_id, "SRC_H",   1080 << 16);

/* 一次提交；BLOCK 标志表示等 vblank 生效后才返回 */
int ret = drmModeAtomicCommit(drm_fd, req,
                              DRM_MODE_ATOMIC_ALLOW_MODESET |
                              DRM_MODE_ATOMIC_BLOCK, NULL);
if (ret) perror("atomic commit");             /* 整批被拒：查能力超限 */
drmModeAtomicFree(req);
```

两个实操要点：

**非阻塞提交配 page-flip 事件。** 每帧刷新时不能每次都 BLOCK 等 vblank（那会把帧率钉死在刷新率以下还没有流水线），正确做法是 `DRM_MODE_ATOMIC_NONBLOCK | DRM_MODE_PAGE_FLIP_EVENT`，提交后立即返回去准备下一帧，生效时内核通过 `drmHandleEvent` 回调通知——这与 25.2 的 DQBUF/QBUF 循环是同一个流水线哲学：永远别让生产者和消费者互相堵死。

**先 TEST_ONLY 再真提交。** `DRM_MODE_ATOMIC_TEST_ONLY` 标志让内核只校验不生效。bring-up 阶段先 TEST_ONLY 跑一遍配置序列，把"plane 不支持 NV12""缩放超出硬件范围"这类问题在配置期暴露，而不是上屏后才看到黑屏。

## <span class="blue"> Direct Display vs Compositor：一帧之差

相机预览上屏有两条典型路径，延迟差出一个量级，这是 25.7 门铃案例的关键一步：

**路径 A：经 Compositor（weston 等桌面合成器）。** camera 帧 → Wayland 协议交给 weston → weston 用 GPU 把预览窗口和桌面其他元素合成一张完整帧 → 合成结果作为 primary plane 上屏。问题出在两个地方：GPU 合成本身要 10~60ms（取决于分辨率和 GPU 负载），而且合成是按 weston 自己的节拍走的，最坏情况 camera 帧要等下一个合成周期，**天然多吃约一帧延迟**。

**路径 B：Direct Display（直接写 plane）。** camera 帧的 dma-buf 直接绑到 overlay plane，UI 保持 primary plane 不动，硬件 scanout 时合成。GPU 完全不参与，延迟就是"帧写完 → 下一个 vblank 上屏"，理论下限一帧以内。

实测差异（1080p 预览，RK3568）：路径 A 从帧就绪到上屏典型 40~70ms，路径 B 典型 8~17ms（一个 vblank 周期）。**这不是软件优化的差别，是架构的差别**——Compositor 的通用性（任意窗口叠任意内容）就是用这段延迟买来的。产品上预览延迟敏感（门铃、后视镜、机器人避障视觉）且画面布局固定的场景，就该绕开合成器直接管 plane。

> 💡 验证你的系统走了哪条路：运行预览时 `cat /sys/kernel/debug/dri/0/state`（或 `modetest` 看 plane 的 fb 字段）。camera 帧的 FB 出现在 overlay plane 上是路径 B；所有 plane 的 FB 都不变、只有 weston 的 FB 在刷，就是路径 A。

## <span class="blue"> 显示侧高频故障

**Tearing（撕裂）。** 画面中部出现水平错位的"接缝"，运动场景明显。成因几乎只有一个：更新没等 vblank。排查方向：是否用了非 atomic 的老 ioctl 直改 FB？NONBLOCK 提交是否没有等 page-flip 事件就又改同一块 buffer（正在 scanout 的 buffer 被覆写）？后者在零拷贝链路里是新形态：**camera 正在写的 buffer 不能同时挂在 plane 上**，buffer 轮转池和 plane 切换要配合好，池子太小（<2）必然撕裂。

**Underrun（扫描欠载）。** 画面闪黑条、抖动，dmesg 里有 `vop: underrun` 类报错。显示控制器 scanout 是刚性节拍：60Hz 1080p 意味着每 16.6ms 必须从 DDR 读走约 124MB 的有效像素数据，DDR 带宽被 camera 写入、GPU、NPU 抢占了，显示控制器读不到数据就欠载。治理：降低叠加层数量和分辨率验证、`perf` 看 DDR 占用、平台 QoS 调显示优先级（RK 的 `/sys/class/devfreq/dfi` 相关节点）。

**Plane 能力超限（EINVAL/atomic 被拒）。** 攒了一堆属性提交被拒，最常见三个原因：plane 不支持该像素格式（回 modetest 输出查 formats）、缩放比例超硬件范围（很多 overlay 只支持有限缩放比）、超出同时活动的 plane 数上限。这就是 TEST_ONLY 存在的意义——被拒时逐属性回退重试，定位是哪一项越界。

## <span class="blue"> 本节总结

显示控制器的工作是刚性节拍的 scanout，多图层硬件合成让"camera 帧直接上屏"不需要 GPU。DRM 用 plane/crtc/encoder/connector 四个对象描述这套硬件，modetest 是查看资源清单的入口（plane 格式支持、possible crtcs、crtc 路数三个要点）。atomic commit 把多对象改动打包到 vblank 边界一次生效，配合 NONBLOCK+page-flip 事件和 TEST_ONLY 校验构成显示更新的标准范式。上屏路径的架构选择——Compositor 还是 Direct Display——决定 preview 延迟是几十毫秒还是十几毫秒，这是产品级决策而非优化技巧。显示侧三大故障 tearing/underrun/plane 超限，分别对应 vblank 时机、DDR 带宽、硬件能力约束，各有明确的排查入口。

**关键结论速查：**

| 问题 | 答案 |
|------|------|
| 四对象分工 | plane=哪块内存，crtc=怎么扫，encoder=接口转换，connector=物理口 |
| 资源清单入口 | `modetest -M <驱动名>`，抓 plane formats/possible crtcs/crtc 数 |
| 硬件自检 | `modetest -s <connector>@<crtc>:<mode>` 彩条 |
| 为什么 atomic | 多对象改动必须在一个 vblank 一起生效，否则半成品画面 |
| 每帧刷新姿势 | NONBLOCK + PAGE_FLIP_EVENT，回调里准备下一帧 |
| Compositor vs Direct | 通用性换约一帧+GPU 合成延迟；预览敏感场景直管 plane |
| 三大故障 | tearing=vblank 时机，underrun=DDR 带宽，EINVAL=能力超限 |

1. 为什么显示更新必须等 vblank？不等会出现什么现象？
2. `modetest` 输出里某 plane 的 formats 没有 NV12，对 25.3 的零拷贝链路意味着什么？有哪几条出路？
3. atomic commit 被拒（EINVAL）时的标准定位方法是什么？
