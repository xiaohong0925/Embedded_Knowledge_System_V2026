## <span class="blue"> 本节导读

25.1 用 media-ctl 把拓扑配通了，`v4l2-ctl --stream-mmap` 也抓到了帧。但那条命令替你做了所有事——轮到自己在代码里开流采集时，一连串问题就冒出来了：buffer 谁来分配？为什么帧还没采到就要先把 buffer "queue" 进去？应用处理慢了，帧是在哪一环丢的？这些问题不搞清楚，写出来的采集代码要么帧率不达标，要么莫名其妙丢帧，还无从下手查。

本节把 V4L2 采集的机制拆到底：先走完一遍标准的 VIDIOC 调用序列（每个 ioctl 在驱动里对应什么动作），再深入 VB2（Video Buffer 2）框架的队列模型——这是理解一切采集行为的钥匙，最后用"帧丢失"这个最常见的故障把机制串起来，给出完整的调试路径。本节覆盖：

- 采集的完整 VIDIOC 序列：open 到 STREAMOFF 的十一步
- 三种 buffer 模式的区别与选型：read / mmap / DMABUF
- VB2 队列模型：buffer 的四种归属状态和流转
- 可运行的最小采集程序（逐行注释）
- 帧丢失的机理与调试：丢在哪、怎么看出来、怎么治

> 💡 本节代码针对 `/dev/video0` 这样的 V4L2 video 节点。Sensor/ISP 等 subdev 节点的配置在 25.1 已由 media-ctl 完成，应用层一般不再直接操作。

## <span class="blue"> VIDIOC 调用序列：十一步走完一次采集

V4L2 的采集不是一个 `read()` 那么简单，它是一套有严格顺序的状态迁移。先把全流程的代码骨架摆出来，再逐段解释（完整可运行版在本节后半）：

```c
int fd = open("/dev/video0", O_RDWR);                // ① 打开设备

struct v4l2_capability cap;
ioctl(fd, VIDIOC_QUERYCAP, &cap);                    // ② 查能力：是不是采集设备

struct v4l2_format fmt = { .type = V4L2_BUF_TYPE_VIDEO_CAPTURE };
fmt.fmt.pix.width  = 1920;                           // ③ 设格式：分辨率+像素格式
fmt.fmt.pix.height = 1080;
fmt.fmt.pix.pixelformat = V4L2_PIX_FMT_NV12;
ioctl(fd, VIDIOC_S_FMT, &fmt);

struct v4l2_requestbuffers req = {0};                // ④ 申请 buffer：4个，mmap方式
req.count  = 4;
req.type   = V4L2_BUF_TYPE_VIDEO_CAPTURE;
req.memory = V4L2_MEMORY_MMAP;
ioctl(fd, VIDIOC_REQBUFS, &req);

for (int i = 0; i < 4; i++) {                        // ⑤ 把每个buffer映射到用户空间
    struct v4l2_buffer buf = { .type = req.type, .memory = req.memory, .index = i };
    ioctl(fd, VIDIOC_QUERYBUF, &buf);                //    查出buffer的偏移和长度
    buffers[i] = mmap(NULL, buf.length, PROT_READ|PROT_WRITE, MAP_SHARED, fd, buf.m.offset);
    ioctl(fd, VIDIOC_QBUF, &buf);                    // ⑥ 把buffer"上交"给驱动排队
}

enum v4l2_buf_type type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
ioctl(fd, VIDIOC_STREAMON, &type);                   // ⑦ 开流：硬件开始出帧

while (running) {
    poll(&pfd, 1, -1);                               // ⑧ 等一帧就绪
    struct v4l2_buffer buf = { .type = type, .memory = V4L2_MEMORY_MMAP };
    ioctl(fd, VIDIOC_DQBUF, &buf);                   // ⑨ 取走一帧：buffer回到应用手里
    process(buffers[buf.index], buf.bytesused);      //    用数据……
    ioctl(fd, VIDIOC_QBUF, &buf);                    // ⑩ 用完立刻还给驱动
}

ioctl(fd, VIDIOC_STREAMOFF, &type);                  // ⑪ 关流
```

十一步里，初学者最容易卡在三个地方：

**③ 的返回值必须检查。** `VIDIOC_S_FMT` 是"协商"不是"命令"——你要 1920×1080，驱动可能只支持到它能力内的最近值，改完会把实际生效的格式写回 `fmt`。不读回检查，后面按错误的 stride/大小分配处理逻辑，出图全是花的。

**④⑤⑥ 的次序不能乱。** buffer 由**驱动**分配（REQBUFS），应用只是映射（QUERYBUF+mmap）和借用（QBUF）。为什么不让应用自己 malloc？因为 DMA 对内存有要求：物理连续（或 IOMMU 映射过的）、cache 属性受控。驱动从 CMA 或专用池里拿内存，应用 malloc 的堆内存不满足 DMA 条件。

**⑥ 必须在 ⑦ 之前。** 开流瞬间硬件就开始往 buffer 里写帧，如果队列是空的，帧无处可写——驱动要么丢弃要么报错。这就是大纲里那句"buffer 必须在 STREAMING 之前 QUEUE，否则帧丢失"的出处。

> CMA：Contiguous Memory Allocator，内核的连续物理内存分配器。Camera 这种需要大块物理连续内存做 DMA 的场景几乎都从 CMA 区域分配 buffer。系统 CMA 大小在设备树里配，高分辨率多路采集时 CMA 不够是常见的隐蔽故障（REQBUFS 直接失败）。

## <span class="blue"> 三种 buffer 模式：数据怎么到应用手里

上面用的是 mmap 模式，V4L2 实际提供三种拿到帧数据的方式：

> read 模式：直接 `read(fd, buf, size)`，内核把帧数据**拷贝**到应用的 buffer。代码最简单，但每帧一次内存拷贝，1080p 以上基本不可接受，只适合调试和低分辨率场景。

<!-- -->

> mmap 模式：驱动分配 buffer，应用 mmap 映射后共享访问，全程零拷贝。应用和驱动通过 QBUF/DQBUF 交接 buffer 的"使用权"。**绝大多数采集程序的标准选择。**

<!-- -->

> DMABUF 模式：buffer 不由 V4L2 驱动分配，而是由**另一个子系统**（比如 DRM/显示侧）分配，通过 dma-buf fd 共享给 V4L2 驱动。这是 Camera→Display 全链路零拷贝的关键——采集到的帧不经 CPU 直接给显示控制器 scanout。25.3 专门展开。

选型的判断很直接：纯采集调试用 read（省事）；采集后要处理/编码/显示用 mmap；采集和显示都在本机、追求零拷贝低延迟用 DMABUF。

## <span class="blue"> VB2 队列模型：一个 buffer 的四种归属

mmap 模式下，理解采集行为的全部关键在于搞清楚：**任意时刻，每个 buffer 在谁手里**。VB2 框架（驱动内部的 buffer 管理实现，对应用不可见但决定了外在行为）里，一个 buffer 有四种归属状态：

```
                    QBUF                    硬件写满一帧
   应用手里 ──────────────▶ 驱动队列（queued）──────────────▶ 就绪队列（done）
      ▲                                                            │
      │                         DQBUF                              │
      └────────────────────────────────────────────────────────────┘
```

> 驱动队列（queued）：buffer 已 QBUF，正在等硬件写入或正在被 DMA 写入。这个队列的深度决定了系统能"吞下"多少帧——应用短暂卡顿时，硬件可以把帧继续写进排队的 buffer 而不丢帧。

<!-- -->

> 就绪队列（done）：buffer 已被写满一帧，等应用 DQBUF 取走。poll 返回可读的准确含义就是"就绪队列非空"。

用这个模型重新审视十一步：④⑤ 创建了 4 个 buffer，⑥ 把它们全部推进驱动队列；⑦ 开流后硬件逐帧填充，写满一个就把它挪到就绪队列；⑨ DQBUF 从就绪队列取出（buffer 回到应用手里）；⑩ QBUF 再推回驱动队列。**这是一个循环借还的传送带，buffer 总数恒定，永远在四个状态里流转。**

传送带的节奏决定了系统行为。假设 30fps 出帧（每 33ms 一帧），4 个 buffer：

- 应用每帧处理耗时 < 33ms：DQBUF 后立刻 QBUF，驱动队列始终有位置，一帧不丢；
- 应用偶尔卡顿 100ms：驱动队列里剩下的 3 个 buffer 能吸收 3 帧，第 4 帧到来时队列已满——**帧丢失就发生在这一刻**；
- 应用持续处理耗时 60ms：稳态下每 60ms 才能归还一个 buffer，硬件 33ms 出一帧，驱动队列迅速见底，之后每两帧丢一帧，实际帧率腰斩。

## <span class="blue"> 帧丢失：机理、观测、治理

帧丢失是采集链路最高频的问题，把它拆成"在哪丢、怎么看、怎么治"三步。

**在哪丢。** 出帧的硬件不会等人——Sensor 按自己的帧率源源不断吐数据，ISP 的 DMA 引擎每帧结束找驱动队列要下一个空 buffer，要不到就只能丢。丢帧点几乎永远在**驱动队列耗尽**这一刻，根因则分三类：

1. **应用归还太慢**（最常见）：处理逻辑耗时超过帧间隔，或处理线程被调度延迟；
2. **buffer 数量太少**：REQBUFS 只申请了 1~2 个，没有任何吸收抖动的余量；
3. **带宽竞争**：DDR 带宽被 GPU/显示/其他 master 抢占，DMA 写帧变慢，等效于归还变慢。

**怎么看。** 三个层次的观测手段，从快到深：

```bash
v4l2-ctl -d /dev/video0 --stream-mmap --stream-count=300
```

```
<<<<<<<<<<<<<<<<<<<<<<<<<<<<<< 30.02 fps
<<<<<<<<<<<<<<<<<<<<<<<<<<<< 30.00 fps
<<<<<<<<<<<<<<<<<<<<<<<<<< 27.95 fps          ← 掉速了：应用/系统跟不上了
```

v4l2-ctl 自己不消耗数据，它掉 fps 说明问题在内核/硬件侧；v4l2-ctl 满速而你的应用掉速，问题在应用侧——这一步就把怀疑范围切掉一半。

第二层，看帧序号。`v4l2_buffer` 结构体里有个 `sequence` 字段，驱动每出一帧递增一次。应用在 DQBUF 后检查 sequence 是否连续：

```c
static unsigned int last_seq;
ioctl(fd, VIDIOC_DQBUF, &buf);
if (buf.sequence != last_seq + 1 && last_seq != 0)
    printf("drop! seq %u -> %u, lost %u frames\n",
           last_seq, buf.sequence, buf.sequence - last_seq - 1);
last_seq = buf.sequence;
```

sequence 跳变直接报告丢了几帧、丢在什么时候，配合日志时间戳就能关联到系统当时的负载事件。

第三层，上内核 trace。VB2 和 V4L2 都有 tracepoint，能精确看到每次 QBUF/DQBUF/帧完成的时间：

```bash
cd /sys/kernel/debug/tracing
echo 1 > events/v4l2/enable
echo 1 > events/vb2/enable
cat trace_pipe > /tmp/vb2.log &        # 后台采集，复现后分析
```

trace 里能看到"帧完成中断 → vb2_buffer_done → 唤醒应用 → DQBUF → QBUF"的完整时序，哪一环耗时异常一目了然。

**怎么治。** 按根因对应：

- 应用慢：处理逻辑搬出采集线程（DQBUF 后把 buffer 扔给处理线程，立刻 QBUF——注意此时要加引用计数，别让同一个 buffer 被 QBUF 两次）；或干脆加线程池；
- buffer 少：REQBUFS 从 2 加到 4~6 个。代价是每个 buffer 占一块 CMA 内存（1080p NV12 约 3MB/个），4K 多路采集时内存账要算；
- 带宽竞争：`vmstat`、`perf stat` 看 DDR 利用率，必要时调 QoS（RK 平台有 dfi/qos 节点）或降分辨率/帧率验证。

> ⚠️ 一个经典误判：看到应用实际帧率 15fps、sensor 标称 30fps，第一反应是"丢了一半帧"。但如果应用**故意**每处理一帧就 sleep 到 60ms（比如某些演示代码），帧率也会稳定在 15fps 而 sequence 连续——这是主动降速不是丢帧。先查 sequence，再下结论。

## <span class="blue"> 最小采集程序：完整可运行版

把十一步拼成一个能编译运行的程序，逐行注释：

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <fcntl.h>
#include <unistd.h>
#include <errno.h>
#include <sys/ioctl.h>
#include <sys/mman.h>
#include <poll.h>
#include <linux/videodev2.h>

#define BUF_COUNT 4                                  // buffer数量：吸收抖动的余量

static void *buf_start[BUF_COUNT];                   // mmap后的用户态地址
static size_t buf_len[BUF_COUNT];

static int xioctl(int fd, int req, void *arg)        // ioctl包装：处理EINTR重试
{
    int r;
    do { r = ioctl(fd, req, arg); } while (r == -1 && errno == EINTR);
    return r;
}

int main(void)
{
    int fd = open("/dev/video0", O_RDWR);
    if (fd < 0) { perror("open"); return 1; }

    struct v4l2_capability cap;                      // ② 查能力
    xioctl(fd, VIDIOC_QUERYCAP, &cap);
    if (!(cap.device_caps & V4L2_CAP_VIDEO_CAPTURE)) {
        fprintf(stderr, "not a capture device\n");
        return 1;
    }
    if (!(cap.device_caps & V4L2_CAP_STREAMING)) {   // 不支持流式IO就只能read模式
        fprintf(stderr, "no streaming support\n");
        return 1;
    }

    struct v4l2_format fmt = {0};                    // ③ 协商格式
    fmt.type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
    fmt.fmt.pix.width = 1920;
    fmt.fmt.pix.height = 1080;
    fmt.fmt.pix.pixelformat = V4L2_PIX_FMT_NV12;
    xioctl(fd, VIDIOC_S_FMT, &fmt);
    printf("actual: %ux%u fmt=%.4s\n",               // 必须读回确认实际生效值
           fmt.fmt.pix.width, fmt.fmt.pix.height,
           (char *)&fmt.fmt.pix.pixelformat);

    struct v4l2_requestbuffers req = {0};            // ④ 申请buffer
    req.count = BUF_COUNT;
    req.type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
    req.memory = V4L2_MEMORY_MMAP;
    if (xioctl(fd, VIDIOC_REQBUFS, &req) < 0) {      // 失败先怀疑CMA不够
        perror("VIDIOC_REQBUFS"); return 1;
    }
    printf("granted %u buffers\n", req.count);       // 实际批准数可能少于申请数

    for (int i = 0; i < req.count; i++) {            // ⑤ 映射+⑥上交
        struct v4l2_buffer buf = {0};
        buf.type = req.type; buf.memory = req.memory; buf.index = i;
        xioctl(fd, VIDIOC_QUERYBUF, &buf);
        buf_len[i] = buf.length;
        buf_start[i] = mmap(NULL, buf.length,
                            PROT_READ | PROT_WRITE, MAP_SHARED, fd, buf.m.offset);
        if (buf_start[i] == MAP_FAILED) { perror("mmap"); return 1; }
        xioctl(fd, VIDIOC_QBUF, &buf);               // 开流前全部入队
    }

    enum v4l2_buf_type type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
    xioctl(fd, VIDIOC_STREAMON, &type);              // ⑦ 开流

    struct pollfd pfd = { .fd = fd, .events = POLLIN };
    FILE *out = fopen("/tmp/cap.nv12", "wb");
    unsigned int last_seq = 0;
    for (int n = 0; n < 30; n++) {                   // 采30帧
        if (poll(&pfd, 1, 3000) <= 0) {              // ⑧ 3秒超时兜底
            fprintf(stderr, "poll timeout\n"); break;
        }
        struct v4l2_buffer buf = {0};                // ⑨ 取帧
        buf.type = type; buf.memory = V4L2_MEMORY_MMAP;
        xioctl(fd, VIDIOC_DQBUF, &buf);
        if (buf.sequence != last_seq + 1 && n > 0)   // sequence连续性检查
            printf("drop %u frames\n", buf.sequence - last_seq - 1);
        last_seq = buf.sequence;
        if (n == 15)                                 // 只存中间一帧做样本
            fwrite(buf_start[buf.index], 1, buf.bytesused, out);
        xioctl(fd, VIDIOC_QBUF, &buf);               // ⑩ 立刻归还
    }
    fclose(out);

    xioctl(fd, VIDIOC_STREAMOFF, &type);             // ⑪ 关流
    for (int i = 0; i < req.count; i++)
        munmap(buf_start[i], buf_len[i]);
    close(fd);
    printf("done, sample saved to /tmp/cap.nv12\n");
    return 0;
}
```

编译（在目标板上，或交叉编译加 `--sysroot`）：

```bash
gcc -o cap cap.c
./cap
ffplay -f rawvideo -pixel_format nv12 -video_size 1920x1080 /tmp/cap.nv12
```

这个程序只有两个"加工"动作：sequence 连续性检查（丢帧检测的最小实现）和存一帧样本。把它跑通，你就拥有了一个可随意改造的采集基线——加处理线程、换 DMABUF 模式、接编码器，都是从这份骨架长出来的。

## <span class="blue"> 本节总结

V4L2 采集是一套严格的状态机：协商格式（S_FMT 要读回）、申请 buffer（REQBUFS，失败先查 CMA）、开流前全部 QBUF、DQBUF/QBUF 循环借还、STREAMOFF 收尾。机制的核心是 VB2 的队列模型——buffer 在"应用手里/驱动队列/就绪队列"之间循环，驱动队列深度就是系统吸收抖动的容量。帧丢失几乎总是发生在驱动队列耗尽的瞬间，观测三件套是 v4l2-ctl 满速对比（切分内核侧/应用侧）、sequence 连续性（量化丢帧）、vb2/v4l2 tracepoint（精确定位时序）。治理对症下手：应用慢就剥离处理线程，buffer 少就加数量（算 CMA 账），带宽竞争就查 DDR。

**关键结论速查：**

| 问题 | 答案 |
|------|------|
| 标准采集序列 | open→QUERYCAP→S_FMT→REQBUFS→QUERYBUF/mmap→QBUF→STREAMON→poll/DQBUF/QBUF→STREAMOFF |
| S_FMT 的坑 | 协商式，必须读回实际生效值 |
| buffer 为什么驱动分配 | DMA 要求物理连续/cache 受控，CMA 区域，malloc 不满足 |
| 帧丢失的机理 | 硬件出帧不等人，驱动队列耗尽即丢 |
| 观测三件套 | v4l2-ctl 满速对比 / sequence 连续性 / vb2+v4l2 tracepoint |
| 治理三方向 | 处理剥离采集线程 / 加 buffer / 查 DDR 带宽 |
