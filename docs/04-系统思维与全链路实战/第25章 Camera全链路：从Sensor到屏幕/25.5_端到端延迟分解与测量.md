# 25.5 端到端延迟分解与测量

> 所属章节：第25章 Camera全链路：从Sensor到屏幕
>
> 难度：[E] | 预计阅读时间：40 分钟

## <span class="blue"> 本节导读

前四节把链路的每一段机制都拆开了：采集（25.2）、交接（25.3）、上屏（25.4）。现在面对的是一个工程问题——"画面有点卡"是没法修的，"从按铃到出图 300ms，其中 GPU 合成吃了 60ms"才能修。**延迟优化的一切前提是先把总延迟拆成段、把每段测出来。**

这件事的难点在于：延迟发生在四个不同的世界里——Sensor 硬件、内核驱动、用户空间、显示控制器——没有一把尺子能量全程，每一段要用不同的测量手段。本节给出完整的测量工具箱，本节覆盖：

- 端到端延迟的七段分解：每段的典型值与物理成因
- 分段测量方法：V4L2 时间戳、page-flip 事件、应用打点、GPIO+示波器
- 端到端真值测量：光电二极管法——所有软件测量的校准基准
- 测量实录：门铃设备从总量摸底到对账的五步流程
- 延迟预算表：从"产品指标"反推"每段该花多少"的工作方法
- 场景差异：机器人视觉（SLAM）与门铃预览的延迟要求为什么不一样

## <span class="blue"> 七段分解：延迟藏在哪

一帧从感光到上屏，延迟由七段构成。这张表是全节的地图（典型值基于 1080p30 量级，来自大纲与工程经验）：

| 段 | 环节 | 典型值 | 物理成因 |
|----|------|--------|----------|
| ① | Sensor 曝光 | 8~33ms | 曝光时间就是光线积累时间，低照度下必须拉长 |
| ② | MIPI CSI-2 传输 | 1~5ms | 串行传输一帧的时间，lane 数×速率决定 |
| ③ | ISP 处理 | 5~20ms | 去噪/3A/格式转换的流水线深度 |
| ④ | DMA 写入内存 | 2~10ms | DDR 带宽竞争程度 |
| ⑤ | 用户空间处理 | 0~50ms | 完全取决于应用干了什么 |
| ⑥ | DRM commit → vblank | 8~33ms | 提交后等下一个场消隐，最坏等一整帧 |
| ⑦ | Panel scanout | 8~16ms | 像素逐行扫到屏幕底部的物理时间 |

合计：无用户处理约 25~120ms，带 AI 推理类处理约 50~200ms。

这张表有两个反直觉的点。**第一，①⑥⑦ 三段"硬件税"合计就可能超过 50ms**——它们与代码质量无关，只与帧率和物理规律有关：60Hz 面板单是 vblank 等待+scanout 的平均值就约 24ms。所以"零延迟"在物理上不存在，预算表的意义是知道底线在哪。**第二，大头往往在⑤和⑥**——用户空间处理和上屏路径（25.4 的 Compositor vs Direct）是唯一有数量级压缩空间的两段，这正是 25.7 门铃案例的主战场。

## <span class="blue"> 分段测量：每段一把尺

### ① ② ③ ④：内核段，用 V4L2 时间戳

`v4l2_buffer` 的 `timestamp` 字段是驱动在**帧到达内存的时刻**（帧结束中断）盖的钟，时基是 `CLOCK_MONOTONIC`。它直接给出 ②③④ 的合计终点。①的曝光时间从 V4L2 control 读：

```c
struct v4l2_control ctrl = { .id = V4L2_CID_EXPOSURE_ABSOLUTE };
ioctl(fd, VIDIOC_G_CTRL, &ctrl);        // 曝光时间，单位通常100μs
printf("exposure: %d x100us\n", ctrl.value);
```

帧间隔（连续两帧 timestamp 之差）减去曝光时间，就是 ②+③+④ 的上限。想进一步细分，用 ftrace 看 ISP 帧中断与 vb2 done 的间隔（方法同 25.2 的 tracepoint 采集）：

```bash
cd /sys/kernel/debug/tracing
echo 'rkisp1*' > set_ftrace_filter 2>/dev/null   # 平台ISP中断函数名，按实际改
echo function > current_tracer
```

### ⑤：用户空间段，应用打点

最简单也最可靠：DQBUF 返回时记 `t1`，处理完准备提交显示时记 `t2`（同一 CLOCK_MONOTONIC 时基），`t2-t1` 就是⑤。配合 buffer 的 timestamp，还能算出"帧在队列里等了多久才被应用取走"——排队延迟经常被忽略，buffer 队列深时它能占到十几毫秒（这就是 25.7 里"队列深度 4 帧改 2 帧省 33ms"的机理）。

### ⑥：上屏等待段，page-flip 事件

`drmModeAtomicCommit` 用 NONBLOCK+PAGE_FLIP_EVENT 提交后，`drmHandleEvent` 的回调里带着生效时刻的时间戳（tv_sec/tv_usec）。**提交时刻与回调时刻之差就是⑥**——它应该落在 0~1 个帧周期内，超过就说明你在 vblank 之后才提交（等下一个 vblank，白丢一帧）。

```c
static void page_flip_handler(int fd, unsigned seq, unsigned tv_sec,
                              unsigned tv_usec, void *data)
{
    struct timespec *submit = data;
    long us = (tv_sec - submit->tv_sec) * 1000000L
            + (tv_usec - submit->tv_nsec / 1000);
    printf("commit -> on screen: %ld us\n", us);   // ⑥的实测值
}
```

### ⑦：面板段，按帧周期折算

scanout 时间约等于一个帧周期（60Hz=16.6ms，120Hz=8.3ms）乘以"关心点在画面中的行位置"——关心画面正中央就按半帧算。这段测不出来也不需要测，查面板规格书的刷新率直接折算。

## <span class="blue"> 端到端真值：光电二极管法

分段测量加起来总会有误差——每把尺的时基、打点位置都引入偏差。验证总账必须用端到端的物理测量，金标准是**光电二极管法**：

```
被测系统：闪光灯/LED ──► Camera ──► 全链路 ──► 屏幕显示
测量设备：GPIO 翻转（触发曝光同步）      光电二极管贴屏幕
              │                              │
              └──────► 示波器 ◄──────────────┘
                     两个通道的时间差 = 真实端到端延迟
```

操作方法：一个 LED 对着 camera，点亮 LED 的同时用一路 GPIO 给示波器打标记；屏幕前贴一个光电二极管（对着预览画面中 LED 出现的位置），屏幕上出现亮斑的瞬间二极管输出跳变。示波器两通道的时间差就是**包含全部七段的真实延迟**，精度到亚毫秒级。

没有示波器的穷办法：高速相机（手机 240fps 慢动作即可）同时拍摄 LED 和屏幕，数帧差——240fps 下每帧 4.2ms，精度够验证预算表的量级。

> 💡 光电二极管法的真正价值不是"量一次总延迟"，而是**校准**：如果七段分段测量加起来是 110ms，物理测量是 160ms，那 50ms 的差值本身就是线索——说明有一段延迟被你的打点方式漏掉了（常见漏网之鱼：ISP 内部队列、panel 内部处理延迟、weston 的合成节拍）。

## <span class="blue"> 测量实录：一次完整的分段流程

把上面的尺子按正确顺序用一遍。顺序有讲究：**先总量、再分段、最后物理校准**——先知道总账多大，再决定在哪几段投入测量精力。下面以门铃设备（1080p30 预览，weston 桌面）为例。

**第一步，总量摸底（5 分钟）。** 手机开 240fps 慢动作，同时拍 LED 和屏幕，数出 LED 亮到屏幕上出现亮斑差 72 帧——72×4.2ms≈300ms。总账有了：300ms，目标是 150ms 以内，差一倍。

**第二步，内核段（V4L2 时间戳，10 分钟）。** 在采集程序里打印每帧 timestamp 和 sequence：

```
seq=1001 ts=1695678234.033  interval=33.3ms      ← 帧间隔稳定30fps，②③④没堆积
seq=1002 ts=1695678234.066  interval=33.3ms
seq=1003 ts=1695678234.100  interval=33.4ms
```

帧间隔稳定等于帧周期，说明内核段（②③④）没有异常排队——**这段不用深挖了**。读曝光时间 200（×100μs=20ms），内核段合计约 20+35=55ms，记录下来。

**第三步，用户空间段（应用打点，20 分钟）。** DQBUF 后和处理完各打一个点，连续统计 100 帧取平均：

```
dqbuf->process_done: avg=90ms  (yuv2rgb=30ms, gpu_upload+composite_wait=60ms)
```

⑤ 段 90ms，其中 GPU 合成等待占 60ms——注意这里的 `composite_wait` 不是 GPU 干活的时间，是**等 weston 合成节拍**的时间，它其实属于⑥。这正体现了打点的价值：不按段拆，你会以为 GPU 算得太慢，实际上是节拍等得太久。

**第四步，上屏段（page-flip 事件，10 分钟）。** 提交到生效实测平均 100ms——远超一个帧周期 16.6ms，确认帧在 weston 的合成队列里多等了 5~6 拍。

**第五步，对账。** 55+90+100+35（⑦折算）=280ms，与手机实测 300ms 差 20ms，在⑦的折算误差和 panel 内部延迟范围内，账对得上。预算表的"实测"列就此填齐——整个过程不到一小时，优化靶子已经锁定在⑤⑥。

这个实录藏着一条方法论：**测量顺序就是排除顺序**。总量异常才分段，分段先测最便宜的（时间戳打印），最贵的物理测量（示波器）留到最后做校准。反过来一上来就架示波器，往往量了一个精确的、却不知道花在哪的总数。

## <span class="blue"> 延迟预算表：从指标反推分配

产品指标是"按铃到出图 <150ms"这种总量，工程上必须把它翻译成每段的预算，否则优化没有靶子。预算表的做法是四步：

1. **列段**：把七段抄下来，加上你产品特有的段（按键消抖、网络传输等）；
2. **填实测值**：用上面的分段方法测出当前值；
3. **标物理下限**：①受照度约束、⑦受刷新率约束、⑥下限是 0（vblank 前刚好提交）——下限测不出来但定得出来；
4. **找差额**：实测值与下限差距最大的段，就是优化主战场。

以 25.7 的门铃为例，初始测量的预算表长这样（目标 150ms，实测 300ms）：

| 段 | 实测 | 物理下限 | 差额 | 结论 |
|----|------|----------|------|------|
| ① 曝光 | 20ms | 10ms | 10ms | 可小挤 |
| ②③④ 内核段 | 55ms | 25ms | 30ms | ISP 输出格式要改 |
| ⑤ 用户空间 | 90ms | ~5ms | **85ms** | YUV→RGB 转换+GPU 合成，主战场 |
| ⑥ 上屏等待 | 100ms | 17ms | **83ms** | Compositor 节拍，主战场 |
| ⑦ scanout | 35ms | 17ms | 18ms | 刷新率限制，难动 |

一眼就能看出：85ms 和 83ms 两个差额集中在⑤⑥，而这正是"ISP 直出 RGB + Direct Display"能同时打击的两段——优化方向在动手前就已经清楚了。**预算表的价值不在于表格本身，在于它把"感觉哪里慢"变成"差额在哪里"，防止工程师在物理下限段上做无用功。**

## <span class="blue"> 场景差异：机器人视觉的延迟账不一样

门铃的延迟目标是"人眼看着不迟"，机器人视觉的账要重算——SLAM/避障吃的是**帧的时间戳准确性和抖动**，而不是单纯的总延迟：

| 维度 | 门铃预览 | 机器人视觉（SLAM/避障） |
|------|----------|------------------------|
| 核心指标 | 总延迟 <150ms | 时间戳误差 <5ms，帧间抖动小 |
| 为什么 | 人等门开，晚 100ms 无感 | 运动中的位姿估计按时间戳插值，戳错了地图就歪 |
| 多目要求 | 单路 | 双目/多目帧级同步（硬同步曝光或 PTP 对时） |
| 最忌讳 | 画面卡 | 时间戳漂移、丢帧后序号不连续 |
| 对应手段 | Direct Display | V4L2 时间戳校准 + 队列深度最小化 + 中断亲和性绑定 |

关键差异在测量重点：门铃场景光电二极管量总延迟就够；机器人场景要额外统计**帧时间戳的分布**——连续一万帧的 timestamp 间隔画直方图，抖动（jitter）大的系统即使平均帧率达标，SLAM 也会发散。队列深度的取舍也相反：预览场景留 2~4 个 buffer 吸收抖动，SLAM 输入反而要压到 1~2 个——宁可丢帧，也不要让旧帧排队冒充新帧。

## <span class="blue"> 本节总结

端到端延迟拆成七段，前三段在 Sensor/ISP 硬件，中间两段在内核与用户空间，末两段在显示节拍。分段测量各有专用尺子：V4L2 buffer 时间戳量内核段、应用打点量用户段、page-flip 事件量上屏等待、帧周期折算面板段；总账用光电二极管法做物理真值校准，分段之和与物理实测的差额本身就是定位遗漏段的线索。延迟预算表四步——列段、实测、标下限、找差额——把优化从"碰运气"变成"打靶"。场景决定优化目标：门铃压总延迟（主战场在⑤⑥），机器人保时间戳精度与低抖动（队列深度反向取舍）。

**关键结论速查：**

| 问题 | 答案 |
|------|------|
| 七段分解 | 曝光/CSI/ISP/DMA写/用户处理/等vblank/scanout |
| 内核段尺子 | `v4l2_buffer.timestamp`（CLOCK_MONOTONIC） |
| 上屏等待尺子 | page-flip 事件时间戳 − 提交时刻 |
| 总延迟金标准 | 光电二极管法（GPIO+示波器），手机慢动作可穷替 |
| 预算表四步 | 列段 → 实测 → 标物理下限 → 找差额 |
| 门铃主战场 | ⑤用户空间 + ⑥上屏路径 |
| 机器人主战场 | 时间戳精度 + 抖动，队列深度宁小勿大 |
