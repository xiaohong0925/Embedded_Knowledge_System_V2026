# 25.6 常见故障排查

> 所属章节：第25章 Camera全链路：从Sensor到屏幕
>
> 难度：[M] ~ [E] | 预计阅读时间：40 分钟

## <span class="blue"> 本节导读

前五节建立的是"正常时怎么工作"，这节解决"不正常时怎么查"。Camera 链路的故障表象五花八门，但 bring-up 和量产现场的高频问题收敛起来只有四类：**设备节点不出现、出图颜色错、帧率不达标、延迟抖动大**。每一类的排查都不是背口诀——前五节的机制恰恰就是为这一刻准备的：拓扑图（25.1）、VB2 队列（25.2）、stride 与 cache（25.3）、plane 能力（25.4）、分段测量（25.5）各自对应一类故障的钥匙。

本节按"现象 → 机理 → 排查路径 → 典型根因"四步组织每个故障类，目标是让你拿到现象就知道第一步敲什么命令。本节覆盖：

- 故障定位总原则：先分段、再降维、后换元
- /dev/video0 不出现：Sensor probe 链路的完整排查
- 出图绿色/紫色/花屏：格式类故障的三种面相
- 帧率不达标：带宽链路的逐段收缩
- 延迟抖动大：时序类故障的测量先行

> 💡 摄像头从"不通"到"点亮"的完整流程（含设备树编写）在 B-C.9.5 有专门实战，本节聚焦"点亮之后还不正常"和量产现场的故障。

## <span class="blue"> 总原则：先分段、再降维、后换元

动手查之前记住三个动作，它们适用于所有四类故障：

**先分段。** Camera 链路是 Sensor → CSI → ISP → 内存 → 显示的多段结构，任何故障先问"坏在哪一段"。分段工具就是 25.1 的拓扑图和 25.5 的测量：`media-ctl --print-topology` 看各段在不在、通不通；`v4l2-ctl --stream-mmap` 直接抓帧——能抓到正常帧，说明显示段之前全好，问题在显示侧。

**再降维。** 把系统降到最简形态再观察：分辨率降一半、帧率降一半、关掉其他 DDR 大户（GPU 程序、视频播放）、绕过 compositor 直写 plane。故障随降维消失的方向就是瓶颈方向——降分辨率好了，是带宽问题；关 GPU 好了，是 DDR 竞争问题。

**后换元。** 前两者都定位不了时，用替换法隔离变量：换一块确认好的 Sensor 模组、换一组确认好的设备树配置、换一个确认好的应用（v4l2-ctl 替代你的程序）。每次只换一个变量。

## <span class="blue"> 故障一：/dev/video0 不出现

**现象：** 系统启动后没有 video 节点，或 media-ctl 拓扑里没有 Sensor entity。

**机理：** video 节点的诞生依赖一条完整的 probe 链：Sensor 驱动 probe 成功（I2C 通、电源时钟正常）→ 注册 V4L2 subdev → 设备树 endpoint 把它挂到 CSI/ISP → ISP 驱动 async 等待所有 subdev 就绪 → 注册 video 节点。**链上任何一环失败，末端就没有节点**——所以"没有 /dev/video0"的根因可能远在 Sensor 的上电时序。

**排查路径（按序执行）：**

```
dmesg | grep -iE "imx|ov[0-9]|sensor"        # ① 看Sensor驱动的临终遗言
i2cdetect -y -r 2                             # ② I2C总线上能看到0x1a吗
cat /sys/kernel/debug/devices_deferred        # ③ 有没有卡在资源未就绪
media-ctl -d /dev/media0 --print-topology     # ④ Sensor在但video不在=endpoint断
```

①的几种典型输出直接指路：`no sensor detected`（I2C 通但 ID 寄存器读错——多半是电源/时钟没给对，芯片没真正工作）；`chip id 0x0000 mismatch`（mclk 频率不对或 reset 时序太短）；完全没有任何输出（驱动没被匹配——查设备树 compatible 和 status）。②探测不到地址时，先量硬件：avdd/dovdd 电压、reset/pwdn 引脚电平、mclk 用示波器看频率和幅度。③出现你的 Sensor 或 ISP，说明 probe 被推迟后没等到资源——常见的缺席资源是 regulator 或 csi-dphy。

**典型根因分布：** I2C 地址配错（注意设备树用 7 位地址，datasheet 常标 8 位，差一倍）约占三成；上电时序违反 datasheet（avdd 要先于 dovdd、reset 要保持 N ms）约占三成；mclk 频率/使能错误约两成；设备树 endpoint 互联错误约两成。

## <span class="blue"> 故障二：出图绿色/紫色/花屏

**现象：** 能抓到帧，但颜色整体偏绿、偏紫，或画面斜切、左右互换、规律性条纹。

**机理：** 这一类全是**格式声明与数据实际布局不一致**——数据本身是好的，是"解读方式"错了。三种面相对应三种错法：

**整体偏绿：Bayer 排列声明错误。** Sensor 实际输出 BGGR，ISP 按 GBRG 解，每个像素的 R/B 通道被对调，绿色被双倍计入，画面整体泛绿。验证与修复都在 media-ctl：

```
media-ctl -d /dev/media0 --print-topology | grep -A2 "imx415"
        pad0: Source [fmt:SBGGR10_1X10/1920x1080]     ← 当前声明
```

对照 Sensor datasheet 的实际 Bayer 排列（上电默认通常是 RGGB 或 BGGR），用 25.1 的 `--set-v4l2` 逐段改成正确的 mbus code。改完抓一帧立刻见分晓。

**画面斜切/错位：stride 不匹配。** 图像像被斜着撕开，每行有固定偏移——这是 25.3 讲过的行字节数（bytesperline/pitch）不一致：写的人按 1920 字节一行写，读的人按 2048 字节一行读。用 `v4l2-ctl --get-fmt-video` 看 V4L2 侧的 bytesperline，和显示/读取侧的对照。

**规律性竖条纹或边缘色块：MIPI lane 顺序/极性错误。** 数据线上的差分对顺序接错或极性反了，ISP 收到的字节流错位，呈现周期性图案。这类问题 media-ctl 层面看不出来（格式声明都对），要查设备树里 CSI 的 lane 配置（`data-lanes` 顺序、部分平台支持 `lane-polarities`），以及原理图上 P/N 是否接反。

**颜色发紫发品红：不一定是格式问题。** 如果画面内容正常只是色调异常，更可能是 3A（自动白平衡）没收敛——ISP 的统计信息通路没配好，AWB 算法拿不到数据。确认 ISP 统计节点的 buffer 在流转（ftrace 看 ISP 中断频率），以及 sensor 增益/曝光在正常范围——极端欠曝时 AWB 也会失效。

## <span class="blue"> 故障三：帧率不达标

**现象：** 标称 30fps 的 Sensor 实际只出 15~20fps，或 fps 随负载波动。

**机理：** 帧率是一条带宽链的最短板：Sensor 出帧速率（PLL/hts/vts 配置）→ MIPI 链路带宽（lane 数 × lane 速率）→ ISP 处理吞吐 → DDR 写带宽。任何一段瓶颈都会把全链压到它的速度。

**排查路径（按序执行）：**

```
v4l2-ctl -d /dev/video0 --get-parm            # ① 驱动认为自己在跑多少fps
v4l2-ctl -d /dev/video0 --stream-mmap --stream-count=300   # ② 实测fps
media-ctl -d /dev/media0 --print-topology     # ③ 每段的fmt：分辨率是否符合预期
```

①和②对照出现分歧时方向就明确了：**驱动标称 30、实测 15**，瓶颈在 Sensor 之后——降分辨率到 720p 再测，fps 上去了说明是带宽链问题（MIPI lane 数、ISP 吞吐、DDR），fps 不动说明是 Sensor 自身配置问题（hts/vts 寄存器、帧率 control）。**标称实测一致但就是不达标**，查 Sensor 的帧率上限：`v4l2-ctl --list-ctrls` 里找 frame_interval 类控制，以及设备树/驱动里的 link-frequencies——link 频率配低一半，fps 就封顶一半。

带宽账的快速心算：1080p RAW10 每帧约 2.5MB，30fps 需要 75MB/s；单 lane 1Gbps 的 2-lane 配置理论 250MB/s，够用；但如果设备树只声明了 1 lane，或者 ISP 这边开了双路同时出图，账就要重算。**帧率问题的本质是算术题**，先把每段的 MB/s 算出来再怀疑硬件。

**典型根因：** link-frequencies 配错、lane 数声明与实际硬件不符、ISP 双路同开超吞吐、DDR 被 GPU/NPU 抢占（用降维法验证）。

## <span class="blue"> 故障四：延迟抖动大

**现象：** 平均帧率达标，但帧间隔忽长忽短——预览画面"一顿一顿"，SLAM 输入的时间戳分布发散。

**机理：** 与故障三不同，这里带宽总量够，**问题在时序的确定性**：帧到了没人及时取（调度延迟）、中断来得不准时（中断亲和性/优先级）、内存带宽时快时慢（DVFS 动态调频）。抖动类故障不可肉眼估，必须测量先行。

**排查路径（按序执行）：**

```
# ① 帧间隔直方图：先确认抖动的形态
cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor   # ② CPU频率策略
cat /proc/interrupts | grep -iE "isp|csi|vop"               # ③ 中断绑在哪个核
cyclictest -m -p 80 -i 200 -l 100000                        # ④ 系统调度延迟基线
```

①用 25.5 的方法统计一万帧的 timestamp 间隔：抖动集中在个别尖刺（99.9 分位异常）指向调度/中断延迟；整体间隔在两个值之间来回跳（双峰分布）指向 DVFS 频率切换。②是 `schedutil`/`ondemand` 时，改成 `performance` 立刻对比——抖动消失就确诊了，产品上要权衡功耗决定永久策略。③看 ISP/VOP 中断是否和被抢占严重的核绑在一起，`echo 2 > /proc/irq/<N>/smp_affinity_list` 绑到空闲核对比。④给出系统调度延迟的上限基线——如果 cyclictest 本身就报几十微秒以上的毛刺，说明系统里有长临界区（某个驱动关了太久的硬中断），抖动不是 Camera 链路自身的问题。

**典型根因：** CPU governor 动态调频、中断亲和性不合理、DDR devfreq 跳频、compositor 节拍混入（预览路径先确认是 Direct 还是经 weston——后者天然带节拍抖动，见 25.4）。

## <span class="blue"> 复合故障：两类问题同时存在时

真实现场的故障不总是单因的。一个典型的复合案例：新板卡 bring-up，fps 只有 12 且画面偏绿。如果先按帧率问题查带宽，查到头也治不好颜色；先按颜色问题改 Bayer 声明，改完帧率还是 12。

复合故障的处置原则是**先修"解读层"，再修"性能层"**：格式/颜色类问题先解决，因为数据解读错了，一切性能测量都没有意义（你测的可能是错误处理路径的速度）；颜色正常后再按帧率路径查带宽。这个顺序的依据是依赖关系：性能测量建立在"数据正确"的前提上，反过来不成立。

识别复合故障的信号是**单一路径走不通**：按某类的排查路径走到第三步，现象只改善了一部分。这时停下来重新分类——剩下的现象属于哪一类，就换哪类的路径接着走，不要在原路径上硬推。

## <span class="blue"> 故障复盘单：量产现场的最小记录

量产和客诉现场的故障排查有一个容易被忽视的产出物：复盘记录。最小可用模板只有五行，但缺了任何一行，下次同类问题还得从头查：

```
现象：    一句话，可观测、可复现的描述（"出图偏绿"，不是"图像有问题"）
环境：    硬件批次/固件版本/负载场景——复合故障的线索常藏在环境差异里
第一段命令： 你敲的第一条命令和它的关键输出
根因：    最终确认的机理（不是"改了什么"，是"为什么坏"）
修复与回归： 改动内容 + 验证方法 + 回归时长（如：烘箱48h/一万帧无复发）
```

它的价值在第三章 23 章（系统调试方法论）里已经论证过：调试能力的天花板不是工具数量，而是假设-验证链条的完整度——复盘单就是这条链条落在纸面上的样子。

## <span class="blue"> 症状-入口速查

| 症状 | 第一条命令 | 大概率方向 |
|------|-----------|-----------|
| 没有 /dev/video0 | `dmesg \| grep -i sensor` | I2C/电源时序/设备树 |
| 拓扑里没有 Sensor | `i2cdetect -y -r <bus>` | 地址/上电/mclk |
| 画面整体偏绿 | `media-ctl --print-topology` 查 Bayer | Bayer 排列声明错 |
| 画面斜切 | `v4l2-ctl --get-fmt-video` 查 bytesperline | stride 不匹配 |
| 规律性条纹 | 查设备树 `data-lanes` | lane 顺序/极性 |
| 偏紫偏品红 | 查 ISP 统计中断频率 | 3A 未收敛 |
| fps 砍半 | `v4l2-ctl --get-parm` + 实测对比 | link 频率/带宽链 |
| fps 随负载波动 | 降维：关 GPU 再测 | DDR 竞争 |
| 帧间隔尖刺抖动 | 帧间隔直方图 99.9 分位 | 调度/中断延迟 |
| 帧间隔双峰 | 切 performance governor 对比 | DVFS 跳频 |

## <span class="blue"> 本节总结

Camera 故障四类——节点缺席、颜色错、帧率不够、抖动大——分别落在链路的四个层面：probe 链路、格式声明、带宽算术、时序确定性。排查方法论统一：先分段（拓扑图+抓帧验证）把故障关进一段，再降维（降分辨率/关负载）确认瓶颈方向，后换元（替换单一变量）隔离根因。每类故障的第一条命令是固定的，症状-入口表值得贴在工位上。注意两个跨节呼应：斜切花屏的 stride 问题在 25.3 已有机理，节拍抖动与 compositor 的关系在 25.4 已有结论——故障排查不是新技能，是前五节机制的组合应用。

**本节自查：**

1. "没有 /dev/video0"和"拓扑里没有 Sensor entity"这两种现象，排查方向有什么不同？
2. 画面偏绿和偏紫，为什么前者查 Bayer 声明、后者查 3A 收敛？
3. 驱动标称 30fps、实测 15fps，降分辨率到 720p 后 fps 仍不变——瓶颈在哪一段？为什么？
4. 帧间隔呈双峰分布和个别尖刺，分别指向什么根因？各自的验证动作是什么？
