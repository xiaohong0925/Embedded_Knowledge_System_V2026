# 25.1 Pipeline 全景与 Media Controller 实操

> 所属章节：第25章 Camera全链路：从Sensor到屏幕
>
> 难度：[E] | 预计阅读时间：40 分钟

## <span class="blue"> 本节导读

第 22.5 节已经从决策层面回答过"摄像头数据走哪条路、路上拷贝几次"。本节换一个视角：**把这条路当成一条传送带，跟着一帧图像从头走到尾**，搞清楚每一段由谁驱动、在内核里长什么样、出了问题在哪一段查。

传送带有个现实问题：早期摄像头方案里，Sensor 出来的数据直接进内存，内核只需要一个 `/dev/video0` 就能描述全部。但现代 SoC 的图像通路是 Sensor → CSI 接收器 → ISP → 缩放器 → 内存的多级结构，每一级都可以独立配置格式和分辨率——一个设备节点表达不了这种拓扑。内核为此引入了 Media Controller 框架，把整条通路描述成一张可配置的图。本节覆盖：

- 一帧图像的完整旅程：硬件通路和内核软件栈的对应关系
- 为什么一个 `/dev/video0` 不够用：Media Controller 要解决的问题
- entity / pad / link 三个核心概念
- `media-ctl` 实操：读拓扑、查格式、建链、验证采集
- 拓扑排查的思路：从拓扑图反推"哪一段没通"

> 💡 本节的操作基于 RK3568（rkisp1 驱动，Linux 5.10/6.x）的真实拓扑。其他平台的 entity 名字不同，但图的结构和操作方法完全一致。

## <span class="blue"> 一帧图像的完整旅程

先把整章的地图画出来。一帧图像从光子打到 Sensor 开始，到屏幕上被看见为止，经过的硬件通路：

```
光线 → Sensor（感光+AD转换）
        │  MIPI CSI-2（差分串行，2/4 lane）
        ▼
     CSI-2 接收器（D-PHY 解码，还原像素流）
        │
        ▼
     ISP（去噪/3A/Bayer转YUV）
        │  DMA 写入
        ▼
     DDR 内存（帧缓冲，VB2 管理的 buffer）
        │  DMA 读出
        ▼
     显示控制器（多图层合成）
        │  MIPI DSI / LVDS / eDP
        ▼
     Panel（屏幕）
```

> MIPI CSI-2：摄像头到 SoC 的标准串行接口，"CSI"是 Camera Serial Interface。它用差分对（lane）传输，每条 lane 是一对时钟/数据线，常见 2 lane 或 4 lane。协议细节见 B-C.9.2，本节只需要知道：它是 Sensor 和 SoC 之间的那根"管子"。

<!-- -->

> Bayer：Sensor 感光阵列上每个像素只感一种颜色（R/G/B 之一），按 Bayer  pattern 排列。原始数据（RAW）不是彩色图像，必须经过 ISP 插值运算（demosaic）才变成每个像素都有完整 RGB 的图像。**出图绿色/紫色这类经典故障，多半就和 Bayer 格式声明不匹配有关**（25.6 展开）。

硬件通路在内核里对应一串驱动，每个驱动管一段：

```
内核空间
┌──────────────┐   ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│ Sensor 驱动  │──▶│ CSI-2 接收   │──▶│ ISP 驱动     │──▶│ DRM/KMS      │
│ (V4L2 subdev)│   │ (V4L2 subdev)│   │ (V4L2 video) │   │ 显示驱动     │
└──────────────┘   └──────────────┘   └──────┬───────┘   └──────▲───────┘
                                             │ DMA 写           │ DMA 读
                                        ┌────▼──────────────────┴────┐
                                        │   DDR：VB2 管理的帧缓冲     │
                                        └────────────────────────────┘
用户空间
   应用程序（open/read/ioctl）◀── /dev/video0（ISP 暴露的采集节点）
   配置工具（media-ctl）     ◀── /dev/media0（拓扑配置节点）
```

注意图里出现了一个新东西：`/dev/media0`。它不参与数据传输，存在的唯一目的是**让应用能查看和修改这张拓扑图**——这就是 Media Controller。

## <span class="blue"> 为什么一个 /dev/video0 不够用

要理解 Media Controller 存在的意义，先看没有它时的困境。

早期摄像头方案（比如 USB 摄像头 UVC），数据通路固定：Sensor 出图 → 直接进内存。内核暴露一个 `/dev/video0`，应用对它 `ioctl` 设分辨率、开流、读帧，完事。整条通路没有任何可配置的分支，一个节点足够描述。

现代 SoC 的图像通路完全不同。以 RK3568 为例，ISP 有两个输出通道：mainpath（支持缩放，最高 4K）和 selfpath（小图预览专用）。数据从 ISP 出来后可以走 mainpath、走 selfpath、或者两路同时走。每一段的格式还能独立配置：Sensor 输出 RAW10，CSI 接收器透传 RAW10，ISP 输入 RAW10、输出 NV12。**这不是一条线，是一张图**——有分支，每段有自己的属性。

一个 `/dev/video0` 暴露不了这些信息：

- 应用怎么知道 ISP 后面挂了几个输出节点？
- 应用怎么把"Sensor 输出 1920×1080 RAW10"这个配置告诉 Sensor 驱动，而不是 ISP 驱动？
- 两路同时出图时，应用怎么把 selfpath 那条链路关掉省电？

Media Controller 的答案：**把每个硬件模块抽象成 entity（实体），模块之间的连接点抽象成 pad（焊盘），连接本身抽象成 link（链路），整张图通过 /dev/mediaX 暴露给用户空间**。应用先读图、配好每一段的格式、接通需要的 link，最后才去 `/dev/videoX` 开流采集。

> entity：图中的一个节点，对应一个硬件功能模块（Sensor、CSI 接收器、ISP、视频输出节点）。每个 entity 在内核里由一个驱动注册。

<!-- -->

> pad：entity 上的连接点，分 sink（数据流入）和 source（数据流出）两种。数据总是从某个 entity 的 source pad 流向另一个 entity 的 sink pad。

<!-- -->

> link：两个 pad 之间的连接，有 ENABLED（接通）和 IMMUTABLE（不可改）等标志。配置 pipeline 的本质就是把需要的 link 置为 ENABLED。

这三个概念是读拓扑图的字母表。下面直接看真图。

## <span class="blue"> media-ctl 实操：读懂拓扑

`media-ctl` 是 Media Controller 的命令行工具，Buildroot 里开 `BR2_PACKAGE_LIBMEDIA` 或直接用 v4l-utils 包获得。先看设备上有哪些 media 节点：

```
ls /dev/media*
/dev/media0
```

打印完整拓扑（输出做了删减和注释，保留了关键结构）：

```
media-ctl -d /dev/media0 --print-topology
```

```
Media controller API version 5.10.160

Media device information
------------------------
driver          rkisp1
model           rkisp1
bus info        platform:rkisp1

Device topology
- entity 1: m00_b_imx415 2-001a (1 pad, 1 link)
            type V4L2 subdev subtype Sensor
            device node name /dev/v4l-subdev0
        pad0: Source
                [fmt:SBGGR10_1X10/1920x1080]
                -> "rockchip-csi2-dphy0":0 [ENABLED]

- entity 2: rockchip-csi2-dphy0 (2 pads, 2 links)
            type V4L2 subdev subtype Unknown
            device node name /dev/v4l-subdev1
        pad0: Sink
                [fmt:SBGGR10_1X10/1920x1080]
                <- "m00_b_imx415 2-001a":0 [ENABLED]
        pad1: Source
                [fmt:SBGGR10_1X10/1920x1080]
                -> "rkisp1-csi":0 [ENABLED]

- entity 3: rkisp1-csi (2 pads, 3 links)
            type V4L2 subdev subtype Unknown
        pad0: Sink
                <- "rockchip-csi2-dphy0":1 [ENABLED]
        pad1: Source
                -> "rkisp1-isp-subdev":0 [ENABLED]

- entity 4: rkisp1-isp-subdev (2 pads, 4 links)
            type V4L2 subdev subtype Unknown
            device node name /dev/v4l-subdev2
        pad0: Sink
                [fmt:SBGGR10_1X10/1920x1080]
                <- "rkisp1-csi":1 [ENABLED]
        pad1: Source
                [fmt:NV12/1920x1080]
                -> "rkisp1_mainpath":0 [ENABLED]
                -> "rkisp1_selfpath":0 []

- entity 5: rkisp1_mainpath (1 pad, 1 link)
            type Node subtype V4L2
            device node name /dev/video0
        pad0: Sink
                <- "rkisp1-isp-subdev":1 [ENABLED]

- entity 6: rkisp1_selfpath (1 pad, 1 link)
            type Node subtype V4L2
            device node name /dev/video1
        pad0: Sink
                <- "rkisp1-isp-subdev":1 []
```

这张图就是本节开头那张软件栈图的"内核登记版"。从左到右读出四个关键事实：

1. **Sensor 在 I2C 上**：entity 名字 `m00_b_imx415 2-001a` 里的 `2-001a` 是 I2C 总线 2、地址 0x1a。Sensor 是 I2C 从设备，它的驱动通过 I2C 配置寄存器——如果拓扑里压根没有这个 entity，先去查 I2C 通不通（25.6 的第一个排查路径）。
2. **格式沿链路演进**：Sensor 的 source pad 是 `SBGGR10_1X10/1920x1080`（Bayer 排列 BGGR、每像素 10bit 打包），一路透传到 ISP 的 sink pad 不变；ISP 的 source pad 变成了 `NV12/1920x1080`——Bayer→YUV 的转换就发生在 ISP 内部。`SBGGR10_1X10` 这种名字的读法：`S` 开头表示 packed（打包格式），`BGGR` 是 Bayer 排列，`10` 是位深。
3. **分支在 ISP 的 source pad**：mainpath 的 link 是 `[ENABLED]`，selfpath 的 link 是 `[]`（未使能）。当前只有 `/dev/video0` 在出图。
4. **每个 entity 有自己的设备节点**：Sensor、DPHY、ISP 各有一个 `/dev/v4l-subdevN`，可以给它们单独发 ioctl；数据出口是 `/dev/video0` 和 `/dev/video1`。

> 💡 拓扑里 link 后的方括号是重点检查对象：`[ENABLED]` 接通、`[]` 断开、`[IMMUTABLE]` 硬件固定不可改。采集不出图时，先确认从 Sensor 到 video 节点之间存在一条全 ENABLED 的完整路径。

## <span class="blue"> media-ctl 实操：改链路与配格式

读图只是第一步，Media Controller 的价值在于改图。

**接通 selfpath，实现双路同时出图：**

```
media-ctl -d /dev/media0 --link '"rkisp1-isp-subdev":1 -> "rkisp1_selfpath":0 [1]'
```

引号里的 `"entity名":pad号` 定位一个 pad，`->` 表示从 source 指向 sink，末尾 `[1]` 表示使能（`[0]` 断开）。执行后再 print-topology，能看到 selfpath 那条 link 变成了 `[ENABLED]`，`/dev/video1` 就可以独立开流了。

**修改某一段的格式。** 比如 Sensor 支持 4K，但当前拓扑跑在 1080p，要切到 4K 采集，需要把链路上相关 pad 的格式逐段改掉：

```
media-ctl -d /dev/media0 \
    --set-v4l2 '"m00_b_imx415 2-001a":0[fmt:SBGGR10_1X10/3840x2160]'
media-ctl -d /dev/media0 \
    --set-v4l2 '"rkisp1-isp-subdev":0[fmt:SBGGR10_1X10/3840x2160]'
media-ctl -d /dev/media0 \
    --set-v4l2 '"rkisp1-isp-subdev":1[fmt:NV12/3840x2160]'
```

注意改的是**每一段 pad 的格式**，而不是一个全局命令。这正是 Media Controller 的设计哲学：每一段是独立模块，内核不替你猜"改 Sensor 分辨率要不要联动 ISP"，全部显式配置。配完记得验证——再 print-topology 确认三个 pad 的 fmt 都变了，少配一段的典型症状是开流报错或出图尺寸不对。

**验证采集。** 拓扑配好后，用 `v4l2-ctl` 抓一帧确认链路真的通了：

```
v4l2-ctl -d /dev/video0 --set-fmt-video=width=3840,height=2160,pixelformat=NV12 \
    --stream-mmap --stream-count=10 --stream-to=/tmp/test.nv12
```

`--stream-mmap` 用 mmap 方式开流（对应 25.2 要讲的 VB2 队列机制），`--stream-count=10` 抓 10 帧。能抓到文件且大小非零，说明 Sensor → DPHY → CSI → ISP → DDR 这条链路全通。抓到的 NV12 裸数据可以用 7yuv、ffplay 等工具查看确认图像内容正常：

```
ffplay -f rawvideo -pixel_format nv12 -video_size 3840x2160 /tmp/test.nv12
```

> 💡 这一套"print-topology 读图 → set-v4l2 配段 → v4l2-ctl 抓帧"是摄像头 bring-up 的标准动作。它比直接写应用代码先试，能更快定位问题在哪一段：media-ctl 层面就不通，问题在内核驱动和设备树；media-ctl 层面通了应用不通，问题在应用代码。

## <span class="blue"> 从拓扑图反推故障位置

拓扑图不只是配置工具，还是排查地图。采集链路的故障大体分三类，每一类在拓扑图上有不同的面相：

**Sensor 缺席。** print-topology 里没有 Sensor entity，ISP 的 sink pad 上孤零零没有来源。原因收敛到三处：I2C 不通（地址错、上电时序错）、设备树里 Sensor 节点没配或 status 不是 "okay"、Sensor 驱动 probe 失败。用 `dmesg | grep -i imx`（换成你的 sensor 型号）和 `i2cdetect -y -r 2` 交叉确认。

**链路断裂。** 所有 entity 都在，但某条 link 是 `[]`。可能是设备树里 `remote-endpoint` 配错了对象，也可能是上一节的 `--link` 没执行。整条路径必须是从 Sensor 到 video 节点全 ENABLED。

**格式错配。** 链路全通但开流报错（`VIDIOC_STREAMON: Invalid argument`）或出图异常。逐段对比相邻 pad 的 fmt：上游 source 是 `3840x2160`，下游 sink 还是 `1920x1080`，就是忘了联动配置。Bayer 排列不一致（Sensor 出 BGGR，ISP 按 GBRG 解）不会报错，但出图颜色整个错乱——这就是 25.6 要处理的"绿色/紫色图"的机理。

这三类覆盖了 bring-up 阶段八成的问题，剩下两成（时钟、电源、lane 顺序）在 25.6 展开。

## <span class="blue"> 本节总结

现代 SoC 的摄像头通路是一张多模块、可分支、逐段可配的图，单个 `/dev/video0` 表达不了它，内核用 Media Controller 把整张图暴露给用户空间。读图的字母表只有三个词：entity（模块）、pad（连接点）、link（连接）。`media-ctl --print-topology` 是这张图的入口，读它能直接回答三个问题：Sensor 在不在、链路通不通、每段格式对不对。配置拓扑就是显式地逐段设格式、逐条建 link，然后用 `v4l2-ctl` 抓帧验证。这套"读图→配图→验证"的动作，是后续所有 Camera 工作的起点，也是 25.6 故障排查的基本地图。

**关键结论速查：**

| 问题 | 答案 |
|------|------|
| Media Controller 解决什么 | 单 video 节点表达不了多模块、可分支的现代图像通路 |
| 三个核心概念 | entity=模块，pad=连接点（sink 入/source 出），link=连接 |
| 拓扑入口 | `media-ctl -d /dev/media0 --print-topology` |
| 数据出口 vs 配置出口 | `/dev/videoX` 出数据，`/dev/mediaX` 管拓扑，`/dev/v4l-subdevN` 配模块 |
| 改图两个动作 | `--link` 通断链路，`--set-v4l2` 逐段配格式 |
| 验证链路 | `v4l2-ctl --stream-mmap --stream-count=N` 抓帧 |
| 排查顺序 | Sensor 在不在 → 链路全 ENABLED 否 → 相邻 pad 格式匹配否 |

**本节自查：**

1. 为什么 ISP 之后可以挂 mainpath 和 selfpath 两个 video 节点？这体现了 Media Controller 相对单节点模型的什么能力？
2. `m00_b_imx415 2-001a` 这个名字里包含哪两个硬件事实？
3. 把 Sensor 分辨率从 1080p 改到 4K，为什么要用三条 `--set-v4l2` 而不是一条？
4. print-topology 里某条 link 显示 `[]`，采集一定会失败吗？什么情况下不会？

**下一步：** 拓扑配通了，数据开始流了——但"流"这件事本身是有一套机制的：buffer 谁分配、怎么排队、应用和驱动怎么交接，帧丢了是哪一环丢的。25.2 进入 V4L2 采集链路，拆解 VIDIOC 调用序列和 VB2 队列状态机。
