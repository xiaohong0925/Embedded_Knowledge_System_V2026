# 25.7 综合实战：智能门铃延迟优化

> 所属章节：第25章 Camera全链路：从Sensor到屏幕
>
> 难度：[E] | 预计阅读时间：50 分钟

## <span class="blue"> 本节导读

前六节的内容——拓扑（25.1）、采集（25.2）、零拷贝（25.3）、显示（25.4）、测量（25.5）、排查（25.6）——每一节都解决链路上的一段问题。这一节把它们压进一个完整案例：**智能门铃，从按铃到室内屏出画面，产品指标 <150ms，初版方案实测约 300ms，最终优化到 120ms**。

这个案例的价值不在"门铃"本身，而在于它是 Camera 链路优化的标准形态：指标是总量，瓶颈藏在某几段，每步优化都要有测量依据、有收益数字、有副作用评估。整个复盘分四段：原始架构与初判 → 测量与预算表 → 五步优化逐步拆解 → 验证与复盘。你会发现，五步优化里没有一步是"调参"——全部是架构级改动，这正是 25.5 预算表方法的必然结果：差额大的段全是结构性问题。

---

## <span class="blue"> 背景：初版方案与它的三百毫秒

产品形态：门口机（camera + 按键 + 无线）+ 室内屏（7 寸 MIPI DSI，RK3566，1024×600）。链路范围从"访客按下门铃按钮"到"室内屏上出现门口画面"，产品指标 150ms——超过这个值，访客会觉得"按了没反应"，去按第二次。

初版方案是工程师的直觉写法，每一环单独看都"很合理"：

```
门口机端：Sensor(IMX415) → ISP → NV12帧 → H.264编码 → Wi-Fi → 室内屏
室内屏端：收到码流 → 解码出NV12帧 → 应用转RGB32 → weston/GPU合成上屏
```

系统架构上还有一层背景：室内屏跑着完整的 weston 桌面（要显示天气、日历等 UI），camera 预览只是桌面上的一个窗口——所以初版很自然地走了"解码 → 格式转换 → 交给 weston 合成"的路径。

初版实测 300ms（手机 240fps 慢动作法）。团队的初始判断分两派：一派认为"Wi-Fi 传输是瓶颈，要优化网络协议栈"，另一派认为"H.264 编解码太慢，要换更低延迟的编码参数"。两派都准备动手了——幸好先做了测量。

## <span class="blue"> 第一阶段：测量，先杀掉两个错误假设

按 25.5 的五步流程，先分段。门铃比本地预览多两段（编码+传输、解码），完整分解：

| 段 | 环节 | 实测 | 测量手段 |
|----|------|------|----------|
| A | 按键消抖+门口机唤醒 | 8ms | GPIO 打点 |
| B | 曝光+ISP+采集 | 55ms | V4L2 timestamp |
| C | H.264 编码 | 25ms | 编码器输入输出打点 |
| D | Wi-Fi 传输 | 12ms | 双端 monotonic 时钟对时 |
| E | H.264 解码 | 18ms | 解码器打点 |
| F | NV12→RGB32 转换 | 30ms | 应用打点 |
| G | GPU 合成+weston 节拍 | 110ms | 应用打点+page-flip 事件 |
| H | 等 vblank+scanout | 42ms | page-flip 事件+帧周期折算 |
| — | **合计** | **300ms** | 与光电二极管实测 295ms 对账 ✓ |

测量结果直接把两个初始假设都杀了：**Wi-Fi 只有 12ms，编解码合计 43ms**——网络派和编码派准备的优化方向，加起来只值 55ms 的账面，全抠光也到不了 150ms。真正的大头在 G 段 110ms 和 H 段 42ms：显示路径吃掉了总延迟的一半。

再看 G 段的内部构成（应用打点细分）：GPU 合成计算本身约 40ms，**剩下约 70ms 是等 weston 的合成节拍**——解码出的帧到达时，weston 往往刚合成完一帧，要等下一个合成周期。这正是 25.4 讲过的 Compositor 架构税：通用性换延迟，一分不少。

预算表（25.5 四步法）随即填出"差额"列：

| 段 | 实测 | 物理/合理下限 | 差额 | 备注 |
|----|------|---------------|------|------|
| A 按键 | 8ms | 5ms | 3ms | 不值得动 |
| B 采集 | 55ms | 35ms | 20ms | 队列深度有水分 |
| C 编码 | 25ms | 15ms | 10ms | 可小挤 |
| D 传输 | 12ms | 8ms | 4ms | 不值得动 |
| E 解码 | 18ms | 15ms | 3ms | 不值得动 |
| F 转换 | 30ms | **0ms** | **30ms** | 可以让 ISP 直接出 |
| G 合成 | 110ms | **0ms** | **110ms** | 可以整个绕开 |
| H 上屏 | 42ms | 25ms | 17ms | vblank 节拍，难动 |

靶子清清楚楚：F+G 合计 140ms 的差额，而这两段在物理上可以趋近于零——它们不是"做得慢"，是"根本不该存在"。

## <span class="blue"> 五步优化

### 第一步：ISP 直接输出 RGB，砍掉 F 段（-30ms）

**依据：** F 段存在的唯一原因是"解码输出 NV12，weston 的 GPU 合成吃 RGB32"。但 RK3566 的 ISP/VOP 链路里，解码器（VPU）本身支持直接输出 RGB 格式——格式转换不是必须做的，是初版懒得配置的结果。

**改动：** 解码器输出格式从 NV12 改为 RGB32（`VIDIOC_S_FMT` 换 pixelformat，一行配置），应用里的软件转换代码整段删除。

**收益：** 30ms → 0ms。**代价：** 无——VPU 输出 RGB 与输出 NV12 的耗时实测无差异。

**这一步的教训值得单独记住：** 链路上每一次格式转换都值得问一句"上游能不能直接产出我要的格式"。ISP/VPU/显示控制器的格式能力清单（25.4 的 modetest、V4L2 的 ENUM_FMT）就是答案库，软件转换永远是最后选择。

### 第二步：绕开 weston，预览帧直写 overlay plane（-40ms 起步）

**依据：** G 段 110ms 里 70ms 是节拍等待、40ms 是 GPU 合成——而预览画面是固定位置、固定大小的全屏视频窗口，根本不需要合成器的通用性。25.4 的结论直接适用：Direct Display。

**改动：** 解码后的 dma-buf fd 不走 Wayland/weston，应用直接持有 DRM master（预览激活期间 weston 让出 DRM，门铃挂断后归还），atomic commit 把帧绑到 overlay plane，UI 层（时间、挂断按钮）留在 primary plane 由硬件合成。

**收益：** G 段 110ms → 约 0ms（帧写完即挂 plane），H 段因提交时机改善顺带从 42ms 降到 33ms（NONBLOCK+page-flip 事件让提交总能赶上下一个 vblank）。**合计收益 117ms——单步最大。**

**代价与对策：** 应用要自己管理 DRM 资源（plane 选择、weston 的 DRM 主从切换），代码量增加约 300 行；UI 与视频的叠加从"GPU 任意合成"退化为"硬件图层叠加"，UI 只能整层置顶/置底——产品接受了这一限制（门铃 UI 本来就只有一层按钮）。

### 第三步：采集端 buffer 队列 4 帧改 2 帧（-33ms）

**依据：** B 段 55ms 里藏着队列延迟：门口机采集端 REQBUFS 申请了 4 个 buffer，编码器消费速度略慢于 ISP 生产时，队列里会稳定积压 1~2 帧——编码器拿到的永远是"一帧前的画面"。30fps 下每个排队的帧就是 33ms 的纯延迟。

**改动：** 采集端 buffer 数 4→2，编码器线程提到最高调度优先级（SCHED_FIFO，优先级参考第 20 章实时性设计），保证生产即消费、队列无积压。

**收益：** B 段 55ms → 22ms，省 33ms。**代价：** 抗抖动余量变小——Wi-Fi 发送线程大卡顿时可能丢帧。用 25.2 的 sequence 连续性检查做回归：连续一万帧丢帧 3 帧，产品接受（丢帧的表现是画面轻微一跳，延迟不劣化）。

### 第四步：全链路 DMA-BUF 零拷贝（-20ms）

**依据：** 前三步之后，链路里还剩两处拷贝：解码器输出 buffer → 应用 buffer（memcpy 约 12ms），应用 buffer → DRM dumb buffer（memcpy 约 8ms）。25.3 的五步法直接套用。

**改动：** 解码器以 DMABUF 模式输出（`V4L2_MEMORY_DMABUF`，buffer 由 DRM 侧 GBM 分配并导出），解码帧直接落在可 scanout 的内存里，应用零拷贝转交 atomic commit。stride 对齐按 25.3 的方法处理：先 `VIDIOC_G_FMT` 拿解码器 bytesperline，据此创建 GBM buffer。

**收益：** 20ms。**代价：** 踩了一个坑——首版 GBM 分配的 modifier 与 VOP 期望不符，画面斜切（25.6 的 stride 面相），改为 `GBM_BO_USE_LINEAR` 线性布局后正常。这正是 25.3"先用 TEST_ONLY 和小流量验证"警告的现实版。

### 第五步：收尾微调（-12ms）

剩余差额的小项合并处理：编码器 GOP 结构改为全 I 帧前的低延迟模式（C 段 -8ms，码率上升 15%，Wi-Fi 带宽远未饱和，接受）；按键消抖从 8ms 调到 5ms（A 段 -3ms，双倍触发的误报率实测无变化）；门口机 CPU governor 从 schedutil 改 performance 并把 ISP/编码中断绑到专用核（消除偶发尖刺，平均无收益但 99 分位改善 18ms——25.6 抖动路径的应用）。

## <span class="blue"> 优化后：预算表与验证

五步之后的最终账：

| 段 | 优化前 | 优化后 | 手段 |
|----|--------|--------|------|
| A 按键 | 8ms | 5ms | 消抖参数 |
| B 采集 | 55ms | 22ms | 队列 4→2 |
| C 编码 | 25ms | 17ms | 低延迟 GOP |
| D 传输 | 12ms | 12ms | 未动 |
| E 解码 | 18ms | 18ms | 未动 |
| F 转换 | 30ms | 0ms | VPU 直出 RGB |
| G 合成 | 110ms | 0ms | 绕开 weston |
| H 上屏 | 42ms | 33ms | NONBLOCK+事件 |
| **合计** | **300ms** | **107ms** | |

软件分段合计 107ms，光电二极管法实测 120ms——差值 13ms 在 panel 内部处理延迟与⑦折算误差的合理范围内，对账通过。**120ms < 150ms 指标，且有 30ms 裕量。**

回归验证三件套（零拷贝链路的验收标准，25.3 定下的规矩）：真机满帧率连续运行 72 小时无花屏无泄漏（`bufinfo` 引用计数稳定）；按键-出图延迟抽检 500 次，均值 118ms、99 分位 131ms，无一超 150ms；高低温箱 -10℃/55℃ 各 24 小时，延迟分布无漂移。

## <span class="blue"> 复盘：这个案例教什么

**最大的延迟不是"慢"，是"多余"。** 300ms 里约 160ms 来自两件事：一次本可由硬件完成的格式转换（F），和一套本不需要经过的合成器（G）。它们不是性能问题，是架构问题——单看每一段代码都"没问题"，凑在一起就是 160ms 的冤枉路。这也是全章开头那句话的实证：**最大的延迟往往不是单个环节的延迟，而是不必要的格式转换和数据搬运。**

**测量先行省掉的是无效劳动。** 如果不做分段测量，网络派和编码派的优化各做两周，合计收益上限 55ms 且大概率只能挤出一半——指标照样不达标。一小时的测量（25.5 的五步流程）把两周的无效劳动变成了五步精确打击。

**物理下限要敬畏。** 优化后 H 段 33ms 一动不动——60Hz 面板的 vblank+scanout 就是这么多，谁来都压不下去。预算表里"物理/合理下限"那一列的意义在此：它告诉你哪些段该放弃，把精力留给有差额的段。

**每步改动都有代价，明示出来才能评审。** 直写 plane 牺牲了 UI 合成灵活性，队列减帧牺牲了抗抖动余量，低延迟 GOP 牺牲了码率——优化不是免费的，是拿明确列出的代价换明确测出的收益。这五步里没有一步是"无副作用"的，但每一步的副作用都被量化并接受了。

## <span class="blue"> 延伸：如果这是机器人视觉呢

把同一个链路放进机器人避障场景，预算表的优先序会重排（25.5 的场景差异表在这里兑现）：

- **F/G 两段照样砍**——转换和合成在任何场景都是纯浪费；
- **第三步要反向做**：队列不是 4→2，而是 2→1，宁可丢帧不要旧帧排队（SLAM 吃时间戳新鲜度）；
- **第五步的优先级提到最高**：时间戳精度和抖动是 SLAM 的命脉，governor、中断亲和性、时间戳校准（V4L2 timestamp 与 PTP 系统时钟对时）比平均延迟重要；
- **多目同步成为新段落**：双目 camera 需要硬同步曝光（外部触发信号接两个 Sensor 的 FSIN 引脚）或帧级软同步，这是门铃案例里不存在的一段。

同一个方法论，不同的场景权重——这就是预算表作为工具的泛化能力。

## <span class="blue"> 本节总结

门铃案例五步优化（ISP/VPU 直出 RGB -30ms、绕开 weston -117ms、队列减帧 -33ms、DMA-BUF -20ms、收尾微调 -12ms），把 300ms 压到 120ms，全程靠的是 25.5 的测量方法和预算表：先分段杀掉错误假设，再找差额最大的段做架构级改动，每步改动明示代价。复盘的四条教训——延迟大头是多余而非慢、测量省的是无效劳动、物理下限要敬畏、优化是代价与收益的明账——适用于任何 Camera 链路产品。场景切换到机器人视觉时，方法论不变，权重重排：转换与合成照砍，队列深度反向取舍，时间戳精度升为第一优先级。
