# 28.3 外设功耗管理实操

> 所属章节：第28章 功耗全链路
>
> 难度：[E] | 预计阅读时间：40 分钟

## <span class="blue"> 本节导读

三大件（28.2）之外，外设是功耗问题的第二大案发地——而且这里的案情更隐蔽：CPU 的功耗行为有 cpufreq/cpuidle 的完整读数，外设的功耗状态散落在几十个设备的 sysfs 属性里，没人审计就没人知道"Wi-Fi 模组一直没睡""摄像头断电后引脚还在漏电"。28.7 案例里最大的单笔收益（101mW）不来自任何驱动优化，来自一组引脚的电平配置——外设功耗的战场一半在软件，一半在引脚。

本节把外设功耗管理拆成三件实操：Runtime PM 的行为审计（哪些设备该睡没睡）、pinctrl 的 sleep 状态（引脚漏电的机理与配置）、wake IRQ 的规划（谁能唤醒系统）。本节覆盖：

- Runtime PM 行为审计：全设备扫描与"该睡没睡"的定位
- 审计实录：五台 active 设备四种处置的完整走查
- autosuspend 配置与引用计数占用排查
- pinctrl sleep 状态：floating 引脚漏电的机理与设备树配置
- wake IRQ 与 `/sys/.../power/wakeup`：唤醒源规划
- 常见外设的功耗策略速查

> 💡 Runtime PM 的引用计数模型和 genpd 机制在 15.1.2/15.1.3 有完整讲解，本节只做行为观测与配置实操。

## <span class="blue"> Runtime PM 审计：哪些设备该睡没睡

Runtime PM 的状态机回顾（机制见 15.1）：设备空闲超时后驱动把它挂起（断电/关时钟），有访问时自动恢复。每个设备的当前状态在 sysfs 里一目了然：

```
cat /sys/devices/platform/ff9a0000.gpu/power/runtime_status
suspended
```

审计的目标是回答"全系统有多少设备正处于 active 但本该 suspended"。一条命令扫出候选清单：

```bash
for d in /sys/devices/platform/*/power/runtime_status; do
    st=$(cat $d)
    [ "$st" = "active" ] && echo "ACTIVE: ${d%/power/*}"
done
```

扫出来的 active 设备分三类处置：

**该睡但驱动没开 autosuspend 的**——手动打开并设延迟：

```bash
echo auto > /sys/devices/platform/xxx/power/control        # 允许自动挂起
echo 2000 > /sys/devices/platform/xxx/power/autosuspend_delay_ms  # 空闲2秒后挂起
```

`autosuspend_delay_ms` 的取舍：挂起/恢复本身有开销（恢复延迟几毫秒到几十毫秒），延迟设太短会在频繁访问的设备上造成"睡了就醒、醒了又睡"的抖动耗电；设太长则省电效果打折。经验值：访问间隔明确的设备（传感器轮询）设为访问间隔的一半，访问模式不明的设备从 2 秒起步。

**该睡但引用计数被占着的**——查占用源：

```bash
cat /sys/devices/platform/xxx/power/runtime_usage          # >0 说明有人拿着引用
```

引用计数的持有者可能是：打开的设备节点（某个进程 open 着没关）、子设备（父设备因子设备 active 而不能睡）、驱动自身的 bug（pm_runtime_get 了没 put）。前两类是配置问题，第三类要进驱动代码。

**本来就不该睡的**——正在持续工作的设备（系统盘 eMMC 在读写的设备上 active 是正常的）。审计的判断标准不是"active 数量"，而是"**空闲场景下的 active 清单**"：先把系统置空载，再扫描，这时还 active 的每一个都要能说出理由。

### 审计实录：一次空载扫描的完整处置

把扫描到处置走一遍。设备：手持终端，灭屏空载 5 分钟后扫描：

```
ACTIVE: /sys/devices/platform/ff0d0000.i2c
ACTIVE: /sys/devices/platform/ff3e0000.mmc       ← SD卡槽（没插卡）
ACTIVE: /sys/devices/platform/ff9a0000.gpu
ACTIVE: /sys/devices/platform/ff5c0000.video-codec
ACTIVE: /sys/devices/platform/fe2a0000.serial    ← 调试串口
```

五个候选逐个过堂：

**ff3e0000.mmc（SD 卡槽）：该睡没睡型。** 空载没插卡却 active——查 control 是 `on`（驱动开了 runtime PM 但系统从未允许自动挂起）。处置：`echo auto > power/control`，延迟 1000ms。再测：进入 suspended，空载电流降 8mA。

**ff9a0000.gpu：引用占用型。** runtime_usage=1，追查是显示服务进程持有 GPU fd（合成器常驻）。处置分两问：这个进程空载时还活着合理吗（合理，桌面环境）→ 它持有 fd 但没渲染时驱动该不该挂起（该，是驱动 runtime PM 实现不完整）。短期对策：接受 active；长期项：提驱动修复工单。**审计的价值之一是产出这种"接受但记账"的决策。**

**ff5c0000.video-codec：同 GPU 但不同处置。** runtime_usage=0、control=on——没有占用却没睡，是驱动没实现 runtime suspend。确认芯片手册支持断电后，处置是补丁级任务（28.7 案例的"Runtime PM 优化省 ~200mW"主要就是这类）。本次先登记为已知项。

**fe2a0000.serial：本来就不该睡型（当前形态下）。** 调试串口保持 active 是开发期故意配置（日志随时可看）。但登记一条量产动作：量产固件里调试串口关闭，此项随配置消失。

**ff0d0000.i2c：误报型。** I2C 控制器 active 是因为挂在它上面的 PMIC 每秒有通信——它在正常工作，不需要睡。

五台设备四种处置：开 autosuspend、接受记账、登记补丁、确认误报——**审计的产出不是"全绿了"，是每一台 active 都有书面理由**。空载电流从 68mA 降到 60mA，剩下的大头转交 28.4 的 suspend 策略处理。

## <span class="blue"> pinctrl sleep 状态：107mW 的引脚漏电

这是 28.7 案例的核心案情，先讲机理再讲配置。

**漏电机理。** SoC 的 GPIO 引脚在作为输入时，内部是 CMOS 输入级——它的功耗特性是：电平稳定在 0 或 1 时几乎不耗电，**电平悬浮（floating）在中间电平时，输入级的两个互补管会同时部分导通，形成从电源到地的直通电流**。一个悬浮输入引脚可能漏零点几到几毫安，一组 I2C/MMC/SDIO 引脚（SDIO 4bit+CLK+CMD 就是 6 根）悬浮起来，几十毫瓦就这么没了。

设备 suspend 时这个坑的典型触发场景：外设断电了（Wi-Fi 模组断电、eMMC 进睡眠），但 SoC 侧的引脚还保持 default 状态——对端芯片断电后 IO 电平坍塌，SoC 侧的上拉/输入级面对的就是悬浮电平，漏电开始。**外设睡没睡和引脚漏不漏是两件事，驱动通常只管前者。**

**配置方法。** Linux pinctrl 框架的标准解法是设备树里声明两组引脚状态：

```dts
&i2c4 {
    pinctrl-names = "default", "sleep";        /* 声明两组状态 */
    pinctrl-0 = <&i2c4_xfer>;                  /* default：正常功能 */
    pinctrl-1 = <&i2c4_sleep>;                 /* sleep：挂起时切换 */
    ...
};

/* 在pinctrl节点里定义sleep组：输出低电平，断开输入路径 */
&pinctrl {
    i2c4_sleep: i2c4-sleep {
        rockchip,pins = <4 RK_PC2 RK_FUNC_GPIO &pcfg_output_low>,
                        <4 RK_PC3 RK_FUNC_GPIO &pcfg_output_low>;
    };
};
```

原理是把挂起时的引脚从"功能复用（输入悬浮）"切到"GPIO 输出低电平"——电平确定，输入级不悬浮，直通电流消失。28.7 案例里 I2C 引脚这么改省 6mW，MMC 引脚（6 根线）这么改省 101mW——**同一手法，引脚越多收益越大**。

**排查方法。** 怀疑引脚漏电时不用改代码验证：suspend 状态下用万用表逐组量引脚电平——悬浮引脚的电压读数在 0.5×VDD 附近（1.6V 上下晃），确定的高或低电平都是健康的。对照设备树里哪些外设没有配 sleep 状态组，清单即嫌疑清单。

## <span class="blue"> wake IRQ：谁能把系统叫醒

外设功耗的另一半是唤醒管理。两个层面的控制：

**唤醒使能。** 每个有唤醒能力的设备有一个开关：

```
cat /sys/devices/platform/xxx/power/wakeup
enabled                          ← 该设备可以唤醒suspend中的系统
echo disabled > /sys/devices/platform/xxx/power/wakeup
```

产品上没有唤醒职责的外设（比如调试口 UART）应显式 disabled——否则一个误信号就是一次误唤醒，suspend 功耗测试里的"偶发高功耗"常常就是某个外设在偷偷醒系统。唤醒源排查手段在 28.4（`cat /sys/kernel/debug/wakeup_sources`）。

**唤醒 IRQ 的硬件路径。** 能唤醒 suspend 的中断必须走支持唤醒的中断控制器路径（设备树 `wakeup-source` 属性 + 中断控制器侧 enable_irq_wake）。配置错误的形态是"suspend 后按键叫不醒"或"所有中断都能叫醒"——前者查 wakeup-source 声明，后者查中断控制器的 wake mask 配置。机制细节见 15.5.2（唤醒源与 Wakelock）。

## <span class="blue"> 常见外设策略速查

| 外设 | 空闲策略 | suspend 策略 | 关键坑 |
|------|----------|--------------|--------|
| Wi-Fi 模组 | power save（DTIM 监听间隔） | 完全断电或 sleep 模式 | 断电后引脚漏电（pinctrl sleep）；重连耗时计入唤醒延迟 |
| 摄像头 Sensor | runtime suspend（关 mclk/断电） | 断电 | 恢复后需重新初始化寄存器，首帧延迟 |
| eMMC/SD | autosuspend | 硬件睡眠 | 睡眠唤醒时序违反会导致 resume 失败（28.6） |
| USB 设备 | USB autosuspend | 随主机挂起 | 某些设备的远程唤醒需 wakeup 使能 |
| 屏幕背光 | PWM 调暗→超时熄灭 | 断电 | 背光是常开第一大件，PWM 占空比直接是功耗 |
| 传感器 | 降采样率/中断触发 | 断电或待机模式 | 高频轮询是 CPU 侧功耗凶手（28.2 实录） |
| 音频 codec | runtime suspend | 断电 | 爆音（pop）问题：上下电时序 |

每行的共同结构：**空闲时降档（降频/降采样/调暗），不用时断电，断电时管引脚，恢复时算延迟**。四句话适用于一切外设。

## <span class="blue"> 本节总结

外设功耗三件实操：Runtime PM 审计（空载扫描 active 清单，该睡的用 `echo auto > control` + autosuspend_delay_ms 打开，被占用的查 runtime_usage）、pinctrl sleep 状态（floating 输入级的直通电流机理，设备树 default/sleep 双状态组配置，万用表量中间电平排查）、wake IRQ 规划（power/wakeup 开关 + wakeup-source 声明，误唤醒与叫不醒两个方向的故障形态）。外设策略的统一结构：空闲降档、不用断电、断电管引脚、恢复算延迟。28.7 案例会把这些手段的收益逐项兑付。

**关键结论速查：**

| 问题 | 答案 |
|------|------|
| 审计入口 | 空载扫描 `power/runtime_status` 的 active 清单 |
| 打开自动挂起 | `echo auto > power/control` + autosuspend_delay_ms |
| 睡不下去首查 | `power/runtime_usage`：引用计数持有者 |
| 引脚漏电机理 | floating 输入级双管直通，中间电平耗电 |
| 漏电排查 | suspend 态万用表量引脚，0.5×VDD 即悬浮 |
| 漏电修复 | pinctrl default/sleep 双组，sleep 组输出低电平 |
| 误唤醒治理 | `power/wakeup` 显式 disable 无唤醒职责的设备 |
| 外设四句诀 | 空闲降档、不用断电、断电管引脚、恢复算延迟 |
