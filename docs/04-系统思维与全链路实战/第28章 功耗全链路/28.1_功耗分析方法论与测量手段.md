# 28.1 功耗分析方法论与测量手段

> 所属章节：第28章 功耗全链路
>
> 难度：[E] | 预计阅读时间：40 分钟

## <span class="blue"> 本节导读

功耗优化的第一堂课不是任何优化技巧，而是一个残酷的事实：**大多数功耗优化失败在测量上**。工程师拿着万用表量了整机电流，改了 cpufreq governor，再量一次——读数没变，于是宣布"governor 没用"。真相是那次 suspend 瞬态只有 200ms，万用表每秒采样两次，根本没看见它。功耗问题的特殊性在于：它是模拟量、是瞬态量、是温度的函数——和第 25/26 章那些"内核计数器能读到"的性能问题完全不同，这一关必须先过仪器关。

本节建立全章的地基：功耗从哪来的物理框架（静态/动态功耗公式），测量工具的分级与选择（万用表到功耗分析仪），以及功耗版"预算表"的制作方法。本节覆盖：

- 功耗的三个分析层次：组件级、策略级、系统级
- 物理基础：P = C·V²·f + V·I_leakage 的三个工程推论
- 测量工具分级：万用表/示波器/INA219/SoC 内置 sensor 各管什么
- 分段隔离测量法：怎么把整机功耗拆到组件
- 功耗分解表：功耗版的"预算表"

## <span class="blue"> 三个分析层次：先定位你在哪层

功耗问题按粒度分三层，每层的工具和手段完全不同，混用是最常见的弯路：

**组件级：这颗芯片/这个模块耗多少。** CPU、GPU、DDR、eMMC、Wi-Fi 模组、屏幕背光、传感器——整机功耗是它们的和。这一层的问题是**拆解**：总功耗 720mW，各部分别是多少？答案是测出来的，不是算出来的（测量手段见下文）。

**策略级：每个组件在不同时刻处于什么功耗状态。** CPU 在 1.4GHz 还是 408MHz、eMMC 在读写还是睡眠、Wi-Fi 在收发还是 power save——这一层的问题是**状态**：Linux PM 框架（cpufreq/devfreq/Runtime PM/suspend，第 15 章的机制）管理的正是这层。28.2~28.4 在这层工作。

**系统级：策略组合起来是否达到产品指标。** 续航几小时、suspend 功耗多少毫瓦、温升多少度——这一层的问题是**权衡**：性能、功耗、发热的三角取舍。28.5 在这层工作。

排查顺序永远是自下而上：先拆解找到大头（组件级），再看大头的状态管理对不对（策略级），最后做取舍（系统级）。跳层的典型失败是：suspend 功耗超标，直接改内核 PM 配置——后来发现大头是引脚漏电（28.7 案例的真实剧情），PM 配置根本管不着它。

## <span class="blue"> 物理基础：两个公式，三个推论

功耗的物理模型只有两个公式，但所有优化策略都是它们的推论：

```
P_total = P_static + P_dynamic

P_static  = V × I_leakage        （漏电：与电压成正比，与温度强相关）
P_dynamic = C × V² × f           （开关：与电压平方、频率成正比）
```

> 动态功耗（P_dynamic）：晶体管翻转充放电消耗的能量，正比于电容 C、电压平方 V²、频率 f。CPU/GPU 满载时的功耗大头。

<!-- -->

> 静态功耗（P_static）：晶体管不翻转也在漏电的功耗，与温度呈指数关系——芯片 85℃ 时的漏电可能是 25℃ 时的数倍。这就是"同一块板子高温箱里功耗暴增"的物理原因。

三个工程推论直接指导优化方向：

**推论一：降压比降频有效得多。** 频率降一半，动态功耗降一半；电压降 20%，动态功耗降 36%（0.8²=0.64）。所以 DVFS（电压频率联动调节）总是成对调——单独降频不降电压只能拿到线性收益，电压才是平方项。

**推论二：空闲时静态功耗是主角。** CPU 空闲时 f 趋近于零，动态功耗消失，剩下的全是漏电。所以空闲场景的优化手段完全不同：不是调频率而是进 C-state（关时钟、关电源域）——空闲功耗优化的本质是"关掉"，不是"调低"。

**推论三：深度睡眠省的是静态功耗。** suspend-to-RAM 把大部分电源域关闭，V×I_leakage 里的 V 直接归零——这就是为什么 suspend 功耗能压到运行功耗的 1/100 以下，也是 28.7 案例的战场。

## <span class="blue"> 测量工具分级：每种仪器管什么

功耗测量工具按采样率和精度分四级，选错级别=白测：

| 工具 | 采样率 | 精度 | 能干什么 | 不能干什么 |
|------|--------|------|----------|------------|
| 万用表（串电流档） | 1~2 次/秒 | mA 级 | 稳态功耗：suspend 稳态、待机 | 一切瞬态（唤醒尖峰、负载波动） |
| 示波器+分流电阻/电流探头 | MHz 级 | 取决于探头 | 瞬态波形：suspend/resume 过程、外设上电冲击 | 长期记录 |
| INA219/INA226（I2C 功率计） | kHz 级 | 1% 级 | **长期记录+软件可读**：挂进系统持续采集 | 微秒级瞬态 |
| 功耗分析仪（KEYSIGHT N6705 类） | 100kHz+ | μA 级 | 全都要：瞬态+长期+精确 | 贵 |

**万用表的采样率陷阱值得单独强调**：大纲"常见问题"里"功耗测量不准——万用表采样率不够"说的就是它。一次 suspend 进入过程可能只有几百毫秒，中间夹杂着外设断电的毫秒级电流尖峰——万用表的读数是这段时间的某种平均，既看不见尖峰也分不清阶段。**任何涉及"过程"的功耗问题，都必须上示波器或功耗分析仪。**

### INA219 实操：最平民的长期记录方案

INA219/INA226 是 I2C 接口的电流/电压/功率监测芯片，几块钱一颗，串在供电路径上就能让系统自己记录自己的功耗。接线后从用户态读数（芯片出现在 I2C 总线上）：

```
i2cdetect -y -r 1
     40: 40 -- -- -- -- -- -- --                          ← INA219 在 0x40
```

```
# 寄存器：0x00配置 0x01分流电压 0x02总线电压 0x03功率 0x04电流
i2cget -y 1 0x40 0x02 w          # 读总线电压寄存器
0x1a28                            # 按datasheet换算（需先写校准寄存器）
```

长期记录用脚本每分钟采样写日志，配合业务日志时间戳，就能做出"功耗曲线 vs 系统事件"的对照图——**哪次唤醒花了多少电、哪个业务起来功耗跳多少，全变成可查的数据**。多块 INA219 分别串在 SoC 电源轨、外设电源轨、Wi-Fi 模组供电上，就构成了组件级拆解的硬件基础。

### INA219 校准与记录脚本

INA219 直接读的寄存器值是原始量，要先写校准寄存器才能换算成真实电流/功率。完整流程：

```
# ① 写校准寄存器（0x05）：假设分流电阻0.1Ω、预期最大电流3.2A
#    Cal = 0.04096 / (Current_LSB × R_shunt)，取 Current_LSB=0.1mA → Cal=4096=0x1000
i2cset -y 1 0x40 0x05 0x1000 w

# ② 验证配置寄存器（0x00）默认值即可覆盖±3.2A量程
i2cget -y 1 0x40 0x00 w
```

之后电流寄存器（0x04）的读数 × Current_LSB 就是真实电流。长期记录脚本（扔到后台跑）：

```bash
#!/bin/sh
# power-log.sh：每2秒记录一次电流(mA)与电压(V)，带时间戳
while true; do
    ts=$(date +%s.%N)
    raw_i=$(i2cget -y 1 0x40 0x04 w)
    raw_v=$(i2cget -y 1 0x40 0x02 w)
    # 电流：raw × 0.1mA；总线电压：(raw>>3) × 4mV（寄存器低3位是标志位）
    printf "%s %s %s\n" "$ts" "$raw_i" "$raw_v" >> /data/power.log
    sleep 2
done
```

原始值留在日志里、换算在后处理做——采集脚本只做最简动作，避免脚本自身开销污染测量（脚本本身也让 CPU 醒来耗电，2 秒间隔是记录精度与自干扰的折中）。后处理用 awk/python 把 raw 换算成 mA/V，再画曲线或按时间段积分算电量。

**一个容易漏的坑：** INA219 串在哪条轨就测哪条轨。想测整机功耗时它要串在电池/适配器入口；串在 SoC 的 5V 轨上则看不见屏幕背光和外设。多轨测量需要多颗芯片（I2C 地址用 A0/A1 引脚区分，一颗芯片四个地址）。

> 💡 有些 SoC 内置电源轨传感器（PMIC 的 ADC 通道，如 RK 的 rk818、TI 的 INA 系内嵌），驱动就绪后在 hwmon 里直接可读：`cat /sys/class/hwmon/hwmon*/in*_input`、`curr1_input`。先查这个平台福利，能省掉外接 INA219 的飞线。

## <span class="blue"> 分段隔离测量法：把整机拆到组件

拿到整机功耗只是开始，破案需要知道每个组件的份额。没有多路传感器时，用**隔离测量法**：每次只改变一个变量，测差值。标准动作序列：

```
① 测基线：系统完全空闲（关业务、灭屏、停网络），记录 P_idle
② 逐个唤醒嫌疑组件，记录增量：
   点亮屏幕：P = P_idle + 45mW           → 背光+面板约45mW
   Wi-Fi 关联：P = 基线 + 120mW          → WLAN 活动态约120mW
   eMMC 大文件读写：P = 基线 + 80mW      → 存储活动约80mW
   CPU 满载（stress-ng -c 4）：P = 基线 + 850mW → CPU 动态功耗约850mW
③ 对不上的部分：P_total - 已知各项 = 未知项 → 往往是电源效率损失或漏电
```

三个操作要点：**单一变量**（每次只动一个组件，多个同时动就没法归因）；**稳态读数**（每个状态保持 30 秒以上再记数）；**温度记录**（静态功耗随温度漂移，对比测量要在同温度下进行，否则差值里混着温度项）。

这套方法的局限也明说：它测的是"增量"，组件间的耦合项（比如 CPU 满载时 DDR 功耗也涨）会被归到错误的账上。精确拆解要靠多路同步测量（多颗 INA219 或功耗分析仪的多通道），隔离法是低成本近似。

## <span class="blue"> 功耗分解表：功耗版的预算表

测量的产出物是功耗分解表——与 25.5 延迟预算表同构的工具，把"功耗高"翻译成"每个组件、每种状态下各耗多少"：

| 组件 | 运行态 | 空闲态 | suspend 态 | 优化手段候选 |
|------|--------|--------|------------|--------------|
| CPU | 850mW | 120mW | ~5mW | DVFS 策略、C-state 深度 |
| DDR | 200mW | 180mW | 45mW（自刷新） | 降频、自刷新模式 |
| 屏幕+背光 | 45mW | 45mW | 0mW | 背光 PWM、超时灭屏 |
| Wi-Fi | 120mW | 15mW | 0mW（断电） | power save、断电策略 |
| eMMC | 80mW | 2mW | ~0mW | Runtime PM autosuspend |
| **PMIC 效率损失** | ~10% | ~10% | ~10% | 效率曲线选工作点 |
| 引脚/漏电 | ？ | ？ | ？ | pinctrl sleep 配置 |

填这张表的过程就是破案过程——**最后一行的"？"往往就是答案所在**：分解表合不上账（各项加起来比实测整机少），差值就藏在这些没人测过的地方。28.7 案例里 107mW 的引脚漏电正是这样被"对不上的账"逼出来的。

## <span class="blue"> 本节总结

功耗分析分三层：组件级拆解、策略级状态管理、系统级权衡，排查自下而上不跳层。物理基础两个公式给出三个推论：降压是平方项（DVFS 成对调）、空闲时静态功耗主导（优化手段是"关"不是"调低"）、深睡眠省的是漏电（suspend 的战场）。测量工具按采样率分级，万用表只管稳态，瞬态必须示波器/功耗分析仪，INA219 是长期记录的平民方案（别忘了先查 SoC/PMIC 内置传感器）。分段隔离测量法用差值拆账，产出物是功耗分解表——它合不上的账就是破案方向。

**关键结论速查：**

| 问题 | 答案 |
|------|------|
| 三层分析 | 组件级拆解 → 策略级状态 → 系统级权衡，自下而上 |
| 降压 vs 降频 | 电压是平方项，DVFS 成对调 |
| 空闲功耗主角 | 静态漏电；手段是进 C-state"关掉" |
| suspend 省什么 | 静态功耗（电源域断电，V 归零） |
| 万用表适用域 | 仅稳态；一切瞬态白测 |
| 长期记录方案 | INA219（I2C 可读）或 PMIC 内置 hwmon |
| 拆账方法 | 隔离测量：单一变量、稳态读数、温度记录 |
| 破案线索 | 分解表合不上的差值 |

**本节自查：**

1. 为什么 suspend 功耗能压到运行功耗的 1/100 以下，而 idle（不进 suspend）做不到？
2. 高温箱里整机功耗比常温高 40%，而 CPU 负载没变——功耗模型里哪一项在起作用？
3. 用万用表测 suspend 电流 3.6mA，但电池实测续航只有理论值的一半，测量上最可能漏掉了什么？
4. 隔离测量法中"CPU 满载"一项的读数里实际混入了哪个组件的功耗？为什么会混入？
