# 28.4 系统级功耗优化策略

> 所属章节：第28章 功耗全链路
>
> 难度：[E] | 预计阅读时间：40 分钟

## <span class="blue"> 本节导读

28.2 和 28.3 把组件级的手段备齐了——CPU 调频、外设挂起、引脚防漏。系统级要回答的是另一类问题：**整个系统什么时候睡、睡到多深、凭什么被叫醒**。这三个问题对应三个决策：suspend 形态选型（三档睡眠的深度-唤醒时间取舍）、tickless 配置（空闲时内核自己别折腾）、唤醒源规划（谁能叫醒系统，谁在偷偷叫醒系统）。

系统级策略的特殊性在于它有一个**盈亏平衡点**：睡眠本身有成本（进入和退出的能耗、唤醒延迟），空闲时间不够长就睡反而亏。本节覆盖：

- suspend 三档形态：s2idle / suspend-to-RAM / suspend-to-disk 的决策表
- 盈亏平衡时间：空闲多久才值得睡
- 选型实录：手持终端从两档实测到延迟压线的四天
- tickless 内核：空闲收益与代价的实测
- 唤醒源规划与误唤醒排查
- 唤醒延迟：suspend 方案的隐性指标

> 💡 suspend/resume 的内核机制（流程、Wakelock、设备回调顺序）在 15.5 有完整讲解，本节做选型决策与实操验证。

## <span class="blue"> suspend 三档形态：深度与唤醒时间的取舍

Linux 提供三档系统睡眠，它们的本质区别是"关掉多少东西"：

| 形态 | 关掉什么 | 典型功耗 | 唤醒时间 | 适用场景 |
|------|----------|----------|----------|----------|
| s2idle（freeze+深 idle） | 冻结进程，CPU 进深 C-state，外设 runtime suspend | 较高（百 mW 级） | μs~ms 级 | 秒级空闲：灭屏的手机、短暂间隙 |
| suspend-to-RAM（mem） | 大部分电源域断电，仅 DDR 自刷新+唤醒逻辑 | 最低实用档（mW~几十 mW） | ms~百 ms 级 | 分钟级以上空闲：IoT 设备休眠 |
| suspend-to-disk（hibernate） | 全部断电，状态写交换分区 | ≈0（关机级） | 秒级 | 小时级空闲且要保现场 |

先查本机支持哪几档：

```
cat /sys/power/state
freeze mem disk
cat /sys/power/mem_sleep
s2idle [deep]                    ← 方括号是当前生效的mem形态
```

`deep` 就是真正的 suspend-to-RAM，`s2idle` 是浅档——`mem_sleep` 里两档都列出的平台，`echo mem > /sys/power/state` 的效果取决于方括号在哪：**想进深睡结果平台默认 s2idle，是 suspend 功耗"降不下来"的第一检查点**。

选型决策逻辑按唤醒延迟反推：业务能容忍的唤醒延迟是 1 秒以内还是毫秒以内？毫秒级只能选 s2idle 或 mem；秒级可选 disk。功耗指标的严格程度再筛一遍——**唤醒延迟和功耗是这对决策的两个坐标轴，产品定义里通常只给了其中一个，另一个要主动去要**。

> 💡 hibernate 在嵌入式上的实际使用率很低：交换分区对 eMMC 寿命不友好，秒级唤醒在多数场景不可接受。它的存在意义主要是"知道有这个选项"，默认决策在 s2idle 和 mem 之间做。

## <span class="blue"> 盈亏平衡：空闲多久才值得睡

进入和退出 suspend 不是免费的：DDR 切自刷新、电源域逐一下电、唤醒后逐个恢复——这个过程本身耗能（典型几到几十毫瓦·秒）且耗时（唤醒延迟）。于是存在一个盈亏平衡时间 T_break-even：

```
T_break-even = E_进出开销 / (P_运行 - P_睡眠)
```

举例：进出开销等效 0.1 秒的运行功耗，运行 310mW、深睡 3mW，则 T ≈ 0.1s × 310 / (310-3) ≈ 0.1 秒——空闲超过 0.1 秒就睡就赚。看起来 suspend 总是赚的？注意还有个约束不在公式里：**唤醒延迟是用户体验项**。空闲 2 秒睡一次、用户一碰就等 200ms 唤醒——功耗上赚了，体验上亏了。这就是为什么 IoT 设备的睡眠策略要由"业务空闲模式"决定：知道下次唤醒在 10 分钟后（定时上报设备），放心进 mem；不知道下次操作什么时候来（手持终端），只能依赖超时阈值。

实操验证手段是 rtcwake——定时唤醒的标准工具，同时是唤醒延迟的测量工具：

```
rtcwake -m mem -s 60           # 进mem睡，60秒后RTC唤醒
# 输出里直接带唤醒耗时统计：
rtcwake: wakeup from "mem" using /dev/rtc0 ...
Wake 59.99 seconds later          ← 定时精度
```

配合 28.1 的功耗记录脚本（rtcwake 前后打时间戳、INA219 全程记录），一次实验同时拿到三份数据：睡眠期间功耗、进出过程能耗、唤醒延迟——**这三个数字就是 suspend 方案评审的全部输入**。

## <span class="blue"> 选型实录：手持终端的 suspend 决策

把三档决策走一遍真实流程。产品：巡检手持终端（电池 4000mAh），产品定义给了两个数字：灭屏待机电流 <8mA、按键唤醒到可操作 <500ms。

**第一步，两档候选的实测（半天）。** 同一台机器分别进两档测：

```
s2idle：睡眠电流 42mA，唤醒到可操作 45ms        ← 唤醒优秀，功耗超标5倍
mem(deep)：睡眠电流 5.8mA，唤醒到可操作 380ms   ← 功耗达标，唤醒达标但余量不大
```

先看 checklist 排坑：`mem_sleep` 方括号确实在 deep（第一台样机方括号在 s2idle，直接踩了"假 mem"坑）；pinctrl sleep 配置已按 28.3 修过。

**第二步，算账（半小时）。** 巡检员的实际使用模式：平均每小时亮屏操作约 6 分钟，其余时间灭屏。按小时算账：

- s2idle：54 分钟 × 42mA ≈ 37.8mAh/h 的待机消耗 → 4000mAh 电池理论待机 106 小时
- mem：54 分钟 × 5.8mA ≈ 5.2mAh/h → 理论待机 770 小时
- 进出开销：mem 每次进出约等效 2 秒运行功耗，每小时 60 次进出 ≈ 2 分钟运行——相对 37.8→5.2 的节省可忽略

盈亏平衡时间算出来是 0.3 秒级，而业务空闲都是分钟级——功耗账上 mem 碾压。**但唤醒延迟 380ms 贴着 500ms 红线**，这是唯一的风险项。

**第三步，压延迟（两天）。** 380ms 的分解打点（resume 各阶段时间戳，内核有 `PM: suspend of devices complete after X ms` 类日志）显示：Wi-Fi 模组恢复占 210ms（重新上电+固件加载）、显示链路 90ms、其余 80ms。处置：Wi-Fi 改为不断电只进 sleep（功耗 +2mA，延迟 -190ms），显示背光提前点亮（视觉上的"可操作"提前）。最终 mem 档：睡眠 7.9mA 达标，唤醒 190ms 达标且有余量。

**第四步，验收与固化。** 验收按 28.1 的标准：72 小时循环测试（睡 5 分钟→唤醒→操作 1 分钟）+ 高低温箱复测（-10℃ 唤醒延迟上浮到 240ms，仍达标——温度项是 suspend 验收的必查项，28.6 展开）。配置固化为系统服务，与 26.8 的固化形态相同。

这个实录的核心教训：**suspend 选型不是二选一，是"选定档位后再把唤醒延迟逐项压下去"的工程过程**——档位由功耗指标定，延迟指标靠在档位内优化达成，两个指标分别落在不同的工作阶段。

## <span class="blue"> tickless：让空闲的内核别折腾

标准内核即使在 idle 时也按固定节拍产生 tick 中断（每秒 100~1000 次，HZ 值），每次 tick 都把 CPU 从 C-state 拽出来——**28.2 实录里 sensor-hubd 干的事，内核自己也在干**。tickless（`CONFIG_NO_HZ_IDLE`）让空闲 CPU 停止节拍，只在有实际工作时才中断：

```
Tick模式：                   Tickless模式：
┌──┐  ┌──┐  ┌──┐  ┌──┐      ┌──┐            ┌──┐
│  │  │  │  │  │  │  │      │  │            │  │
──┘  └──┘  └──┘  └──┘  ────┘  └────────────┘  └───
固定节拍持续唤醒             仅在有工作时唤醒
```

收益（大纲数据：减少功耗 5~20%，取决于空闲比例）+ 一个附带好处：减少调度抖动——26.8 的实时场景里 `nohz_full` 与 isolcpus 搭配就是这个动机。

验证配置与效果：

```
grep NO_HZ /boot/config-$(uname -r)          # CONFIG_NO_HZ_IDLE=y 确认开启
cat /proc/timer_list | grep -A2 "active timers" | head   # 空闲时活动定时器应极少
```

效果验证用 cpuidle 读数：开 tickless 前后对比深状态的平均驻留时长——驻留拉长就是收益的直接证据。代价如实说：依赖 tick 的统计精度下降（CPU 使用率是按 tick 采样的）、NO_HZ_FULL 模式下与负载均衡的交互更复杂——嵌入式单应用形态通常无感，服务器多租户形态要评估。

## <span class="blue"> 唤醒源：规划与排查

suspend 方案的最后一块拼图是唤醒源管理——它有两个方向的故障：**该醒不醒**（按键叫不醒设备）和**不该醒乱醒**（suspend 功耗测试里电流周期性跳高）。

**规划侧：明确唤醒源白名单。** 产品上谁能唤醒系统应该是一张明确写出来的清单（RTC 定时、电源键、Wi-Fi 模组唤醒中断、插拔检测），其余设备的 `power/wakeup` 全部 disabled（28.3 的方法）。白名单是产品定义的一部分，不是驱动默认值——驱动默认使能的唤醒源经常是错的起点。

**排查侧：谁在偷偷叫醒系统。** 内核记录了每个唤醒源的活动次数：

```
cat /sys/kernel/debug/wakeup_sources
```

```
name            active_count  event_count  wakeup_count  ...
rtc0            12            12           12            ← RTC定时唤醒：正常
gpio-keys       3             3            3             ← 按键：正常
wlan0           847           847          12            ← ★活跃847次但唤醒12次
```

读法：`active_count` 是该源活动总次数，`wakeup_count` 是真正把系统从 suspend 叫醒的次数。**wlan0 活跃 847 次**意味着 Wi-Fi 在 suspend 期间活动频繁（ beacon 监听、组播包）——其中 12 次把系统整醒了。配合功耗记录里"电流周期性跳高"的时间戳，就能确认：治理手段是调 DTIM/Beacon 过滤参数或干脆 suspend 时断电（28.3 策略表里的两行取舍）。

另一个方向的排查（叫不醒）走中断路径：确认设备树的 `wakeup-source` 声明、`enable_irq_wake` 在驱动 suspend 回调里被调用、`/proc/interrupts` 里该中断带 `wakeup` 标记。三层缺一层都叫不醒，机制详解在 15.5.2。

## <span class="blue"> 本节总结

suspend 三档按"关掉多少"分级：s2idle（百 mW、μs 唤醒）、mem（mW 级、百 ms 唤醒）、disk（≈0、秒级），选型由唤醒延迟和功耗指标两个坐标决定，`mem_sleep` 的方括号位置是"降不下来"的第一检查点。盈亏平衡公式给出理论下限，但唤醒延迟的体验约束往往先触顶——睡眠策略本质是业务空闲模式的函数。rtcwake 一次实验产出睡眠功耗、进出能耗、唤醒延迟三份评审输入。tickless 消灭内核自己的节拍唤醒（5~20% 收益，cpuidle 驻留拉长为证）。唤醒源管理双向：白名单规划 + wakeup_sources 审计（active_count vs wakeup_count 的读法），两个方向的故障各有各的查法。

**关键结论速查：**

| 问题 | 答案 |
|------|------|
| 三档形态 | s2idle 快醒贵 / mem 平衡主力 / disk 零功耗慢醒 |
| mem 不深睡首查 | `/sys/power/mem_sleep` 方括号在 s2idle 还是 deep |
| 盈亏平衡 | T = 进出开销 ÷ 功耗差；唤醒延迟是公式外的体验约束 |
| 一次实验三数据 | rtcwake + INA219：睡眠功耗/进出能耗/唤醒延迟 |
| tickless 收益 | 空闲功耗 -5~20% + 调度抖动减小 |
| tickless 验证 | cpuidle 深状态平均驻留时长拉长 |
| 乱醒排查 | `wakeup_sources`：active_count 高的嫌疑 |
| 不醒排查 | wakeup-source 声明 → enable_irq_wake → /proc/interrupts 标记 |
