# 28.2 CPU/GPU/DDR 功耗分解实操

> 所属章节：第28章 功耗全链路
>
> 难度：[E] | 预计阅读时间：40 分钟

## <span class="blue"> 本节导读

28.1 的分解表框架里，第一梯队嫌疑人永远是三大件：CPU、GPU、DDR——它们合计通常占运行态功耗的 60%~80%。第 15 章已经讲透了它们的电源管理机制（cpufreq/C-state、devfreq、DDR 自刷新），本节回答的是实战问题：**这三大件的功耗行为在 sysfs 里长什么样、读数怎么解读成"功耗是否正常"、 governor 选型的功耗差异怎么验证**。

本节的方法论内核是"占空比思维"：芯片的功耗不是一个固定值，而是各功耗状态的时间加权和——看懂功耗就是看懂时间分布。本节覆盖：

- CPU：time_in_state 时间分布分析与 C-state 驻留率
- governor 的功耗差异：schedutil/performance/powersave 的实测形态
- 分解实录：一台 idle 功耗异常设备的四步排查
- GPU：devfreq 观测与空闲挂起验证
- DDR：devfreq 与自刷新——为什么 suspend 时它关不掉
- PMIC 效率：被忽视的固定抽成

---

## <span class="blue"> CPU：时间分布就是功耗

CPU 功耗的读数入口是 cpufreq 的统计文件——它记录 CPU 在每个频率档上累计花了多少时间：

```
cat /sys/devices/system/cpu/cpu0/cpufreq/stats/time_in_state
```

```
1416000  1523         ← 1.416GHz 档累计 15.23 秒（单位是10ms滴答）
1008000  842
408000   98765        ← 408MHz 档累计 987.65 秒：98%时间都在最低频
```

这份读数直接回答功耗分析的第一个问题：**CPU 的时间都花在哪个频率档上**。上面这个分布（98% 在最低频档）配合空闲场景，说明 DVFS 工作正常；反过来如果空闲时高频档占比异常（比如 1.4GHz 档占了 30% 时间），就是有周期性任务在把 CPU 拉到高频——嫌疑犯名单：定时器过密的应用、日志刷盘、监控脚本。找出真凶的工具是把时间分布和进程占用对照：

```
# 高频档时间异常时，看谁在跑
perf record -a sleep 30 && perf report | head
# 或更直接：看各进程唤醒次数
cat /proc/timer_list | grep -c ".*"   # 定时器密度粗查
```

**空闲时该看的不是频率，是 C-state 驻留率。** CPU 真正省电的时刻不在低频档，而在 idle 状态（WFI→关时钟→关电源域，15.2.1 的机制）。读数在 cpuidle：

```
for s in /sys/devices/system/cpu/cpu0/cpuidle/state*/; do
    echo "$(cat $s/name): $(cat $s/time) us, 进入$(cat $s/usage)次"
done
```

```
WFI: 15234567 us, 进入8923次
cluster-sleep: 45234567 us, 进入1523次    ← 深状态累计45秒：驻留率健康
```

每个 state 的 `time/usage` 除一下是**平均驻留时长**——拿它和 state 目录里 `residency` 文件（该状态"回本"所需的最短驻留时间，微秒）对比：平均驻留时长 < residency，说明**系统在频繁进出深状态却没待够本**——进深状态本身有开销（关电源、保存上下文、恢复），待不够时间反而更费电。根因是某个周期性唤醒源把 CPU 拽出来（唤醒源排查在 28.4），治理要么消灭唤醒源，要么用 `cpuidle.off`/`state disable` 临时禁用进不去本的深状态。

## <span class="blue"> governor 的功耗差异实测

大纲点名的问题是"为什么 schedutil 是嵌入式推荐"。机制答案在 15.2.3（直接从调度器拿负载信号、无采样线程开销），这里给**功耗视角的验证方法**——同一份负载，切换 governor，对比 time_in_state 分布：

```
# 负载：每秒唤醒一次的周期性任务（模拟典型IoT设备）
for gov in performance schedutil powersave; do
    echo $gov > /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor
    cat /sys/devices/system/cpu/cpu0/cpufreq/stats/time_in_state > /tmp/t0
    sleep 60
    # 差值即这60秒的频率分布
done
```

三种 governor 在同一负载下的典型形态：

- **performance**：100% 时间钉在最高频。功耗最高，但任何负载都是零响应延迟——26.6/26.8 的确定性场景用的就是它。**功耗与确定性是直接的交换关系**，这不是错误配置，是代价明示的选择；
- **schedutil**：周期性任务来的一瞬间拉到高频、做完立刻回落——高频档时间占比与真实负载成正比。轻载设备上功耗接近 powersave，响应接近 performance，这就是它成为默认推荐的原因；
- **powersave**：钉在最低频。功耗最低，但负载来了响应慢——任务执行时间被拉长，**总耗电量未必比 schedutil 少**（低频跑 10 秒 vs 高频跑 2 秒的能耗账：race-to-idle）。低功耗不等于低能耗，这个区别在电池设备上要算清楚。

> race-to-idle：负载来了尽快冲到高频快速完成、然后回到深 idle 的策略。因为动态功耗含固定开销（PLL、总线），"高频短跑+深睡"的总能耗经常低于"低频慢跑"。这也是为什么 powersave 不是电池设备的最优解——它把每次唤醒都拉长了。

## <span class="blue"> 分解实录：一台 idle 功耗异常的设备

把本节的读数方法串成一次完整排查。现场：IoT 设备，空载放着不动，功耗 310mW——同平台参考设计是 180mW，130mW 的差值就是案子。

**第一步，看频率分布（2 分钟）。**

```
cat /sys/devices/system/cpu/cpu0/cpufreq/stats/time_in_state
```

```
1416000   45230        ← 高频档占了45%的时间：空载时CPU不该在这里
408000    54770
```

空载时高频档占 45%——DVFS 在工作，但有什么东西持续把 CPU 拉到高频。**功耗差值的第一部分已经锁定方向：不是配置问题，是有活物在跑。**

**第二步，找活物（5 分钟）。**

```
perf record -a sleep 30; perf report --stdio | head -15
```

```
  42.1%  sensor-hubd   [.] read_sensor_burst    ← 传感器采集进程
  12.3%  sensor-hubd   [.] i2c_transfer
   ...
```

传感器采集进程占了 42% 的 CPU——看它的代码，采集循环是 `while(1) { read(); usleep(20000); }`：**20ms 一次的高频轮询**，每次唤醒都把 CPU 从深睡拽出来冲上高频。

**第三步，验证深睡被搅黄（2 分钟）。**

```
cat /sys/devices/system/cpu/cpu0/cpuidle/state2/time
# 与参考设备对比：深状态驻留率只有参考的1/5
```

cpuidle 读数确认：深状态（cluster-sleep）平均驻留时长 400μs，residency 是 1.2ms——**每次进深睡都没待够本就被拽出来**，进出的开销全打了水漂（这就是 residency 概念的实际案发形态）。

**第四步，修复与验证（30 分钟）。** 根因清楚后修复很朴素：采集从 20ms 轮询改成传感器中断触发（硬件支持 data-ready 中断），数据率不变。改后验证：高频档时间占比降到 3%，深状态驻留率恢复正常，空载功耗 186mW——**130mW 差值收回 124mW**，剩余 6mW 在测量误差内。

这个实录的形状在全章会反复出现：**功耗异常 → 读数定位方向 → 找到活物 → 修复往往是改行为而不是改配置**。cpufreq 参数一个没动——问题从来不在 governor，在一个 20ms 的 usleep。

## <span class="blue"> GPU：空闲挂起比调频更重要

GPU 的功耗特性与 CPU 不同（大纲数据：渲染时占系统总功耗 30~50%），观测走 devfreq 框架：

```
ls /sys/class/devfreq/                     # 平台相关：gpu、dmc(DDR)等条目
cat /sys/class/devfreq/ff9a0000.gpu/cur_freq      # 当前频率
cat /sys/class/devfreq/ff9a0000.gpu/governor      # 当前governor
cat /sys/class/devfreq/ff9a0000.gpu/load          # 瞬时负载（部分驱动支持）
```

GPU 功耗优化的第一优先级不是频率策略而是**空闲时的 Runtime PM 状态**——很多 GPU 驱动默认不开 runtime suspend，空载时 GPU 一直全压供电。验证：

```
cat /sys/class/devfreq/ff9a0000.gpu/power/runtime_status
suspended                        ← 空闲时应为这个；active 常驻就是问题
```

`active` 常驻的处理：查驱动是否启用 runtime PM（`echo auto > power/control`），查是否有什么东西持有引用计数（`power/runtime_usage`）——引用计数语义在 15.1.2，观测与排查在 28.3 展开。

## <span class="blue"> DDR：suspend 里关不掉的那一项

DDR 也有 devfreq（dmc 节点，调频率降带宽省电），但它最重要的功耗特性是另一个：**suspend-to-RAM 时 DDR 必须保持自刷新**——RAM 里的内容是系统状态本身，断电就没了。这就是 28.1 分解表里 DDR 在 suspend 态仍有 45mW 的原因，也是 suspend 功耗的物理下限的重要组成部分。

自刷新（self-refresh）是 DDR 芯片内部的低功耗保持模式：控制器关掉接口时钟，颗粒自己维持刷新。软件能影响的有两点：设备树/驱动里确认自刷新使能（部分平台需要显式配置），以及 DDR 训练参数正确（参数错的 DDR 在自刷新时电流异常偏高，是隐蔽的 suspend 功耗来源）。观测手段是测量：suspend 态下 DDR 电源轨的电流（28.1 的 INA219 分轨测量在这里派上用场）。

## <span class="blue"> PMIC 效率：被忽视的固定抽成

分解表里有一行"PMIC 效率损失 ~10%"——它不是任何组件的功耗，是电源转换的损耗：电池 3.7V 到 SoC 各路 0.9V/1.8V/3.3V 的转换不是免费的。两个工程要点：

**DC-DC 与 LDO 的效率差。** DC-DC 转换效率 85~95%，LDO 效率约等于"输出电压÷输入电压"（3.7V→1.8V 只有 49%）。PMIC 上每路用哪种是硬件设计决定的，软件能做的是**知道每路的效率形态**：LDO 路线上的大电流负载是效率黑洞，原理图评审阶段就该拦下来。

**DC-DC 的效率曲线不是平的。** 典型 DC-DC 在 10%~80% 负载区间效率最高，轻载（<5%）时效率骤降——suspend 态整机电流极小，PMIC 恰好工作在效率最差区间。这就是为什么 suspend 实测功耗经常比"各组件理论值之和"高出一块：**PMIC 轻载效率是分解表的常见对账差项**。高端 PMIC 有 PFM/轻载高效模式（寄存器可配），查 PMIC datasheet 的模式切换位。

## <span class="blue"> 本节总结

三大件的功耗分析核心是占空比思维：CPU 看 time_in_state 频率分布（异常高频档=周期性任务嫌疑）和 cpuidle 驻留率（平均驻留 vs residency 回本期），governor 三形态里 schedutil 平衡、performance 买确定性、powersave 不一定省能耗（race-to-idle）。GPU 的第一优先级是空闲 runtime suspend 验证（runtime_status），其次才是 devfreq。DDR 在 suspend 态必须自刷新，是 suspend 功耗物理下限的组成；PMIC 轻载效率是分解表常见的对账差项。所有读数都回到 28.1 的分解表——本节给的是三大件那几行的填法。

**关键结论速查：**

| 问题 | 答案 |
|------|------|
| CPU 功耗读数 | `stats/time_in_state`：频率档时间分布 |
| 空闲健康度 | cpuidle `state*/time`+`usage`：平均驻留 ≥ residency 才回本 |
| governor 选型 | schedutil 平衡/performance 买确定性/powersave 慎用于电池 |
| race-to-idle | 高频短跑+深睡常比低频慢跑省能耗 |
| GPU 第一优先 | `power/runtime_status` 空闲应 suspended |
| DDR 的 suspend 角色 | 自刷新必须保持，suspend 功耗下限组成 |
| PMIC 对账差项 | 轻载效率骤降，查 PFM 模式位 |
