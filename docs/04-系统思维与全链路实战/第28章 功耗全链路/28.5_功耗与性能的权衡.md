# 28.5 功耗与性能的权衡

> 所属章节：第28章 功耗全链路
>
> 难度：[E] | 预计阅读时间：40 分钟

## <span class="blue"> 本节导读

28.1~28.4 给的是手段：怎么测、怎么拆、怎么睡。本节回答手段之上的问题——**先优化谁、放弃谁、拿什么验收**。功耗优化没有"全局最优"，只有"在产品目标下的排序"：同一个 governor 调整，对手持终端是续航收益，对桌面网关是发热收益，对实时设备可能是性能损失。目标不同，同一组手段的排序完全不同。

本节把大纲的决策框架落成可操作的工作流，并处理一个容易被忽视的目标耦合：**发热与性能通过 thermal throttling 纠缠在一起**——被动散热的设备上，功耗优化往往就是性能优化。本节覆盖：

- 决策框架五步：从分解到验证的完整工作流
- 多目标矩阵：续航/发热/性能三种目标下的手段排序
- 低垂果实排序法：收益/代价二维评估
- 权衡实录：同一块网关主板的电池版与密闭版两套方案
- 发热与性能的耦合：被动散热设备的特殊账
- 场景差异：机器人动态工况的功耗预算
- 验收口径：标准化工况与回归门禁

---

## <span class="blue"> 决策框架五步：落地版

大纲给功耗优化的决策框架五步，每一步对接前几节的具体工具：

**第一步：测量当前功耗分解。** 28.1 的分解表——隔离测量或分轨 INA219，把整机拆到组件。产出：各组件在运行/空闲/suspend 三态的功耗数字。**没有分解表不动手**，这条纪律和第 25/26 章"测量先行"同源。

**第二步：确定优化目标。** 这是最容易被跳过、后果最重的一步。目标有三种，手段排序完全不同（下文矩阵展开）：续航优先（电池设备）、发热优先（密闭/高温环境）、性能保底前提下的功耗（实时/算力设备）。**目标没定下来之前，"收益"两个字没有定义**——省 50mW 对续航优先是胜利，对性能保底可能是事故。

**第三步：识别低垂果实。** 收益/代价二维排序（下文详表），先做"收益大、代价小"的项。经验上嵌入式设备的低垂果实高度雷同：背光/屏幕、pinctrl sleep、Runtime PM 补全、governor 修正——这四项覆盖了大多数设备的前 80% 收益。

**第四步：评估性能影响。** 每个优化项回答一个问题：用户可见的延迟增加了多少？（外设恢复延迟、CPU 爬坡延迟、网络重连时间）——用 25.5/26.6 的测量方法量化，写进优化项的"代价"列。

**第五步：实施并验证。** 验证口径是"优化后功耗下降多少 + 性能影响是否可接受"的双指标，验收方法见本节末尾。

## <span class="blue"> 多目标矩阵：同一手段的三种排序

三种目标下的手段排序对照（收益按典型量级）：

| 手段 | 续航优先 | 发热优先 | 性能保底 |
|------|----------|----------|----------|
| pinctrl sleep 修漏电 | ★★★（suspend 收益大） | ★（发热影响小） | ★★★（零性能代价） |
| 背光/屏幕管理 | ★★★（常是第一功耗件） | ★★ | ★★★（无代价） |
| Runtime PM 补全 | ★★★ | ★★ | ★★（恢复延迟要算） |
| governor 调保守 | ★★ | ★★★（直接压发热） | ✗（性能受损） |
| CPU/GPU 限频 | ★ | ★★★ | ✗✗（直接违反目标） |
| tickless | ★★（空闲占比高收益大） | ★ | ★★★（还降抖动） |
| suspend 深睡 | ★★★ | ★ | 取决于唤醒延迟约束 |

矩阵的读法有三层。**第一，行内的差异就是目标的意义**：governor 调保守在发热优先列是首选，在性能保底列是禁区——脱离目标谈优化没有结论。**第二，有两行在三列全绿**（pinctrl sleep、背光管理）——零代价项永远先做，不分目标。**第三，没有一行能解决全部问题**：功耗优化是组合拳，单项收益 10~30% 的项叠加出总收益。

## <span class="blue"> 低垂果实排序：收益/代价比

第三步"识别低垂果实"需要一张量化表。按工程经验给出常见优化项的三维评估（收益量级/性能代价/工程代价），供排期参考：

| 优化项 | 典型收益 | 性能代价 | 工程代价 | 优先级 |
|--------|----------|----------|----------|--------|
| pinctrl sleep 配置 | suspend -10~100mW | 无 | 设备树半天 | **最先做** |
| 背光超时与 PWM | 运行态 -几十~几百mW | 无（体验调参） | 小时级 | **最先做** |
| Runtime PM 补全 | 空闲 -10~200mW | 恢复延迟 ms 级 | 天级（驱动） | 高 |
| Wi-Fi power save | 空闲 -50~100mW | 延迟抖动（DTIM） | 小时级 | 高 |
| governor→schedutil | 运行态 -5~15% | 爬坡延迟 μs 级 | 一行配置 | 高 |
| tickless | 空闲 -5~20% | 统计精度降 | 内核配置 | 中 |
| DDR 降频/自刷新优化 | -10~50mW | 带宽敏感场景受损 | 天级（验证重） | 中 |
| suspend 形态下探 | -mW 级→μW 级 | 唤醒延迟 | 周级（全链路验证） | 中 |
| 应用轮询改中断 | -几十mW+CPU 时间 | 无 | 代码改动 | 视案情 |

读法注意两点：**"工程代价"列往往比"收益"列更决定顺序**——pinctrl sleep 收益不是最大，但半天能做完，所以排最前；suspend 形态下探收益最大但验证周期是周级，排期上放后。**性能代价为"无"的项闭眼先做**——它们是纯收益，决策表里不需要权衡的行。

### 权衡实录：同一台网关的两种目标两种方案

决策框架的价值在对比里最清楚。同一块网关主板，出了两个产品变体——同一套工具箱，走出两套方案。

**变体 A：野外电池版（续航优先）。** 指标：7 天待机。分解表显示空闲功耗占大头（设备 90% 时间在等定时上报）。五步走完的方案排序：

1. suspend 下探到 mem（空闲态 310→8mW，周级验证但收益碾压）——**续航目标下它排第一**，工程代价再大也绕不开；
2. pinctrl sleep + 外设断电清单（suspend 态再省 110mW→8mW 的组成项）；
3. Wi-Fi 策略改为"唤醒才连"（断开常驻关联）；
4. tickless + governor 保持 schedutil。

性能代价的处置：唤醒 380ms 对"定时上报"业务无感——**性能代价在续航目标下几乎免费**，这是续航列能收下 suspend 下探的原因。

**变体 B：机柜密闭版（发热优先，市电供电）。** 指标：55℃ 环温箱内满载不降频。同一分解表，完全不同的排序：

1. 持续负载测试定水位：满载 4 分钟后 CPU 从 1.8GHz 掉到 1.2GHz——发热是当前性能的实际上限；
2. governor 降档上限（1.8→1.5GHz 封顶）+ GPU 限频：**牺牲 15% 峰值性能换持续频率不掉**——水位测试变成全程稳 1.5GHz，持续性能反而提升 25%；
3. PMIC 效率检查（LDO 路换 DC-DC 的硬件改版建议立项）；
4. suspend 手段全部不做——市电设备没有续航指标，"空闲省电"在这台设备上没有定义。

两个变体的对照把矩阵读法坐实了：**变体 A 的第一优先级在 B 里不存在，变体 B 的核心手段（限频）在 A 里是禁区**。同一块板、同一套测量工具、两套方案——差异全部来自第二步"确定优化目标"。

## <span class="blue"> 发热与性能的耦合：被动散热的账

有一类设备的功耗问题其实是性能问题：**无风扇的密闭设备**（手持、车载、户外盒）。它们的持续性能上限不由 SoC 决定，由散热决定——SoC 满载 10 秒就撞 thermal 阈值，thermal throttling 强制降频（15.4.3 的机制），性能腰斩。

这类设备上的功耗优化直接是性能优化：每省 1W 功耗，就是给持续负载多出 1W 的热预算。观测入口：

```
cat /sys/class/thermal/thermal_zone*/temp          # 各温区当前温度
cat /sys/class/thermal/thermal_zone*/trip_point_*_temp  # 降频阈值
dmesg | grep -i thermal                            # throttling事件记录
```

评估手法是**持续负载测试**：stress-ng 满载跑 10 分钟，记录频率曲线——频率在第几分钟开始掉、掉到多少，就是这台设备的"持续性能水位"。功耗优化前后各跑一次，频率水位的提升就是发热优先目标的收益量化。

## <span class="blue"> 场景差异：机器人的动态工况账

手持/IoT 设备的功耗模型是"静态占空比"（运行 X%、空闲 Y%），机器人完全是另一套账——**负载是动态的、任务相关、且大头不在计算**：

| 维度 | 手持/IoT 设备 | AGV/机器狗等机器人 |
|------|---------------|-------------------|
| 功耗大头 | 屏幕/射频/SoC | **电机（占 60~80%）+计算** |
| 负载形态 | 事件驱动，占空比稳定 | 工况驱动：爬坡/加速时电流数倍于巡航 |
| 优化主战场 | suspend/空闲管理 | 任务规划与运动控制的功耗联动 |
| 计算功耗角色 | 主角 | 配角但不可牺牲（SLAM/避障停不得） |
| 关键指标 | 待机时长 | 单任务续航里程、剩余电量预测精度 |

机器人的功耗优化有两个独特抓手：**运动规划层**（路径规划里把坡度/加速度的能耗代价纳入代价函数——少走一个陡坡比任何 governor 调参都省电）；**电量预测**（BMS 的电量计读数+工况模型的续航预测，直接影响任务的"去不去充电"决策）。计算侧的原则是"保底不可动"：SLAM/避障/控制环的计算资源不做功耗妥协——这正对应矩阵里"性能保底"列的思维方式。

## <span class="blue"> 验收口径：标准化工况与回归门禁

功耗验收的常见失败是"测了一次达标，下版本又回去了"。两个机制防回归：

**标准化工况。** 功耗数字必须绑定工况才有意义：定义 3~5 个标准场景（空闲灭屏、典型业务、满载、 suspend），每个场景固定测试流程和时长，验收数字按场景出。"功耗 310mW"没有工况前缀就不是一个可验收的数字。

**回归门禁进 CI。** 功耗测试台架（INA219/功耗分析仪+脚本自动化）接入 CI：每个固件版本自动跑标准工况，功耗超基线 5% 即告警。功耗回归的隐蔽性极强——它不出任何功能错误，只在用户手里变成"续航变短"的投诉，没有门禁就一定会漏。这是第 23 章"监控四件套"思想在功耗域的重演：不可观测的指标必然退化。

## <span class="blue"> 本节总结

决策框架五步——分解（28.1 表）、定目标（续航/发热/性能保底三选一）、找低垂果实（收益/工程代价排期）、评估性能影响（延迟量化）、双指标验证——是前几节手段的组织方式。多目标矩阵说明同一手段在不同目标下的排序完全不同，全绿行（pinctrl sleep、背光）闭眼先做。被动散热设备上功耗优化就是性能优化，持续负载频率水位是它的量化读数。机器人场景把功耗账换成动态工况：大头在电机，抓手在运动规划与电量预测，计算资源保底不动。验收靠标准化工况+CI 门禁，防的是不出错的退化。

**关键结论速查：**

| 问题 | 答案 |
|------|------|
| 五步框架 | 分解→定目标→低垂果实→评估影响→双指标验证 |
| 目标的三种形态 | 续航优先/发热优先/性能保底——排序完全不同 |
| 闭眼先做项 | pinctrl sleep、背光管理（零性能代价） |
| 排期决定列 | 工程代价往往比收益更决定顺序 |
| 被动散热设备 | 功耗优化=性能优化；看持续负载频率水位 |
| 机器人功耗 | 大头是电机，抓手在运动规划/电量预测 |
| 防退化 | 标准工况 + CI 功耗门禁（超基线 5% 告警） |
