# 28.7 综合实战：WRM247LTE 功耗优化

> 所属章节：第28章 功耗全链路
>
> 难度：[E] | 预计阅读时间：50 分钟

## <span class="blue"> 本节导读

前六节建立的内容——测量方法论（28.1）、三大件分解（28.2）、外设管理（28.3）、系统级策略（28.4）、权衡框架（28.5）、故障分诊（28.6）——这节压进大纲自带的完整案例：**WRM247LTE 工业物联网设备，电池供电，产品指标 suspend 功耗 <200mW，初始实测 720mW，最终压到 199mW（-72%）**。

这个案例与 25.7/26.8 的打法同构（测量先行→分解→逐项打击→验证收口），但敌人完全不同：门铃案打的是多余的数据搬运，网关案打的是调度的不确定性，**本案打的是"看不见的电"——最大单笔收益不来自任何驱动或算法优化，来自一组引脚的电平配置**。这也是它能成为功耗教学样板的原因：它把"功耗问题是系统协同问题"这句抽象结论变成了一串可复核的数字。

全程四步治理：引脚漏电修复（-107mW）→ WLAN 断电策略（-12mW）→ Runtime PM 补全（-200mW）→ 残余项归因（-200mW）。

---

## <span class="blue"> 背景：720mW 的初始现场

WRM247LTE：野外部署的工业数据采集终端，4G 回传，电池+太阳能供电。产品定义里 suspend 功耗 <200mW 是硬指标——它决定太阳能板和电池的选型成本，超标意味着 BOM 重做。

初版固件的 suspend-to-RAM 实测 720mW，超标 3.6 倍。团队的第一反应是两个直觉方向："4G 模组没睡好"（无线模组是功耗大户的刻板印象）和"CPU 没进深睡"（cpufreq/cpuidle 派）。两个方向都值得怀疑，但按 28.1 的纪律：**没分解表不动手**。

---

## <span class="blue"> 第一阶段：分解，账对不上的地方藏着答案

按 28.1 的分段隔离法做 suspend 态功耗分解。设备进入 suspend-to-RAM 后，逐路测量与估算各组件份额：

| 组件/项 | suspend 态实测/估算 | 备注 |
|---------|---------------------|------|
| CPU+SoC 核心域 | ~180mW | 电源域断电+保持电，合理 |
| DDR 自刷新 | ~45mW | 28.2 的物理下限项，合理 |
| 4G/WLAN 模组（sleep 模式） | ~12mW | 模组自家 sleep 状态 |
| 其他外设（传感器/接口芯片） | ~100mW | Runtime PM 未生效 |
| PMIC 轻载损耗 | ~60mW | 效率曲线最差区间（28.2） |
| **已识别小计** | **~397mW** | |
| **实测整机** | **720mW** | |
| **对不上的差值** | **~323mW** | ★ |

**323mW 的账对不上**——这是整个案子真正的起点。28.1 说过：分解表合不上的差值就是破案方向。

按 28.3 的引脚漏电排查法上万用表：suspend 态下逐组量引脚电平。结果发现两组引脚悬在中间电平（1.6V 附近晃）：**I2C 总线引脚**（挂了 PMIC 和传感器，suspend 时对端已断电）和 **MMC/SDIO 引脚**（4 根数据线+CLK+CMD 共 6 根，卡槽电路断电后全部悬浮）。用分流法粗测这两组的直通电流：I2C 组约 2mA、MMC 组约 34mA——**换算成功耗约 6mW + 114mW ≈ 120mW**，差值的大头找到了。剩余差值后查为 estimate 误差与测试点损耗，量级闭合。

> 💡 这个发现把最初的两个直觉方向都证伪了：4G 模组睡得挺好（12mW），CPU 也进对了深睡——**720mW 里约 1/6 是没人想到的引脚漏电**。直觉方向没有测量护航，就是把预算花在错的地方。

## <span class="blue"> 四步治理

### 第一步：pinctrl sleep 状态（-107mW）

**依据：** 28.3 的漏电机理——外设断电后 SoC 侧引脚悬浮，CMOS 输入级直通。两组引脚实测 120mW，是分解表差值的主体。

**改动：** 设备树为 I2C4 和 MMC 控制器各加 sleep 状态组（28.3 的 DTS 模式），suspend 时切到"GPIO 输出低电平"：

```dts
&mmc1 {
    pinctrl-names = "default", "sleep";
    pinctrl-0 = <&mmc1_pins>;
    pinctrl-1 = <&mmc1_sleep>;        /* sleep组：6根引脚全部output low */
};
```

**收益：** I2C 组 -6mW，MMC 组 -101mW（6 根线，收益与引脚数正相关——28.3 的规律实证）。**代价：** 零——引脚电平切换不影响任何功能，恢复时切回 default 即可。这是全案收益/代价比最高的一步，也是 28.5 排序表里"闭眼先做"项的现实形态。

### 第二步：WLAN 完全断电（-12mW）

**依据：** 分解表里 WLAN sleep 模式 12mW。设备的使用模式是"每小时唤醒一次采集+回传"，WLAN 的空闲价值为零——sleep 模式的 12mW 是纯粹的浪费。

**改动：** 网络驱动从"模组 sleep 模式"改为"GPIO 控制模组电源，不用时完全断电"；唤醒路径加到 rtcwake 流程里（唤醒→上电→模组初始化→连接）。

**收益：** -12mW。**代价：** 唤醒后 4G 回传就绪时间从 2s 增加到 9s（模组上电初始化+网络注册）——对每小时回传一次的业务无感。**但这是一个"代价明示"的决策**：如果产品后续改成"随时可被平台唤醒下发指令"，这一步要回滚。代价写在决策记录里，回滚条件也写进去。

### 第三步：Runtime PM 补全（-200mW）

**依据：** 分解表"其他外设 ~100mW"加上运行态与 suspend 过渡期的外设浪费——按 28.3 的审计法空载扫描，一批外设（传感器接口、USB hub、音频 codec 等）的 runtime_status 常驻 active。

**改动：** 逐设备处置（28.3 实录的四种形态这里全用上了）：没开 autosuspend 的打开并配延迟、引用计数被占的修调用方、两个驱动没实现 suspend 回调的补驱动补丁、一个确认不该睡的登记误报。

**收益：** suspend 态与过渡期合计约 -200mW。**代价：** 两个驱动补丁引入的 resume 时序风险——用 28.6 的 pm_test 分级+50 次循环回归覆盖，这也是本案测试周期最长的一步（天级）。

### 第四步：残余项归因与接受（-200mW）

治理到这一步实测约 320mW，还差 120mW 到指标。最后一段的构成逐项归因：

- **CPU 电源域配置复核**：一个本该断电的 always-on 域（给调试模块供电）在设备树里被标成保持电——改配置，-85mW；
- **PMIC 轻载模式**：启用 PFM 模式寄存器位（28.2 的轻载效率项），-25mW；
- **剩余 ~10mW 的测量与估计误差**：归因后接受。

**这一步的教训单列：** 最后的差值不是一项大优化，是三个小项的归因——**功耗优化的收尾阶段永远是"归因残差"而不是"再找大鱼"**，因为大鱼在分解表阶段就都被看见了。

## <span class="blue"> 验收：199mW 的证明方式

最终实测 suspend-to-RAM 199mW，压线达标（指标 <200mW）。验收按 28.5 的口径四件套：

**全温区。** -10℃/+25℃/+55℃ 三档复测：+55℃ 时静态漏电增长（28.1 的指数项），suspend 功耗上浮到 226mW——超标。追加动作：高温档把 4G 模组断电（原方案 sleep），高温下达标。**温度项在这里从"验收项目"升级成了"方案的一部分"**——最终方案是"常温 WLAN sleep、高温 WLAN 断电"的温度自适应策略，由 thermal 框架的 trip point 驱动（15.4 的机制在这里兑付）。

**长稳循环。** suspend 5 分钟→唤醒→工作 1 分钟循环 72 小时（约 500 循环）：无 resume 失败（28.6 工单实录的回归方法），功耗读数无漂移。

**唤醒功能回归。** 三种唤醒源（RTC 定时、按键、4G 平台下发）各验证 100 次：唤醒成功率 100%，唤醒延迟分布稳定。

**续航实测。** 最终指标落到产品语言：满电野外部署续航从 4.2 天提升到 11.6 天——这个数字才是 199mW 的意义。

## <span class="blue"> 复盘：这个案例教什么

**最大的功耗源是一个配置问题。** 107mW 的引脚漏电——全案最大单笔收益——不来自驱动优化、不来自 governor、不来自任何"高深"手段，来自设备树里少了六行 pinctrl 配置。这就是大纲那句教训的完整实证：功耗问题往往不是单一子系统的问题，而是 GPIO 配置、总线状态、网络策略、PM 回调之间的协同问题。**协同问题的敌人是"没人负责接缝"——引脚归硬件工程师管、断电归驱动工程师管、而漏电恰好在两者的接缝上。**

**分解表对不上的账，比对的账更值钱。** 本案的转折点不是任何测量技术，是那个 323mW 的差值——它逼出了万用表量引脚的动作。分解表的全部意义在于"能不能合上账"：合不上，差值就是方向；合上了，优化才谈得上排期。

**每项收益都要带着代价一起记。** WLAN 断电的 9 秒重连、Runtime PM 补丁的时序风险、高温策略的复杂度——这些代价与收益写在同一张决策记录里。功耗优化没有免费的午餐，只有记了账的午餐。

**方法论与 25.7/26.8 完全同构。** 测量先行（分解表杀掉两个直觉方向）、逐项打击（四步各有依据/收益/代价）、验收收口（温度/长稳/回归三件套）、教训归档。三个案例（门铃、网关、WRM247LTE）领域完全不同，骨架一模一样——这就是第四部想交付的东西：**链路与对象各异，全链路实战的方法论只有一个。**

## <span class="blue"> 本节总结

WRM247LTE 案四步治理（pinctrl sleep -107mW、WLAN 断电 -12mW、Runtime PM -200mW、残余归因 -200mW）把 suspend 功耗从 720mW 压到 199mW。全案的三个转折点都不是优化技巧：分解表的 323mW 差值逼出引脚漏电、WLAN 断电的代价明示与回滚条件、残余阶段的归因而非找大鱼。验收在高温档反弹后以"温度自适应策略"收口——功耗方案的验收永远带温度条件。复盘四条：最大功耗源是配置问题、对不上的账最值钱、收益代价同账记、方法论三案同构。
