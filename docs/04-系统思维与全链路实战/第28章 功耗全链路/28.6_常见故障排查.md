# 28.6 常见故障排查

> 所属章节：第28章 功耗全链路
>
> 难度：[M] ~ [E] | 预计阅读时间：35 分钟

## <span class="blue"> 本节导读

功耗域的故障有一个别处没有的特点：**大量故障是优化自己引入的**——Runtime PM 打开了，某设备在传输中途被断电；suspend 调深了，某个外设的 resume 再没成功过。这类故障的迷惑性在于时间错位：改动发生在上周，故障出现在今天的客户现场，中间隔着"设备空闲了几分钟"这个看不见的触发条件。大纲列的四类高频问题（优化后功能异常、suspend 无法 resume、测量不准、温度差异），本节逐一给出分诊路径。本节覆盖：

- 优化引入故障的时间相关性判据
- 功能异常：过早挂起的定位与二分法
- suspend/resume 失败：pm_test 分级定位法
- 工单实录：唤醒后网口死掉的电源顺序破案
- 测量不准：仪器、自干扰、环境三个来源
- 温度差异：漏电的指数项与验收纪律
- 症状-入口速查表

> 💡 第 15.7.1 节有功耗排查的机制视角实战（PM 框架内部），本节是速查视角：拿到故障先查什么的顺序手册。

## <span class="blue"> 故障一：优化后偶发功能异常

**现象：** 开了 Runtime PM/autosuspend 之后，某外设偶发失灵——传感器偶发读错、存储偶发写失败、通信偶发丢数据。重启不复现，放一会儿就出。

**机理：** 设备被过早挂起——**数据还在传输/处理途中，驱动就把电源断了**。典型触发是 autosuspend_delay_ms 设得比业务间隔短：业务每 5 秒访问一次，延迟设 3 秒，每次访问都是"唤醒-用-睡"的循环，某次时序不巧就在传输中途被挂。

**分诊路径：**

1. **时间相关性验证**（关键第一步）：故障是否总发生在"设备空闲一段时间后"？连续访问设备保持忙碌，故障是否消失？——消失即高度指向挂起时序问题；
2. **定位设备**：故障时刻读嫌疑设备的 `power/runtime_status`，如果在 `suspended`，基本坐实；
3. **二分确认**：`echo on > power/control` 禁止该设备挂起，跑 24 小时——故障消失则结案；
4. **修复（不是禁止）**：正确的修法是调 autosuspend_delay_ms（大于业务访问间隔）或修驱动的挂起回调（传输未完成的标志位没检查）——`echo on` 是确诊手段不是修复手段，留着它等于放弃这部分功耗收益。

**典型根因：** autosuspend 延迟过短、驱动挂起回调没等传输完成、恢复时序不完整（寄存器没恢复全）。

## <span class="blue"> 故障二：suspend 后无法 resume

**现象：** 设备进 suspend 后叫不醒，或唤醒后某功能永久失效（网口不通了、屏幕花了），只能重启。

**机理：** resume 是一条长链——每个设备的 resume 回调按序执行，任一环节失败都可能导致后续设备状态错乱。最常见的失败形态是某设备的 resume 回调报错（时钟/电源没恢复全，寄存器读写失败）。

**分诊路径：pm_test 分级定位。** 内核提供了 suspend 流程的分级测试——不真正睡死，逐级深入：

```
echo core > /sys/power/pm_test       # 级别1：只测内核核心层
echo processors > /sys/power/pm_test # 级别2：+CPU
echo platform > /sys/power/pm_test   # 级别3：+平台设备（最常用）
echo devices > /sys/power/pm_test    # 级别4：+所有设备
echo freezer > /sys/power/pm_test    # 级别5：只冻结进程
echo mem > /sys/power/state          # 触发测试（5秒后自动返回）
```

从浅到深逐级测试，**哪一级开始失败，故障域就在哪一级**：freezer 失败是进程冻结问题（某进程不可冻结——查 D 状态进程），devices 失败是某设备回调问题。设备级的精确点名靠唤醒阶段的日志：

```
echo 1 > /sys/power/pm_print_times      # 打印每个设备suspend/resume耗时
echo 1 > /sys/power/pm_debug_messages   # 打印PM调试信息
```

```
dmesg | grep -E "resume|suspend" | grep -vE "complete"
[   45.2] dpm_run_callback: mmc1_resume returns -110    ← ★MMC的resume超时失败
[   45.2] PM: Device mmc1 failed to resume: error -110
```

失败设备被直接点名——剩下的工作就是查这颗设备的 resume 依赖（时钟/电源/复位时序），eMMC/SD 的 resume 失败尤其高发（睡眠唤醒时序违反，见 28.3 策略表）。

> ⚠️ pm_test 各级都会在 5 秒后自动返回，不真正进入睡眠——所以它是安全的带外测试。但**它测不出真睡才暴露的问题**（电源域真正断电后的状态丢失），pm_test 全过而真 suspend 失败时，嫌疑转向 PMIC 配置与保持电（always-on）域的边界。

### 工单实录：一次"唤醒后网口死掉"的分级定位

把故障二的工具链走一遍。现场报障：工业平板，suspend 唤醒概率性出现——约十次里三次唤醒后以太网完全不通，`ifconfig down/up` 也救不回来，只能重启。

**第一步，分级定位（1 小时）。** 从 freezer 逐级测到 devices：freezer/core/processors/platform 四级各测 50 次全部正常；devices 级第 30 次左右复现——网口唤醒后不通。**故障域锁定在设备层**。

**第二步，点名（30 分钟）。** 开 `pm_print_times` 复测，失败时刻的 dmesg：

```
[  312.5] dpm_run_callback: stmmac_resume returns -110
[  312.5] PM: Device fe010000.ethernet failed to resume: error -110
[  312.5] dpm_run_callback: mdio_bus stmmac-0:00 ...     ← PHY的resume在MAC之后跑了
```

MAC 驱动 resume 超时（-110 = ETIMEDOUT），且紧随其后的日志显示 PHY 的 resume 排在 MAC **之后**——顺序错了：MAC 恢复时要通过 MDIO 读 PHY，但 PHY 的电源还没恢复。

**第三步，根因与修复（半天）。** 设备树里 PHY 的电源域（regulator）声明挂错位置：PHY 的 vdd 被声明成了 MAC 节点的子资源，导致电源恢复顺序跟着 MAC 走而不是跟着 PHY 走。修正 regulator 归属后，resume 顺序变成"电源→PHY→MAC"，50 次循环测试无一失败。

**复盘要点：** 这类"概率性失败"的根因几乎都是时序/顺序问题——十次里三次失败的概率性来自电源上电时间与 MDIO 首次访问的竞争。概率性故障不改成分诊问题就永远是玄学，pm_test+pm_print_times 的价值就是把"偶尔醒不来"变成"某个设备回调返回 -110"的确定结论。

## <span class="blue"> 故障三：功耗测量不准

**现象：** 测出来的功耗数字和理论值对不上、两次测量结果差很多、或者"优化了但表上看不出来"。

**分诊路径（按嫌疑排序）：**

1. **仪器采样率**（28.1 已展开）：万用表测瞬态是白测——suspend 进出过程、唤醒尖峰必须示波器/功耗分析仪。判据：被测过程短于仪器的有效采样周期；
2. **自干扰**：测量动作本身改变了被测对象——开着调试串口日志测 suspend 功耗（日志唤醒）、用着 SSH 会话测 Wi-Fi 功耗（keepalive 流量）。判据：断开调试通道后读数变化。这是实测中最常踩的：**所有功耗测量要在"产品真实运行形态"下进行**，开发形态（串口、SSH、调试件全插着）的数字没有意义；
3. **参考点混淆**：测电池入口 vs 测 SoC 电源轨，差着 PMIC 效率那一档（28.2）——对比数字前先对齐测量点；
4. **温度漂移**：见故障四。

**典型根因：** 万用表测瞬态、调试件自干扰、测量点不一致。

## <span class="blue"> 故障四：不同温度下功耗差异大

**现象：** 常温测试达标的功耗指标，高温箱里超标 30~50%；或者低温下设备直接起不来。

**机理：** 28.1 的静态功耗公式里藏着温度项——漏电流随温度指数增长，85℃ 时的静态功耗可以是 25℃ 时的数倍。高温超标的不是"哪里坏了"，是物理规律在收税。低温方向的故障形态不同：电池低温下内阻增大、电压坍塌，大电流脉冲（射频发射、CPU 冲刺）触发欠压复位。

**分诊路径：**

1. **高温超标先分静动态**：高温箱里分别测满载与 idle——idle 功耗涨得多是漏电（物理项，软件能做的是确认该关的电源域都关了）；满载涨得多是动态功耗+thermal throttling 的共同作用（28.5 的频率水位）；
2. **低温起不来查电源路径**：示波器抓上电瞬间的电压跌落——欠压复位阈值 vs 低温电池内阻的组合，软件侧手段是限制冷启动时的峰值电流（推迟射频上电、CPU 限频启动）；
3. **验收纪律**：功耗指标必须带温度条件——"25℃ 达标"不是验收，"-10℃~+55℃ 全温区达标"才是。温箱测试要覆盖**温度渐变过程**（升温过程中漏电平滑增长，某些设计在过渡态出问题）。

**典型根因：** 漏电指数项（高温）、电池内阻+欠压复位（低温）、验收口径缺温度条件。

## <span class="blue"> 症状-入口速查

| 症状 | 第一条命令/动作 | 大概率方向 |
|------|----------------|-----------|
| 优化后偶发失灵 | 连续访问保持忙碌，故障是否消失 | autosuspend 过早挂起（28.6 一） |
| suspend 后叫不醒 | `echo platform > /sys/power/pm_test` 分级测试 | 某设备 resume 回调失败 |
| 唤醒后某功能失效 | `pm_print_times` + dmesg 找 returns -XX | 该设备时钟/电源/时序未恢复 |
| 功耗测不出优化效果 | 断开调试串口/SSH 再测 | 自干扰（调试件在耗电/唤醒） |
| 瞬态功耗看不见 | 换示波器/功耗分析仪 | 万用表采样率（28.1） |
| 高温功耗超标 | 高温下分测 idle 与满载 | 漏电指数项 / throttling |
| 低温起不来 | 示波器抓上电电压跌落 | 电池内阻+欠压复位 |
| suspend 功耗"降不下来" | `cat /sys/power/mem_sleep` 看方括号 | 停在 s2idle 没进 deep（28.4） |
| suspend 电流周期跳高 | `cat /sys/kernel/debug/wakeup_sources` | 唤醒源偷醒（28.4） |

## <span class="blue"> 本节总结

功耗故障四类分诊：优化后功能异常抓"时间相关性"（空闲后发病=挂起时序），二分确认后修延迟参数或驱动回调而不是永久禁用；suspend/resume 失败用 pm_test 五级定位层、pm_print_times 点名设备，真睡才暴露的问题查 PMIC 与保持电边界；测量不准三来源是采样率、自干扰（调试形态的数字没意义）、测量点不一致；温度差异分方向——高温是漏电指数项收税，低温是电池内阻加欠压复位，验收口径必须带全温区。速查表九行把功耗域的高发报障归口到具体章节方法。
