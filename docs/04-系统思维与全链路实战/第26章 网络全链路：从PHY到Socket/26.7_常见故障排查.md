# 26.7 常见故障排查

> 所属章节：第26章 网络全链路：从PHY到Socket
>
> 难度：[M] ~ [E] | 预计阅读时间：35 分钟

## <span class="blue"> 本节导读

前五节建立了链路上每一段的机理和观测点，本节回答"拿到一个网络故障先干什么"。网络故障的高发形态收敛起来是四类：**吞吐不达标、偶发丢包、延迟抖动、连接建立慢**。与 Camera 故障（25.6）不同，网络故障几乎从不出在"完全不通"——链路层不通是 26.1 的事；本节四类的共同点是**系统在 degraded 状态下运行**，表象模糊，没有明确的报错，全靠观测手段分层收敛。

本节按"现象 → 第一条命令 → 分诊路径 → 典型根因"组织每个故障类，分诊路径中的每一步都指回前五节的具体方法。本节覆盖：

- 分诊总原则：证据先行、每层可证伪
- 吞吐不达标：iperf3 决策树的现场版
- 偶发丢包：三位置判据的快速归口
- 工单实录：一次"所有计数器都正常"的丢包完整归口
- 延迟抖动：先分调度段还是链路段
- 连接建立慢：队列、DNS、SYN 三个嫌疑犯
- 症状-入口速查表

> 💡 第 14.7.1 节有一个 UDP 丢包排查的深挖实战（协议栈视角），本节是速查视角——拿到故障先查什么的顺序手册，两者互补不重复。

## <span class="blue"> 总原则：证据先行、每层可证伪

网络故障排查最大的浪费是"凭经验直接调参"——调了 NAPI budget、绑了中断、开了 GRO，一通操作后故障还在，而且系统状态被改得无法归因。两条纪律贯穿本节：

**证据先行。** 每个故障类的第一条命令都是只读的观测命令（计数器、状态、分布），先确定故障在哪一层，再动任何配置。

**每层可证伪。** 分诊路径上每一步都要能回答"如果假设错了，我怎么知道"——26.6 决策树的纪律在这里通用：试完一个分支没改善就退回，不在错误分支上深挖。

## <span class="blue"> 故障一：吞吐不达标

**现象：** iperf3 实测显著低于链路标称（千兆跑 400~700M），或业务吞吐不达设计值。

**第一条命令：** `mpstat -P ALL 1`（打流期间）——看 CPU 分布形态，直接进 26.6 决策树的四个分支。

**分诊路径：**

1. **各核都闲** → 查中断分布：`grep eth0 /proc/interrupts` 看是否集中一核 → 配 RSS/亲和性（26.2）、XPS（26.3）；中断正常则直下第 4 步查物理链路；
2. **某核 %soft 100%** → 协议栈瓶颈 → `ethtool -k eth0` 查 GRO/GSO/TSO 卸载开关 → 开满仍不够则评估 XDP（26.4 决策边界）；
3. **某核 %sys 100%** → 应用层 syscall 瓶颈 → recvmmsg 批处理、rcvbuf 调大（26.5）；
4. **CPU 全部不忙** → 物理链路：`ethtool eth0` 看协商速率（千兆掉百兆，26.1 故障三）、`ethtool -S` 看错包计数、iperf3 -R 反向对比、换直连拓扑隔离中间链路。

**典型根因：** 中断默认绑核不合理（嵌入式平台高发）、协商掉速、offload 被某个"优化脚本"关掉、应用小包高频 syscall。

## <span class="blue"> 故障二：偶发丢包

**现象：** 业务层偶发超时、重传，ping 偶发丢包，但链路灯正常、平均吞吐正常。

**第一条命令：** 计数器三件套差值（26.2 的归属判断）：

```
ethtool -S eth0 | grep -iE "miss|fifo|drop|crc"     # 位置一：硬件/MAC
nstat -az | grep -iE "RcvbufErrors|ListenDrops|InErrors"   # 位置三：socket/协议栈
dropwatch -l kas                                     # 位置二：协议栈主动丢
```

**分诊路径：**

1. **ethtool -S 的 missed/fifo 涨** → ring 满：调大 ring（-G）→ 查中断亲和性 → 查 CPU 争抢（26.2 实操实验）；
2. **crc/errors 涨** → 物理层：线缆、RGMII phy-mode（26.1 故障二）、EMI——百兆强制验证；
3. **dropwatch 热点指向 nf_hook** → Netfilter 规则丢包（26.4 nftrace 定位具体规则）；
4. **nstat 的 RcvbufErrors 涨** → 应用读太慢（26.5：取包节奏、队列深度）；
5. **以上全不涨但业务仍丢** → conntrack 表满：`nf_conntrack: table full` 查 dmesg，count/max 对比（26.4）——**这是"所有计数器都正常但就是丢包"形态的首犯**；
6. **UDP 业务且对端在发** → 别忘了最后一层：可能是对端发包侧丢的（26.3 的 qdisc dropped），抓包确认包到底有没有到本机。

**典型根因：** ring 深度不足、conntrack 表满、应用队列满、对端发包侧丢包。

### 工单实录：一次"所有计数器都正常"的丢包

按分诊路径走一遍真实形态。现场报障：视频推流网关，上游平台每隔几分钟报一次"流中断 2~3 秒后自愈"。

**第一步，三位置归口（10 分钟）。** 复现窗口内取三组差值：

```
ethtool -S eth0 | grep -iE "miss|fifo|crc"     # 差值全部为0：硬件侧干净
nstat -az | grep RcvbufErrors                   # 差值为0：socket队列没满
dropwatch -l kas                                # 无热点：协议栈没在丢
```

三位置全干净——按分诊路径第 5 步，查 conntrack：

```
dmesg | grep conntrack
nf_conntrack: table full, dropping packet        ← 果然在，时间戳与中断时刻吻合
cat /proc/sys/net/netfilter/nf_conntrack_count   # 65534
cat /proc/sys/net/netfilter/nf_conntrack_max     # 65536——顶格
```

**第二步，找是谁撑爆的表（15 分钟）。**

```
conntrack -S | sort -k2 -n -r | head            # 按条目数排序看分布
```

```
udp      17  src=10.0.0.0/8 类型条目 58000+     ← UDP短连接占了九成
```

追查发现是新增的设备心跳服务：每台设备每 2 秒一个 UDP 心跳包，源端口随机——**每个心跳包就是一条新 conntrack 条目**，三千台设备把表顶的满满的。视频流本身的 TCP 长连接反而是无辜受害者：表满时它的新包也被丢。

**第三步，治本（5 分钟）。** 心跳流量不需要状态追踪，直接豁免：

```
iptables -t raw -A PREROUTING -p udp --dport 7777 -j NOTRACK
```

conntrack_count 回落到四位数，观察一周无复发。扩容（`nf_conntrack_max` 调大）作为备用方案没有启用——**把不该进表的流量请出去，比把表做大更治本**。

这个工单的教训对应分诊路径的设计意图：conntrack 排在第 5 步不是因为它罕见，而是因为它的证据形态是"排除法之后的那一个"——三位置计数器全正常本身就是它的指纹。

## <span class="blue"> 故障三：延迟抖动大

**现象：** 平均延迟正常，但偶发尖刺——实时业务最怕的形态。

**第一条命令：** `ping -i 0.002 -c 5000 -q <目标>` 看 mdev/max——确认是抖动问题而非延迟问题（26.6）。

**分诊路径：**

1. **SO_TIMESTAMPING 打点切分**（26.6 实录）：硬件戳→软件戳的差值大 → 链路/内核段问题（查中断合并参数 ethtool -c、ring 深度）；软件戳→读取时刻差值大 → 调度段问题，继续往下；
2. **调度段确诊后查三大嫌犯**：CPU governor（`scaling_governor` 非 performance → DVFS 跳频尖刺）、中断亲和性（ksoftirqd 与业务线程抢核）、内核长临界区（cyclictest 基线差 → 考虑 PREEMPT_RT 评估，第 20 章）；
3. **抖动随流量负载变化** → NAPI budget 与中断合并（ethtool -C）的 trade-off：合并过激省 CPU 但增加单包等待；
4. **仅特定业务抖** → 应用自身：epoll 事件循环里干了重活（26.5 坑二）、GC/日志刷盘等周期性任务抢占。

**典型根因：** 调度延迟（最大头）、DVFS、中断合并过激、应用事件循环阻塞。

## <span class="blue"> 故障四：连接建立慢

**现象：** 客户端 connect 偶发超时、首字节延迟高，但建立后通信正常。

**第一条命令：** `ss -ltn` 看 Recv-Q/Send-Q——accept 队列是否顶满（26.5）。

**分诊路径：**

1. **Recv-Q ≥ Send-Q 或 ListenOverflows 涨** → accept 队列溢出：accept 循环提优 → 调 backlog/somaxconn → syncookies 确认（26.5）；
2. **队列正常但 connect 慢** → 区分建连慢还是首字节慢：`tcpdump` 看三次握手耗时——握手快而首字节慢，问题在应用 accept 后的处理链（鉴权、初始化）；
3. **握手本身慢** → SYN 丢包重传（看 SYN 重传计数 `nstat -az | grep -i syn`）→ 回到故障二的丢包路径；
4. **域名场景** → DNS 解析阻塞：`strace -c` 或应用打点区分 connect 与 getaddrinfo 的耗时——嵌入式设备 DNS 服务器不可达时，默认超时链（5s×重试×多 nameserver）能拖到几十秒，是"连接慢"最冤的根因；
5. **反向路径**（服务端主动连客户端/网关回连）→ 对端的 backlog 和防火墙规则同样过一遍。

**典型根因：** accept 队列溢出、DNS 超时链、SYN 丢包重传、应用 accept 后处理链阻塞。

## <span class="blue"> 症状-入口速查

| 症状 | 第一条命令 | 大概率方向 | 详解 |
|------|-----------|-----------|------|
| 吞吐不达标 | `mpstat -P ALL 1`（打流中） | 26.6 决策树四分支 | 26.2/26.3 |
| 偶发丢包 | ethtool -S + nstat + dropwatch 差值 | 三位置归口，全不涨查 conntrack | 26.2/26.4/26.5 |
| 延迟尖刺 | `ping -q` 看 mdev/max | 调度段（governor/亲和性/临界区） | 26.6 |
| 连接建立慢 | `ss -ltn` 看 Recv-Q | accept 队列/DNS/SYN 重传 | 26.5 |

## <span class="blue"> 本节总结

四类高发故障的分诊都是前五节工具的组合应用：吞吐看 CPU 形态进决策树，丢包用三位置计数器归口（全不涨时查 conntrack），抖动先用时间戳切调度段/链路段，连接慢先查 accept 队列再分握手/首字节/DNS。两条纪律贯穿：证据先行（第一条命令永远只读）、每层可证伪（分支没改善就退回）。速查表九行覆盖了现场九成的报障形态——连同 26.1 的链路层三条和 26.3 的 tx timeout，它们共同构成链路全段的故障地图。

**本节自查：**

1. "偶发丢包"排查中，三个位置的计数器都不涨时，下一个该查什么？为什么它常被漏掉？
2. 延迟抖动排查里，为什么 SO_TIMESTAMPING 的打点切分要放在调 governor 之前？
3. connect 慢但三次握手耗时正常，故障域收敛到哪？举两个候选根因。
4. 吞吐不达标且 CPU 全闲时，为什么要做 iperf3 -R 反向测试？它区分什么？

**下一步：** 四张分诊路径备齐，最后一节把它们全部压进一个完整案例：工业网关在 1Gbps 链路上把确定性延迟从 5~20ms 抖动压到 99.9 分位 <500μs 的全过程——PREEMPT_RT、CPU 隔离、busy polling、NAPI budget 五步的系统化落地。26.8 综合实战。
