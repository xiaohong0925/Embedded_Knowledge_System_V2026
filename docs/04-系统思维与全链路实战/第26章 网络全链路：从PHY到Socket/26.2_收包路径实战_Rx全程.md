# 26.2 收包路径实战：Rx 全程

> 所属章节：第26章 网络全链路：从PHY到Socket
>
> 难度：[E] | 预计阅读时间：45 分钟

## <span class="blue"> 本节导读

26.1 结束时，包已经由 DMA 搬进了 DDR 的 ring buffer。从这往后的每一站都在内核里——第 14 章已经把 NAPI 的内部机制、sk_buff 的结构讲透了（14.3.2、14.1.2），所以本节不重复"NAPI 是什么"，而是回答实战问题：**收包路径上每一站长什么样、用什么工具看、丢包丢在哪一环、对应哪个计数器**。

收包路径的故障有一个特点：它几乎从不"完全不通"，而是"吞吐量上不去""偶发丢包""CPU 打满"——都是渐变劣化，必须用计数器和观测手段量化，不能靠感觉。本节覆盖：

- 收包旅程的七个站点：每站的输入/输出/可观测点
- ring buffer 与描述符：DMA 和内核之间的交接协议
- NAPI 的行为观测：中断↔轮询切换在 /proc/interrupts 上的指纹
- 丢包点地图：三个丢包位置与各自的 ethtool 统计项
- 实操实验：iperf3 打流下用计数器差值定位丢包环节

> 💡 本节所有观测手段基于通用工具（ethtool、/proc、tracepoint），不依赖特定网卡驱动；但统计项的名字因驱动而异，读自己平台 `ethtool -S` 的完整清单是第一步。

## <span class="blue"> 收包旅程：七个站点

一个包从 ring buffer 到应用手里，经过七站：

```
① DMA 写入 ring buffer（硬件，无 CPU 参与）
        │ ② 中断：MAC 通知"有包到了"
        ▼
③ NAPI poll：softirq 里批量收包，skb 被组装出来
        │ ④ GRO：多个同流小包合并成一个大 skb（可选卸载）
        ▼
⑤ 协议栈：Netfilter 钩子 → 路由 → TCP/UDP
        │
        ▼
⑥ socket 接收队列：skb 排队等应用
        │ ⑦ read()/recvmsg()：应用取走，数据拷贝到用户态
        ▼
     应用程序
```

每一站都有独立的观测点和独立的劣化方式——这就是为什么"网络慢"必须分段查。对照表先给出，后面逐站展开：

| 站 | 干什么 | 观测点 | 典型劣化 |
|----|--------|--------|----------|
| ① DMA | 硬件搬包进 ring | ethtool -S 硬件计数 | ring 满，硬件丢包 |
| ② 中断 | 通知内核 | /proc/interrupts | 中断风暴或中断合并过度 |
| ③ NAPI poll | 批量组装 skb | top 的 %si、ksoftirqd | softirq 打满 CPU |
| ④ GRO | 小包合并 | ethtool -S gro 相关项 | 关闭时吞吐骤降 |
| ⑤ 协议栈 | Netfilter/路由/TCP | perf、dropwatch | 规则过多拖慢 |
| ⑥ socket 队列 | 排队等应用 | ss -m、`/proc/net/snmp` | 队列满丢包 |
| ⑦ 应用读 | 拷贝到用户态 | strace/perf | 应用读太慢反压 |

## <span class="blue"> ring buffer 与描述符：DMA 的交接协议

ring buffer 是 MAC 和内核之间的交接协议，值得看懂结构。它本质上是一个**环形数组**，每个槽位是一个描述符：

> 描述符（descriptor）：一个固定大小的结构体，核心内容是"一块内存的物理地址 + 状态位"。RX 方向下，内核预先把空 buffer 的地址填进描述符；MAC 收包后把数据 DMA 到该地址，翻转状态位表示"这格有货"；内核取走数据后把描述符复位重新挂回。**ring 的深度就是"硬件和软件之间能缓冲多少个包"。**

查看和调整 ring 深度：

```
ethtool -g eth0
```

```
Ring parameters for eth0:
Pre-set maximums:
RX:             512          ← 硬件支持的最大深度
RX Mini:        0
RX Jumbo:       0
TX:             512
Current hardware settings:
RX:             256          ← 当前生效值：没用满
TX:             256
```

```
ethtool -G eth0 rx 512 tx 512     # 调到最大
```

ring 深度的取舍逻辑：**深 ring 抗突发**（流量尖峰到来时，硬件能囤住包等内核来收）；**浅 ring 低延迟**（包在 ring 里排队的时间短）。这与 25.2 的 VB2 队列、25.7 的队列减帧是同一个哲学——缓冲深度永远是在"抗抖动"和"低延迟"之间取点。默认 256 对大多数场景合理；跑高吞吐且允许延迟的场景调大，跑确定性延迟的场景（26.8）反而要配合中断合并一起调小。

## <span class="blue"> NAPI 的行为观测：中断指纹

NAPI 机制本身（14.3.2）一句话回顾：第一个包触发中断，中断里关中断转轮询，poll 批量收包直到 budget 耗尽或无包，再重新开中断。这个机制在系统里留下的**可观测指纹**有三个，逐个看。

**指纹一：中断数与包数脱钩。** 打流前后对比中断计数：

```
grep eth0 /proc/interrupts
```

```
 45:   1234567   GICv3  45 Level   eth0     ← 记下此刻值
# iperf3 打流 10 秒（千兆打满，约每秒 8 万包）
 45:   1241567   GICv3  45 Level   eth0     ← 只涨了约 7000
```

10 秒约 80 万个包，中断只涨了 7000 次——**平均一次中断服务了一百多个包**，这就是 NAPI 轮询在工作。反过来，如果中断数 ≈ 包数，说明 NAPI 没生效或驱动没启用，CPU 会被中断处理活活打死（高吞吐下 %si 飙到 90%+）。

**指纹二：softirq 占比。** 打流时看：

```
mpstat -P ALL 1
```

```
CPU    %usr  %sys  %iowait  %irq  %soft  ...
 0     1.0   2.0    0.0     0.5   45.0    ← %soft 45%：收包软中断在吃 CPU0
 1     0.5   1.0    0.0     0.0    2.0
```

NAPI poll 跑在 softirq 上下文，全部体现在 %soft。单核 %soft 打满而总吞吐不达标，是"中断亲和性/多队列没配好"的确定性信号——解法（RSS/RPS/中断绑核）在 26.3 展开，机制在 14.6。

**指纹三：ksoftirqd 登场。** `top` 里出现 ksoftirqd 进程持续占 CPU，说明 softirq 处理不过来、内核把收包工作推给了内核线程——这既是负载信号也是延迟信号：ksoftirqd 参与后收包延迟跟着进程调度走了，抖动会明显变大。26.8 的工业网关案例里，它就是抖动的首犯之一。

## <span class="blue"> 丢包点地图：三个位置，三套计数器

收包路径上包会在三个位置被丢，每个位置有专属的计数器——**定位丢包就是给计数器读数做归属判断**。

**位置一：MAC 硬件丢包（ring 满）。** 内核来不及收，ring 被填满，MAC 没地方放新包，硬件直接丢。计数器名字因驱动而异，常见的有：

```
ethtool -S eth0 | grep -iE "miss|fifo|overrun|drop"
```

```
rx_missed_errors: 1523          ← ring满，硬件丢包（stmmac系叫这个名）
rx_fifo_errors: 0
```

rx_missed 增长 = 内核收得不够快。对策链：调大 ring（-G）→ 查中断亲和性/多队列 → 查 CPU 是否被其他负载抢占。**这是"吞吐不达标+CPU 不高"组合的第一嫌疑。**

**位置二：协议栈主动丢包。** 包过了 Netfilter 被规则丢弃，或 GRO/协议处理出错。这类不是"来不及"而是"不想要"：

```
dropwatch -l kas          # 内核丢包点实时监控（需内核开 NET_DROP_MONITOR）
```

```
drop at: ip_rcv_finish+0x... (0xffffffff....)
drop at: nf_hook_slow+0x...                  ← 被Netfilter规则丢了
```

**位置三：socket 队列满。** 包顺利走完协议栈，但应用读得慢，socket 接收队列撑满被丢。这层的计数不在 ethtool，在协议栈统计：

```
nstat -az | grep -iE "TcpExtListenOverflows|UdpRcvbufErrors|TcpExtTCPBacklogDrop"
```

```
UdpRcvbufErrors     4521     ← UDP接收buffer满丢包：应用读太慢
TcpExtListenDrops   0
```

`UdpRcvbufErrors` 涨 = 应用消费速度 < 到达速度，解法在 26.5（socket buffer 调参与应用侧批处理）。

> 💡 三个位置的判据可以合成一句话：**ethtool -S 涨是硬件侧来不及，dropwatch 有热点是协议栈在丢，nstat 涨是应用侧来不及。** 上手先各看一眼，丢包归属一分钟内定。

## <span class="blue"> 实操实验：一次完整的丢包定位

把上面的工具按真实顺序走一遍。场景：千兆 iperf3 UDP 打流，实测带宽只有 600Mbps，接收端有丢包。

**第一步，定归属（30 秒）。** 打流前记录三组计数器的基线，打流 30 秒后取差值：

```
ethtool -S eth0 | grep -iE "miss|fifo" > /tmp/before.txt
nstat -az | grep -iE "RcvbufErrors|ListenDrops" >> /tmp/before.txt
iperf3 -s &   # 对端打流30秒……
ethtool -S eth0 | grep -iE "miss|fifo" | diff /tmp/before.txt -
```

```
> rx_missed_errors: 8901        ← 差值8901：丢在位置一，ring满
```

**第二步，试深 ring（1 分钟）。**

```
ethtool -G eth0 rx 512
# 重打流：rx_missed 增量降到 1200，带宽升到 800Mbps
```

改善了但没根治——ring 加深只是给了更多缓冲，内核收包的根本速度没变。

**第三步，查收包速度为什么不够（2 分钟）。** `mpstat` 显示 CPU0 的 %soft 98%，其余核闲置——所有中断集中在一个核。查队列与亲和性：

```
ls /sys/class/net/eth0/queues/           # rx-0 rx-1 rx-2 rx-3：硬件有4队列
cat /proc/interrupts | grep eth0         # 但中断全绑在CPU0
echo f > /proc/irq/45/smp_affinity       # 把中断撒到4个核（示例）
```

重打流：带宽 940Mbps，rx_missed 归零。收工。

**这个三分钟流程的结构值得记住：** 归属判断（计数器差值）→ 最便宜的对策先试（调参数）→ 不根治再查根因（亲和性/多队列）。26.7 的故障排查节会把这套流程推广到全部四类网络故障。

## <span class="blue"> 本节总结

收包路径七站各有观测点：ring buffer 深度决定硬件能囤多少包（ethtool -g/-G），NAPI 的中断指纹是"中断数远小于包数"（/proc/interrupts 差值），softirq 压力看 %soft 和 ksoftirqd。丢包只发生在三个位置——MAC 硬件（ethtool -S 的 missed/fifo）、协议栈（dropwatch 热点）、socket 队列（nstat 的 RcvbufErrors）——各看一眼计数器，丢包归属一分钟可定。实操流程的骨架：计数器差值定归属 → 最便宜的对策先试 → 不根治查亲和性/多队列。

**关键结论速查：**

| 问题 | 答案 |
|------|------|
| ring buffer 是什么 | 描述符环形数组：物理地址+状态位，DMA 与内核的交接协议 |
| ring 深度取舍 | 深抗突发，浅低延迟；`ethtool -g` 查 `-G` 调 |
| NAPI 正常指纹 | 中断数 ≪ 包数；中断数≈包数则 NAPI 失效 |
| softirq 压力信号 | 单核 %soft 打满 / ksoftirqd 常驻 |
| 丢包三位置 | MAC 硬件（ethtool -S）/协议栈（dropwatch）/socket 队列（nstat） |
| 定位流程 | 计数器差值定归属 → 参数先试 → 根因后查 |

**本节自查：**

1. ring buffer 加深后丢包减少但不归零，说明什么？下一步该查什么？
2. 打流时中断计数几乎不涨，是好现象还是坏现象？什么情况下它反而是故障信号？
3. `rx_missed_errors` 和 `UdpRcvbufErrors` 同时增长，说明系统有哪两层问题？处理顺序是什么？
4. ksoftirqd 持续占 CPU，对收包延迟意味着什么？为什么？
