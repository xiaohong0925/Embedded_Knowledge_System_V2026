# 26.3 发包路径实战：Tx 与多队列

> 所属章节：第26章 网络全链路：从PHY到Socket
>
> 难度：[E] | 预计阅读时间：45 分钟

## <span class="blue"> 本节导读

收包侧（26.2）的核心矛盾是"包来得太快、内核收不过来"，发包侧的矛盾不一样：**包是应用主动发的，问题不在速度而在竞争**——多核系统里多个 CPU 同时往一个网口发包，大家在 qdisc 锁和 TX ring 上排队抢资源。发包路径的劣化形态因此也不同：不是丢包，而是"CPU 核数翻倍吞吐不涨""perf 里 spinlock 热点刺眼""偶发的 tx timeout 复位"。

本节把发包路径走一遍，重点放在多核竞争这个独有问题上：先看旅程和观测点，再深入 qdisc 这层"看不见的队列"，然后用多队列（MQ）和 XPS 把竞争摊开，最后处理发包侧特有的故障（tx timeout）。本节覆盖：

- 发包旅程的六个站点与观测点
- qdisc：协议栈和网卡之间的排队层
- 多核锁竞争：机理与 perf 观测
- MQ 多队列与 XPS 的配置实操
- 实操实验：四线程锁竞争从确诊到摊平的完整过程
- tx timeout：发包侧最典型的硬件级故障
- TC 的位置：限速与整形在哪一层生效

## <span class="blue"> 发包旅程：六个站点

应用 `write()` 一个 socket 之后，包的下行旅程：

```
① 应用 write()/sendmsg()
        │ ② TCP/UDP 层：分段、拥塞控制、组 skb
        ▼
③ IP 层 + Netfilter LOCAL_OUT/POST_ROUTING 钩子
        │ ④ dev_queue_xmit()：进 qdisc 排队
        ▼
⑤ 驱动 xmit：skb 挂到 TX ring 描述符，DMA 就绪
        │ ⑥ MAC 发出 + 发送完成中断：释放 skb，回收描述符
        ▼
     PHY → 网线
```

对照收包路径看两个结构性差异。第一，**发包有一层收包没有的设施——qdisc（④）**：收包从 ring 出来直接进协议栈，发包却要先排队。第二，**发包是"闭环"的**：⑥的完成中断回收描述符后，驱动才给 qdisc 放行下一批——TX ring 的深度和中断合并参数因此直接决定发包节奏。

| 站 | 干什么 | 观测点 | 典型劣化 |
|----|--------|--------|----------|
| ② TCP 层 | 分段/拥塞控制 | `ss -i` 看 cwnd/rtt | 拥塞窗口限制吞吐 |
| ③ IP/Netfilter | 路由+钩子规则 | perf / 26.4 的实测方法 | 规则链过长 |
| ④ qdisc | 排队+整形 | `tc -s qdisc` | backlog 堆积丢包 |
| ⑤ 驱动 xmit | 挂 TX ring | perf 锁热点 | 多核锁竞争 |
| ⑥ 完成中断 | 回收描述符 | /proc/interrupts | 中断合并过度致吞吐受限 |

## <span class="blue"> qdisc：发包路径上的隐形队列

> qdisc（queueing discipline）：排队规则层。每个 netdev 的发送路径上都挂着一棵 qdisc 树，包在交给驱动之前先在这里排队。它决定了"驱动忙的时候包怎么办"：排队等待、按优先级插队、还是直接丢弃。默认 qdisc 在大多数发行版是 fq_codel（公平排队+防 bufferbloat），嵌入式精简系统上常见 pfifo_fast（三个优先级 FIFO）。

查看当前配置与实时状态：

```
tc -s qdisc show dev eth0
```

```
qdisc mq 0: root                        ← mq：多队列占位qdisc，每个TX队列挂一个子qdisc
 Sent 89012345 bytes 123456 pkt (dropped 0, overlimits 0 requeues 0)
qdisc fq_codel 0: parent :1 ...         ← 队列1的子qdisc
  dropped 1523                          ← ★发包侧丢包计数：队列满丢的
```

发包侧丢包就发生在这里：`dropped` 计数 = qdisc 队列满时被丢的包。它与收包侧丢包的语义完全不同——**收包丢是"来太快"，发包丢是"发不出去"**：驱动来不及把包挂上 TX ring（ring 满或锁竞争），qdisc 队列被撑爆。`requeues` 字段也值得关注：包被重新排队的次数异常增长，说明驱动层在反复拒绝接收（NETDEV_TX_BUSY），是 TX ring 深度不足或完成中断不及时的信号。

## <span class="blue"> 多核锁竞争：发包侧的核心矛盾

单队列网卡时代，所有 CPU 发的包都要过同一个 qdisc 锁和同一个 TX ring 锁。竞争在 perf 里的形态非常典型：

```
perf top -g -- sleep 30
```

```
  18.2%  [kernel]  [k] _raw_spin_lock
          ├─ 71.3% dev_queue_xmit
          │          └─ ip_finish_output ...
  ...
```

`_raw_spin_lock` 吃掉 18% 的 CPU 且调用链指向 `dev_queue_xmit`——这就是锁竞争的确定性证据。**业务表现为：单线程发包能打 400Mbps，四个线程并发发包只有 900Mbps 而不是 1600Mbps**——核数翻倍吞吐不涨，CPU 全耗在互相等待上。

消解法是给每个核发一条独立的"跑道"，这就是多队列的两个层次：

**第一层：硬件多队列（MQ）。** 现代 MAC 有多个独立的 TX 队列，每个队列有自己的 ring 和中断。查与调：

```
ethtool -l eth0                 # 查通道数
```

```
Channel parameters for eth0:
Pre-set maximums:  Combined: 4
Current hardware settings:  Combined: 2    ← 4个队列只用了2个
```

```
ethtool -L eth0 combined 4      # 开满
```

`mq` qdisc 会自动给每个 TX 队列挂独立子 qdisc——锁从"全局一把"变成"每队列一把"。

**第二层：XPS（Transmit Packet Steering）。** 硬件队列多了，但**哪个 CPU 的包进哪个队列**还需要策略——随机分配会让同一连接的包从不同队列出去导致乱序，也让锁保护失效。XPS 把 CPU 与 TX 队列显式绑定：

```
cat /sys/class/net/eth0/queues/tx-0/xps_cpus     # 当前绑定（位图）
echo 1 > /sys/class/net/eth0/queues/tx-0/xps_cpus    # tx-0 绑 CPU0
echo 2 > /sys/class/net/eth0/queues/tx-1/xps_cpus    # tx-1 绑 CPU1
echo 4 > /sys/class/net/eth0/queues/tx-2/xps_cpus    # tx-2 绑 CPU2
echo 8 > /sys/class/net/eth0/queues/tx-3/xps_cpus    # tx-3 绑 CPU3
```

绑定后每个 CPU 固定走自己的队列：同连接的包同队列（保序）、锁只在单核内竞争（≈无竞争）。绑定的对照实验很容易做——绑之前四线程 900Mbps + spinlock 18%，绑之后 1500Mbps+ 且 spinlock 跌出热点榜。

### 实操实验：锁竞争从确诊到摊平

把上面两件事按真实顺序做一遍。场景：四核 SoC（RK3568 级），千兆口，四个 iperf3 并发流。

**第一步，基线与确诊（2 分钟）。**

```
iperf3 -c <对端> -P 4 -t 30        # 4并发流打30秒
```

```
[SUM]   0.00-30.00 sec  3.12 GBytes   894 Mbits/sec   ← 四流合计894M，未打满
```

同时另一个终端：

```
perf top -g
```

```
  16.8%  [kernel]  [k] _raw_spin_lock          ← 锁热点指向dev_queue_xmit，确诊
```

**第二步，开满队列（30 秒）。**

```
ethtool -l eth0                    # Pre-set: Combined 4；Current: Combined 1
ethtool -L eth0 combined 4
tc -s qdisc show dev eth0 | grep fq_codel    # 确认mq下挂出4个子qdisc
```

重打流：1030Mbps。涨了 15%——锁摊开了但 CPU→队列映射还是随机的，仍有竞争与乱序重排开销。

**第三步，XPS 绑核（1 分钟）。** 把四个 tx 队列绑到四个核（位图 1/2/4/8 对应 CPU0~3）：

```
for i in 0 1 2 3; do echo $((1<<i)) > /sys/class/net/eth0/queues/tx-$i/xps_cpus; done
```

重打流：941Mbps 单流上限不再存在，四流合计 1503Mbps，perf 里 spinlock 跌到 2% 以下。**从 894 到 1503，总共三条命令，但每一步都有量化证据支撑**——先确诊（perf）、再摊锁（-L）、再定映射（XPS），顺序反过来（先绑 XPS 再开队列）也能到终点，但中间无法归因哪一步带来多少收益。

**注意持久化问题：** 以上 ethtool/sysfs 配置重启即失效，量产要落到 systemd unit、udev rule 或 rc.local 里——这是调优类配置的共同归宿，26.8 案例里会给完整形态。

> 💡 XPS 是发包侧的亲和性，收包侧的对应物是 RSS/RPS（14.6.1 的机制、26.2 实操里已见过中断绑核）。高配性能的场景两侧都要绑，且**收发队列绑同一组核**——包在同一个核上进进出出，cache 局部性最好。

## <span class="blue"> tx timeout：发包侧的典型硬件故障

`dmesg` 里这行是发包侧独有的告警：

```
------------[ cut here ]------------
NETDEV WATCHDOG: eth0 (stmmac): transmit queue 0 timed out
```

机理：驱动把包挂上 TX ring 后启动一个看门狗计时器（默认 5 秒），等待 MAC 的发送完成中断来回收描述符。**超时意味着包发出去了（或没发出去）但完成中断始终没来**——TX 队列被卡死，之后的包全部堆在 qdisc 里，网络表现为"突然完全断流几秒，然后恢复"（驱动 watchdog 复位了整个网口）。

分诊路径按出现频率排序：

1. **完成中断丢失/粘连**：中断合并参数过激（`ethtool -c eth0` 看 tx-coalesce），或中断亲和性把完成中断绑到了一个被打满的核。先 `ethtool -C` 放宽合并、换绑核验证；
2. **TX ring 深度不足 + 突发**：bursty 流量下 ring 长期满载，`ethtool -G eth0 tx 512` 加深验证；
3. **MAC/PHY 层卡住**：RGMII 时序边缘问题（26.1 的 phy-mode）或 PHY 流控（pause frame）被对方狂发——`ethtool -a eth0` 看流控状态，`ethtool -S` 里找 pause 相关计数；
4. **驱动 bug**：上述都排除后，升级/降级内核版本对比——stmmac、fec 等常见驱动历史上都有真实的 tx timeout 修复 commit。

> ⚠️ tx timeout 的"几分钟后自愈"极具迷惑性——watchdog 复位网口后流量恢复，问题看似消失，但复位期间业务是全断的。工业现场把这类故障报成"偶发断网"，根因链要追到 watchdog 那一行才算到头。

## <span class="blue"> TC 的位置：限速与整形

qdisc 这层除了排队，还是流量控制（Traffic Control）的挂载点。两个高频用途知道存在即可（具体配置属于部署运维范畴）：

**限速/整形**：`tbf`（令牌桶限速）、`htb`（分层带宽分配）挂在出方向，把某个口的流量限制在指定速率——产品上做"管理口限速保业务口"就是这类配置。

**mqprio 与 TSN**：多队列设备可以用 `mqprio` qdisc 把不同优先级的流量映射到不同硬件队列——这是 TSN（时间敏感网络）流量整形的软件接口，工业场景（第 27 章）会用到。

记住架构事实就够了：**TC 只作用于发包方向（egress）**，收包方向的"限速"只能丢包不能排队（ingress 只有简单 policer）。这就是为什么 QoS 方案都建立在出口整形上。

## <span class="blue"> 本节总结

发包旅程六站，核心矛盾是多核竞争而不是速度。qdisc 是协议栈与驱动之间的排队层，`tc -s qdisc` 的 dropped/requeues 是发包侧丢包与拥塞的直接读数。锁竞争的证据链是"perf 里 _raw_spin_lock 热点指向 dev_queue_xmit + 核数翻倍吞吐不涨"，消解靠两层：MQ 把锁摊到每队列一把（ethtool -l/-L），XPS 把 CPU 与队列显式绑定（xps_cpus 位图）保序又去竞争。tx timeout 是发包侧最典型的硬件级故障——完成中断没到、watchdog 复位网口，"偶发断网自愈"的现场报告要追到这一行 dmesg。TC 挂在 qdisc 上做出口整形，mqprio 是通往 TSN 的接口。

**关键结论速查：**

| 问题 | 答案 |
|------|------|
| 发包侧核心矛盾 | 多核锁竞争，不是速度不够 |
| 发包丢包在哪看 | `tc -s qdisc` 的 dropped/requeues |
| 锁竞争证据 | perf top：_raw_spin_lock ← dev_queue_xmit |
| 第一层消解 | MQ：`ethtool -l` 查 `-L` 开满 |
| 第二层消解 | XPS：`queues/tx-N/xps_cpus` 绑核，保序+去竞争 |
| tx timeout 含义 | 完成中断 5 秒未到，watchdog 复位网口 |
| tx timeout 首查 | 中断合并参数 → 亲和性 → ring 深度 → 流控 |
| TC 的作用方向 | 只在 egress 整形，ingress 只能丢 |
