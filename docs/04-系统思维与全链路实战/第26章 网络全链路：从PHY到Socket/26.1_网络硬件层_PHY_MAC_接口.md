# 26.1 网络硬件层：PHY/MAC/接口

> 所属章节：第26章 网络全链路：从PHY到Socket
>
> 难度：[M] ~ [E] | 预计阅读时间：40 分钟

## <span class="blue"> 本节导读

第 14 章把内核网络栈的机制讲透了，但那是从 sk_buff 开始的故事——包"已经在内存里"之后的事。本章补上前半段：包还在网线上的时候发生了什么。这段硬件旅程决定了太多软件层解释不了的现象：link 灯亮了但 ping 不通、协商成千兆实测只有百兆、换了个 PHY 芯片驱动就不工作——这些问题的答案都不在内核里，在 PHY 和 MAC 之间的那几毫米走线上。

本节先把硬件通路讲清楚（PHY 和 MAC 各干什么、为什么 PHY 通常是外挂芯片），再落到接口选型（RGMII/SGMII 的取舍）和两件实操工具（MDIO 寄存器读写、ethtool 链路诊断），最后给硬件层的三个经典故障画像。本节覆盖：

- 一个包在硬件层的旅程：RJ45 → PHY → MAC → DMA → DDR
- PHY 与 MAC 的分工：模拟与数字的边界
- MAC-PHY 接口选型：MII/RMII/RGMII/SGMII 的对比与决策
- 交换芯片与 DSA：多网口设备的硬件形态
- 硬件时间戳：PTP 的物理基础
- MDIO 实操：直接读 PHY 寄存器定位链路问题
- ethtool 链路诊断：协商结果、速率、双工、统计
- 硬件层三个经典故障：link 不上、link 上了不通、千兆掉百兆

## <span class="blue"> 硬件通路：一个包进内存之前

包在到达内核协议栈之前，先走过这条路：

```
网线（RJ45，变压器隔离）
   │  差分模拟信号（1000BASE-T 是四对双绞线上的 PAM-5 编码）
   ▼
PHY 芯片 ──── 模数转换、均衡、时钟恢复、解码 ───▶ 数字比特流
   │                                              （同时完成链路协商、线缆诊断）
   │  MAC-PHY 接口（RGMII/SGMII/...）
   ▼
MAC（通常集成在 SoC 里）── 帧校验（CRC）、地址过滤、时间戳 ──▶
   │  DMA
   ▼
DDR：ring buffer 描述符指向的一块块内存 —— 到这里，第 14 章的故事才开始
```

> PHY：物理层收发器。负责把数字比特变成网线上的模拟电信号（发送），以及反向的采样、均衡、解码（接收）。它还负责链路协商（和对方 PHY 商量速率/双工）、链路状态检测（插拔）、线缆诊断（TDR 测断点）。PHY 是一块"小模拟芯片+状态机"，内部有几十个可读写寄存器，软件通过 MDIO 总线访问它们。

<!-- -->

> MAC：介质访问控制器。负责以太网帧层面的工作：帧的封装/解封、CRC 校验、MAC 地址过滤、DMA 搬运、硬件时间戳。现代 SoC 基本内置 MAC（常叫 GMAC/EMAC），外挂 MAC 只出现在特殊场景。

<!-- -->

> MDIO：MAC 和 PHY 之间的管理总线（两根线：MDC 时钟 + MDIO 数据），类似 I2C 的地位。它不传网络数据，只传寄存器读写——"PHY 现在 link 状态如何""协商到什么速率""强制百兆模式"都走这条路。

整条通路上软件能看见的界面有三个：PHY 的 MDIO 寄存器（硬件状态）、MAC 驱动暴露的 ethtool 接口（协商与统计）、DMA ring buffer 的描述符（26.2 展开）。本节管前两个。

## <span class="blue"> 为什么 PHY 通常外挂

SoC 里集成了 MAC，却很少集成 PHY——PHY 几乎总是板子上 RJ45 连接器旁边那颗独立小芯片。原因不是技术做不到，是工程上不划算：

**模拟信号怕走线。** 网线上跑的是对噪声敏感的模拟差分信号，PHY 内部的 ADC/驱动器也是模拟电路。把 PHY 集成进 SoC，意味着 SoC 要内置模拟前端——数字工艺做模拟电路性能差、面积大，还要给芯片引入模拟电源域。外挂 PHY 用成熟的混合信号工艺，性能好且便宜。

**位置必须靠近连接器。** 从连接器到 PHY 的模拟走线越短，EMI 风险越低、信号完整性越好——所以 PHY 永远贴着 RJ45 放。而 SoC 的位置由整板布局决定，两者很难兼得。

**PHY 是选型件，MAC 不是。** 工业要宽温 PHY、车载要车载 PHY、千兆和百兆的成本差好几倍——PHY 随产品定义走，集成进 SoC 就失去了这个灵活性。

对软件工程师的实际推论：**"网口不通"的故障域天然分成两半**——PHY 之前（线缆、连接器、变压器、PHY 芯片本身）和 PHY 之后（MAC-PHY 接口、MAC 驱动、DMA）。MDIO 就是这两个故障域的分界线：MDIO 能读到 PHY 寄存器，说明 PHY 活了，问题在之后；读不到，问题在 PHY 本身或更靠外。

## <span class="blue"> MAC-PHY 接口：四代的取舍

MAC 和 PHY 之间的数字接口是选型时的一个重要决策，四个主流选项：

| 接口 | 速率上限 | 信号线数 | 时钟 | 典型场景 |
|------|----------|----------|------|----------|
| MII | 100M | 16 | 25MHz | 老设计，教学价值为主 |
| RMII | 100M | 7 | 50MHz 单时钟 | 低引脚数 MCU/小 SoC，百兆产品 |
| RGMII | 1000M | 12 | 125MHz DDR | **当前嵌入式千兆的主流** |
| SGMII | 1000M | 2（一对差分） | 内嵌时钟 SerDes | 板级走线长、多网口、接交换机芯片 |

**RGMII 是当前的主流选择，但它有一个著名的坑：延迟补偿。** RGMII 用 DDR（双沿采样）在 125MHz 时钟上传 4bit 数据，时钟与数据之间的建立/保持时间窗口很小，规范要求时钟相对数据有约 2ns 的延迟。这个延迟有三种实现方式：PCB 走线加长（老做法）、PHY 内部加延迟（`rgmii-id` 模式，主流做法）、MAC 内部加延迟。设备树里 `phy-mode` 属性的四个值（`rgmii` / `rgmii-id` / `rgmii-rxid` / `rgmii-txid`）就是在声明"延迟由谁加、加在哪个方向"：

- `rgmii`：谁也不加（PCB 走线补偿，几乎绝迹）；
- `rgmii-id`：PHY 收发两个方向都加延迟（最常见）；
- `rgmii-rxid` / `rgmii-txid`：PHY 只加接收/发送方向。

**声明错一个字母，症状就是"link 正常、协商千兆、但 ping 丢包率 30%"**——这是 RGMII 板卡 bring-up 的第一经典故障，本节末尾展开。

**SGMII 是走 SerDes 的路线**：MAC-PHY 之间用一对差分线串行传输，时钟内嵌。引脚省、走线距离容忍大、可以穿连接器到子卡——多网口设备（交换机、网关）和子卡形态（你熟悉的 PCIe 卡场景同理）几乎都走 SGMII 或更高速的 SerDes 变体。软件上 SGMII 还引入 in-band 协商（链路状态通过数据流本身传递），设备树里写法与 RGMII 不同。

选型的决策逻辑很朴素：百兆产品且引脚紧张选 RMII；千兆单网口贴板 PHY 选 RGMII；千兆多网口、走线长、或接交换芯片选 SGMII。

## <span class="blue"> 交换芯片与 DSA：多网口设备的硬件形态

单网口产品之外的常见形态是**外挂交换芯片**（Marvell 88E6xxx、Microchip KSZ 系列等）：SoC 的一个 MAC 通过 RGMII/SGMII 接交换芯片，交换芯片再分出 4~8 个对外网口。包在交换芯片内部按 MAC 表直接转发，只有发给本机的包才上行给 SoC——所以网口数量不等于 MAC 数量。

> DSA（Distributed Switch Architecture）：Linux 对这类交换芯片的标准支持框架。它给交换芯片的每个对外口生成一个独立 netdev（`lan1`、`lan2`…），交换芯片的转发表通过 switchdev 机制与内核桥接同步。用户看到的效果：每个物理口都能独立配置 IP/VLAN，而硬件转发不经过 CPU。

实操上 DSA 暴露两个关键界面：`ip link` 看到的 lanX 口是"软件视角的口"，真正的转发硬件状态要用 `bridge fdb show`（转发表）和交换芯片的 ethtool 统计看。诊断"两个 lan 口之间转发不通"时，第一查就是 fdb 表项学没学到——学到的转发是硬件做的，CPU 抓包都看不见；没学到才是协议栈的事。

## <span class="blue"> 硬件时间戳：PHY 和 MAC 里的时钟

工控和机器人场景会用到 PTP（IEEE 1588 精密时间协议，亚微秒级对时），它依赖硬件时间戳：包发出/到达的瞬间由 PHY 或 MAC 里的硬件时钟直接盖戳，绕开协议栈延迟。查询本机支持程度：

```
ethtool -T eth0
```

```
Time stamping parameters for eth0:
Capabilities:
        hardware-transmit     (SOF_TIMESTAMPING_TX_HARDWARE)
        hardware-receive      (SOF_TIMESTAMPING_RX_HARDWARE)
        ...
PTP Hardware Clock: 0          ← 有一个PHC硬件时钟，编号0
```

`PTP Hardware Clock: -1` 意味着这颗 MAC/PHY 不支持硬件时间戳——PTP 就只能退化为软件时间戳（精度从亚微秒掉到几十微秒）。这个差异在 26.8 的工业网关案例里会用到：确定性方案的第一步就是确认时间戳在哪一层盖。

## <span class="blue"> MDIO 实操：直接读 PHY 的寄存器

内核提供了直接读写 PHY 寄存器的通道，工具是 `phytool`（Buildroot：`BR2_PACKAGE_PHYTOOL`）或部分驱动的 debugfs。最常用的三个寄存器：

```
phytool read eth0/0/2        # 寄存器2+3：PHY ID（厂商/型号），确认PHY活了
phytool read eth0/0/1        # 寄存器1：状态——bit2=link up，bit5=协商完成
phytool read eth0/0/0        # 寄存器0：控制——bit12=自协商使能，bit9=重启协商
```

读 ID 寄存器的典型输出：

```
phytool read eth0/0/2
0x001c          ← 结合寄存器3算出OUI，对照 datasheet 确认是料单上那颗 PHY
phytool read eth0/0/1
0x796d          ← bit2=1（link up）、bit5=1（协商完成）、bit1=1（jabber...）
```

`eth0/0/2` 的三段是"接口/MDIO 总线号/寄存器地址"。这套读写绕过了驱动的所有抽象——**驱动层报告的一切链路信息，源头都是这些寄存器的某几个 bit**。当你怀疑驱动 bug 或想确认真相时，直接读寄存器就是终审判决。

> 💡 有些平台 MDIO 挂在独立总线上，不跟网口走，比如 `mdio_bus stmmac-0: MDIO device at address 0 is missing` 这类启动日志。找不到 PHY 时先 `ls /sys/bus/mdio_bus/devices/` 看 MDIO 总线上到底扫到了什么。

## <span class="blue"> ethtool 链路诊断

ethtool 是链路层的瑞士军刀，bring-up 和现场诊断的第一站。基础输出逐字段读：

```
ethtool eth0
```

```
Settings for eth0:
        Supported ports: [ TP MII ]                    ← 支持的介质类型
        Supported link modes:   10baseT/Half ... 1000baseT/Full   ← 本端能力
        Supports auto-negotiation: Yes
        Advertised link modes:  10baseT/Half ... 1000baseT/Full   ← 我方广播的能力
        Link partner advertised link modes:  10baseT/Half 100baseT/Full  ← 对方能力
        Speed: 100Mb/s                                  ← ★协商结果：千兆掉成了百兆
        Duplex: Full
        Auto-negotiation: on
        Link detected: yes
```

上面这份输出直接定位了一个真实故障：`Link partner advertised` 只有百兆——对端只广播了百兆能力。千兆需要四对双绞线全部连通，百兆只用两对，**"千兆掉百兆"的最常见原因就是线缆/水晶头有两对没通**（或对方设备本身就是百兆口）。一行输出完成定位。

常用子命令速查：

```
ethtool -i eth0        # 驱动名/版本/固件——确认MAC驱动身份
ethtool -S eth0        # 硬件统计计数器（26.2 丢包排查的主战场）
ethtool -a eth0        # 流控（pause frame）状态——偶发卡顿的嫌疑犯之一
ethtool -k eth0        # 卸载特性开关状态（TSO/GSO/GRO，26.6 吞吐优化用）
ethtool --cable-test eth0   # PHY线缆诊断（TDR）：能报出大约几米处断线/短路
```

`--cable-test` 值得单独说：PHY 往线缆里发脉冲、测反射，能报出"open at 23m"这种级别的诊断——现场"网线在哪断的"以前要拿寻线仪爬天花板，现在一条命令出答案（PHY 需支持 TDR，千兆 PHY 基本都支持）。

## <span class="blue"> 硬件层三个经典故障

**故障一：link 不上（Link detected: no）。** 分诊顺序：① `phytool read eth0/0/1` 的 bit2——读不到值（MDIO 都不通），查 PHY 供电、复位时序、MDIO 总线配置（设备树 phy-handle 指向、MDIO 地址）；② MDIO 通但 link bit=0，查线缆/对端/变压器；③ 对端强制了固定速率而本端自协商——两边协商策略不匹配时 link 表现为"时好时坏"，把两端都改回自协商或都强制同参数。

**故障二：link 上了但不通（就是 RGMII 延迟坑）。** 特征组合非常固定：link up、协商千兆、能收到少量包但大量丢包/CRC 错（`ethtool -S eth0` 里 rx_crc_errors 疯涨）。分诊：换百兆强制模式测试（`ethtool -s eth0 speed 100 autoneg off`）——百兆下正常而千兆丢包，几乎确诊 RGMII 时序问题。修复：设备树 `phy-mode` 在四个 rgmii 变体间轮换验证，或查 PHY 驱动是否正确实现了延迟配置（有些 PHY 驱动忽略 phy-mode 里的延迟位，是真实存在的驱动 bug 类别）。

**故障三：千兆掉百兆。** 前面 ethtool 输出已演示：看 `Link partner advertised`，对方没广播千兆 → 查线缆四对通不通（`--cable-test`）、水晶头质量、中间经过的面板/模块。对方广播了千兆但协商结果百兆 → 查本端线缆质量或 PHY 的 EEE（节能以太网）兼容性问题（少数 PHY 组合下 EEE 导致协商降级，关掉 EEE 验证：`ethtool --set-eee eth0 eee off`）。

## <span class="blue"> 本节总结

包进内存之前要过 PHY（模拟世界与链路协商）、MAC-PHY 接口（数字搬运）、MAC（帧处理与 DMA）三站。PHY 外挂是模拟工艺、布局位置、选型灵活性三个工程因素的结果，由此得到故障域的分界线：MDIO 通不通是"PHY 活了没有"的终审。接口选型的主流是 RGMII（千兆贴板）和 SGMII（多口/长距/SerDes），RGMII 的 phy-mode 延迟声明是 bring-up 第一坑——"link 正常但 CRC 疯涨"就是它。工具上，phytool 读寄存器给真相，ethtool 给协商结果与统计，`--cable-test` 把线缆诊断变成了软件功能。

**关键结论速查：**

| 问题 | 答案 |
|------|------|
| PHY/MAC 分工 | PHY=模拟收发+协商+诊断，MAC=帧处理+DMA+时间戳 |
| PHY 为什么外挂 | 模拟工艺差、必须贴连接器、PHY 是选型件 |
| 故障域分界线 | MDIO 能读 = PHY 活了，问题在 MAC 侧；读不到 = PHY 及以外 |
| 千兆主流接口 | RGMII（12 线 DDR，注意 phy-mode 四变体） |
| 多口/长距接口 | SGMII（一对差分 SerDes，in-band 协商） |
| link 不上第一查 | `phytool read eth0/0/1` 的 bit2 |
| link 上但不通 | 强制百兆验证 → phy-mode 延迟配置 |
| 千兆掉百兆 | 看 Link partner advertised + `--cable-test` |

1. MDIO 总线传不传网络数据？这个属性为什么让它成为故障域的分界线？

3. `ethtool` 输出里 `Link partner advertised` 只有百兆，最可能的两个根因是什么？分别怎么验证？
