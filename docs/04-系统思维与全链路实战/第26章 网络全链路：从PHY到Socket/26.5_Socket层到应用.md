# 26.5 Socket 层到应用

> 所属章节：第26章 网络全链路：从PHY到Socket
>
> 难度：[E] | 预计阅读时间：40 分钟

## <span class="blue"> 本节导读

包走完协议栈，到达最后一站：socket 接收队列。这是内核与应用的交接面，也是一类经典扯皮故障的边界——**应用说"没收到包"，内核说"我收到了"，两边都对**：包确实到了内核，但应用在队列满之前没来得及取，包被丢了。这类故障在抓包时呈现出极强的迷惑性：tcpdump 明明抓到了，应用日志却一片空白。

本节把这个交接面讲透：socket 的队列结构、UDP 与 TCP 在"应用读太慢"时的两种截然不同的行为、listen backlog 与连接建立失败的关系、以及应用侧的取包节奏优化。本节覆盖：

- socket 接收队列：buffer 的语义与观测
- UDP vs TCP：读太慢时的丢包与流控两种形态
- listen backlog：连接建立慢/失败的队列根源
- 应用侧取包节奏：批处理与 busy polling
- epoll 两个经典踩坑：ET 没读干净、慢连接拖累事件循环
- 扯皮定位法：用 tcpdump 的位置属性切分责任域

> 💡 socket 参数的完整清单（14.3.3 已系统讲过调参大全），本节只讲与"交接面故障"直接相关的几个，重点在行为观测而非参数罗列。

## <span class="blue"> 接收队列：内核替应用囤包的地方

socket 接收队列的本质是一层缓冲：协议栈把包放进队列，应用按自己的节奏取。**队列深度 = rcvbuf 上限 ÷ 每包大小**——它吸收的是"应用短暂卡顿"的抖动，但改变不了长期速率差。

> sk_rcvbuf：socket 接收缓冲区的字节数上限。每个 socket 独立，创建时继承系统默认值（`net.core.rmem_default`），可被 `SO_RCVBUF` 调高但受 `net.core.rmem_max` 封顶。注意内核实际给的是设置值的两倍（内部记账开销），`ss -m` 里看到的就是翻倍后的。

观测当前各 socket 的队列占用：

```
ss -umap | head -20          # UDP：看每个socket的队列
```

```
UNCONN 0       0      192.168.1.10:5000   *:*    
         skmem:(r524288,rb524288,t212992,tb212992,f0,w0,o0,bl0,d15360)
```

关键字段在括号里：`rb524288` 是 rcvbuf 上限（512KB），`r524288` 是**当前已占用**——r 贴近 rb 就是队列即将撑满；末尾 `d15360` 是这个 socket 已经丢了多少包（drop 计数）。**一行读数同时回答了"离满还差多远"和"已经丢了多少"。**

调 buf 的姿势（14.3.3 有完整参数谱系）：

```c
int bufsize = 4 * 1024 * 1024;                     /* 想要4MB */
setsockopt(fd, SOL_SOCKET, SO_RCVBUF, &bufsize, sizeof(bufsize));
int actual; socklen_t len = sizeof(actual);
getsockopt(fd, SOL_SOCKET, SO_RCVBUF, &actual, &len);
printf("actual rcvbuf: %d\n", actual);             /* 必须读回：被rmem_max封顶时是封顶值 */
```

读回检查的理由与 25.2 的 S_FMT 相同：SO_RCVBUF 是协商不是命令，超过 `net.core.rmem_max` 会被静默截断（需要突破封顶时要么调 sysctl，要么用特权 socket 的 `SO_RCVBUFFORCE`）。

## <span class="blue"> 应用读太慢：UDP 丢包，TCP 减速

"应用消费速度 < 到达速度"时，两个协议的行为完全不同——这是排查时最重要的分野：

**UDP：直接丢。** 队列满即丢，计数在 `UdpRcvbufErrors`（26.2 的丢包位置三）。UDP 没有任何机制通知对端"我慢了"，发端继续全速发，收端继续丢——**丢包率直接等于速率差**。应用层的典型画像：抓包看对端发了 10000 个包，应用只读到 6000 个，`nstat` 里 RcvbufErrors 差值正好 4000。

**TCP：不丢包，但对端被"勒住"。** 接收队列满时，TCP 把接收窗口（rwnd）通告为零，对端协议栈收到零窗口后停止发送，进入定期探测。**包不丢，但吞吐崩了、延迟涨了**——`ss -i` 能看到这个状态：

```
ss -ti dst 192.168.1.20
```

```
tcp   ESTAB  ...  rwnd:0 ...                    ← 本端接收窗口已关为零
    lastsnd:12340 lastrcv:12340 ...             ← 12秒没有数据动作
```

排查分野一句话：**UDP 的问题看丢包计数，TCP 的问题看窗口**——同样症状（业务吞吐低），一个查 `nstat`，一个查 `ss -i` 的 rwnd，别串。

无论 UDP 还是 TCP，根治都在应用侧：取包线程别干重活（取到就扔给处理线程，参考 25.2 采集循环的同一哲学）、批处理取包（见下文）、必要时调大 rcvbuf 增加抖动吸收。

## <span class="blue"> listen backlog：连接建立慢的队列根源

TCP 服务端还有另一条队列容易出事：**已完成三次握手、等应用 accept() 的连接队列**（accept queue），深度由 `listen(fd, backlog)` 的 backlog 参数和 `net.core.somaxconn` 共同决定（生效值 = min(backlog, somaxconn)）。

> accept queue：已完成握手、等待 accept 的连接队列。溢出时内核默认直接丢 SYN-ACK 后的 ACK——客户端表现是 connect 超时或极慢。这是"连接建立慢"故障在内核侧的头号嫌疑。

观测溢出的直接读数：

```
ss -ltn
```

```
State    Recv-Q   Send-Q   Local Address:Port
LISTEN   129      128      0.0.0.0:8080        ← ★Recv-Q=129 超过 Send-Q=128
```

LISTEN 状态下这两个字段的语义变了：Send-Q 是 backlog 上限，Recv-Q 是**当前排队等 accept 的连接数**。Recv-Q 顶到或超过 Send-Q，溢出正在发生。累计统计看：

```
nstat -az | grep -iE "ListenOverflows|ListenDrops"
```

```
TcpExtListenOverflows    8923        ← accept队列溢出次数
TcpExtListenDrops        8910        ← 因此被丢的连接
```

治理三层，按序：应用把 accept 提到高优先级线程（别让业务逻辑堵了 accept 循环）→ 调大 listen backlog 参数和 `net.core.somaxconn`（很多发行版默认 128，对高并发服务太小）→ 突发 SYN 洪峰场景确认 `net.ipv4.tcp_syncookies=1`（SYN cookie 让半连接不占队列）。连接建立慢的另一个常见嫌疑犯 DNS 解析在应用层（`getaddrinfo` 阻塞），用 `strace -c` 或打点区分。

## <span class="blue"> 应用侧取包节奏：批处理与 busy polling

应用从队列取包的效率直接决定队列会不会满。三个层级的取法，开销递减：

**基准：每包一次 recvmsg。** 每取一个包一次系统调用——小包高 pps 场景下 syscall 开销本身就成为瓶颈（26.6 的决策树里"CPU 100% 在 syscall"就是它）。

**批处理：recvmmsg/sendmmsg。** 一次系统调用取/发一批包（最多 VLEN 个）：

```c
struct mmsghdr msgs[16];                           /* 一次最多收16个包 */
struct iovec iovecs[16];
char bufs[16][2048];
/* ……填充 iovec 指向 bufs…… */
int n = recvmmsg(fd, msgs, 16, MSG_DONTWAIT, NULL); /* 一次syscall取走一批 */
for (int i = 0; i < n; i++)
    process(bufs[i], msgs[i].msg_len);              /* 用户态逐包处理 */
```

syscall 次数降为 1/16，小包场景的吞吐提升立竿见影。

**极限：SO_BUSY_POLL。** 取包前先在驱动层"原地空转"轮询 NAPI，包一到立刻取走——省掉"中断→softirq→唤醒进程"的整条调度路径（这条路径正是 26.8 工业网关抖动的主因）：

```c
int busy_us = 50;                                  /* 轮询50μs */
setsockopt(fd, SOL_SOCKET, SO_BUSY_POLL, &busy_us, sizeof(busy_us));
```

代价明明白白：轮询期间这个核 100% 占用（空转烧电），所以它只属于"延迟比功耗重要"的场景。26.8 会给出它在确定性方案里的精确位置。

## <span class="blue"> epoll 的两个经典踩坑

多连接服务的取包循环基本都架在 epoll 上，两个坑的出现频率高到值得单独列出。

**坑一：EPOLLET（边沿触发）下没把数据读干净。** 边沿触发的语义是"状态变化时通知一次"——socket 从"无数据"变"有数据"通知一次，此后**队列里剩多少都不再通知**。如果事件到来时只 `recv` 一次就返回，队列里剩余的数据可能永远等不到下一次通知：表现为"连接偶发假死，新包来了才复活"。正确姿势是循环读到 EAGAIN：

```c
/* EPOLLET模式：必须把队列读空 */
for (;;) {
    int n = recv(fd, buf, sizeof(buf), MSG_DONTWAIT);
    if (n > 0) { process(buf, n); continue; }
    if (n < 0 && (errno == EAGAIN || errno == EWOULDBLOCK)) break;  /* 读干净了 */
    if (n == 0 || (n < 0 && errno != EINTR)) { close_conn(fd); break; }
}
```

水平触发（默认模式）没有这个问题——只要队列里有数据就反复通知——但代价是每次 epoll_wait 都要重新检查所有就绪 fd。**规则很简单：用 ET 就必须读到 EAGAIN，不想读空就用 LT。** 选 ET 的理由是极端高并发下的通知效率，大多数嵌入式服务用 LT 的代价完全可忽略。

**坑二：一个慢连接拖累全部。** epoll 循环里如果在事件回调中做了重活（比如收到数据后顺手做 200ms 的算法处理），这期间其他 socket 的读事件全部排队——队列在涨、延迟在抖。这正是 25.2/26.2 反复出现的同一模式在应用层的重演：**事件循环里只做"取数据、扔队列"，处理永远在线程池**。自查信号：业务日志里各连接的处理时间正常，但 socket 队列占用（ss 的 r 值）周期性顶高——说明积压发生在取包之前。

## <span class="blue"> 扯皮定位法：tcpdump 站在哪

回到开头的扯皮场景："应用没收到，网络说发了"。定位的关键是知道 **tcpdump 的抓包点在哪**：它挂在驱动收包之后、协议栈 Netfilter 之前的位置（AF_PACKET 探针）。于是：

- **tcpdump 抓不到** → 包没进协议栈：往前查 26.2 的位置一（MAC/ring 丢包）或 26.1 的链路层；
- **tcpdump 抓到、应用没收到** → 包进了栈但没到应用：查 Netfilter 规则丢包（26.4 的 nftrace）、socket 队列满丢包（本节的 ss/nstat）、应用过滤条件错误（绑错端口/地址）。

这个二分法把"网络还是应用"的无限扯皮压缩成一条命令的判断。注意一个进阶细节：tcpdump 抓的是**镜像**，它抓到不代表包被投递——包完全可能在 tcpdump 镜像之后的 Netfilter 阶段被丢。所以"抓到了"只是排除前半段，后半段要靠 nstat 和 nftrace 收尾。

## <span class="blue"> 本节总结

socket 接收队列是内核替应用囤包的最后缓冲，`ss` 输出里 r/rb/d 三个字段同时回答"离满多远、丢了多少"。应用读太慢时 UDP 丢包（UdpRcvbufErrors）、TCP 关窗（rwnd=0）——排查分野是"UDP 看丢包计数，TCP 看 ss -i 窗口"。listen backlog 溢出（ss -ltn 的 Recv-Q 顶 Send-Q、ListenOverflows 增长）是连接建立慢的内核侧首犯，治理顺序是 accept 提优→调 backlog/somaxconn→确认 syncookies。取包节奏三级：recvmsg 基准、recvmmsg 批处理、SO_BUSY_POLL 极限（延迟换功耗）。扯皮定位靠 tcpdump 的位置属性：抓不到查前半段，抓到了用 nstat/nftrace 查后半段。

**关键结论速查：**

| 问题 | 答案 |
|------|------|
| 队列占用与丢包读数 | `ss -umap`：r=已占用，rb=上限，d=已丢 |
| SO_RCVBUF 的坑 | 协商式，受 rmem_max 封顶，必须读回 |
| UDP 读太慢 | 队列满即丢，UdpRcvbufErrors 计数 |
| TCP 读太慢 | rwnd 通告为零，对端停发；`ss -i` 看窗口 |
| 连接建立慢首查 | `ss -ltn` Recv-Q≥Send-Q + ListenOverflows |
| 取包三级 | recvmsg → recvmmsg 批处理 → SO_BUSY_POLL |
| 扯皮二分 | tcpdump 抓不到=前半段；抓到收不到=栈内或队列 |
