# 26.6 端到端延迟与吞吐测量

> 所属章节：第26章 网络全链路：从PHY到Socket
>
> 难度：[E] | 预计阅读时间：45 分钟

## <span class="blue"> 本节导读

前五节把包的路拆成了五段，每段给了观测工具。本节做和第 25.5 节同样的事：**把"网络慢"翻译成数字**——一个包从 PHY 到应用的每一毫秒（其实是微秒）花在哪，怎么测，以及吞吐不达标时按什么顺序分诊。

网络延迟测量比 Camera 链路有一个明显的好处和一个明显的坑。好处：协议栈自带时间戳体系（SO_TIMESTAMPING），测量不用外接示波器。坑：分解表里各段的量级差达到**三个数量级**——PHY 处理按微秒计，调度器段按毫秒计——看不出这一点的人会拿着微秒级的工具去查毫秒级的问题。本节覆盖：

- 每包延迟的六段分解：量级与物理成因
- 分段测量工具箱：SO_TIMESTAMPING、ftrace、cyclictest 各管哪段
- 测量实录：网关延迟尖刺从确认形态到方向移交的四步
- 吞吐分诊决策树：iperf3 不达预期的四条分支完整走查
- 抖动测量：为什么平均值会骗人
- 场景差异：机器人 ROS2/DDS 通信的延迟账

## <span class="blue"> 六段分解：一个包的延迟账

一个包从 PHY 到应用读取，延迟由六段构成（数据来自大纲与实测经验）：

| 段 | 环节 | 典型值 | 优化手段 |
|----|------|--------|----------|
| ① | PHY 处理 | 1~5μs | 无法优化（物理限制） |
| ② | DMA 到内存 | 1~10μs | DMA/PCIe 参数（内嵌 SoC 基本固定） |
| ③ | NAPI 轮询调度 | 0~1ms | budget/中断合并参数 |
| ④ | 协议栈处理 | 5~50μs | XDP 绕过、CPU 亲和性 |
| ⑤ | 调度器唤醒应用线程 | 0~10ms | RT 优先级、CPU 隔离、busy polling |
| ⑥ | 用户空间处理 | 取决于应用 | 批处理、零拷贝 |

内核路径（①~④）合计约 10~100μs；加上 ⑤⑥ 后，端到端完全取决于系统状态。

这张表最刺眼的事实是**③和⑤的量级**：它们的最大值（毫秒级）比其余各段总和（微秒级）大两个数量级，而它们都不是"处理包"的时间——是**等待被调度**的时间。NAPI poll 在等 softirq 被调度，应用线程在等进程调度。这就是大纲案例里那句结论的出处：**确定性延迟的关键不是降低平均延迟，而是消除抖动来源——主要是调度延迟和中断合并。** 26.8 的工业网关案例五步优化，四步打在这两段上。

## <span class="blue"> 分段测量工具箱

### ① ② ③ ④：内核段，SO_TIMESTAMPING + ftrace

socket 时间戳是网络测量的"原生仪器"。开启后，每次 recvmsg 都能拿到包进协议栈时刻的戳（软件戳），支持硬件时间戳的 MAC/PHY（26.1 的 ethtool -T）还能拿到包到达硬件时刻的戳：

```c
int ts = SOF_TIMESTAMPING_RX_SOFTWARE | SOF_TIMESTAMPING_SOFTWARE;
setsockopt(fd, SOL_SOCKET, SO_TIMESTAMPING, &ts, sizeof(ts));
/* recvmsg() 的 msg_control 里会带回时间戳——recvmsg 需要传 msghdr，不能用 recv 简化版 */
```

硬件戳与软件戳的差值 ≈ ②③④的合计（硬件到协议栈的旅程）。要再细分，用 bpftrace/ftrace 量协议栈函数耗时（方法同 26.4 的 nf_hook_slow 测量，换函数名即可，常用 `netif_receive_skb`、`ip_rcv`、`tcp_v4_rcv`）。

### ⑤：调度段，cyclictest + 打点

调度延迟不归网络子系统管，要用调度工具量：cyclictest 给出系统调度延迟的基线分布（第 20 章的工具）：

```
cyclictest -m -p 80 -i 200 -l 100000 --histogram=100
```

应用侧的直接打点同样有效：记录"socket 时间戳（包进栈时刻）"与"应用读到包的时刻"之差，就是 ⑤ 的实测值——**这个差值在负载高峰期的分布，就是抖动的形状**。

### 端到端 RTT 与抖动：ping 的正确用法

ping 不是只能看通不通：

```
ping -i 0.002 -c 5000 -q 192.168.1.20      # 2ms间隔打5000个
```

```
--- 192.168.1.20 ping statistics ---
5000 packets transmitted, 5000 received, 0% packet loss
rtt min/avg/max/mdev = 0.180/0.245/12.430/0.521 ms
                   ↑                        ↑
              平均值很好看              mdev=0.52ms：抖动是均值的两倍
```

**看 ping 输出先看 mdev（标准差）不看 avg**——avg 0.245ms 配合 mdev 0.521ms 意味着大量包远超均值，实时业务感受到的是后者。内网 RTT 的 max 值飙到毫秒级，几乎都对应调度段的尖刺。

## <span class="blue"> 测量实录：一次网关延迟尖刺的分段定位

把工具箱按顺序用一遍。场景：工业网关（四核 A55），业务反映"控制指令偶发延迟 10ms 以上"，平均延迟完全正常。

**第一步，确认抖动形态（5 分钟）。** ping 直打网关 5000 包：

```
rtt min/avg/max/mdev = 0.192/0.261/18.7/0.694 ms
```

avg 正常、max 18.7ms、mdev 是均值两倍多——**这是抖动问题不是延迟问题**，直觉要查的"协议栈优化"直接排除（协议栈段是 μs 级，造不成 18ms 的尖刺）。

**第二步，内核段 vs 调度段切分（15 分钟）。** 网关上加 SO_TIMESTAMPING 打点：硬件戳（这颗 MAC 支持 PHC）到软件戳的差值统计一万包：

```
hw->sw: p50=8μs  p99=41μs  p99.9=380μs        ← 内核段最坏也只有0.4ms
```

内核段的最大值都够不着 18ms 的量级——**尖刺不在内核路径里**。同时应用打点"软件戳→读取时刻"：

```
sw->read: p50=12μs  p99=180μs  p99.9=19.2ms   ← 尖刺在这：应用被调度延迟
```

**第三步，调度段确诊（10 分钟）。** cyclictest 跑基线：

```
cyclictest -m -p 80 -i 200 -l 100000
# Max Latencies: 18523μs                       ← 调度延迟上限18.5ms，与尖刺吻合
```

三个数字互相印证（ping max 18.7、cyclictest max 18.5、打点 p99.9 19.2），证据链闭合：**尖刺全部来自应用线程的调度延迟**。根因是网关没做实时性配置——PREEMPT 普通内核 + 业务线程普通优先级，某次内核长临界区就把 10ms 延迟塞给了它。

**第四步，方向移交。** 到这里网络侧的工作完成了：结论是"去治调度"，治法就是 26.8 案例的五步（PREEMPT_RT、isolcpus、RT 优先级、busy polling）——测量只花四十分钟，但把优化方向从"协议栈调参"（注定无效）掰到了"调度确定性"（正解）。

这个实录再次印证 25.5 的那条方法论：**测量顺序就是排除顺序**。先看分布确认是抖动（第一步），再用时间戳切内核/调度（第二步），最后专业工具钉死（第三步）。四十分钟买到的是"方向不会错"。

## <span class="blue"> 吞吐分诊决策树：iperf3 不达预期

iperf3 实测吞吐低于链路标称（千兆实测 400M、600M 这类），按大纲的决策树走，每个分支配齐验证命令：

```
iperf3 吞吐不达标
    │
    ├─ A. CPU 利用率不高（mpstat 看各核都闲）
    │      → 中断集中在一核？cat /proc/interrupts 看 eth0 各队列分布
    │      → 是：配 RSS/中断亲和性（26.2 实操）/ XPS（26.3 实操）
    │
    ├─ B. CPU 100% 且大头在 %soft
    │      → 协议栈处理是瓶颈
    │      → 查卸载开关：ethtool -k eth0 看 gro/gso/tso 是否 on
    │      → 开满后仍不够：评估 XDP/AF_XDP（26.4 决策边界）
    │
    ├─ C. CPU 100% 且大头在 %sys（syscall）
    │      → 应用层瓶颈：每包一次 syscall
    │      → 批处理 recvmmsg、调大 rcvbuf、零拷贝（26.5）
    │
    └─ D. CPU 和 softirq 都不高
           → 瓶颈不在本机 CPU：查物理链路
           → ethtool -S eth0 看 crc/丢包错包计数（26.1/26.2）
           → ethtool eth0 看协商结果是否掉速（26.1 千兆掉百兆）
           → 对端与中间链路：iperf3 -R 反向测、换直连验证
```

决策树的价值在于**每个分支都有"证伪手段"**：A 分支配完亲和性后重测，没改善就说明分诊错了，退回树根看下一个分支——不要在一个分支里深挖到底。实测中约七成"吞吐不达标"落在 A 和 D：嵌入式平台的中断默认绑核常常不合理（A），物理链路掉速/错包则是最容易被忘记的选项（D）。

## <span class="blue"> 抖动测量：平均值会骗人

吞吐分诊解决"慢"，抖动分诊解决"不稳"。抖动问题的测量原则只有一条：**分布比均值重要**。工具上对应三个层次：

```
# 层次一：ping 的 mdev/max（上文，分钟级上手）
# 层次二：iperf3 UDP 模式的 jitter 报告
iperf3 -c 192.168.1.20 -u -b 100M -t 60
```

```
[  5]  60.0 sec  715 MBytes  100 Mbits/sec  jitter=0.183ms  lost=12/52341 (0.023%)
```

iperf3 UDP 的 jitter 是包间隔偏差的滑动平均——但它仍是均值，看不出尖刺。

```
# 层次三：应用侧打点 + 直方图（分钟级代码，分布级结论）
```

在应用里记录每包"socket 时间戳 vs 读取时刻"的差值，一万个样本画直方图（或直接输出 p50/p99/p99.9）：p99.9 与 p50 的比值是抖动严重度的最直接数字。实时业务的验收指标应该写成"p99.9 < X ms"而不是"平均延迟 < X ms"——**均值验收是抖动问题漏进量产的典型通道**。

## <span class="blue"> 场景差异：机器人 ROS2/DDS 的延迟账

与 25.5 的机器人视觉对比表同构，网络场景下机器人通信的账也不同：

| 维度 | 通用网络服务 | 机器人 ROS2/DDS 通信 |
|------|-------------|---------------------|
| 核心指标 | 吞吐、平均延迟 | 抖动（p99.9）、截止时间满足率 |
| 流量形态 | 连接型、大报文 | 发布订阅、小报文高频（控制环 100~1000Hz） |
| 协议栈敏感点 | Netfilter 规则、offload | multicast 发现流量、DDS QoS 队列深度 |
| 最忌讳 | 丢包 | 延迟尖刺打断控制环节拍 |
| 对应手段 | 分诊树四条分支 | busy polling、RT 优先级、DDS QoS 的 KEEP_LAST 深度压小 |

一个高频误区：ROS2 节点通信"偶尔卡顿"，工程师去调网络参数——实际瓶颈常在 DDS 的可靠性 QoS（RELIABLE 模式下丢包会触发重传，一次重传就是一次节拍延迟尖刺）。控制环话题配 BEST_EFFORT + KEEP_LAST(depth=1) 是标准答案，理由与 25.7 采集队列减帧相同：**宁可丢旧帧，不要等重传**。

## <span class="blue"> 本节总结

每包延迟六段分解的核心洞察是量级差：PHY/DMA/协议栈按微秒计，调度段按毫秒计——确定性问题的战场在调度不在协议栈。分段测量各有原生工具：SO_TIMESTAMPING 量内核段（硬件戳-软件戳的差值）、cyclictest+打点量调度段、ping 的 mdev 量端到端抖动。吞吐分诊树四条分支（中断分布/%soft/%sys/物理链路）各带证伪手段，分错支要能退回。抖动测量的铁律是分布优于均值，验收写 p99.9。机器人 DDS 场景权重重排：抖动与节拍优先于吞吐，QoS 队列深度与控制环队列同哲学。

**关键结论速查：**

| 问题 | 答案 |
|------|------|
| 六段量级 | ①②④ μs 级，③⑤ ms 级——调度段是主战场 |
| 内核段测量 | SO_TIMESTAMPING 硬件戳减软件戳 |
| 调度段测量 | cyclictest 基线 + 应用打点分布 |
| ping 看什么 | mdev 和 max，不看 avg |
| 吞吐分诊四分支 | 中断分布 / %soft 协议栈 / %sys 应用 / 物理链路 |
| 分诊纪律 | 每分支带证伪手段，错了退回树根 |
| 抖动验收口径 | p99.9 < X ms，不写均值 |
