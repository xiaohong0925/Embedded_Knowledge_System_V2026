# 26.8 综合实战：工业网关确定性调优

> 所属章节：第26章 网络全链路：从PHY到Socket
>
> 难度：[E] | 预计阅读时间：50 分钟

## <span class="blue"> 本节导读

前七节建立的一切——硬件层分诊（26.1）、收发路径（26.2/26.3）、Netfilter 开销（26.4）、socket 交接（26.5）、测量方法（26.6）、故障分诊（26.7）——这节压进一个完整案例：**工业协议网关，1Gbps 链路上跑 EtherNet/IP，要求转发延迟的 99.9 分位 <500μs，初版标准内核的抖动是 5~20ms**。

这个案例与 25.7 门铃案形成对照：门铃优化的是**平均延迟**（300→120ms，砍的是多余环节），本案优化的是**抖动上限**（20ms→500μs，砍的是不确定性来源）。两者的测量方法论相同，治理手段完全不同——平均延迟问题的敌人是多余的数据搬运，抖动问题的敌人是调度的不确定性。全程五步：测量定位 → PREEMPT_RT → CPU 隔离 → busy polling → NAPI 参数收敛，每步给出依据、改动、收益、代价。

---

## <span class="blue"> 背景：指标与初版方案

产品形态：EtherNet/IP 协议网关，一头接产线 PLC 网络（控制环周期 4ms），一头接工厂骨干网（1Gbps）。网关在两个网络之间转发实时控制报文，**关键指标不是吞吐而是确定性：单包转发延迟 p99.9 < 500μs**——PLC 控制环 4ms 一拍，转发延迟超 500μs 会挤占控制回路的计算余量，偶发超标可能导致整线节拍异常。

初版方案：标准 Buildroot 内核（无 RT 补丁），网关程序是普通优先级的用户态进程，socket 收发 + 协议转换，跑在四核 A55 SoC 上。实验室实测：

```
转发延迟（一万包统计）：
p50 = 85μs    ← 平均很好看
p99 = 2.1ms
p99.9 = 18.3ms ← 指标线500μs，超标36倍
max  = 22.4ms
```

平均延迟 85μs 完全达标，p99.9 超标 36 倍——这是确定性问题的标准画像：**均值没问题，尾巴没法看**。现场的表现形式是"每天偶发几次节拍告警"，抓不到规律。

## <span class="blue"> 第一阶段：测量，把尾巴拆开

按 26.6 的分段方法给转发路径打点。网关在"收到包→发出包"之间只有四段可测：

```
① 包进协议栈 → 应用读到（socket时间戳 vs 读取时刻）
② 应用处理（协议转换打点）
③ 应用发出 → 包进 TX ring（发送打点到驱动确认）
④ TX 完成（隐性段，由①③的残差反映）
```

一万包统计：

| 段 | p50 | p99.9 | 判定 |
|----|-----|-------|------|
| ① 收包到应用 | 15μs | **9.8ms** | 主犯一：softirq 调度+应用唤醒 |
| ② 协议转换 | 22μs | 45μs | 干净 |
| ③ 发包路径 | 18μs | **8.1ms** | 主犯二：发包调度+qdisc 等待 |
| ④ 残差 | ~30μs | ~0.4ms | 可忽略 |

结论与 26.6 实录的形态一致但更彻底：**②④两段（真正的处理工作）最坏情况都在 50μs 内，①③两段（调度等待）贡献了全部尾巴**。18ms 的尖刺里没有任何一微秒是"算得慢"，全是"没被调度"。

补充一个旁证：cyclictest 基线 max 18.5ms（与 26.6 实录同源）——标准内核的长临界区（关中断的驱动区段、不可抢占的自旋锁区）就是调度延迟的物理来源。两条证据链闭合后，优化方向唯一：**治调度，不是治网络**。

## <span class="blue"> 五步优化

### 第一步：PREEMPT_RT 补丁（p99.9：18.3ms → 1.2ms）

**依据：** 标准内核的自旋锁区段不可抢占——网卡驱动、块设备驱动里都有持锁数百微秒甚至更久的临界区，实时线程来了也只能等。PREEMPT_RT 把绝大多数自旋锁换成可抢占的 rtmutex，把中断处理线程化（第 20 章有原理展开），长临界区从机制上消失。

**改动：** 内核配置打开 `CONFIG_PREEMPT_RT`（5.15+ 的主线已合入，本项目用 6.1 直接开配置即可），重编内核。无代码改动。

**收益：** cyclictest max 从 18.5ms 降到 380μs；转发延迟 p99.9 从 18.3ms 降到 1.2ms。**代价：** 全系统吞吐实测下降约 8%（锁变重、中断线程化的开销）——网关吞吐余量充足，接受。

### 第二步：CPU 隔离与亲和性绑定（p99.9：1.2ms → 720μs）

**依据：** RT 之后剩下的尖刺来自两类打扰：无关中断落在业务核上、内核 housekeeping（定时器、工作队列、RCU 回调）在业务核上运行。隔离的思路是把 CPU2/CPU3 划成"专用核"，所有打扰都赶到 CPU0/CPU1。

**改动：**

```
# 内核启动参数：隔离CPU2/3（不再参与普通调度）
bootargs 追加：isolcpus=domain,managed_irq,2-3 nohz_full=2-3 rcu_nocbs=2-3
```

```bash
# 网卡中断绑到CPU2（收发包处理在专用核）
echo 4 > /proc/irq/$(awk '/eth0/{print $1}' /proc/interrupts | tr -d ':')/smp_affinity_list
# 网关进程绑CPU3，RT优先级80
chrt -f 80 taskset -c 3 /usr/bin/gatewayd
```

> 💡 中断绑 CPU2、业务进程绑 CPU3 而不是同一核：收包 softirq 与业务进程同核会互相抢占（RT 线程优先级更高时 softirq 被压制，反而积压），分核后"收包核"和"处理核"各司其职，socket 队列成为两者间的天然缓冲。这是 26.3"收发绑同组核"原则在实时场景的修正——那里要 cache 局部性，这里要互不打扰。

**收益：** p99.9 降到 720μs。**代价：** 系统只剩两个核跑其他所有任务，监控/日志类进程的吞吐受限——网关形态可接受，通用设备要慎重。

### 第三步：busy polling（p99.9：720μs → 380μs）

**依据：** 剩余尾巴的大头是①段里"包到→softirq→唤醒业务线程"的唤醒延迟：RT 线程的唤醒本身仍有调度延迟。busy polling（26.5）让业务线程在收包前主动轮询 NAPI，包一到立刻处理，**整条"中断→调度→唤醒"路径被旁路**。

**改动：**

```c
int busy_us = 50;                                   /* 空转上限50μs */
setsockopt(rx_fd, SOL_SOCKET, SO_BUSY_POLL, &busy_us, sizeof(busy_us));
/* sysctl 全局开关：net.core.busy_poll=50（或按socket单独设置） */
```

**收益：** ①段 p99.9 从 680μs 降到 45μs，整体 p99.9 380μs——**首次达标**（指标 500μs）。**代价：** CPU3 在轮询期间 100% 占用，整机功耗上升约 0.4W——工业网关 24 小时插着电，接受。

### 第四步：NAPI budget 与中断合并收敛（p99.9：380μs → 290μs）

**依据：** 前两步之后做了一次反向检查：繁忙时段（骨干网上有大文件传输经过网关转发）延迟仍有零星 600~900μs 尖刺。打点定位到 NAPI poll 的 budget——默认 64 的 budget 意味着一次 poll 最多收 64 个包，大流量时段单个 poll 周期变长，实时包在 ring 里等前面的批量包处理完。

**改动：**

```
ethtool -C eth0 rx-usecs 25 rx-frames 8    # 中断合并：最多等25μs或攒8帧（默认通常100μs级）
echo 32 > /proc/sys/net/core/netdev_budget  # 单次poll预算64→32：每批少收点，轮转快点
```

参数方向与吞吐优化**相反**：26.2/26.3 里为吞吐调大的参数，这里为延迟调小。中断合并等得短、budget 每批收得少——用 CPU 开销换延迟上限。

**收益：** 繁忙时段尖刺消失，p99.9 收敛到 290μs。**代价：** 同吞吐下 CPU 占用上升约 12%——busy polling 已经把收包工作搬到业务线程，这部分开销实际被第三步的轮询吸收了大部分。

### 第五步：配置固化与验收门禁

临时命令全部落地为持久配置（26.3 提醒过的归宿）：

```
# /etc/systemd/system/gateway-rt.service（片段）
[Service]
ExecStartPre=/sbin/ethtool -C eth0 rx-usecs 25 rx-frames 8
ExecStartPre=/sbin/ethtool -L eth0 combined 2
ExecStart=/usr/bin/chrt -f 80 /usr/bin/taskset -c 3 /usr/bin/gatewayd
CPUAffinity=3
```

```
# sysctl.d/90-gateway-rt.conf
net.core.busy_poll = 50
net.core.netdev_budget = 32
```

isolcpus 等启动参数进 bootloader 配置，随 OTA 镜像一起受控（第 21 章的升级链覆盖内核与 bootargs，无需特殊处理）。

## <span class="blue"> 验收：确定性的证明方式

确定性指标的验收和性能指标不同——**它要用时间和负载来证明，不能用平均值来证明**。验收三件套：

**长稳烤机。** cyclictest + 业务打流并行 72 小时，全量记录转发延迟（不是抽样）：

```
72h 全量统计（约 2.6 亿个转发包）：
p50 = 68μs   p99 = 145μs   p99.9 = 287μs   max = 412μs
```

max 值 412μs 都压在 500μs 指标线内——注意这里看的是 **max** 而不是 p99.9：控制环场景里"最坏情况"才是产品承诺，分位数只是工程上的近似。

**负载叠加。** 在骨干网方向灌入 900Mbps 背景流量重复烤机：p99.9 上浮到 310μs，仍达标——第四步的 budget 收敛在这里兑付。

**故障注入。** 拔插网线、对端重启、广播风暴模拟（10K pps 组播）各注入一次：业务延迟曲线无可见扰动（组播风暴被 XDP 黑名单规则挡在栈外——26.4 的第一道筛形态在本案顺手落地）。

## <span class="blue"> 复盘：这个案例教什么

**确定性的敌人是调度，不是速度。** 初版 85μs 的平均延迟说明处理能力完全够用——22ms 的尾巴里没有一微秒是计算。五步优化里四步（RT、隔离、busy polling、budget）都在消除"等待被调度"，没有一步让任何计算变快。这就是大纲那句教训的完整实证：**确定性延迟的关键不是降低平均延迟，而是消除抖动来源。**

**每步优化都是确定性与别的东西的交换。** RT 换了 8% 吞吐，隔离换了两个通用核，busy polling 换了 0.4W，budget 收敛换了 12% CPU——与 25.7 门铃案"每步改动有明示代价"的纪律相同，但这里的代价表更尖锐：确定性是用资源余量买的，资源紧张的系统上没有免费的 p99.9。

**验收口径决定结论可信度。** 均值 85μs 的初版和 p99.9 287μs 的终版，若只看均值两者"都很好"。确定性产品的验收必须写成分位数+max+时长+负载条件，四者缺一就是验收漏洞。

**方法论与 25.7 完全同构。** 测量先行（分段打点杀掉"网络处理慢"的直觉）、预算分解（各段 p99.9 对比）、逐段打击、代价明示、长稳回归——链路不同，打法相同。这就是第四部"全链路实战"的通用骨架。

## <span class="blue"> 延伸：还要更硬怎么办

500μs 是软件方案（RT+隔离+轮询）的实用下限。指标再往下压一个数量级（<50μs）就进入另一类技术的领土：

- **TSN（时间敏感网络）**：802.1Qbv 时间感知整形器把流量按时刻表调度，硬件保证窗口——26.3 提到的 mqprio 是它的软件接口，完整主题在第 27 章工业通信；
- **EtherCAT**：绕过 TCP/IP 全栈，从站芯片硬件级转发，延迟按纳秒计——同样在 27 章展开；
- **DPDK/XDP 直通**：协议栈整体旁路，26.4 的决策边界已划好。

选择逻辑与第 20 章的实时决策树一致：先看指标量级，再看生态代价，别为上而上的技术买单。

## <span class="blue"> 本节总结

工业网关案五步（PREEMPT_RT → CPU 隔离 → busy polling → NAPI 收敛 → 配置固化）把转发延迟 p99.9 从 18.3ms 压到 287μs、72 小时 max 412μs 达标。全案没有一步提升计算速度——抖动来自调度不确定性，治理就是把"等待被调度"的环节逐一旁路或隔离。代价表（吞吐 -8%、两个核、0.4W、CPU +12%）证明确定性是拿资源余量换的。验收用 max+分位数+时长+负载四件套，均值不参与结论。
