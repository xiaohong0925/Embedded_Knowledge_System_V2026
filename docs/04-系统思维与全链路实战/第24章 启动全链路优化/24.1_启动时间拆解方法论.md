# 24.1 启动时间拆解方法论

> 所属章节：第24章 启动全链路优化
>
> 难度：[E] | 预计阅读时间：25分钟

## <span class="blue">本节导读

一台智能安防摄像头，冷启动到出预览画面 5.8 秒，产品要求是 2 秒。启动优化会开了半小时，结论是"大家回去各砍各的"——内核组裁驱动，应用组压加载，硬件组看看能不能换快的 eMMC。三个月后省出来 0.9 秒，还差得远。

问题出在哪？出在开那半小时会的时候，**没有任何人知道 5.8 秒的真实分布**。事后用本节的方法测出来：U-Boot 阶段 1.6 秒（其中等 PHY 协商 0.8 秒）、内核 2.2 秒（其中两个 initcall 占 1.1 秒）、用户空间 1.4 秒、应用自身 0.6 秒。之前砍的三刀有两刀砍在了根本不疼的地方。启动优化的第一条铁律：**你不能优化你无法测量的东西**。

> 本节覆盖：启动链的全景时间轴（每一段典型占多少）、五层测量基础设施（从示波器到 systemd-analyze，每层管哪段、怎么搭）、测量纪律（冷启动与热启动、批次差异、多次测量取什么值）、优化经济学（每项优化回答三个问题再动手）、三种"启动时间"的口径区分（真实就绪 vs 用户感知 vs 产品指标），以及"测量→排序→验证→防回归"的全章方法论。

---

## <span class="blue">全景时间轴：毫秒都住在哪 [E]

启动链六段，每段有典型的耗时量级（ARM SoC、eMMC/SD 启动的常见值，因平台而异，仅用于建立直觉）：

```
上电 ────────────────────────────────────────────────────► 用户可用
 │        │         │          │           │             │
 ▼        ▼         ▼          ▼           ▼             ▼
BootROM   SPL      U-Boot     Kernel      Init       Application
(固定)   (可变)    (可变)     (可变)      (可变)        (可变)
 │        │         │          │           │             │
~50ms   ~200ms    ~500ms     ~800ms     ~1200ms       ~2000ms
 │        │         │          │           │             │
 └ 固化在芯片里    └ DDR初始化  └ 驱动/脚本  └ initcall    └ 服务与依赖
   基本动不了        加载二阶段    /内核加载    长尾          └ 应用自己的账
```

三个结构性认知先于一切优化：

1. **BootROM 段基本不可优化**（固化在芯片 ROM 里），但要知道它占多少——50ms 的 BootROM 和 500ms 的 BootROM（某些启动介质校验慢的芯片）直接决定你的优化天花板；
2. **越往后段越大、方差也越大**——前面的段固定、干净，后面的段依赖文件系统状态、服务依赖、应用逻辑，"启动时间随使用变长"这种病只发生在后半段；
3. **每段的优化手段完全不同**——这就是为什么必须先分段测量，"启动慢"三个字不提供任何行动方向。

## <span class="blue">五层测量基础设施 [E]

没有单一工具能覆盖全链，每层管一段，拼起来才是完整时间轴。按从上电到应用的顺序：

### 第一层：硬件层——示波器 + GPIO

BootROM 和 SPL 早期没有任何软件可借助，唯一的观测手段是让代码翻 GPIO、用示波器量电平跳变：

```c
/* SPL 入口与出口各翻一次 GPIO，示波器量脉宽 = SPL 真实耗时 */
writel(1, GPIO_BASE + 0x00);   /* 进 SPL：拉高 */
/* ... DDR 初始化、加载 U-Boot ... */
writel(0, GPIO_BASE + 0x00);   /* 出 SPL：拉低 */
```

这一层同时是**全链的时间基准**：各层软件时间戳的时钟源不同（SPL 用定时器 tick、内核用 jiffies、用户空间用 CLOCK_MONOTONIC），跨段对表时以 GPIO 翻转的物理时刻对齐。没有示波器条件的退而求其次：串口时间戳（上位机 minicom/日志工具给每行打印打到达时刻）——精度差些（串口本身有缓冲延迟），但分段量级够用。

### 第二层：Bootloader 层——bootstage

U-Boot 内置启动记账：内核配置 `CONFIG_BOOTSTAGE=y` 后，U-Boot 在关键节点自动记录时刻，启动后一条命令看账：

```
=> bootstage report
Timer summary in microseconds (11 records):
       Mark    Elapsed  Stage
          0          0  reset
    105,000    105,000  board_init_f
    312,000    207,000  board_init_r
    480,000    168,000  id=64 (driver model init)
    850,000    370,000  main_loop
  1,600,000    750,000  bootm_start
```

这份账直接回答"U-Boot 的 1.6 秒花哪了"——上例里 `main_loop` 前那 370ms 是驱动初始化，`bootm_start` 后 750ms 是内核加载与解压。24.2 的每个优化动作都对应这张表里的某一行。

### 第三层：内核层——initcall_debug

内核启动参数加两个：

```
initcall_debug printk.time=1
```

dmesg 里每个 initcall 的调用时刻、返回值、耗时全部可见：

```
[    1.234567] calling  ov5640_sensor_init+0x0/0x40 @ 1
[    1.512890] initcall ov5640_sensor_init+0x0/0x40 returned 0 after 278323 usecs
```

这个传感器初始化一次吃掉 278ms——**长尾就长这样**。处理命令：

```bash
dmesg | grep "initcall.*returned" | \
    sed 's/.*after \([0-9]*\) usecs/\1 &/' | sort -rn | head -20
```

排出耗时前 20 的 initcall，通常前 5 名就占了内核段的一半以上——这就是 24.3 的工作清单。

### 第四层：Init 层——systemd-analyze

systemd 系统的用户空间账最好算：

```bash
systemd-analyze                    # 总账：kernel + userspace 各多少
systemd-analyze blame              # 每个服务花多少，降序
systemd-analyze critical-chain     # 关键路径：谁等谁
systemd-analyze plot > boot.svg    # 全服务时间线（给评审用）
```

`blame` 告诉你哪个服务最慢，`critical-chain` 告诉你它**挡没挡路**——一个慢 2 秒但不在关键路径上的服务（比如日志上传）对启动时间毫无影响，这是用户空间优化最常见的误判。24.4 展开。

不用 systemd 的系统（busybox init/自定义 init）退回第一层办法：init 脚本里每步 `echo` + 串口时间戳。

### 第五层：应用层——应用内打点

应用从 `main()` 到"用户可用"的账，只有应用自己知道。以摄像头为例，关键打点是：

```c
static uint64_t now_us(void) {
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return ts.tv_sec * 1000000ULL + ts.tv_nsec / 1000;
}
/* main() 入口、V4L2 打开、ISP 就绪、第一帧回调、预览上屏 各打一点 */
```

"第一帧上屏"这个点就是产品指标（<2 秒出预览）的真实测量点——它通常既不是"应用启动完成"也不是"系统就绪"，这个区分是本节最后一段的主题。

## <span class="blue">测量纪律：别让数字骗了你 [E]

五条纪律，每条都对应一个真实的踩坑场景：

1. **冷启动与热启动分开测**。冷启动（断电上电）含 DDR 初始化、文件系统 journal 恢复；热启动（reboot）跳过很多硬件初始化，数据页缓存状态也不同。指标通常指冷启动，混着测出来的"优化收益"可能是测量误差。
2. **批次差异要警觉**。同一固件，不同批次板子启动差几百毫秒——最常见原因是 DDR training 时间不稳定（24.2 会讲怎么固定 training 参数）。测优化收益要在同一块板子上做前后对照。
3. **至少测 5 次取什么值？** 启动时间不是实时指标（第 27 章的最坏值逻辑），产品验收通常取**典型值 + 上限**：5 次测量，报中位数，同时保证最大值不超指标。偶发的慢启动（文件系统检查、日志轮转）要单独归因，不能藏进平均。
4. **"启动时间随使用变长"是病，要单独查**。文件系统碎片化、日志文件膨胀、data 分区将满——这些让第 1000 次启动比第 1 次慢。优化验收应该包含"老化后复测"。
5. **每次优化前后同条件复测**。优化动作之间互相影响（裁掉 USB 驱动可能让某个 initcall 消失），账本要逐项更新，最后总账才经得起评审。

## <span class="blue">优化经济学：动手之前的三问 [E]

测量账拿到手，面对十几项可优化的条目，按什么顺序做？每项先回答三个问题：

**第一问：省多少毫秒？** 只看绝对值，不看百分比——省 50% 的 BootROM（25ms）不如省 10% 的内核段（220ms）。

**第二问：付什么代价？** 启动优化的每项收益都标着价格，按四档记账：

| 代价维度 | 典型优化 | 失去什么 |
|:---|:---|:---|
| 功能 | 裁掉 USB/蓝牙驱动 | 产测与现场扩展能力 |
| 调试能力 | `quiet`、关 earlycon、裁 printk | 下次出问题时手里没有日志 |
| 可维护性 | 自定义 init 替代 systemd | 团队新成员要重学一套私有体系 |
| 鲁棒性 | 删超时等待、跳校验 | 偶发失败率上升（24.5 的"优化后偶发启动失败"） |

**第三问：省的是真实时间还是感知时间？** 这是最重要的一问，留到下面专门讲。

三问答完，排序原则自然浮现：**先做零代价的**（删重复初始化、修错误配置），**再做低代价高收益的**（lz4、异步 probe），**高代价的逐项评审**（自定义 init、砍调试能力），**最后考虑感知优化**（它常常比所有真实优化加起来都值钱）。

> 💡 还有一条纪律：不要全做。账本上排名靠后的项（每项 <50ms）加起来往往不如前三项，但每一项都引入风险与维护负担。启动优化是"够了就停"的工程——指标 2 秒，做到 1.5 秒就该收手，追 1.2 秒的边际投入通常该花在别处。

## <span class="blue">三种"启动时间"：口径决定一切 [E]

评审"启动 2 秒达标没有"之前，先对齐说的是哪一种：

> 真实就绪时间：从上电到系统全部服务就绪、应用完成全部初始化的时间。这是工程师直觉里的"启动时间"，也是账本逐项优化的对象。

<!-- -->

> 感知可用时间：从上电到**用户认为设备能用了**的时间——摄像头是"看到第一帧预览"，仪表盘是"指针动起来"，机器人是"可以接受指令"。它几乎总是小于真实就绪时间。

<!-- -->

> 产品指标口径：合同或需求文档里写的那一个数。它必须明确指向某个可测量的物理事件（"第一帧上屏""背光点亮且 UI 可交互"），否则验收必吵架。

摄像头案例把三者分得很开：真实就绪 5.8 秒，产品指标"2 秒出预览"是感知口径，而 24.5 里省掉最多时间的那一招——**先出预览、AI 分析延后初始化**——没有让真实就绪快一秒，只是把感知时间从 2.6 秒压到 1.2 秒。这不是作弊，是对"用户到底要什么"的诚实回答；但它必须建立在真实账本上——**感知优化是压轴戏，不是遮羞布**，真实段里该省的毫秒一分也逃不掉。

## <span class="blue">本章的方法论 [E]

收拢成四步工作循环，后面四节严格按它走：

1. **测量**——搭五层基础设施，拿到带时间戳的全链账本（本节）；
2. **排序**——每项候选优化过"三问"，按性价比排队（本节）；
3. **验证**——逐项实施、逐项复测、账本逐项更新（24.2~24.4）；
4. **防回归**——启动时间进 CI：每次构建自动量启动时间，超阈值报警——启动时间是所有指标里退化最悄无声息的，没有 CI 看门，半年后准回到原点（24.5 落地）。

## <span class="blue">本节总结

启动优化的第一条铁律：不能优化无法测量的东西。全链六段（BootROM/SPL/U-Boot/Kernel/Init/App）每段量级不同、优化手段不同——"启动慢"三个字不提供行动方向，分段账本才提供。五层测量各管一段：示波器 GPIO 管硬件段兼作时间基准、bootstage 管 U-Boot、initcall_debug 管内核、systemd-analyze 管服务、应用打点管首帧。

测量纪律五条：冷热分开、同板对照、中位数加上限、老化复测、逐项更新账本。动手顺序由三问决定：省多少毫秒（绝对值）、付什么代价（功能/调试/维护/鲁棒四档）、省的是真实时间还是感知时间。三种启动时间口径（真实就绪/感知可用/产品指标）必须在评审前对齐——感知优化是压轴戏不是遮羞布。最后记住"够了就停"：指标 2 秒做到 1.5 秒收手，边际投入花在别处。
