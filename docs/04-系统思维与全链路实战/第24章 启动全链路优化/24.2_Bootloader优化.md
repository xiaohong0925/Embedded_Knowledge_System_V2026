# 24.2 Bootloader 优化

> 所属章节：第24章 启动全链路优化
>
> 难度：[E] | 预计阅读时间：25分钟

## <span class="blue">本节导读

24.1 的 bootstage 账本把 U-Boot 段拆成了两行主要开销：驱动初始化 370ms、内核加载 750ms——再加上 bootstage 看不到的 SPL 段和脚本轮转，Bootloader 全段在这台摄像头上吃掉约 1.6 秒，是五段里第二大的。好消息是：**这一段也是优化性价比最高的**——它逻辑简单、没有依赖地狱，每个动作都直接对应 bootstage 表里的某一行，做完立刻能复测。

> 本节覆盖：SPL 段的优化（能瘦到什么程度、DDR training 怎么固定）、Falcon 模式跳过整个 U-Boot 二阶段（-400ms 的代价是什么）、U-Boot 驱动初始化裁剪（含摄像头案例里 0.8 秒的 PHY 协商等待）、bootcmd 与 bootdelay、内核加载三要素（压缩算法选型、加载地址对齐、存储时钟提升），以及一份"动作 → bootstage 行 → 收益 → 代价"的总表。

---

## <span class="blue">SPL 段：小空间里的大文章 [E]

SPL 是第一段可控制的软件，空间极紧（通常 SRAM 只有几十到 128KB），职责只有两个：**初始化 DDR、把下一阶段的镜像从启动介质搬进 DDR**。它的优化方向也对应这两件事：

**职责一：DDR 初始化**。大头是 DDR training（内存控制器与颗粒之间的时序校准），耗时与颗粒批次、温度相关——这正是 24.1 说的"不同批次板子启动差异大"的头号来源。优化不是跳过 training（跳过就是稳定性灾难），而是**固定 training 结果**：量产后将校准参数固化（厂商工具通常支持导出 training 参数表），启动时直接写寄存器而不再跑校准流程。收益 50~200ms 且**消除了批次方差**——注意这是拿"换颗粒批次要重新导出参数"换来的，来料变更流程里必须加这一条。

**职责二：搬镜像**。SPL 读镜像的速度受限于它初始化的存储控制器时钟——SPL 里通常用保守低速率（25MHz SD、低速 eMMC 模式），把时钟提上去是后面"存储时钟"一节的主题，SPL 段先记住：**SPL 搬的镜像越小，低速率的损失越小**——这又回到"SPL 自身和它的载荷都要瘦"。

## <span class="blue">Falcon 模式：跳过整个二阶段 [E]

默认启动链是 SPL → U-Boot 二阶段（完整 U-Boot）→ 内核。**Falcon 模式让 SPL 直接加载内核，U-Boot 二阶段根本不运行**——摄像头案例里这一跳省 400ms，是单笔最大的 Bootloader 优化。

```
默认：  SPL ──加载──▶ U-Boot二阶段 ──驱动/脚本──▶ 加载内核
Falcon：SPL ───────────────直接加载内核──────────────▶ 内核
              （U-Boot 二阶段仍存在，仅需要时进入）
```

做法（U-Boot 主线支持）：`CONFIG_SPL_OS_BOOT=y`，SPL 里用 `spl_export_fdt()` 准备好内核需要的设备树与参数（通常事先用 U-Boot 的 `spl fdt` 流程导出一份"启动参数快照"），SPL 判断直接 `jump_to_image_linux()`。

代价要照 24.1 的三问记账：

- **失去交互**：没有倒计时、没有命令行，现场想手动换内核/改参数进不了 U-Boot——缓解办法是留后门：按住某个按键（或 GPIO 拉低）时 SPL 退回加载 U-Boot 二阶段，产线与研发照常进命令行，量产默认走 Falcon；
- **失去灵活性**：bootcmd 逻辑、环境变量解析都不存在了，内核地址与参数必须提前定死——OTA 双槽切换（第 21 章）要改由 SPL 读 bootcount 变量选择槽位，逻辑前移、复杂度没消失只是搬了家；
- **调试变难**：SPL 阶段打印有限，Falcon 失败时现场信息少——保留串口 earlycon 到内核接管。

工程结论：Falcon 是启动时间敏感产品的标准动作，但**永远配"按键退回 U-Boot"的后门**，没有后门的 Falcon 是给产线和售后挖坑。

## <span class="blue">U-Boot 驱动初始化：砍掉用不上的 [E]

bootstage 表里 `driver model init` 那 370ms，大头是初始化一堆"产品根本不用"的控制器。摄像头案例最典型：**网口 PHY 协商等待 0.8 秒**——U-Boot 默认初始化网络（为了 TFTP 加载的调试便利），PHY link 协商要等上将近一秒，而这台摄像头的产品形态根本不在 U-Boot 阶段用网络。

裁剪动作三类，按收益排序：

1. **整类裁掉**：`defconfig` 里关掉 `CONFIG_CMD_NET`、`CONFIG_USB`、`CONFIG_VIDEO` 及对应驱动——不需要在 U-Boot 里联网/插 U 盘/点屏的产品，每类省 100~300ms，还顺手缩小镜像；
2. **设备树配合**：保留下来的控制器，不用的实例在 U-Boot 设备树里 `status = "disabled"`——驱动不 probe，每个省几到几十毫秒；
3. **等待类参数清零**：`bootdelay=0`（倒计时，量产必须关）、网络相关的 `phy` 复位延时按手册给的最小值而非默认值。

一份真实的裁剪片段（摄像头板 defconfig 增量，注释为收益来源）：

```kconfig
# 网络整类裁掉——产品不在 U-Boot 阶段用网（省 PHY 协商 0.8s）
# CONFIG_CMD_NET is not set
# CONFIG_NET is not set
# CONFIG_PHY_REALTEK is not set

# USB/显示整类裁掉（各省 100~300ms）
# CONFIG_USB is not set
# CONFIG_VIDEO is not set

# 倒计时与打印
CONFIG_BOOTDELAY=0
# CONFIG_SILENT_CONSOLE is not set   # 调试用，量产变体里置 y

# SPL 侧同步瘦身：Falcon 需要的保留，其余关
CONFIG_SPL_OS_BOOT=y
# CONFIG_SPL_NET_SUPPORT is not set
# CONFIG_SPL_USB_SUPPORT is not set
```

注意 SPL 有自己的一套 `CONFIG_SPL_*` 开关——U-Boot 主体裁掉的功能，SPL 侧不一定会自动跟着裁，两边要对着检查；SPL 每多一个驱动，SRAM 占用和初始化时间都跟着涨，128KB 的空间预算会逼着你做第二次裁剪。

> ⚠️ 裁网络之前确认一件事：产线烧录和现场救砖走不走网络？走的话裁掉 `CONFIG_CMD_NET` 就是把产线流程一起裁了。这类"启动用不上但产测要用"的功能，正确做法是**分固件变体**（产测固件带网络、量产固件不带），而不是硬裁。

## <span class="blue">bootcmd 与脚本：每一次判断都是毫秒 [E]

默认 `bootcmd` 常常长成一个通用脚本：先试 SD 卡、再试 eMMC、再试网络，每个分支带 `if` 判断和 `echo`。量产产品的启动介质是确定的，脚本该收敛成一条直线：

```
# 通用版（研发期）：多介质尝试，约 100~200ms 浪费在失败分支
bootcmd=run distro_bootcmd

# 收敛版（量产）：直接干，无判断无打印
bootcmd=load mmc 0:1 ${kernel_addr_r} fitImage && bootm ${kernel_addr_r}
```

原则：**脚本里每多一次介质探测、每多一个条件分支、每多一行 echo，都是毫秒级开销**——串口打印在 115200 波特率下每秒只能输出约 11KB，一句几十字节的打印就是几毫秒。U-Boot 阶段的打印量产版全部去掉（留 `silent` 选项或编译期裁剪），调试变体再打开。

还有一个隐藏开销在脚本之外：**环境变量的读取**。默认配置下 U-Boot 启动时从存储（ENV 分区）读环境变量并 CRC 校验，环境分区大、存储慢时这一步也有几十毫秒。量产环境变量基本不变，两个收敛方向：编译期把关键变量直接内嵌（`CONFIG_DEFAULT_ENV_FILE` 或 defconfig 里的 `CONFIG_BOOTCOMMAND`），ENV 分区的读取留作覆盖机制；或干脆 `CONFIG_ENV_IS_NOWHERE`（放弃运行时修改环境的能力，只适合无 OTA 变体的极简产品）。选哪个取决于第 21 章的 OTA 方案要不要 U-Boot 读 bootcount——要，就老实留 ENV 分区。

## <span class="blue">内核加载三要素 [E]

bootstage 表里最大的单项：`bootm_start` 后那 750ms——从存储读内核镜像 + 解压 + 校验。三个可调的要素：

**要素一：压缩算法**。解压速度 lz4 > lzo > gzip > bzip2，压缩率正好反过来：

| 算法 | 解压速度（量级） | 镜像体积（相对） | 适用 |
|:---|:---|:---|:---|
| lz4 | 最快（~3× gzip） | 最大（~1.3× gzip） | 启动时间敏感，存储宽裕 |
| lzo | 快 | 较大 | 折中 |
| gzip | 基准 | 基准 | 存储紧张 |
| 不压缩 | 零解压时间 | 最大 | 存储读速快、空间充足时反而最优 |

注意这笔账是"解压时间 vs 读取时间"的赛跑：**镜像越大，从存储读出来的时间也越长**。lz4 快是因为解压省的时间大于多读几 MB 花的时间；不压缩是否最优取决于存储速度——eMMC HS400 读 8MB 未压缩镜像可能比解压 5MB gzip 更快，SD 卡上则通常 lz4 赢。结论必须用自己的 bootstage 复测验证，不抄别人的表格。复测方法：同一板子上分别烧 gzip/lz4/未压缩三个固件变体，各测 5 次 `bootm_start → 内核移交` 的耗时取中位数——半小时的实验，顶一周的邮件讨论。

**要素二：加载地址对齐**。内核镜像被加载到的地址如果与它的链接地址不一致，启动时要做一次整体重定位拷贝（几十 MB 拷贝就是几十毫秒）。U-Boot 的 `kernel_addr_r` 与内核 `CONFIG_PHYSICAL_START`/内核头里声明的加载地址对齐，这次拷贝就消失。检查方法：开 U-Boot 的 `bootm` 调试输出，看到 `relocating kernel` 字样就是没对齐。

**要素三：存储时钟**。摄像头案例里 SD 卡从 25MHz 提到 50MHz，内核加载时间减半（-200ms）；eMMC 平台同理（HS200/HS400 模式）。代价是信号完整性风险——**提速后必须在最差工况（高温、满载、长排线）下验证读取误码**，启动介质读错是灾难性故障，省 200ms 不值这个险。

## <span class="blue">优化总表：动作对应到账本行 [E]

| 优化动作 | bootstage 对应行 | 典型收益 | 代价（24.1 四档） |
|:---|:---|:---|:---|
| DDR training 参数固化 | SPL 段（bootstage 外） | 50~200ms + 消除批次方差 | 可维护性（换料要重导） |
| Falcon 模式 | 整个二阶段消失 | ~400ms | 功能+调试（留按键后门） |
| 裁 USB/Net/Display | `driver model init` | 100~300ms/类 | 功能（产测变体） |
| 设备树禁用多余实例 | `driver model init` | 几~几十 ms/个 | 几乎无 |
| bootdelay=0 + 脚本收敛 | `main_loop` | 100~300ms | 调试（研发变体保留） |
| 去打印 | 全段 | 几十 ms | 调试能力 |
| lz4/不压缩 | `bootm_start` 后 | 100~300ms | 存储空间 |
| 加载地址对齐 | `bootm_start` 后 | 几十 ms | 无 |
| 存储时钟提升 | `bootm_start` 后 | 100~200ms | 鲁棒性（需最差工况验证） |

执行顺序照 24.1 的经济学：先做零代价的（设备树、地址对齐、bootdelay），再做低代价高收益的（lz4、脚本收敛），Falcon 与裁驱动过评审，存储提速最后做并配验证。

## <span class="blue">验证：bootstage 前后对照 [E]

每个动作做完，`bootstage report` 前后各存一份——优化评审的材料就是这两份表的 diff。一个真实的中间态（摄像头案例，做完驱动裁剪 + 脚本收敛 + lz4 后）：

```
优化前：main_loop 到达 850,000μs；bootm_start → 内核移交 750,000μs
优化后：main_loop 到达 180,000μs；bootm_start → 内核移交 410,000μs
U-Boot 段合计：1.60s → 0.59s（SPL Falcon 尚未启用，留作评审项）
```

账本逐项更新，最后喂给 24.5 的总表——单项优化的"感觉快了"不作数，bootstage 的差值才作数。

## <span class="blue">本节总结

Bootloader 段是启动优化性价比最高的一段：逻辑简单、每个动作对应 bootstage 一行、效果立等可测。SPL 段两件事——DDR training 参数固化（收益之外还消除批次方差，代价是换料要重导）、载荷要瘦；Falcon 模式跳过整个 U-Boot 二阶段是单笔最大优化（-400ms），但必须配按键退回 U-Boot 的后门。

U-Boot 段三类裁剪：整类驱动（每类 100~300ms，产测功能走固件变体）、设备树禁用实例、等待参数清零；bootcmd 收敛成一条直线，脚本里每次判断和每行打印都是毫秒。内核加载三要素：压缩算法（解压与读取的赛跑，lz4 常胜但结论要复测）、加载地址对齐（消掉重定位拷贝）、存储时钟提升（必须最差工况验证误码）。验证纪律：每个动作前后各存一份 bootstage，差值才作数。
