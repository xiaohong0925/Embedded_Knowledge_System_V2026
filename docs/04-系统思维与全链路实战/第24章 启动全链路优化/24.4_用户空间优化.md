# 24.4 用户空间优化

> 所属章节：第24章 启动全链路优化
>
> 难度：[E] | 预计阅读时间：25分钟

## <span class="blue">本节导读

账本来到最后两段：Init 1.4 秒、应用自身 0.6 秒。这两段和前面三段性格不同——Bootloader 和内核的优化对象是"通用的基础设施"，做法全行业内大同小异；用户空间的优化对象是**你自己产品的服务架构**，没有标准答案，只有权衡：systemd 那 500ms 买的是服务管理生态，自定义 init 省下的 500ms 靠的是把生态砍掉。选哪边，取决于你的产品复杂度和团队构成，不取决于网上的最佳实践。

> 本节覆盖：init 系统三档选型（systemd / busybox init / 自定义）的真实代价对照、保留 systemd 时的四招优化（critical-chain 实战）、socket activation 把服务初始化挪出启动窗口、自定义 init 的最小形态与能力清单、应用侧的最后一公里（静态链接、延迟加载、首帧最短路径），以及文件系统布局这个容易忽略的影响因子。

---

## <span class="blue">init 选型：500ms 买的是生态 [E]

先把三档的账摆平：

| 维度 | systemd | busybox init | 自定义 init |
|:---|:---|:---|:---|
| 启动开销（量级） | 300~600ms | 50~150ms | 10~50ms |
| 并行启动 | 依赖图自动并行 | 脚本串行为主 | 自己实现 |
| 服务管理 | 依赖/重启/日志/资源控制全套 | 极简 | 零 |
| OTA/双槽配合 | 原生（systemd-sysupdate 生态） | 手写 | 手写 |
| 团队成本 | 行业标准，新人即战力 | 低 | 私有体系，全组重学 |
| 调试生态 | journalctl/analyze 全套 | 串口打印 | 自己造 |

选型的决策逻辑不是"哪个快"，是三句话：

1. **产品服务架构复杂**（十几个服务、有依赖网、要在线升级、要远程诊断）——systemd 的 500ms 是买生态，留下来，走下一节的四招优化，通常能压回 200ms 内；
2. **产品形态极简**（开机就跑一个主程序，两三个辅助进程）——busybox init 加手写 rcS 是甜点区，500ms 省得毫无痛感；
3. **介于中间、且团队有老人镇场**——才考虑自定义 init。它是三档里唯一"每省 1ms 都增加私有债务"的选项，摄像头案例用了它（-500ms），代价在第 24.5 的复盘里会算。

## <span class="blue">留下 systemd：四招优化 [E]

选择留 systemd，优化对象是**关键路径**——24.1 说过，`blame` 里慢的服务不一定挡路，`critical-chain` 里的才挡：

```bash
systemd-analyze critical-chain
multi-user.target @1.420s
└─camera-app.service @1.180s +240ms
  └─network-online.target @1.150s
    └─NetworkManager-wait-online.service @850ms +300ms
```

这份输出直接改写优化清单：`camera-app` 等 `network-online`，而 NetworkManager 等网卡拿到 IP 就花了 300ms——**但摄像头出预览根本不需要网络**。第一刀就砍这。

**招式一：拆掉假依赖**。关键路径上逐个审"真的需要吗"：预览不依赖网络，把 `camera-app.service` 的 `After=network-online.target` 改成只等真正需要的（`After=dev-video0.device`）。假依赖是 systemd 系统启动慢的头号原因——发行版默认单元文件的依赖是为通用场景写的，偏保守。

**招式二：精确化依赖声明**。`Wants=`（弱依赖，失败不阻塞）与 `Requires=`（强依赖）分开用；`After=`（顺序）与依赖类型分开声明——很多单元文件把两者混写，造成的串行等待比实际需要的多得多。

**招式三：socket activation**。对于"迟早要用但启动时不急"的服务（Web 配置界面、OTA 代理、调试接口），systemd 可以先创建监听 socket，**首次有连接进来才真正拉起服务**：

```ini
# ota-agent.socket —— 启动时只占一个 socket，服务本体延后
[Socket]
ListenStream=8080
[Install]
WantedBy=sockets.target
```

效果：服务的初始化时间从启动窗口里整个消失，且对客户端完全透明（连接稍等几百毫秒服务就起来了）。这一招把"延后"思想从内核模块（24.3）延伸到了用户空间服务。

**招式四：整批禁用**。`systemctl disable` 掉产品不用的服务——`bluetooth`、`avahi`、`ModemManager`、`cups`，发行版根文件系统里这类"默认带"的服务一批就是几百毫秒。

四招做完，systemd 段从 1.4s 压到 0.6s 量级是常态——剩下的是 journald、udev、dbus 这些"生态税"，再往下压就要动选型本身了。

## <span class="blue">自定义 init：最小形态与能力清单 [E]

摄像头案例的最终选择。自定义 init 不是玄学，最小形态就是一个几百行的 C 程序（或一个收敛过的 shell 脚本），做四件事：

```c
int main(void)
{
    mount("proc", "/proc", "proc", 0, NULL);
    mount("sysfs", "/sys", "sysfs", 0, NULL);
    mount("devtmpfs", "/dev", "devtmpfs", 0, NULL);

    /* 关键路径：拉起摄像头管线（不等任何非必要项） */
    if (fork() == 0) { execl("/usr/bin/camera-preview", NULL); }

    /* 非关键路径：后台陆续拉起 */
    if (fork() == 0) { execl("/usr/bin/net-service", NULL); }

    /* init 的本职：回收孤儿僵尸进程 */
    while (1) wait(NULL);
}
```

省掉 500ms 的同时，失去的东西要列清楚——这就是选型评审的 B 面：服务的自动拉起与崩溃重启（自己加监控循环）、结构化日志（自己重定向到文件）、依赖管理（自己编排 fork 顺序）、关机的优雅停止（自己处理 SIGTERM 转发）。**每一样都要么自己写、要么确认产品不需要**——摄像头产品四项里三项"不需要"（崩溃重启有看门狗兜底、日志直接写文件、依赖就两级），所以这笔买卖成立。换一个有十几个服务的产品，答案会反过来。

## <span class="blue">应用侧最后一公里 [E]

应用自身的 0.6 秒，优化点在三个层面：

**静态链接（-100ms）**。动态链接的应用启动时，动态链接器要逐个加载 `.so`、解析符号——依赖几十个共享库的大型应用，这一步就是几百毫秒。静态链接把它归零，代价是镜像体积变大、库升级要全量重编（与第 21 章 OTA 的包大小有联动，差分更新能缓解）。中间路线是减少 `.so` 数量（合并自有库）+ 预链接。

**延迟加载非必要模块（-200ms）**。应用内部的"模块"同样适用延后思想：摄像头应用启动时不必加载 AI 分析引擎、不必连接云平台、不必初始化 Web 配置界面——这些都可以等首帧之后。这一条直接通向 24.5 的感知优化。

**首帧最短路径（-300ms）**。把应用内打点（24.1 第五层）摆出来，从 `main()` 到第一帧上屏的路径上，每个环节问"能不能挪到首帧之后"：

- 配置解析：全量配置文件解析 → 首帧只需要传感器与 ISP 参数，其余懒解析；
- 资源加载：字库/图标/语言包 → 首帧不需要 UI 资源；
- 算法初始化：AI 模型加载（几十 MB 的模型文件读盘 + 解析）→ 明确挪到首帧后；
- 参数预计算：上次运行的标定参数缓存到文件 → 跳过标定流程直接用，后台再校验。

首帧路径收敛到最小集合后，剩下的就是硬件管线的真实耗时——那才是不可压缩的部分。

**文件系统布局**（常被忽略）：启动早期要读的文件（内核、dtb、init、应用二进制、首帧必需的配置）在读速上吃存储介质与文件系统布局的亏——碎片化会让读同样字节数多花寻道时间（eMMC/SD 上影响小但存在），EROFS/squashfs 这类压缩只读文件系统则让"读"变成"读+解压"。对策两个方向：**构建期把启动关键文件聚簇**（Yocto/Buildroot 都有镜像布局手段），以及根文件系统选型时把启动速度纳入评估（第 17 章的文件系统决策里有完整对照）。

## <span class="blue">优化总表 [E]

| 优化动作 | 典型收益 | 代价 |
|:---|:---|:---|
| 拆假依赖（关键路径审计） | 100~400ms | 无（纯修正） |
| 依赖精确化（Wants/After 分家） | 50~200ms | 无 |
| socket activation | 每服务 100~500ms | 客户端首次连接稍慢 |
| 整批禁用无用服务 | 100~300ms | 功能（确认产测不用） |
| busybox init 替代 systemd | 200~400ms | 生态（视产品复杂度） |
| 自定义 init | 300~600ms | 私有债务（四项能力清单） |
| 静态链接 | 50~150ms | 体积/升级（OTA 差分缓解） |
| 应用模块延迟加载 | 100~300ms | 无（设计纪律） |
| 首帧最短路径 | 200~500ms（感知口径） | 无（编排工作） |

## <span class="blue">本节总结

用户空间优化没有标准答案只有权衡。init 三档选型的决策逻辑：服务架构复杂留 systemd（500ms 买生态，四招能压回 200ms 内）、形态极简用 busybox init、介于中间且有老人镇场才考虑自定义 init——它是唯一"每省 1ms 都增加私有债务"的选项。

留 systemd 的四招都指向关键路径：拆假依赖（发行版默认依赖偏保守，预览不等网络）、依赖精确化、socket activation（服务初始化挪出启动窗口，对客户端透明）、整批禁用。自定义 init 的最小形态四件事（挂载伪文件系统/拉关键路径/后台拉非关键/回收僵尸），选型评审必须把失去的四项能力（自动重启/结构化日志/依赖管理/优雅关机）逐项确认"自己写或不需要"。

应用侧三招：静态链接消掉动态链接开销、模块延迟加载、首帧最短路径（配置懒解析/资源懒加载/AI 后置/标定缓存）——首帧路径收敛后剩下的硬件管线耗时才是不可压缩的。别忘了文件系统布局：启动关键文件聚簇 + 根文件系统选型纳入启动速度评估。
