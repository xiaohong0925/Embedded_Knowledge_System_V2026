# 24.5 综合实战：智能摄像头 5.8s→1.2s

> 所属章节：第24章 启动全链路优化
>
> 难度：[E] | 预计阅读时间：30分钟

## <span class="blue">本节导读

安防摄像头，产品指标一句话：**冷启动到出预览画面 <2 秒**（小偷进门到画面可用的每一秒都是产品价值的流失）。起点 5.8 秒。前四节的工具这一节全部上战场：五层测量、优化三问、Bootloader/内核/用户空间三段的全部招式，以及那个最后被证明最重要的一招——它不省任何真实启动时间。

> 本节覆盖：5.8 秒的完整测量账本、三阶段优化战役（零代价先行 → 结构优化 → 高代价评审）与 12 项优化的逐项流水、为什么真实就绪停在 2.5 秒还没达标、感知优化怎么把验收口径压到 1.2 秒、优化后偶发失败的实战处置、启动时间进 CI 的防回归机制，以及一份可直接用的评审清单。

---

## <span class="blue">起点：5.8 秒的完整账本 [E]

按 24.1 的五层基础设施测出来的原始分布（冷启动，中位数）：

| 段 | 耗时 | 主要构成（测量手段） |
|:---|:---|:---|
| BootROM | 180ms | 芯片固化的介质校验（示波器 GPIO） |
| SPL | 260ms | DDR training + 低速率搬 U-Boot（示波器 GPIO） |
| U-Boot | 1,600ms | 驱动初始化 370ms（含 PHY 协商 800ms 等待）；加载+解压 750ms（bootstage） |
| 内核 | 2,200ms | Top2 initcall 合计 1,100ms（initcall_debug） |
| Init | 1,400ms | systemd 生态税 + 假依赖等待（critical-chain） |
| 应用 | 640ms | 动态链接 + 全量初始化（应用打点） |
| **合计** | **≈5,800ms** | |

账本直接给出战役部署：**没有一段能省出 4 秒，必须全段作战**；且按 24.1 的经济学，顺序是零代价先行、高代价评审、感知优化压轴。

## <span class="blue">战役三阶段与逐项流水 [E]

### 阶段一：零代价先行（一周，无副作用）

先做"不做就是错"的项：`bootdelay=0`、bootcmd 收敛、quiet 参数、设备树精简（删掉评估板残留的 HDMI/第二网口节点）、加载地址对齐。这些没有评审价值，直接做。

### 阶段二：结构优化（逐项过三问）

| # | 优化动作 | 收益 | 三问结论 |
|:---|:---|:---|:---|
| 1 | SD 卡时钟 25→50MHz | -100ms | 收益实、代价是信号完整性 → 最差工况验证后通过 |
| 2 | lz4 替代 gzip | -150ms | 复测三个变体，lz4 赢（存储慢、CPU 快） |
| 3 | 裁剪内核驱动（USB/蓝牙/音频） | -300ms | 产品无此外设，产测走固件变体 |
| 4 | 异步驱动 probe（ov5640 等） | -100ms（总账） | 依赖已在设备树显式化， reboot 压测通过 |
| 5 | CMA 预分配（cma=256M） | -150ms | 从首帧路径挪走内存整理，代价是常驻预留 |
| 6 | 静态链接应用 | -100ms | 体积增大，OTA 差分更新可接受 |
| 7 | 延迟加载非必要模块（WiFi 改 ko） | -200ms | 网络功能可用时间推后 2s，用户无感 |

### 阶段三：高代价评审

| # | 优化动作 | 收益 | 评审结论 |
|:---|:---|:---|:---|
| 8 | Falcon 模式 | -400ms | 通过——配按键退回 U-Boot 后门，OTA bootcount 逻辑前移 SPL |
| 9 | 自定义 init 替代 systemd | -500ms | 通过——产品服务仅两级依赖，四项失去的能力三项确认"不需要"，崩溃重启有看门狗兜底 |

### 完整流水账

```
原始：5800ms
├─ 阶段一（零代价五项打包）           -330ms → 5470ms
├─ Falcon 模式                        -400ms → 5070ms
├─ SD 卡时钟提升                      -100ms → 4970ms
├─ lz4 替代 gzip                      -150ms → 4820ms
├─ 裁剪内核驱动                       -300ms → 4520ms
├─ 自定义 init 替代 systemd           -500ms → 4020ms
├─ 静态链接应用                       -100ms → 3920ms
├─ 延迟加载非必要模块                 -200ms → 3720ms
├─ 异步驱动 probe                     -100ms → 3620ms
├─ CMA 预分配                         -150ms → 3470ms
├─ 应用首帧最短路径（真实就绪部分）    -300ms → 3170ms
└─ 细枝末节合计（脚本/打印/节点清理）  -470ms → ≈2700ms

真实就绪：≈2.5~2.7 秒
```

真实就绪 2.5 秒——**没达标**。12 项优化做完，指标还差 0.5 秒以上。如果故事到此为止，结论只能是"加钱换硬件"。

## <span class="blue">感知优化：压轴的才是主角 [E]

回到 24.1 的三种口径：产品指标写的是"出预览画面"，这是**感知口径**。应用打点显示，首帧上屏发生在 2.6 秒——因为应用把"全部初始化"做完才肯出图：AI 模型加载（80MB，读盘 + 解析 700ms）、云平台连接、Web 界面初始化，全部排在首帧前面。

最后一招：**重排应用内部初始化顺序，pipeline 延迟初始化**——

```
原顺序：main → 解析全部配置 → 加载AI模型 → 连云平台 → 初始化Web → 开管线 → 首帧
新顺序：main → 读首帧必需配置 → 开管线 → 【首帧上屏】→ 后台：AI模型/云平台/Web
```

首帧必需集只有"传感器参数 + ISP 配置 + 显示通路"三样，其余全部挪到首帧后的后台线程。**感知时间：2.6s → 1.2s**，指标 <2 秒达成，余量 40%。

注意这一招的性质：真实就绪时间一秒没省（还是 2.5 秒），它改变的是"用户什么时候认为设备活了"。所以它在流水账里的"收益"记作感知口径 -1400ms——**比前面 12 项真实优化的总和还大**。24.1 说"感知优化是压轴戏不是遮羞布"，这个案例是完整的注脚：先有 12 项真实优化把账本压到 2.5 秒（没有这些，感知优化之后真实就绪 5 秒的系统会处处露馅——AI 报警延迟、远程连接慢），再有感知重排把验收口径做到 1.2 秒。两者是先后关系，不是替代关系。

## <span class="blue">副作用处置与防回归 [E]

**偶发启动失败**。优化全面铺开后的 reboot 压测（500 次）抓到 3 次失败：异步 probe 之后，显示控制器偶发先于摄像头时钟就绪——隐式时序依赖被打破（24.3 预告过）。处置：设备树补全 `clocks` 引用让 fw_devlink 建立顺序，复测 1000 次零失败结案。

**老化复测**。量产前做"使用老化"模拟（写满日志、data 分区填到 80%、开关机 200 次），启动时间从 1.2s 漂到 1.5s——根因是日志文件膨胀导致挂载检查变慢。处置：日志分区独立 + 大小上限 + tmpfs 兜底，复测漂移 <100ms。

**防回归进 CI**。启动时间是退化最悄无声息的指标，唯一的守卫是自动化：

1. 硬件农场留 2 块基准板，每晚构建自动刷机、自动冷启动、串口时间戳量到"首帧上屏"；
2. 阈值门禁：超过 1.4s（1.2s 指标 + 15% 容忍）构建标红，附分段账本的 diff；
3. 每季度的启动时间台账进评审——单次 +50ms 不报警，连续三个构建 +50ms 必须有人认领。

没有这道门禁，历史上所有启动优化的结局都一样：半年后一个新需求悄悄吃掉全部收益。

## <span class="blue">评审清单 [E]

**测量（24.1）**
- [ ] 五层测量基础设施就位，分段账本有书面记录
- [ ] 冷/热启动分开测，同板对照，中位数 + 上限口径
- [ ] 三种时间口径（真实就绪/感知/指标）评审前对齐

**Bootloader（24.2）**
- [ ] bootstage 前后对照存档，每项收益有差值证据
- [ ] Falcon 模式配按键退回后门；OTA bootcount 逻辑已前移
- [ ] DDR training 参数固化，换料流程含重导参数
- [ ] 存储时钟提升经最差工况误码验证

**内核（24.3）**
- [ ] initcall Top 20 归类开方存档（删/异步/延后各有依据）
- [ ] 驱动与设备树节点成对清理；启动关键路径未裁
- [ ] 异步 probe 的依赖在设备树显式化；reboot 压测 ≥500 次
- [ ] CMA 预分配覆盖所有大块连续内存用户

**用户空间（24.4）**
- [ ] 关键路径审计过，假依赖拆除（预览不等网络）
- [ ] init 选型评审记录：三档对比 + 失去能力逐项确认
- [ ] 首帧最短路径清单：每个模块回答"为什么必须在首帧前"

**综合（本节）**
- [ ] 感知优化与真实优化的先后关系成立（真实账本先压到位）
- [ ] 老化复测漂移 <10%；日志/data 分区有防膨胀设计
- [ ] CI 启动时间门禁上线，阈值与报警流程评审过

## <span class="blue">本节总结

5.8 秒的账本决定了必须全段作战：阶段一零代价先行、阶段二结构优化逐项过三问、阶段三 Falcon 与自定义 init 走评审——12 项做完真实就绪 2.5 秒，**没达标**。压轴的感知重排（首帧必需集 + 后台初始化）把感知口径做到 1.2 秒，收益超过 12 项真实优化的总和；但先后关系不能反——没有真实优化压底，感知优化遮不住 AI 报警延迟这些露馅点。

三条带走的教训：**指标口径决定战术**（"出预览"是感知口径，就别只在真实就绪上死磕）；**副作用要预案化**（reboot 压测抓竞态、老化复测抓漂移，都是规定动作不是选做）；**收益靠 CI 看守**（启动时间是退化最悄无声息的指标，没有门禁半年后准回原点）。
