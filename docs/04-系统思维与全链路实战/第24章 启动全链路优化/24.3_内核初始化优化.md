# 24.3 内核初始化优化

> 所属章节：第24章 启动全链路优化
>
> 难度：[E] | 预计阅读时间：25分钟

## <span class="blue">本节导读

摄像头的内核段 2.2 秒，`initcall_debug` 排出的账触目惊心：**前两名 initcall 合计 1.1 秒**——一个摄像头传感器初始化等上电稳定 480ms，一个 SDIO WiFi 驱动扫描等固件加载 620ms。内核段的优化基本就是"长尾猎杀"：几百个 initcall 里，前十名往往占掉一半以上的时间，剩下几百个加起来不足零头。这一节的方法论只有一句话：**把长尾找出来，然后对每一条问——能删吗？能异步吗？能延后吗？**

> 本节覆盖：initcall 的执行模型（哪段严格串行、哪段可以动）、长尾的三类成因（硬件等待/枚举扫描/计算校准）与三招处理（删、异步、延后）、驱动裁剪的 defconfig 纪律、quiet 参数的正确姿势、设备树精简、CMA 预分配，以及"优化后偶发启动失败"这个副作用的来源与对策。

---

## <span class="blue">initcall 的执行模型：先分清哪段能动 [E]

第 7 章讲过完整流程，这里只回顾与优化直接相关的结构。内核初始化分两个世界：

```
start_kernel() ── 同步世界，严格顺序，优化空间小
  setup_arch / mm_init / sched_init / timekeeping_init / console_init ...
       │
       ▼
rest_init() → kernel_init() → do_initcalls() ── initcall 世界，优化的主战场
  early → core → postcore → arch → subsys → fs → device → late
                                                  ▲
                                          绝大多数驱动在这一级
```

两个优化相关的关键事实：

1. **同步世界基本动不了**——架构初始化、内存、调度器是地基，总计通常 200~400ms，裁无可裁；
2. **initcall 世界默认是串行的**——`do_initcalls()` 按级别、按链接顺序逐个调用，一个 480ms 的传感器初始化会**堵住后面所有 initcall**。长尾的危害不是它自己慢，是它串在队伍里让全队慢。

所以内核段的优化问题等价于：**怎么让长尾别堵路**——这就是三招的由来。

## <span class="blue">长尾的三类成因 [E]

对着 `initcall_debug` 的 Top 20，先归类再开方：

| 成因类别 | 典型现场 | 钱的去向 |
|:---|:---|:---|
| 硬件等待 | 传感器等上电稳定、PLL 等锁定、eMMC 等就绪、HDMI 等 EDID | `msleep()`/轮询超时——数据手册要求的固定等待 |
| 枚举扫描 | USB 枚举、SDIO 扫描、PCIe 链路训练与枚举、I2C 探测 | 总线协议规定的探测过程 |
| 计算校准 | 解包 initramfs、算法自校准、加密自检 | CPU 纯算 |

分类的意义在于：三招对三类的效果完全不同——**硬件等待类删不掉只能异步或延后，枚举扫描类多半整个可以删，计算校准类靠换算法或预计算**。

拿摄像头的真实 Top 8 过一遍，演示"归类→开方"的判断过程：

```
 620ms  sdio_wifi_init        → 枚举扫描（SDIO扫卡+固件加载）
 480ms  ov5640_sensor_init    → 硬件等待（上电稳定+寄存器配置）
 210ms  usb_core_init         → 枚举扫描（产品无USB外设）
 180ms  bt_init               → 子系统init（产品无蓝牙功能）
 150ms  cma_declare_contiguous→ 计算校准（运行时分配触发整理）
 120ms  alsa_init             → 子系统init（产品无音频）
  90ms  ext4_rootfs_mount     → 启动关键路径，不能动
  60ms  hdmi_init             → 硬件等待（产品无屏，评估板残留）
```

逐条开方：SDIO WiFi——功能要留但不挡首帧，**延后**（改模块，网络管理器拉起前加载）；ov5640——产品主功能，删不得，**异步**（与后续 initcall 并行）；USB/蓝牙/音频——产品没有，**整类删**；CMA——改启动期预分配（**预计算**思路）；ext4 挂载——关键路径，不动；HDMI——评估板残留，**删**。八条账，每条三秒内能归完类——这就是"Top 20 工作清单"的实际用法。

## <span class="blue">第一招：删 [E]

收益最大、最该先做的永远是删。摄像头案例把 USB、蓝牙、音频整类子系统裁掉，省 300ms——裁掉的不只是驱动的 probe 时间，还有**子系统自身的初始化**（USB core、蓝牙协议栈、ALSA core 各自都有 initcall）和镜像体积（24.2 的加载时间跟着降）。

裁剪纪律两条：

1. **从"产品不需要什么"出发，不从"配置项是什么"出发**。先列产品的硬件清单（这块板子上实际有什么芯片、量产固件用哪些功能），凡不在清单上的控制器与协议栈整类关。厂商 SDK 的 defconfig 是为评估板的全功能准备的，直接用在产品上是内核段臃肿的头号原因。
2. **砍完过一遍启动日志**。`dmesg` 里出现 `probe failed -19`（ENODEV）之类的报错，说明设备树节点还在但驱动没了——节点和驱动要成对清理，否则留着节点白付设备树解析时间（后面"设备树精简"一节细说）。

> ⚠️ 别裁到启动关键路径：控制台串口、启动介质的存储控制器、根文件系统所需的块设备与文件系统——这些是"裁了就起不来"的清单。拿不准的配置项，宁留勿删，或者做成模块（第三招）而不是硬删。

## <span class="blue">第二招：异步 [E]

删不掉的硬件等待类长尾，让它别堵路。内核提供 async probe：驱动的 probe 函数声明可以异步执行后，`do_initcalls()` 不再等它，继续往下走——480ms 的传感器等待与后续 initcall **并行**进行。

```c
static struct platform_driver ov5640_driver = {
    .probe  = ov5640_probe,
    .driver = {
        .name           = "ov5640",
        .probe_type     = PROBE_PREFER_ASYNCHRONOUS,   /* 关键一行 */
        .of_match_table = ov5640_of_match,
    },
};
```

一行改动，但要想清楚两件事：

1. **谁依赖这个设备？** 异步意味着"probe 完成的时间点不再确定"——如果显示驱动要等摄像头就绪才能初始化（共享时钟、共享电源域），异步化就是引入竞态。内核的解法是设备依赖关系（fw_devlink/设备树的 `power-domains`、`clocks` 引用）会让依赖方自动等待，但**前提是依赖关系在设备树里表达完整**——这也是"优化后偶发启动失败"的主要来源（本节末尾细说）。
2. **用户空间什么时候能看到设备节点？** `/dev/video0` 的出现时间被推迟了——如果 init 脚本或应用启动时立即打开它，可能赶上设备还没 probe 完。对策：应用层改成等待设备节点出现（udev 事件或轮询），或者该驱动不异步（它就是关键路径本身，比如摄像头产品的相机驱动）。

## <span class="blue">第三招：延后 [E]

既不是关键路径、又不能在编译期删掉的（研发/产测要用），改成内核模块，启动后按需加载：

```kconfig
# 内置（启动时 probe，堵队伍）
CONFIG_USB_NET_DRIVERS=y

# 模块（启动后 modprobe，不占启动账）
CONFIG_USB_NET_DRIVERS=m
```

配套动作是**编排加载时机**：WiFi 固件加载那 620ms，改成系统起来之后、网络管理器拉起之前再 `modprobe`——它从启动关键路径上整个消失。注意"延后"和"异步"的区别：异步是内核内并行，仍然占启动窗口的 CPU；延后是彻底移出启动窗口，代价是功能可用时间推后——只适用于用户感知不到的功能。

> 💡 initramfs 里的模块是灰色地带：打进 initramfs 的模块在 rootfs 挂载前加载，仍然占启动账；只有确认"挂载根文件系统之前必须用"的模块才进 initramfs（存储控制器、文件系统），其余一律挪到 rootfs 里。

## <span class="blue">三笔零碎但真实的收益 [E]

**quiet 参数（-80ms）**：内核启动参数加 `quiet loglevel=3`，控制台输出从几百行压到几行——串口 115200 每秒约 11KB，几百行日志就是几百毫秒。正确姿势要记牢：**`quiet` 只关控制台输出，`dmesg` 缓冲区里的记录一条不少**——调试时登录后 `dmesg` 照样看全量。真正伤调试的是裁掉 `CONFIG_PRINTK`，那是另一回事，别做。

**设备树精简（-50ms）**：每个设备树节点都要解析、都要尝试匹配驱动。厂商 SDK 的设备树为评估板全配置准备，产品板上没有的设备（第二个网口、HDMI、扩展座）整节点删除——省解析时间，也省 probe 失败的时间。纪律与驱动裁剪成对：**节点删了驱动可以留（匹配不上自然跳过），驱动删了节点必须删**。

**CMA 预分配（-150ms）**：摄像头的 ISP/编码器需要大块连续物理内存，由 CMA（Contiguous Memory Allocator）提供。如果 CMA 区域不在启动时预留，camera 子系统初始化时会触发大块内存整理（ compaction，把零散的页搬走腾出连续区），这一步在内存已用的系统上可达数百毫秒。启动参数 `cma=256M` 在启动早期静态预留，把这笔开销从"camera 启动时的不确定卡顿"变成"启动早期的固定小开销"。推理：**凡需要大块连续内存的子系统（camera、GPU、DSP），CMA 都要启动期预分配**。

## <span class="blue">副作用：优化后偶发启动失败 [E]

24.1 说过优化有代价，内核段最典型的一种是：**优化后功能正常，但偶发启动失败**。根因几乎都是时序假设被打破——原来的代码里藏着"驱动 A 先于驱动 B 初始化"的隐式依赖（靠链接顺序保证），异步化或裁剪改变了顺序，依赖以竞态的形式暴露：十次里九次正常，一次 B 先跑、找不到 A 的资源，probe 失败。

对策三条：

1. **依赖显式化**：设备树里把 `clocks`、`power-domains`、`gpios`、`interconnects` 引用补全——内核靠 fw_devlink 自动建立 probe 顺序，依赖写全了，乱序也不怕；
2. **接受 `-EPROBE_DEFER` 语义**：驱动拿不到资源时返回 defer 让内核稍后重试，而不是写死轮询等待——defer 机制就是内核给乱序准备的官方答案（第 11 章讲过机制）；
3. **回归测试加抖动**：优化后的固件做启动压力测试（连续 reboot 几百次），偶发竞态只有数量能逼出来。

## <span class="blue">优化总表与验证 [E]

| 优化动作 | 长尾类别 | 典型收益 | 代价 |
|:---|:---|:---|:---|
| 整类子系统裁剪 | 枚举扫描 + 子系统 init | 100~300ms/类 | 功能（产测变体） |
| 异步 probe | 硬件等待 | 等待时间与后续并行 | 依赖必须显式化 |
| 改模块延后加载 | 各类 | 移出启动窗口 | 功能可用时间推后 |
| quiet 参数 | 控制台输出 | 50~100ms | 无（dmesg 仍在） |
| 设备树精简 | 解析 + 失败 probe | 30~80ms | 无（成对清理） |
| CMA 预分配 | 内存整理 | 100~300ms（camera 类） | 常驻内存预留 |

验证照旧：`initcall_debug` 前后各存一份 Top 20，摄像头案例的内核段从 2.2s 降到 1.3s——删 300ms（USB/蓝牙/音频）、异步传感器 init 收益约 400ms（与后续并行）、quiet 80ms、设备树 50ms、CMA 从 camera 首帧路径挪走 150ms。注意异步那 400ms 的收益体现在**总时间**上而不是该 initcall 的耗时上——它自己还是 480ms，只是不再堵路。

## <span class="blue">本节总结

内核段优化 = 长尾猎杀：先分清同步世界（动不了）和 initcall 世界（主战场），再用 `initcall_debug` 排出 Top 20，按成因分三类（硬件等待/枚举扫描/计算校准）对症下三招——**删**（整类子系统裁剪，从产品硬件清单出发、与设备树成对清理）、**异步**（`PROBE_PREFER_ASYNCHRONOUS` 一行改动，但依赖必须在设备树里显式化）、**延后**（改内核模块移出启动窗口，initramfs 只留挂载 rootfs 必需的模块）。

零碎三笔：quiet 只关控制台不关 dmesg、设备树与驱动成对精简、需要大块连续内存的子系统必须 CMA 预分配。副作用要防：优化打破隐式时序依赖，靠依赖显式化 + `-EPROBE_DEFER` + reboot 压力测试兜底。验证看总账不看单项——异步的收益体现在队伍不再被堵上。
