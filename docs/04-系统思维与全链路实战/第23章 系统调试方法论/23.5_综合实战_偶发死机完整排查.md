# 23.5 综合实战：一次偶发死机的完整排查

> 所属章节：第23章 系统调试方法论
>
> 难度：[E] | 预计阅读时间：45 分钟

## <span class="blue">本节导读

结案时间。23.1 登场的案子——仓库巡检机器人偶发死机，每周一两台、日志无异常、实验室不复现——本节从报案到结案走完整流程。它不是一个"正确答案演示"，而是一次**方法论的完整行军**：每一步用哪一节的哪条纪律、每个岔路口为什么这样选，都展开给你看。

先给你一张全程地图，读的时候可以随时对照位置：

```text
第0周  报案与症状分类（23.1）        → 偶发异常，黄金律：预先布设观测
第1周  观测四件套上线（23.2）        → pstore / 看门狗改造 / 最小监控 / 远程日志
第2周  第一批数据到手               → 临终栈 + 温度相关性，证据挂树（23.3）
第3周  判别实验序列（23.3）          → 温度叠加统计 → 烘箱加压复现
第4周  复现现场解剖                 → 逻辑分析仪抓电源轨，交叉验证
第5周  根因确认三关与修复           → 机制/互证/修复验证，回归固化（23.3）
第6周  复盘                         → 方法论兑现清单与成本对比
```

此前三周（报案前）团队已经空转过一次：翻日志、改参数、换驱动版本——这是本案例的第一个标本价值：**没有方法论的排查，三周等于零周**。

> 本节覆盖：报案与症状分类的原始记录、观测布设的落地细节、三批数据的逐一判读、假设树的消长过程、烘箱复现与电源轨解剖、根因确认三关的完整论证、修复方案与回归固化、全案复盘。

## <span class="blue">第 0 周：报案与症状分类

现场上报的原始信息：巡检机器人（RK3568 平台，Linux 5.10 定制内核，4G 回传）在三个仓库陆续"死机"——屏幕冻结、无 SSH 响应、物理按键无效，只能拔电池重启。频率约每周一两台、每台每月一两次。现场运维已通过断电重启恢复，未保留任何现场。

按 23.1 分类学过一遍：**终态是功能异常**（系统级挂死），但**过程是偶发异常**（低复现率、现场已被断电重启销毁）。偶发异常的黄金律自动生效：第一动作不是分析（无现场可分析），是**布设观测 + 找复现条件**。

报案会上还得到三条免费线索，先记下但不许过度解读（23.3 的纪律：证据挂双向）：①三个仓库中朝西、午后暴晒的那个仓库案发率明显偏高；②案发机器人都"刚执行完长距离巡检"；③有一台案发前一周刚换过电池仓的批次。三条都可能是真金，也都可能是幸存者口径——此刻它们只是假设树的待验证输入。

---

## <span class="blue">第 1 周：观测四件套上线

按 23.2 的方案落地，两天工作量：

**pstore/ramoops**：设备树在 DDR 顶部预留 1MB（`reserved-memory { ramoops@7ff00000 { ... } }`），内核打开 `CONFIG_PSTORE_RAM`+`CONFIG_PSTORE_CONSOLE`。验证：开发板上 `echo c > /proc/sysrq-trigger` 触发 panic，重启后 `/sys/fs/pstore/console-ramoops-0` 成功捞回临终日志——机制打通。

**看门狗改造**：硬件看门狗超时从"无操作"改为触发复位；复位前由一个高优先级 IRQ 线程往 pstore 里打最后状态快照（负载、内存、最后喂狗时间）。死机从"客户上门发现"变成"监控里的一次带现场复位"。

**最小监控集**：每 10 秒记录 CPU 温度、负载、内存剩余、PMIC 各路电压（机器人主板 PMIC 的电压轨可经 I2C 读寄存器——这条后面会证明是关键设计），本地环形存 7 天，复位后自动上传前 1 小时数据。

**远程日志**：内核与应用日志经 4G 实时推送中心服务器。

同时启动**复现条件排查**：实验室模拟巡检路线连续跑、压测、振动台——一周内零复现。这在预期内（偶发率摆在那），真正的复现要等环境线索。

> 💡 这一周的产出没有一行是在"调试"，全是布设与验证。团队里有人嘀咕"两周了什么都没修"——23.1 的时间账在这里复背一遍：偶发异常里，布设观测就是调试本身，而且是杠杆率最高的部分。

## <span class="blue">第 2 周：第一批数据到手

布设上线第九天，朝西仓库一台机器人死亡并自动复位。三份数据第一次同时到场：

**pstore 临终日志**（节选判读）：

```text
[  +0.004] INFO: task sensor_mgr:812 blocked for more than 122 seconds.
[  +0.001]       Tainted: G        W  O    5.10.66-custom #3
[  +0.002] "echo 0 > /proc/sys/kernel/hung_task_timeout_secs" disables this message.
[  +0.003] task:sensor_mgr state:D stack:0 pid:812 ppid:1 flags:0x00000004
[  +0.002] Call trace:
[  +0.001]  __schedule+0x2c8/0x708
[  +0.001]  schedule+0x44/0xd0
[  +0.001]  schedule_timeout+0x88/0xf8
[  +0.001]  wait_for_completion_timeout+0x70/0x98
[  +0.001]  rk3x_i2c_xfer+0x1a0/0x3e8
[  +0.001]  i2c_transfer+0xa8/0xd0
[  +0.001]  regmap_i2c_read+0x14/0x28
...
[  +0.004] NMI backtrace for cpu 3 skipped: idling at pc 0x...
```

判读：hung task 检测器抓到 `sensor_mgr` 进程在 **D 状态（不可中断睡眠）超过 122 秒**——它堵在一次 I2C 传输的完成等待里（`wait_for_completion_timeout` 上面的栈帧是 `rk3x_i2c_xfer`）。I2C 主机发出去了，完成中断永远没来。随后更多任务陆续堵在与该 I2C 总线相关的锁上，喂狗停止，看门狗复位。

**监控叠加图**：死机时刻 14:37，仓内温度曲线显示当日 14:00 起仓温 41℃、机身 CPU 温度 78℃；**PMIC 电压记录**里 3.3V 轨在 14:36:50 起出现一连串下冲尖峰（采样 10 秒一次，只抓到轮廓）。死前 5 分钟应用日志一切正常——A 族（应用逻辑错）的证据栏里，反对票+1。

**统计验证**：把三周 11 次案发与仓温曲线做叠加——11 次全部落在仓温 >36℃ 时段，而朝西仓库同期 >36℃ 的时段占总时长的 31%。若死机与温度无关，11 次全部落进 31% 时段的概率约 0.31¹¹ ≈ 百万分之三。相关性成立，且这不是"上周三高温时确实死了"的幸存者口径——分子分母都摆在这。

## <span class="blue">假设树的消长

把三批证据挂上 23.3 建好的树，各分支现状：

| 分支 | 证据变动 | 状态 |
|------|---------|------|
| A 应用层（A1~A3） | 死前日志正常；hung task 栈在驱动等待而非应用锁 | 大幅压低，未排除（栈顶应用只是受害者候选） |
| B1 内核死锁 | 栈形态不像死锁（在等硬件完成而非持锁互等） | 压低 |
| B2 中断风暴 | 临终期无 IRQ 异常计数 | 排除 |
| B4 内核内存耗尽 | 监控内存余量正常 | 排除 |
| **C1 驱动等硬件永不返回** | **栈顶实锤** | **症状层定位：就是它** |
| C2 协处理器/PMIC 固件 | 无直接证据 | 保留 |
| **D1 电源跌落** | **温度强相关+电压尖峰轮廓** | **升为头号根因嫌疑** |
| D2 DDR 时序 | 高温兼容，无直接证据 | 保留 |
| D3 虚焊 | 批次线索（换电池仓）指向过，但温度统计覆盖全部批次 | 压低 |
| D4 eMMC | 无 IO 异常计数 | 排除 |
| E1 高温 | 统计成立——但它是条件不是根因 | 转化为加压方向 |
| E2 电网质量 | 三仓库都有案发，公共性弱 | 压低 |
| E3 振动 | 巡检中振动常态，无时间相关性 | 排除 |

此刻树的状态完美演示 23.3 的一个要点：**症状层（C1）和根因层（D1/D2）开始分离**。栈顶告诉我们系统"怎么死的"（I2C 等待永不返回），但它不回答"硬件为什么不应答"——答案在物理层。如果此刻停手去改 I2C 驱动加超时，那就是 23.4 陷阱三的路径：把报警器当事故，修出一个掩盖症状的方案。

## <span class="blue">第 3 周：判别实验——烘箱加压复现

按 23.3 排的实验序列，序 3 上场：环境舱设定 55℃（仓温 41℃ + 机身温升裕量，高于现场不高于器件极限），机器人满路线连续巡检。

结果：**复现率从"每月一两次"变成"平均 5 小时一次"**——三天收集 9 次挂死，全部呈现相同的症状签名（I2C 挂起→看门狗复位→pstore 同款栈）。症状签名比对通过（23.1 的防伪纪律）：这不是加压引入的新 bug，是同一个死法被催熟了。

复现率抬升两个数量级的意义立刻兑现：序 4 这种"必须守在死亡现场"的测量，从不可能变成日常班次。

## <span class="blue">第 4 周：复现现场解剖

逻辑分析仪挂上 3.3V 电源轨与 I2C 总线（SDA/SCL），烘箱内等到第 3 次复现，抓到了完整的死亡过程：

```text
T-38ms   电机驱动电流骤升（长直道加速段）
T-36ms   3.3V 轨从 3.31V 跌到 2.68V，持续约 22ms
T-34ms   I2C 挂在此轨的传感器电源欠压，应答停止
T-34ms   SCL 被从设备拉低不放（欠压状态下的从机常见行为：总线锁死）
T-0      I2C 主机等完成中断永不至 → sensor_mgr 进 D 状态
T+122s   hung task 告警 → 相关锁连锁 → 喂狗停止 → 看门狗复位
```

**机制链完整浮出**：55℃ 环境下 DC-DC 转换效率下降、输出裕量收窄 → 电机加速浪涌电流抽干 3.3V 轨 → 电压跌破 I2C 传感器工作下限（2.7V）→ 传感器欠压锁死总线（SCL 持续拉低）→ I2C 主机永远等不到完成 → 用户态任务 D 状态堆积 → 看门狗复位。**高温不是根因，是缩小电源裕量的条件；浪涌不是根因，是触发器；根因是 3.3V 轨在高温工况下的瞬态裕量不足，叠加欠压时 I2C 总线锁死的硬件行为。**

为什么表现为"挂死"而不是"复位"？PMIC 的欠压复位阈值设在 2.5V——跌落到 2.68V 恰好落在**"传感器已死、SoC 还活着、复位不触发"的灰色地带**。SoC 以为世界还在，外设已经阵亡，系统就这样"活着死了"。

交叉验证（23.3 三关之二）：证据一，pstore 栈（I2C 等待，软件视角）；证据二，逻辑分析仪波形（电源轨跌落+SCL 锁死，物理视角）——两个独立测量互证同一条因果链。再加旁证：把该传感器从 3.3V 轨改挂到稳定的 3.3V 辅助轨上复测 72 小时，零复现——切断因果链中的一环，症状消失。

> 💡 一个值得记住的硬件常识：I2C 从设备欠压时把 SCL/SDA 拉低不放是多种器件的真实行为（从机状态机掉电卡在中途）。这解释了为什么"电源问题"经常以"I2C 挂死"的形态报案——症状层的 I2C 驱动从第一行代码起就是无辜的。

## <span class="blue">第 5 周：修复、验证与回归

根因定了，修复分三层，各管一段因果链：

**硬件层（治本）**：3.3V 轨输出电容加大并并联低 ESR 钽电容吸收浪涌；I2C 传感器群改挂带独立 LDO 的辅助电源轨。下一批 PCB 改版落实；存量设备出改版 sensor 转接板。

**软件层（止血与报警）**：I2C 传输加超时与总线恢复（检测到 SCL 锁死，按规范打 9 个时钟脉冲解锁总线+复位主机控制器）——下次再发生，系统报警并自愈而非挂死；PMIC 欠压复位阈值从 2.5V 上调到 2.9V——灰色地带消灭，"挂死"降级为"可记录的复位"（复位比挂死好一百倍：它留下现场、自动恢复、监控可见）。

**监控层（长期哨兵）**：PMIC 电压采样从 10 秒加密到 1 秒并加欠压告警——同类问题今后的第一报警人。

**修复验证**：改版后的机器人在 55℃ 烘箱满路线连跑 7 天，零复现；软件止血层在人为拉低电源轨的注入测试里，100% 触发恢复路径并产生告警日志。**回归固化**：烘箱 55℃×72h 满路线测试写入产线抽测流程；欠压注入测试进研发回归套件——这个死法正式除名。

## <span class="blue">第 6 周：复盘

**时间账**：报案前空转 3 周（翻日志/试参数/换驱动，零产出）；方法论流程 6 周结案（布设 1 周、等数据 1 周、实验 2 周、修复验证 2 周）。后 6 周里真正的"分析"只有几天——其余是让数据自己成熟的必要等待。**偶发问题的真实成本单位是"观测周期"，不是"工时"**——这个认知能让管理层对排期有正确预期。

**方法论兑现清单**：

| 纪律（出处） | 本案兑现 |
|-------------|---------|
| 症状分类（23.1） | 偶发异常 → 第一动作布设观测而非翻日志 |
| 复现率是第一生产力（23.1） | 烘箱把月级复现催成 5 小时级，现场解剖才可行 |
| 症状签名比对（23.1） | 加压产物与原症状签名一致，排除"自造新 bug" |
| 观测三层栈（23.2） | 监控缩窗（温度）→ pstore 临终栈（怎么死）→ 分析仪解剖（为什么死） |
| 假设树与判别力排序（23.3） | 温度统计一刀砍掉 A/B 族大半分支 |
| 三关确认（23.3） | 机制链完整+两独立证据互证+断环复现消失+回归固化 |
| 报警器≠事故（23.4 陷阱三） | 看门狗从"嫌疑人"变"黑匣子"，I2C 栈顶从"凶手"变"受害者" |
| 症状层≠根因层（23.4） | C1 是死法，D1 是死因；改 I2C 驱动只能止血不能除根 |

**遗留观察项**（三关后的 1% 尊重）：修复后保持监控观察一个夏季——D2（DDR 高温时序）分支只是压低未排除，若今夏出现签名不同的新死法，树还在，随时重新挂证据。

## <span class="blue">本节总结

机器人案的全貌：一次"无头偶发死机"，六周走完"分类→布设→数据→建树→复现→解剖→三关→回归"的完整行军，根因是 3.3V 电源轨在高温工况下瞬态裕量不足、触发 I2C 传感器欠压锁死总线——症状层（I2C 挂起）和根因层（电源跌落）隔着整整两个抽象层，这正是报案前三周空转的原因：所有努力都打在了症状层。案件同时验证了本章的核心论断：偶发问题的成本单位是观测周期不是工时；复现率是调试的第一生产力；"症状的层≠根因的层"是七个陷阱共同的妈妈。修复的三层结构（硬件治本/软件止血报警/监控放哨）是根因修复的标准形态——治本让死法除名，止血让万一复发时系统自愈留证，放哨让同类问题早警。

### 本节自查

- 能把一个偶发问题按"分类→布设→数据→树→复现→三关"排出六周计划，并向管理层解释排期逻辑
- 能从 hung task 栈里读出"任务在等硬件"和"任务在等锁"的区别
- 能设计加压复现方案并用症状签名比对防伪
- 能论证"改 I2C 驱动加超时"为什么只是止血不是除根
- 能把根因修复拆成"治本/止血/放哨"三层
- 修复后能坚持把复现流程固化进产测/回归，并保留观察期
