# 23.4 常见陷阱：看似是 A 问题，实际是 B 问题

> 所属章节：第23章 系统调试方法论
>
> 难度：[M] ~ [E] | 预计阅读时间：35 分钟

## <span class="blue">本节导读

前三节给了你框架：分类、观测、假设-验证。本节是一面案例墙——嵌入式调试历史上反复重演的"看似 A 实为 B"错位，每个案例都按同一个格式解剖：**表象**（你看到什么）、**错误路径**（大多数人怎么走进死胡同）、**拐点**（哪个观测或纪律本可以救人）、**真凶与机制**、**条款**（对应前三节的哪条纪律）。

这些案例的价值不在答案本身——你迟早会遇到它们中的一部分，遇到时认得出来就省了别人付过的工期。更重要的是看错落位的共同结构：**症状显现的层和根因居住的层之间，隔着一层或多层**，而直扑症状层的本能每次都赢过分层证伪的纪律。23.1 的分层链在这里兑现利息。

> 本节覆盖：七个经典错位（OOM 疑云、CPU 100% 真身、死机背锅侠、网络丢包冤案、Heisenbug 的把戏、越用越慢的两种死因、"内核 bug"的最后答案）+ 陷阱与纪律的对照总表。

## <span class="blue">陷阱一：OOM Killer 杀了你的进程 ≠ 你的进程吃了内存

**表象**：日志里 OOM Killer 精准地杀掉了你的业务主进程，所有人都看着你说"你的程序内存泄漏"。

**错误路径**：给自己的进程做内存体检——valgrind、asan、逐行 review 分配路径，一无所获（因为确实没漏），开始怀疑人生。

**拐点**：把 OOM 的完整日志读完而不是只读最后一行。OOM Killer 的选择是**按当时的内存占用排序打分**挑牺牲品的——被杀的只是"此刻最肥的"，不是"漏了的"。看日志前面的全系统内存统计段：`cat /proc/meminfo` 的历史趋势、各进程 RSS 排名（`ps aux --sort=-rss | head`）。

**真凶与机制**：同机的另一个进程（常见是日志服务、缓存服务、某个定时任务）缓慢泄漏数周，你的主进程只是体量最大被选中献祭。嵌入式变体更冤：**tmpfs/共享内存**（/dev/shm、/run）不计入任何进程的 RSS，但实实在在吃物理内存——RSS 排名全员清白，内存照样耗尽。

**条款**：症状分类先做好（这是"功能异常"，先固定现场=读完完整 OOM 日志）；23.2 的"监控趋势告警抓泄漏"——阈值告警永远等不到这一天，趋势告警在漏第一周就报警。

## <span class="blue">陷阱二：CPU 100% ≠ 代码跑得慢

**表象**：top 里 CPU 100%，应用响应迟钝。结论是"算法太慢，要优化"。

**错误路径**：逐函数 profiling、SIMD 优化、算法换数据结构——性能纹丝不动。因为 perf 报告里那个"热点"根本就不是你的代码。

**拐点**：看 CPU 时间的**构成**而不是总量。`mpstat 1` 拆开 `%usr %sys %softirq %iowait`：usr 高才是应用慢；softirq 高是内核在替你扛活；iowait 高是"CPU 在等盘"——它算在"忙"里但其实 CPU 闲得发慌。

**真凶与机制**（三种常见真身）：**中断风暴**——某个外设/网卡中断频率失控，softirq 占满一个核，应用只是被挤得没机会跑（看 `/proc/interrupts` 逐秒增量，某个 IRQ 每秒几十万次就是它）；**锁竞争**——多线程应用里一把热锁，线程们排队自旋烧 CPU（perf top 里 spinlock 函数登顶）；**iowait 伪装**——存储慢导致的"100%"，优化代码纯属南辕北辙。

**条款**：23.2 的 vmstat 判读示范就是为此准备的——"看均值会误诊"；23.3 的判别实验：mpstat 一分钟，三个真身直接分家。

## <span class="blue">陷阱三：偶发死机的背锅侠——看门狗

**表象**：设备偶发"死机"，现场日志最后一行是看门狗驱动报的复位——"看门狗把系统搞重启了"。

**错误路径**：禁用看门狗，"问题消失"——其实死机照旧，只是设备死了没人收尸，从"自动复位的偶发故障"变成"客户上门发现的永久停机"。

**拐点**：分清因果方向。看门狗复位是**结果**——它复位是因为系统先死了（没人喂狗）。日志时间线对齐：复位事件前系统就已经无响应，看门狗只是验尸官兼收尸人，不是凶手。

**真凶与机制**：真凶在别处（电源、内存、驱动——23.5 的机器人案就是这条路径的完整版）。看门狗不仅无罪，还是偶发死机的第一恩人：它把"挂死等人发现"变成"自动复位+留下 pstore 现场"（23.2 的四件套第二件）。

**条款**：23.1 的认知模型——"矛盾即路标"在这里的形态是**别把报警器当事故**；23.2 的看门狗改造把报警器升级成黑匣子。

## <span class="blue">陷阱四：网络丢包冤案——驱动不总是凶手

**表象**：iperf 打流丢包/吞吐不达标，第一反应"网卡驱动有问题"或"PHY 硬件不行"。

**错误路径**：换驱动版本、调 PHY 寄存器、怀疑变压器——嵌入式网口问题的经典三件套， weeks 级消耗。

**拐点**：分层链上先问一句"包在哪一段丢的"。`ethtool -S eth0` 的计数器把话说清楚：rx_missed/rx_fifo_errors 涨是**接收端来不及取**（CPU 软中断处理不过来，不是链路丢）；tx 方向正常、对端收到乱序是交换机的事；只有 rx_crc_errors 涨才轮到 PHY 和线缆。

**真凶与机制**（高频真身）：**接收侧 CPU 瓶颈**——单核跑满 softirq，网卡 FIFO 溢出丢包，表现为"丢包"实为"收不动"（NAPI 权重、中断聚合、RSS 多队列分流可解）；**流控背压**——对端发太快触发了 pause 帧或直接溢出；**全双工/速率协商错位**——一端 100M 全双工一端自协商残废成半双工，冲突丢包。

**条款**：分层证伪（链路/驱动/协议栈/CPU 四层各有一个观测接口）；B-C 板块的网络篇有协议栈各层计数器的完整地图。

## <span class="blue">陷阱五：Heisenbug——加打印就好了，删打印就复发

**表象**：偶发崩溃/数据错乱，加一行打印想抓现场——它不复现了。删了打印，又回来了。怀疑编译器优化、怀疑编译选项、怀疑人生。

**错误路径**：在"打印加哪"和"优化开几级"之间反复横跳，永远抓不到稳定现场。

**拐点**：认出这个行为模式本身就是诊断结论——**观测改变行为=时序敏感=竞争条件或内存踩踏**，几乎从不例外。打印拖慢了某个线程几十微秒，原本会输的赛跑现在赢了。

**真凶与机制**（两类）：**锁缺失/顺序错误的竞争**——两个线程对共享数据的访问窗口在特定时序下重叠；**内存踩踏**——越界写恰好踩到另一个变量的时机窗口。对应的抓捕工具也要换"不改变时序"的：不改代码的观测（ftrace 跟踪点、core dump 事后分析）、静态检查（编译器警告拉满、thread sanitizer 在开发机上跑）、**提升复现率**（23.1 三件套里的"加扰"——给线程调度注入随机延迟，让赛跑输得更频繁）。

**条款**：23.1 的 Heisenbug 概念卡；23.3 实验设计——观测手段本身要进"变量清单"：加了打印的系统已经不是原来的系统。

## <span class="blue">陷阱六：越用越慢——两种长得一模一样的死因

**表象**：设备跑几周后逐渐变卡，重启就好，好完又慢慢变卡。"内存泄漏"成为全场唯一嫌疑人。

**错误路径**：盯 RSS 趋势——它平得像一条直线，没有泄漏。排查陷入僵局，"定期重启"被当成解决方案写进运维手册（这是症状管理，不是修复）。

**拐点**：内存的故事不只在 RSS 里。两个常驻真凶各有观测口：

**真凶 A：slab/内存碎片**。长期运行的内核里 slab 缓存膨胀、内存碎片化——`cat /proc/meminfo` 的 Slab 行持续增长、`/proc/buddyinfo` 里大块连续页越来越少。RSS 看不出，因为它不是用户态内存。结局：大块分配（DMA、高阶页）失败，IO 路径变慢变卡。

**真凶 B：存储老化降速**。eMMC/SD 卡的写放大与垃圾回收随磨损加剧——`iostat -x` 里 await 逐周爬升，CPU 的 iowait 随之爬升，"系统变慢"实为"盘变慢"。监控里加一条存储 await 趋势，这类死因从"玄学"变成"曲线"。

**条款**：23.2 监控层——"正常基线"要覆盖 Slab、buddyinfo、存储 await 这些二线指标，一线指标正常不等于系统健康。

---

## <span class="blue">陷阱七："这是内核/编译器的 bug"——最后才轮到它

**表象**：代码逻辑审了八遍没问题，行为就是错的。"内核 bug"或"编译器优化 bug"成为桌面上唯一的解释。

**错误路径**：降优化等级、换内核版本、给社区发邮件——偶尔"恰好"好了（优化等级改变时序，同陷阱五），多数时候原地打转。

**拐点**：一条统计纪律——**你遇到内核/编译器真实 bug 的先验概率，远低于你自己的代码里有一个你还没看到的假设错误**。开工"怀疑系统软件"之前，先完成三件事：把自己代码里所有"它一定是这样"的假设列出来逐一验证（内存模型、API 语义、初始化顺序）；在最小复现工程里重现场景（剥离业务代码后问题还在，嫌疑才轮得到系统软件）；查勘误表（SoC 的 errata 文档——**硅 bug 比内核 bug 常见**，"uart 在特定波特率下丢字节"这类条目真实地躺在 errata 里）。

**真凶与机制**：九成九是自己代码里的隐性假设（API 的边界条件、未同步的共享访问、未初始化的边界路径）；剩下的零头里，SoC errata 占大头，内核/编译器 bug 是真有——但它是排完所有其他项之后剩下的那个，不是第一个跳出来的那个。

**条款**：23.3 建树纪律一——"我觉得不可能"的层恰恰要列进树里，但**排序按先验概率**：系统软件是树的最后一层，不是第一层。

## <span class="blue">陷阱与纪律对照总表

| 陷阱 | 症状的层 | 真凶的层 | 本可救场的纪律 |
|------|---------|---------|---------------|
| OOM 冤案 | 被杀的进程 | 别的进程/tmpfs | 读完整现场；趋势告警 |
| CPU 100% | top 总量 | 中断/锁/IO | 拆构成看形态（mpstat/perf） |
| 看门狗背锅 | 复位日志 | 先发生的挂死 | 报警器≠事故；因果方向对齐 |
| 丢包冤案 | "网络不通" | CPU/流控/协商 | ethtool -S 分层定位 |
| Heisenbug | 偶发错乱 | 竞争/踩踏 | 观测进变量清单；换零扰动观测 |
| 越用越慢 | "内存泄漏" | slab 碎片/存储老化 | 二线指标进基线 |
| 系统软件背锅 | 自己的症状 | 自己的假设/errata | 先验概率排序；最小复现 |

错位共同结构一句话：**症状的层≠根因的层，而本能永远指向症状的层**——这就是 23.1 分层证伪纪律存在的全部理由。

| 维度 | 评价 |

| 案例库经验 vs 方法论框架 | 案例库碰到同款时秒解，碰不到时归零；框架慢但全覆盖——本节是前者的索引，前三节是后者 |

| 直觉直扑 vs 分层证伪 | 直觉在 30% 的时候快一天，在 70% 的时候慢两周；分层证伪把期望时间压到稳定 |
| 怀疑系统软件 | 排完所有层之后的合法结论；作为第一反应时，它是放弃思考的体面说法 |

## <span class="blue">本节总结

七个陷阱的共同结构：症状显现的层和根因居住的层之间隔着层，而直扑症状层的本能每次都比分层证伪的纪律先出手——OOM 杀的是最肥的不是漏了的，CPU 100% 的真身常是中断/锁/IO 而不是代码，看门狗是收尸人不是凶手，丢包的凶手常在 CPU 和协商表而不在 PHY，加打印就好=时序敏感=竞争或踩踏，越用越慢有两个 RSS 看不见的死因（slab 碎片、存储老化），"内核 bug"是先验概率最低的合法结论。对照总表把每个陷阱映射回前三节的纪律——它们不是孤立的劝诫，每一条都是这类错位案例的通用解药。下一节 23.5 把全章收进实战：机器人偶发死机案从报案到结案，假设树的每个分支怎么倒下，最后一个分支怎么站起来。

关键结论速查：

| 问题 | 一句话答案 |
|------|-----------|
| 错位的共同结构 | 症状的层≠根因的层，本能永远指向症状的层 |
| OOM 被杀≠泄漏 | 被杀的是最肥的牺牲品；tmpfs 不进 RSS 也要查 |
| CPU 100% 三真身 | 中断风暴/锁竞争/iowait——mpstat 拆构成一分钟分家 |
| 看门狗复位 | 系统先死，狗收尸——禁看门狗=扔掉黑匣子 |
| 加打印就好 | 时序敏感的签名：换零扰动观测+加扰提升复现 |
| 越用越慢 RSS 正常 | 查 Slab/buddyinfo（碎片）和存储 await（老化） |
| "内核 bug" | 排完所有层才轮得到；SoC errata 比内核 bug 更常见 |

### 本节自查

- 七个陷阱各自能说出"错误路径为什么看起来合理"——理解本能，才能对抗本能
- 遇到 OOM 杀进程，第一反应是读完整日志+查全系统与 tmpfs，而不是审受害者
- 遇到 CPU 100%，先 mpstat 拆构成再决定优化方向
- 遇到观测改变行为的现象，能直接报出"时序敏感/竞争/踩踏"三个关键词
- 排查清单里为 slab 碎片和存储老化留了位置（长期运行设备）
- 能把"怀疑系统软件"压到假设树排序的末尾，并知道 errata 文档的存在
