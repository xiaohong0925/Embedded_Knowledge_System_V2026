## 核心问题

出了问题怎么系统调试？——面对"偶发死机""偶发卡顿"这种没有稳定复现路径的问题，怎么从一团症状走到一个能验证、能修复的根因？

## 本章简介

本章不调试某个具体子系统，而是调试"整个系统"。高级工程师的调试能力不在于他会多少个工具，而在于他能在复杂系统里建立"假设-验证"的思维链条：先把症状归类，再按症状选择信息收集手段，然后用假设树收敛范围，最后设计实验把根因钉死。

主线一句话：**框架决定上限，工具决定下限**。没有方法论，工具再多也只是在现场碰运气；有了方法论，即使工具受限，也能知道下一步该补什么信息。

本章用一个贯穿案例落地全部方法：一台仓库机器人（RK3568，Linux 5.10）在现场偶发死机——23.1 登场分类，23.2 布设信息收集四件套（pstore/看门狗/最小监控/远程日志），23.3 建假设树并排定实验序列，23.4 复盘同类案件里的典型误判，23.5 完整结案。

## 学习目标

- 面对一个陌生故障，能先归类（性能/功能/偶发），再决定收集什么信息
- 能为现场设备布设 pstore、看门狗、最小监控、远程日志四件套，并说明各自解决什么盲区
- 能为一个偶发问题画出假设树，并按"信息量/成本"排定实验顺序
- 能识别"症状层与根因层不一致"的典型陷阱模式，避免在错误方向上投入
- 能完整走通一次"接报→信息收集→假设→验证→修复→回归"的调试闭环
