# 23.3 假设-验证法：缩小问题范围的科学方法

> 所属章节：第23章 系统调试方法论
>
> 难度：[E] | 预计阅读时间：30 分钟

## <span class="blue">本节导读

23.2 的四件套装上机器人一周后，数据来了三份：pstore 捞到了第一段临终 dmesg 尾部，监控曲线显示死机时刻与仓内高温时段高度重合，远程日志显示死前 5 分钟系统一切正常。线索不少——但**线索多不等于方向明**。三个线索指向不同方向（临终栈在驱动层、温度指向硬件层、日志正常指向"非软件逻辑错误"），如果没有一个组织线索的框架，接下来的排查就是东一榔头西一棒子：今天怀疑驱动改一版，明天怀疑电源换个件，两周后问题还在，而你已经记不清哪次实验排除了什么。

假设-验证法就是这个组织框架，它是科学方法在调试里的直接应用：**把"可能是什么"显式列成一棵假设树，用实验逐一分支证伪，直到只剩一个分支——那就是根因**。它和 23.1 的关系：23.1 教的是原则（复现优先、分层证伪），本节教的是流程（树怎么建、实验怎么排、什么算确认）。23.5 的完整破案，走的正是本节这棵树的每一条枝。

> 本节覆盖：假设树的构建方法（列全候选根因族）、实验设计的两条铁律（单变量、可证伪）、判别力排序（先做哪个实验）、机器人案例的假设树成稿、根因的确认标准（交叉验证）与确认偏误陷阱。

## <span class="blue">假设树：把"可能是什么"列全

调试低效的头号原因不是验证慢，是**候选根因从一开始就没列全**——脑子里只有最先想到的两三个嫌疑，它们恰好都不是根因时，排查就陷入"反复验证同样的假设"的死循环。假设树的价值首先在这里：它强迫你把根因空间**系统地展开**，而不是只看你顺眼的角落。

建树的方法是从症状出发，沿系统的层次把每一层能导致此症状的根因族列出来。对机器人的"挂死"（屏幕冻结、无响应、需断电重启），第一级展开：

```text
症状：系统级挂死（无响应、需断电重启）
│
├─ A. 应用软件层
│    ├─ A1 应用进程死锁（业务锁顺序错误）
│    ├─ A2 应用内存耗尽引发连环 OOM
│    └─ A3 应用把某个驱动/设备节点打挂
│
├─ B. 内核层
│    ├─ B1 内核死锁（驱动持锁睡眠、RCU 停滞）
│    ├─ B2 中断风暴/中断线程占满 CPU
│    ├─ B3 调度子系统异常（RT 任务饿死一切）
│    └─ B4 内核内存泄漏→耗尽→kswapd 风暴
│
├─ C. 驱动/固件层
│    ├─ C1 驱动等待硬件响应永不返回（I2C/SPI 超时缺失）
│    └─ C2 协处理器/PMIC 固件异常拖死总线
│
├─ D. 硬件层
│    ├─ D1 电源跌落（高温→PMIC 降载→电压不稳→SoC 锁死）
│    ├─ D2 DDR 时序 marginal（高温下信号完整性失稳）
│    ├─ D3 虚焊/接触不良（热胀冷缩断开）
│    └─ D4 eMMC 老化坏块导致关键 IO 卡死
│
└─ E. 环境层
     ├─ E1 高温（与 D1/D2 联动）
     ├─ E2 电源质量（仓库大功率设备启停拉低电压）
     └─ E3 振动（连接器松脱）
```

三个建树纪律。**分层列全**：每一层都问"这一层有没有可能造成这个症状"，不许跳过"我觉得不可能"的层——23.4 会告诉你，最终根因住在"我觉得不可能"的层里的概率高得反常。**根因族而非根因**：第一级展开列的是"族"（A1 是"应用死锁"这一类），具体是哪把锁、哪段代码，是验证到那一步才展开的事——一开始就列太细，树会漏枝。**每条分支标注"什么证据支持/反对它"**：已有的三条线索此刻就挂上去——温度重合支持 D/E 族，pstore 临终栈在驱动层支持 C 族，死前日志正常反对 A2/B4（这两类死前通常有内存压力迹象）。

树建好的标志：**每个分支都是可证伪的**——存在某个实验或观测，它的某个结果能明确排除这个分支。写不出证伪方法的分支不是假设，是信仰。

> MECE 的实用口径：严格"不重不漏"做不到，追求"主干不漏"。一个兜底问题能帮大忙："如果这个症状发生在别的设备上，我还会怀疑什么？"——它能把被当前设备细节锚住的思维解放出来，E 层（环境）经常是这样被补进树里的。

## <span class="blue">实验设计：两条铁律

假设树给地图，实验给脚步。实验设计质量决定排查是收敛还是发散，铁律就两条：

**铁律一：一次只改一个变量。** 改了驱动同时换了电源，问题消失——你不知道是谁的功劳，更糟的是你以为知道了。多变量实验的"成功"是调试里最昂贵的假币：它给你虚假的根因自信，问题在下一批设备上换个组合再回来。工程上唯一允许的多变量是**确认性实验**（根因已定位，验证修复包整体有效）——定位阶段，永远单变量。

**铁律二：实验前写下预期。** 每个实验动手前先写："如果假设 X 成立，我预期看到 Y；如果看到 Z，X 被排除。"没写预期的实验是钓鱼——看到什么就解释成什么，确认偏误会替你把任何结果都解释成支持原假设（下一节展开这个陷阱）。预期写不出来，说明这个实验没有判别力，换一个。

### 判别力排序：先砍哪一刀

树有二十个分支，实验资源有限，排序按两个轴：

**判别力优先**：一个实验能把树砍成两半的，先做。温度叠加图就是这样的实验——"死机与高温时段的相关性"直接把 E1 从分支提升为强嫌疑，同时把 A 族（与温度无关的软件逻辑错）的先验概率大幅压低。**成本修正**：判别力相近时，便宜的先做——查 `/proc/interrupts` 历史（一分钟）排在拆机量电压（半天）前面，哪怕后者的判别力略高。

机器人案例的第一轮实验序列就是这样排的：

| 序 | 实验 | 针对分支 | 预期（假设成立时） | 成本 |
|---|------|---------|-------------------|------|
| 1 | 读 pstore 临终栈内容 | B/C 族全体 | 栈顶函数指向具体子系统 | 分钟级 |
| 2 | 死机时刻×温度曲线叠加统计 | E1 vs A 族 | 相关系数显著则 E1 成立 | 已布设 |
| 3 | 烘箱加压复现（60℃ 环境舱） | D1/D2/D3 | 复现率从"每月一次"变"每天数次" | 半天 |
| 4 | 复现态下挂逻辑分析仪量电源轨 | D1 | 死前电压轨出现跌落/抖动 | 一天 |

注意序 3 就是 23.1 的"加压复现"在兑现：烘箱把复现率抬两个数量级之后，序 4 这种"必须守在复现现场"的测量才变得可行——**观测布设、复现率、判别实验，三节的内容在这里扣成一条链**。

## <span class="blue">确认标准：什么才算"找到根因了"

某个分支在实验里活到最后，是不是就可以宣布破案？还不够。调试史上的大量"修复"死于把"强相关"当成"根因"。确认根因要过三关：

**机制关**：能讲清楚从根因到症状的完整因果链，每一环都有证据或已验证的机制支撑。"电源跌落导致 SoC 锁死"要能讲出：跌落到什么程度、触发了 SoC 的什么行为（欠压锁死还是 DDR 训练失败）、为什么表现为"挂死"而非"重启"。讲不出机制的"修复"大概率是碰对了触发条件没碰对根因。

**交叉验证关**：至少两个**相互独立**的证据指向同一结论。pstore 临终栈显示挂在 I2C 等待（证据一）+ 逻辑分析仪抓到死前电源轨跌落（证据二）——两个独立测量互证。反例：同一份日志里的两行互相印证不算交叉验证，它们共享同一个信息源，可能共享同一个错误。

**修复验证关**：针对根因的修复（不是绕过症状）上线后，在原复现条件下症状消失，且能解释"为什么这个修复消除了因果链的哪一环"。最后是 23.1 说过的终点：复现流程固化成回归测试——烘箱测试进产测流程，这个死法才从你的产品里正式除名。

> 💡 一个实用的置信度标尺：过机制关=60%，加交叉验证=85%，加修复验证+回归=99%。剩下 1% 留给"还有第二个潜伏根因"——复杂系统里两个根因共享一套症状并不罕见，修复后主根因消失、次根因以更低频率继续作案。修复后继续保持观测一个月，是对这 1% 的尊重。

## <span class="blue">确认偏误：假设-验证法的头号内鬼

方法论最大的敌人不在系统里，在脑子里。**确认偏误**：人一旦有了一个假设，会不自觉地去寻找支持它的证据、忽略或重新解释反对它的证据。调试里的典型形态：

**钓鱼式实验**：不测预期，看到什么解释成什么——日志里翻到一条 WARN，"就是它了"，尽管这条 WARN 在健康设备上也每天出现。**沉没成本绑架**：在某分支上投入三天后，反对证据出现时的本能反应是"再验证一次"而不是"换分支"——树是拿来砍的，不是拿来守的。**幸存者口径**：只统计支持样本（"上周三高温时确实死了"），不统计反例（"上周四五次高温都没死"——相关性当场破产）。

对抗手段都写在流程里而不靠意志力：实验前写预期（铁律二）；树的分支上同时挂支持与反对证据（建树纪律三）；以及一个团队实践——**让没参与排查的人评审你的证据链**，没有预设立场的眼睛对偏误天然免疫。23.4 的陷阱案例里，至少有三个的真凶是确认偏误，技术是配角。

## <span class="blue">方案对比（Trade-off）

| 维度 | 评价 |
|------|------|
| 先列全树再验证 vs 边想边试 | 树的前期成本半小时；边想边试的死循环成本按周计 |
| 单变量纪律 vs 打包实验 | 打包实验省时于一时，假根因浪费于一世；只有确认性实验允许打包 |
| 判别力优先 vs 成本优先 | 默认判别力优先；判别力相近时便宜先行——别为省半天把判别力第二的实验拖到最后 |
| 强相关即根因 vs 三关确认 | 强相关只值一个"优先嫌疑"；机制/交叉/修复三关过完才叫根因 |
| 独自排查 vs 引入评审 | 独自排查高效但偏误无人拦截；关键节点一次外部评审，成本一小时收益一条命 |

## <span class="blue">本节总结

假设-验证法把调试从"碰运气"变成"可收敛的流程"：假设树强迫你分层列全根因族（每个分支可证伪，证据挂双向），实验设计两条铁律（单变量、预期先行）保证每一步产生真信息，判别力×成本决定实验顺序——机器人案例里，温度叠加图这一刀把二十个分支砍到个位数，烘箱加压把"守在复现现场"的测量变得可行。确认根因要过三关：机制关（因果链讲得通）、交叉验证关（两个独立证据互证）、修复验证关（修复消除了因果链且复现固化成回归）。方法论的头号内鬼是确认偏误，对抗它靠流程不靠意志力——预期先行、证据挂双向、关键节点请人评审。下一节 23.4 换视角：看一批"看似 A 实为 B"的真实错位案例，检验你这三节攒下的框架能不能避开前人掉过的坑。

关键结论速查：

| 问题 | 一句话答案 |
|------|-----------|
| 排查死循环的根源 | 候选根因没列全，在错误子集里打转 |
| 建树三纪律 | 分层列全/先族后细/证据挂双向 |
| 实验铁律一 | 一次只改一个变量（确认性实验除外） |
| 实验铁律二 | 动手前写下预期——写不出预期的实验没有判别力 |
| 实验排序 | 判别力优先，成本做修正 |
| 根因确认三关 | 机制讲得通 + 独立证据互证 + 修复验证并回归 |
| 三关后的残余风险 | 双根因共享症状——修复后保持观测一个月 |
| 头号内鬼 | 确认偏误；对抗靠流程（预期/双向/评审）不靠自觉 |

### 本节自查

- 面对一个新症状，能分层展开假设树并说清每个分支的证伪方法
- 能为一组实验排序（判别力×成本）并写出每个实验的预期结果
- 能解释"实验前写预期"为什么是对抗确认偏误的流程手段
- 能说出"强相关"和"根因"之间隔着哪三关
- 修复上线后，能坚持把复现流程固化成回归测试并安排后续观察期
- 能识别自己或同事发言里的确认偏误信号（钓鱼式实验/沉没成本/幸存者口径）

## <span class="blue">下一步

方法论齐了。下一节 23.4《常见陷阱：看似是 A 问题实际是 B 问题》是一面案例墙——"OOM"背后的真凶、"CPU 100%"的真身、"偶发死机"的经典误会，每个案例都给出错误的排查路径和本可以拐弯的那个拐点。看完你会明白为什么前三节的纪律每一条都是前人用工期换来的。

> 💡 动手入口：拿一个你正在纠结的问题（任何项目），花半小时建一棵假设树——分层列全、证据挂双向、标出判别力最高的那个实验。多数人第一次建树会发现两件事：自己原来只盯着整棵树的一根枝，以及判别力最高的那个实验一直没做。回读：23.1（复现优先与分层证伪的原则层）、23.2（实验所需的观测手段清单）。
