# 10.6.4 Tickless副作用与调试

> 所属章节：第10章 中断与时间 > 10.6 Tickless与动态时钟
>
> 难度：[I] 中级 | 预计阅读时间：18分钟

## <span class="blue">本节导读

Tickless（CONFIG_NO_HZ）让CPU在空闲时不再被打断，听起来很美好。但你有没有想过——**如果tick不固定了，那些依赖tick计时的机制怎么办？** CPU使用率统计会不会乱？jiffies还准不准？RCU会不会罢工？<br>
本节带你逐一拆解tickless的三大副作用，并学会用内核自带的调试工具来验证和诊断问题。学完后，你将能从容评估tickless的收益与代价，而不是盲目开启。

---

## <span class="blue">副作用一：CPU使用率统计失真

`top`、`vmstat`、`/proc/stat`这些工具是怎么算出CPU使用率的？说白了，它们靠**数tick**。内核每来一个tick中断，就统计一下这段时间CPU在干嘛——是在跑用户代码、内核代码，还是闲着？然后按比例算使用率。

```
CPU使用率 = 忙碌tick数 / 总tick数 × 100%
```

Tickless模式下，tick间隔不固定了。系统可能100ms没tick，然后突然来一堆。这意味着采样窗口忽长忽短，统计出来的数字自然也漂。

举个例子：某进程连续跑了90ms，正好赶上tick停了，一个采样都没抓住。`top`一看——"这进程CPU使用率0%"，你说冤不冤？

**解决方案**：改走事件驱动统计。`perf stat`基于PMU硬件计数器，不受tick影响：

```bash
# perf stat基于CPU cycles计数，不受tick间隔影响
$ perf stat -a sleep 5
# 输出：真实的cycles/instructions/cache-misses，而非采样估算值
```

## <span class="blue">副作用二：jiffies精度崩塌

`jiffies`是Linux内核的"心跳计数器"，传统模式下每1ms~10ms加1。很多内核代码习惯拿它做时间判断：

```c
// ⚠️ 这种写法在tickless下可能不准确
unsigned long start = jiffies;
while (time_before(jiffies, start + HZ)) {   // 等1秒
    /* 做点什么 */
}
```

Tickless下，tick间隔可能拉长到几十毫秒。`jiffies`只在tick到来时才更新，所以它的时间粒度完全取决于tick什么时候来。**说白了，jiffies从"准时钟"变成了"大概时钟"**。

| 场景 | tick默认模式 | tickless模式 |
|------|-------------|-------------|
| jiffies更新频率 | 固定（如250Hz） | 不固定，可能几十毫秒才跳一次 |
| 超时判断精度 | ±4ms（250Hz） | ±几十ms，甚至更差 |
| 适用场景 | 粗略延迟、超时 | 不适合精确计时 |

**解决方案**：需要精度的地方，用`ktime_get()`系列代替：

```c
#include <linux/ktime.h>
#include <linux/hrtimer.h>

// ✅ tickless安全的精确计时
u64 start = ktime_get_ns();
while (ktime_get_ns() - start < NSEC_PER_SEC) {
    /* 精确等待1秒，不受tick影响 */
}
```

> ⚠️ **陷阱**：tickless下绝对不要用`jiffies`做精确超时判断！如果你的驱动在tickless系统上用`msleep(1)`期望精确1ms延迟，实际可能被拖到几十毫秒。精度要求高的场景（音频缓冲、传感器采样），务必切到hrtimer或`ktime_get()`。

## <span class="blue">副作用三：RCU Grace Period延长

RCU（Read-Copy-Update）是内核高性能锁-free同步机制。RCU要安全回收旧数据，必须等所有CPU都经历一次**quiescent state**（安静态）——简单说就是每个CPU都离开临界区一次。

怎么知道CPU进入quiescent state？靠tick中断来检查。Tickless模式下CPU可能长时间收不到tick，RCU就没法确认这个CPU"安静"了。

```
正常tick模式：          tickless模式：
  tick → 检查RCU          tick停很久 → 不检查RCU
  tick → 检查RCU          tick → 检查RCU（延迟很久）
  tick → 检查RCU          ...
  grace period短          grace period明显延长
```

Grace period拖长意味着什么？旧数据结构迟迟不能被回收，内存占用升高，某些热路径可能出现延迟尖刺。

**缓解方案**：内核提供了`CONFIG_RCU_FAST_NO_HZ`。开启后，RCU在需要时会主动唤醒tick来推进grace period，拿一点点功耗换RCU效率：

```
Kernel Hacking  --->
    RCU Debugging  --->
        [*] RCU fast no_hz    # CONFIG_RCU_FAST_NO_HZ
```

## <span class="blue">三大副作用速查

| 副作用 | 表现 | 根因 | 影响 | 解决方案 |
|--------|------|------|------|----------|
| CPU统计失真 | top/ps显示使用率不准，波动大 | tick间隔不均匀，采样窗口不稳定 | 性能分析误判 | `perf stat`代替；关闭NO_HZ做基准对比 |
| jiffies精度崩塌 | 超时延迟忽长忽短 | jiffies只在tick时更新，tick间隔不固定 | 驱动定时、超时逻辑出错 | `ktime_get()` + hrtimer替代 |
| RCU grace period延长 | 内存回收慢，旧数据滞留 | tick停太久，RCU无法检测quiescent state | 内存占用升高、同步延迟 | `CONFIG_RCU_FAST_NO_HZ` |

## <span class="blue">调试工具箱

| 工具/文件 | 命令 | 输出解读 |
|-----------|------|----------|
| `/proc/timer_list` | `cat /proc/timer_list \| grep -E "(tick|nohz|hz)"` | 查看每个CPU的tick状态，`nohz_mode`显示是否进入tickless |
| `/proc/stat` | `cat /proc/stat \| head -1` | 对比tick/jiffies计数，看是否与真实时间匹配 |
| ftrace tracepoint | `cat /sys/kernel/debug/tracing/events/tick/enable` | 捕获`tick_nohz_stop_sched_tick`等事件 |
| `trace-cmd` | `trace-cmd record -e tick:* sleep 10` | 记录10秒内所有tick相关事件，分析tick停止时长 |
| `kernelshark` | 配合trace-cmd产生的trace.dat | 可视化查看tick停启时间线 |

### 验证tickless是否生效：`/proc/timer_list`

```bash
$ cat /proc/timer_list | grep -A5 "Tick Device:"
Tick Device: tick0
  Clock Event Device: arch_sys_timer
  Mode:        ONESHOT        # ← 看到ONESHOT说明在用tickless
  tick_nohz_mode: NOHZ_MODE_IDLE   # ← CPU空闲时tick停掉
  next_event:  1234567890 ns
```

关键点看两个字段：
- `Mode: ONESHOT` → tick设备工作在单次触发模式，是tickless的基础
- `tick_nohz_mode: NOHZ_MODE_IDLE` 或 `NOHZ_MODE_HIGHRES` → 当前CPU处于tickless模式

### 用tracepoint追踪tick事件

```bash
# 1. 挂载debugfs（如果没挂）
$ mount -t debugfs none /sys/kernel/debug

# 2. 启用tick_nohz相关tracepoint
$ echo 1 > /sys/kernel/debug/tracing/events/tick/tick_nohz_stop_sched_tick/enable
$ echo 1 > /sys/kernel/debug/tracing/events/tick/tick_nohz_restart_sched_tick/enable

# 3. 实时查看
$ cat /sys/kernel/debug/tracing/trace_pipe
tick_nohz_stop_sched_tick:  cpu=1  expires=4294967296  ...
tick_nohz_restart_sched_tick: cpu=1  ...

# 4. 或者用trace-cmd批量记录后分析
$ trace-cmd record -e tick:* sleep 10
$ trace-cmd report | grep tick_nohz
```

输出中重点关注`tick_nohz_stop_sched_tick`到`tick_nohz_restart_sched_tick`之间的时间间隔——间隔越长，说明tick停得越久，副作用越明显。

---

> 💡 **提示**：`CONFIG_NO_HZ_FULL`（全核tickless，连运行态也停tick）比`CONFIG_NO_HZ_IDLE`（仅空闲停tick）副作用**大得多**。NO_HZ_FULL下jiffies几乎冻结、RCU检测更困难、调试也更复杂。除非你是做HPC（高性能计算）或实时音频处理，否则别轻易开FULL模式。先评估收益是否值得。

## <span class="blue">本节总结

| 要点 | 内容 |
|------|------|
| **副作用1：CPU统计失真** | tick不均匀导致`top`/`/proc/stat`采样偏差，改用`perf stat` |
| **副作用2：jiffies精度崩塌** | tick间隔不固定→jiffies不再是精确时间基准，改用`ktime_get()`+hrtimer |
| **副作用3：RCU grace period延长** | tick停太久→RCU回收延迟，开启`CONFIG_RCU_FAST_NO_HZ`缓解 |
| **调试核心** | `/proc/timer_list`验模式 + `tracepoint`抓事件 + 对比`/proc/stat` |
| **选型建议** | NO_HZ_IDLE副作用可控；NO_HZ_FULL代价大，需严格评估 |

Tickless不是银弹。它省功耗、降延迟，但会破坏那些**暗依赖tick**的机制。你的调试策略应该是：先通过`/proc/timer_list`确认tickless真的在工作，再用tracepoint量化tick停得多久，最后对照副作用清单逐一排查。把问题拆成"验模式→测影响→找替代方案"三步，思路就清晰了。
