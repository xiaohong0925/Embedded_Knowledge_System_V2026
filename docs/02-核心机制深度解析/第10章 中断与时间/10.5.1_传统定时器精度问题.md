# 10.5.1 传统定时器的精度瓶颈

> 所属章节：第10章 中断与时间 > 10.5 时间子系统
>
> 难度：[I] | 预计阅读时间：18分钟

## <span class="blue">本节导读

程序经常需要"过一会儿再叫我"：500ms 没收到应答就重发、3 秒没心跳就判离线、每 10ms 轮询一次状态。这类需求的通用解法是**定时器**——你告诉内核一个未来的时刻，内核到点叫你，中间这段时间系统可以去做别的事。

内核里兑现这类承诺的一整套机制叫**时间子系统**，管两件事："现在几点"（计时）和"到点叫人"（定时）。本节回答它的第一个问题：**这套机制当初是怎么设计的？** 看懂最初的设计，"精度天花板 1/HZ"就不是一个要背的结论，而是这个设计自带的属性。

> 本节覆盖：传统定时器"数第几声钟"的设计与当年这样设计的理由、HZ 与 jiffies 两个基础概念、精度公式 `1/HZ` 的由来与内核模块实验验证、提高 HZ 为什么不是出路、这套设计后来在哪儿顶不住（hrtimer 的铺垫）。读完你应该能向人讲清楚 Linux 传统定时器的工作方式，并用实验亲眼看到 tick 量化。

---

## <span class="blue">最初的设计：定时器就是"第几声钟到期"</span>

设想你是 1990 年代的内核作者，要实现定时器。机器上有一件现成的资源：**硬件时钟芯片会按固定频率打断 CPU**——这就是时钟中断，每一次叫一个 tick。于是最朴素的设计自然浮现：

> tick（时钟中断）：硬件时钟按固定频率周期性地打断 CPU，每次打断就是一声"钟"。中断处理里内核做一批例行家务：更新计时、检查定时器、驱动调度记账。

<!-- -->

> HZ：内核编译时确定的常量，表示 **tick 每秒多少次**。HZ=250 即每秒敲 250 声、每 4ms 一声；HZ=1000 即每 1ms 一声。嵌入式 ARM 内核常见 100/250，桌面发行版常见 250/1000。查看当前值：`zcat /proc/config.gz | grep CONFIG_HZ`。

<!-- -->

> jiffies：内核里的全局计数器，**每来一次 tick 就加 1**——它就是"这是第几声钟"。内核想知道"现在过了多久"，最省事的办法就是读 jiffies。

有了这两样，定时器的实现简单到一句话：**"到点叫我"= 把"第 N 声钟"存进一个列表，每次 tick 处理时扫一遍，谁的 N ≤ 当前 jiffies 就执行谁**。

```
tick中断（每秒 HZ 次）
    │
    ▼
┌─────────────┐
│ jiffies++   │   ← 计数器只在这里 +1
└─────────────┘
    │
    ▼
┌──────────────────┐
│ run_timer_softirq │  ← 只在 tick 路径上检查定时器列表
└──────────────────┘
```

这个内核里的传统定时器结构体叫 `timer_list`，驱动里通过 `mod_timer()` 一族 API 使用。注意 API 的一个细节：**到期时间以 jiffies 为单位填写**——设计层面就决定了，你只能说"第几声钟叫我"，说不出"100 微秒后叫我"。

当年这样设计是明智的，三个理由至今成立：

1. **省 CPU**：定时器检查搭 tick 的便车，不为它单独打断系统；
2. **批处理便宜**：一次 tick 扫一整批到期定时器，成千上万个也不怕；
3. **需求匹配**：当年的定时需求（网络超时、设备探测、延迟任务）全是毫秒到秒级，tick 粒度绰绰有余。

## <span class="blue">设计自带的属性：精度 = 1/HZ</span>

从上面的工作方式直接读出一个事实：**tick 与 tick 之间，没有任何代码去看定时器列表一眼**。

定时器在一声钟刚结束时到期，也要干等到下一声钟才被发现——最长白等一整个 tick 周期。HZ=250 时，任何定时器的实际触发时刻都被对齐到 4ms 的整数倍边界上。于是：

**传统定时器精度 = 1/HZ**——这不是缺陷，是"数第几声钟"这个设计的固有属性。

| HZ 值 | 一声钟多长 | timer_list 最小间隔 | 典型选择方 |
|:---:|:---:|:---:|:---|
| 100 | 10ms | 10ms | 服务器、低功耗优先 |
| 250 | 4ms | 4ms | 桌面发行版默认，折中 |
| 300 | 3.33ms | 3.33ms | 部分发行版的历史选择 |
| 1000 | 1ms | 1ms | 低延迟交互（音频/游戏） |

## <span class="blue">实验：亲眼看 tick 量化</span>

设计特性要在内核态才看得见，用一个最小内核模块验证：每触发一次就请求"下一声钟再叫我"，并打印两次触发的实际间隔。

先写代码 `tick_timer_demo.c`：

```c
/* tick_timer_demo.c — 观察 timer_list 的触发间隔被量化到 tick 边界 */
#include <linux/module.h>
#include <linux/timer.h>
#include <linux/jiffies.h>
#include <linux/ktime.h>

static struct timer_list demo_timer;
static ktime_t prev;

static void demo_cb(struct timer_list *t)
{
	ktime_t now = ktime_get();
	/* ktime_us_delta：两个时间戳之差，单位微秒 */
	pr_info("demo: delta=%lld us\n", ktime_us_delta(now, prev));
	prev = now;
	mod_timer(t, jiffies + 1);   /* 请求"下一声钟"触发 */
}

static int __init demo_init(void)
{
	prev = ktime_get();
	timer_setup(&demo_timer, demo_cb, 0);
	mod_timer(&demo_timer, jiffies + 1);
	return 0;
}

static void __exit demo_exit(void)
{
	del_timer_sync(&demo_timer);
}

module_init(demo_init);
module_exit(demo_exit);
MODULE_LICENSE("GPL");
```

同目录放一个 Makefile：

```makefile
obj-m += tick_timer_demo.o
```

编译与运行（开发板上直接编译需安装内核头文件；交叉编译见第 4 章的内核模块编译流程）：

```bash
# 板子上本机编译：
make -C /lib/modules/$(uname -r)/build M=$PWD modules

# 交叉编译（在 PC 上，指向你的内核源码树）：
make -C <内核源码路径> M=$PWD ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- modules

# 加载、观察、卸载：
insmod tick_timer_demo.ko
dmesg | tail -20
rmmod tick_timer_demo
```

HZ=250 的板子上，输出里每一行都在 4000μs 附近：

```text
[  123.104] demo: delta=4002 us
[  123.108] demo: delta=3998 us
[  123.112] demo: delta=4001 us
```

请求的是"尽快"（下一声钟），拿到的是整齐的 4ms——触发时刻全部被量化到 tick 边界，与设计预期分毫不差。

> 💡
> 你可能会拿用户态的 `setitimer` 去验证这个结论，然后发现 100μs 是准的——这不是本节错了，是 `setitimer` 的内核实现在 2006 年（2.6.16）已经从 timer_list 搬到后面要讲的 hrtimer 上（见 `kernel/time/itimer.c` 里的 `hrtimer_init()`）。所以"`1/HZ`"这句话今天对 setitimer、nanosleep 等用户态接口已失效，它锁住的是内核态的 `timer_list`。读老教材时注意这个年代差。

## <span class="blue">提高 HZ 为什么不是答案</span>

直觉反应是把 HZ 调到 1000 甚至更高。算一下账就知道此路不通：

| 提高 HZ 的代价 | 具体影响 |
|:---|:---|
| CPU 开销 | 每声钟都要更新统计、检查定时器、驱动调度记账；1000Hz 的这部分开销是 100Hz 的 10 倍 |
| 缓存干扰 | tick 越频繁，打断正在运行的任务越多，缓存局部性越差 |
| 功耗 | 高频 tick 阻止 CPU 进入深度睡眠（详见 10.6） |
| 精度仍不够 | 即使 1000Hz 也只有 1ms，对微秒级需求仍差 10 倍 |

拿中断频率线性换精度，开销、干扰、功耗同步上升，封顶还够不到微秒级——方向本身就不对。而且别忘了当年设计的第三个理由仍然成立：内核里毫秒到秒级的粗粒度定时需求占绝大多数（TCP 重传、设备超时、延迟工作），对它们来说 tick 定时器依然是最便宜的工具。所以这套老设计**没有被淘汰，而是留下来继续管粗活**。

## <span class="blue">需求升级后：换计时基准</span>

真正的变化发生在需求侧：多媒体、工业控制、高分辨率超时开始要微秒级。突破方向不是把钟敲得更快，而是**换计时基准**——不数"第几声钟"，直接读硬件时钟的纳秒计数，把"到期的准确时刻"写进硬件定时器的比较寄存器，硬件到点自己产生中断，不等敲钟。这就是 hrtimer（高精度定时器）的思路，用户态接口变准靠的就是它：

```
┌─────────────────────────────────────────────┐
│  用户态接口层：setitimer / timer_create      │
│  （2006 年起已落在 hrtimer 上）              │
├─────────────────────────────────────────────┤
│  通用时间层：  hrtimer（高精度）| timer_list │
│                （纳秒基准）    （jiffies 基准）│
├─────────────────────────────────────────────┤
│  时钟事件层：  clockevents（编程下一次中断）  │
├─────────────────────────────────────────────┤
│  时钟源层：    clocksource（纳秒计数）       │
├─────────────────────────────────────────────┤
│  硬件层：      ARM Generic Timer / TSC / HPET│
└─────────────────────────────────────────────┘
```

`timer_list` 卡在第二层右列，绑死 jiffies；`hrtimer` 走左列，直接利用第三、四层——微秒级精度的来源就在这里。下一节逐层拆这张图的每一层。

## <span class="blue">本节总结</span>

一句话记住本节：**传统定时器是"数第几声钟"——到期检查只在敲钟那一刻发生，所以精度天花板就是一声钟的长度 `1/HZ`**。这是 1990 年代那个省 CPU、批量扫描、匹配粗粒度需求的设计自带的属性，不是缺陷；实验里 4ms 的整齐间隔就是它的心跳。

这套设计今天仍在内核里管着海量粗粒度定时任务，没有被淘汰。它顶不住的是微秒级新需求，而出路不是把钟敲快（提高 HZ 的账算不过来），是换计时基准——让定时器脱离 jiffies，直接编程硬件时钟"到点叫我"。这是 hrtimer 的方向，也是下一节要逐层展开的架构。
