# 10.3.3 tasklet详解

> 所属章节：第10章 中断与时间 > 10.3 软中断与tasklet
>
> 难度：[E][M] | 预计阅读时间：18分钟

## <span class="blue"> 本节导读

上节你啃完了softirq的硬核机制——位图、per-cpu数组、ksoftirqd。但你心里可能也在嘀咕：软irq搞起来太繁琐了，有没有一种"自动挡"？<br>
tasklet就是答案。它本质上是对softirq的封装，把注册、调度、执行全打包成API，让你不用直接碰softirq的底层细节。<br>
不过别高兴太早——tasklet的限制和softirq一样严格：不能睡眠、同一个tasklet串行执行。而且到了2024年，它已经被标记为deprecated，新代码应该用workqueue或threaded IRQ替代。<br>
学完后，你将理解tasklet的内核实现、会用代码写一个完整的tasklet驱动、并且知道为什么它正在被时代淘汰。

---

## <span class="blue"> tasklet的本质——softirq的"自动挡" [E]

想想你刚学开车时，手动挡的softirq要你踩离合、换挡、给油——全得自己来。而tasklet就像自动挡，内核帮你处理调度细节，你只需要挂D挡（调用tasklet_schedule）就能走。

tasklet基于softirq的两个向量实现：

| 类型 | 值 | 优先级 | 典型延迟 |
|------|-----|--------|----------|
| `HI_SOFTIRQ` | 0 | 最高 | 微秒级 |
| `TASKLET_SOFTIRQ` | 5 | 普通 | 略长于HI_SOFTIRQ |

**HI_SOFTIRQ** 用于高优先级tasklet，比如对延迟极度敏感的网络收包路径。**TASKLET_SOFTIRQ** 是给普通tasklet用的。两种类型的tasklet共用同一套机制，只是在softirq位图中的优先级不同。

> 💡 **提示**：HI_SOFTIRQ比TASKLET_SOFTIRQ优先级高，延迟更低。如果你的tasklet处理的是GPIO状态翻转这种极短的操作，可以考虑用`tasklet_hi_schedule()`把它挂到HI_SOFTIRQ上，减少被其他softirq抢占的等待时间。

tasklet和softirq的核心区别是什么？一句话：**同一种tasklet保证串行执行**。什么意思？同一个`tasklet_struct`实例，哪怕你在多个CPU上同时触发，内核也保证它不会并行运行。这是怎么做到的？后面拆解代码你就明白了。

## <span class="blue"> tasklet_struct与串行保证 [E]

tasklet的"身份证"就是这个结构体，定义在 `include/linux/interrupt.h`：

```c
struct tasklet_struct
{
    struct tasklet_struct *next;    /* 链表指针，同一CPU上的tasklet串成链表 */
    unsigned long state;            /* 状态位：TASKLET_STATE_SCHED / TASKLET_STATE_RUN */
    atomic_t count;                 /* 禁用计数器，count>0时tasklet不会执行 */
    void (*func)(unsigned long);    /* 回调函数 */
    unsigned long data;             /* 传递给func的参数 */
};
```

**state字段**只有两个有效位，但这俩位撑起了tasklet的串行语义：

| 状态位 | 含义 | 作用 |
|--------|------|------|
| `TASKLET_STATE_SCHED` (bit 0) | 已调度未执行 | 防止重复入队 |
| `TASKLET_STATE_RUN` (bit 1) | 正在执行 | 防止同一tasklet在多个CPU上并行 |

当`tasklet_schedule()`被调用时，第一件事就是`test_and_set_bit(TASKLET_STATE_SCHED)`。如果返回非零，说明这个tasklet已经在某个CPU的待执行链表上了，直接返回——**重复调度被静默丢弃**。

```c
/* kernel/softirq.c - tasklet_schedule 简化核心逻辑 */
static inline void tasklet_schedule(struct tasklet_struct *t)
{
    /* 如果已经在调度队列中，直接返回——这就是防重入的关键 */
    if (!test_and_set_bit(TASKLET_STATE_SCHED, &t->state))
        __tasklet_schedule(t);  /* 真正插入softirq队列 */
}
```

```c
/* __tasklet_schedule 的实现 */
void __tasklet_schedule(struct tasklet_struct *t)
{
    unsigned long flags;
    local_irq_save(flags);
    /* 把tasklet挂到当前CPU的tasklet_vec链表头部 */
    t->next = __this_cpu_read(tasklet_vec.head);
    __this_cpu_write(tasklet_vec.head, t);
    /* 触发TASKLET_SOFTIRQ */
    raise_softirq_irqoff(TASKLET_SOFTIRQ);
    local_irq_restore(flags);
}
```

那`TASKLET_STATE_RUN`呢？在`tasklet_action()`（tasklet的执行函数）里，取出tasklet后会`test_and_set_bit(TASKLET_STATE_RUN)`。如果别的CPU正在执行同一个tasklet，这个操作会失败，当前CPU就把tasklet塞回去，等下一轮再试。

> ⚠️ **陷阱**：tasklet中**绝对不能睡眠**。tasklet运行在软中断上下文，没有进程栈，没有调度实体。你一旦在tasklet里调用`sleep()`、`kmalloc(GFP_KERNEL)`或任何可能阻塞的函数，内核立刻oops——因为没有进程上下文可以切换回来。

## <span class="blue"> tasklet_schedule()的完整调用链 [M]

一个tasklet从被触发到执行，经历哪些站点？

```mermaid
flowchart LR
    A[你的中断处理函数<br>top half] -->|tasklet_schedule| B[test_and_set_bit<br>STATE_SCHED]
    B -->|未设置过| C[__tasklet_schedule]
    C --> D[挂入当前CPU的<br>tasklet_vec链表]
    D --> E[raise_softirq_irqoff<br>TASKLET_SOFTIRQ]
    E --> F[退出中断上下文]
    F --> G[do_softirq<br>或 ksoftirqd]
    G --> H[tasklet_action]
    H --> I[遍历链表执行<br>func(data)]
    I --> J[clear_bit<br>STATE_SCHED & RUN]
```

具体走一遍：

1. **你的中断处理函数**里调用`tasklet_schedule(&my_tasklet)`
2. 内核检查`TASKLET_STATE_SCHED`——如果已设置，说明还在排队，直接返回
3. 未设置的话，`__tasklet_schedule()`把它挂到**当前CPU**的`tasklet_vec`链表
4. `raise_softirq_irqoff(TASKLET_SOFTIRQ)`点亮softirq位图
5. 中断返回后，内核检查pending softirq，进入`do_softirq()`
6. `tasklet_action()`被调用，遍历链表，逐个执行`func(data)`
7. 执行完`clear_bit(TASKLET_STATE_SCHED)`和`clear_bit(TASKLET_STATE_RUN)`，tasklet又可以被重新调度了

> 🔴 **危险**：**tasklet_schedule()在tasklet执行期间再次调用会丢失**。假设你的tasklet函数还在CPU0上跑，这时中断又来了，CPU1调用`tasklet_schedule()`——`test_and_set_bit(TASKLET_STATE_SCHED)`发现bit已清（执行完才会清），就把tasklet挂到CPU1的链表。但CPU0执行完后会清STATE_RUN，不会感知CPU1的操作。更严重的是，如果tasklet执行期间（STATE_RUN置位）再次调度，`tasklet_schedule()`发现STATE_SCHED已清，会把它挂到另一个CPU，然后两边同时竞争同一个tasklet——这是经典的race condition。别在tasklet执行期间重新调度自己，用workqueue才是正道。

## <span class="blue"> 实战：写一个完整的tasklet驱动 [E]

光说不练假把式。下面是一个驱动tasklet从初始化到使用的完整示例：

```c
/* tasklet_demo.c - 完整tasklet驱动示例 */
#include <linux/module.h>
#include <linux/interrupt.h>
#include <linux/gpio.h>

static struct tasklet_struct my_tasklet;

/* Tasklet回调函数——软中断上下文，不能睡眠！ */
static void my_tasklet_handler(unsigned long data)
{
    /* data就是初始化时传的值，这里传的是irq号 */
    int irq = (int)data;
    
    /* 可以读硬件状态、更新buffer、唤醒等待队列 */
    pr_info("tasklet running on CPU%d, irq=%d\n",
            smp_processor_id(), irq);
    
    /* ❌ 绝对不能做这些事：
     * msleep(10);          -- 会oops！
     * kmalloc(100, GFP_KERNEL); -- GFP_KERNEL可能睡眠！
     * mutex_lock(&lock);   -- 可能睡眠！
     */
    
    /* ✅ 安全操作：自旋锁、读寄存器、flag标记 */
}

static irqreturn_t my_irq_handler(int irq, void *dev_id)
{
    /* top half：极短，只清中断源 */
    gpio_set_value(LED_GPIO, 1);  /* 示意：点个灯 */
    
    /* 调度tasklet，剩下的交给bottom half */
    tasklet_schedule(&my_tasklet);
    
    return IRQ_HANDLED;
}

static int __init tasklet_demo_init(void)
{
    int irq = gpio_to_irq(GPIO_BUTTON);
    
    /* 初始化tasklet：绑定回调函数和数据 */
    tasklet_init(&my_tasklet,           /* tasklet结构体 */
                 my_tasklet_handler,    /* 回调函数 */
                 (unsigned long)irq);   /* 传给回调的数据 */
    
    /* 或者用宏声明+初始化（静态场景） */
    // DECLARE_TASKLET(my_tasklet, my_tasklet_handler, irq);
    
    request_irq(irq, my_irq_handler,
                IRQF_TRIGGER_FALLING,
                "tasklet_demo", NULL);
    
    pr_info("tasklet demo loaded\n");
    return 0;
}

static void __exit tasklet_demo_exit(void)
{
    int irq = gpio_to_irq(GPIO_BUTTON);
    
    /* 必须先关中断再kill tasklet，否则还在跑的tasklet访问已释放资源 */
    free_irq(irq, NULL);
    tasklet_kill(&my_tasklet);  /* 等待tasklet执行完，防止资源泄漏 */
}

module_init(tasklet_demo_init);
module_exit(tasklet_demo_exit);
```

有几个关键点要盯住：

- `tasklet_init()`：动态初始化，用于模块加载时创建的tasklet。如果你的是静态全局变量，可以直接用`DECLARE_TASKLET()`宏。
- `tasklet_kill()`：模块卸载时**必须调用**，它会阻塞等待tasklet执行完成。少了这一步，rmmod时tasklet还在跑，访问已卸载的模块代码段——直接panic。
- 回调函数的`data`参数是`unsigned long`，传指针时要强转，64位平台上尤其要小心。

## <span class="blue"> tasklet vs softirq：你该怎么选？

对比一下三种下半部机制，心里就有数了：

| 特性 | softirq | tasklet | workqueue |
|------|---------|---------|-----------|
| 执行上下文 | 软中断上下文 | 软中断上下文 | **进程上下文** |
| 同类型并行性 | 同一种softirq可在多CPU**并行** | **同一种tasklet串行**执行 | 可并行 |
| 编程复杂度 | 手动管理注册/调度 | 封装好的API，简单 | 最直观 |
| 能否睡眠 | ❌ 不能 | ❌ 不能 | ✅ 可以 |
| 状态管理 | 手动bitmap | STATE_SCHED/RUN自动 | 无特殊限制 |
| 延迟 | 最低 | 低（略高于softirq） | 最高（上下文切换） |
| 内核状态（2024） | 核心机制 | **Deprecated** | 推荐方案 |

看出门道了吗？tasklet的卖点是"比softirq简单，比workqueue快"。但2024年的内核已经明确：**别用tasklet了**。` Documentation/core-api/softirq.rst `里写得清清楚楚——新代码用workqueue或threaded IRQ。

为什么 deprecated？主要是两个原因：

1. **没法睡眠**的限制在复杂驱动里越来越难受。比如你想在bottom half里访问用户空间、做I/O、等DMA完成——tasklet全干不了。
2. **同一个tasklet的串行语义**在某些场景下反而成了性能瓶颈。你的网卡收了8个队列的包，想并行处理？tasklet帮不了你。

## <span class="blue"> 本节总结

| 项目 | 内容 |
|------|------|
| tasklet的本质 | 对HI_SOFTIRQ/TASKLET_SOFTIRQ的封装，简化softirq编程 |
| 串行保证机制 | `TASKLET_STATE_SCHED`防重入队 + `TASKLET_STATE_RUN`防并行执行 |
| 核心API | `tasklet_init()`、`tasklet_schedule()`、`tasklet_kill()` |
| 关键限制 | **不能睡眠**、同一tasklet串行、执行期间重调度会丢 |
| 适用场景 | GPIO中断、极短状态更新、禁止睡眠的上下文 |
| 现代推荐 | **已deprecated**，新代码用workqueue（10.3.4）或threaded IRQ |
| 易犯错误 | tasklet里睡眠→oops、卸载忘`tasklet_kill()`→panic |
