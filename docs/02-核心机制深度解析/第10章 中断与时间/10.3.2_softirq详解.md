# 10.3.2 softirq详解

> 所属章节：第10章 中断与时间 > 10.3 底半部机制

> 难度：[E→M] | 预计阅读时间：20分钟

## <span class="blue"> 本节导读

上一节确定了中断必须拆成"顶半部+底半部"。<br>
底半部机制里优先级最高、跑得最快的是 **softirq**——网络收发包、块设备 IO 完成、定时器到期，全跑在它上面。<BR>

本节覆盖：

- softirq 的静态类型体系（v6.6 共 10 种）、
- `irq_exit()` 处的执行时机与 `do_softirq()` 的真实代码、
- 防重入与多 CPU 并行的机制、
- `ksoftirqd` 的触发条件与 100% CPU 故障排查、
- `/proc/softirqs` 的读法，
- 以及 NAPI 收包链上 softirq 的位置。

## <span class="blue"> softirq 的类型与静态定义 [E]

softirq 是 Linux 里**优先级最高的底半部机制**，设计上追求极致的速度。

先看数量约束：softirq 最多 32 种，v6.6 实际定义了 10 种（`include/linux/interrupt.h`），已全部被内核核心子系统占用：

| 类型宏 | 名称 | 用途 | 典型触发者 |
|--------|------|------|-----------|
| `HI_SOFTIRQ` | 高优先级 tasklet | 执行高优先级 tasklet | `tasklet_hi_schedule()` |
| `TIMER_SOFTIRQ` | 定时器 | 处理到期的普通定时器 | tick 处理 |
| `NET_TX_SOFTIRQ` | 网络发包 | 发送网络数据包 | 发送路径 |
| `NET_RX_SOFTIRQ` | 网络收包 | 接收网络数据包 | NAPI 调度 |
| `BLOCK_SOFTIRQ` | 块设备 | 处理块设备 I/O 完成 | I/O 完成路径 |
| `IRQ_POLL_SOFTIRQ` | IRQ 轮询 | 替代中断的轮询模式 | 高 IOPS 存储设备 |
| `TASKLET_SOFTIRQ` | 普通 tasklet | 执行普通 tasklet | `tasklet_schedule()` |
| `SCHED_SOFTIRQ` | 调度 | 调度域负载均衡等 | 调度器 |
| `HRTIMER_SOFTIRQ` | 高精度定时器 | 处理高精度定时器到期 | hrtimer 子系统 |
| `RCU_SOFTIRQ` | RCU 回调 | 执行 RCU 宽限期回调 | RCU 子系统 |

这张表说明两件事：

1. softirq 被网络、块设备、定时器、调度、RCU 这些"命脉子系统"瓜分完毕；
2. 普通驱动**不能**新增 softirq 类型——这是内核的明确信号：**普通驱动用 tasklet 或 workqueue，softirq 不对外开放。**

```c
/* kernel/softirq.c:59 */
static struct softirq_action softirq_vec[NR_SOFTIRQS] __cacheline_aligned_in_smp;
```

每个 softirq 类型对应一个 `softirq_action`，核心就是一个函数指针 `action`。

> softirq_vec：softirq 的"注册表"——编译期定死的静态数组，下标就是类型号（`HI_SOFTIRQ`=0、`TASKLET_SOFTIRQ`=6……），元素是该类型的处理函数。<br>
> "静态数组"意味着运行时不能增删类型，这正是"普通驱动不能新增 softirq"在代码层面的实现。

## <span class="blue"> softirq 的执行机制：谁在什么时候跑？ [E]

softirq 的执行遵循一个核心原则：**在中断退出路径上"顺路"跑**。既保证低延迟，又不无限占用 CPU。

```mermaid
flowchart TD
    %%{init: {'flowchart': {'ranksep': 25, 'nodesep': 12, 'curve': 'basis'}}}%%
    A[硬件中断发生<br>网卡/定时器/磁盘] --> B[顶半部执行<br>ack中断, raise_softirq]
    B --> C[irq_exit 调用]
    C --> D{检查<br>local_softirq_pending?}
    D -->|有pending| E[do_softirq 执行<br>softirq 处理函数]
    D -->|无pending| F[返回正常上下文]
    E --> G{处理超阈值<br>或需要调度?}
    G -->|是| H[唤醒 ksoftirqd/<n><br>内核线程接替]
    G -->|否| F
    H --> I[ksoftirqd 在进程上下文<br>继续处理 softirq]
    I --> J[可被调度, 不饿死用户态]
```

真实代码（v6.6，`kernel/softirq.c:441`）：

```c
asmlinkage __visible void do_softirq(void)
{
    __u32 pending;                /* 当前 CPU 待处理的 softirq 位图 */
    unsigned long flags;          /* 用于保存/恢复中断状态的临时变量 */

    /* 
     * 安全检查：如果当前已经在中断上下文（硬中断、软中断、NMI 等），直接返回，防止 softirq 嵌套执行。
     * 这是硬性规则：同一 CPU 上 softirq 不允许递归，否则栈可能爆掉，且 pending 位图会被并发修改。
     */
    if (in_interrupt())
        return;

    /*
     * 关闭本地中断，同时把进入前的中断状态（开/关）保存到 flags。
     * 
     * 为什么必须关？因为接下来要读 pending 位图并执行 handler，
     * 如果此时硬中断插入，可能再次置位 pending 并触发 __do_softirq()的循环逻辑，导致竞态。
     */
    local_irq_save(flags);

    /* 读取当前 CPU 的 __softirq_pending 位图，每一位代表一类 softirq 是否 pending */
    pending = local_softirq_pending();

    /* 
     * 如果有任何 pending 的 softirq，进入实际执行路径。
     * 
     * do_softirq_own_stack() 通常会把执行切换到 softirq 专用栈（如果架构支持），
     * 然后调用 __do_softirq() 逐位扫描 pending 并执行对应的 handler。
     */
    if (pending)
        do_softirq_own_stack();

    /*
     * 恢复进入前的中断状态。
     * 如果进入前本地中断是开的，这里打开；如果是关的，保持关。
     * 与 local_irq_save() 配对使用，保证中断状态的原子性恢复。
     */
    local_irq_restore(flags);
}
```

> pending 位图（`__softirq_pending`）：每个 CPU 独享的一张 32 位位图，第 N 位置 1 表示第 N 类 softirq 有待处理任务。<br>
> 顶半部里 `raise_softirq()` 负责置位，`__do_softirq()` 读出并清零后逐位执行——它是"顶半部只标记、底半部再执行"这一分工的物理载体。

逐位执行的处理循环在 `__do_softirq()` 里，两个关键细节：

1. **处理期间中断是打开的**。`__do_softirq()` 进入循环前重新 `local_irq_enable()`； softirq 可以被硬中断打断，这正是它比硬中断"软"的地方。
2. **防重入靠计数，不靠关中断**。执行前把 `preempt_count` 加上 `SOFTIRQ_OFFSET`，同一 CPU 上 softirq 不会嵌套重入；但这只限制本 CPU，`NET_RX_SOFTIRQ` 在 CPU0 跑的同时，CPU1 可以跑同一个 `NET_RX_SOFTIRQ`。**同类型 softirq 可在多 CPU 上真正并行**，写 softirq 处理函数必须考虑这一点。

## <span class="blue"> ksoftirqd：softirq 的限流阀 [M]

如果网卡疯狂收包，`NET_RX_SOFTIRQ` 被一次次 raise，`__do_softirq()` 岂不是永远跑不完、用户态永远拿不到 CPU？

内核的解法是把它移交进程上下文：

> ksoftirqd：每个 CPU 一个的内核线程（`ksoftirqd/0`、`ksoftirqd/1`……），专职在进程上下文里执行 softirq。<br>
> 中断上下文里跑不完的剩余工作由它接手慢慢跑，因为它可以被调度，用户态就不会被饿死。

那么什么时候触发移交？`__do_softirq()` 的处理循环有两道上限（`kernel/softirq.c:474` 附近）：

- **时间上限 `MAX_SOFTIRQ_TIME`**：2ms；
- **重启次数上限 `MAX_SOFTIRQ_RESTART`**：10 次。

任一超限（或者 `need_resched()` 置位）而 pending 还没清完，就唤醒 `ksoftirqd`，把剩余处理移交进程上下文慢慢跑——用户态因此不会被饿死。

> ⚠️ `ksoftirqd` 占用 100% CPU 是生产环境经典故障。`top` 里看到 `ksoftirqd/0` 吃满一个核，说明这个 CPU 上的 softirq 流量已爆表。<BR>
> 常见原因：网卡流量过大（DDoS、广播风暴）、块设备 I/O 过于密集、某个驱动在 softirq 里做了太多事。<BR>
> 排查：`watch -n1 'cat /proc/softirqs'`，看哪个类型的计数在暴涨。

<!-- -->

## <span class="blue"> 实战：网络收包链上的 softirq [M]

理论讲完，看最经典的场景——网络收包，softirq 最高频的触发场景：

```
网卡收到数据包
    │
    ▼
┌──────────────┐
│  硬件中断     │  ← 顶半部开始，关本地中断
│  irq_handler │
└──────┬───────┘
       │
       ▼
┌──────────────┐
│ napi_schedule│  ← 将 napi_struct 加入 CPU 的 poll_list
│              │     并 raise NET_RX_SOFTIRQ
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  irq_exit()  │  ← 顶半部结束
│invoke_softirq│
└──────┬───────┘
       │
       ▼
┌──────────────┐
│NET_RX_SOFTIRQ│ ← __do_softirq() 执行
│ net_rx_action│  ← 遍历 poll_list，调用 napi->poll()
└──────┬───────┘
       │
       ▼
┌─────────────┐
 napi->poll() │  ← 真正从 ring buffer 取包
│             │     交给协议栈处理
└─────────────┘
```

关键代码路径（节选）：

```c
/* drivers/net/ethernet/intel/igb/igb_main.c —— igb 网卡中断处理（节选） */
static irqreturn_t igb_msix_ring(int irq, void *data)
{
    struct igb_q_vector *q_vector = data; /* 从 data 取出该中断对应的队列向量 */
    ...
     /*
     * 精髓：顶半部只干一件事——把 NAPI 结构挂到轮询队列并触发 softirq。
     * 
     * 注意后缀 _irqoff：调用者已经保证本地中断是关闭的（硬中断上下文），
     * 所以内部可以直接操作 per-CPU 的 poll_list 而不用再加锁。
     * 这里一个包都不收，顶半部几微秒就返回，关中断窗口极短。
     */
    napi_schedule_irqoff(&q_vector->napi);   /* 精髓：只调度，不收包 */
    return IRQ_HANDLED;
}

/* net/core/dev.c —— NAPI 调度（节选） */
static inline void ____napi_schedule(struct softnet_data *sd,
                                      struct napi_struct *napi)
{
    /*
     * 把这个 napi_struct 挂到本 CPU softnet_data 的 poll_list 尾部。
     * 每个 CPU 独享一个 softnet_data，所以 list 操作不需要锁（关中断即保护）。
     */
    list_add_tail(&napi->poll_list, &sd->poll_list);      /* 挂到本 CPU 轮询表 */

    /*
     * 置位 NET_RX_SOFTIRQ，标记本 CPU 有网络接收软中断待处理。
     * 后缀 _irqoff 同样表示调用者已关中断，直接写 per-CPU pending 位图即可。
     * 等硬中断返回、irq_exit() 时就会触发 net_rx_action() 执行。
     */
    __raise_softirq_irqoff(NET_RX_SOFTIRQ);               /* 标记 pending */
}

/* net/core/dev.c —— NET_RX_SOFTIRQ 的处理函数（节选） */
static __latent_entropy void net_rx_action(struct softirq_action *h)
{
     /* 取本 CPU 的 softnet_data，里面存着 poll_list（待轮询的 NAPI 设备链表） */
    struct softnet_data *sd = this_cpu_ptr(&softnet_data);
    struct list_head *list = &sd->poll_list;

    /* 遍历 poll_list，处理所有挂在上面的 NAPI 设备 */
    while (!list_empty(list)) {
        struct napi_struct *n;
        int work, weight;

        /* 取出链表头（FIFO，先调度先执行） */
        n = list_first_entry(list, struct napi_struct, poll_list);
        /* weight 是本次轮询的收包配额上限（默认 64），防止一个设备吃光 CPU */
        weight = n->weight;

        work = n->poll(n, weight);     /* 调用网卡驱动的 poll 收包 */

        if (likely(work < weight))
            list_del(&n->poll_list);   /* 配额没用完：收干净了，摘下并重新开中断 */
        /* 配额用完：还有包，留在 poll_list 上下一轮继续 */
    }
}
```

这个设计的精妙之处：**一次中断可以收多个包**。<br>
传统方式每包一次中断，中断开销极高；NAPI 模式下中断触发后先关该中断源，通过 `NET_RX_SOFTIRQ` 批量轮询收包，收完再开。<br>
高流量下中断率大幅下降。NAPI 的完整机制在 10.3.5 展开。

## <span class="blue"> softirq 的限制与红线 [E]

softirq 运行在原子上下文，铁律与顶半部同源：

1. **不能睡眠**：虽然执行时 `current` 指向被中断的进程，但这个执行流不属于任何可调度的任务，调度器不能在这里切换。
2. **不能访问用户态内存**：中断/softirq 上下文与具体用户进程无关。
3. **执行时间要尽量短**：比硬中断宽松，但太长会堆积 pending、触发 ksoftirqd 兜底。

> 🔴 在 softirq 中调用 `schedule()` 或 `mutex_lock()` 会导致 `scheduling while atomic` 错误乃至崩溃。<br>
> 需要睡眠的场景，改用 **workqueue**——它在进程上下文中运行，可以安全睡眠。

| 特性 | softirq | tasklet | workqueue |
|------|---------|---------|-----------|
| 执行上下文 | 原子（softirq） | 原子（基于 softirq） | 进程上下文 |
| 可否睡眠 | ❌ 不可 | ❌ 不可 | ✅ 可以 |
| 同类型并行 | ✅ 多 CPU 并行 | ❌ 同一 tasklet 串行 | ✅ 多 CPU 并行 |
| 注册方式 | 静态编译时 | 动态运行时 | 动态运行时 |
| 适用场景 | 网络/块设备等核心子系统 | 普通驱动底半部 | 需要睡眠的操作 |

## <span class="blue"> 本节总结

softirq 是内核命脉子系统的专用快车道，普通驱动用不到也注册不了。<br>
理解它不是为了写，而是为了读懂两个现场——`ksoftirqd` 吃满 CPU 时系统到底在忙什么，以及 NAPI 为什么扛得住高流量收包。
