## <span class="blue"> 本节导读

工业 PLC 产线上，GPIO 中断的正常响应是几十微秒，高负载下偶尔飙到 1 毫秒以上，机械臂动作滞后。<BR>
这 1 毫秒花在哪里——硬件慢、软件卡、还是调度延迟？<br>
本节用这个故障现场建立一张"延迟地图"：把从硬件信号到 CPU 响应的完整链路拆成段，每段对应明确的排查工具。<BR>

本节覆盖：

- 中断延迟的三段分解（硬件/软件/调度）与排查工具irqsoff tracer 的能力边界
- 全章基石——定时器到期本身就是中断（tick 走 GIC PPI 通道）。

## <span class="blue"> 工业PLC的中断延迟谜案

某工厂产线上的PLC用GPIO中断检测传感器信号，正常响应时间是几十微秒。但高负载下偶尔出现 **>1ms 的延迟**，机械臂动作滞后导致废品率上升。

工程师用 ftrace 的 irqsoff tracer 测量：

```bash
# 打开 irqsoff tracer 查看中断关闭时间
echo irqsoff > /sys/kernel/debug/tracing/current_tracer
cat /sys/kernel/debug/tracing/trace
# tracer: irqsoff
#
# irqsoff latency trace v1.1.5 on 5.15.0-rt30
# --------------------------------------------------------------------
# latency: 823 us, #4/4, CPU#2 | (M:preempt VP:0, KP:0, SP:0 HP:0 #P:4)
#    -----------------
#    | task: ksoftirqd/2-19 (uid:0 nice:0 policy:0 rt_prio:0)
#    -----------------
#
#                  _------=> CPU#            
#                 / _-----=> irqs-off        
#                | / _----=> need-resched    
#                || / _---=> hardirq/softirq 
#                ||| / _--=> preempt-depth   
#                |||| /     delay            
#  cmd     pid   ||||| time  |   caller     
#     \   /      |||||  \    |   /          
    <...>-19    2d...1    0us!: trace_hardirqs_off_thunk <-call_function_interrupt
    <...>-19    2d..s1   10us!: __local_bh_disable_ip <-do_softirq
    <...>-19    2d..s1  823us : __local_bh_enable_ip <-do_softirq
    <...>-19    2d..s1  823us : trace_hardirqs_on_thunk <-call_function_interrupt
#
# (stack trace here)
# => __do_softirq
# => call_function_interrupt
# => smp_call_function_single
# => some_driver_function
# => spi_transfer_one

日志是一个带时间戳的调用链：它告诉你谁（哪个进程/函数）、在哪个 CPU、关中断多久（latency），以及具体代码路径（stack trace）。
```

- ftrace 是 Linux 内核内置的动态追踪框架，通过 debugfs 文件系统暴露接口。它无需修改源码或重新编译，就能在运行时记录内核函数的调用、耗时、中断状态变化等信息，相当于内核的"飞行记录仪"。
- irqsoff tracer 是 ftrace 的一种工作模式，专门捕获内核代码关闭本地中断的时长。它会自动记录从 local_irq_disable() 到 local_irq_enable() 的时间间隔，并标记出最长的一次及对应的代码调用栈，帮助定位"谁让 CPU 捂住了耳朵"。

输出显示最长中断关闭时间达 **800μs**——这意味着某段代码在关中断状态下跑了800微秒。但这只是冰山一角。更深层的问题是：即使中断没有被屏蔽，从信号触发到CPU真正执行中断处理函数，中间还有多少"暗箱"？

> 高负载下，内核软中断（如网络 NAPI 轮询、块设备完成中断）或驱动里持有 spin_lock_irqsave() 的临界区变长，导致 local_irq_disable() 的保护窗口被撑大——irqsoff 抓到的 823μs 往往就来自这类临界区。

与此同时，IoT网关在高网络负载下也遇到了类似的困境。网卡使用NAPI模式收包，中断风暴来临时，系统几乎无响应。两个看似不同的场景，根因却指向同一个问题：**从中断信号到达，到CPU响应处理，中间到底发生了什么？**

## <span class="blue"> 延迟根因拆解与本章路线图

把延迟拆开来看，它不是一个数字，而是一串链式反应。

```mermaid
graph LR
    A["外部信号<br/>GPIO翻转"] --> B["SoC内部<br/>引脚同步/去抖"]
    B --> C["中断控制器<br/>GIC收集/仲裁"]
    C --> D["总线分发<br/>AXI/APB到CPU"]
    D --> E["CPU响应<br/>异常向量入口"]
    E --> F["内核处理<br/>do_IRQ → handler"]
    F --> G["调度决策<br/>唤醒用户态任务"]
    style A fill:#f9f
    style G fill:#ff9
```

信号从外部世界出发，经过SoC内部的引脚同步电路，进入中断控制器（如ARM的GIC, 即Generic Interrupt Controller），再由总线传递到CPU核心。CPU认出这是中断后跳转到异常向量表，内核的通用中断处理框架接管，最后可能唤醒某个等待的任务。每一个环节都可能是延迟的"肇事者"。

这串链路上，延迟可以归纳为三类：

| 延迟类型 | 发生位置 | 典型量级 | 排查工具 |
|----------|----------|----------|----------|
| **硬件延迟** | 引脚同步→GIC→总线 | 数十~数百纳秒 | 示波器、逻辑分析仪 |
| **软件延迟** | 内核中断处理框架 | 数~数百微秒 | ftrace irqsoff/wakeup |
| **调度延迟** | 中断→唤醒→任务运行 | 数十微秒~数毫秒 | latencytop、sched trace |

> 💡 区分'中断到达延迟'和'中断处理延迟'：前者是信号产生到 CPU 收到中断的时间，后者是 CPU 进入处理函数到处理完成的时间。irqsoff tracer 测量的是'中断被关闭的最长时间窗口'，它反映的是中断响应的潜在最大延迟（若中断恰好在关闭期间到达），既不覆盖硬件传播延迟，也不等同于实际测得的中断处理耗时。

本章的路线图就是沿这张地图逐段推进：先拆 ARM64 异常机制与 GIC 硬件（10.1），看中断怎么"报到"CPU；再看顶半部为什么必须快（10.2）；不能在中断里做的事交给底半部（10.3）和线程化中断（10.4）；随后进入时间子系统（10.5）与 tickless（10.6）；最后用一个综合故障现场把两条线合起来（10.7）。展开之前，先建立全章的基石认知。

## <span class="blue"> 为什么中断和时间"绑定"在一起

**操作系统本身没有时间自动流逝的概念。** 裸机上晶振振荡是物理事实，但 Linux 不会"看着表"过日子——它的心跳完全依赖中断一巴掌一巴掌拍醒，每拍一次才知道"又过了一拍"。

> 有读者可能误以为"给 CPU 的 1.8GHz 时钟就是操作系统打节拍的时钟"。这是两码事：
> 
> - **CPU 核心时钟**（如 RK3576 的 1.8GHz）决定指令执行速度；
> - **ARM Generic Timer**（通常固定 24MHz）才是给 OS 提供统一时间基准的硬件；
> - 操作系统把它分频成 `HZ`（如 100/1000）次 tick 中断，且现代内核往往启用 Tickless，空闲时连固定 tick 都取消。
> 
> 简言之：硬件计数器频率固定，但**操作系统多久被中断拍醒一次**，是软件策略，不是硬件焊死的。

定时器到期，本质上就是**中断的一种**。

系统滴答（tick）由定时器硬件周期性触发，每次到期向CPU发送中断请求。<br>
在ARM64上，tick通常走GIC的PPI（Private Peripheral Interrupt）通道，即每个CPU核心私有的中断。<br>
`kernel/time/tick-common.c:107` 的 `tick_handle_periodic()` 就是在处理这类中断。

> GPIO 传感器中断通常走 GIC 的 SPI（Shared Peripheral Interrupt）通道，被多个 CPU 共享；而 tick 走 PPI（Private Peripheral Interrupt），每个 CPU 核心私有。但在 GIC 仲裁逻辑和 CPU 响应机制上，它们遵循同一套规则。


```c
/* kernel/time/tick-common.c:107（有删减） */
/* traditional periodic mode 示例，现代系统默认 one-shot 模式，入口为 tick_sched_timer */
void tick_handle_periodic(struct clock_event_device *dev)
{
    int cpu = smp_processor_id();

    /* 核心：推进系统时间、检查调度、更新进程统计 */
    tick_periodic(cpu);

}

static void tick_periodic(int cpu)
{
    /* 只有指定的 CPU 负责更新全局 jiffies */
    if (tick_do_timer_cpu == cpu) {
        write_seqlock(&jiffies_lock);
        do_timer(1);              /* jiffies++，全局时间基准 */
        write_sequnlock(&jiffies_lock);
    }

    /* 更新当前进程的运行时间、触发调度检查、处理信号等 */
    update_process_times(user_mode(get_irq_regs()));
}

```

注意 do_timer(1) 这行：在 traditional periodic tick 模式下，没有 tick 中断，do_timer() 就不会执行，jiffies 不会前进。（现代 tickless 内核在空闲时会取消 periodic tick，通过其他机制补偿 jiffies，详见 10.6 节。）。 调用链如下：

```text
硬件定时器到期
    → GIC PPI 中断 → CPU 响应
        → tick_handle_periodic()
            → tick_periodic()
                → do_timer(1)           【时间往前走一步】
                → update_process_times() 【调度器、定时器、信号】
```

这意味着，如果你连普通的外部中断（GPIO、网卡）都没搞明白，tick定时器的工作原理也会让你一头雾水。反过来，优化定时器精度、理解hrtimer如何绕过传统tick——这些也需要你对中断子系统有深入理解。

> 🔴 不要把"定时器中断"和"普通外设中断"割裂看待：在 GIC 眼里它们都是 IRQ 信号，区别只是中断号和触发源。**关中断（local_irq_disable()）会同时屏蔽两者**。

| 要点 | 核心结论 |
|------|----------|
| 延迟分布 | 中断延迟=硬件传播+软件处理+调度等待，不可笼统归因 |
