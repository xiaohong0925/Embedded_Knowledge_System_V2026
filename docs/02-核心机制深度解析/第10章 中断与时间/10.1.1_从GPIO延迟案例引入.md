## <span class="blue"> 本节导读

想象一个工业PLC控制机械臂的场景——外部传感器信号一来，GPIO电平翻转，CPU必须在微秒级响应。可偏偏偶尔延迟飙到1毫秒以上，机械臂动作错位，整条产线报警。<br>
本节用真实案例带你拆解：这1毫秒到底花在了哪里？是硬件慢？软件卡？还是调度在"走神"？<br>
学完后，你将拥有一张"延迟地图"，能从硬件信号到CPU响应的整条链路上定位问题。

---

## <span class="blue"> 工业PLC的中断延迟谜案

某工厂产线上的PLC用GPIO中断检测传感器信号，正常响应时间是几十微秒。但高负载下偶尔出现 **>1ms 的延迟**，机械臂动作滞后导致废品率上升。

工程师祭出ftrace的`irqsoff` tracer：

```bash
# 打开 irqsoff tracer 查看中断关闭时间
echo irqsoff > /sys/kernel/debug/tracing/current_tracer
cat /sys/kernel/debug/tracing/trace
```

输出显示最长中断关闭时间达 **800μs**——这意味着某段代码在关中断状态下跑了800微秒。但这只是冰山一角。更深层的问题是：即使中断没有被屏蔽，从信号触发到CPU真正执行中断处理函数，中间还有多少"暗箱"？

与此同时，IoT网关在高网络负载下也遇到了类似的困境。网卡使用NAPI模式收包，中断风暴来临时，系统几乎无响应。两个看似不同的场景，根因却指向同一个问题：**从中断信号到达，到CPU响应处理，中间到底发生了什么？**

## <span class="blue"> 延迟根因拆解与本章路线图

把延迟拆开来看，它不是一个数字，而是一串链式反应。

```mermaid
graph LR
    A["外部信号<br/>GPIO翻转"] --> B["SoC内部<br/>引脚同步/去抖"]
    B --> C["中断控制器<br/>GIC收集/仲裁"]
    C --> D["总线分发<br/>AXI/APB到CPU"]
    D --> E["CPU响应<br/>异常向量入口"]
    E --> F["内核处理<br/>do_IRQ → handler"]
    F --> G["调度决策<br/>唤醒用户态任务"]
    style A fill:#f9f
    style G fill:#ff9
```

信号从外部世界出发，经过SoC内部的引脚同步电路，进入中断控制器（如ARM的GIC），再由总线传递到CPU核心。CPU认出这是中断后跳转到异常向量表，内核的通用中断处理框架接管，最后可能唤醒某个等待的任务。每一个环节都可能是延迟的"肇事者"。

这串链路上，延迟可以归纳为三类：

| 延迟类型 | 发生位置 | 典型量级 | 排查工具 |
|----------|----------|----------|----------|
| **硬件延迟** | 引脚同步→GIC→总线 | 数十~数百纳秒 | 示波器、逻辑分析仪 |
| **软件延迟** | 内核中断处理框架 | 数~数百微秒 | ftrace irqsoff/wakeup |
| **调度延迟** | 中断→唤醒→任务运行 | 数十微秒~数毫秒 | latencytop、sched trace |

> 💡 **提示**：区分"中断到达延迟"和"中断处理延迟"。前者是信号产生到CPU收到中断的时间，后者是CPU进入处理函数到处理完成的时间。irqsoff tracer只关心后者中的"中断被屏蔽"部分，它无法追踪硬件传播延迟。

本章的路线图就是沿着这张"地图"逐步推进：先从ARM64的异常机制和GIC硬件架构入手（10.1），理解中断是怎么"报到"CPU的；再看内核的中断管理子系统如何处理（10.2）；然后深入软中断和tasklet的底半部机制（10.3）；最后把时间子系统拉进来（10.4），因为你会发现——

## <span class="blue"> 为什么中断和时间"绑定"在一起

定时器到期，本质上就是**中断的一种**。

系统滴答（tick）由定时器硬件周期性触发，每次到期向CPU发送中断请求。在ARM64上，tick通常走GIC的PPI（Private Peripheral Interrupt）通道，即每个CPU核心私有的中断。`kernel/time/tick-common.c`中的`tick_handle_periodic()`就是在处理这类中断。

```c
// kernel/time/tick-common.c
static void tick_handle_periodic(struct clock_event_device *dev)
{
    // 更新jiffies、计算负载、检查是否需要调度...
    do_timer(1);
    // 可能触发 scheduler_tick()
}
```

这意味着，如果你连普通的外部中断（GPIO、网卡）都没搞明白，tick定时器的工作原理也会让你一头雾水。反过来，优化定时器精度、理解hrtimer如何绕过传统tick——这些也需要你对中断子系统有深入理解。

> 🔴 **危险**：不要把"定时器中断"和"普通外设中断"割裂看待。在GIC眼里，它们都是IRQ信号，区别只是中断号和触发源的差异。关中断（`local_irq_disable()`）会同时屏蔽两者。

## <span class="blue"> 本节总结

| 要点 | 核心结论 |
|------|----------|
| 延迟分布 | 中断延迟=硬件传播+软件处理+调度等待，不可笼统归因 |
| 排查工具 | ftrace irqsoff定位软件侧，示波器定位硬件侧 |
| 中断≈时间 | 定时器到期就是中断，tick走GIC PPI通道 |
| 本章主线 | 沿"信号→GIC→CPU→内核→底半部→时间"链路逐步深入 |
