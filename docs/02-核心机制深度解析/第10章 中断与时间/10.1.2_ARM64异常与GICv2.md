# 10.1.2 ARM64异常级别与GICv2

> 所属章节：第10章 中断与时间 > 10.1 中断子系统全景
>
> 难度：[I][M] | 预计阅读时间：25分钟

## <span class="blue">本节导读

想象一下CPU是一座四层城堡——你的用户程序在最底层的集市里卖货（EL0），操作系统在第二层指挥全局（EL1），虚拟化层在第三层调度多个平行世界（EL2），而最高层的安全监控者掌握着城堡的终极钥匙（EL3）。当外设"敲门"请求CPU处理数据时，这个请求要经过GIC（通用中断控制器）的层层分发，最终才能到达CPU手中。<br>

本节带你深入ARM64的异常级别体系，理解同步异常与异步中断的本质区别，以及GICv2如何通过Distributor和CPU Interface两个组件来管理中断。学完后，你将能读懂`entry.S`向量表的结构、解释中断从外设到CPU的完整路径，以及搞明白为什么GIC的中断优先级数字"越小反而越高"。

---

## <span class="blue">异常级别体系：EL0到EL3的四层城堡 [I]

ARM64架构把CPU的执行状态划分为四个异常级别（Exception Level），级别数字越大，权限越高。这种设计不是凭空想出来的——它把CPU的特权层次直接硬件化了。

### 四层城堡各自做什么

| 异常级别 | 用途 | 运行代码 | 特权 | 典型操作 |
|:---:|:---|:---|:---:|:---|
| **EL0** | 用户态（应用层） | 普通应用程序 | 最低 | 访问用户空间内存、标准库调用 |
| **EL1** | 内核态（操作系统） | Linux内核、驱动 | 高 | MMU配置、进程调度、系统调用处理 |
| **EL2** | 虚拟化层 | Hypervisor（KVM/Xen） | 更高 | CPU虚拟化、中断虚拟化、VM切换 |
| **EL3** | 安全监控 | Trusted Firmware、OP-TEE | 最高 | 安全世界切换、信任链管理 |

CPU上电后从EL3开始执行，初始化完成后逐级下降。Linux这种普通操作系统跑在EL1，用户程序跑在EL0。如果你在做虚拟化，KVM的代码运行在EL2，管理多个Guest OS。<br>

EL3是个特殊的存在——它负责"安全世界"和"普通世界"的切换。当你用手机指纹解锁时，指纹传感器的数据处理就是在安全世界里完成的，EL3充当两个世界之间的"守门人"。

### 异常级别怎么切换

切换方向只有一条规则：**只能通过异常（Exception）提升级别，只能通过ERET指令降低级别**。

```mermaid
graph LR
    A[EL0 用户程序] --"系统调用 svc #0"--> B[EL1 内核]
    A --"访问非法地址"--> B
    B --"eret返回"--> A
    B --"访问虚拟化寄存器陷入"--> C[EL2 Hypervisor]
    C --"eret返回"--> B
    C --"安全世界调用smc"--> D[EL3 Secure Monitor]
    D --"eret返回"--> C

    style A fill:#e1f5fe
    style B fill:#fff3e0
    style C fill:#f3e5f5
    style D fill:#ffebee
```

用户程序想要读个文件？触发`svc #0`系统调用，CPU从EL0"跳"到EL1，内核接手处理。处理完了执行`eret`，沿着来时的路返回。这条路径不能绕过——硬件里写死了。<br>

想知道自己当前跑在哪个级别？读`CurrentEL`寄存器就行：

```asm
/* 读取当前异常级别 */
mrs x0, CurrentEL         /* CurrentEL[3:2] 存放EL值 */
lsr x0, x0, #2            /* 右移2位，得到 0/1/2/3 */
```

系统启动时，内核把异常向量表的地址写入`VBAR_EL1`（Vector Base Address Register），这样CPU遇到异常时就知道该跳到哪里：

```asm
/* arch/arm64/kernel/head.S 中设置向量表 */
ldr x0, =vectors
msr VBAR_EL1, x0          /* 将向量表基地址写入VBAR_EL1 */
isb                       /* 指令同步屏障，确保生效 */
```

### 异常向量表：entry.S里的"应急手册"

`arch/arm64/kernel/entry.S` 里定义了ARM64的异常向量表`vectors`。它不是一张简单的跳转表，而是按照异常来源和当前级别精心排列的16个入口：

```mermaid
graph TD
    V[vectors 基地址] --> S1[同步异常: 当前EL使用SP_EL0]
    V --> S2[IRQ: 当前EL使用SP_EL0]
    V --> S3[FIQ: 当前EL使用SP_EL0]
    V --> S4[SError: 当前EL使用SP_EL0]
    V --> S5[同步异常: 当前EL使用SP_ELx]
    V --> S6[IRQ: 当前EL使用SP_ELx]
    V --> S7[FIQ: 当前EL使用SP_ELx]
    V --> S8[SError: 当前EL使用SP_ELx]
    V --> S9[同步异常: 低EL运行在AArch64]
    V --> S10[IRQ: 低EL运行在AArch64]
    V --> S11[FIQ: 低EL运行在AArch64]
    V --> S12[SError: 低EL运行在AArch64]
    V --> S13[同步异常: 低EL运行在AArch32]
    V --> S14[IRQ: 低EL运行在AArch32]
    V --> S15[FIQ: 低EL运行在AArch32]
    V --> S16[SError: 低EL运行在AArch32]

    style V fill:#fff3e0
    style S5 fill:#e8f5e9
    style S6 fill:#e8f5e9
    style S9 fill:#e1f5fe
    style S10 fill:#e1f5fe
```

**16个入口的排列逻辑**：4种异常类型（同步、IRQ、FIQ、SError）× 4种上下文（当前EL用SP_EL0、当前EL用SP_ELx、来自低EL且AArch64、来自低EL且AArch32）。Linux内核中最常用的是**S6（EL1中发生的IRQ）**和**S9（用户态触发的同步异常，如系统调用、page fault）**。

## <span class="blue">同步异常与异步中断：两种完全不同的"打扰" [M]

异常不是只有一种。有些是你自己踩了坑（同步异常），有些是外设来敲门（异步中断）。搞混这两者，排查问题时容易南辕北辙。

### 同步异常：自己踩的坑

同步异常的特点是——**跟你的某条指令直接相关，执行到哪条就炸哪条**。触发原因包括：

- **Data Abort**：访问了非法内存地址（最常见的page fault就属于这类）
- **Instruction Abort**：取指令时地址翻译失败
- **Undefined Instruction**：执行了CPU不认识的指令码
- **SVC/HVC/SMC**：软件主动触发的系统调用
- **Alignment Fault**：未对齐的内存访问

> 💡 **提示**：page fault是同步异常中的data abort，这是**正常的内存管理机制**，不是错误。进程访问的虚拟地址还没映射到物理页，MMU触发data abort，内核的page fault处理函数分配物理页、建立映射，一切恢复如常。如果你看到日志里频繁的page fault，别慌，这可能是正常的按需分配（demand paging）在工作。

### 异步中断：外设来敲门

异步中断跟当前执行的指令没有直接关系——它**随时可能到来**，由外部设备触发：

- **IRQ（Interrupt Request）**：普通中断，如定时器到期、网卡收到数据包
- **FIQ（Fast Interrupt Request）**：快速中断，优先级高于IRQ，Linux中很少用
- **SError**：系统错误，如外部总线故障、奇偶校验错误

| 对比维度 | 同步异常 | 异步中断 |
|:---:|:---|:---|
| **触发原因** | 指令执行本身导致 | 外部设备信号触发 |
| **与指令关系** | 与触发指令精确相关 | 与当前指令无关，随机到达 |
| **典型类型** | Data Abort、SVC、Undefined Instruction | IRQ（定时器、网卡）、FIQ |
| **是否可屏蔽** | 一般不可屏蔽 | IRQ/FIQ可通过PSTATE.I/F位屏蔽 |
| **Linux处理** | do_mem_abort、el0_svc | handle_IRQ |
| **返回值** | 通常返回触发指令的下一条 | 返回被中断的位置继续执行 |
| **是否可恢复** | 多数可恢复（page fault），有些不可（Oops） | 总是可恢复 |

怎么处理同步异常？CPU把触发异常的指令地址存入`ELR_EL1`（Exception Link Register），把异常原因写入`ESR_EL1`（Exception Syndrome Register），然后跳到向量表中对应的入口。内核从`ESR_EL1`读取`EC`（Exception Class）字段，就知道具体是哪类异常了。

异步中断的处理流程则完全不同——它需要GIC的参与。这就是下一个知识点的主题。

## <span class="blue">GICv2双组件架构：Distributor与CPU Interface [I]

GICv2（Generic Interrupt Controller version 2）是ARM最经典的中断控制器架构。从软件角度看，它由两个独立的硬件组件构成，各自有独立的寄存器接口。

### GICv2整体架构

```mermaid
graph LR
    subgraph "SoC内部"
        D[🎯 GIC Distributor<br/>GICD_* 寄存器] 
        CI[🖥️ CPU Interface<br/>GICC_* 寄存器]
    end
    
    SPI[外设: SPI<br/>共享外设中断] --> D
    PPI[CPU私有: PPI<br/>定时器/调试] --> CI
    SGI[软件触发: SGI<br/>CPU间中断] --> D
    
    D --"中断分发<br/>路由到目标CPU"--> CI
    CI --"ACK/EOI信号"--> D
    CI --"断言IRQ/FIQ<br/>到CPU核心"--> CPU[ARM CPU核心]

    style D fill:#fff3e0
    style CI fill:#e1f5fe
    style CPU fill:#f3e5f5
```

| 组件 | 寄存器前缀 | 核心职责 |
|:---:|:---:|:---|
| **Distributor** | `GICD_*` | 全局中断使能、优先级设置、目标CPU路由、SGI生成 |
| **CPU Interface** | `GICC_*` | 中断确认（ACK）、优先级屏蔽、向CPU发送IRQ/FIQ信号、EOI通知 |

**Distributor**是全局的，所有CPU共享同一个。它决定了这个中断该发给哪个CPU（或哪些CPU）。**CPU Interface**是每个CPU核心私有的，它决定"当前这个CPU要不要响应这个中断"。<br>

一个中断从外设到CPU的完整路径是：外设拉高中断线 → Distributor检测到Pending → Distributor根据路由规则发给目标CPU的CPU Interface → CPU Interface判断优先级是否足够高 → CPU Interface向CPU核心断言IRQ信号 → CPU从异常向量表进入IRQ处理 → 读取GICC_IAR确认中断 → 处理中断 → 写GICC_EOI通知完成。<br>

### 中断状态机：四个状态的流转

每个中断在GIC内部都有一个状态机，这是理解中断处理的核心：

```mermaid
stateDiagram-v2
    [*] --> Inactive : 初始/复位
    Inactive --> Pending : 外设触发中断
    Pending --> Active : CPU读取GICC_IAR (ACK)
    Active --> Inactive : CPU写入GICC_EOI
    Active --> ActiveAndPending : 中断处理期间外设再次触发
    ActiveAndPending --> Active : 写EOI但仍有新Pending
    ActiveAndPending --> Pending : 不常见（重新分发）
    Pending --> Inactive : 软件清除或屏蔽
```

| 转换 | 条件 | 说明 |
|:---:|:---|:---|
| **Inactive → Pending** | 中断源触发 | 外设拉高信号线，Distributor检测到 |
| **Pending → Active** | CPU读`GICC_IAR`（ACK） | CPU"签收"了这个中断，开始处理 |
| **Active → Inactive** | CPU写`GICC_EOI` | 处理完毕，通知GIC可以清理 |
| **Active → Active and Pending** | 处理期间再次触发 | 边沿触发的中断可能重复触发 |
| **Active and Pending → Active** | 写EOI但新Pending仍在 | 需要再次ACK/处理 |
| **Pending → Inactive** | 软件写`GICD_ICPENDR` | 手动清除pending状态 |

**Inactive**表示这个中断线当前没事。**Pending**表示"有个活等你干"，但CPU还没开始处理。**Active**表示CPU正在处理。**Active and Pending**表示CPU正在处理上一轮，但外设又触发了新一轮——这在高速外设上很常见。<br>

### 优先级机制：数字越小越 urgent

GICv2支持中断优先级，通常用3-8位表示（0-255）。**数值越小，优先级越高**。这意味着优先级0是最高优先级，优先级255是最低。

> ⚠️ **陷阱**：优先级数字越小越高，这与大多数人的直觉相反！很多新手设了个高数值以为优先级高，结果中断被其他中断抢了。记住：**GIC的优先级是"倒数"的，0最急，255最闲。**

高优先级中断可以抢占低优先级中断的处理。CPU Interface里有一个`GICC_PMR`（Priority Mask Register），只有优先级高于这个阈值的中断才能打断当前CPU。Linux内核初始化时会在这里设置合适的掩码。

### 关键代码路径：irq-gic.c

GICv2的Linux驱动在`drivers/irqchip/irq-gic.c`中。初始化流程会配置Distributor和CPU Interface：

```c
/* drivers/irqchip/irq-gic.c: GIC Distributor初始化 */
static void __init gic_dist_config(void __iomem *base, int gic_irqs,
                                    void (*sync_access)(void))
{
    unsigned int i;

    /* 1. 关闭所有中断的转发（全局禁用） */
    writel_relaxed(0, base + GICD_CTLR);
    gic_dist_wait_for_rwp(base, sync_access);

    /* 2. 设置所有SPI的默认目标CPU（通常是CPU0） */
    for (i = 32; i < gic_irqs; i += 4)
        writel_relaxed(cpu_mask, base + GICD_ITARGETSR + i * 4 / 4);

    /* 3. 设置所有中断的默认优先级 */
    for (i = 0; i < gic_irqs; i += 4)
        writel_relaxed(0xa0a0a0a0, base + GICD_IPRIORITYR + i);

    /* 4. 清除所有中断的Pending状态 */
    for (i = 0; i < gic_irqs; i += 32)
        writel_relaxed(0xffffffff, base + GICD_ICPENDR + i / 8);

    /* 5. 全局使能中断转发 */
    writel_relaxed(GICD_CTLR_ENABLE_GRP0 | GICD_CTLR_ENABLE_GRP1,
                   base + GICD_CTLR);
}
```

`0xa0a0a0a0`这个默认值很有意思——每个字节是160（0xa0），属于中等偏低的优先级。具体设备的驱动注册中断时通常会调用`irq_set_priority()`调整自己的优先级。<br>

CPU Interface的初始化更简洁：

```c
/* drivers/irqchip/irq-gic.c: CPU Interface初始化 */
static void gic_cpu_init(struct gic_chip_data *gic)
{
    void __iomem *dist_base = gic->dist_base;
    void __iomem *cpu_base = gic->cpu_base;
    unsigned int cpu_mask, cpu;

    cpu_mask = gic_get_cpumask(gic);
    cpu = gic_smp_processor_id();

    /* 1. 确保SGI和PPI的目标包含当前CPU */
    writel_relaxed(cpu_mask, dist_base + GICD_ITARGETSR);

    /* 2. 设置SGI和PPI的优先级 */
    for (i = 0; i < 32; i += 4)
        writel_relaxed(0xa0a0a0a0,
                       dist_base + GICD_IPRIORITYR + i);

    /* 3. 使能当前CPU的SGI和PPI */
    writel_relaxed(0xffff0000, dist_base + GICD_ISENABLER);

    /* 4. 设置优先级掩码：允许优先级高于0xf0的中断通过 */
    writel_relaxed(0xf0, cpu_base + GICC_PMR);

    /* 5. 使能CPU Interface的中断信号 */
    writel_relaxed(GICC_CTLR_ENABLE_GRP0 | GICC_CTLR_ENABLE_GRP1,
                   cpu_base + GICC_CTLR);
}
```

`GICC_PMR = 0xf0` 是个关键值——只有优先级数值**小于0xf0**（即0-239）的中断才能穿过这道门。结合前面默认优先级0xa0（160），0xa0 < 0xf0，所以默认配置的中断都能通过。<br>

GICv2在现代芯片中（如Cortex-A53/A57）非常常见，但更新的架构已经用上了GICv3/GICv4（支持LPI、更灵活的路由）。不过对于理解中断控制器的基本原理，GICv2的这套模型已经足够经典。

## <span class="blue">本节总结

| 主题 | 核心要点 |
|:---|:---|
| **异常级别EL0-EL3** | 四级权限体系，EL0用户态→EL1内核→EL2虚拟化→EL3安全监控，只能经异常提升、ERET降低 |
| **同步异常** | 与触发指令直接相关，包括page fault（data abort）、SVC系统调用、undefined instruction |
| **异步中断** | 由外部设备触发，与当前指令无关，包括IRQ/FIQ/SError |
| **异常向量表** | `arch/arm64/kernel/entry.S`中16个入口，按异常类型×来源上下文排列 |
| **GICv2 Distributor** | 全局组件，负责中断使能、优先级、目标CPU路由 |
| **GICv2 CPU Interface** | 每CPU私有，负责ACK、EOI、优先级屏蔽、向CPU发IRQ信号 |
| **中断状态机** | Inactive→Pending→Active→Active and Pending，ACK读IAR、EOI写EOIR |
| **优先级规则** | **数字越小优先级越高**，0x00最高，可配置PMR做阈值屏蔽 |
