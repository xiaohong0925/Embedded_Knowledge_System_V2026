# 10.5.5 深度睡眠唤醒延迟与hrtimer精度

> 所属章节：第10章 中断与时间 > 10.5 hrtimer高分辨率定时器
>
> 难度：[E] Expert | 预计阅读时间：25分钟

## <span class="blue"> 本节导读

你有没有遇到过这样的诡异 bug？音频播放偶尔"啪"地爆一下音，而且完全随机、无法复现。查了半天代码逻辑都没问题，最后才发现——原来是CPU在偷懒睡大觉！<br>
本节带你深入 CPU C-state 与 hrtimer 之间的"爱恨情仇"：当 CPU 进入深度睡眠，hrtimer 的回调可能被延迟数百微秒，这对音视频、实时控制等场景是致命的。<br>
学完后，你将理解 C-state 对定时器精度的影响机制，掌握排查此类问题的思路，并学会在系统中找到低延迟与省电的最佳平衡点。

## <span class="blue"> CPU C-state：省电的代价是延迟 [E]

现代 CPU 为了省电，支持多种睡眠状态（C-state）。C0 是正常运行，C1-C7 则是逐层递进的"昏睡"——睡得越深，省得越多，但叫醒的时间也越长。

```
     ┌─────────────────────────────────────────────────────┐
     │  CPU C-state 层级与功耗/延迟关系                      │
     │                                                      │
     │  C0(运行) ──► C1(暂停) ──► C3(睡眠) ──► C6(深睡)    │
     │     │              │              │              │    │
     │   0μs           ~1μs         ~100μs        ~500μs    │
     │  唤醒延迟          功耗递增 ◄──────────────────────   │
     │                                                      │
     │  问题：hrtimer 精度在深 C-state 下劣化严重              │
     └─────────────────────────────────────────────────────┘
```

### C-state 等级与唤醒延迟对照

| C-state | 名称 | 典型唤醒延迟 | 节省功耗 | 适用场景 | 对 hrtimer 影响 |
|:---:|:---:|:---:|:---:|:---:|:---:|
| C0 | 运行 | 0 μs | 无 | 全速计算 | 无影响 |
| C1/C1E | 暂停时钟 | ~1 μs | 低 | 轻负载 | 可忽略 |
| C2 | 停止时钟 | ~5 μs | 中低 | 间歇负载 | 轻微 |
| C3 | 睡眠 | ~50-100 μs | 中 | 桌面空闲 | 中等 |
| C6 | 深睡 | ~200-500 μs | 高 | 笔记本空闲 | 严重 |
| C7 | 更深睡 | ~500+ μs | 极高 | 极致省电 | 致命 |

> 💡 **提示**：`/sys/devices/system/cpu/cpuN/cpuidle/state*/latency` 可以读取每个 C-state 的唤醒延迟，比上表更准——那是你手上那台 CPU 的真实数据。

不同架构的延迟数值会有差异，但趋势是一致的：**C-state 越深，唤醒延迟越大**。这个延迟不是文档里写的"大概"数字，而是 hrtimer 唤醒 CPU 后必须等待的时间窗口。定时器到期了，可 CPU 还在"睁眼"的过程中，回调函数只能干等着。

## <span class="blue"> 音频爆音：一个真实的hrtimer延迟案例 [E]

说了半天理论，到底会出什么 bug？来看一个我排查过的真实案例。

某 ARM 设备播放 48kHz 音频时，偶发爆音。音频驱动通过 hrtimer 每 20.8μs 触发一次 DMA 传输（`1000000 / 48000 ≈ 20.8μs`）。大部分时候正常，但每隔几分钟就"咔"一声。

```
    正常情况                         爆音时刻
    ──────────────────────────────────────────────────
    hrtimer到期 ──► 回调 ──► DMA填充 ──► 播放正常     (CPU在C0/C1)
    
    hrtimer到期 ──► CPU在深C6沉睡 ──► 500μs唤醒延迟   
                                     ──► 回调迟到 ──► 
                                     DMA缓冲区欠载 ──► 爆音!
```

咋回事？当系统负载低、CPU 进入 C6 深睡状态时，hrtimer 到期信号发了出去，但 CPU 要从 C6 醒来需要 200-500μs。音频 DMA 每 20.8μs 就要喂一次数据，这一下子欠了二十多个周期的数据，缓冲区空了，DAC 没得输出了——爆音就是这么来的。

```
    DMA缓冲区水位变化（爆音时刻）
    
    水位
     ▲
  满 ┤    ╱╲    ╱╲    ╱╲    ╱╲    ╱╲
     │   ╱  ╲  ╱  ╲  ╱  ╲  ╱  ╲  ╱  ╲
     │  ╱    ╲╱    ╲╱    ╲╱    ╲╱    ╲  ← 正常填充
  空 ┤─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─╲── 💥 欠载爆音!
     └─────────────────────────────────────► 时间
              ↑
         CPU进入C6，hrtimer回调延迟500μs
```

> ⚠️ **陷阱**：这种 bug 很难复现，因为它只在 CPU "恰好"进入深 C-state 时才会触发。如果你用高负载测试，CPU 根本睡不着，问题反而不会出现——这就是为啥好多人踩了这个坑还摸不着头脑。

## <span class="blue"> 问题根因与解决方案对照 [E]

| 问题现象 | 根因 | 解决方案 | 副作用 |
|:---:|:---:|:---:|:---:|
| 音频偶发爆音/卡顿 | CPU深C-state导致hrtimer延迟 | 禁用音频CPU的deep idle | 该CPU功耗增加 |
| 实时任务周期性抖动 | tickless模式下CPU休眠过深 | 改用WAKEUP_LATENCY敏感的cpuidle governor | 功耗微调 |
| hrtimer精度不稳定 | 任务在不同CPU间迁移，C-state不同 | 使用HRTIMER_MODE_ABS_PINNED绑定CPU | 失去负载均衡 |
| 高分辨率采样任务丢数据 | NO_HZ_IDLE导致tick完全停掉 | 对该CPU启用nohz_full并隔离 | 需要额外CPU |

### 方案一：禁用深 C-state

最直接粗暴的方式——让负责音频的 CPU 不准睡那么死：

```bash
# 查看CPU0有哪些idle state
$ ls /sys/devices/system/cpu/cpu0/cpuidle/
state0  state1  state2  state3

# 查看每个state的延迟和名称
$ for s in /sys/devices/system/cpu/cpu0/cpuidle/state*; do
>   echo "$(basename $s): latency=$(cat $s/latency) name=$(cat $s/name)"
> done
state0: latency=1 name=POLL
state1: latency=10 name=C1
state2: latency=100 name=C3
state3: latency=500 name=C6

# 禁用C6（延迟500μs的那个）
$ echo 1 > /sys/devices/system/cpu/cpu0/cpuidle/state3/disable
```

> 🔴 **危险**：`echo` 到 `cpuidle/disable` 的值在重启后会丢失！如果你是在产品上做这个改动，务必写个 systemd 服务来持久化：
> ```ini
> # /etc/systemd/system/disable-c6.service
> [Unit]
> Description=Disable CPU C6 for audio CPU
> After=multi-user.target
> 
> [Service]
> Type=oneshot
> ExecStart=/bin/bash -c 'echo 1 > /sys/devices/system/cpu/cpu0/cpuidle/state3/disable'
> RemainAfterExit=yes
> 
> [Install]
> WantedBy=multi-user.target
> ```

### 方案二：hrtimer 绑定 CPU

让音频相关的 hrtimer 只在指定的 CPU 上跑，配合方案一锁定该 CPU 的 C-state：

```c
// 设置 hrtimer 为 ABS + PINNED 模式
hrtimer_init(&audio_timer, CLOCK_MONOTONIC, HRTIMER_MODE_ABS_PINNED);

// 这样timer到期只在绑定的CPU上处理，不会迁移到"正在深睡"的CPU
// 注意：需要配合kthread的cpu亲和性设置
```

### 方案三：换 cpuidle governor

从"尽量省电"切换到"平衡延迟"模式：

```bash
# 查看当前governor
$ cat /sys/devices/system/cpu/cpuidle/current_driver
intel_idle
$ cat /sys/devices/system/cpu/cpuidle/current_governor
menu

# 切换到ladder或自定义的延迟敏感governor
$ echo ladder > /sys/devices/system/cpu/cpuidle/current_governor
```

`menu` governor 偏向省电，`ladder` governor 更保守，对 wakeup latency 更敏感。有些实时 Linux 发行版还会自带专门的 `teo` 改进版本。

## <span class="blue"> 实战带练：hrtimer精度测试实验 [E]

光说不练假把式。下面这个内核模块可以实测 hrtimer 在不同 C-state 下的精度表现，是你排查此类问题的利器。

### 测试模块代码

```c
// hrtimer_precision_test.c
// 测试hrtimer在不同CPU idle状态下的精度

#include <linux/module.h>
#include <linux/hrtimer.h>
#include <linux/ktime.h>
#include <linux/kernel.h>
#include <linux/kthread.h>
#include <linux/sched.h>
#include <linux/spinlock.h>

#define TEST_DURATION_MS    5000    // 总测试时长5秒
#define TIMER_INTERVAL_US   10      // 目标间隔10微秒
#define MAX_SAMPLES         600000  // 最大采样数（5秒/10us）

static struct hrtimer test_timer;
static ktime_t last_expire;
static ktime_t start_time;

// 记录每次的实际间隔（单位：纳秒）
static s64 intervals_ns[MAX_SAMPLES];
static int sample_count;
static DEFINE_SPINLOCK(sample_lock);

// 统计结果
static s64 min_ns, max_ns, sum_ns, avg_ns;
static s64 stddev_ns;

static enum hrtimer_restart test_timer_callback(struct hrtimer *timer)
{
    ktime_t now = ktime_get();
    s64 interval;
    unsigned long flags;

    interval = ktime_to_ns(ktime_sub(now, last_expire));
    last_expire = now;

    // 记录间隔，忽略第一个（没有前次参考）
    spin_lock_irqsave(&sample_lock, flags);
    if (sample_count < MAX_SAMPLES && sample_count > 0) {
        intervals_ns[sample_count - 1] = interval;
    }
    sample_count++;
    spin_unlock_irqrestore(&sample_lock, flags);

    // 重新设置下一个到期时间（绝对时间模式）
    hrtimer_forward_now(timer, ns_to_ktime(TIMER_INTERVAL_US * 1000));
    
    return HRTIMER_RESTART;
}

static void analyze_results(void)
{
    s64 target_ns = TIMER_INTERVAL_US * 1000LL;
    s64 sum_sq = 0;
    int i;
    int valid_samples = min(sample_count - 1, MAX_SAMPLES);

    if (valid_samples <= 0) {
        pr_err("No valid samples collected\n");
        return;
    }

    min_ns = intervals_ns[0];
    max_ns = intervals_ns[0];
    sum_ns = 0;

    for (i = 0; i < valid_samples; i++) {
        s64 v = intervals_ns[i];
        if (v < min_ns) min_ns = v;
        if (v > max_ns) max_ns = v;
        sum_ns += v;
    }

    avg_ns = div64_s64(sum_ns, valid_samples);

    // 计算标准差
    for (i = 0; i < valid_samples; i++) {
        s64 diff = intervals_ns[i] - avg_ns;
        sum_sq += diff * diff;
    }
    stddev_ns = int_sqrt64(div64_s64(sum_sq, valid_samples));

    pr_info("=== hrtimer Precision Test Results ===\n");
    pr_info("Target interval: %lld us\n", target_ns / 1000);
    pr_info("Total samples:   %d\n", valid_samples);
    pr_info("Min interval:    %lld us (%+lld us)\n",
            min_ns / 1000, (min_ns - target_ns) / 1000);
    pr_info("Max interval:    %lld us (%+lld us)\n",
            max_ns / 1000, (max_ns - target_ns) / 1000);
    pr_info("Avg interval:    %lld us (%+lld us)\n",
            avg_ns / 1000, (avg_ns - target_ns) / 1000);
    pr_info("Std deviation:   %lld us\n", stddev_ns / 1000);
    
    // 关键指标：最大延迟是否超过目标间隔的10倍
    if (max_ns > target_ns * 10) {
        pr_warn("⚠️  Max delay exceeds 10x target! "
                "C-state interference detected.\n");
    }
}

static int __init hrtimer_test_init(void)
{
    ktime_t interval = ns_to_ktime(TIMER_INTERVAL_US * 1000);

    pr_info("hrtimer precision test starting...\n");
    pr_info("Target interval: %d us, Duration: %d ms\n",
            TIMER_INTERVAL_US, TEST_DURATION_MS);

    last_expire = ktime_get();
    start_time = last_expire;

    hrtimer_init(&test_timer, CLOCK_MONOTONIC, HRTIMER_MODE_ABS_PINNED);
    test_timer.function = test_timer_callback;
    hrtimer_start(&test_timer, interval, HRTIMER_MODE_ABS_PINNED);

    return 0;
}

static void __exit hrtimer_test_exit(void)
{
    hrtimer_cancel(&test_timer);
    analyze_results();
    pr_info("hrtimer precision test exited\n");
}

module_init(hrtimer_test_init);
module_exit(hrtimer_test_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("hrtimer precision test module");
```

### 实验步骤

**第一步：编译并加载模块**

```bash
# Makefile
obj-m += hrtimer_precision_test.o
all:
    make -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules
clean:
    make -C /lib/modules/$(shell uname -r)/build M=$(PWD) clean
```

```bash
$ make
$ sudo insmod hrtimer_precision_test.ko
$ dmesg -w
```

**第二步：对比不同配置下的精度**

| 测试场景 | 操作命令 | 预期结果 |
|:---:|:---:|:---:|
| 基准（正常负载） | 直接加载模块 | max 延迟 ~20μs |
| CPU强制深睡 | `echo 0 > /sys/devices/system/cpu/cpu0/cpuidle/state0/disable` 后等待系统空闲 | max 延迟可达 500μs+ |
| 禁用C6 | `echo 1 > /sys/devices/system/cpu/cpu0/cpuidle/state3/disable` 后测试 | max 延迟 < 100μs |
| NO_HZ 开启 | 确认 `CONFIG_NO_HZ_IDLE=y` | 空闲时精度更差 |
| NO_HZ 关闭 | 使用 `CONFIG_HZ_PERIODIC` | 精度更稳定但费电 |

**第三步：分析 dmesg 输出**

重点关注这几个指标：

- **Max interval**：如果远大于目标值（如 10μs 目标出现 500μs），说明深 C-state 在捣乱
- **Std deviation**：标准差越大，抖动越严重
- **Min interval**：几乎总是接近目标值（CPU 醒着的时候很快）

> 💡 **提示**：做对比实验时，用 `taskset -c 0 insmod ...` 把模块绑定到固定 CPU 上，避免 CPU 迁移带来的额外噪声干扰数据。

## <span class="blue"> tickless 与低延迟的权衡 [E]

这个问题本质上是一个 trade-off：

```
        ┌──────────────────────────────────────┐
        │        tickless (CONFIG_NO_HZ)       │
        │                                      │
        │   NO_HZ_IDLE  ◄────────►  HZ_PERIODIC │
        │                                      │
        │   更省电 ✓          更高精度 ✓         │
        │   更深C-state        CPU保持警觉       │
        │   hrtimer延迟大      hrtimer延迟小      │
        │                                      │
        │   手机/笔记本        工业/音频/实时     │
        └──────────────────────────────────────┘
```

`CONFIG_NO_HZ_IDLE` 模式下，空闲 CPU 的 tick 会完全停掉，CPU 可以毫无顾虑地睡到最深处。这对手机续航是好事，对音频播放就是噩梦。

如果你追求的是**确定性延迟**而不是极致续航，有这几个方向可选：

| 配置选项 | 效果 | 适用场景 |
|:---:|:---:|:---:|
| `CONFIG_HZ_PERIODIC` | 关闭tickless，保持固定tick | 硬实时系统 |
| `CONFIG_NO_HZ_FULL` + CPU隔离 | 仅指定CPU关闭tick，其余正常 | 混合负载 |
| `irqaffinity=` + 深C-state禁用 | 关键任务独占CPU | 音视频设备 |
| `intel_pstate=disable` | 关闭P-state调节，减少唤醒因素 | 老旧平台调试 |

内核编译时的一个关键选择：`CONFIG_NO_HZ_IDLE=y` 是大多数发行版的默认配置——省电优先。如果你在做工业控制、音视频处理，这个默认配置可能就是你的定时器精度问题的根因。

## <span class="blue"> 本节总结

| 要点 | 内容 |
|:---:|:---|
| 核心问题 | CPU 深 C-state（C3/C6/C7）唤醒延迟可达数十至数百微秒，导致 hrtimer 回调迟到 |
| 典型症状 | 音视频偶发爆音/卡顿、实时任务周期性抖动、高频率采样数据丢失 |
| 根因机制 | hrtimer 到期信号需要唤醒 CPU，但深 C-state 退出延迟远大于定时器周期 |
| 诊断方法 | 用精度测试模块测量实际间隔分布，对比 min/max/stddev |
| 解决方案 | ① 禁用相关 CPU 的深 C-state ② ABS_PINNED 模式绑定 CPU ③ 换 latency 敏感 governor |
| 持久化注意 | cpuidle/disable 的写入重启后失效，需 systemd 服务或 initscript |
| 权衡取舍 | tickless 省电 vs 低延迟不可兼得，需按场景选择内核配置 |
