# 10.5.5 深度睡眠唤醒延迟与hrtimer精度

> 所属章节：第10章 中断与时间 > 10.5 时间子系统
>
> 难度：[E] | 预计阅读时间：25分钟

## <span class="blue"> 本节导读

音频播放偶尔爆音，随机出现、难以复现，代码逻辑查不出问题——最后一查，是 CPU 进了深度睡眠。

本节覆盖：

- C-state 唤醒延迟对 hrtimer 精度的影响机制、
- 一个真实音频爆音案例的完整分析、
- 三种解决方案（禁用深 C-state / 定时器绑核 / 换 cpuidle governor），
- 以及一个可直接编译运行的 hrtimer 精度测试模块。

## <span class="blue"> CPU C-state：省电的代价是唤醒延迟 [E]

现代 CPU 支持多级睡眠状态（C-state）：C0 正常运行，C1 到 C7 逐级加深——睡得越深省电越多，唤醒耗时也越长。

```
     ┌─────────────────────────────────────────────────────┐
     │  CPU C-state 层级与功耗/延迟关系                   │
     │                                                  │
     │  C0(运行) ──► C1(暂停) ──► C3(睡眠) ──► C6(深睡)   │
     │     │              │              │         │    │
     │   0μs           ~1μs         ~100μs      ~500μs  │
     │  唤醒延迟          省电递增 ◄──────────────────────   │
     │                                                   │
     │  hrtimer 精度在深 C-state 下显著劣化               │
     └─────────────────────────────────────────────────────┘
```

### C-state 等级与唤醒延迟对照

| C-state | 名称 | 典型唤醒延迟 | 省电程度 | 对 hrtimer 影响 |
|:---:|:---:|:---:|:---:|:---:|
| C0 | 运行 | 0 μs | 无 | 无影响 |
| C1/C1E | 暂停时钟 | ~1 μs | 低 | 可忽略 |
| C2 | 停止时钟 | ~5 μs | 中低 | 轻微 |
| C3 | 睡眠 | ~50–100 μs | 中 | 中等 |
| C6 | 深睡 | ~200–500 μs | 高 | 严重 |
| C7 | 更深睡 | ~500+ μs | 极高 | 严重 |

> 💡 上表是量级参考。手上设备的真实数据在 `/sys/devices/system/cpu/cpuN/cpuidle/state*/latency`，以它为准。

趋势恒定：**C-state 越深，唤醒延迟越大**。<BR>
这个延迟就落在 hrtimer 的关键路径上—> 定时器到期信号发出后，CPU 还要花这段时间完成唤醒，回调只能等唤醒完成后才执行。

## <span class="blue"> 音频爆音：一个真实的hrtimer延迟案例 [E]

某 ARM 设备播放 48kHz 音频，偶发爆音。<BR>
音频驱动用 hrtimer 每 20.8μs（`1000000 / 48000`）触发一次 DMA 填充。<BR>
大部分时候正常，每隔几分钟出现一声爆音。

```
    正常情况                         爆音时刻
    ──────────────────────────────────────────────────
    hrtimer到期 ──► 回调 ──► DMA填充 ──► 播放正常     (CPU在C0/C1)

    hrtimer到期 ──► CPU在C6深睡 ──► 唤醒延迟数百μs
                                     ──► 回调迟到 ──►
                                     DMA缓冲区欠载 ──► 爆音
```

机制：系统负载低时 CPU 进入 C6 深睡，hrtimer 到期后 CPU 从 C6 唤醒需要数百微秒；而音频 DMA 每 20.8μs 就要补一次数据，唤醒期间欠了二十多个周期，缓冲区耗尽、DAC 无数据可输出——爆音。

```
    DMA缓冲区水位变化（爆音时刻）

    水位
     ▲
  满 ┤    ╱╲    ╱╲    ╱╲    ╱╲    ╱╲
     │   ╱  ╲  ╱  ╲  ╱  ╲  ╱  ╲  ╱  ╲
     │  ╱    ╲╱    ╲╱    ╲╱    ╲╱    ╲  ← 正常填充
  空 ┤─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─╲── 欠载爆音
     └─────────────────────────────────────► 时间
              ↑
         CPU进入C6，hrtimer回调延迟数百μs
```

> ⚠️ 这类 bug 难以复现的原因：它只在 CPU"恰好"进入深 C-state 时触发。<BR>
> 高负载测试时 CPU 不会进深睡，问题反而不出现——所以压力测试测不出来，空闲场景才暴露。

## <span class="blue"> 问题根因与解决方案对照 [E]

| 问题现象 | 根因 | 解决方案 | 代价 |
|:---:|:---:|:---:|:---:|
| 音频偶发爆音/卡顿 | CPU 深 C-state 唤醒延迟 | 禁用相关 CPU 的深 C-state | 功耗增加 |
| 实时任务周期性抖动 | tickless 下 CPU 休眠过深 | 换延迟敏感的 cpuidle governor | 功耗微调 |
| hrtimer 精度不稳定 | 定时器迁移到正在深睡的 CPU | HRTIMER_MODE_*_PINNED 绑核 | 失去迁移灵活性 |
| 高频采样丢数据 | NO_HZ_IDLE 停 tick + 深睡 | CPU 隔离 + 禁用深 C-state | 需独占 CPU |

### 方案一：禁用深 C-state

直接的办法——不让负责音频的 CPU 睡那么深：

```bash
# 查看 CPU0 有哪些 idle state
ls /sys/devices/system/cpu/cpu0/cpuidle/
# state0  state1  state2  state3

# 查看每个 state 的延迟和名称
for s in /sys/devices/system/cpu/cpu0/cpuidle/state*; do
  echo "$(basename $s): latency=$(cat $s/latency) name=$(cat $s/name)"
done
# state0: latency=1 name=POLL
# state1: latency=10 name=C1
# state2: latency=100 name=C3
# state3: latency=500 name=C6

# 禁用延迟 500μs 的 C6
echo 1 > /sys/devices/system/cpu/cpu0/cpuidle/state3/disable
```

> 🔴 写 `cpuidle/state*/disable` 的设置在重启后丢失。产品化时必须持久化，例如用 systemd 服务：
> ```ini
> # /etc/systemd/system/disable-c6.service
> [Unit]
> Description=Disable CPU C6 for audio CPU
> After=multi-user.target
>
> [Service]
> Type=oneshot
> ExecStart=/bin/bash -c 'echo 1 > /sys/devices/system/cpu/cpu0/cpuidle/state3/disable'
> RemainAfterExit=yes
>
> [Install]
> WantedBy=multi-user.target
> ```

### 方案二：hrtimer 绑定 CPU

让音频相关的 hrtimer 只在指定 CPU 上执行，配合方案一锁定该 CPU 的 C-state 上限：

```c
/* PINNED 模式：回调只在启动它的 CPU 上执行 */
hrtimer_init(&audio_timer, CLOCK_MONOTONIC, HRTIMER_MODE_ABS_PINNED);

/* 配合该 CPU 禁用深 C-state，定时器就不会落在"正在深睡"的核上 */
```

### 方案三：换 cpuidle governor

从"尽量省电"切换为"延迟敏感"的选择策略：

```bash
# 查看当前 driver 与 governor
cat /sys/devices/system/cpu/cpuidle/current_driver
cat /sys/devices/system/cpu/cpuidle/current_governor
# menu

# 切换 governor（可用项见 available_governor）
echo teo > /sys/devices/system/cpu/cpuidle/current_governor
```

主线内核的 cpuidle governor 主要有 `menu` 和 `teo`（Timeout Estimation Order，5.x 引入）：<BR>
`menu` 偏省电，`teo` 对"马上会有唤醒事件"的场景预测更积极，倾向选较浅的 C-state。<BR>
governor 是否可在线切换取决于内核配置与驱动。

## <span class="blue"> 实战：hrtimer精度测试模块 [E]

下面这个内核模块实测 hrtimer 在不同 C-state 配置下的精度分布，是排查此类问题的直接工具。

### 测试模块代码

```c
/* hrtimer_precision_test.c — 测试 hrtimer 在不同 CPU idle 状态下的精度 */
#include <linux/module.h>
#include <linux/hrtimer.h>
#include <linux/ktime.h>
#include <linux/kernel.h>
#include <linux/spinlock.h>

#define TIMER_INTERVAL_US   10      /* 目标间隔 10μs */
#define MAX_SAMPLES         600000  /* 最大采样数 */

static struct hrtimer test_timer;
static ktime_t last_expire;

static s64 intervals_ns[MAX_SAMPLES];
static int sample_count;
static DEFINE_SPINLOCK(sample_lock);

static enum hrtimer_restart test_timer_callback(struct hrtimer *timer)
{
	ktime_t now = ktime_get();
	s64 interval;
	unsigned long flags;

	interval = ktime_to_ns(ktime_sub(now, last_expire));
	last_expire = now;

	spin_lock_irqsave(&sample_lock, flags);
	if (sample_count < MAX_SAMPLES && sample_count > 0)
		intervals_ns[sample_count - 1] = interval;
	sample_count++;
	spin_unlock_irqrestore(&sample_lock, flags);

	hrtimer_forward_now(timer, ns_to_ktime(TIMER_INTERVAL_US * 1000));
	return HRTIMER_RESTART;
}

static void analyze_results(void)
{
	s64 target_ns = TIMER_INTERVAL_US * 1000LL;
	s64 min_ns, max_ns, sum_ns = 0, avg_ns, sum_sq = 0, stddev_ns;
	int i, valid = min(sample_count - 1, MAX_SAMPLES);

	if (valid <= 0) {
		pr_err("No valid samples\n");
		return;
	}

	min_ns = max_ns = intervals_ns[0];
	for (i = 0; i < valid; i++) {
		s64 v = intervals_ns[i];
		if (v < min_ns) min_ns = v;
		if (v > max_ns) max_ns = v;
		sum_ns += v;
	}
	avg_ns = div64_s64(sum_ns, valid);

	for (i = 0; i < valid; i++) {
		s64 diff = intervals_ns[i] - avg_ns;
		sum_sq += diff * diff;
	}
	stddev_ns = int_sqrt64(div64_s64(sum_sq, valid));

	pr_info("=== hrtimer Precision Test ===\n");
	pr_info("Target: %lld us, samples: %d\n", target_ns / 1000, valid);
	pr_info("Min: %lld us (%+lld us)\n",
		min_ns / 1000, (min_ns - target_ns) / 1000);
	pr_info("Max: %lld us (%+lld us)\n",
		max_ns / 1000, (max_ns - target_ns) / 1000);
	pr_info("Avg: %lld us, stddev: %lld us\n",
		avg_ns / 1000, stddev_ns / 1000);

	if (max_ns > target_ns * 10)
		pr_warn("Max delay exceeds 10x target: C-state interference suspected\n");
}

static int __init hrtimer_test_init(void)
{
	ktime_t interval = ns_to_ktime(TIMER_INTERVAL_US * 1000);

	pr_info("hrtimer precision test: interval %d us\n", TIMER_INTERVAL_US);

	last_expire = ktime_get();

	hrtimer_init(&test_timer, CLOCK_MONOTONIC, HRTIMER_MODE_ABS_PINNED);
	test_timer.function = test_timer_callback;
	hrtimer_start(&test_timer, interval, HRTIMER_MODE_ABS_PINNED);
	return 0;
}

static void __exit hrtimer_test_exit(void)
{
	hrtimer_cancel(&test_timer);
	analyze_results();
	pr_info("hrtimer precision test exited\n");
}

module_init(hrtimer_test_init);
module_exit(hrtimer_test_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("hrtimer precision test module");
```

### 实验步骤

**第一步：编译加载**

```makefile
obj-m += hrtimer_precision_test.o
all:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules
clean:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) clean
```

```bash
make
sudo insmod hrtimer_precision_test.ko
dmesg -w
```

**第二步：对比不同配置下的精度**

| 测试场景 | 操作 | 预期现象 |
|:---:|:---:|:---:|
| 基准（正常负载） | 直接加载 | max 延迟接近目标间隔的数倍以内 |
| 迫使 CPU 深睡 | 禁用浅层 state（`echo 1 > state0/disable`、`state1/disable`），让 idle 时只能选深层 | max 延迟可达数百 μs |
| 禁用深层 C6 | `echo 1 > state3/disable` | max 延迟回落 |
| NO_HZ_IDLE 开启 | `CONFIG_NO_HZ_IDLE=y` | 空闲时抖动更大 |
| 固定 tick | `CONFIG_HZ_PERIODIC` | 抖动更小但功耗上升 |

**第三步：分析输出**

- **Max interval**：远大于目标值（10μs 目标出现数百 μs）→ 深 C-state 唤醒延迟所致
- **Std deviation**：越大抖动越严重
- **Min interval**：通常接近目标值（CPU 醒着时很准）

> 💡 PINNED 模式下定时器回调在 `hrtimer_start()` 执行时所在的 CPU 上触发。<BR>
> 想把测试钉在指定核上，用 `taskset -c N insmod ...` 控制模块初始化运行的 CPU。

## <span class="blue"> tickless 与低延迟的权衡 [E]

```
        ┌──────────────────────────────────────┐
        │        tickless (CONFIG_NO_HZ)       │
        │                                      │
        │   NO_HZ_IDLE  ◄────────►  HZ_PERIODIC │
        │                                      │
        │   更省电              更稳定精度        │
        │   允许更深 C-state    CPU 保持周期性唤醒 │
        │   hrtimer 抖动大      hrtimer 抖动小     │
        │                                      │
        │   手机/笔记本          工业/音频/实时    │
        └──────────────────────────────────────┘
```

`CONFIG_NO_HZ_IDLE` 下，空闲 CPU 的 tick 完全停止，CPU 可以进入最深的 C-state——对续航有利，对微秒级定时不利。

追求确定性延迟时的可选方向：
| 配置/手段 | 效果 | 适用场景 |
|:---:|:---:|:---:|
| `CONFIG_HZ_PERIODIC` | 保持固定 tick | 硬实时系统 |
| `CONFIG_NO_HZ_FULL` + CPU 隔离 | 指定 CPU 关 tick 并独占 | 混合负载 |
| 禁用深 C-state + 中断亲和性 | 关键任务所在 CPU 不深睡 | 音视频设备 |

发行版默认 `CONFIG_NO_HZ_IDLE=y`——省电优先。<BR>
工业控制、音视频设备的定时器精度问题，根因往往就在这个默认配置上。tickless 的机制细节见 10.6。

## <span class="blue"> 本节总结

| 要点 | 内容 |
|:---:|:---|
| 核心问题 | 深 C-state（C3/C6/C7）唤醒延迟数十至数百微秒，hrtimer 回调随之迟到 |
| 典型症状 | 音频偶发爆音、实时任务周期性抖动、高频采样丢数据 |
| 根因 | hrtimer 到期需唤醒 CPU，深睡退出延迟远大于定时器周期 |
| 诊断 | 精度测试模块测 min/max/stddev 分布 |
| 解决方案 | 禁用深 C-state / PINNED 绑核 / 换 teo governor / CPU 隔离 |
| 持久化 | cpuidle 的 disable 设置重启失效，需 systemd 等服务固化 |
| 权衡 | tickless 省电与低延迟不可兼得，按场景选内核配置 |
