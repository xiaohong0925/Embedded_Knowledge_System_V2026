# 第10章：中断与时间

> 所属：第 二 部 核心机制深度解析
>
> BIEM：[I→E] | 核心问题：硬件中断如何变成软件事件？

## 核心问题

硬件中断如何变成软件事件？

## 为什么需要这一章

有经验工程师知道中断是"硬件通知 CPU 的方式"，知道顶半部和底半部的概念，知道 timer 可以定时触发。但面对"中断响应偶尔延迟几百微秒""hrtimer 的精度为什么比传统 timer 高一个数量级""tickless 模式下系统时间还能准确吗""为什么高精度定时器会触发 CPU 从 idle 唤醒"这些实际问题时，需要源码级的理解。

本章要解决的核心认知是：**中断和时间不是两个独立的子系统——定时器到期本身就是中断的一种**。理解它们在源码级的耦合关系（tick device layer 连接两者），是优化嵌入式系统响应性和功耗的关键。

## 本章主线：两条线，一个交汇点

本章的七节沿着两条主线展开，它们在 tick device 处交汇：

```
主线一：一个中断从硬件触发到被处理完的完整路径

  硬件信号 ──> 10.1 GIC ──> 10.2 顶半部 ──> 10.3 底半部 ──> 10.4 线程化中断
  （电平/边沿）  （路由/屏蔽）  （快速确认）   （延后处理）    （纳入调度）

主线二：时间从哪来

  硬件计数器 ──> 10.5 clocksource / clockevent / hrtimer ──> 10.6 tickless
                                                                 │
       两条主线在 tick device 交汇：定时器到期本身就是一种中断 <──┘

  10.7 综合实战：把两条主线放进同一个故障现场
```

每一节要深入的细节，都由主线上的**一个必须回答的问题**驱动：

| 小节 | 主线上要回答的问题 | 为什么必须深入这些细节 | 对应的典型故障/场景 |
|------|------------------|----------------------|-------------------|
| **10.1 GIC 与中断硬件** | 硬件信号怎么变成 Linux 中断号？ | GICv2/v3 的 SPI/PPI/SGI 分类、irq_domain 映射是设备树 interrupts 属性背后的机制；不掌握它，中断不触发和绑核不生效都无从排查 | 中断不触发、中断亲和性配置无效 |
| **10.2 顶半部** | 中断入口路径上发生了什么，为什么必须快？ | 顶半部在关本地中断的状态下运行，其执行时长直接决定系统实时性上限；irqsoff tracer 是量化它的标准工具 | 中断响应偶发延迟数百微秒 |
| **10.3 底半部** | 不能在中断里做的事交给谁？ | softirq、tasklet、workqueue 的上下文约束与延迟特性各不相同；选错机制是中断类 bug 和性能问题的主要来源 | softirq 过载、中断风暴、底半部延迟不可控 |
| **10.4 线程化中断** | 中断处理能不能像普通线程一样被调度？ | request_threaded_irq 让中断处理可睡眠、可设调度优先级，是实时系统压制中断干扰的标准手段，也是 PREEMPT_RT 的核心 | RT 任务被长时间的中断处理阻塞 |
| **10.5 时间子系统** | 微秒级定时从哪来？ | clocksource/clockevent 的分层与 hrtimer 的红黑树队列，决定定时精度能否突破 HZ 限制；用户态定时 API 的精度差异根源都在这里 | 定时精度只有毫秒级、hrtimer 回调间隔抖动 |
| **10.6 tickless** | CPU 没事做时为什么还被周期性打断？ | NO_HZ 消除空转 tick 是低功耗的前提，但与低延迟互斥；理解与 cpuidle 的协同才能为延迟敏感任务保留"热 CPU" | idle 唤醒导致定时延迟、CPU 统计失真 |
| **10.7 综合实战** | 两条主线在真实故障中如何配合？ | GPIO 延迟与音频爆音两类经典故障横跨中断与时间两条线，是本章排查方法论的完整演练 | 复杂延迟问题的端到端定位 |

> 💡 中断类问题先问自己"卡在哪一段"：硬件没到 GIC？顶半部太长？底半部排队？还是被 idle 唤醒拖住？每一段都有对应的观测工具，按段定位比通读代码快得多。

## 学习目标

建立"GIC → 顶半部 → 底半部/线程化"中断路径与"clocksource → clockevent → hrtimer → tickless"时间子系统的源码级认知，面对中断延迟或定时精度问题时，能按段定位并用 irqsoff tracer、ftrace 等工具量化根因。

## 与前后章的关联

- **第 7 章 启动链深度解析**：start_kernel 中 timekeeping_init() 初始化时间子系统，是 hrtimer 工作的基础
- **第 8 章 进程与调度**：定时器中断（tick）是触发调度决策的主要事件，scheduler_tick() 在每次 tick 时更新 vruntime
- **第 9 章 内存管理**：中断处理中的 kmalloc 必须使用 GFP_ATOMIC（不可睡眠分配）
- **第 11 章 设备模型**：驱动通过 request_irq() 注册中断处理函数，中断是驱动与硬件交互的核心机制
- **第 15 章 电源管理**：tickless 与 cpuidle 深度耦合——无 tick 允许 CPU 进入更深的 C-state
