## <span class="blue"> 从entry.S到handler的七步链路 [I→M]

### 一条irq触发后的完整旅程

中断从硬件信号到驱动 handler，中间经过 7 个明确的阶段，每个阶段的代码位于内核不同层次：

```mermaid
flowchart LR
    A["① entry.S<br/>保存现场"] --> B["② handle_arch_irq<br/>ARCH层入口"]
    B --> C["③ GIC驱动<br/>读取IAR获取中断号"]
    C --> D["④ generic_handle_domain_irq<br/>hwirq→virq"]
    D --> E["⑤ irq_desc.handle_irq<br/>中断流控"]
    E --> F["⑥ handle_irq_event<br/>遍历irqaction"]
    F --> G["⑦ 驱动handler<br/>执行具体处理"]

    style A fill:#e8f4fd
    style B fill:#e8f4fd
    style C fill:#fff3cd
    style D fill:#d4edda
    style E fill:#d4edda
    style F fill:#f8d7da
    style G fill:#f8d7da
```

### 第①站：entry.S —— 保存现场

中断信号到达 CPU 核心时，硬件自动完成几个动作：把 PSTATE 存入 `SPSR_EL1`、把返回地址存入 `ELR_EL1`、切换到 EL1 并按向量表跳到 IRQ 入口。<BR>
通用寄存器（x0-x30）还在原地，由汇编代码保存：

```asm
/* arch/arm64/kernel/entry.S（简化示意） */
el1h_64_irq:
    kernel_entry 1                /* 分配栈帧，x0-x30 与 SPSR/ELR 入栈 */
    mov     x0, sp
    bl      el1h_64_irq_handler   /* 进入 C 代码，现场已安全存放在栈上 */
    ...
```

这里最关键的概念是**中断现场**。CPU在这一步把"我正在执行什么"完整封存，确保处理完中断后能无缝恢复。<BR>
`S_FRAME_SIZE` 在 arm64 上是 272 字节，包含 31 个通用寄存器加几个系统寄存器。

> 💡 本链路以"内核态（EL1）被打断"为例。若中断到来时 CPU 正在用户态（EL0）执行，入口是 `el0t_64_irq`，现场保存在该进程的内核栈上；过了 `handle_arch_irq` 之后，C 代码路径完全一致。

### 第②站：handle_arch_irq —— ARCH层统一入口

C 侧的第一站在 `arch/arm64/kernel/entry-common.c:520`：

```c
/* arch/arm64/kernel/entry-common.c:520 */
asmlinkage void noinstr el1h_64_irq_handler(struct pt_regs *regs)
{
    el1_interrupt(regs, handle_arch_irq);
}
```

`handle_arch_irq` 是一个函数指针，在GIC驱动初始化时被赋值（`set_handle_irq(gic_handle_irq)`）。<br>
设计理念很清晰：不同SoC的中断控制器千差万别，但CPU核心进来后第一个调用的C函数必须是统一的，`handle_arch_irq` 就是这层抽象。

### 第③站：GIC驱动 —— 读取IAR，获取硬件中断号

以 GICv3 为例（`drivers/irqchip/irq-gic-v3.c:861`）：

```c
/* drivers/irqchip/irq-gic-v3.c:861（v6.6 真实链，有删减） */
static asmlinkage void __exception_irq_entry gic_handle_irq(struct pt_regs *regs)
{
    if (unlikely(gic_supports_nmi() && !interrupts_enabled(regs)))  /* 是否在中断已关时闯入的 pseudo-NMI？ */
        __gic_handle_irq_from_irqsoff(regs);   /* pseudo-NMI 路径：中断已关，走快速通道 */
    else
        __gic_handle_irq_from_irqson(regs);    /* 常规路径：中断开启状态下处理 */
}

/* :801 常规路径 → :764 分发 */
static void __gic_handle_irq_from_irqson(struct pt_regs *regs)
{
    irqnr = gic_read_iar();        /* 读 ICC_IAR1_EL1，认领中断 */
    ...
    __gic_handle_irq(irqnr, regs);
}

static void __gic_handle_irq(u32 irqnr, struct pt_regs *regs)
{
    if (gic_irqnr_is_special(irqnr))    /* 1020~1023：spurious，直接返回 */
        return;
    gic_complete_ack(irqnr);            /* supports_deactivate 时写 ICC_EOIR1_EL1 */
    if (generic_handle_domain_irq(gic_data.domain, irqnr))  /* → 第④站 */
        WARN_ONCE(true, "Unexpected interrupt (irqnr %u)\n", irqnr);
}
```

`gic_read_iar()` 读的是 GIC CPU Interface 的 `ICC_IAR1_EL1` 寄存器。<br>
这个读操作是"原子认领"——读一次，GIC就认为这个中断已被CPU接管，状态从Pending变为Active。<br>
这个设计避免了多个CPU核同时处理同一个中断。

### 第④站：generic_handle_domain_irq() —— hwirq翻译成virq

`generic_handle_domain_irq()`（`kernel/irq/irqdesc.c`）拿着 GIC 给的 hwirq，查 irq_domain 映射得到 virq，取出对应的 `irq_desc`，进入内核通用层。<br>
ARCH 和 irqchip 相关的代码到此结束，后面全是 irq core 的通用逻辑。

> 💡 `cat /proc/interrupts` 看到的计数在这条处理链上累加（`kstat_incr_irqs_this_cpu()`）。<br>
> 计数不涨，说明中断卡在硬件层或 GIC 配置，根本没进入这条链——先用 10.1.5 的方法核对设备树和 `/proc/interrupts`。

### 第⑤站：irq_desc.handle_irq —— 中断流控层

每个 `irq_desc` 都有一个 `handle_irq` 成员，它不是驱动注册的handler，而是**流控处理函数**（flow handler）。<br>
不同类型的中断用不同的流控：

```c
/* include/linux/irqdesc.h（字段节选） */
struct irq_desc {
    struct irq_data        irq_data;      /* irq号、芯片操作函数 */
    irq_flow_handler_t     handle_irq;    /* 流控函数: handle_level_irq / handle_edge_irq */
    struct irqaction       *action;       /* 驱动handler链表头 */
    unsigned int           istate;        /* 内部状态位 IRQS_*（详见下文） */
    /* ... */
};

/* kernel/irq/chip.c —— 电平触发: 屏蔽+应答+处理+解除屏蔽（v6.6 节选） */
void handle_level_irq(struct irq_desc *desc)
{
    raw_spin_lock(&desc->lock);
    mask_ack_irq(desc);          /* 1. 屏蔽并应答，防止电平持续触发 */
    if (!irq_may_run(desc))
        goto out_unlock;
    ...
    handle_irq_event(desc);      /* 2. 调用所有注册的驱动handler */

    cond_unmask_irq(desc);       /* 3. 解除屏蔽——但 IRQS_ONESHOT 时跳过 */
out_unlock:
    raw_spin_unlock(&desc->lock);
}

/* 边沿触发: 应答后直接处理，处理期间再来的边沿靠 PENDING 循环补 */
void handle_edge_irq(struct irq_desc *desc)
{
    raw_spin_lock(&desc->lock);

    desc->istate &= ~(IRQS_REPLAY | IRQS_WAITING);

    if (!irq_may_run(desc)) {              /* 正被其他 CPU 处理等 */
        desc->istate |= IRQS_PENDING;      /* 此时才记 PENDING */
        mask_ack_irq(desc);
        goto out_unlock;
    }
    if (irqd_irq_disabled(&desc->irq_data) || !desc->action) {
        desc->istate |= IRQS_PENDING;      /* 禁用或无 handler，也记 PENDING */
        mask_ack_irq(desc);
        goto out_unlock;
    }

    desc->irq_data.chip->irq_ack(&desc->irq_data);

    do {
        /* 处理期间又来了边沿（被记 PENDING），unmask 后重新处理 */
        if (unlikely(desc->istate & IRQS_PENDING)) {
            if (!irqd_irq_disabled(&desc->irq_data) &&
                irqd_irq_masked(&desc->irq_data))
                unmask_irq(desc);
        }
        handle_irq_event(desc);
    } while ((desc->istate & IRQS_PENDING) &&
             !irqd_irq_disabled(&desc->irq_data));

out_unlock:
    raw_spin_unlock(&desc->lock);
}
```

电平触发和边沿触发的处理差异就在这一层。<br>
电平触发必须**先 mask 再处理**，否则 handler 执行期间中断线一直有效，CPU 会反复进入中断。<br>
边沿触发没有"持续有效"的问题，但 `IRQS_PENDING` 不是"记一次补一次"的标记——处理完成后有个 do-while 循环，只要处理期间又来了新边沿就再走一遍 `handle_irq_event()`，直到没有 pending 为止。

### 中断的内部状态位：istate

上面代码里反复出现的 `IRQS_PENDING`、`IRQS_ONESHOT` 都是 `irq_desc.istate` 上的标志位——irq core 为每条中断线维护的**内部状态机**。<br>
v6.6 里它定义在 `kernel/irq/internals.h`，字段本名是 `core_internal_state__do_not_mess_with_it`，靠 `#define istate` 宏访问；这个名字本身就是警告：**irq core 之外的代码不许碰它**。

与本节直接相关的位：

| 状态位 | 置位时机 | 含义 |
|--------|----------|------|
| `IRQS_PENDING` | 中断来了但当下不能处理（被禁用、无 handler、别的 CPU 正在处理） | "欠着一次没办"。edge 流控的 do-while 靠它补处理期间到来的边沿；fasteoi 靠它决定是否 `check_irq_resend()` 重发 |
| `IRQS_ONESHOT` | `request_threaded_irq()` 带 `IRQF_ONESHOT` | 顶半部返回后保持 mask，等内核线程的 `thread_fn` 跑完才 unmask |
| `IRQS_REPLAY` / `IRQS_WAITING` | 软件重发机制记账 | 边沿中断可能丢失时的重发 bookkeeping，进流控时先清掉，驱动基本碰不到 |

另一个容易找错地方的位："**正在处理中**"不在 istate 里，而在 `irq_data` 的 `IRQD_IRQ_INPROGRESS` 位上（include/linux/irq.h:241）。<br>
流控开头的 `irq_may_run()` 查的就是它——发现这个中断正在其他 CPU 上处理，就记 `IRQS_PENDING` 走人，等正在处理的那轮结束后补做。

一句话模型：`istate`/`irqd` 就是这条中断线的状态机寄存器。<br>
流控函数每次进来，先读位决定"现在能不能跑 handler、要不要记账"，跑完再按位决定"要不要补一轮、要不要重发"。<br>
10.3 底半部的 pending 位图（`raise_softirq()` 置位、`__do_softirq()` 清零执行），是同一套"先标记、后补做"思想的延续。

`cond_unmask_irq()` 藏着一个线程化中断的关键细节：`request_threaded_irq()` 带了 `IRQF_ONESHOT` 时，顶半部 handler 返回 `IRQ_WAKE_THREAD` 后**不会立即解除屏蔽**——中断线保持 mask，等内核线程把 `thread_fn` 跑完才 unmask。发现 oneshot 中断"顶半部返回了线还关着"，不是 bug，就是这个设计。

### GICv3 上的主流流控：handle_fasteoi_irq

上面两个是教科书流控，但在 arm64 + GICv3 的真实系统里，绝大多数 SPI/LPI 中断走的既不是 `handle_level_irq` 也不是 `handle_edge_irq`，而是 `handle_fasteoi_irq`。<br>
GICv3 驱动在 `irq_domain_set_info()` 里直接把它绑给 SPI 和 LPI（`drivers/irqchip/irq-gic-v3.c:1538/1547`）：

```c
/* kernel/irq/chip.c:687 —— 透明控制器的流控（v6.6 节选） */
void handle_fasteoi_irq(struct irq_desc *desc)
{
    raw_spin_lock(&desc->lock);
    ...
    kstat_incr_irqs_this_cpu(desc);
    if (desc->istate & IRQS_ONESHOT)
        mask_irq(desc);                  /* oneshot 同样保持屏蔽 */

    handle_irq_event(desc);              /* 处理期间中断线不 mask */

    cond_unmask_eoi_irq(desc, chip);     /* 收尾写 EOIR（irq_eoi 回调） */

    if (unlikely(desc->istate & IRQS_PENDING))
        check_irq_resend(desc, false);   /* 亲和性切换竞争时重发 */
    raw_spin_unlock(&desc->lock);
    ...
}
```

三种流控的分工：

| 特性 | `handle_level_irq` | `handle_edge_irq` | `handle_fasteoi_irq` |
|------|-------------------|-------------------|---------------------|
| 进入时是否 mask | 先 `mask_ack` | 仅异常路径 mask | 不 mask |
| 处理期间中断线 | 被屏蔽 | 保持开启 | **保持开启**，靠 GIC 硬件优先级仲裁防止重入 |
| handler 返回后 | `cond_unmask_irq()` | do-while 补 pending 边沿 | 写 `ICC_EOIR1_EL1`（`irq_eoi` 回调） |
| 适用场景 | 传统电平中断控制器 | 传统边沿中断控制器 | GICv2/v3 等支持优先级仲裁的现代控制器 |

这个差异对理解中断延迟很关键：fasteoi 路径上 handler 执行期间中断线是开着的，更高优先级的中断可以抢占——读 GICv3 系统的延迟数据时，不能套用"电平中断处理期间线被屏蔽"的模型。

> 💡 PPI（如定时器中断）在 GICv3 上用的是 `handle_percpu_devid_irq`（irq-gic-v3.c:1533）——每核独立、不遍历共享链表、不做 fasteoi 的 resend 检查，路径更短。

电平触发中断还有一个经典陷阱：handler 没清设备侧的中断源就返回，unmask 后中断线仍有效，立刻再次进入，形成中断风暴。案例与排查见 10.1.5。

### 第⑥站：handle_irq_event() —— 遍历irqaction链表

```c
/* kernel/irq/handle.c（节选） */
irqreturn_t handle_irq_event(struct irq_desc *desc)
{
    struct irqaction *action;
    irqreturn_t retval = IRQ_NONE;

    /* 遍历该irq上的所有action（共享中断会有多个） */
    for (action = desc->action; action; action = action->next) {
        irqreturn_t res;

        res = action->handler(action->irq, action->dev_id);  /* 第⑦站 */

        if (res == IRQ_HANDLED)
            retval = IRQ_HANDLED;
    }
    return retval;
}
```

注意这个 for 循环**没有 break**：即使某个 handler 已经返回 `IRQ_HANDLED`，后续 handler 仍会被逐个调用——共享线上的每个驱动都会被轮到。<br>
慢 handler 拖住的是整条线，这一点在本节末尾的"阻塞风险"里展开。

### 第⑦站：驱动handler —— 你的代码在这里跑

这就是你用 `request_irq()` 或 `request_threaded_irq()` 注册的那个函数。<br>
它执行完返回 `IRQ_HANDLED` 或 `IRQ_NONE`。返回路径是来路的镜像：`handle_irq_event()` 返回 → 流控函数收尾（unmask 或写 EOIR）→ `generic_handle_domain_irq()` 返回 → `gic_handle_irq()` 返回 → entry.S 的 `kernel_exit` 恢复现场 → `eret` 回到被打断的上下文继续执行。

| 层级 | 核心函数/结构 | 所在文件 | 职责 |
|------|--------------|---------|------|
| 汇编入口 | `el1h_64_irq` → `kernel_entry` | `arch/arm64/kernel/entry.S` | 保存寄存器现场 |
| ARCH层 | `el1h_64_irq_handler` → `handle_arch_irq` | `arch/arm64/kernel/entry-common.c` | 架构统一入口 |
| IRQChip | `gic_handle_irq()` | `drivers/irqchip/irq-gic-v3.c` | 读取IAR，认领中断 |
| IRQ Core | `generic_handle_domain_irq()` | `kernel/irq/irqdesc.c` | hwirq→virq，找 irq_desc |
| 流控层 | `handle_fasteoi_irq()`（GICv3 主流）/ `handle_level_irq()` / `handle_edge_irq()` | `kernel/irq/chip.c` | 屏蔽/应答/EOI/调用handlers |
| 事件层 | `handle_irq_event()` | `kernel/irq/handle.c` | 遍历irqaction链表 |
| 驱动层 | `my_irq_handler()` | 各驱动文件 | 实际的设备处理逻辑 |

## <span class="blue"> 共享中断与handler的"认领"机制 [I]

### 一条中断线，多个设备

前面我们看到 `irqaction` 是个链表。为什么要链表？因为多个设备可能共享同一个中断号（尤其是IRQ资源紧张的SoC）。

```c
/* include/linux/interrupt.h（字段节选） */
struct irqaction {
    irq_handler_t       handler;     /* 顶半部handler函数 */
    void                *dev_id;     /* 设备的唯一标识，free_irq要用 */
    void                __percpu    *percpu_dev_id;
    struct irqaction    *next;       /* 链表指针，指向下一个共享irq的action */
    irq_handler_t       thread_fn;   /* 如果注册了线程化中断 */
    struct task_struct  *thread;     /* 对应的内核线程 */
    unsigned int        irq;         /* 中断号 */
    unsigned int        flags;       /* IRQF_SHARED / IRQF_TRIGGER_* */
    unsigned long       thread_flags;
    const char          *name;       /* /proc/interrupts中显示的名字 */
} ____cacheline_internodealigned_in_smp;
```

当多个驱动都传了 `IRQF_SHARED` 标志注册同一个irq时，内核会把它们的 `irqaction` 串成链表：

```c
/* 驱动A注册 */
request_irq(irq_num, handler_a, IRQF_SHARED, "dev_a", (void *)dev_a_ptr);

/* 驱动B注册 */
request_irq(irq_num, handler_b, IRQF_SHARED, "dev_b", (void *)dev_b_ptr);

/* 内核中的irqaction链表结构：
 *
 *  irq_desc[irq_num].action
 *       │
 *       ▼
 *   ┌──────────┐     ┌──────────┐
 *   │ handler_a│────▶│ handler_b│────▶ NULL
 *   │ dev_id=a │next │ dev_id=b │next
 *   └──────────┘     └──────────┘
 */
```

### handler怎么知道"是不是我的中断"

关键在返回值。每个handler都要检查自己的设备状态寄存器，确认这次中断是否由自己触发：

```c
/* 共享中断handler的标准写法 */
static irqreturn_t my_shared_handler(int irq, void *dev_id)
{
    struct my_device *dev = dev_id;

    /* 第一步：读设备的中断状态寄存器 */
    u32 status = readl(dev->regs + IRQ_STATUS_REG);

    /* 第二步：检查是否有挂起的中断位 */
    if (!(status & MY_IRQ_PENDING))
        return IRQ_NONE;          /* 不是我的中断 */

    /* 第三步：清中断标志（必须在顶半部完成！） */
    writel(status, dev->regs + IRQ_CLEAR_REG);

    /* 第四步：做该做的处理 */
    /* ... */

    return IRQ_HANDLED;           /* 是我处理的 */
}
```

| 返回值 | 含义 | 内核行为 | 共享中断场景 |
|--------|------|----------|-------------|
| `IRQ_HANDLED` | 该handler处理了此中断 | 计数+1，正常返回 | 链表中可以有多个HANDLED |
| `IRQ_NONE` | 不是我的中断 | 内核记录一次"unhandled" | 如果全部handler都返回NONE，触发警告 |

> ⚠️ 共享中断中，如果链表中所有 handler 都返回 `IRQ_NONE`，内核会判定为**虚假中断（spurious interrupt）**，<br>
> 打印 `irq X: nobody cared` 警告（`kernel/irq/spurious.c`），达到阈值后甚至关闭该 irq 线。<br>
> 这在调试时非常隐蔽——明明设备在发中断，怎么突然就收不到了？
<!-- -->
> 💡 调用 `free_irq(irq, dev_id)` 时，`dev_id` 必须和 `request_irq()` 时传入的完全一致。<br>
> 内核用这个指针在irqaction链表中匹配要卸载的节点。传错了会卸载错handler，或者返回 `-EINVAL`。

### 共享线上的阻塞风险

共享中断有个隐性风险：假设设备A的handler执行时间很长，而设备B也在同一个irq上频繁触发<br>
——设备B的中断会被设备A的handler拖延处理。

```
时间线：
├─ 设备A触发 ──[handler_a执行10ms]─────────────────────────────┤
├─ 设备B触发 ──[等待]──[等待]──[等待]──[handler_b终于执行]──────┤
```

极端情况下，如果某个handler死循环或耗时过长，整个中断线会被"卡死"。<br>
解法是**中断线程化**：用 `request_threaded_irq()` 把handler放到内核线程里跑，顶半部只做快速ack，真正的处理在进程上下文执行（10.4 展开）。

这样即使处理慢，也不会阻塞其他共享设备的中断响应。中断风暴的检测方法（`watch` 采样 `/proc/interrupts`）见 10.1.5。

## <span class="blue"> 本节总结

| 要点 | 核心结论 |
|------|----------|
| 7步链路 | entry.S → el1h_64_irq_handler → gic_handle_irq → generic_handle_domain_irq → irq_desc.handle_irq → handle_irq_event → 驱动handler |
| irq_desc的作用 | 每个virq对应一个irq_desc，是中断管理的中枢节点，包含irq_data、action链表、流控函数 |
| 流控函数差异 | GICv3 主流是 handle_fasteoi_irq（不 mask、EOI 收尾、可被高优先级抢占）；电平触发(handle_level_irq)必须先mask/ack再处理、oneshot 时 unmask 推迟到线程跑完；边沿触发(handle_edge_irq)直接处理，do-while 循环补记期间的边沿 |
| 共享中断机制 | 多个驱动的irqaction通过next指针串成链表，中断来时逐个调用 |
| handler返回值 | IRQ_HANDLED表示"我处理了"，IRQ_NONE表示"不是我的"；全NONE会触发虚假中断警告 |
| dev_id的重要性 | request_irq/free_irq配对使用dev_id来定位链表节点，必须保持一致 |
| 共享线风险 | 一个handler耗时过长会拖住整条中断线，可用 irq 线程化解决 |
