# 第7章：启动链深度解析

> 所属：第 二 部 核心机制深度解析
>
> BIEM：[I→E] | 核心问题：从 BootROM 到 Shell，每一行日志背后发生了什么？

## 核心问题

从 BootROM 到 Shell，每一行日志背后发生了什么？

## 为什么需要这一章

有经验的工程师能移植 U-Boot、能编译内核、能让系统跑起来——但面对启动日志中某一行的失败，常常束手无策。原因在于：对启动链的每个阶段只有"大概在这时候初始化"的模糊认知，缺乏精确的源码级对应关系。

本章要建立的是**"启动日志 ↔ 源码路径 ↔ 子系统初始化"的三重映射**。看到 `Waiting for root device` 卡住时，能立刻定位到是块设备子系统还没初始化完；看到 `VFS: Cannot open root device` 时，能判断出是设备名错误还是驱动未加载。启动链是整个系统初始化的缩影，理解了启动链，就理解了内核初始化的全局图景。

## 本章主线：一场接力赛，四个交接点

启动链的本质是**一场接力赛**：每个阶段只做一件事——把下一个阶段加载进来、把控制权交出去。本章的六节不是并列的知识点，而是沿着同一条时间线依次展开的五个接力棒加一次终点冲刺：

```
上电
 │
 ▼
7.1 BootROM ──交接①──> 7.2 SPL ──交接②──> 7.3 U-Boot ──交接③──> 7.5 内核 ──交接④──> 7.6 init
 固化在芯片里        初始化DDR         完整的loader        建立内核世界      进入用户空间
                        │
                        └── 7.4 设备树：U-Boot 与内核之间唯一的"交接信件"
```

每一节要深入的细节，都由这个交接点上的**一个必须回答的问题**驱动：

| 小节 | 交接点上的问题 | 为什么必须深入这些细节 | 对应的典型故障 |
|------|--------------|----------------------|--------------|
| **7.1 BootROM** | 上电后 PC 指向哪里？第一段代码存在哪、怎么找到 SPL？ | BootROM 不可改、不可调试，只有搞清它的加载协议（IVT、IDBlock），才知道启动介质该怎么烧、烧到哪 | 上电无任何输出、进不了下载模式 |
| **7.2 SPL** | SRAM 只有几十 KB，装不下 U-Boot，怎么办？ | SPL 的全部设计（双区域内存布局、不能用 malloc、board_init_f/r 分阶段）都是"内存不够"这一个约束推出来的 | SPL 打印后 hang 住、DDR 初始化失败 |
| **7.3 U-Boot** | 完整的 loader 如何初始化自己和外设？ | 重定位是 U-Boot 最反直觉的设计：把自己搬到 DDR 顶部。不理解它，就读不懂 gd、环境变量、DM 框架为什么分两个阶段 | `Starting kernel` 前的各类崩溃 |
| **7.4 设备树交接** | 硬件信息怎么从 bootloader 传到内核？ | memory 节点、bootargs 是 U-Boot 现场修改的。不理解 dtb 的传递与解析，设备树问题就只能靠猜 | 内存大小识别错误、启动参数不生效 |
| **7.5 内核启动** | 内核如何从汇编入口建立起整个 C 世界？ | start_kernel 的初始化顺序是严格的依赖链：mm 必须在 sched 前、VFS 缓存必须在 initcalls 前。理解了顺序依赖，任意一行日志都能对应到源码位置 | `Starting kernel` 后黑屏、initcall 阶段 panic |
| **7.6 init** | 控制权如何最终交给用户空间？ | 根文件系统挂载（initramfs 与真实 rootfs 的切换）是"内核态收尾"与"用户态开始"的边界，启动问题的一半发生在这里 | `Waiting for root device`、init 进程崩溃、服务启动超时 |

> 💡 读每一节之前，先回到这张表确认"这一节在接力赛的哪一棒"。细节是为主问题服务的，脱离了交接点的细节不需要死记。

## 排错索引：从症状反查小节

本章的排错价值可以直接按症状反查：

```
无任何输出 / 黑屏          → 7.1（BootROM）或 7.2（SPL），先查供电、时钟、串口
SPL 打印后 hang 住         → 7.2，查 DDR 初始化与存储介质
Starting kernel 后卡住     → 7.5.1（head.S/MMU），启用 earlycon/CONFIG_DEBUG_LL
initcall 阶段 panic        → 7.5.3，按日志中最后一个 initcall 定位
Waiting for root device    → 7.6.2，查设备名、驱动、设备树
VFS: Cannot open root      → 7.6.2，区分设备名错误与驱动未加载
No working init found      → 7.6.1，查根文件系统完整性与动态链接库
服务启动超时               → 7.6.3，查 systemd 依赖与配置
```

## 学习目标

建立 BootROM→SPL→U-Boot→Kernel→init 完整链路的源码级认知，能将启动日志中的任意一行对应到具体的源码位置与初始化阶段。
