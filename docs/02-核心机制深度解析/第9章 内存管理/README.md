# 第9章：内存管理

> 所属：第 二 部 核心机制深度解析

## 核心问题

内核如何管理物理与虚拟内存？

## 为什么需要这一章

有经验工程师知道 free 看内存、vmstat 看换页、知道 OOM killer 会杀进程。但面对"系统运行 3 天后越来越慢""kmalloc 返回 NULL 但 free 显示还有内存""dma_alloc_coherent 偶尔失败"这些实际问题时，缺乏对内存分配器内部机制的理解就会束手无策。

本章要解决的核心矛盾是：**空闲内存 ≠ 可分配内存**。Buddy 分配器的外碎片、SLUB 的缓存组织、CMA 的预留策略——这些机制共同决定了"还有多少内存能用"这个问题的答案远比 free 命令复杂。理解这些机制，是设计内存充足、不会出现诡异分配失败的嵌入式系统的关键。

## 本章主线：一次内存申请的完整旅程

本章的六节沿着同一条主线展开：**任意一次内存申请，最终都要落到 Buddy 系统的物理页上；申请方不同，中间经过的机制层不同；内存不够时，依次由 zswap 和 OOM killer 兜底**：

```
  用户态 malloc            内核态 kmalloc            DMA 连续大块
       │                        │                        │
       ▼                        ▼                        ▼
   9.1 虚拟内存与页表       9.3 SLUB 分配器           9.4 CMA
  （虚拟地址怎么映射       （小对象怎么从物理页       （连续物理内存
    到物理页）               里切出来）                 从哪预留）
       │                        │                        │
       └──────────────┬─────────┴────────────────────────┘
                      ▼
              9.2 Buddy：所有物理页的唯一源头
                      │
        内存紧张时 ──> 9.5 zswap：压缩换时间
                      │
        还不够时   ──> 9.6 OOM killer：杀进程保命
```

每一节要深入的细节，都由旅程上的**一个必须回答的问题**驱动：

| 小节 | 主线上要回答的问题 | 为什么必须深入这些细节 | 对应的典型故障/场景 |
|------|------------------|----------------------|-------------------|
| **9.1 虚拟内存与页表** | 一个虚拟地址怎么变成物理地址？ | ARM64 四级页表、TLB 与缺页中断是所有内存机制的地基；不理解它，/proc/\<pid\>/maps 的每一列和缺页日志都读不懂 | 缺页异常定位、地址空间布局疑问 |
| **9.2 Buddy 与碎片** | 物理页从哪来，为什么"有空闲却分不出"？ | 外碎片是 Buddy 的固有难题；/proc/buddyinfo 是判断"还有没有连续大块"的唯一窗口，compaction 的代价决定要不要开 | free 显示有内存但高阶分配失败 |
| **9.3 SLUB 与 kmalloc** | 内核的小对象怎么从物理页里切出来？ | kmem_cache 的三级分配路径（per-cpu → partial slab → Buddy）决定 kmalloc 性能；slabinfo 是内核内存泄漏排查的第一利器 | kmalloc 返回 NULL、SLUB 缓存持续增长 |
| **9.4 CMA** | DMA 要的连续大块从哪预留？ | ISP、编解码器等子系统必须有大块连续物理内存；CMA 的页面迁移机制与失败原因直接决定相机类子系统能否长期稳定运行 | dma_alloc_coherent 偶发失败 |
| **9.5 zswap** | 内存不够时能不能先压缩而不是换出？ | zswap 在 swap 前插入压缩缓存层，是小内存设备延缓 OOM 的低成本手段；收益与 CPU 代价的权衡需要量化判断 | 小内存设备频繁触发 OOM |
| **9.6 OOM killer** | 内存耗尽时谁被杀、怎么保护关键进程？ | badness 评分的逻辑是"杀最少的进程释放最多的内存"，而不是"杀最不重要的"；oom_score_adj 是保护关键进程的唯一手段 | 关键进程被 OOM 误杀、OOM 日志读不懂 |

> 💡 读每一节之前，先回到这张表确认"这次申请走到了旅程的哪一段"。所有分配失败问题的排查，本质上都是沿着这张图反推：先确认申请方类型，再检查对应机制层的状态。

## 排错索引：从症状反查小节

```
free 显示有内存却分配失败    → 9.2，cat /proc/buddyinfo 查高阶连续块（外碎片）
dma_alloc_coherent 返回 NULL → 9.4，查 CMA 区域大小与区域内不可迁移页占用
kmalloc 失败但 MemFree 充足  → 9.3，cat /proc/slabinfo 查缓存占用与泄漏
某个 cache 持续增长          → 9.3.3，启用 CONFIG_SLUB_DEBUG 定位泄漏点
系统运行几天后越来越慢        → 9.2.3，碎片化评估；9.5，确认 zswap 是否生效
小内存设备频繁 OOM           → 9.5，启用 zswap 压缩换时间；9.6.3，预防策略
关键进程被 OOM 杀掉          → 9.6.2，调整 oom_score_adj 或用 cgroup 保护
缺页异常定位                 → 9.1.4，区分正常缺页（按需分配）与非法访问
进程级内存占用分析           → 9.1，/proc/<pid>/smaps 与 pmap 的逐段解读
```

## 学习目标

建立"虚拟地址 → 页表 → Buddy → SLUB/CMA → zswap → OOM"完整链路的机制认知，面对任何分配失败或 OOM 问题时，能用 buddyinfo、slabinfo、/proc 接口定位到具体机制层并给出修复方案。

## 与前后章的关联

- **第 7 章 启动链深度解析**：start_kernel 中 mm_init() 建立页表与 Buddy 系统，是本章所有分配的运行时基础

- **第 10 章 中断与时间**：缺页中断（page fault）是由 MMU 触发的异常；中断上下文的 kmalloc 必须使用 GFP_ATOMIC
- **第 12 章 文件系统与存储**：页缓存（page cache）建立在 struct page 与 address_space 之上
- **第 13 章 并发与同步**：Buddy 与 SLUB 内部的并发访问依赖 spinlock 保护，是分析分配器性能的基础
