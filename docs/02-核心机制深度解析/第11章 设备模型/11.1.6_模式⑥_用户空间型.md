# 11.1.6 模式⑥ 用户空间型：不写内核驱动读 LM75

> 所属章节：第11章 设备模型 > 11.1 其然台阶·六种写法
>
> 难度：[I] | 预计阅读时间：30分钟（含上板实操） | 验证分级：A级（上板可验证）

## <span class="blue"> 本节导读

本节覆盖：

- 六种写法中的第六种：**用户空间型**——一个内核模块都不写，通过 `/dev/i2c-1` 字符设备直接收发 I2C 数据
- 一份 50 行的用户空间 C 程序，`gcc` 编译后直接打印温度
- 这种写法的适用边界：什么时候它是正确答案，什么时候它会反噬

## <span class="blue"> 场景一句话 [B]

原型验证、产线测试、非性能敏感的慢速传感器——功能逻辑简单到"每 5 秒读两个字节"，为它写内核驱动是杀鸡用牛刀，一个用户态程序就够了。

## <span class="blue"> 前提：i2c-dev 接口 [B]

内核的 `i2c-dev` 模块把每条 I2C 总线暴露为一个字符设备 `/dev/i2c-N`（N 是总线号）。打开它、用 `ioctl` 声明从机地址、然后直接 `read`/`write`——内核 I2C 核心替你完成总线时序，你的程序和普通读写文件没有区别。

确认前提条件：

```bash
ls /dev/i2c-*
```

没有的话检查内核配置：`zcat /proc/config.gz | grep I2C_CHARDEV`，需要 `CONFIG_I2C_CHARDEV=y/m`。

## <span class="blue"> 用户空间程序 temp_userspace.c [I]

```c
// SPDX-License-Identifier: GPL-2.0
/*
 * temp_userspace.c - 用户空间直接读 LM75，不涉及任何内核模块
 * 编译：aarch64-linux-gnu-gcc temp_userspace.c -o temp_userspace
 * （也可以在开发板上直接 gcc 编译）
 */
#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>
#include <stdint.h>
#include <sys/ioctl.h>
#include <linux/i2c-dev.h>    /* I2C_SLAVE 等 ioctl 定义 */
#include <linux/i2c.h>

#define I2C_BUS		"/dev/i2c-1"
#define LM75_ADDR	0x48
#define LM75_REG_TEMP	0x00

int main(void)
{
	int fd;
	uint8_t buf[2];
	int16_t raw;
	int millic;

	fd = open(I2C_BUS, O_RDWR);
	if (fd < 0) {
		perror("open");
		return 1;
	}

	/* 声明接下来通信的从机地址 */
	if (ioctl(fd, I2C_SLAVE, LM75_ADDR) < 0) {
		perror("ioctl I2C_SLAVE");
		close(fd);
		return 1;
	}

	/* 先写寄存器地址，再连读 2 字节（LM75 的读时序） */
	buf[0] = LM75_REG_TEMP;
	if (write(fd, buf, 1) != 1 || read(fd, buf, 2) != 2) {
		perror("i2c transfer");
		close(fd);
		return 1;
	}

	raw = (int16_t)((buf[0] << 8) | buf[1]);
	millic = (raw >> 7) * 500;

	printf("Temperature: %d.%d C\n", millic / 1000, (millic % 1000) / 100);
	close(fd);
	return 0;
}
```

## <span class="blue"> 编译、运行、验证 [B]

在 PC 上交叉编译，或在开发板上直接编译：

```bash
aarch64-linux-gnu-gcc temp_userspace.c -o temp_userspace
```

开发板上运行（同样先确认 0x48 没有被内核驱动占用，`i2cdetect` 显示 `48` 而不是 `UU`）：

```bash
./temp_userspace
```

预期输出：

```
Temperature: 26.5 C
```

> ⚠️ 如果 `0x48` 已被内核驱动绑定（`i2cdetect` 显示 `UU`），`ioctl I2C_SLAVE` 会返回 `EBUSY`。两个选择：先 `unbind` 内核驱动（见 11.1.2 实验二），或改用 `I2C_SLAVE_FORCE` 强制占用——后者绕过内核的保护，可能和正在运行的驱动打架，仅限调试。

## <span class="blue"> 边界：什么时候这是正确答案 [I]

**适合**：读数频率低（秒级以上）、无中断需求、逻辑单一的传感器；原型阶段一天要改十遍代码的场景；不想维护内核构建环境的产线工具。

**不适合，且原因明确**：

- **有中断**：用户空间拿不到 GPIO 中断的实时通知（`gpio_poll` 轮询的延迟是毫秒级）
- **多进程共享**：两个程序同时打开 `/dev/i2c-1` 读不同芯片没问题，但读写时序交叉时没有内核帮你做事务隔离
- **要进系统框架**：hwmon/thermal/输入子系统的数据消费方（如温控风扇策略）只认内核接口，用户空间数据进不去

经验法则：数据要不要被内核里的其他模块消费？要，就必须写成内核驱动（模式①②）；不要，用户空间方案往往是最便宜的正确答案。

## <span class="blue"> 引出的问题

模式⑥能成立，是因为内核把 I2C 总线"借"给了用户空间——`/dev/i2c-1` 这个字符设备本身就是 i2c-dev 这个内核驱动创建的。所以**即使你一行内核代码不写，你仍然站在设备模型的肩膀上**：总线、设备、驱动、`/dev` 节点，一环不少。

到这里六种写法全部看完。它们形态差异巨大：有的走设备树、有的硬编码；有的注册到内核总线、有的挂进厂商框架、有的干脆不进内核。但内核不可能为每种写法单独发明一套管理逻辑——**这背后一定有一个统一的抽象层**。下一节先用一张表把六种写法放在一起看，然后 11.2 进入这个抽象层本身：总线-设备-驱动三元模型。

## 本节总结

| 要件 | 要点 |
|------|------|
| 写法定位 | 原型验证、低频慢速传感器、产线工具 |
| 内核依赖 | 仅 `i2c-dev` 字符设备，零内核模块开发 |
| 硬边界 | 无中断、无框架集成、事务隔离靠自己 |
| 本质 | 仍是站在 i2c-dev 驱动创建的 `/dev` 节点上工作 |
