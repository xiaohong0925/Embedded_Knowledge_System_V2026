# 11.1.3 模式③ 厂商框架型：SDK 抽象层下的驱动

> 所属章节：第11章 设备模型 > 11.1 其然台阶·六种写法
>
> 难度：[I] | 预计阅读时间：30分钟 | 验证分级：**B级（可编译 + 设计剖析，不要求上板验证）**

> 💡 本节的验证分级是 B 级：骨架代码可 `make` 通过、可 `insmod` 观察日志，但不追求读到真实温度。原因很直接——厂商 SDK 是闭源或半闭源的，本节用**模拟海思/瑞芯微风格的自建框架**演示这种写法的结构，模拟部分在代码中有明确标注。真实的厂商框架剖析见本节后半。

## <span class="blue"> 本节导读

本节覆盖：

- 六种写法中的第三种：**厂商框架型**——使用海思/瑞芯微/全志 BSP 快速出产品时，你面对的不是内核原生框架，而是厂商 SDK 的抽象层
- 一份可编译的"模拟 SDK 风格"骨架代码，展示这种写法的三个结构特征：配置结构体、回调注册、框架反向调用
- 真实厂商框架的共性剖析，以及这种写法的工程取舍

## <span class="blue"> 场景一句话 [B]

项目周期紧、芯片厂商提供了成熟 SDK（摄像头 ISP、NPU、视频编解码 pipeline），你的驱动不直接注册到内核子系统，而是作为"插件"挂进厂商框架——快速出产品时的现实选择。

## <span class="blue"> 这种写法的三个结构特征 [I]

对照模式①②回忆一下：你写一个 `platform_driver` 或 `i2c_driver`，注册到内核总线，内核在匹配时调用你的 `probe()`。厂商框架型写法把这个关系换了一层皮：

1. **配置结构体代替设备树属性**：硬件参数填进厂商定义的结构体，而不是 `.dts` 属性
2. **回调表代替框架注册**：你把一组函数指针（init/read/deinit）打包成 ops 表，交给厂商框架
3. **框架反向调用**：厂商框架在自己的线程/中断上下文里调你的回调，调用时机由厂商代码决定，文档之外不可见

代码形式变了，本质没变——依然是"驱动提供回调，框架负责调度"。只是"框架"从内核总线换成了厂商 SDK。

## <span class="blue"> 可编译骨架：模拟 SDK 风格 [I]

下面的模块**自包含**：前半部分模拟厂商框架（真实 SDK 中这些函数由厂商闭源库提供），后半部分是你要写的驱动代码。它能真实编译、`insmod`，并在 `dmesg` 里演示"框架注册 → 框架轮询 → 回调驱动"的完整链条。

```c
// SPDX-License-Identifier: GPL-2.0
/*
 * sdkstyle_temp.c - 厂商 SDK 框架型写法骨架（模拟风格）
 * 前半部分为模拟的厂商框架，真实 SDK 中由厂商库提供
 */
#include <linux/module.h>
#include <linux/workqueue.h>
#include <linux/delay.h>

/* ============ 模拟厂商框架（真实 SDK 中由厂商提供） ============ */

/* 厂商风格的配置结构体：硬件参数集中填写 */
struct vendor_sensor_cfg {
	int id;			/* 传感器编号 */
	int sample_ms;		/* 采样周期 */
};

/* 厂商风格的回调表：驱动实现，框架调用 */
struct vendor_sensor_ops {
	int (*init)(int id);
	int (*read_millic)(int id, int *val);
	void (*deinit)(int id);
};

static struct vendor_sensor_ops const *g_ops;   /* 框架保存驱动注册的回调表 */
static struct delayed_work g_poll_work;

static void vendor_poll(struct work_struct *work)
{
	int val;

	if (g_ops && g_ops->read_millic && !g_ops->read_millic(0, &val))
		pr_info("vendor framework: polled temperature %d\n", val);

	schedule_delayed_work(&g_poll_work, msecs_to_jiffies(2000));
}

/* 模拟厂商 API：注册/注销传感器驱动 */
static int vendor_sensor_register(const struct vendor_sensor_cfg *cfg,
				  const struct vendor_sensor_ops *ops)
{
	if (!ops || !ops->init || ops->init(cfg->id))
		return -EINVAL;
	g_ops = ops;
	INIT_DELAYED_WORK(&g_poll_work, vendor_poll);
	schedule_delayed_work(&g_poll_work, msecs_to_jiffies(cfg->sample_ms));
	pr_info("vendor framework: sensor %d registered\n", cfg->id);
	return 0;
}

static void vendor_sensor_unregister(int id)
{
	cancel_delayed_work_sync(&g_poll_work);
	if (g_ops && g_ops->deinit)
		g_ops->deinit(id);
	g_ops = NULL;
	pr_info("vendor framework: sensor %d unregistered\n", id);
}

/* ============ 以上是模拟框架；以下才是"你写的驱动" ============ */

static int mytemp_init(int id)
{
	pr_info("mytemp: init sensor %d\n", id);
	return 0;
}

static int mytemp_read_millic(int id, int *val)
{
	*val = 25500;	/* 真实代码在这里访问硬件，示例返回固定值 25.5°C */
	return 0;
}

static void mytemp_deinit(int id)
{
	pr_info("mytemp: deinit sensor %d\n", id);
}

static const struct vendor_sensor_cfg mytemp_cfg = {
	.id = 0,
	.sample_ms = 2000,
};

static const struct vendor_sensor_ops mytemp_ops = {
	.init        = mytemp_init,
	.read_millic = mytemp_read_millic,
	.deinit      = mytemp_deinit,
};

static int __init mytemp_module_init(void)
{
	return vendor_sensor_register(&mytemp_cfg, &mytemp_ops);
}

static void __exit mytemp_module_exit(void)
{
	vendor_sensor_unregister(mytemp_cfg.id);
}

module_init(mytemp_module_init);
module_exit(mytemp_module_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Vendor SDK style driver skeleton (simulated)");
```

```bash

```

## <span class="blue"> 真实厂商框架剖析 [I]

剥掉具体 API 的名字，主流厂商 SDK 的结构高度相似：

| 厂商 | 框架 | 你面对的形式 |
|------|------|-------------|
| 海思 | MPP（媒体处理平台） | `HI_MPI_*` 系列函数，传感器作为 pipeline 的一环注册 |
| 瑞芯微 | RKISP/RKMPP/RKNN | 摄像头/NPU 驱动按厂商 dts 节点和 ioctl 协议接入 |
| 全志 | Tina Linux 框架 | 驱动 + 板级配置文件（sys_config 风格的键值配置） |

三个共性值得记住：

- **驱动逻辑被拆成两半**：内核侧一个厂商已写好的"代理驱动"，用户空间一套闭源库，你的代码和两边都打交道
- **配置入口不统一**：设备树、厂商配置文件、ioctl 参数三种渠道并存，同一块板子的启动参数可能分散在三处
- **版本强绑定**：SDK 通常钉死某个内核 LTS 版本，升级内核等于重做 BSP 适配

## <span class="blue"> 工程取舍 [I]

这种写法能一周点亮摄像头，代价在三年后兑现：内核安全补丁合不进厂商内核、框架日志看不懂只能提工单、换芯片时驱动经验清零。模式①②的代码资产属于内核主线，模式③的代码资产属于某一颗芯片的某一个 SDK 版本。

> 💡 产品选型阶段就要回答一个问题：这颗芯片的 SDK 维护到什么时候？答案写不进驱动代码，但决定了驱动代码的寿命。

## <span class="blue"> 引出的问题

厂商框架自己也是建立在内核之上的——海思的代理驱动最终还是要注册成 platform 或 I2C 设备。**厂商只是在标准机制上又包了一层。** 那内核的原生机制到底是什么样子，能让所有厂商都在上面盖房子？这个问题指向 11.2。下一节先看另一种极端：什么框架都不用的 Legacy 裸驱动。
