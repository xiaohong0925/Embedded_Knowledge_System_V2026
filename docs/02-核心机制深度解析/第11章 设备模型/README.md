# 第11章：设备模型

> 所属：第 二 部 核心机制深度解析
>
> BIEM：[I→E] | 核心问题：内核如何抽象和匹配设备？

## 核心问题

内核如何抽象和匹配设备？

## 为什么需要这一章

有经验工程师会写 platform_driver，知道设备树 compatible 字符串要与驱动 of_match_table 匹配。但当面对"insmod 后 probe 没有执行""两个驱动竞争同一个设备""设备树节点存在但 /sys 中没有对应设备""设备树 overlay 加载后驱动不自动 probe"这些实际问题时，需要对设备模型的源码级理解。

本章的核心认知是：**设备模型不是"驱动的容器"，而是一个完整的匹配和生命周期管理系统**。理解总线-设备-驱动三角关系、probe 的执行条件、uevent 的通知机制，是设计健壮驱动架构的基础。

## 本章主线：一个设备从设备树节点到 probe 成功的完整旅程

本章的五节围绕同一条主线展开：**一个设备从 .dts 中的一个节点出发，经历创建设备对象、与驱动匹配、执行 probe、通知用户空间的完整旅程**：

```
 设备树节点 ──> 11.2 生成 platform_device ──> 11.3 匹配 ──> probe()
  (.dts)         （of_platform_populate）      （compatible）  （资源获取
      │                                        ▲               与硬件初始化）
      │                                        │
      │                              11.1 总线-设备-驱动：
      │                              匹配发生的框架与规则
      │
      └── 运行时修改：11.5 overlay（不重启增删设备）

 probe 成功之后：11.4 sysfs / uevent 把设备状态通知用户空间，udev 创建 /dev 节点
```

每一节要深入的细节，都由旅程上的**一个必须回答的问题**驱动：

| 小节 | 主线上要回答的问题 | 为什么必须深入这些细节 | 对应的典型故障/场景 |
|------|------------------|----------------------|-------------------|
| **11.1 总线-设备-驱动** | 匹配这件事在哪个框架里发生？ | bus_type / device / device_driver 三角关系与 kobject 层次是设备模型的骨架；不理解它，probe 未执行时连排查入口都找不到 | 设备模型概念混乱、sysfs 层次看不懂 |
| **11.2 platform 与 probe** | 设备树节点怎么一步步变成 probe() 调用？ | of_platform_populate 创建设备、match 触发 probe、devm_\* 管理资源——这是嵌入式驱动绝大部分的日常路径，每一步都有明确的失败模式 | insmod 成功但 probe 不执行、probe 内资源获取失败 |
| **11.3 设备树匹配** | compatible 字符串凭什么匹配上？ | 匹配优先级规则与 of_match_table 的组织决定"哪个驱动赢得设备"；绑定规范是写对设备树的验收标准 | 两个驱动竞争同一设备、匹配到错误的驱动 |
| **11.4 sysfs 与 uevent** | probe 成功后用户空间怎么知道？ | sysfs 三视图与 uevent 机制是内核态设备到 /dev 节点的桥梁；udev 规则写不对，设备节点就不会自动出现 | /dev 节点未创建、/sys 中找不到设备属性 |
| **11.5 设备树 overlay** | 不重启怎么增删设备？ | overlay 的运行时合并是 FPGA 动态重配置与扩展板热插拔的标准方案；它的限制（不能删除已有节点等）直接决定方案边界 | overlay 加载后驱动不 probe、加载失败 |

> 💡 probe 不执行是本章最高频的问题。排查时沿着主线反推：驱动注册了吗（/sys/bus/.../drivers）？设备存在吗（/sys/bus/.../devices）？匹配条件满足吗（compatible 对比）？资源就绪吗（clk/regulator/pinctrl）？四步必中其一。

                               cat /proc/device-tree/<path>/compatible

## 学习目标

建立"设备树节点 → platform_device → 匹配 → probe → uevent"完整旅程的源码级认知，面对 probe 不执行类问题时，能按四步反推法（驱动注册 → 设备存在 → 匹配条件 → 资源就绪）定位到具体环节。

- 第 10 章 中断与时间：request_irq() 与中断注册机制

## 与前后章的关联

- **第 7 章 启动链深度解析**：do_initcalls() 中 device 级别的初始化是驱动 probe 的触发点——子系统初始化完成后才开始 probe 设备
- **第 9 章 内存管理**：probe() 中常用的 devm_ioremap_resource() 与 devm_kzalloc() 依赖内存管理子系统
- **第 10 章 中断与时间**：驱动 probe 流程中通过 request_irq() 注册中断处理函数，中断是驱动与硬件交互的核心机制
- **第 12 章 文件系统与存储**：驱动通过字符设备接口（cdev）或块设备接口暴露给用户空间
- **第 15 章 电源管理**：probe() 中获取的 clock 与 regulator 是电源管理的核心资源，Runtime PM 的 dev_pm_ops 也在 probe 中注册
