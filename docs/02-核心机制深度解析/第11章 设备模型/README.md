# 第11章：设备模型

> 所属：第 二 部 核心机制深度解析
>
> BIEM：[I→E] | 核心问题：内核如何抽象和匹配设备？

## 核心问题

内核如何抽象和匹配设备？

## 为什么需要这一章

你在工作中迟早会遇到这些问题："insmod 后 probe 没有执行""两个驱动竞争同一个设备""设备树节点存在但 /sys 中没有对应设备""设备树 overlay 加载后驱动不自动 probe"。它们有一个共同点：驱动的代码本身没有报错，问题出在驱动与内核设备模型的衔接处。没有对设备模型的源码级理解，这类问题只能靠猜。

本章的核心认知是：**设备模型不是"驱动的容器"，而是一个完整的匹配和生命周期管理系统**。理解总线-设备-驱动三角关系、probe 的执行条件、uevent 的通知机制，是设计健壮驱动架构的基础。

## 其然台阶：先写，再懂（11.0-11.1）

机制讲解需要具象锚点。本章开篇不设理论，先让你动手：

- **11.0 先写一个驱动**：基于第6章的 LED 硬件，从零写一个最小 platform 驱动，亲眼看到 `probe()` 被调用、`/sys/class/leds/` 下出现自己的节点
- **11.1 六种写法**：用 SoC 内置温度传感器和 LM75，把实际工程中驱动的六种形态各写一遍（platform、I2C、厂商 SDK、Legacy、MFD、用户空间），并亲手制造一次"两个驱动竞争同一设备"

走完这两节，你会带着三个亲身体验进入机制部分：probe 被执行过、probe 不执行的迷茫过、驱动竞争的规则困惑过。11.2 起的每一个机制，都对应你刚刚的某一次动手。

## 本章主线：一个设备从设备树节点到 probe 成功的完整旅程

机制主体（11.2-11.6）围绕同一条主线展开：**一个设备从 .dts 中的一个节点出发，经历创建设备对象、与驱动匹配、执行 probe、通知用户空间的完整旅程**：

```
 设备树节点 ──> 11.3 生成 platform_device ──> 11.4 匹配 ──> probe()
  (.dts)         （of_platform_populate）      （compatible）  （资源获取
      │                                        ▲               与硬件初始化）
      │                                        │
      │                              11.2 总线-设备-驱动：
      │                              匹配发生的框架与规则
      │
      └── 运行时修改：11.6 overlay（不重启增删设备）

 probe 成功之后：11.5 sysfs / uevent 把设备状态通知用户空间，udev 创建 /dev 节点
```

每一节要深入的细节，都由旅程上的**一个必须回答的问题**驱动：

| 小节 | 主线上要回答的问题 | 为什么必须深入这些细节 | 对应的典型故障/场景 |
|------|------------------|----------------------|-------------------|
| **11.2 总线-设备-驱动** | 匹配这件事在哪个框架里发生？ | bus_type / device / device_driver 三角关系与 kobject 层次是设备模型的骨架；不理解它，probe 未执行时连排查入口都找不到 | 设备模型概念混乱、sysfs 层次看不懂 |
| **11.3 platform 与 probe** | 设备树节点怎么一步步变成 probe() 调用？ | of_platform_populate 创建设备、match 触发 probe、devm_\* 管理资源——这是嵌入式驱动绝大部分的日常路径，每一步都有明确的失败模式 | insmod 成功但 probe 不执行、probe 内资源获取失败 |
| **11.4 设备树匹配** | compatible 字符串凭什么匹配上？ | 匹配优先级规则与 of_match_table 的组织决定"哪个驱动赢得设备"；绑定规范是写对设备树的验收标准 | 两个驱动竞争同一设备、匹配到错误的驱动 |
| **11.5 sysfs 与 uevent** | probe 成功后用户空间怎么知道？ | sysfs 三视图与 uevent 机制是内核态设备到 /dev 节点的桥梁；udev 规则写不对，设备节点就不会自动出现 | /dev 节点未创建、/sys 中找不到设备属性 |
| **11.6 设备树 overlay** | 不重启怎么增删设备？ | overlay 的运行时合并是 FPGA 动态重配置与扩展板热插拔的标准方案；它的限制（不能删除已有节点等）直接决定方案边界 | overlay 加载后驱动不 probe、加载失败 |

> 💡 probe 不执行是本章最高频的问题。排查时沿着主线反推：驱动注册了吗（/sys/bus/.../drivers）？设备存在吗（/sys/bus/.../devices）？匹配条件满足吗（compatible 对比）？资源就绪吗（clk/regulator/pinctrl）？四步必中其一。这个顺序你在 11.0 已经用过一次，11.3.5 会把它扩展成完整方法论。

## 排错索引：从症状反查小节

```
insmod 成功但 probe 未执行   → 11.3.5，分别确认 /sys/bus/platform/drivers
                               与 devices 两侧是否存在对应条目
设备树节点存在但无设备        → 11.3.1，查 status = "disabled"；
                               cat /proc/device-tree/<path>/compatible
probe 被调用但失败            → 11.3.3，查 clk/regulator/pinctrl 资源获取，
                               依赖子系统可能尚未初始化完成
匹配到了错误的驱动            → 11.4.4，compatible 从精确到通用排列，
                               避免过度通配
两个驱动竞争同一设备          → 11.4.4，dmesg 中 "already bound to driver"；
                               11.1.2 有亲手制造竞争的完整实验
/sys 中找不到设备属性         → 11.5.1，理解 sysfs 三视图的对应关系
/dev 节点未自动创建           → 11.5.2 / 11.5.3，udevadm monitor 观察 uevent，
                               udevadm info 检查规则匹配
overlay 加载后驱动不 probe    → 11.6.3，查 overlay 应用日志与节点状态
设备树写法存疑               → 11.4.3，按绑定规范验证节点
```

## 学习目标

建立"设备树节点 → platform_device → 匹配 → probe → uevent"完整旅程的源码级认知，面对 probe 不执行类问题时，能按四步反推法（驱动注册 → 设备存在 → 匹配条件 → 资源就绪）定位到具体环节。

## 前置知识

## 与前后章的关联

- **第 7 章 启动链深度解析**：do_initcalls() 中 device 级别的初始化是驱动 probe 的触发点——子系统初始化完成后才开始 probe 设备
- **第 9 章 内存管理**：probe() 中常用的 devm_ioremap_resource() 与 devm_kzalloc() 依赖内存管理子系统
- **第 10 章 中断与时间**：驱动 probe 流程中通过 request_irq() 注册中断处理函数，中断是驱动与硬件交互的核心机制
- **第 12 章 文件系统与存储**：驱动通过字符设备接口（cdev）或块设备接口暴露给用户空间
- **第 15 章 电源管理**：probe() 中获取的 clock 与 regulator 是电源管理的核心资源，Runtime PM 的 dev_pm_ops 也在 probe 中注册
