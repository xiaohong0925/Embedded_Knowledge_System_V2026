## <span class="blue"> overlay 应用的内核链 [E]

dtbo 写入 configfs 的 `dtbo` 文件后，内核按一条固定的四步链处理，每一步对应一个明确的子系统：

```
dtbo写入 → of_overlay_apply() 合并 → of_reconfig 通知链 → 实例化新设备 → 驱动probe
```

**第一步：合并。** `of_overlay_apply()` 是内核 OF 子系统的 overlay 入口函数。它把 dtbo 解析成 changeset（变更集），逐条叠加到基板设备树上：overlay 里的新节点在 target 位置新增，同名属性用新值覆盖，`__overlay__` 节点的内容展开后挂到 target 节点下。

**第二步：通知。** 合并每落地一条变更，内核沿 `of_reconfig` 通知链广播事件（`OF_RECONFIG_ADD_NODE`、`OF_RECONFIG_UPDATE_PROPERTY` 等）。关心设备树变化的子系统注册在这个通知链上，能第一时间感知"树被改了"。

**第三步：实例化。** 合并后的节点还只是内存中的 `device_node` 数据结构。`of_platform_populate()` 遍历新增的子树，把 `status = "okay"` 的节点转换成 `platform_device` 并注册进 platform 总线。

**第四步：probe。** 新设备注册触发总线匹配，命中的驱动执行 probe；同时 `kobject_uevent()` 向用户空间发出 `add` 事件，udev/mdev 据规则处理设备节点。整条链走完，`dmesg` 里能看到典型输出：

```
[  12.345678] OF: overlay: applying overlay 'my_eeprom'
[  12.346012] at24 1-0050: 256 byte 24c02 EEPROM, writable
```

任何一步失败，日志都带 `OF: overlay:` 前缀，这是排查的第一落点。

## <span class="blue"> overlay 的能力与限制 [E]

overlay 的合并语义决定了它能做什么、做不到什么：

| 操作 | 是否可行 | 说明 |
|------|---------|------|
| 添加新节点 | ✅ 可以 | overlay 的核心能力，挂到任意 target 下 |
| 修改已有属性值 | ✅ 可以 | 新值覆盖旧值，如 `status = "okay"` |
| 给已有节点新增属性 | ✅ 可以 | 基板没有的属性直接补上 |
| 删除已有节点 | ❌ 不可靠 | `/delete-node/` 是 dtc 编译期指令，运行时动态叠加不应依赖 |
| 删除已有属性 | ❌ 不可靠 | 同上，`/delete-property/` 不适用动态场景 |
| 修改 `#address-cells` / `#size-cells` | ❌ 不行 | 子节点 `reg` 的解析格式由它们决定，改动会破坏整棵子树的地址解析 |
| 修改 `interrupt-parent` | ❌ 不行 | 中断树在启动早期已建立，动态变更会破坏已注册的中断映射 |
| 修改根节点 `compatible` | ❌ 不行 | 机器类型在启动时即确定 |

规律很明确：**叠加是安全的，拆改是危险的。** 11.6.1 从工程角度给出过同样结论：这类"拿走"需求一律回到重编 dtb 的路线，不在 overlay 上耗时间。本节这张表把它落到合并语义层面——哪些操作在设计上就不成立，一目了然。

> 🔴 overlay 合并失败不会让内核 panic，但可能留下半成品状态：部分变更已应用、部分失败。此时若有驱动 probe 到不完整的节点，可能触发 oops。工程上的稳妥做法是一次只加载一份 overlay，确认 `status` 为 `applied` 且设备上线后再叠加下一份。

> ⚠️ overlay 加载成功但设备没反应时，先别怀疑语法。用下文的 `dtc -I fs` 导出合并后的设备树，确认改动确实落到了预期位置——`target` 路径差一个字符，overlay 就会原样合并到错误的分支上，且不报任何错误。

## <span class="blue"> 实锤验证：导出合并后的设备树 [E]

确认合并成功靠 `status` 读数加 `OF: overlay:` 日志，这套两步排查法在 11.6.2 已经讲过，这里不再重复。但 `applied` 只代表"合并过程没报错"，不代表改动落在了预期位置——前面的 ⚠️ 已经说明，`target` 指错时 overlay 照样合并且不报任何错误。要把改动看清楚，得把合并后的整棵树导出来。

```bash
dtc -I fs -O dts /sys/firmware/devicetree/base -o merged.dts
```

这条命令把内核通过 `/sys/firmware/devicetree/base` 暴露的设备树反向转成 dts 源文件，得到的是基板与所有 overlay 合并之后的完整结果。在 `merged.dts` 里搜索 overlay 添加的节点名和属性名，逐项确认：节点是否挂在正确的父节点下、属性值是否符合预期、有没有被后加载的 overlay 再次覆盖。板子上没有 dtc 时，可以把 `/sys/firmware/devicetree/base` 整树拷到开发机上再转换。

状态显示 `applied` 但设备仍不工作时，按两步排查：

1. **查设备节点是否出现**：`ls /sys/bus/platform/devices/` 找目标设备名。节点不存在，说明实例化环节出了问题，检查 `compatible` 拼写和 `status = "okay"`。
2. **查驱动是否绑定**：`ls /sys/bus/platform/drivers/<驱动名>/` 看设备是否在驱动目录下。节点在、绑定不在，问题在驱动端：`of_match_table` 没对上，或 probe 里资源申请失败返回了 `-EPROBE_DEFER`（此时 `cat /sys/kernel/debug/devices_deferred` 能看到它）。

> 💡 `dtc -I fs` 导出的是合并后的整棵树，分不出哪个节点来自基板、哪个来自 overlay。需要区分时，在 overlay 的新增节点里加一个标记属性，如 `overlay-source = "my_eeprom";`，导出后按属性名一搜即得。

## <span class="blue"> 本节总结

| 概念 | 核心要点 | 自查操作 |
|------|---------|---------|
| 应用四步链 | 合并 → `of_reconfig` 通知 → 实例化 `platform_device` → 驱动 probe | `dmesg \| grep "OF: overlay"` 跟踪一次加载 |
| 能做的 | 添加节点、修改/新增属性 | `dtc -I fs` 导出确认 |
| 做不到的 | 删除节点/属性不可靠，核心结构属性不可改 | 遇到这类需求直接重编 dtb |
| 实锤验证 | `dtc -I fs -O dts /sys/firmware/devicetree/base -o merged.dts` | 导出后 grep 目标节点 |
| 排查路径 | 先查节点是否实例化，再查驱动是否绑定 | `/sys/bus/platform/devices/` 与 `drivers/` 对照 |
