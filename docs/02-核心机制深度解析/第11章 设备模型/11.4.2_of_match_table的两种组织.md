## <span class="blue"> 本节导读

11.4.1 解决了"怎么比对"，本节解决"比对数据从哪来、怎么被系统用上"：匹配表在驱动源码里怎么写，编译期经 `MODULE_DEVICE_TABLE` 进入模块元数据，运行期再经 modalias 机制驱动 `modprobe` 自动加载。同一份驱动要同时跑在设备树平台（ARM/RISC-V）和 ACPI 平台（x86）时，需要第二张表，组织方式随之变化。<BR>

## <span class="blue"> of_device_id 数组：设备树平台的标准写法 [E]

设备树平台的驱动在内核源码里的标准形态：

```c
static const struct of_device_id mydrv_match[] = {
    { .compatible = "myvendor,mydevice-v2" },  /* 新版型 */
    { .compatible = "myvendor,mydevice" },     /* 旧版型，兜底 */
    { },  /* 空哨兵，内核以此判定表尾 */
};
MODULE_DEVICE_TABLE(of, mydrv_match);

static struct platform_driver my_driver = {
    .driver = {
        .name = "my_driver",
        .of_match_table = mydrv_match,
    },
    .probe = my_probe,
    .remove = my_remove,
};
```

每行填一个 `.compatible`，与设备树节点 `compatible` 列表中的某一项对上即匹配。空哨兵漏写时内核遍历会越过数组边界，直到碰巧读到一块全零内存才停，表现为偶发的匹配错乱，这类问题不会在编译期暴露。

设备树节点有多个 compatible（`"v2", "v1"`）时，驱动表把历史版本都列上，新老设备树就都能匹配。按 11.4.1 的评分规则，最终选中哪个条目由节点列表顺序决定，驱动表内部的排列顺序不影响结果。

## <span class="blue"> MODULE_DEVICE_TABLE 与 modalias：自动加载的完整链路 [E]

`MODULE_DEVICE_TABLE(of, mydrv_match)` 这行宏与运行时匹配无关——去掉它，驱动照样注册、照样匹配、照样 probe。它服务的是另一条链路：**模块自动加载**。整条链路分四段：

1. **编译期**：宏把匹配表导出到模块的 `__mod_of_device_table` 段，modpost 据此在生成的 `.mod.c` 里写入 MODULE_ALIAS，可用 `modinfo my_driver.ko | grep alias` 看到 `alias: of:N*T*Cmyvendor,mydevice-v2*`
2. **安装期**：`depmod` 扫描 `/lib/modules/$(uname -r)/` 下所有模块的别名，汇总生成 `modules.alias` 文件
3. **运行期（内核侧）**：OF 设备注册时，内核根据设备节点算出 modalias 字符串（形如 `of:N<节点名>T<类型>C<compat1>C<compat2>`，携带节点全部 compatible），随 uevent 事件发给用户空间
4. **运行期（用户空间）**：udev 收到 uevent 后执行 `modprobe $MODALIAS`，modprobe 拿 modalias 去 `modules.alias` 里查出模块名并加载

缺了第 1 段，整条链从源头断掉：`modules.alias` 里没有这个驱动的条目，modprobe 查不到，系统永远不会自动加载它。手动 `insmod` 能工作，恰恰是因为手动加载绕过了整条 modalias 机制——这是"insmod 能用、重启后不自动加载"这一类问题的标准成因。

自查两个位置：

```bash
# 模块是否携带 of 别名
modinfo my_driver.ko | grep alias

# 别名是否已进入系统数据库（安装新模块后需重跑 depmod）
grep myvendor /lib/modules/$(uname -r)/modules.alias
```

两处任一为空，自动加载都不会发生。

## <span class="blue"> of_match_ptr：条件编译的兼容层 [E]

部分驱动写成 `.of_match_table = of_match_ptr(mydrv_match)`。该宏在 `CONFIG_OF` 开启时原样返回指针，关闭时展开为 NULL：

```c
#ifdef CONFIG_OF
#define of_match_ptr(_ptr)  (_ptr)
#else
#define of_match_ptr(_ptr)  NULL
#endif
```

作用是让同一份代码在不含设备树支持的内核配置下也能编译通过。宏不改变匹配行为，读代码时把它当成透明的即可。新代码更常见的做法是直接用 `struct platform_driver` 较新的封装宏，原理相同。

## <span class="blue"> ACPI 双表并存：跨平台驱动的组织方式 [E]

x86 平台用 ACPI 表而非设备树描述硬件，匹配依据是 ACPI 设备对象的 `_HID`（Hardware ID）字符串。驱动要同时支持两类平台时，两张表并列提供：

```c
static const struct of_device_id mydrv_of_match[] = {
    { .compatible = "myvendor,mydevice" },
    { },
};
MODULE_DEVICE_TABLE(of, mydrv_of_match);

static const struct acpi_device_id mydrv_acpi_match[] = {
    { "MYV0001", 0 },   /* 对应 ACPI _HID */
    { }
};
MODULE_DEVICE_TABLE(acpi, mydrv_acpi_match);

static struct platform_driver my_driver = {
    .driver = {
        .name = "my_driver",
        .of_match_table = mydrv_of_match,
        .acpi_match_table = ACPI_PTR(mydrv_acpi_match),
    },
    .probe = my_probe,
};
```

| 对比项 | of_match_table | acpi_match_table |
|-------|----------------|------------------|
| 匹配依据 | compatible 字符串 | ACPI `_HID`/`_CID` |
| 数据结构 | `struct of_device_id` | `struct acpi_device_id` |
| 别名宏 | `MODULE_DEVICE_TABLE(of, ...)` | `MODULE_DEVICE_TABLE(acpi, ...)` |
| 生效平台 | ARM/RISC-V 等设备树平台 | x86 PC/服务器 |

`ACPI_PTR` 与 `of_match_ptr` 同构：`CONFIG_ACPI` 关闭时展开为 NULL。

platform 总线的 `platform_match()` 对单个驱动的检查顺序是固定的：先试 OF 匹配（`of_driver_match_device()`），再试 ACPI 匹配（`acpi_driver_match_device()`），再试 `id_table`，最后回退到驱动名与设备名的字符串比较，任一步成功即判定匹配。当前平台启用了哪套固件接口，对应的表就生效；另一张表在该平台上不被触及，两者不存在竞争。

> 💡 ARM 平台上 `MODULE_DEVICE_TABLE(acpi, ...)` 生成的别名没有消费者——udev 收到的 uevent 里只有 OF modalias。反过来 x86 上 of 别名同样无效。双表并存时两个别名宏都要写，各管各的平台。

> ⚠️ 数组改名后记得同步改 `MODULE_DEVICE_TABLE` 的第二个参数。参数名与实际数组名不一致时编译即报错，属于容易改漏的位置；真正麻烦的是漏写整个宏——编译通过、insmod 可用、自动加载静默失效，排查时先跑上面的 `modinfo` 自查。

## <span class="blue"> 本节总结

| 概念 | 核心要点 | 自查操作 |
|------|---------|---------|
| of_device_id 数组 | 设备树平台标准写法，空哨兵结尾 | 核对 compatible 与设备树逐字节一致 |
| MODULE_DEVICE_TABLE | 生成模块别名，支撑 modprobe 自动加载，与运行时匹配无关 | `modinfo xxx.ko \| grep alias` |
| modalias | 内核按节点算出的匹配串，经 uevent 传给 udev | `cat /sys/bus/.../uevent` 看 MODALIAS |
| of_match_ptr/ACPI_PTR | 条件编译宏，配置关闭时填 NULL | 确认 CONFIG_OF/CONFIG_ACPI 状态 |
| ACPI 双表 | 平台 match 内按 OF→ACPI→id_table→名字的顺序检查 | 核对 _HID 与固件 ACPI 表一致 |
