# 11.1.1 模式① 现代标准型：platform 写法读 SoC 内置温度

> 所属章节：第11章 设备模型 > 11.1 其然台阶·六种写法
>
> 难度：[I] | 预计阅读时间：25分钟（含上板实操） | 验证分级：A级（上板可验证）

## <span class="blue"> 本节导读

本节覆盖：

- 六种写法中的第一种：新设计、主流 ARM/RISC-V 板卡上的**现代标准型**——platform_driver + 设备树 + 标准内核 API
- 一颗"SoC 内置温度传感器"的完整驱动：i.MX6ULL 的 TEMPMON / RK3568 的 TSADC，经 thermal 框架读取
- 完整 `.c` + 设备树片段 + 编译加载 + 上板验证，三块正文板卡（i.MX6ULL / RK3568 / 全志D1）零新增硬件全部可跑

## <span class="blue"> 场景一句话 [B]

你的外设集成在 SoC 内部（或挂在 SoC 的片上总线上）、由设备树静态描述、没有 probe 以外的总线枚举过程——这是新项目里最常见的形态，写法和 11.0 的 LED 驱动完全同构。

## <span class="blue"> 一个重要判断：不直读寄存器 [I]

SoC 内置温度传感器是真实存在的硬件：i.MX6ULL 有 TEMPMON，RK3568 有 TSADC。但本节的驱动**不去读写它们的寄存器**，原因很实际：这些传感器已经被内核 thermal 子系统接管（`imx_thermal` / `rockchip_thermal` 驱动），寄存器正在被它们轮询。你的驱动绕过子系统直接摸寄存器，等于和两个驱动同时操作一个硬件——这是制造冲突，不是写驱动。

现代标准型写法的正确姿势是：**设备树描述你的设备，用标准内核 API 拿数据，注册标准用户接口**。thermal 框架提供数据，hwmon 框架提供接口，你的驱动只做两者的连接件。

> 💡 验证数据一直在那里等着：`cat /sys/class/thermal/thermal_zone0/temp`，三块板开机即有。本节要做的是用你自己的驱动、以你自己的设备名，把同一个数据通过 hwmon 接口再发布一次。

## <span class="blue"> 驱动源码 mysoctemp.c [I]

```c
// SPDX-License-Identifier: GPL-2.0
/*
 * mysoctemp.c - platform 写法示例：读取 SoC 内置温度
 * 配合设备树节点 compatible = "myvendor,soctemp" 使用
 */
#include <linux/module.h>
#include <linux/platform_device.h>
#include <linux/of.h>
#include <linux/thermal.h>        // thermal 框架：thermal_zone_device
#include <linux/hwmon.h>          // hwmon 框架：标准温度接口

/* 私有数据：一个 thermal zone 句柄 */
struct mysoctemp_priv {
	struct thermal_zone_device *tz;
};

/* hwmon 可见性：只暴露一个只读的 temp1_input */
static umode_t mysoctemp_is_visible(const void *data,
				    enum hwmon_sensor_types type,
				    u32 attr, int channel)
{
	if (type == hwmon_temp && attr == hwmon_temp_input)
		return 0444;
	return 0;
}

/* hwmon 读回调：用户 cat temp1_input 时执行，val 输出毫摄氏度 */
static int mysoctemp_read(struct device *dev, enum hwmon_sensor_types type,
			  u32 attr, int channel, long *val)
{
	struct mysoctemp_priv *priv = dev_get_drvdata(dev);
	int temp, ret;

	if (type != hwmon_temp || attr != hwmon_temp_input)
		return -EOPNOTSUPP;

	ret = thermal_zone_get_temp(priv->tz, &temp); // 向 thermal 框架要温度
	if (ret)
		return ret;

	*val = temp;    // thermal 框架返回的单位已是毫摄氏度
	return 0;
}

static const struct hwmon_ops mysoctemp_ops = {
	.is_visible = mysoctemp_is_visible,
	.read       = mysoctemp_read,
};

/* 通道描述：本设备有一个 temp 通道，带 input 属性 */
static const struct hwmon_channel_info * const mysoctemp_info[] = {
	HWMON_CHANNEL_INFO(temp, HWMON_T_INPUT),
	NULL
};

static const struct hwmon_chip_info mysoctemp_chip_info = {
	.ops  = &mysoctemp_ops,
	.info = mysoctemp_info,
};

static const struct of_device_id mysoctemp_of_match[] = {
	{ .compatible = "myvendor,soctemp", },
	{ }
};
MODULE_DEVICE_TABLE(of, mysoctemp_of_match);

static int mysoctemp_probe(struct platform_device *pdev)
{
	struct device *dev = &pdev->dev;
	struct mysoctemp_priv *priv;
	const char *zone_name;
	struct device *hwmon_dev;

	priv = devm_kzalloc(dev, sizeof(*priv), GFP_KERNEL);
	if (!priv)
		return -ENOMEM;

	/* 从设备树读出目标 thermal zone 的名字，再向框架要句柄 */
	if (of_property_read_string(dev->of_node, "thermal-zone", &zone_name))
		return dev_err_probe(dev, -EINVAL, "missing thermal-zone property\n");

	priv->tz = thermal_zone_get_zone_by_name(zone_name);
	if (IS_ERR(priv->tz))
		return dev_err_probe(dev, PTR_ERR(priv->tz),
				     "thermal zone %s not found\n", zone_name);

	/* 注册为 hwmon 设备：/sys/class/hwmon/hwmonX/ 自动出现 */
	hwmon_dev = devm_hwmon_device_register_with_info(dev, "mysoctemp",
							 priv, &mysoctemp_chip_info,
							 NULL);
	if (IS_ERR(hwmon_dev))
		return dev_err_probe(dev, PTR_ERR(hwmon_dev),
				     "hwmon register failed\n");

	dev_info(dev, "probe success, reading zone %s\n", zone_name);
	return 0;
}

static struct platform_driver mysoctemp_driver = {
	.probe  = mysoctemp_probe,
	.driver = {
		.name           = "mysoctemp",
		.of_match_table = mysoctemp_of_match,
	},
};
module_platform_driver(mysoctemp_driver);

MODULE_AUTHOR("reader");
MODULE_DESCRIPTION("SoC temperature via thermal framework, platform style");
MODULE_LICENSE("GPL");
```

## <span class="blue"> 设备树片段 [B]

在板级设备树根节点下添加：

```dts
/ {
	soctemp {
		compatible = "myvendor,soctemp";
		thermal-zone = "cpu-thermal";   /* i.MX6ULL 用这个 */
		/* thermal-zone = "soc-thermal"; RK3568 改成这个 */
		status = "okay";
	};
};
```

zone 名字以你的板卡实际为准，先确认再填：

```bash
cat /sys/class/thermal/thermal_zone0/type
```

## <span class="blue"> 编译、加载、验证 [B]

`Makefile` 与 11.0 完全同款（`obj-m += mysoctemp.o`，指向第4章的内核源码树）。编译并拷贝到开发板后：

```bash
insmod /home/root/mysoctemp.ko
dmesg | tail -3
```

预期输出：

```
[  88.123456] mysoctemp soctemp: probe success, reading zone cpu-thermal
```

验证 hwmon 接口（hwmon 编号以实际为准）：

```bash
cat /sys/class/hwmon/hwmon*/name
cat /sys/class/hwmon/hwmon0/temp1_input
```

预期输出：`mysoctemp`，温度值为毫摄氏度（如 `42500` 即 42.5°C）。与原始数据来源交叉验证：

```bash
cat /sys/class/thermal/thermal_zone0/temp
```

两个数值应基本一致。手摸 SoC 表面或跑一段 `stress-ng --cpu 4`，能看到两边同步上升。

> 💡 内核版本差异只有一行：≤4.19 的内核 `thermal_zone_get_temp` 第二个参数是 `unsigned long *`，更新的内核是 `int *`。编译报指针类型警告时，把 `int temp` 改成 `unsigned long temp` 即可。

## <span class="blue"> 引出的问题

这个驱动和 11.0 的 LED 驱动骨架几乎一样——of_match 表、probe、`module_platform_driver`。但注意一个区别：这次的设备节点**没有对应一段我们独占的硬件寄存器**，probe 里拿到的是 thermal 框架的句柄。那么问题来了：

1. platform 总线上的设备，到底需不需要"真实独占的硬件地址"？设备树节点的本质是什么？
2. 如果传感器不是 SoC 内置的，而是挂在 I2C 总线上的独立芯片（比如一颗 ¥3 的 LM75），写法会怎么变？

第二个问题就是模式②，也是六种写法里工程中使用最频繁的一种。

## 本节总结

| 要件 | 要点 |
|------|------|
| 写法定位 | SoC 内置/片上总线外设，新项目首选形态 |
| 资源来源 | 不直读寄存器，用 thermal 框架标准 API |
| 用户接口 | 注册 hwmon，获得 `/sys/class/hwmon/` 标准目录 |
| 骨架复用 | 与 11.0 LED 驱动同构：of_match → probe → 注册框架接口 |
