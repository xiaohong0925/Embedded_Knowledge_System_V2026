## <span class="blue"> 本节导读

上一节把设备树节点翻译成了 platform_device，设备侧就位。本节进入主线"设备树节点→platform_device→匹配→probe"的第二环：驱动侧。`platform_driver_register()` 一行背后是一条多层调用链，终点是总线的 match 函数 `platform_match()`；match 内部四种匹配方式有严格的优先级顺序，配置写错一级，驱动就永远等不到 probe。<BR>

## <span class="blue"> 注册链路：从 platform_driver_register 到 platform_match [E]

### platform_driver 是什么

platform_driver 是驱动在 platform 总线上的注册凭据，定义在 `<linux/platform_device.h>`：

```c
struct platform_driver {
    int (*probe)(struct platform_device *);      /* 匹配成功时调用 */
    int (*remove)(struct platform_device *);     /* 解绑/卸载时调用 */
    void (*shutdown)(struct platform_device *);  /* 关机时调用 */
    int (*suspend)(struct platform_device *, pm_message_t);
    int (*resume)(struct platform_device *);
    struct device_driver driver;                 /* 内嵌的通用驱动对象 */
    const struct platform_device_id *id_table;   /* 第 3 级匹配用的 ID 表 */
    bool prevent_deferred_probe;
};
```

内嵌的 `struct device_driver` 里放匹配信息：`name` 字段和 `of_match_table` 指针。注册一个驱动的最小形态：

```c
static const struct of_device_id my_of_match[] = {
    { .compatible = "myvendor,mydevice" },
    { .compatible = "myvendor,mydevice-v2" },
    { }   /* 必须以空表项结尾 */
};
MODULE_DEVICE_TABLE(of, my_of_match);

static struct platform_driver my_driver = {
    .probe  = my_probe,
    .remove = my_remove,
    .driver = {
        .name = "my_device",
        .of_match_table = my_of_match,
    },
};

module_platform_driver(my_driver);
```

`module_platform_driver()` 是模块 init/exit 的一键封装，展开后核心动作就是 `platform_driver_register(&my_driver)`。

### 注册调用链

`platform_driver_register` 本身是宏，真实入口是 `__platform_driver_register()`。完整链路：

```
platform_driver_register()          /* 宏，包一层 THIS_MODULE */
  └── __platform_driver_register()
        └── driver_register()             /* 通用驱动核心 */
              └── bus_add_driver()        /* 挂到 platform 总线 */
                    ├── 挂接到总线驱动链表，导出 sysfs 目录
                    └── driver_attach()   /* 立即扫描总线上所有设备 */
                          └── bus_for_each_dev(__driver_attach)
                                └── __driver_attach()
                                      ├── driver_match_device()
                                      │     └── platform_match()   /* 总线 match 函数 */
                                      └── driver_probe_device()    /* 匹配成功才走到这 */
```

链路上最关键的一环：`bus_add_driver()` 不只负责挂链表，挂完立刻调用 `driver_attach()` 主动扫描总线上已存在的全部设备。匹配动作在设备注册和驱动注册两个方向都会触发，这就是"驱动比设备晚加载也能正常绑定"的原因。

### platform_match 的四级优先级

`platform_match()`（`drivers/base/platform.c`）按固定顺序尝试四种匹配方式，前一种命中即返回成功。在此之前还有一个特例：设备的 `driver_override` 属性非空时只做驱动名比较，四种匹配全部旁路（详见 11.3.4）。

| 优先级 | 匹配方式 | 依赖数据 | 适用场景 |
|:--:|---------|---------|---------|
| 1 | OF 设备树匹配 | 节点 compatible × `of_match_table` | ARM/RISC-V 嵌入式主流 |
| 2 | ACPI 匹配 | ACPI 设备描述 | x86 服务器/桌面 |
| 3 | id_table 匹配 | `platform_device_id` 数组 | 无设备树的老式板级代码 |
| 4 | name 字符串匹配 | `pdev->name` 与 `drv->name` 逐字节相等 | 最原始的兜底方式 |

嵌入式场景几乎只用第 1 级：设备节点的 compatible 是否出现在驱动的 of_match_table 里。两点细节：

- 设备树 compatible 可以写多个值，约定从最具体到最通用排列，例如 `compatible = "myvendor,uart-v2", "myvendor,uart"`。匹配时任一值命中 of_match_table 即算成功；驱动表里多个表项都能命中时，由 `of_match_node()` 的计分规则选出最具体的那个。
- of_match_table 数组内部的排列顺序不影响匹配结果。

> 💡 `MODULE_DEVICE_TABLE(of, my_of_match)` 不参与运行时匹配。它把 ID 表导出到模块的 modinfo，`depmod` 据此生成别名表，udev/modprobe 收到设备的 uevent 后才能自动加载对应模块。编译进内核的驱动不写这行，匹配照常工作；编成模块又不写，匹配仍然工作，但自动加载失效。

四种匹配并存是历史层积：name 匹配最早，id_table 服务于板级文件时代，设备树普及后 OF 匹配成为主流，ACPI 服务于 x86 生态。新写的嵌入式驱动直接配置 of_match_table 即可。

## <span class="blue"> 匹配成功之后：probe 是怎么被调起来的 [E]

`platform_match()` 返回成功后，链路继续向驱动核心深处走：

```
__driver_attach()
  └── driver_probe_device()
        └── really_probe()
              ├── 建立 dev 与 drv 的双向绑定、通知总线
              └── platform_drv_probe()   /* platform 总线的 probe 包装 */
                    └── drv->probe(pdev) /* 驱动实现的 .probe */
```

`platform_drv_probe()` 是一层薄封装：从 `struct device` 取出外层的 platform_device，再调用驱动注册的 `.probe`。注意传参类型：`.probe` 收到的是 `struct platform_device *`，不是 `struct device *`。platform_device 内嵌 `struct device dev`，并携带 resource 数组和 `num_resources`，probe 里取寄存器地址、中断号都从这里来——下一节展开 probe 内部。

反向动作在同一条链上：`remove()` 由设备注销（`platform_device_unregister()`）或驱动卸载触发，经驱动核心调到 `platform_drv_remove()`，最终进入驱动的 `.remove`。

维护老内核代码时偶见 id_table 写法，需要认得：

```c
/* id_table 匹配方式（老式写法，仅用于阅读老代码） */
static const struct platform_device_id my_ids[] = {
    { "mydevice",    0 },
    { "mydevice-v2", 1 },
    { }
};

static struct platform_driver my_driver = {
    .id_table = my_ids,      /* 第 3 级匹配 */
    .probe    = my_probe,
    .driver   = { .name = "my_device" },
};
```

新驱动不采用这种写法，直接走设备树。

## <span class="blue"> 本节总结

| 概念 | 核心要点 | 自查操作 |
|------|---------|---------|
| 注册链路 | `platform_driver_register()` → `__platform_driver_register()` → `driver_register()` → `bus_add_driver()` → `driver_attach()` | 跟代码走一遍调用链 |
| 双向触发 | 设备注册和驱动注册都会触发匹配，加载顺序不影响绑定 | 后加载驱动模块验证绑定 |
| 匹配优先级 | OF → ACPI → id_table → name，前一种命中即返回 | 读 `drivers/base/platform.c` |
| probe 调用路径 | match 成功 → `really_probe()` → `platform_drv_probe()` → `.probe()` | 在 probe 入口加打印确认 |
| MODULE_DEVICE_TABLE | 供 depmod 生成别名，实现模块自动加载；不参与运行时匹配 | `modinfo` 查看模块别名 |
