# 11.0.1 先写一个驱动：从0到1的最小平台驱动

> 所属章节：第11章 设备模型 > 11.0 其然台阶
>
> 难度：[B→I] | 预计阅读时间：45分钟（含上板实操）

## <span class="blue"> 本节导读

本节覆盖：

- 基于第6章的 LED 硬件上下文（同一个 GPIO、同一块开发板），从零写一个约 80 行的最小 platform 驱动，替代内核自带的 `leds-gpio`
- 完整的 `.c` 文件、`Makefile`、设备树片段，复制粘贴即可编译
- 编译、`insmod` 加载、`dmesg` 确认 probe 被调用、`/sys/class/leds/` 下出现自定义节点并点亮 LED 的完整验证流程
- 驱动编写中最常见的两个"第一次"问题：compatible 不一致、GPIO 被占用

本节只回答"驱动长什么样、怎么让它跑起来"，不解释背后的匹配机制——那是 11.2 的任务。<br>
你唯一需要的前置基础是第6章：用过 `/sys/class/leds/`、写过 LED 设备树节点。

## <span class="blue"> 目标：写一个属于自己的 LED 驱动 [B]

第6章里，你用的是内核自带的 `leds-gpio` 驱动：在设备树里写一个 `compatible = "gpio-leds"` 的节点，内核就自动把 LED 注册到 `/sys/class/leds/` 下。整个过程你没有写一行代码。

本节把这件事反过来：**自己写一个驱动，取代 `leds-gpio`**。<br>
完成后你会亲眼看到三件事：

1. `insmod myled.ko` 之后，`dmesg` 打印出你自己写的 `pr_info` 信息——probe 函数真的被内核调用了
2. `/sys/class/leds/` 下出现一个名为 `myled` 的新目录
3. `echo 1 > /sys/class/leds/myled/brightness`，板上的 LED 点亮

这三件事和第6章用现成驱动的体验几乎一样，但这一次，每一行都是你的代码做的。

> 💡 本节代码适配野火 i.MX6ULL 开发板（与第3-6章一致），LED 接在 `gpio0` 的第 21 号引脚、低电平有效。<br>
> 使用其他板卡时，只需修改设备树片段中的 GPIO 控制器和引脚号，`.c` 文件不用动。

## <span class="blue"> 驱动源码 myled.c [I]

新建一个工作目录（PC 上），创建 `myled.c`，内容如下：

```c
// SPDX-License-Identifier: GPL-2.0
/*
 * myled.c - 最小 platform LED 驱动
 * 配合设备树节点 compatible = "myvendor,myled" 使用
 */
#include <linux/module.h>        // 模块基础设施：MODULE_LICENSE 等
#include <linux/platform_device.h> // platform_driver / platform_device
#include <linux/of.h>            // 设备树匹配：of_device_id
#include <linux/gpio/consumer.h> // gpiod_* GPIO 消费接口
#include <linux/leds.h>          // LED 子系统：led_classdev

/* 驱动的私有数据：本驱动只需要一个 GPIO 和一个 LED 设备对象 */
struct myled_priv {
	struct gpio_desc *gpiod;      // LED 连接的 GPIO（描述符形式）
	struct led_classdev cdev;     // 注册到 LED 子系统的设备对象
};

/* LED 子系统调用的回调：用户写 brightness 文件时执行
 * brightness_set_blocking 表示内核保证在可睡眠的上下文调用它 */
static void myled_set(struct led_classdev *cdev, enum led_brightness val)
{
	struct myled_priv *priv = container_of(cdev, struct myled_priv, cdev);

	gpiod_set_value_cansleep(priv->gpiod, val); // 把亮度值写到 GPIO 引脚
}

/* 设备树匹配表：声明本驱动支持哪些 compatible 字符串 */
static const struct of_device_id myled_of_match[] = {
	{ .compatible = "myvendor,myled", },
	{ /* 结尾空项，必须存在 */ }
};
MODULE_DEVICE_TABLE(of, myled_of_match); // 让模块自动加载机制能看到这张表

/* probe：内核发现设备与本驱动匹配后调用，返回值 0 表示成功 */
static int myled_probe(struct platform_device *pdev)
{
	struct myled_priv *priv;

	/* 分配私有数据结构，devm_ 前缀表示由内核自动释放 */
	priv = devm_kzalloc(&pdev->dev, sizeof(*priv), GFP_KERNEL);
	if (!priv)
		return -ENOMEM;

	/* 从设备树节点的 gpios 属性获取 GPIO，GPIOD_ASIS 表示不改变当前状态 */
	priv->gpiod = devm_gpiod_get(&pdev->dev, NULL, GPIOD_ASIS);
	if (IS_ERR(priv->gpiod))
		return dev_err_probe(&pdev->dev, PTR_ERR(priv->gpiod),
				     "failed to get GPIO\n");

	/* 填写 LED 设备对象并注册到 LED 子系统
	 * 注册成功后 /sys/class/leds/myled/ 自动出现 */
	priv->cdev.name = "myled";
	priv->cdev.max_brightness = 1;
	priv->cdev.brightness_set_blocking = myled_set;
	devm_led_classdev_register(&pdev->dev, &priv->cdev);

	dev_info(&pdev->dev, "probe success, LED registered\n");
	return 0;
}

/* platform_driver 对象：本驱动的主体 */
static struct platform_driver myled_driver = {
	.probe  = myled_probe,
	.driver = {
		.name           = "myled",
		.of_match_table = myled_of_match, // 挂接设备树匹配表
	},
};

/* 模块入口/出口：注册与注销 platform_driver 的样板宏 */
module_platform_driver(myled_driver);

MODULE_AUTHOR("reader");
MODULE_DESCRIPTION("Minimal platform LED driver");
MODULE_LICENSE("GPL");
```

整份代码只有四个函数级要件，记住它们的名字就够了：

| 要件 | 作用 | 用户可观察到的效果 |
|------|------|------------------|
| `myled_of_match` | 声明"我支持 `myvendor,myled`" | 决定设备树节点能不能找到这个驱动 |
| `myled_probe` | 拿到 GPIO、注册 LED 设备 | `dmesg` 里的日志、`/sys/class/leds/myled/` |
| `myled_set` | 把亮度值写到引脚 | `echo 1 > brightness` 时 LED 亮 |
| `module_platform_driver` | 模块加载/卸载时注册与注销驱动 | `insmod`/`rmmod` 的行为 |

代码里的注释只说明每行"是什么"。<BR>
至于"为什么 insmod 之后 probe 就会被调用""compatible 字符串是谁和谁比较的"，先按下不表——11.2 会逐层拆开。

## <span class="blue"> Makefile [B]

同一目录下创建 `Makefile`：

```makefile
obj-m += myled.o

# 内核源码树路径：指向第4章编译过的内核源码目录
KDIR ?= $(HOME)/linux-imx
ARCH ?= arm
CROSS_COMPILE ?= arm-linux-gnueabihf-

all:
	make -C $(KDIR) M=$(PWD) ARCH=$(ARCH) CROSS_COMPILE=$(CROSS_COMPILE) modules

clean:
	make -C $(KDIR) M=$(PWD) clean
```

`obj-m += myled.o` 告诉内核构建系统：把 `myled.c` 编译成一个可加载模块（`.ko`）。<BR>
`M=$(PWD)` 表示构建当前目录下的模块，内核源码树里已有的编译规则会完成其余工作。

> ⚠️ `KDIR` 必须指向**为目标板配置并编译过**的内核源码树（第4章的产物），而不是 PC 上 `/lib/modules` 下的内核。<BR>
> 模块和运行内核的版本、配置必须一致，否则 `insmod` 会报 `Invalid module format`。

## <span class="blue"> 设备树片段 [B]

打开第6章使用的板级设备树文件，做两处修改。

第一处：把原来的 `gpio-leds` 节点禁用（它占着同一个 GPIO，不禁用的话，你的驱动申请 GPIO 会失败）：

```dts
leds {
	compatible = "gpio-leds";
	status = "disabled";    /* 新增：让位给自己的驱动 */

	led0: led-green {
		label = "green";
		gpios = <&gpio0 21 GPIO_ACTIVE_LOW>;
		default-state = "off";
	};
};
```

第二处：在根节点下添加你自己的设备节点：

```dts
/ {
	myled {
		compatible = "myvendor,myled";        /* 与驱动 of_match 表一致 */
		gpios = <&gpio0 21 GPIO_ACTIVE_LOW>;  /* 与第6章同一个引脚 */
		status = "okay";
	};
};
```

修改完成后重新编译设备树并复制到启动分区（命令与第3章一致）：

```bash
make ARCH=arm CROSS_COMPILE=arm-linux-gnueabihf- imx6ull-14x14-evk-myboard.dtb
```

> 🔴 `compatible = "myvendor,myled"` 这个字符串必须和设备驱动里 `myled_of_match` 表中的字符串**逐字符一致**，包括逗号和连字符。<BR>
> 一个字母的差异，就是"insmod 成功但 probe 毫无反应"的全部原因。

## <span class="blue"> 编译、加载、验证 [B]

在 PC 上编译模块，并拷贝到开发板（SD 卡根文件系统或 NFS 均可）：

```bash
cd myled/
make
cp myled.ko /path/to/rootfs/home/root/
```

开发板上电，依次执行：

```bash
insmod /home/root/myled.ko
dmesg | tail -5
```

预期输出：

```
[  123.456789] myled myled: probe success, LED registered
```

看到这一行，说明内核调用了你的 `myled_probe()`。接着验证用户接口：

```bash
ls /sys/class/leds/
```

预期输出中出现 `myled`：

```
myled  mmc0::
```

然后点亮 LED：

```bash
echo none > /sys/class/leds/myled/trigger
echo 1 > /sys/class/leds/myled/brightness
```

板上的 LED 点亮。`echo 0` 熄灭。最后卸载模块，观察目录消失：

```bash
rmmod myled
ls /sys/class/leds/
```

`myled` 目录随模块卸载自动消失——代码里没有写任何"删除目录"的逻辑，这是 `devm_` 系列函数在驱动注销时自动完成的资源清理。

## <span class="blue"> 两个最常见的"第一次"问题 [I]

第一次写驱动的人，几乎全部栽在下面两个坑里。先认识它们，11.2 会解释它们背后的原理。

**症状一：insmod 成功，但 dmesg 没有任何输出，`/sys/class/leds/` 里没有 `myled`。**

按顺序检查三项：

```bash
ls /sys/bus/platform/drivers/myled/                          # 驱动注册上了吗
cat /proc/device-tree/myled/compatible                       # 设备树节点生效了吗
```

- 第一项不存在：模块没真正加载成功，`dmesg | grep myled` 查报错
- 第二项报错 `No such file or directory`：设备树没改对或没重新编译烧录
- 两项都在但 probe 没执行：两边 compatible 字符串不一致，逐字符对比

**症状二：probe 执行了，但打印 `failed to get GPIO: -16`。**

错误码 `-16` 即 `-EBUSY`：这个 GPIO 已经被别人占用。<BR>
最常见的原因是原来的 `gpio-leds` 节点没有禁用，`leds-gpio` 驱动抢先申请了引脚。回到设备树片段一节，确认 `status = "disabled"` 已添加。

> 💡 排查时记住一个顺序：驱动注册了吗 → 设备存在吗 → 匹配条件满足吗 → 资源空闲吗。<BR>
> 这个顺序在 11.3.5 会扩展成完整的 probe 失败排查方法论。

## <span class="blue"> 引出的问题

到这里，你已经亲手写完并验证了一个驱动。但有三件事，你只是在"用"，并不知道原理：

1. **你只是 `insmod` 了一个模块，谁去调用了 `myled_probe()`？** 模块里没有 `main` 函数，probe 也不是你调用的。
2. **设备树里那么多节点，内核怎么知道 `myled` 节点该归你的驱动管？** 字符串比较发生在哪里、什么时候发生？
3. **`echo 1 > brightness` 是一个文件写操作，它怎么变成 `myled_set()` 的一次函数调用？** 这个文件是谁创建的？

这三个问题正是 11.2 的核心内容。<br>
但在深入机制之前，先看一眼更大的世界: 实际工程中的驱动远不止 platform 这一种写法：挂在 I2C 总线上的传感器、被厂商 SDK 封装的外设、硬编码地址的遗留代码……

下一节（11.1）用一颗温度传感器把六种写法全部写一遍。

## 本节总结

| 要件 | 要点 | 验证方式 |
|------|------|---------|
| of_match 表 | 声明驱动支持的 compatible 字符串 | 与设备树节点逐字符一致 |
| probe() | 获取资源、注册设备，返回 0 表示成功 | `dmesg` 出现 probe 日志 |
| devm_* 函数 | 资源由内核自动释放，remove 可不写 | `rmmod` 后接口自动消失 |
| Makefile | `obj-m` + `M=$(PWD)`，依赖已编译的内核树 | `make` 产出 `.ko` |
| 设备树节点 | 原驱动节点先禁用，避免 GPIO 占用冲突 | `cat /proc/device-tree/myled/compatible` |
