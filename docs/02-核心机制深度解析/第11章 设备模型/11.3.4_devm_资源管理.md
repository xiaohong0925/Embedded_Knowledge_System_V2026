# 11.3.4 devm_*资源管理

> 所属：第11章 设备模型 > 11.3 platform设备与probe流程
> 
> 难度：[I→E] | 预计阅读时间：18分钟

## <span class="blue"> 本节导读

11.3.3 的 `dw8250_probe()` 里反复出现 `devm_` 前缀的 API：`devm_kzalloc()`、`devm_ioremap_resource()`、`devm_clk_get()`。这些调用之后没有配对的释放代码，错误路径上也不见 `goto` 清理链——上一节埋下的这个疑问，就是本节的主题。`devm_` 背后是内核的 device resource management（devres，设备资源托管）子系统，实现于 drivers/base/devres.c：申请资源时把它挂到 device 的托管链表上，由内核在固定时机统一释放。资源泄漏是驱动开发最常见的缺陷类别之一，devres 是内核给出的系统性解法。<BR>
本节覆盖：devres 链表的真实数据结构、释放时机的内核源码、LIFO 释放顺序的成因、常用 devm 函数对照、devm 管不到的三类边界、传统写法与 devm 写法的对比，结尾附完整调用链与动手练习。

## <span class="blue"> devres 的数据结构：资源挂到 device 上 [I→E]

每个 `struct device` 内部维护两条链表，一条存资源节点，一条存资源组节点（include/linux/device.h，有删节）：

```c
struct device {
    ...
    struct list_head devres_head;   /* 托管资源链表头 */
    struct list_head devres_group;  /* 资源组链表头（组管理用） */
    spinlock_t      devres_lock;    /* 两条链表的并发保护锁 */
    ...
};
```

调用 `devm_kzalloc()` 等函数时，内核除分配资源外，还在 `devres_head` 链表上挂一个 `struct devres_node` 节点（drivers/base/devres.c，有删节）：

```c
struct devres_node {
    struct list_head    entry;   /* 挂入 devres_head 的钩子 */
    dr_release_t        release; /* 释放回调，如 devm_kzalloc 对应 devm_kfree */
    const char          *name;   /* 资源名，调试输出用 */
    size_t              size;    /* 节点+资源数据的总大小 */
};

struct devres {
    struct devres_node node;     /* 链上节点 */
    u8 data[];                   /* 资源本体紧跟节点之后分配 */
};
```

资源本体（`data[]`）与节点在同一块内存里。以 `devm_kzalloc()` 为例，其释放回调就是 `devm_kfree()`，释放时按节点里记录的回调逐个调用。

## <span class="blue"> 释放时机：devres_release_all 的两个调用点 [I→E]

自动释放不是"内核什么时候想起来就清一下"，而是挂在两个固定的失败/退出路径上。

**时机一：probe 返回错误**。驱动核心在 probe 失败路径调用清理（drivers/base/dd.c，有删节）：

```c
static int really_probe(struct device *dev, struct device_driver *drv)
{
    ...
probe_failed:
    if (dev->bus)
        blocking_notifier_call_chain(&dev->bus->p->bus_notifier,
                                     BUS_NOTIFY_DRIVER_NOT_BOUND, dev);
pinctrl_bind_failed:
    device_links_no_driver(dev);
    devres_release_all(dev);          /* probe 失败：全量释放托管资源 */
    arch_teardown_dma_ops(dev);
    ...
}
```

`really_probe()` 与 11.3.2 的调用链是同一个函数——probe 中途在任意一步失败，走到 `probe_failed` 标签时，`devres_release_all()` 把已挂接的托管资源全部释放，驱动一行清理代码都不用写。

**时机二：设备与驱动解绑**。remove 路径的收尾同样是它（drivers/base/dd.c，有删节）：

```c
static void __device_release_driver(struct device *dev, struct device *parent)
{
    ...
    if (dev->driver && dev->driver->remove)
        dev->driver->remove(dev);     /* 先调驱动的 remove() */
    ...
    devres_release_all(dev);          /* remove 之后：全量释放托管资源 */
    ...
}
```

注意顺序：先执行驱动自己的 `remove()`，再做 devres 全量清理。驱动的 `remove()` 里还能安全使用托管资源（时钟、映射、中断都还在），`remove()` 返回后才轮到内核兜底释放。

## <span class="blue"> LIFO 释放顺序的成因 [I→E]

释放顺序与申请顺序**相反**（后进先出）。这不是风格选择，而是实现方式直接导出的结果（drivers/base/devres.c，有删节）：

```c
static void add_dr(struct device *dev, struct devres_node *node)
{
    devres_log(dev, node, "ADD");
    list_add_tail(&node->entry, &dev->devres_head);  /* 追加到链表尾部 */
}

void devres_release_all(struct device *dev)
{
    ...
    /* Looks like an uninitialized device structure */
    if (WARN_ON(list_empty(&dev->devres_head)))
        return;
    ...
    list_for_each_entry_safe_reverse(dr, tmp, &dev->devres_head, entry) {
        dr->node.release(dev, dr->data);            /* 逆序遍历：尾部先释放 */
        ...
    }
    ...
}
```

新资源 `list_add_tail()` 挂到尾部，释放时 `list_for_each_entry_safe_reverse()` 从尾部开始逆序回调——先进链表的后释放，后进链表的先释放，LIFO 由此而来。

这个顺序恰好满足资源间的依赖关系：probe 里通常先申请时钟、再做寄存器映射、最后注册中断；清理时中断先摘、映射后撤、时钟最后关，依赖链条不倒挂。驱动的申请顺序写对了，释放顺序自动就是对的。

> ⚠️ 自动释放运行在进程上下文（probe 失败清理路径、remove 路径），不提供"立即释放"语义。需要精确控制释放时序的场景（如中断处理中的缓冲区轮换），不应依赖这套机制。

## <span class="blue"> 常用 devm 函数对照表 [I→E]

规律：传统函数名前加 `devm_`，第一个参数多一个 `struct device *`，内核用它找到对应的托管链表。

| devm 版本（自动释放） | 传统版本（手动配对） | 用途 |
|----------------------|---------------------|------|
| `devm_kzalloc()` | `kzalloc()` / `kfree()` | 设备私有内存 |
| `devm_ioremap_resource()` | `request_mem_region()` + `ioremap()` / `iounmap()` | IO 内存映射 |
| `devm_request_irq()` | `request_irq()` / `free_irq()` | 中断申请 |
| `devm_clk_get()` | `clk_get()` / `clk_put()` | 时钟引用（不含 enable/disable） |
| `devm_regulator_get()` | `regulator_get()` / `regulator_put()` | 电源引用 |
| `devm_gpiod_get()` 等 | `gpio_request()` / `gpio_free()` | GPIO |
| `devm_dma_alloc_coherent()` | `dma_alloc_coherent()` / `dma_free_coherent()` | 一致性 DMA 内存 |

devm 风格的 probe，整段没有一行释放代码：

```c
static int my_probe(struct platform_device *pdev)
{
    struct my_priv *priv;
    int irq, ret;

    priv = devm_kzalloc(&pdev->dev, sizeof(*priv), GFP_KERNEL);  /* 私有内存，挂托管链表 */
    if (!priv)
        return -ENOMEM;

    priv->base = devm_ioremap_resource(&pdev->dev,
                platform_get_resource(pdev, IORESOURCE_MEM, 0)); /* 申请内存区+映射，一体完成 */
    if (IS_ERR(priv->base))
        return PTR_ERR(priv->base);

    irq = platform_get_irq(pdev, 0);   /* 从 resource 取中断号 */
    if (irq < 0)
        return irq;

    priv->clk = devm_clk_get(&pdev->dev, NULL);  /* 取时钟引用，挂托管链表 */
    if (IS_ERR(priv->clk))
        return PTR_ERR(priv->clk);

    ret = devm_request_irq(&pdev->dev, irq, my_handler, 0, "my_drv", priv);  /* 注册中断，挂托管链表 */
    if (ret)
        return ret;

    platform_set_drvdata(pdev, priv);  /* 私有数据挂到 device 上，供 remove 取回 */
    return 0;
}
```

## <span class="blue"> devm 管不到的三类边界 [I→E]

1. **生命周期必须等于 device 的生命周期**。要在两个设备间共享的 DMA buffer、remove 之后仍需保留的数据，不能用 devm 托管——解绑那一刻内核会无差别释放。
2. **运行时状态切换不托管**。`clk_prepare_enable()`、`regulator_enable()` 这类 enable/disable 配对是状态切换，不是一次性资源申请，devres 不管，remove 里仍要手动 `clk_disable_unprepare()`。新版本内核补了两个例外手段：`devm_clk_get_enabled()`（取时钟并使能一体托管）与 `devm_add_action_or_reset()`（把任意清理动作挂成托管回调）。
3. **非托管子系统资源不托管**。`alloc_chrdev_region()`、`cdev_add()`、`device_create()` 等属于字符设备子系统的注册动作，不属于 devres 体系，失败和 remove 时仍需手动反注册（11.3.3 的完整示例展示了托管与非托管资源共存的清理写法）。

> 💡 需要提前释放个别托管资源时，内核提供配套函数（`devm_kfree()`、`devm_free_irq()`、`devm_iounmap()`），把资源从托管链表摘除并立即释放。常规驱动很少用到；决定能否用 devm 的判据是第一条——生命周期是否与 device 一致。

## <span class="blue"> 传统写法与 devm 写法对比 [E]

同一个 GPIO 按键驱动，先看传统的手动配对写法：

```c
/* 传统写法：每种资源一层清理标签 */
static int key_probe(struct platform_device *pdev)
{
    struct key_priv *priv;
    int ret, irq;

    priv = kzalloc(sizeof(*priv), GFP_KERNEL);   /* 普通分配，失败路径要手动 kfree */
    if (!priv)
        return -ENOMEM;

    irq = platform_get_irq(pdev, 0);
    if (irq < 0) {
        ret = irq;
        goto err_free_priv;      /* 还没申请别的资源，直接释放内存 */
    }

    ret = request_irq(irq, key_handler, IRQF_TRIGGER_FALLING, "key", priv);
    if (ret)
        goto err_free_priv;      /* 中断没申请成，同上 */

    priv->clk = clk_get(&pdev->dev, NULL);       /* 手动版时钟引用 */
    if (IS_ERR(priv->clk)) {
        ret = PTR_ERR(priv->clk);
        goto err_free_irq;       /* 中断已注册，先撤中断再释放内存 */
    }

    ret = clk_prepare_enable(priv->clk);
    if (ret)
        goto err_put_clk;        /* 时钟引用已拿到，先 put 再撤中断 */

    platform_set_drvdata(pdev, priv);
    return 0;

err_put_clk:
    clk_put(priv->clk);
err_free_irq:
    free_irq(irq, priv);
err_free_priv:
    kfree(priv);
    return ret;
}
```

四种资源对应四层清理标签，清理顺序必须严格反序；中途新增一种资源，整条 `goto` 链都要重排，漏一处就是泄漏。

devm 写法：

```c
static int key_probe(struct platform_device *pdev)
{
    struct key_priv *priv;
    int ret, irq;

    priv = devm_kzalloc(&pdev->dev, sizeof(*priv), GFP_KERNEL);  /* 挂托管链表 */
    if (!priv)
        return -ENOMEM;

    irq = platform_get_irq(pdev, 0);
    if (irq < 0)
        return irq;              /* 直接返回：内存由 devres_release_all 释放 */

    ret = devm_request_irq(&pdev->dev, irq, key_handler,
                           IRQF_TRIGGER_FALLING, "key", priv);   /* 挂托管链表 */
    if (ret)
        return ret;              /* 直接返回：内存+中断自动释放 */

    priv->clk = devm_clk_get(&pdev->dev, NULL);                  /* 挂托管链表 */
    if (IS_ERR(priv->clk))
        return PTR_ERR(priv->clk);  /* 直接返回 */

    /* enable 属于状态切换，不在托管范围 */
    ret = clk_prepare_enable(priv->clk);
    if (ret)
        return ret;              /* clk 引用自动 put，但 enable 要 remove 里配对 */

    platform_set_drvdata(pdev, priv);
    return 0;
}
```

错误路径收缩为逐级 `return`：probe 在任一位置失败，走到 `really_probe()` 的 `probe_failed` 标签时，`devres_release_all()` 统一兜底。唯一残留的手动动作是 remove 里的 `clk_disable_unprepare()`——状态切换不托管，这正是上一节"三类边界"的第二条。

> ⚠️ devm 消除的是"资源申请与释放"层面的清理代码，不消除逻辑错误。混用托管与非托管资源时（注册子系统之后），非托管部分仍要按反序手动回收。

## <span class="blue"> 完整调用链：从 devm_kzalloc 到统一释放 [E]

```
devm_kzalloc(&pdev->dev, ...)
    └─ drivers/base/devres.c: devres_alloc_node()
           分配 devres_node + 资源本体（同一块内存）
           release 回调 = devm_kfree
    └─ add_dr()
           list_add_tail(&node->entry, &dev->devres_head)   ← 挂链表尾部
           （随后 devm_ioremap_resource / devm_clk_get / devm_request_irq 依次追加）

probe 返回错误
    └─ drivers/base/dd.c: really_probe() → probe_failed:
           devres_release_all(dev)
           list_for_each_entry_safe_reverse()               ← 从尾部逆序
           逐个 node.release(dev, node->data)               ← LIFO 全量释放

或 remove 路径
    └─ drivers/base/dd.c: __device_release_driver()
           dev->driver->remove(dev)                         ← 驱动先做自己的事
           devres_release_all(dev)                          ← 内核再兜底
```

## <span class="blue"> 动手练习

1. **查结构**。在 Linux 6.6 源码 include/linux/device.h 中找到 `struct device` 的 `devres_head` 字段，再到 drivers/base/devres.c 找到 `struct devres_node`，确认释放回调字段名是 `release`。
2. **验顺序**。在 drivers/base/devres.c 中找到 `add_dr()` 与 `devres_release_all()`，确认前者用 `list_add_tail()`、后者用 `list_for_each_entry_safe_reverse()`，说明 LIFO 顺序由此两段代码共同决定。
3. **找调用点**。在 drivers/base/dd.c 中 grep `devres_release_all`，确认它在 `really_probe()` 失败路径和 `__device_release_driver()` 中各出现一次，并确认 remove 路径中它排在 `dev->driver->remove(dev)` 之后。

## <span class="blue"> 本节总结

| 概念 | 核心要点 | 源码佐证（Linux 6.6） |
|------|---------|----------------------|
| devres 数据结构 | `devres_node` 记录释放回调，资源本体与节点同块分配 | include/linux/device.h；drivers/base/devres.c |
| 释放时机一 | probe 失败时 `really_probe()` 走 `probe_failed` 全量清理 | drivers/base/dd.c |
| 释放时机二 | remove 执行后 `__device_release_driver()` 全量清理 | drivers/base/dd.c |
| 释放顺序 | 尾插+逆序遍历导出 LIFO，依赖不倒挂 | drivers/base/devres.c |
| 命名规律 | 传统函数名前加 `devm_`，首参为 `struct device *` | 对照 `kzalloc()` 与 `devm_kzalloc()` 原型 |
| 三类边界 | 生命周期不一致、enable 类状态切换、非托管子系统资源 | 数一下 probe 里还剩哪些手动配对 |
