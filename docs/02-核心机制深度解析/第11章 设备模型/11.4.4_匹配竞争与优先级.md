# 11.4.4 匹配竞争与优先级

> 所属：第11章 设备模型 > 11.4 设备树匹配机制
> 
> 难度：[E] | 预计阅读时间：12分钟

## <span class="blue"> 本节导读

11.4.1 的评分规则发生在单个驱动的匹配表内部。本节处理表外的情况：同一设备的 compatible 被多个驱动的表同时命中时，内核让谁绑定。这类问题会真实地表现为"硬件基本能用但性能不对、个别寄存器操作异常"——设备被通用驱动接管，专用驱动一直没机会上场，而且内核默认不打任何日志。<BR>
本节覆盖：内核跨驱动仲裁的真实规则（先注册先绑定，无评分）、驱动注册顺序的决定因素、绑定关系的排查手段、细化 compatible / 合并驱动 / driver_override 三种规避策略。

---

## <span class="blue"> 仲裁规则：先注册先绑定，没有跨驱动评分 [E]

竞争场景的典型形态：设备节点声明 `compatible = "myvendor,my-device-v2", "myvendor,my-device"`，系统里同时存在专用驱动 B（认领 `"myvendor,my-device-v2"`）和通用驱动 A（认领 `"myvendor,my-device"`）。两个驱动都能匹配这个设备。

需要先纠正一个流传较广的说法：内核会对多个候选驱动按"匹配精度"打分，精确匹配优先。这个说法不成立。跨驱动仲裁的真实规则只有一条：

**设备注册（或驱动注册）时，总线遍历另一侧的链表，第一个 match 成功且 probe 成功的驱动完成绑定；此后设备已有归属，后续注册的驱动即使也能 match，绑定也不会转移。**

也就是说，11.4.1 的评分制只解决"单个驱动内部用哪个条目"，驱动之间纯粹是先到先得的竞争。所谓"OF 匹配优先于名字匹配"的描述，对象是 `platform_match()` 内部对**单个驱动**的检查顺序，不是驱动之间的裁决依据：

```c
/* platform_match() 检查顺序（drivers/base/platform.c，简化） */
static int platform_match(struct device *dev, struct device_driver *drv)
{
    struct platform_device *pdev = to_platform_device(dev);

    /* 0. driver_override 非空时只做字符串比较，其余机制全部旁路 */
    if (pdev->driver_override)
        return !strcmp(pdev->driver_override, drv->name);

    /* 1. OF 匹配 → 2. ACPI 匹配 → 3. id_table → 4. 名字匹配 */
    if (of_driver_match_device(dev, drv))
        return 1;
    ...
}
```

这张顺序表决定的是"一个驱动凭什么认领设备"，决定不了"两个驱动谁认领"。

### 后来的驱动安静地走开

设备已绑定后，后续驱动的 attach 流程发现设备有主就直接跳过，**默认没有任何日志**。竞争失败的驱动不会报错、不会重试、不会在 dmesg 里留痕迹——这是匹配竞争问题难排查的根本原因：所有当事方都"工作正常"，只有硬件行为不对。

### "先注册"由什么决定

注册顺序不是随机的，但也很少有文档保证：

- **内置驱动**：按 initcall 级别先后执行（`module_platform_driver()` 展开为 `device_initcall`），同级别按内核链接顺序，链接顺序由 Makefile 中 obj-y 的排列决定
- **模块驱动**：按加载顺序；自动加载场景下取决于 udev 处理 uevent 的顺序和 modprobe 解析 modules.alias 的顺序

依赖链接顺序或加载顺序来保证"专用驱动先到"是脆弱的：换一个内核配置、调整一次模块安装顺序，竞争结果就可能翻转。确定性方案见下文三种策略。

## <span class="blue"> 排查：确认设备实际绑定的驱动 [E]

怀疑竞争绑定时，先看事实再看日志：

```bash
# 设备当前绑定的驱动（driver 是指向驱动目录的符号链接）
ls -l /sys/bus/platform/devices/43c00000.my_device/driver

# uevent 文件同时给出绑定结果与匹配凭据
cat /sys/bus/platform/devices/43c00000.my_device/uevent
DRIVER=my_driver_a
OF_COMPATIBLE_0=myvendor,my-device-v2
OF_COMPATIBLE_1=myvendor,my-device
MODALIAS=of:Nmy_deviceT<NULL>Cmyvendor,my-device-v2Cmyvendor,my-device
```

`OF_COMPATIBLE_*` 列出节点全部 compatible，`DRIVER` 给出实际绑定者。两者对照，如果节点声明了专用串而绑定的是通用驱动，竞争失败即坐实。需要观察绑定过程本身时，用动态调试打开总线核心日志：

```bash
echo 'file drivers/base/dd.c +p' > /sys/kernel/debug/dynamic_debug/control
echo 'file drivers/base/platform.c +p' > /sys/kernel/debug/dynamic_debug/control
```

> ⚠️ 硬件"基本能用"恰恰是竞争绑定的典型表象：通用驱动走兼容路径，基本功能正常，专用驱动才有的优化路径和扩展寄存器支持全部缺失。性能数据不达预期时，绑定关系应列入排查清单。

## <span class="blue"> 策略一：把 compatible 写全写细 [E]

设备树侧的基础动作是按"从特定到通用"写全列表：

```dts
my_device: my_device@43c00000 {
    compatible = "myvendor,my-device-v2", "myvendor,my-device";
    reg = <0x43c00000 0x1000>;
};
```

这个动作解决的是**正确性与可回退**，不是仲裁本身：

- 单驱动多变体的场景（见策略二），评分机制凭首项选中正确的变体配置
- 专用驱动缺席时（没编译、没加载），通用驱动仍能通过 fallback 串匹配，系统保底可用
- 专用驱动若先注册，首项精确命中后绑定，竞争在事实上被避免

它不能解决的：专用驱动与通用驱动同时存在且通用驱动先注册——此时 fallback 串让通用驱动照样命中，设备被先到的通用驱动拿走。要覆盖这种场景，需要策略二从机制上消除竞争，或策略三显式指定。

## <span class="blue"> 策略二：合并驱动，用 .data 区分变体 [E]

两个驱动大部分代码相同、只是寄存器布局或时序参数有差异时，内核社区的主流做法是**不留两个驱动**：合并成一个驱动、一张匹配表，用 `of_device_id` 的 `.data` 字段携带变体信息。`of_device_id` 除了 compatible 字符串还带一个 `void *data` 指针，匹配成功后驱动可以从匹配条目里取回它：

```c
struct mydev_variant {
    const char *name;
    unsigned int fifo_depth;
    unsigned int reg_offset;
};

static const struct mydev_variant v1_info = { "v1", 16, 0x00 };
static const struct mydev_variant v2_info = { "v2", 64, 0x40 };

static const struct of_device_id mydrv_of_match[] = {
    { .compatible = "myvendor,my-device-v2", .data = &v2_info },
    { .compatible = "myvendor,my-device",    .data = &v1_info },
    { }
};
MODULE_DEVICE_TABLE(of, mydrv_of_match);

static int mydrv_probe(struct platform_device *pdev)
{
    const struct of_device_id *match =
        of_match_device(mydrv_of_match, &pdev->dev);
    const struct mydev_variant *variant = match->data;
    /* 按 variant 配置寄存器偏移、FIFO 深度等 */
}
```

一个驱动一张表，设备永远只可能绑到这一个驱动，竞争从机制上消失；评分规则（11.4.1）保证节点首项对应的变体被选中。主线内核里同族硬件普遍采用这种组织——以 8250 串口子系统的 `8250_of.c` 为例，一张 `of_platform_serial_table` 里并列 `ns8250`、`ns16450`、`ns16550a`、`ns16750` 等兼容性递进的字符串，每个条目用 `.data` 标注端口类型（PORT_8250、PORT_16550A……），而不是为每个变体拆一个驱动互相竞争。

## <span class="blue"> 策略三：driver_override 显式指定 [E]

两个驱动必须并存、又必须让指定的那一个绑定时，用 platform 设备的 `driver_override` 属性。它经 sysfs 暴露，非空时 `platform_match()` 只做驱动名字符串比较，OF、ACPI、id_table 匹配全部旁路：

```bash
# 强制设备只接受 my_driver_b 绑定
echo my_driver_b > /sys/bus/platform/devices/43c00000.my_device/driver_override

# 触发重新匹配（设备已绑定其它驱动时先 unbind）
echo 43c00000.my_device > /sys/bus/platform/devices/43c00000.my_device/driver/unbind
echo 43c00000.my_device > /sys/bus/platform/drivers_probe
```

这是优先级最高、行为最确定的手段，常用于调试期验证"换驱动后问题是否消失"，也可固化为产品配置（由启动脚本或 udev 规则写入）。代价是绕过了设备树的声明式匹配，override 写错驱动名时设备将拒绝一切绑定，需要与部署文档一起管理。

| 策略 | 适用场景 | 确定性 | 维护成本 |
|------|---------|--------|---------|
| 细化 compatible | 一切场景的基础动作；保证可回退 | 不解决跨驱动竞争 | 低 |
| 合并驱动 + .data | 变体差异小、代码可共享 | 机制上消除竞争 | 中（一次性重构） |
| driver_override | 必须并存且需指定绑定 | 最高 | 低，但需固化到部署 |

> 💡 判断该合并还是该分立，看代码差异占比：变体间差异集中在寄存器偏移、参数表这类"数据"上，合并几乎总是更优；差异体现在中断处理流程、DMA 机制这类"逻辑"上，保持分立、靠 driver_override 或注册顺序控制绑定。

## <span class="blue"> 本节总结

| 概念 | 核心要点 | 自查操作 |
|------|---------|---------|
| 跨驱动仲裁 | 先注册先绑定，无评分；后来的驱动静默退出 | `ls -l .../devices/<dev>/driver` |
| platform_match 顺序 | driver_override → OF → ACPI → id_table → 名字，仅针对单个驱动 | 不把它当成跨驱动优先级 |
| 注册顺序 | 内置驱动看 initcall 级别与链接顺序，模块看加载顺序 | 不依赖顺序做产品化设计 |
| 合并驱动 .data | 一驱动一表一变体，机制上消除竞争 | `of_match_device()` 取 `.data` |
| driver_override | 最高优先级，旁路全部匹配机制 | `cat .../driver_override` 确认取值 |
