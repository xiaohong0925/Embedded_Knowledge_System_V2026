# 11.2.4 kobject/kset与sysfs映射

> 所属：第11章 设备模型 > 11.2 总线-设备-驱动模型
> 
> 难度：[I→E] | 预计阅读时间：18分钟

## <span class="blue"> 本节导读

「设备从设备树节点到 probe 成功」之后还有一环：设备的状态与拓扑要暴露给用户空间，出口就是 `/sys`。<BR>
`/sys` 下的目录和文件不是手工创建的，而是内核中 kobject 树的自动投影——前面三节出现的 `bus_type`、`device`、`device_driver`，全部建立在 kobject 之上。这套基础设施包含两条线：对象树到 `/sys` 的**映射**，和对象状态变化到用户空间的**事件广播**（uevent 内核侧）。本节作为 11.2 的收尾，把这两条线讲透。<BR>
本节覆盖：kobject 的字段与生命周期、kobj_type 与 release 语义、kset 的归类与 uevent 过滤、sysfs 映射机制、`kobject_init_and_add()` 代码走读、uevent 的内核侧源码链（用户空间段见 11.5.2）。

## <span class="blue"> 本节定位 [I]

前三节讲了 bus、device、driver 怎么配对（match→probe 的调用链），本节回答更底层的四个问题：

- 内核怎么给设备起名字？（`/sys/devices/platform/ff000000.serial` 从哪来？）
- 内核怎么知道「这个设备挂在 platform 总线下」？（`/sys/bus/platform/devices/` 的目录层次从哪来？）
- 驱动卸载时，内存怎么安全释放？（直接 `kfree()` 行不行？）
- 设备插入时，内核怎么通知用户空间「去 `/dev` 下创建设备节点」？（uevent 从哪发出来的？）

这些都不是 `struct device` 自己能解决的。`struct device` 里只是**内嵌**了一个 `struct kobject`，「名字、层次、生命周期、事件通知」这四项能力全部由 kobject 提供。


11.2.2 提到 `struct device` 里内嵌的 `struct kobject kobj` 字段，也在代码导读中展示了 `device_add()` 发出的 uevent（core.c:3605）；11.2.3 的 `really_probe()` 另发 `KOBJ_BIND`。本节把这两处伏笔展开：`device_add()` 内部调用 `kobject_add()` 才有了 `/sys/devices/...` 目录，调用 `kobject_uevent()` 才有了用户空间的设备节点自动创建。

## <span class="blue"> kobject：设备模型对象的公共基座 [I]

### 每个 /sys 目录背后都有一个 kobject

kobject 是内核为「需要名字、需要层次关系、需要引用计数」的对象抽象出的基础结构体。<br>
`struct device`、`struct device_driver` 等都内嵌一个 kobject，从而获得统一的生命周期管理和 sysfs 入口。

```bash
ls /sys/
block  bus  class  dev  devices  firmware  fs  kernel  module  power
```

这些顶层目录不是 `mkdir` 创建的，每一个都对应内核里的一个 kobject；目录的嵌套关系对应 kobject 的父子关系，目录里的普通文件对应 kobject 的属性。

### 关键字段

```c
/* 精简示意：理解映射机制所需的核心字段 */
struct kobject {
    const char          *name;     /* 对象名，即 sysfs 目录名 */
    struct kobject      *parent;   /* 父对象，决定目录层级 */
    struct kset         *kset;     /* 所属集合 */
    struct kobj_type    *ktype;    /* 类型描述：release 回调与默认属性 */
    struct list_head     entry;    /* 挂入 kset 链表的节点 */
    struct kref          kref;     /* 引用计数 */
};
```

| 字段 | 作用 | 映射到 sysfs 的什么 |
|------|------|--------------------|
| `name` | 对象名称 | 目录名 |
| `parent` | 父 kobject | 父目录 |
| `ktype` | 属性文件的读写操作与默认属性 | 目录里的 `uevent` 等文件 |
| `kset` | 所属集合 | 父指针缺省时归入集合目录 |
| `kref` | 引用计数 | 不直接映射，决定对象何时销毁 |

`struct kobj_type` 是 kobject 的「类型说明」：同一类 kobject 共享一份 kobj_type，其中最关键的是 `release()` 回调（引用计数归零时执行真正的内存释放）和默认属性组（决定这类对象在 sysfs 中自带哪些文件）。

### 生命周期与释放语义

kobject 的使用分四步：`kobject_init()`（lib/kobject.c:331）初始化、`kobject_add()`（lib/kobject.c:408）注册进层次并出现在 sysfs、使用中用 `kobject_get()`/`kobject_put()` 增减引用计数、计数归零时由内核调用 `ktype->release()` 完成释放。

释放语义有一个硬约束：**kobject 占用的内存只能在 `release()` 里释放**。只要还有引用存在，就可能有代码正在访问这个对象，直接 `kfree()` 会留下悬垂指针。这也是 kobject 几乎总是内嵌在更大结构体中的原因——`release()` 里通过 `container_of()` 从 kobject 指针反推出外层结构体，再释放整体。

```c
// include/linux/device.h
struct device {
    struct kobject          kobj;           /* ← 内嵌在这里 */
    struct device           *parent;
    struct bus_type         *bus;
    struct device_driver    *driver;
    void                    *platform_data;
    struct dev_pm_info      power;
    struct device_node      *of_node;
    // ... 还有很多字段
};
```

> 🔴 kobject 的父指针缺省时有一套回退规则：`parent` 为 NULL 但指定了 `kset`，就挂到该 kset 的目录下；两者都未指定，则直接出现在 `/sys` 根目录，与 `block`、`bus` 平级。设备出现在 `/sys` 中意料之外的位置，通常就是 `parent` 设置错误，排查时先核对 parent 与 kset 的赋值。

## <span class="blue"> kset：归类与 uevent 事件出口 [I]

**kset 是同类型 kobject 的集合**，自身内嵌一个 kobject，所以在 sysfs 中也是一个目录。它承担两个职责：

1. **归类**：把同类 kobject 组织在一起。`devices_kset` 对应 `/sys/devices/`，`bus_kset` 对应 `/sys/bus/`（创建过程见 11.2.2 的代码导读），加入集合即自动出现在对应目录下。
2. **uevent 过滤**：kset 上挂有 `uevent_ops`，决定该类对象的事件是否发送、附加哪些环境变量。

```c
/* 精简示意 */
struct kset {
    struct list_head    list;        /* 集合内所有 kobject 的链表 */
    spinlock_t          list_lock;
    struct kobject      kobj;        /* 内嵌 kobject，代表集合自身 */
    const struct kset_uevent_ops *uevent_ops;  /* uevent 过滤与命名 */
};
```

11.2.3 中 `bus_add_driver()` 把驱动的 kobject 挂到 `bus->p->drivers_kset`，驱动注册后自动出现在 `/sys/bus/platform/drivers/` 下，就是 kset 归类职责的直接体现。

## <span class="blue"> sysfs：对象树的实时投影 [I]

sysfs 是 kobject 树的内存映射文件系统，不占用磁盘空间。映射规则只有两条：

- 每个 kobject 对应一个**目录**，由 `kobject_add()` 自动创建；
- 每个 `struct attribute` 对应目录下一个**文件**，由 ktype 的默认属性组或 `sysfs_create_file()` 创建。

读写这些文件时内核现场执行回调：读文件调用属性的 `show()` 方法生成内容，写文件调用 `store()` 方法处理输入。`/sys` 因此是内核对象状态的实时投影——目录树随对象注册、注销自动增减，不需要任何手工维护。

## <span class="blue"> 代码走读：kobject_init_and_add() [I→E]

先说明这段代码的定位：真实驱动开发中几乎不会手写裸 kobject——`struct device`、`struct device_driver` 注册时，kobject 的创建由 `device_add()`、`driver_register()` 内部代劳。下面这段代码是教学切片，把「kobject 注册 → sysfs 目录诞生」的动作从大函数里孤立出来看。代码创建一个独立的 kobject 并挂到 platform 总线目录下：

```c
struct kobject *my_kobj;
int ret;

my_kobj = kzalloc(sizeof(*my_kobj), GFP_KERNEL);
if (!my_kobj)
    return -ENOMEM;

ret = kobject_init_and_add(my_kobj, &my_ktype,
                           &platform_bus.dev.kobj, "my_device");
if (ret) {
    kobject_put(my_kobj);   /* 失败也必须走 put，释放已初始化的内部状态 */
    return ret;
}

kobject_uevent(my_kobj, KOBJ_ADD);   /* 主动向用户空间广播 add 事件 */
```

逐行看：

- `kobject_init_and_add()`（lib/kobject.c:446）一步完成初始化与注册：设置 ktype、parent，把对象挂入层次，并在 sysfs 创建目录 `/sys/devices/platform/my_device/` 及 ktype 声明的默认属性文件。`platform_bus` 是 platform 总线的根设备（`platform_bus_init()` 里注册，见 11.2.2），用它的 kobj 作 parent，新目录就落在 `/sys/devices/platform/` 之下。
- 失败路径必须调用 `kobject_put()` 而不是直接 `kfree()`，原因正是前面说的释放语义：对象的内存由 `ktype->release()` 负责，`put` 触发计数归零才会走到 `release()`。
- 最后一个参数是可变格式化字符串，作为 kobject 的名字，即 sysfs 目录名。

> ⚠️ `kobject_init_and_add()` 内部要分配内存、操作 sysfs 文件系统，可能睡眠，**只能在进程上下文调用**。中断处理函数或持有自旋锁的临界区内调用它，可能直接导致死锁。

## <span class="blue"> uevent：内核侧的事件广播机制 [I→E]

uevent 是内核向用户空间广播设备变更消息的机制：设备添加、移除、绑定驱动时，内核通过 netlink 套接字发出一条包含环境变量的文本消息（`ACTION=add`、`DEVPATH=...`），由用户空间的 udevd 或 mdev 接收处理。本节拆解内核侧的源码链（行号以 v6.6 为准）；消息到达用户空间之后的旅程（udevd 规则匹配、`/dev` 节点创建、ACTION 取值）在 11.5.2 展开，本节不重复。

### 内核侧：uevent 从产生到广播

**第 1 步：触发点 `device_add()`**

```c
// drivers/base/core.c:3506，精简
int device_add(struct device *dev)
{
    // ... 前面做了很多初始化：kobject_add、bus_add_device 等 ...

    // ★ 设备挂到总线、创建 sysfs 目录后，发 uevent 通知用户空间
    kobject_uevent(&dev->kobj, KOBJ_ADD);     // core.c:3605

    // ...
}
```

**第 2 步：`kobject_uevent()` —— 入口**

```c
// lib/kobject_uevent.c:640
int kobject_uevent(struct kobject *kobj, enum kobject_action action)
{
    return kobject_uevent_env(kobj, action, NULL);
}
```

`KOBJ_ADD` 是枚举值，`kobject_actions[action]`（kobject_uevent.c:51）把它转成字符串 `"add"`。同组还有 `KOBJ_REMOVE`（`"remove"`）、`KOBJ_CHANGE`（`"change"`）、`KOBJ_BIND`（`"bind"`）等。

**第 3 步：`kobject_uevent_env()` —— 核心逻辑**

```c
// lib/kobject_uevent.c:457，精简
int kobject_uevent_env(struct kobject *kobj, enum kobject_action action,
                       char *envp_ext[])
{
    struct kobj_uevent_env *env;
    const char *action_string = kobject_actions[action];   // "add"
    const struct kset_uevent_ops *uevent_ops;
    struct kobject *top_kobj;
    struct kset *kset;

    // ★ 1. 向上查找所属 kset：自身没有就沿 parent 链向上找（:481）
    top_kobj = kobj;
    while (!top_kobj->kset && top_kobj->parent)
        top_kobj = top_kobj->parent;
    if (!top_kobj->kset)
        return -ENOENT;                 // 整条链上都没有 kset，不发事件
    kset = top_kobj->kset;

    // ★ 2. uevent_ops->filter()：这类对象要不要发事件（:503）
    uevent_ops = kset->uevent_ops;
    if (uevent_ops && uevent_ops->filter)
        if (!uevent_ops->filter(kobj))
            return -ENOENT;             // 被过滤，不发

    // ★ 3. 添加标准环境变量（:536 起）
    add_uevent_var(env, "ACTION=%s", action_string);   // ACTION=add
    add_uevent_var(env, "DEVPATH=%s", devpath);        // DEVPATH=/devices/platform/...
    add_uevent_var(env, "SUBSYSTEM=%s", subsystem);    // SUBSYSTEM=platform
    // 还有 SEQNUM；字符设备另有 MAJOR、MINOR、DEVNAME

    // ★ 4. uevent_ops->uevent()：追加该类对象特有的环境变量（:556）
    if (uevent_ops && uevent_ops->uevent) {
        retval = uevent_ops->uevent(kobj, env);
        if (retval)
            goto exit;
    }

    // ★ 5. 通过 netlink 广播到用户空间（:593）
#if defined(CONFIG_NET)
    retval = kobject_uevent_net_broadcast(kobj, env, action_string, devpath);
#endif
    ...
}
```

注意两个容易读错的细节：kset 是**沿 parent 链向上查找**的，不是直接取 `kobj->kset`；`filter()` 只拿 kobj 做判断，返回 0 表示事件被丢弃。

**第 4 步：`kobject_uevent_net_broadcast()` —— 真正发出去**

```c
// lib/kobject_uevent.c:381，精简
static int kobject_uevent_net_broadcast(struct kobject *kobj,
                                        struct kobj_uevent_env *env,
                                        const char *action_string,
                                        const char *devpath)
{
    // 把环境变量打包成 skb，对每个网络命名空间：
    //   netlink_broadcast(uevent_sock, skb, 0, 1, GFP_KERNEL);
    // 末参 1 是 netlink 组号，udevd 监听的正是这个组
    ...
}
```

`netlink_broadcast()` 把消息发给所有监听该 netlink 组的用户空间进程。没有监听者时广播静默丢弃，内核不缓存事件——这就是开机早期（udevd 启动前）的 uevent 会丢失、需要 coldplug 机制补发的原因（coldplug 见 5.4.3）。

### 亲手触发一次：重放 uevent

```bash
# 重放 add 事件（不插拔硬件，让内核重走一遍 uevent 流程）
echo add > /sys/bus/usb/devices/1-1/uevent
```

`echo add > .../uevent` 能重放，是因为 `uevent` 是 kobject 的 sysfs 属性文件：写入 `"add"` 触发其 `store()` 方法，内部按字符串反查 `kobject_actions[]`（kobject_uevent.c:85）后调用 `kobject_uevent(kobj, KOBJ_ADD)`。观察内核广播与 udevd 处理结果的完整实验（`udevadm monitor --kernel --udev`）在 11.5.2，与本节机制互为验证。

### 一句话串起来（内核侧）

`device_add()` → `kobject_uevent(KOBJ_ADD)` → `kobject_uevent_env()` → 沿 parent 链找 kset → `filter()` 过滤 → 加标准环境变量 → `uevent_ops->uevent()` 追加特有变量 → `kobject_uevent_net_broadcast()` 广播。消息到达用户空间之后——udevd 收包、规则匹配、`/dev` 节点创建——接 11.5.2。

## <span class="blue"> 本节总结

| 概念 | 核心要点 | 自查操作 |
|------|---------|---------|
| kobject | 设备模型对象的公共基座：名字、层次、引用计数 | `ls /sys/devices/` 对照目录理解层次 |
| kobj_type | 类型说明：release 回调 + 默认属性组 | 理解释放必须走 release 的原因 |
| kset | kobject 集合：归类 + uevent 过滤 | `ls /sys/bus/` 与 `bus_kset` 对应 |
| sysfs 映射 | kobject 树自动投影为 /sys 目录树，不占磁盘 | 读写属性文件验证 show/store |
| uevent | kobject 状态变化经 netlink 广播（内核侧机制） | `echo add > .../uevent` 重放事件；用户空间段见 11.5.2 |
