# 11.2.4 kobject/kset与sysfs映射

## <span class="blue"> 本节导读

「设备从设备树节点到 probe 成功」之后还有一环：设备的状态与拓扑要暴露给用户空间，出口就是 `/sys`。<BR>
`/sys` 下的目录和文件不是手工创建的，而是内核中 kobject 树的自动投影——前面三节出现的 `bus_type`、`device`、`device_driver`，全部建立在 kobject 之上。本节作为 11.2 的收尾，把这套基础设施讲透。<BR>
本节覆盖：kobject 的字段与生命周期、kobj_type 与 release 语义、kset 的归类与 uevent 过滤、sysfs 映射机制、`kobject_init_and_add()` 代码走读、uevent 从内核到 `/dev` 节点的完整源码链。

## <span class="blue"> 引言 [I]

### 一句话定位

前面三节讲了 **bus、device、driver 怎么配对**（match→probe 的调用链）。这节回答一个更底层的问题：**这些对象在内核里是怎么"活"起来的？**

- 内核怎么给设备起名字？（`/sys/devices/platform/ff000000.serial` 从哪来？）
- 内核怎么知道"这个设备挂在 platform 总线下"？（`/sys/bus/platform/devices/` 的目录层次从哪来？）
- 设备插入时，内核怎么通知用户空间"去 `/dev` 下给我创个节点"？（uevent 从哪发出来的？）
- 驱动卸载时，内存怎么安全释放？（直接 `kfree()` 行不行？）

这些都不是 `struct device` 自己能解决的。`struct device` 里只是**内嵌**了一个 `struct kobject`，所有"名字、层次、生命周期、事件通知"的能力，都是 `kobject` 提供的。

> **不讲 kobject，前面的 bus/device/driver 就是"没有身份证的幽灵"**——能干活，但内核不知道怎么管理它们，用户空间也看不到它们。

## <span class="blue"> 用户籍管理来理解这节 [I]

内核管理设备、驱动、总线，很像一个国家管理公民。把这套逻辑想通了，后面那些抽象概念就都有了落脚点。

### 身份证：kobject

每个公民都有身份证，上面写着名字、父亲是谁。内核里也一样，每个需要被管理的对象（设备、驱动、总线）都要有一张"身份证"，这就是 `struct kobject`。身份证上 `name` 字段就是对象的名字，对应到 `/sys` 下就是一个目录名；`parent` 字段指向父亲，对应到 `/sys` 里就是"这个目录挂在谁的下面"。

身份证上还有个计数器，记录"还有几个人在找我办事"——这就是 `kref` 引用计数。只要还有人拿着这个对象的指针，就不能销毁它。所以你不能直接 `kfree()` 一个 kobject，必须走 `kobject_put()` 让计数归零，内核才会按规矩（`ktype->release()`）来释放。这就像公民的档案不能随意销毁，必须确认无人查阅后，按流程正式注销。

`struct device` 内嵌了一个 `kobject`，所以注册设备时，内核自动知道"这个设备叫什么名字、挂在谁的下面"——身份证一办，户籍系统立刻有记录。

### 身份证类型：kobj_type

身份证不是只有一种。成年人的身份证有"去世处理流程"（`release` 回调），还有一些默认档案内容（`default_attrs`，对应 sysfs 里的默认属性文件）。内核里这叫 `struct kobj_type`，同一类对象共享一份类型说明。比如所有 platform 设备的 kobject 都共享同一个 `kobj_type`，规定了它们释放时要做什么、在 sysfs 里默认带哪些文件。

这里的关键是：**释放必须走流程**。直接 `kfree()` 相当于把公民档案直接烧了，但可能还有人正在查这份档案（引用计数不为零）。`kobject_put()` 才是正规流程：计数归零 → 调用 `release()` → 安全释放。这也是 kobject 几乎总是内嵌在更大结构体（如 `struct device`）里的原因——`release()` 里通过 `container_of()` 从身份证指针反推出整个 `struct device`，再一起释放。

### 户口本：kset

光有身份证还不够，公民得归到户口本里。`devices_kset` 就是"居民户口本"，对应 `/sys/devices/` 这本档案；`bus_kset` 是"公交户口本"，对应 `/sys/bus/`。内核里这叫 `struct kset`，本质是同类型 kobject 的集合，自己也有张身份证（内嵌 kobject），所以在 sysfs 里表现为一个目录。

把公民加入户口本，档案就自动出现在对应的户籍档案室。`bus_add_driver()` 里把驱动的 kobject 挂到 `bus->p->drivers_kset`，驱动注册后自动出现在 `/sys/bus/platform/drivers/` 下——就是这么来的。

户口本还有个功能：过滤广播。kset 上挂着 `uevent_ops`，决定"这个户口本里的公民，出生时要不要发通知、通知叫什么名字"。

### 户籍查询窗口：sysfs

`/sys` 不是真实文件，而是户籍系统的实时投影。你打开 `/sys/devices/platform/my_device/name`，内核现场调用 `show()` 方法生成内容给你看；你往里面写数据，内核调用 `store()` 方法处理。这就像户籍查询窗口的档案不是写在纸上的，而是工作人员根据数据库现场打印出来的。

内核里这叫 `sysfs`，是 `kobject` 树的内存映射文件系统，不占磁盘空间。每个 kobject 对应一个目录，每个 `attribute` 对应一个文件。目录和文件不是 `mkdir`/`touch` 创建的，而是 `kobject_add()` 和 `sysfs_create_file()` 自动生成的。设备模型的状态对用户空间完全透明。

### 新生儿出生通知：uevent

孩子出生了（设备注册了），户籍系统发一条广播："某某家添了个孩子，叫张三，身份证号是..."。居委会（`udev`/`systemd-udevd`）收到后，去给孩子上户口（创建 `/dev` 节点）、办医保（加载模块）、分配房间（设置权限）。

内核里这叫 `kobject_uevent()`，通过 netlink 套接字向用户空间广播事件。事件携带环境变量（`ACTION=add`、`DEVPATH=...` 等）。你插拔 USB 设备时，`/dev/sdb` 的自动创建和删除，源头就是内核里 `device_add()` → `kobject_uevent(KOBJ_ADD)` 这条链。

## <span class="blue"> kobject：设备模型对象的公共基座 [I]

### 每个 /sys 目录背后都有一个 kobject

对应用层工程师来说，kobject 可以先这样理解：**内核为「需要名字、需要层次关系、需要引用计数」的对象抽象出的基础结构体**。<br>
`struct device`、`struct device_driver` 等都内嵌一个 kobject，从而获得统一的生命周期管理和 sysfs 入口。

```bash
ls /sys/
block  bus  class  dev  devices  firmware  fs  kernel  module  power
```

这些顶层目录不是 `mkdir` 创建的，每一个都对应内核里的一个 kobject；目录的嵌套关系对应 kobject 的父子关系，目录里的普通文件对应 kobject 的属性。

> 对应户籍系统：每个 `/sys` 目录就是一个公民的档案袋，名字和层级由身份证（kobject）决定。

### 关键字段

```c
/* 精简示意：理解映射机制所需的核心字段 */
struct kobject {
    const char          *name;     /* 对象名，即 sysfs 目录名 */
    struct kobject      *parent;   /* 父对象，决定目录层级 */
    struct kset         *kset;     /* 所属集合 */
    struct kobj_type    *ktype;    /* 类型描述：release 回调与默认属性 */
    struct list_head     entry;    /* 挂入 kset 链表的节点 */
    struct kref          kref;     /* 引用计数 */
};
```

| 字段 | 作用 | 映射到 sysfs 的什么 |
|------|------|--------------------|
| `name` | 对象名称 | 目录名 |
| `parent` | 父 kobject | 父目录 |
| `ktype` | 属性文件的读写操作与默认属性 | 目录里的 `uevent` 等文件 |
| `kset` | 所属集合 | 父指针缺省时归入集合目录 |
| `kref` | 引用计数 | 不直接映射，决定对象何时销毁 |

`struct kobj_type` 是 kobject 的「类型说明」：同一类 kobject 共享一份 kobj_type，其中最关键的是 `release()` 回调（引用计数归零时执行真正的内存释放）和默认属性组（决定这类对象在 sysfs 中自带哪些文件）。

> 对应户籍系统：`kobj_type` 就是身份证的类型说明，同一类公民（比如"成年人"）共享一份类型说明，规定了"去世处理流程"（release）和"默认档案内容"（属性文件）。

### 生命周期与释放语义

kobject 的使用分四步：`kobject_init()` 初始化、`kobject_add()` 注册进层次并出现在 sysfs、使用中用 `kobject_get()`/`kobject_put()` 增减引用计数、计数归零时由内核调用 `ktype->release()` 完成释放。

释放语义有一个硬约束：**kobject 占用的内存只能在 `release()` 里释放**。因为只要还有引用存在，就可能有代码正在访问这个对象。这也是 kobject 几乎总是内嵌在更大结构体（如 `struct device`）中的原因——`release()` 里通过 `container_of()` 从 kobject 指针反推出外层结构体，再释放整体。

```c
// include/linux/device.h
struct device {
    struct kobject          kobj;           /* ← 内嵌在这里 */
    struct device           *parent;
    struct bus_type         *bus;
    struct device_driver    *driver;
    void                    *platform_data;
    struct dev_pm_info      power;
    struct device_node      *of_node;
    // ... 还有很多字段
};
```

> 对应户籍系统：公民的档案袋（kobject）不能随意销毁，必须确认"还有没有人需要查这份档案"（引用计数）。确认无人使用后，按身份证类型规定的"去世处理流程"（release）正式注销。

> 🔴 kobject 的父指针缺省时有一套回退规则：`parent` 为 NULL 但指定了 `kset`，就挂到该 kset 的目录下；两者都未指定，则直接出现在 `/sys` 根目录，与 `block`、`bus` 平级。设备出现在 `/sys` 中意料之外的位置，通常就是 `parent` 设置错误，排查时先核对 parent 与 kset 的赋值。

## <span class="blue"> kset：归类与 uevent 事件出口 [I]

**kset 是同类型 kobject 的集合**，自身内嵌一个 kobject，所以在 sysfs 中也是一个目录。它承担两个职责：

1. **归类**：把同类 kobject 组织在一起。`devices_kset` 对应 `/sys/devices/`，`bus_kset` 对应 `/sys/bus/`，加入集合即自动出现在对应目录下。
2. **uevent 过滤**：kset 上挂有 `uevent_ops`，决定该类对象的事件是否发送、以什么事件名发送。

uevent 是内核向用户空间广播设备变更消息的机制：设备添加、移除、绑定驱动时，内核通过 netlink 套接字发出一条包含环境变量的文本消息（如 `ACTION=add`、`DEVPATH=...`），由用户空间的 udev 或 systemd-udevd 接收处理。事件的实际发送函数是 `kobject_uevent()`，它会沿 kobject 找到所属 kset，经 `uevent_ops` 过滤后广播。

> 对应户籍系统：kset 就是户口本。`devices_kset` 是"居民户口本"，对应 `/sys/devices/`；`bus_kset` 是"公交户口本"，对应 `/sys/bus/`。把公民加入户口本，档案就自动出现在对应户籍档案室里。

```c
/* 精简示意 */
struct kset {
    struct list_head    list;        /* 集合内所有 kobject 的链表 */
    spinlock_t          list_lock;
    struct kobject      kobj;        /* 内嵌 kobject，代表集合自身 */
    const struct kset_uevent_ops *uevent_ops;  /* uevent 过滤与命名 */
};
```

## <span class="blue"> 注册一个 kobject：代码走读 [I→E]

下面这段代码在内核中创建一个独立的 kobject 并挂到 platform 总线目录下：

```c
struct kobject *my_kobj;
int ret;

my_kobj = kzalloc(sizeof(*my_kobj), GFP_KERNEL);
if (!my_kobj)
    return -ENOMEM;

ret = kobject_init_and_add(my_kobj, &my_ktype,
                           &platform_bus->dev.kobj, "my_device");
if (ret) {
    kobject_put(my_kobj);   /* 失败也必须走 put，释放已初始化的内部状态 */
    return ret;
}

kobject_uevent(my_kobj, KOBJ_ADD);   /* 主动向用户空间广播 add 事件 */
```

逐行看：

- `kobject_init_and_add()` 一步完成初始化与注册：设置 ktype、parent，把对象挂入层次，并在 sysfs 创建目录 `/sys/devices/platform/my_device/` 及 ktype 声明的默认属性文件。
- 失败路径必须调用 `kobject_put()` 而不是直接 `kfree()`，原因正是前面说的释放语义：对象的内存由 `ktype->release()` 负责，`put` 触发计数归零才会走到 `release()`。
- 最后一个参数是可变格式化字符串，作为 kobject 的名字，即 sysfs 目录名。

> ⚠️ `kobject_init_and_add()` 内部要分配内存、操作 sysfs 文件系统，可能睡眠，**只能在进程上下文调用**。中断处理函数或持有自旋锁的临界区内调用它，可能直接导致死锁。

![kobject 树到 sysfs 目录树的映射：sysfs 根 kobject 分出 bus、devices、class 等集合，devices 下 platform kobject 再到具体设备 kobject，ktype 的属性导出为目录中的文件](images/11.2.4-kobject到sysfs映射.png)

映射关系是完全自动的：注册 kobject 就多一个目录，为 ktype 声明一组 `struct attribute` 就多几个可读写的文件。读 sysfs 文件实际是内核调用属性的 `show()` 方法现场生成内容，写文件对应 `store()` 方法——`/sys` 不占磁盘，它是内存对象树的实时投影。

> 对应户籍系统：`kobject_init_and_add()` 就是"给新生儿办身份证并录入户籍系统"。录入后，户籍查询窗口（`/sys`）立刻能看到这个新档案。档案内容不是写在纸上的，而是现场生成的（show/store）。

## <span class="blue"> uevent：从内核事件到 /dev 节点 [I→E]

kobject 状态变化产生 uevent，用户空间接收后完成设备节点创建等动作。下面从源码层面拆解这条链路。

### 内核侧：uevent 从产生到广播

**第 1 步：触发点 `device_add()`**

```c
// drivers/base/core.c
device_add(struct device *dev)
{
    // ... 前面做了很多初始化：kobject_add、bus_add_device、class_add 等 ...

    // ★ 设备挂到总线、创建 sysfs 目录后，发 uevent 通知用户空间
    kobject_uevent(&dev->kobj, KOBJ_ADD);

    // ...
}
```

> 对应户籍系统：孩子出生（设备注册）→ 户籍系统准备发广播通知。

**第 2 步：`kobject_uevent()` —— 入口**

```c
// lib/kobject_uevent.c
int kobject_uevent(struct kobject *kobj, enum kobject_action action)
{
    return kobject_uevent_env(kobj, action, NULL);
}
```

`KOBJ_ADD` 是一个枚举值，`kobject_actions[action]` 会转成字符串 `"add"`。还有 `KOBJ_REMOVE`（`"remove"`）、`KOBJ_CHANGE`（`"change"`）等。

**第 3 步：`kobject_uevent_env()` —— 核心逻辑**

```c
// lib/kobject_uevent.c
int kobject_uevent_env(struct kobject *kobj, enum kobject_action action,
                       char *envp_ext[])
{
    struct kobj_uevent_env *env;
    const char *action_string = kobject_actions[action];  // "add", "remove"...
    struct kset *kset;
    int retval = 0;

    // 分配环境变量缓冲区
    env = kzalloc(sizeof(struct kobj_uevent_env), GFP_KERNEL);

    // ★ 1. 找到这个 kobject 所属的 kset（户口本）
    kset = kobj->kset;
    if (!kset)
        goto exit;   // 没有 kset，不发事件

    // ★ 2. 调用 kset 的 uevent_ops->filter()：这户人家要不要发通知？
    if (kset->uevent_ops && kset->uevent_ops->filter) {
        if (!kset->uevent_ops->filter(kset, kobj)) {
            // filter 返回 0：事件被过滤掉，不发
            retval = -ENOENT;
            goto exit;
        }
    }

    // ★ 3. 调用 kset 的 uevent_ops->uevent()：往通知里加自定义内容
    if (kset->uevent_ops && kset->uevent_ops->uevent) {
        retval = kset->uevent_ops->uevent(kset, kobj, env);
        if (retval)
            goto exit;
    }

    // ★ 4. 添加标准环境变量
    add_uevent_var(env, "ACTION=%s", action_string);     // ACTION=add
    add_uevent_var(env, "DEVPATH=%s", devpath);          // DEVPATH=/devices/platform/...
    add_uevent_var(env, "SUBSYSTEM=%s", subsystem);      // SUBSYSTEM=platform
    // 还会加 SEQNUM、MAJOR、MINOR 等

    // ★ 5. 通过 netlink 广播到用户空间
#if defined(CONFIG_NET)
    uevent_netlink_broadcast(env, action_string, devpath);
#endif

exit:
    kfree(env);
    return retval;
}
```

> 对应户籍系统：找到户口本（kset）→ 确认这户人家要不要发通知（filter）→ 往通知里加备注（uevent_ops->uevent）→ 写标准通知内容（ACTION、DEVPATH、SUBSYSTEM）→ 贴到社区公告栏（netlink 广播）。

**第 4 步：`uevent_netlink_broadcast()` —— 真正发出去**

```c
// lib/kobject_uevent.c
static int uevent_netlink_broadcast(struct kobj_uevent_env *env,
                                    const char *action_string,
                                    const char *devpath)
{
    struct sk_buff *skb;
    struct sock *uevent_sock;

    // 把环境变量打包成 netlink 消息
    skb = alloc_skb(len, GFP_KERNEL);
    // ... 把 env 里的字符串逐个塞进 skb ...

    // ★ 广播到 uevent 这个 netlink 组
    netlink_broadcast(uevent_sock, skb, 0, 1, GFP_KERNEL);
    // 参数 1 是组号，用户空间的 udevd 就加入了这个组

    return 0;
}
```

`netlink_broadcast()` 是内核网络子系统的函数，把消息发给所有监听这个 netlink 组的用户空间进程。

### 用户空间：udevd 怎么收的

udevd（systemd-udevd 或 eudev）启动时会做这件事：

1. 创建一个 netlink socket，加入 "uevent" 这个组
2. 循环 `recvmsg()` 等内核广播
3. 收到消息后解析环境变量（`ACTION=add`, `DEVPATH=...`, `SUBSYSTEM=...`）
4. 根据 `/etc/udev/rules.d/` 里的规则匹配
5. 匹配上了就：`mknod` 创建 `/dev` 节点、`chmod` 设权限、`modprobe` 加载模块

### 在运行中的系统上直接观察这条链路

```bash
# 终端 1：监听内核发出的原始 uevent（KERNEL 行）
$ udevadm monitor --kernel
KERNEL[12345.678] add    /devices/pci0000:00/0000:00:14.0/usb1/1-1 (usb)

# 终端 2：监听 udevd 处理后的结果（UDEV 行）
$ udevadm monitor --udev
UDEV  [12345.679] add    /devices/pci0000:00/0000:00:14.0/usb1/1-1 (usb)
```

注意时间戳：`KERNEL` 是内核发出来的时间，`UDEV` 是 udevd 处理完的时间，两者差几毫秒。

```bash
# 查看某个设备最近一次 add 事件携带的环境变量
$ udevadm info /sys/bus/usb/devices/1-1
P: /devices/pci0000:00/0000:00:14.0/usb1/1-1
E: SUBSYSTEM=usb
E: DEVTYPE=usb_device
E: PRODUCT=1234/5678/100
E: ACTION=add
...

# 重放 add 事件（不需要插拔硬件，内核再走一遍 uevent 流程）
$ echo add > /sys/bus/usb/devices/1-1/uevent
```

> `echo add > .../uevent` 为什么能重放？因为 `uevent` 是 sysfs 的一个属性文件，写 `add` 会触发 `store()` 方法，内部就是调用 `kobject_uevent(kobj, KOBJ_ADD)`。这就是你文档里写的"往它写入 add 可以让内核重放一次该设备的 add 事件"。

### 一句话串起来

`device_add()` → `kobject_uevent(KOBJ_ADD)` → `kobject_uevent_env()` → 找到 kset → `filter()` 过滤 → `uevent_ops->uevent()` 加自定义内容 → `add_uevent_var()` 加标准环境变量 → `netlink_broadcast()` 广播 → udevd `recvmsg()` 收到 → 匹配规则 → `mknod` 创建 `/dev` 节点。

> 对应户籍系统：孩子出生 → 户籍系统发广播 → 居委会收到 → 给孩子上户口（`/dev` 节点）、办医保（加载模块）、分配房间（设置权限）。

## <span class="blue"> 本节总结

| 概念 | 核心要点 | 自查操作 |
|------|---------|---------|
| kobject | 设备模型对象的公共基座：名字、层次、引用计数 | `ls /sys/devices/` 对照目录理解层次 |
| kobj_type | 类型说明：release 回调 + 默认属性组 | 理解释放必须走 release 的原因 |
| kset | kobject 集合：归类 + uevent 过滤 | `ls /sys/bus/` 与 `bus_kset` 对应 |
| sysfs 映射 | kobject 树自动投影为 /sys 目录树，不占磁盘 | 读写属性文件验证 show/store |
| uevent | 内核经 netlink 广播设备变更，udev 接收处理 | `udevadm monitor` 插拔设备观察 |
