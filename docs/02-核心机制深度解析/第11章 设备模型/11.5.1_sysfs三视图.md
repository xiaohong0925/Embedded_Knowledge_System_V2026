# 11.5.1 sysfs三视图

> 所属：第11章 设备模型 > 11.5 sysfs与uevent
> 
> 难度：[I] | 预计阅读时间：12分钟

## <span class="blue"> 本节导读

probe 成功只意味着内核侧完成了设备与驱动的绑定，接下来的主线问题是：用户空间如何看到这些设备、内核如何把设备变化通知出去、`/dev` 节点又是如何出现的。11.5 节按这三步展开，本节解决第一步——观察入口。sysfs 是设备模型在用户空间的投影：一个只存在于内存中的虚拟文件系统，挂载在 `/sys`，每个目录对应一个 kobject，每个普通文件对应对象的一个属性。这套目录看似庞杂，核心入口只有三个。<BR>
本节覆盖：`/sys/bus`、`/sys/class`、`/sys/devices` 三个视图的组织维度与符号链接关系、按排查场景选择视图的方法、一条完整的"总线→功能→拓扑"排查路径。

---

## <span class="blue"> 同一批设备，三个观察入口 [I]

`/sys` 下目录很多，日常打交道最多的是三个。它们不是三份设备清单，而是**同一批设备按三种维度建立的索引**：设备实体只在 `/sys/devices` 下存在一份，`/sys/bus` 和 `/sys/class` 下的条目几乎都是指向实体的符号链接。

| 视图 | 组织维度 | 回答的问题 | 主要使用者 |
|------|---------|-----------|-----------|
| `/sys/bus` | 设备挂在哪条总线上 | 内核认没认这个设备、哪个驱动在管它 | 驱动开发、总线层排查 |
| `/sys/class` | 设备提供什么功能 | 这个功能对用户空间的接口在哪 | 应用程序、脚本 |
| `/sys/devices` | 设备在硬件拓扑中的位置 | 它物理上挂在哪个控制器下面 | 硬件连接、资源排查 |

### /sys/devices：物理拓扑的唯一实体

`/sys/devices` 按真实的硬件连接关系组织，从 SoC、总线控制器一路向下到具体外设，是 sysfs 的骨架：

```text
/sys/devices/
├── platform/          # 平台设备
│   └── soc/
│       └── 2000000.pinctrl/    # 实际的引脚控制器
├── pci0000:00/        # PCIe 根复合体
├── system/            # CPU、内存等系统设备
└── virtual/           # 无物理实体的虚拟设备（如 loopback）
```

### /sys/bus：按总线排队

`/sys/bus` 按总线类型归类，每条总线目录下固定分 `devices/` 和 `drivers/` 两个子目录，分别记录挂在这条总线上的设备和注册在这条总线上的驱动。11.2.3 节的 `match()` 调用链，发生的就是这个维度：

```bash
# 查看 I2C 总线上注册了哪些设备
ls /sys/bus/i2c/devices/
0-0050  0-0068  i2c-0
```

`0-0050` 表示 0 号 I2C 控制器下、从机地址 0x50 的设备。要看某个驱动管着哪些设备，进对应的 `drivers/` 目录即可。

### /sys/class：按功能排队

`/sys/class` 不关心设备接在哪条总线上，只按功能分类。一个 LED 不管是 GPIO 直驱、I2C 扩展芯片还是 PWM 模块驱动的，都归到 `/sys/class/leds/` 下，操作接口是同一个 `brightness` 属性：

```text
/sys/class/
├── leds/              # LED
├── gpio/              # GPIO 控制器
├── net/               # 网络接口
├── input/             # 输入设备
├── rtc/               # 实时时钟
└── ...
```

这是给应用程序准备的视角：控制 LED 亮度只需要找到 `/sys/class/leds/<名字>/brightness`，不需要知道底层是哪种硬件方案。

### 三个视图靠符号链接互通

以 GPIO 直驱的状态灯为例，它在三个视图中的路径：

| 视图 | 路径 |
|------|------|
| bus | `/sys/bus/platform/devices/gpio-leds` |
| class | `/sys/class/leds/status_led` |
| devices | `/sys/devices/platform/gpio-leds/leds/status_led` |

前两条是符号链接，第三条是实体，用 `ls -l` 可以直接看到指向关系：

```bash
ls -l /sys/class/leds/status_led
lrwxrwxrwx ... /sys/class/leds/status_led -> ../../devices/platform/gpio-leds/leds/status_led/
```

三者关系收敛成一张图：

```text
                ┌──────────────────────┐
                │  /sys/devices/...    │
                │  设备实体（唯一）     │
                └──────────┬───────────┘
                           │ 符号链接
              ┌────────────┴────────────┐
              ▼                         ▼
       /sys/bus/...              /sys/class/...
       按总线索引                 按功能索引
       驱动匹配使用               应用操作使用
```

> 🔴 `/sys/bus` 和 `/sys/class` 下大量条目是符号链接。对 `/sys` 做递归复制、磁盘统计等操作时容易跟随链接重复遍历同一份数据，个别情况下还会踩到循环链接。批量处理前先确认操作对象是链接还是实体，需要真实路径时用 `readlink -f` 解析。

> ⚠️ `/sys/class` 下的名字由驱动决定，并非稳定接口。网卡在不同内核版本和发行版上可能是 `eth0` 也可能是 `enp2s0`，脚本里不要硬编码设备名，按 class 目录遍历或借助 udev 符号链接（11.5.3 节）获取稳定别名。

## <span class="blue"> 按排查场景选视图 [I]

三个视图各有分工，排查问题时先想清楚"要问哪一层的问题"：

| 排查场景 | 该看的视图 | 原因 | 常用命令 |
|---------|-----------|------|---------|
| 驱动有没有加载 | `/sys/bus/.../drivers/` | 驱动名出现在对应总线的 drivers 目录即注册成功 | `ls /sys/bus/platform/drivers/` |
| 设备有没有被识别 | `/sys/bus/.../devices/` | 设备名挂在对应总线下即枚举成功 | `ls /sys/bus/i2c/devices/` |
| 应用怎么操作设备 | `/sys/class/.../` | 功能接口集中在这里，与底层总线无关 | `echo 1 > /sys/class/leds/xxx/brightness` |
| 硬件连接对不对 | `/sys/devices/` | 反映 SoC→控制器→外设的真实拓扑 | `ls /sys/devices/platform/soc/` |

### 一条完整的排查路径

以 I2C 触摸屏无响应为例，三个视图依次回答三个层次的问题：

1. **先查 bus**：`ls /sys/bus/i2c/devices/` 里有没有触摸屏的地址条目（如 `1-0038`）。没有，说明内核根本没枚举到设备，问题在设备树配置或硬件连接，应用层查什么都没用
2. **设备树修复后复查 bus**：条目出现，枚举这层通过
3. **再查 class**：`ls /sys/class/input/` 里有没有新增的 `eventN`。有，说明 input 子系统已经把它注册成输入设备，应用层可以用了
4. **最后查 devices**：`cat /sys/devices/platform/soc/<i2c控制器>/i2c-1/1-0038/name`，确认内核识别出的芯片型号与物料一致

四层信息串起来：**bus 回答"内核认没认"，class 回答"能不能用"，devices 回答"物理上挂在哪"**。任何设备类问题都可以先按这个顺序过一遍，再决定深入哪一层。

## <span class="blue"> 本节总结

| 概念 | 核心要点 | 自查操作 |
|------|---------|---------|
| sysfs | 设备模型在用户空间的投影，内存中的虚拟文件系统 | `mount | grep sysfs` |
| `/sys/bus` | 按总线组织，设备与驱动各有一个子目录 | `ls /sys/bus/i2c/devices/` |
| `/sys/class` | 按功能组织，面向应用程序的统一接口 | `ls /sys/class/leds/` |
| `/sys/devices` | 按物理拓扑组织，唯一的设备实体 | `ls /sys/devices/platform/` |
| 三视图关系 | bus 和 class 的条目是指向 devices 实体的符号链接 | `readlink -f /sys/class/xxx/yyy` |
| 排查顺序 | bus 看枚举、class 看功能、devices 看拓扑 | 按场景表选入口 |
