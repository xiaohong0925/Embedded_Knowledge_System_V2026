# 11.5.3 udev规则与实战

> 所属：第11章 设备模型 > 11.5 sysfs与uevent
> 
> 难度：[I] | 预计阅读时间：15分钟

## <span class="blue"> 本节导读

上一节走完 uevent 链路后，udev 规则是整条链上唯一需要亲手维护的部分：udevd 收到事件后做什么，完全由规则文件决定。本节把规则从"照抄别人的片段"变成能自己写、能自己调的配置，并落到嵌入式场景回答一个现实问题——资源紧张的系统上，mdev 够不够用、什么时候必须上 udev。<BR>
本节覆盖：规则文件的位置与加载顺序、匹配键与动作键的语法、udevadm 三个调试子命令、mdev 与 udev 的取舍。

---

## <span class="blue"> 规则文件：两个目录与加载顺序 [I]

规则文件分两处存放，职责不同：

| 目录 | 优先级 | 用途 |
|------|--------|------|
| `/lib/udev/rules.d/` | 低 | 发行版或根文件系统自带的默认规则，软件包升级会覆盖 |
| `/etc/udev/rules.d/` | 高 | 管理员自定义规则，稳定不被升级覆盖 |

三个硬约束：

1. 文件名必须以 `.rules` 结尾，否则直接被忽略
2. 文件名格式为 `数字-描述.rules`，udevd 按数字前缀**升序**处理，自定义规则一般用较大的数字（如 `99-` 开头）保证在默认规则之后执行
3. 同一设备会被多条规则依次处理，后处理的规则里同名键赋值会覆盖先处理的；`+=` 形式的键（如 `SYMLINK+=`）则是叠加

改完规则必须执行 `udevadm control --reload-rules` 让 udevd 重新加载，否则磁盘上的新文件不会生效。

## <span class="blue"> 一条规则的语法：左匹配右赋值 [I]

一条规则是逗号分隔的一串键值表达式，左半段挑设备，右半段定动作：

```text
SUBSYSTEM=="tty", ATTRS{idVendor}=="1a86", ATTRS{idProduct}=="7523", SYMLINK+="ch340", MODE="0666"
```

### 四个运算符不能混

| 符号 | 含义 | 能用的地方 |
|------|------|-----------|
| `==` | 匹配比较：是不是等于 | 匹配条件 |
| `!=` | 不匹配 | 匹配条件 |
| `=` | 赋值：设置成 | 执行动作 |
| `+=` | 追加赋值：在已有值上再加一项 | 执行动作 |

把 `SUBSYSTEM=="tty"` 误写成 `SUBSYSTEM="tty"`，语义从"筛选 tty 子系统的设备"变成"给 SUBSYSTEM 赋值"，规则直接失效或报错。`SYMLINK=` 与 `SYMLINK+=` 的区别同样实际：前者清掉之前规则建的所有符号链接再设置，后者在已有基础上追加，需要多个别名时必须用 `+=`。

### 常用匹配键

| 键 | 匹配目标 | 示例 |
|----|---------|------|
| `KERNEL` | 内核设备名 | `KERNEL=="sd*"` |
| `SUBSYSTEM` | 子系统名 | `SUBSYSTEM=="usb"` |
| `ATTR{file}` | 本设备 sysfs 属性值 | `ATTR{removable}=="1"` |
| `ATTRS{file}` | 沿父链向上找属性 | `ATTRS{idVendor}=="1a86"` |
| `ENV{key}` | uevent 环境变量 | `ENV{DEVTYPE}=="partition"` |
| `ACTION` | 事件类型 | `ACTION=="add"` |

`ATTR` 与 `ATTRS` 的区别高频踩坑：`ATTR` 只看设备自身目录下的属性文件，`ATTRS` 沿 sysfs 父链逐级向上找。USB 转串口这类设备，`idVendor`/`idProduct` 在父级 USB 设备目录里，必须用 `ATTRS`。

### 常用动作键

| 键 | 作用 | 示例 |
|----|------|------|
| `SYMLINK+=` | 追加符号链接 | `SYMLINK+="ch340"` |
| `MODE=` | 设备节点权限 | `MODE="0660"` |
| `OWNER=` / `GROUP=` | 属主 / 属组 | `GROUP="dialout"` |
| `NAME=` | 指定节点名 | `NAME="mydev"` |
| `RUN+=` | 事件处理时执行外部程序 | `RUN+="/usr/local/bin/on-add.sh"` |

> ⚠️ `NAME=` 和 `RUN+=` 都要克制使用。`NAME=` 与 devtmpfs 已建节点叠加时行为依子系统而异，网络接口改名在新版 udev 里已不被支持，多数场景用 `SYMLINK+=` 拿稳定别名即可。`RUN+=` 里跑的程序一旦阻塞会拖住整个事件队列，长任务应交给 systemd service 或后台脚本。

### 两条常用规则

**CH340 固定别名**：CH340 是最常见的 USB 转串口芯片（VID:PID 为 `1a86:7523`），多串口混插时 `ttyUSB0/1` 的编号随插入顺序漂移。固定一个别名：

```bash
# /etc/udev/rules.d/99-ch340.rules
SUBSYSTEM=="tty", ATTRS{idVendor}=="1a86", ATTRS{idProduct}=="7523", \
    SYMLINK+="ch340", MODE="0666", GROUP="dialout"
```

之后程序打开 `/dev/ch340`，不用再猜编号。

**自定义设备按组授权**：假设自研 GPIO 按键驱动经 input 子系统注册，设备名 `my_gpio_button`，需要 `gpio` 组可读写：

```bash
# /etc/udev/rules.d/50-mybutton.rules
SUBSYSTEM=="input", ATTRS{name}=="my_gpio_button", \
    MODE="0660", GROUP="gpio"
```

## <span class="blue"> 规则不生效：udevadm 三个子命令 [I]

规则写完不生效，按"看、查、试"三步走，不要重启。

### monitor：看事件流

```bash
udevadm monitor --kernel --udev --property
```

开两个终端，一个跑监控，一个插拔设备。输出分两段：`KERNEL[...]` 行是内核发出的原始事件，`UDEV [...]` 行是 udevd 处理完毕的事件。什么都没打印，是驱动或硬件层的问题；有 KERNEL 没有 UDEV，是 udevd 没跑或事件被过滤。

### info：查可用属性

写匹配条件前先确认设备到底有哪些属性可用：

```bash
udevadm info --attribute-walk --path=/sys/class/tty/ttyUSB0
```

输出从设备自身沿父链逐级列出 `ATTR`/`ATTRS` 能匹配到的全部键值，`idVendor` 在哪一级、该用 `ATTR` 还是 `ATTRS`，照着抄不会错。

### test：模拟匹配过程

不插拔硬件，直接让 udevd 把某个设备的规则匹配过程完整演练一遍：

```bash
udevadm test /sys/class/tty/ttyUSB0 2>&1 | less
```

输出里能看到每条规则文件的加载顺序、哪条命中、最终 `SYMLINK` 和 `MODE` 是什么。

> 💡 `udevadm test` 只模拟不落地：它不创建节点、不执行 `RUN+=`，适合改完规则后先确认匹配逻辑；确认无误后用 `udevadm trigger` 让已在线的设备重新走一遍规则。

### 三个高频错误

| 现象 | 根因 | 处理 |
|------|------|------|
| 规则完全没效果 | 文件名不是 `.rules` 结尾 | 改后缀 |
| 改了规则行为照旧 | 没 reload | `udevadm control --reload-rules` |
| `udevadm test` 报语法错 | `==` 和 `=` 写反 | 条件用 `==`，动作用 `=` 或 `+=` |

> 🔴 `udevadm control --reload-rules` 只重新读规则文件，不会对已接入的设备重新生效。让在线设备走新规则，执行 `udevadm trigger --action=add` 或重新插拔一次。

## <span class="blue"> 嵌入式裁剪：mdev 与 udev 的取舍 [I]

mdev 是 BusyBox 自带的极简设备管理器，和 udev 消费同一份 uevent，但实现路线完全不同：没有常驻进程、没有规则引擎，靠一份 `/etc/mdev.conf` 做设备名到权限的映射。两者不是新旧关系，是面向不同资源约束的两套方案。

### mdev 的工作方式

- **冷插拔**：启动时执行 `mdev -s`，遍历 `/sys/class` 和 `/sys/block`，为已存在的设备补齐 `/dev` 节点
- **热插拔**：传统做法是把 `/sbin/mdev` 写进 `/proc/sys/kernel/hotplug`，内核每产生一条 uevent 就调用一次 mdev——这正是 11.5.2 节提到的 uevent helper 机制，依赖 `CONFIG_UEVENT_HELPER`；较新的 BusyBox 提供 `mdev -d` 守护进程模式，直接监听 netlink，绕开 uevent helper
- **权限与属主**：`/etc/mdev.conf` 用"正则 属主:属组 权限"的简格式，例如 `ttyUSB[0-9] root:dialout 0660`

### 对照表

| 维度 | udev / eudev | mdev |
|------|--------------|------|
| 体积与依赖 | 常驻守护进程，依赖较多；systemd 体系外可用 eudev | BusyBox 内置，几乎零额外体积 |
| 规则能力 | 完整匹配键、属性沿父链查找、外部程序辅助匹配 | 设备名正则 + 权限属主，能力有限 |
| 稳定命名 | `SYMLINK+=` 任意别名、by-id/by-path 体系 | 只能按内核名映射 |
| 模块自动加载 | 按 MODALIAS 自动请求 | 需额外脚本配合 |
| 热插拔实现 | netlink 常驻监听 | uevent helper 或 `mdev -d` |
| 典型场景 | 桌面/服务器、节点命名复杂的系统 | 设备集合固定的嵌入式产品 |

### 怎么选

设备集合出厂即固定、节点名稳定、无复杂热插拔需求：裸 devtmpfs 或 devtmpfs + mdev 足够，省下 udev 的常驻内存和规则维护成本。需要按设备属性区分同类设备、维护稳定别名、插拔时自动挂载或加载模块：上 udev（systemd 体系）或 eudev（非 systemd 根文件系统），Buildroot 和 Yocto 都提供现成集成。

> 💡 判断依据不是"嵌入式就该用 mdev"，而是规则复杂度：mdev.conf 表达不了的匹配需求（沿父链查属性、按序号起别名、插拔触发脚本），就是该换 udev 的信号。

## <span class="blue"> 本节总结

| 概念 | 核心要点 | 自查操作 |
|------|---------|---------|
| 规则文件位置 | `/etc/udev/rules.d/` 自定义优先于 `/lib/udev/rules.d/` 默认 | `ls /etc/udev/rules.d/` |
| 加载顺序 | 数字前缀升序，全部过一遍，后者覆盖前者 | `udevadm test` 看加载列表 |
| 运算符 | `==`/`!=` 匹配，`=`/`+=` 赋值，混用即失效 | 写完规则先 `udevadm test` |
| ATTR vs ATTRS | 前者看本设备，后者沿父链向上找 | `udevadm info --attribute-walk` |
| 调试三命令 | monitor 看流、info 查属性、test 模拟 | 插拔设备对照 KERNEL/UDEV 行 |
| mdev 取舍 | 设备固定选 mdev/devtmpfs，规则复杂选 udev/eudev | 评估 mdev.conf 能否表达现有需求 |
