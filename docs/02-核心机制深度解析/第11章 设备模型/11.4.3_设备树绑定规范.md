# 11.4.3 设备树绑定规范

> 所属：第11章 设备模型 > 11.4 设备树匹配机制
> 
> 难度：[I→E] | 预计阅读时间：15分钟

## <span class="blue"> 本节导读

前两节默认设备树的写法天然正确，本节回答"怎么保证写对"。内核为几乎每个 compatible 配了一份绑定规范（device tree binding）：一份书面契约，规定该节点允许哪些属性、哪些必填、各属性取什么类型。早期契约是纯文本文档，靠人读靠人执行；2017 年起内核社区把它迁到 YAML，配合 dt-schema 工具链变成可自动执行的校验规则。<BR>
本节覆盖：绑定规范的作用与存放位置、YAML schema 的关键字段、dt-schema 校验的正确用法、绑定规范与 `of_match_table` 的对应关系、用反编译核对实际生效的设备树。

---

## <span class="blue"> 绑定规范：每个 compatible 的属性契约 [I]

写设备树节点时，属性不是自由发挥的。驱动代码在 probe 里按固定名字读属性——`of_get_named_gpio()` 读 `gpios`、`of_property_read_string()` 读 `label`——节点里属性名错一个字母，驱动读到的是"不存在"，后果轻则功能缺失，重则 probe 失败。绑定规范就是把这些隐性约定写成显性契约的文档。

全部规范存放在内核源码树：

```
Documentation/devicetree/bindings/     # 按子系统分目录：leds/、i2c/、net/、serial/ ...
```

旧文件是 `.txt` 纯文本，只能人读；新文件是 `.yaml`，遵循 Devicetree Specification 组织维护的 json-schema 方言，可以机器校验。查某个 compatible 的契约，直接在目录里搜：

```bash
grep -rl '"gpio-leds"' Documentation/devicetree/bindings/
Documentation/devicetree/bindings/leds/leds-gpio.yaml
```

> 💡 网上教程里的属性写法可能基于旧内核的 txt 文档，而 txt 正在持续被 YAML 取代、属性也在演进。一切以目标内核版本源码树里的 YAML 文件为准，不确定时对照驱动源码里实际读取的属性名。

## <span class="blue"> YAML 规范的关键字段 [E]

一份典型的绑定规范（以下为教学用简化版，真实文件含更多继承与条件约束）：

```yaml
# leds-gpio.yaml 结构示意（简化）
$schema: http://devicetree.org/meta-schemas/core.yaml#
$id: http://devicetree.org/schemas/leds/leds-gpio.yaml#
title: LEDs connected to GPIO lines

maintainers:
  - Jacek Anaszewski <jacek.anaszewski@gmail.com>

properties:
  compatible:
    const: gpio-leds          # 该节点的 compatible 必须等于此值

patternProperties:
  # led 子节点的属性约束
  "^led-[0-9a-z]$":
    type: object
    properties:
      gpios:
        maxItems: 1           # 单个 GPIO 引用
      label:
        description: LED 的用户可见名称
      linux,default-trigger:
        description: 默认触发器名
    required:
      - gpios                 # 子节点必填属性

required:
  - compatible                # 节点级必填属性

additionalProperties: false   # 不允许规范之外的属性
```

核心字段的含义：

| 字段 | 作用 |
|------|------|
| `$id` / `title` | 规范的唯一标识与说明 |
| `properties` | 逐属性定义名称、类型、取值约束 |
| `patternProperties` | 对匹配正则的子节点名批量施加约束 |
| `required` | 必填属性列表，缺失即校验失败 |
| `const` / `enum` | 属性取值限定为常量或枚举集合 |
| `allOf` / `anyOf` | 组合多个子模式：全部满足 / 满足其一 |
| `additionalProperties` | 为 false 时禁止规范未声明的属性 |

`allOf` 常见于继承场景：一个 SoC 专用的 eMMC 控制器既要满足通用 MMC 主控规范，又要满足厂商扩展规范，用 `allOf` 把两份约束叠加。

## <span class="blue"> 校验工具链：dt-schema 而非 dtc [I→E]

校验分两层，工具完全不同，混用是最常见的误解。

**第一层：dtc 自带检查。** `dtc` 编译设备树时只报它内置的警告（单元地址格式、`reg` 属性长度、节点命名等），它**不认识 YAML 绑定规范**，不存在 `--bindings-dir` 之类的选项。dtc 全绿不代表符合绑定。

**第二层：dt-schema。** YAML 规范的机器校验由内核构建系统的两个目标完成，底层依赖 Python 包 `dtschema`（`pip install dtschema`）：

```bash
# 校验绑定规范文档本身是否合法（schema 写对了没有）
make dt_binding_check DT_SCHEMA_FILES=leds/leds-gpio.yaml

# 用绑定规范校验设备树（dts 写对了没有）
make dtbs_check DT_SCHEMA_FILES=leds/leds-gpio.yaml
```

不加 `DT_SCHEMA_FILES` 则对全部规范/全部设备树跑校验，速度较慢。`dtbs_check` 的输出按节点定位到具体属性和规则，例如必填属性缺失、属性类型不符、出现 `additionalProperties: false` 禁止的多余属性，都会逐条列出。

> ⚠️ dt-schema 只对已迁到 YAML 的绑定生效。仍为 txt 格式的绑定没有机器校验，只能靠人读。校验通过也不保证硬件工作——它保证的是"写法符合契约"，不保证契约与实际硬件接线一致。

## <span class="blue"> 绑定规范与 of_match_table 的对应关系 [E]

三者的分工：绑定规范管写法、设备树管实例、`of_match_table` 管配对。链条上任何一环脱节都会表现为 probe 失败或静默降级：

| 环节 | 约束来源 | 典型错误 | 后果 |
|------|---------|---------|------|
| compatible 拼写 | 绑定规范的 `compatible: const/enum` | 大小写混用、厂商前缀拼错 | dtbs_check 报错；与驱动表失配 |
| 属性名 | 绑定规范的 `properties` | `gpios` 写成 `gpio`、`label` 写成 `name` | 驱动读不到属性，静默降级 |
| 属性类型 | 绑定规范的类型声明 | 该写 phandle 写了 u32 | dtbs_check 报错，驱动解析失败 |
| 必填属性 | 绑定规范的 `required` | 漏写 `gpios` | dtbs_check 报错，probe 返回错误 |

写新节点的可靠流程：先在驱动源码的 `of_match_table` 里确认 compatible 字符串，再 `grep -rl` 找到对应 YAML，照 `required` 和 `properties` 逐项填写，最后 `dtbs_check` 过一遍。`additionalProperties: false` 的文件尤其要逐字照抄属性名，任何"自创属性"都会被拦下。

## <span class="blue"> 反编译 DTB：核对实际生效的设备树 [E]

dts 源文件、编译出的 dtb、bootloader 实际加载的 dtb，三者可能不是同一份——构建脚本用错路径、bootloader 用 FIT 镜像里内嵌的旧 dtb、U-Boot 运行时修改节点（fdt fixup），都是常见情况。核对手段是反编译和运行时读数：

```bash
# 把 dtb 反编译回 dts，检查实际内容
dtc -I dtb -O dts -o actual.dts myboard.dtb

# 运行时直接读内核解析后的节点树（含 bootloader 的全部修改）
ls /proc/device-tree/
cat /proc/device-tree/leds/compatible
```

`/proc/device-tree` 是内核内存中设备树的实时导出，属性值以二进制存储，字符串属性可直接 `cat`，数值属性用 `xxd` 看。怀疑"改了设备树没生效"时，先在这里确认，再回头查构建与烧录环节。

> 🔴 dtc 反编译会丢失注释、宏展开前的原始形态和标签引用（phandle 变成数字），反编译产物只适合核对取值，不适合当源码维护。

## <span class="blue"> 本节总结

| 概念 | 核心要点 | 自查操作 |
|------|---------|---------|
| 绑定规范 | 每个 compatible 的属性契约，存于 `Documentation/devicetree/bindings/` | `grep -rl '"<compatible>"' 该目录` |
| YAML 字段 | properties/required/patternProperties/additionalProperties | 通读目标节点对应 YAML 原文 |
| dt-schema 校验 | `make dt_binding_check` 校规范、`make dtbs_check` 校设备树 | 装 dtschema 后对改动节点跑校验 |
| dtc 的边界 | 只做语法与内置警告，不做绑定校验 | 不用 dtc 全绿代替 dtbs_check |
| 反编译核对 | `dtc -I dtb -O dts` 与 `/proc/device-tree` 反映实际生效内容 | 改设备树不生效时先核对运行时节点 |
