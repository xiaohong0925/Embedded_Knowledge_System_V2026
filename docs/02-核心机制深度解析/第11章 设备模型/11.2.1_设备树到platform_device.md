# 11.2.1 设备树到platform_device

> 所属：第11章 设备模型 > 11.2 platform设备与probe流程

> 难度：[E] | 预计阅读时间：14分钟

## <span class="blue"> 本节导读

11.1 节建立了总线-设备-驱动三角：驱动要工作，总线上必须先有一个设备对象。对挂在 platform 总线上的片内外设（UART、I2C 控制器、GPIO 控制器这类不通过标准枚举总线发现的设备）来说，这个设备对象不是硬件扫描出来的，而是从设备树节点翻译出来的。本节位于主线"设备树节点→platform_device→匹配→probe"的第一环：内核在启动早期如何把设备树节点逐个翻译成 platform_device，以及 status 一个属性为什么能决定设备对象存在与否。<BR>
本节覆盖：device_node 与 platform_device 的分工、of_platform_populate 的遍历逻辑与真实调用点、status 属性语义、reg 和 interrupts 到 resource 数组的映射规则。

## <span class="blue"> 从 device_node 到 platform_device：两个世界之间的翻译 [E]

内核启动时拿到的 DTB 是一块扁平的二进制数据。`setup_arch()` 阶段调用的 `unflatten_device_tree()` 把它展开成一棵内存中的树，每个节点是一个 `struct device_node`（设备树节点的内存表示，保存节点名和属性链表）。device_node 不属于设备模型：没有 kobject，不进 sysfs，总线看不见它，驱动无法直接跟它绑定。

驱动模型认的是 `struct device`。因此内核需要一个翻译步骤：把设备树里描述片内外设的节点转成挂在 platform 总线上的 `struct platform_device`（内部内嵌 struct device，并携带 resource 资源数组）。完成翻译的核心函数是 `of_platform_populate()`，定义在 `drivers/of/platform.c`。

### of_platform_populate 的遍历逻辑

函数从指定节点（通常是根节点）出发遍历子节点，逻辑可概括为：

```c
/* 逻辑示意，实际代码见 drivers/of/platform.c */
of_platform_populate(root)
{
    for_each_child_of_node(root, child) {
        if (!of_device_is_available(child))   /* status 检查，disabled 直接跳过 */
            continue;
        if (child 没有 compatible 属性)
            continue;                         /* 纯容器节点不创建设备 */
        of_platform_device_create(child);     /* 创建 platform_device */
        if (of_match_node(of_default_bus_match_table, child))
            递归展开 child 的子节点;           /* simple-bus 等总线节点 */
    }
}
```

对照真实实现，有三点容易被示意图掩盖，值得单独说明：

- **必须有 compatible 才创建设备**。没有 compatible 的节点（只起分组作用的容器节点）被直接跳过，不为它创建 platform_device。
- **递归只发生在总线型节点上**。子节点是否要展开，取决于它的 compatible 是否命中 `of_default_bus_match_table`（表内含 "simple-bus"、"simple-mfd" 等条目）。这正是设备树里 `/soc` 节点惯例写成 `compatible = "simple-bus"` 的原因：它本身会被创建成一个 platform_device，同时它的子节点也被逐个翻译。普通外设节点不递归——外设的子节点（如 I2C 控制器下挂的 EEPROM）由对应总线子系统负责创建，不归 platform 总线管。
- **调用点是通用 initcall，不是板级文件**。现代 ARM64 内核里，翻译动作由 `drivers/of/platform.c` 中的 `of_platform_default_populate_init()` 完成，它注册为 `arch_initcall_sync`，在 initcall 阶段从根节点统一调用 `of_platform_populate()`。板级代码通常不参与；个别 SoC 只对特殊节点（如电源域）另行调用。

### status 属性：一个字段决定设备是否存在

`of_device_is_available()` 的判定规则很窄：节点**不写 status 默认可用**；写 `"okay"` 或 `"ok"` 可用；其余取值（`"disabled"`、`"fail"`、`"reserved"`）一律视为不可用。判定不可用的节点直接跳过，platform_device 根本不会创建。

这个设计背后的取舍：disabled 的语义是"SoC 上有这个外设，但当前板级配置没有使用它"。既然板子上等于没有这块硬件，内核就让它彻底不存在——不进设备模型、不占 sysfs 目录、不参与匹配。假如 disabled 节点也创建设备，sysfs 里会多出一批永远绑定不上驱动的空壳设备，干扰后续排查。

> 🔴 probe 始终不执行时，排查顺序建议：先查设备树 status 是否写成了 `"disabled"`（节点常从参考板 DTS 复制而来，原厂默认关闭），再查 compatible 字符串。设备树侧的问题占此类故障的大头。

## <span class="blue"> resource 数组：platform_device 携带的硬件资源清单 [E]

platform_device 创建出来时，光有名字和 compatible 不够，驱动还需要知道寄存器在哪、中断号是多少。这些信息从节点属性翻译而来，按顺序填入 platform_device 的 resource 数组。数组元素是 `struct resource`（`<linux/ioport.h>`）：

```c
struct resource {
    resource_size_t start;   /* 起始地址或中断号 */
    resource_size_t end;     /* 结束地址（中断资源 start == end） */
    const char *name;        /* 名称，来自 reg-names / interrupt-names */
    unsigned long flags;     /* IORESOURCE_MEM / IORESOURCE_IRQ 等 */
    /* 内部链表字段从略 */
};
```

### 属性到 resource 的映射规则

| 设备树属性 | 翻译路径 | resource 类型 | 说明 |
|-----------|---------|--------------|------|
| `reg = <addr size>` | `of_address_to_resource()` | `IORESOURCE_MEM` | 寄存器基地址与长度，可多个条目 |
| `interrupts = <...>` | of_irq 解析 | `IORESOURCE_IRQ` | 中断号，可多个条目 |
| `reg-names` | 写入 resource.name | — | 配合 `platform_get_resource_byname()` 按名索引 |
| `interrupt-names` | 写入 resource.name | — | 配合 `platform_get_irq_byname()` 按名索引 |
| `dmas` / `dma-names` | DMA 子系统单独申请 | 不进 resource 数组 | DMA 通道由 `dma_request_chan()` 获取 |

条目顺序与设备树书写顺序一致：两个 reg 区间对应数组里两个 `IORESOURCE_MEM` 条目，`platform_get_resource(pdev, IORESOURCE_MEM, 0)` 取第一个、索引 1 取第二个。

### 驱动侧的标准取法

```c
static int my_probe(struct platform_device *pdev)
{
    struct resource *res;
    void __iomem *base;
    int irq;

    res = platform_get_resource(pdev, IORESOURCE_MEM, 0);
    if (!res)
        return -ENODEV;

    /* 一次完成 request_mem_region + ioremap，并纳入 devm 托管 */
    base = devm_ioremap_resource(&pdev->dev, res);
    if (IS_ERR(base))
        return PTR_ERR(base);

    irq = platform_get_irq(pdev, 0);   /* 成功返回中断号，失败返回负错误码 */
    if (irq < 0)
        return irq;
    /* ... */
}
```

`devm_ioremap_resource()` 内部先做 `request_mem_region()` 标记该区域被本驱动占用，再做 `ioremap()` 建立页表映射。若区域已被其他驱动占用，直接返回 `-EBUSY`——resource 数组因此不仅是信息载体，也是资源仲裁的凭据。

> ⚠️ 不要把中断号写成常量再直接用 `request_irq()` 申请。中断号属于板级信息，标准做法是从 platform_device 的 resource 数组里取（`platform_get_irq()`）。换板子只需改设备树，驱动代码不动。

## <span class="blue"> 本节总结

| 概念 | 核心要点 | 自查操作 |
|------|---------|---------|
| device_node | DTB 展开后的内存表示，不属于设备模型 | 对照 `/proc/device-tree` 目录树 |
| of_platform_populate | 为 status 可用且带 compatible 的节点创建 platform_device | 读 `drivers/of/platform.c` |
| 递归条件 | 仅 compatible 命中 of_default_bus_match_table 的总线节点递归展开 | 查 `/soc` 节点的 compatible |
| status 属性 | 缺省可用；"okay"/"ok" 可用；其余跳过，不创建设备 | probe 不执行时先查这个属性 |
| 调用点 | `of_platform_default_populate_init()`，arch_initcall_sync 阶段 | 在函数入口加打印验证 |
| resource 数组 | reg→MEM、interrupts→IRQ，顺序与设备树书写一致 | `platform_get_resource()` 按类型和索引取 |
