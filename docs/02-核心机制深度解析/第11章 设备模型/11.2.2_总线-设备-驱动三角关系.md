## <span class="blue"> 本节导读

「设备从设备树节点到 probe 成功」这条主线的第一步，是认清参与配对的三个角色：`bus_type`、`device`、`device_driver`。<BR>
设备持有硬件资源，驱动持有操作函数，总线负责把两边配成对——所有驱动的加载与绑定，都是这三者交互的结果。<BR>
本节把这套静态结构讲清楚，为 11.2.3 的动态调用链打底。<BR>
本节覆盖：三个核心结构体的关键字段与分工、配对的双向触发机制、不同总线的 match 对比规则、三角关系在 sysfs 中的可见形态，以及一段从 `start_kernel()` 到 `drv->probe()` 的源码入口导读。

## <span class="blue"> 三个结构体：一条总线、一台设备、一个驱动 [I]

### 先立三个定义

三个结构体都定义在 `<linux/device.h>` 体系中，对应用层工程师来说可以先建立一句话认知：

- **`struct bus_type`**：描述一类总线（platform、i2c、pci、usb……）的内核对象，持有一份设备链表、一份驱动链表，以及一套配对规则（`match()`）。
- **`struct device`**：内核中代表一台硬件设备的对象。它本身不存寄存器地址和中断号，但持有指向资源描述的入口（设备树节点 `of_node`、板级数据 `platform_data`）。
- **`struct device_driver`**：内核中代表一个驱动程序的对象，持有 `probe()`、`remove()` 等回调函数和描述「支持哪些设备」的匹配表。

### 关键字段

日常驱动开发不需要记住全部字段，但下面这些必须眼熟：

```c
/* 以下均为精简示意，只保留理解配对逻辑所需的字段 */

/* 总线：维护设备与驱动两条链表，定义配对规则 */
struct bus_type {
    const char  *name;            /* 总线名，如 "platform"、"i2c" */
    int (*match)(struct device *dev, struct device_driver *drv);
    struct subsys_private *p;     /* 内部结构：设备链表、驱动链表都在这里 */
};

/* 设备：代表一台硬件，持有资源描述入口 */
struct device {
    struct device        *parent;         /* 父设备，构成层次结构 */
    struct bus_type      *bus;            /* 挂在哪条总线 */
    struct device_driver *driver;         /* 配对成功后指向驱动 */
    struct device_node   *of_node;        /* 对应的设备树节点 */
    void                 *platform_data;  /* 板级私有数据（非设备树方式） */
    struct kobject        kobj;           /* 内嵌的内核对象，11.2.4 展开 */
};

/* 驱动：代表一段软件实现，持有操作函数与匹配表 */
struct device_driver {
    const char          *name;
    struct bus_type     *bus;             /* 要注册到哪条总线 */
    int (*probe)(struct device *dev);     /* 配对成功后由内核调用 */
    int (*remove)(struct device *dev);
    const struct of_device_id *of_match_table;  /* 设备树匹配表 */
};

struct platform_device {
    const char      *name;          /* 设备名，用于老式的 name 匹配 */
    int             id;             /* 设备编号，-1 表示只有一个 */
    struct device   dev;            /* ← 内嵌的 struct device，包含 of_node、bus、parent 等 */
    u32             num_resources;  /* resource 数组长度 */
    struct resource *resource;      /* ← I/O 内存、中断号等资源数组 */

    const struct platform_device_id *id_entry;  /* 老式的平台 ID 匹配表 */
    /* ... 还有 DMA、PM 相关字段，日常驱动开发很少直接碰 */
};
```

> 💡 硬件资源（I/O 内存地址、中断号）不在 `struct device` 里，而在包装它的具体设备结构体中。<br>以 platform 设备为例：`struct platform_device` 内嵌一个 `struct device`，外加 `struct resource *resource` 数组和 `num_resources`。驱动在 probe 里通过 `platform_get_resource()` 取资源，而不是直接访问 `struct device`。


### 配对是双向触发的

先回答一个前置问题：为什么需要"配对"这件事本身？因为设备和驱动来自**两个互不知情的世界**。<BR>
设备对象由硬件描述翻译而来——开机时设备树解析出一批 platform 设备，或 USB 设备插入时枚举出一个；驱动对象由软件加载而来——模块 `insmod` 的那一刻，或内核 initcall 执行到它的那一刻。<BR>
两边的到达时间不可预知、顺序不可保证：设备树在开机几秒内就翻译完了，而适配它的驱动可能作为模块三个月后才被加载。<BR>
内核等不到一个"两边都齐了"的统一时刻，唯一可行的策略是：**任何一方到达时，立刻在对方已有成员里试配一次**。

这就是两条链表存在的原因。总线维护 `klist_devices`（已注册设备）和 `klist_drivers`（已注册驱动），配对在两个方向上都会发生：

- **设备注册时**：`device_add()` 把设备挂到总线，随后遍历总线的驱动链表，逐个调用 `match()`，命中则执行该驱动的 `probe()`。
- **驱动注册时**：`driver_register()` 把驱动挂到总线，随后遍历总线的设备链表，逐个调用 `match()`，命中则执行 `probe()`。

因此设备和驱动的注册顺序不影响最终结果：先到的一方挂在链表上等待，后到的一方注册时完成配对。一个驱动可以依次匹配多台设备（同一型号的串口可以有多路），一台设备同一时间只绑定一个驱动。

* 路径 A：设备先到，驱动后到
```
device_add(dev)
    ├── bus_add_device(dev)          // ← 挂进 klist_devices : 单纯挂链表，没做匹配
    └── bus_probe_device(dev)        // ← 尝试给这个设备找驱动 : 触发遍历对方链表
          └── device_attach(dev)
                └── bus_for_each_drv(bus, NULL, dev, __device_attach) // ← 遍历总线上已注册的驱动/设备
                      // 遍历 klist_drivers 里的每一个驱动
                      └── __device_attach(dev, drv)
                            ├── driver_match_device(drv, dev) // ← 加锁后调用 bus->match()，返回 1 表示匹配成功 
                            │         └── bus->match(dev, drv)   // ← match()
                            └── driver_probe_device(drv, dev)      // match 返回 1 才走这里
                                  └── really_probe(dev, drv)  // 内核里真正干活的函数：调用 drv->probe()，处理 devlink、电源管理、绑定 sysfs 等
                                        └── drv->probe(dev)        // ← probe()
```

* 路径 B：驱动先到，设备后到
```
driver_register(drv)
    ├── bus_add_driver(drv)          // ← 挂进 klist_drivers : 单纯挂链表，没做匹配
    └── driver_attach(drv)           // ← 尝试给这个驱动找设备 : 触发遍历对方链表
          └── bus_for_each_dev(bus, NULL, drv, __driver_attach) // ← 遍历总线上已注册的驱动/设备
                // 遍历 klist_devices 里的每一个设备
                └── __driver_attach(dev, drv)
                      ├── driver_match_device(drv, dev)
                      │         └── bus->match(dev, drv)         // ← 同样的 match()
                      └── driver_probe_device(drv, dev)
                            └── really_probe(dev, drv)
                                  └── drv->probe(dev)              // ← 同样的 probe()
```

**关键结论**：两条路径在 `driver_match_device()` 之后完全重合，后面走的是同一套 `really_probe()`。

### 不同总线的 match 规则

`match()` 由各总线自己实现，对比内容取决于总线枚举设备的方式：

| 总线 | match 对比内容 | 典型来源 |
|------|---------------|---------|
| platform | 设备树 `compatible` vs `of_match_table`，退化到 `id_table`、设备名 | 设备树节点 |
| i2c / spi | 设备树 `compatible` vs `of_match_table`，退化到 `id_table` 名字 | 设备树节点或板级声明 |
| usb | `idVendor` + `idProduct` vs `usb_device_id` 表 | 设备插入时协议枚举 |
| pci | vendor/device ID、class 码 vs `pci_device_id` 表 | 总线扫描枚举 |

platform 总线的实际实现（`drivers/base/platform.c` 中的 `platform_match()`）核心优先级为：OF（设备树 compatible）> `id_table` > 设备名字符串。<br>现代 ARM 嵌入式开发以 OF 匹配为主，`id_table` 与名字匹配用于非设备树平台。完整实现还有两级——最前的 `driver_override` 旁路与 OF 之后的 ACPI 级，四级完整版在 11.3.2 展开。


```c
// drivers/base/platform.c
static int platform_match(struct device *dev, struct device_driver *drv)
{
    struct platform_device *pdev = to_platform_device(dev);
    struct platform_driver *pdrv = to_platform_driver(drv);

    /* 1. OF 匹配：设备树 compatible vs of_match_table */
    if (of_driver_match_device(dev, drv))
        return 1;

    /* 2. id_table 匹配 */
    if (pdrv->id_table)
        return platform_match_id(pdrv->id_table, pdev) != NULL;

    /* 3. 退化到名字字符串匹配 */
    return (strcmp(pdev->name, drv->name) == 0);
}
```

这个 `platform_match()` 就是 `bus_type` 结构体里的 `match` 函数指针。内核在 `driver_match_device()` 里调用它：

```c
// drivers/base/base.h（旧版本在 drivers/base/dd.c）
static inline int driver_match_device(struct device_driver *drv,
                                      struct device *dev)
{
    return drv->bus->match ? drv->bus->match(dev, drv) : 1;
}
```

所以 `match()` 的返回值决定了是否进入 `probe()`：

- 返回 **1** → 匹配成功 → 继续走 `driver_probe_device()` → `really_probe()` → `drv->probe()`
- 返回 **0** → 匹配失败 → 跳过，继续遍历下一个

> 💡 各类总线驱动写法差别很大，但匹配表的结构是统一的：设备树节点的 `compatible` 字符串与驱动 `of_match_table` 中的条目做精确字符串比对，一个字符不一致就匹配失败，且内核不打印任何日志。

### 三者职责对比

| 角色 | 核心数据 | 关键回调 | 驱动开发中主要做什么 |
|------|---------|---------|---------------------|
| bus_type | 设备链表、驱动链表 | `match()` | 很少直接涉及，`platform_bus_type` 等已由内核实现 |
| device | `of_node`、`resource` | 无（被动等待驱动） | 在设备树中描述硬件，或手工填充 `platform_device` |
| device_driver | `of_match_table`、`id_table` | `probe()`、`remove()` | **主要工作**：实现回调、填写匹配表 |

### 三角关系在 sysfs 中是可见的

三个结构体都内嵌或关联 `kobject`（内核对象基础设施，负责命名、层次和引用计数，11.2.4 展开），因此配对状态直接投影在 `/sys` 下：

```
/sys/bus/platform/
├── devices/                    <- 挂在 platform 总线上的设备
│   └── ff000000.serial -> ../../../devices/platform/...
└── drivers/                    <- 挂在 platform 总线上的驱动
    └── my_serial/
        └── ff000000.serial -> ../../../devices/...   <- 绑定关系的符号链接
```

设备目录下的 `driver` 符号链接指向其绑定的驱动，驱动目录下的设备符号链接列出它管理的所有设备。内核日志里的 `probe`、`bind` 打印，对应的就是这两条链表上发生的配对动作。

## <span class="blue"> 代码导读：从 start_kernel 走到 drv->probe() [I]

上面讲的三个结构体和两条配对路径，如果只停留在框图上，看源码时会有一种「虚」的感觉——这些对象究竟是谁、在哪一行创建的？本节做一次入口溯源：从内核启动的真实入口 `start_kernel()` 出发，分三条线分别找到总线、设备、驱动的诞生点，最后汇合到 `probe()` 被调用的那一行。<br>
所有行号以 v6.6 内核为准，不同版本会有漂移，但文件位置与调用关系多年未变。

### 入口：`driver_init()`

设备模型一切的起点在 `start_kernel()` 里（`init/main.c:1326`）：

```c
// init/main.c
asmlinkage __visible void __init start_kernel(void)
{
    ...
    driver_init();        // init/main.c:1326
    ...
}
```

`driver_init()` 本体在 `drivers/base/init.c:21`，它只做一件事：按顺序初始化设备模型的各个子系统：

```c
// drivers/base/init.c
void __init driver_init(void)
{
    devtmpfs_init();        // /dev 的自动填充，见第5章
    devices_init();         // 建 /sys/devices
    buses_init();           // 建 /sys/bus        ← 溯源线一
    classes_init();         // 建 /sys/class
    firmware_init();
    hypervisor_init();
    of_core_init();         // 设备树核心初始化
    platform_bus_init();    // 注册 platform 总线  ← 溯源线一
    ...
}
```

### 溯源线一：总线的诞生

`buses_init()`（`drivers/base/bus.c:1374`）只创建了一个 kset：

```c
// drivers/base/bus.c
int __init buses_init(void)
{
    bus_kset = kset_create_and_add("bus", &bus_uevent_ops, NULL);
    ...
}
```

这个名为 `"bus"` 的 kset 就是 `/sys/bus/` 目录本身。此时目录是空的，因为还没有任何总线注册进来。

紧接着 `platform_bus_init()`（`drivers/base/platform.c:1517`）注册内核里的第一条总线：

```c
// drivers/base/platform.c
int __init platform_bus_init(void)
{
    ...
    error = device_register(&platform_bus);          // 建 /sys/devices/platform
    error =  bus_register(&platform_bus_type);       // 建 /sys/bus/platform
    ...
}
```

`platform_bus_type` 的定义就在同文件 `platform.c:1482`——这就是前文「三个结构体」里那个抽象的 `bus_type` 的第一个实体：

```c
// drivers/base/platform.c:1482
struct bus_type platform_bus_type = {
    .name   = "platform",
    .match  = platform_match,      // ← 配对规则，platform.c:1335
    .uevent = platform_uevent,
    .probe  = platform_probe,      // ← 注意：probe 挂在总线上，platform.c:1379
    ...
};
EXPORT_SYMBOL_GPL(platform_bus_type);
```

`bus_register()`（`bus.c:844`）内部再创建 `devices` 和 `drivers` 两个 kset（`bus.c:876`、`bus.c:882`），对应 `/sys/bus/platform/devices/` 和 `/sys/bus/platform/drivers/` 两个目录。<br>
**至此，`/sys/bus/platform/{devices,drivers}` 在启动早期就已存在，只是两条链表都是空的，等待设备和驱动进来。**

### 溯源线二：设备的诞生

设备树节点的转换发生在一个 `arch_initcall_sync` 里（`drivers/of/platform.c:633`），入口是 `of_platform_default_populate_init()`（同文件 `:546`），整条链如下：

```
of_platform_default_populate_init()        // drivers/of/platform.c:546
    └── of_platform_populate()             // :494 遍历设备树根节点的子节点
          └── of_platform_bus_create()     // :372 逐个节点处理
                └── of_platform_device_create_pdata()   // :200
                      ├── of_device_alloc()             // :212 分配 platform_device，
                      │                                 //    把 reg/interrupts 翻译成 resource 数组
                      ├── dev->dev.bus = &platform_bus_type;  // :219 ← 挂到 platform 总线
                      └── of_device_add()               // :223 内部调用 device_add()
```

设备树节点到 `platform_device` 的转换细节（地址翻译、中断映射）是 11.3 的内容，这里只需要记住汇入口：`device_add()`（`drivers/base/core.c:3506`）。它做三件与本节直接相关的事：

```c
// drivers/base/core.c，精简
int device_add(struct device *dev)
{
    ...
    error = bus_add_device(dev);                    // core.c:3581 挂进总线的设备链表，
                                                    //   建 /sys/bus/platform/devices/xxx 链接
    ...
    kobject_uevent(&dev->kobj, KOBJ_ADD);           // core.c:3605 发 uevent，
                                                    //   用户态 mdev/udev 据此建 /dev 节点（见5.4.3）
    ...
    bus_probe_device(dev);                          // core.c:3624 ← 触发配对，路径 A 的起点
    ...
}
```

`bus_probe_device()`（`bus.c:523`）调用 `device_initial_probe()`（`drivers/base/dd.c:1077`），进入 `__device_attach()`（`dd.c:1000`），用 `bus_for_each_drv()` 遍历总线驱动链表逐个尝试配对——这就是前文「路径 A」在源码里的真实落点。

> 💡 非设备树的板级写法殊途同归：手工调用 `platform_device_register()`（`platform.c:775`）→ `platform_device_add()`（`platform.c:656`，其中 `:667` 同样执行 `pdev->dev.bus = &platform_bus_type`）→ `device_add()`。两条路最终都汇入同一个函数。

### 溯源线三：驱动的诞生

驱动的注册入口是你写在模块里的 `module_init(xxx_init)`。它展开后是一个 `__initcall`，由内核启动时的 `do_initcalls()` 依次执行（initcall 机制见第 7 章）。`xxx_init()` 里的 `platform_driver_register()` 是一个宏（`include/linux/platform_device.h:272`），展开后调用：

```c
// drivers/base/platform.c:861
int __platform_driver_register(struct platform_driver *drv,
                               struct module *owner)
{
    drv->driver.owner = owner;
    drv->driver.bus   = &platform_bus_type;   // :865 ← 挂到 platform 总线

    return driver_register(&drv->driver);     // :867
}
```

往下走 `driver_register()`（`drivers/base/driver.c:222`）→ `bus_add_driver()`（`bus.c:642`）。`bus_add_driver()` 把驱动挂进总线的驱动链表、建好 `/sys/bus/platform/drivers/xxx` 目录后，在 `bus.c:673` 调用 `driver_attach()`（`dd.c:1231`），用 `bus_for_each_dev()` 遍历总线上的设备，对每个设备执行 `__driver_attach()`（`dd.c:1156`）——这就是前文「路径 B」的真实落点：

```c
// drivers/base/dd.c:1156，精简
static int __driver_attach(struct device *dev, void *data)
{
    struct device_driver *drv = data;
    ...
    ret = driver_match_device(drv, dev);      // :1172 ← 问总线：这一对配吗？
    if (ret == 0)
        return 0;                             // 不配，看下一个设备
    ...
    driver_probe_device(drv, dev);            // :1216 ← 配上了，进 probe 流程
    ...
}
```

### 汇合点：`match()` 与 `probe()`

三条线至此汇合。`driver_match_device()` 在 v6.6 中是 `drivers/base/base.h` 里的内联函数（旧版本在 `dd.c`，前文引用的就是它的本体），一句 `return drv->bus->match(dev, drv)` 把调用转给总线——对 platform 总线来说就是 `platform.c:1335` 的 `platform_match()`。

match 命中后，`driver_probe_device()`（`dd.c:824`）→ `really_probe()`（`dd.c:603`，其中 `:623` 那条 `pr_debug("bus: '%s': really_probe: probing driver %s with device %s\n")` 就是动态调试开关打开后能看到的著名日志）→ `call_driver_probe()`（`dd.c:572`），在这里做最后一次分发：

```c
// drivers/base/dd.c:572，精简
static int call_driver_probe(struct device *dev, struct device_driver *drv)
{
    if (dev->bus->probe)
        ret = dev->bus->probe(dev);     // :577 platform 走这里 → platform_probe()
    else if (drv->probe)
        ret = drv->probe(dev);          // :579 无总线 probe 时直接调驱动的
    ...
}
```

platform 总线的 `.probe` 是 `platform_probe()`（`platform.c:1379`），它做完电源管理、时钟、pinmux 等公共准备后，才调用你写的 `pdrv->probe()`。**从 `start_kernel()` 到你的 `probe()`，整条链上的每一环都在上面有据可查。**

### 自己动手：怎么在源码树里找到这些函数

上面每个结论都可以用两条 grep 复现，不需要任何专用工具：

```bash
# 找定义：搜结构体/函数的名字本身
grep -rn "struct bus_type platform_bus_type" drivers/
grep -n "^int device_add" drivers/base/core.c

# 找调用点：搜名字看谁引用它（从结果里顺藤摸瓜）
grep -rn "platform_bus_init" init/ drivers/base/
grep -rn "platform_match" drivers/base/
```

两条经验：一，sysfs 里的目录名（如 `"platform"`）就是很好的反查关键词，`grep -rn '"platform"' drivers/base/` 能直接定位 `platform_bus_type`；二，在线交叉引用站 bootlin.com/elixir 可以点着函数名跳定义和引用，比本地 grep 省力。读代码时从「我知道的现象」（sysfs 目录、内核日志字符串）反推源码位置，通常比从入口正向硬啃快得多。

## <span class="blue"> 本节总结

| 概念 | 核心要点 | 自查操作 |
|------|---------|---------|
| bus_type | 总线维护设备/驱动两条链表，定义 match 规则 | `ls /sys/bus/` 查看系统注册的总线 |
| device | 代表硬件，资源在 platform_device 的 resource 数组中 | `ls /sys/bus/platform/devices/` |
| device_driver | 代表软件实现，持有 probe/remove 与匹配表 | `ls /sys/bus/platform/drivers/` |
| 双向配对 | 设备或驱动任一方注册都会触发遍历匹配，顺序不影响结果 | 读设备目录下的 `driver` 符号链接 |
| match 规则 | platform 以 of_match_table 比对 compatible 为主 | 对比设备树 compatible 与驱动匹配表 |
