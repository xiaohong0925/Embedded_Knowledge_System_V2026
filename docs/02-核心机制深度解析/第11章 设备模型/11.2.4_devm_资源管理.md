# 11.2.4 devm_*资源管理

> 所属：第11章 设备模型 > 11.2 platform设备与probe流程
> 
> 难度：[I→E] | 预计阅读时间：14分钟

## <span class="blue"> 本节导读

上一节的 probe 里反复出现 `devm_` 前缀的 API，本节解释这套机制的原理与边界。`devm_` 背后是内核的 device resource management（devres，设备资源托管）子系统：申请资源时把它挂到 device 结构的托管链表上，由内核在固定时机统一释放，驱动因此不用为每一种资源维护一条错误清理路径。资源泄漏是驱动开发最常见的缺陷类别之一——ioremap 忘了 iounmap、申请了中断忘了 free，热插拔几个来回系统状态就被腐蚀。devres 是内核给出的系统性解法。<BR>
本节覆盖：devres 的链表结构与释放时机、释放顺序、常用 devm 函数对照、devm 管不到的三类边界、传统写法与 devm 写法的对比。

---

## <span class="blue"> devres 机制：资源挂到 device 上，内核统一释放 [I→E]

每个 `struct device` 内部维护一条托管资源链表（devres 链表）。调用 `devm_kzalloc()` 等函数时，内核除分配资源外还在链表上挂一个节点，节点里记录资源指针和对应的释放回调。

```
struct device {
    ...
    struct list_head devres_head;   /* 托管资源链表头 */
    ...
};
```

释放发生在两个固定时机：

1. **probe 返回错误**：驱动核心在 probe 失败路径执行全量清理，已挂接的 devm 资源全部释放。probe 中途失败时，驱动不需要为托管资源写任何清理代码。
2. **设备与驱动解绑**：remove 执行后（含设备注销、驱动卸载），内核遍历链表逐个调用释放回调。

释放顺序与申请顺序**相反**（后进先出）：先申请的时钟比后申请的映射晚释放，资源间的依赖关系不会在清理时倒挂。

> ⚠️ 自动释放运行在进程上下文（probe 失败清理路径、remove 路径），不提供"立即释放"语义。需要精确控制释放时序的场景（如中断处理中的缓冲区轮换），不应依赖这套机制。

### 常用 devm 函数对照表

规律很明显：传统函数名前加 `devm_`，第一个参数多一个 `struct device *`。

| devm 版本（自动释放） | 传统版本（手动配对） | 用途 |
|----------------------|---------------------|------|
| `devm_kzalloc()` | `kzalloc()` / `kfree()` | 设备私有内存 |
| `devm_ioremap_resource()` | `request_mem_region()` + `ioremap()` / `iounmap()` | IO 内存映射 |
| `devm_request_irq()` | `request_irq()` / `free_irq()` | 中断申请 |
| `devm_clk_get()` | `clk_get()` / `clk_put()` | 时钟引用（不含 enable/disable） |
| `devm_regulator_get()` | `regulator_get()` / `regulator_put()` | 电源引用 |
| `devm_gpiod_get()` 等 | `gpio_request()` / `gpio_free()` | GPIO |
| `devm_dma_alloc_coherent()` | `dma_alloc_coherent()` / `dma_free_coherent()` | 一致性 DMA 内存 |

devm 风格的 probe，整段没有一行释放代码：

```c
static int my_probe(struct platform_device *pdev)
{
    struct my_priv *priv;
    int irq, ret;

    priv = devm_kzalloc(&pdev->dev, sizeof(*priv), GFP_KERNEL);
    if (!priv)
        return -ENOMEM;

    priv->base = devm_ioremap_resource(&pdev->dev,
                platform_get_resource(pdev, IORESOURCE_MEM, 0));
    if (IS_ERR(priv->base))
        return PTR_ERR(priv->base);

    irq = platform_get_irq(pdev, 0);
    if (irq < 0)
        return irq;

    priv->clk = devm_clk_get(&pdev->dev, NULL);
    if (IS_ERR(priv->clk))
        return PTR_ERR(priv->clk);

    ret = devm_request_irq(&pdev->dev, irq, my_handler, 0, "my_drv", priv);
    if (ret)
        return ret;

    platform_set_drvdata(pdev, priv);
    return 0;
}
```

### devm 管不到的三类边界

1. **生命周期必须等于 device 的生命周期**。要在两个设备间共享的 DMA buffer、remove 之后仍需保留的数据，不能用 devm 托管。
2. **运行时状态切换不托管**。`clk_prepare_enable()`、`regulator_enable()` 这类 enable/disable 配对属于状态切换，不是一次性资源申请，devm 不管（新版本内核的 `devm_clk_get_enabled()`、`devm_add_action_or_reset()` 是后来补的两个例外手段）。
3. **非托管子系统资源不托管**。`alloc_chrdev_region()`、`cdev_add()`、`device_create()` 等申请的资源仍需失败时手动回收（11.2.3 的完整示例展示了托管与非托管资源共存的清理写法）。

> 💡 需要提前释放个别托管资源时，内核提供配套函数（`devm_kfree()`、`devm_free_irq()`、`devm_iounmap()`），会把资源从托管链表摘除并立即释放。常规驱动很少用到；决定能否用 devm 的判据是第一条——生命周期是否与 device 一致。

## <span class="blue"> 传统写法与 devm 写法对比 [E]

同一个 GPIO 按键驱动，先看传统的手动配对写法：

```c
/* 传统写法：每种资源一层清理标签 */
static int key_probe(struct platform_device *pdev)
{
    struct key_priv *priv;
    int ret, irq;

    priv = kzalloc(sizeof(*priv), GFP_KERNEL);
    if (!priv)
        return -ENOMEM;

    irq = platform_get_irq(pdev, 0);
    if (irq < 0) {
        ret = irq;
        goto err_free_priv;
    }

    ret = request_irq(irq, key_handler, IRQF_TRIGGER_FALLING, "key", priv);
    if (ret)
        goto err_free_priv;

    priv->clk = clk_get(&pdev->dev, NULL);
    if (IS_ERR(priv->clk)) {
        ret = PTR_ERR(priv->clk);
        goto err_free_irq;
    }

    ret = clk_prepare_enable(priv->clk);
    if (ret)
        goto err_put_clk;

    platform_set_drvdata(pdev, priv);
    return 0;

err_put_clk:
    clk_put(priv->clk);
err_free_irq:
    free_irq(irq, priv);
err_free_priv:
    kfree(priv);
    return ret;
}
```

四种资源对应四层清理标签，且清理顺序必须严格反序；中途新增一种资源，整条 `goto` 链都要重排，漏一处就是泄漏。

devm 写法：

```c
static int key_probe(struct platform_device *pdev)
{
    struct key_priv *priv;
    int ret, irq;

    priv = devm_kzalloc(&pdev->dev, sizeof(*priv), GFP_KERNEL);
    if (!priv)
        return -ENOMEM;

    irq = platform_get_irq(pdev, 0);
    if (irq < 0)
        return irq;

    ret = devm_request_irq(&pdev->dev, irq, key_handler,
                           IRQF_TRIGGER_FALLING, "key", priv);
    if (ret)
        return ret;

    priv->clk = devm_clk_get(&pdev->dev, NULL);
    if (IS_ERR(priv->clk))
        return PTR_ERR(priv->clk);

    /* enable 不托管，remove 里配对 clk_disable_unprepare() */
    ret = clk_prepare_enable(priv->clk);
    if (ret)
        return ret;

    platform_set_drvdata(pdev, priv);
    return 0;
}
```

错误路径收缩为逐级 `return`：probe 在任一位置失败，已挂接的 devm 资源由内核在失败清理路径统一释放。唯一残留的手动动作是 remove 里的 `clk_disable_unprepare()`。

> ⚠️ devm 消除的是"资源申请与释放"层面的清理代码，不消除逻辑错误。混用托管与非托管资源时（注册子系统之后），非托管部分仍要按反序手动回收。

## <span class="blue"> 本节总结

| 概念 | 核心要点 | 自查操作 |
|------|---------|---------|
| devres 机制 | 资源挂到 device 的托管链表，内核统一调释放回调 | 查 `struct device` 的 devres 字段 |
| 释放时机 | probe 失败时全量清理；remove/解绑时全量清理 | 模拟 probe 中途返回错误，确认无泄漏 |
| 释放顺序 | 与申请顺序相反（后进先出），依赖不倒挂 | 对照申请顺序推演清理顺序 |
| 命名规律 | 传统函数名前加 `devm_`，首参为 `struct device *` | 对比 `kzalloc()` 与 `devm_kzalloc()` 原型 |
| 三类边界 | 生命周期不一致、enable 类状态切换、非托管子系统资源 | 数一下 probe 里还剩哪些手动配对 |
| 提前释放 | `devm_kfree()`、`devm_free_irq()` 等可摘除单个托管资源 | 非常规手段，常规驱动无需使用 |
