## <span class="blue"> READ_ONCE()/WRITE_ONCE() —— 编译器屏障的精确武器 [E]

### 编译器优化的"黑手"

编译器在优化时有个坏习惯：它假设当前代码是唯一的执行者。在高并发场景下，这个假设是致命的。看看这段代码：

```c
/* 共享标志，由中断处理程序置位 */
static int data_ready;
static int shared_data;

void irq_handler(void)
{
    shared_data = 42;          /* 准备数据 */
    data_ready = 1;            /* 通知主循环 */
}

int main_loop(void)
{
    while (!data_ready)        /* 编译器可能只读一次 */
        cpu_relax();
    return shared_data;        /* 可能读不到42 */
}
```

编译器看到`main_loop()`里`data_ready`没有被修改，就会把它优化成只读一次进寄存器。问题来了——中断处理程序在其他上下文中修改了`data_ready`，主循环永远检查不到变化。

READ_ONCE()和WRITE_ONCE()就是用来解决这类问题的。v6.6 的真实定义在 include/asm-generic/rwonce.h：

```c
#ifndef __READ_ONCE
#define __READ_ONCE(x)	(*(const volatile __unqual_scalar_typeof(x) *)&(x))
#endif

#define READ_ONCE(x)							\
({									\
	compiletime_assert_rwonce_type(x);				\
	__READ_ONCE(x);							\
})

#define __WRITE_ONCE(x, val)						\
do {									\
	*(volatile typeof(x) *)&(x) = (val);				\
} while (0)
```

核心手段是强制类型转换为`volatile`指针，实现对变量的**精确单次访问**，告诉编译器："这个变量的每次读写都必须实实在在地访问内存，不许合并、不许缓存到寄存器、不许删除。"外层的 `compiletime_assert_rwonce_type()` 会在编译期检查操作数是标量类型——对结构体等聚合类型使用会直接编译报错，防止你以为"整个结构体被原子地读写"。

### 关键特性：只拦编译器，不拦CPU

READ_ONCE/WRITE_ONCE的核心定位非常明确——**编译器屏障，而非内存屏障**。

```c
/* 正确使用：确保每次循环都重新读取内存 */
while (!READ_ONCE(data_ready))     /* 每次循环都从内存读 */
    cpu_relax();

/* WRITE_ONCE确保写操作确实发生 */
WRITE_ONCE(shared_data, 42);       /* 必须写入内存 */
WRITE_ONCE(data_ready, 1);         /* 必须写入内存 */
```

但要注意，它们**不保证**以下两点：

- **不阻止CPU指令重排**：编译器不会重排READ_ONCE/WRITE_ONCE周围的内存访问，但CPU仍可能乱序执行
- **不保证立即可见性**：一个CPU写入后，另一个CPU不会立刻看到，这需要缓存一致性协议和真正的内存屏障

> ⚠️ READ_ONCE不提供内存屏障！如果你需要保证读写之间的顺序关系，必须显式搭配`smp_mb()`、`smp_rmb()`或`smp_wmb()`使用。单纯靠READ_ONCE/WRITE_ONCE无法阻止CPU将两条写指令乱序执行。

### READ_ONCE vs C volatile：天壤之别

很多开发者第一反应是："这不就是volatile吗？" 错。内核源码的文档里白纸黑字写着：**Don't use volatile in kernel code**。看看区别：

| 维度 | READ_ONCE/WRITE_ONCE | C `volatile` | 原子读取 (atomic_read) | `smp_rmb()` |
|------|---------------------|-------------|----------------------|-------------|
| **核心目标** | 单次访问语义，阻止编译器优化 | 暗示"可能被外部修改"，语义模糊 | 读取 atomic_t（本质即 READ_ONCE） | CPU读内存屏障 |
| **编译器优化** | ✅ 精确阻止合并/删除访问 | ⚠️ 行为因编译器而异，不一致 | ✅ 阻止优化 | ❌ 不影响编译器 |
| **原子性保证** | ⚠️ 仅对齐标量单次访问不撕裂 | ❌ 不保证 | ⚠️ 同左（对齐字宽单次访问） | ❌ 不保证 |
| **CPU内存序** | ❌ 不提供内存屏障 | ❌ 不提供内存屏障 | ❌ **不提供**（无返回值原子操作均无内存序） | ✅ 阻止读-读/读-写重排 |
| **可移植性** | ✅ 与内核内存模型精确配合 | ❌ 编译器实现差异大 | ✅ 统一接口 | ✅ 架构无关抽象 |
| **推荐使用场景** | 与另一个CPU/中断共享的简单标志 | **内核中不要使用** | 计数器、引用计数的读取 | 需要读顺序保证时 |

`volatile`的问题在于它的语义太过模糊。C标准说volatile访问是"副作用"，但到底怎么实现完全由编译器说了算。不同编译器、不同优化级别下，volatile的行为可能千差万别。内核需要**精确的、可预期的**内存访问语义，这正是READ_ONCE/WRITE_ONCE的设计初衷。

> 💡 在内核代码中，永远不要用`volatile`修饰变量。如果你需要阻止编译器优化，用READ_ONCE/WRITE_ONCE；如果你需要原子性，用`atomic_t`系列接口；如果你需要内存序保证，用`smp_mb()`家族。各司其职，不要混用。

### 典型使用模式：共享标志位检查

这是READ_ONCE/WRITE_ONCE最常见的战场——一个CPU（或中断）生产数据，另一个CPU消费：

```c
/* ==== 生产者（中断上下文或另一个CPU）==== */
void produce_data(void)
{
    /* 步骤1：先准备好数据 */
    WRITE_ONCE(shared_buffer, compute_result());

    /* 步骤2：设置标志通知消费者
     *
     * 注意：这里仅保证WRITE_ONCE本身不被优化，
     * 但shared_buffer和flag的写入顺序仍可能被CPU重排！
     */
    WRITE_ONCE(flag, 1);
}

/* ==== 消费者（主循环或另一个CPU）==== */
int consume_data(void)
{
    /* 循环检查标志，每次从内存重新读取 */
    while (!READ_ONCE(flag))
        cpu_relax();           /* 自旋等待，提示CPU节能 */

    /* 标志已设置，读取数据
     *
     * 危险：如果没有smp_rmb()，CPU可能先执行下面的读，
     * 再完成flag的读，导致读到旧数据！
     */
    smp_rmb();                   /* 关键：确保flag读在data读之前完成 */

    return READ_ONCE(shared_buffer);
}
```

上面的`smp_rmb()`是点睛之笔。没有它，消费端的CPU可能先执行`READ_ONCE(shared_buffer)`，再确认`flag == 1`——结果读到的是旧值。READ_ONCE只能保证访问动作本身不被编译器吃掉，跨指令的顺序保证还得靠内存屏障。

下图展示了编译器优化 vs READ_ONCE保护的区别：

```
┌─────────────────────────────────────────────────────────────────┐
│                    编译器优化（危险）                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   C代码: while (!data_ready) cpu_relax();                       │
│                                                                 │
│   优化后伪代码:                                                  │
│   ┌─────────────┐                                               │
│   │ r = data_ready │  ← 只读一次，缓存到寄存器r                  │
│   │ while (!r) {   │  ← 永远读不到新值！                         │
│   │     cpu_relax()│                                            │
│   │ }              │  ← 死循环                                   │
│   └─────────────┘                                               │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│                    READ_ONCE保护（安全）                           │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   C代码: while (!READ_ONCE(data_ready)) cpu_relax();            │
│                                                                 │
│   生成伪代码:                                                    │
│   ┌─────────────┐                                               │
│   │ loop:        │                                              │
│   │   r = *(volatile*)&data_ready │  ← 每次都从内存重新读取      │
│   │   if (!r) goto loop │  ← 能看到中断写入的新值                │
│   └─────────────┘                                               │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 什么时候必须搭配内存屏障？

READ_ONCE/WRITE_ONCE和`smp_mb()`家族的分工可以这样理解：

| 你面临的问题 | 解决方案 |
|-------------|---------|
| 编译器把多次读合并成一次 | READ_ONCE |
| 编译器删掉了"多余的"写 | WRITE_ONCE |
| CPU把两条读的顺序颠倒了 | smp_rmb() |
| CPU把两条写的顺序颠倒了 | smp_wmb() |
| 读和写之间的顺序都要保证 | smp_mb() |

大多数实际场景中，你需要**组合使用**：

```c
/* 正确：标志位检查 + 顺序保证 */
WRITE_ONCE(data, new_value);     /* 确保写不被优化掉 */
smp_wmb();                       /* 确保data写在flag写之前 */
WRITE_ONCE(flag, 1);             /* 确保写不被优化掉 */

/* 消费端 */
while (!READ_ONCE(flag))         /* 每次从内存读 */
    cpu_relax();
smp_rmb();                       /* 确保flag读在data读之前 */
value = READ_ONCE(data);         /* 确保读不被优化掉 */
```

> 🔴 如果你在生产者和消费者之间传递的是指针（如`struct device *dev`），千万别只依赖READ_ONCE/WRITE_ONCE。指针本身的读写虽然是原子的（在64位平台上），但指针指向的内容的可见性需要完整的内存屏障来保证。标准做法是使用`smp_store_release()`和`smp_load_acquire()`，它们在提供编译器屏障的同时还带有获取/释放语义。

## <span class="blue"> 本节总结

| 要点 | 核心内容 |
|------|---------|
| **本质定位** | READ_ONCE/WRITE_ONCE是**编译器屏障**，阻止对单次内存访问的优化合并/删除 |
| **真实定义** | `include/asm-generic/rwonce.h`，volatile 指针强转 + 标量类型编译期检查 |
| **不做的事** | 不提供CPU内存屏障，不保证跨CPU立即可见，超出对齐字宽的访问可能撕裂 |
| **vs volatile** | 精确的单次访问语义，与内核内存模型配合；`volatile`语义模糊，内核中禁止使用 |
| **典型场景** | 共享标志位轮询、中断与主循环间的简单信号传递 |
| **正确搭档** | 需要顺序保证时，必须配合`smp_mb()`/`smp_rmb()`/`smp_wmb()`使用 |
| **进阶替代** | 需要获取/释放语义时，优先考虑`smp_load_acquire()`/`smp_store_release()` |
