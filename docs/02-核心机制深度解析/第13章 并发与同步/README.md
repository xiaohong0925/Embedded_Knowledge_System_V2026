# 第13章：并发与同步

> 所属：第 二 部 核心机制深度解析
>
> BIEM：[I→E] | 核心问题：多核并发怎么不崩？

## 核心问题

多核并发怎么不崩？

## 为什么需要这一章

有经验的工程师知道并发需要加锁、知道 spinlock 和 mutex 的区别、会用锁保护共享数据。但面对"系统随机崩溃、dmesg 显示无法复现的 oops""加了锁但数据仍然不一致""lockdep 报告了什么警告"这些问题时，缺乏源码级的理解就只能靠猜。

本章要建立的核心认知是：并发 bug 不是"少加了一把锁"这么简单——**80% 的并发 bug 来自对锁的适用范围和使用上下文的误解**。理解每种同步原语的精确语义、适用上下文和限制条件，是编写在任何场景下都能正确工作的并发代码的基础。

## 本章主线：一个竞态从产生到被消灭的完整链条

处理并发问题有一条固定的方法论链条：**先识别竞态从哪来，再选对原语，再写对内存序细节，最后用工具验证**。本章的七节正是这条链条的逐环展开——前六节各补一环，第七节把链条完整走一遍：

```
一个竞态的生命周期
 │
 ├─ 13.1 识别：谁在什么上下文中访问什么数据？
 │
 ├─ 13.2 选原语：spinlock 还是 mutex ──┐
 │   13.5 补充：rwlock/seqlock/per-cpu/completion
 │
 ├─ 13.3 写对细节：原子操作、内存屏障、伪共享
 │
 ├─ 13.4 进阶：读多写少时用 RCU 去掉读端的锁
 │
 ▼
13.6 验证：lockdep / KASAN / KCSAN ──> 13.7 实战：把链条走一遍
```

| 小节 | 链条这一环要回答的问题 | 为什么必须深入这些细节 | 对应的典型故障/场景 |
|------|----------------------|----------------------|--------------------|
| **13.1 竞态识别** | 这段代码的并发来源有哪几种？共享数据是谁？ | 并发来源有四类：多线程、中断、底半部、SMP。来源没识别全，锁就加不对——这是所有并发 bug 的起点 | 随机崩溃、无法复现的 oops |
| **13.2 spinlock/mutex** | 该用哪种锁？持有锁时能做什么、不能做什么？ | 两者的根本区别是适用上下文而非"忙等 vs 睡眠"：持有 spinlock 时不能睡眠，mutex 只能在进程上下文。spin_lock_irqsave() 防的是中断嵌套取同一把锁的死锁 | `scheduling while atomic`、软死锁 |
| **13.3 原子操作与内存屏障** | 不加锁的原子操作，为什么多核上仍可能看到旧值？ | ARM64 的 LDXR/STXR 实现原子性，但 CPU 乱序执行和编译器优化会重排内存访问。smp_mb()/READ_ONCE()/WRITE_ONCE() 是无锁代码正确的底线 | 加了"锁"数据仍不一致、偶发逻辑错误 |
| **13.4 RCU** | 读多写少的场景，能不能让读者完全无锁？ | RCU 读者零开销、写者复制替换、grace period 延迟回收。不理解宽限期和读者不能睡眠的约束，就会把 RCU 用出 use-after-free | 路由表等高并发读路径的锁竞争 |
| **13.5 补充原语** | 读写锁、seqlock、per-cpu、completion 各自补什么空缺？ | rwlock 在读多写少时退化、seqlock 适合极短读临界区、per-cpu 消灭伪共享竞争、waitqueue/completion 处理"等待事件"而非"保护数据" | 场景与原语错配导致的性能问题 |
| **13.6 验证工具** | 怎么证明并发代码是对的、bug 出在哪？ | lockdep 记录锁获取顺序检测循环依赖与 irq-safe 混用，KASAN 查 use-after-free，KCSAN 查 data race。不会用这三件工具，并发 bug 就只能靠运气撞 | AB-BA 死锁、lockdep 警告看不懂 |
| **13.7 综合实战** | 面对一个真实的并发崩溃，链条怎么走？ | 把前六节的方法论落到一个完整排查案例中，验证闭环 | 压力测试下的偶发崩溃排查 |

> 💡 读每一节之前，先回到这张表确认"这一节补的是链条的哪一环"。并发知识不是并列的清单，脱离链条单独记某个 API 的用法没有意义。

## 排错索引：从症状反查小节

本章的排错价值可以直接按症状反查：

```
随机 oops / paging request    → 13.1.1 / 13.6.2，用 KASAN/KCSAN 定位 data race 或 use-after-free
BUG: scheduling while atomic  → 13.2.1 / 13.2.3，查原子上下文中调用了可能睡眠的函数
系统无响应 / softlockup       → 13.2.4 / 13.6.1，lockdep 报告 circular locking dependency
加了锁数据仍不一致            → 13.3.2 / 13.3.3，查内存序与编译器优化
高并发下性能反而下降          → 13.3.4（伪共享）/ 13.4.1（RCU 替代 rwlock）
锁太多不知该用哪种            → 13.2.3，按上下文走选择决策树
```

## 学习目标

能对任意一段内核/驱动代码列出全部并发来源，按上下文选择正确的同步原语，并用 lockdep/KASAN/KCSAN 验证并发正确性。

## 与前后章的关联

- **第 8 章 进程与调度**：调度器决定任务何时执行，直接影响并发 bug 的触发概率；优先级继承依赖 rtmutex
- **第 9 章 内存管理**：Buddy/SLUB 分配器内部大量使用 spinlock，是分析内存路径性能的基础
- **第 10 章 中断与时间**：中断处理程序是主要并发来源，顶半部/底半部的拆分本质是并发管理
- **第 12 章 文件系统**：dentry cache 的 RCU 保护、inode 锁是本章原语的大规模应用实例
- **第 14 章 网络子系统**：收发包路径是内核最热的并发路径之一，SKB 引用计数与 socket 锁依赖本章机制
