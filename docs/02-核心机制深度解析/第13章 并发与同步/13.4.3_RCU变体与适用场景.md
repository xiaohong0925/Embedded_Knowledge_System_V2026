# 13.4.3 RCU变体与适用场景

> 所属章节：第13章 并发与同步 > 13.4 RCU
>
> 难度：[E] | 预计阅读时间：15分钟

## <span class="blue"> 本节导读

本节覆盖：v6.6 内核中的五种 RCU 变体（经典 RCU、PREEMPT_RCU、BH RCU、SCHED RCU、SRCU）各自的读者限制与适用场景，以及一张"RCU vs 锁 vs 原子操作"的选型指南。

---

## <span class="blue"> RCU变体大家族 [E]

Linux内核的RCU不是单一的实现，而是一个家族。不同变体对读者的限制不同，内核版本演进中也逐步加入了更多选择。下面是 v6.6 内核中主要的RCU变体：

### 经典RCU（Classic RCU）

这是最老也是最常用的版本。`rcu_read_lock()`本质上只是关抢占，`rcu_read_unlock()`开抢占。

```c
/* 经典RCU的读者侧 - 不能睡眠！ */
rcu_read_lock();           /* 关抢占 */
p = rcu_dereference(gp);   /* 安全读取指针 */
do_something_with(p);      /* 处理数据 */
rcu_read_unlock();         /* 开抢占 */
```

说白了，读者区就是一个禁止抢占的临界区。因为不能睡眠，所以效率极高。

> 💡 不确定就用经典RCU——覆盖90%的场景。这是内核代码里的默认选择。

### 可抢占RCU（PREEMPT_RCU）

配置项`CONFIG_PREEMPT_RCU=y`时启用（启用 `CONFIG_PREEMPT`/`PREEMPT_RT` 时自动选中）。读者**可以被抢占**，这意味着grace period的检测要复杂得多——内核需要跟踪每个CPU上被抢占的读者，确保所有可能持有RCU引用的任务都完成了。

PREEMPT_RCU让RCU在抢占式内核中也能安全工作，但grace period的延迟会稍微增加。

### BH RCU（Bottom-Half RCU）

```c
/* BH RCU - 关底半部，不是关抢占！ */
rcu_read_lock_bh();
p = rcu_dereference(gp);
/* ... 处理数据 ... */
rcu_read_unlock_bh();
```

`rcu_read_lock_bh()`关的是**软中断和底半部**，不是抢占。这招在网络收包路径特别管用——NAPI轮询、软中断处理函数里经常需要它。

### SCHED RCU

```c
/* SCHED RCU - 用于调度器代码路径 */
rcu_read_lock_sched();
/* ... 访问受保护数据 ... */
rcu_read_unlock_sched();
```

专门给**调度器代码**用的。在调度器上下文里，经典RCU的关抢占语义会有问题，SCHED RCU解决了这个尴尬。

### SRCU（Sleepable RCU）

这是RCU家族里最特殊的成员——**读者可以睡眠！**

```c
static struct srcu_struct my_srcu;

/* 初始化 */
init_srcu_struct(&my_srcu);

/* 读者侧 - 可以睡眠！ */
idx = srcu_read_lock(&my_srcu);
p = srcu_dereference(gp, &my_srcu);
/* ... 这里可以调用kmalloc(GFP_KERNEL) ... */
/* ... 可以获取互斥锁 ... */
/* ... 可以调度出去 ... */
srcu_read_unlock(&my_srcu, idx);

/* 写者侧 - 同步结束后清理 */
synchronize_srcu(&my_srcu);  /* 等待所有SRCU读者退出 */
kfree(old_p);
```

每个SRCU域（`struct srcu_struct`）**独立管理自己的grace period**，互不干扰。这是它跟经典RCU的关键区别。

但自由是有代价的：SRCU的读侧开销比经典RCU大（读侧要做每CPU计数器的原子增减），而且grace period的延迟也更长。

> ⚠️ 不要在经典RCU读者中睡眠！一旦睡眠，这个CPU就再也过不了grace period，`synchronize_rcu()`可能永远等不到头，写者被活活饿死。

---

### 五兄弟对比一览

| 变体 | 读者限制 | 核心API | 适用场景 | 读侧开销 | Grace Period检测方式 |
|------|---------|---------|---------|---------|-------------------|
| 经典RCU | 禁止抢占，不能睡眠 | `rcu_read_lock/unlock` | 通用读多写少 | 极低（一条指令） | 等待所有CPU经过quiescent state |
| PREEMPT_RCU | 可被抢占，但仍不能睡眠 | `rcu_read_lock/unlock` | 抢占式内核的通用场景 | 低 | 跟踪每个任务的抢占嵌套深度 |
| BH RCU | 禁止底半部 | `rcu_read_lock_bh/unlock_bh` | 网络收包、软中断路径 | 低 | 等待所有底半部完成 |
| SCHED RCU | 禁止调度 | `rcu_read_lock_sched/unlock_sched` | 调度器内部代码 | 低 | 等待调度点经过 |
| SRCU | **可以睡眠** | `srcu_read_lock/unlock` | 读者需分配内存、持锁 | 中等（每CPU计数） | 每个SRCU域独立等待 |

---

### RCU vs 锁 vs 原子操作选型指南

| 场景 | 推荐方案 | 理由 | 不推荐 |
|------|---------|------|-------|
| 读极多、写极少，读者不睡眠 | **经典RCU** | 读侧零开销，可线性扩展 | 读写锁（读侧有竞争） |
| 读者需要`kmalloc(GFP_KERNEL)` | **SRCU** | 允许睡眠，安全分配内存 | 经典RCU（睡眠=死锁） |
| 网络软中断/NAPI路径 | **BH RCU** | 语义匹配底半部模型 | 自旋锁（可能死锁） |
| 调度器内部数据结构 | **SCHED RCU** | 调度器上下文安全 | 经典RCU（语义冲突） |
| 读写频率差不多 | **读写锁/rwsem** | RCU写者代价太高 | RCU（写者需要等GP+复制） |
| 单个计数器增减 | **原子操作** | 最简单，开销最小 | RCU（杀鸡用牛刀） |
| 需要严格的写顺序保证 | **互斥锁+顺序控制** | RCU写者异步，顺序需额外保证 | 仅靠RCU |

```
选型决策树（ASCII图）：

                    开始选型
                      │
            ┌─────────┴─────────┐
            ▼                   ▼
      读多写少？           读写均衡？
            │                   │
       是 ◄─┤                   ├─► 用 读写锁/rwsem
            │                   │
            ▼                   ▼
     读者需要睡眠？        单个变量？
            │                   │
      是 ◄──┤                是 ├─► 用 原子操作
            │                   │
            ▼                   ▼
       用 SRCU            需要严格顺序？
            │                   │
       否 ◄─┤                是 ├─► 用 互斥锁
            │                   │
            ▼                   ▼
    网络/软中断路径？      通用场景
            │                   │
      是 ◄──┤                   ├─► 用 经典RCU
            │
            ▼
       用 BH RCU
```

> 💡 一个数据结构可以混用多种保护方式。读侧用RCU保证并发安全，写侧用互斥锁串行化，这是内核里常见的模式。

## <span class="blue"> 本节总结


RCU 家族的选型按"读者需要多大自由度"排开：经典 RCU 是默认选择，读者不能睡眠，开销最低；PREEMPT_RCU 在抢占式内核自动启用，无需显式选择；BH RCU 服务网络/软中断路径，关的是底半部而非抢占；SCHED RCU 是调度器代码专用，避免与调度上下文冲突；SRCU 允许读者睡眠，每个域有独立的 GP，代价是开销最大。

口诀收口：不确定就用经典 RCU；要睡眠用 SRCU；网络路径用 BH；调度器里用 SCHED。

核心要记住的是这族机制的定价逻辑：从经典 RCU 的"不能动"到 SRCU 的"可以睡"，读者的自由度逐级升高，开销逐级变大——选型从来不是选"最强的 RCU"，而是在自由度和性能之间找到刚好够用的那一档。
