## <span class="blue"> 知识点222 Netfilter性能开销与优化策略 [I]

### 性能开销从哪来？

每个数据包经过Netfilter时，要走一条相当复杂的"安检流程"。想象一下机场安检——你得过多个检查口，每个检查口有多条通道，每条通道还要逐项核对清单。Netfilter差不多就是这个感觉：

**钩子点遍历**：一个包最多可能经过5个钩子点（PREROUTING → INPUT/FORWARD → POSTROUTING，或者 OUTPUT 等路径组合）。

**表遍历**：每个钩子点可能挂载多个表（raw → mangle → nat → filter），包要逐个表检查。

**规则匹配**：每个表内的规则是线性遍历的，直到匹配某条规则的target为止。如果你有500条规则，而匹配发生在第499条……那就得遍历499次。

**连接跟踪（conntrack）**：每个包还要做一次哈希表查找，确认是否属于已有连接。这个哈希表的碰撞率直接影响性能。

把这几层开销叠加起来，你就能理解为什么规则多了以后CPU会"喘"了。

> 💡 **提示**：iptables规则是从上到下匹配的——把高频命中的规则放前面，能显著减少平均匹配次数。比如允许已建立连接的规则，通常应该放在最前面。

```bash
# 优化前：允许ESTABLISHED的规则放在后面，每条包都要先扫一堆规则
iptables -A INPUT -p tcp --dport 22 -j ACCEPT
iptables -A INPUT -p tcp --dport 80 -j ACCEPT
# ... 几十条规则 ...
iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT

# 优化后：已建立连接放最前面，大多数包直接命中
iptables -I INPUT 1 -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
iptables -A INPUT -p tcp --dport 22 -j ACCEPT
iptables -A INPUT -p tcp --dport 80 -j ACCEPT
```

### 五种优化策略

| 策略 | 具体方法 | 预期效果 | 适用场景 |
|------|----------|----------|----------|
| 规则排序 | 高频规则前移，ESTABLISHED放首位 | 减少30~60%平均匹配次数 | 所有iptables场景 |
| conntrack调优 | 增大hashsize、调整max和timeouts | 降低哈希碰撞，减少内存压力 | 高并发短连接场景 |
| 迁移nftables | 用nftables替代iptables | 原子更新、更好性能 | 新项目和规则重构 |
| 合并规则 | 把相似规则合并为一条 | 减少规则总数 | 规则高度重复时 |
| 使用ipset | 批量IP/端口匹配 | O(1)集合查找 vs O(n)线性匹配 | 大量IP黑白名单 |

### conntrack调优实战

连接跟踪的哈希表大小默认是根据内存自动计算的，但在嵌入式设备上往往不够。如果`conntrack -L`变得很慢，或者dmesg里出现"nf_conntrack: table full"，就该调了。

```bash
# 查看当前conntrack统计
cat /proc/net/nf_conntrack

# 调整哈希表大小（运行时）
echo 262144 > /sys/module/nf_conntrack/parameters/hashsize

# 调整最大连接数
echo 524288 > /proc/sys/net/netfilter/nf_conntrack_max

# 优化超时时间（嵌入式设备内存紧张时）
# 缩短TCP ESTABLISHED超时，让表项更快释放
echo 600 > /proc/sys/net/netfilter/nf_conntrack_tcp_timeout_established

# 写入/etc/sysctl.conf持久化
net.netfilter.nf_conntrack_max = 524288
net.netfilter.nf_conntrack_tcp_timeout_established = 600
```

### 从iptables迁移到nftables

nftables是Linux内核3.13+引入的新一代包过滤框架，它底层仍然基于Netfilter，但用户态接口完全不同。

| 对比项 | iptables | nftables |
|--------|----------|----------|
| 规则更新 | 逐条添加，非原子 | 整表原子替换 |
| IPv4/IPv6 | 两套独立规则 | 统一接口 |
| 规则组织 | 扁平列表 | 集合(set)、字典、流表 |
| 性能 | 线性匹配 | 可编译为内部字节码 |
| 内核接口 | 每个工具独立二进制 | 统一的netlink接口 |
| 维护状态 | legacy模式，逐渐冻结 | 积极开发，推荐迁移 |

```bash
# nftables基本规则示例：等价于iptables的filter规则
nft add table inet filter
nft add chain inet filter input { type filter hook input priority 0 \; policy drop \; }

# 允许已建立连接（利用集合快速匹配）
nft add rule inet filter input ct state established,related accept

# 允许SSH和HTTP
nft add rule inet filter input tcp dport { 22, 80 } accept

# 保存规则
nft list ruleset > /etc/nftables.conf
```

> ⚠️ **陷阱**：规则数量过多（5000+条）时，iptables性能会急剧下降。此时单纯排序优化已经不够，你应该考虑迁移到nftables（利用集合做O(1)匹配），或者如果只做简单ACL过滤，可以进一步考虑XDP/eBPF方案，直接在驱动层丢弃数据包，完全不进入Netfilter路径。

## <span class="blue"> 本节总结

| 要点 | 关键内容 |
|------|----------|
| 性能开销来源 | 钩子点遍历 × 表遍历 × 规则线性匹配 × conntrack哈希查找 |
| 最简优化 | ESTABLISHED规则放第一条，减少无效匹配 |
| conntrack调优 | hashsize和max根据连接数调整，超时时间根据场景缩短 |
| 规则数量大 | 用ipset做批量匹配，或迁移nftables |
| 终极方案 | 5000+规则考虑nftables；纯ACL场景可考虑XDP/eBPF |
