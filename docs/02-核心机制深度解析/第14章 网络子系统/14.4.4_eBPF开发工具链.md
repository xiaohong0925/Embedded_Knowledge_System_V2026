## <span class="blue"> eBPF开发工具链 [I]

### 完整的开发流程

eBPF程序的开发不像普通C程序那样"编译完直接跑"，它需要经过一条特殊的工具链流水线。这条链路由四个核心步骤组成，缺一不可。

**第一步：用clang编译C代码为BPF字节码。**

BPF虽然有自己的指令集，但你不需要手写字节码。clang从LLVM 3.7版本开始就内置了BPF后端，你可以直接用C语言编写，然后让clang帮你翻译：

```bash
# 编译BPF目标文件的典型命令
clang -O2 -g -target bpf -c prog.c -o prog.o

# 参数解释：
# -O2        开启优化，生成更紧凑的字节码
# -g         保留调试信息，方便后续bpftool查看源码映射
# -target bpf指定BPF后端，而不是x86/arm
# -c         只编译不链接
# -o prog.o  输出目标文件
```

编译产物`prog.o`是一个ELF格式的目标文件，里面包含了BPF字节码、map定义、程序段元数据等信息。这个ELF文件本身不能直接在CPU上执行——它要等内核验证器来检查和加载。

> ⚠️ **陷阱**：clang版本要足够新才能支持最新的BPF指令集。Linux内核5.x以后引入了不少新的BPF辅助函数和指令，如果你还在用LLVM 9以下的版本，编译出来的程序可能在内核加载时失败，报"invalid func unknown#XXX"之类的错误。建议至少使用LLVM 12+。

**第二步：用`ip link`将程序加载到网卡。**

对于XDP程序，最直观的加载方式是通过`ip link`命令，把BPF对象绑定到某个网卡：

```bash
# 将XDP程序加载到eth0网卡
ip link set dev eth0 xdp obj prog.o sec xdp

# 参数解释：
# dev eth0    目标网卡
# xdp         指定XDP模式（默认是原生模式）
# obj prog.o  BPF目标文件
# sec xdp     加载ELF中名为"xdp"的段（section）
```

XDP有多种挂载模式：

| 模式 | 命令写法 | 执行时机 | 性能 |
|------|----------|----------|------|
| 原生（Native） | `xdp` | 网卡驱动层 | 最高 |
| 通用（Generic） | `xdpgeneric` | 内核协议栈入口 | 中等 |
| 卸载（Offload） | `xdpoffload` | 网卡硬件 | 依赖硬件 |

原生模式性能最好，但并非所有驱动都支持。如果不确定，可以先尝试原生模式，失败了再回退到通用模式：

```bash
# 卸载XDP程序
ip link set dev eth0 xdp off

# 回退到通用模式加载
ip link set dev eth0 xdpgeneric obj prog.o sec xdp
```

**第三步：用`bpftool`查看已加载的程序。**

> 💡 **提示**：用`bpftool prog show`查看已加载的BPF程序。这个命令会列出所有BPF程序的类型、ID、运行次数、挂载点等关键信息，是排查"我的程序到底挂上没"的首选工具。

```bash
# 查看所有已加载的BPF程序
bpftool prog show

# 典型输出：
# 42: xdp  name my_xdp_prog  tag abcd1234  gpl
#     loaded_at 2024-01-15T08:23:11+0000  uid 0
#     xlated 512B  jited 1024B  memlock 4096B
#     map_ids 10,11
#     btf_id 5
```

**第四步：用`bpftool`导出和审查字节码。**

有时候你需要确认内核最终看到的BPF指令到底长什么样——比如排查一个验证器拒绝的问题，或者想对比优化前后的差异。`bpftool prog dump`可以帮你：

```bash
# 以可读格式导出已加载程序的指令（通过ID）
bpftool prog dump xlated id 42

# 同时显示对应的C源代码（需要编译时加-g）
bpftool prog dump xlated id 42 linum

# 查看JIT编译后的机器码
bpftool prog dump jited id 42

# 导出为可视化图（需要graphviz）
bpptool prog dump xlated id 42 visual &> prog.dot
```

下面这张表格汇总了整个工具链的核心组件：

| 工具 | 用途 | 典型命令示例 | 适用阶段 |
|------|------|-------------|---------|
| clang | 编译C→BPF字节码 | `clang -O2 -target bpf -c prog.c -o prog.o` | 开发/编译 |
| ip link | 加载XDP程序到网卡 | `ip link set dev eth0 xdp obj prog.o sec xdp` | 部署/加载 |
| bpftool | 查看/导出/调试BPF程序 | `bpftool prog show` / `bpftool prog dump xlated` | 调试/运维 |
| bpftool | 操作BPF map | `bpftool map show` / `bpftool map lookup` | 调试/运维 |
| bpftool | 生成skeleton头文件 | `bpftool gen skeleton prog.o > prog.skel.h` | 开发/编译 |

### libbpf库：简化BPF开发的C库

上面的手动流程（clang编译 → ip link加载 → bpftool查看）每一步都要敲命令，而且BPF程序里的map声明、重定位符号等细节都要自己处理。`libbpf`库的出现就是为了把这些繁琐工作自动化。

libbpf是一个用户空间的C库，提供了几层关键抽象：

```c
/* 使用libbpf加载BPF程序的基本骨架 */
#include <bpf/libbpf.h>
#include "prog.skel.h"  /* bpftool生成的skeleton头文件 */

int main(void)
{
    struct prog_bpf *skel;
    int err;

    /* 打开并加载BPF程序——自动处理map创建和重定位 */
    skel = prog_bpf__open_and_load();
    if (!skel) {
        fprintf(stderr, "Failed to open and load BPF skeleton\n");
        return 1;
    }

    /* 附加到XDP hook点 */
    err = prog_bpf__attach(skel);
    if (err) {
        fprintf(stderr, "Failed to attach BPF program\n");
        goto cleanup;
    }

    /* ... 程序运行期间 ... */

    /* 清理：自动卸载程序、销毁map */
cleanup:
    prog_bpf__destroy(skel);
    return err < 0 ? -err : 0;
}
```

libbpf最核心的价值在于**skeleton模式**：在编译阶段，bpftool读取`prog.o`中的BPF字节码和元数据，生成一个C头文件`prog.skel.h`。这个头文件里包含了BPF程序的二进制字节码和内联加载逻辑。到了运行时，你的用户态程序只需要调用`prog_bpf__open_and_load()`，库就会自动完成所有bpf()系统调用——创建map、加载字节码、处理重定位，一气呵成。

```bash
# 生成skeleton头文件的命令
bpftool gen skeleton prog.o > prog.skel.h
```

这种模式的优点是**零外部依赖**：运行时不需要`prog.o`文件，所有BPF代码都已经内嵌在最终的可执行文件里。这在嵌入式场景中特别实用——你的设备出厂时只需要一个二进制程序，不需要附带BPF对象文件。

### BCC：Python/C++封装的高级前端

libbpf适合追求性能和部署简洁性的场景，但如果你只是想快速写一个原型、抓个包看看、或者调一下延迟分布，每次都要写C代码+Makefile+skeleton，未免太沉重。

BCC（BPF Compiler Collection）提供了更高层的抽象，让你用Python（或C++）就能写eBPF程序：

```python
#!/usr/bin/env python3
# 用BCC编写一个简单的XDP程序
from bcc import BPF

# BPF程序直接写在Python字符串里
bpf_text = """
#include <uapi/linux/if_ether.h>

int xdp_drop(struct xdp_md *ctx) {
    return XDP_DROP;  // 简单粗暴：丢弃所有包
}
"""

# 编译并加载
b = BPF(text=bpf_text)
fn = b.load_func("xdp_drop", BPF.XDP)

# 附加到eth0
BPF.attach_xdp("eth0", fn, 0)

print("XDP drop program attached. Press Ctrl+C to exit.")
try:
    b.trace_print()
except KeyboardInterrupt:
    pass
finally:
    # 卸载时自动清理
    BPF.remove_xdp("eth0", 0)
```

BCC的魔力在于：**BPF程序以字符串形式嵌入Python代码中**，BCC在运行时调用clang临时编译、自动加载、自动创建map，并通过Python接口暴露出来。你不需要手写任何加载逻辑。

BCC内置了大量现成工具，覆盖网络、存储、调度等多个子系统：

- `tcptop` —— 按进程统计TCP发送/接收的吞吐量
- `biolatency` —— 块I/O延迟分布直方图
- `execsnoop` —— 追踪新进程创建
- `funccount` —— 统计内核函数的调用次数

这些工具本身就是很好的学习素材，它们的源码在BCC仓库的`tools/`目录下，你可以直接阅读和修改。

### 工具选择：根据场景选对武器

eBPF生态里有三套主流开发工具，各自有明确的适用边界：

| 工具 | 语言 | 特点 | 适用场景 |
|------|------|------|---------|
| libbpf | C | 编译时生成skeleton，运行时无外部依赖，性能最优 | 生产环境部署、嵌入式设备 |
| BCC | Python/C++ | 运行时编译，开发迭代快，内置丰富工具集 | 快速原型、调试、一次性脚本 |
| bpftrace | 类AWK脚本 | 语法极简，一行命令搞定常见追踪 | 命令行交互调试、快速排查 |

选型的核心原则是：**离生产越近，越偏向libbpf；离调试越近，越偏向BCC/bpftrace。**

在实际项目中，团队的典型工作流是这样的：先用BCC或bpftrace快速验证想法、确认hook点、采集数据做分析；方案成熟后，再用libbpf重写为C代码，集成到正式的产品二进制中。这种"先用Python跑通，再用C固化"的分层策略，既保留了开发效率，又保障了上线质量。

```
┌─────────────────────────────────────────────────────────┐
│                    eBPF 开发工作流                        │
├─────────────────────────────────────────────────────────┤
│  原型验证 ──► 生产开发 ──► 部署上线                       │
│     │           │            │                          │
│     ▼           ▼            ▼                          │
│  ┌──────┐   ┌──────┐   ┌─────────┐                     │
│  │ BCC/ │   │libbpf│   │ 编译为  │                     │
│  │bpftra│   │+ C   │   │ 单个二进制│                     │
│  │ -ce  │   │代码  │   │ 无外部依赖│                     │
│  └──────┘   └──────┘   └─────────┘                     │
│  (1~2小时)  (1~2天)    (长期运行)                        │
└─────────────────────────────────────────────────────────┘
```

## <span class="blue"> 本节总结

| 要点 | 内容 |
|------|------|
| 编译 | `clang -O2 -target bpf -c prog.c -o prog.o`，LLVM 12+才能支持新内核特性 |
| 加载 | `ip link set dev eth0 xdp obj prog.o sec xdp`，原生模式性能最高 |
| 查看 | `bpftool prog show`列出所有BPF程序，`prog dump xlated`导出指令 |
| libbpf | C库+skeleton模式，编译时嵌入字节码，运行时无依赖，适合生产 |
| BCC | Python/C++前端，运行时编译，内置丰富工具，适合原型和调试 |
| bpftrace | 类AWK脚本语言，极简语法，适合命令行快速追踪 |
| 选型原则 | 原型用BCC，生产用libbpf，调试用bpftrace |
