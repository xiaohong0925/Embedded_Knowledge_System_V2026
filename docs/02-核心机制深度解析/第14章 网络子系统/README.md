## 核心问题

网络包怎么走？

## 为什么需要这一章

有经验的工程师会用 ifconfig/ip 配置网络、会用 tcpdump 抓包、会写 socket 程序。但面对"高负载下丢包怎么排查""NAPI 到底做了什么优化""XDP 和 eBPF 是什么关系""网络栈的瓶颈在哪一段"这些问题时，缺乏源码级的理解就只能靠猜。

本章要建立的核心认知是：网络栈不是"一个管道"——**它是一条多阶段流水线，每个阶段都有独立的优化空间和瓶颈特征**。理解 SKB 在栈内的旅程、NAPI 如何保护 CPU 不被中断淹没、XDP 如何在驱动层就做出转发决策，是优化嵌入式网络设备性能的关键。

## 本章主线：一个数据包的收包路径与它的抄近道方案

本章以一个数据包从网卡到 socket 的完整收包路径为主线（发包路径反向对称）。14.1 先解决"包在内核里长什么样"，然后沿路径自下而上：入口引擎 NAPI、路径上的关卡 Netfilter、终点的 socket 缓冲区；14.4 到 14.6 是三个层次的"抄近道与分流"方案——在驱动层拦截、在路径上合包、把流量分到多核：

```
收包路径（发包路径反向对称）

网卡
 │ 中断 → 14.3 NAPI：批量收包，保护 CPU 不被中断淹没
 ▼
驱动层 ── 14.4 XDP/eBPF：在这里就可以 DROP/TX/REDIRECT，绕过协议栈
 │ 14.1 sk_buff：包的载体贯穿全程，skb_push/pull 实现零拷贝分层
 ▼
协议栈分层处理（L2→L3→L4）
 │ 14.2 Netfilter：五个钩子点逐关卡卡
 │ 14.5 GRO：路径上把同流小包合并（发包侧对应 GSO）
 ▼
14.6 RSS/RPS/RFS：把不同流的包分到不同 CPU
 ▼
14.3.3 socket 缓冲区 ──> 应用 read()
```

| 小节 | 路径这一站要回答的问题 | 为什么必须深入这些细节 | 对应的典型故障/场景 |
|------|----------------------|----------------------|--------------------|
| **14.1 sk_buff** | 包在内核里以什么结构存在、怎么流动？ | SKB 的 head/data/tail 指针操作让分层处理不需要复制数据，克隆与拷贝、引用计数决定了谁能动这个包。不懂 SKB 就读不懂网络栈的任何一段代码 | 改驱动时 skb 生命周期错误导致崩溃 |
| **14.2 Netfilter** | 路径上哪些位置可以拦截和处理包？ | 五个钩子点（PRE_ROUTING/LOCAL_IN/FORWARD/LOCAL_OUT/POST_ROUTING）的精确位置决定 iptables/nftables 规则何时生效；conntrack 的状态维护是所有 NAT/防火墙的基础 | 规则配了不生效、NAT 后回包异常 |
| **14.3 NAPI** | 高负载时收包引擎怎么不被中断淹没？ | 传统每包一中断在高负载下会把 CPU 打满。NAPI 的"中断触发一次→关中断→轮询批量收→配额耗尽再开中断"混合模式是吞吐与延迟的权衡旋钮 | 高负载丢包、中断风暴、控制任务被延迟 |
| **14.4 XDP/eBPF** | 能不能不进协议栈就把包处理掉？ | XDP 在驱动层执行 eBPF 程序，DROP/PASS/TX/REDIRECT 四种动作对应四条出路；eBPF 验证器保证程序安全，BPF maps 实现内核与用户空间共享数据 | iptables 规则多导致延迟高、需要线速过滤 |
| **14.5 GRO/GSO** | 路径上的合包/拆包卸载带来什么、埋什么坑？ | GRO 在收包路径合并同流小包、GSO 在发包路径延迟分段，两者提升吞吐但会改变抓包看到的包形态——不知道这点会误判问题 | tcpdump 抓到的"巨型包"、卸载相关丢包 |
| **14.6 多核分发** | 多核 SoC 上，包怎么分到对的 CPU 上？ | RSS（网卡硬件分流）、RPS/RFS（软件分流与流跟踪）、中断亲和性共同决定哪个核处理哪个流，分不好就是一个核打满其他核看戏 | 单核 100% 而其他核空闲、流内乱序 |
| **14.7 综合实战** | 真实丢包问题怎么定位到路径的哪一段？ | 把前面各段的排查工具（ethtool/nstat/perf/dropwatch）组织成分层定位流程 | UDP 高负载丢包的完整排查 |

> 💡 读每一节之前，先回到这张表确认"包此刻走到了路径的哪一站"。网络问题排查的本质就是沿路径逐站确认"包是在哪一站丢的、慢的"。

## 排错索引：从症状反查小节

本章的排错价值可以直接按症状反查：

```
高负载丢包、CPU 却不高     → 14.1.1 / 14.3.3，先查 ethtool -S 的 ring buffer 溢出
每包一中断、CPU 被打满     → 14.3.1 / 14.3.2，切 NAPI 并调 budget
iptables 规则多时延迟高    → 14.2.3 / 14.4.2，评估用 XDP 做前置过滤
Recv-Q 堆积                → 14.3.3，应用读得慢或 socket 缓冲区太小
流量全压在一个 CPU 上      → 14.6.1 / 14.6.2，配 RSS/RPS 与中断亲和性
抓包看到的包形态异常       → 14.5.2，检查 GRO/GSO/TSO 等卸载是否开启
定位不到丢包点             → 14.7.1，perf record -e skb:kfree_skb 统计丢包原因
```

## 学习目标

能沿收包路径从网卡中断追踪到 socket 缓冲区，并定位任意一层的丢包或性能瓶颈；能根据场景在 Netfilter、NAPI 调参、XDP 之间选择合适的优化手段。

- **第 9 章 内存管理**：SKB 的分配使用 kmem_cache，大流量下 SKB 分配可能成为瓶颈
- **第 10 章 中断与时间**：收包由硬件中断触发，NAPI 在 softirq 上下文执行，中断亲和性直接影响网络性能

- **第 15 章 电源管理**：网卡的 Runtime PM 需要在有流量时保持唤醒，WOL 与 autosuspend 需要与网络栈协同
