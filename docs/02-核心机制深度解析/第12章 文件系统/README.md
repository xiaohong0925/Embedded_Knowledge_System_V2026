## 核心问题

数据怎么存？

## 为什么需要这一章

有经验的工程师知道 ext4 是常用文件系统、知道 Flash 有擦写次数限制、知道要用 fsync 保证数据落盘。但面对"选 ext4 还是 f2fs 还是 UBIFS""掉电后文件系统损坏怎么恢复""为什么写小文件特别慢"这些问题时，缺乏源码级的理解就只能靠猜。

本章要建立的核心认知是：文件系统选择不是"哪个好"的问题，而是**存储介质、读写模式、可靠性需求三者的匹配问题**。断电安全也不是文件系统自己的事——它是从应用层（fsync 策略）到页缓存（回写策略）到文件系统（journal 模式）到存储介质（FTL/MTD）的全链路设计，任何一环薄弱都会成为短板。

## 本章主线：一次 write() 从应用到 Flash 的数据旅程

一次 `write()` 调用返回，不代表数据到了 Flash——它可能还躺在内存里。本章的五节正是沿着这次写操作的数据旅程逐站展开，每一站都要回答"数据现在在哪、下一步去哪、在哪里可能丢"：

```
write()
 │
 ▼
12.1 VFS 统一接口 ──> 12.2 页缓存 ──> 12.3 文件系统 ──> 12.4 MTD/Flash ──> 介质
 四个核心对象          dirty page       数据如何组织       擦除块与磨损     NAND/eMMC
                          │
                          └── 回写之前断电，数据就会丢
                              → 12.5 断电安全：每一环各出一道防线
```

| 小节 | 数据旅程这一站要回答的问题 | 为什么必须深入这些细节 | 对应的典型故障/场景 |
|------|--------------------------|----------------------|--------------------|
| **12.1 VFS** | write() 进来后，内核怎么把请求路由到具体文件系统？ | super_block/inode/dentry/file 四个对象是所有文件操作的载体。不理解 VFS 操作表如何对接具体文件系统，就看不懂任何一层文件系统的源码 | 挂载失败、/proc/mounts 字段看不懂 |
| **12.2 页缓存与回写** | 数据写到内存后，什么时候、以什么条件真正落盘？ | dirty page 的生命周期和 dirty_ratio/dirty_expire_centisecs 两个回写条件，决定了"写性能"和"断电风险"这两个互相打架的目标如何平衡；fsync() 到底强制了什么也必须从这里理解 | 写性能波动大、sync 后数据仍然丢失 |
| **12.3 ext4/f2fs/UBIFS** | 落到文件系统层，数据以什么结构组织？journal/LFS/UBIFS 各自保证什么？ | 三种文件系统的内部结构差异（ext4 的 extent 与 journal、f2fs 的 LFS 与 GC、UBIFS 的 LEB 与原子更新）直接决定了断电时损失什么、恢复要多久、eMMC 磨损多快 | 掉电后 fsck 修复时间长、写小文件慢、eMMC 寿命衰减快 |
| **12.4 MTD/UBI** | 裸 NAND 没有块设备层，数据最后怎么写进 Flash？ | MTD 以擦除块为单位、必须先擦后写，与块设备是两种世界观。UBI 的磨损均衡和坏块管理决定了裸 Flash 的实际寿命，ubiformat/ubiupdatevol 是量产烧录的必备工具 | 裸 NAND 上坏块处理、卷容量规划错误 |
| **12.5 断电安全** | 断电发生在旅程的哪一环，各用什么手段兜住？ | 断电安全是全链路设计：应用层双写+原子 rename、文件系统层 data=journal 与 barrier、块层 cache flush、硬件层电容续电。只配一环等于没配 | 断电后文件系统损坏、配置文件半写丢失 |
