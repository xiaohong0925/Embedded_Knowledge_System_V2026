## <span class="blue"> 本节导读

系统进入`suspend`状态后，谁来负责"叫醒"它？如果一个用户空间程序正在后台做重要的事情，系统又凭什么"赖着不睡"？这两个问题分别对应**唤醒源（Wakeup Source）**和**Wakelock/Wakeup Source机制**。本节将带你理解Linux电源管理中最关键的"开关"——谁有权阻止系统休眠，以及谁能把系统从睡梦中唤醒。

## <span class="blue"> 唤醒源：让系统从睡梦中醒来 [I]

当SoC进入深度休眠（`mem`或`disk`）后，几乎所有外设和CPU核心都已停止工作。要让系统恢复运行，必须依赖特定的**唤醒源（Wakeup Source）**。常见的唤醒源包括网络唤醒（WOL）、GPIO中断、RTC闹钟等。

### 唤醒源的类型与配置

| 类型 | 配置路径/命令 | 适用场景 | 示例 |
|------|-------------|---------|------|
| GPIO中断 | `/sys/devices/.../power/wakeup` | 按键触发、传感器事件 | 电源键按下唤醒 |
| RTC Alarm | `/sys/class/rtc/rtcN/wakealarm` | 定时任务、周期性唤醒 | 每5分钟采集一次传感器数据 |
| WOL (Wake-on-LAN) | `ethtool -s eth0 wol g` | 远程管理、网络唤醒 | 服务器远程开机 |
| USB Remote Wakeup | `/sys/bus/usb/.../power/wakeup` | USB外设事件 | USB键盘/鼠标唤醒 |
| UART中断 | 设备树`wakeup-source`属性 | 串口指令唤醒 | 调试接口远程唤醒 |

<br>

每个设备的唤醒能力可以通过`sysfs`独立控制：

```bash
# 查看系统当前注册的唤醒源总数
cat /sys/power/wakeup_count
# 输出示例：7

# 查看某个设备是否具备唤醒能力
cat /sys/devices/platform/gpio-keys/power/wakeup
# 输出：enabled  或  disabled

# 启用/禁用特定设备的唤醒功能
echo enabled > /sys/devices/platform/gpio-keys/power/wakeup
echo disabled > /sys/devices/platform/gpio-keys/power/wakeup
```

> ⚠️ **陷阱**：某个设备的唤醒功能被禁用后，即使硬件上产生了中断信号，也无法唤醒系统。排查"suspend后无法唤醒"问题时，第一步应该检查对应设备的`power/wakeup`状态。

### RTC Alarm唤醒配置

RTC（实时时钟）是最常用的定时唤醒源，特别适合需要周期性执行任务的嵌入式设备：

```bash
# 查看RTC设备列表
ls /sys/class/rtc/
# 输出：rtc0  rtc1

# 设置5秒后通过RTC0唤醒（单位：秒，从1970-01-01起算）
echo $(($(date +%s) + 5)) > /sys/class/rtc/rtc0/wakealarm

# 验证唤醒闹钟是否设置成功
cat /sys/class/rtc/rtc0/wakealarm
# 输出：1704067205

# 清除已设置的闹钟
echo 0 > /sys/class/rtc/rtc0/wakealarm
```

> 💡 **提示**：设置RTC唤醒闹钟后，立即执行`echo mem > /sys/power/state`。如果闹钟时间设置得当，你会在控制台看到系统被RTC中断唤醒的日志。

### Wake-on-LAN配置

对于以太网接口，可以通过WOL功能实现远程网络唤醒：

```bash
# 检查网卡是否支持WOL
ethtool eth0 | grep Wake-on
# 输出示例：
#   Supports Wake-on: pumbg
#   Wake-on: d        # 'd' = disabled

# 启用Magic Packet唤醒
ehtool -s eth0 wol g

# 验证配置生效
ethtool eth0 | grep Wake-on
# 输出：Wake-on: g    # 'g' = Magic Packet

# 从另一台机器发送Magic Packet唤醒
wakeonlan AA:BB:CC:DD:EE:FF
```

> 🔴 **危险**：WOL功能需要网卡PHY在系统休眠后继续供电（通常需要待机电源支持）。部分嵌入式板卡的硬件设计不支持WOL，此时无论软件如何配置都无法生效。

## <span class="blue"> Wakelock与Wakeup Source：谁阻止了系统休眠？ [I]

### 从Android Wakelock到主线Wakeup Source

早期Android为了阻止系统在后台任务执行期间自动休眠，引入了**Wakelock**机制。用户空间程序通过`acquire()`获取wakelock，系统suspend流程检测到存在活跃的wakelock时就会放弃休眠。这个机制虽然有效，但增加了主线内核的维护负担。

Linux 3.4之后，主线内核将wakelock重构为更通用的**Wakeup Source**框架。Android的wakelock变成了wakeup source的一种封装，但核心概念保持不变：

```
用户空间（Android）          内核空间
+----------------------------+----------------------------+
| acquire_wake_lock()        |  +----------------------+  |
|        |                   |  |   wakeup_source      |  |
|        v                   |  |   (active_count++)   |  |
| /sys/power/wake_lock       |  |        |             |  |
|        |                   |  |        v             |  |
|        +------------------>|  | pm_wakeup_pending()? |  |
| release_wake_lock()        |  |   -> true = 阻止suspend |
|        |                   |  +----------------------+  |
|        v                   |                            |
| /sys/power/wake_unlock    |  /sys/kernel/debug/        |
|                            |       wakeup_sources       |
+----------------------------+----------------------------+
```

### 查看活跃的Wakeup Source

`/sys/kernel/debug/wakeup_sources`是排查电源管理问题的核心工具，它展示了系统中所有已注册的wakeup source及其状态：

```bash
# 查看所有wakeup source的状态
cat /sys/kernel/debug/wakeup_sources

# 典型输出（已截断）：
# name            active_count event_count hit_count active_since last_change
# radio0            23         45          23        0            1234567890
# event0            0          120         0         0            1234568000
# alarm             5          10          5         0            1234569000
# usb1              1          2           1         1234570000   1234570000
```

### wakeup_sources关键字段解读

| 字段 | 含义 | 判断标准 |
|------|------|---------|
| `name` | Wakeup source的名称（驱动注册） | 用于定位具体驱动或子系统 |
| `active_count` | 被激活的总次数 | 值越大说明该源越频繁阻止休眠 |
| `event_count` | 产生唤醒事件的总数 | 反映该源的实际活跃度 |
| `hit_count` | 成功阻止suspend的次数 | `hit_count > 0`说明曾阻止过休眠 |
| `active_since` | 当前活跃状态的起始时间戳（ns） | 非0表示**当前正在活跃** |
| `last_change` | 最后一次状态变化的时间戳 | 用于判断最近一次活动距今多久 |

<br>

> 💡 **提示**：`/sys/kernel/debug/wakeup_sources`是排查suspend问题的利器。重点关注`active_since`字段非零的条目——这些就是当前正在阻止系统休眠的"罪魁祸首"。

### 实际问题排查

当系统无法自动进入`suspend`状态时，按以下步骤排查：

```bash
# 第一步：查看是否有wakeup source当前处于active状态
cat /sys/kernel/debug/wakeup_sources | awk '$5 != 0 {print}'

# 第二步：查看suspend/resume相关的内核日志
dmesg | grep -i -E "suspend|resume|wakeup"

# 第三步：检查某个具体设备的唤醒能力
cat /sys/devices/platform/serial0/power/wakeup

# 第四步：追踪autosuspend状态（如果是USB设备）
cat /sys/bus/usb/devices/1-1/power/autosuspend_delay_ms
```

> ⚠️ **陷阱**：某个内核模块（如蓝牙驱动、Wi-Fi固件）可能因bug持续持有wakelock而不释放，导致系统永远无法自动suspend。典型症状是`active_since`字段始终非零，且对应的`name`固定不变。此时可以通过`rmmod`卸载可疑模块验证。

### Wakelock问题的经典场景

```
场景：嵌入式设备夜间应该自动休眠省电，
      但电量持续消耗，无法进入低功耗。

排查过程：
    $ cat /sys/kernel/debug/wakeup_sources
    ...
    wlan0            12    50    12    1700000000000    1700000000000
    ...
    ↑ active_since非零，说明Wi-Fi驱动持有wakelock

    $ dmesg | grep -i suspend
    [  120.456] PM: Some devices failed to suspend
    [  120.457] PM: Wakeup source 'wlan0' blocking suspend

根因：Wi-Fi固件在扫描AP时未正确释放wakeup source。
解决：更新固件或在夜间时段禁用Wi-Fi扫描。
```

## <span class="blue"> 本节总结

| 知识点 | 核心内容 | 排查/配置命令 |
|--------|---------|-------------|
| 唤醒源类型 | GPIO、RTC、WOL、USB等可唤醒系统的中断源 | `cat /sys/power/wakeup_count` |
| RTC唤醒 | 通过`/sys/class/rtc/rtcN/wakealarm`设置定时唤醒 | `echo $(date +%s) > wakealarm` |
| WOL配置 | 需要网卡+PHY硬件支持，通过ethtool启用 | `ethtool -s eth0 wol g` |
| Wakelock → Wakeup Source | 阻止系统自动suspend的机制 | `cat /sys/kernel/debug/wakeup_sources` |
| 排查核心 | 找`active_since != 0`的条目，即当前阻止休眠的源 | `awk '$5 != 0'` |
| 日志排查 | suspend/resume流程的详细日志 | `dmesg \| grep -i suspend` |

本节的关键在于理解**"谁能唤醒"**和**"谁不让睡"**这两个互补的维度。唤醒源解决的是"suspend后如何恢复"，wakelock/wakeup source解决的是"什么时候不该睡"。两者配合，才能让嵌入式设备在"省得下电"和"唤得回来"之间找到平衡。
