# 15.4.2 Thermal Governor与设备树配置

>
> 难度：[E] Expert | 预计阅读时间：20分钟

## <span class="blue"> 本节导读

上一篇我们了解了Thermal Framework的整体架构。Sensor负责测温，Cooling Device负责降温——但谁来当"指挥官"，决定什么时候、按什么策略来调节温度？这就是 **Thermal Governor** 的角色。它读取传感器温度，根据预设策略选择合适的cooling state，实现闭环温控。同时，所有这些硬件关联和温度阈值，都需要通过**设备树**来描述。本篇将深入对比三种主流governor的优劣，并手把手教你写出一套完整的thermal设备树配置。

## <span class="blue"> 知识点251 [E]：三种Thermal Governor策略对比

### 三种Governor的核心机制

Thermal Governor是thermal framework的"大脑"。Linux内核提供了多种governor实现，其中最常用的三种如下：

**step_wise** —— 阶梯式调节，最简单直接。温度上升超过trip point → cooling state加1；温度回落 → cooling state减1。每次只迈一步，不跳级。这种线性推进的策略虽然不够"聪明"，但行为可预测、调试友好，是嵌入式平台的默认选择。

**fair_share** —— 公平分摊式。它会根据各个cooling device的降温能力（max_state），按比例分配降温负载。比如两个cooling device A和B，A的能力是B的两倍，那么A承担的state增量就是B的两倍。适合有多个异构cooling device的系统。

**power_allocator** —— 功耗分配式，最智能也最复杂。它基于**功耗模型**（Power Model），计算出当前需要降低多少功耗才能将温度拉回目标范围，然后将这个"降功预算"分配给各个cooling device。理论上效果最好，但前提是你有准确的功耗数据。

### 三种Governor对比

| Governor | 核心策略 | 复杂度 | 数据依赖 | 适用场景 |
|:---:|:---|:---:|:---|:---|
| **step_wise** | 温度上升+1 / 下降-1 | 低 | 无 | 单/少cooling device、无风扇嵌入式设备 |
| **fair_share** | 按cooling device能力比例分配负载 | 中 | cooling device的max_state | 多个异构cooling device的均衡降温 |
| **power_allocator** | 基于功耗模型计算降功预算并分配 | 高 | 功耗模型 + 动态功耗数据 | 高端移动设备、有精准功耗建模的系统 |

> 💡 **提示**：无风扇嵌入式设备（如工业网关、ARM单板机）强烈推荐 `step_wise` —— 简单可靠，不依赖额外数据，调试时一眼就能看出它在做什么。power_allocator虽然听起来很美好，但如果你的功耗模型不准，反而会"帮倒忙"。

### 如何选择Governor

选择governor的核心原则是：**先让系统work，再让系统smart**。

- 新项目起步 → 先用 `step_wise`，确认整条温控链路（sensor→thermal→cpufreq）跑通
- 多cooling device场景 → 尝试 `fair_share`，让各设备合理分担
- 有功耗建模团队支持 → 考虑 `power_allocator`，追求最优能效比

> ⚠️ **陷阱**：`power_allocator` 需要内核开启 `CONFIG_THERMAL_GOV_POWER_ALLOCATOR`，并且设备树中必须提供功耗相关属性。很多开发者看到它"最智能"就盲目选择，结果因为缺少功耗模型数据导致governor无法正常工作，温控完全失效。

## <span class="blue"> 知识点252 [E]：设备树Thermal配置详解

Thermal硬件关系全部通过设备树描述。核心是 `thermal-zones` 节点，内部包含 `trips`（温度阈值）和 `cooling-maps`（绑定关系）两个子系统。

### 节点结构

```
thermal-zones              ← 所有thermal zone的容器
└── cpu-thermal            ← 一个thermal zone实例
    ├── polling-delay-passive
    ├── polling-delay
    ├── thermal-sensors    ← 绑定温度传感器
    ├── trips              ← 温度阈值点集合
    │   ├── cpu_passive    ← passive trip：启动降温
    │   └── cpu_critical   ← critical trip：紧急关机
    └── cooling-maps       ← trip与cooling device的映射
        └── map0
```

### 完整设备树配置示例

以下是一个典型的ARM SoC CPU温控配置：

```dts
/ {
    /* ========== 1. 定义温度传感器（假设已存在） ========== */
    /* tsens: thermal-sensor@... { ... }; */

    /* ========== 2. 定义Cooling Device（cpufreq） ========== */
    /* cpufreq cooling device 由 cpufreq-dt 驱动自动注册 */

    /* ========== 3. Thermal Zone 主配置 ========== */
    thermal-zones {
        cpu-thermal {
            /* 被动轮询间隔：有trip触发时每隔250ms检查一次 */
            polling-delay-passive = <250>;
            /* 主动轮询间隔：无trip触发时每隔1000ms检查一次 */
            polling-delay = <1000>;
            /* 温度传感器引用 */
            thermal-sensors = <&tsens 0>;

            /* ---------- Trips：温度阈值 ---------- */
            trips {
                /* 被动降温点：70°C 开始降频 */
                cpu_passive: cpu-passive {
                    temperature = <70000>;    /* 毫摄氏度！70°C */
                    hysteresis = <2000>;      /* 回差2°C，防止抖动 */
                    type = "passive";         /* 类型：被动降温 */
                };

                /* 紧急关断点：95°C 直接关机 */
                cpu_critical: cpu-critical {
                    temperature = <95000>;    /* 毫摄氏度！95°C */
                    hysteresis = <0>;
                    type = "critical";        /* 类型：紧急关机 */
                };
            };

            /* ---------- Cooling Maps：绑定关系 ---------- */
            cooling-maps {
                map0 {
                    trip = <&cpu_passive>;    /* 引用passive trip */
                    cooling-device = <&cpu0 2 6>;
                    /* &cpu0: cpufreq cooling device phandle */
                    /* 2: 最低cooling state（对应最高频的节能档） */
                    /* 6: 最高cooling state（对应最低频） */
                };
            };
        };
    };
};
```

### 关键字段解析

| 字段 | 说明 | 注意事项 |
|:---|:---|:---|
| `temperature` | 触发温度 | **单位是毫摄氏度**（°C × 1000） |
| `hysteresis` | 温度回差 | 防止温度在阈值附近反复触发，避免抖动 |
| `type` | trip类型 | `passive` = 启动cooling device；`critical` = 系统关机 |
| `cooling-device` | 三元组 | `<phandle min-state max-state>`，state越大=降温越强 |

> ⚠️ **陷阱**：`temperature` 字段使用**毫摄氏度**（millicelsius），70°C 要写成 `70000`，而不是 `70`。这是设备树thermal配置中最常见的错误，一旦写错，trip point会在远低于预期温度时就触发，导致系统严重降频甚至意外关机。

### Trip Point工作原理

```text
温度 ────────────────────────────────────────────────►

     68°C   70°C               95°C
      │      │                  │
      ▼      ▼                  ▼
     ┌────────┐               ┌──────┐
     │ 正常   │    降温区     │ 关机 │
     │ 运行   │───────────────│      │
     └────────┘               └──────┘
              ▲              ▲
              │ hysteresis=2°C 回差保护
              └──────────────┘
              温度降至68°C才恢复（不是70°C）
```

温度升到70°C → 触发passive trip → cpufreq governor限制频率。温度回落时，因为有 `hysteresis = <2000>`，必须降到68°C以下才解除限制。这个"回差"机制非常关键，避免了温度在阈值附近来回震荡导致的频率抖动。

> 🔴 **危险**：`critical` 类型的trip point一旦触发，内核会立即调用 ` orderly_poweroff() ` 或 `kernel_halt()` 关闭系统。**不要滥用 critical** —— 它应该是最后一道防线（如95°C+），而不是常规降温手段。建议至少保留 passive → critical 的两级梯次结构。

## <span class="blue"> 本节总结

| 要点 | 核心内容 |
|:---|:---|
| Governor职责 | 读取sensor温度，按策略选择cooling state，实现闭环温控 |
| step_wise | 阶梯式±1调节，最简单可靠，嵌入式首选 |
| fair_share | 按cooling device能力比例分配负载，适合多设备系统 |
| power_allocator | 基于功耗模型智能分配，效果最好但依赖精准功耗数据 |
| thermal-zones节点 | 设备树thermal配置的顶层容器 |
| trips子节点 | 定义温度阈值点，包含temperature（毫摄氏度！）、hysteresis、type |
| cooling-maps子节点 | 将trip point绑定到cooling device，格式`<phandle min max>` |
| 典型两级架构 | passive trip（~70°C，降频）+ critical trip（~95°C，关机） |
