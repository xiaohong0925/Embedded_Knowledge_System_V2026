## <span class="blue"> schedutil vs ondemand：架构差异 [E]

ondemand是Linux老牌governor，它的工作方式简单粗暴：定时采样CPU使用率（`/proc/stat`），当使用率超过阈值就升频，低于阈值就降频。这个机制有几个天然缺陷：

- **采样延迟**：定时器周期通常是10ms~100ms，负载突变时反应慢半拍
- **精度有限**：只能看到"CPU忙不忙"，不知道"谁在忙、忙什么"
- **噪声敏感**：采样窗口内的突发负载容易被平滑掉

schedutil从Linux 4.7引入，彻底改变了这个模式。它不再自己采样，而是直接从**调度器的PELT（Per-Entity Load Tracking）**获取负载数据。

```
┌─────────────────────────────────────────────────────────────┐
│                    负载信息获取路径对比                        │
├─────────────────────────────┬───────────────────────────────┤
│       ondemand              │          schedutil             │
│                             │                                │
│   ┌──────────────┐         │    ┌──────────────────────┐    │
│   │  定时采样器   │         │    │   调度器PELT数据      │    │
│   │ (/proc/stat) │         │    │  (per-entity load)   │    │
│   └──────┬───────┘         │    └──────────┬───────────┘    │
│          │                  │               │                │
│          ▼                  │               ▼                │
│   ┌──────────────┐         │    ┌──────────────────────┐    │
│   │  CPU使用率    │         │    │   实体级负载信息      │    │
│   │   百分比     │         │    │  (util_avg / load_avg)│   │
│   └──────┬───────┘         │    └──────────┬───────────┘    │
│          │                  │               │                │
│          ▼                  │               ▼                │
│   ┌──────────────┐         │    ┌──────────────────────┐    │
│   │  阈值比较     │         │    │  sugov_update()回调   │    │
│   │  (up/down)   │         │    │   事件驱动调用        │    │
│   └──────┬───────┘         │    └──────────┬───────────┘    │
│          │                  │               │                │
│          ▼                  │               ▼                │
│   频率调整决策               │        频率调整决策             │
└─────────────────────────────┴───────────────────────────────┘
```

PELT是Linux调度器内部的负载追踪机制，它为每个调度实体（task、task group、CPU runqueue）维护一个**指数衰减加权移动平均**的负载值。这个值不是简单采样，而是每个tick都在更新，因此schedutil能做到：

- **事件驱动**：调度事件发生时立即更新频率，不需要轮询
- **毫秒级响应**：负载变化的感知延迟在1ms以内
- **精确到任务**：知道是哪些任务在贡献负载，区分计算密集和IO密集

| 特性 | ondemand | schedutil |
|------|----------|-----------|
| **负载来源** | `/proc/stat`定时采样 | 调度器PELT直接读取 |
| **响应速度** | 10~100ms（采样周期） | <1ms（事件驱动） |
| **负载精度** | CPU整体使用率百分比 | 实体级util_avg + load_avg |
| **更新机制** | 定时器轮询 | 调度事件回调 |
| **IO感知** | 无 | iowait boost支持 |
| **内核版本** | 2.6+ | 4.7+ |
| **推荐使用** | 旧系统兼容 | **新系统默认推荐** |

> 💡 **提示**：schedutil在Linux 4.7+是默认推荐的governor。如果你在做新系统设计，不需要犹豫，直接用schedutil。它已经被绝大多数主流发行版和Android设备采用。

## <span class="blue"> 三大核心机制深入 [E]

### 1. PELT负载映射

schedutil通过`sugov_update()`函数在每个调度事件点被调用。它读取当前CPU的`util_avg`，然后映射到频率：

```
freq_next = map_util_freq(util_avg, max_freq, capacity_orig)
```

`util_avg`是PELT计算出的CPU利用率（0~1024范围），映射是线性比例关系。这意味着schedutil能非常平滑地反映负载变化，没有ondemand那种"突然跳频"的阶梯感。

### 2. iowait boost —— IO等待时的临时升频

这是schedutil针对IO密集型场景的一个巧妙设计。当CPU处于**iowait状态**时（等待磁盘/网络IO完成），传统的governor会看到CPU"空闲"而降低频率。但此时应用实际上是在等IO，降频会导致IO完成后的处理变慢。

iowait boost的机制是这样的：

```
CPU状态检测：
├── 正常running → 按util_avg正常调频
├── idle状态  → 正常降频
└── iowait状态 → **临时升频到中间档/最高频**
         ↓
    IO完成后，升频状态会逐渐衰减
    （半衰期控制，避免突然掉频）
```

这个特性对以下场景特别有用：
- 数据库查询（等磁盘IO）
- Web服务器响应（等网络IO）
- 文件拷贝和解压（等存储IO）

### 3. rate_limit —— 频率调整的限速器

schedutil虽然响应快，但"快"不一定总是好事。如果负载在毫秒级剧烈波动，频率跟着上下抖动会带来两个问题：**功耗增加**（每次切频有开销）和**性能不稳定**（频率波动导致延迟抖动）。

rate_limit就是给频率调整加了一个"最小冷却时间"：

```
上次调整频率
     │
     ▼
┌──────────┐    rate_limit_us = 1000 (默认)
│  1ms内？  │ ──→ 是 → 跳过本次调整
│          │
└──────────┘ ──→ 否 → 允许调整
     │
     ▼
  执行频率变更
```

> ⚠️ **陷阱**：rate_limit设得太小（比如<500μs），会导致频率抖动。CPU负载稍有波动就切频，不仅增加功耗（频率切换本身有能量开销），还会导致性能基准测试结果波动很大。如果你发现性能测试结果方差很大，先检查rate_limit设置。

## <span class="blue"> schedutil调优参数与场景实践 [E]

schedutil的调优参数通过sysfs暴露，路径在 `/sys/devices/system/cpu/cpufreq/schedutil/` 下。

| 参数 | 默认值 | 建议值 | 作用说明 |
|------|--------|--------|----------|
| `rate_limit_us` | 1000 | 500~2000 | 频率调整最小间隔（微秒），限制调频速率 |
| `iowait_boost_enable` | 1 | 0或1 | 是否启用iowait boost（1=启用，0=禁用） |
| `hispeed_load` | 99 | 90~99 | （部分平台）快速升频阈值 |
| `hispeed_freq` | - | - | （部分平台）快速升频目标频率 |

不同平台的参数路径可能略有差异：

```bash
# 查看schedutil调优参数（路径因内核版本而异）
# 方式1：sysfs标准路径
cat /sys/devices/system/cpu/cpufreq/policy0/schedutil/rate_limit_us
cat /sys/devices/system/cpu/cpufreq/policy0/schedutil/iowait_boost_enable

# 方式2：部分内核版本路径
cat /sys/devices/system/cpu/cpufreq/schedutil/rate_limit_us

# 方式3：通过scaling_driver确认schedutil是否生效
cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_driver
# 输出：schedutil（说明当前governor是schedutil）
```

### 场景化调优

#### 场景A：交互式设备（手机、平板、HMI）

交互式设备要求触摸响应快、动画流畅。需要schedutil对负载变化更加灵敏。

```bash
#!/bin/bash
# 交互式设备调优：降低rate_limit，提升响应速度
# 对所有CPU policy生效

for policy in /sys/devices/system/cpu/cpufreq/policy*; do
    if [ -f "$policy/schedutil/rate_limit_us" ]; then
        # 降低rate_limit到500μs，让频率调整更灵敏
        echo 500 > "$policy/schedutil/rate_limit_us"
        echo "已设置 $policy/rate_limit_us = 500"
    fi
done

# 启用iowait boost，提升IO场景响应
echo 1 > /sys/devices/system/cpu/cpufreq/policy0/schedutil/iowait_boost_enable

# 验证设置
cat /sys/devices/system/cpu/cpufreq/policy0/schedutil/rate_limit_us
```

#### 场景B：服务器/边缘计算网关

服务器追求稳定，不需要极限响应速度。保持默认参数即可。

```bash
#!/bin/bash
# 服务器调优：保持稳定，防止频率抖动

for policy in /sys/devices/system/cpu/cpufreq/policy*; do
    if [ -f "$policy/schedutil/rate_limit_us" ]; then
        # 保持默认1ms，或略微提升到2ms增加稳定性
        echo 2000 > "$policy/schedutil/rate_limit_us"
    fi
done

# 如果服务器是纯计算型（无IO瓶颈），可关闭iowait boost节省功耗
echo 0 > /sys/devices/system/cpu/cpufreq/policy0/schedutil/iowait_boost_enable
```

#### 场景C：IO密集型嵌入式设备（NVR、工业采集）

这类设备频繁读写存储或网络，iowait boost是关键。

```bash
#!/bin/bash
# IO密集型设备调优：最大化IO吞吐

for policy in /sys/devices/system/cpu/cpufreq/policy*; do
    if [ -f "$policy/schedutil/rate_limit_us" ]; then
        # 适度降低rate_limit
        echo 750 > "$policy/schedutil/rate_limit_us"
    fi
    if [ -f "$policy/schedutil/iowait_boost_enable" ]; then
        # 务必启用iowait boost
        echo 1 > "$policy/schedutil/iowait_boost_enable"
    fi
done
```

> 💡 **提示**：实际调优时，建议用`perf`或`ftrace`对比调频事件频率。rate_limit调整前后，观察`cpufreq:cpu_frequency` trace点的触发密度，就能直观看到限速效果。

## <span class="blue"> 本节总结

| 主题 | 核心要点 |
|------|----------|
| **PELT负载来源** | schedutil直接从调度器获取`util_avg`，事件驱动、毫秒级响应 |
| **vs ondemand** | 无需定时采样，精度更高、延迟更低，4.7+推荐默认使用 |
| **iowait boost** | IO等待时临时升频，衰减回落，对IO密集型场景收益明显 |
| **rate_limit** | 限制频率调整最小间隔，防止抖动；默认1000μs |
| **交互式调优** | rate_limit降到500μs，提升灵敏度 |
| **服务器调优** | 保持默认或提高到2000μs，保证稳定性 |
| **IO密集型调优** | 启用iowait boost，适度降低rate_limit |
| **常见陷阱** | rate_limit太小→频率抖动→功耗和性能不稳定 |
