# 21.5 签名验证与更新策略

> 所属章节：第21章 OTA与更新架构设计
>
> 难度：[M] | 预计阅读时间：30分钟

## <span class="blue">本节导读

前四节把防线都建在"意外"上：断电、坏包、起不来。本节转向另一类威胁——**人**。恶意固件投毒、骗设备装回带漏洞旧版本的回滚攻击，这两种是外部攻击者干的；还有一种是自己人干的：周五下午对三千台设备点"全量发布"。

设备端的防线（A/B、回切）对这三类攻击全部无效：恶意固件如果验签通过，会被客客气气地写进 B 槽、切换、mark-good。对人的防线只有两道：**密码学（签名与防降级）和策略（灰度与时机）**。

> 本节覆盖：OTA 的 PKI 最小集（离线 CA → 签名密钥 → 设备 keyring）、openssl 到 `rauc bundle` 的完整签名命令链、密钥管理与轮换的纪律、回滚攻击与单调版本号、灰度分波的晋级判据与自动暂停、更新时机设计（充电窗口与电量门槛）、离线设备的迟到更新，以及"失败率 <0.1%"这个数字到底怎么度量。

## <span class="blue">PKI 最小集：三样东西 [M]

签名验证的全貌一句话：**构建端用私钥给更新包签名，设备端用预置的公钥验签，验不过就不装**。落地到 OTA 只需要三样东西：

> PKI 最小集（OTA 版）：① **离线根 CA**——一把离线保存的私钥和它的自签名证书，整个体系的信任根；② **签名密钥**——由根 CA 签发的签名证书和私钥，CI 流水线日常用它签包，泄露了可以由 CA 吊销重签；③ **设备 keyring**——设备上预置的 CA 证书（只有公钥，没有私钥），RAUC 用它验证"这个包的签名链是否通向我信任的根"。私钥永远不上设备，设备上只有公钥——这是整个体系的命门。

为什么是两层（CA + 签名密钥）而不是一把钥匙直接签？因为私钥会泄露——CI 服务器被入侵、离职工程师带走副本，都是要面对的剧本。两层结构下，日常暴露面只有签名密钥，泄露后的处置是"CA 签一把新的、下一次更新换掉设备 keyring 的信任链"；根 CA 离线保存（断网机器或 HSM），泄露概率压到最低。

### 生成命令链

```bash
# ① 根 CA（离线机器上执行一次，私钥封存）
openssl genrsa -out ca.key 4096
openssl req -x509 -new -nodes -key ca.key -sha256 -days 3650 \
    -out ca.cert.pem -subj "/CN=Robot OTA Root CA"

# ② 签名密钥（由 CA 签发，给 CI 用）
openssl genrsa -out signing.key 2048
openssl req -new -key signing.key -out signing.csr \
    -subj "/CN=OTA Signing 2026"
openssl x509 -req -in signing.csr -CA ca.cert.pem -CAkey ca.key \
    -CAcreateserial -out signing.cert.pem -days 365 -sha256

# ③ CI 流水线签 bundle（构建产物目录 → 签名后的 .raucb）
rauc bundle \
    --cert=signing.cert.pem \
    --key=signing.key \
    --keyring=ca.cert.pem \
    build/bundle-content/ \
    amr-rootfs-2.4.1.raucb
```

设备端一侧早就配好了——21.2 的 `system.conf` 里 `[keyring] path=/etc/rauc/ca.cert.pem`，CA 证书（公钥部分）随出厂镜像烧入。设备安装任何 bundle 前，RAUC 自动完成验签：bundle 内嵌 CMS 签名，签名证书必须能链到设备 keyring 里的根，且 manifest 里记录的每个镜像哈希与实际内容一致。验不过，安装根本不会开始。

> 💡 这条链上最容易被问的问题是"HTTPS 不也有加密吗"。TLS 保护的是**通道**（下载途中不被篡改），签名保护的是**产物**（这个包是不是我签的那个）。服务器被攻破时 TLS 完好无损但包是假的——两道防线管两个故障域，缺一不可。

## <span class="blue">密钥管理：比算法难的部分 [M]

算法和命令一天能配好，密钥管理是五年的纪律。四条：

1. **根 CA 离线**。断网机器或 HSM，只在签发/吊销签名密钥时启用。根私钥泄露 = 整个 OTA 体系信任根易主。
2. **签名密钥定期轮换**。哪怕没泄露也换（比如每年）。轮换动作本身是一次已签名的更新：新 bundle 里携带新的 keyring 信任链，用旧密钥签——旧密钥还有效时完成交接，这就是轮换窗口。
3. **轮换有 chicken-and-egg 窗口期**：新旧 keyring 交接的那次更新必须被所有在线设备吃到。有设备离线错过了轮换包，它之后的新包全部验签失败——这就是 21.5 后半"离线设备"必须和密钥轮换一起设计的原因。
4. **吊销要靠新版本而不是黑名单**：设备大多离线，实时 CRL 不现实。实际做法是轮换 keyring 后旧签名证书自然失效。

## <span class="blue">回滚攻击与防降级 [M]

签名验证挡不住回滚攻击——攻击者给的包是**官方签的真包**，验签完全通过，只是版本是带已知漏洞的旧版。装完设备裸奔，审计日志还一切正常。

防降级的机制是**单调版本**：设备记录"我见过的最高安全版本"，凡是低于它的包一律拒装。

```
版本号（2.4.1）        ← 人类读的，语义化，可比较大小但不防伪造语义
安全版本号（47）       ← 单调递增整数，每次安全相关发版 +1，永不回退
                        RAUC manifest 可携带，设备端策略拒装低于当前值的包
```

落地强度分两档：

- **软件档**：设备把最高安全版本存在 data 分区（或 U-Boot env），安装前比较。能挡住"骗装旧版"的常规攻击，但 data 分区被物理改写就失效。
- **硬件档**：eMMC 的 RPMB（Replay Protected Memory Block，重放保护分区）——一块带密钥认证和单调计数器的硬件存储区，写入需密钥、计数器物理上只增不减。安全版本存这里，拆机读改写也伪造不了。高安全等级产品（支付、车规）选这档。

> ⚠️ 防降级和"允许回滚"是矛盾的，要显式裁决。21.4 的 bootcount 回切是**系统自动回切到上一个已知好版本**——这在防降级视角下就是一次降级。工程上的裁决是：自动回切只在"新版本起不来"这一个出口发生（安全版本差 ≤1 且由启动链触发），业务层的"我想回退到上个版本"默认禁止、运维显式授权才放行。把矛盾摆在设计文档里，比假装它不存在强。

## <span class="blue">灰度发布：分波、晋级判据与自动暂停 [M]

第三种"人祸"是分发压垮加坏包放大：一个没测透的版本全量推给三千台，要么网络压垮，要么三千台同时出问题。灰度的本质是给"我不知道这个版本有没有问题"留一个**用最小代价发现问题的缓冲带**。

机器人公司的三波设计：

```
第一波：50 台   → 内部仓库 + 配合度高的客户现场，观察 48 小时
第二波：500 台  → 覆盖全部仓库类型（不同 Wi-Fi 环境、不同离线习惯），观察 72 小时
第三波：全量    → 剩余设备，按仓库分批，单仓库限并发 20 台
```

每一波的**晋级判据**必须事先写死，不能"看着办"：

| 判据 | 阈值 | 数据源 |
|:---|:---|:---|
| 安装成功率 | ≥ 99.9%（千分之一的容忍度在这落地） | 设备上报的安装结果 |
| 回切率 | < 0.5% | bootcount 回切事件上报 |
| 关键业务指标 | 导航成功率、任务完成率不劣于旧版基线 | 业务遥测 |
| 无新增 crash 类型 | crash 签名全部已知 | crash 上报 |

任何一条跌破阈值 → **自动暂停**，不依赖值班工程师的反应速度。hawkBit 的 rollout 功能原生支持这个模型：按设备组分波、每波带成功/失败阈值条件、条件不满足自动停。设备端 RAUC 的安装结果通过 hawkBit 的反馈通道回流，闭环在服务端完成。

> 💡 灰度还有一个隐性收益：它顺便做了差分更新（21.3）的压力测试。第一波 50 台的自适应下载量、失败率，就是全量前对"这个包在真实网络里表现如何"的最准预估。

## <span class="blue">更新时机：机器人不是服务器 [M]

服务器 OTA 的时机策略是"挑低峰期"。机器人多两个约束：**电池**和**任务**。

- **电量门槛**：电量低于 30% 不启动下载、低于 50% 不启动安装（写 B 槽是十分钟级的高功耗操作）；
- **充电窗口**：机器人回充电桩时是天然更新窗口——电量在涨、业务在停、Wi-Fi 信号通常最好（充电桩位置是设计过的）。更新调度策略"优先在充电窗口执行"；
- **任务互斥**：执行任务中的机器人只下载不安装，安装与重启排在任务结束回到充电桩之后；
- **强制窗口**：安全漏洞修复包（CRA 语境下这是法规义务）不受窗口限制，但必须保留"机器人停稳再装"的底线——安全与生产事故的权衡写进策略，不留给现场。

## <span class="blue">离线设备与失败率度量 [M]

**离线三周的设备上线了，怎么办？** 策略三要素：

1. **直接跳最新**：A/B 全量镜像天然支持任意版本跨越（装的是完整新系统，不依赖旧版）；这正是 21.3 里 adaptive 差分"不要求精确旧版本"的红利——bsdiff 路线在这里要维护逐级补丁链，离线设备越多越痛苦；
2. **密钥轮换兼容**：离线设备错过 keyring 轮换包的，先投递一个"过渡包"（旧密钥签、含新 keyring），再投新包——服务端要按设备 last-seen 版本记账；
3. **落后太多要人看**：离线超过 90 天的设备进人工清单——它可能不是离线，是坏了。

**失败率 <0.1% 怎么度量**——这个数字不写清楚度量口径就是口号：

```text
失败率 = 需要人工干预的设备数 / 本期更新触达的设备数

分子只算"变砖/人工到场"：自动回切成功的不算失败（那是机制在工作）
分母只算"触达"：离线下载没开始的不进分母
按版本、按波次、按仓库三个维度分别统计
```

注意分子的定义：自动回切不算失败。这条口径必须在评审时讲明——否则团队为了压低"失败率"会去收紧回切判据，方向完全拧了。**回切是防线在工作，不是防线被击穿。**

## <span class="blue">本节总结

对人的防线两道：密码学挡恶意包，策略挡自己人。PKI 最小集三样东西——离线根 CA、CI 用的签名密钥、设备上只含公钥的 keyring；TLS 管通道、签名管产物，缺一不可。密钥管理的五年纪律是离线、轮换、交接窗口，轮换和离线设备策略必须一起设计。

回滚攻击要靠单调安全版本号挡，软件档存 data 分区、硬件档上 RPMB；防降级与 bootcount 自动回切的矛盾要显式裁决（回切仅限"起不来"出口）。灰度三波带事先写死的晋级判据与自动暂停，时机策略贴合机器人特性（充电窗口、电量门槛、任务互斥、安全包的强制窗口）。失败率的口径决定团队行为：自动回切不算失败——回切是防线在工作。
