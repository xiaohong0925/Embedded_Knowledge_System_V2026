# 21.4 启动链配合与回滚：bootcount 机制落地

> 所属章节：第21章 OTA与更新架构设计
>
> 难度：[M] | 预计阅读时间：30分钟

## <span class="blue">本节导读

21.3 把新系统写进了 B 槽、启动项切了过去。现在问一个不舒服的问题：**B 槽起不来的时候，谁把它切回 A？**

注意这个问题的主语不能是"系统"——起不来的系统没有能力切回自己。能兜底的只有启动链里比内核更早、更简单、更难坏的那一段：Bootloader。第 7 章讲了 U-Boot 怎么把内核拉起来，但没讲 U-Boot 怎么判断"这次启动失败了"——这正是本节要自包含补上的机制：bootcount。

> 本节覆盖："起不来"的四种形态（决定回滚要兜到哪一层）、U-Boot bootcount 四变量怎么串成自动回切、RAUC 的 `BOOT_ORDER`/`BOOT_x_LEFT` 约定、mark-good 的时序设计（什么时候确认"这版是好的"才不算早也不算晚）、环境变量自身的可靠性（冗余 env），以及救砖的最后一道防线。

---

## <span class="blue">"起不来"是个连续谱 [M]

设计回滚之前，先把"起不来"拆成四种形态——它们的触发点不同，能兜底的层也不同：

| 形态 | 卡在哪 | 谁看得见 |
|:---|:---|:---|
| ① 内核起不来 | kernel 镜像损坏、dtb 不匹配、挂载 rootfs 失败 panic | 只有 Bootloader/硬件（内核没活到能说话） |
| ② 系统起不来 | 内核活了，systemd 起不来或根文件系统只读挂载失败 | 内核日志、看门狗 |
| ③ 业务起不来 | 系统活了，机器人导航进程 crash 循环 | systemd、业务自检 |
| ④ 业务"活了但不对" | 进程都在，但定位漂移、底盘无响应 | 只有业务层的健康检查 |

A/B 回滚能自动兜住的是 ①②③——它们的共同点是"系统自己知道没起来"。④ 最阴险：bootcount 计数器看一切都正常，只有业务知道不对。**这决定了 mark-good 不能在"系统 boot 完成"时打，必须在"业务健康检查通过"时打**——后文展开。

## <span class="blue">bootcount：U-Boot 的计数器回滚 [M]

机制本身很朴素，四个环境变量串起来：

> bootcount / bootlimit：U-Boot 的启动失败计数机制（`CONFIG_BOOTCOUNT_LIMIT`）。每次启动 U-Boot 把 `bootcount` 加一并写回环境变量；系统正常起来后由用户态把它清零。如果 `bootcount` 超过了 `bootlimit`，U-Boot 就不走正常 `bootcmd`，改走 `altbootcmd`——"备用启动命令"，回滚逻辑就写在这里。

<!-- -->

> altbootcmd：bootcount 超限后执行的备用启动命令。OTA 场景里它的内容就是"把启动槽切回另一个，重置计数，照常启动"——回滚不需要任何新硬件，它是 U-Boot 脚本语言就能表达的逻辑。

一个最小 A/B 回滚的环境变量片段（手写流派，帮助理解原理）：

```text
bootlimit=3

bootcmd=if test ${slot} = A; then run boot_a; else run boot_b; fi

altbootcmd=echo "boot failed ${bootcount} times, rolling back"; \
           if test ${slot} = A; then setenv slot B; else setenv slot A; fi; \
           setenv bootcount 0; saveenv; run bootcmd
```

逻辑链：正常启动路径每次给 `bootcount` 加一（U-Boot 自动做）；Linux 起来后用户态用 `fw_setenv bootcount 0` 清零；如果新系统起不来，没人清零，重启三次后 `bootcount > bootlimit`，`altbootcmd` 把 `slot` 切回去——设备自己把自己救活了。

> 💡 用户态读写 U-Boot 环境变量用 `fw_printenv` / `fw_setenv`（来自 u-boot-tools）。它俩需要 `/etc/fw_env.config` 告诉它环境变量在存储器的哪个偏移、多大——这个文件的偏移量必须和 U-Boot 编译时的 env 地址一致，配错的表现是"读出来全是乱码"或"写了但没生效"，是 bring-up 阶段的经典坑。

## <span class="blue">RAUC 的约定：BOOT_ORDER 与 BOOT_x_LEFT [M]

手写的 `slot` 变量能用，但社区打磨过的 RAUC 约定更稳，它把"每个槽还有几次机会"显式化：

```text
BOOT_ORDER=A B      ← 启动尝试顺序，写 B 槽更新后变成 "B A"
BOOT_A_LEFT=3       ← A 槽还剩 3 次尝试机会
BOOT_B_LEFT=3       ← B 槽还剩 3 次尝试机会
```

U-Boot 的启动脚本（RAUC 文档与 meta-rauc 提供的标准模板）做三件事：

```
1. 按 BOOT_ORDER 取第一个 LEFT > 0 的槽；
2. 把该槽的 LEFT 减一，写回环境变量；
3. 从这个槽加载 kernel/dtb 启动。
```

对应关系一目了然：`BOOT_x_LEFT` 就是 per-slot 的 bootcount，`BOOT_ORDER` 的顺序就是"先试谁"。RAUC 安装更新到 B 槽时做两件事：把 `BOOT_ORDER` 改成 `B A`、把 `BOOT_B_LEFT` 重置为 3。于是 B 起不来的结局是：三次尝试后 `BOOT_B_LEFT` 归零，脚本落到顺序里的下一个——A 槽，设备回到旧系统。

这套约定比手写强在哪：**状态全部显式可读**。`fw_printenv` 一眼看出当前在试哪个槽、还剩几次机会、上次更新装了什么——产线测试和售后诊断都靠这个。

```bash
# 设备上实时查看启动槽状态
fw_printenv BOOT_ORDER BOOT_A_LEFT BOOT_B_LEFT
# BOOT_ORDER=B A
# BOOT_A_LEFT=3
# BOOT_B_LEFT=2        ← B 槽已经失败过一次了
```

## <span class="blue">mark-good：什么时候确认"这版是好的" [M]

回切机制讲完了，还差最后一块：**谁来把 `BOOT_B_LEFT` 重置回 3，宣告 B 槽"转正"**？这个动作叫 mark-good（RAUC 命令 `rauc status mark-good`），它的时序是整个回滚设计里最值得推敲的地方。

打太早：系统刚 boot 完就打——形态④（业务活了但不对）完全漏网，坏版本被永久落锤，回滚机制形同虚设。打太晚：等业务跑满 24 小时再打——期间任何一次正常重启都消耗一次 `LEFT`，三次正常重启就能把一个好版本误杀回滚。

合理的判据是**业务健康检查通过**，而不是"系统启动完成"。机器人公司的健康检查服务：

```ini
# /etc/systemd/system/ota-mark-good.service
[Unit]
Description=Mark booted slot as good after health checks
# 等业务进程起来，而不是只等 multi-user
After=robot-navigation.service robot-chassis.service network-online.target
Wants=network-online.target

[Service]
Type=oneshot
ExecStart=/usr/lib/ota/health-check.sh
# 健康检查全部通过才执行到这
ExecStartPost=/usr/bin/rauc status mark-good

[Install]
WantedBy=multi-user.target
```

配套的健康检查脚本（按业务裁剪）：

```bash
#!/bin/sh
# /usr/lib/ota/health-check.sh — 全部通过返回 0，任何一项失败非 0
set -e

# 1. 关键进程活着且稳定运行超过 60 秒（防 crash 循环）
for svc in robot-navigation robot-chassis; do
    systemctl is-active --quiet "$svc"
    started=$(systemctl show "$svc" -p ActiveEnterTimestampMonotonic --value)
    now=$(cat /proc/uptime | cut -d. -f1)
    [ $((now - started / 1000000)) -gt 60 ]
done

# 2. 底盘通信真的通（不只是进程活着）
robotctl chassis ping > /dev/null

# 3. 能连上云端（更新系统自己也要活着，否则下次更新收不到）
curl -sf --max-time 10 https://ota.robotics.example.com/ping > /dev/null
```

三条检查对应三种"活了但不对"：进程 crash 循环、进程活着但硬件链路死了、系统活了但更新通道死了——最后一条尤其容易漏：**更新通道本身坏了的设备收不到下一次更新，它应该在 mark-good 阶段就被拦下来**。

> ⚠️ mark-good 失败不等于立刻回切。健康检查不过 → 不打标 → `BOOT_B_LEFT` 不重置 → 后续重启继续消耗次数 → 三次后自动回切。整个链条没有一处需要人工干预，这正是设计目标：无人值守的三千台设备，回滚必须是自动的。

<!-- -->

> 🔴 健康检查别做成"永远通过"。见过产线脚本把 `set -e` 去掉、检查失败也返回 0 的写法——理由是"怕误回滚"。代价是坏版本全部落锤。正确方向是把检查做准，不是把检查做松。

## <span class="blue">环境变量自己的可靠性 [M]

整套回滚机制的地基是 U-Boot 环境变量——它存在 Flash 上，它自己也会坏：写 env 时断电，环境变量损坏，`BOOT_ORDER` 变成乱码，回滚逻辑瘫痪。

对策是 U-Boot 的**冗余环境变量**（`CONFIG_ENV_REDUNDANT`）：两份 env 各带 CRC 校验，U-Boot 读主份校验失败自动读备份，写入时交替写两份。开启后"写 env 断电"的最坏结果是丢最近一次修改，而不是整个环境区报废。

```text
# 典型布局（eMMC 硬件 boot 分区或 Flash 固定偏移）
env 主份   @ 0xC0000  (带 CRC)
env 冗余份 @ 0xE0000  (带 CRC)
```

配置纪律：冗余 env 打开；`fw_env.config` 里两个地址都登记；产线测试里加一项"写 env 中途断电，重启后 env 可读"。

## <span class="blue">救砖的最后一道 [M]

回切机制兜住"新系统起不来"，还有一层更坏的：A 槽 B 槽都起不来（比如 data 分区错误把两个系统都拖死、或两次更新连续写出坏包）。最后一道防线按侵入性排：

1. **recovery 启动项**：U-Boot 检测到两个槽都 `LEFT=0`，落进 recovery 小系统（21.3 的分区模式在这里和 A/B 合流——大存储产品也可以留一个小 recovery 保底），从网络或 U 盘重新拉包；
2. **硬件启动模式**：BootROM 级的 USB/SD 启动（i.MX 的 SDP、RK 的 MaskRom），不依赖 eMMC 上任何内容，串口+USB 就能救——前提是产品设计时把这个接口引出来了；
3. **看门狗兜底**：内核起来了但 systemd 卡死这种"半活"状态，硬件看门狗负责把它踹回 U-Boot 重新计一次失败——看门狗在此是回滚机制的传感器。

> 💡 这三道防线的共同启示：**救砖能力是设计出来的，不是出了事再找的**。USB 救砖口没在结构件上开孔、recovery 没进分区表、看门狗没使能——出了事每一项都是"早知道"。21.6 的断电测试矩阵会把这些逐项变成测试用例。

## <span class="blue">本节总结

回滚的本质是"让比内核更简单更难坏的 Bootloader 来裁决内核的生死"。bootcount 四变量（计数、上限、备用命令、清零责任）串起最小可用机制；RAUC 的 `BOOT_ORDER`/`BOOT_x_LEFT` 约定把它升级成 per-slot 显式状态，`fw_printenv` 可读、产线可测。

设计重心在 mark-good 的时序：判据是业务健康检查通过，不是系统启动完成——进程存活、硬件链路、更新通道三类检查对应三种"活了但不对"。地基也要打：冗余 env 防环境变量自己写坏；recovery 启动项、硬件启动模式、看门狗构成 A/B 双双失效后的最后三道防线。整条链上没有任何一处需要人工干预——无人值守设备的回滚必须是自动的。
