## <span class="blue">本节导读

21.1 立了规矩：带着失败模式清单选方案，方案是防线的载体。本节把三个主流方案放上同一张桌子——RAUC、SWUpdate、Mender，看它们各自的架构长什么样、防线覆盖到哪、要配什么后端、跟 Yocto 集成到什么程度，最后用机器人公司的场景把决策走完一遍。

## <span class="blue">三个方案是什么 [E]

三个方案解决同一个问题，但出身和形状完全不同。先把每家"装一次更新"的样子看清楚，后面的矩阵才有意义。

### RAUC：专注于设备端的更新框架

RAUC（Robust Auto-Update Controller，Pengutronix 出品，LGPL）的形状是一个**只管设备端的更新守护进程**：更新包是一个 `.raucb` bundle（squashfs 镜像 + manifest + 签名），RAUC 校验签名、按 manifest 把镜像写进备用槽位、操作 bootloader 环境切换启动。

一个真实 bundle 的 manifest（bundle 内 `manifest.raucm`）：

```ini
[update]
compatible=amr-robot-jetson
version=2.4.1
description=AMR rootfs update 2026-09

[bundle]
format=verity

[image.rootfs]
filename=rootfs.ext4.img
size=1258291200
sha256=9f2c...
```

设备侧的配置 `/etc/rauc/system.conf` 长这样：

```ini
[system]
compatible=amr-robot-jetson
bootloader=uboot
bundle-formats=verity

[keyring]
path=/etc/rauc/ca.cert.pem

[slot.rootfs.0]
device=/dev/mmcblk0p2
type=ext4
bootname=A

[slot.rootfs.1]
device=/dev/mmcblk0p3
type=ext4
bootname=B
```

注意这个文件把 21.3~21.5 的伏笔全埋下了：`[slot.*]` 是 A/B 分区（21.3）、`bootloader=uboot` 是回切配合（21.4）、`[keyring]` 是签名验证（21.5）。RAUC 的接口是 D-Bus API，业务程序可以监听安装进度；云端对接靠配套的 hawkBit 客户端（`rauc-hawkbit-updater`）。

### SWUpdate：handler 驱动的更新引擎

SWUpdate（Eclipse 基金会项目，Stefano Babic 主导，GPLv2）的形状是一个**可插拔的更新引擎**：更新包是一个 `.swu` 文件（cpio 归档，内含 `sw-description` 描述文件和镜像），SWUpdate 解析描述文件，把每个镜像交给对应的 handler（raw、uboot、lua 脚本、archive……）处理。

`sw-description` 的骨架：

```lua
software =
{
    version = "2.4.1"
    amr_robot_jetson = {
        hardware-compatibility = [ "1.0", "1.1" ]
        images = (
            {
                filename = "rootfs.ext4.img"
                device = "/dev/mmcblk0p3"
                type = "raw"
                sha256 = "9f2c..."
            }
        )
        bootenv = (
            { name = "swupdate_slot", value = "B" }
        )
    }
}
```

和 RAUC 的气质差异一眼可见：SWUpdate 把"每一步做什么"交给描述文件和 handler，**灵活度更高、约定更少**——单分区 recovery 更新、双备份更新、甚至更新中执行 Lua 脚本，都是同一个引擎的不同描述文件。云端对接用 suricatta 模式（轮询 hawkBit 服务器），或自带的 mongoose webserver 做本地网页更新。

### Mender：端到端的商业闭环

Mender（挪威 Mender 公司，客户端 Apache-2.0 开源，服务端分开源版与商业版）的形状是**一套完整的"客户端 + 服务器"系统**：设备上跑 mender-client（Go 写的守护进程，只管 rootfs A/B 双备份一种模式），服务器端提供设备管理、分组、灰度发布、失败率统计的完整 Web UI。

设备侧 `/etc/mender/mender.conf`：

```json
{
    "ServerURL": "https://ota.robotics.example.com",
    "TenantToken": "eyJhbGci...",
    "UpdateControlMapExpirationTimeSeconds": 3600,
    "RootfsPartA": "/dev/mmcblk0p2",
    "RootfsPartB": "/dev/mmcblk0p3"
}
```

Mender 的特点是把 21.5 要讲的更新策略**产品化**了： phased rollout（分阶段灰度）、按设备属性分组、失败自动暂停，这些都是服务端界面里点出来的，不用自己写。代价也直接：高级功能（增量更新、 phased rollout、多租户）在商业版里，按设备数量计费。

## <span class="blue">12 维决策矩阵 [M]

| 维度 | RAUC | SWUpdate | Mender |
|:---|:---|:---|:---|
| 许可证/商业模式 | LGPL，全开源 | GPLv2，全开源 | 客户端开源，服务端开源/商业两档 |
| 定位 | 设备端更新框架 | 设备端更新引擎 | 端到端 OTA 系统 |
| 分区模型 | A/B（也支持单槽+recovery） | 双备份 / 单分区 recovery，靠描述文件约定 | 仅 rootfs A/B |
| Bootloader | U-Boot / Barebox / GRUB / EFI / 自定义 | U-Boot / EFI（env 操作） | U-Boot / GRUB（官方集成） |
| 签名验证 | bundle 整体签（CMS 格式），keyring 在设备上 | sw-description 签名（RSA/证书） | artifact 签名（可选）+ TLS 通道 |
| 云端后端 | hawkBit（开源，Eclipse） | hawkBit / 自建 webserver | Mender Server（含管理 UI） |
| 灰度发布 | hawkBit rollout 功能 | hawkBit rollout 功能 | 服务端内置（商业版功能完整） |
| 差分更新 | adaptive updates（块哈希索引，v1.10+） | 需自行组合（zsync/delta handler） | 商业版 mender-binary-delta |
| 应用层更新 | 靠 bundle 内多 image 扩展 | handler 天然支持任意文件/包 | Update Module（应用/容器/文件） |
| Yocto 集成 | meta-rauc（社区活跃） | meta-swupdate（社区活跃） | meta-mender（官方维护） |
| 状态与进度接口 | D-Bus API，业务可监听 | 进度输出 + webserver | 客户端状态机 + 服务端可视 |
| 上手曲线 | 中（概念少，约定清晰） | 中高（灵活意味着决策多） | 低（官方文档与 demo 完整） |

三个方案在防线上的位置一句话概括：**RAUC 和 SWUpdate 给你的是"设备端的枪"，云端要自己配；Mender 给你的是"整支军队"，但军饷按人头算**。

## <span class="blue">决策树 [M]

把矩阵收敛成可执行的分叉：

```
你的产品要更新的是什么？
│
├─ MCU/单分区小固件（几百KB~几MB，无 Linux rootfs 概念）
│     → 三个方案都 oversized，走"自研边界"一节
│
├─ Linux 设备，要 rootfs 级 A/B 更新
│     │
│     ├─ 需要现成的设备管理后台（分组/灰度/失败率看板）
│     │   且接受按设备付费 ──────────────→ Mender
│     │
│     ├─ 云端自己运维或已有 hawkBit，要全开源 ──→ 继续分叉：
│     │     │
│     │     ├─ 只要 A/B + 签名 + 回切，要约定清晰、少做决策
│     │     │     → RAUC
│     │     │
│     │     └─ 更新流程有特殊形状（单分区 recovery、
│     │        包内要执行脚本、要更新多种非 rootfs 内容）
│     │           → SWUpdate
│     │
│     └─ 团队已有运维中台，只缺设备端代理
│           → RAUC（D-Bus API 最干净）或 SWUpdate
```

> 💡 "后端"这个词需要展开一下：OTA 的服务端要管四件事——存包、登记设备、决定"谁什么时候更新到什么版本"、回收每台设备的安装结果。hawkBit 是 Eclipse 的开源实现（Java/Spring），提供 DDI API 供设备轮询；Mender Server 是 Mender 自家的实现；也可以完全自研一个 HTTP 服务。三个设备端方案里，RAUC 和 SWUpdate 对后端的态度是"你随便，按 API 来就行"，Mender 的态度是"用我的"。

<!-- -->

> ⚠️ 商业版计价要算全生命周期：Mender 商业版按活跃设备数订阅。3000 台设备、五年产品周期，订阅费是一笔百万级的账（具体以官方报价为准）——在决策矩阵里"功能完整"和"全开源"从来不只是技术偏好。

## <span class="blue">用失败模式表盘问三方案 [M]

把 21.1 的清单拿来逐家问一遍——挡住几类、哪类要自己补：

| 失败模式 | RAUC | SWUpdate | Mender |
|:---|:---|:---|:---|
| 断电变砖 | ✅ A/B + bootloader 回切框架 | ✅ 双备份模式可配出同等能力 | ✅ A/B 内置，开箱即回切 |
| 坏包变砖 | ✅ 安装前校验 manifest + 哈希 + 签名 | ✅ sw-description 哈希 + 签名 | ✅ artifact 校验 |
| 恶意固件 | ✅ keyring 验签（21.5 展开） | ✅ 签名验证（配置项，要开） | ⚠️ 签名是可选功能，默认靠 TLS 通道 |
| 回滚攻击 | ⚠️ 靠版本策略自己定（无内置单调计数） | ⚠️ 同左 | ⚠️ 服务端可约束最低版本 |
| 分发压垮 | ⚠️ 设备端无限速概念，靠 hawkBit rollout | ⚠️ 同左 | ✅ 服务端 phased rollout（商业版） |

两家开源方案的共性结论：**设备端防线（断电、坏包）三家都能配齐；策略防线（防降级、灰度）开源方案给的是零件，要自己组装**。这不是缺陷，是"框架"与"产品"的分工——但选型时必须把组装成本算进去。

## <span class="blue">自研什么时候反而合理 [M]

三个方案聊完，必须认真回答"为什么不自己写"——因为对一类产品，自己写真的是对的：

- **固件小且单分区**：MCU 级产品（固件几百 KB 到几 MB），没有 rootfs 概念，更新就是"收包→校验→写 Flash→跳转"。三个方案的 A/B rootfs 模型对它是杀鸡用牛刀。一个带断点续传的接收器加一个备份区，几百行 C 就够。
- **更新通道特殊**：CAN 总线上的 ECU、串口连接的传感器节点——根本没有 IP 网络，三个方案的轮询模型全不适用，协议得自己定（汽车 UDS 刷写就是典型的"自研"标准）。
- **设备量极小且无远程需求**：几十台设备、更新靠工程师到现场插 U 盘。SWUpdate 的本地模式能干，但一个校验哈希的 shell 脚本也能干，还少一层维护对象。

反过来，只要产品是**联网的 Linux 整机、数量上百、要远程无人值守更新**，自研就是重复发明轮子——而且是一个要在"断电变砖"这种细节上交过学费才造得圆的轮子。RAUC/SWUpdate 的回切、验签、槽位管理是上千个产品踩坑踩出来的约定，照抄比自研便宜。

## <span class="blue">机器人公司怎么走矩阵 [M]

把场景参数代进决策树：Linux 整机、3000 台、要无人值守远程更新、公司已有运维中台（18 章的 CI/CD 体系延伸）、成本敏感、团队有 Yocto 经验。

- 要现成管理后台吗？——已有运维中台，接受 API 集成，**排除 Mender 商业版**（五年订阅费对比中台改造成本，不划算；开源版 Mender Server 功能与 hawkBit 重叠，不引入第二套）。
- 更新流程有特殊形状吗？——rootfs A/B 为主，需求是"约定清晰、少做决策、D-Bus 接口干净"，**选 RAUC**；bootloader 是 U-Boot，原生支持；meta-rauc 直接进 18 章的 Yocto 流水线。
- 云端？——hawkBit 部署进现有 K8s，灰度用 rollout 功能（21.5 展开）。

决策落点：**RAUC（设备端）+ hawkBit（云端）+ meta-rauc（构建集成）**。21.3~21.5 的所有配置示例都以这个组合为准——但请注意，每一节的原理（分区、bootcount、签名、灰度）都是方案无关的，换成 SWUpdate 或 Mender，只是语法不同。

## <span class="blue">本节总结

三方案一句话各自定位：RAUC 是约定清晰的设备端更新框架（bundle + 槽位 + D-Bus），SWUpdate 是 handler 驱动的灵活引擎（描述文件决定一切），Mender 是端到端的商业闭环（设备管理产品化）。

选型的实质是算账：设备端防线三家都能配齐，差异在策略防线——开源方案给零件自己组装（hawkBit 后端、防降级逻辑），Mender 给成品按设备收费。决策树两个关键分叉：要不要现成管理后台、更新流程有没有特殊形状。自研的合理边界在 MCU 小固件、非 IP 通道、极小批量三处，联网 Linux 整机过百台就别造轮子。机器人公司的落点是 RAUC + hawkBit，后续各节配置以此为准。
