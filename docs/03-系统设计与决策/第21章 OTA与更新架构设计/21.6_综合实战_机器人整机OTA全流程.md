## <span class="blue">场景参数与决策一览 [M]

先把机器人公司的约束摆上桌（与 18 章同一家公司：AMR/协作机械臂/人形三条产品线）：

| 约束 | 参数 | 对 OTA 的含义 |
|:---|:---|:---|
| 规模 | 3000 台 AMR，十几个仓库 | 分发必须灰度，不能全量硬推 |
| 硬件 | Jetson + x86 工控机双架构 | 同一后端，两套 bundle，防错刷 |

| 电源 | 电池运行，客户随时断电 | 断电测试矩阵是验收标准 |

| 红线 | 更新失败率 < 0.1%（人工到场口径） | 灰度晋级判据的阈值来源 |

## <span class="blue">三个悬念当面裁决 [M]

架构评审前还剩三个没有标准答案的问题，评审会上必须当面定掉。

### 悬念①：双架构，一套 OTA 还是两套？

Jetson 和 x86 的镜像不能互刷——但要不要为此搭两套后端？裁决：**一套 hawkBit 后端，两套 bundle，用 RAUC 的 compatible 机制防错刷**。

机制是现成的：bundle 的 manifest 里有 `compatible=amr-robot-jetson`，设备 `system.conf` 里有 `compatible=amr-robot-jetson`——**不匹配，RAUC 直接拒装**。后端按 compatible 给设备分组，Jetson 组的 rollout 只投 Jetson 包。即使运维手滑把 x86 的包派给了 Jetson 设备，设备端拒装，事故止步于一条告警。

```ini
# 同一套 system.conf 模板，构建时按 MACHINE 渲染
[system]
compatible=amr-robot-jetson     # x86 机型渲染为 amr-robot-x86
bootloader=uboot
```

这一裁决的深层原则：**设备端要有最后一道"这包是不是给我的"校验，不能只靠云端不犯错**。云端一定会犯错，设备端兜住才是架构。

### 悬念②：差分定档，bsdiff 还是 adaptive？

21.3 列了三档，评审会上基础设施组倾向 bsdiff（压缩率极致），OTA 组倾向 adaptive。裁决：**adaptive**。

理由三条，全部来自本场景的具体约束：版本线多（3000 台在线版本必然发散，bsdiff 要为每对版本组合维护补丁链）、离线设备多（bsdiff 的"精确旧版"前提在离线数周的设备上不成立，21.5 已点）、服务端零组合维护（adaptive 一个 bundle 全量差分通吃，CI 只多一步索引生成）。bsdiff 省下的那部分流量，买不到这三条的运维成本。

### 悬念③：协作机械臂产品线，要不要迁就同一套方案？

协作机械臂控制器是 1GB NAND，装不下 A/B。两个选项：给机械臂单独搞一套 OTA，或强行统一。裁决：**设备端各自选型，云端统一**——机械臂用 SWUpdate 单分区 recovery 模式（21.3 的对比账：它更新时产线本来停机，业务中断代价为零），通过 suricatta 模式接同一个 hawkBit。

这样云端只有一套：分组、灰度、反馈的模型对两种设备端一致；设备端各取所需——21.2 的"选型按产品不按公司"落地为"**云端按公司统一，设备端按产品选型**"。人形产品线（Jetson 同架构、未量产）直接复用 AMR 的 RAUC 方案，零新增决策。

## <span class="blue">分区表定稿 [M]

AMR（Jetson，32GB eMMC）最终布局：

```text
mmcblk0boot0  4MB    → SPL + U-Boot（硬件分区，OTA 不更新）
env 主/冗余   各 1MB  → U-Boot 环境变量（冗余 env，21.4）
mmcblk0p1     128MB  → 出厂救援内核（recovery 保底，21.4 最后一道）
mmcblk0p2     4GB    → rootfs.A（RAUC slot rootfs.0，含 kernel+dtb 同槽）
mmcblk0p3     4GB    → rootfs.B（RAUC slot rootfs.1，出厂留空）
mmcblk0p4     ~23GB  → data（地图/配置/日志，前向兼容纪律，21.3）
```

x86 工控机变体仅两处不同：bootloader 是 GRUB（RAUC `bootloader=grub`，回切语义相同）、存储是 SATA SSD 但布局同构。评审要点：分区表在首台量产机出厂后冻结，4GB 槽位按"rootfs 三年增长到 2.5GB"留的余量。

## <span class="blue">流水线：从 CI 到签名 [M]

```
Yocto 构建（18.4 流水线）
   │  产出 rootfs 镜像 + SBOM
   ▼
生成 bundle 内容（manifest + 镜像 + 块哈希索引 ← adaptive）
   │
   ▼
rauc bundle --cert --key --keyring   ← CI 内签名（签名密钥在 CI 凭据仓）
   │
   ▼
上传 hawkBit + 登记元数据（版本、安全版本号、compatible、目标组）
   │
   ▼
按 rollout 计划分波投递 ──────────→  设备端验签 → 写 B 槽 → 切换 → 健康检查 → mark-good
                                            ▲
                                     设备 keyring（CA 公钥，出厂烧入）
```

两条纪律：签名动作在 CI 内完成且签名密钥不出凭据管理系统（对应 21.5 纪律②）；**先小流量验证签名链再放量**——每个新签名周期的第一个 bundle，先在 5 台内部设备上验证 keyring 交接正确，这是 21.5 轮换窗口纪律的执行形态。

## <span class="blue">灰度计划表 [M]

| 波次 | 规模 | 范围 | 观察期 | 晋级判据（全部满足） | 不满足 |
|:---:|:---:|:---|:---:|:---|:---|
| 一 | 50 台 | 内部仓库 + 2 个配合客户 | 48h | 安装成功率 ≥99.9%；回切率 <0.5%；业务指标不劣化；无新 crash 签名 | 自动暂停，人工介入 |
| 二 | 500 台 | 覆盖全部仓库类型 | 72h | 同上 | 同上 |
| 三 | 全量 | 按仓库分批，单仓库并发 ≤20 | — | 分批间巡检 | 暂停该仓库 |

更新时机叠加 21.5 的机器人约束：电量 <30% 不下载、<50% 不安装、优先充电窗口、任务中只下载不安装；安全修复包走强制窗口但保留"停稳再装"底线。

## <span class="blue">断电测试矩阵：全章的验收标准 [M]

这是评审的核心证据。矩阵的每一行对应一类死法，每一行都必须有**实测记录**而非推理结论：

| # | 断电/故障时刻 | 重启后预期行为 | 依赖机制 | 通过标准 |
|:---:|:---|:---|:---|:---|
| 1 | 下载到 40% | 旧系统照常运行，稍后重下 | A/B 只写备份槽（21.3） | 业务无感知 |
| 2 | 校验 bundle 时 | 坏包丢弃，不误装 | 哈希+签名校验（21.5） | 无 B 槽写入 |
| 3 | 写 B 槽 30% / 90% | 旧系统照常，B 槽半成品下次重装 | 启动项未切换（21.3） | A 槽启动正常 |
| 4 | 写完已切换，首次启动失败 | 3 次尝试后自动回切 A | `BOOT_B_LEFT` 递减（21.4） | 回切发生，env 可读 |
| 5 | 新系统 running 但健康检查不过 | 不 mark-good，3 次重启后回切 | mark-good 判据（21.4） | 回切且 crash 上报 |
| 6 | mark-good 完成后 | B 槽转正，下次更新写 A | `LEFT` 重置（21.4） | fw_printenv 验证 |
| 7 | 写 env 中途 | 冗余 env 接管，丢最近修改 | `CONFIG_ENV_REDUNDANT`（21.4） | env 可读可写 |
| 8 | 回切后旧系统启动 | 旧系统读 data 分区正常 | 数据前向兼容（21.3） | 业务数据可用 |
| 9 | 下载用错架构的包 | 设备拒装并告警 | compatible 校验（本节①） | 拒装日志 |
| 10 | 投递旧版本包（回滚攻击） | 拒装 | 单调安全版本（21.5） | 拒装日志 |

测试方法分两档：**矩阵 1~7 用继电器自动断电台架**跑（机器人公司在 18.4 的 HIL 池里加固件断电夹具，每次发版回归）；8~10 为专项安全测试，每季度或每次策略变更时跑。

> 🔴 矩阵里最容易被砍的是第 8 行"回切后数据可用"。它的测试成本最高（要构造新旧两版数据格式），被砍的理由最充分（"我们格式没变"）——直到有一次格式变了。数据格式变更的版本，第 8 行升级为强制项。

## <span class="blue">离线设备处置清单 [M]

| 情形 | 策略 | 依据 |
|:---|:---|:---|
| 离线 3 周内上线 | 直接跳最新版（adaptive 无版本要求） | 21.5 |
| 错过 keyring 轮换 | 先投过渡包（旧密钥签、含新 keyring），再投新包 | 21.5 纪律③ |
| 离线 90 天+ | 进人工清单排查：是离线还是损坏 | 本节 |
| 安全版本落后 2 代+ | 上线后走强制窗口，但保留停稳再装 | 21.5 时机 |

服务端按设备 `last-seen 版本 + 安全版本 + keyring 代次` 三项记账——这三个字段决定每台设备上线后收到什么包。

## <span class="blue">本节总结

这份架构的评审逻辑一句话：每类失败模式有防线、每条防线有测试、每个裁决有记录。三个悬念的裁决——一套后端两套 bundle 用 compatible 防错刷、差分选 adaptive、云端统一设备端按产品选型——都不是技术偏好，是场景约束的推论。

断电测试矩阵是全章的验收标准：10 行覆盖从"下载中"到"回滚攻击"的每种死法，每行要实测记录不要推理结论，其中"回切后数据可用"最容易被砍也最不能砍。评审清单 18 项逐条挂在 21.1~21.5 的依据上——拿到这套东西，OTA 从"功能"变成了"架构"。
