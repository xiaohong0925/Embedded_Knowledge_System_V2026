# 21.3 分区策略：A/B、recovery 与差分更新

> 所属章节：第21章 OTA与更新架构设计
>
> 难度：[M] | 预计阅读时间：30分钟

## <span class="blue">本节导读

21.2 的 `system.conf` 里写下了两个 slot：`/dev/mmcblk0p2` 和 `/dev/mmcblk0p3`。这两个分区不是白来的——它们的背后是一张分区表，而分区表是 OTA 里**最早被定死、最晚能改**的东西：产品一旦出货，分区表就焊死在几千台设备的 eMMC 里，改分区表约等于召回。本节把这张表怎么画讲清楚。

> 本节覆盖：A/B 双槽的机制与"断电任意时刻安全"的精髓、存储成本的量化（多大存储才配玩 A/B）、小存储设备的 recovery 单分区模式、Yocto `wic` 分区表实例、差分更新三档（全量/bsdiff/adaptive）的流量账，以及 A/B 架构下最容易踩的数据分区迁移陷阱。

---

## <span class="blue">A/B 双槽：OTA 的基石 [M]

A/B 的机制一句话就能说完：**rootfs 占两个槽位，当前跑 A，更新就写 B，写完切启动项到 B，确认没问题再永久落锤**。

```
        更新前                 更新中                 更新后
   ┌───────────┐         ┌───────────┐         ┌───────────┐
A  │ 正在运行 ✓ │         │ 正在运行 ✓ │  ←──    │ 旧版本     │
   └───────────┘         └───────────┘   重启   └───────────┘
B  │ 空/旧版本  │ ← 写入  │ 写入新包 ✍ │         │ 正在运行 ✓ │
   └───────────┘         └───────────┘         └───────────┘
```

这张图的精髓在"更新中"那一列：**写入动作从头到尾只碰备份槽，当前系统一个字节都没动**。所以 21.1 的"断电变砖"在 A/B 下被改写了结局——任意时刻断电：

- 写到一半断电：备份槽里是半成品，**但启动项还指着 A**。设备重启，旧系统照常起来，更新当作没发生过，下次重新下包再写。
- 写完了、切换了、新系统起不来：启动链的 bootcount 机制把启动项切回 A（21.4 展开），旧系统接管。
- 新系统起来了、自检通过：标记 B 为好，A 变成下一次更新的备份槽。

也就是说，A/B 把"更新"从一次原地修改变成了**一次原子切换**——任意时刻，设备上总有一个完整可启动的系统。这是"更新失败不会变砖"的第一块基石。

> 💡 A/B 不是新发明：Android 从 7.0（2016）开始推 A/B（无缝更新），ChromeOS 更早。嵌入式 Linux 的 RAUC/SWUpdate/Mender 都是同一思想的实现。这个概念在不同资料里也叫 dual bank、dual slot、双备份——都是一回事。

## <span class="blue">成本量化：多大存储才配玩 A/B [M]

A/B 的代价直截了当：**rootfs 的空间乘二**。机器人公司的账好算：rootfs 解压后约 1.2GB，留足余量每槽 4GB，双槽 8GB，32GB eMMC 毫无压力。但不是每个产品都这么阔绰：

| 存储总量 | 能不能 A/B | 结论 |
|:---:|:---|:---|
| 512MB（NAND/小 eMMC） | 不能 | rootfs 一个就占 300MB+，只能走 recovery 模式 |
| 1GB | 勉强 | rootfs 压到 400MB 以内才放得下两槽，代价是砍功能或上只读压缩文件系统（squashfs/EROFS，见 17.3） |
| 4GB | 紧凑可行 | 每槽约 1.5GB，数据分区被挤得很薄，要精打细算 |
| ≥8GB | 舒适 | 常规选择，不用为几百 MB 纠结 |

成本不只是空间。A/B 还有三笔隐性账：

1. **写入量翻倍不影响寿命，但更新流量翻倍影响体验**——每次更新写整个新 rootfs，差分更新（后文）就是冲这笔账来的；
2. **数据必须搬出 rootfs**——配置、日志、业务数据放数据分区（后文展开），否则一切槽数据全丢；
3. **分区表出厂定死**——槽位大小后期改不了，rootfs 的"天花板尺寸"在画表那一刻就决定了，要给三年的功能增长留余量。

> ⚠️ 分区表里不该有 bootloader。eMMC 的 U-Boot 通常放在硬件 boot 分区（`mmcblk0boot0`，不占分区表），SPI NAND 方案放在开头的固定偏移。**不要常规性地用 OTA 更新 bootloader**：bootloader 写坏就是 21.1 说的"全砖"，A/B 也救不了。bootloader 的更新策略是"出厂版本尽量稳定，非必要不更新"。

## <span class="blue">分区表实例：从 wic 到 eMMC [M]

Yocto 里分区表用 `wic` 的 kickstart 文件（`.wks`）描述，机器人公司的 32GB eMMC 布局：

```text
# amr-robot-ab.wks — 32GB eMMC 的 A/B 布局（示意）
part /boot  --source bootimg-partition --fstype=vfat  --size 128M   --label boot
part        --source rootfs            --fstype=ext4  --size 4096M  --label rootfsA
part                                                  --fstype=ext4  --size 4096M  --label rootfsB
part        --source rootfs-data       --fstype=ext4                 --label data
```

落到 eMMC 上的物理布局：

```
mmcblk0boot0 (4MB, 硬件分区)  → SPL + U-Boot（不进分区表）
mmcblk0p1   128MB   boot      → kernel + dtb（也可并入 rootfs 槽，二选一）
mmcblk0p2   4GB     rootfsA   → RAUC slot rootfs.0
mmcblk0p3   4GB     rootfsB   → RAUC slot rootfs.1
mmcblk0p4   约23GB  data      → 配置、地图、日志、业务数据（不随 A/B 切换）
```

两个细节：

- **出厂时 B 槽是空的**。工厂烧录只写 A 槽（B 槽格式化留空），设备的第一次 OTA 才第一次写 B——生产线省一半烧录时间。
- **kernel 放哪是二选一的设计点**：放独立 boot 分区（本例），则 kernel 不随 rootfs 切换，更新 kernel 要单独处理；把 kernel 放进 rootfs 槽（`/boot` 目录随槽走），则 kernel 和 rootfs 一起原子切换——后者一致性更好，RAUC 社区的推荐做法也是 kernel+dtb+rootfs 同槽。机器人公司选同槽，p1 只留出厂救援用途。

## <span class="blue">小存储的活法：recovery 单分区模式 [M]

512MB 存储的产品玩不起 A/B，但不等于放弃"断电不变砖"。答案是 **recovery 模式**：

```
┌────────────────────────────────────────────┐
│ recovery 系统（~80MB，只读，出厂后不更新）   │ ← 永远完好
├────────────────────────────────────────────┤
│ 主系统 rootfs（剩余空间，单份）              │ ← 唯一被更新的对象
└────────────────────────────────────────────┘
```

机制：设备默认从主系统启动；更新时**重启进 recovery 系统**——一个小而全的只读 Linux（Buildroot 几十 MB 就能拼出来），由它下载完整新镜像、校验、整体覆盖主分区。主分区写坏了？重启又进 recovery，重新下载重写。recovery 自身只读且不更新，永远完好。

和 A/B 的对比账：

| 维度 | A/B 双槽 | recovery 单分区 |
|:---|:---|:---|
| 存储成本 | rootfs × 2 | recovery 一份固定开销（几十 MB） |
| 更新时业务中断 | 几乎无（后台写备份槽，重启即完成） | **有**（全程在 recovery 里，业务停摆） |
| 更新包 | 可以差分 | 通常全量 |
| 回滚 | 自动回切旧版本 | 无旧版本可回，只有"重写成功为止" |
| 适用 | 存储 ≥4GB、业务不能停 | 存储 ≤1GB、能接受停机更新 |

机器人公司的对照实验：AMR 是 32GB eMMC 走 A/B；同厂的协作机械臂控制器是 1GB NAND，走 recovery——它更新时产线本来就停机，"业务中断"这条代价对它不存在。**同一个公司两种分区策略并存是常态，选型按产品不按公司**。

## <span class="blue">差分更新三档：流量账 [M]

全量包在机器人场景是什么概念：rootfs 包约 1.2GB，三千台设备每个季度更新一次就是 3.6TB 出口流量，仓库 Wi-Fi 里单台要拉几十分钟。差分更新就是砍这笔账的。三档方案，省流量的能力和复杂度同步上升：

### 档一：全量 + 压缩（基线）

什么都不做，bundle 内 squashfs/verity 格式自带压缩，1.2GB 的 ext4 镜像压完通常 500~700MB。这是基线，零额外成本。

### 档二：bsdiff 二进制差分

服务器用 `bsdiff` 对"旧版本镜像 → 新版本镜像"算出二进制补丁，设备端 `bspatch` 把本地旧镜像打成新的：

```bash
# 服务器端：从 2.4.0 到 2.4.1 的差分包
bsdiff rootfs-2.4.0.img rootfs-2.4.1.img delta-2.4.0-to-2.4.1.patch

# 设备端：本地旧镜像 + 补丁 = 新镜像
bspatch /dev/mmcblk0p2.tmp rootfs-new.img delta.patch
```

版本相近时补丁只有全量的 5%~20%（1.2GB → 60~240MB）。代价有两条，都不轻：**设备上必须有精确的那个旧版本**（2.4.0→2.4.1 的补丁打不到 2.3.9 上），版本组合要服务器全量维护；差分要按"当前槽里的旧系统"逐字节读出来打补丁，补丁应用阶段出错恢复路径要单独设计。

### 档三：RAUC adaptive updates（块哈希索引）

RAUC v1.10 引入的机制：bundle 生成时同时产出镜像的**块哈希索引**（把镜像切成固定大小的块，记录每块哈希）。设备安装时把目标槽按同样方式切块算哈希，**只下载哈希不匹配的那些块**（通过 HTTP range 请求流式拉取）。

它相对 bsdiff 的两个关键优势：不要求设备是某个精确旧版本——2.3.9 升 2.4.1 也能只拉差异块；不需要单独的差分包，**一个 bundle 全量和差分通吃**，服务器侧零组合维护。代价是 RAUC 版本要 ≥1.10、bundle 用 verity 格式、以及云端要支持 HTTP range（hawkBit 配对象存储即可）。

### 三档怎么选

| 档位 | 典型包大小（相对） | 旧版本要求 | 服务端成本 | 适用 |
|:---|:---:|:---|:---|:---|
| 全量压缩 | 100% | 无 | 零 | 带宽充裕、包小、低频更新 |
| bsdiff | 5~20% | 精确旧版 | 每对版本组合一个补丁 | 版本线单一、流量极敏感 |
| adaptive | 约等于实际变更块 | 无 | bundle 生成多一步索引 | 版本线多、要免维护差分 |

> 💡 流量账的直觉校准：rootfs 相邻版本的真实变更通常集中在应用层——内核、库文件大块复用。1.2GB 镜像的季度更新，实际变化块往往只有一两百 MB，adaptive 能把这个数字直接变成下载量。机器人公司仓库 Wi-Fi 抖动大，下载量砍到五分之一意味着失败率也近似砍到五分之一——差分在这是**可靠性措施**，不只是省钱。

## <span class="blue">数据分区：A/B 架构的最大陷阱 [M]

A/B 切换的是 rootfs，但设备上不只有 rootfs——配置、地图、日志、校准参数、业务数据库，这些必须活在独立的 data 分区里，跟着系统走而不是跟着槽走。这带来一个新手几乎必踩的坑：**数据格式的版本兼容**。

场景：2.4.1 把地图数据库从 v3 格式升级到 v4，转换在首次启动时自动完成。然后新系统自检失败，bootcount 回切到 2.4.0——旧系统打开 data 分区，看到的是 v4 格式的数据库，**它不认识**。系统能启动，业务全废。砖以另一种形式回来了。

防御手段按强度排：

1. **前向兼容设计**（首选）：数据格式变更保证"旧版本能读新版本的数据"——新增字段而非修改语义，像 Protobuf 的兼容性纪律一样管数据格式；
2. **迁移可逆**：升级转换时保留旧格式副本（`map.db.v3.bak`），回切后旧系统发现格式不符时回退到副本；
3. **数据随槽分版本**（重武器）：关键数据目录按版本隔离（`/data/v2.4.0/`、`/data/v2.4.1/`），启动时挂载对应版本——彻底但复杂，只建议给最核心的业务数据用。

> 🔴 回滚测试必须包含"回滚后数据可用"这一项。大量团队的断电测试矩阵只测"系统起不起得来"，不测"旧系统起来后业务数据还认不认识"——后者才是真正的产线事故。

另一个 data 分区的纪律：**写寿命**。data 分区是整机上写入最频繁的地方（日志、地图增量），它的文件系统选择、掉电安全、寿命量化都按第 17 章（17.2/17.5）的结论来，本章不重复——OTA 视角只有一句话：data 分区坏了 A/B 也救不了业务，它的可靠性设计和 rootfs 同等重要。

## <span class="blue">本节总结

A/B 双槽的精髓是"写入只碰备份槽"，把更新变成原子切换，任意时刻断电设备上总有一个完整系统——它是"不变砖"的第一块基石，代价是 rootfs 空间乘二和数据必须搬出系统分区。存储 4GB 是 A/B 的舒适下限；1GB 以下走 recovery 单分区模式，用"业务停机"换"断电安全"，两种策略在同一家公司并存是常态。

差分三档按流量敏感度选：带宽充裕用全量压缩，版本线单一且流量极敏感用 bsdiff，版本线多又要免维护用 RAUC adaptive（块哈希索引，只拉变更块）——在弱网场景差分是可靠性措施不只是省钱。最大的陷阱在数据分区：回切后旧系统读新格式数据是"能启动的砖"，靠前向兼容、可逆迁移、按版本隔离三层手段防，回滚测试必须覆盖数据可用性。
