# 第21章：OTA与更新架构设计

> 所属：第 三 部 系统设计与决策
>
> BIEM：[E→M] | 核心问题：一套"更新失败不会变砖"的更新系统怎么设计出来？

## 核心问题

不是"RAUC 和 Mender 哪个好"——那是没有约束就问出口的空问题。本章回答的是：**给你的产品形态、部署规模、网络条件和存储预算，怎么推导出一整套更新架构的决策——方案选型、分区策略、回滚机制、签名验证、更新策略——并且拿得出证据证明：更新到一半断电，设备一定能活过来。**

## 为什么需要这一章

OTA 已经从"锦上添花"变成法规要求：欧盟 CRA 要求 2027 年起在欧盟销售的含数字元素产品必须具备安全更新能力。但对嵌入式工程师来说，OTA 真正难的不是"能更新"，而是**失败模式**：更新包下载到一半断电、写到一半断电、新系统起不来、起得来但业务不正常、恶意固件被刷进来、五千台设备同时拉包把服务器压垮。每一种失败模式都有对应的工程手段，但每一种手段都要花钱——存储空间、启动链复杂度、签名基础设施、云端容量。本章要回答的就是：你的钱该花在哪几种手段上。

OTA 还是全书第一个把**设备端和云端作为一个系统**来设计的主题：分区表在设备上，更新策略在云端，签名密钥在双方手里，启动链在中间负责兜底。只设计设备端是半截工程。

有经验工程师对固件更新不陌生——你 scp 替换过文件，或在 U-Boot 里手动烧过镜像。但这些问题不会自动有答案：A/B 双槽要多吃一倍存储，1GB 的 eMMC 还够吗？新系统起不来，谁在第几次启动时把它切回去？灰度发布第一波放 50 台还是 500 台？离线三周的设备上线后，该不该立刻强制它更新？

## 本章主线：一张失败模式清单，五个决策域，一次合流

本章的核心洞察是：**OTA 设计的起点不是选方案，而是列失败模式**——断电变砖、坏包变砖、恶意固件、回滚攻击、分发压垮，每一类失败模式对应一章中的一个决策域。方案选型是结果，不是起点。

```
  失败模式：断电变砖 / 坏包变砖 / 恶意固件 / 回滚攻击 / 分发压垮
        │
        ▼

  决策矩阵               差分更新三档           mark-good 时序         防降级与灰度
  自研的边界             数据分区陷阱           断电测试矩阵           离线设备处理
        │                                                              │
        └──────────────────────────┬───────────────────────────────────┘
                                   ▼
              21.6 综合实战：机器人整机 OTA 全流程
                   3000 台 AMR 的分区表 / 灰度三波 / 断电测试 / 离线处理
```

贯穿全章的场景：第 18 章那家机器人整机厂商——3000 台 AMR 机器人部署在十几个仓库，Jetson + x86 双架构，rootfs 约 1.2GB，eMMC 32GB，仓库 Wi-Fi 覆盖不均，机器人靠电池运行且随时可能被客户断电，有些仓库的设备离线数周，更新失败率的容忍度是千分之一。21.1 用它列失败模式，21.2~21.5 各自回答它的一类问题，21.6 把整套设计合成一份可评审的 OTA 架构。
