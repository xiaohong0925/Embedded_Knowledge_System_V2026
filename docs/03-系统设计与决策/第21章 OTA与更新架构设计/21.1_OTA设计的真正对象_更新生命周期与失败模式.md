# 21.1 OTA 设计的真正对象：更新生命周期与失败模式

> 所属章节：第21章 OTA与更新架构设计
>
> 难度：[E] | 预计阅读时间：20分钟

## <span class="blue">本节导读

先说一个大多数工程师都经历过的起点：设备在实验室里，固件更新就是 `scp` 一个新文件上去、`reboot`，完事。这个做法在实验室里从来没有出过问题——因为实验室里断电有通知、网络是满的、设备只有一台、刷坏了大不了串口救回来。

然后产品出货了。3000 台 AMR 机器人散在十几个仓库里，Wi-Fi 覆盖不均，客户随时可能直接断电，有的仓库离线三周才开一次机。这时候"更新"不再是复制一个文件，而是一个要回答"三千台设备里任何一台在任何时刻出任何意外，都不能变砖"的系统工程。

> 本节覆盖：OTA 为什么本质上是一个分布式系统（设备端、云端、通道、存储、启动链五方协同）、法规怎么把它从可选项变成必选项（EU CRA）、更新生命周期的六个阶段（全章的路线图）、五类失败模式清单（全章的设计起点）、更新窗口怎么定（断电概率的量化入口）、一支 fleet 多种硬件时包怎么不刷错，以及为什么"先列失败模式，再选方案"是本章的方法论。

---

## <span class="blue">OTA 不是功能，是分布式系统 [E]

把"OTA 怎么做"拆开看，它至少牵涉五方，每一方都有自己的故障域：

```
                    ┌─────────────┐
                    │    云端      │  更新包托管、版本管理、灰度策略
                    │ （服务器）   │  故障域：被打垮、发错包、策略配错
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │   传输通道   │  Wi-Fi / 4G / 有线
                    │             │  故障域：带宽抖动、断连、中间人
                    └──────┬──────┘
                           │
        ┌──────────────────┼──────────────────┐
        │                  │                  │
 ┌──────▼──────┐   ┌───────▼─────┐   ┌───────▼─────┐
 │  存储布局    │   │   设备端     │   │   启动链     │
 │ A/B 槽位     │   │  更新代理    │   │ U-Boot 兜底  │
 │ 数据分区     │   │  下载/校验   │   │ 回切旧版本   │
 │ 故障域：写坏 │   │  故障域：断电│   │ 故障域：判错 │
 └─────────────┘   └─────────────┘   └─────────────┘
```

只设计其中任何一方都是半截工程：选了最好的更新代理，分区表没留双槽位置，断电照样变砖；分区设计完美，启动链不会自动回切，新系统起不来就是三千块砖；设备端全部做对，云端一次性向三千台推 200MB，分发当晚就是一场事故。

> 变砖（brick）：设备因固件损坏或启动失败而无法正常启动到可用状态，且无法通过常规软件手段（重新刷机、远程恢复）修复的状态。"砖"的分级要分清：系统起不来但 U-Boot 还活着、能用 recovery 或串口救回的，是"半砖"；连 Bootloader 都损坏、必须拆机接烧录器的，才是"全砖"。OTA 设计的目标不是"永不出错"，而是**任何单一故障最多造成半砖，且半砖能自动恢复**。

> CRA（Cyber Resilience Act，网络弹性法案）：欧盟法规，要求 2027 年起在欧盟销售的"含数字元素的产品"必须具备安全更新能力——包括漏洞修复的交付机制、更新完整性的保护、默认安全配置。对嵌入式产品的直接含义：OTA 不再是"旗舰功能"，而是准入门槛；本章 21.5 讲的签名验证正是 CRA"更新完整性"要求的技术对应物。

<!-- -->

> 💡 国内销售的产品同样躲不开：关键信息基础设施相关产品有等保 2.0 的补丁管理要求，车联网有 GB 44495-2024《汽车整车信息安全技术要求》对软件更新的强制规定。就算都不沾，"三千台设备里 1% 变砖就是三十次上门"这本账也够说服任何产品经理。

## <span class="blue">失败模式清单：设计的真正起点 [E]

大多数 OTA 教程从"选 RAUC 还是 Mender"开始讲。这是把答案放在问题前面。工程上正确的顺序是反过来的：**先把会怎么死列清楚，再看哪个方案、哪些机制能挡住这些死法**。

以 3000 台 AMR 的场景过一遍，失败模式一共五类：

### 失败模式一：断电变砖

机器人在充电座上更新，客户下班直接拉闸；或者更新包正在写入 eMMC，机器人电量耗尽自动关机。写到一半的 rootfs 是不完整的，下次启动就是死局——除非系统根本没有"写到一半的系统"这个概念（21.3 的 A/B 双槽）加上"起不来就切回去"的兜底（21.4 的 bootcount）。

### 失败模式二：坏包变砖

下载在抖动的 Wi-Fi 上中断又续传，拼接出的包字节数对了、内容是错的；或者构建机上打包时混入了测试版本的文件。设备装上一个"能装上但起不来"的系统。挡住它靠两道：安装前的完整性与签名校验（21.5），以及起不来时的自动回切（21.4）。

### 失败模式三：恶意固件

更新服务器被攻破，或者中间人在仓库 Wi-Fi 里塞了一个"更新包"。没有验签的设备会高高兴兴地把攻击者的系统装上——三千台机器人就是三千台跳板。挡住它靠签名验证（21.5），这是 CRA 的硬性要求，没有商量余地。

### 失败模式四：回滚攻击

攻击者不投毒新包，而是骗设备装回一个**带已知漏洞的旧版本**——包是官方签的、验签完全通过，但装完设备就裸奔了。挡住它靠防降级机制（21.5 的安全版本号）。

### 失败模式五：分发压垮

运维在周五下午对"全部设备"点了发布：三千台机器人同时拉 200MB 的包，服务器带宽打满、仓库 Wi-Fi 瘫痪、更新反而大面积失败。挡住它靠更新策略：灰度分波、限速、按仓库分批（21.5）。

把清单收敛成一张表，右边就是它对应的本章决策域：

| 失败模式 | 死的姿势 | 防御机制 | 在哪节 |
|:---|:---|:---|:---:|
| 断电变砖 | 写一半的 rootfs 被启动 | A/B 双槽 + bootcount 回切 | 21.3 / 21.4 |
| 坏包变砖 | 装上了起不来的系统 | 完整性校验 + 自动回切 | 21.5 / 21.4 |
| 恶意固件 | 刷了攻击者的系统 | 签名验证 | 21.5 |
| 回滚攻击 | 被骗装回有漏洞的旧版 | 防降级（安全版本号） | 21.5 |
| 分发压垮 | 三千台同时拉包 | 灰度策略与限速 | 21.5 |

> 💡 这张表还有一列隐藏信息：bootcount 回切出现了两次，签名验证出现了两次——**回切和验签是性价比最高的两道防线**，预算再紧也得有。而灰度策略只挡一类失败，却是唯一一类"设备端全都做对也会发生"的失败——它常被设备端出身的团队漏掉。

## <span class="blue">更新窗口：断电概率的量化入口 [E]

"断电变砖"听着像小概率事件，量化一下就不是了。先把更新过程的时间账算出来：

| 阶段 | 耗时（AMR 实测口径） | 说明 |
|:---|:---|:---|
| 下载 1.2GB 更新包 | 10~40 分钟 | 仓库 Wi-Fi 抖动，断点续传 |
| 写入备用槽位 | 3~6 分钟 | eMMC 连续写约 200MB/s，含校验翻倍 |
| 重启 + 新系统自检 | 1~2 分钟 | 起服务、跑健康检查、mark-good |
| **合计危险窗口** | **约 15~45 分钟** | 其中写槽位阶段最致命 |

下载阶段断电不致命（包没写完，下次续传重来），**真正致命的是写槽位到 mark-good 之间的几分钟**。拿这几分钟乘一下 fleet 规模：3000 台 × 每年 12 次更新 × 每次 5 分钟危险窗口，一年暴露在"写着一半"状态的设备-次数是 30 万次·分钟。哪怕单次断电概率只有万分之一，一年也有几十台设备要在断电中走一遭——没有 A/B 和回切，这就是几十次上门。

所以 OTA 设计里有一个独立于方案的决策：**更新窗口——什么条件下才允许进入危险窗口**。常见约束四条，全是产品场景的直接推论：

1. **电量门槛**：电池电量 >50% 或正插在充电座上，排除"更新中途电量耗尽自动关机"；
2. **业务空窗**：机器人处于空闲任务态，不在搬运途中——写槽位时 CPU/IO 繁忙，业务会抖；
3. **时段偏好**：仓库熄灯后的夜间时段，进一步压低"客户随手拉闸"的概率；
4. **错过容忍**：离线三周的设备醒来后错过灰度波次，下次开机要能补更，而不是永远停留在旧版——这条决定 21.5 灰度策略里"补更队列"的存在。

窗口约束挡不住断电（客户拉闸不讲道理），它只能把暴露在危险窗口里的次数压到最低；真正兜底断电后果的，仍然是 21.3/21.4 的 A/B 与回切。这就是"防线分层"：窗口是概率控制，双槽是后果控制，两层缺一不可。

## <span class="blue">一支 fleet 不止一种设备：包不能刷错 [E]

前面所有讨论都假设 fleet 是均质的，现实不是。机器人公司三条产品线（AMR、协作机械臂、人形），单 AMR 一条线就有两代硬件：老款 Jetson 平台、新款 x86 平台，外壳一样、客户混用。这带来失败模式清单之外的一个独立问题：**包必须只装到对的设备上**。

刷错的后果比不更新严重得多。x86 的 rootfs 刷进 Jetson 设备，镜像本身校验和签名全部合法——它是官方包，只是不属于这台机器。装完起不来，靠回切能救，但三千台里只要有几十台因为后台配置分错组而误刷，就是一场可避免的批量回切事故，客户看到的是"这批机器人更新完集体重启了两遍"。

防误刷要求更新包里有一个"我属于哪类硬件"的标识，设备安装前先比对——RAUC 里这个字段叫 `compatible`，21.2 会看到它的配置，21.6 会裁决双架构 fleet 怎么用一套后端管两套包。这里只需要记住：**fleet 的硬件多样性必须在 21.1 的失败模式清单阶段就被点名**，否则选型时一定会漏掉"防误刷"这条评估项——自研脚本最容易漏的正是它（脚本只认 IP 段分组，分组配错就全错）。

同样属于 fleet 多样性的还有硬件批次：同一代 AMR 换过雷达供应商，两批设备跑同一个 rootfs、靠不同的设备树区分。这类差异不决定 OTA 包怎么分，但决定 21.4 mark-good 的健康检查必须覆盖"本批次的外设真的起来了"——健康检查判据写得太泛，新批次设备的驱动问题会被误判成更新失败而触发大面积回切。

## <span class="blue">那"scp 替换文件"错在哪 [E]

回到开头的做法，用失败模式清单量一下它：

| 失败模式 | scp 替换的表现 |
|:---|:---|
| 断电变砖 | 写到一半断电，rootfs 残缺，**全砖**，串口救砖 |
| 坏包变砖 | 没有任何校验，传错一字节就是砖 |
| 恶意固件 | 没有任何验签，能 ssh 上就能刷 |
| 回滚攻击 | 没有版本概念，随便装 |
| 分发压垮 | 没有分发概念，一台一台来 |

五种死法全中。它不是"简化版 OTA"，它是 OTA 要消灭的东西。这个对照也是评估一切 OTA 方案的尺子：21.2 选型时，任何一个候选方案都可以拿这张表问一遍——它挡住了哪几类，没挡住的那几类你打算怎么办。

## <span class="blue">本章的方法论 [E]

把本节的逻辑收拢成一条工作顺序，后面五节严格按它走：

1. **先列失败模式**——用你的产品场景把五类死法具体化（谁的设备会断电？网络有多差？离线多久？）；
2. **再定防线**——每类失败模式至少有一道机制兜底，标注它花什么成本（存储、复杂度、密钥基础设施、云端容量）；
3. **最后选方案**——带着防线清单去评估 RAUC / SWUpdate / Mender / 自研，方案是防线的载体，不是起点。

这也是 21.6 综合实战的评审逻辑：机器人公司的 OTA 架构能不能过评审，就看每一类失败模式有没有被点名、被分配、被验证（断电测试矩阵）。

## <span class="blue">本节总结

OTA 的本质是一个跨设备端、云端、通道、存储、启动链的分布式系统，设计目标是"任何单一故障最多造成能自动恢复的半砖"。它已经从旗舰功能变成法规准入门槛（EU CRA 2027，国内等保与车规同理）。

设计的起点不是选方案，是列失败模式：断电变砖、坏包变砖、恶意固件、回滚攻击、分发压垮——五类死法各自对应本章的一个决策域，其中回切与验签是性价比最高的两道防线。失败模式之外还有两个场景约束必须先点名：更新窗口（把暴露在危险窗口里的次数压到最低，是概率控制层）和 fleet 硬件多样性（包必须只装到对的设备上，误刷是可避免的批量事故）。`scp` 替换文件五类全中，它就是 OTA 要消灭的东西。带着这张清单，下一节开始评估方案。
