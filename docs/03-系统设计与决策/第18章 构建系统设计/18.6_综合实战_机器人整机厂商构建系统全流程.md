# 18.6 综合实战：机器人整机厂商构建系统全流程

> 所属章节：第18章 构建系统设计
>
> 难度：[E] | 预计阅读时间：80分钟

## <span class="blue"> 本节导读

18.1~18.5 各自闭环了一个决策域：18.1 给出选型矩阵和决策树，18.2 给出 TCO 的算账方法，18.3 给出 Layer 组织的工程纪律，18.4 给出 CI 的分层与预算，18.5 给出合规的工具链。但每一节的结论都是在"其他域已收敛"的假设下做出的——18.1 的决策树默认你只选一个系统，18.4 的预算表默认 Layer 组织已经干净，18.5 的 CVE 闭环默认 CI 里有一环能挂上 yocto-vex-check。<BR>
本节把这些假设全部撤掉，回到那家贯穿全章的机器人整机厂商：3 条产品线、5 个 SKU、4 小时的 CI、9 月 11 日生效的 CRA 漏洞报告义务。全章埋下的三个悬念在这里当面裁决：

- **悬念一**（18.1 埋下）：人形新品线想用 Buildroot 快速启动，全公司统一 Yocto 还是放行？
- **悬念二**（18.4 埋下）：CI 全量 4 小时，怎么砍到研发能忍的范围？
- **悬念三**（18.3 埋下）：5 个 SKU 的 Layer 到底怎么分，目录树长什么样？

每个悬念的裁决都明确标注它调用了哪一节的哪件工具——这不是修辞，是本章方法论的最后一次演练：架构决策的质量，取决于你调用的工具是否覆盖了这个问题的真实约束。<BR>
走查之后是三案例复盘（医疗 FDA / IoT Buildroot / Buildroot→Yocto 迁移）和 20 项评审清单，把全章结论固化为三个里程碑上的证据检查。

## <span class="blue"> 走查一：人形产品线，统一 Yocto 还是放行 Buildroot

### 悬念的来路

18.1 的决策树在"团队 < 3 人、单 SKU、无合规压力"的分支上把答案给了 Buildroot。人形产品线的现状恰好踩在这条分支的边缘：团队 4 人（略超线），单 SKU（人形只有一个机型），合规压力名义上存在（公司层面有 CRA 和大客户审计），但产品还在原型期，对外发布至少一年以后。人形线负责人的原话是："AMR 线的 Yocto 构建要等 40 分钟，我们一天要改十几版电机控制参数，等不起。"

这是一个真实的冲突，不是矫情。原型期的迭代速度是生存问题，18.2 的 TCO 曲线在"前 6 个月"那一段确实站在 Buildroot 一边。

### 调用 18.1 的决策树：先问"多 SKU 计划"

决策树的第一个分叉不是团队规模，是**产品线的 SKU 演化方向**。把人形线的路线图摆上桌面问三个问题：

1. 人形产品量产后会不会出第二个机型？（答：几乎必然——AMR 线就是这么走过来的，第一代单机型，第三年裂成两个 SKU。）
2. 人形线要不要过 CRA？（答：要在欧盟卖就绕不开，2027-12-11 全面适用，恰好落在人形线的量产窗口内。）
3. 人形线的镜像结构和 AMR 线有多大共性？（答：recovery、OTA 分区、出厂烧录流程完全同构，差异只在应用层和 BSP。）

三个回答合起来，决策树的指针已经不再指向 Buildroot 分支——它指向的是 18.1 的"混合策略"区域。但直接否决人形线的诉求是另一种错误：原型期的迭代速度损失是**现在就要付的现金**，而 Yocto 的回报是**两年后的期权**。用 18.2 的语言说，这是一个"现金 vs 期权"的权衡，不能用期权的名义没收现金。

### 裁决：按镜像角色选型，不按产品线选型

最终裁决不是二选一，而是把"镜像"拆成两种角色，每种角色独立选型：

| 镜像角色 | 选型 | 理由 |
|----------|------|------|
| 主系统镜像（rootfs，跑 ROS 2 和业务） | Yocto，全公司统一 | 合规产物（SBOM、CVE 闭环）挂在这条流水线上；多 SKU 差异由 Layer 吸收 |
| recovery / 工厂烧录镜像 | Buildroot，全公司统一一份 | 小包数（< 40 个包）、无包管理、构建 8 分钟；原型期人形线直接拿它当日常开发镜像用 |

这个裁决的关键在于：**人形线抱怨的"等不起"，痛点不是 Yocto 本身，而是把"日常迭代调试"和"出合规镜像"混在了同一条流水线上**。拆开后：

- 原型期日常迭代走 Buildroot 镜像：改参数、重编、烧录，8 分钟闭环，人形线的诉求被完整满足。
- 每周一次和每次对外送样，走 Yocto 流水线出主系统镜像：SBOM、CVE 扫描、签名一并产出，合规债不积累。
- Buildroot 侧只做"能跑起来"的最小集，**禁止**在 Buildroot 镜像里堆积业务包——这是防止"临时方案永久化"的纪律条款。18.2 讲过的 local.conf 膨胀，在双系统架构里有一个变种：Buildroot 的 defconfig 悄悄长成第二个发行版。防御方法写在评审清单第 6 项。

> 💡 这个"recovery 用 Buildroot、主系统用 Yocto"的组合不是本书的发明，是行业里的常见实践：recovery 镜像的技术画像（小包数、静态、无网络更新需求、构建要快）恰好是 Buildroot 的最优点；主系统的技术画像（多 SKU、合规、长期维护）恰好是 Yocto 的最优点。按镜像角色选型比按产品线选型精确一级。

### 迁移期权定价

18.2 的框架里，Buildroot 原型期是一张"迁移期权"：现在付小的持有成本（维护两份 defconfig 纪律），换取"万一主系统 Yocto 化遇到阻力时再迁移"的权利。这张期权在本裁决里其实没有被行使——人形线从第一天起主系统就在 Yocto 流水线上，Buildroot 只是加速器。期权的价值体现在另一面：**如果人形线项目在原型期被砍，沉没成本只有 Buildroot 侧的一点配置，没有 Layer 和 CI 的废墟**。这是 18.2"首次发布前迁移成本是发布后一半"的镜像命题：首次发布前砍项目，损失也只有发布后砍项目的一半。

走查一的结论登记：人形线放行 Buildroot 作日常开发镜像，主系统镜像仍走统一 Yocto 流水线；defconfig 包数红线 40，纳入首版发布里程碑检查。

## <span class="blue"> 走查二：4 小时 CI 砍到多少算够

### 悬念的来路

18.4 末尾留了一笔账：全量构建 4 小时，其中 ROS 2 相关 recipe 占了将近一半，Jetson 和 x86 双架构各跑一遍，sstate 命中率只有 61%。研发的实际体验是：上午提 PR，下午才能看到构建结果，下班前才能看到 HIL 报告。18.4 给了归因方法和预算表模板，但没有替这家公司把数字填上。

### 调用 18.4 的归因表

先把 4 小时拆开。归因方法来自 18.4（按 recipe 维度统计耗时、按阶段统计等待），实测数据如下：

| 阶段 | 耗时 | 占比 | 归因结论 |
|------|------|------|----------|
| 源码 fetch（含 git clone） | 22 min | 9% | 无本地镜像，每次全量拉取 |
| 编译（sstate 未命中部分） | 118 min | 49% | 命中率 61%，ROS 2 recipe 变更多、缓存碎片化 |
| 镜像打包 + SDK 生成 | 18 min | 8% | 每次全量生成 SDK，无人使用 |
| x86 仿真测试 | 34 min | 14% | 串行执行，与 ARM 构建互相等待 |
| HIL（Jetson + ARM 板各一轮） | 48 min | 20% | 只有 2 块测试板，排队严重 |

归因表的价值在于它直接指出钱该花在哪：编译占 49%，但编译时间的大头不是"机器慢"，是 sstate 命中率低；HIL 占 20%，大头不是测试本身慢，是板子少。

### 三层优化与预算表

按 18.4 的分层触发策略，把"一次 4 小时"拆成三个目标不同的层级：

**PR 层（目标：40 分钟内给反馈）**。只构建变更影响的 Layer 涉及的 image，用共享 sstate 镜像 + 本地源码镜像（fetch 从 22 分钟降到 3 分钟）；SDK 生成移出 PR 层；测试只跑 x86 仿真的冒烟集（8 分钟）。预算：fetch 3 + 编译（命中率高，增量小）18 + 打包 4 + 冒烟 8 = **33 分钟**。

**Nightly 层（目标：全量，但无人等待）**。完整双架构构建 + 完整仿真测试集 + yocto-vex-check（18.5 挂进来的那一环）。sstate 命中率是优化的主战场：ROS 2 recipe 的 `SRCREV` 浮动引用改为锁定 + `BB_SIGNATURE_HANDLER` 排错后，命中率从 61% 提到 89%，编译时间从 118 分钟降到 52 分钟。总时长降到约 2 小时，但它在夜里跑，时长只影响"第二天早上报告齐不齐"，不影响研发节奏。

**Release 层（目标：正确性，不计时）**。全量 + SDK + SBOM 归档 + 签名 + HIL 全量。HIL 排队用资源调度解（18.4 的 HIL 池化方案：测试板从 2 块扩到 5 块，按 SKU 分池），Release 候选每周出一次，排队可接受。

优化前后对比：

| 指标 | 优化前 | 优化后 |
|------|--------|--------|
| PR 反馈时间 | 4 小时+ | 33 分钟 |
| 全量构建时长 | 4 小时 | ~2 小时（夜间） |
| sstate 命中率 | 61% | 89% |
| HIL 等待 | 不确定，排队 | 池化调度，Release 层独占窗口 |
| 研发感知 | 一天一轮迭代 | 一天 5~8 轮迭代 |

注意这张表里**没有一项是"换更快的机器"**。构建系统的性能问题，九成是结构问题（层级、缓存、触发策略），一成才是硬件问题——先改结构，结构改完还不够再买机器，顺序反了会把钱扔进水里。

> ⚠️ sstate 命中率从 61% 到 89% 的具体操作是 18.4 已讲过的方法（锁定 SRCREV、清理 recipe 里的时间戳/绝对路径、统一 `TMPDIR`），此处不重复。走查只负责证明"调用那件工具能把这家的数字改掉"。

走查二的结论登记：三层预算 33 分钟 / 2 小时 / 不计时；sstate 命中率 ≥ 85% 写入 CI 健康指标，纳入年度复审里程碑。

## <span class="blue"> 走查三：5 个 SKU 的 Layer 组织定稿

### 悬念的来路

18.3 给了分层的四条纪律（按变化频率分层、bbappend 只准向下、补丁集中管理、MACHINE 驱动差异），并以"一家多产品线公司"为例画了目录树。现在把抽象例子替换成这家公司的真名：AMR 两个 SKU（差速底盘 amr-d、麦克纳姆底盘 amr-m），协作机械臂两个 SKU（6 轴 arm-6、7 轴 arm-7），人形一个 SKU（humanoid-h1），双架构（AMR 用 Jetson Orin，机械臂 x86 工控机，人形 Jetson Thor）。

### 调用 18.3 的纪律逐条落地

**纪律一：按变化频率分层。** 变化最慢的是 BSP（跟着芯片厂商走），其次是公司公共层（distro 配置、安全基线、OTA 框架），再次是产品线层（AMR 的导航栈、机械臂的运动学库），最快的是 SKU 层（具体机型的参数和外设配置）。四层对应四个 Layer 目录：

```text
meta-robot-company/          /* 公司层：distro、安全基线、OTA、CVE 处置 */
├── conf/distro/robotos.conf
├── recipes-core/base-files/...
└── classes/robotos-image.bbclass

meta-robot-amr/              /* AMR 产品线层：导航栈、底盘抽象 */
meta-robot-arm/              /* 机械臂产品线层：运动学、力控 */
meta-robot-humanoid/         /* 人形产品线层：全身控制 */

meta-bsp-jetson/             /* BSP 层：Jetson 全系，厂商 meta-tegra 之上的公司适配 */
meta-bsp-x86-industrial/     /* BSP 层：x86 工控机 */
```

**纪律二：bbappend 只准向下。** 产品线层可以 bbappend 公司层的 recipe，SKU 配置可以 bbappend 产品线层，反向禁止。这条纪律的实际约束力在一个具体场景体现：AMR 线的导航栈需要改公司层 OTA 客户端的一个配置项——不允许在 meta-robot-amr 里 bbappend 公司层的 OTA recipe，正确做法是公司层 OTA recipe 暴露一个 `PACKAGECONFIG` 旋钮，AMR 层拧旋钮。改别人层的内容是借债，拧自己层暴露的旋钮是调用接口。

**纪律三：补丁集中。** 所有 `.patch` 文件集中放在各层自己的 `files/` 目录，补丁头必须有 `Upstream-Status` 字段。18.5 的 CVE 处置闭环依赖这个字段：`CVE_STATUS` 标注为"已修复"的 CVE，必须能指到带 `Upstream-Status: Backport` 的具体补丁文件，否则审计时"修复了"三个字没有证据。

**纪律四：MACHINE 驱动差异。** 5 个 SKU 的差异全部落为 MACHINE 配置 + 对应 image recipe 的组合，不允许出现"某个 SKU 专属改 distro 配置"的情况——distro 是全公司一张脸，SKU 差异碰 distro 意味着分层失守。SKU 矩阵定稿：

| SKU | MACHINE | 产品线 Layer | image recipe |
|-----|---------|-------------|--------------|
| amr-d | jetson-orin-amr-d | meta-robot-amr | robotos-image-amr |
| amr-m | jetson-orin-amr-m | meta-robot-amr | robotos-image-amr |
| arm-6 | x86-ind-arm-6 | meta-robot-arm | robotos-image-arm |
| arm-7 | x86-ind-arm-7 | meta-robot-arm | robotos-image-arm |
| humanoid-h1 | jetson-thor-h1 | meta-robot-humanoid | robotos-image-humanoid |

注意 `robotos-image-amr` 是一个 recipe 服务两个 SKU：机型差异在 MACHINE conf 里（设备树、内核 fragment、启动参数），image 只关心"AMR 要装哪些包"。这是 18.3"MACHINE 驱动差异"纪律的直接产物——如果 image recipe 按 SKU 拆成五个，包列表的漂移就不可控了。

走查三的结论登记：四层 Layer 目录树定稿，`layerindex` 风格的依赖声明文件归档到仓库根目录；bbappend 方向检查和补丁 Upstream-Status 检查做成 CI 静态检查项（挂在走查二的 PR 层，成本约 40 秒）。检查脚本本身简单到可以全文给出——这正是"纪律自动化"应有的成本：

```bash
#!/bin/bash
# ci/layer-hygiene.sh —— PR 层静态检查，跑在构建之前
fail=0

# 检查一：bbappend 只准指向更低层（层优先级由 LAYERDEPENDS 声明）
# 规则：meta-robot-* 产品线层不许 bbappend 其他产品线层的 recipe
for bb in $(git diff --name-only origin/main...HEAD | grep '\.bbappend$'); do
    layer=$(echo "$bb" | cut -d/ -f1)                 # 改动所在层
    target=$(basename "$bb" .bbappend | cut -d_ -f1)  # 叠加的 recipe 名
    # 该 recipe 的原生层必须出现在本层的 LAYERDEPENDS 里
    grep -q "LAYERDEPENDS.*$target" "$layer/conf/layer.conf" || {
        echo "违规：$bb 叠加了未声明依赖的 recipe"; fail=1; }
done

# 检查二：所有补丁必须带 Upstream-Status 头
for p in $(git diff --name-only origin/main...HEAD | grep '\.patch$'); do
    grep -q "^Upstream-Status:" "$p" || {
        echo "违规：$p 缺 Upstream-Status 头"; fail=1; }
done

exit $fail
```

脚本不需要完美——它拦的是"方向性错误在 PR 阶段混入"，哪怕只有 80% 准确率，也把纪律从"靠人记"变成了"靠门拦"。

### 三个悬念的合流

回头看，三个裁决互相咬合：走查一决定"主系统统一 Yocto"，走查三的 Layer 树才有存在的前提；走查三的干净分层是走查二 sstate 命中率 89% 的结构性原因——分层乱了，签名就碎，缓存就废；走查二的 PR 层 33 分钟，让走查一里"Yocto 等不起"的反对意见失去了力度。这正是本节开头那句话的实证：**单独看每个决策域的结论都是对的，但只有当它们在同一张桌面上互相咬合时，架构才算完成**。

## <span class="blue"> 案例复盘一：医疗设备厂商的 Yocto 与 FDA

### 约束

一家做床旁监护仪的公司，产品在美国上市，走 FDA 上市前通告路径。2023 年 9 月 FDA 发布最终版上市前网络安全指南后，申报资料里必须包含 SBOM，且 FDA 明确期望制造商具备"监控上市后漏洞并修复交付"的闭环能力。设备生命周期 10 年以上，现场设备不能随意升级，但每次升级一旦被审查，就要能回答"五年前发布的那一版，里面每个组件的版本和已知漏洞状态是什么"。

### 选择

Yocto，并且做了两个超出常规配置的决定：

1. **构建可复现作为一等目标**。`create-spdx` 之外，锁定所有 `SRCREV`、启用 sstate 归档、源镜像离线保存。目标不是技术洁癖，是审计需求：五年后监管机构问"版本 3.2.1 的 SBOM"，公司必须能重新构建出同一份 SBOM，而不是从某个工程师的电脑里翻出一个 PDF。
2. **合规产物与镜像同流水线**。SBOM、CVE 报告、许可证清单不作为独立流程，全部是构建的自然产物——`bitbake` 出镜像的同一个任务顺带产出。任何"单独跑一个脚本生成 SBOM"的做法都被拒绝，因为单独流程必然和实际发布物漂移。

### 代价

学习曲线由两个专职工程师承担了三个月；构建时间比团队之前的 Makefile 方案长了 5 倍（从 20 分钟到约 100 分钟），用 sstate 和夜间构建消化；`REPRODUCIBLE_BUILD` 目标迫使团队清理了几十个 recipe 里的时间戳和绝对路径，这些债本来就在，只是现在被要求当场还清。

### 教训

合规压力在这个案例里不是发布前的补票，而是**选型时的第一约束**——"五年后能重新证明当时构建了什么"这条需求，直接排除了所有不具备可复现能力的方案。教训的普适形式：先确认你的行业监管者五年后会问什么问题，再回头决定今天用什么构建系统。CRA 把这条教训从医疗行业推广到了整个欧盟市场，这正是 18.5 的内容。

## <span class="blue"> 案例复盘二：LoRa 传感器厂商的 Buildroot

### 约束

两人团队，一款 LoRa 温湿度传感器，瑞芯微低功耗 SoC，8MB SPI NOR，无屏幕、无网络管理界面、无包管理需求——固件升级就是整机换镜像。投资人给的窗口是六周内出可演示样机，实际目标被压到两周出第一版。

### 选择

Buildroot，毫无悬念。18.1 决策树上这是最干净的一条路径：团队 2 人、单 SKU、镜像小包数（31 个）、无合规压力、无 OTA 差分需求。defconfig 第一天下午就建好了，第一版可烧录镜像在第四天产出，剩下的时间全部给了应用开发——这正是 Buildroot 的价值定位：**它不解决构建系统问题，它让构建系统从问题清单上消失**。

### 代价

当时看几乎没有。五年后回头看，有两笔账浮现过但都被接住了：一次是客户要求提供组件清单（出口合规筛查），`make legal-info` 一小时解决；一次是想给传感器加 OTA 差分，发现 Buildroot 没有包管理粒度的更新机制，最终用双分区 A/B 整镜像替换实现——对 8MB 的固件，整镜像替换本来就是合理方案，这不算代价，算边界确认。

### 教训

这个案例是 18.2 TCO 模型的反向实证：所有"Buildroot 五年后还债"的剧本（多 SKU 分裂、合规审计、包管理需求）在这个产品上一个都没发生，因为它的产品形态天然免疫——单 SKU 到底、生命周期内功能冻结、升级整镜像。**Buildroot 的风险不是"用了就会还"，是"用的时候误判了自己产品的演化方向"**。这家公司的幸运在于产品真的没变；如果第三年投资人要求"基于这个硬件平台出一个网关产品线"，故事就会滑向案例三。

## <span class="blue"> 案例复盘三：从 Buildroot 迁移到 Yocto

### 约束

一家工业网关公司（不是 17.6 那家，但处境相似），Buildroot 起步，两年内从 1 个 SKU 长到 4 个 SKU，两个架构（ARM + x86）。压垮现状的是两件事先后发生：大客户把 IEC 62443 审计条款写进了采购合同，要求 SBOM 和漏洞处置记录；同时第四个 SKU 的 defconfig 和前三个的差异已经没人敢合并——每个 SKU 的 defconfig 都是从前一个拷贝修改而来，公共修改要手工同步四份。

### 选择

迁移到 Yocto。决策本身没有悬念，有悬念的是**时机和方式**。公司选择不停产品线、边维护旧系统边建新系统：两名工程师投入四个月，第一个月建公司层和 BSP 层，第二个月迁移第一个 SKU 并双跑验证（同一源码，Buildroot 和 Yocto 各出镜像，现场各装一半设备对比运行），第三、四个月滚动迁移剩余 SKU 并下线 Buildroot 流水线。

### 代价

2 人 × 4 个月 = 8 人月，占当时研发总人力的 40%。隐藏成本有两笔：一是双跑期发布节奏减半，错过了一个招标窗口；二是迁移完成后发现 Buildroot 时代积累的一批"直接改包源码"的本地补丁没有记录，逐包考古花掉了预算外的三周——这就是 18.3"补丁集中管理"纪律要防的债，这家公司是带着疤学到的。

### 教训

18.2 里"首次发布前迁移成本是发布后一半"在这家公司身上精确应验：他们自己估算，如果在第三个 SKU 立项时（产品尚未大规模出货）就迁移，工作量约 2 人 × 2 个月。晚一年半，代价翻一倍，外加一个招标窗口。教训的可执行形式：**在 Buildroot 项目的 README 里写死迁移触发条件**（SKU 数 > 2、出现合规要求、defconfig 出现第二次跨 SKU 同步冲突——任一命中即启动评估），把"什么时候该走"从事后惋惜变成事前约定。

### 三案例的公共结构

三个案例放在一起，重复出现的是同一个骨架：**约束不可控（监管、产品形态、客户条款），解法是结构性的（可复现流水线、选型与产品形态匹配、触发条件前置），代价被量化接受（人月、构建时长、错过的窗口）**。构建系统决策没有"选对了就免费"的选项，只有"清楚地知道自己为什么付钱"的选项。

## <span class="blue"> 构建系统评审清单

20 项，分四组，对应 18.1/18.3/18.4/18.5 四个决策域（18.2 的 TCO 方法渗透在各组的"证据"要求里）。每项都要证据，不接受口头回答。三个里程碑：**S** = 选型评审（项目立项），**R** = 首版发布评审，**Y** = 年度复审。

### 第一组：构建系统选择（对应 18.1）

| # | 检查项 | 要看的证据 | 里程碑 |
|---|--------|-----------|--------|
| 1 | 选型决策走了决策树且记录了每个分叉的回答 | 选型文档，含"多 SKU 计划""合规压力"两问的明确回答 | S |
| 2 | 产品线 SKU 演化方向有书面判断，并由产品线负责人签字 | 路线图文档，不是口头共识 | S |
| 3 | TCO 测算覆盖了 5 年，含学习成本与构建时间成本 | TCO 表，公式可追溯（18.2 口径） | S |
| 4 | 未入选方案的放弃原因被记录（防止两年后重开议题） | 选型文档的"被否方案"章节 | S |
| 5 | 若为混合方案（如主系统 Yocto + recovery Buildroot），各镜像角色的职责边界成文 | 镜像角色表（18.6 走查一格式） | S |

### 第二组：Layer 与配置组织（对应 18.3）

| # | 检查项 | 要看的证据 | 里程碑 |
|---|--------|-----------|--------|
| 6 | 单一系统内无配置膨胀：Yocto 的 local.conf < 50 行有效配置；Buildroot 的 defconfig 包数在产品红线内 | 仓库实况 + 红线值记录 | R, Y |
| 7 | Layer 按变化频率分层，每层有 owner 和变更评审规则 | Layer 目录树 + 每层 README 声明 | R |
| 8 | bbappend 只指向更低层，无反向引用 | CI 静态检查报告（18.6 走查三的 40 秒检查项） | R, Y |
| 9 | 全部补丁带 Upstream-Status 头，集中存放，无"直接改包源码" | 补丁目录审计 + grep 验证 | R, Y |
| 10 | SKU 差异全部经 MACHINE/image recipe 吸收，distro 配置与 SKU 无关 | distro conf 的 git log 无 SKU 专属提交 | R |

### 第三组：CI/CD（对应 18.4）

| # | 检查项 | 要看的证据 | 里程碑 |
|---|--------|-----------|--------|
| 11 | PR / Nightly / Release 三层触发策略成文，各层有明确时长预算 | CI 配置 + 预算表（18.6 走查二格式） | R |
| 12 | PR 反馈时间达标（预算内），超标有归因流程 | 最近一个月的 CI 时长统计 | R, Y |
| 13 | sstate 命中率纳入健康指标（基线 ≥ 85%），低于阈值触发排查 | 命中率监控看板截图或导出 | Y |
| 14 | HIL 资源有池化调度，测试板数量与 SKU 矩阵匹配 | HIL 排队时长统计 | R |
| 15 | 每次 Release 的镜像可追溯到具体 commit、Layer 版本与构建环境 | 一次真实 Release 的追溯演练记录 | R |

### 第四组：开源合规与 SBOM（对应 18.5）

| # | 检查项 | 要看的证据 | 里程碑 |
|---|--------|-----------|--------|
| 16 | SBOM 是构建流水线的自然产物，非独立流程 | 最近一次构建的 SBOM 产物与镜像同批次记录 | R |
| 17 | CVE 处置六态标注完整，"已修复"项能指到具体补丁 | cve-check / yocto-vex-check 报告抽样 | R, Y |
| 18 | 历史版本的 SBOM 可重新生成（可复现性） | 抽一个 ≥6 个月前的版本现场重建 SBOM | Y |
| 19 | 许可证清单与 copyleft 隔离审查完成（GPL 组件不进专有链路） | legal-info / archiver 产物 + 审查记录 | R |
| 20 | CRA 漏洞报告义务流程就绪：24h 预警与 72h 通报的责任人、模板、演练记录 | 漏洞响应演练记录（桌面推演即可） | R, Y |

清单的用法和 17.6 一致：评审不是逐项打勾，是逐项看证据。第 18 项的"现场重建"是整张清单里最贵的一项，也是最诚实的一项——它直接检验第 16 项和第 17 项是不是纸面功夫。

## <span class="blue"> 本节总结

本节把三个悬念在同一张桌面上裁决：人形线放行 Buildroot 作日常开发镜像、主系统仍走统一 Yocto——按镜像角色选型而不是按产品线选型；CI 拆成 33 分钟 PR 层、2 小时 Nightly 层、不计时 Release 层，sstate 命中率 61% 到 89% 靠结构不靠加机器；5 个 SKU 落进四层 Layer 树，bbappend 方向与补丁 Upstream-Status 固化为 CI 静态检查。三个裁决互相咬合，证明了"每个决策域单独正确"不等于"架构完成"。三案例复盘重复了同一个结构：约束不可控、解法是结构性的、代价被量化接受；20 项评审清单把全章结论转化为选型、首版发布、年度复审三个里程碑上的证据检查。至此第 18 章闭环：构建系统设计的产出不是一个 Makefile 或一张 defconfig，是一套能在五年尺度上持续证明"我们构建了什么、为什么这样构建"的组织能力。

### 速查表

| 问题 | 一句话答案 | 出处 |
|------|-----------|------|
| 统一 Yocto 还是放行 Buildroot？ | 按镜像角色选型：主系统 Yocto 统一，recovery/开发镜像 Buildroot | 走查一 |
| CI 4 小时怎么砍？ | 三层触发：PR 33 min / Nightly 2 h / Release 不计时；sstate 命中率 ≥85% | 走查二 |
| 5 个 SKU 怎么组织 Layer？ | 按变化频率四层：公司层/产品线层×3/BSP 层；SKU 差异进 MACHINE | 走查三 |
| 医疗 FDA 案的核心？ | 合规是选型第一约束；SBOM 必须是构建的自然产物 | 案例一 |
| IoT Buildroot 案的核心？ | Buildroot 的风险是误判产品演化方向，不是工具本身 | 案例二 |
| 迁移案的核心？ | 触发条件事前写死；晚一年半，代价翻倍 | 案例三 |
| 评审怎么落？ | 20 项、四组、三里程碑（S/R/Y），逐项要证据 | 评审清单 |
