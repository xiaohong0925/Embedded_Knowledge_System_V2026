## 核心问题

用Yocto还是Buildroot？

## 本章简介

“Yocto还是Buildroot？怎么设计长期可维护的构建流程？” 构建系统的选择不是一个纯粹的技术偏好问题，而是一个组织性决策。它影响团队的速度、镜像大小、安全姿态、合规能力和长期维护成本。本章的目标是让你能基于产品特征和团队能力做出有理据的选择，并设计出能持续5年以上的构建流程。

有经验工程师通常能熟练使用至少一种构建系统——你可能用Buildroot做过几个项目，或者在Yocto里写过bbappend。

但当你需要带领一个团队、维护一条产品线时，以下问题变得尖锐：团队3个人vs 30个人，构建系统选择应该不同吗？产品需要通过FDA认证，SBOM怎么自动生成？CI构建时间从15分钟变成4小时，增量缓存怎么设计？5年后，当原构建工程师离职时，还有人能维护这个构建系统吗？本章的核心洞察是：构建系统的真实成本不在初始设置，而在5年后的维护。你是一家医疗设备公司的构建系统负责人。

公司有3个产品线的5个SKU，都基于Yocto。合规团队要求每个发布版本都生成完整的SBOM并通过CVE扫描。CI构建目前需要4小时，工程师每天多次等待构建。同时，一个新产品在评估是否用Buildroot”快速启动”。你需要决策：统一用Yocto还是允许Buildroot？怎么优化CI构建时间？Layer/Recipe怎么组织才能管理5个SKU的共享和差异？...
