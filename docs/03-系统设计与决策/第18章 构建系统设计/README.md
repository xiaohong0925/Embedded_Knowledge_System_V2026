# 第18章：构建系统设计

> 所属：第 三 部 系统设计与决策
>
> BIEM：[E] | 核心问题：一套构建流程怎么设计出来，并被证明它能撑五年？

## 核心问题

不是"Yocto 和 Buildroot 哪个好"——那是没有约束就问出口的空问题。本章回答的是：**给你一支团队、一条产品线的演化预期和一组合规要求，怎么推导出一整套构建系统的决策——选型、成本、组织、流水线、合规——并且拿得出证据证明它能撑过五年。**

## 为什么需要这一章

第 17 章说存储架构的风险在于**失效滞后**——断电损坏在量产半年后才出现。构建系统的风险形态不同，是**债务滞后**：local.conf 从 20 行膨胀到 400 行用了两年；defconfig 从单 SKU 拷贝出第四份时没人敢合并；CI 从 15 分钟爬到 4 小时时，团队已经把"等构建"当成了工作节奏的一部分；当年搭构建的工程师离职，留下的 recipe 没人敢动。每一笔债发生时都很小，小到不值得开会讨论；等它大到必须讨论时，利息已经按复利滚了三年。

更棘手的是，构建系统选型是全书第一个把**团队和组织**作为一等决策变量的决策：3 个人的团队和 30 个人的团队，正确答案不一样；一个 SKU 的产品和五个 SKU 的产品线，正确答案不一样；卖欧盟和只卖国内，2026 年 9 月 11 日之后正确答案不一样。纯技术参数对比回答不了这些问题。

有经验工程师对构建系统不陌生——你用 Buildroot 出过镜像，或在 Yocto 里写过 bbappend。但这些问题不会自动有答案：人形新品线想用 Buildroot 快速启动，放行还是统一？CI 4 小时，该砍哪一段、砍到多少算够？五个 SKU 的 Layer 怎么分，差异才不会漂移？SBOM 要怎么做，五年后的审计才认账？

## 本章主线：一个场景，五个决策域，一次合流

本章的核心洞察是：**构建系统决策不是技术选型，是组织能力设计**——它要回答的不是"哪个工具强"，而是"我的团队、产品线、合规环境，五年后需要什么样的构建能力"。

```
18.1 决策矩阵：Yocto / Buildroot / OpenWrt
  13 维对比 + 两棵决策树（产品复杂度×团队规模；合规需求）
  立场：选型 = f(团队规模, 产品线数量, 合规要求, 上市时间)
        │
        ▼
18.2 TCO 模型 ──────> 18.3 Layer/Recipe 组织 ──> 18.4 CI/CD 流水线 ──> 18.5 合规与 SBOM
  真实成本在五年后      分层纪律与 bbappend 方向    三层触发与时长预算     CRA 倒计时
  技术债务的四种形态    补丁 Upstream-Status        sstate 命中率          CVE 处置六态
  迁移期权定价          MACHINE 驱动 SKU 差异       HIL 池化               VEX 与可复现
        │                                                              │
        └──────────────────────────┬───────────────────────────────────┘
                                   ▼
              18.6 综合实战：三个悬念当面裁决（镜像角色选型 / CI 预算 / Layer 定稿）
```

贯穿全章的场景：一家机器人整机厂商，3 条产品线（AMR / 协作机械臂 / 人形）5 个 SKU，双架构（Jetson + x86 工控机），CI 全量 4 小时，欧盟 CRA 漏洞报告义务生效在即，人形新品线想用 Buildroot 快速启动。18.1 用它做初判，18.2~18.5 各自回答它的一类问题，18.6 把三个悬念当面裁决。

学习方案按手头情况二选一：

- **手头有项目**：读 18.1 时给自己产品走一遍决策树并记录每个分叉的回答，读 18.2 时把 TCO 公式填上自己的数字，18.3~18.5 每读完一节对照评审清单（18.6 末尾）自查一遍现状。读完本章你应该攒出一份能过评审的构建架构文档。
- **手头没项目**：跟住机器人公司场景。18.6 会把 18.1~18.5 的每件工具都调用一次——包括"按镜像角色选型"这个决策树之外的第三答案，那是离真实架构评审现场最近的部分。
