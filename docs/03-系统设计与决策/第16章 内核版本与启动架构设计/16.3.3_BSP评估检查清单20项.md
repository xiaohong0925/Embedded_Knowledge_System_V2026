### 3.1 为什么需要系统化评估

SoC选型是一个**高杠杆决策**——一旦硬件设计完成、PCB打样，更换SoC的成本可能高达数十万美元（重新设计、重新验证、重新认证）。而BSP评估是SoC选型中**最容易被低估**的环节。

本节提供一个**20项BSP评估检查清单**，每项都有明确的评分标准和验证方法。

### 3.3 逐项详解

#### 检查项1-3：基础外设支持

这些是最基本的外设——如果它们不工作，产品根本不可用。

**评分标准**：
- **5分**：全部在主线内核中有完整驱动，无需任何厂商patch
- **4分**：主线支持，但需要少量Device Tree调整
- **3分**：需要厂商patch，但patch质量高、易于维护
- **2分**：厂商驱动，无主线支持，patch质量差
- **1分**：驱动不稳定，已知问题多

**验证命令**：
```bash
# GPIO测试
gpioinfo | grep -c "GPIO"  # 确认GPIO线数量正确

# UART回环测试
stty -F /dev/ttyUSB0 115200 raw
echo "TEST" > /dev/ttyUSB0 && cat /dev/ttyUSB0

# SPI回环测试（MOSI短接到MISO）
spidev_test -v -D /dev/spidev0.0

# I2C设备扫描
i2cdetect -y 0
```

#### 检查项4-7：多媒体与加速器

这些是现代嵌入式产品的**核心竞争力**——GPU决定UI体验，VPU决定视频能力，NPU决定AI能力。

> ⚠️ **陷阱（GPU/VPU成熟度）**：很多SoC datasheet上写着"支持4K@60fps H.265解码"，但实际BSP可能只支持特定profile、特定分辨率，或者用户空间库极不稳定。**必须在实际硬件上跑完整的视频测试集**，不能只相信datasheet。

**GPU验证命令**：
```bash
# 检查GPU驱动加载
dmesg | grep -i "gpu\|drm\|mali"

# OpenGL ES测试
/glmark2-es2-wayland  # 分数应与厂商标称值差距<20%

# Vulkan测试
vulkaninfo | grep -E "deviceName|apiVersion"
vkcube  # 基本渲染测试

# GPU压力测试（30分钟）
gpu-burn 600  # 检查是否过热/崩溃
```

**VPU验证命令**：
```bash
# H.264解码测试
time ffmpeg -hwaccel drm -i test_1080p_h264.mp4 -f null -
# 应接近实时（1x speed），CPU占用<30%

# H.265/HEVC解码测试
time ffmpeg -hwaccel drm -i test_4k_h265.mp4 -f null -

# GStreamer硬件加速确认
gst-inspect-1.0 | grep -E "v4l2|vaapi|rockchip|hantro"
```

#### 检查项8：音频输入输出

音频是工业HMI、智能音箱、网关等产品的常见需求，但容易被忽视。

**评分标准**：
- **5分**：ALSA主线完整支持，包括播放、录制、音量控制
- **4分**：ALSA支持，但需要少量Device Tree或mixer配置
- **3分**：需要厂商patch，但功能稳定
- **2分**：仅支持播放或录制中的一个，或存在明显bug
- **1分**：音频不可用或驱动极不稳定

**验证命令**：
```bash
# 检查声卡识别
aplay -l  # 列出播放设备
arecord -l  # 列出录制设备

# 播放测试
speaker-test -t sine -f 1000 -c 2 -l 3

# 录制测试
arecord -d 10 -f cd -t wav /tmp/test.wav
aplay /tmp/test.wav  # 回放检查

# 检查ALSA mixer配置
amixer scontrols  # 查看可用控件
```

> ⚠️ **陷阱**：很多SoC的音频codec需要外部codec芯片配合，即使SoC本身有I2S/PDIF接口，如果配套codec没有主线驱动，音频功能仍然不可用。评估时必须确认你的硬件上实际使用的codec芯片是否有驱动支持。

#### 检查项9-11：软件栈支持

**内核版本评估**是关键决策点。使用以下公式：

```
内核评分 = min(5, max(1, 
  2 * (厂商支持最新LTS ? 1 : 0) +
  2 * (内核EOL > 产品EOL + 2年 ? 1 : 0) +
  1 * (有CIP SLTS支持 ? 1 : 0)
))
```

**Yocto支持评估**：
```bash
# 检查Yocto层的活跃度
curl -s https://api.github.com/repos/<vendor>/meta-<xxx>/commits \
  | jq -r '.[0].commit.committer.date'  # 最后提交日期

# 检查支持的Yocto版本
git ls-remote --heads https://github.com/<vendor>/meta-<xxx>.git \
  | grep -E "scarthgap|kirkstone|dunfell"
```

#### 检查项12-13：文档与参考设计

**文档质量直接影响 bring-up 时间**。评估维度：

| 文档类型 | 必需内容 | 评分权重 |
|---------|---------|---------|
| Technical Reference Manual (TRM) | 寄存器描述、模块框图、时序 | 30% |
| BSP User Guide | 构建步骤、已知问题、配置选项 | 25% |
| Application Notes | 具体应用场景指导（如启动优化） | 20% |
| Hardware Design Guide | PCB layout建议、电源设计、信号完整性 | 15% |
| FAQ / Errata | 已知bug列表、workaround | 10% |

> ⚠️ **陷阱（参考设计质量）**：有些厂商的参考设计只是"能点亮"的最低限度实现，存在电源设计不合理、EMC考虑不足、关键信号未做阻抗匹配等问题。**不要盲目复制参考设计**，要有硬件工程师独立review。

#### 检查项14-15：社区支持

**社区活跃度的量化评估方法**：

```bash
# 邮件列表活跃度（统计最近3个月邮件数量）
# linux-rockchip 示例
wget -q "http://lists.infradead.org/pipermail/linux-rockchip/" -O - \
  | grep -c "2025-"  # 高活跃度 > 100封/月

# GitHub issue响应时间统计
curl -s "https://api.github.com/repos/<vendor>/<repo>/issues?state=all&per_page=100" \
  | jq -r '.[] | select(.closed_at != null) 
         | (.closed_at | fromdateiso8601) - (.created_at | fromdateiso8601)' \
  | awk '{sum+=$1; count++} END {print "Avg response:", sum/count/86400, "days"}'
```

#### 检查项16-18：长期维护

**这是工业/汽车产品最关键的评估维度**。

| 厂商 | Longevity Program | CIP参与 | 历史EOL记录 |
|------|------------------|---------|------------|
| NXP | 10-15年（Product Longevity） | 参与者 | 优秀 |
| TI | 10-15年（Extended Life） | 参与者 | 优秀 |
| Renesas | 通过CIP保障 | **核心成员** | 优秀 |
| Rockchip | 无明确承诺 | 无 | 不明确 |
| Qualcomm | 有限承诺 | 无 | 一般 |

#### 检查项19-20：风险评估

**闭源组件审计清单**：

```bash
# 扫描内核中的闭源firmware
find /lib/firmware -type f | wc -l  # 数量统计
find /lib/firmware -type f -name "*.bin" | while read f; do
    echo "$(stat -c%s $f) $f"  # 大小统计
done | sort -rn | head -20

# 扫描内核模块中的闭源符号
grep -r "MODULE_FIRMWARE" /lib/modules/$(uname -r)/ \
  | wc -l  # 依赖firmware的模块数量

# 检查vendor-specific库
find /usr/lib -name "*vendor*" -o -name "*imx*" -o -name "*rockchip*" \
  | while read f; do file $f; done | grep "ELF" | wc -l
```

### 3.4 评分卡使用方法

```
总分计算：
1. 对每个检查项按1-5分评分
2. 乘以权重系数
3. 加权求和，最高100分
4. 按阈值判断：
   - 90-100分：优秀BSP，放心使用
   - 75-89分：  良好BSP，注意风险项
   - 60-74分：  一般BSP，需要额外投入
   - <60分：    高风险BSP，不建议使用
```

## 本节总结

### 核心要点回顾

1. **20项检查清单覆盖6大维度**：
   - 硬件功能（8项，47%权重）：GPIO/UART/SPI/I2C、USB/ETH/SD/eMMC、Wi-Fi/蓝牙、GPU、VPU、NPU、摄像头ISP/CSI、音频
   - 软件栈（3项，22%权重）：内核版本/LTS、Yocto/Buildroot、RT-Patch
   - 文档与参考设计（2项，14%权重）：文档质量、参考设计完整性
   - 社区支持（2项，9%权重）：论坛/ML活跃度、Issue响应时间
   - 长期维护（3项，24%权重）：厂商承诺、EOL/CIP、安全补丁节奏
   - 风险评估（2项，9%权重）：闭源依赖、定制扩展性

2. **评分标准统一为1-5分制**：
   - 5分 = 全部主线支持/最佳
   - 4分 = 主线支持，需少量调整
   - 3分 = 需厂商patch但质量高
   - 2分 = 厂商驱动无主线支持
   - 1分 = 驱动不稳定
   
   加权总分：90-100分优秀，75-89分良好，60-74分一般，<60分高风险。

3. **评分卡可定量对比不同SoC**：案例显示i.MX8M Plus（78.5分）vs RK3588（70.3分）——长生命周期工业项目中NXP综合评分更高。

4. **验证方法必须结合实际硬件测试**：不能只看datasheet，必须在真实硬件上跑完整的压力测试（至少72小时）。

5. **闭源组件是最大风险项**：评估时务必量化闭源blob数量和关键度，制定去闭源化路线图。

### 使用建议

**评估流程推荐**：
1. 先填写评分卡（1-5分），不要花太多时间纠结——先快速填完
2. 对评分<=3分的项，标记为风险项，制定缓解计划
3. 总分<75分的SoC，需要额外投入资源（专职BSP工程师或商业支持）
4. 总分<60分的SoC，建议直接排除
5. 评估完成后，保留评分卡作为产品决策文档的一部分
