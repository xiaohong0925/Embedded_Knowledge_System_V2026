# 第16章：内核版本与启动架构设计

> 所属：第 三 部 系统设计与决策
>
> BIEM：[E] | 核心问题：一套内核版本与启动链方案怎么定下来，并在十年后仍然成立？

## 核心问题

不是"内核怎么编译、U-Boot 怎么配"——那是第 3/4/7 章已经回答过的问题。本章回答的是：**给你一组产品约束（生命周期、启动时限、认证、团队），怎么推导出内核版本、BSP 来源、启动链、设备树组织这四个决策，并且每个决策都拿得出证据。**

## 为什么需要这一章

内核版本与启动架构是嵌入式产品中最难回头的决策——不是因为技术难，而是因为**窗口滞后**：你做的每个选择都绑定一个时间窗口，窗口在你看不见的地方移动。内核 LTS 的 EOL 窗口、厂商 BSP 的支持窗口、CIP SLTS 的维护窗口、启动时间的预算窗口——这些窗口的关闭时间都写在别人的日程表上，等产品卖到第三年、第五年，窗口一个个关上门，修改成本已翻了几倍。

更棘手的是错位：选版本时产品还没做出来，等发现生命周期缺口时产线已经跑顺；配启动链时按开发板调试方便来，等客户测出启动超时时固件架构已冻结；写设备树时只有一个板卡，等第 6 个 SKU 到来时差异已经腐烂进代码分支。这些决策的共性是：**影响跨越整个产品生命周期，回退成本极高，且没有标准答案。**

有经验工程师对这些工具不陌生：你会编译内核、会配 U-Boot、会写设备树。但面对一个真实产品时，这些问题不会自动有答案：工业控制器要活 10 年，看中的 LTS 只支持 6 年怎么办？厂商 BSP 开箱即用但上游已 EOL，这个便宜能不能占？3 秒启动砍掉 U-Boot 省下的时间，拿什么代价换？8 个板卡变体的设备树，从第几个开始必须重构？

## 本章主线：四个决策，一条咬合链

本章的核心结构是：**版本 → BSP → 启动链 → DTS 不是四个孤立的选择题，而是一条咬合链**——版本选定后 BSP 来源基本锁定，BSP 锁定后启动链的可裁剪空间确定，启动链确定后 DTS 的加载与 overlay 时机也随之确定。
