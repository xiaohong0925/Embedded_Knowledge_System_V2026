## <span class="blue">知识点387上</span> — LTS政策变迁：从6年到2年的地震

### 3.1 历史背景：LTS政策是如何演变的

理解当前LTS政策的混乱局面，需要回顾过去7年的历史。这不是一个突然的决定，而是一系列渐进变化的累积结果。

#### 3.1.1 黄金时代：2017–2023年的"6年LTS"

2017年9月，Linux社区做出一个重要决定：**将LTS支持周期从2年延长到6年** [^grsecurity-xlts^]。这个决定的背景是：

- 智能手机（Android）和物联网设备的爆发式增长
- 这些设备的生命周期通常为4–6年，但之前LTS只覆盖2年
- 设备厂商被迫自行维护老版本内核，导致安全补丁分散和重复劳动

6年LTS政策的典型例子：

| 版本 | 发布日期 | 原2年EOL | 6年EOL | 实际受益 |
|------|----------|----------|--------|----------|
| 4.4 | 2016-01 | 2018-01 | **2022-01** | Android 7/8设备 |
| 4.9 | 2016-12 | 2018-12 | **2022-12** | 嵌入式设备 |
| 4.14 | 2017-11 | 2019-11 | **2024-01** | Android 9设备 |
| 4.19 | 2018-10 | 2020-10 | **2024-12** | 工业设备 |
| 5.4 | 2019-11 | 2021-11 | **2025-01** | 通用平台 |

6年LTS政策被誉为嵌入式行业的"福音"——它让设备厂商可以安心选择LTS版本， knowing that security patches would be available for the entire product lifetime.

#### 3.1.2 地震来袭：2023年9月的"2年 shock"

2023年9月，Linux内核维护者之一Sasha Levin在邮件列表中宣布：**未来的LTS版本将只维护2年** [^thenewstack-ltschange^][^linuxorg-ltscut^]。

这个决定的核心原因是**维护者burnout**（职业倦怠）：

> "维护6个以上的LTS版本，每个版本每周处理数十个补丁，这是一份全职工作。但我们大多数人没有为此获得报酬。" —— 匿名维护者

具体数据：
- 2023年时，Stable Team同时维护**6个LTS版本**（4.14/4.19/5.4/5.10/5.15/6.1）
- 每周review和backport约**200–400个补丁**
- 测试覆盖**30+种架构和配置组合**
- 只有Greg KH和Sasha Levin是全职维护者，其余依赖志愿者

#### 3.1.3 行业反击与政策妥协

2年LTS的消息在嵌入式和Android行业引发了强烈反对 [^linuxjournal-lts^]：

**Google的应对（2024年7月）**：
Google宣布为Android ACK（Android Common Kernel）提供**4年扩展支持**——从6.6开始，ACK内核将维护4年（而非原来的2年）。这意味着Android设备厂商至少能获得4年的内核安全补丁 [^androidauthority-ack^]。

**CIP的表态（2023–2024年）**：
CIP项目明确表示不受上游LTS政策影响——CIP的SLTS版本将继续提供**10年支持**。这使得CIP成为长生命周期设备的"避风港"。

**Greg KH的妥协（2024–2025年）**：
面对业界压力，Greg KH做出了一系列调整：
- 2024年12月：**意外延长6.1 LTS到2027年12月**（从原计划的2026年底延长1年）
- 2025年初：**宣布6.6 LTS延长到2027年底**
- 2025年中：**宣布6.12和6.18延长到2028年底**

### 3.3 维护者burnout：被忽视的行业危机

LTS政策变化的根本原因是**维护者资源的枯竭**。这个问题比大多数人意识到的更严重。

#### 3.3.1 Stable Team的工作负荷

Greg Kroah-Hartman在2023年的Linux Plumbers Conference上分享了以下数据 [^gregkh-burnout^]：

| 指标 | 2020年 | 2023年 | 增长率 |
|------|--------|--------|--------|
| 活跃LTS版本数 | 4 | 6 | +50% |
| 每周stable补丁数 | ~150 | ~300 | +100% |
| 贡献者数量 | ~3,000 | ~4,000 | +33% |
| 全职维护者 | 2 | 2 | 0% |

**简单的数学**：2个全职维护者 + 少量志愿者 = 无法可持续地维护6个LTS版本 × 每周300个补丁。

#### 3.3.2 为什么没有人愿意为老版本维护买单？

| 障碍 | 说明 |
|------|------|
| **技能门槛高** | 需要深入理解内核各子系统，能判断哪些补丁应该backport |
| **工作单调** | Backport是重复性劳动，缺乏创新性和成就感 |
| **薪酬不匹配** | 大厂内核工程师年薪20–50万美元，维护工作的薪酬远低于此 |
| **责任重大** | 一个错误的backport可能导致数百万设备崩溃 |
| **缺乏认可** | Backport工作很少被学术界或社区赞扬 |

#### 3.3.3 可能的解决方案

| 方案 | 可行性 | 说明 |
|------|--------|------|
| **企业资助维护者** | 进行中 | 部分公司（如Google、Meta）资助维护者时间 |
| **LTS版本轮换制** | 讨论中 | 每年维护2个LTS版本，每个维护2年，但交替进行 |
| **自动化测试** | 进行中 | KernelCI等项目增加自动化测试覆盖 |
| **CIP模式扩展** | 有潜力 | 让更多行业（如汽车、医疗）效仿CIP的资助模式 |

### 3.4 对嵌入式行业的实际影响

#### 3.4.1 短期影响（2025–2027年）

```
当前活跃版本的生命线：

6.18 (2025-11) ────────────────────────────── 2028-12 ✓
6.12 (2024-11) ────────────────────────────── 2028-12 ✓ + CIP到2035
6.6  (2023-10) ─────────────────────── 2027-12 ✓
6.1  (2022-12) ─────────────────────── 2027-12 ✓ + CIP到2033
5.15 (2021-10) ─────────── 2026-12 ⚠️ 即将结束！
5.10 (2020-12) ─────────── 2026-12 ⚠️ 即将结束！
```

#### 3.4.2 中长期影响（2027–2035年）

| 情景 | 概率 | 结果 |
|------|------|------|
| LTS保持2–4年 | 60% | 更多设备厂商转向CIP SLTS或商业支持 |
| 社区恢复6年LTS | 20% | 需要新的资助模式支撑 |
| LTS版本减少（每年仅1个） | 15% | 更少的版本选择，但更可持续 |
| 行业分裂（各厂商自行维护） | 5% | 最坏情景，安全补丁分散 |

#### 3.4.3 工程师的应对策略

> 💡 **提示**:  面对不稳定的LTS政策，嵌入式工程师应该采取以下策略：
>
> 1. **优先选择有CIP SLTS支持的版本**（6.12/6.1/5.10），SLTS的10年承诺不受上游LTS政策变化影响
> 2. **关注Linux Foundation的公告**，及时了解LTS政策变化
> 3. **建立内核升级能力**，不要把内核版本锁定视为"一次性决策"
> 4. **考虑商业支持**（如Timesys的安全维护服务）作为保险

## 本节总结与下一步

### 核心要点回顾

1. **黄金时代（2017–2023）**：6年LTS政策让嵌入式行业安心选择LTS版本，安全补丁覆盖整个产品生命周期。

2. **2023年9月"2年shock"**：Sasha Levin宣布未来LTS只维护2年，根本原因是维护者burnout——2个全职维护者要处理6个LTS版本×每周300个补丁。

3. **政策妥协**：面对行业反对，Greg KH做出弹性调整——6.1延长到2027、6.6延长到2027、6.12/6.18延长到2028，实际形成"2–4年"弹性政策。

4. **维护者危机未解决**：技能门槛高、工作单调、薪酬不匹配、责任重大，导致backport工作缺乏可持续的人力资源。

5. **工程师应对策略**：优先选择有CIP SLTS支持的版本、关注Linux Foundation公告、建立内核升级能力、考虑商业支持作为保险。

### 对嵌入式行业的关键影响

- **短期（2025–2027）**：5.10/5.15即将EOL，6.12/6.18是可靠选择
- **中长期（2027–2035）**：60%概率LTS保持2–4年，更多设备厂商将转向CIP SLTS或商业支持
