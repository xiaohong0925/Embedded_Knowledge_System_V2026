## 决策场景：-40°C低温启动失败谜案

你负责一款工业网关的固件，在-40°C环境下约有15%概率启动失败。日志显示U-Boot能运行但内核加载后hang住。经过排查，最终发现是**SPL阶段的DDR初始化参数在低温下裕量不足**——DDR PHY的ZQ校准在-40°C时产生偏差，导致后续U-Boot从eMMC读取数据时偶发bit错误。

这个案例暴露了一个深层问题：**你对启动链的了解不够深入**。本文先从BootROM开始，代码级解析每个阶段。


## 启动链全景图

在深入代码之前，先建立整体认知。嵌入式Linux系统的启动链（Boot Chain）通常由以下五个阶段组成：

```
┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
│ BootROM │───→│   SPL   │───→│ U-Boot  │───→│  Kernel │───→│ Rootfs  │
│ (SoC固化)│    │(阶段一加载器)│   │(完整Bootloader)│   │(Linux内核) │   │(用户空间) │
│  ~100ms │    │ ~200ms  │    │ ~500ms  │    │ ~800ms  │    │ ~500ms  │
│  SRAM   │    │  SRAM   │    │   DDR   │    │   DDR   │    │   DDR   │
└─────────┘    └─────────┘    └─────────┘    └─────────┘    └─────────┘
   SoC上电       初始化DDR       加载内核       内核初始化      启动init
  自动执行      加载U-Boot      传递参数       挂载rootfs     启动服务
```

**阶段总览表：**

| 阶段 | 代码位置 | 执行环境 | 主要工作 | 典型耗时 | 调试方法 |
|------|---------|---------|---------|---------|---------|
| BootROM | SoC内部ROM（不可修改） | SRAM/ROM | 硬件初始化、加载SPL | 50-300ms | JTAG、BOOT_MODE引脚、ROM日志 |
| SPL | 外部存储→SRAM | SRAM（通常<256KB） | 初始化DDR、加载U-Boot | 100-500ms | UART早期打印、SPL调试符号 |
| U-Boot | 外部存储→DDR | DDR | 初始化外设、加载内核/DTB | 300ms-3s | 命令行、bootm调试、trace |
| Kernel | 外部存储→DDR | DDR | 内核初始化、驱动probe | 500ms-5s | initcall_debug、printk、kgdb |
| Rootfs | 外部存储→DDR | DDR | 挂载文件系统、启动init | 300ms-10s | systemd-analyze、bootchart |

> 💡 **提示**: 以上耗时是"典型未优化"系统的参考值。优化后的系统（Falcon Mode + 裁剪内核 + 最小rootfs）可以将总启动时间压缩到1.5-3秒。

## 1. BootROM：SoC上电后第一条代码

### 1.1 BootROM的本质

BootROM（Boot Read-Only Memory）是固化在SoC芯片内部的一块只读存储器，通常位于芯片的**ROM区域**（地址0x0000_0000或SoC特定的复位向量地址）。它是**不可修改的**——由芯片厂商在流片时固化，用户无法通过软件更新。

BootROM的代码大小通常在**16KB-128KB**之间，取决于SoC复杂度。例如：

| SoC系列 | BootROM大小 | 复位向量地址 | 启动模式检测方式 |
|---------|------------|-------------|----------------|
| NXP i.MX6系列 | ~80KB | 0x0000_0000 | BOOT_MODE[1:0]引脚 + eFUSE |
| NXP i.MX8系列 | ~96KB | 0x0000_0000 | BOOT_MODE[3:0]引脚 + eFUSE |
| TI AM335x | ~64KB | 0x0000_0000 | SYSBOOT[15:0]引脚 |
| Rockchip RK3399 | ~32KB | 0xFFFF_0000 | OM引脚 + eFUSE |
| Allwinner H6 | ~24KB | 0x0000_0000 | BOOT_SEL引脚 |
| STM32MP1 | ~48KB | 0x0000_0000 | BOOT0/BOOT1/BOOT2引脚 |

### 1.2 BootROM的执行流程（代码级）

BootROM的执行流程虽然因厂商而异，但遵循统一模式。以NXP i.MX6为例，BootROM的伪代码逻辑如下：

```c
/* arch/arm/cpu/armv7/mx6/soc.c — i.MX6 BootROM 执行流程 */
void bootrom_main(void)
{
    /* 1. 最硬件初始化（关中断、设置栈指针） */
    disable_interrupts();
    setup_temp_stack();          /* 使用SRAM中的临时栈 */
    
    /* 2. 读取启动模式选择 */
    boot_mode = read_boot_pins(); /* 读取BOOT_MODE[1:0]引脚 */
    /*  00 = 内部Boot（从eFUSE/引脚选择具体介质） */
    /*  01 = 串行下载（USB/UART刷机模式）          */
    /*  10 = 保留                                  */
    /*  11 = 保留                                  */
    
    /* 3. 如果是Internal Boot模式，进一步检测具体介质 */
    if (boot_mode == BOOT_MODE_INTERNAL) {
        boot_dev = read_boot_device_fuses(); /* eFUSE或GPIO覆盖 */
    }
    
    /* 4. 初始化对应存储接口 */
    switch (boot_dev) {
    case BOOT_DEV_MMC:
        mmc_boot_init();         /* 初始化USDHC控制器 */
        break;
    case BOOT_DEV_NAND:
        nand_boot_init();        /* 初始化GPMI/NFC */
        break;
    case BOOT_DEV_SPI_NOR:
        spi_boot_init();         /* 初始化ECSPI/QSPI */
        break;
    case BOOT_DEV_SATA:
        sata_boot_init();        /* 初始化SATA（仅部分型号） */
        break;
    case BOOT_DEV_I2C:
        i2c_boot_init();         /* 从EEPROM加载（小容量） */
        break;
    default:
        goto serial_download;    /* 未知设备，进入下载模式 */
    }
    
    /* 5. 从存储介质加载SPL到SRAM */
    /* i.MX6的SRAM（OCRAM）位于0x0090_0000，大小128KB */
    spl_load_addr = 0x00907000;  /* SPL加载目标地址 */
    spl_size = load_spl_from_media(boot_dev, spl_load_addr);
    
    if (spl_size == 0) {
        /* 加载失败——可能是： */
        /* - 存储介质不存在/未焊接 */
        /* - SPL签名验证失败（Secure Boot） */
        /* - 存储介质损坏 */
        goto serial_download;
    }
    
    /* 6. Secure Boot签名验证（如果启用） */
#if CONFIG_SECURE_BOOT
    if (!verify_hab_signature(spl_load_addr, spl_size)) {
        /* HAB（High Assurance Boot）验证失败 */
        /* 进入HAB错误状态，CPU锁定或重置 */
        hab_failure_handler();
    }
#endif
    
    /* 7. 跳转到SPL执行 */
    jump_to_spl(spl_load_addr);
}
```

### 1.3 BootROM的存储介质检测流程

BootROM如何知道从哪个存储介质加载SPL？这是启动问题的高发区。

**NXP i.MX6的启动介质检测**：

```
                    ┌──────────────────┐
                    │   CPU Reset      │
                    │  (POR_B rising)  │
                    └────────┬─────────┘
                             ▼
                    ┌──────────────────┐
                    │ 读取BOOT_MODE[1:0]│
                    │  GPIO引脚物理电平  │
                    └────────┬─────────┘
                             ▼
              ┌──────────────────────────────┐
              │ BOOT_MODE = 00 (Internal Boot)│
              └──────────────┬───────────────┘
                             ▼
              ┌──────────────────────────────┐
              │ 读取BOOT_CFG1[7:4] (eFUSE或  │
              │ GPIO覆盖)确定具体介质         │
              │  0000 = NOR/OneNAND          │
              │  0001 = SD/MMC (eSD/eMMC)    │
              │  0010 = SPI NOR/EEPROM       │
              │  0011 = SPI NOR/EEPROM (alt) │
              │  0100 = NAND                 │
              │  0101 = SD/MMC (alt)         │
              │  011x = SATA                 │
              │  100x = I2C/SPI 串行EEPROM   │
              └──────────────┬───────────────┘
                             ▼
              ┌──────────────────────────────┐
              │ 初始化对应存储控制器         │
              │ 按协议读取SPL镜像            │
              └──────────────┬───────────────┘
                             ▼
              ┌──────────────────────────────┐
              │ SPL加载到SRAM → 跳转执行     │
              └──────────────────────────────┘
```

**i.MX6从eMMC加载SPL的详细流程**：

```
1. BootROM初始化USDHC1/USDHC2控制器
2. 发送CMD0 (GO_IDLE_STATE) — 重置eMMC
3. 发送CMD1 (SEND_OP_COND) — 查询电压范围
4. 发送CMD2 (ALL_SEND_CID) — 获取CID
5. 发送CMD3 (SET_RELATIVE_ADDR) — 分配RCA
6. 发送CMD9 (SEND_CSD) — 获取CSD（容量/速度信息）
7. 发送CMD7 (SELECT_CARD) — 选中设备
8. 发送CMD6 (SWITCH) — 切换到High Speed模式
9. 发送CMD17/CMD18 (READ_SINGLE_BLOCK/READ_MULTIPLE_BLOCK)
   — 从LBA 0x2（即偏移0x400）开始读取SPL
   
   ⚠️ i.MX6从eMMC加载SPL时，默认从偏移0x400开始读取！
   ⚠️ 不是LBA 0！这是最常见的SPL烧录偏移错误。
```

### 1.4 BootROM的硬件签名验证（Secure Boot）

如果SoC启用了Secure Boot（通过eFUSE的SEC_CONFIG[1:0]），BootROM会在加载SPL后执行**HAB（High Assurance Boot）**签名验证：

```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│  CSF (命令序列 │ → │  SRK (超级   │ → │ 签名验证     │
│   文件)      │    │  根密钥)表   │    │  引擎        │
└─────────────┘    └─────────────┘    └──────┬──────┘
       ↑                                      │
       └──────────────────────────────────────┘
                    HAB验证流程

CSF包含：
- 密钥索引和证书
- 签名算法（RSA-2048/4096, ECDSA P-256/P-384）
- 需要验证的代码区域地址和长度
- 签名数据
```

**HAB验证失败的常见错误码**（从i.MX6的ROM日志读取）：

| HAB事件 | 错误码 | 含义 | 排查方向 |
|---------|-------|------|---------|
| HAB_FAILURE | 0x1B | 签名验证失败 | SPL镜像被修改但未重新签名 |
| HAB_FAILURE | 0x19 | SRK哈希不匹配 | eFUSE中烧录的SRK与CSF中的不符 |
| HAB_FAILURE | 0x18 | CSF格式错误 | CSF工具版本不匹配 |
| HAB_FAILURE | 0x21 | 证书过期 | 证书有效期问题 |
| HAB_FAILURE | 0x2E | 不允许的加密算法 | 使用了BootROM不支持的算法 |
| HAB_WARNING | 0x69 | 工程模式（未关闭调试） | 生产设备应关闭DEBUG eFUSE |

```bash
# 从U-Boot中读取HAB状态（验证Secure Boot状态）
=> hab_status

# Secure boot disabled
# 或
# HAB Configuration: 0xcc, HAB State: 0x99
# = HAB_CFG_CLOSED (生产状态) + HAB_STATE_SECURE (安全状态)
```

### 1.5 BootROM的存储介质加载细节

BootROM从不同介质加载SPL的方式和偏移地址各不相同：

| 存储介质 | SPL加载偏移 | 最大SPL大小 | 加载方式 | 特殊要求 |
|---------|------------|------------|---------|---------|
| SD卡 | LBA 0x400 (偏移2KB) | ~1MB | 原始扇区读取 | 需要特定分区格式 |
| eMMC Boot分区 | 偏移0 | ~1MB | 原始读取 | BOOT_PARTITION_ENABLE需设置 |
| eMMC User分区 | 偏移0x400 | ~1MB | 原始扇区读取 | 从LBA 0x2开始 |
| NAND Flash | 第0块 | 与页大小相关 | MTD读取 | 坏块跳过 |
| SPI-NOR | 偏移0 | 与Flash大小相关 | SPI读取 | 支持XIP（直接执行） |
| UART/USB | 串流接收 | ~1MB | 串行下载协议 | 需要USB/UART连接 |

> ⚠️ **陷阱 — BootROM从错误的介质加载SPL**：某批次产品的拨码开关贴错标签，BOOT_MODE引脚被接地而非接VDD，导致BootROM进入Serial Download模式而非Internal Boot。产品表现为"上电完全无输出"——因为BootROM在等待USB/UART连接。排查方法是测量BOOT_MODE引脚的实际电平，并与原理图对比。eFUSE可以锁定BOOT_MODE防止引脚被篡改，但烧录eFUSE是不可逆操作。

### 1.6 BootROM常见错误与排查

**错误1：BootROM无法找到有效的SPL**

```
# 症状：上电后无任何串口输出，或JTAG显示CPU在0x0000_0000附近循环
# 原因：
#   a) SPL未烧录到正确的偏移地址
#   b) 存储介质本身故障或未焊接
#   c) BootROM不支持该存储介质的配置（如eMMC的bus width不正确）

# 排查步骤：
# 1. 检查存储介质的物理连接（用万用表测阻抗）
# 2. 用JTAG读取BootROM的ROM日志（部分SoC支持）
# 3. 强制进入Serial Download模式，用工具重新烧录SPL

# i.MX6用uuu/mfgtool重新烧录：
$ sudo uuu spl.uuu
```

**错误2：Secure Boot签名验证失败**

```
# 症状：BootROM打印部分日志后停止，或进入HAB错误状态
# 排查：
# 1. 检查eFUSE的SEC_CONFIG状态
# 2. 确认SPL镜像已用正确的CSF密钥签名
# 3. 对比eFUSE中的SRK哈希与CSF中的公钥哈希

# 用uuu读取HAB日志：
$ sudo uuu -HABInfo
```

**错误3：存储介质时序问题**

```
# 症状：偶发启动失败（如本节的决策场景），尤其温度极端时
# 原因：
#   a) eMMC/SD的CLK频率在低温下超出 spec
#   b) 走线过长导致信号完整性问题
#   c) 上电时序不满足存储介质的tRST要求

# 解决：
# 1. 降低eMMC的CLK频率（从52MHz降到26MHz）
# 2. 调整BootROM的I/O驱动强度（部分SoC可通过eFUSE配置）
# 3. 检查PCB走线阻抗匹配
```

## 本节总结

### 核心要点回顾

```
BootROM关键认知：
1. BootROM是SoC固化的只读代码，不可修改
2. 上电后自动执行：初始化 → 读取BOOT_MODE → 检测存储介质 → 加载SPL
3. Secure Boot(HAB)在BootROM阶段验证SPL签名
4. 存储介质检测是启动问题的第一高发区
5. 不同SoC的SPL加载偏移不同，烧录时必须确认
```

### 关键决策清单

1. **BOOT_MODE引脚配置**：确保BOOT_MODE引脚电平正确，测量实际电平而非依赖原理图
2. **Secure Boot密钥管理**：生产环境启用前必须建立完整的密钥备份流程
3. **存储介质时序裕量**：极端温度下需降低CLK频率或提高驱动强度
