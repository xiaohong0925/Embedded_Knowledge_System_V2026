## <span class="blue">知识点387下</span> — PREEMPT_RT 6.12+主线化：实时Linux的新纪元

### 5.1 二十年征程：从2004年的一个补丁到2024年的历史性合并

PREEMPT_RT（Real-Time Preemption）是Linux内核发展史上最持久、最雄心勃勃的项目之一。它的故事跨越了整整20年，涉及数十名内核开发者，改变了工业控制、医疗设备、机器人等领域对Linux的认知。

#### 5.1.1 起源：2004年，一个疯狂的想法

2004年9月，Linux内核邮件列表上出现了一场激烈的讨论 [^kaiwantech-rt^][^gleixner-interview^]。多个嵌入式Linux厂商的开发者发布了各自的实时补丁，但没有一个提供完整的解决方案。这些补丁主要解决了当时Linux内核在实时场景下的几个核心问题：

- **不可抢占的内核代码路径**：内核中有大量持有spinlock时禁用抢占的代码，导致高优先级任务被迫等待
- **中断处理的原子性**：中断处理程序运行在中断上下文，无法被抢占
- **优先级反转**：低优先级任务持有高优先级任务需要的锁，且没有优先级继承机制

Ingo Molnar（当时Red Hat的内核开发者，Linux调度器维护者）开始收集这些补丁，重写不一致的部分，目标是创建一个**完全集成在Linux内核中的实时解决方案**——而不是像RTLinux或RTAI那样采用双内核架构 [^linutronix-festschrift^]。

#### 5.1.2 关键里程碑时间线

| 年份 | 内核版本 | 里程碑 | 核心贡献者 |
|------|----------|--------|-----------|
| **2004** | 2.6.9 | PREEMPT_RT项目启动 | Ingo Molnar, Thomas Gleixner |

| **2015** | 4.1+ | Linux Foundation RT Collaborative Project成立 | 多家企业资助 |

#### 5.1.3 最后的拼图：printk()的RT兼容

PREEMPT_RT合并到主线的最大障碍之一是`printk()`——内核中最古老的调试机制之一 [^lwn-990985^]。

printk()的问题在于：它使用了大量**不可抢占的代码路径**和**自旋锁**。在实时内核中，printk()的调用可能阻塞高优先级任务长达数毫秒——这对实时应用是不可接受的。

解决printk()的RT兼容性花费了**超过5年的时间**（2019–2024）：
- 2020–2022年：逐步重构printk的核心数据结构和锁机制
- 2023年：引入`atomic_printk()`和`deferred_printk()`概念
- 2024年9月：Petr Mladek提交了最后的printk RT补丁
- 2024年9月19日：Thomas Gleixner在欧洲开源峰会（维也纳）上，将这份pull request**用金色纸张打印、系上丝带**，亲手交给Linus Torvalds [^kaiwantech-rt^]

Linus当天就合并了补丁，commit hash: `baeb9a7d8b60b021d907127509c44507539c15e5`

> 💡 **这个仪式感满满的提交标志着一个时代的结束**：从此，实时Linux不再是"二等公民"——它是Linux内核的一等公民。

### 5.2 6.12内置RT的技术意义

#### 5.2.1 不再需要打补丁

主线化之前，使用PREEMPT_RT意味着：

```bash
# 以前（6.11及之前）：繁琐的RT补丁流程
git clone git://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git
cd linux
git checkout v6.11

# 下载对应版本的RT补丁（必须严格匹配版本！）
wget https://mirrors.edge.kernel.org/pub/linux/kernel/projects/rt/6.11/patch-6.11-rt1.patch.xz
xzcat patch-6.11-rt1.patch.xz | patch -p1

# 解决补丁冲突（常见！）
# 某些驱动可能需要额外修复
```

这个过程的痛苦之处在于：
- **版本必须严格匹配**：6.11.1的补丁不能用于6.11.2
- **补丁冲突频发**：特别是SoC厂商的out-of-tree驱动
- **测试覆盖有限**：RT补丁只在特定配置上测试，你的硬件组合可能未被覆盖
- **社区支持分裂**：问题可能来自主线代码、RT补丁或厂商驱动，责任不清

**现在（6.12+）**：

```bash
# 现在：一行配置即可
git clone git://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git
cd linux
git checkout v6.12

# 配置内核时启用RT
make menuconfig
# → General Setup → Preemption Model → Fully Preemptible Kernel (Real-Time)
# 或直接在.config中设置：
echo "CONFIG_PREEMPT_RT=y" >> .config
```

#### 5.2.2 驱动兼容性成为上游标准

主线化后，所有进入Linux内核的驱动**必须通过RT编译测试**。这意味着：
- GPU驱动、网络驱动、存储驱动——所有驱动都不能使用不可抢占的锁
- 驱动开发者必须考虑RT兼容性
- 不再存在"RT内核上这个驱动不工作"的问题（至少理论上如此）

#### 5.2.3 发行版原生支持

```bash
# Ubuntu 24.10+ 提供官方RT内核包
sudo apt install linux-image-rt

# Debian trixie/testing
sudo apt install linux-image-6.12.0-rt-amd64

# Fedora
sudo dnf install kernel-rt

# 验证RT是否启用
cat /sys/kernel/realtime
# 输出: 1 (表示RT已启用)

uname -v | grep -i preempt
# 输出应包含 PREEMPT_RT
```

### 5.3 CONFIG_PREEMPT_RT=y启用方法

#### 5.3.1 配置选项详解

在`make menuconfig`中，RT相关的配置路径：

```
General setup
  └── Preemption Model
        ├── ( ) None (Server focussed)          ← 无抢占，最大吞吐量
        ├── ( ) Voluntary Kernel Preemption     ← 自愿抢占，桌面默认
        ├── ( ) Preemptible Kernel              ← 标准抢占，低延迟
        └── (X) Fully Preemptible Kernel (RT)   ← 完全抢占，实时
```

#### 5.3.2 关键依赖配置

```bash
# RT启用时自动设置的关键选项
CONFIG_PREEMPT_RT=y
CONFIG_PREEMPT=y
CONFIG_PREEMPT_COUNT=y
CONFIG_PREEMPTION=y

# RT依赖的子系统配置
CONFIG_RT_MUTEXES=y           # RT互斥锁（优先级继承）
CONFIG_FUTEX=y               # 快速用户空间锁（RT优化）
CONFIG_THREAD_INFO_IN_TASK=y  # 线程信息在task_struct中

# 中断线程化
CONFIG_IRQ_FORCED_THREADING=y  # 强制中断线程化

# 高精度定时器（RT必需）
CONFIG_HIGH_RES_TIMERS=y
```

#### 5.3.3 嵌入式设备的RT配置检查清单

```bash
#!/bin/bash
# check_rt_config.sh - RT内核配置检查脚本
# 用法: ./check_rt_config.sh .config

CONFIG=${1:-.config}

echo "=== RT Kernel Configuration Check ==="
echo ""

# 核心RT选项
check_option() {
    local opt=$1
    local val=$(grep "^${opt}=y" $CONFIG 2>/dev/null)
    if [ -n "$val" ]; then
        echo "✅ $opt"
    else
        echo "❌ $opt MISSING"
    fi
}

echo "--- Core RT Options ---"
check_option "CONFIG_PREEMPT_RT"
check_option "CONFIG_HIGH_RES_TIMERS"
check_option "CONFIG_RT_MUTEXES"

echo ""
echo "--- IRQ Threading ---"
check_option "CONFIG_IRQ_FORCED_THREADING"

echo ""
echo "--- Timer Subsystem ---"
check_option "CONFIG_HIGH_RES_TIMERS"
check_option "CONFIG_NO_HZ_FULL"

echo ""
echo "--- Memory Management ---"
# RT下应避免CONFIG_TRANSPARENT_HUGEPAGE（增加延迟不确定性）
if grep -q "CONFIG_TRANSPARENT_HUGEPAGE=y" $CONFIG; then
    echo "⚠️  CONFIG_TRANSPARENT_HUGEPAGE enabled (may increase latency jitter)"
else
    echo "✅ Transparent HugePages disabled"
fi

echo ""
echo "--- Debugging (disable in production) ---"
if grep -q "CONFIG_DEBUG_KERNEL=y" $CONFIG; then
    echo "⚠️  DEBUG_KERNEL enabled (performance impact)"
fi
if grep -q "CONFIG_FTRACE=y" $CONFIG; then
    echo "⚠️  FTRACE enabled (small overhead)"
fi

echo ""
echo "=== Check Complete ==="
```

### 5.4 RT对内核其他子系统的影响

启用`CONFIG_PREEMPT_RT=y`后，内核的行为发生以下关键变化 [^tuteworld-rt^][^imd-rt^]：

#### 5.4.1 Spinlock → RT-Mutex转换

```c
// 标准内核（非RT）
spin_lock(&lock);      // 禁用抢占，忙等待
// ... critical section ...
spin_unlock(&lock);    // 启用抢占

// RT内核
// spin_lock() 被宏替换为：
rt_spin_lock(&lock);   // 可睡眠的锁，支持优先级继承
// ... critical section ...
rt_spin_unlock(&lock); // 唤醒等待者
```

**影响**：
- 中断处理程序不再禁用抢占（它们运行在内核线程中）
- 优先级继承防止优先级反转
- 锁持有时间不再是硬实时边界

#### 5.4.2 中断线程化

```
标准内核:    硬件中断 → 中断上下文（不可抢占）→ 返回
                ↓
RT内核:      硬件中断 → 快速ack → 唤醒中断线程（可抢占）→ 线程执行处理
                ↓
            高优先级任务可以抢占中断线程！
```

这意味着：在RT内核上，一个高优先级的用户空间任务**可以抢占正在执行的中断处理程序**——这是标准内核绝对不可能的行为。

#### 5.4.3 延迟表现对比

| 配置 | 调度延迟（典型） | 调度延迟（最坏情况） | 适用场景 |
|------|-----------------|---------------------|----------|
| PREEMPT_NONE | 10–100 ms | 数秒 | 服务器吞吐量 |
| PREEMPT_VOLUNTARY | 1–10 ms | 100 ms | 桌面系统 |
| PREEMPT (标准) | 100 µs – 1 ms | 10 ms | 低延迟桌面 |
| **PREEMPT_RT** | **5–30 µs** | **50–200 µs** | **工业/医疗/机器人** |

### 5.5 当前限制和已知问题

> ⚠️ **陷阱（RT不是万能的）**:  PREEMPT_RT主线化是里程碑，但不意味着"开箱即用"的硬实时。以下是当前的关键限制：

#### 5.5.1 不是"硬实时"

PREEMPT_RT提供的是**软实时**（soft real-time），不是硬实时（hard real-time）：

| 特性 | PREEMPT_RT Linux | 硬实时RTOS（QNX/VxWorks） |
|------|-----------------|--------------------------|
| 最坏情况延迟 | 50–500 µs | 1–10 µs |
| 延迟保证 | 统计性保证 | 确定性保证 |
| 功能安全认证 | 无（IEC 61508 SIL 3不可用） | 有（SIL 3/ASIL D） |
| 延迟失败后果 | 可接受偶发超时 | 不允许任何超时 |

**结论**：PREEMPT_RT适用于"偶尔超时不会导致灾难"的场景——如工业协议网关、数据采集、非安全关键的控制系统。对于**功能安全关键**的应用（如汽车制动、飞机飞控、核反应堆控制），仍然需要认证的RTOS。

#### 5.5.2 GPU和加速器驱动的RT兼容性

虽然RT代码已主线化，但某些驱动（尤其是GPU和AI加速器）在RT环境下可能表现不佳：

- **GPU驱动的调度依赖于非抢占的代码路径**
- **DMA传输的同步原语可能与RT假设冲突**
- **固件加载（firmware loading）通常是同步阻塞的**

**实际案例**：在i.MX8M Plus上使用NPU（Ethos-U）进行AI推理时，如果同时运行RT任务，NPU驱动的中断处理可能导致RT任务延迟增加20–50µs。

#### 5.5.3 调试困难

RT问题的调试比标准内核困难得多：
- **ftrace在RT路径上的开销影响实时性能**
- **printk的RT版本（atomic printk）可能丢失消息**
- **printk的RT版本（atomic printk）可能丢失消息**
- **lockdep在RT下不可用**（RT-Mutex的实现与lockdep假设冲突）

#### 5.5.4 性能开销

RT功能有轻微的性能开销：

| 指标 | 标准内核 | RT内核 | 开销 |
|------|----------|--------|------|
| 上下文切换 | 1.5 µs | 2.0 µs | +33% |
| 系统调用 | 80 ns | 100 ns | +25% |
| 吞吐量（网络） | 100% | 95–98% | -2~5% |

对于绝大多数嵌入式设备，这个开销是可以接受的。但对于追求极致吞吐量的场景（如网络设备），需要进行评估。

### 5.6 实际调优案例：工业网关的RT配置

```bash
# 工业网关RT调优示例（基于NXP i.MX93 + Linux 6.12-rt）

# === 1. 内核启动参数 ===
# 在U-Boot环境变量中设置：
setenv bootargs "console=ttymxc0,115200 root=/dev/mmcblk0p2 rw \
    preempt=rt \                    # 启用RT（冗余，但安全）
    nohz_full=1 \                    # 将CPU1隔离为全tickless
    isolcpus=1 \                     # 隔离CPU1（专用RT任务）
    rcu_nocbs=1 \                    # CPU1上不运行RCU回调
    irqaffinity=0 \                  # 所有中断绑定到CPU0
    default_hugepagesz=2M \          # 大页支持（减少TLB miss）
    hugepagesz=2M hugepages=32"     # 预分配32个2MB大页

# === 2. RT任务优先级设置 ===
# 使用chrt命令设置实时优先级
chrt -f 99 /usr/bin/modbus-gateway    # Modbus网关：FIFO优先级99
chrt -f 80 /usr/bin/data-collector    # 数据采集：FIFO优先级80
chrt -f 50 /usr/bin/cloud-uploader   # 云上传：FIFO优先级50

# === 3. CPU亲和性绑定 ===
# RT任务绑定到隔离的CPU1
taskset -c 1 /usr/bin/modbus-gateway

# === 4. 内存锁定 ===
# 防止RT任务的内存被换出
ulimit -l unlimited
# 在程序中使用mlockall(MCL_CURRENT | MCL_FUTURE)

# === 5. 延迟测试 ===
# 使用cyclictest验证RT延迟
cyclictest -t1 -p 80 -n -i 1000 -l 100000 --affinity 1
# 预期结果（i.MX93）:
# 最小延迟: ~8 µs
# 平均延迟: ~15 µs
# 最大延迟: ~80 µs
```

## 本节总结与下一步

### 核心要点回顾

1. **20年征程**：从2004年Ingo Molnar启动项目到2024年Thomas Gleixner将RT补丁亲手交给Linus合并，PREEMPT_RT经历了跨越20年的开发历程。

2. **6.12主线化的革命性意义**：不再需要手动打补丁，`CONFIG_PREEMPT_RT=y`一行配置即可启用；所有上游驱动必须通过RT编译测试；主流发行版均提供原生RT包。

3. **技术核心**：Spinlock→RT-Mutex转换、中断线程化（高优先级任务可抢占中断）、优先级继承防止优先级反转。典型延迟5–30µs，最坏情况50–200µs。

4. **不是"硬实时"**：PREEMPT_RT提供软实时（统计性保证），最坏情况延迟50–500µs。对于功能安全关键应用（汽车制动、飞机飞控），仍需认证RTOS（QNX/VxWorks）。

5. **需要调优**：仅设置`CONFIG_PREEMPT_RT=y`不够，还需要CPU隔离（`isolcpus`）、优先级设置（`chrt`）、内存锁定（`mlockall`）、禁用动态频率等。

### 必须避开的2个陷阱

> ⚠️ **陷阱1：RT不是万能的**。GPU和加速器驱动在RT环境下可能引入额外延迟，RT问题的调试比标准内核困难得多，lockdep在RT下不可用。
>
> ⚠️ **陷阱2：以为"主线化=开箱即用"**。RT仍然需要正确的配置、调优和测试。未经调优的RT内核延迟可能比标准内核更差。
