你皱起眉头。6个活跃LTS版本，EOL从2026年底到2028年底不等。你的疑问包括：实时需求、BSP支持、10年生命周期如何保障、CIP SLTS是什么？

## <span class="blue">知识点385</span> — Linux内核发布周期与版本生态基础

### 1.1 10–11周主线发布节奏：一台精密的分布式时钟

Linux内核的开发遵循着**世界上最高效的分布式协作模型之一**。每年约发布5–6个主线版本，每个版本的开发周期严格控制在**9–10周**（约2–2.5个月）。这个节奏自2005年Git工具引入后逐渐稳定，至今已经运转了近20年 [^gregkh-release^]。

理解这个节奏对嵌入式工程师至关重要，因为它直接决定了：
- **新功能何时可用**（某个驱动或子系统何时进入稳定版）
- **bug修复的backport路径**（你的内核版本能否获得某个关键修复）
- **LTS版本的选择时机**（每年只有一个版本会成为LTS，错过就要等下一年）

#### 1.1.1 Merge Window（2周）：新功能的大门

每个开发周期以**Merge Window**（合并窗口）开始，持续约2周。这是新功能进入主线的唯一通道。

```
[主线发布 v6.N] → Merge Window打开（2周） → rc1 → rc2 → ... → rc7 → [v6.N+1 稳定发布]
                     ↑
              子系统维护者向Linus提交pull request
              仅接受已 Review + Tested 的补丁集
```

Merge Window的运作机制 [^lwn-merge^]：

**Week 1（高强度合并期）**：
- Linus Torvalds每天合并**数百个pull request**，涵盖所有子系统（ARM架构、网络、文件系统、驱动等）
- 每个pull request来自子系统维护者（如ARM SoC维护者Arnd Bergmann、网络维护者David Miller等）
- 一个典型merge window处理约**12,000–15,000个commits**

**Week 2（收尾期）**：
- 合并速度放缓，处理延迟提交的请求和修复合并冲突
- 窗口关闭的标志：Linus发布 **-rc1**，同时宣布"Merge window is closed"

> ⚠️ **陷阱**:  Merge window关闭后再提交新功能？不可能。如果错过窗口，你的功能必须等待**下一个周期（约9–10周后）**。这就是为什么SoC厂商的驱动代码需要提前一个周期进入linux-next树，确保在merge window开启时能被顺利合并。

#### 1.1.2 RC阶段（6–8周）：只有修复，没有新功能

Merge Window关闭后，进入**Release Candidate**（RC）阶段。这是内核走向稳定的关键期。

| RC | 发布时间 | 主要工作 | 接受的内容 |
|----|----------|----------|-----------|
| **rc1** | 第2周末 | 初始稳定性检查 | 仅回归修复 |
| **rc2–rc3** | 第3–4周 | 主要bug修复 | 回归修复 + 重要bug修复 |
| **rc4–rc6** | 第5–7周 | 细节打磨 | 仅回归修复 |
| **rc7** | 第8周 | 最终验证 | 仅关键回归修复 |
| **rc8（可选）** | 第9周 | 额外稳定化 | 仅在发现严重问题时发布 |
| **Final** | 第8–10周 | 稳定发布 | 无 |

RC阶段的核心规则：**不接受任何新功能**，只修复回归（regression）——即该版本引入的新bug。这个规则的严格执行是Linux内核质量的核心保障。

**实际案例**：Linux 6.12的RC周期（2024年9月–11月）[^phoronix-612^]：
```
6.12-rc1  2024-09-29  Merge window关闭，PREEMPT_RT代码进入rc1
6.12-rc2  2024-10-06  ARM64 DTS修复、驱动稳定性调整
6.12-rc3  2024-10-13  网络子系统回归修复
6.12-rc4  2024-10-20  文件系统bug修复
6.12-rc5  2024-10-27  最后的驱动修复
6.12-rc6  2024-11-03  仅2个关键修复
6.12 Final 2024-11-17  v6.12稳定发布
```

这个7周的RC周期是典型的"干净"发布——没有需要rc8的严重问题。

#### 1.1.3 LTS版本的诞生：每年一个幸运儿

每年，Linux社区会从当年的主线版本中**选择一个作为LTS**（Long-Term Support）版本。选择规则 [^gregkh-lts^]：

1. **通常选择当年最后一个稳定版本**（即11月/12月发布的版本）
2. 由Greg Kroah-Hartman（稳定版维护者）正式宣布
3. 一经宣布，该版本将获得**2–6年的维护期**

近年来的LTS选择历史：

| 年份 | LTS版本 | 发布时间 | 选择依据 |
|------|---------|----------|----------|
| 2020 | 5.10 | 2020-12 | 当年最后一个稳定版 |
| 2021 | 5.15 | 2021-10 | 当年最后一个稳定版 |
| 2022 | 6.1 | 2022-12 | 当年最后一个稳定版 |
| 2023 | 6.6 | 2023-10 | 当年最后一个稳定版 |
| 2024 | 6.12 | 2024-11 | 当年最后一个稳定版，含PREEMPT_RT |
| 2025 | 6.18 | 2025-11 | 当年最后一个稳定版 |

> 💡 **提示**: 选择当年最后一个稳定版作为LTS，是因为经过一年的开发积累，该版本通常拥有最多的新功能和最好的硬件支持，同时又是"成熟的"——它后面的RC周期在冬季假期前完成，社区有足够时间进行测试。

### 1.2 Stable Team的工作原理：Greg KH的"每周五补丁日"

主线版本发布后，**Stable Team**接手维护工作。这个团队由Greg Kroah-Hartman和Sasha Levin领导，负责将主线中的bug修复和安全补丁**backport**（向后移植）到所有仍在维护的stable和LTS版本。

#### 1.2.1 每周发布流程

Stable Team的工作节奏是**每周一个发布** [^stable-process^]：

```
周一–周三：  Greg审查主线commits，选择适合backport的修复
周四：      生成stable-queue，构建发布候选
周五：      发布新的stable版本（如 v6.12.5）
```

一个典型的stable发布包含**20–100个补丁**，涵盖：
- 安全修复（CVE补丁）
- 回归修复
- 驱动bug修复
- 文件系统稳定性修复

#### 1.2.2 Backport选择标准

不是所有主线修复都会被backport到所有LTS版本。Greg KH有一套严格的选择标准 [^gregkh-backport^]：

```c
/* 理想情况下，我会将所有修复都backport到所有版本。但 */
/* 1. 有些修复依赖之前的重构（无法干净地cherry-pick）   */
/* 2. 有些修复"理论上"会影响老版本，但从未被报告          */
/* 3. 资源有限——6个LTS版本 × 每周 = 大量工作              */

/* 实际标准： */
/* - 有CVE编号的安全修复：必须backport                    */
/* - 有Reported-by标签的回归修复：优先backport            */
/* - 新硬件驱动修复：通常只backport到较新的LTS            */
/* - 内部重构清理：通常不backport                         */
```

> 🔴 **危险**: 这意味着**老版本LTS可能错过一些修复**。特别是5.10/5.15这样的老版本，随着EOL临近，backport的优先级会越来越低。2025年选5.10/5.15做新产品的内核，意味着你可能在EOL前一年就开始感受到补丁覆盖率的下降。

#### 1.2.3 Stable发布的实际数据

让我们看一组真实数据——Linux 6.12 LTS从发布到2025年7月的stable发布频率 [^kernelorg^]：

```
v6.12   2024-11-17  初始LTS发布
v6.12.1 2024-11-22  第1周修复（23个补丁）
v6.12.2 2024-11-29  第2周修复（41个补丁）
v6.12.3 2024-12-06  第3周修复（38个补丁）
v6.12.4 2024-12-13  第4周修复（55个补丁）
v6.12.5 2024-12-20  第5周修复（29个补丁）
...（省略中间版本）...
v6.12.28 2025-07-18 第32周修复（18个补丁）
```

平均每周一个版本，发布节奏极其稳定。这种可预测性正是工业设备依赖LTS的核心原因。

### 1.3 如何阅读kernel.org的版本矩阵

[kernel.org/releases.html](https://www.kernel.org/releases.html) 是Linux内核版本的权威信息源。但页面上大量的版本号和标签容易让人困惑。下面是阅读指南。

#### 1.3.1 页面结构解析

```
┌─────────────────────────────────────────────────────┐
│  Mainline:   6.19 (Linus Torvalds)                  │ ← 当前开发中的主线
│  Stable:     6.18.12 (Greg K-H)    ← 最新稳定版     │
│  Stable:     6.12.28 (Greg K-H)    ← 6.12 LTS       │
│  longterm:   6.6.57 (Greg K-H)     ← 6.6 LTS        │
│  longterm:   6.1.135 (Greg K-H)    ← 6.1 LTS        │
│  longterm:   5.15.178 (Greg K-H)   ← 5.15 LTS       │
│  longterm:   5.10.237 (Greg K-H)   ← 5.10 LTS       │
│  ...                                                │
└─────────────────────────────────────────────────────┘
```

#### 1.3.2 关键术语定义

| 术语 | 含义 | 维护期 | 适用场景 |
|------|------|--------|----------|
| **mainline** | Linus树中的当前开发版本 | 持续更新 | 内核开发者、测试者 |
| **stable** | 最新的稳定版本 | 直到下一个stable发布 | 通用桌面/服务器 |
| **longterm** | LTS版本，长期维护 | 2–6年 | **嵌入式/工业设备** |
| **SLTS** | CIP超长期支持 | 10年 | **关键基础设施** |

#### 1.3.3 EOL日期查询

除了kernel.org，[endoflife.date/linux](https://endoflife.date/linux) 提供了更直观的EOL查询界面。这个社区维护的网站汇总了所有Linux版本的EOL日期 [^endoflife^]：

```bash
# 用curl查询Linux 6.12的EOL日期
curl -s https://endoflife.date/api/linux/6.12.json | jq '.eol'
# 输出: "2028-12-31"

# 查询所有活跃版本
curl -s https://endoflife.date/api/linux.json | jq '.[] | select(.eol > "2025-07-01") | .cycle, .eol'
```

> 💡 **提示**: 建议将endoflife.date的API集成到你的CI/CD管道中，自动化监控产品所依赖的内核版本的EOL状态。

### 1.4 为什么嵌入式工程师必须关注主线节奏

一个常见的误解是："我选了一个LTS版本，主线开发跟我没关系。" 这个观念在嵌入式领域**非常危险**。

#### 1.4.1 主线→LTS的修复传导链

```
[Bug在主线被发现] → [主线修复] → [Stable Team审查] → [Backport到LTS] → [你的设备获得修复]
        ↑                                                    ↑
   社区报告/开发者发现                              你的BSP供应商整合
```

这个链条的延迟通常为**1–4周**（从主线修复到LTS版本发布）。但对于老版本LTS，如果修复无法干净cherry-pick，延迟可能延长到数月，甚至被跳过。

#### 1.4.2 硬件支持的上游优先原则

新的SoC和外围设备的支持**总是先进入主线**，然后才可能被backport到LTS。这意味着：

- 如果你使用的是最新SoC（如2025年发布的芯片），你可能**需要较新的LTS版本**才能获得完整的驱动支持
- 老版本LTS（如5.10）可能永远无法获得新硬件的支持

**案例**：NXP i.MX93于2023年发布，其完整Device Tree支持直到Linux 6.4才进入主线。这意味着6.1 LTS需要大量NXP的out-of-tree补丁才能支持i.MX93，而6.6 LTS和6.12 LTS的i.MX93支持则好得多。

#### 1.4.3 新功能vs稳定性的永恒平衡

| 策略 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| **紧跟最新LTS** | 最新硬件支持、最新功能、最长维护期 | 可能存在未发现的bug | 新产品开发、消费者设备 |
| **选择成熟LTS** | 社区验证充分、补丁覆盖完善 | 硬件支持可能不足、EOL较早 | 保守的工业应用 |
| **使用CIP SLTS** | 10年保障、工业级验证 | 版本较老、新硬件支持有限 | 关键基础设施、长生命周期产品 |

## 本节总结与下一步

### 核心要点回顾

1. **10–11周发布节奏**：每年约5–6个主线版本，Merge Window（2周）→ RC阶段（6–8周）→ 稳定发布。错过Merge Window意味着等待下一个周期。

2. **Stable Team每周发布**：Greg KH和Sasha Levin领导的团队每周将主线修复backport到所有活跃LTS版本。老版本的backport覆盖率会随EOL临近而下降。

3. **每年一个LTS**：通常选择当年最后一个稳定版（11月/12月发布），获得2–6年维护。2025年有6个活跃LTS版本同时存在，这是历史罕见的情况。

4. **kernel.org阅读指南**：区分mainline（开发中）、stable（最新稳定版）、longterm/LTS（长期维护，适合嵌入式）和SLTS（CIP超长期支持，适合关键基础设施）。

5. **嵌入式工程师必须关注主线**：新硬件支持总是先进入主线，修复传导链有1–4周延迟，老版本LTS可能错过一些关键修复。
