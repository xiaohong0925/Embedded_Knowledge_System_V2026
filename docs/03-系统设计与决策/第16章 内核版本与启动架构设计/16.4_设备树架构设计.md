## 16.4.1 为什么设备树组织是架构决策

单块开发板时代，设备树组织不成问题：一个 `.dts` 文件，抄厂商 EVK 的参考实现，改几个 `status` 属性，编译出 dtb，结束。问题出现在产品化之后：

- 同一款 SoC 衍生出标准版、宽温版、带 4G 模块版、不带显示屏版等多个 SKU
- 每个 SKU 一份独立 DTS，改一个共用的电源时序要同步修改十几个文件，漏改一个就是一批返修
- 硬件团队出了 V1.1 改版，换了 PMIC，所有 SKU 的 DTS 都要跟着动

设备树是硬件描述的唯一事实源。它的文件组织方式，决定了"硬件变更"这件事在软件侧的传导成本。这不是格式洁癖，是维护成本的数学问题：N 个 SKU 共享的部分如果被复制了 N 份，每次变更的出错概率就乘以 N。

> 💡 与第 18 章的划界：DTS 文件应该放在哪个 Yocto layer、以什么 recipe 打包，属于第 18 章的 Layer 纪律；本章讨论的是 DTS 文件本身怎么拆分和继承。

## 16.4.2 三种组织模式

### 模式一：独立 DTS（SKU ≤ 3）

每块板子一个完整的 `.dts` 文件，内部 `#include` 厂商提供的 SoC 级 `.dtsi`（如 `imx8mp.dtsi`），除此之外没有自建继承层。

```dts
/* product-gateway-v1.dts — 完整描述一块板子 */
/dts-v1/;
#include "imx8mp.dtsi"          /* 厂商 SoC 级 dtsi，描述芯片内部资源 */

/ {
    model = "ACME Industrial Gateway V1";
    compatible = "acme,gateway-v1", "fsl,imx8mp";

    chosen {
        stdout-path = &uart2;    /* 早期控制台走 UART2 */
    };
};

&i2c1 {
    status = "okay";
    pmic@4b {                    /* 本板特有：PMIC 挂在 I2C1 */
        compatible = "nxp,pca9450c";
        reg = <0x25>;
    };
};
```

**适用条件**：产品线只有 1~3 块板卡，且板卡间硬件差异大（不同 SoC 或不同功能定位）。此时抽象出一层共享 dtsi 的收益为零，反而增加理解成本。

**失效信号**：发现自己在两个 DTS 之间复制粘贴超过 20 行的相同节点——这就是该升级到模式二的信号。

### 模式二：dtsi 继承（SKU 3~20）

把共性抽到自建 `.dtsi`，每个 SKU 的 `.dts` 只写差异。这是厂商 SoC dtsi 模式在产品级的复刻。

```dts
/* acme-gateway-common.dtsi — 产品线共享层 */
/ {
    aliases {
        ethernet0 = &fec;        /* 全线产品网口命名统一 */
    };
};

&fec {
    pinctrl-names = "default";
    pinctrl-0 = <&pinctrl_fec>;
    status = "okay";             /* 全线产品都有以太网 */
};

&wdog1 {
    status = "okay";             /* 全线产品启用看门狗 */
};
```

```dts
/* acme-gateway-4g.dts — 4G 变体，只写差异 */
/dts-v1/;
#include "acme-gateway-common.dtsi"

/ {
    model = "ACME Industrial Gateway 4G";
    compatible = "acme,gateway-4g", "acme,gateway", "fsl,imx8mp";
};

&uart3 {                         /* 4G 模块接在 UART3 */
    status = "okay";
};

&usdhc2 {                        /* 4G 变体没有 eMMC，改用 SD */
    status = "disabled";
};
```

**关键纪律**：

1. **继承层级不超过三层**（SoC dtsi → 产品线 dtsi → 板卡 dts）。层级再深，定位一个属性最终被哪一层覆盖就需要人工遍历整条链，审查成本陡增。
2. **差异下沉，共性上浮**。每个属性先问"这是全线共性还是本 SKU 差异"，放错层的属性是后续所有混乱的源头。
3. **`compatible` 从具体到通用排列**（`acme,gateway-4g` → `acme,gateway` → `fsl,imx8mp`），让驱动可以按产品线级别匹配。

**适用条件**：同一 SoC 的 3~20 个 SKU，差异集中在外设增减和引脚复用。

### 模式三：动态 overlay（可插拔/模块化硬件）

核心板与载板分开出货、或者存在 HAT 式扩展模块时，编译期继承不够用——载板可能是整机厂自己设计的，你无法在出厂 dtb 里预知。这时用 overlay：基座 dtb 只描述核心板和已知的载板接口，扩展模块以 `.dtbo` 形式在启动时（U-Boot `fdt apply`）或运行时（`configfs`）叠加。

```dts
/* acme-expansion-rs485.dts — RS485 扩展卡 overlay */
/dts-v1/;
/plugin/;                      /* 声明这是 overlay，而非完整设备树 */

&uart1 {
    status = "okay";             /* 插入扩展卡才启用 UART1 */
};

&i2c2 {
    eeprom@50 {                  /* 扩展卡上的 ID EEPROM */
        compatible = "atmel,24c02";
        reg = <0x50>;
    };
};
```

```bash
# U-Boot 启动时按检测到的扩展卡叠加 overlay
fdt addr ${fdt_addr_r}
fdt apply /boot/overlays/acme-expansion-rs485.dtbo
```

**适用条件**：硬件配置在编译期无法确定——模块化仪器、载板生态、售后扩展卡。Raspberry Pi HAT 和 BeagleBone Cape 是这个模式的标杆实现。

**代价**：overlay 的符号解析依赖基座 dtb 保留 `__symbols__` 节点（编译时加 `-@`），版本不匹配会静默叠加失败；运行时叠加的节点无法参与早期启动（比如不能用 overlay 配置控制台）。调试难度显著高于编译期继承。

### 三种模式对比

| 维度 | 独立 DTS | dtsi 继承 | 动态 overlay |
|------|---------|----------|-------------|
| 适用规模 | SKU ≤ 3 | SKU 3~20 | 编译期无法确定的组合 |
| 变更传导成本 | 高（逐文件同步） | 低（改共享层） | 低（只改对应 dtbo） |
| 运行时灵活性 | 无 | 无 | 可按需加载/卸载 |
| 调试难度 | 低 | 中（需理清继承链） | 高（叠加失败静默） |
| 典型反例 | 10 个 SKU 各自完整 DTS | 5 层继承链 | 用 overlay 配启动控制台 |

> ⚠️ 模式选择不是二选一。实际产品线常见组合是"模式二打底 + 模式三补扩展"：SKU 变体用 dtsi 继承解决，可插拔模块用 overlay 解决。

## 16.4.3 DTS 质量指标

DTS 评审不能停留在"看着没问题"。以下指标可以量化并纳入检查：

| 指标 | 测量方法 | 健康阈值 | 说明 |
|------|---------|---------|------|
| 跨文件重复率 | 相似节点块在多个 DTS 中出现的次数 | 重复块 ≤ 3 处 | 超出即应抽 dtsi |
| `compatible` 精确度 | 是否使用板级专属 compatible 而非直接复用 EVK 的 | 100% 精确 | 直接抄 `fsl,imx8mp-evk` 是最常见坏味道 |
| `status` 显式性 | 每个外设节点是否有明确的 `status` | 无"隐式继承看不懂"的节点 | 读者不翻继承链就应能判断外设是否启用 |
| 与驱动一致性 | `dtbs_check` 通过 dt-schema 校验 | 0 error | 见下一节 |
| 注释覆盖 | 非标节点（自定义 regulator、gpio 用途）是否有注释 | 关键节点 100% | 半年后接手的人是主要受益者 |

最常见的三个坏味道，评审时优先查：

1. **`model` / `compatible` 照抄 EVK**。后果是用户空间工具（如 fwupd、OTA 代理）把你的产品识别成 NXP EVK，升级策略全错。
2. **时钟/复位/电源属性顺序混乱**。`clocks`、`resets`、`power-domains` 的引用顺序必须与 binding 文档一致，顺序错了 probe 时拿到的是错误的资源。
3. **`status = "okay"` 散落在多层**。在 SoC dtsi 层不应出现产品级的 `status = "okay"`——厂商 dtsi 里默认 `disabled` 的外设，启用动作应该只在板卡层发生，否则你无法从板卡文件判断这块板子到底有什么。

## 16.4.4 dtc 与 CI 检查

设备树的错误大多在编译期就能拦住，前提是把检查接进 CI。

### 编译期警告

```bash
# dtc 默认只报语法错误，-W 打开属性级警告
dtc -W node_name_chars_strict -W property_name_chars_strict \
    -W address_cells_is_cell -W interrupt_provider_is_node \
    -I dts -O dtb -o product.dtb product.dts
```

内核构建系统中 `make dtbs W=1` 会启用 dtc 的一组推荐警告；`W=2` 进一步检查节点命名规范。

### dt-schema 语义校验

`dtc` 只保证语法，`dtbs_check`（内核 `scripts/dtc/` 集成的 dt-schema）会对照 binding 文档做语义校验——属性类型、必填项、取值范围：

```bash
# 在内核源码树中对单个 dtb 执行 schema 校验
make dtbs_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/i2c/nxp,pca9450.yaml
```

它能抓到的典型错误：`reg` 地址位数与 `#address-cells` 不匹配、interrupts 数量与 binding 声明不符、必填的 `clocks` 属性缺失。

### CI 集成示例

```yaml
# .gitlab-ci.yml — DTS 变更的 CI 关卡
dt-check:
  script:
    # 1. 所有变更的 dts/dtsi 必须通过编译
    - for f in $(git diff --name-only origin/main -- '*.dts*'); do
        cpp -nostdinc -I include -undef -x assembler-with-cpp $f | \
        dtc -W node_name_chars_strict -I dts -O dtb -o /dev/null - || exit 1;
      done
    # 2. 通过 dt-schema 语义校验
    - make -C $KERNEL_SRC dtbs_check
    # 3. 禁止在 SoC dtsi 层新增 status = "okay"（本产品线纪律）
    - '! git diff origin/main -- "*soc*.dtsi" | grep -q "^\+.*status.*okay"'
```

第三条是自定义纪律检查的例子——dtc 和 dt-schema 管不了的团队约定，用 grep 级别的规则兜底。它能拦住"把产品级启用动作写进共享层"这类结构性错误。

## 本节总结

设备树组织方式决定硬件变更在软件侧的传导成本。SKU 少时独立 DTS 最简单；SKU 增多后共性必须上浮到共享 dtsi；编译期无法确定的硬件组合交给 overlay。质量的底线由工具守住：dtc 警告管语法，dt-schema 管语义，CI 自定义规则管团队约定。

| 问题 | 一句话答案 | 详见 |
|------|-----------|------|
| 几个 SKU 该抽 dtsi？ | 3 个以上或出现 20 行级复制粘贴时 | 16.4.2 |
| 继承层数上限？ | 三层，再深审查成本失控 | 16.4.2 |
| 什么时候用 overlay？ | 载板/扩展卡等编译期无法确定的组合 | 16.4.2 |
| 评审先查什么？ | compatible 照抄 EVK、status 散落多层 | 16.4.3 |
| 怎么自动拦错？ | dtc -W + dtbs_check + CI 自定义规则 | 16.4.4 |
