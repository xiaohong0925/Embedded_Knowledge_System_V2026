启动链分析从一个真实故障开始：-40°C 低温下 15% 概率启动失败，日志显示 U-Boot 能运行但内核加载后 hang 住。谜底要到 16.5.2 才揭晓——而定位它的前提，是先建立从 BootROM 到 Shell 的完整链路认知。


### 决策场景：-40°C低温启动失败谜案

你负责一款工业网关的固件，在-40°C环境下约有15%概率启动失败。日志显示U-Boot能运行但内核加载后hang住。经过排查，最终发现是**SPL阶段的DDR初始化参数在低温下裕量不足**——DDR PHY的ZQ校准在-40°C时产生偏差，导致后续U-Boot从eMMC读取数据时偶发bit错误。

这个案例暴露了一个深层问题：**你对启动链的了解不够深入**。本节先从BootROM开始，代码级解析每个阶段。


### 启动链全景图

在深入代码之前，先建立整体认知。嵌入式Linux系统的启动链（Boot Chain）通常由以下五个阶段组成：

```
┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
│ BootROM │───→│   SPL   │───→│ U-Boot  │───→│  Kernel │───→│ Rootfs  │
│ (SoC固化)│    │(阶段一加载器)│   │(完整Bootloader)│   │(Linux内核) │   │(用户空间) │
│  ~100ms │    │ ~200ms  │    │ ~500ms  │    │ ~800ms  │    │ ~500ms  │
│  SRAM   │    │  SRAM   │    │   DDR   │    │   DDR   │    │   DDR   │
└─────────┘    └─────────┘    └─────────┘    └─────────┘    └─────────┘
   SoC上电       初始化DDR       加载内核       内核初始化      启动init
  自动执行      加载U-Boot      传递参数       挂载rootfs     启动服务
```

**阶段总览表：**

| 阶段 | 代码位置 | 执行环境 | 主要工作 | 典型耗时 | 调试方法 |
|------|---------|---------|---------|---------|---------|
| BootROM | SoC内部ROM（不可修改） | SRAM/ROM | 硬件初始化、加载SPL | 50-300ms | JTAG、BOOT_MODE引脚、ROM日志 |
| SPL | 外部存储→SRAM | SRAM（通常<256KB） | 初始化DDR、加载U-Boot | 100-500ms | UART早期打印、SPL调试符号 |
| U-Boot | 外部存储→DDR | DDR | 初始化外设、加载内核/DTB | 300ms-3s | 命令行、bootm调试、trace |
| Kernel | 外部存储→DDR | DDR | 内核初始化、驱动probe | 500ms-5s | initcall_debug、printk、kgdb |
| Rootfs | 外部存储→DDR | DDR | 挂载文件系统、启动init | 300ms-10s | systemd-analyze、bootchart |

> 💡 以上耗时是"典型未优化"系统的参考值。优化后的系统（Falcon Mode + 裁剪内核 + 最小rootfs）可以将总启动时间压缩到1.5-3秒。

### 1. BootROM：SoC上电后第一条代码

#### 1.1 BootROM的本质

BootROM（Boot Read-Only Memory）是固化在SoC芯片内部的一块只读存储器，通常位于芯片的**ROM区域**（地址0x0000_0000或SoC特定的复位向量地址）。它是**不可修改的**——由芯片厂商在流片时固化，用户无法通过软件更新。

BootROM的代码大小通常在**16KB-128KB**之间，取决于SoC复杂度。例如：

| SoC系列 | BootROM大小 | 复位向量地址 | 启动模式检测方式 |
|---------|------------|-------------|----------------|
| NXP i.MX6系列 | ~80KB | 0x0000_0000 | BOOT_MODE[1:0]引脚 + eFUSE |
| NXP i.MX8系列 | ~96KB | 0x0000_0000 | BOOT_MODE[3:0]引脚 + eFUSE |
| TI AM335x | ~64KB | 0x0000_0000 | SYSBOOT[15:0]引脚 |
| Rockchip RK3399 | ~32KB | 0xFFFF_0000 | OM引脚 + eFUSE |
| Allwinner H6 | ~24KB | 0x0000_0000 | BOOT_SEL引脚 |
| STM32MP1 | ~48KB | 0x0000_0000 | BOOT0/BOOT1/BOOT2引脚 |

#### 1.2 BootROM的执行流程（代码级）

BootROM的执行流程虽然因厂商而异，但遵循统一模式。以NXP i.MX6为例，BootROM的伪代码逻辑如下：

```c
/* arch/arm/cpu/armv7/mx6/soc.c — i.MX6 BootROM 执行流程 */
void bootrom_main(void)
{
    /* 1. 最硬件初始化（关中断、设置栈指针） */
    disable_interrupts();
    setup_temp_stack();          /* 使用SRAM中的临时栈 */
    
    /* 2. 读取启动模式选择 */
    boot_mode = read_boot_pins(); /* 读取BOOT_MODE[1:0]引脚 */
    /*  00 = 内部Boot（从eFUSE/引脚选择具体介质） */
    /*  01 = 串行下载（USB/UART刷机模式）          */
    /*  10 = 保留                                  */
    /*  11 = 保留                                  */
    
    /* 3. 如果是Internal Boot模式，进一步检测具体介质 */
    if (boot_mode == BOOT_MODE_INTERNAL) {
        boot_dev = read_boot_device_fuses(); /* eFUSE或GPIO覆盖 */
    }
    
    /* 4. 初始化对应存储接口 */
    switch (boot_dev) {
    case BOOT_DEV_MMC:
        mmc_boot_init();         /* 初始化USDHC控制器 */
        break;
    case BOOT_DEV_NAND:
        nand_boot_init();        /* 初始化GPMI/NFC */
        break;
    case BOOT_DEV_SPI_NOR:
        spi_boot_init();         /* 初始化ECSPI/QSPI */
        break;
    case BOOT_DEV_SATA:
        sata_boot_init();        /* 初始化SATA（仅部分型号） */
        break;
    case BOOT_DEV_I2C:
        i2c_boot_init();         /* 从EEPROM加载（小容量） */
        break;
    default:
        goto serial_download;    /* 未知设备，进入下载模式 */
    }
    
    /* 5. 从存储介质加载SPL到SRAM */
    /* i.MX6的SRAM（OCRAM）位于0x0090_0000，大小128KB */
    spl_load_addr = 0x00907000;  /* SPL加载目标地址 */
    spl_size = load_spl_from_media(boot_dev, spl_load_addr);
    
    if (spl_size == 0) {
        /* 加载失败——可能是： */
        /* - 存储介质不存在/未焊接 */
        /* - SPL签名验证失败（Secure Boot） */
        /* - 存储介质损坏 */
        goto serial_download;
    }
    
    /* 6. Secure Boot签名验证（如果启用） */
#if CONFIG_SECURE_BOOT
    if (!verify_hab_signature(spl_load_addr, spl_size)) {
        /* HAB（High Assurance Boot）验证失败 */
        /* 进入HAB错误状态，CPU锁定或重置 */
        hab_failure_handler();
    }
#endif
    
    /* 7. 跳转到SPL执行 */
    jump_to_spl(spl_load_addr);
}
```

#### 1.3 BootROM的存储介质检测流程

BootROM如何知道从哪个存储介质加载SPL？这是启动问题的高发区。

**NXP i.MX6的启动介质检测**：

```
                    ┌──────────────────┐
                    │   CPU Reset      │
                    │  (POR_B rising)  │
                    └────────┬─────────┘
                             ▼
                    ┌──────────────────┐
                    │ 读取BOOT_MODE[1:0]│
                    │  GPIO引脚物理电平  │
                    └────────┬─────────┘
                             ▼
              ┌──────────────────────────────┐
              │ BOOT_MODE = 00 (Internal Boot)│
              └──────────────┬───────────────┘
                             ▼
              ┌──────────────────────────────┐
              │ 读取BOOT_CFG1[7:4] (eFUSE或  │
              │ GPIO覆盖)确定具体介质         │
              │  0000 = NOR/OneNAND          │
              │  0001 = SD/MMC (eSD/eMMC)    │
              │  0010 = SPI NOR/EEPROM       │
              │  0011 = SPI NOR/EEPROM (alt) │
              │  0100 = NAND                 │
              │  0101 = SD/MMC (alt)         │
              │  011x = SATA                 │
              │  100x = I2C/SPI 串行EEPROM   │
              └──────────────┬───────────────┘
                             ▼
              ┌──────────────────────────────┐
              │ 初始化对应存储控制器         │
              │ 按协议读取SPL镜像            │
              └──────────────┬───────────────┘
                             ▼
              ┌──────────────────────────────┐
              │ SPL加载到SRAM → 跳转执行     │
              └──────────────────────────────┘
```

**i.MX6从eMMC加载SPL的详细流程**：

```
1. BootROM初始化USDHC1/USDHC2控制器
2. 发送CMD0 (GO_IDLE_STATE) — 重置eMMC
3. 发送CMD1 (SEND_OP_COND) — 查询电压范围
4. 发送CMD2 (ALL_SEND_CID) — 获取CID
5. 发送CMD3 (SET_RELATIVE_ADDR) — 分配RCA
6. 发送CMD9 (SEND_CSD) — 获取CSD（容量/速度信息）
7. 发送CMD7 (SELECT_CARD) — 选中设备
8. 发送CMD6 (SWITCH) — 切换到High Speed模式
9. 发送CMD17/CMD18 (READ_SINGLE_BLOCK/READ_MULTIPLE_BLOCK)
   — 从LBA 0x2（即偏移0x400）开始读取SPL
   
   ⚠️ i.MX6从eMMC加载SPL时，默认从偏移0x400开始读取！
   ⚠️ 不是LBA 0！这是最常见的SPL烧录偏移错误。
```

#### 1.4 BootROM的硬件签名验证（Secure Boot）

如果SoC启用了Secure Boot（通过eFUSE的SEC_CONFIG[1:0]），BootROM会在加载SPL后执行**HAB（High Assurance Boot）**签名验证：

```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│  CSF (命令序列 │ → │  SRK (超级   │ → │ 签名验证     │
│   文件)      │    │  根密钥)表   │    │  引擎        │
└─────────────┘    └─────────────┘    └──────┬──────┘
       ↑                                      │
       └──────────────────────────────────────┘
                    HAB验证流程

CSF包含：
- 密钥索引和证书
- 签名算法（RSA-2048/4096, ECDSA P-256/P-384）
- 需要验证的代码区域地址和长度
- 签名数据
```

**HAB验证失败的常见错误码**（从i.MX6的ROM日志读取）：

| HAB事件 | 错误码 | 含义 | 排查方向 |
|---------|-------|------|---------|
| HAB_FAILURE | 0x1B | 签名验证失败 | SPL镜像被修改但未重新签名 |
| HAB_FAILURE | 0x19 | SRK哈希不匹配 | eFUSE中烧录的SRK与CSF中的不符 |
| HAB_FAILURE | 0x18 | CSF格式错误 | CSF工具版本不匹配 |
| HAB_FAILURE | 0x21 | 证书过期 | 证书有效期问题 |
| HAB_FAILURE | 0x2E | 不允许的加密算法 | 使用了BootROM不支持的算法 |
| HAB_WARNING | 0x69 | 工程模式（未关闭调试） | 生产设备应关闭DEBUG eFUSE |

```bash
# 从U-Boot中读取HAB状态（验证Secure Boot状态）
=> hab_status

# Secure boot disabled
# 或
# HAB Configuration: 0xcc, HAB State: 0x99
# = HAB_CFG_CLOSED (生产状态) + HAB_STATE_SECURE (安全状态)
```

#### 1.5 BootROM的存储介质加载细节

BootROM从不同介质加载SPL的方式和偏移地址各不相同：

| 存储介质 | SPL加载偏移 | 最大SPL大小 | 加载方式 | 特殊要求 |
|---------|------------|------------|---------|---------|
| SD卡 | LBA 0x400 (偏移2KB) | ~1MB | 原始扇区读取 | 需要特定分区格式 |
| eMMC Boot分区 | 偏移0 | ~1MB | 原始读取 | BOOT_PARTITION_ENABLE需设置 |
| eMMC User分区 | 偏移0x400 | ~1MB | 原始扇区读取 | 从LBA 0x2开始 |
| NAND Flash | 第0块 | 与页大小相关 | MTD读取 | 坏块跳过 |
| SPI-NOR | 偏移0 | 与Flash大小相关 | SPI读取 | 支持XIP（直接执行） |
| UART/USB | 串流接收 | ~1MB | 串行下载协议 | 需要USB/UART连接 |

> ⚠️ BootROM 从错误的介质加载 SPL 的实际案例：某批次产品的拨码开关贴错标签，BOOT_MODE引脚被接地而非接VDD，导致BootROM进入Serial Download模式而非Internal Boot。产品表现为"上电完全无输出"——因为BootROM在等待USB/UART连接。排查方法是测量BOOT_MODE引脚的实际电平，并与原理图对比。eFUSE可以锁定BOOT_MODE防止引脚被篡改，但烧录eFUSE是不可逆操作。

#### 1.6 BootROM常见错误与排查

**错误1：BootROM无法找到有效的SPL**

```
# 症状：上电后无任何串口输出，或JTAG显示CPU在0x0000_0000附近循环
# 原因：
#   a) SPL未烧录到正确的偏移地址
#   b) 存储介质本身故障或未焊接
#   c) BootROM不支持该存储介质的配置（如eMMC的bus width不正确）

# 排查步骤：
# 1. 检查存储介质的物理连接（用万用表测阻抗）
# 2. 用JTAG读取BootROM的ROM日志（部分SoC支持）
# 3. 强制进入Serial Download模式，用工具重新烧录SPL

# i.MX6用uuu/mfgtool重新烧录：
sudo uuu spl.uuu
```

**错误2：Secure Boot签名验证失败**

```
# 症状：BootROM打印部分日志后停止，或进入HAB错误状态
# 排查：
# 1. 检查eFUSE的SEC_CONFIG状态
# 2. 确认SPL镜像已用正确的CSF密钥签名
# 3. 对比eFUSE中的SRK哈希与CSF中的公钥哈希

# 用uuu读取HAB日志：
sudo uuu -HABInfo
```

**错误3：存储介质时序问题**

```
# 症状：偶发启动失败（如本节的决策场景），尤其温度极端时
# 原因：
#   a) eMMC/SD的CLK频率在低温下超出 spec
#   b) 走线过长导致信号完整性问题
#   c) 上电时序不满足存储介质的tRST要求

# 解决：
# 1. 降低eMMC的CLK频率（从52MHz降到26MHz）
# 2. 调整BootROM的I/O驱动强度（部分SoC可通过eFUSE配置）
# 3. 检查PCB走线阻抗匹配
```

---

<!-- 【待补图】SPL 执行流程图（★必要，建议生图）
生图提示词:流程图风格：从 BootROM 接收控制→初始化时钟→初始化 DDR（DDR PHY ZQ 校准）→加载 U-Boot 到 DDR→跳转 U-Boot，重点标注 DDR 初始化步骤。白底，中文标注。 -->

上一节走完 BootROM：它把 SPL 从存储介质搬进 SRAM。SPL 的使命只有一个——唤醒 DDR，这也是全链路对硬件参数最敏感的一环，低温启动失败的谜底就在这一层。

### 2. SPL（Secondary Program Loader）：DDR的唤醒者

#### 2.1 SPL的本质与必要性

SPL是BootROM加载的第一阶段加载器，它的核心使命只有一个：**初始化DDR内存，然后把U-Boot完整版加载到DDR中执行**。

为什么需要SPL？因为存在一个**鸡生蛋问题**：

- U-Boot完整版通常需要**数百KB到数MB**的内存来运行
- 但SoC上电时只有**几十KB到几百KB**的内部SRAM
- DDR控制器需要复杂的初始化序列才能工作（PHY训练、ZQ校准、write leveling等）
- 这个初始化序列本身就需要代码来执行
- 但代码不能放在DDR里——DDR还没初始化

SPL就是解决这个悖论的关键：它足够小（通常<128KB），可以放在SRAM中运行；但它又足够聪明，能完成DDR的初始化。

```
┌─────────────────────────────────────────────────────────┐
│                    内存布局（SPL阶段）                     │
├─────────────────────────────────────────────────────────┤
│  0x0000_0000 - 0x008F_FFFF │  BootROM区域（只读）       │
│  0x0090_0000 - 0x0091_FFFF │  OCRAM 128KB（SPL运行于此） │
│  0x0092_0000 - 0x009F_FFFF │  OCRAM 保留区域            │
│  0x1000_0000 - 0x4FFF_FFFF │  DDR（1GB，未初始化时不可用）│
└─────────────────────────────────────────────────────────┘

SPL的典型大小限制：
- i.MX6 SPL: ~60-100KB（SRAM 128KB，预留栈和堆）
- Rockchip SPL/TPL: ~80-120KB
- TI AM335x MLO（即SPL）: ~50-80KB（SRAM 109KB）
- Allwinner SPL: ~24-32KB（SRAM 32KB）
```

#### 2.2 SPL的编译配置

SPL不是独立的软件，它是U-Boot源码树的一部分，通过特定的Kconfig选项启用：

```bash
# U-Boot的SPL编译配置
make menuconfig

# 核心SPL选项：
# CONFIG_SPL=y                    — 启用SPL构建
# CONFIG_SPL_BUILD=y              — 标记当前为SPL编译（自动生成）
# CONFIG_SPL_MMC_SUPPORT=y        — SPL支持从MMC/eMMC加载
# CONFIG_SPL_NAND_SUPPORT=y       — SPL支持从NAND加载
# CONFIG_SPL_SPI_SUPPORT=y        — SPL支持从SPI-NOR加载
# CONFIG_SPL_ETH_SUPPORT=y        — SPL支持网络加载（SPL-netboot）
# CONFIG_SPL_ENV_SUPPORT=y        — SPL支持环境变量
# CONFIG_SPL_FAT_SUPPORT=y        — SPL支持FAT文件系统
# CONFIG_SPL_EXT_SUPPORT=y        — SPL支持EXT文件系统
# CONFIG_SPL_USBETH_SUPPORT=y     — SPL支持USB以太网
# CONFIG_SPL_LOAD_FIT=y           — SPL使用FIT镜像格式
# CONFIG_SPL_OF_CONTROL=y         — SPL支持设备树
# CONFIG_SPL_DM=y                 — SPL使用Driver Model
# CONFIG_SPL_SERIAL_SUPPORT=y     — SPL支持串口输出
# CONFIG_SPL_GPIO_SUPPORT=y       — SPL支持GPIO
# CONFIG_SPL_LIBCOMMON_SUPPORT=y  — SPL使用common库
# CONFIG_SPL_LIBGENERIC_SUPPORT=y — SPL使用generic库

# DDR初始化相关（SoC特定）：
# CONFIG_SPL_DDR_SUPPORT=y        — SPL包含DDR初始化
```

**实际编译命令**：

```bash

#### 2.3 SPL的执行流程（代码级）

SPL的入口代码位于`arch/arm/cpu/armv7/start.S`，是启动链中最底层的汇编代码之一：

```asm
/* arch/arm/cpu/armv7/start.S — SPL入口 */

/* 复位向量表 */
.globl _start
_start:
    b   reset           /* 复位入口 */
    b   _undefined_instruction
    b   _software_interrupt
    b   _prefetch_abort
    b   _data_abort
    b   _not_used
    b   _irq
    b   _fiq

/* 复位后的第一条指令 */
.globl reset
reset:
    /* 1. 设置CPU为SVC模式，关中断 */
    mrs r0, cpsr
    bic r0, r0, #0x1f
    orr r0, r0, #0xd3         /* SVC模式 + 关IRQ/FIQ */
    msr cpsr, r0
    
    /* 2. 关闭MMU、D-cache、I-cache（如果之前开启了） */
    mrc p15, 0, r0, c1, c0, 0 /* 读取SCTLR */
    bic r0, r0, #0x00002300   /* 清V、I、C位 */
    bic r0, r0, #0x00000005   /* 清D、M位 */
    bic r0, r0, #0x00001000   /* 清I位（I-cache） */
    mcr p15, 0, r0, c1, c0, 0 /* 写回SCTLR */
    
    /* 3. 设置临时栈指针（在SRAM中） */
    ldr sp, =(CONFIG_SPL_STACK) /* 如 0x0091_FFF0 */
    
    /* 4. 跳转到C代码 */
    bl  board_init_f            /* SPL的板级初始化 */
    
    /* 注意：SPL的board_init_f与U-Boot完整版的board_init_f不同！ */
    /* SPL版本位于 common/spl/spl.c */
```

SPL的C代码入口`spl.c`：

```c
/* common/spl/spl.c — SPL主流程 */

void board_init_r(gd_t *new_gd, ulong dest_addr)
{
    gd = new_gd;
    
    /* 1. 初始化全局数据指针 */
    memset(gd, '\0', sizeof(gd_t));
    
    /* 2. 初始化驱动模型（DM）基础 */
    dm_init_and_scan(true);
    
    /* 3. 初始化串口（如果能）——这是我们看到SPL日志的起点 */
    preloader_console_init();
    printf("SPL: board_init_r starting...\n");
    
    /* 4. 初始化存储设备 */
    spl_board_init();
    
    /* 5. 根据启动模式加载下一阶段 */
    boot_device = spl_boot_device();
    
    switch (boot_device) {
    case BOOT_DEVICE_MMC1:
    case BOOT_DEVICE_MMC2:
        spl_mmc_load_image();
        break;
    case BOOT_DEVICE_NAND:
        spl_nand_load_image();
        break;
    case BOOT_DEVICE_SPI:
        spl_spi_load_image();
        break;
    case BOOT_DEVICE_USB:
        spl_usb_load_image();
        break;
    case BOOT_DEVICE_ETH:
        spl_net_load_image();
        break;
    default:
        hang(); /* 未知启动设备，死循环 */
    }
    
    /* 6. 跳转到加载的镜像 */
    spl_image.entry_point(); /* 通常是U-Boot的_entry */
}
```

#### 2.4 SPL的DDR初始化（关键代码）

DDR初始化是SPL最重要的任务，也是最复杂的部分。以i.MX6为例，DDR初始化通过DCD（Device Configuration Data）表格实现：

```c
/* arch/arm/mach-imx/spl.c — i.MX6的DDR初始化 */

/* DCD表格定义了需要写入的寄存器地址和值 */
/* 这些值来自DDR芯片的数据手册和PCB layout参数 */

/* 典型的DCD配置（DDR3-1066, 1GB, 2片x16） */
static struct mx6_ddr3_cfg ddr_cfg = {
    .mem_speed = 1066,           /* DDR3-1066 (533MHz clock) */
    .density = 4,                /* 4Gb per chip */
    .width = 16,                 /* x16 */
    .banks = 8,                  /* 8 banks */
    .rowaddr = 15,               /* 15 row bits */
    .coladdr = 10,               /* 10 column bits */
    .pagesz = 2,                 /* 2KB page size */
    .trcd = 1375,                /* tRCD = 13.75ns → 1375ps */
    .trcmin = 4875,              /* tRC = 48.75ns */
    .trasmin = 3500,             /* tRAS = 35ns */
    /* ... 更多时序参数 */
};

/* DDR PHY（MMDC）寄存器配置 */
static void spl_ddr_init(void)
{
    /* 1. 使能MMDC时钟 */
    enable_mmdc_clock();
    
    /* 2. 配置I/O引脚驱动强度和 slew rate */
    /* ⚠️ 这个参数直接影响低温下的信号完整性！ */
    writel(0x30, IOMUXC_SW_PAD_CTL_PAD_DRAM_SDCLK0);
    writel(0x30, IOMUXC_SW_PAD_CTL_PAD_DRAM_SDCLK1);
    /* drive strength = 0x30 (240 Ohm / 7 = ~34 Ohm) */
    /* 低温下可能需要提高drive strength到0x38或更高 */
    
    /* 3. 执行ZQ校准 */
    /* ZQ校准使用外部240Ω电阻校准输出驱动器阻抗 */
    /* 低温下ZQ校准结果会偏移！ */
    mmdc_do_zq_calibration();
    
    /* 4. Write Leveling — 补偿DQ/DQS与CLK的skew */
    /* 这是DDR3的关键校准步骤 */
    mmdc_do_write_leveling();
    
    /* 5. Read DQS Gating校准 */
    mmdc_do_dqs_gating();
    
    /* 6. 最终时序配置 */
    mmdc_set_timing_params(&ddr_cfg);
    
    /* 7. 使能DDR控制器 */
    mmdc_enable();
}
```

> ⚠️ SPL 的 DDR 初始化参数在低温下不稳定是常见问题：本节开篇的决策场景就是典型案例。DDR PHY的ZQ校准在低温下会产生偏差，因为外部240Ω参考电阻的温度系数不为零（典型±50 ppm/°C，-40°C时偏差约2.4%）。同时，PCB走线的阻抗也会随温度变化。解决方案：(1) 在DDR初始化代码中加入温度补偿；(2) 提高I/O drive strength的裕量（从最小值调到中值）；(3) 降低DDR频率（从533MHz降到400MHz）增加时序裕量；(4) 使用工业级DDR芯片（-40°C~+105°C spec）。最严重的情况下，需要在SPL中加入DDR训练（training）的retry机制——如果第一次训练失败，调整参数重试。

### 3. U-Boot：完整的Bootloader

#### 3.2 board_init_f() 代码分析

```c
/* common/board_f.c — board_init_f() */

void board_init_f(ulong boot_flags)
{
    gd_t *new_gd;
    
    /* 初始化全局数据指针 gd */
    /* gd（global data）是U-Boot的全局数据结构，贯穿整个启动过程 */
    new_gd = &gdata;  /* 使用SRAM中的静态实例 */
    memset(new_gd, '\0', sizeof(gd_t));
    gd = new_gd;
    
    /* 设置标志位 */
    gd->flags = boot_flags;
    gd->have_console = 0;
    
    /* 执行init_sequence_f[]数组中的所有初始化函数 */
    for (init_fnc_ptr = init_sequence_f; *init_fnc_ptr; ++init_fnc_ptr) {
        if ((*init_fnc_ptr)() != 0)
            hang();  /* 初始化失败，死循环 */
    }
    
    /* 计算重定位地址 */
    /* U-Boot可能需要将自己从加载地址复制到DDR的更高地址 */
    gd->relocaddr = calculate_relocation_addr();
    
    /* 跳过重定位 */
    relocate_code(gd->start_addr_sp, gd->relocaddr);
}

/* init_sequence_f[] — board_init_f阶段的初始化函数表 */

#### 3.4 环境变量加载机制

U-Boot的环境变量是启动配置的核心，存储了bootcmd、bootargs、网络参数等关键配置。

```c
/* env/common.c — 环境变量加载 */

int env_init(void)
{
    struct env_driver *drv;
    int ret;
    
    /* 1. 查找环境变量存储驱动 */
    drv = env_driver_lookup_default();
    
    /* 2. 从存储介质加载 */
    /* 优先级：MMC → NAND → SPI-NOR → EEPROM → 内存 */
    ret = drv->load();
    
    if (ret == -ENOENT) {
        /* 环境变量不存在，使用编译时默认值 */
        gd->env_addr = (ulong)&default_environment[0];
        gd->env_valid = ENV_VALID;
        return 0;
    }
    
    if (ret < 0) {
        /* 加载失败（如CRC校验失败） */
        /* 使用默认环境变量，并标记为需要保存 */
        gd->env_addr = (ulong)&default_environment[0];
        gd->env_valid = ENV_INVALID;
        return 0;
    }
    
    /* 3. CRC校验 */
    if (!env_crc_ok()) {
        printf("*** Warning - bad CRC, using default environment\n");
        gd->env_addr = (ulong)&default_environment[0];
        gd->env_valid = ENV_INVALID;
    }
    
    return 0;
}

/* 环境变量的存储位置（以eMMC为例） */
/* 通常存储在eMMC的特定偏移或独立分区 */
#define CONFIG_ENV_OFFSET      0xC0000    /* 偏移768KB */
#define CONFIG_ENV_SIZE        0x20000    /* 大小128KB */
#define CONFIG_ENV_IS_IN_MMC   1
```

> ⚠️ U-Boot 环境变量损坏会导致无法找到 kernel：某产品在现场偶发启动失败，U-Boot提示"Failed to load 'zImage'"，但实际文件存在。排查发现环境变量区的CRC偶发校验失败（eMMC的bit flip），U-Boot回退到默认环境变量，但默认的`bootcmd`指向的是错误的分区号（`mmc 0:1` vs 实际的`mmc 0:2`）。解决方案：(1) 在U-Boot配置中增加`CONFIG_ENV_REDUND`启用冗余环境变量（双份存储+CRC）；(2) 在生产烧录时确保默认环境变量也是正确的；(3) 在kernel启动脚本中加入fallback逻辑。

#### 3.5 设备树（DTB）加载机制

现代U-Boot使用设备树（Device Tree）来描述硬件，内核启动时需要传递正确的DTB。

```c
/* cmd/bootz.c — bootz命令的执行流程 */

int do_bootz(struct cmd_tbl *cmdtp, int flag, int argc, char *const argv[])
{
    ulong kernel_addr, initrd_addr, dtb_addr;
    struct bootm_headers images;
    
    /* 1. 解析参数 */
    kernel_addr = argv[1] ? simple_strtoul(argv[1], NULL, 16) : image_load_addr;
    initrd_addr = argv[2] && strcmp(argv[2], "-") ? simple_strtoul(argv[2], NULL, 16) : 0;
    dtb_addr = argv[3] ? simple_strtoul(argv[3], NULL, 16) : 0;
    
    /* 2. 验证zImage魔数 */
    if (!valid_zimage_magic(kernel_addr)) {
        printf("Bad Linux ARM zImage magic!\n");
        return 1;
    }
    
    /* 3. 设置bootm images结构 */
    memset(&images, '\0', sizeof(images));
    images.ep = kernel_addr;           /* 入口点 */
    images.os.start = kernel_addr;     /* OS镜像起始 */
    images.os.type = IH_OS_LINUX;      /* OS类型 = Linux */
    images.os.comp = IH_COMP_GZIP;     /* 压缩方式 = gzip */
    
    /* 4. 加载/验证DTB */
    if (dtb_addr) {
        /* 用户指定了DTB地址 */
        images.ft_addr = (void *)dtb_addr;
    } else {
        /* 尝试从bootm环境变量或FIT镜像获取DTB */
        images.ft_addr = locate_dtb(&images);
    }
    
    /* 5. 验证DTB */
    if (fdt_check_header(images.ft_addr) != 0) {
        printf("Invalid device tree blob!\n");
        return 1;
    }
    
    /* 6. 修改DTB — 插入内核命令行参数和内存信息 */
    fdt_setup(&images);
    /* 这会将bootargs插入到DTB的/chosen节点 */
    /* 将内存布局插入到DTB的/memory节点 */
    
    /* 7. 关闭缓存、MMU，准备跳转到内核 */
    boot_prep_linux(&images);
    
    /* 8. 跳转到内核 */
    boot_jump_linux(&images, 0);
    
    return 0;  /* 不应该到达 */
}
```

int fdt_setup(struct bootm_headers *images)
{
    void *fdt = images->ft_addr;
    int nodeoffset;
    
    /* 1. 展开FDT（如果压缩） */

    }
    
    /* 3. 插入bootargs（从环境变量读取） */
    char *bootargs = env_get("bootargs");
    if (bootargs) {
        fdt_setprop_string(fdt, nodeoffset, "bootargs", bootargs);
    }
    
    /* 4. 插入initrd信息（如果使用initramfs） */
    if (images->rd_start) {
        fdt_setprop_u32(fdt, nodeoffset, "linux,initrd-start", images->rd_start);
        fdt_setprop_u32(fdt, nodeoffset, "linux,initrd-end", images->rd_end);
    }
    
    /* 5. 设置/machine-model */
    fdt_setprop_string(fdt, 0, "model", CONFIG_SYS_BOARD);
    
    return 0;

### 4. Kernel：Linux内核的启动流程

#### 4.1 Kernel镜像格式与解压

当U-Boot执行`bootz`或`booti`命令后，控制权转移到Linux内核。内核启动的第一步是解压（如果内核是压缩的）。

```
┌─────────────────────────────────────────────────────────┐
│                    内核镜像结构（zImage）                   │
├─────────────────────────────────────────────────────────┤
│  0x0000 - 0x0003 │ ARM zImage魔数: 0x016F2818 (小端)    │
│  0x0004 - 0x0023 │ 启动参数（内核加载地址等）             │
│  0x0024 - 0x00EF │ 解压代码（自解压stub）                 │
│  0x00F0 - ...    │ 压缩的内核镜像（gzip/bzip2/lzma/lz4）  │
└─────────────────────────────────────────────────────────┘

自解压流程：
1. U-Boot跳转到zImage的入口点
2. zImage的前0x24字节是解压stub代码
3. 解压stub在原地或指定地址解压内核
4. 解压完成后跳转到真正的内核入口（stext）
```

```asm
/* arch/arm/boot/compressed/head.S — zImage自解压入口 */

_start:
    /* 保存寄存器（U-Boot传递的参数） */
    /* r0 = 0 (必须为0) */
    /* r1 = machine type (ATAGS，现在用DTB) */
    /* r2 = DTB物理地址 */
    mov r7, r0
    mov r8, r1
    mov r9, r2
    
    /* 检测我们运行在哪 */
    bl  __lookup_processor_type    /* 查找CPU类型 */
    bl  __lookup_machine_type      /* 查找机器类型（legacy） */
    
    /* 计算解压目标地址 */
    /* 如果启用了CONFIG_AUTO_ZRELADDR，自动计算 */
    /* 否则使用CONFIG_PHYS_OFFSET */
    
    /* 创建页表（用于解压期间的MMU映射） */
    bl  create_page_tables
    
    /* 使能MMU */
    bl  __enable_mmu
    
    /* 调用解压函数 */
    bl  decompress_kernel        /* 解压内核 */
    
    /* 关闭MMU和缓存 */
    bl  __mmu_off
    
    /* 跳转到解压后的内核 */
    b   __enter_kernel
    
__enter_kernel:
    /* 恢复寄存器 */
    mov r0, #0                   /* 必须为0 */
    mov r1, r8                   /* machine type */
    mov r2, r9                   /* DTB地址 */
    
    /* 跳转 */
    mov pc, r4                   /* r4 = 解压后的内核入口 */
```

#### 4.2 start_kernel() — Linux内核的主入口

解压完成后，内核跳转到`stext`（ARM）或`_stext`（ARM64），最终汇聚到`start_kernel()`函数。

```c
/* init/main.c — start_kernel() — Linux内核的C语言入口 */

asmlinkage __visible void __init start_kernel(void)
{
    char *command_line;
    char *after_dashes;
    
    /* === 第一阶段：架构无关的最早期初始化 === */
    
    set_task_stack_end_magic(&init_task);  /* 设置init任务的栈 */
    smp_setup_processor_id();              /* 设置当前CPU ID */
    cgroup_init_early();                   /* 早期cgroup初始化 */
    local_irq_disable();                   /* 关本地中断 */
    early_boot_irqs_disabled = true;
    
    /* === 第二阶段：架构相关初始化 === */
    
    boot_cpu_init();                       /* 标记boot CPU */
    page_address_init();                   /* 页地址初始化 */
    setup_arch(&command_line);             /* ★ 架构特定初始化 ★ */
    /* setup_arch是各架构的核心初始化函数：
     * ARM: arch/arm/kernel/setup.c
     * ARM64: arch/arm64/kernel/setup.c
     * x86: arch/x86/kernel/setup.c
     * 主要工作：
     *   - 解析设备树（DTB）
     *   - 设置内存布局（memory banks）
     *   - 初始化MMU/页表
     *   - 设置定时器
     *   - 解析bootargs
     */
    
    /* === 第三阶段：内存管理初始化 === */
    
    mm_init_cpumask(&init_mm);             /* 初始化init_mm的CPU掩码 */
    setup_per_cpu_areas();                 /* 设置per-CPU变量区域 */
    trap_init();                           /* 异常/中断向量初始化 */
    mm_init();                             /* 内存管理子系统初始化 */
    /* mm_init内部：
     *   - page_alloc_init()   页分配器初始化
     *   - mem_init()          内存最终初始化
     *   - kmem_cache_init()   slab分配器初始化
     *   - vmalloc_init()      vmalloc初始化
     */
    
    /* === 第四阶段：调度器和IRQ初始化 === */
    
    sched_init();                          /* 进程调度器初始化 */
    preempt_disable();                     /* 禁止抢占 */
    radix_tree_init();                     /* 基数树初始化 */
    irq_early_init();                      /* 早期IRQ初始化 */
    tick_init();                           /* tick初始化 */
    init_timers();                         /* 定时器子系统 */
    hrtimers_init();                       /* 高精度定时器 */
    softirq_init();                        /* 软中断 */
    timekeeping_init();                    /* 时间keeping */
    time_init();                           /* 架构特定时间初始化 */
    
    /* === 第五阶段：控制台和printk === */
    
    console_init();                        /* 控制台初始化 */
    /* 从此printk可以输出到控制台 */
    /* 之前的printk存储在log buffer中 */
    
    if (panic_later)
        panic("%s", panic_later);         /* 处理早期panic */
    
    /* === 第六阶段：内核子系统初始化 === */
    
    mem_init();                            /* 内存最终初始化 */
    kmem_cache_init();                     /* slab分配器 */
    calibrate_delay();                     /* BogoMIPS计算 */
    pidhash_init();                        /* PID哈希表 */
    vfs_caches_init_early();               /* VFS缓存早期初始化 */
    pagecache_init();                      /* 页缓存 */
    
    /* === 第七阶段：rest_init — 创建init进程和kthreads === */
    
    rest_init();                           /* ★ 创建PID 1 ★ */
    /* rest_init永不返回 */
}
```

#### 4.3 setup_arch() — 架构特定初始化（ARM）

```c
/* arch/arm/kernel/setup.c — setup_arch() */

void __init setup_arch(char **cmdline_p)
{
    const struct machine_desc *mdesc;
    
    /* 1. 处理器初始化 */
    processor.id = read_cpuid_id();       /* 读取CPU ID */
    processor.ctrl = read_cpuid_ctrl();   /* 读取控制寄存器 */
    
    /* 2. 查找机器描述符 */
    /* 从设备树兼容字符串匹配 machine_desc */
    mdesc = setup_machine_fdt(__atags_pointer); /* __atags_pointer = DTB地址 */
    if (!mdesc)
        mdesc = lookup_machine_type(processor.id); /* fallback到ATAGS */
    machine_desc = mdesc;
    
    /* 3. 设置内存布局 */
    /* 从设备树解析/memory节点 */
    setup_machine_tags(mdesc, &tags);
    parse_tags(tags);
    
    /* 4. 解析命令行参数 */
    /* 从设备树/chosen/bootargs读取 */
    *cmdline_p = default_command_line;
    strlcpy(boot_command_line, *cmdline_p, COMMAND_LINE_SIZE);
    parse_early_param();                   /* 解析early参数 */
    
    /* 5. 初始化分页 */
    paging_init(mdesc);                    /* 设置页表 */
    
    /* 6. 请求标准内存区域 */
    request_standard_resources(&meminfo, mdesc);
    
    /* 7. 初始化IRQ */
    init_irq();                            /* IRQ子系统 */
    
    /* 8. 初始化timer */
    time_init();                           /* 架构特定timer */
    
    /* 9. 控制台初始化 */
    console_init();
    
    /* 10. 缓存和TLB */
    cacheid_init();                        /* 缓存类型检测 */
    
#ifdef CONFIG_OF
    /* 11. 设备树展开（unflatten） */
    unflatten_device_tree();               /* 将FDT展开为内核设备树 */
#endif
    
    /* 12. 遍历设备树，注册平台设备 */
    of_platform_populate(NULL, of_default_bus_match_table, NULL, NULL);
}

#### 4.4 rest_init() — 创建init进程

```c
/* init/main.c — rest_init() */

noinline void __init_refok rest_init(void)
{
    int pid;
    
    /* 1. 创建kernel_init线程 — 这就是PID 1（init进程） */
    /* kernel_init最终会启动用户空间的/sbin/init */
    pid = kernel_thread(kernel_init, NULL, CLONE_FS | CLONE_SIGHAND);
    
    /* 2. 创建kthreadd — 内核线程的守护进程（PID 2） */
    pid = kernel_thread(kthreadd, NULL, CLONE_FS | CLONE_FILES);
    kthreadd_task = find_task_by_pid_ns(pid, &init_pid_ns);
    
    /* 3. 当前进程变成idle进程（PID 0） */
    init_idle_bootup_task(current);
    schedule_preempt_disabled();
    cpu_startup_entry(CPUHP_ONLINE);       /* idle循环 */
}

/* kernel_init — PID 1的执行路径 */
static int __ref kernel_init(void *unused)
{
    /* 1. 等待kthreadd准备就绪 */
    wait_for_completion(&kthreadd_done);
    
    /* 2. 设置init进程的命名空间 */
    kernel_init_freeable();
    
    /* 3. 初始化 SMP（如果启用） */
    smp_init();
    
    /* 4. 调度器策略初始化 */
    sched_init_smp();
    
    /* 5. 工作队列初始化 */
    workqueue_init();
    
    /* 6. 初始化驱动模型 */
    driver_init();
    
    /* 7. ★ 初始化所有内置驱动（initcall）★ */
    /* 这是内核驱动probe的关键阶段！ */
    do_initcalls();
    /* do_initcalls按level顺序执行：
     *   early_initcall   — 最早期（0级）
     *   core_initcall    — 核心子系统（1级）
     *   postcore_initcall — 核心后（2级）
     *   arch_initcall    — 架构特定（3级）
     *   subsys_initcall  — 子系统（4级）
     *   fs_initcall      — 文件系统（5级）
     *   device_initcall  — 设备驱动（6级）
     *   late_initcall    — 晚期（7级）
     */
    
    /* 8. 初始化tmpfs */
    init_tmpfs();
    
    /* 9. 打开/dev/console作为stdin/stdout/stderr */
    /* 如果/dev/console不存在，会报错但继续 */
    if (sys_open((const char __user *) "/dev/console", O_RDWR, 0) < 0)
        printk(KERN_WARNING "Warning: unable to open an initial console.\n");
    
    /* 10. 尝试执行用户空间init程序 */
    /* 按以下顺序尝试： */
    if (execute_command) {
        /* 如果指定了init=参数 */
        ret = run_init_process(execute_command);
    }
    if (!ret) ret = run_init_process("/sbin/init");
    if (!ret) ret = run_init_process("/etc/init");
    if (!ret) ret = run_init_process("/bin/init");
    if (!ret) ret = run_init_process("/bin/sh");
    
    /* 全部失败 → panic */
    panic("No working init found. Try passing init= option to kernel."
          " See Linux Documentation/admin-guide/init.rst");
}
```

### 5. Rootfs：用户空间的起点

#### 5.1 initramfs vs 直接挂载rootfs

内核启动的最后一步是挂载rootfs并执行init程序。这里有两种主要方式：

```
方式一：直接挂载rootfs（最常见）
┌─────────┐    ┌─────────┐    ┌─────────────┐    ┌─────────┐
│ Kernel  │───→│ 挂载    │───→│ 执行/sbin/init│───→│ systemd │
│ 启动    │    │ /dev/xx │    │             │    │/sysvinit│
└─────────┘    └─────────┘    └─────────────┘    └─────────┘

方式二：initramfs（两阶段启动）
┌─────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────┐
│ Kernel  │───→│ 挂载        │───→│ 执行/init   │───→│ switch  │
│ 启动    │    │ initramfs   │    │（准备rootfs）│    │ _root   │
└─────────┘    │ (tmpfs)     │    │             │    │         │
               └─────────────┘    └─────────────┘    └────┬────┘
                                                          │
                              ┌───────────────────────────┘
                              ▼
                         ┌─────────┐    ┌─────────┐
                         │ 挂载    │───→│ 执行    │
                         │ 真实root│    │ 真实init│
                         └─────────┘    └─────────┘
```

**initramfs的用途**：

1. **驱动模块化**：rootfs所在存储介质的驱动未编译进内核，需要initramfs先加载驱动模块
2. **LVM/RAID/加密**：复杂的存储堆栈需要用户空间工具来组装
3. **网络rootfs**：NFS/ iSCSI root需要用户空间配置网络
4. **恢复模式**：提供一个最小的shell环境用于系统恢复
5. **A/B升级**：在切换rootfs前执行升级逻辑

**initramfs的构建**：

```bash
# 使用initramfs-tools（Debian/Ubuntu）
update-initramfs -c -k $(uname -r)
# 产物: /boot/initrd.img-$(uname -r)

# 使用dracut（Fedora/RHEL/openSUSE）
dracut -f /boot/initramfs-$(uname -r).img $(uname -r)

# 使用Yocto/Buildroot自定义
# 配置CONFIG_INITRAMFS_SOURCE指向cpio归档或目录

# 查看initramfs内容
mkdir /tmp/initramfs && cd /tmp/initramfs
zcat /boot/initrd.img-$(uname -r) | cpio -idmv
ls -la
```

#### 5.2 init进程的选择与启动

内核会按优先级尝试多个init程序位置：

```c
/* init/main.c — 用户空间init的执行顺序 */

static int __ref kernel_init(void *unused)
{
    /* ... 前面的初始化 ... */
    
    /* 如果内核参数指定了init= */
    if (execute_command) {
        ret = run_init_process(execute_command);
        if (!ret)
            return 0;
        panic("Requested init %s failed (error %d).", execute_command, ret);
    }
    
    /* 默认搜索路径 */
    if (!run_init_process("/sbin/init"))
        return 0;
    if (!run_init_process("/etc/init"))
        return 0;
    if (!run_init_process("/bin/init"))
        return 0;
    if (!run_init_process("/bin/sh"))
        return 0;
    
    panic("No working init found.");
}
```

**三种主流init系统对比**：

| 特性 | systemd | SysV init | BusyBox init |
|------|---------|-----------|--------------|
| 启动速度 | 中等（并行启动） | 慢（串行） | 快（最简单） |
| 内存占用 | 大（~20-50MB） | 中（~5-10MB） | 小（~1-2MB） |
| 功能丰富度 | 极高（cgroup、log、network、timer…） | 低 | 低 |
| 依赖管理 | 自动（socket/dbus激活） | 手动（启动脚本顺序） | 手动（inittab） |
| 调试难度 | 中（systemd-analyze） | 低（简单脚本） | 低 |
| 嵌入式适用 | 资源充足时可用 | 传统系统 | ★ 资源受限首选 ★ |
| 启动日志 | journalctl | syslog | dmesg/文件 |

#### 5.3 BusyBox init的启动流程

资源受限的嵌入式系统通常使用BusyBox init，其配置通过`/etc/inittab`：

```bash
# /etc/inittab — BusyBox init配置

# 系统启动时执行
::sysinit:/etc/init.d/rcS

# 控制台登录
::respawn:/sbin/getty -L ttymxc0 115200 vt100

# Ctrl+Alt+Del重启
::ctrlaltdel:/sbin/reboot

# 关机时执行
::shutdown:/etc/init.d/rcK

# 电源故障
::powerfail:/sbin/poweroff
```

```bash
# /etc/init.d/rcS — 系统启动脚本（典型嵌入式）
#!/bin/sh

# 1. 挂载基本文件系统
mount -t proc proc /proc
mount -t sysfs sysfs /sys
mount -t devtmpfs devtmpfs /dev
mount -t tmpfs tmpfs /tmp
mount -t tmpfs tmpfs /run

# 2. 创建必要的设备节点
mkdir -p /dev/pts
mount -t devpts devpts /dev/pts

# 3. 设置主机名
hostname $(cat /etc/hostname 2>/dev/null || echo "embedded")

# 4. 配置网络
ifconfig lo 127.0.0.1 up
ifconfig eth0 192.168.1.100 netmask 255.255.255.0 up

# 5. 加载内核模块（如果驱动未内置）
modprobe imx_sdma
modprobe galcore  # GPU驱动

# 6. 启动主应用
echo "Starting main application..."
/usr/bin/my_app &

# 7. 可选：启动sshd
dropbear -B &
```

> ⚠️ initramfs 与 rootfs 的职责容易混淆：某系统使用initramfs作为过渡，initramfs中的`/init`脚本负责解密磁盘后switch_root。但由于脚本中的一个条件判断错误（`if [ -f /dev/mapper/rootfs ]`而非`-b`），导致在特定时序下解密未完成就尝试切换，表现为"kernel panic - not syncing: Attempted to kill init"。排查了三天才发现是initramfs的问题而非内核问题。关键教训：(1) initramfs中的`/init`必须正确处理所有错误路径；(2) 使用`set -e`让shell脚本在错误时退出；(3) 在initramfs中加入调试模式（如通过内核参数`rd.debug`启用详细日志）。

### 5. 存储介质选型深度

#### 5.1 六种存储介质详解

##### NOR Flash

NOR Flash是嵌入式系统中最古老的存储介质之一，其最大特点是**支持XIP（eXecute In Place，就地执行）**。

```
NOR Flash特性：
- 接口: 并行（CFI）或 SPI（SPI-NOR）
- 读取: 随机读，类似SRAM，支持XIP
- 写入: 慢（需要erase-before-write，erase时间ms级）
- 容量: 通常1MB-256MB（SPI-NOR）或最大2GB（并行NOR）
- 可靠性: 极高，100K-1M擦写寿命
- 成本: 高（$/MB最高）
- 温度范围: 工业级-40°C~+105°C常见

XIP工作原理：
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│   CPU       │────→│  NOR Flash  │     │             │
│             │     │  （存储代码）  │     │   DDR       │
│  执行代码    │     │  直接执行     │     │  （不需要）   │
│  取指       │────→│  无需加载     │     │             │
└─────────────┘     └─────────────┘     └─────────────┘
    地址线直接映射        代码原地执行        不需要DDR！

XIP的限制：
- 代码必须是位置无关或链接到NOR的地址空间
- 写操作期间不能执行代码（需要复制到RAM再写）
- 速度受限于NOR的读取带宽（通常50-133MB/s）
```

##### NAND Flash

```
NAND Flash特性：
- 接口: 并行（ONFI/Toggle）或 SPI（SPI-NAND/pSPI）
- 读取: 顺序读快，随机读慢，不支持XIP
- 写入: 快（page编程200μs-1ms）
- 容量: 大（1GB-TB级）
- 可靠性: 中（2K-10K擦写寿命），需要ECC和坏块管理
- 成本: 低（$/MB最低）
- 特殊要求: 必须处理坏块、ECC、wear leveling

NAND的坏块管理：
出厂坏块: ~2%的block可能是出厂坏块
增长坏块: 使用过程中产生的坏块
管理方式: BBT（Bad Block Table）存储在NAND的特定区域
          通常在block 0或最后几个block

ECC要求：
SLC NAND: 通常1bit ECC/512B（Hamming码）
MLC NAND: 4-8bit ECC/512B（BCH/Reed-Solomon）
TLC NAND: 40bit+ ECC/1KB（LDPC）
```

##### eMMC

```
eMMC（embedded MultiMediaCard）特性：
- 接口: 并行（8-bit数据线 + CMD + CLK），兼容SD/MMC
- 内部结构: NAND Flash + 控制器（MMC + FTL + ECC + wear leveling）
- 读取: 快（HS400模式下400MB/s）
- 写入: 快（取决于NAND类型和控制器）
- 容量: 4GB-256GB常见
- 可靠性: 高（控制器管理wear leveling和坏块）
- 成本: 中
- 标准: JEDEC eMMC标准（当前v5.1A）

eMMC的速度等级：
┌──────────┬─────────────┬─────────────┬─────────────┐
│ 模式     │ 总线宽度    │ 时钟频率    │ 理论带宽    │
├──────────┼─────────────┼─────────────┼─────────────┤
│ Legacy   │ 1/4/8 bit   │ 0-26 MHz    │ 26 MB/s     │
│ HSSDR52  │ 4/8 bit     │ 0-52 MHz    │ 52 MB/s     │
│ HSDDR52  │ 4/8 bit     │ 0-52 MHz    │ 104 MB/s    │
│ HS200    │ 4/8 bit     │ 0-200 MHz   │ 200 MB/s    │
│ HS400    │ 8 bit       │ 0-200 MHz   │ 400 MB/s    │
│ HS400ES  │ 8 bit       │ 0-200 MHz   │ 400 MB/s    │
└──────────┴─────────────┴─────────────┴─────────────┘

★ 选型建议：至少选择HS200（200MB/s），有条件选HS400
★ 注意：HS400对PCB走线要求更高（需要阻抗控制和等长）

eMMC分区：
- Boot Area Partition 1: 128KB-4MB（存储SPL/U-Boot）
- Boot Area Partition 2: 128KB-4MB（冗余备份）
- RPMB: 4MB-16MB（安全存储，Replay Protected Memory Block）
- User Data Area: 剩余容量（存储kernel、rootfs、数据）

分区配置：
# 设置BOOT_PARTITION_ENABLE
# 使能BootROM从Boot Partition加载
mmc bootpart enable 1 0 /dev/mmcblk0
# 参数: boot_partition(1=partition1), send_ack(0), device
```

##### SD卡

```
SD卡特性：
- 接口: SD协议（兼容MMC子集）
- 速度: UHS-I(104MB/s), UHS-II(312MB/s), UHS-III(624MB/s)
- 容量: SD(2GB), SDHC(32GB), SDXC(2TB), SDUC(128TB)
- 可靠性: 低（消费级产品为主，工业级较少且贵）
- 可插拔: 是（便于开发和维护）
- 温度范围: 消费级0-70°C，工业级-40-85°C（少且贵）

★ 生产环境不建议使用SD卡作为主存储 ★
原因：
1. 接触不良：振动/温度循环导致连接不可靠
2. 质量参差不齐：不同品牌/批次差异大
3. 寿命不确定：没有eMMC的wear leveling保证
4. 安全性差：可随意插拔导致数据泄露
```

##### SPI-NOR

```
SPI-NOR特性：
- 接口: SPI（4线：CS/CLK/MOSI/MISO）
- 容量: 通常128KB-256MB
- 读取: 快（QSPI模式下80-133MB/s）
- XIP支持: 是（通过QSPI的XIP模式）
- 引脚: 少（4-6线），PCB布局简单
- 成本: 低（小容量）
- 适合: Bootloader存储、小系统固件

SPI-NOR的XIP模式：
QSPI控制器支持XIP模式，CPU可以直接从SPI-NOR取指执行，
无需先将代码复制到RAM。这对最小系统（无DDR或DDR极小）
非常有价值。

典型应用：
- 存储SPL/U-Boot（16MB SPI-NOR足够）
- 存储小内核和initramfs（如路由器）
- 配合大容量eMMC（SPI-NOR存bootloader，eMMC存系统）
```

##### pSPI（SPI NAND，pSPI = pseudo SPI）

```
SPI NAND（pSPI）特性：
- 接口: SPI（与SPI-NOR相同引脚）
- 内部: NAND Flash + 简单控制器（ECC + 坏块管理）
- 容量: 通常128MB-4GB
- 读取: 中（SPI速度限制）
- XIP支持: 否（NAND不支持随机读）
- 成本: 低（$/GB低于SPI-NOR，高于并行NAND）
- 折中方案: 在SPI接口引脚数限制下获得NAND的容量

SPI NAND vs SPI-NOR：
- SPI NAND容量更大、成本更低
- SPI-NOR支持XIP、读取更快（随机读）
- SPI NAND需要驱动支持（MTD子系统）
- SPI-NOR驱动更简单（可直接映射到地址空间）
```

#### 5.2 物理接口对比

| 存储介质 | 信号引脚 | 总线类型 | 最大CLK | PCB要求 | 连接器类型 |
|---------|---------|---------|---------|---------|-----------|
| 并行NOR | 40-56 | 地址+数据并行 | 66-133MHz | 大量走线，等长要求 | 焊接/插槽 |
| 并行NAND | 16-48 | 命令+地址+数据 | 50-100MHz | 中等走线 | 焊接 |
| eMMC | 11 | CMD+8位数据+CLK | 200MHz(HS400) | ★ 阻抗控制+等长 ★ | BGA焊接 |

| SPI-NAND | 4-6 | 同SPI-NOR | 100MHz | 简单 | 焊接 |

#### 5.4 选型决策树

```
存储介质选型决策：

Q1: 需要XIP（就地执行）吗？
├── 是 → SPI-NOR（小容量）或 并行NOR（大容量）
│         适合: 最小系统、快速启动Bootloader
│
└── 否 → Q2: 容量需求？
    ├── <256MB → SPI-NOR 或 SPI-NAND
    │             SPI-NOR: 需要XIP或简单系统
    │             SPI-NAND: 需要更大容量但引脚受限
    │
    ├── 256MB-4GB → ★ eMMC ★ 或 SPI-NAND
    │                 eMMC: 首选（可靠性高、驱动成熟）
    │                 SPI-NAND: 引脚受限时的替代
    │
    └── >4GB → eMMC（HS200/HS400）或 NAND+控制器
                考虑: 成本、可靠性、PCB空间

Q3: 温度环境？
├── -40°C ~ +85°C → 选择工业级eMMC/工业级NOR
├── -40°C ~ +105°C → 选择车规级/极端工业级
└── 0°C ~ +70°C → 消费级即可

Q4: 是否需要可插拔？
├── 是（开发维护）→ SD卡槽（仅开发阶段）
└── 否（生产环境）→ 全部焊接（BGA/WSON/SOIC）
```

### 6. 常见启动失败排查

#### 6.1 故障排查速查表

| 症状 | 可能原因 | 排查命令 | 解决方法 |
|------|---------|---------|---------|
| 上电完全无输出 | BootROM未执行（电源/复位/BootROM损坏） | 测量POR_B、电源轨、BOOT_MODE引脚 | 检查电源时序、BOOT_MODE配置 |
| BootROM日志后停止 | SPL加载失败（偏移错误/存储故障） | JTAG读取SRAM、检查SPL烧录偏移 | 重新烧录SPL到正确偏移 |
| "Bad Data CRC" | SPL/U-Boot镜像损坏 | 重新编译和烧录、检查SPL签名 | 重新烧录，检查Secure Boot配置 |
| DRAM检测失败 | DDR参数错误/硬件故障 | 读取DDR配置寄存器、检查DDR供电 | 调整DDR参数、检查硬件 |
| "File not found" | 分区错误/文件系统损坏 | `mmc part`、`fatls`/`ext4ls` | 检查分区表、重新格式化 |
| Kernel panic VFS | rootfs找不到 | 检查bootargs的root=参数 | 修正root=参数、检查分区 |
| Kernel panic init | init程序不存在/不可执行 | 检查rootfs的/sbin/init | 确保rootfs完整、init可执行 |
| 启动hang住（无panic） | 驱动probe超时/死锁 | initcall_debug、printk日志分析 | 裁剪驱动、添加超时处理 |
| 偶发启动失败 | 时序/温度/信号完整性 | 温度循环测试、降低CLK频率 | 调整时序参数、提高驱动强度 |
| 启动慢 | 驱动过多/服务过多 | systemd-analyze/initcall_debug | 裁剪驱动和服务 |

#### 6.2 五大典型故障深度分析

##### 故障1：BootROM无法加载SPL

```
症状: 上电后串口完全无输出，或只有一行BootROM日志

排查流程:
1. 测量BOOT_MODE引脚电平 → 确认是Internal Boot模式
2. 检查SPL烧录偏移 → 确认与SoC spec一致
   i.MX6 eMMC: 偏移0x400 (LBA 2)
   i.MX6 SD: 偏移0x400 (LBA 2)
   Rockchip: 偏移0x40 (LBA 0x40)
   TI AM335x: 偏移0x200 (LBA 0x200)
   
3. 用JTAG或串行下载模式重新烧录SPL:
   $ sudo uuu SPL-mfgtool.bin
   
4. 检查存储介质是否可访问:
   - 测量存储芯片的供电电压
   - 检查CLK/CMD/DATA走线
   - 用示波器看信号质量

常见原因:
- 拨码开关错误（BOOT_MODE接错电平）
- SPL烧录到错误的偏移地址
- 存储芯片未焊接好
- eMMC未配置Boot Partition
- Secure Boot签名不匹配
```

##### 故障2：SPL无法初始化DDR

```
症状: SPL打印部分日志后停止，或DRAM检测显示错误容量

排查流程:
1. 检查SPL的DDR配置参数:
   - DDR类型（DDR3/DDR3L/DDR4/LPDDR4）
   - 容量配置（row/column/bank/rank）
   - 时序参数（tRCD/tRP/tRAS/tWR等）
   
2. 检查硬件:
   - DDR芯片供电（VDDQ = 1.5V for DDR3, 1.35V for DDR3L）
   - 参考电压（VTT = VDDQ/2）
   - 时钟信号完整性
   
3. 低温问题特殊排查:
   - DDR芯片是否为工业级（-40°C spec）
   - PCB阻抗是否匹配（50Ω单端，100Ω差分）
   - DDR PHY的ZQ校准值
   
4. 调整参数:
   - 降低DDR频率（533→400MHz）
   - 提高drive strength
   - 放宽时序参数
   - 增加training retry次数
```

##### 故障3：U-Boot无法加载Kernel

```
症状: U-Boot提示"Failed to load 'zImage'"或类似错误

排查流程:
1. 检查MMC/存储设备:
   => mmc dev 0          # 选择正确的设备
   => mmc rescan         # 重新扫描
   => mmc part           # 查看分区表
   => fatls mmc 0:1 /    # 列出文件
   
2. 检查文件是否存在:
   => fatload mmc 0:1 0x80800000 zImage
   ** Unable to read file zImage **
   → 文件不存在或文件系统损坏
   
3. 检查环境变量:
   => printenv bootcmd   # 确认bootcmd正确
   => printenv bootargs  # 确认bootargs正确
   => printenv loadaddr  # 确认加载地址
   
4. 手动加载测试:
   => fatload mmc 0:1 ${loadaddr} zImage
   => fatload mmc 0:1 ${fdtaddr} dtb_file
   => bootz ${loadaddr} - ${fdtaddr}
   
常见原因:
- 环境变量损坏（CRC失败回退到默认值）
- 分区号错误（mmc 0:1 vs mmc 0:2）
- 文件名拼写错误
- 文件系统损坏（需要fsck或重新格式化）
- eMMC bit flip（启用冗余环境变量）
```

##### 故障4：Kernel panic — rootfs找不到

```
症状: 内核启动后panic，信息包含"VFS: Cannot open root device"或"Unable to mount root fs"

排查流程:
1. 检查panic信息:
   Kernel panic - not syncing: VFS: Unable to mount root fs on unknown-block(0,0)
                                                     │              │
                                                     │              └─ (major,minor) = (0,0)
                                                     │                 表示root=参数无效
                                                     └─ 无法挂载rootfs
   
   Kernel panic - not syncing: VFS: Unable to mount root fs on unknown-block(179,2)
                                                     │              │
                                                     │              └─ (179,2) = /dev/mmcblk0p2
                                                     │                 设备存在但挂载失败
                                                     └─ 可能是文件系统类型不匹配

2. 检查bootargs中的root=参数:
   root=/dev/mmcblk0p2   # eMMC第2分区
   root=/dev/mmcblk1p1   # SD卡第1分区
   root=/dev/sda1        # SATA/USB
   root=UUID=xxxxx       # UUID（最可靠，不受设备号变化影响）
   
3. 检查文件系统驱动是否编译进内核:
   CONFIG_EXT4_FS=y      # 必须是y，不能是m
   CONFIG_EXT4_USE_FOR_EXT2=y
   
4. 检查存储驱动是否编译进内核:
   CONFIG_MMC=y
   CONFIG_MMC_BLOCK=y
   CONFIG_MMC_SDHCI=y
   CONFIG_MMC_SDHCI_PLTFM=y
   CONFIG_MMC_SDHCI_ESDHC_IMX=y  # i.MX specific
   
5. 如果驱动是模块（.ko），需要initramfs:
   bootargs=... rdinit=/init root=/dev/ram0
   # 或
   bootargs=... root=/dev/mmcblk0p2 rootwait
   # 但initramfs需要先加载存储驱动模块
```

##### 故障5：启动hang住（无panic）

```
症状: 内核日志输出到某一行后停止，没有panic信息

排查方法:
1. 启用initcall_debug:
   bootargs=... initcall_debug loglevel=8
   → 查看最后打印的initcall，就是hang住的驱动
   
2. 启用打印所有内核线程状态:
   bootargs=... sysrq_always_enabled
   # 然后通过串口发送SysRq触发stack dump
   
3. 使用看门狗:
   bootargs=... watchdog_thresh=10
   # 如果hang住超过10秒，看门狗复位
   # 然后从U-Boot读取复位原因
   
4. 逐步禁用可疑驱动:
   bootargs=... modprobe.blacklist=suspect_driver
   
常见原因:
- 某个驱动probe函数死循环或等待超时
- I2C/SPI通信超时（设备未响应但驱动不断重试）
- 设备树描述与实际硬件不匹配（驱动尝试访问不存在的寄存器）
- 内存不够（某些驱动分配大块连续内存失败）
- 中断风暴（某个设备不断触发中断）
```

#### 6.3 启动故障排查案例

**案例：设备树与实际硬件不匹配导致驱动probe失败**

```
症状: 内核启动到某驱动时hang住约30秒，然后继续但某个外设不工作

排查过程:
1. 启用initcall_debug，发现hang在i2c_imx_probe:
   [   2.345] initcall i2c_imx_driver_init returned 0 after 32456 usecs
   # 32ms是正常的，但前面可能有等待
   
2. 查看dmesg中的I2C相关日志:
   [   1.234] i2c i2c-1: IMX I2C adapter registered
   [   1.235] i2c i2c-1: can't use DMA
   [   1.236] i2c i2c-1: timeout waiting for BUS READY
   # ↑ 这就是hang的原因！
   
3. 检查设备树中的I2C引脚配置:
   &i2c1 {
       pinctrl-names = "default";
       pinctrl-0 = <&pinctrl_i2c1>;
       clock-frequency = <100000>;
       status = "okay";
   };
   
   &iomuxc {
       pinctrl_i2c1: i2c1grp {
           fsl,pins = <
               MX6QDL_PAD_CSI0_DAT9__I2C1_SCL  0x4001b8b1
               MX6QDL_PAD_CSI0_DAT8__I2C1_SDA  0x4001b8b1
           >;
       };
   };
   
4. 发现pinmux错误：
   原理图上I2C1接的是CSI0_DAT8/DAT9，但PCB上因为走线原因
   实际连接的是CSI0_DAT6/DAT7！
   
5. 修正设备树:
   MX6QDL_PAD_CSI0_DAT7__I2C1_SCL  0x4001b8b1
   MX6QDL_PAD_CSI0_DAT6__I2C1_SDA  0x4001b8b1

根本原因: 硬件改版时改了走线，但设备树没有同步更新。
预防措施: 
- 建立设备树版本与PCB版本的对应关系
- 自动化测试检查所有引脚配置
- 硬件改版时必须同步检查设备树
```

> ⚠️ 设备树与实际硬件不匹配是最隐蔽的启动问题之一。设备树中的一个引脚配置错误（如把I2C SCL配成了GPIO，或drive strength不正确）不会导致panic，而是表现为某个外设"偶尔不工作"或"启动变慢"。因为驱动可能会retry多次才放弃。更隐蔽的是，有些引脚错误在常温下工作正常（因为信号裕量充足），但在低温/高温下失败。排查方法是：(1) 对比原理图和设备树的每一个引脚配置；(2) 使用pinctrl工具查看实际引脚状态：`cat /sys/kernel/debug/pinctrl/pinctrl-maps`；(3) 对可疑的驱动添加probe日志。

## 本节总结

启动链设计的第一原则是知道时间花在哪里：五阶段各有典型耗时区间和专属调试方法，未优化基线 3~9 秒、优化后 1.5~3 秒的差距全部来自逐段的针对性裁剪。介质选型贯穿全链路——它同时决定启动速度、可靠性和成本，必须在启动链设计阶段就定下来。
