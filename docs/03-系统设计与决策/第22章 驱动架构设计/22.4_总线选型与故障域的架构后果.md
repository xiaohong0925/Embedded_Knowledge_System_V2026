# 22.4 总线选型与故障域的架构后果

> 所属章节：第22章 驱动架构设计
>
> 难度：[E] | 预计阅读时间：50分钟

## <span class="blue"> 本节导读

22.1~22.3 把驱动的"对内"问题谈完了：放哪、出错怎么办、语义在哪层翻译。本节向外看一层——驱动下面的总线。<BR>
总线选型通常被当成硬件部门的事：速率够不够、引脚够不够、物料便不便宜。但每条总线都是一份**架构合同**，签字（画进原理图）的那一刻，软件就继承了一组义务和限制：选 I2C，你签下的是"一个设备抽风全总线陪葬"的故障域和总线恢复的义务；选 SPI，你签下的是"没有设备发现，一切静态描述"的约束；选 CAN，你得到的是一个被 SocketCAN 优雅接进网络模型的生态；选 USB，你买下的是热插拔和自描述，连同它的复杂度。<BR>
本节覆盖四条总线的架构画像（I2C / SPI / CAN / USB），每条回答三个问题：这条总线的故障域长什么样、它对驱动和拓扑设计施加了什么约束、生态里有什么现成资产。协议的电气细节、时序、寄存器级编程在 B 扩展有系统讲解，本节只在论证需要时取最小片段，节末给出完整指针。

## <span class="blue"> I2C：共享总线就是共享故障域

I2C 的架构本质：**一条总线，两根线，所有设备并联**。这个拓扑决定了它的一切优点（省引脚、地址寻址、多设备）和一个致命的架构后果——**故障域是整条总线**。任何一个从设备异常（固件卡死、电源毛刺、静电击穿）把 SDA 拉低不放，总线上所有设备的通信全部中断。你的温度传感器抽风， EEPROM 和 PMIC 一起失联。

### 后果一：总线恢复是设计项，不是可选项

22.2 已经给过机制和代码：设备树声明 `scl-gpios`/`sda-gpios` 后，I2C 核心在检测到总线挂死时自动把 SCL 切成 GPIO，打 9 个时钟脉冲把从设备状态机推回空闲。这里补它的架构推论：**挂了两个以上设备的 I2C 总线，评审时必须回答"总线恢复能力在哪"**。没有恢复能力的共享总线，等于把最不可靠的那颗芯片的故障率乘以设备数量，摊到整条总线上。

### 后果二：电容预算决定设备数上限

I2C 规范的上升沿靠上拉电阻把总线电容充起来，标准模式要求总线电容 ≤ 400pF。每颗芯片约 10pF，PCB 走线每厘米约 1~2pF，线缆每米 50~100pF——十几个传感器加十几米线缆（22.2 的工业网关场景），预算是会爆的。电容超标的直接后果是上升沿变缓、抗干扰能力下降，表现就是"偶发 NAK、偶发数据错"——22.2 案例里 95% 可用率的病根之一。

架构层面的应对是**分段**：用 I2C 多路复用器（如 PCA9548）把一条总线切成多个段，每段挂少数设备，故障域和电容预算都按段隔离：

```text
&i2c1 {
    i2c-mux@70 {
        compatible = "nxp,pca9548";
        reg = <0x70>;
        #address-cells = <1>;
        #size-cells = <0>;

        i2c_seg0: i2c@0 {        /* 段 0：板内传感器，低电容 */
            reg = <0>;
        };
        i2c_seg1: i2c@1 {        /* 段 1：出线缆的外部传感器 */
            reg = <1>;
        };
    };
};
```

分段之后，段 1 的长线缆故障不再传染板内的 PMIC 和 EEPROM——故障域从"整条总线"收敛到"一个段"。设备树层面每段是独立的 I2C adapter，驱动无感。

### 后果三：地址是稀缺资源，要规划

7 位地址空间只有 112 个可用值，而传感器厂商的地址选择往往只有 2~4 个（一两个地址引脚的高低组合）。同型号两颗传感器上同一条总线就可能撞地址。架构动作：设计期产出一张**地址分配表**，撞车的用 mux 分段或换地址变体解决——这个问题在画原理图时改是一个电阻，量产后再改是一批板子。

## <span class="blue"> SPI：无发现机制的代价是全静态描述

SPI 的架构本质和 I2C 相反：**点对点思维的总线**——没有地址，靠片选（CS）一对一选中；没有应答，主机发出去不知道从机收没收到；没有设备发现，总线上挂了什么全靠事先声明。

### 后果一：设备树是唯一的事实来源

I2C 至少还能 `i2cdetect` 扫一遍看谁在总线上，SPI 连这个都没有——总线上有什么设备、什么型号、什么速率，全部写在设备树里，写错就是驱动 probe 错芯片。SPI 设备的设备树描述是全静态契约：

```text
&spi1 {
    cs-gpios = <&gpio4 26 GPIO_ACTIVE_LOW>,   /* CS0：硬件或 GPIO 皆可 */
               <&gpio4 27 GPIO_ACTIVE_LOW>;   /* CS1：GPIO 扩展 */

    adc@0 {
        compatible = "ti,ads7950";
        reg = <0>;                      /* 用 CS0 */
        spi-max-frequency = <1000000>;  /* 每设备独立限速 */
    };

    flash@1 {
        compatible = "jedec,spi-nor";
        reg = <1>;                      /* 用 CS1 */
        spi-max-frequency = <50000000>;
    };
};
```

### 后果二：CS 管理是拓扑决策

CS 引脚每个设备一根，设备多了 GPIO 不够，两条出路：**译码器**（GPIO 少，选中经 74HC138 译码成多路 CS）或**菊花链**（设备串成一串，数据像水流一样流过每个设备，一个 CS 管全部，常见于多通道 ADC 级联）。菊花链省引脚但把故障域串了起来——链上任何一级坏了，下游全部失联，而且软件必须按链路位置组织数据帧。这个取舍和 I2C 分段的思路同构：**省引脚和故障域隔离是一对永恒的 trade-off**。

### 后果三：速率的免费午餐不存在

SPI 动辄 50MHz、100MHz，看起来比 I2C 快两个数量级。但速率越高对信号完整性越敏感：超过 10~20MHz 后，走线长度、阻抗、串扰都开始咬人，长距离传输基本不可行（22.2 案例里传感器拉出去十几米，SPI 直接出局，这正是 I2C/CAN 存在的理由）。选型时 SPI 的高速只在**板内短距离**成立——"SPI 快"这个认知要带上作用域。

## <span class="blue"> CAN：SocketCAN 为什么被称为完美设计

CAN 的架构故事和其他总线完全不同——它的价值一半在协议本身（差分、仲裁、错误帧、自动重发，B-C 扩展详解），另一半在 Linux 给它的接口形态：**SocketCAN 把 CAN 控制器抽象成了网络设备**。

```bash
ip link set can0 up type can bitrate 500000    /* 像配网卡一样配 CAN */
candump can0                                    /* 像 tcpdump 一样抓帧 */
cansend can0 123#DEADBEEF                       /* 发一帧              */
```

应用层用标准的 socket API 收发 CAN 帧：

```c
int s = socket(PF_CAN, SOCK_RAW, CAN_RAW);     /* 一个 socket 而已 */
struct sockaddr_can addr = { .can_family = AF_CAN,
                             .can_ifindex = if_nametoindex("can0") };
bind(s, (struct sockaddr *)&addr, sizeof(addr));

struct can_frame frame = { .can_id = 0x123, .len = 2,
                           .data = {0x11, 0x22} };
write(s, &frame, sizeof(frame));               /* 发送 */
read(s, &frame, sizeof(frame));                /* 接收 */
```

这个设计的优雅之处在于**复用**：CAN 设备自动获得网络栈的全部基础设施——多进程共享访问（socket 各自开）、按 ID 过滤（内核态过滤，应用只收关心的帧）、虚拟 CAN（vcan，没有硬件也能开发测试）、Wireshark 抓包、`ip -details -statistics link show can0` 查总线错误计数（bus-off、错误被动状态全在里面）。对比之下，一个私有字符设备接口的 CAN 驱动要自己实现队列、过滤、多路复用——SocketCAN 证明的命题是：**把新总线映射到内核已有的成熟模型，几乎永远优于发明私有接口**。这个命题在 22.3 的"进子系统"决策里出现过，在 CAN 这里得到了最极端的正例。

对驱动架构的直接后果：写 CAN 应用不需要"CAN 驱动工程师"，任何会 socket 编程的人都能上手；总线错误处理（bus-off 恢复）由内核的 CAN 网络设备框架统一提供，应用订阅 `NETLINK_ROUTE` 事件即可感知总线健康——22.2 的四级错误模型在 CAN 上是基础设施自带的。

## <span class="blue"> USB：复杂度换来的两个超能力

USB 是四条总线里最复杂的（协议栈分层的厚度超过其他三条之和），但它的复杂度买到两个架构级超能力：

**超能力一：热插拔与自描述。** 每个 USB 设备插入时主动上报描述符（厂商 ID、产品 ID、设备类、端点布局），内核按描述符自动匹配驱动——不需要设备树，不需要人工声明。IoT 场景的 4G 模块走 USB，获得的即插即用就是这个机制。22.2 讲的热插拔三纪律（probe 可重入、remove 安全失败），在 USB 上是日复一日的现实而非边缘场景。

**超能力二：设备类的标准化。** USB 定义了设备类规范：串口（CDC-ACM）、存储（MSC）、网卡（CDC-ECM/RNDIS/…）、音频（UAC）、摄像头（UVC）。符合类规范的设备不需要厂商专用驱动——这就是"4G 模块插上就出 `/dev/ttyUSB*` 或 `wwan0`"的原因。架构含义：**选 USB 接口的模块时，优先选走标准设备类的型号**，私有协议的 USB 模块意味着厂商驱动的维护债（内核升级时它会不会编过，是每次内核升级都要还一次的钱）。

4G/5G 模块还有一层协议资产：QMI/MBIM 是调制解调器的标准控制协议，用户态有 ModemManager 完整封装（22.3 的 D-Bus 服务形态实例）。数据面走 USB 网卡类，控制面走 QMI/MBIM——这个"双通道"结构是行业标准做法，自己发明私有 AT 指令通道是已知的弯路。

## <span class="blue"> 选型收束：四条总线的架构画像对照

| 维度 | I2C | SPI | CAN | USB |
|------|-----|-----|-----|-----|
| 故障域 | **整条总线共享**（分段可收敛） | 单 CS 一域；菊花链串联故障 | 总线共享，但协议自带错误界定与 bus-off 恢复 | 单设备为主，hub 层级隔离 |
| 发现机制 | 地址 + 可扫描 | **无，全静态设备树** | 无（帧 ID 语义化） | **完整自描述，热插拔** |
| 距离 | 板内；分段+缓冲可出板 | 板内短距，高速更短 | 百米级差分，工业现场主力 | 数米， hub 扩展 |
| 速率量级 | 100k~3.4MHz | 10~100MHz（板内） | 125k~1MHz（FD 到 5M 数据段） | 480Mbps 起 |
| 引脚成本 | 2 根 | 3 + 每设备 1 CS | 2（加收发器） | 2 差分 |
| 生态资产 | regmap / IIO 大量传感器 | spi-nor / 高速 ADC | **SocketCAN + can-utils** | 设备类驱动 + ModemManager |

IoT 平台场景过一遍这张表：温湿度传感器（低速、板外、要多点）→ I2C 分段；加速度计（高速采样、板内）→ SPI；4G 模块（热插拔、标准化）→ USB；如果平台将来进工业现场接执行器（长线、抗扰、多主）→ CAN。每个选择背后都是一行"架构合同条款"，而不是一句"这个常用"。

## <span class="blue"> 深入指针

本节的每条总线只讲了架构层，协议层与实战层在 B 扩展成体系展开：

- **I2C**：时序与电气细节、上拉电阻计算、总线恢复的波形级原理 → B 扩展 I2C 系列（物理层 / 协议层 / 调试实战）
- **SPI**：四种 mode 的 CPOL/CPHA 细节、高速布线规则 → B 扩展 SPI 系列
- **CAN**：帧格式、仲裁与错误界定状态机、CAN FD、CANopen/J1939 上层协议 → B 扩展 CAN 系列
- **USB**：描述符结构、传输类型（控制/批量/中断/等时）、USB 3.x 与 Type-C → B 扩展 USB 系列

阅读建议：本节定选型，B 扩展对应篇定实现；调试现场先回 B 扩展的调试篇，查不出问题时回本节检查"是不是总线选型本身欠的债"。

## <span class="blue"> 本节总结

总线选型是一份架构合同：I2C 的合同条款是共享故障域（总线恢复必选、mux 分段收敛、400pF 电容预算、地址规划）；SPI 的条款是无发现机制（设备树全静态契约）加 CS 拓扑权衡（译码器省引脚、菊花链串故障域）加"高速只在板内成立"的作用域；CAN 是反方向的范本——SocketCAN 把它映射成网络设备，白拿 socket API、内核过滤、vcan、统计与 bus-off 恢复，证明了"映射到成熟模型优于私有接口"；USB 用复杂度换自描述热插拔与设备类标准化，4G 模块的 QMI/MBIM + ModemManager 是行业标准姿势。选型的正确姿势是按故障域、发现机制、距离、速率作用域、生态资产逐项对照，而不是按"哪个常用"。总线之下再无更底层，下一节上探到驱动架构的极限场景：多媒体——多个子系统协同搬运数据时，架构问题会以带宽和延迟的形式重新出现。

### 速查表

| 问题 | 一句话答案 |
|------|-----------|
| I2C 的最大架构风险？ | 共享故障域：一个设备拉死 SDA，全总线瘫痪 |
| I2C 设备多了怎么办？ | PCA9548 类 mux 分段：故障域与电容预算按段隔离 |
| SPI 的设备从哪来？ | 无发现机制，设备树是唯一事实来源，写错即 probe 错芯片 |
| SPI 菊花链的代价？ | 省 CS 引脚，但故障沿链串联，数据帧须按链路位置组织 |
| SocketCAN 优雅在哪？ | CAN 映射为网络设备，白拿 socket/过滤/vcan/统计/bus-off 恢复 |
| USB 选型铁律？ | 优先走标准设备类（CDC/UVC/UAC…），私有协议 = 厂商驱动维护债 |
| 4G 模块标准接法？ | USB 数据面 + QMI/MBIM 控制面 + ModemManager 封装 |
