# 第22章：驱动架构设计

> 所属：第 三 部 系统设计与决策
>
> BIEM：[E] | 核心问题：怎么设计"硬件变更时影响范围最小"的驱动层？

## 核心问题

不是"驱动怎么写"——那是第 10/11 章（机制）和 D 篇（写法）已经回答过的问题。本章回答的是：**给你一组外设、一条五年的产品线演进预期和一堆现场约束，怎么设计驱动层的整体结构，使得换一颗传感器、换一块板卡、换一家 SoC 供应商时，改动被锁进最小的舱室里。**

## 为什么需要这一章

第 17 章的风险形态是失效滞后，第 18 章是债务滞后，驱动架构的风险形态是**耦合滞后**：驱动代码单独看每个都"能跑"，接口的腐烂在平时的功能测试里完全不可见——直到某一天硬件换代。换一颗传感器，发现换算公式散落在五个应用里；换一块板卡，发现 GPIO 编号硬编码在驱动中；换一家 SoC，发现驱动和板级代码长在一起。耦合在写字的那天免费，在改动的那天收全款。

有经验工程师通常已经写过字符设备驱动、用过 regmap、调通过 I2C。但"会写驱动"和"会设计驱动架构"之间的问题不会自动有答案：同一颗触摸屏，放内核还是用户态，量化依据是什么？现场偶发的 I2C 错误，重试、复位、上报各做到什么程度？八款产品共享的驱动层，抽象应该放在内核子系统还是用户态库？选 I2C 还是 SPI 的时候，签下的故障域是什么？4 路摄像头同时开，DDR 带宽账算过吗？

## 本章主线：五个决策域，一次合流

本章的核心洞察是大纲的原话：**好的驱动架构不是让单个驱动更好，而是让驱动之间的关系更清晰**。"关系"具体落在四处：错误的语义、电源的依赖、抽象的层次、总线的故障域。

```
22.1 驱动放置：用户空间 vs 内核的量化决策
  六位置光谱；四条否决线（延迟/中断频率/PM/DMA）
  两阶段迁移：用户态探针 → 冻结 → 内核化
        │
        ▼
22.2 三条路径 ────> 22.3 HAL 放在哪 ────> 22.4 总线选型 ────> 22.5 多媒体 pipeline
  正常：可被打断      内核子系统            故障域即合同          拓扑与零拷贝
  错误：L1~L4 分级   用户态 HAL 库         I2C 分段/电容预算     V4L2 vs libcamera
  电源：依赖图/唤醒   D-Bus 服务           SocketCAN 范本        DMA-BUF 与带宽预算
        │                                                             │
        └──────────────────────────┬──────────────────────────────────┘
                                   ▼
              22.6 综合实战：IoT 平台五类外设过堂
                   + 三代硬件时间轴演练 + 三案例复盘 + 20 项评审清单
```

贯穿全章的场景：一个 IoT 硬件平台，5 年 3 代硬件演进，五类外设（I2C 温湿度、SPI 加速度计、USB 4G、I2C+IRQ 触摸屏、MIPI CSI 摄像头），电池供电、热插拔、错误可感知。22.1~22.5 各自回答它的一类问题，22.6 把五类外设逐个过堂，并用"第 2 代换传感器、第 3 代换 SoC"两道时间轴考题验收架构。

学习方案按手头情况二选一：

- **手头有项目**：读 22.1 时给自己产品的每个外设走一遍决策树并记录路径，22.2 读完画出电源依赖图和唤醒源表，22.6 的 20 项清单直接当评审自查表用。
- **手头没项目**：跟住 IoT 平台场景。22.6 会把 22.1~22.5 的每件工具调用一次，包括"4G 模块零自研驱动""触摸屏不加库""摄像头不上零拷贝"这三个否决型裁决——识别"不需要做什么"是架构能力的一半。
