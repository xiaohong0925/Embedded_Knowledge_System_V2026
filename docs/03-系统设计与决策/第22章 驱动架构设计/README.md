## 核心问题

驱动架构怎么设计？

## 本章简介

“怎么设计可维护的驱动层？怎么抽象硬件差异？” 驱动层是嵌入式系统中耦合度最高、最容易产生技术债务的部分。一个产品的驱动代码通常占内核代码的30-50%，且直接绑定特定硬件。当硬件升级、供应商变更或产品迭代时，驱动层的僵化架构会让迁移变成噩梦。本章的目标是让你设计出”硬件变更时影响范围最小”的驱动架构，并在用户空间和内核空间之间做出正确权衡。

有经验工程师通常已经写过简单的字符设备驱动、用过regmap框架、会调试I2C通信。

但当你面临以下架构级问题时，“会写驱动”和”会设计驱动架构”之间有巨大差距：产品需要支持3款不同厂商的触摸屏（互换而不改应用层代码），怎么做抽象？一个传感器驱动在实验室工作正常，到现场偶发数据错误——怎么设计错误恢复机制？设备需要支持runtime suspend/resume，但驱动和5个子系统都有电源管理交互，怎么避免死锁？多媒体pipeline需要同时处理camera→ISP→GPU→display的数据流，怎么设计零拷贝路径？本章的核心洞察是：好的驱动架构不是让单个驱动更好，而是让驱动之间的关系更清晰。

你正在设计一个IoT硬件平台的驱动框架，该平台计划支持5年，预计会有3代硬件演进。当前一代有：温度/湿度传感器（I2C）、加速度计（SPI）、4G模块（USB）、触摸屏（I2C+IRQ）、摄像头（MIPI CSI）。需求：每代硬件可能更换传感器型号（但保持接口兼容），驱动需要支持热插拔（4G模块），所有外设需要电源管理集成（电池供电），错误需要被上层感知和处理。

你会怎么组织驱动代码？抽象层放在内核还是用户空间？错误恢复怎么做？电源管理和驱动的交互怎么设...
