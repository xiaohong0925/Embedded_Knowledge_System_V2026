# 第17章：存储架构设计

> 所属：第 三 部 系统设计与决策
>
> BIEM：[E] | 核心问题：一套存储方案怎么设计出来，并被证明是对的？

## 核心问题

不是"存储介质和文件系统怎么选"——那是第 12 章和第 16 章已经回答过的问题。本章回答的是：**给你一块板子的存储预算和一组产品约束，怎么从零推导出一整套存储架构，并且拿得出证据证明它是对的。**

## 为什么需要这一章

存储架构是嵌入式系统中最容易设计失误的部分——不是因为技术难，而是因为**决策后果滞后显现**。失效按四波到来：分区缺陷在产线暴露，断电损坏在量产半年后出现，介质磨损在一两年后爆发，分区撑爆在两三年后随 OTA 到来。开发期的功能测试天然覆盖不到任何一波——失效由"时间 × 次数"驱动，开发期两头都不够。

更棘手的是锁死节奏：介质在原理图评审时锁死，分区表在产线导入时锁死，文件系统与挂载参数在首批发货时锁死。等问题暴露时，每一个决策都已过了低成本修改窗口。所以存储架构必须在设计期定量决策——这正是本章训练的能力。

有经验工程师对文件系统不陌生：你知道 ext4、听过 UBIFS、可能用过 SquashFS。但面对一个真实产品时，这些问题不会自动有答案：每天 100MB 日志打在 8GB eMMC 上，五年寿命够不够（答案反直觉）？消费级和工业级 eMMC 数倍的价差，买到的到底是什么？A/B 分区和原地更新的断电安全性差异怎么量化？分区大小预留多少才能撑过五年 OTA？断电保护做到什么程度算够、又怎么证明够？

## 本章主线：一个方法论，四个决策域，一次合流

本章的核心洞察是：**存储架构设计不是选文件系统，而是设计一个数据生命周期管理系统**——每类数据有不同的写入频率、持久化要求和恢复策略，把它们分类定量之后，介质、文件系统、分区、断电防护四个决策域各自变成一个可计算的问题。

```
17.1 方法论：数据生命周期分类
  每类数据过三问：写多勤？丢不丢得起？坏了怎么救？
  输出物：存储需求清单（五个可计算的问题）
        │
        ▼
17.2 介质决策 ──> 17.3 文件系统决策 ──> 17.4 分区架构 ──> 17.5 断电安全
  寿命够不够             断电后坏成什么样        只读 rootfs 布局      防到什么程度 + 怎么验证
  黑盒信不信             EROFS 时代选型         大小预留与配额        代价量化与测试设计
  2026 还要不要 eMMC     故障模式视角           eMMC 硬件分区         样本量倒推
        │                                                             │
        └──────────────────────┬──────────────────────────────────────┘
                               ▼
              17.6 综合实战：四域合流走查（会发现一处真实的账算不平）
                   + 三案例复盘 + 16 项评审清单
```

贯穿全章的场景：户外工业网关，-40°C~85°C，8GB eMMC，每天 100MB 日志，设计寿命 5 年，每天可能断电数次，OTA 必须可回滚。17.1 用它演练分类法，17.2~17.5 各自回答它的一类问题，17.6 把全部结论合流成一份可签字的方案。

学习方案按手头情况二选一：

- **手头有项目**：读 17.1 时同步做自己产品的数据分类表，之后每读一节，把对应决策域的结论写进自己的设计文档。读完 17.6 时你应该已经攒出一份能过评审的方案初稿。
