# 20.1 实时需求评估：硬实时、软实时，还是根本不需要

> 所属章节：第20章 实时性设计
>
> 难度：[E] | 预计阅读时间：25 分钟

## <span class="blue">本节导读

"我们的产品需要实时吗？"——这是实时性设计的第一个问题，也是最常被答错的问题。答错的代价在两个方向上都很贵：给不需要实时的系统上了 Xenomai 双内核，开发和维护成本翻倍，换来客户感知不到的价值；给真的需要硬实时的系统用了普通 Linux，产品在客户现场以"偶发卡顿"的形式暴露问题，而这种 bug 几乎无法复现和调试。

答错的根源是一个普遍的误解：**实时 = 快**。实际上实时 = **确定性**——不是平均多快，而是最坏情况下能不能在截止时间前完成。一个平均响应 50μs 但偶尔跳到 50ms 的系统是快而不实时；一个每次都稳定 500μs 响应的系统才是实时——尽管它慢了十倍。几乎所有"感觉需要实时"的争论，把这句话讲透就消失了一半。

另一半靠测量消失。本章的方法论从第一节就立下：**先测量，再决策**。大多数声称"需要硬实时"的系统，在真实负载下用 cyclictest 量一遍之后，会发现 PREEMPT_RT 甚至普通 Linux 已经足够——20.2 的方案选择必须以本节的量化结论为输入，拍脑袋选的实时方案一定错配。

> 本节覆盖：实时的正确定义（确定性/WCET）、硬实时/软实时/非实时的分级判据、延迟需求的三要素量化法（截止时间/抖动/可容忍 miss 率）、"感觉是实时需求"的五种伪需求、cyclictest 测量的正确姿势。读完产出一份实时需求规格——它是 20.2 决策树的输入。

## <span class="blue">实时的定义：确定性，不是速度

把定义钉死再往下走：

> 实时系统（Real-time System）：结果的正确性不仅取决于计算的逻辑值，还取决于结果产生的时间——**在截止时间之前完成才算正确，迟到的正确答案等于错误答案**。

定义里的关键推论是"正确性的判据是时间"，这直接引出实时工程的核心概念 **WCET（Worst-Case Execution Time，最坏情况执行时间）**：一个任务在最不利条件下的执行时间上限。实时系统的设计目标不是优化平均值，而是**压低并证明 WCET**——平均值漂亮没有意义，第 99.99 百分位的那个尖峰才会让电机失控、让音频爆音。

"快"和"确定性"经常冲突，这是新手最难接受的点：cache 让平均访问快十倍，但 miss 时的不确定性也放大十倍；动态内存分配平均很快，但分配器在最坏情况下的耗时无界；Linux 的公平调度让吞吐最大化，恰恰意味着任何单个任务的延迟不保证。**普通 Linux 的每一个性能优化，几乎都是用确定性换吞吐**——实时改造的本质就是逐一把这些交换谈回来。

## <span class="blue">三级分类与判据

| 级别 | 判据 | 超时后果 | 典型场景 | 方案候选 |
|------|------|---------|---------|---------|
| 硬实时 | WCET 必须 ≤ 截止时间，**数学上可证明** | 系统失效：设备损坏、人身危险 | 电机控制环、安全回路、PLC 扫描周期 | Xenomai/RTOS/双系统（20.2） |
| 软实时 | 截止时间是设计目标，**偶发超时允许但可统计** | 质量下降：音频爆音、视频掉帧 | 音频处理、视频流、EtherCAT 主站、运动轨迹 | PREEMPT_RT |
| 非实时 | 只有平均性能要求 | 用户等一等 | HMI、日志、网络管理 | 普通 Linux |

判据的关键不在延迟数字的大小，在**超时后果的严重度**。一个常见的误判是按数字分："1ms 以内就是硬实时"——错。1ms 的音频周期是软实时（超时=爆音，难听但无害）；100ms 的急停响应是硬实时（超时=伤人）。先问"超时了会怎样"，再看数字。

还有一个值得记住的工程常识：**截止时间越紧，方案越贵，而且贵得非线性**。从 10ms 压到 1ms，PREEMPT_RT 加调优通常够；从 1ms 压到 50μs，就要评估 Xenomai 或双系统；压到 10μs 以下，答案几乎一定是"别用 Linux 做这件事"——把这部分功能卸载到 MCU/FPGA（20.2 的 offload 路线）。需求评审时把这条成本曲线拍在桌上，很多"客户说要硬实时"会被重新谈判。

## <span class="blue">延迟需求的量化三要素

"要实时"不是一个规格。把它变成规格需要三个数，缺一不可：

**截止时间（deadline）**：任务从触发到完成允许的最大时间。注意定义清楚两端——从"中断线电平变化"开始算，还是从"数据到达网卡"开始算？到"GPIO 翻转"结束，还是到"数据发出"结束？端点定义不同，数字差一个数量级。

**抖动（jitter）**：周期的稳定性要求。音频 48kHz 采样要求每 20.8μs 处理一个块，平均周期对了但相邻周期忽长忽短，听感照样是坏的——所以对周期任务，"每次间隔的偏差范围"和"截止时间"是两个独立的数。

**可容忍 miss 率**：允许多大比例的任务实例超时。硬实时是 0（可证明的 0，不是"测试没遇到"）；音频可能容忍每小时一次爆音；EtherCAT 从站同步可能容忍 10⁻⁶ 的周期丢失。这个数决定了测试要多长——声称 10⁻⁶ 的 miss 率，至少要跑 10⁷ 次以上的测量才有统计意义。

```text
成稿示例（工业机器人关节控制器的一条实时需求）：
  任务：电流环控制
  触发：ADC 采样完成中断（每 62.5μs，16kHz）
  截止时间：中断触发到 PWM 更新 ≤ 20μs
  抖动：连续 1 小时内，周期偏差 ≤ ±2μs
  miss 率：0（硬实时，超时=扭矩指令错误）
  → 结论：Linux 用户态方案出局，归 MCU/Xenomai 域
```

## <span class="blue">五种伪实时需求

评审会上"需要实时"的呼声里，至少有五种其实不是：

**"数据量大所以实时"。** 吞吐需求不是延迟需求——4K 视频流带宽巨大，但缓冲几百毫秒完全可接受。要的是吞吐工程（DMA、零拷贝），不是实时。

**"用户觉得卡"。** 交互流畅的目标是 60fps 和响应 <100ms，这在普通 Linux 上是性能调优问题（调度器、内存、IO 优化），不是实时问题。

**"通信协议要求"。** "EtherCAT 所以必须实时"——主站周期的确定性要求其实落在主站实现和网卡路径上，多数场景 PREEMPT_RT 足够（B-E.15.3 的人形机器人全身 EtherCAT 就是 RT 方案）；真正硬实时的部分是 FPGA/从站硬件承担的。

**"采样率高所以实时"。** 高速采集靠 DMA 和环形缓冲把数据搬走，CPU 的响应延迟被硬件吸收——JESD204C 采集系统（B-F.16.4）的 CPU 侧从来不是硬实时任务。

**"客户说要实时"。** 客户说的是现象（"你们的系统偶尔会顿一下"），不是需求。用三要素反问他：哪个任务、什么截止时间、超时会怎样——答不上来的"实时需求"按软实时以下处理，先测量。

## <span class="blue">cyclictest：把"感觉"变成数字

怀疑系统有实时问题、或要验证"普通 Linux 够不够"，标准测量工具是 **cyclictest**（rt-tests 包）：它以指定周期唤醒一个高优先级线程，记录每次实际唤醒时刻与预期时刻的偏差，跑上几个小时，输出延迟分布——重点看**最大值**，那就是你的 WCET 实测下界。

```bash
# 四核满负载下的经典测量姿势
stress-ng --cpu 4 --io 4 --vm 2 &          # 先制造系统压力（空载测的延迟没意义）
cyclictest -m -p 99 -i 1000 -l 10000000    # 1ms 周期、SCHED_FIFO 99、一千万次、锁定内存
```

判读输出只有一行关键：`Max Latencies: 12 15 11 234`——前三个核的峰值在十几微秒，第四个核冒出 234μs。这个分布本身就是诊断信息：单核异常指向该核上的中断或驱动问题（20.3 的归因），全核普涨指向全局因素（SMM、电源管理、内存带宽争抢）。

> 💡 测量纪律三条：必须带负载测（空载延迟是自欺）；必须够长（声称的 miss 率决定时长，10⁷ 次起步）；必须覆盖工况（温度、CPU 频率切换、网络流量高峰都要进测试矩阵）。在实验室空载下测出的"我们延迟只有 20μs"，到客户现场会变成事故报告的标题。

## <span class="blue">方案对比（Trade-off）

| 维度 | 评价 |
|------|------|
| 按数字分级 vs 按后果分级 | "1ms 内=硬实时"是误读；超时后果（失效 vs 质量下降）才是判据 |
| 优化平均值 vs 证明 WCET | 普通 Linux 的每个优化都用确定性换吞吐；实时工程是逆向谈判 |
| 需求写"要实时" vs 三要素 | 前者无法设计无法验收；三要素齐了方案空间自然收敛 |
| 空载短测 vs 带载长测 | 前者是自欺，后者是规格；测试时长由声称的 miss 率决定 |
| 软件硬扛 vs 卸载 MCU/FPGA | <10μs 级需求软件路线成本非线性爆炸，卸载几乎总是对的 |

## <span class="blue">本节总结

实时 = 确定性不是快：正确性的判据是时间，设计目标是压低并证明 WCET，而普通 Linux 的每个性能优化都在用确定性换吞吐。分级看超时后果不看数字大小——1ms 的音频是软实时，100ms 的急停是硬实时。需求必须用三要素量化（截止时间/抖动/可容忍 miss 率），端点定义要钉死；"要实时"不是规格，三要素齐了方案空间自然收敛。五种伪需求（数据量大/觉得卡/协议要求/采样率高/客户说要）各归各的真实解法。测量是唯一裁决者：cyclictest 带负载、够时长、覆盖工况，看最大值不看平均值——20.2 的方案决策树只接受这种量化输入。

关键结论速查：

| 问题 | 一句话答案 |
|------|-----------|
| 实时的定义 | 在截止时间前完成才算正确；迟到的正确答案=错误答案 |
| 实时工程的目标 | 压低并证明 WCET，不是优化平均值 |
| 硬/软实时的分界 | 超时后果：系统失效 vs 质量下降，与数字大小无关 |
| 需求三要素 | 截止时间（端点钉死）/抖动/可容忍 miss 率 |
| 普通 Linux 的本质 | 每个性能优化都用确定性换吞吐 |
| 最常见的伪需求 | "客户说要实时"——用三要素反问 |
| 测量工具与纪律 | cyclictest：带负载、10⁷ 次起步、看 Max 不看 Avg |
| <10μs 需求的答案 | 卸载 MCU/FPGA，别让 Linux 硬扛 |
