# 20.2 实时方案决策树：PREEMPT_RT、Xenomai、双系统与卸载

> 所属章节：第20章 实时性设计
>
> 难度：[E] | 预计阅读时间：25 分钟

## <span class="blue">本节导读

20.1 给了你量化的需求规格。这一节把它变成技术选型。Linux 生态的实时路线有四条，各自的确定性天花板、开发成本、生态健康度完全不同：

- **PREEMPT_RT**：给标准内核打实时补丁，把"几乎处处可抢占"做到底
- **Xenomai**：双内核——Linux 旁边跑一个实时微核，实时任务归微核管
- **双系统/AMP**：Linux 管富功能，独立 MCU/RTOS 管实时，物理分割
- **MCU/FPGA 卸载**：干脆不让 Linux 碰实时任务

选错的典型剧本是"按二十年前的文章选了 Xenomai"——2026 年的格局和这些文章写作时已经完全不同：PREEMPT_RT 补丁在 2024 年随 6.12 LTS **全量并入主线内核**，结束了长达二十年的"外挂补丁"时代，这个事件直接改写了决策树的形状。本节的决策树按当前生态现状画，每条路线都给天花板数字、真实成本和选型边界。

> 本节覆盖：四条路线的机制一句话、PREEMPT_RT 进主线的选型含义、各路线延迟天花板对照、按三要素收敛的决策树、生态健康度评估（为什么这是决策的一部分）。

## <span class="blue">四条路线的机制一句话

**PREEMPT_RT：把 Linux 自己变成 RTOS。** 主线 Linux 里有三类"不可抢占区"会制造延迟尖峰：自旋锁临界区、中断处理、软中断。RT 补丁的三板斧：自旋锁换成可睡眠的 rtmutex（持锁也能被抢占）、中断处理线程化（IRQ handler 变成可调度线程，高优先级实时任务可以抢占它）、软中断线程化。改完之后的内核，高优先级任务的 WCET 有了上界——这就是它"够用"的机理。

**Xenomai：Linux 降级为实时微核的客人。** 在硬件和 Linux 之间插一层实时微核（Cobalt），中断先经过微核：实时中断微核直接处理，普通中断才转给 Linux——Linux 整体变成微核调度的一个低优先级任务。实时应用跑在微核上，用它的原生 API（或 POSIX 皮肤），WCET 压到微秒级。代价：实时任务不能用 Linux 的系统调用（进 Linux 域就失去确定性），驱动要双份，编程模型分裂。

**双系统/AMP：物理隔离。** SoC 里的 Cortex-M 核或独立 MCU 跑 RTOS/裸机承载实时任务，A 核跑 Linux，经 RPMsg/共享内存通信。和 19.5 的混合关键性分割是同一个架构——实时性和功能安全在这里共享同一个答案：**让关键任务不依赖 Linux**。

**卸载：实时任务根本不在 CPU 上。** 电机电流环进 FPGA、EtherCAT 从站进专用芯片、高速采集进 DMA——CPU 只发参数和收结果。延迟需求紧到 10μs 以下时，这不是选项而是必然。

## <span class="blue">天花板对照与真实成本

| 路线 | WCET 天花板（典型平台实测量级） | 开发成本 | 编程模型 | 生态现状（2026） |
|------|------------------------------|---------|---------|-----------------|
| 普通 Linux | ms 级且无界 | 零 | 标准 Linux | 主线 |
| PREEMPT_RT | **几十~一百 μs 级** | 低：应用无需修改，调优为主 | 标准 Linux+优先级 | **已全量入主线（6.12 LTS），发行版直接提供** |
| Xenomai | **几~十几 μs 级** | 高：双域编程、驱动双份、应用改写 | 微核 API/POSIX 皮肤 | 社区萎缩，商业支持（Xenomai 4/EVL）续命 |
| 双系统/AMP | μs 级（RTOS 保证） | 中高：双固件、IPC、生命周期管理 | RTOS+Linux 两套 | 工业主流，SoC 厂商 BSP 成熟 |
| 卸载 MCU/FPGA | ns~μs 级（硬件保证） | 高：异构开发 | 硬件逻辑/MCU 固件 | 随需求分布 |

读表的两个要点。**天花板不是唯一轴**：PREEMPT_RT 的"几十微秒"对音频（20μs 周期）不够，对 1ms 控制环（需求 100μs）绰绰有余——够用与否永远相对 20.1 的三要素而言。**生态健康度是决策变量**：Xenomai 的天花板最漂亮，但社区萎缩意味着内核升级要等项目跟版、新 SoC 支持要看运气、招人会的人少——技术债以年计复利。PREEMPT_RT 进主线后，"打补丁、维护补丁集"的成本项消失了，这是它成为默认答案的直接原因。

> 💡 PREEMPT_RT 进主线的实际含义：`CONFIG_PREEMPT_RT` 现在就是标准内核的一个配置项，Debian/Ubuntu 等发行版直接提供 -rt 内核包。你的产品内核从"自己维护一套补丁"变成"打开一个开关"——这件事把 RT 的采用成本砍了一个数量级，也把"要不要上 RT"的决策门槛降到"为什么不呢，反正零边际成本"。决策问题从"上不上 RT"变成"RT 够不够，不够往哪走"。

## <span class="blue">决策树：按三要素收敛

```text
实时需求三要素在手（20.1）
   │
   ▼ 截止时间 ≥ 1ms 且 miss 率允许 ppm 级？
   │         ├─ 是 → PREEMPT_RT（零应用改造成本，先上再调）
   │         │        │
   │         │        ▼ cyclictest 实测 WCET 满足？
   │         │              ├─ 满足 → 定型，进 20.3 预算表固化
   │         │              └─ 差 2~3 倍 → 20.3 调优后复测；差一个数量级 → 往下走
   │         │
   ▼ 截止时间 10μs~1ms 且 miss 率 = 0？
   │         ├─ 有 MCU/M 核可用 → 双系统/AMP（工业主流，安全侧顺带解决）
   │         └─ 无 MCU、必须单系统 → Xenomai（评估生态成本后上车）
   │
   ▼ 截止时间 < 10μs？
             └─ 卸载 FPGA/MCU，别犹豫——软件路线在此区间成本非线性爆炸
```

决策树的三个使用纪律。**从便宜的路线开始验证**：PREEMPT_RT 零边际成本，永远是第一个试的——实测够了就是终局，不够的数据（差多少、差在哪）还是下一步决策的输入。**miss 率 = 0 的硬实时慎选 Linux 域方案**：RT 的 WCET 是"工程上界"不是"数学证明"，要求可证明的 0 就上 RTOS/双系统（19.5 的安全场景同理）。**把生态成本写进决策记录**：选 Xenomai 时明确记录"接受社区萎缩风险，备付商业支持预算"——两年后内核升不上去时，这份记录能区分失策和已评估的取舍。

## <span class="blue">每种路线的典型踩坑

**PREEMPT_RT**：以为打开 CONFIG 就完事——不，RT 只是给了你调优的资格。IRQ 亲和性没绑、CPU 没隔离、电源管理没关（CPU 频率切换和 C-state 进出都是几十微秒的延迟源）、应用优先级没设，实测和没打补丁一样。20.3 就是讲这套调优的。

**Xenomai**：低估双域编程的摩擦——实时任务调了一个普通 Linux 库函数（printf 进日志也算），就滑出实时域（mode switch），当次任务的确定性报废。排查这类"偶发超时"极其痛苦，因为代码看起来什么都没做错。

**双系统**：低估系统级复杂度——双固件版本同步、启动顺序、共享内存的一致性、Linux 侧崩溃时 MCU 侧的安全态，每一项都是嵌入式系统工程，不是"再写个小固件"那么轻松。

**卸载**：接口设计没想清楚就动手——参数下发和结果回传的协议、时标同步（硬件时间戳 vs Linux 时间）、异常恢复，这些决定了卸载方案是可维护的还是一次性的。

## <span class="blue">方案对比（Trade-off）

| 维度 | 评价 |
|------|------|
| RT vs Xenomai | 够用即 RT（零改造+主线生态）；只有硬 μs 级且无 MCU 才值得 Xenomai 的双域成本 |
| RT vs 双系统 | 单系统简单 vs 物理隔离的确定性+安全分割红利；有 M 核时双系统常是更优总账 |
| Xenomai vs 双系统 | 天花板相近；Xenomai 省一颗核但押注萎缩社区，双系统押注成熟 BSP——2026 年后者胜率大 |
| 卸载 vs 任何软件方案 | <10μs 区间卸载几乎必胜；代价是异构开发与接口设计的系统复杂度 |
| 跟随主线 vs 锁定版本 | RT 进主线后跟版成本低；任何外挂路线都要把"内核升级谁负责"写进决策 |

## <span class="blue">本节总结

2026 年的实时选型被一件事改写：PREEMPT_RT 随 6.12 LTS 全量进主线，采用成本从"维护补丁集"变成"打开配置项"，它因此成为所有实时问题的默认第一试——实测够用就是终局。决策树按三要素收敛：1ms 级以上软实时走 RT；10μs~1ms 硬实时优先双系统/AMP（有 MCU 时总账最优），无 MCU 才考虑 Xenomai（并把社区萎缩写进决策记录）；10μs 以下直接卸载 FPGA/MCU。每条路线的天花板数字要和 20.1 的三要素对照着读，"够用"永远相对需求而言；每种路线的典型踩坑（RT 不调优、Xenomai 模式切换、双系统生命周期、卸载接口设计）在选型时就该列入风险清单。下一节 20.3 讲选定 RT 之后的事：延迟预算怎么拆、逐项怎么调。

关键结论速查：

| 问题 | 一句话答案 |
|------|-----------|
| 2026 年实时选型的默认起点 | PREEMPT_RT——已入主线，零边际成本先试 |
| RT 的 WCET 天花板 | 几十~一百 μs 级（工程上界，非数学证明） |
| Xenomai 的两张账单 | 双域编程摩擦 + 社区萎缩的生态债 |
| 硬实时（miss=0）的首选 | 双系统/AMP——确定性可证明，还顺带解决安全分割 |
| <10μs 的唯一答案 | 卸载 FPGA/MCU，软件路线成本非线性爆炸 |
| RT 打开后最常见的误会 | 以为 CONFIG 一设就完事——不调优等于没打 |
| 决策记录必须写的一条 | 外挂路线的内核升级责任与生态风险 |
