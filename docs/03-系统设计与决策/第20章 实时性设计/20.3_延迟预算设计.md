# 20.3 延迟预算设计：从中断到响应的全链路拆解

> 所属章节：第20章 实时性设计
>
> 难度：[M] ~ [E] | 预计阅读时间：40 分钟

## <span class="blue"> 本节导读

选定 PREEMPT_RT（选型决策见 20.2）之后，工作才真正开始。RT 内核给你的不是"实时"，而是**调优的资格**：它消灭了内核里最大的不可抢占区，但从中断触发到应用响应的五段链路上，每一段都藏着多个延迟源。不对这些环节做预算分配和逐项调优，实测出来的 WCET 和没打补丁差不多。

> WCET（Worst-Case Execution Time，最坏情况执行时间）：一条链路在所有可能条件下的耗时上限。实时保证只对 WCET 负责，平均值不构成任何承诺。20.1 建立了"按最坏情况评估需求"的口径，本节把它拆到链路的每一段。

延迟预算（Latency Budget）就是把 20.1 的截止时间拆成链路上每一段的配额：总预算 100μs，中断处理分多少、调度分多少、用户态处理分多少、余量留多少。预算表的价值在两个时刻兑现：设计期，它告诉你每一段该用什么手段压住；超标时，它告诉你超的是哪一段。没有预算表的调优是玄学，有预算表的调优是工程。

预算要能兑现，前提是测得准、归因得动。本节因此按"拆解 → 预算 → 测量 → 归因 → 调优"的顺序展开，最后给一段完整实录和一份可直接编译的应用侧代码骨架。

> 本节覆盖：中断→响应全链路五段拆解、预算表模板与余量纪律、测量方法论（为什么只看 Max、负载怎么加、基线怎么建）、归因工具实操（cyclictest、osnoise、timerlat）、逐项调优手段清单、从 Max 214μs 压回预算内的调优实录、应用侧最小实时代码骨架。

## <span class="blue"> 全链路五段拆解

以一个典型实时任务为例：外部信号触发，应用做出响应。

```text
①硬件中断延迟   ②中断处理      ③调度延迟        ④用户态处理     ⑤输出生效
信号→中断线  → IRQ handler → 唤醒实时线程    → 计算/逻辑     → GPIO/总线/网络
  ns 级        μs 级（线程化）  几~几十 μs       取决于应用      μs 级
  硬件决定      ← 软件调优主战场 →             ← 应用纪律 →     软硬交界
```

**①硬件中断延迟**：信号从引脚到中断控制器再到 CPU 开始响应，纳秒级，软件管不了，记在账上不分配预算。

**②中断处理**：RT 内核里 IRQ handler 已线程化（中断机制见第 10 章）：handler 本身只做最紧急的确认，其余作为内核线程执行，可以被抢占。这一段的主要风险不是 handler 长，而是**别的中断**挤占：网卡中断风暴、定时器中断、无关外设的 IRQ，全是这一段的延迟源。

**③调度延迟**：实时线程被唤醒到真正跑上 CPU 的时间，含一次上下文切换（3~5μs）。它取决于：当前 CPU 在跑什么（有没有更高优先级任务占着）、CPU 在不在深度睡眠、频率在不在爬坡。这一段是 RT 调优的主战场。

> C-state：CPU 空闲时进入的省电状态，分级越深关闭的电路越多、越省电，唤醒回运行态也越慢。浅层几微秒，深层几十微秒（整簇断电更深）。"CPU 在睡觉"是调度延迟里最稳定的几十微秒来源。

**④用户态处理**：应用自己的代码时间。预算分给它之后，应用的义务是遵守实时编程纪律：不动态分配内存（或预分配）、不碰 page fault（栈和堆锁定）、不用无界阻塞的锁。

> page fault（缺页）：CPU 访问尚未建立映射的虚拟地址时触发的异常，内核现场分配物理页（minor fault），甚至从磁盘或交换分区读回（major fault）。量级：minor 微秒级（典型 1~2μs），major 几十微秒到毫秒级。实时路径上的一次 major fault 就足以击穿整条预算。

**⑤输出生效**：写 GPIO、发总线帧、回网络包，微秒级。但"写到寄存器"和"信号出现在总线上"之间还有硬件传播时间，硬实时场景要算进去。

## <span class="blue"> 预算表模板与余量纪律

成稿示例（1ms 控制环，截止 100μs，PREEMPT_RT 平台）：

| 段 | 预算 | 手段 | 实测 |
|----|-----:|------|-----:|
| ②中断处理 | 10μs | IRQ 线程化 + 亲和性绑定 | 6μs |
| ③调度延迟 | 30μs | CPU 隔离 + 禁 C-state + 锁频 | 22μs |
| ④用户态 | 30μs | mlockall + 预分配 + FIFO 优先级 | 18μs |
| ⑤输出 | 5μs | — | 3μs |
| **余量** | **25μs** | — | — |
| 合计 | 100μs | | 49μs |

①硬件段不在表内：它由芯片和布线决定，软件没有手段，只在验收时确认其量级（纳秒级，可忽略）。

余量纪律两条。**余量 ≥ 25%**：实测峰值会随固件升级、负载变化、温度漂移而移动，贴着截止时间排的预算等于把产品押给运气。**余量不许被预支**：某段超标了，正确动作是回去压那一段，不是从余量里借。借来的预算没有手段背书，只是数字搬家。

## <span class="blue"> 测量方法论：先看 Max，再谈数字

预算表右列的"实测"怎么来，决定了整张表是工程还是许愿。四条纪律。

**只看 Max，不看 Avg。** 实时失效发生在分布的尾部：一个 Avg 8μs、Max 214μs 的系统，对 100μs 的截止时间就是不合格，哪怕它 99.9% 的时间都很快。验收口径写 Max（或 p99.9）；写平均值的验收标准，是抖动漏进量产的典型通道。

**测量时长按事件稀有度定。** 尖峰是低频事件：十秒跑不出来的东西，十小时未必跑不出来。迭代期用 1~10 分钟快速对比，验收跑 24 小时以上，覆盖温度循环和业务高峰。被问"测多久够"时，答案是"长到最坏情况有理由出现过"。

**负载必须主动加。** 空载的 Max 只是入场券，延迟噪声几乎全部来自资源竞争：CPU 竞争、内存压力、IO 中断、网络流量。标准做法是用 stress-ng 把非实时侧打满：

```
# CPU 打满 + 内存压力 + 磁盘 IO，持续 24 小时
stress-ng --cpu 3 --vm 2 --vm-bytes 75% --hdd 1 --timeout 24h
```

`--cpu 3` 占满三个核制造调度竞争，`--vm 2 --vm-bytes 75%` 制造内存压力与缺页竞争，`--hdd 1` 制造 IO 中断与脏页回写。网络中断负载另开一台机器用 iperf3 长连接打流（用法见 26.6）。把量产工况里"最忙的那个小时"复现出来，Max 才有验收意义。

**基线分三级建立。** ①空载基线：只跑实时任务，记录 Max；②业务负载基线：加上真实业务全套，记录 Max；③压力基线：再叠 stress-ng，记录 Max。三个数字一起构成交付证据：①证明手段本身生效，②证明工况达标，③证明余量真实存在。

> ⚠️ 只测一次的 Max 不可信。同配置连测三轮，Max 漂移超过 20% 就说明还有没控制住的变量（温度、后台服务、动态频率），先排掉再记数。

## <span class="blue"> 归因工具实操：超标了，超在哪段

### cyclictest：基线测量与判读

cyclictest（rt-tests 套件）是延迟测量的标准仪器：起一个定时线程，周期醒来时对比"应该醒的时刻"与"实际醒的时刻"，差值就是②③段的合计延迟。

```
cyclictest -m -p 80 -i 1000 -l 100000 --histogram=200
```

参数：`-m` 锁内存（内部调 mlockall，排除自身缺页干扰）、`-p 80` 以 SCHED_FIFO（先进先出实时调度类）优先级 80 运行、`-i 1000` 周期 1000μs、`-l 100000` 循环十万次（约 100 秒）、`--histogram=200` 输出 200μs 以内的分布直方图。输出形如：

```
T: 0 ( 2449) P:80 I:1000 C: 100000 Min:      4 Act:      9 Avg:      8 Max:     214
```

逐字段判读：T 线程号，P 优先级，I 周期（μs），C 循环数；右侧 Min/Act/Avg/Max 是本次窗口内唤醒延迟的最小/最近一次/平均/最大值（μs）。纪律照旧：Avg 8 配 Max 214，结论是"尾部失控"，不是"平均很好"。直方图看形状：单峰贴底是健康，右尾拖长说明存在偶发大延迟源。迭代用 `-l` 控制次数，验收用 `-D 24h` 按时长跑。

### osnoise tracer：把噪声拆成分

cyclictest 告诉你"超标了"，osnoise（内核 5.14 引入的 tracer）告诉你"超的是什么"。它在指定 CPU 上放一个最高优先级采样线程，把采样线程没跑上 CPU 的时间按来源归因：硬中断、软中断（内核延后处理中断事务的机制，见第 10 章）、抢占它的线程、NMI（不可屏蔽中断）。入口有两个，优先用 rtla（内核 tools/rtla 的用户态封装）：

```
rtla osnoise top -c 3 -d 10m
```

输出按 CPU 分行，关键列形如（列名随版本略有差异）：

```
CPU    Period    Runtime    Noise    %CPU Aval    IRQ Noise    Thread Noise    Softirq Noise
  3   1000000     999712      288      99.9712          41            207               40
```

判读直接对应预算表：**IRQ Noise 高**说明段②没治理好（中断亲和性没绑，或中断频率本身太密）；**Thread Noise 高**说明有别的任务或内核线程抢占了实时核（隔离不彻底）；**Softirq Noise 高**指向网络或块设备的软中断（回查 IRQ 绑核与收包参数）。

没有 rtla 的系统走 tracefs（内核追踪接口，挂载于 /sys/kernel/tracing）原始入口，前提内核开了 CONFIG_OSNOISE_TRACER：

```
cd /sys/kernel/tracing
echo osnoise > current_tracer
echo 1 > tracing_on
sleep 60
echo 0 > tracing_on
cp trace /tmp/osnoise.txt
```

### timerlat tracer：控制环路径的直连测量

timerlat（5.17 引入，需 CONFIG_TIMERLAT_TRACER）测的是定时器到期到测量线程被唤醒的完整路径，正好是控制环 `clock_nanosleep` 走的那条路，比 osnoise 更贴近应用体感：

```
rtla timerlat top -c 3 -d 10m
```

它把每次延迟拆成两列：**IRQ latency**（定时器中断进来到 handler 执行完，对应段②）和 **Thread latency**（唤醒测量线程的调度耗时，对应段③）。超标时哪列高就回哪段下药，归因零猜测。

归因顺序定型为：cyclictest 看分布形状确认超标 → osnoise 拆成分定位噪声类型 → timerlat 对照 IRQ/Thread 两列指认段落 → 用下文的手段清单按段下药。经验猜十次，不如 tracer 拆一次。

## <span class="blue"> 逐项调优手段清单

①无软件手段、⑤靠硬件选型与验收时实测确认，软件能压的是②③④。按段给手段，每条注明它压的是哪一段。

**压②：IRQ 治理。** 无关中断全部从实时核上赶走：`/proc/irq/N/smp_affinity` 把网卡、磁盘中断绑到 housekeeping 核；实时外设的中断绑到实时核，IRQ 线程优先级抬到仅次于实时任务（实时任务 SCHED_FIFO 80，IRQ 线程给 70：IRQ 线程名形如 `irq/24-eth0`，用 `ps -eLo pid,comm | grep irq/` 找到线程号后 `chrt -f -p 70 <pid>`）；网络场景评估 NAPI（网卡驱动的中断-轮询混合收包机制，见 26.2）与中断聚合参数，中断频率本身是可调的。

> housekeeping 核：CPU 隔离划分后承担全部"杂务"的普通核：内核线程、RCU 回调（内核同步机制的善后工作，见第 13 章）、定时器 tick、无关中断、非实时应用。实时核的理想状态是除了实时任务什么都没有，杂务统统归它。

**压③：CPU 隔离与电源锁定。** 内核启动参数 `isolcpus=domain,nohz,managed_irq,3 nohz_full=3 rcu_nocbs=3` 把核 3 隔离出来：调度域摘掉（普通任务进不来）、定时器 tick 停掉、RCU 回调挪走、可管理中断默认不往这核派；实时线程用 `taskset` 独占这个核。电源侧用 `cpupower` 锁 performance 模式（频率不浮动），禁用深度 C-state（唤醒延迟从几十微秒压到近零）。代价是功耗，这就是 20.1 说的"确定性换吞吐（和电费）"；电源管理机制本身见第 15 章。

**压④：应用的实时纪律。** `mlockall(MCL_CURRENT|MCL_FUTURE)` 锁死内存防 page fault；栈和关键缓冲启动时预触碰；堆用预分配池；锁用支持优先级继承的 `pthread_mutex`（`PTHREAD_PRIO_INHERIT`）；日志走 lock-free 环形缓冲异步落盘，不在实时路径上 printf。完整代码骨架见下文。

> 优先级反转：低优先级任务持有锁时被中优先级任务抢占，高优先级任务等锁的时间因此失去上界（火星探路者号的真实事故类型）。解法是让持锁的低优先级任务临时继承等待者的优先级（PI futex / PI mutex），把它抬过中优先级任务。RT 内核的 rtmutex 原生支持 PI，这是实时场景选它的原因之一。

**压全链路：归因工具。** 即上节的 cyclictest / osnoise / timerlat 组合拳，不再重复。纪律只有一条：手段加上去之后必须回工具复测，收益以 Max 变化为准，不以"理论上应该有用"为准。

## <span class="blue"> 调优实录：从 Max 214μs 压回预算内

把上面三节按顺序走一遍。平台：RK3568（四核 Cortex-A55）加 PREEMPT_RT 内核，1kHz 控制环，预算表给②+③合计 40μs。全程执行测量方法论：stress-ng 负载常驻，每步只改一个变量，每步复测 Max。

**基线：RT 内核默认配置，Max 214μs。** 预算是 40μs，超了四倍有余。cyclictest 直方图右尾拖长，osnoise 显示 IRQ Noise 占大头：网卡和磁盘 IRQ 默认撒在所有核上，包括将来要跑实时任务的核 3。

**第 1 步，IRQ 亲和性，Max 148μs。** 先查 IRQ 号再绑核（掩码 7 = CPU0/1/2，实时核是 3）：

```
cat /proc/interrupts | grep -E "eth|mmc"
 24:    1528336          0          0          0  GICv2  50 Level     eth0
 31:     882341          0          0          0  GICv2  57 Edge      mmc0

echo 7 > /proc/irq/24/smp_affinity
echo 7 > /proc/irq/31/smp_affinity
```

输出第一列就是要写进 `/proc/irq/` 路径的 N；计数全堆在 CPU0 一列，说明还没绑核。网卡、存储中断不再落在核 3，实时信号源的 IRQ 线程同步抬优先级（`ps -eLo pid,comm | grep irq/` 找到线程后 `chrt -f -p 70 <pid>`，实时任务是 80，IRQ 线程给 70），这两笔收益合并记进本步。osnoise 的 IRQ Noise 列应声下降。还剩 148μs，Thread Noise 成为新的大头：普通任务仍会被调度到核 3。

**第 2 步，CPU 隔离，Max 96μs。** 启动参数加 `isolcpus=domain,nohz,managed_irq,3 nohz_full=3 rcu_nocbs=3`，重启后实时线程 `taskset -c 3` 独占核 3，cyclictest 也加 `-a 3` 绑到同核复测。调度干扰基本清零，剩下的 96μs 里 osnoise 各列都不高了：瓶颈转移到硬件状态。

**第 3 步，锁频禁 C-state，Max 58μs。**

```
cpupower frequency-set -g performance
for s in /sys/devices/system/cpu/cpu3/cpuidle/state*/disable; do echo 1 > "$s"; done
```

这 38μs 的收益正是 C-state 的唤醒成本：核 3 空闲时进深层睡眠，控制环定时器到期后要先花几十微秒把核叫醒。全局禁用简单直接；只想保护实时进程时，折中是进程打开 `/dev/cpu_dma_latency` 写入 0（PM QoS 接口，进程退出自动恢复），机制见第 15 章。

**第 4 步，应用侧纪律，Max 37μs。** cyclictest 的 `-m` 锁的是它自己的内存，测不出真实应用的缺页，这一步的测量口径要换：应用每拍醒来时用 `clock_gettime` 对比实际与应醒时刻之差，运行期维护 Max（下文骨架里控制环的注释位置就是打点处）。把真实应用按骨架补齐 mlockall、栈预触碰、PI 锁后复测：负载下偶发缺页与内存竞争贡献的尖刺消失，应用自测 Max 收在 37μs。

手段-收益对照（某次实录的量级，不同平台绝对值不同，方法不变）：

| 步骤 | 手段 | 负载下 Max | 本步收益 |
|-----:|------|-----------:|---------:|
| 基线 | RT 内核默认配置 | 214μs | — |
| 1 | IRQ 亲和性 + IRQ 线程优先级 | 148μs | -66μs |
| 2 | CPU 隔离三参数 | 96μs | -52μs |
| 3 | 锁频 + 禁深度 C-state | 58μs | -38μs |
| 4 | 应用内存与锁纪律 | 37μs | -21μs |

对照预算表：②+③ 配额 40μs，实录最终 37μs 收进配额内，25μs 余量全程未动——预算表的纪律和数字一起立住了。

> ⚠️ 每步只开一个变量，复测后再开下一个。三个手段同时上、Max 也降了，得到的只是"能用了"，失去的是归因能力；下个月固件升级 Max 反弹时，没人知道该回哪一段。

## <span class="blue"> 应用侧最小实时代码骨架

段④的纪律落到代码，一个可直接编译的最小骨架（mlockall + 栈预触碰 + PI mutex + FIFO 优先级 + 绝对时间周期）：

```c
/* rt_app.c：最小实时任务骨架 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdint.h>
#include <string.h>
#include <unistd.h>
#include <sys/mman.h>
#include <pthread.h>
#include <sched.h>

#define RT_STACK (256 * 1024)
static uint8_t rt_stack[RT_STACK] __attribute__((aligned(64))); /* 静态线程栈，对齐避免校验失败 */
static volatile int sched_ok;       /* worker 置 1 表示实时优先级生效 */
static pthread_mutex_t lock;

static void *worker(void *arg)
{
    (void)arg;
    struct sched_param sp = { .sched_priority = 80 };
    if (pthread_setschedparam(pthread_self(), SCHED_FIFO, &sp) != 0) {
        perror("pthread_setschedparam");  /* 需要 root 或 CAP_SYS_NICE */
        return NULL;                      /* sched_ok 保持 0，main 会检出 */
    }
    sched_ok = 1;
    struct timespec next;
    clock_gettime(CLOCK_MONOTONIC, &next);
    for (;;) {
        next.tv_nsec += 1000 * 1000;      /* 1ms 控制周期 */
        while (next.tv_nsec >= 1000000000L) {
            next.tv_sec++;
            next.tv_nsec -= 1000000000L;
        }
        clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, &next, NULL);
        /* 绝对时间睡眠：以上次应醒时刻为基准，周期不漂移 */
        /* 打点处：此处 clock_gettime 与 next 之差就是本拍延迟，运行期维护 Max */
        pthread_mutex_lock(&lock);
        /* 控制环计算：只做确定性工作，不分配内存，不 printf */
        pthread_mutex_unlock(&lock);
    }
    return NULL;
}

int main(void)
{
    if (mlockall(MCL_CURRENT | MCL_FUTURE) != 0) {
        perror("mlockall");               /* 现有页 + 未来页全部锁进 RAM */
        return 1;
    }
    memset(rt_stack, 0, sizeof(rt_stack));/* 预触碰：启动期把栈页全部 fault 进来 */

    pthread_mutexattr_t ma;
    pthread_mutexattr_init(&ma);
    pthread_mutexattr_setprotocol(&ma, PTHREAD_PRIO_INHERIT); /* PI 锁 */
    pthread_mutex_init(&lock, &ma);

    pthread_attr_t ta;
    pthread_attr_init(&ta);
    pthread_attr_setstack(&ta, rt_stack, sizeof(rt_stack));   /* 用预触碰过的栈 */
    pthread_t th;
    pthread_create(&th, &ta, worker, NULL);
    usleep(50 * 1000);                    /* 等 worker 完成优先级设置 */
    if (!sched_ok) {
        fprintf(stderr, "实时优先级未生效，拒绝静默降级运行为非实时\n");
        return 1;                         /* 宁可退出，不以非实时身份跑控制环 */
    }
    pthread_join(th, NULL);
    return 0;
}
```

编译与运行：

```
gcc -O2 -Wall -o rt_app rt_app.c -pthread
taskset -c 3 ./rt_app
```

四个设计点对应预算表：**mlockall 加 memset 预触碰**把缺页全部推到启动期，运行期 page fault 归零；**PTHREAD_PRIO_INHERIT** 让持锁者继承等待者优先级，段④不会因为锁失去上界；**TIMER_ABSTIME** 用绝对时间排下一拍，避免相对睡眠的误差累积；**sched_ok 检查**挡住最常见的事故形态——权限不够导致实时优先级没设上，进程一声不吭地以普通任务身份跑控制环。骨架之外还有两条没有代码形态的纪律：日志走异步环形缓冲（printf 的格式化、加锁、写 IO 都是无定界操作），堆用启动期预分配的内存池。

> 💡 验证骨架是否真的零缺页：跑起来后读 `/proc/<pid>/status` 的 `VmLck` 应等于进程全部内存，再观察 `/proc/<pid>/stat` 第 10、12 字段（minflt / majflt）在稳态运行时不再增长。

## <span class="blue"> 方案对比（Trade-off）

| 维度 | 评价 |
|------|------|
| CPU 隔离 vs 全局调优 | 隔离一个核最简单可预期，代价是少一个核的算力；核数紧张时改走全局 IRQ 治理 |
| 锁频禁 C-state vs 省电 | 确定性与功耗的直接交换；电池设备按工况动态切换（工作模式锁，待机放开），启动期权衡见第 24 章 |
| mlockall vs 精细内存管理 | 全锁简单但吃内存；大内存应用改预分配池加关键页锁定 |
| 余量预支 vs 回段压缩 | 预支是数字搬家；超标永远回段解决，预算表的纪律就是工程的可信度 |
| 经验调参 vs tracer 归因 | 经验猜十次不如 osnoise 拆一次；归因工具用熟，调优从玄学变工程 |

## <span class="blue"> 本节总结

RT 内核给的是调优资格，不是实时本身：中断到响应的五段链路（硬件/中断处理/调度/用户态/输出）各自贡献延迟，预算表把截止时间拆成每段配额加 25% 余量，余量永不预支。预算兑现靠测量纪律撑腰：只看 Max 不看 Avg，负载用 stress-ng 主动加，验收跑满 24 小时、按三级基线取证。超标后的归因是固定套路：cyclictest 看分布形状，osnoise 把噪声拆成中断/线程/软中断成分，timerlat 用 IRQ 与 Thread 两列直接指认段②还是段③，然后按段下药：IRQ 亲和性压段②，隔离三参数加锁频禁 C-state 压段③（实录里 214μs 逐项压到 37μs，收进 40μs 配额），mlockall 加预触碰加 PI 锁加异步日志压段④。预算表和复测数据合起来，就是 20.2 里"RT 够用"这个结论的可交付证据。

关键结论速查：

| 问题 | 一句话答案 |
|------|-----------|
| 打开 PREEMPT_RT 后第一件事 | 建延迟预算表，不是直接测 |
| 五段链路的调优主战场 | ③调度延迟（IRQ/隔离/电源三板斧都在这） |
| 验收口径 | Max（或 p99.9），绝不写平均值 |
| 测量时长与负载 | 迭代 10 分钟、验收 24h 以上；stress-ng 复现最忙工况 |
| CPU 隔离三参数 | `isolcpus` + `nohz_full` + `rcu_nocbs`，实时线程独占 |
| 电源侧两大延迟源 | 频率浮动、C-state 进出；确定性换电费 |
| 应用纪律四条 | mlockall、预触碰/预分配、PI 锁、日志异步 |
| 优先级反转的解法 | PI mutex（持锁者继承等待者优先级） |
| 余量纪律 | ≥25%，且永不预支；超标回段压缩 |
| 归因工具链 | cyclictest 看形状 → osnoise 拆成分 → timerlat 指认段落 |

- 能写出（或审查出违规的）mlockall + 栈预触碰 + PI mutex + 绝对时间周期的实时代码骨架
