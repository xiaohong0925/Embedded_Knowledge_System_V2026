# 20.3 延迟预算设计：从中断到响应的全链路拆解

> 所属章节：第20章 实时性设计
>
> 难度：[M] ~ [E] | 预计阅读时间：28 分钟

## <span class="blue">本节导读

选了 PREEMPT_RT 之后，工作才真正开始。RT 内核给你的不是"实时"，是**调优的资格**——它消灭了内核里最大的不可抢占区，但从中断触发到应用响应的链路上，还有七八个环节各自贡献延迟。不对这些环节做预算分配和逐项调优，实测出来的 WCET 和没打补丁差不多。

延迟预算（Latency Budget）就是把 20.1 的截止时间拆成链路上每一段的配额：总预算 100μs，中断处理分多少、调度分多少、用户态处理分多少、余量留多少。预算表的价值在两个时刻兑现：设计期，它告诉你每一段该用什么手段去压住；超标时，它告诉你超的是哪一段——没有预算表的调优是玄学，有预算表的调优是工程。

> 本节覆盖：中断→响应全链路的五段拆解、预算表模板与余量纪律、每一段的调优手段清单（IRQ 亲和性、CPU 隔离、电源管理、内存锁定、优先级与继承）、归因工具（cyclictest 分布判读、osnoise/timerlat tracer）。

---

## <span class="blue">全链路五段拆解

以一个典型实时任务为例——外部信号触发，应用做出响应：

```text
①硬件中断延迟   ②中断处理      ③调度延迟        ④用户态处理     ⑤输出生效
信号→中断线  → IRQ handler → 唤醒实时线程    → 计算/逻辑     → GPIO/总线/网络
  ~ns 级       μs 级（线程化）  几~几十 μs       取决于应用      ~μs 级
─────────────  操作系统能管的部分  ─────────────  应用自己的部分  ─────────
```

**①硬件中断延迟**：信号从引脚到中断控制器到 CPU 开始响应，纳秒级，软件管不了，记在账上不分配预算。

**②中断处理**：RT 内核里 IRQ handler 已线程化——handler 本身只做最紧急的确认，剩下的作为内核线程执行，可以被抢占。这一段的主要风险不是 handler 长，是**别的中断**挤占：网卡中断风暴、定时器中断、无关外设的 IRQ，全是这一段的延迟源。

**③调度延迟**：实时线程被唤醒到真正跑上 CPU 的时间。它取决于：当前 CPU 在跑什么（有没有更高优先级任务占着）、CPU 在不在深度睡眠（C-state 唤醒要几十微秒）、频率在不在爬坡。这一段是 RT 调优的主战场。

**④用户态处理**：应用自己的代码时间。预算分给它之后，应用的义务是遵守实时编程纪律：不动态分配内存（或预分配）、不碰 page fault（栈和堆锁定）、不用无界阻塞的锁。

**⑤输出生效**：写 GPIO、发总线帧、回网络包——μs 级，但"写到寄存器"和"信号出现在总线上"之间还有硬件传播时间，硬实时场景要算进去。

## <span class="blue">预算表模板与余量纪律

成稿示例（1ms 控制环，截止 100μs，PREEMPT_RT 平台）：

| 段 | 预算 | 手段 | 实测 |
|----|-----:|------|-----:|
| ②中断处理 | 10μs | IRQ 线程化+亲和性绑定 | 6μs |
| ③调度延迟 | 30μs | CPU 隔离+禁 C-state+锁频 | 22μs |
| ④用户态 | 30μs | mlockall+预分配+FIFO 优先级 | 18μs |
| ⑤输出 | 5μs | — | 3μs |
| **余量** | **25μs** | — | — |
| 合计 | 100μs | | 49μs |

余量纪律两条。**余量 ≥ 25%**：实测峰值会随固件升级、负载变化、温度漂移——贴着截止时间排的预算，等于把产品押给运气。**余量不许被预支**：某段超标了，正确动作是回去压那一段，不是从余量里借——借来的预算没有手段背书，只是数字搬家。

## <span class="blue">逐项调优手段清单

按五段顺序给手段，每条注明它压的是哪一段：

**压②：IRQ 治理。** 无关中断全部从实时核上赶走：`/proc/irq/N/smp_affinity` 把网卡、磁盘中断绑到 housekeeping 核；实时外设的中断绑到实时核且 IRQ 线程优先级抬到仅次于实时任务；网络场景评估 NAPI 与中断聚合参数（中断频率本身是可调的）。

**压③：CPU 隔离与电源锁定。** 内核启动参数 `isolcpus=3 nohz_full=3 rcu_nocbs=3` 把核 3 隔离出来（调度器不往里塞普通任务、定时器 tick 停掉、RCU 回调挪走），实时线程 `taskset` 独占这个核；电源侧 `cpupower` 锁性能模式（频率不浮动）、禁用深度 C-state（`idle=poll` 或 PM QoS，唤醒延迟从几十 μs 压到近零）——代价是功耗，这就是 20.1 说的"确定性换吞吐（和电费）"。

**压④：应用的实时纪律。** `mlockall(MCL_CURRENT|MCL_FUTURE)` 锁死内存防 page fault（一次缺页就是几十 μs 的磁盘/换页延迟）；栈和关键缓冲启动时预触碰；堆用预分配池；锁用支持优先级继承的 `pthread_mutex`（`PTHREAD_PRIO_INHERIT`，防优先级反转——低优先级任务持锁把高优先级任务卡住，中优先级任务插队的经典事故）；日志走 lock-free 环形缓冲异步落盘，不在实时路径上 printf。

> 优先级反转：低优先级任务持有锁时被中优先级任务抢占，导致等高优先级任务的时间无界——火星探路者号的真实事故类型。解法是让持锁的低优先级任务临时继承等待者的优先级（PI-futex/PI-mutex），把它"抬"过中优先级任务。RT 内核的 rtmutex 原生支持 PI，这是它比普通锁在实时场景更优的原因之一。

**压全链路：排查工具。** cyclictest 的逐核 Max 分布定位"是哪个核在捣乱"；内核的 **osnoise tracer**（`trace/osnoise`）直接把噪声拆成中断/线程/软中断/其他分项，告诉你延迟尖峰的成分；**timerlat** tracer 专门测量 timer 中断到用户态的完整路径。归因顺序：先看 cyclictest 分布形状，再用 osnoise 拆成分，最后针对性用上面三段的手段。

## <span class="blue">方案对比（Trade-off）

| 维度 | 评价 |
|------|------|
| CPU 隔离 vs 全局调优 | 隔离一个核最简单可预期；代价是少一个核的算力——核数紧张时改走全局 IRQ 治理 |
| 锁频禁 C-state vs 省电 | 确定性 vs 功耗的直接交换；电池设备要按工况动态切换（工作模式锁，待机放开） |
| mlockall vs 精细内存管理 | 全锁简单但吃内存；大内存应用改预分配池+关键页锁定 |
| 余量预支 vs 回段压缩 | 预支是数字搬家；超标永远回段解决——预算表的纪律就是工程的可信度 |
| 经验调参 vs tracer 归因 | 经验猜十次不如 osnoise 拆一次；归因工具用熟，调优从玄学变工程 |

## <span class="blue">本节总结

RT 内核给的是调优资格不是实时本身——从中断到响应的五段链路（硬件/中断处理/调度/用户态/输出）各自贡献延迟，延迟预算表把截止时间拆成每段配额加 25% 余量，余量永远不许预支。调优按段下药：IRQ 亲和性治理压中断段，CPU 隔离三参数+锁频禁 C-state 压调度段（代价是功耗），mlockall+预分配+PI 锁+异步日志压用户态段；归因靠 cyclictest 分布形状加 osnoise 成分拆解，经验猜十次不如 tracer 拆一次。预算表和实测数据合起来，就是 20.2 里"RT 够用"这个结论的可交付证据。

关键结论速查：

| 问题 | 一句话答案 |
|------|-----------|
| 打开 PREEMPT_RT 后第一件事 | 建延迟预算表，不是直接测 |
| 五段链路的调优主战场 | ③调度延迟（IRQ/隔离/电源三板斧都在这） |
| CPU 隔离三参数 | `isolcpus` + `nohz_full` + `rcu_nocbs`，实时线程独占 |
| 电源侧两大延迟源 | 频率浮动、C-state 进出——确定性换电费 |
| 应用纪律四条 | mlockall、预分配、PI 锁、日志异步 |
| 优先级反转的解法 | PI-mutex（持锁者继承等待者优先级） |
| 余量纪律 | ≥25%，且永不预支——超标回段压缩 |
| 归因工具链 | cyclictest 看形状 → osnoise 拆成分 → 按段下药 |
