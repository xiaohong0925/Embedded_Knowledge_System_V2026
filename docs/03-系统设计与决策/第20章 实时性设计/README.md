## 核心问题

系统需要实时吗？怎么实现？

## 本章简介

“需要硬实时吗？PREEMPT_RT够了吗？” 实时性决策是嵌入式Linux中最容易产生过度设计或设计不足的地方。选错了实时方案，要么付出不必要的开发和维护代价，要么在产品运行时暴露不可接受的延迟抖动。本章的目标是让你基于真实的延迟需求（而非”感觉需要实时”）做出选择，并设计出可测量的实时保证。有经验工程师对”实时”这个词通常有误解——认为”实时=快”。

实际上实时意味着确定性，即在最坏情况下仍能满足截止时间。

当你面对以下问题时，这种误解会导致错误决策：一个运动控制系统要求1ms内响应中断，PREEMPT_RT能满足吗？一个音频处理系统需要50μs的延迟保证，该用Xenomai还是双系统？一个PLC需要同时处理通信和实时控制，怎么分配CPU资源？一个智能座舱系统有安全相关的ADAS显示和非安全的娱乐功能，怎么隔离？本章的核心洞察是：先测量，再决策——大多数声称”需要硬实时”的系统，在测量后发现PREEMPT_RT已经足够。

你正在设计一款工业运动控制器，基于ARM Cortex-A72双核。需求：电机控制环需要每250μs执行一次（4kHz控制频率），抖动<10μs；同时运行一个HMI界面（Qt）和EtherCAT通信。CPU怎么分配？实时方案选哪个？HMI的图形渲染会不会影响控制环？如果未来升级到4核，方案是否需要重新设计？...
