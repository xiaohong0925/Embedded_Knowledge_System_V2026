# 20.5 综合实战：工业运动控制器的实时架构

> 所属章节：第20章 实时性设计
>
> 难度：[E] | 预计阅读时间：30 分钟

## <span class="blue">本节导读

把 20.1~20.4 押进本章开篇那道题：

> 工业运动控制器，ARM Cortex-A72 双核。电机控制环每 250μs 执行一次（4kHz），抖动 <10μs；同时跑 Qt HMI 和 EtherCAT 主站通信。CPU 怎么分配？实时方案选哪个？HMI 渲染会不会影响控制环？未来升级到 4 核方案要重设计吗？

这道题的每一个坑都在前面各节埋过答案：4kHz/10μs 是什么级别的需求（20.1 的三要素）、双核 A72 意味着什么资源约束（20.2 的决策树输入）、HMI 和控制环共存是什么问题（20.4 的混合关键性）、方案要不要为 4 核重设计（架构的前瞻性）。本节按真实工作顺序走：量化需求 → 决策树选型 → 架构分割 → 延迟预算 → 验收方案，最后正面回答原题的四个问题。

> 本节覆盖：需求三要素成稿、双核约束下的决策树推演（含被否决路线）、OpenAMP 式架构分割落稿、延迟预算表、验收测试矩阵、原题四问的完整答案。

## <span class="blue">第一步：需求三要素成稿

按 20.1 的方法，先把题面里的"需求"改写成规格：

| 任务 | 周期/触发 | 截止时间 | 抖动 | miss 率 | 定级 |
|------|----------|---------|------|--------|------|
| 电机控制环 | 250μs（4kHz，定时器触发） | 触发到 PWM 更新 ≤ 50μs | ±10μs | 0（超时=扭矩错误，设备抖动） | **硬实时** |
| EtherCAT 主站 | 1ms 周期帧 | 帧发出时刻偏差 ≤ 20μs | ±20μs | ppm 级（丢帧=从站同步漂移） | 软实时偏硬 |
| Qt HMI | 事件驱动 | 响应 <100ms | 无要求 | 可容忍 | 非实时 |
| 日志/网络管理 | — | 秒级 | 无 | 可容忍 | 非实时 |

两个关键判断。**控制环的 miss 率 = 0**：超时意味着输出给电机的扭矩指令错拍，累积起来是机械抖动甚至过载——这是硬实时，"工程上界"不够，要的是可证明的保证。**EtherCAT 藏在中间档**：主站周期帧的时刻精度影响从站同步，但多数从站有本地时钟补偿（DC 机制），容忍 ppm 级偏差——软实时偏硬，PREEMPT_RT 域可解（B-E.15.3 的人形机器人全身 EtherCAT 走的就是这条路）。

---

## <span class="blue">第二步：决策树推演与被否决路线

控制环硬实时 + miss 率 0，按 20.2 决策树走：

**先量 PREEMPT_RT？** 理论上天花板几十 μs，似乎能够到 50μs 的边——但 miss 率要求是 0（可证明的 0），RT 给的是工程上界不是数学证明；且这台机器还要跑 Qt——图形栈的内存带宽和 GPU 活动是 20.4 说的"最难治的内存干扰"，在只有**两个核**的平台上，连"隔离一个核给实时"都意味着 Linux 侧只剩一个核跑 Qt+EtherCAT+系统服务，资源和确定性两头受挤。结论：RT 单系统方案在本约束下出局，但它仍是 EtherCAT 任务域的方案（见架构）。

**Xenomai？** 天花板够，但双域编程+社区萎缩（20.2），且同样解决不了"双核怎么分"的资源问题。出局。

**双系统/AMP？** A72 双核平台没有片上 M 核——但工业运动控制器的外挂 MCU 是标准玩法：一颗 Cortex-M4 协处理器专跑电流环，A72 只管轨迹规划与通信。这正是 20.2 说的"工业主流"。**入选**。

**卸载 FPGA？** 电流环进 FPGA 是更激进的正解，但当前产品没有 FPGA，BOM 变动大——记为下代平台候选。

被否决路线全部留档：RT 单系统（miss=0 不可证明+双核资源不足）、Xenomai（生态账+不解决资源问题）、FPGA 卸载（BOM 约束，下代候选）。

## <span class="blue">第三步：架构分割落稿

```text
┌─────────────────────────────┐      SPI/UART + 共享参数区      ┌──────────────┐
│ A72×2：Linux（PREEMPT_RT）  │ ◄──────────────────────────────► │ M4 协处理器   │
│                             │   参数下发（目标位置/增益）        │ 裸机/RTOS     │
│  核0：EtherCAT 主站（RT 线程）│   状态上报（实际位置/电流/告警）   │  电流环 4kHz  │
│  核1：Qt HMI + 系统服务      │                                 │  PWM/ADC 直控 │
└─────────────────────────────┘                                  └──────────────┘
```

通道纪律按 20.4 执行：**M4 永不等待 A72**——控制环每个周期读共享参数区，A72 没写新值就用上一次的（轨迹规划侧 1ms 更新一次参数，远松于 250μs 控制周期）；M4 对 A72 下发的参数做范围与变化率校验（不可信的输入全检）；急停回路完全在 M4 域内（硬件急停信号直连 M4，不经过 Linux——这也是 19.5 功能安全分割的雏形）。

A72 侧内部再按 20.3 做次级分割：EtherCAT 主站线程绑核 0、IRQ 亲和全绑核 0、SCHED_FIFO 优先级；Qt HMI 和系统服务限在核 1（cgroup/taskset），内存带宽用 QoS 或预留策略限制图形栈对核 0 的干扰。

## <span class="blue">第四步：延迟预算表

M4 域（硬件保证，这里记账不分配）：ADC 采样→电流环计算→PWM 更新 < 20μs，M4 单核裸机循环，WCET 可在代码审查级证明——这是"可证明的 0"的落点。

A72 域（PREEMPT_RT，EtherCAT 任务）：

| 段 | 预算 | 手段 | 实测目标 |
|----|-----:|------|---------:|
| 定时器中断→RT 线程唤醒 | 30μs | IRQ 线程化+亲和绑核 0 | ≤15μs |
| 帧处理与协议栈 | 200μs | 核 0 独占，预分配缓冲 | ≤150μs |
| 网卡发送生效 | 20μs | — | ≤10μs |
| 余量 | ≥250μs | — | — |
| 合计（1ms 周期内） | 500μs | | ≤175μs |

HMI 对控制环的影响被架构吸收：Qt 崩了，控制环照跑（M4 自治+上次参数安全值）；Qt 跑满内存带宽，核 0 的 EtherCAT 延迟漂移进验收项（20.4 的内存干扰验收）。

## <span class="blue">第五步：验收测试矩阵

| 测试项 | 方法 | 通过判据 |
|--------|------|---------|
| 控制环 WCET | M4 侧 GPIO 打点+示波器，连续 72h | 触发→PWM ≤ 20μs，抖动 ≤10μs，零超时 |
| 参数丢失容错 | 阻断 A72→M4 通信 10s | 控制环用上期参数平稳运行，恢复后平滑接管 |

| EtherCAT 周期精度 | cyclictest 式测量+总线分析仪 | 帧时刻偏差 ≤20μs，含 HMI 满载工况 |
| 内存干扰 | Qt 满载+内存压测工具，测核 0 延迟漂移 | WCET 漂移 ≤ 预算内 |
| 双固件升级 | OTA 升级配对测试（四种版本组合） | 协议版本协商正确，错配拒绝启动并告警 |

## <span class="blue">原题四问的完整答案

**CPU 怎么分配？** 三域而非两核：M4 协处理器独占电流环；A72 核 0 专给 EtherCAT 主站（RT 线程+IRQ 亲和）；A72 核 1 扛 Qt HMI 与系统服务。分配的原则是"关键性分域"，不是"负载均衡"。

**实时方案选哪个？** 分层答案：控制环=外挂 M4 裸机（miss=0 要可证明）；EtherCAT=A72 上的 PREEMPT_RT（软实时偏硬，调优后工程上界够用）；HMI=普通 Linux 调度。一个系统三种实时等级，各付各的成本——这正是本章的方法论落地。

**HMI 渲染会影响控制环吗？** 架构上不会：控制环在 M4 上物理隔离，A72 死机都不影响；残余影响在 EtherCAT 域（内存带宽争抢），用核隔离+QoS 压制，并写进验收矩阵第五行。

**升级 4 核要重设计吗？** 不要——这是本架构的前瞻性所在：4 核只是让 A72 侧从"核 0/核 1 紧巴巴"变成"隔离更从容"，三域划分、通道协议、M4 自治全部原样成立。重设计的触发点不是核数，是需求升级到 M4 算力不够（比如上力控算法）——那时候选是下代平台的 FPGA 卸载路线，决策记录里已经留好了位置。

## <span class="blue">本节总结

工业运动控制器案例把全章串成一条线：三要素量化先把"4kHz/10μs"翻译成"控制环硬实时 miss=0、EtherCAT 软实时偏硬、HMI 非实时"三档需求；决策树推演留下 RT 单系统/Xenomai/FPGA 三条被否决路线及理由；架构落稿是"M4 电流环 + 核 0 EtherCAT + 核 1 HMI"的三域分割，通道纪律执行"高侧永不等待、输入全校验、急停不碰 Linux"；延迟预算分域记账——M4 域证明 WCET，A72 域预算表调优；验收矩阵把"Qt 崩了控制环照跑""阻断通信用上期参数"这类架构承诺变成可执行的测试项。回到开篇四问，答案分别是：按关键性分域不按负载均衡、一个系统三种实时等级各付各价、HMI 影响被架构吸收、4 核升级不需要重设计——因为分割是按关键性做的，不是按核数做的。
