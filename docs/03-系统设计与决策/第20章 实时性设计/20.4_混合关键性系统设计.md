# 20.4 混合关键性系统设计：Jailhouse、Xen 与 OpenAMP

> 所属章节：第20章 实时性设计
>
> 难度：[E] | 预计阅读时间：25 分钟

## <span class="blue">本节导读

20.2 的决策树有一个分支反复出现：单系统调优到极限还是不够，或者系统里天然住着两类互相敌对的负载——一类要确定性（实时控制、安全监控），一类要富生态（Linux UI、网络、存储）。这两类负载共享一个内核时，富生态那一侧永远是确定性那一侧的噪声源。混合关键性系统（Mixed-Criticality System）的答案是把它们**分家**：各跑各的运行环境，中间用受控接口通信。

19.5 从功能安全视角讲过同一架构（安全侧不信任 Linux 侧）。本节换实时性视角：三条分割路线（Jailhouse 静态分区、Xen 虚拟化、OpenAMP 异构核）各自的隔离强度、实时性保证、工程成本，以及怎么按系统约束选。深度的 hypervisor 机制归第 35 章（未写），本节止于决策层。

> 本节覆盖：混合关键性的问题本质（干扰源隔离）、三条路线的机制与对比、通信通道（RPMsg/virtio/共享内存）的设计要点、分割架构的系统级代价（启动、升级、调试、生命周期）、选型决策。

## <span class="blue">问题本质：把干扰源关进笼子

混合关键性要隔离的"干扰"具体是什么？四类，按难治程度排：

**调度干扰**：Linux 侧的任务和内核活动抢占实时任务需要的 CPU——20.3 的隔离手段只能在单系统内缓解，分家是从根上消除。**内存干扰**：共享内存控制器和 cache 的争抢（Linux 侧跑一个大带宽任务，实时侧的内存延迟立刻漂移）——这条最难治，因为即使用了不同核，内存控制器还是同一个。**中断干扰**：Linux 侧的 IRQ 风暴波及共享的中断控制器。**故障干扰**：Linux 崩溃不能拖死实时侧——这既是实时问题也是 19.5 的安全问题。

四条干扰里，分家架构对①③④给出硬保证，对②只能缓解（cache 染色、内存带宽 QoS、预留内存区域）——评估混合关键性方案时，内存干扰是你验收测试要专门设计的项目：Linux 侧跑满内存带宽，实时侧的 WCET 漂移多少，就是这条路的真实隔离成色。

> 关键性（Criticality）：功能失效后果的等级。混合关键性 = 同一硬件上跑着失效后果不同等级的功能——实时控制（失效=事故）和娱乐 UI（失效=重启）共存。架构的任务是让低关键性侧的任何行为都无法破坏高关键性侧的保证。

## <span class="blue">三条路线对比

| 维度 | Jailhouse（静态分区） | Xen（虚拟化） | OpenAMP（异构核） |
|------|---------------------|---------------|------------------|
| 机理 | hypervisor 把硬件**静态切开**：核/内存/设备启动时固定分给各分区，之后零调度介入 | 完整 Type-1 hypervisor：虚拟机动态调度、设备虚拟化 | 不切硬件：A 核跑 Linux，M 核（或另一组 A 核）跑 RTOS/裸机，框架只管通信与生命周期 |
| 隔离强度 | 高（分区即物理） | 高（但 hypervisor 本身要进信任链） | 最高（物理上就是两拨硬件） |
| 实时性保证 | 分区独占核，无 hypervisor 调度开销 | dom0/驱动域模型引入额外延迟路径 | RTOS 核完全自治，最强 |
| 硬件要求 | 一颗多核 SoC 即可 | 需要虚拟化扩展（ARM VE） | 需要异构核（A+M）或双 SoC |
| 动态性 | 无——分区启动时定死，运行时不可调 | 有——可动态创建/迁移虚拟机 | 无——但本来就物理分离 |
| 生态与成本 | 配置即一切（cell 配置文件描述分区），学习曲线在设备树级 | 概念重、组件多（dom0、工具栈），安全认证版本（Xen 车规）存在 | SoC 厂商 BSP 成熟（NXP/TI/ST），远程核固件加载、RPMsg 都是现成件 |

一句话定位：**Jailhouse 是"一颗核劈两半用"的极简方案，Xen 是"需要虚拟化动态性"的重方案，OpenAMP 是"SoC 本来就给了异构核"的顺水推舟**。2026 年嵌入式 Linux 的现实分布：工业与机器人以 OpenAMP 为主流（异构 SoC 普及），车载以 Xen（车规认证版）和各家私有 hypervisor 为主，Jailhouse 在"同构多核要硬分区"的场景稳稳占住一角。

> RPMsg（Remote Processor Messaging）：异构核间的标准消息协议，跑在共享内存+mailbox 中断之上——OpenAMP 框架的通信层。通道是命名端点（endpoint）模型，Linux 侧有现成的 rpmsg_char 驱动暴露字符设备，用户态 `open("/dev/rpmsg0")` 就能和 M 核固件对话。它是 AMP 架构里"受控接口"的事实标准。

## <span class="blue">通信通道的设计要点

分家之后，两侧必然要说话——参数下发、状态上报、日志汇聚。通道设计的纪律直接决定分割是否白做：

**单向依赖原则**：高关键性侧永远**不等待**低关键性侧。实时核可以收 Linux 的参数，但控制环的每一个周期都不允许"等 Linux 回话"——所有来自低关键性侧的输入都走"随时可用、过期可弃"的共享状态区，高关键性侧读不到就用上一次的安全值。一旦高侧开始同步等待低侧，分割就名存实亡：低侧的延迟又成了高侧的预算。

**数据校验原则**：高侧对低侧的一切输入做合理性校验（范围、速率、时序）——这和 19.5"安全侧不信任 Linux 侧"是同一条军规。

**版本与升级配对**：双固件意味着两套版本号、两次升级、四种组合兼容矩阵。OTA 设计（21 章）必须把"两侧固件的原子配对升级"列为需求——Linux 升了而 M 核没升，通信协议错位的故障比不升级更糟。

## <span class="blue">系统级代价清单

混合关键性不是免费架构，选型时把代价摆全：

| 代价项 | 内容 |
|--------|------|
| 启动复杂度 | 多核启动顺序（谁加载 M 核固件、失败怎么办）、分区配置的构建集成 |
| 调试割裂 | 两套工具链、两份日志、跨侧时序问题的复现地狱（GDB 在 Linux，M 核靠 JTAG/日志） |
| 资源静态化 | 分给实时侧的核与内存被锁定，Linux 侧的峰值算力受损 |
| 生命周期 | 双固件配对升级、M 核固件的构建与签名也进安全启动链（19.2 的链要延伸到它） |
| 团队结构 | 需要同时懂 Linux 和 RTOS/裸机的人，或两个团队的接口纪律 |

这些代价的共性是**它们出现在架构的每一天，而收益只在关键时刻兑现**——这就是为什么混合关键性必须是需求驱动（三要素证明单系统不够），而不是架构师的技术审美驱动。

## <span class="blue">方案对比（Trade-off）

| 维度 | 评价 |
|------|------|
| Jailhouse vs Xen | 极简静态分区零开销 vs 动态虚拟化全功能；不需要动态性时 Jailhouse 的简单就是可靠 |
| OpenAMP vs 虚拟化两案 | 物理异构的天然隔离 vs 同构核的切分；SoC 有异构核时 OpenAMP 几乎总是总账最优 |
| 共享内存 vs 硬件队列通信 | 共享内存带宽高但一致性自管；mailbox/RPMsg 慢但边界清晰——控制信令走 RPMsg，批量数据走共享内存 |
| 分家 vs 单系统极限调优 | 分家是架构级确定性，单系统调优是预算级；三要素超标一个数量级就该分家，别在单系统里硬熬 |
| 实时侧放 Linux RT vs RTOS | Linux RT 生态富但天花板在几十 μs；RTOS 天花板 μs 级——实时侧内核按 WCET 需求选，不按熟悉度选 |

## <span class="blue">本节总结

混合关键性的本质是把四类干扰（调度/内存/中断/故障）关进笼子，分家架构对其中三类给出硬保证，内存干扰要靠 cache 染色与带宽 QoS 缓解并专门验收。三条路线按硬件形态收敛：SoC 有异构核选 OpenAMP（工业主流，BSP 成熟），同构多核要硬分区选 Jailhouse（配置即一切），需要虚拟化动态性或车规认证选 Xen。分家的成败在通道纪律：高关键性侧永不等待低关键性侧、一切输入校验、双固件原子配对升级。系统级代价（启动/调试/资源静态化/生命周期/团队）天天发生而收益只在关键时刻兑现——所以它是三要素驱动的选择，不是审美驱动的。20.5 的实战会把 OpenAMP 路线在工业运动控制器上完整走一遍。

关键结论速查：

| 问题 | 一句话答案 |
|------|-----------|
| 混合关键性隔离什么 | 调度/内存/中断/故障四类干扰；内存干扰最难治，要专门验收 |
| 三路线速选 | 异构核→OpenAMP；同构核硬分区→Jailhouse；要动态性/车规→Xen |
| 通道第一纪律 | 高关键性侧永不等待低关键性侧，输入过期可弃 |
| RPMsg 的角色 | AMP 间控制信令的事实标准，Linux 侧 rpmsg_char 直接可用 |
| 升级的特殊需求 | 双固件原子配对——协议错位比不升级更糟 |
| 代价的特征 | 每天发生（启动/调试/生命周期），收益只在关键时刻兑现 |
| 何时该分家 | 三要素超标一个数量级，别在单系统里硬熬 |

- 能按 SoC 形态（有无异构核/是否需要动态性）收敛出路线并说出理由
- 能解释"高侧永不等待低侧"为什么是分家成败的分水岭

- 评估混合关键性方案时，能设计"Linux 侧跑满内存带宽测实时侧 WCET 漂移"的验收项
