# 19.6 综合实战：智能门锁的 $3 安全预算

> 所属章节：第19章 安全架构设计
>
> 难度：[E] | 预计阅读时间：35 分钟

## <span class="blue">本节导读

前五节是方法论，这一节把它们押进一个真实约束里。场景就是本章开篇那道题：

> 你正在设计一款智能门锁，ARM Cortex-A53，Wi-Fi 连接、指纹传感器、触摸屏。售价 $200，BOM 控制在 $80 以内。硬性安全要求四条：指纹数据不能被提取、OTA 不能被劫持、物理拆机不能获取密钥、通过 ETSI EN 303 645 认证。安全预算只有 $3。

这道题的难点不在任何单项技术——全章的方法都讲过了——而在**约束互斥**：四条硬性要求里至少两条按教科书解法就要吃掉整个 $3（安全元件一颗就是 $1.5~3），预算却还要覆盖启动链、运行时、认证测试。这就是真实的安全架构工作：不是"把安全措施做对"，而是"在预算红线内把威胁覆盖做到可辩护"。

本节按真实工作顺序走：威胁模型先行（哪些条目是"高×高"），然后逐条把硬性要求翻译成技术方案，每一步都报价，最后给出完整的预算分配表和取舍辩护。读完你应该能把这套"从威胁清单到预算表"的推导过程，复用到你自己的产品上。

> 本节覆盖：门锁的威胁模型成稿、四条硬性要求的逐条方案推导与报价、$3 预算的完整分配表、ETSI EN 303 645 条款到方案的映射、被否决方案的记录（为什么这些"更安全"的做法没被选）。

## <span class="blue">第一步：威胁模型定档

按 19.1 的三问法过一遍。

**资产。** ①指纹模板（用户隐私，泄露即舆情+法律责任，且生物特征不可更换——这是全表最高危资产）；②设备密钥（开锁指令签名、云连接认证，泄露可批量克隆开锁权限）；③固件（被替换则门锁变后门）；④开锁服务的可用性（被远程锁死或恶意开锁都是安全事故）；⑤家庭物理安全本身——这道资产的特殊性在于：门锁被攻破的后果不是数据泄露，是**物理空间的失防**。

**对手。** 定档牟利黑产（第二档）：批量克隆、破解后转卖"万能开"。排除第三档的辩护：单户门锁不值得定向攻击者投入人力，值得定向攻击的目标（豪宅、机房）不会买 $200 的消费锁。好奇用户档顺带覆盖（拆自己的锁）。

**攻击向量（按 19.1 五类面过一遍，只留成立的）。** 网络面：Wi-Fi 通信劫持、云服务假冒、OTA 包替换、默认口令——全部成立；物理面：拆外壳接 UART/JTAG、拆 Flash 离线读取——成立；总线面：指纹传感器走 SPI/UART 挂主控，通信明文则模板在板内裸奔——成立；供应链面：OTA 构建环节、第三方库 CVE——成立；维护面：产线密钥注入、返修——成立。

**分级落格（节选关键条目）：**

| 威胁 | 可能×影响 | 处置 |
|------|:---------:|------|
| 指纹模板被提取（网络或物理） | 中×高 | 必须防：模板不出安全存储，比对不出安全区 |
| 开锁指令被伪造/重放 | 高×高 | 必须防：指令签名+时间戳+防重放 |
| OTA 被替换/劫持 | 中×高 | 必须防：安全启动+验签（19.2 半链） |
| 拆 Flash 读出设备私钥 | 低×高 | 必须防：密钥不可读出（19.4 的抉择点） |
| 默认口令被扫 | 高×高 | 必须防：无默认口令（合规基线） |
| 拆机接 UART 拿 shell | 高×中 | 工程防：关 console+认证解锁 |
| 云服务器被假冒 | 中×高 | 必须防：TLS 双向证书+证书锁定 |
| Wi-Fi 被 deauth 反复踢下线 | 高×中 | 工程防：本地开锁路径不依赖网络 |

这张表就是后面每一笔预算的出处——每一项支出必须能指回某一行。

## <span class="blue">四条硬性要求的方案推导与报价

### 要求一：指纹数据不能被提取

教科书画法是指纹模组带安全芯片、模板加密存储、比对在安全区内完成。报价：带安全特性的指纹模组比普通模组贵 $1.5~2.5——**一项就要吃掉大半个预算**。

替代推导回到威胁表：模板被提取的路径有两条——从传感器到主控的总线嗅探（板内 SPI 明文），和拆 Flash 读存储。拆开防：

- **总线段**：选支持"模板在模组内存储、模组内比对"的指纹模组（模组只回"过/不过"和模板 ID，模板永不出模组）。这类模组比"回传特征值让主控比对"的贵 $0.5~1，但比带完整安全芯片的便宜——取中间档，报价 **$0.8**。
- **存储段**：模板不出模组，Flash 里就没有模板可偷，这一段零成本解决。主控侧只存模板 ID 与指纹模组的配对关系。

辩护要点：这个方案的攻击残留是"换掉指纹模组"——但换模组需要拆锁+重新配对（配对关系在主控侧且绑密钥），攻击成本已超过第二档对手的收益。残留风险明示记录。

### 要求二：OTA 不能被劫持

19.2 的半链正合适：安全启动（ROM→U-Boot→kernel 验签）+ OTA 包验签（21.5 的 RAUC+签名），不上 OP-TEE 全链、不做 dm-verity（rootfs 运行时篡改在本威胁表是"低×中"，明示接受）。

成本核：硬件上 SoC 自带安全启动与 eFuse，**零 BOM**；成本在人——签名流程进 CI、密钥管理、产线烧录工序，摊到单台约 **$0.2**（按 10 万台摊薄开发成本）。防回滚用 eFuse 单调计数器，OTA 侧 A/B 分区+bootcount（第 21 章全套，复用不另计）。

### 要求三：物理拆机不能获取密钥

这是 $3 预算的真正战场。两个候选：

- **安全元件（SE）**：$1.5~2.5，防拆认证、密钥永不出片。上了它，预算见底，指纹模组只能选最便宜的"回传特征值"档——模板在板内裸奔，要求一塌方。
- **SoC eFuse + 软件组合**：设备根密钥烧 eFuse（只能作为硬件 AES 引擎输入，软件不可读出），通信私钥用根密钥加密后存 Flash，使用时在硬件引擎内解密到安全内存。强度定位：防"拆 Flash 离线读取"（密钥明文不落 Flash），防不住芯片级探针攻击——但那是第三档对手，本威胁模型已排除。成本 **$0**。

决策：选 eFuse 方案，理由两条——威胁模型对手上限是第二档，SE 的防拆认证对付的是第三档；省下的预算让要求一的指纹模组能上中间档，**两个要求的覆盖度比单点堆 SE 更高**。这是本次实战最典型的安全取舍：不为单一威胁买最高档防御，为整张清单买均衡覆盖。

### 要求四：通过 ETSI EN 303 645

合规不是额外工作，是把已有方案映射到条款。关键条款对照：

| EN 303 645 条款 | 本方案对应 |
|----------------|-----------|
| 无通用默认口令 | 首启绑定流程生成设备唯一凭证，无口令登录入口 |
| 漏洞报告渠道 | 公司安全页+响应 SLA（流程项，零 BOM） |
| 软件更新与安全补丁 | RAUC OTA + 验签 + 防回滚（要求二） |
| 敏感参数安全存储 | 密钥 eFuse、指纹模板不出模组（要求一/三） |
| 通信加密 | TLS 双向证书+证书锁定 |
| 攻击面最小化 | 关闭 telnet/调试端口、UART 关输入（19.3 及格线） |
| 软件完整性 | 安全启动验签链（要求二） |

认证测试与文档成本摊薄约 **$0.3/台**。提前把条款映射表做出来还有一个隐藏收益：认证机构的预评估阶段，你直接交这张表，比逐条被问快得多。

## <span class="blue">$3 预算分配表与取舍辩护

```text
指纹模组中间档（模组内比对）        $0.8
安全启动+OTA 验签（摊薄）           $0.2
密钥体系（eFuse 方案）              $0.0  ← SoC 自带
运行时加固（19.3 及格线三件套）     $0.0  ← 纯软件
认证摊薄                            $0.3
产线密钥烧录工序                    $0.2
TLS 证书体系（CA+签发流程摊薄）     $0.3
应急预留（认证整改/漏洞响应）       $0.5
─────────────────────────────────────────
合计                               $2.3   （预留 $0.7 机动）
```

**被否决方案的记录**（这部分是架构案的精华，评审时一定会被问）：

| 被否决项 | 理由 | 代价 |
|---------|------|------|
| 上安全元件 SE | 对手定档第二档，SE 防的是第三档；且挤占指纹模组预算导致要求一塌方 | 接受芯片级攻击残留风险（明示） |
| 上 OP-TEE 全链 | A53 支持但开发复杂度陡增，密钥用 eFuse 方案已覆盖 | rootfs 运行时篡改残留（明示，dm-verity 未做） |
| 指纹模组最高档（带 SE） | 中间档+配对绑定已把提取路径压到可接受 | 换模组攻击残留（需拆锁+配对，成本已超收益） |
| SELinux | 无合规点名，团队无维护人力；用 seccomp+沙箱替代 | 内核级行为边界放弃，爆炸半径靠降权控制 |

每条否决都留下"接受什么风险"的记录——这就是 19.1 说的"明示的不作为"。两年后产品要出高配版（保险柜锁、公寓门锁平台）时，这张表就是升级路线的起点：对手定档上调，SE 和 OP-TEE 重新进入候选。

## <span class="blue">复盘：这套推导的可复用部分

把这个案例的方法抽出来，是能搬到任何产品的四步：

1. **威胁模型先行**，对手档位必须写出辩护（为什么是这个档，排除更高档的理由）——档位定错，后面全盘错配。
2. **硬性要求逐条拆路径**，每条要求先找"教科书解法"报价，再找"覆盖同一威胁的次档方案"——次档方案的存在性是议价空间所在。
3. **预算不按技术分，按威胁分**——问"哪个威胁条目还裸着"，而不是"哪个安全技术还没上"。本案里 $0 的密钥方案省下的钱，买到了指纹威胁的更高覆盖。
4. **否决记录即架构资产**——每条否决注明"接受什么残留风险、什么条件下重新评估"，它是产品演进时的安全路线图。

## <span class="blue">方案对比（Trade-off）

| 维度 | 评价 |
|------|------|
| 单点最高档 vs 全清单均衡覆盖 | 本案核心取舍：SE 堆满密钥一点 vs 省出预算抬指纹覆盖——均衡赢，因为威胁清单是整体的 |
| 模组内比对 vs 主控比对 | 模板不出模组 vs 便宜 $0.5~1；最高危资产值得中间档 |
| eFuse 密钥 vs SE | 第二档对手下覆盖等价；第三档对手时 SE 不可替代——对手定档是分水岭 |
| 半链 vs 全链启动 | 半链覆盖"刷机/替换"主威胁；verity 留作高配版升级项 |
| 认证后置 vs 条款前置 | 条款映射表在设计期做，认证变核对；事后补条款，认证变返工 |

## <span class="blue">本节总结

智能门锁案例演示了安全架构的完整工作流：威胁模型定档（第二档黑产，排除第三档并写出辩护）→ 四条硬性要求逐条拆攻击路径 → 每条路径找覆盖同一威胁的次档方案 → 预算按威胁分配而非按技术分配。最终 $2.3 的方案里没有一颗安全芯片，但清单上每个"高×高"条目都有对应防线：指纹模板不出模组、密钥只可用不可读（eFuse）、启动与 OTA 验签半链、TLS 双向证书、EN 303 645 条款映射前置。被否决的 SE、OP-TEE、SELinux 全部留下"接受什么残留、何时重新评估"的记录——这份否决记录和方案本身同等重要。安全架构的产出物从来不是"一堆安全措施"，而是一份**每一笔花费都能指回威胁清单、每一处留白都明示了风险的辩护文档**。

### 本节自查

- 能把一个产品的硬性安全要求拆成攻击路径，并为每条路径找到至少两档候选方案
- 能解释本案为什么不上 SE——并能反推"什么条件下必须上"（对手定档上调/资产升级）
- 能为自己产品做出一张预算分配表，每笔支出指回威胁清单条目
- 能写出被否决方案记录，每条注明残留风险与重新评估条件
- 能把 EN 303 645 或同类合规条款映射成已有方案的核对表
