# 19.3 运行时安全：SELinux、AppArmor 与最小权限的落地

> 所属章节：第19章 安全架构设计
>
> 难度：[M] ~ [E] | 预计阅读时间：28 分钟

## <span class="blue">本节导读

安全启动保证了"跑的是你的固件"。但你的固件不是一个程序，是几十个进程的集合——网络服务、媒体处理、OTA 代理、日志守护、你的业务主程序。这些进程里任何一个有漏洞被远程利用，攻击者就获得了该进程的全部权限。如果这个进程跑在 root 下，游戏结束：19.2 精心建立的启动链保护的一切（密钥、固件、数据）对它全部敞开。

运行时安全就是回答这个问题：**系统跑起来之后，单个进程被攻破的爆炸半径怎么控制到最小**。这不是一个工具的问题，是一组纵深手段的组合：最小权限（进程本来就不该有那么多权）、MAC（强制访问控制，内核级的行为边界）、seccomp（系统调用白名单）、namespace（资源视图隔离）。每一项都有明确的维护成本，本节的目标是让你按威胁清单选出"够用"的组合，而不是把手册上的手段全堆上去。

> 本节覆盖：最小权限的落地三步（降权/capability/文件归属）、SELinux vs AppArmor vs 不用的决策树、seccomp 的嵌入式适配用法、namespace 与容器边界的真实强度、纵深组合的成本账。

---

## <span class="blue">最小权限：零工具成本的第一道墙

在讨论任何安全框架之前，有三件事不需要任何新组件，却消灭了嵌入式设备上一半的真实漏洞影响面。它们构成运行时安全的及格线：

**第一步：服务降权，告别 root 裸奔。** 逐个数你的系统里哪些守护进程真的需要 root——答案通常只有 init、网络配置、少数硬件管理。业务服务全部跑在独立用户下：创建一个无登录、无家目录的系统用户，服务以它运行。一个跑在独立用户下的媒体服务被攻破，攻击者得到的是一个连自己家目录都没有的账号。

**第二步：必须要的特权用 capability 细分。** root 的权限在内核里其实是约 40 个独立的 capability（`CAP_NET_BIND_SERVICE` 绑低端口、`CAP_SYS_TIME` 改时间、`CAP_DAC_OVERRIDE` 无视文件权限……）。服务需要绑 80 端口，给它 `CAP_NET_BIND_SERVICE` 一个位，而不是整个 root。systemd 服务单元里一行配置的事：

```ini
# /etc/systemd/system/camera.service 节选
[Service]
User=camera
AmbientCapabilities=CAP_NET_BIND_SERVICE
NoNewPrivileges=true        ; 禁止 exec 后获得新权限（堵 setuid 提权）
ProtectSystem=strict        ; 整个文件系统只读，只放开白名单目录
ReadWritePaths=/var/lib/camera /run/camera
ProtectKernelModules=true   ; 禁止加载内核模块
PrivateTmp=true             ; /tmp 独立视图，防临时文件攻击
```

> capability：把 root 的"全能"拆成约 40 个独立权限位的内核机制。进程可以持有其中几个位而不是全部——`setcap 'cap_net_bind_service=ep' /usr/bin/myserver` 让一个普通用户的程序也能绑 1024 以下端口。它是"最小权限"从口号变成可操作配置的关键设施。

**第三步：文件归属收紧。** 配置文件 640、私钥 400 且属主为服务用户、二进制目录 root 所有不可写。`chmod -R 777` 是嵌入式现场最常见的自杀式配置——它让"任意进程被攻破"等于"全盘可写"。

这三步的成本是几小时审计加几十行配置，收益是爆炸半径的直接收缩。在它们做到位之前，讨论 SELinux 是本末倒置。

## <span class="blue">MAC 决策树：SELinux、AppArmor，还是不用

最小权限管"进程是谁"，MAC（Mandatory Access Control，强制访问控制）管"进程能干什么"——即使进程被攻破且拿到了 root，内核级的策略仍然限制它只能访问策略允许的文件、端口、接口。这是纵深防御里最硬的一层，也是维护成本最高的一层。两个主流实现加"不用"这个合法选项，构成决策树：

| 维度 | SELinux | AppArmor | 不用 MAC |
|------|---------|----------|---------|
| 策略模型 | 类型强制（TE），一切皆标签，策略描述"类型间允许的操作" | 路径名强制，策略按文件路径写"这个程序能碰哪些路径" | DAC（属主权限）兜底 |
| 表达能力 | 最强，可表达全系统级策略 | 中等，适合"圈住单个程序" | 无内核级行为边界 |
| 学习曲线 | 陡峭（周级入门） | 平缓（天级入门） | 零 |
| 策略维护 | 每次软件升级可能需调策略，需要专职或半专职 | 单程序 profile 独立维护，成本低 | 零 |
| 生态 | Android 强制、RHEL 系默认、Yocto 有 meta-selinux | Ubuntu/SUSE 默认，OpenWrt 有支持 | 多数嵌入式现状 |
| 行业背书 | 高安全等级认证、政务金融场景的常客 | 消费级与工业场景够用 | 无 |

决策路径按序问三个问题：

**有硬性合规或认证要求吗？** 有（如某些行业规范点名 SELinux），选型结束，成本照付。

**威胁清单里"进程被攻破后横向移动"在高×高象限吗？** 在——上 MAC。系统复杂度高、团队有 Linux 安全功底选 SELinux；团队小、目标是"圈住几个对外服务"选 AppArmor。

**不在高×高象限？** 用及格线三件套（降权/capability/文件归属）+ seccomp（下节）的组合替代，把省下的维护成本投到网络面加固——这是多数消费级嵌入式产品的最优解。

> 💡 一个诚实的提醒：SELinux 策略写错了不会让你的系统更安全，只会让它更难用——然后团队会找一个通宵把它调成 permissive（只记录不拦截），从此 SELinux 在你的产品里就是一个昂贵的日志系统。没有维护策略的人力，就不要打开它；打开了又调成 permissive，比不开更糟，因为它给了你虚假的安全感。

## <span class="blue">seccomp：被低估的性价比之王

seccomp（secure computing mode）做的事很单纯：给进程配一张**系统调用白名单**，名单之外的系统调用直接拒绝（杀进程或返回错误）。Linux 用户态和内核之间只有 syscall 这一个接口——把接口面砍掉 80%，内核漏洞的可利用面就跟着砍掉 80%。

嵌入式的适配场景特别合适：守护进程的生命周期固定、行为高度可预测——一个 MQTT 客户端进程没有理由调用 `mount()`、没有道理加载内核模块、不需要 `ptrace` 别的进程。这些反常调用被禁掉，不影响任何正常功能，却能掐断大量漏洞利用链的中段（很多 exploit 的提权步骤依赖非常用 syscall）。

落地形态两条路：systemd 服务单元里 `SystemCallFilter=@system-service` 一组预定义清单起步，再按需加减；或者用 libseccomp 在代码里精细定义。成本是一次性的行为审计（`strace` 跑一遍正常业务流程，收集真实用到的调用集合），维护成本接近零——行为模型不变，清单就不变。

> 💡 性价比排序的直觉：及格线三件套（几小时）＞ seccomp（一两天）＞ AppArmor 单服务 profile（几天）＞ SELinux 全系统策略（按月计）。从便宜的开始做，每升一档前问威胁清单"这一档在防哪条"。

## <span class="blue">namespace 与容器：边界的真实强度

容器（Docker/podman/嵌入式轻量运行时）在嵌入式上越来越常见——应用打包方便、依赖隔离、OTA 可以按容器更新。它的隔离基础是 namespace（进程看到独立的文件系统/网络/PID 视图）加 cgroup（资源限额）。

安全上要记住一句话：**容器是进程隔离，不是安全边界**。所有容器共享同一个内核——容器内拿到 root 且触发一个内核漏洞，就拥有了宿主的一切。相比之下虚拟机（第 35 章）有独立内核，边界硬得多。所以容器的正确安全定位是：**它把"应用之间的依赖和文件"隔开了，但没有把"内核漏洞"隔开**。用容器承载不可信负载（比如第三方插件）时，容器必须再叠加 seccomp+降权+只读文件系统才够看。

嵌入式容器的合理用法：不可信程度不同的业务分容器跑（联网服务一个、本地业务一个），每个容器按上面三件套+seccomp 加固，容器间通信用受控接口（unix socket 而非共享文件）。这在不付出 VM 开销的前提下，把横向移动的成本抬高了一个量级。

## <span class="blue">纵深组合的成本账

把本节手段按"防御强度/维护成本"两个轴摆开，选型就是按预算点菜：

| 手段 | 防御什么 | 一次性成本 | 维护成本 |
|------|---------|-----------|---------|
| 降权+文件归属 | 爆炸半径 | 几小时 | 近零 |
| capability 细分 | root 全能拆分 | 几小时 | 近零 |
| systemd 沙箱指令 | 文件系统/权限边界 | 每服务半小时 | 近零 |
| seccomp | 内核攻击面收缩 | 一两天审计 | 近零 |
| AppArmor profile | 单服务行为边界 | 每服务几天 | 低 |
| SELinux 全策略 | 系统级行为边界 | 周级起 | **中~高（长期人力）** |
| 容器+加固 | 业务间隔离 | 架构级 | 中 |

两个叠加原则：**手段之间要正交**（seccomp 管 syscall、MAC 管对象访问、降权管身份，互不重复）；**成本最高的一层必须有威胁清单背书**（通常是 SELinux 或容器化改造，这两个决策错配的代价以人月计）。

## <span class="blue">方案对比（Trade-off）

| 维度 | 评价 |
|------|------|
| SELinux vs AppArmor | 表达力与背书 vs 可维护性；团队无专职安全人力时 AppArmor 是现实上限 |
| MAC vs seccomp | 对象级边界 vs 接口级收缩；seccomp 便宜一个数量级，先做它 |
| 容器 vs VM | 进程隔离省资源 vs 内核级硬边界；不可信负载才值得 VM，业务隔离容器+加固够用 |
| permissive 模式 | 调试期的必要过渡；量产必须切 enforcing，否则等于没开 |
| 自写策略 vs 发行版基线 | 基线策略覆盖通用服务，自写只补业务进程——别从零造轮子 |

## <span class="blue">本节总结

运行时安全控制的是"单个进程被攻破的爆炸半径"，手段按性价比分四层：及格线三件套（降权/capability/文件归属，几小时零维护）消灭一半真实影响面；seccomp 用一两天把内核攻击面砍掉大半，是被低估的性价比之王；MAC 按决策树上——合规点名就选 SELinux，高威胁选 AppArmor 起步，不够格就老实不做，开了又调成 permissive 比不开更糟；容器是依赖隔离不是安全边界，承载不可信负载必须叠加三件套加 seccomp。所有手段的选择都指回 19.1 的清单：每一层要能说出在防哪一条，成本最高的那层尤其如此。

关键结论速查：

| 问题 | 一句话答案 |
|------|-----------|
| 运行时安全防什么 | 单进程被攻破后的横向移动与提权 |
| 零成本第一刀 | 服务降权 + 文件归属收紧，几小时见效 |
| 需要绑低端口怎么办 | `CAP_NET_BIND_SERVICE` 一个位，不给整个 root |
| MAC 决策第一问 | 有没有合规点名？没有就问威胁清单象限 |
| 最被低估的手段 | seccomp——行为固定的守护进程做 syscall 白名单 |
| 容器的安全定位 | 进程隔离不是内核边界，不可信负载要叠加固或上 VM |
| SELinux 的最大风险 | 没人力维护 → 调成 permissive → 昂贵的日志系统 |
| 手段叠加原则 | 正交不重复；最贵的一层必须有清单背书 |

### 本节自查

- 能对手上系统的守护进程做一次 root 审计，列出该降权的名单
- 能为一个服务写出 systemd 沙箱配置（User/capability/ProtectSystem/NoNewPrivileges）
- 能走通 MAC 决策三问并给出选型与理由
- 能解释 seccomp 为什么在嵌入式守护进程上性价比最高，并说出审计方法
- 能向同事说清"容器不是安全边界"的论据和正确加固姿势
- 能按成本账表给一个产品排出运行时安全的实施顺序
