# 19.4 密钥管理与 TPM：最硬资产的保险箱选型

> 所属章节：第19章 安全架构设计
>
> 难度：[M] ~ [E] | 预计阅读时间：30 分钟

## <span class="blue">本节导读

前面三节的防御最后都会收拢到同一个问题上：安全启动的验签靠公钥，TLS 双向认证靠私钥，OTA 验签靠公钥，全盘加密靠密钥——**整个安全体系的强度，最终等于密钥存放处的强度**。密钥放在 Flash 明文里，19.2 的启动链就是个昂贵的仪式：攻击者拆 Flash 读出私钥，签名伪造、通道劫持全部解锁。

19.1 的清单里，"拆 Flash 离线读出设备私钥"通常是"低可能×高影响"——概率不高，但一旦得手是灾难性的批量损失（所有用这把密钥的设备全部沦陷）。这一象限的正确处置是上硬件。密钥管理要回答的就是：密钥分几层、每层放哪、硬件载体选哪家、产线怎么烧进去、产品退役时怎么办。

> 本节覆盖：密钥层次与"一设备一密钥"原则、四种存储载体的对比（eFuse/TPM/安全元件/OP-TEE secure storage）、TPM 2.0 的功能边界与 Linux 软件栈、OP-TEE 安全存储的玩法、密钥生命周期的量产流程设计、按威胁清单选型的决策。

## <span class="blue">密钥层次：不要一把钥匙开所有门

设备里的密钥不是一把，是一个层次体系，每层的安全要求和使用频率不同：

```text
根密钥（设备身份，出厂注入，终身不变，极少使用）
  │  派生
  ├── 存储加密密钥（加密 Flash 分区，随每次解锁使用）
  ├── 通信私钥（TLS 客户端证书，每次连云使用）
  └── 会话密钥（每次连接临时协商，内存中生灭）
```

层次的意义是**损失隔离**：会话密钥泄露只影响一次连接；通信私钥泄露影响一台设备；根密钥泄露影响的是这台设备的整个身份——而全网共用一把根密钥的泄露，就是产品线级灾难。

由此引出密钥管理的第一原则：**一设备一密钥**。每台设备的根密钥在产线上独立生成（或独立注入），全网没有任何两台设备相同。对手拆解一台设备、付出最高成本读出了密钥——他得到的只是一台设备的身份，克隆不了产品线。这条原则是"按第二档对手设计"时最划算的投资：它不改变单台设备被攻破的概率，却把"攻破一台"的收益压到接近零，让黑产的批量攻击模型直接破产。

> 密钥派生（Key Derivation）：用根密钥加一个上下文标签（设备序列号、用途字符串），经 KDF 算法算出子密钥。子密钥泄露可以从根密钥换标签重派一把，根密钥本身从不出保险箱。这把"轮换"从换锁变成了换钥匙胚。

## <span class="blue">四种存储载体对比

密钥的"保险箱"有四档主流载体，按安全强度和成本同步递增：

| 载体 | 机理 | 防拆读能力 | BOM 成本 | 生态与坑 |
|------|------|-----------|---------|---------|
| 软件加密存储 | 密钥加密后放 Flash，加密密钥从设备特征派生 | 弱：拆 Flash+逆向算法即可还原 | 0 | 只挡最低档对手；防"批量复制"尚可，防定向拆解无效 |
| eFuse/OTP | 密钥烧进 SoC 熔丝区，软件不可读出（只能作为硬件引擎的输入使用） | 中：需芯片级攻击（去封装、探针） | 0（SoC 自带） | 容量极小（几十~几百字节）；烧录不可逆；不同 SoC 的硬件加速接口差异大 |
| OP-TEE secure storage | 密钥存安全世界，普通世界只能通过 TA 调用"用密钥"不能"读密钥" | 中高：需攻破 TEE 本身 | 0（软件方案） | 依赖 19.2 上了 OP-TEE；存储介质本身在 Flash（加密存放），防的是"读出明文" |
| TPM 2.0 / 安全元件（SE） | 独立安全芯片，密钥永不出芯片，所有运算在片内 | 高：防物理探针、防故障注入，有防拆认证（如 CC EAL4+） | $0.5~3 | I2C/SPI 接口；速率低（只适合密钥运算不适合批量加解密）；供应链多一家 |

读这张表抓两个要点。**一是"不可读出"是分水岭**：eFuse、OP-TEE、SE 的共同特征是密钥只能被"使用"不能被"读取"——系统里任何进程（包括 root）都拿不到明文，能拿到的只有"用这把密钥做一次签名/解密"的服务。软件存储做不到这一点，这就是它垫底的原因。**二是成本跳变点**：eFuse 和 OP-TEE 是零 BOM（SoC 能力范围内），SE/TPM 是实打实的美元——19.6 的 $3 预算能不能放下它，是门锁案例的核心决策。

> TPM 与安全元件的区别：TPM（Trusted Platform Module）是按 TCG 规范实现的标准化安全芯片，功能面向"平台可信"（密钥保管、度量启动、远程证明）；SE（Secure Element）是更泛的称谓，面向"密钥与支付"（如 NXP A71CH、ST STSAFE）。嵌入式 Linux 语境下两者用法高度重叠，SE 通常更便宜、认证更聚焦，TPM 的度量启动和证明功能是 SE 没有的。

## <span class="blue">TPM 2.0：功能边界与 Linux 软件栈

选 TPM/SE 时先搞清它能干什么、不能干什么，避免按"安全芯片=万能"的错误预期设计。

**能干的三件事。密钥保管与片内运算**：私钥生成和签名/解密都在片内完成，明文永不出片——这是主用途。**度量启动（Measured Boot）**：启动各阶段的哈希被记录进 TPM 的 PCR 寄存器，形成一份"我启动的是什么软件"的可信记录——注意它和 19.2 的安全启动是互补不是重复：安全启动是"不合格就拒绝启动"，度量启动是"启动了什么如实记账，供事后验证"。**远程证明（Attestation）**：设备向云端证明"我当前运行的软件栈哈希是这些"，云端据此决定是否信任这台设备——这是大规模 fleet 可信管理的基建。

**不能干的事**：TPM 不是加密加速器，批量数据加解密走 SoC 的硬件加密引擎（CAAM/AES-NI），TPM 只保管密钥和做小数据量运算；TPM 也不防设备物理被毁，它防的是"密钥被提取"。

Linux 软件栈三层：内核驱动（`tpm_tis`/`tpm-i2c`，设备树里挂 I2C 节点）→ `tpm2-tss`（用户态库）→ `tpm2-tools`（命令行）与应用绑定（OpenSSL engine、dm-crypt 密钥封存）。内核 keyring 可以把 TPM 封存的密钥挂进内核钥匙环供 dm-crypt 这类子系统使用——"Flash 加密密钥封在 TPM 里，启动时解封"是工业设备防拆盘的经典组合。

## <span class="blue">OP-TEE 安全存储：零 BOM 的中间档

19.2 如果上了 OP-TEE，密钥管理就多了一个零成本选项：TA（Trusted Application，安全世界里的小程序）持有密钥，CA（Client Application，普通世界）只能发起"用它签名/解密"的请求。存储形态是安全世界把密钥加密后放 Flash（防的是明文落盘），加密密钥来自 SoC 的硬件唯一密钥（HUK，每颗芯片不同且不可读出）——这意味着加密后的密钥文件即使被整盘拷走，换一块板子也解不开。

这套组合（HUK + OP-TEE + RPMB）的强度定位：防住了"拆 Flash 离线读取"（19.1 清单上那条低×高），防不住"攻破 TEE 本身"（TEE 也有漏洞史，只是攻击面比普通世界小几个量级）。对多数消费级产品，这是投入产出比的甜点——零 BOM、复用已有的 OP-TEE 基建、把最高危资产从普通世界拿走。

> RPMB（Replay Protected Memory Block）：eMMC 上的一个特殊分区，读写需密钥认证且带防重放计数器——写入旧数据会被拒绝。它是"防回滚"和"安全存储"在存储介质上的硬件支撑：OP-TEE 的安全存储默认放 RPMB，没有 RPMB 的平台（SPI NAND 方案）强度要打折评估。

## <span class="blue">密钥生命周期：产线到退役的流程设计

密钥安全问题的一半在产线流程，不在芯片。完整生命周期五段，每段都有典型事故：

**生成。** 设备密钥应该在设备上生成（TPM/SE 片内生成，私钥从不离开芯片），而不是在服务器上生成后注入——注入意味着密钥以文件形式流过产线网络和烧录工位，每一步都是泄露点。必须注入的场景（如厂商 CA 签发的证书），注入通道本身要加密且工位要管控。

**烧录。** eFuse 烧录是不可逆工序：烧录文件按"最小可见"管控（烧录软件只接触哈希或加密后的密钥材料），工位权限独立，烧录日志留档。19.2 的警告在这里再叠加一层：密钥烧错不只变砖，还可能造成"一批设备共用一把错密钥"的隐蔽事故。

**使用。** 正常世界里密钥永不以明文出现——应用通过 PKCS#11、OpenSSL engine 或 TA 接口"调用"密钥。代码评审的一条红线：全局搜索密钥材料的明文落盘（日志打印、core dump、临时文件）。

**轮换。** 根密钥不换，派生密钥可换——通信证书要有到期换发机制（设备证书有效期设多长、到期前怎么OTA续期，是要在架构期回答的问题；答不上来的产品会在第 3~5 年迎来一批证书集体到期的故障潮）。

**退役。** 产品 EOL 时密钥怎么办：TPM/SE 有清除指令，设备回收流程里要有"密钥销毁"一步；二手市场上流出带有效设备证书的旧设备，是设备身份体系的慢性出血。

## <span class="blue">方案对比（Trade-off）

| 维度 | 评价 |
|------|------|
| 设备上生成 vs 服务器注入 | 前者私钥不出芯片最安全；后者便于统一签发但产线通道成软肋——能生成就不注入 |
| eFuse vs OP-TEE vs SE | 零成本中强度 → 零成本中高强度（依赖 TEE 基建）→ $0.5~3 高强度防拆认证；按威胁清单的"影响"列定档 |
| TPM vs SE | 要度量启动/远程证明选 TPM；只要密钥保管+支付级认证选 SE 更便宜 |
| 软件加密垫底 | 零成本但只挡最低档；用它保护高影响资产等于接受风险——要明示 |
| RPMB vs 普通分区 | RPMB 防重放是安全存储的硬件底座；无 RPMB 平台（SPI NAND）要在方案评审时点名 |

## <span class="blue">本节总结

整个安全体系的强度等于密钥存放处的强度，所以密钥管理的核心是"不可读出"——eFuse、OP-TEE、SE/TPM 三档硬件载体的共同特征是让密钥只能被使用不能被读取，软件加密存储做不到这点，只能垫底防最低档对手。密钥体系分层次（根/派生/会话）实现损失隔离，第一原则是一设备一密钥——把"攻破一台"的收益压到零，黑产的批量模型自然破产。TPM 的边界要记清：密钥保管、度量启动、远程证明三件事，不是加密加速器；OP-TEE+HUK+RPMB 是零 BOM 的甜点组合。另一半战场在流程：密钥能设备上生成就不注入，烧录工位最小可见，派生密钥要规划轮换，退役要销毁——产线到退役的每一段都有对应的真实事故。19.6 的门锁会演示 "$3 预算到底买不买 SE" 的完整推导。

关键结论速查：

| 问题 | 一句话答案 |
|------|-----------|
| 密钥管理的分水岭 | 密钥是"可读出"还是"只能使用不可读出" |
| 第一原则 | 一设备一密钥——攻破一台的收益压到零 |
| 零 BOM 的两档 | eFuse（容量小不可逆）、OP-TEE secure storage（依赖 TEE 基建） |
| TPM 三大功能 | 密钥保管、度量启动、远程证明；不是加密加速器 |
| 安全启动 vs 度量启动 | 不合格拒绝启动 vs 启动了什么如实记账——互补 |
| OP-TEE 存储的底座 | HUK（芯片唯一不可读密钥）+ RPMB（防重放） |
| 产线第一守则 | 能设备上生成就不要注入；烧录文件最小可见 |
| 最常见的远期事故 | 设备证书集体到期——轮换机制必须在架构期回答 |
