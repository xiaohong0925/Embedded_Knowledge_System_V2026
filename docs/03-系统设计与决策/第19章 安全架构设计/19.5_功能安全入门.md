# 19.5 功能安全入门：IEC 61508、ISO 26262 与 Linux 的位置

> 所属章节：第19章 安全架构设计
>
> 难度：[I] ~ [M] | 预计阅读时间：25 分钟

## <span class="blue">本节导读

前面四节讲的"安全"都是 Security——防攻击者。嵌入式工程师迟早会撞上这个词的另一半：Safety，功能安全——**防的不是攻击，是故障**；保护的不是数据，是人。机器人关节控制器的一个软件 bug 可能夹伤人，车载控制器的一次死机可能指向一场事故，这类产品的"安全"是另一套话语体系：IEC 61508、ISO 26262、SIL、ASIL、FMEDA、安全认证。

两个体系的真实碰撞通常以一次误会开场：老板说"我们的产品要做安全认证"，信息安全出身的工程师开始配 SELinux，功能安全出身的工程师开始写 FMEA——两个人说的是两件事。本节目的是给你一套坐标：Safety 在防什么、等级体系怎么读、和 Security 怎么互相影响，以及最关键的现实问题——**Linux 在功能安全产品里到底能放在什么位置**。

> 本节覆盖：Safety 与 Security 的本质分野、IEC 61508/ISO 26262 的等级坐标（SIL/ASIL）、功能安全开发的核心方法（危险分析、安全机制、诊断覆盖率）、Linux 为什么不能做安全关键件以及"分割架构"的通行解法、认证路径的现实成本。

---

## <span class="blue">两套"安全"的分野

| 维度 | 信息安全（Security） | 功能安全（Safety） |
|------|---------------------|-------------------|
| 防什么 | 恶意攻击者 | 随机硬件失效 + 系统性软件缺陷 |
| 保护什么 | 数据、密钥、服务、商业利益 | 人命、健康、财产、环境 |
| 对手模型 | 聪明的、会适应的人 | 物理规律与统计概率 |
| 核心方法 | 威胁模型、纵深防御 | 危险分析、安全机制、量化指标 |
| 标准 | ETSI 303 645、IEC 62443、ISO 27001 | IEC 61508、ISO 26262、EN 50128 |
| 失败后果 | 数据泄露、设备沦陷、召回 | 伤人、死人、刑事责任 |

分野里最微妙的一条是**对手模型**：Security 的对手会研究你的防御然后绕开它，所以安全设计要持续演进；Safety 的"对手"是失效率，它不会研究你——所以 Safety 的方法论是量化统计：计算这个系统每运行一小时发生危险失效的概率，压到标准要求的刻度以下。一个防"聪明人"，一个防"坏运气"，方法论的根系完全不同。

两者的交叉在近年变成硬议题：**联网让 Safety 系统暴露在 Security 威胁下**。一辆车的制动控制器过去只要防故障，现在它联网了，还要防被远程攻击制造故障——所以 ISO 26262 的配套标准 ISO/SAE 21434（道路车辆网络安全工程）出现了，行业共识是"没有 Security 就没有 Safety"。你在功能安全产品里做信息安全，依据的就是这条逻辑链。

## <span class="blue">等级坐标：SIL 与 ASIL 怎么读

功能安全不讲"安全/不安全"，讲**安全完整性等级**——系统把危险失效概率压到了哪个刻度：

**IEC 61508（工业母标准）的 SIL 1~4。** SIL（Safety Integrity Level）按"每小时危险失效概率"分档：SIL1 是 10⁻~10⁻⁵ 量级，SIL3 到 10⁻⁸~10⁻⁷，SIL4（核电站级）到 10⁻⁹~10⁻⁸。等级每升一级，对开发流程、硬件冗余、诊断覆盖率的要求跳一档，成本跳得更多。多数工业产品的目标区间是 SIL2~SIL3。

**ISO 26262（汽车专用）的 ASIL A~D。** 从 IEC 61508 派生，按"严重度×暴露率×可控性"三个因子查表定级：ASIL A 最松，ASIL D 最严（转向、制动这类失效即高危的功能）。另有一个特殊档 **QM（Quality Management）**——"按普通质量体系开发即可，无功能安全要求"。QM 这个档的存在至关重要：它意味着**同一辆车里不同功能的安全等级是不同的**，车窗控制和转向控制不共用一套开发标准。

> 定级（HARA/危险分析）：功能安全开发的第一步——枚举系统的每个功能，分析它失效时可能造成的危险场景，按严重度、暴露率、可控性打分定级。定级决定后续一切：开发流程的严格度、硬件要不要冗余、软件要什么覆盖率。**定级权不在工程师，在系统安全工程师和评审会**——这是功能安全和信息安全在工程文化上的最大差异之一：等级是评出来的，不是选出来的。

## <span class="blue">方法论内核：安全机制与诊断覆盖率

功能安全的工程手段可以收成一句话：**任何单点失效都不能导致危险后果**。落地靠两类机制：

**硬件冗余与监控。** 双通道采样互相校验、看门狗监督主控心跳、独立的安全监控芯片（电压/温度/时钟异常直接进安全态）、锁步核（两个核跑同样的指令流逐拍比对）。注意这些机制大多不需要软件参与决策——它们的职责是"主系统不可靠时，有一条更简单的路径把系统带进安全状态（断电、松刹车、停机）"。

**软件诊断与安全态。** 内存自检（RAM March 测试）、程序流监控（代码是否按预期顺序执行）、通信 CRC 与超时检测、传感器数据合理性校验。每个诊断机制有一个量化指标：**诊断覆盖率（DC，Diagnostic Coverage）**——它能探测到的失效模式占全部可能失效模式的百分比。SIL/ASIL 等级直接对应 DC 的门槛（如 SIL3 要求高 DC 档 ≥90%），这就是"定级决定设计"的具体含义：等级定了，你要堆多少诊断机制就有了硬指标。

> 安全态（Safe State）：系统失效时必须进入的、不造成危险的状态。机械臂的安全态可能是"断电抱闸"，加热设备可能是"切断加热丝供电"。**安全态设计优先于一切**——它回答"当所有软件都不可信时，系统靠哪条最短的硬件路径停下来"。安全态都定义不出来的系统，谈不上功能安全。

## <span class="blue">Linux 的位置：为什么以及怎么办

直接说结论：**Linux 本身没有、也不适合取得功能安全认证**。原因不是代码质量，是认证方法论的要求——SIL2 以上要求软件的失效模式可分析、测试覆盖率可证明、每一行代码有需求可追溯。Linux 内核千万行代码、数十万提交者、没有单一需求文档，这套论证在工程上不可行。历史上也有商业化的"安全认证 Linux"尝试（如 ELISA 项目在推进 Linux 进入安全论证的路径），但 2026 年的现实是：主流做法不是认证 Linux，而是**分割**。

通行的分割架构叫**混合关键性系统（Mixed Criticality）**：安全关键功能和非安全功能分开，各用各的技术栈，中间用受控接口通信。三种典型形态：

**多核异构分割（AMP）。** SoC 里的 Cortex-M 核（或独立 MCU）跑 RTOS/裸机承载安全功能（急停回路、安全监控），Cortex-A 核跑 Linux 干富功能（UI、网络、日志）。两侧经 RPMsg/共享内存通信，安全侧不信任 Linux 侧的任何输入（全部合理性校验）。这是工业网关、机器人控制器的主流形态——20.4 会从实时性视角再讲一次同一架构。

**虚拟化分割。** 用 Jailhouse/Xen 这类静态分区 hypervisor，安全 RTOS 和 Linux 各在一个分区，硬件资源在启动时静态切分。适合单核性能富余、隔离要求更高的场景。

**单系统降级。** 安全等级要求低（SIL1/QM 场景）时，Linux 直接承载，靠"安全相关部分单独按安全流程开发+系统其余部分当干扰源做防护"处理——前提是有正式的自由度论证（Freedom From Interference）：证明 Linux 侧的故障（内存踩踏、资源耗尽）影响不到安全相关部分。这个论证本身就要脱一层皮，所以这条路的适用范围比看起来窄。

> 💡 选型直觉：产品里有"失效会伤人"的功能，第一反应不是"怎么让 Linux 更可靠"，而是"怎么让这个功能不依赖 Linux"。安全回路越短、越简单、越少软件越好——一个独立 MCU 加看门狗的急停回路，比任何 Linux 加固都接近安全的本质。

## <span class="blue">认证路径的现实

最后泼一盆必要的冷水，让你对"做功能安全产品"的资源量级有真实预期：

**流程成本大于技术成本。** 认证审的不只是产品，是开发过程——需求追溯矩阵、变更管理、工具链置信度（你用的编译器本身要被鉴定）、测试覆盖率报告、独立评估。一个团队从"能做出安全产品"到"能拿出安全产品的认证证据"，中间的差距是一个安全流程体系的建设，通常以年计。

**认证机构与顾问是产业链的一部分。** TÜV、exida 这类机构既做评估也做培训咨询；商业 RTOS（SafeRTOS、QNX、Green Hills）的核心卖点就是"带着认证证据包卖"。自研 OS 过认证的总账几乎总是输给买现成认证件——这是功能安全市场被少数商业 RTOS 把持的根本原因。

**入门路径的现实建议。** 工程师个人的切入顺序：先在混合关键性产品里做 Linux 侧（理解安全侧对 Linux 的接口要求），再参与一次危险分析评审（看定级怎么评出来），有余力读 IEC 61508 第 3 部分（软件要求）的目录结构——标准原文极枯燥，但目录本身就是功能安全方法论的骨架。

## <span class="blue">方案对比（Trade-off）

| 维度 | 评价 |
|------|------|
| Security vs Safety 方法 | 防聪明人（持续演进）vs 防坏运气（量化统计）；联网产品两个都要，ISO 21434 是桥 |
| 定级高一点 vs 低一点 | 定高了流程成本白付，定低了认证不过+法律责任——定级必须走正式评审 |
| AMP vs 虚拟化分割 | AMP 物理隔离最简单可靠，多一颗核的 BOM；虚拟化省硬件但要论证 hypervisor 本身——工业主流选 AMP |
| 商业安全 RTOS vs 自研 | 买证据包 vs 自己攒证据；自研过认证的总账几乎必输 |
| Linux 直载（QM/SIL1） | 省架构复杂度；代价是自由度论证与天花板——SIL2 以上别走这条 |

## <span class="blue">本节总结

功能安全（Safety）防故障伤人，信息安全（Security）防攻击获利，对手模型一个是物理统计一个是聪明人类，联网产品两者都要——"没有 Security 就没有 Safety"是当代共识。Safety 的等级是评出来的：IEC 61508 的 SIL 1~4 和 ISO 26262 的 ASIL A~D 按危险失效概率划档，QM 档让同一产品不同功能各按其级。方法论内核是"单点失效不导致危险"：硬件冗余、诊断机制、安全态三件套，诊断覆盖率把等级翻译成设计指标。Linux 进不了认证，通行解法是混合关键性分割——AMP 异构核承载安全回路，Linux 干富功能，安全侧永远不信任 Linux 的输入。认证的真实成本在流程证据不在技术，这也是商业安全 RTOS 存在的理由。对工程师的现实定位：你大概率不会亲手做安全回路，但你做的 Linux 系统会和安全回路共存——理解它的边界要求，就是本节的目标。

关键结论速查：

| 问题 | 一句话答案 |
|------|-----------|
| Safety 和 Security 的本质区别 | 防故障伤人（统计）vs 防攻击获利（对抗） |
| SIL/ASIL 是什么 | 危险失效概率的等级刻度，评审定级不是自选的 |
| QM 档的意义 | 同一产品不同功能安全等级不同——无要求功能按普通质量流程 |
| 方法论一句话 | 单点失效不导致危险：冗余+诊断+安全态 |
| 诊断覆盖率（DC） | 等级翻译成设计指标的桥梁，SIL3 要求高 DC 档 |
| Linux 的位置 | 不做安全关键件，混合关键性分割里干富功能 |
| 安全侧对 Linux 的态度 | 永远不信任，全部输入做合理性校验 |
| 认证的真实成本 | 流程证据体系建设，以年计；买认证件 RTOS 是主流 |
