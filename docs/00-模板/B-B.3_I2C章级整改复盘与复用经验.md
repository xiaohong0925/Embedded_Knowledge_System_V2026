1. **应当复用的内容**：唯一主问题、手工完整基线、首次依赖、参与者时序、实例贯穿、正常与错误路径、盲删、四种读者和验证分层。

6. **最新用户确认优先**：旧方案或旧验收记录 `next_action` 若要求恢复用户已经取消的交付物，必须先更新方案，不得沿旧记录施工。

## 一、这次整改究竟解决了什么

### 1. 章级主问题

全章最终围绕一个问题组织：

> 一笔 I2C 访问，怎样从两根信号线进入 Linux 代码，变成真实器件读写，并在失败时取得证据？

六篇不再各自堆积一套名词，而是分别回答主线上的一个环节：

| 篇目 | 当前主问题 | 整改后的主要产出 |
|---|---|---|
| B-B.3.1 | 为什么软件参数相同，物理总线仍可能失败？ | 电气边界、速率、仲裁和地址冲突的判断依据 |
| B-B.3.2 | 软件请求怎样变成 START、地址、数据、ACK/NACK 和 STOP？ | 一笔读取从软件字段到线上帧的逐拍解释 |
| B-B.3.3 | Linux 怎样把板级描述、外设协议和可替换控制器连起来？ | 源码地图、对象关系、完整教学代码和控制器替换路径 |
| B-B.3.4 | 一笔访问失败时，怎样逐层缩小故障范围？ | 命令、完整程序、trace、逻辑分析仪和示波器的证据链 |
| B-B.3.5 | 一颗真实 EEPROM 怎样可靠完成端到端读写？ | 正常产品路径、页写与写周期、内核实现和受控对照实验 |
| B-B.3.6 | 已有 I2C 后，SMBus、PMBus 和 pmbus/hwmon 还解决什么问题？ | 同一电压读取在 raw、SMBus、PMBus 三条路径上的工作分配 |

### 2. 核心变化

本轮最重要的变化不是“增加了多少字”，而是改变了材料组织方式：

- 从**按名词分节**改为按同一笔操作的输入、处理、状态和结果推进；
- 从**先讲抽象框架**改为先让读者看见一笔完整操作，再拆框架职责；
- 从**只给调用链和片段**改为正文解释机制，步骤片段定位当前动作，完整函数恢复上下文，完整源码提供核验依据；
- 从**只展示成功路径**改为同时推演失败、清理、恢复、重绑和并发参与者；
- 从**把构建当验证**改为分别登记源码核验、浏览器检查、软件构建、目标板运行和仪器测量。

## 二、六篇实际整改记录

### 1. B-B.3.1：物理层与电气特性

**原断点**

- 开漏、线与和共享总线容易停留在定义，读者不容易把它们与 ACK、仲裁和地址冲突连起来。
- 上拉电阻、总线电容的长计算和电平兼容展开过深，偏离软件工程师判断“继续改软件还是转查硬件”的需要。
- “两个同地址设备”容易被误解成总线按先后顺序选择一个设备。

**实际改法**

- 用同一组 SoC、AT24C02、SHT30 和 DS3231 总线贯穿开漏、线与、速率、时序、电平和地址条件。
- 接入开漏、线与／ACK、时序与 RC 三个交互演示，但保留正文自己的因果解释。
- 删除偏原理图设计的电阻与电容长计算，保留上升沿、采样和软件配置不能改变物理波形这些必要边界。
- 电平部分收束为两个软件人员必须会提出的问题：接收方能否识别，引脚能否承受。
- 明确同地址冲突不是“先到先得”：两个设备可能同时响应，ACK 正常也不能证明数据语义正确。

**当前资产**

- `html/open-drain-demo.html`
- `html/wired-and-ack-demo.html`
- `html/i2c-timing-rc-demo.html`

**验证边界**

正文机制与演示用于教学推演，不证明某块板卡的上拉、电容、电平、波形或同地址行为已经测量。

### 2. B-B.3.2：协议层与帧格式

**原断点**

- START、STOP、ACK 和重复 START 若分开背定义，读者仍无法把软件地址、寄存器地址和读回数据对应到一笔抓包。
- 主设备末尾 NACK、STOP 对内部访问位置的影响、时钟延展与总线清除容易混成“传输失败”的笼统描述。

**实际改法**

- 当前正文固定使用“从 `0x50` 的寄存器 `0x01` 读取一字节，得到 `0xAB`”作为主实例。
- 把 `0x50` 与写方向地址字节 `0xA0`、读方向地址字节 `0xA1` 的换算写清，避免把线上地址字节传给 Linux 的 7 位地址参数。
- 用同一笔事务解释第 9 拍、重复 START、主设备末尾 NACK 和 STOP，并逐字段还原最终抓包。
- 分别推演时钟延展、SDA 卡低补钟和 SCL 持续拉低，避免把等待与恢复当成同一件事。
- 保留 10 位地址扩展和三个交互演示，扩展内容不抢占主实例。

**当前资产**

- `html/i2c-race-condition-lanes.html`
- `html/i2c-clock-stretch-bus-clear-demo.html`
- `html/i2c-10bit-address-demo.html`
- `images/b-b-3-2-repeated-start.png`

**验证边界**

抓包序列是依据协议规则构造的教学示例，不是本篇在目标板上采得的实测数据。

### 3. B-B.3.3：Linux 驱动框架

**原断点**

- “三层”“五个对象”的抽象讲法没有回答寄存器操作去了哪里，也没有让读者形成代码主干。
- 结构体只给名字或字段结论，`client`、`algo`、`I2C_M_RD`、`I2C_FUNC_I2C` 等首次依赖缺少可跟随的定义与使用场景。
- DTS 属性停在“给驱动看”，没有继续跟到读取、转换和生效代码。
- `/dev/i2c-N` 的来源、匿名 client 和完整用户程序之间缺少闭环。
- 对熟悉直接修改厂商 SDK 或寄存器驱动的读者，没有说明复用框架究竟改变了谁的职责。

**实际改法**

- 开头直接回答：寄存器操作没有消失，而是集中由控制器驱动负责；外设驱动描述器件事务，Core 负责连接与通用语义。
- 先给 Linux 源码地图，再沿同一笔读取介绍 Core、`i2c_msg`、`i2c_client`、`i2c_adapter`、`i2c_algorithm`、`i2c_driver` 和 RK3568 控制器。
- 把 DTS → adapter/client → probe、Core → algorithm → 控制器、`clock-frequency` 的生效路径和 GPIO 位模拟替换路径接成主干。
- 增加完整教学模块、用户态程序、DTS、GPIO DTS 与 Makefile，解释返回值、消息数和读取值的区别。
- 用两个进程的操作序列区分独立文件状态与共享 adapter／总线锁。
- 增加 I2C Framework Lab，让正文、步骤片段、完整函数和完整源码可以相互回查；提炼出通用 Framework Lab 模板。

### 4. B-B.3.4：调试工具与故障排查

**原断点**

- 工具清单、命令输出和内核函数各自成立，但没有围绕同一笔读取组成证据链。
- `i2c-dev` 的匿名 client、消息复制、锁、返回值和用户态回拷没有完整出现。
- 容易把 `UU`、NACK、全 `0xff`、`EFAULT` 或偶发失败直接等同于某个根因。

**实际改法**

- 先确认总线和占用，再解释扫描结果中的 `50`、`--`、`UU`，把内核驱动与用户进程视为不同访问者。
- 用 `i2cget` 和 `i2ctransfer` 表达同一类读取，说明固定 SMBus 事务与显式消息组合的选择依据。
- 给出完整 C 程序，贯穿 `I2C_RDWR`、两条消息、返回值 `2` 和最终四字节检查。
- 沿 Linux v6.6 源码解释匿名 client、内核缓冲区、Core 持锁、控制器完成数和 `copy_to_user()`；明确 `EFAULT` 不代表总线从未执行。
- 用 tracepoint 对齐消息、数据和完成数，再分别用逻辑分析仪检查协议、示波器检查电平与边沿。
- 每种证据都必须改变下一步，不再建立“一个症状必然对应一个根因”的速查幻觉。

### 5. B-B.3.5：AT24C02 EEPROM 端到端读写

**原断点**

- 开头过早进入 `dd` 和源码，读者尚未从手册理解真实页大小、页内回卷、WP 和写周期。
- 正常产品使用路径被排障与源码逆向推迟，失败实验容易替代正常读写闭环。
- at24、regmap、NVMEM 的对象关系、8＋4 切页、非对齐 6＋2 和锁顺序没有统一到一个实例。
- `/dev/i2c` 对照路径如果没有隔离与恢复，会干扰正式驱动和芯片内容。

**实际改法**

- 先读 AT24C02C 手册，再进入 DTS、Kconfig、at24/regmap/NVMEM 建链。
- 正常产品实验优先：备份不足 256 字节必须停止，之后才能写读、比较边界并按需恢复。
- 用从 `0x10` 写 12 字节解释为什么必须拆成 8＋4，以及不拆时为什么得到页内回卷结果。
- 继续推演非对齐 6＋2、RK3568 不支持 `I2C_M_NOSTART` 时的 regmap 线性化回退、写失败重试和返回口径。
- 完整 `/dev/i2c` 对照程序自行完成页切分、等待、复合读和 `memcmp()`，并明确解绑、停止其他访问者和恢复顺序。
- 用 A/B/C 三个参与者区分 at24 实例锁与 I2C 总线锁；重绑后新建软件对象，但 EEPROM 内容不自动清空。

### 6. B-B.3.6：SMBus 与 PMBus

**原断点**

- 没有先回答“明明已有 I2C，为什么还需要 SMBus 和 PMBus”，三条路径容易变成新的名词分层。
- raw、SMBus、pmbus/hwmon 的代码量与工作分配不直观，读者会怀疑绕开它们、自行用 I2C 加应用解析是否等价。
- PAGE 共享状态、VOUT_MODE 解码、页恢复、PEC 和 hwmon 属性编号缺少同一笔数据上的完整推演。

**实际改法**

- 用同一笔 TPS40422 第二路电压读取，按 raw I2C → SMBus → pmbus/hwmon 的顺序逐层减少手工工作。
- 固定 `PAGE=1`、`VOUT_MODE=0x17`、`READ_VOUT=0x8B`，将 `00 03` 组合为 `0x0300=768`，再按指数 `-9` 解码为 `1.5 V` 和 `1500 mV`。
- raw 路径自己处理页切换、模式读取、事务组织、恢复与解码；SMBus 复用固定事务；正式驱动继续复用页缓存、锁、解码与 sysfs 导出。
- 用交错访问说明 `PAGE` 是器件共享状态，`old_page`、`currpage` 和 `update_lock` 分别解决什么问题。
- 推导 `in2_input` 的属性编号，说明负错误不能继续解码成电压，PAGE 恢复也要读回，PEC 标志需要保存与恢复。
- 明确“可以完全不用 SMBus/PMBus 框架”在技术上可行，但调用者因此必须自行承担事务语义、共享状态、恢复、解码、错误传播和导出接口。

## 三、贯穿实例：统一语义，不机械统一数字

早期设计稿曾计划把更多篇目统一成 `0x10/Hell`，实际施工没有全部照此执行。复盘必须保留这个事实，不能倒写成“全章已经使用同一组数值”。当前各篇主实例为：

| 篇目 | 当前实际实例 | 它主要回答的问题 |
|---|---|---|
| B-B.3.1 | 多设备共享总线 | 物理条件与地址冲突 |
| B-B.3.2 | `0x50`、寄存器 `0x01`、读回 `0xAB` | 一笔协议帧怎样逐拍成立 |
| B-B.3.3 | `0x50`、寄存器 `0x10`、读回 `0x5a` | Linux 对象和函数怎样接力 |
| B-B.3.4 | `0x50`、偏移 `0x10`、读回 `Hell` | 多层证据怎样对齐 |
| B-B.3.5 | 从 `0x10` 写读 `Hello-EEPROM` | 页写、写周期与系统集成 |
| B-B.3.6 | TPS40422 `PAGE=1`、`0x0300`、`1500 mV` | 三种软件路径怎样分工 |

由此得到一条更准确的复用规则：

1. **单篇内部必须统一。** 正文、代码、输出、Q&A 和实验室中的地址、长度、数据、返回值不能各自变化。
2. **相邻篇目必须能换算和区分。** 若使用不同实例，要在首次出现时说明当前设备、寄存器、长度和目的，不能让读者误以为是同一笔数据被写错。
3. **跨篇统一服务于主线，不为了形式一致牺牲最合适的教育实例。** 协议篇的一字节读取适合逐拍解码，EEPROM 的 12 字节写入适合暴露页边界，PMBus 的固定样本适合完整解码。
4. **全量复检要检查衔接，而不是只搜索数字。** 若当前篇目没有说清“这是另一笔教学访问”，应记录为跨篇衔接问题，再按单节流程处理。

## 四、可复用的正文写作规范

### 1. 先确定唯一主问题，再决定材料顺序

一节只承担一个主问题。每个小节必须推进“输入 → 对象／机制 → 状态变化 → 输出／证据”，不能只因某个名词相关就加入。若删除小节后主线完全不受影响，应重新判断它是否属于本篇。

### 2. 先建立手工完整基线，再讲框架减少了什么

读者先看见一笔操作不依赖高级封装时需要完成哪些工作，才能理解辅助函数、子系统或正式驱动真正省掉了什么。先给抽象分层，再让读者自己想象底层工作，通常只会增加名词负担。

### 3. 首次依赖必须在首次使用前解释

术语、结构体字段、宏、函数、命令参数和输出字段，应在首次使用前就地解释，或链接到确实讲过该内容的准确前置篇目。Q&A 只能检查理解，不能替正文补课；源码地图和实验室引入的新名词也受同一约束。

### 4. 比较两个对象前，双方都要先出现

不能只介绍推荐方案，再拿一个读者尚未见过的方案作对照。比较应落在同一笔操作上，说明双方分别负责什么、保留什么、失败时谁处理，而不是只列优缺点。

### 5. 结构体必须进入操作序列

讲解结构体至少回答：

- 谁创建、谁持有、谁销毁；
- 当前操作使用哪些字段，初值从哪里来；
- 哪行代码改变字段或对象关系；
- 哪些状态被共享，哪些状态每次调用独立；
- 成功、失败和清理路径分别留下什么结果。

只给字段表不能替代这些推演。

### 6. 共享状态必须至少有两个参与者

锁、缓存、器件页、内部地址和软件副本，必须通过参与者 A、B 的具体时间序列说明。若只有一个参与者，通常只能证明字段存在，不能证明为什么需要同步、保存、恢复或失效处理。

### 7. 调用链只是目录，完整函数才是代码上下文

正文调用链负责定位，不能代替关键行解释。步骤片段回答“现在看哪里”，完整函数回答“前后还有什么”，完整源码回答“这份定义从哪里来”。三者的路径、版本、行号和高亮必须指向同一份原文，不能手工拼出看似连续的假代码。

### 8. 正常产品路径先于排障和源码逆向

先让读者在推荐路径上完成一次正常操作，再进入失败注入、替代路径和内核实现。不能用“故意写坏看现象”代替正常闭环，也不能把只适合受控实验的强制访问写成日常默认操作。

### 9. 错误、清理和恢复属于主机制

负错误、短传输、部分写入、回拷失败、解绑、重绑和恢复错误都应沿主实例说明。第二笔失败不等于第一笔未发生，`EFAULT` 不等于硬件未执行，重绑也不等于旧运行时对象仍然存在。

### 10. 实验判据不能把动态值硬改成常量

备份长度、实时遥测、硬件状态和并发结果不一定是确定性常量。实验应先检查前提，不满足就停止或记录当前值，再按语义判断；不能为了让脚本“通过”而把动态观测写成固定预期。

### 11. 正文必须盲删成立

删除 iframe、图片、表格、代码块和命令输出后，剩余正文仍应保留完整因果、状态和验证论证。图表与实验室用于降低跟随成本，不承担正文中缺席的唯一解释。

### 12. Q&A 检查真正的理解障碍

问题应覆盖首次依赖、对象生命周期、共享状态、返回口径、错误恢复和验证边界，不重复正文标题，不用“是否理解了某某”的勾选表代替回答。

## 五、交互实验室复用规范

通用操作细节已写入 [Framework Lab 可复用模板](./framework-lab-template/README.md)，B-B.3.3 是领域参考实现。本次整改进一步确认以下原则：

1. **先写正文源码地图，再做实验室。** 不从控件和动画倒推知识结构。
2. **一个领域实例对应一份源码真源。** 完整代码由指定文件提取，片段、完整函数和源码工作台不能维护三份互相漂移的副本。
3. **每一步同时显示代码位置、对象状态和观察结果。** 只高亮一行调用，不解释为什么执行、改变了什么，仍然无法跟随。
4. **正常、失败、共享状态和恢复场景都应从同一实例出发。** 失败场景要显示判断、未执行部分、清理、返回值和调用者动作。
5. **正文与实验室可以并排。** “在新标签页打开”使用 `target="_blank" rel="noopener noreferrer"`，避免覆盖正文，便于双屏对照。
6. **移动端允许代码区自身滚动。** 页面主体不能整体横向溢出，长路径应可换行，控件在窄屏仍可点击。
7. **浏览器通过只代表 DOM 模型通过。** 不得把状态机推演写成真实总线、存储芯片、传感器或仪器仿真。

新增其他 Linux 子系统实验室时，应复制交互骨架和验收方法，不照搬 I2C 的对象、目录和状态数据。

## 八、全量复检时的使用方式

### 1. 先区分三类问题

- **正文教学问题**：依赖、主线、盲删或跟随仍无法回答，按对应单节 reopen，不用复盘文档替正文遮缺。
- **跨篇衔接问题**：实例、术语、前置链接或职责边界不清，先记录具体段落，再确认只改哪一篇。
- **真实验证缺口**：需要编译器、目标板、器件或仪器才能补齐，不通过润色文字把它改写成已验证。

### 2. 不把以下内容误判为已经完成

- 旧设计稿中的计划顺序、统一数字计划或“待创建资产”，不代表当前状态；实际资产以本复盘和文件系统为准。
- 本复盘记录了阶段性整改，不代表正在全量复检的用户已经认可所有细节。
- 有代码、DTS、Makefile 和实验室，不等于已经具备可部署镜像或完成目标板实验。
- 某一篇浏览器测试通过，不等于全章所有演示和实验室都通过。

### 3. 每篇断点仍须可续作

后续暂停、压缩上下文或切换会话时，每篇至少留下：

```text
当前篇目：
唯一主问题：
实际修改文件：
已完成源码／手册核验：
已完成浏览器／软件验证：
未完成的编译、运行、上板与仪器验证：
当前正文与配套资产：
四种读者检查仍存的问题：
下一步唯一动作：
```

断点不能只写“进行中”“已优化”或“构建通过”，也不能只复制旧计划。它必须让下一位读者不问作者，也能知道当前真实进度和下一步该做什么。
