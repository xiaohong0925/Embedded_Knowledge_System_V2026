# 流程文档：章节复检与整篇重写 SOP

**负责人：** 项目所有者负责人工决策与最终验收，当次执行 AI 负责诊断、修改、证据和断点记录  
**最后更新：** 2026-11-10  
**审核周期：** 每次形成新的人工复检经验、调整规则或发现流程性漏检后更新

> 本 SOP 是操作索引，不是第三套规则真源。写作与验收以 `agent.md`、`plan.md` 为最高依据；本文件与它们冲突时，立即以规则文件为准并修正本文件。

## 一、目的

把全书复检从“依赖某个会话或某个模型记住写法”，变成可以暂停、换会话和逐节续作的工作流程。

本流程要解决四类反复出现的问题：

1. 局部事实正确，但整篇没有主问题、实例和教学闭环；
2. 把其他篇目的代码、图表或实验室要求机械套到当前篇目；
3. 把静态检查、严格构建或验收记录 `current` 误写成教学质量通过；
4. 上下文切换后，旧计划、旧自评和最新用户确认相互冲突。

## 二、范围

### 包含

- 主线与扩展篇的单节复检、局部修复和整篇重写；
- 章级、节组级设计与跨篇边界检查；
- 正文、图示、交互资产、教学代码和命令示例的配套验收；
- 新会话交接、机器可读记录和人工复检闭环。

### 不包含

- 未经用户确认的一次性跨多节批量改写；
- 用行数、字数、标题数量或图片数量代替质量判断；
- 没有真实环境支撑的编译、上板、仪器或功能验证声明；
- 为历史章节批量回填没有证据的 `pass`。

## 三、角色与责任

| 步骤 | 执行者（R） | 决策者（A） | 咨询依据（C） | 知会对象（I） |
|---|---|---|---|---|
| 最小上下文与差异检查 | 当次执行 AI | 项目所有者 | `agent.md`、`plan.md`、Git 差异 | 后续会话 |
| 章级／节组级设计 | 当次执行 AI | 项目所有者 | 对应设计大纲、相邻目录与正文 | 后续会话 |
| 单节诊断与重写方案 | 当次执行 AI | 项目所有者 | 人工复盘、相近正例、源码与手册 | 项目所有者 |
| 正文与配套资产修改 | 当次执行 AI | 项目所有者 | 已确认方案、首次依赖和证据区间 | 后续会话 |
| 自动检查与语义验收 | 当次执行 AI | 项目所有者 | 四种读者、浏览器、编译和构建结果 | 项目所有者 |
| 最终教学质量判定 | 项目所有者 | 项目所有者 | 实际正文、资产和 AI 证据 | 后续会话 |
| 复盘与 SOP 更新 | 当次执行 AI 提议 | 项目所有者确认 | 人工否决点和可复用经验 | 全部后续会话 |

AI 可以给出 `pass` 作为自身检查结论，但不能替用户作出最终人工合格判定。

## 四、总流程

```text
读取规则与检查现有差异
→ 完成章级／节组级定位
→ 判定单节类型、影响面和交付物边界
→ 通读诊断并提交重写方案
→ 用户确认
→ 只修改获批范围
→ 四种读者检查与分项验证
→ 更新验收记录并提交人工复检
→ 用户关闭反馈，必要时沉淀新经验
```

一次只推进一个节级闭环。需要暂停时，先留下真实断点，再换会话。

## 五、详细步骤

### 步骤 1：建立最小可信上下文

**何时：** 每次新会话、恢复任务或切换篇目时。

**操作：**

1. 完整读取 `agent.md`、`plan.md`；读取目标正文及理解它所需的短前后文。
2. 按任务类型选读对应设计大纲、人工复盘和一篇相近正例，不通读全部历史资料。
3. 检查 Git 差异，保留用户和其他任务的修改。
4. 若已有 `reviews/sections/<节号>.json`，运行校验器检查正文与规则哈希。
5. 按 `agent.md` §13 判定 T0～T4 影响面，不因字数多就机械扩大验收，也不因改动少就跳过事实核验。

**产出：** 当前规则、正文、已有修改和证据位置的可靠基线。

### 步骤 2：先完成章级与节组级定位

**何时：** 开始一个章或节组的复检前。

**操作：**

1. 对照设计意图和实际目录，确认本章或本节组回答什么主问题。
2. 检查小节是否充分必要、顺序是否顺畅、相邻内容是否重复或断层。
3. 明确每个实践或系统问题由哪一篇负责，不用当前篇目的“补充讲解”吞掉其他篇目的职责。
4. 先提交书面定位与边界结论，得到用户确认后再逐节处理。

**产出：** 章级／节组级缺口、分工与阅读顺序结论。

### 步骤 3：判定篇目类型与交付物路由

**何时：** 单节诊断和设计方案之前。这是防止经验机械迁移的闸口。

先写清四项：

- **篇目类型**：本篇主要解决哪一类理解问题；
- **必要交付物**：没有哪些材料就无法回答主问题；
- **禁止进入的依赖**：哪些内容会引入另一条主线；
- **移交去向**：被排除内容应由哪一篇系统讲解。

| 篇目类型 | 通常必需的教学材料 | 默认不应强行加入 |
|---|---|---|
| 物理层／电气机制 | 信号方向、参与者状态、逐拍波形、电气边界、仪器证据 | Linux 对象、驱动调用链、完整内核模块 |
| 协议层／帧格式 | 同一事务的字段、位序、状态变化、正常与异常帧、抓包解释 | 与帧语义无关的完整驱动框架 |
| Linux 子系统／驱动框架 | 源码地图、对象生命周期、真实调用链、完整代码、构建与返回路径 | 用抽象分层名单代替代码主干 |
| 调试工具／故障排查 | 真实命令、前置条件、完整输出、退出状态、证据边界和恢复步骤 | 没有输出与判断依据的命令清单 |
| 端到端器件实践 | 正常产品路径、器件约束、完整实现、失败清理和结果验证 | 用受控强制路径代替日常推荐路径 |
| 决策／选型 | 同一操作上的双方机制、适用条件、代价和选择依据 | 一方尚未介绍就给出的优缺点表 |

该表是路由起点，不是固定栏目。若主问题确实需要跨越默认边界，必须在方案中说明为什么不可替代，并由用户确认。

**产出：** 当前篇目的交付物边界与禁止内容清单。

### 步骤 4：通读诊断，不提前修改

**操作：**

1. 用一句话写出唯一主问题和贯穿实例。
2. 扫描首次出现的术语、字段、函数、宏、命令、输出和图中符号。
3. 按篇目类型检查对象生命周期、参与者时序、调用链、代码跟随或观测验证；不适用项说明原因，不机械补齐。
4. 检查正常路径、错误恢复、系统集成归属和图表盲删。
5. 逐个小节说明存在理由，引用具体段落、代码或输出作为诊断证据。
6. 分别执行依赖、主线、盲删、跟随四种读者预检，指出读者会在哪里卡住。

**产出：** “问题清单＋修改方案”。系统性深度不足时提出整篇重写，骨架正确时才局部修复。

### 步骤 5：提交设计方案并等待用户确认

整篇重写方案至少包含：

1. 唯一主问题与贯穿实例；
2. 篇目类型、必要交付物、禁止内容和移交去向；
3. 正文顺序及各小节存在理由；
4. 首次依赖的处理位置；
5. 图示、交互、代码或命令为何需要，分别承担什么教学任务；
6. 人工经验到本篇的具体映射；
7. 四种读者和分项验证的验收办法。

复用人工经验时，映射的是**定义、时序、实例、机制、盲删和验证方法**，不是自动复制原篇的代码、目录、图片数量或实验室形态。

用户确认前不修改正文。后续若用户改变边界，更新方案后再写，最新确认优先于旧计划和旧 `next_action`。

**产出：** 已确认、可供新会话继续执行的方案。

### 步骤 6：按确认范围重写或修复

**操作：**

1. 只修改获批正文和直接配套资产，不顺手整改其他篇目或共享规则。
2. 先建立不依赖高级封装的手工完整基线，再讲框架、工具或抽象概念减少了什么。
3. 首次依赖在使用前解释；比较双方时，双方先分别出现。
4. 机制按参与者、输入、动作、状态变化和下一步推演。
5. 图表用于辅助，正文在盲删后仍须独立成立。
6. 代码与命令只在主问题需要时出现，并交代来源、上下文、关键行、参数、返回值、错误路径和验证方法。
7. 交互资产只是已核验内容的另一视图，不能承担正文缺席的唯一解释。

**产出：** 实际正文、配套资产及可审查的差异。

### 步骤 7：执行四种读者语义验收

| 检查 | 必答问题 | 不合格处理 |
|---|---|---|
| 依赖 | 哪个词、字段、函数或符号第一次见却没有解释？ | 回首次出现处补定义或准确前置指针 |
| 主线 | 这段为什么在这里，删除后是否影响主问题？ | 删除、移动或补承接关系 |
| 盲删 | 去掉图、表、代码、输出和 iframe 后，论证是否完整？ | 把唯一解释写回正文 |
| 跟随 | 能否用同一实例推完机制，并知道怎样观察或验证结果？ | 补状态序列、完整上下文或验证步骤 |

每项都要记录具体证据位置。关键词存在、文件存在和测试通过不能代替语义回答。任一关键卡点未关闭，不得写成 `pass`。

### 步骤 8：分项执行验证

| 项目 | 执行要求 | 未执行或不适用时的记录 |
|---|---|---|
| 源码／手册核验 | 核对实际使用的函数、字段、命令、参数和硬件结论，保留路径与必要区间 | 无法核实的结论不得写成确定事实 |
| 浏览器检查 | 交互资产变化后检查构建后页面、控件、键盘、异常恢复和窄屏 | 无交互变化才记 `not_applicable` |
| 教学代码编译 | 有完整教学代码时按当前可用环境实际编译 | 无教学代码记 `not_applicable`；有代码但未编译记 `not_verified` |
| 目标运行 | 在匹配目标环境执行并记录真实输出 | 未执行记 `not_verified` |
| 仪器测量 | 用逻辑分析仪、示波器等取得实际证据 | 未执行记 `not_verified`，示意图不得冒充实测 |
| 严格构建 | 使用项目指定 Python 执行 `mkdocs build --strict` | 记录真实命令、退出码和输出，不用旧结果替代 |

浏览器模型通过不等于硬件功能通过，严格构建成功不等于教学质量通过。

### 步骤 9：更新记录并提交人工复检

1. 按模板更新 `reviews/sections/<节号>.json`，绑定正文、`agent.md` 和 `plan.md` 哈希。
2. 四种读者与分项验证分别填写证据，不用一句“已检查”概括。
3. 运行记录校验器。`current` 只表示记录结构和哈希有效，`stale` 表示旧结果过期。
4. 汇报实际修改范围、四种读者发现、验证命令与结果、未验证项。
5. 用户整体浏览但未逐段确认时，记为“用户初审认可”，不写成“人工全面复检通过”。
6. 用户否决任一关键问题时，撤回对应 AI `pass`，修复后重新检查。

**产出：** 当前、可追溯但不夸大的 AI 验收记录和人工待办。

### 步骤 10：留下可续作断点

暂停或换会话前，至少记录：

```text
当前篇目与任务阶段：
唯一主问题与贯穿实例：
篇目类型、禁止内容和移交去向：
已确认方案路径：
实际修改文件：
已完成的源码／手册核验：
已完成的浏览器、编译和构建验证：
目标运行与仪器测量状态：
四种读者仍存的问题：
最新用户确认：
下一步唯一动作：
```

断点不能只写“进行中”“已优化”或“构建成功”，也不能只复制旧计划。

## 六、全书逐步复检的推进方式

1. **按章级 → 节组级 → 单节推进。** 不跳过整体定位直接逐节补丁。
2. **一次完成一个节级闭环。** 连续写作或复检不超过 1～2 节，达到后停下汇报。
3. **每节类型先路由。** 物理机制篇和驱动框架篇不能用同一份交付物清单验收。
4. **每篇只选少量相近正例。** B 层人工经验优先，未经人工认可的章节只作候选。
5. **每篇保留自己的证据。** 其他篇目的浏览器、编译、构建或人工认可不能自动继承。
6. **历史记录不批量补录。** 没有记录只表示尚未按现流程登记，不代表合格或不合格。
7. **人工否决驱动流程改进。** 若同类问题第二次出现，不只改正文，还要检查 SOP、规则入口或交接模板缺少哪一道闸口。
8. **完成量不按字数和 `pass` 数衡量。** 以主问题是否回答、四种读者是否可走通、证据是否真实和人工反馈是否关闭为准。

## 七、异常与边界情况

| 场景 | 处理方式 |
|---|---|
| 旧 AI 自评 `pass`，用户人工判定不合格 | 立即撤回对应结论，记录具体证据，按用户确认的范围内修复 |
| 设计方案与旧验收记录冲突 | 以最新用户确认和现行规则为准，更新方案后再执行 |
| 人工复盘中的交付物不适合当前篇目 | 只复用教学方法，重新路由必要材料，不机械复制代码或实验室 |
| 多个小节同时存在抽象堆积、定义缺失或无法跟随 | 提出 T2 整篇重写，不做逐点补丁后宣称完成 |
| 只需修正局部定义或衔接 | 按 T1 精准修改，检查新增依赖、前后文和严格构建 |
| 缺少源码、手册或关键证据 | 暂停相关结论，标记待核验，不凭记忆补齐 |
| 缺少编译器、目标板或仪器 | 保留 `not_verified`，不把代码外观、浏览器或构建结果当替代证据 |
| 上下文不足以高质量完成 | 保存方案、证据位置和断点，换新会话，不压缩成仓促改写 |
| 用户只批准单节修改 | 不修改其他章节、共享规则或无关资产 |

## 八、过程指标

| 指标 | 目标 | 衡量方式 |
|---|---|---|
| 主问题与实例 | 每节均可明确回答 | 导读、正文顺序和总结使用同一主问题 |
| 未解释首次依赖 | 0 个阻断项 | 依赖读者逐项扫描正文、图注、代码和实验室 |
| 无归属的越界内容 | 0 个 | 方案中的禁止内容和移交去向逐项核对 |
| 盲删缺失的唯一解释 | 0 处 | 删除辅助材料后通读正文 |
| 虚假验证声明 | 0 项 | 对照实际命令、输出和验证状态 |
| 过期验收记录继续标为当前 | 0 项 | 修改后重新运行哈希校验器 |
| 人工反馈闭环 | 每项有处理结果 | 用户初审、否决、修复和复审记录 |

这些指标用于发现漏检，不用于制造新的勾选式验收。

## 九、新会话交接模板

```text
先完整读取 agent.md、plan.md 和已确认设计方案，再按方案选读指定人工复盘与正例。
本次只处理【篇目】及其获批配套资产，不修改其他章节或共享规则。
当前任务阶段是【诊断／已确认后重写／局部修复／验收】。
唯一主问题与贯穿实例为【填写】。
篇目类型为【填写】；必要交付物为【填写】；禁止内容为【填写】；移交去向为【填写】。
最新用户确认为【填写】，旧计划或旧 next_action 与之冲突时不得恢复旧要求。
完成后分别报告四种读者、源码／手册、浏览器、教学代码编译、目标运行、仪器测量和严格构建。
未执行写 not_verified，不适用写 not_applicable；current 和构建成功不等于教学质量通过，最终由用户人工复检。
```
