## 1. 全书定位

- **双重使命**：带萌新入门 · 助进阶蜕变。
- **目标读者**：3-8 年经验的嵌入式 Linux 工程师（同时兼容零基础入门路径）。
- **难度体系 BIEM 四级**：B Beginner / I Intermediate / E Expert / M Master。章节标题后用 `[I→E]` 等形式标注覆盖区间。
- **38 章 = 5 部**，每部对应一个认知阶段，不是随机分组。

## 2. 五个认知跃迁与五部的映射

| 跃迁 | 内容 | 承载部 |
|------|------|--------|
| ① | 知其然 → 知其所以然 | 第二部（核心机制） |
| ② | 会使用 → 会设计 | 第三部（系统设计决策） |
| ③ | 解决问题 → 预防问题 | 第四部（全链路拆解） |
| ④ | 单点优化 → 系统权衡 | 第三部 + 第四部 |
| ⑤ | 技术执行 → 技术判断 | 第五部（行业与路线） |

第一部是跃迁的起点：先跑起来、建立动机（"需要时再学"），不追求一次讲透。

## 3. 五部设计哲学与章节模板（复检的结构基准）

每部有**固定的章节模板**。复检"是否符合大纲"时，第一判断就是结构是否对齐本部模板。

### 第一部：系统启动与运行（第 1-6 章）

- 设计哲学：**"需要时再学"**。目标是让读者从零把板子跑到 Shell，先建立完整路径的感性认识，概念级出现即可，深入留给第二部。
- 章模板（7 个固定块）：
  1. 为什么有这一章
  2. 与前后章的关系（前置知识 / 后续关联 / 位置定位）
  3. 螺旋关联（★第 N 次出现，标注概念级/操作级）
  4. 各小节内容
  5. 实践案例
  6. 常见陷阱
  7. 设计 Rationale
- 部末有：学习旅程总结、终点成就检查清单（10 项）、通向第 II 部的问题之门。

### 第二部：核心机制深度解析（第 7-15 章）

- 设计哲学（三条原则）：
  1. **问题导向，而非机制导向**——每个机制的存在必须有问题 rationale；
  2. **Trade-off 为中心，而非最优解为中心**——参照 DDIA，关键技术选择给结构化对比表格；
  3. **子系统关联，而非孤立深入**——章末分析与前后章的依赖。
- 章模板（**四段式**，这是第二部的核心纪律）：
  1. 问题场景——工程中遇到的实际问题（建立共鸣）
  2. 机制深入——源码级工作原理（真正理解）
  3. 设计考量——关键配置的权衡（决策能力）
  4. 排错指南——该子系统的排查方法论（实战能力）
- 四段式之外的固定块：各小节详述（含核心内容 / 关键代码路径 / 读者应掌握）、Trade-off 表格、实践案例、常见陷阱、与前后章的关联。
- 部末有：九章节知识图谱、"知其然→知其所以然"跃迁检查表、通往第三部的桥梁、学习路径建议。

### 第三部：系统设计决策（第 16-22 章）——大纲自称"全书的灵魂"

- 设计哲学：不再教"怎么做"，而是帮你在"A 和 B 之间"做选择。参照 DDIA 的决策问题驱动模式——真正的工程师不是不知道工具，而是不知道什么时候用什么工具。
- 章模板（9 个固定块）：
  1. 核心决策问题
  2. 为什么需要这一章
  3. 决策场景
  4. 选项分析
  5. Trade-off 表格
  6. 决策树
  7. 架构评审清单
  8. 案例研究
  9. 各小节详述
- 部末总结：决策思维五原则（先量化再决策 / TCO 优于初始成本 / 技术债务分类 / 没有银弹只有 trade-off / 能工作→能维护）+ 架构评审综合检查清单（启动/存储/构建/安全/实时/OTA/驱动七域）。

### 第四部：全链路拆解（第 23-30 章）

- 设计哲学：参照 AOSA + Systems Performance——不教"怎么做"，带你"拆开看"。每章以一个真实系统为线索，追踪数据/控制流从进入到离开的完整路径。
- 章模板（7 个固定块）：
  1. 核心系统/链路
  2. 系统架构图
  3. 链路拆解
  4. 跨子系统交互点
  5. 优化与权衡（部分章并入链路拆解）
  6. 常见问题
  7. 真实案例（每章一个带具体数字的实战案例，如"ClickHouse 消失的 CPU"、"智能摄像头 5.8 秒到 1.2 秒"）

### 第五部：前沿技术与行业视野（第 31-38 章）

- 设计哲学：不是技术教程，而是"行业分析 + 技术路线图 + 个人规划"。每章回答战略问题：行业在发生什么变化？对我意味着什么？我该做什么准备？**数据驱动**——基于真实市场数据、技术趋势和招聘需求，不是主观臆测。
- 章模板（6 个固定块）：
  1. 核心问题
  2. 现状分析
  3. 发展趋势
  4. 对工程师的影响
  5. 决策建议
  6. 延伸阅读

## 4. 螺旋上升机制

- 同一概念在多部中多次出现，深度递增。第一部用「★第 N 次出现」标注，并区分**概念级**（知道是什么）与**操作级**（会动手做）。
- 第二部总纲明确与第一部、第三部的螺旋关系：第一部给感性认识，第二部给源码级理解，第三部把机制变成设计决策的输入。
- 复检时的含义：某概念在低部"讲得不深"不一定是缺陷，先看它在本部的螺旋层级定位；但跨部引用必须闭合（例如 13.5.4 引用 8.1.2 的状态宏，8.1.2 就必须真的有）。

## 7. 复检与写作的可校验要求清单（本文档的核心产出）

复检任意主线章节时，按本部模板逐项核对：

**所有部通用**
- [ ] 难度标注与大纲一致（[B]/[I]/[E]/[M]），且与内容实际深度匹配
- [ ] 有"为什么需要这一章"式的问题动机（问题导向，非机制罗列）
- [ ] 章末有与前后章的关联说明，跨章引用闭合（引用的目标节确实存在对应内容）
- [ ] 关键技术选择有 Trade-off 对比（表格或等效结构化对比）
- [ ] 代码路径引用真实可核（内核 v6.6 源码行号、函数名经 jsdelivr 核对）

**第一部加查**
- [ ] 七块齐全（为什么/前后章/螺旋/小节/案例/陷阱/Rationale）
- [ ] 螺旋标注「★第 N 次出现」且区分概念级/操作级
- [ ] 深度克制：概念级出现即可，不抢第二部的内容

**第二部加查（四段式纪律——章级叙事意图，非节级标题模板）**

> ⚠️ 四段式描述的是**整章**的内容组织弧线（章级问题驱动），禁止把"问题场景/机制深入"等作为字面小标题逐节重复（2026-08-25 用户判定该写法枯燥模板化）。节内行文按 agent.md §14「机制两问」自然展开，真实工程问题融进开场叙述。

- [ ] 章级有真实工程问题驱动（README/章首给出主线与问题地图，非"本章介绍 XX 子系统"）
- [ ] 机制深入到源码级（函数调用链、关键结构体字段）
- [ ] 设计考量给出配置权衡（不是"最优解"宣讲）
- [ ] 排错方法论有可操作落点（步骤化、带具体工具命令；可收编进某节 + README 排错索引汇聚）
- [ ] 实践案例带症状→排查→根因→解决→教训的完整链
- [ ] 节内无"### 问题场景 / ### 机制深入"式字面模板标题，无"知识点N / ~字数"残留

**第三部加查**
- [ ] 核心决策问题是一句话问句（"A 还是 B？"）
- [ ] 有决策树与架构评审清单两个可带走的工具
- [ ] 案例研究有真实数字支撑

**第四部加查**
- [ ] 有系统架构图（链路可视）
- [ ] 链路拆解按数据流顺序，标注跨子系统交互点
- [ ] 真实案例带量化结果（优化前后数字）

**第五部加查**
- [ ] 现状分析有数据来源（市场数据/招聘需求，非臆测）
- [ ] 结尾落到"对工程师的影响"和"决策建议"，不止于行业科普
