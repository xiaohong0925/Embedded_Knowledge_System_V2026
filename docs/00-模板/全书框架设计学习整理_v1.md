> 现行口径：本文保留的“固定块”“模板”“检查清单”等原始设计措辞只描述章级叙事意图，不是节级栏目配额。写作、图示和验收以 `agent.md`、`plan.md` 为唯一规则真源；不得要求七块齐全、固定 Trade-off 表格、固定排障栏目或行数指标。

## 1. 全书定位

- **双重使命**：带萌新入门 · 助进阶蜕变。
- **目标读者**：3-8 年经验的嵌入式 Linux 工程师（同时兼容零基础入门路径）。
- **难度体系 BIEM 四级**：B Beginner / I Intermediate / E Expert / M Master。章节标题后用 `[I→E]` 等形式标注覆盖区间。
- **38 章 = 5 部**，每部对应一个认知阶段，不是随机分组。

## 2. 五个认知跃迁与五部的映射

| 跃迁 | 内容 | 承载部 |
|------|------|--------|
| ① | 知其然 → 知其所以然 | 第二部（核心机制） |
| ② | 会使用 → 会设计 | 第三部（系统设计决策） |
| ③ | 解决问题 → 预防问题 | 第四部（全链路拆解） |
| ④ | 单点优化 → 系统权衡 | 第三部 + 第四部 |
| ⑤ | 技术执行 → 技术判断 | 第五部（行业与路线） |

第一部是跃迁的起点：先跑起来、建立动机（"需要时再学"），不追求一次讲透。

## 3. 五部设计哲学与原始章节结构

下列结构用于理解各章的叙事意图和素材分工，不是要求每章、每节机械复制的固定栏目。复检时先判断主问题、内容边界与跨章关系是否成立，具体结构按 `agent.md` 重新设计。

### 第一部：系统启动与运行（第 1-6 章）

- 设计哲学：**"需要时再学"**。目标是让读者从零把板子跑到 Shell，先建立完整路径的感性认识，概念级出现即可，深入留给第二部。
- 章模板（7 个固定块）：
  1. 为什么有这一章
  2. 与前后章的关系（前置知识 / 后续关联 / 位置定位）
  3. 螺旋关联（★第 N 次出现，标注概念级/操作级）
  4. 各小节内容
  5. 实践案例
  6. 常见陷阱
  7. 设计 Rationale
- 部末有：学习旅程总结、终点成就检查清单（10 项）、通向第 II 部的问题之门。

### 第二部：核心机制深度解析（第 7-15 章）

- 设计哲学（三条原则）：
  1. **问题导向，而非机制导向**：每个机制的存在必须有问题 rationale；
  2. **选择依据，而非最优解宣讲**：关键技术选择要在正文中给出适用条件与代价，不为凑模板设置独立对比表；
  3. **子系统关联，而非孤立深入**：章末分析与前后章的依赖。
- 章模板（**四段式**，这是第二部的章级叙事意图，不是逐节标题模板）：
  1. 问题场景：工程中遇到的实际问题，建立阅读动机；
  2. 机制深入：用贯穿实例、源码路径和状态推演讲清工作原理；
  3. 设计考量：把关键配置的权衡融入对应机制与应用场景；
  4. 验证与排错：给核心结论可观察的验证落点，有必要时展开排查方法，不堆砌排障速查表。
- 各小节须有核心内容、关键代码路径和读者应掌握的独立能力。实践案例与前后章关联按主题自然组织，具体教学闭环和验收标准以 `agent.md` §12 为准。
- 部末有：九章节知识图谱、"知其然→知其所以然"跃迁检查表、通往第三部的桥梁、学习路径建议。

### 第三部：系统设计决策（第 16-22 章）——大纲自称"全书的灵魂"

- 设计哲学：不再教"怎么做"，而是帮你在"A 和 B 之间"做选择。参照 DDIA 的决策问题驱动模式——真正的工程师不是不知道工具，而是不知道什么时候用什么工具。
- 章模板（9 个固定块）：
  1. 核心决策问题
  2. 为什么需要这一章
  3. 决策场景
  4. 选项分析
  5. Trade-off 表格
  6. 决策树
  7. 架构评审清单
  8. 案例研究
  9. 各小节详述
- 部末总结：决策思维五原则（先量化再决策 / TCO 优于初始成本 / 技术债务分类 / 没有银弹只有 trade-off / 能工作→能维护）+ 架构评审综合检查清单（启动/存储/构建/安全/实时/OTA/驱动七域）。

### 第四部：全链路拆解（第 23-30 章）

- 设计哲学：参照 AOSA + Systems Performance——不教"怎么做"，带你"拆开看"。每章以一个真实系统为线索，追踪数据/控制流从进入到离开的完整路径。
- 章模板（7 个固定块）：
  1. 核心系统/链路
  2. 系统架构图
  3. 链路拆解
  4. 跨子系统交互点
  5. 优化与权衡（部分章并入链路拆解）
  6. 常见问题
  7. 真实案例（每章一个带具体数字的实战案例，如"ClickHouse 消失的 CPU"、"智能摄像头 5.8 秒到 1.2 秒"）

### 第五部：前沿技术与行业视野（第 31-38 章）

- 设计哲学：不是技术教程，而是"行业分析 + 技术路线图 + 个人规划"。每章回答战略问题：行业在发生什么变化？对我意味着什么？我该做什么准备？**数据驱动**——基于真实市场数据、技术趋势和招聘需求，不是主观臆测。
- 章模板（6 个固定块）：
  1. 核心问题
  2. 现状分析
  3. 发展趋势
  4. 对工程师的影响
  5. 决策建议
  6. 延伸阅读

## 4. 螺旋上升机制

- 同一概念在多部中多次出现，深度递增。第一部用「★第 N 次出现」标注，并区分**概念级**（知道是什么）与**操作级**（会动手做）。
- 第二部总纲明确与第一部、第三部的螺旋关系：第一部给感性认识，第二部给源码级理解，第三部把机制变成设计决策的输入。
- 复检时的含义：某概念在低部"讲得不深"不一定是缺陷，先看它在本部的螺旋层级定位；但跨部引用必须闭合（例如 13.5.4 引用 8.1.2 的状态宏，8.1.2 就必须真的有）。

## 7. 内容规划核对（不是栏目验收清单）

复检主线章节时，本文件只用于回答以下规划问题：

- 本章难度定位、核心问题和在全书中的位置是否仍与原始设计一致；
- 与前后章的依赖、重复和内容移交是否闭合；
- 第一部是否保持“先跑起来、需要时再学”，同时把首次依赖讲清；
- 第二部是否以真实问题驱动机制、源码和验证，而不是重复“问题场景／机制深入”等字面标题；
- 第三部是否让读者理解选择依据与代价，而不是必须产出决策树、Trade-off 表格或评审清单；
- 第四部是否沿真实数据流或控制流拆解系统，图示与量化案例按主问题需要配置；
- 第五部的行业判断是否基于可核验来源，并落到工程师的实际选择。

实际正文是否需要某个栏目、图、表、代码或实践，以及最终是否合格，统一按 `agent.md`、`plan.md` 和当前主问题判断。本文件不再设置“七块齐全”、固定栏目、行数或图片数量要求。
