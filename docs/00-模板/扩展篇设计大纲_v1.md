## 扩展篇定位

主线 38 章是认知主线——讲机制、讲决策、讲系统思维，刻意不讲写法细节（"够用即可"与 DDIA 决策驱动两条设计公理）。扩展篇是**参考与实操层**：主线选定方向后，读者到这里查"具体怎么写、怎么调、怎么落地"。

选址两条标准：

- **补缺型**：主线完全没有的知识域（A/B/D/E/F/G/H）
- **深挖型**：主线第五部已有概念判断，扩展做工程级展开（C）

## 设计特色

- 每篇开头必须有一行「与第 N 章的分工」声明，写清主线讲什么、本篇讲什么（沿用 B 扩展惯例）
- 每专题沿用 B 扩展验证过的四段式：认知/原理 → 框架/接口 → 实操/写法 → 调试/选型
- 扩展之间不重复，跨域主题一律互链（如 D.3 的业务侧 → A.3；G.3 的输入对接 → D.10）
- D 扩展 Part 1 采用贯穿案例教学法：虚构复合传感器芯片 TS502（温度寄存器 + 32 级 FIFO + 中断脚 + PWM 报警），从空骨架起步每篇加一块拼图，终点是约 400 行产品级模板驱动（现代版 scull 教学法）
- 实践案例遵循第 6 章 LED 的选型标准：硬件简单、结果可见、主线有现成驱动可对照、绑定简单、不依赖复杂初始化

## D. 驱动开发实战（第一波，最高优先级 · v2 完整大章）

核心问题："第10/11/12/13/22章把机制都讲透了——但让我从零写一个能进产品的驱动，从哪行代码开始写起？"

两条线并行：

- **Part 1 通用写法线（D.1-D.9）**：任何驱动都绕不开的九件兵器——骨架、cdev/ioctl、等待与通知、中断、定时、内存与 DMA、设备树、电源管理、调试接口
- **Part 2 子系统框架线（D.10-D.18）**：进框架的写法，每篇一个真实外设场景 + "用现成驱动 vs 自己写"判定

### 为什么需要这一扩展

v1 的 D 扩展只覆盖 Part 2（7 篇子系统注册参考），隐含假设读者已经会写骨架、cdev、中断、定时器——但这恰恰是主线刻意不讲、而初学者到独立工程师之间最宽的一段鸿沟。第22章的决策树停在"选 input 子系统"，第11章停在"六种接合方式"，从选定/挂上到跑通之间的写法细节，主线无人承担。v2 补上 Part 1 通用写法线，把 D 从"参考"升级为"完整大章"。

### 贯穿案例：TS502 复合传感器（Part 1）

虚构一颗 I2C 复合传感器芯片 TS502——温度寄存器 + 32 级采样 FIFO + 数据就绪中断脚 + PWM 报警输出。D.1 从空骨架起步，每篇加一块拼图：

| 篇目 | 加上的拼图 |
|---|---|
| D.1 | probe / devm 骨架 |
| D.2 | cdev read / ioctl |
| D.3 | FIFO 非空 poll 唤醒 + fasync |
| D.4 | 中断脚接入 |
| D.5 | 周期采样定时器 |
| D.6 | kfifo 批量读 + DMA 对比 |
| D.7 | 设备树描述 |
| D.8 | suspend 停采样 |
| D.9 | debugfs 寄存器 dump |

终点是一个约 400 行的产品级模板驱动。虚构理由：真实芯片没有这么全的特性组合，且读者板子未必有；寄存器手册随篇附表，读者照抄骨架、换自己芯片的寄存器定义即可。

### 与主线的分工口径

定位原则：**D 是实战篇**——一切内容以 TS502 驱动生长为主线，回答"这一步代码怎么写"；原理只给指针（一句话引用 + 链接），绝不展开。

执行细则（2026-08-12 重叠审计结论）：主线有四节实际写作时已越界进入写法地盘，D 在这些点上禁止照着重讲，只在实战流程中引用主线结论，篇幅全部花在主线没覆盖的实战细节上：

| 主线节 | 已越界写成的用法内容 | D 的处置 |
|---|---|---|
| 12.1.4 | cdev 三层注册 API、fops 方法语义、ioctl 编码、poll、mmap | D.2 不重讲基础，只写 read/write 边界与 *ppos、ABI 版本演进、compat_ioctl、per-fd 状态 |
| 13.5.4 | wait_event 模板、waitqueue 完整示例、驱动实战模式 | D.3 不重讲模板，只写 missed wakeup 防法、poll 驱动侧、fasync、三者选型 |
| 10.4.2 | 两阶段模型、API 角色分工、handler NULL 模式 | D.4 不重讲模型，只写 edge/level 与假中断、IRQF 标志、DT interrupts、底半部选型、中断调试 |
| 15.1.2 | dev_pm_ops 注册、probe 启用 Runtime PM、完整驱动示例 | D.8 不重讲注册，只写上下文保存恢复、enable_irq_wake、wakeup source、全链路验证 |

D 的独特价值：它是唯一把主线散点（12.1.4 的 fops、13.5.4 的 waitqueue、15.1.2 的 PM）拼装成一颗完整驱动（TS502）的地方。

每篇开头必须写「与第 N 章的分工」声明（沿用 B 扩展惯例）：

- 第10章讲中断/定时器机制（为什么）↔ D.4/D.5 讲驱动里怎么用（怎么写）

### Part 1 篇目详述（通用写法线）

**D.1 驱动骨架与生命周期 [I]**

核心内容：D.1.1 最小骨架与 probe/remove 正确姿势——`module_platform_driver` 宏展开、probe 初始化顺序、remove 与 probe 严格对称释放；D.1.2 错误处理两件套——goto 链逆序释放 vs `devm_*` 全家桶（`devm_kzalloc`/`devm_ioremap_resource`/`devm_request_irq`），产品驱动应全 devm；D.1.3 多实例与私有数据——`dev_set_drvdata`、idr/xarray 分配 minor、模块参数。

关键代码路径：`drivers/base/platform.c: platform_driver_register() → really_probe()`

读者应掌握：可进产品的驱动骨架模板、devm 资源管理、多实例设备的数据组织

**D.2 字符设备与用户态数据通道 [I→E]**

核心内容：D.2.1 read/write 实战边界——`copy_to_user` 返回值语义、`*ppos` 正确推进、部分读写与短读（cdev 三层注册 API 见 12.1.4，不重讲）；D.2.2 ioctl 设计学——结构体版本演进（payload 带 size/version）、`compat_ioctl`、命令编码只给指针（编码规则见 12.1.4）；D.2.3 open/release 与 per-fd 状态——`filp->private_data`、`nonseekable_open`、llseek 的四种取值。

关键代码路径：接 12.1.4 的 chrdev_open fops 替换链

读者应掌握：产品级 ioctl ABI 设计、读写边界条件处理、per-fd 状态管理

**D.3 等待、阻塞与事件通知 [E]**

核心内容：D.3.1 missed wakeup 防法——"条件先判后睡"、`wake_up` 与条件变更的配对纪律（wait_event 模板本身见 13.5.4，不重讲）；D.3.2 poll/epoll 驱动侧——`fops->poll` = `poll_wait` + 返回掩码、POLLIN 语义、EPOLLET 对驱动侧的要求；D.3.3 fasync——`fasync_helper`/`kill_fasync` 发 SIGIO、三种通知机制的驱动侧选型。

关键代码路径：机制见 12.1.4 的 do_poll，本篇给驱动侧实现

读者应掌握：三种通知机制的实现与选型、missed wakeup 的正确写法

**D.4 中断实战 [E]**

核心内容：D.4.1 驱动侧中断接入——edge/level 触发与假中断处理、设备树 interrupts 声明与触发类型的对应、IRQF_SHARED/IRQF_ONESHOT 的实际选用（两阶段模型与 API 分工见 10.4.2，不重讲）；D.4.2 底半部在驱动里的选型——threaded_fn vs workqueue vs tasklet（已废弃，仅认知），中断里禁睡眠/禁耗时/禁用户态拷贝；D.4.3 中断调试——`/proc/interrupts` 解读、中断风暴定位、smp_affinity、丢事件的三种典型根因。

关键代码路径：`kernel/irq/manage.c: request_threaded_irq() → __setup_irq()`

读者应掌握：线程化中断的正确分工、触发方式与设备树声明的对应、中断问题排查套路（互链第10章机制篇与 B-A GPIO 消抖）

**D.5 定时与延迟 [I→E]**

核心内容：D.5.1 timer_list vs hrtimer——精度/开销/回调上下文对照；D.5.2 三大范式——mod_timer 消抖、超时重试、`hrtimer_forward_now` 周期采样；D.5.3 延时家族——ndelay/udelay/mdelay 忙等待边界、msleep、fsleep（v6.6+）。

关键代码路径：`kernel/time/timer.c`、`kernel/time/hrtimer.c`

读者应掌握：定时器选型、周期采样的正确实现、忙等待与睡眠的边界

**D.6 内存与 DMA [E→M]**

核心内容：D.6.1 分配选型——kmalloc 与 GFP_KERNEL/GFP_ATOMIC/GFP_NOIO 场景表、kvmalloc/vmalloc/kmem_cache/mempool；D.6.2 DMA 两种映射——`dma_alloc_coherent` vs `dma_map_single` 三方向与 cache 同步点，ARM 上 cache 一致性是驱动自己的事；D.6.3 scatter-gather 概念 + kfifo 环形缓冲（单读单写无锁）；D.6.4 mmap 直通——`remap_pfn_range` 映射寄存器/保留内存、`dma_mmap_coherent` 零拷贝、vm_pgoff 与权限——"野路子 mmap"的正统形态（与 11.1.4 裸驱动篇分工）。

关键代码路径：`kernel/dma/mapping.c`、`drivers/char/mem.c`（对照 /dev/mem）

读者应掌握：分配函数选型、DMA cache 一致性、mmap fop 实现

**D.7 设备树进阶 [E]**

核心内容：D.7.1 `of_property_read` 全家桶——u32/string/bool/数组、`of_get_named_gpio`、`of_irq_get`、phandle 引用链；D.7.2 自定义 binding——硬件事实进 DT vs 软件策略写死代码、compatible 命名规范、deprecated 演进；D.7.3 资源编排时序——reg→ioremap、interrupts→IRQ、clocks/resets/pinctrl 的获取使能顺序（互链 11.3.5 probe 失败排查树）。

读者应掌握：复杂属性读取、为自己的芯片设计 binding、资源依赖顺序

**D.8 电源管理 [E→M]**

核心内容：D.8.1 suspend/resume 实战——回调实现、寄存器上下文保存恢复清单、`enable_irq_wake`（Runtime PM 注册与引用计数用法见 15.1.2，不重讲）；D.8.2 wakeup source——设备树 wakeup-source 声明、`/sys/power/wakeup_count` 验证；D.8.3 休眠唤醒全链路验证——TS502 suspend 停采样、resume 恢复 FIFO 状态的完整演练。

关键代码路径：`drivers/base/power/runtime.c`

读者应掌握：两级电源管理的实现、休眠唤醒全链路验证

**D.9 调试与可维护接口 [I→E]**

核心内容：D.9.1 打印的艺术——`dev_dbg`/`pr_debug` + dynamic debug 运行时分文件分行开关、ratelimit、结构化寄存器状态输出；D.9.2 sysfs 属性——DEVICE_ATTR_RO/RW、一值一属性原则、与 ioctl 的选型；D.9.3 debugfs + seq_file——寄存器 dump、统计计数器、debugfs 非 ABI 的自由。

关键代码路径：`fs/debugfs/`、`lib/seq_file.c`

读者应掌握：三级可观测接口的分工、产品驱动的可维护性设计

### Part 2 篇目详述（子系统框架线）

独特设计：每篇一个真实外设场景，从设备树写到用户态收数据，给出"用现成驱动 vs 自己写"的判定标准。第22章教选型决策，本线教选定后的写法。

Part 2 写作规范（2026-08-12 审计修订）：

- **四段骨架**：每篇统一为「场景与判定（三条路怎么选）→ 框架最小骨架（注册-上报-用户态最短路径 + 现成驱动源码走读）→ 完整案例 → 调试与验收（子系统专属工具）」，结尾沿用 Part 1 格式
- **单篇最低配额**：判定标准表 ≥1、可编译骨架、内核源码走读 ≥1 段、工具验证命令 ≥2 条、陷阱 ≥4 条、框架关系图 ≥1 张（ASCII/mermaid 优先，需生图处加 `> 📷` 描述）
- **无硬件验证路径**：每篇必须给"没有这颗料怎么练"的后备方案（如 iio_dummy、开发板自带按键）
- **依赖复用**：中断/定时器/kfifo/等待等写法一句话引用 Part 1 对应篇，不重复；总线事务细节链 B 扩展；用户态深入链 A.3/A.8
- **TS502 对照标本**：D.11 把 TS502 改写成 IIO 版、D.15 把寄存器访问 regmap 化，与 Part 1 cdev 版形成三形态对照（D.18 汇总对照表）

**D.10 input 子系统：按键与旋转编码器（含 counter 对照） [I]**

核心内容：以 EC11 旋转编码器 + 轻触按键（音量调节旋钮，按下静音）为案例——嵌入式产品中最标准的输入组合。设备树声明相位 A/B 两个中断 GPIO 与按键 GPIO → `request_threaded_irq` → 定时器消抖与四状态机方向判定 → `input_allocate_device`/`input_register_device` 注册 → `input_report_rel(REL_WHEEL)` 与 `input_report_key(KEY_ENTER)` 上报 → 业务侧 `epoll` 读 `/dev/input/eventX`。对照主线现成驱动：`drivers/input/misc/rotary_encoder.c` 与 `gpio-keys`——给出判定标准：硬件接法与现成驱动 binding 兼容时直接用设备树声明；消抖逻辑、事件语义需要定制时才自己写。**counter 对照小节**：要"绝对位置计数"语义（电机码盘、累计脉冲）时 counter 子系统（`drivers/counter/`）比 input REL 事件更合适，给出两者的语义分界。

关键代码路径：`drivers/input/input.c: input_register_device()` → `drivers/input/evdev.c: evdev_events()` → 用户态 `struct input_event` 读取

读者应掌握：`input_dev` 注册全流程、EV_KEY/EV_REL/EV_ABS 三类事件的语义选择、消抖的定时器实现、`evtest` 调试、业务侧 epoll 读 evdev 的最小代码

**D.11 IIO 子系统：传感器的标准写法（含 TS502 改写对照） [I→E]**

核心内容：以一颗 I2C 温湿度传感器（SHT3x）为案例。channel 定义（`IIO_CHAN_INFO_RAW`/`SCALE`/`OFFSET`）、`indio_dev` 注册、sysfs 直读接口、buffer + hrtimer trigger 连续采样。与 11.1.1 的 hwmon 写法对照：同一颗芯片两条路，什么时候进 IIO（需要缓冲采样、标准化通道）什么时候留 hwmon（只需温度监控）。**TS502 对照标本**：把 Part 1 的 TS502 cdev 驱动改写成 IIO 版本，一页对照"自写 cdev vs 进框架"的代码量、用户态接口、业务兼容性差异。无硬件后备：内核自带 `iio_dummy` 虚拟驱动。

关键代码路径：`drivers/iio/industrialio-core.c: iio_device_register()` → `drivers/iio/buffer/` 采样路径

读者应掌握：IIO channel 语义、`iio_device_register` 流程、sysfs 与 buffer 两种读取路径、`iio_info`/`iio_readdev` 调试工具

**D.12 hwmon 与 thermal 联动：从读温度到控风扇 [E]**

核心内容：11.1.1 的 hwmon 写法的产品化延续。`hwmon_device_register` 之外的另一半：thermal zone 绑定、cooling device（PWM 风扇）注册、trip point 与调速策略（step_wise/fair_share）。形成"传感器 → 热区 → 风扇"的完整闭环。**写前核实**：先读主线 15.4.2（Thermal Governor 与设备树配置）实际内容，按 v2.1 口径收缩——Governor 机制与 DT 概念引用主线，本篇只写 cooling device 注册与闭环案例。

关键代码路径：`drivers/thermal/thermal_core.c: thermal_zone_device_register()` → `thermal_bind_cdev`

读者应掌握：hwmon 与 thermal 的分工、cooling device 写法、设备树 thermal-zones 声明

**D.13 LED/PWM/背光子系统 [I]**

核心内容：第 6 章 LED 的螺旋上升。`led_classdev` 注册、led-trigger 机制（heartbeat/timer/mtd）、PWM 框架（`pwm_apply_state`）、背光驱动（`backlight_device`）与显示栈的关系。

关键代码路径：`drivers/leds/led-class.c: led_classdev_register()` → `drivers/leds/trigger/`

读者应掌握：led_classdev 写法、trigger 的注册与挂载、什么时候不用自己写（`leds-gpio`、`pwm-leds` 现成驱动）

**D.14 watchdog / RTC / misc：小件三剑客 [I]**

核心内容：三个高频小框架。watchdog：`watchdog_device` 注册、超时与 keepalive 语义、与内核 watchdog core 的分工；RTC：`rtc_device_register`、alarm 中断；misc 与 cdev 的选择判据（小驱动用 misc，需要主设备号语义用 cdev）。

关键代码路径：`drivers/watchdog/watchdog_core.c: watchdog_register_device()`

读者应掌握：三个框架的最小驱动骨架、与 11.1.4 Legacy 裸写法的对照（框架版省掉了什么）

**D.15 regmap 与资源三件套：pinctrl / clk / regulator [E]**

核心内容：驱动代码里最常出现却最少被系统讲解的三组 API。regmap：统一 I2C/SPI/MMIO 寄存器访问、cache 与 volatile 配置——**TS502 对照标本**：把 TS502 的 `i2c_smbus_*` 直读改写成 regmap 版，展示 reg_read/reg_write 回调、`regmap_config` 与 cache 模式选择；资源三件套的消费者视角（`devm_clk_get`、`devm_regulator_get`、`pinctrl_get_select`）与提供者视角（什么情况下你要写 clk/regulator 驱动）。

关键代码路径：`drivers/regmap/regmap.c: regmap_init()` → `drivers/clk/clk.c: clk_prepare_enable()`

读者应掌握：regmap 初始化与读写、三件套的获取-使能-禁用时序、probe 失败时最常见的三种资源错误（与 11.3.5 排查树互链）

**D.16 MFD 与复合设备 [M]**

核心内容：一颗 PMIC 里同时有 regulator + GPIO + RTC + ADC——怎么组织？MFD 核心注册子设备、共享寄存器走 regmap、irq_chip 中断级联。判定标准：多功能复合芯片用 MFD，单功能芯片别硬套。

关键代码路径：`drivers/mfd/mfd-core.c: mfd_add_devices()`

读者应掌握：复合设备的拆分原则、子设备间共享资源的方式、MFD 与"一个驱动包揽"的边界

**D.17 用户态驱动 [I→E]**

核心内容：不写内核驱动也是正经方案。UIO（`uio_register` + 用户态 mmap + 中断计数）、VFIO（DMA 直通，FPGA/PCIe 卡场景）、spidev/i2c-dev（快速验证与产测）。判定：迭代速度优先、硬件未定型、单产品绑定 → 用户态；需并发访问、中断密集、多进程共享 → 必须进内核。

关键代码路径：`drivers/uio/uio.c`

读者应掌握：UIO 最小实现、内核态 vs 用户态的决策边界（互链 11.1.6 用户态驱动机制篇）

**D.18 子系统选型速查与全扩展知识图谱 [I]**

### Trade-off 表格

| 决策 | 选项 A | 选项 B | 权衡分析 |
|---|---|---|---|
| 资源释放 | devm_* | goto 链逆序释放 | devm 免维护但顺序受框架控制；goto 链精确但易漏 |
| 底半部 | threaded_fn | workqueue | threaded_fn 实时性好；workqueue 上下文自由但延迟更大 |
| 读数据 | 阻塞 read | poll + 非阻塞 | 阻塞简单；poll 支持多路复用与超时 |
| 事件通知 | poll | fasync | poll 生态好（epoll 兼容）；fasync 信号语义适合简单场景 |
| DMA 映射 | coherent | streaming | coherent 省心但内存受限；streaming 高效但要管 cache 同步 |
| 配置接口 | ioctl | sysfs | ioctl 二进制高效可带版本；sysfs 文本直观但仅适合单值 |
| 复合芯片 | MFD | 单驱动包揽 | MFD 结构清晰可复用；单驱动简单但难维护 |
| 驱动位置 | 内核态 | 用户态（UIO/spidev） | 内核态性能好可共享；用户态迭代快、崩溃不挂系统 |
| 按键驱动 | 现成 gpio-keys | 自写 input 驱动 | 现成零代码但语义固定；自写可控但需维护 |
| 传感器接口 | IIO | hwmon | IIO 有缓冲与触发但复杂；hwmon 简单但只读 |
| 消抖方式 | 定时器延迟上报 | 滤波状态机 | 定时器简单但引入固定延迟；状态机实时但实现复杂 |
| 小驱动注册 | misc | cdev | misc 自动分配 minor 但语义弱；cdev 可控但代码多 |
| 用户态读取 | evdev/sysfs | netlink/自定义 ioctl | 标准接口生态好；自定义灵活但业务层绑死 |

### 实践案例

案例 1：某手持终端音量旋钮误报——症状：旋转一格上报 3-4 个事件。根因：未做消抖，EC11 触点弹跳被每次边沿都上报。修复：四状态机 + 5ms 定时器确认。教训：机械触点的驱动，消抖逻辑与上报逻辑同等重要。

案例 2：某网关按键双击失效——症状：业务双击判定偶发失败。根因：驱动在硬中断上下文直接上报，中断风暴期间事件丢失。修复：改 threaded_irq + workqueue。教训：input 上报路径的上下文选择直接影响事件可靠性。

案例 3：某 FPGA 数据采集卡原型期的驱动路线之争——硬件寄存器布局每周都在变，内核驱动改了五版仍跟不上硬件节奏。改走 UIO + 用户态 mmap，两周出 demo 完成算法验证；硬件定型后重写为内核态 DMA 驱动进产品。教训：硬件未定型时内核驱动是负债不是资产——原型期用 UIO/spidev 买迭代速度，定型后再进内核。

案例 4：某传感器驱动 remove 后 oops——症状：rmmod 后系统随机崩溃。根因：devm_ 与手动释放混用导致 double free，且退出路径漏了 `del_timer_sync`，定时器回调访问已释放内存。修复：统一全 devm，定时器与 workqueue 一律同步销毁。教训：释放路径与申请路径严格对称；任何异步回调（定时器/工作队列/中断）销毁必须 sync。

### 常见陷阱

| 陷阱 | 表现 | 根因 | 修正方法 |
|---|---|---|---|
| missed wakeup | read 永远睡死，数据其实已到 | 先睡眠后检查条件 | wait_event 系列"条件先判后睡"，wake_up 与条件变更配对 |
| 中断里 copy_to_user | 偶发死锁/崩溃 | 中断上下文禁止用户态拷贝 | 中断先存 kfifo，底半部或 read 时再拷 |
| DMA cache 不同步 | 读到旧数据/数据偶发错乱 | 忘 `dma_sync_*_for_cpu` | streaming DMA 严格按同步点配对 |
| ioctl ABI 破坏 | 升级驱动后业务崩溃 | 结构体直接改字段 | payload 带 size/version，只增不改 |
| probe 里长延时 | 开机慢数秒 | probe 中 msleep 等硬件就绪 | 延迟到 workqueue 或 async probe |
| 忘记 input_sync | 业务收到残缺事件包 | 上报后未发同步事件 | 每组上报后 `input_sync()` |
| 消抖定时器泄漏 | rmmod 后内核 oops | 卸载时未 del_timer_sync | exit 路径同步删除定时器 |
| 事件类型选错 | 业务按相对量解码绝对量 | REL 与 ABS 语义混淆 | 旋钮用 REL，摇杆/触摸用 ABS |
| evdev 独占 | 业务读不到事件 | 另一进程 grab 了设备 | `EVIOCGRAB` 排查 |
