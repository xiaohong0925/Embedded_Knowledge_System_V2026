## D. 驱动子系统实战（第一波，最高优先级）

核心问题："第22章告诉我该选 input 子系统——然后呢？`input_dev` 怎么注册？事件怎么上报？业务怎么收？"

独特设计：每篇一个真实外设场景，从设备树写到用户态收数据，给出"用现成驱动 vs 自己写"的判定标准。第11章教的是驱动与内核的**接合方式**（六种写法），本扩展教的是**子系统框架内的写法**——两者正交，不重复。

### 为什么需要这一扩展

有经验工程师会写 platform_driver，但面对一颗按键时仍有三条路在眼前分叉：主线已有 `gpio-keys` 现成驱动，直接设备树声明即可；也可以自己注册 `input_dev`；还可以 sysfs 轮询硬读。选错代价真实存在——该用现成的重写了轮子，或该进子系统的用了 sysfs 轮询导致业务层永远无法标准复用。第22章的决策树停在"选 input 子系统"这一步，从选定到跑通之间的注册、上报、去抖、用户态配套，主线无人承担。这是 BSP/驱动工程师日常工作中频率最高的一类任务。

### 篇目详述

**D.1 input 子系统：按键与旋转编码器 [I]**

核心内容：以 EC11 旋转编码器 + 轻触按键（音量调节旋钮，按下静音）为案例——嵌入式产品中最标准的输入组合。设备树声明相位 A/B 两个中断 GPIO 与按键 GPIO → `request_threaded_irq` → 定时器消抖与四状态机方向判定 → `input_allocate_device`/`input_register_device` 注册 → `input_report_rel(REL_WHEEL)` 与 `input_report_key(KEY_ENTER)` 上报 → 业务侧 `epoll` 读 `/dev/input/eventX`。对照主线现成驱动：`drivers/input/misc/rotary_encoder.c` 与 `gpio-keys`——给出判定标准：硬件接法与现成驱动 binding 兼容时直接用设备树声明；消抖逻辑、事件语义需要定制时才自己写。

关键代码路径：`drivers/input/input.c: input_register_device()` → `drivers/input/evdev.c: evdev_events()` → 用户态 `struct input_event` 读取

读者应掌握：`input_dev` 注册全流程、EV_KEY/EV_REL/EV_ABS 三类事件的语义选择、消抖的定时器实现、`evtest` 调试、业务侧 epoll 读 evdev 的最小代码

**D.2 IIO 子系统：传感器的标准写法 [I→E]**

核心内容：以一颗 I2C 温湿度传感器（SHT3x）为案例。channel 定义（`IIO_CHAN_INFO_RAW`/`SCALE`/`OFFSET`）、`indio_dev` 注册、sysfs 直读接口、buffer + hrtimer trigger 连续采样。与 11.1.1 的 hwmon 写法对照：同一颗芯片两条路，什么时候进 IIO（需要缓冲采样、标准化通道）什么时候留 hwmon（只需温度监控）。

关键代码路径：`drivers/iio/industrialio-core.c: iio_device_register()` → `drivers/iio/buffer/` 采样路径

读者应掌握：IIO channel 语义、`iio_device_register` 流程、sysfs 与 buffer 两种读取路径、`iio_info`/`iio_readdev` 调试工具

**D.3 hwmon 与 thermal 联动：从读温度到控风扇 [E]**

核心内容：11.1.1 的 hwmon 写法的产品化延续。`hwmon_device_register` 之外的另一半：thermal zone 绑定、cooling device（PWM 风扇）注册、trip point 与调速策略（step_wise/fair_share）。形成"传感器 → 热区 → 风扇"的完整闭环。

关键代码路径：`drivers/thermal/thermal_core.c: thermal_zone_device_register()` → `thermal_bind_cdev`

读者应掌握：hwmon 与 thermal 的分工、cooling device 写法、设备树 thermal-zones 声明

**D.4 LED/PWM/背光子系统 [I]**

核心内容：第 6 章 LED 的螺旋上升。`led_classdev` 注册、led-trigger 机制（heartbeat/timer/mtd）、PWM 框架（`pwm_apply_state`）、背光驱动（`backlight_device`）与显示栈的关系。

关键代码路径：`drivers/leds/led-class.c: led_classdev_register()` → `drivers/leds/trigger/`

读者应掌握：led_classdev 写法、trigger 的注册与挂载、什么时候不用自己写（`leds-gpio`、`pwm-leds` 现成驱动）

**D.5 watchdog / RTC / misc：小件三剑客 [I]**

核心内容：三个高频小框架。watchdog：`watchdog_device` 注册、超时与 keepalive 语义、与内核 watchdog core 的分工；RTC：`rtc_device_register`、alarm 中断；misc 与 cdev 的选择判据（小驱动用 misc，需要主设备号语义用 cdev）。

关键代码路径：`drivers/watchdog/watchdog_core.c: watchdog_register_device()`

读者应掌握：三个框架的最小驱动骨架、与 11.1.4 Legacy 裸写法的对照（框架版省掉了什么）

**D.6 regmap 与资源三件套：pinctrl / clk / regulator [E]**

核心内容：驱动代码里最常出现却最少被系统讲解的三组 API。regmap：统一 I2C/SPI/MMIO 寄存器访问、cache 与 volatile 配置；资源三件套的消费者视角（`devm_clk_get`、`devm_regulator_get`、`pinctrl_get_select`）与提供者视角（什么情况下你要写 clk/regulator 驱动）。

关键代码路径：`drivers/regmap/regmap.c: regmap_init()` → `drivers/clk/clk.c: clk_prepare_enable()`

读者应掌握：regmap 初始化与读写、三件套的获取-使能-禁用时序、probe 失败时最常见的三种资源错误（与 11.3.5 排查树互链）

**D.7 子系统选型速查与全扩展知识图谱 [I]**

核心内容：设备类型 → 子系统映射速查表（按键/旋钮→input，传感器→IIO 或 hwmon，温度监控→hwmon，背光→backlight，看门狗→watchdog……），与第22章决策树互链；全扩展知识点关联图与自测题（沿用 B.99 格式）。

### Trade-off 表格

| 决策 | 选项 A | 选项 B | 权衡分析 |
|---|---|---|---|
| 按键驱动 | 现成 gpio-keys | 自写 input 驱动 | 现成零代码但语义固定；自写可控但需维护 |
| 传感器接口 | IIO | hwmon | IIO 有缓冲与触发但复杂；hwmon 简单但只读 |
| 消抖方式 | 定时器延迟上报 | 滤波状态机 | 定时器简单但引入固定延迟；状态机实时但实现复杂 |
| 小驱动注册 | misc | cdev | misc 自动分配 minor 但语义弱；cdev 可控但代码多 |
| 用户态读取 | evdev/sysfs | netlink/自定义 ioctl | 标准接口生态好；自定义灵活但业务层绑死 |

### 实践案例

案例 1：某手持终端音量旋钮误报——症状：旋转一格上报 3-4 个事件。根因：未做消抖，EC11 触点弹跳被每次边沿都上报。修复：四状态机 + 5ms 定时器确认。教训：机械触点的驱动，消抖逻辑与上报逻辑同等重要。

案例 2：某网关按键双击失效——症状：业务双击判定偶发失败。根因：驱动在硬中断上下文直接上报，中断风暴期间事件丢失。修复：改 threaded_irq + workqueue。教训：input 上报路径的上下文选择直接影响事件可靠性。

### 常见陷阱

| 陷阱 | 表现 | 根因 | 修正方法 |
|---|---|---|---|
| 忘记 input_sync | 业务收到残缺事件包 | 上报后未发同步事件 | 每组上报后 `input_sync()` |
| 消抖定时器泄漏 | rmmod 后内核 oops | 卸载时未 del_timer_sync | exit 路径同步删除定时器 |
| 事件类型选错 | 业务按相对量解码绝对量 | REL 与 ABS 语义混淆 | 旋钮用 REL，摇杆/触摸用 ABS |
| evdev 独占 | 业务读不到事件 | 另一进程 grab 了设备 | `EVIOCGRAB` 排查 |

## E. 调试与可观测性（第一波）

核心问题："第23章教了怎么思考——ftrace/perf/kgdb 这些工具具体怎么按？"

为什么需要：主线第23章是调试方法论（怎么定位问题域），但方法论落地时每一步都依赖工具操作：trace 怎么开、火焰图怎么出、panic 现场怎么从 ramoops 里捞。这些内容主线大纲从未安排（38 章以机制与决策为纲），而它们是工程师每天的真实工作界面。

### 篇目详述

- **E.1 ftrace 与 trace-cmd [I→E]**：function/event tracer、irqsoff/preemptoff 延迟追踪、trace-cmd record + KernelShark 分析。关键代码路径：`kernel/trace/`。读者应掌握：三类 tracer 的启用与解读、用 irqsoff 定位第 10 章"顶半部过长"类问题
- **E.2 perf 全家桶 [E]**：perf top/record/stat、PMU 硬件计数器、火焰图生成与解读。读者应掌握：CPU 瓶颈定位三板斧、cache miss/分支预测计数器的嵌入式意义
- **E.3 eBPF/bpftrace 实战 [E→M]**：kprobe/uprobe 挂载、第一个观测脚本、嵌入式交叉部署的 BTF/内核配置前提。读者应掌握：不改内核代码加观测点的方法
- **E.4 崩溃取证 [E]**：pstore/ramoops 配置与读取、kdump/kexec、core dump 符号化（addr2line/faddr2line）。读者应掌握：panic 后第一时间保全现场的标准动作
- **E.5 硬件级调试 [E→M]**：JTAG/SWD 连接、OpenOCD + gdb 内核源码单步、逻辑分析仪核对总线时序（与 B 扩展各总线调试篇互链）
- **E.6 用户态侧 [I]**：strace/ltrace、gdbserver 远程调试、ASan 交叉移植
