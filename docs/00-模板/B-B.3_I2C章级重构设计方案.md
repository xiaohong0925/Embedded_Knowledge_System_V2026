### 3. 总体改造原则

本次不是六篇一起换皮，而是先确定全章共享的实例、术语、代码和证据，再逐篇施工。

1. **一条主线**：每篇都回答“同一笔访问当前走到哪一层”，不各自建立一套互不相干的知识体系。
2. **两个层次**：正文负责完整因果和状态推演，代码与输出负责让读者跟随和验证。二者不能互相替代。
3. **三类验证**：源码／手册核验、软件构建／运行验证、真实硬件／仪器验证分别记录，严格构建不属于功能验证。
4. **四种材料**：正文、完整代码、观察输出、证据图片统一登记。实验室只提供导航和单步推演。
5. **一次一节**：章级方案确认不等于获准批量修改六篇。实际正文从 B-B.3.4 开始，完成后停下验收。

### 1. 主线实例固定数据

全章优先复用同一实验总线和 EEPROM。除 B-B.3.6 的电源器件外，不再无意义更换数字。

| 项目 | 统一值 | 含义与使用位置 |
|---|---|---|
| 控制器 | RK3568 I2C1，Linux 编号以实际 `i2c-1` 为前提 | B-B.3.3 建链，B-B.3.4／3.5 命令执行；编号必须先核实，不能由芯片标签直接推断 |
| EEPROM | Microchip AT24C02C | B-B.3.5 必须锁定准确后缀；其他篇只把它作为 2 Kbit I2C EEPROM 实例 |
| 7 位器件地址 | `0x50` | A2/A1/A0 接地的受控实验条件，不能推广为所有模块 |
| 内部偏移 | `0x10` | 芯片内部存储位置，不是总线地址 |
| 前四字节 | `48 65 6c 6c`，ASCII `Hell` | B-B.3.2 逐拍解码，B-B.3.3 只读首字节 `0x48`，B-B.3.4 读四字节 |

| 正常消息返回值 | 内核 `i2c_transfer()` 返回 2；用户态该 `ioctl()` 返回 2 | 两条消息完成，不等于读到了 2 字节，也不等于内容正确 |
| 末尾应答 | 前三个读数据字节后 ACK，最后一字节后 NACK，再 STOP | 正常读取收尾，不是故障 |

B-B.3.6 使用另一颗器件是不可避免的内容差异，但仍固定同一组数据：TPS40422 地址 `0x30`，旧 `PAGE=0`，目标 `PAGE=1`，`VOUT_MODE=0x17`，`READ_VOUT` 线上低高字节 `00 03`，原始字 `0x0300=768`，结果 1.5 V，hwmon 文本 `1500` mV。

## 四、统一材料与写作规范

### 1. 正文、代码、输出和实验室分别负责什么

- **正文**：即使删除 iframe、图片、表格、代码块和命令输出，仍须回答输入是什么、经过哪些对象和状态、为什么产生该结果、失败如何判断。
- **完整代码**：放入 `code/<节号>/`，正文用片段包含或明确文件入口。代码注释解释字面值、参数和当前行用途，正文解释跨函数因果、所有权、状态和验证。
- **观察输出**：紧跟对应命令，标明“实测”或“依据文档构造的预期示例”。关键字段在块内注释或紧随其后的短段判读，不让读者跨几个小节寻找命令。
- **实验室**：复用 Framework Lab 的“步骤片段／完整函数／源码工作台”，只帮助定位代码和状态，不成为正文的唯一解释。
- **图片**：优先使用官方手册、官方工具文档或许可明确的网图；找不到合适图片时给详细生图描述。AI 图只能标作机制示意，不能伪装成仪器实测。

### 2. 代码展示规则

1. 每段代码前先交代文件名、版本、原创或源码节选、运行上下文和当前任务。
2. 节选必须说明省略了什么，重要错误路径不能为了短而删掉。需要完整上下文时进入完整文件，不在正文拼接不连续行号。
3. 字面值尽量就近放注释，例如 `0x50`、`0x10`、`nmsgs=2`、`0xff`、`PAGE=1`。正文不重复逐字念注释，而解释这些值为什么在此出现。
4. 函数返回分别核对：消息数、字节数、0／负错误、系统调用 `-1/errno`、进程退出状态和数据内容。
5. 完整示例必须有输入、构建或运行前提、命令、预期输出、结果验证和清理步骤。
6. 内核配置优先教 `make menuconfig` 搜索和启用，`.config` 检查只做结果核验，不教手工绕过 Kconfig 依赖。
7. 不为“代码多”而重复同一实现。B-B.3.3 保留最小一字节程序，B-B.3.4 的四字节诊断版必须增加明确价值：参数检查、长度处理、完整返回判断和可观察输出。

### 3. 命令与输出展示规则

- 危险命令先写器件、权限、驱动占用和备份前提，再写命令。
- `-y` 只跳过确认，`-f` 绕过忙设备检查，二者都不能被描述成安全开关。
- 示例输出必须含足够字段，让读者能对应输入，而不是只给一个孤立 `0x48`。
- 退出状态、错误文本和数据内容分开判断。`echo $?` 只证明命令退出结果，不证明 EEPROM 内容符合预期。
- 恢复命令和观察命令放在同一操作闭环中，尤其是 trace、动态调试、解绑和教学驱动实验。

## 五、六篇逐段教学脚本

### B-B.3.1 I2C 物理层与电气特性

**关键对象生命周期**：I2C Core 创建 client；教学模块只使用该 client 并在栈上保存 old_page；正式 TPS40422 驱动声明 `pmbus_driver_info`；pmbus 核心创建 `pmbus_data`、页缓存、锁和传感器属性；hwmon 注册导出文件；解绑回收驱动状态但不销毁 DTS 描述的 client。PAGE 属于芯片，currpage 属于驱动缓存，old_page 属于单次调用，三者不能混写。

**首次依赖登记**：SMBus、Byte Data、Word Data、PEC、`tTIMEOUT/tLOW:SEXT`、PMBus、PAGE、VOUT_MODE、READ_VOUT、`s32`、原生／模拟 SMBus、`EOPNOTSUPP`、`pmbus_driver_info`、`pmbus_data`、`currpage/update_lock/phase`、hwmon、LINEAR11／LINEAR16 均在首次实际操作前解释。PEC 只作为边界说明，不让未实现的校验逻辑混入主程序。

**盲删要求**：删除协议图、调用图、表格、代码和输出后，正文仍能独立说明为什么需要 SMBus／PMBus、Word Data 的字节顺序、三条路径的工作分配、PAGE 并发错页、指数来源和 hwmon 文件的生命周期。路径 C 不能只剩一条调用链。

### 2. `i2cdev-lab`：一笔用户态读取怎样进入内核并返回

**代码资产**：`i2c-rdwr-read.c`、`drivers/i2c/i2c-dev.c`、`drivers/i2c/i2c-core-base.c`、`include/uapi/linux/i2c.h`、`include/uapi/linux/i2c-dev.h`、`include/trace/events/i2c.h`。RK3568 控制器只在完整函数需要时引用，不重新制作整套框架实验室。

**共享初始状态**：`bus=/dev/i2c-1`、`addr=0x50`、`offset=0x10`、`read_len=4`、用户数据初值未知、预期完成消息数 2。

| 步骤 | 路径与代码范围 | 本步状态字段 | 观察结果与教学目的 |
|---|---|---|---|
| 1. 解析命令 | 教学 `main()` 参数与消息初始化 | `msgs[0].len=1`、`msgs[1].len=4`、`nmsgs=2` | 命令参数变成两条消息，不是两次 ioctl |
| 2. 打开总线 | 教学 `open()` → `i2cdev_open()` | `fd`、`file.private_data`、匿名 `client.adapter`、adapter 引用 | 每次打开有独立匿名 client，不注册新硬件 |
| 3. 进入 I2C_RDWR | `i2cdev_ioctl()` 分派 | `cmd=I2C_RDWR`、用户指针、`nmsgs=2` | 为什么本例不需要 I2C_SLAVE |
| 4. 复制消息和写数据 | `i2cdev_ioctl_rdwr()` 前半 | 内核 `msgs`、`data_ptrs`、每条内核 buf、已分配计数 | 用户地址与内核地址分开，失败要释放已分配部分 |
| 5. 提交 Core | `i2c_transfer()`、`__i2c_transfer()` | `bus_lock`、当前 algorithm、`res` 尚未返回 | 同一 adapter 的事务串行，匿名 client 不提供 at24 锁 |
| 6. 写偏移并重复 START | `master_xfer()` 与 i2c_write/read 事件 | `#0 f=0000 l=1 [10]`、`#1 f=0001 l=4` | 软件消息与协议两段对应，波形仍须仪器验证 |
| 7. 返回读数据和消息数 | `i2c_reply/i2c_result` 与 Core 返回 | 内核读 buf=`48 65 6c 6c`、`res=2` | 返回值 2 是消息数，不是读字节数 |
| 8. 复制回用户并释放 | `i2cdev_ioctl_rdwr()` 后半 | `copy_to_user` 结果、内核 buf 释放、用户 readback | 只有读消息回写；`EFAULT` 时总线可能已经执行 |
| 9. 用户检查并打印 | 教学 `ret<0`、`ret!=2`、printf | `ret=2`、进程输出和退出状态 | 数据、消息数和进程退出分别验证 |
| 10. 关闭文件 | 教学 `close()` → `i2cdev_release()` | 匿名 client 释放、adapter 引用放下、`private_data=NULL` | 不销毁正式 client 和 adapter |

**失败场景**：

- `open` 失败：没有匿名 client 可继续使用，打印节点／权限错误，不进入 ioctl。
- `I2C_SLAVE` 遇 `EBUSY`：只用于 `UU` 对照场景，正式 client 仍绑定，用户传输未开始，不强制绕过。
- 地址 NACK：控制器返回负错误，事件只出现实际到达的阶段；用户 `ioctl=-1/errno`，不打印四字节成功。
- 短事务 `res=1`：第二条未完整完成，教学程序转 `EIO`，不使用未完整 readback。
- `copy_to_user=-EFAULT`：总线已执行但结果复制失败，内核临时内存仍释放，用户不能把旧缓冲区当新数据。
- close 失败：通信结果与关闭结果分别报告，不静默丢失。

**浏览器验收**：正常和每个失败场景逐步执行；每步切换片段／完整函数；核对匿名 client、data_ptrs、res 和 readback 同步变化；源码工作台至少加载教学 C、i2c-dev 和 core-base；验证 hash、键盘、复制、下载、错误 URL、375／768／1024／1440 px 和无自身资源 404。没有像素截图时只报告 DOM 和布局结果。

### 3. `at24-lab`：`dd` 怎样变成 8＋4，并重绑恢复

**代码资产**：`at24c02c_rw.c`、DTS、`at24.c`、`nvmem/core.c`、`regmap-i2c.c`、at24 DT binding 和 Kconfig。

**共享初始状态**：`off=0x10`、`count=12`、`page_size=8`、`write_max=8`、`byte_len=256`、数据 `Hello-EEPROM`。

| 步骤 | 路径与代码范围 | 本步状态字段 | 观察结果与教学目的 |
|---|---|---|---|
| 1. DTS 进入匹配 | 教学 DTS、at24 匹配表 | `addr=0x50`、`compatible=atmel,24c02`、`pagesize=8` | 器件地址、内部偏移和页大小不是同一字段 |
| 2. probe 创建对象 | `at24_probe()` | regmap、`at24_data`、`lock`、`nvmem_config` | 每个对象来源和关联清楚 |
| 3. NVMEM 创建文件 | `devm_nvmem_register()`、`nvmem_sysfs_setup_compat()` | `nvmem_device`、`eeprom` bin file | `eeprom` 是内核入口，不是磁盘文件 |
| 4. dd 写入 12 字节 | `bin_attr_nvmem_write()`、`nvmem_reg_write()` | `pos=16`、`count=12`、用户 buf | 文件位置成为 EEPROM 偏移 |
| 5. 第一轮切为 8 | `at24_write()`、`at24_adjust_write_count()` | `off=0x10`、`next_page=0x18`、本轮 8 | 页切分同时考虑起始偏移 |
| 6. 第一笔上线 | `at24_regmap_write()`、regmap-i2c | 写 buf=`0x10＋Hello-EE`、at24 lock 持有 | 一次写消息含内部地址和 8 个数据字节 |
| 7. 等待／重试后推进 | at24 写重试环和循环 | `buf+=8`、`off=0x18`、`count=4` | 写周期通过失败重试处理，不是固定成功睡 5 ms |
| 8. 第二笔写 4 | 同一写路径 | 写 buf=`0x18＋PROM`、最终 count=0 | 两笔合起来才是完整 12 字节 |
| 9. 顺序读 12 | NVMEM read、at24 read、regmap-i2c | 两个 msg、读 buf 12 字节、文件返回 12 | 页写限制不适用于顺序读 |
| 10. 解绑与重绑 | unbind、devm 回收、重新 probe | 旧 at24_data 释放，新 lock/NVMEM 创建，EEPROM 内容保留 | 软件对象生命周期与非易失内容分开 |

**失败与对照场景**：

- 第二笔持续 NACK 到超时：第一笔可能已写，第二笔失败，无整笔回滚。
- 从 `0x12` 请求写 8：第一轮 6、第二轮 2，用来反驳“总长度除以 8”。
- `pagesize` 缺失：按 v6.6 实际代码推演 page_size 回退，结论必须重新核验，不写成硬件自动探测。
- 错写 16 字节页：只展示危险模型，不能引导对真实器件执行；显示回卷风险。
- A/B 经 sysfs：等待同一 at24 lock；C 经 `/dev/i2c`：绕过该锁，展示交叉访问风险。
- 零长度 ACK 探测不受支持：用户程序回退固定等待，最终仍须读回验证。

**浏览器验收**：正常、第二笔失败、非对齐写入、锁对照和解绑重绑场景逐步执行；重点核对 `off/count/buf/page_size/lock` 和文件存在状态；完整函数可回到 `at24_write()` 和 `at24_adjust_write_count()`；源码工作台可下载用户程序与 DTS；其余按共用浏览器清单验收。

| 3. 读取 VOUT_MODE | raw／SMBus Byte Data | mode=0x17 | 格式与测量值分两次读取 |
| 4. Word Data Read | raw 两消息、`i2c_smbus_read_word_data()` | wire low=00、high=03、raw=0x0300 | 辅助函数组合低高字节，但不知道电压 |
| 5. 原生或模拟 SMBus | `i2c_smbus_xfer()`、`i2c_smbus_xfer_emulated()` | `smbus_xfer` 可用性或 `EOPNOTSUPP`、fallback msgs | SMBus 不是另一套物理总线 |
| 6. 解码为毫伏 | 教学 `demo_decode_mv()`、pmbus linear 分支 | exponent=-9、millivolts=1500 | 指数来自 VOUT_MODE，不来自 raw 高 5 位 |
| 7. 恢复原 PAGE | raw／SMBus 写 PAGE | 芯片 PAGE=0，恢复错误显式上传 | 成功和失败路径都要恢复，恢复不修正已读错数据 |
| 8. 正式驱动建链 | `tps40422_probe()`、`pmbus_do_probe()` | pages=2、`currpage=-1`、update_lock、hwmon | 器件驱动声明能力，通用核心创建状态 |
| 9. `cat in2_input` | show/update/read/set_page/decode/sysfs_emit | 目标 page=1、sensor raw、文本 1500 | 路径 C 复用页管理、解码和标准接口 |

**失败场景**：

- A/B 交错切页：A 的 old_page 正确但 READ_VOUT 读错通道，展示驱动外访问不受 update_lock 约束。
- 原生 SMBus 不支持：回退普通 I2C 消息，比较线上事务不变。
- VOUT_MODE 非 `0x17`：本教学解码拒绝继续，不硬套 -9。
- READ_VOUT 负错误：不把负值强转 u16，不输出旧传感器值。
- PAGE 恢复失败：读取值即使得到，也不能静默宣称整个操作成功。
- 两次实时测量不同：不据此断言 raw 与 SMBus 不等价，保持电源稳定或比较事务轨迹。

**浏览器验收**：路径 A/B/C 使用同一初始状态可切换；PAGE、old_page、currpage 分开显示；每步能进入完整函数；`in2_input` 的读取链可回到真实 pmbus 源码；失败场景显示恢复和错误传播；其余按共用浏览器清单验收。

## 十、Q&A 与四种读者代理验收设计

### 1. Q&A 必须覆盖的理解障碍

每篇正文重写后从下列问题池选择并调整，答案必须能由本篇正文独立支持。问题中必须自带必要数字和状态，不写“上述命令”“这个值”之类脱离正文就失去含义的指代。

**B-B.3.1**：

- 开漏器件放手后为什么由上拉形成高电平，这与第 9 拍 ACK 有何关系？
- `clock-frequency=<400000>` 已生效，为什么实际波形仍可能不满足当前模式？
- 两个地址均为 `0x50` 的设备为什么能同时 ACK，并在返回 `0x5A/0x3C` 时让主机读到 `0x18`？
- 降速后通信恢复，为什么不能直接宣布上拉、电容或布局问题已修复？
- 多主仲裁为什么不是任何情况下都由较小地址获胜？

**B-B.3.2**：

- `0x50` 为什么在线上变成 `0xA0/0xA1`，软件参数为什么不能直接填 `0xA0`？
- 主命令为什么是两个消息段、一笔事务，重复 START 阻止了什么？
- 读取 `48 65 6c 6c` 时，为什么前三个字节后 ACK、最后一个字节后 NACK？
- M1 写偏移 `0x10` 后若 STOP，M2 怎样在所有字节都 ACK 的情况下让 M1 读错？
- SDA 卡低和 SCL 卡低为什么不能共用“补 9 拍”结论？

**B-B.3.3**：

- `probe(client)` 中的 client 由谁创建，`reg=<0x50>` 经哪些代码进入它？
- 为什么 `i2c->adap.algo` 分别使用 `.` 和 `->`？
- `i2c_transfer()` 返回 2、`demo_read_reg()` 返回 0 和读到 `0x48` 分别表示什么？
- 两个进程打开 `/dev/i2c-1` 后，哪些对象独立，哪些对象共享？
- GPIO 模拟替换后，为什么外设的 `demo_read_reg()` 不必改变？

**B-B.3.4**：

- 对 `/dev/i2c-1` 执行 `w1@0x50 0x10 r4` 时，open、ioctl 和 close 各创建或销毁什么？
- `UU` 出现时，at24 的正式 client 与用户匿名 client 分别处于什么状态，为什么总线锁不够？
- `i2cdev_ioctl_rdwr()` 为什么同时需要内核 buf 和 `data_ptrs`，`EFAULT` 为何不代表总线未执行？
- trace 中 `#0/#1`、`a=050`、`f=0001`、`l=4`、`n=2`、`ret=2` 怎样对应主命令？
- 读回全 `0xff` 为什么不能直接等同于设备不在线或数据帧 NACK？
- 逻辑分析仪与示波器分别能排除哪类问题，为什么 trace 成功不能替代波形？

**B-B.3.5**：

- 从 `0x10` 写 `Hello-EEPROM` 为什么是 8＋4，一次发送 12 字节会覆盖哪里？
- “随机存取”为什么不等于批量写入无页限制，过去不分页也可能成功的四种原因是什么？
- `eeprom` 文件由谁创建，client、at24_data、regmap 和 NVMEM 如何关联？
- 第一笔 8 字节成功、第二笔 4 字节超时后，芯片内容可能是什么，驱动能否回滚？
- 为什么读 12 字节不需要按页拆分，`dd` 的 12 字节返回与 at24_write 的 0 是否矛盾？
- at24 锁能否保护 `/dev/i2c` 访问，解绑和重绑分别保留或重建什么？

**B-B.3.6**：

- 只用 `i2c_transfer()` 读取 TPS40422，为什么仍须实现 PAGE、VOUT_MODE 和 READ_VOUT 语义？
- `i2c_smbus_read_word_data()` 已返回 `0x0300`，为什么仍不知道电压是 1.5 V？
- A 已保存 `old_page=0`，B 为什么仍能使 A 的 READ_VOUT 读到错误通道？
- `00 03` 和 `0x17` 怎样得到 `0x0300`、指数 -9 和 1500 mV，为什么不能套 LINEAR11？
- 三条路径是否使用不同硬件总线，各自省掉了什么、保留了什么？
