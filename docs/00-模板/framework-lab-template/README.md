# Framework Lab 可复用模板

## 什么时候使用

当一个章节的理解障碍不是“缺少名词解释”，而是读者难以同时跟随**代码位置、对象关系、状态变化和返回值**时，可以在完整正文之外增加交互实验室。

三种材料各司其职：

- **正文**：独立回答主问题，交代前置依赖、完整调用链、关键代码、验证方法与未验证边界。删除 iframe、图、表、代码块和命令输出后，剩余文字仍须保留完整论证；正文中的代码和输出用于帮助跟随，不是省略文字解释的理由。
- **步骤片段**：把同一笔操作拆成可前进、后退和复位的步骤，同步高亮当前几行代码、对象状态和观察结果。片段回答“这一步看哪里”，不能只剩一行孤立调用。
- **完整函数与源码工作台**：完整函数视图恢复当前片段的真实前后文和绝对行号；源码工作台直接加载正文引用的完整文件，支持复制和下载。二者回答“这段代码从哪里来、周围还有什么”。

实验室是正文的另一种视图，不是正文省略机制讲解的理由。本模板只提供交互骨架和占位数据。`B-B.3.3 I2C Linux 驱动框架` 及其 `i2c-framework-lab` 是完整领域参考实现；不要把 I2C 的具体对象和推演数据误当成通用模板内容。

## 先在正文建立源码地图

不要从实验室控件开始设计。先围绕本节的同一贯穿实例，在正文回答以下问题：

1. 子系统入口、核心层、硬件适配层和用户接口分别由哪些真实文件承担？
2. 对象在哪个初始化入口创建，在哪条运行路径建立关系，经哪些函数完成一次操作，最后在哪里释放？
3. 当前步骤属于启动路径还是运行路径？它与前后函数如何衔接？
4. 哪些代码是本节教学代码，哪些逐字来自内核或厂商源码？版本、配置和路径分别是什么？
5. 读者要修改功能、移植硬件或排查故障时，应回到哪个文件和函数？

以 Linux 子系统为例，可以按实际源码核验核心入口、UAPI、总线核心、控制器或设备驱动、算法与构建入口。不要机械套用 I2C 的目录，也不要把源码地图写成只有路径和名词的清单。每个入口都应挂到同一笔操作的启动链或运行链上；与主线无关的目录不为了“完整”而堆入。

## 文件结构

```text
framework-lab-template/
├── README.md                 # 本说明；复制到具体章节后可不带走
├── lab.html                  # 语义结构、两个视图和所有控件
├── lab.css                   # 无外部依赖的固定深色工作台与移动布局
├── lab.js                    # LAB_CONFIG、单步、代码视图、hash、键盘、源码加载与复制
├── extract_fullcode.py       # 从源文件提取完整代码并计算真实起始行
├── test_extract_fullcode.py  # 提取器的标准库单元测试
├── fullcode.manifest.json    # 提取清单
├── fullcode.js               # 生成的 window.LAB_FULL_CODE；不要手改
└── code/
    └── example.c             # 占位教学文件，不是驱动
```

无需 npm、打包器、在线字体或第三方脚本。MkDocs 构建会把 HTML、CSS、JS 和源码作为静态文件复制到站点。修改提取器后，在模板目录运行 `python test_extract_fullcode.py`，至少验证函数首尾、绝对起始行、多函数连续区间和乱序拒绝；新增源码族还要补充针对该语法形式的测试。

## 复制到具体章节

推荐沿用当前总线章节的目录约定：

```text
docs/<板块>/<节组>/
├── <节号>_<标题>.md
├── html/<主题>-lab.html
├── html/<主题>-lab.css
├── html/<主题>-lab.js
├── html/<主题>-fullcode.js
├── html/<主题>-fullcode.manifest.json
└── code/<节号>/<完整教学源码>
```

复制后同步完成以下工作：

1. 将 `lab.*` 重命名为本章主题，并修改 HTML 中 CSS、完整代码 JS 和交互 JS 的引用文件名。
2. 修改 `lab.js` 顶部的 `LAB_CONFIG`，替换标题、贯穿实例、场景、步骤和源码清单。
3. 根据实验室与源码目录的相对位置修改每个源码条目的 `url`。若 HTML 位于 `html/`、源码位于平行的 `code/<节号>/`，通常使用 `../code/<节号>/<文件名>`。
4. 把提取脚本放在本章源码工作目录，或在命令行传入本章 manifest；不要覆盖其他章节生成的完整代码数据。
5. 逐字核验教学代码和引用源码，分别标注来源、版本、运行上下文和验证状态。

## 生成统一完整代码数据

在 manifest 所在目录运行：

```bash
python extract_fullcode.py fullcode.manifest.json
```

模板示例生成两个资产：`exampleFile` 是 `code/example.c` 整文件，从第 1 行开始；`exampleExecute` 是完整 `example_execute()`，从第 12 行开始。生成结果为 `fullcode.js`，并在 `lab.js` 之前加载：

```html
<script src="fullcode.js"></script>
<script src="lab.js"></script>
```

manifest 支持三类提取项：

- `wholeFile`：保留整个文件，起始行为 1。
- `function`：提取一个函数定义。
- `functions`：按源码顺序列出同一文件中的多个函数，输出覆盖首尾函数的连续区间，函数之间的原文也保留；函数不得重叠或乱序。

每项以输出 `key` 为名称，并登记源文件 `source`、展示路径 `displayPath` 和来源性质 `origin`。可用顶层 `output` 与 `globalName` 修改输出文件名和浏览器全局变量名，默认分别为 `fullcode.js` 与 `LAB_FULL_CODE`。

提取脚本只使用 Python 标准库，支持常见 C 函数定义，**不是通用 C 解析器**。宏拼接、复杂声明、条件编译或其他语言可能无法可靠识别。每加入一种新源码形式，都必须对照原文件检查首尾行、函数完整性和起始行；识别失败时先修正清单或提取方法，不能猜行号。

完整代码必须逐字来自指定源文件。不得拼接不相关片段后伪造连续行号，不得把教学代码写成内核原文，也不得为了让高亮“好看”而调整原源码。生成只完成文本提取，不证明源码能编译或运行。

## 配置步骤数据

`LAB_CONFIG.scenarios` 可以包含正常、NACK、超时等不同条件。每个场景由有序步骤组成，每一步字段如下：

- `label`：步骤按钮上的短名称，应描述动作而不是泛泛的“阶段一”。
- `path`：真实源码路径与函数上下文；教学代码须明确标注。
- `code`：本步骤需要跟随的短片段，聚焦当前几行及其必要条件。
- `startLine`：片段第一行在原文件中的绝对行号，从 1 开始。
- `line`：当前高亮行的绝对行号，必须落在 `startLine` 至片段末尾之间。
- `full`：可选，形如 `{ key: "exampleExecute", needle: "if (!request)" }`。`key` 引用 `window.LAB_FULL_CODE`，`needle` 是该资产中唯一的原文片段，用于计算完整视图的高亮行。
- `states`：本步骤结束时的对象字段、锁、缓冲区、状态机和返回值。
- `observations`：读者此刻能够核对的现象，不再重复一遍代码名称。
- `note`：解释为什么执行到这里、关键行改变了什么、下一步为何发生。

初始化时，`makeFullView()` 把 `full` 解析为 `fullView`。缺少 key、找不到 needle、needle 不唯一、起始行非法都会抛出带具体 key 或 needle 的错误，避免静默展示错误代码。没有 `full` 的步骤仍显示片段，但“完整函数”按钮禁用；不得拿另一段代码冒充完整来源。

片段和完整视图共用绝对行号。切换按钮只改变代码范围，不改变当前步骤、对象状态或解释；前后单步、场景切换、复位、hash 和键盘操作仍沿用同一步骤数据。源码工作台加载完整文件，行号从 1 开始。

正常路径和失败路径应从同一贯穿实例出发。失败路径要说明判断条件、未执行部分、状态保留或清理方式、返回值以及调用者如何判断，不能只把结果染红。

源码工作台条目字段为 `name`、`kind`、`url`、`context`。`context` 必须说明文件用途、构建或运行上下文及验证状态。示例值、占位引脚和模型推演不得写成实测结果。

## 正文嵌入方式

以下片段放在正文相应机制讲解之后，不要用它取代正文：

```markdown
<div class="interactive-demo">
  <iframe
    src="../html/<主题>-lab.html"
    title="<节号> <主题>交互实验室"
    loading="lazy"
    style="width:100%;height:960px;border:0;"
  ></iframe>
</div>

[在新窗口打开交互实验室](./html/<主题>-lab.html){: target="_blank" rel="noopener noreferrer" }。实验室展示的是依据已核验资料构造的模型，不连接真实硬件。
```

`target="_blank"` 让实验室在新标签页打开，正文保留在原标签页，便于双屏或并排对照；`rel="noopener noreferrer"` 避免新页面取得原页面的 `window.opener`。项目的 `mkdocs.yml` 已启用 `attr_list`，因此这段属性写法可用。

iframe 高度应按实际内容调整，并检查嵌入视图是否出现不必要的双层滚动。正文中的链接路径与 iframe 的 `src` 不一定相同：前者相对当前 Markdown 页面 URL，后者相对生成的 HTML 页面 URL，必须在构建后的站点中点击验证。

## 正文与实验室怎样互相跳转

- 正文在对应小节后嵌入实验室，并用一句话说明它辅助回答哪个问题。
- 实验室的步骤 `path` 使用与正文一致的源码路径和函数名，读者可以按名字回查。
- 正文给出关键调用链和完整论证；实验室给出步骤片段，完整函数视图恢复前后文，源码工作台提供整份文件。
- 对特别长的章节，可在正文中给实验室链接增加 `#mechanism` 或 `#source`，直接进入对应视图。
- 不要在实验室里复制整篇正文；需要完整论证时返回正文，需要完整文件时进入源码工作台。

## 四种读者代理验收

每次替换为具体章节后，逐项实际通读，不以模板曾通过验证代替本章验收：

- **依赖读者**：首次出现的术语、字段、宏、函数、命令和输出字段，是否已在正文就地解释或指向准确前置篇目？源码地图、步骤片段、完整函数和源码工作台是否又悄悄引入了新名词？
- **主线读者**：从第一个步骤到最后一个步骤，是否始终回答本节唯一主问题？源码地图是否串起同一笔操作，而非目录清单？切换正常和失败场景后，贯穿实例是否仍是同一笔操作？
- **盲删读者**：删除 iframe、图、表、代码块和命令输出后，正文能否独立讲清机制？反过来，实验室是否也能让读者看清每一步的代码、状态和解释，而不是只有动画？删掉步骤片段后，完整函数与文字能否恢复上下文？
- **跟随读者**：能否按步骤指出当前源码位置、绝对行号、输入、关键行、状态变化、返回值和验证方法？能否在片段与完整函数之间来回切换，并从源码工作台取得同一份完整文件，知道它是否编译、运行或上板过？

任一关键问题回答不出来，就先修正文或步骤数据，不用视觉美化掩盖教学缺口。

## 浏览器与构建验收

在真实浏览器中至少执行以下操作：

1. 从构建后的正文点击“在新窗口打开”，确认正文标签页保留、实验室出现在新标签页，且链接带有上述 `target` 和 `rel`。
2. 逐一点击所有场景的步骤按钮、上一步、下一步和复位；在每一步分别切换“步骤片段／完整函数”，确认路径、真实起始行、绝对高亮行、计数、状态和解释同步变化。没有完整代码的步骤必须禁用切换。
3. 使用左右方向键推进机制步骤，切换 `#mechanism` 与 `#source` 并刷新，确认 hash 路由仍可用。
4. 逐个加载源码文件，执行复制和下载；制造一次错误 URL 时，应出现可读错误而不是空白或脚本异常。
5. 在 375、768、1024、1440 px 视口检查页面无整体横向溢出；代码区和步骤条允许自身横向滚动，控件可点击且长路径能够换行。
6. 确认实验室无 JavaScript 异常、无 `console.error`、无自身资源 404。全站其他脚本产生的已知问题要单独记录，不能混作本实验室结果。
7. 使用项目规定的用户 Python 运行严格构建，退出码必须为 0，且无 MkDocs WARNING。本项目的命令是：

   ```bash
   "/c/Users/75672/AppData/Local/Python/pythoncore-3.14-64/python.exe" -m mkdocs build --strict
   ```

构建成功只证明文档和静态资源能够生成，不证明教学源码已经编译、运行或上板验证。最终汇报必须分别列出源码／文档核验、浏览器交互验证和尚未完成的硬件相关验证。若未获得可用像素截图，只能报告 DOM 交互和布局检查，不得宣称完成视觉截图验收。
