    二、六篇实际整改记录¶

    1. B-B.3.1：物理层与电气特性¶

    原断点

    • 开漏、线与和共享总线容易停留在定义，读者不容易把它们与 ACK、仲裁和地址冲突连起来。
    • 上拉电阻、总线电容的长计算和电平兼容展开过深，偏离软件工程师判断“继续改软件还是转查硬件”的需要。
    • “两个同地址设备”容易被误解成总线按先后顺序选择一个设备。

    实际改法

    • 用同一组 SoC、AT24C02、SHT30 和 DS3231 总线贯穿开漏、线与、速率、时序、电平和地址条件。
    • 接入开漏、线与／ACK、时序与 RC 三个交互演示，但保留正文自己的因果解释。
    • 删除偏原理图设计的电阻与电容长计算，保留上升沿、采样和软件配置不能改变物理波形这些必要边界。
    • 电平部分收束为两个软件人员必须会提出的问题：接收方能否识别，引脚能否承受。
    • 明确同地址冲突不是“先到先得”：两个设备可能同时响应，ACK 正常也不能证明数据语义正确。

    当前资产

    • html/open-drain-demo.html
    • html/wired-and-ack-demo.html
    • html/i2c-timing-rc-demo.html

    验证边界

    正文机制与演示用于教学推演，不证明某块板卡的上拉、电容、电平、波形或同地址行为已经测量。

    2. B-B.3.2：协议层与帧格式¶

    原断点

    • START、STOP、ACK 和重复 START 若分开背定义，读者仍无法把软件地址、寄存器地址和读回数据对应到一笔抓包。
    • 主设备末尾 NACK、STOP 对内部访问位置的影响、时钟延展与总线清除容易混成“传输失败”的笼统描述。

    实际改法

    • 当前正文固定使用“从 0x50 的寄存器 0x01 读取一字节，得到 0xAB”作为主实例。
    • 把 0x50 与写方向地址字节 0xA0、读方向地址字节 0xA1 的换算写清，避免把线上地址字节传给 Linux 的 7 位地址参数。

    6. B-B.3.6：SMBus 与 PMBus¶

    原断点

    • 没有先回答“明明已有 I2C，为什么还需要 SMBus 和 PMBus”，三条路径容易变成新的名词分层。
    • raw、SMBus、pmbus/hwmon 的代码量与工作分配不直观，读者会怀疑绕开它们、自行用 I2C 加应用解析是否等价。
    • PAGE 共享状态、VOUT_MODE 解码、页恢复、PEC 和 hwmon 属性编号缺少同一笔数据上的完整推演。

    实际改法

    • 用同一笔 TPS40422 第二路电压读取，按 raw I2C → SMBus → pmbus/hwmon 的顺序逐层减少手工工作。

    • 用交错访问说明 PAGE 是器件共享状态，old_page、currpage 和 update_lock 分别解决什么问题。
    • 推导 in2_input 的属性编号，说明负错误不能继续解码成电压，PAGE 恢复也要读回，PEC 标志需要保存与恢复。

    四、可复用的正文写作规范¶

    1. 先确定唯一主问题，再决定材料顺序¶

    一节只承担一个主问题。每个小节必须推进“输入 → 对象／机制 → 状态变化 → 输出／证据”，不能只因某个名词相关就加入。若删除小节后主线完全不受影响，应重新判断它是否属于本篇。

    2. 先建立手工完整基线，再讲框架减少了什么¶

    读者先看见一笔操作不依赖高级封装时需要完成哪些工作，才能理解辅助函数、子系统或正式驱动真正省掉了什么。先给抽象分层，再让读者自己想象底层工作，通常只会增加名词负担。

    3. 首次依赖必须在首次使用前解释¶

    术语、结构体字段、宏、函数、命令参数和输出字段，应在首次使用前就地解释，或链接到确实讲过该内容的准确前置篇目。Q&A 只能检查理解，不能替正文补课；源码地图和实验室引入的新名词也受同一约束。

    4. 比较两个对象前，双方都要先出现¶

    不能只介绍推荐方案，再拿一个读者尚未见过的方案作对照。比较应落在同一笔操作上，说明双方分别负责什么、保留什么、失败时谁处理，而不是只列优缺点。

    5. 结构体必须进入操作序列¶

    讲解结构体至少回答：

    • 谁创建、谁持有、谁销毁；
    • 当前操作使用哪些字段，初值从哪里来；
    • 哪行代码改变字段或对象关系；
    • 哪些状态被共享，哪些状态每次调用独立；
    • 成功、失败和清理路径分别留下什么结果。

    只给字段表不能替代这些推演。

    6. 共享状态必须至少有两个参与者¶

    锁、缓存、器件页、内部地址和软件副本，必须通过参与者 A、B 的具体时间序列说明。若只有一个参与者，通常只能证明字段存在，不能证明为什么需要同步、保存、恢复或失效处理。

    7. 调用链只是目录，完整函数才是代码上下文¶

    正文调用链负责定位，不能代替关键行解释。步骤片段回答“现在看哪里”，完整函数回答“前后还有什么”，完整源码回答“这份定义从哪里来”。三者的路径、版本、行号和高亮必须指向同一份原文，不能手工拼出看似连续的假代码。

    8. 正常产品路径先于排障和源码逆向¶

    先让读者在推荐路径上完成一次正常操作，再进入失败注入、替代路径和内核实现。不能用“故意写坏看现象”代替正常闭环，也不能把只适合受控实验的强制访问写成日常默认操作。

    9. 错误、清理和恢复属于主机制¶

    负错误、短传输、部分写入、回拷失败、解绑、重绑和恢复错误都应沿主实例说明。第二笔失败不等于第一笔未发生，EFAULT 不等于硬件未执行，重绑也不等于旧运行时对象仍然存在。

    10. 实验判据不能把动态值硬改成常量¶

    备份长度、实时遥测、硬件状态和并发结果不一定是确定性常量。实验应先检查前提，不满足就停止或记录当前值，再按语义判断；不能为了让脚本“通过”而把动态观测写成固定预期。

    11. 正文必须盲删成立¶

    删除 iframe、图片、表格、代码块和命令输出后，剩余正文仍应保留完整因果、状态和验证论证。图表与实验室用于降低跟随成本，不承担正文中缺席的唯一解释。

    12. Q&A 检查真正的理解障碍¶

    问题应覆盖首次依赖、对象生命周期、共享状态、返回口径、错误恢复和验证边界，不重复正文标题，不用“是否理解了某某”的勾选表代替回答。

    五、交互实验室复用规范¶

    通用操作细节已写入 Framework Lab 可复用模板，B-B.3.3 是领域参考实现。本次整改进一步确认以下原则：

    1. 先写正文源码地图，再做实验室。 不从控件和动画倒推知识结构。
    2. 一个领域实例对应一份源码真源。 完整代码由指定文件提取，片段、完整函数和源码工作台不能维护三份互相漂移的副本。
    3. 每一步同时显示代码位置、对象状态和观察结果。 只高亮一行调用，不解释为什么执行、改变了什么，仍然无法跟随。
    4. 正常、失败、共享状态和恢复场景都应从同一实例出发。 失败场景要显示判断、未执行部分、清理、返回值和调用者动作。
    5. 正文与实验室可以并排。 “在新标签页打开”使用 target="_blank" rel="noopener noreferrer"，避免覆盖正文，便于双屏对照。
    6. 移动端允许代码区自身滚动。 页面主体不能整体横向溢出，长路径应可换行，控件在窄屏仍可点击。
    7. 浏览器通过只代表 DOM 模型通过。 不得把状态机推演写成真实总线、存储芯片、传感器或仪器仿真。

    新增其他 Linux 子系统实验室时，应复制交互骨架和验收方法，不照搬 I2C 的对象、目录和状态数据。
