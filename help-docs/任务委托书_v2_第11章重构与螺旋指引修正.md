### 3.2 与第二部"四段式"模板的共存关系（v2 新增，必须遵守）

第二部 9 章共享"问题场景 → 机制深入 → 设计考量 → 排错指南"四段式模板，该一致性必须保持。第11章的处理规则：

1. **11.0 / 11.1 定位为"其然台阶"**，在章首"为什么需要这一章"之后、"四段式内容"之前，使用第一部式实践小节格式（代码 + 命令 + 验证步骤），**不套用四段式**。
2. **11.2 起的机制主体继续沿用四段式**：原"问题场景"改写为以 11.0/11.1 的亲身经历为锚（"你在 11.0 已经看过 probe() 被调用，但如果 insmod 后 probe 没有执行呢？"），机制深入/设计考量/排错指南内容不变。
3. 章级 H3 结构保持第二部模板不变：为什么需要这一章 / **其然台阶（11.0-11.1）** / 四段式内容（11.2-11.6 详述）/ Trade-off表格 / 实践案例 / 常见陷阱 / 与前后章的关联。即"其然台阶"作为新增 H3 插入，其余 H3 不动。

### 3.3 衔接话术

**11.0结尾 → 11.1开头**：
> 你已经写出了一个最简单的 Platform Driver，也亲眼看到 probe() 被调用了。但实际工作中，驱动不只有这一种写法。有的走 I2C 总线，有的被厂商 SDK 封装，有的干脆硬编码地址……

**11.1结尾 → 11.2开头**：
> 这六种写法看起来天差地别：有的走设备树，有的硬编码；有的注册到内核总线，有的注册到厂商框架。但内核不可能为每种写法单独写管理逻辑——这背后一定有一个统一的抽象层：总线-设备-驱动三元模型。下一节从源码层面拆解这个模型，回答一个核心问题：为什么 insmod 成功不等于 probe() 执行？

## 四、任务清单

### 任务1：撰写 11.0 先写一个驱动 [B→I]

- **内容**：基于第6章 LED 实验的硬件上下文（同一个 GPIO、同一个设备树节点），写一个最简 Platform Driver，替代 `leds-gpio`。
- **必须包含**：完整 `.c` 文件（含头文件）、完整 `Makefile`、设备树 `.dts` 片段、编译命令、加载命令（`insmod`）、验证步骤（`ls /sys/class/leds/` 出现自定义节点、`echo 1 > brightness` 点亮 LED）、预期 `dmesg` 输出。
- 代码注释只解释"这是什么"，不解释"为什么"（机制留给 11.2）。
- **只写这一种写法**，不展开六种，避免信息过载。

### 任务2：撰写 11.1 原来驱动还有这么多种写法 [I]

**硬件假设（v2 修正）**：
- 模式①：使用 **SoC 内置温度传感器**（RK3568 TSADC / i.MX6ULL TEMPMON，platform + IIO 或 hwmon，真实存在于正文所用板卡）。**禁止**用 platform_driver 包装 LM75——那是教学上有害的怪胎写法。
- 模式②-⑥：使用 **LM75/TMP75 温度传感器**（I2C 地址 0x48，模块约 ¥3，或 GPIO 模拟 I2C）。
- 开发板：RK3568 / i.MX6ULL / 全志D1，与第一部一致。

**六种模式**：

| 模式 | 名称 | 验证分级（v2 修正） | 必须包含 | 验证标准 |
|------|------|-------------------|---------|---------|
| ① | 现代标准型 platform_driver + DT | **A级：上板可验证** | `.c` + `Makefile` + dts（SoC TSADC 节点） | `dmesg` 出现 probe 日志，`/sys/class/hwmon/` 或 IIO `in_temp_input` 可读 |
| ② | 总线依附型 i2c_driver | **A级：上板可验证** | `.c` + `Makefile` + dts（`&i2c0 { lm75@48 {...} }`） | `cat /sys/class/hwmon/hwmonX/temp1_input` 有数值 |
| ③ | 厂商框架型（海思/瑞芯微/全志 SDK 风格） | **B级：可编译 + 设计剖析** | 可 `make` 通过的树外模块骨架 + 框架结构剖析图 | 编译通过；验证环节改为代码走读，注明 API 为"模拟风格" |
| ④ | Legacy 裸驱动（无DT、硬编码、`register_chrdev`） | **A级：上板可验证** | `.c` + `Makefile`（无设备树） | `mknod /dev/temp c 240 0` 后 `cat /dev/temp` 读出温度 |
| ⑤ | MFD 复合型（PMIC 子功能，`regmap`） | **B级：可编译 + 设计剖析** | 可 `make` 通过的模块骨架 + 父子设备关系剖析 | 编译通过；验证环节改为代码走读（若目标板恰好有 RK809 等真实 PMIC，可附可选上板步骤） |
| ⑥ | 用户空间型（`/dev/i2c-0` + ioctl） | **A级：上板可验证** | 用户空间 C 程序 + `gcc` 编译命令 | 直接运行打印 `Temperature: 25.5 C` |

**模式②必须包含的教学点（v2 新增）**：厂商内核通常内置官方 `lm75` 驱动（`CONFIG_SENSORS_LM75`），会与读者自写驱动竞争绑定。验证步骤必须包含：检查 `CONFIG_SENSORS_LM75`、必要时禁用或用 `driver_override` 让自己的驱动先绑定。这是"两个驱动竞争同一个设备"的第一次实体化体验，直接呼应 11.2 的机制讲解。

**篇幅控制（v2 新增）**：模式②作为最典型总线写法**详写**（完整五板块）；模式①④⑥给完整代码但叙述从简；模式③⑤以剖析为主、代码给骨架。目标：11.1 全节控制在普通章节的 1.5 倍篇幅以内。

**每种模式固定板块**：场景一句话（什么时候用这种写法）→ 代码 → 编译指令 → 验证（A级）或走读（B级）→ 引出的问题（为 11.2 埋钩子）。

## 五、写作原则与约束

### 结构约束

1. 11.0 只教一种写法（Platform Driver）；六种放 11.1。
2. 机制讲解（match/probe/uevent/kobject）严格留在 11.2 及之后，11.0 和 11.1 只建立现象级认知。
3. 模式③的 API 名称可虚构，但必须注明"模拟海思/瑞芯微/全志 SDK 风格"。
4. BIEM 标记：11.0 为 [B→I]，11.1 为 [I]，11.2 及之后维持原标注。
5. 11.0 代码必须复用第6章 LED 硬件上下文，读者无需购买新器件。

### 风格约束（plan.md 22条规则，关键条款）

- **R2/R3**：提示框用 `> 💡 / > ⚠️ / > 🔴`，不加"提示/警告/陷阱"标签词；粗体放核心观点，不放 emoji 后第一个词。
- **R6**：代码块去掉 `$` 提示符。
- **R15/R20**：小节开场用"本节覆盖：…"清单式，不用"学完本节，你能…"承诺式，不用比喻式导读。
- 拒绝生活化比喻，工程化直接表述；AI 生成内容须优化为"人写感"读物。

### 验收清单（可 grep 验证）

1. 第11章目录含 11.0-11.6，无 11.7+，无编号跳跃；
2. 11.0/11.1 正文中不出现 `bus_type`/`kobject`/`uevent` 的机制性解释（只允许出现在"引出的问题"中作为提问）；

4. 全文无 `$ ` 开头的代码行、无"**提示**"标签词、无"学完本节"句式；
5. 第一部不再存在"第II部第6章/第7章/第8章/第9章"形式的旧引用；

## 六、最终结论

> 第一部没有"太简单"，它的终点"看到shell"定位合理。真正的问题是第二部"跃迁1"在驱动维度缺少一个台阶：从"用驱动"直接跳到"懂机制"，中间缺了"写驱动"。
>
> 解决方案：第11章建立三级台阶——先亲手写一个（11.0）→ 再看世间百态（11.1，六种写法）→ 最后深入内核机制（11.2 及之后）；同时把第一部的螺旋指引回填到真实章节。这样第二部的"知其然 → 知其所以然"才能真正落地。
