    14.5.2 卸载机制的陷阱与调试¶

    所属章节：第14章 网络子系统 > 14.5 网络卸载机制

    难度：[I] Intermediate | 预计阅读时间：15分钟

    本节导读¶

    上一节我们认识了GRO、GSO、TSO这些卸载机制的原理和优势。但在实际工程中，它们并非总是"开箱即用"——TC限速遇上GSO大包会变成"假限速"，隧道封装让GRO路径变得扑朔迷离，LRO的遗留代码还在某些驱动里"诈尸"。
    本节带你绕过这些常见的卸载陷阱，掌握排查手段。学完后，你将能够诊断卸载相关的问题，并知道何时该果断关掉某个特性。

    知识点233：LRO已废弃与GRO的优势 [I]¶

    LRO 的问题¶

    LRO（Large Receive Offload）是早期网卡采用的一种接收端卸载方案。它的做法非常激进：把多个TCP包直接合并成一个巨大的skb，上层协议栈只看到这一个"超级包"。

    这种做法带来了几个根本性缺陷：

    问题 具体表现
    Netfilter不兼容 合并后的skb丢失了原始包边界，iptables规则无法按单包匹配
    校验和计算错误 巨大skb的伪头部校验和与每个原始包不匹配
    时间戳丢失 多个包的到达时间被压缩成一个，影响RTT计算
    非TCP流量受限 LRO通常只处理TCP，对其他协议无效

    正是因为这些问题，LRO已经被内核社区明确废弃，由GRO取而代之。

    GRO 的改进¶

    GRO（Generic Receive Offload）的核心思想完全不同：它在聚合数据的同时，保留每个包的头部信息。你可以把GRO想象成把多个信封里的信纸叠在一起，但信封还保留着——需要的时候可以随时拆开查看。

    特点 LRO GRO 为什么GRO更好
    头部保留 丢弃原始头部，生成虚假头部 保留每个包的完整头部 Netfilter可以按原始头部规则匹配
    校验和处理 需要重新计算，容易出错 基于原始头部分别校验 校验结果准确可靠
    协议支持 主要支持TCP 支持TCP、UDP等多种协议 适用范围更广
    可逆性 不可逆，合并后无法拆分 可通过GSKB的frag_list还原 灵活性更高，便于后续处理

    GRO和GSO形成了一对"对称"的设计：GRO在接收端把小包聚合成大包走协议栈，GSO在发送端让协议栈处理大包到网卡前再拆分。这种对称性让代码路径更一致，维护起来也更清晰。

    GSO与TC qdisc的交互陷阱¶

    限速作用于"假"大包¶

    GSO的机制是：协议栈生成一个64KB级别的TSO packet，这个包一直走到网卡驱动前的最后一刻才被拆分成真实的MTU大小（如1500字节）的包。
    这意味着，如果你在中间加了TC qdisc做限速（比如HTB），限速器看到的是那个64KB的大包，而不是最终发出去的几十个1500字节小包。

    举个例子：你配置了HTB限速10Mbps。一个64KB的GSO包在qdisc处被视为一个包，按64KB计算令牌消耗。但实际上这个包出去后会变成约43个1500字节小包，总带宽其实是43倍于你的配置——限速形同虚设。

    ⚠️ 陷阱：TC限速 + GSO同时启用时，限速作用于大包而非真实小包。实际限速值可能远大于配置值，在网络拥塞时导致缓冲区溢出和丢包。

    修复方案¶

    解决这个问题的方法是确保TC qdisc在GSO分段之后生效。有几种途径：

    1. 启用gso_split：在qdisc前添加gso_split动作，让大包先被分段，qdisc看到的是真实小包
    2. 降低GSO分段阈值：通过ethtool减小gso_max_size，但会削弱GSO的收益
    3. 在网卡出口限速：把限速放在分段完成后的位置，但这需要驱动支持

    通常推荐第一种方案，在内核较新版本中已经得到良好支持。

    隧道场景下的复杂度¶

    二次封装带来的挑战¶

    VXLAN、GRE等隧道协议有一个外层封装（UDP/GRE头部）和一个内层封装（原始以太网/IP头部）。这导致GRO/GSO需要同时处理两层协议——复杂度不是翻倍，而是呈指数级增长。

    以VXLAN为例：

    • 外层：UDP目的端口4789，这是VXLAN的标识
    • 内层：被封装在内的原始以太网帧，可能是TCP也可能是UDP

    GRO需要判断：外层是VXLAN，然后取出内层再做内层的GRO。这需要专门的实现函数，比如vxlan_gro_receive()。

    💡 提示：隧道场景下要仔细检查内外层GRO/GSO是否都正确启用。只启用外层而忽略内层，会导致被封装在内的TCP流无法享受GRO聚合的收益，CPU消耗居高不下。

    隧道卸载的启用逻辑¶

    隧道设备的卸载启用有一个"级联"关系：

    物理网卡支持GRO/GSO
    └── 隧道设备才能在内层做GRO/GSO
        └── 容器/VM的网络接口才能享受端到端的卸载收益

    任何一环断开，卸载效果就会大打折扣。排查时要从物理网卡逐层向上检查。

    卸载机制陷阱速查表¶

    陷阱 表现 根因 修复方法
    TC限速无效 实际带宽远超HTB配置 GSO大包绕过qdisc计量 启用gso_split，或降低gso_max_size
    隧道内TCP性能差 tun设备CPU高，但物理网卡低 内层GRO未启用 检查vxlan_gro_receive是否注册，确认外网卡GRO开启
    校验和错误 tcpdump看到bad checksum 硬件卸载与软件路径冲突 ethtool -K eth0 rx off tx off 关闭HW offload
    LRO导致防火墙失效 iptables统计不匹配 LRO合并包跳过Netfilter钩子 关闭LRO，改用GRO
    TSO开启但性能无提升 sendmsg未返回大包 协议层未正确构造GSO skb 检查sock结构gso_size设置

    调试方法¶

    查看各卸载状态¶

    # 查看网卡各项卸载特性的当前状态
ethtool -k eth0 | grep -E "(gro|gso|tso|lro)"

# 典型输出：
# tcp-segmentation-offload: on    ← TSO
# generic-segmentation-offload: on ← GSO
# generic-receive-offload: on      ← GRO
# large-receive-offload: off [fixed] ← LRO（应关闭）

    查看TC qdisc统计¶

    # 查看qdisc的详细统计，判断限速是否实际生效
tc -s qdisc show dev eth0

# 关注以下字段：
# - Sent bytes/packets: 实际发出的流量
# - dropped: 被丢弃的包数（若为0可能限速未生效）
# - backlog: 队列积压情况

    抓包对比法¶

    这是最有力的调试手段——对比tcpdump看到的大小和实际线路上的大小：

    # 在主机上抓包（看到GSO大包）
tcpdump -i eth0 -w host.pcap

# 在对端或交换机上抓包（看到真实小包）
tcpdump -i eth0 -w wire.pcap

# 用wireshark对比：同一个流的包大小差异
# 如果差异巨大 → GSO正在工作
# 如果一样大  → GSO未生效，需排查

    抓包对比法的思路很简单：tcpdump在内核协议栈层面抓包，看到的是GSO大包；而线路上的真实流量是分段后的小包。两者不一致，恰好证明GSO在工作。如果一致，说明GSO没有生效。

    知识点260：TC qdisc流量控制基础 [I]¶

    什么是 qdisc¶

    qdisc（queueing discipline，排队规则）是 Linux 内核对所有出站流量进行调度和整形的统一框架。每个网络接口在发送方向上都绑定有一个 qdisc，所有从协议栈发往网卡的 sk_buff 都必须先经过该 qdisc 的处理——排队、调度、丢弃或放行。

    理解 qdisc 的关键在于：它只作用于 egress（出向） 流量，入向流量不受 qdisc 控制（入向限速需要借助 ingress policing 或其他机制）。qdisc 的决策直接影响包的延迟、吞吐和丢包率，是网络性能调优中不可绕过的一环。

    常见 qdisc 一览¶

    qdisc 算法 适用场景 复杂度 推荐
    pfifo_fast 3 个 band 的优先级 FIFO 默认、无特殊需求 低 否（已过时）
    htb Hierarchical Token Bucket 分层令牌桶 精确带宽限速、多租户隔离 高 是（限速场景）
    fq_codel Fair Queue + CoDel AQM 通用、低延迟、防 bufferbloat 中 是（默认推荐）
    mq Multi-Queue 多队列 多队列网卡、减少锁竞争 低 是（多队列网卡）
    • pfifo_fast：内核的默认 qdisc，实现最简单。内部维护 3 个优先级 band（0~2），band 0 最高。它不具备真正的流量整形能力，只是按优先级出队，无法做带宽限制。
    • htb：最灵活的整形器，通过令牌桶算法实现精确速率控制，支持分层分类（如按 IP、端口、mark 划分子类），是云平台带宽隔离的首选。
    • fq_codel：结合了公平队列（Fair Queue，按流隔离）和 CoDel（主动队列管理，对抗 bufferbloat）。它能自动识别不同流并公平分配带宽，同时控制队列延迟。当前内核社区和多数发行版推荐用它替代 pfifo_fast 作为默认 qdisc。
    • mq：多队列 qdisc，与网卡的多队列（RSS/多 TXQ）配合，为每个硬件发送队列创建独立的 qdisc 实例，大幅降低锁竞争。

    tc 命令速查¶

    命令 功能 示例
    tc qdisc show dev <dev> 查看接口当前 qdisc tc qdisc show dev eth0
    tc qdisc add dev <dev> root <qdisc> 为接口设置根 qdisc tc qdisc add dev eth0 root fq_codel
    tc qdisc del dev <dev> root 删除接口的根 qdisc tc qdisc del dev eth0 root
    tc -s qdisc show dev <dev> 查看 qdisc 详细统计 tc -s qdisc show dev eth0 
    # 查看当前 qdisc（默认通常是 pfifo_fast 或 fq_codel）
$ tc qdisc show dev eth0
qdisc fq_codel 0: root refcnt 2

# 显式设置为 fq_codel（推荐）
$ sudo tc qdisc add dev eth0 root fq_codel

# 查看统计，判断限速/队列是否生效
$ tc -s qdisc show dev eth0
qdisc fq_codel 0: root refcnt 2
 Sent 1234567 bytes 8901 pkt (dropped 12, overlimits 0 requeues 5)

    qdisc 与 GSO 的交互¶

    当 GSO（或 TSO）启用时，协议栈交给 qdisc 的并非最终线路上的真实小包，而是一个64KB 级别的大 sk_buff。这个 GSO 大包在 qdisc 队列中只被视为一个包，令牌桶消耗也按大包体积计算。

    问题在于：一个约 64KB 的 GSO 大包，实际拆分后会产生约 43 个 1500 字节的小包。如果 qdisc 做 HTB 限速，它按 1 个包来调度，而网卡最终发出 43 个包——限速精度差了整整一个数量级。

    ⚠️ 陷阱：GSO + TC 限速同时启用时，实际限速值远大于配置值。一个 GSO 大包 ≈ 64 个小包，但 qdisc 只算 1 个。HTB 看到的带宽消耗与真实线路速率严重不符，在网络拥塞场景下会导致缓冲区溢出和不可预期的丢包。

    解决方案：

    1. 在 qdisc 前添加 gso_split：让 GSO 大包先被拆分，qdisc 看到的是真实小包，计量准确
    2. 降低 GSO 分段阈值：通过 ethtool 减小 gso_max_size，但会削弱 GSO 的性能收益
    3. 采用合适的 burst 参数：对于 HTB，设置与实际分段后包数匹配的 burst 值，作为折中方案

    💡 提示：fq_codel 是当前推荐的通用 qdisc——替代 pfifo_fast。它内置了流级公平调度和主动队列管理，对 bufferbloat 有显著改善，且不需要复杂配置。多数现代发行版（如 Fedora、OpenWrt）已将其设为默认。若你的系统仍在使用 pfifo_fast，建议通过 tc qdisc replace dev eth0 root fq_codel 切换。

    本节总结¶

    主题 关键要点
    LRO vs GRO LRO已废弃，GRO保留头部信息、兼容Netfilter
    TC + GSO陷阱 qdisc作用于GSO大包导致限速失真，启用gso_split修复
    隧道场景 需同时处理内外层封装，检查vxlan_gro_receive等专用实现
    调试三板斧 ethtool -k查状态、tc -s看统计、两端抓包比大小
    通用排查思路 物理网卡→隧道设备→容器接口，逐层确认卸载链完整
