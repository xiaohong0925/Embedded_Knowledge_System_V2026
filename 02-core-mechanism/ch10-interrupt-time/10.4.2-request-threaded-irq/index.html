    10.4.2 request_threaded_irq() 机制¶

    所属章节：第10章 中断与时间 > 10.4 线程化中断

    难度：[E→M] | 预计阅读时间：25分钟

    本节导读¶

    中断处理里经常有这样的矛盾：需要 msleep() 等待硬件就绪，但中断上下文不能睡眠；需要 i2c_transfer() 读传感器，但总线传输内部会调度。request_irq() 把处理函数绑死在中断上下文，这类需求无法直接满足。

    request_threaded_irq() 就是内核给出的方案：中断处理拆成两阶段——极短的 hardirq 做快速确认，可调度的内核线程做耗时处理。

    本节覆盖：

    • 两阶段模型的工作机制、
    • irq_thread 的创建与生命周期、
    • 默认优先级的出处与调整方法，
    • 以及一个可直接套用的驱动模板。

    两阶段模型：hardirq + irq_thread [E→M]¶

    API 与角色分工¶

    request_threaded_irq() 声明在 include/linux/interrupt.h：

    int request_threaded_irq(unsigned int irq,
             irq_handler_t handler,      /* hardirq：快速处理 */
             irq_handler_t thread_fn,    /* thread_fn：线程化慢处理 */
             unsigned long flags,
             const char *name, void *dev_id);

    irq、flags、name、dev_id 与 request_irq() 相同——事实上 request_irq() 就是 thread_fn 传 NULL 的 request_threaded_irq() 宏封装。
    关键区别在 handler 和 thread_fn 这对组合。

    两阶段处理流程¶

            硬件中断触发
             │
             ▼
    ┌─────────────────┐
    │   hardirq()    │  ← 中断上下文
    │  你的handler    │  ← 读状态寄存器、确认中断源
    │                │  ← 必须极快，返回 IRQ_WAKE_THREAD
    └────────┬────────┘
             │ IRQ_WAKE_THREAD
             ▼
    ┌─────────────────┐
    │  irq_thread    │  ← 内核线程，可调度、可睡眠
    │  thread_fn()   │  ← 做真正的工作：I2C/SPI 通信、数据处理
    │                │  ← 返回 IRQ_HANDLED
    └─────────────────┘

    第一阶段：hardirq。运行在中断上下文的快速处理函数。
    任务是：确认中断源、读状态寄存器、必要时屏蔽中断，然后返回 IRQ_WAKE_THREAD——这个返回值通知内核"后续工作交给线程"。
    如果返回 IRQ_HANDLED，内核认为处理完毕，不唤醒线程。

    第二阶段：irq_thread。内核自动创建的内核线程，命名格式 irq/N-name。
    它平时处于睡眠状态，hardirq 返回 IRQ_WAKE_THREAD 时被唤醒，在进程上下文执行 thread_fn。
    这里可以 msleep()、可以 mutex_lock()、可以调用任何可能睡眠的函数。

    ⚠️ thread_fn 应当返回 IRQ_HANDLED。
    v6.6 里如果 thread_fn 返回 IRQ_WAKE_THREAD，irq_thread() 会把它当作"唤醒次级 action"的信号调用 irq_wake_secondary()（manage.c:1322）
    ——这是给共享次级线程用的机制，普通驱动触发它只会让行为偏离预期。

    handler 为 NULL 的简化模式¶

    如果硬件只需要最简单的确认（比如中断源在 hardirq 阶段已由芯片层屏蔽），可以不写 handler，传 handler = NULL。内核自动替换为默认 primary handler（manage.c:1031）：

    /*
 * Default primary interrupt handler for threaded interrupts. Is
 * assigned as primary handler when request_threaded_irq is called
 * with handler == NULL. Useful for oneshot interrupts.
 */
static irqreturn_t irq_default_primary_handler(int irq, void *dev_id)
{
    return IRQ_WAKE_THREAD;
}

    它只做一件事：返回 IRQ_WAKE_THREAD，把处理整个转交给线程。
    这是最常见的用法。完整的驱动示例：

    /* 典型的 request_threaded_irq 使用方式 */
static irqreturn_t my_irq_handler(int irq, void *dev_id)
{
    struct my_device *dev = dev_id;
    u32 status;

    /* 快速读取中断状态寄存器 */
    status = readl(dev->base + REG_IRQ_STATUS);
    if (!(status & MY_IRQ_MASK))
        return IRQ_NONE;          /* 不是本设备的中断 */

    /* 清中断标志，否则硬件会持续触发 */
    writel(status, dev->base + REG_IRQ_STATUS);

    return IRQ_WAKE_THREAD;       /* 唤醒 irq_thread 继续处理 */
}

/* 线程函数——可以睡眠，可以做耗时工作 */
static irqreturn_t my_irq_thread_fn(int irq, void *dev_id)
{
    struct my_device *dev = dev_id;
    u8 buf[64];
    int ret;

    /* 进程上下文：I2C 读传感器合法 */
    ret = i2c_smbus_read_i2c_block_data(dev->client, 0x00,
                        sizeof(buf), buf);
    if (ret < 0) {
        dev_err(&dev->client->dev, "I2C read failed: %d\n", ret);
        return IRQ_HANDLED;
    }

    process_sensor_data(dev, buf, ret);

    /* 数据就绪，唤醒等待的用户态进程 */
    wake_up_interruptible(&dev->wait_queue);

    return IRQ_HANDLED;
}

static int my_probe(struct platform_device *pdev)
{
    struct my_device *dev;
    int irq, ret;

    dev = devm_kzalloc(&pdev->dev, sizeof(*dev), GFP_KERNEL);
    irq = platform_get_irq(pdev, 0);
    if (irq < 0)
        return irq;

    ret = devm_request_threaded_irq(&pdev->dev, irq,
                    my_irq_handler,   /* hardirq */
                    my_irq_thread_fn, /* thread_fn */
                    IRQF_TRIGGER_FALLING | IRQF_ONESHOT,
                    "my_sensor", dev);
    if (ret)
        return ret;

    init_waitqueue_head(&dev->wait_queue);
    return 0;
}

    注意 IRQF_ONESHOT：它告诉内核在 irq_thread 执行完之前，保持这条中断线屏蔽。
    没有它，hardirq 结束后中断立即重新打开，而 irq_thread 可能还没跑完，同一中断源再次触发导致重入。

    线程化中断场景下 IRQF_ONESHOT 基本是标配（这也呼应 10.3.6 的提示：ONESHOT 语义下不需要在处理函数里手动开关中断）。

    irq_thread 的创建与生命周期¶

    两阶段模型里说 irq_thread "平时睡眠、被唤醒执行"——它什么时候被创建？平时在哪等？被什么唤醒？最后怎么退出？
    这一小节按 v6.6 源码逐个回答。

    何时创建：注册路径上内核自动完成¶

    驱动只调一次 request_threaded_irq()（示例里的 devm 版本只是多了自动释放），线程创建是内核在注册路径上自动做的：

    request_threaded_irq()
    └── __setup_irq()                     kernel/irq/manage.c，注册核心函数
            ├── setup_irq_thread()        manage.c:1456（前提：thread_fn 非空且线程未建）
            │       └── kthread_create(irq_thread, action, "irq/%d-%s", ...)
            │               创建 task_struct，入口函数设为 irq_thread——但还没跑起来
            ├── irq_request_resources()   申请中断控制器侧资源
            └── irq_startup()             写寄存器，真正使能中断线

    线程名格式 irq/<中断号>-<注册名>，ps 里看到的 irq/45-my_sensor 就是它。

    两个容易误解的点：

    1. kthread_create 只是"创建"，不是"启动"。它创建 task_struct、设置好入口函数 irq_thread，但线程还没被调度执行。
    2. 线程创建后不需要手动 wake_up_process。kthread_create 内部会把新线程加入调度器就绪队列，调度器择机选中它，自动进入 irq_thread()。

    首次运行：irq_thread() 主循环¶

    irq_thread() 是内核写好的通用包装器（manage.c:1294，节选精简：省略退出清理与强制线程化分支）——驱动注册的 thread_fn 只是它循环里的一个调用点：

    /* kernel/irq/manage.c:1294（节选精简） */
static int irq_thread(void *data)
{
    struct irqaction *action = data;
    struct irq_desc *desc = irq_to_desc(action->irq);

    irq_thread_set_ready(desc, action);   /* 标记线程就绪，free_irq 靠它识别 */

    sched_set_fifo(current);              /* 先提优先级再进循环，只此一次
                                           *（为什么是 FIFO/50，下一节展开） */

    for (;;) {
        /* 无事可做时睡在 irq_wait_for_interrupt；返回非 0 表示要退出 */
        if (irq_wait_for_interrupt(action))
            break;

        irq_thread_fn(desc, action);      /* 包装：调 thread_fn + ONESHOT 收尾 */
    }

    return 0;
}

    其中 irq_thread_fn()（manage.c:1207）是真正的包装：先调你注册的 thread_fn()，再调 irq_finalize_oneshot() 恢复中断线。

    平时在哪等：双事件睡眠循环¶

    等待方式不是 completion，而是一个经典的可中断睡眠循环（irq_wait_for_interrupt()，manage.c:1052）：

    static int irq_wait_for_interrupt(struct irqaction *action)
{
    for (;;) {
        /* 设为可中断睡眠，让出 CPU；后续被唤醒时从这里继续 */
        set_current_state(TASK_INTERRUPTIBLE);

        /* 收到 kthread_stop() 信号，线程被要求退出 */
        if (kthread_should_stop()) {
            /* ... 退出处理 ... */
            return -1;
        }

        /* 顶半部（硬中断）设置了 IRQTF_RUNTHREAD，表示有活要干。
         * 原子地测试并清掉该标志，防止重复执行 */
        if (test_and_clear_bit(IRQTF_RUNTHREAD,
                       &action->thread_flags)) {
            __set_current_state(TASK_RUNNING);
            return 0;      /* 有活干了，返回去执行 thread_fn */
        }

        /* 无事可做，真正让出 CPU，进入睡眠等待被唤醒 */
        schedule();
    }
}

    关键设计：双事件等待。

    • IRQTF_RUNTHREAD：顶半部（hardirq）设置的"来活"标志
    • kthread_should_stop()：free_irq() 发起的"退出"信号

    用 completion 或 wait_event 只能等单一事件，而这里需要同时响应工作和退出。自旋睡眠循环是内核线程的标准做法。

    test_and_clear_bit 是原子的：如果多个中断密集触发，标志位只被消费一次，不会累积出多次重复执行。

    被什么唤醒：__irq_wake_thread()¶

    hardirq 返回 IRQ_WAKE_THREAD 后，中断核心层调用 __irq_wake_thread()（kernel/irq/handle.c:61）：

    /* kernel/irq/handle.c:61（节选，省略 ONESHOT 序列化的大段注释） */
void __irq_wake_thread(struct irq_desc *desc, struct irqaction *action)
{
    /* 线程正在退出（崩溃被 kill）时假装已处理，直接返回 */
    if (action->thread->flags & PF_EXITING)
        return;

    /* 置位"有活要干"；已置位说明上一轮还没跑完，直接返回不重复唤醒 */
    if (test_and_set_bit(IRQTF_RUNTHREAD, &action->thread_flags))
        return;

    desc->threads_oneshot |= action->thread_mask; /* ONESHOT 记账：此线程在跑 */
    atomic_inc(&desc->threads_active);  /* 活动线程计数，synchronize_irq 靠它等 */
    wake_up_process(action->thread);    /* 把线程从 schedule() 里拉起来 */
}

    怎么退出：free_irq 路径¶

    模块卸载或驱动解绑时走 free_irq() → __free_irq()，线程在这里被终止（manage.c，__free_irq() 尾部）：

    /* kernel/irq/manage.c，__free_irq()（v6.6 真实代码） */
if (action->thread) {
    kthread_stop(action->thread);     /* 发退出信号，并阻塞等待线程真正退出 */
    put_task_struct(action->thread);  /* 释放 task_struct 引用 */
}

    kthread_stop() 置退出标志并唤醒线程，然后阻塞等它退出返回——线程在 irq_wait_for_interrupt() 里检测到 kthread_should_stop()，返回 -1，主循环结束，irq_thread() 返回，线程终止。
    所以 free_irq() 返回时 irq_thread 一定已经不在运行，驱动可以安全释放 thread_fn 用到的资源——这和 10.3.4 的 destroy_workqueue() 语义相同。

    串起来，irq_thread 的一生：注册时创建 → 首次运行先提优先级 → 睡眠等待 → 被 IRQ_WAKE_THREAD 唤醒 → 执行 thread_fn → 恢复中断线 → 继续睡眠，直到 free_irq。

    💡 如果 hardirq 返回 IRQ_HANDLED 而不是 IRQ_WAKE_THREAD，线程不会被唤醒。
    可以利用这一点做快速过滤：共享中断场景下，hardirq 先查状态寄存器，不是本设备的中断就直接返回 IRQ_NONE，避免无谓的线程调度。

    irq_thread 的优先级与调度策略 [E]¶

    上一小节停在"线程被唤醒"——但唤醒只意味着它进了就绪队列，什么时候真正跑上 CPU，是调度器说了算。
    中断处理的延迟从此多了一层调度延迟：如果 irq_thread 是普通 CFS 线程，它要和所有用户进程按权重排队，延迟变得不可预期，线程化"把处理挪到进程上下文"的意义就丢了一半。
    所以内核必须回答一个问题：给这个线程什么调度策略和优先级？

    默认值：SCHED_FIFO，优先级 50¶

    内核的回答写在 irq_thread() 的开头——线程一启动就调用 sched_set_fifo(current) 把自己设为实时调度（manage.c:1304）。
    这个函数的定义在 kernel/sched/core.c:7935：

    void sched_set_fifo(struct task_struct *p)
{
    /* 默认 RT 优先级：MAX_RT_PRIO / 2，即中间档。
     * 在 RT 内核里，线程化中断 handler 常用这个函数把线程提到 FIFO 类，
     * 避免被普通 CFS 任务抢占，降低中断处理延迟。 */
    struct sched_param sp = { .sched_priority = MAX_RT_PRIO / 2 };

    /* nocheck 版本：绕过权限检查（内核内部调用时自己保证安全）。
     * WARN_ON_ONCE：如果设置失败（比如参数非法）只报一次警告，不刷屏。 */
    WARN_ON_ONCE(sched_setscheduler_nocheck(p, SCHED_FIFO, &sp) != 0);
}

    SCHED_FIFO：实时调度策略之一——实时优先级 1~99（数值越大越优先），全部高于普通 CFS 进程；同优先级下先入先出，不主动让出 CPU 就一直跑。
    MAX_RT_PRIO/2 = 50，即实时优先级的正中间。

    属性 默认值 出处
    调度策略 SCHED_FIFO sched_set_fifo()，manage.c:1304
    优先级 50（MAX_RT_PRIO/2） core.c:7935
    亲和性 继承中断 affinity irq_thread_check_affinity()

    SCHED_FIFO/50 是一个折中：保证中断线程比普通进程（CFS）更快得到 CPU，又不会抢占优先级更高的关键实时任务（如视频采集的 80）。

    如何调整优先级¶

    驱动里拿到线程的 task_struct 指针后（比如注册成功后通过私有结构保存），用 sched_setscheduler() 调整；用户态用 chrt：

    # 找到 irq_thread 的 PID
ps -eo pid,comm | grep irq/

# 把 irq/45-my_dev (PID 123) 提升到 SCHED_FIFO/90
sudo chrt -f -p 90 123

# 确认
chrt -p 123

    ⚠️ 不要盲目把 irq_thread 优先级拉到 99。优先级越高，越容易撞上优先级反转：
    thread_fn 里若需要获取一个低优先级线程持有的锁，高优先级线程会被低优先级线程拖住；而 irq_thread 卡住期间，这条 IRQ 线上的后续中断都无法处理。

    优先级反转问题¶

    irq_thread 运行在 SCHED_FIFO 下，一旦被低优先级任务持有的锁挡住，就形成优先级反转。
    内核层面的解法是带优先级继承（PI）的锁——rt_mutex 和 PI-futex，它们会把持锁线程的优先级临时提升到等待者的水平。

    对驱动开发者来说，更务实的原则是：thread_fn 里避免获取可能被长时间持有的锁。
    需要与用户态或其他线程交换数据时，优先用 waitqueue、kfifo 这类无锁或短临界区机制，把复杂同步挪出中断线程。

    锁与优先级继承的完整讨论见第 13 章。

    request_irq vs request_threaded_irq：核心对比¶

    对比维度 request_irq() request_threaded_irq()
    处理上下文 纯中断上下文 hardirq（中断）+ thread_fn（进程）
    能否睡眠 不能 thread_fn 中可以
    本质 request_threaded_irq(irq, handler, NULL, ...) 的宏封装 完整两阶段 API
    线程创建 不创建 自动创建 irq/N-name 内核线程
    hardirq 典型返回 IRQ_HANDLED / IRQ_NONE IRQ_WAKE_THREAD
    ONESHOT 需求 不涉及 线程化场景基本标配
    适用场景 处理极快（10.2.3 的 100μs 经验阈值内） 需要睡眠、I/O、复杂处理
    额外开销 无 一次线程唤醒 + 上下文切换
    资源占用 无额外线程 每个线程化中断一个内核线程

    判断标准只有一个问题：handler 里有没有可能睡眠的操作？ 有，就用 request_threaded_irq()。

    本节总结¶

    线程化中断用一句话概括：hardirq 只做"确认+清源"，其余全部交给一个专属内核线程——从此 handler 里可以睡眠，代价是一次线程唤醒的调度延迟。
    真正要记住的是三件事：

    1. hardirq 返回 IRQ_WAKE_THREAD 才会唤醒线程；
    2. IRQF_ONESHOT 是线程化场景的标配；
    3. 线程默认 SCHED_FIFO/50，够用，别盲目调高。
