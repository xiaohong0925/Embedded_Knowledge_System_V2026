    8.1.3 内核线程：kthread机制¶

    所属章节：第8章 进程与调度 > 8.1 task_struct 与任务描述

    难度：[I→E] | 预计阅读时间：35分钟

    本节导读¶

    在 /proc 下看到 kworker/u16:1、ksoftirqd/3、kthreadd 这些进程名时，它们不是普通用户进程，而是内核自己创建的"线程"。本节讲清 kthread 机制的完整生命周期。
    本节覆盖：为什么内核需要线程（中断上下文 vs 进程上下文）、kthread_create() 的工厂模式与 v6.6 真实调用链、停放（park）与停止（stop）语义、内核线程与用户线程的本质区别、驱动中创建内核线程的标准范式。

    为什么需要内核线程 [I]¶

    问题场景¶

    编写网络驱动时需要周期性地轮询网卡收包队列。方案 A：在定时器中断里完成轮询。方案 B：创建一个内核线程，在进程上下文中轮询。哪个正确？

    答案是 B。内核中大量工作必须在进程上下文中执行，这是理解 kthread 存在必要性的根本出发点。

    机制深入¶

    Linux 内核的执行上下文分为两类，二者有本质差异：

    属性 中断上下文（Interrupt Context） 进程上下文（Process Context）
    调度能力 ❌ 不可调度（不可阻塞） ✅ 可以睡眠/阻塞
    栈空间 固定大小中断栈（通常8KB-16KB） 完整的内核栈（通常8KB-16KB per task）
    current 宏 指向被中断的随机进程 指向当前 task_struct
    可用 API 不可调用 kmalloc(GFP_KERNEL)、不可访问用户空间 完整内核 API
    执行时间 要求尽可能短（硬中断：μs级） 可长期运行（ms 甚至 s 级）
    代表场景 ISR（中断服务例程）、软中断（softirq） 内核线程、系统调用处理

    许多内核子系统的需求天然与中断上下文的限制冲突：

    • 软中断负载过重时：ksoftirqd 被唤醒，将软中断处理从硬中断上下文迁移到进程上下文
    • 异步工作需要睡眠：文件系统回写（flush 线程）、内存回收（kswapd）都需要在 I/O 等待时睡眠
    • 需要独立调度的实体：kworker 工作队列中的 work 可能长时间运行，必须能参与 CFS 调度

    关键代码路径¶

    ksoftirqd 的经典示例——当 __do_softirq() 的处理预算耗尽（软中断反复触发、处理不完）时，唤醒本 CPU 的 ksoftirqd 兜底（kernel/softirq.c:74）：

    /* kernel/softirq.c:74 wakeup_softirqd()（v6.6 原文） */
static void wakeup_softirqd(void)
{
    /* Interrupts are disabled: no need to stop preemption */
    struct task_struct *tsk = __this_cpu_read(ksoftirqd);

    if (tsk)
        wake_up_process(tsk);
}

    旧版代码里还有 tsk->state != TASK_RUNNING 的状态检查，v6.6 已移除——wake_up_process() 内部对运行中任务的重复唤醒是安全的，外层不必再过滤。

    ⚠️ 试图在中断上下文中调用 schedule() 或可能睡眠的函数（如 mutex_lock()、kmalloc(GFP_KERNEL)），将触发 "scheduling while atomic" 内核崩溃。kthread 的存在正是为了"把活交给线程去做"。

    💡 驱动中判断当前上下文的标准范式：

    if (in_interrupt()) {
    /* 中断上下文：快速处理，或交给 kthread/workqueue */
    queue_work(my_wq, &my_work);
} else {
    /* 进程上下文：可以直接做重活 */
    do_heavy_work();
}

    kthread_create() 背后：kthreadd 工厂 [E]¶

    问题场景¶

    内核模块需要在后台持续监控某个硬件状态，调用 kthread_create(monitor_fn, data, "hwmon")——这个调用之后内核究竟发生了什么？新线程为什么不是调用者直接创建，而是由 PID=2 的 kthreadd 代劳？

    机制深入¶

    kthreadd：内核线程的"工厂"¶

    内核启动阶段，rest_init() 会创建两个特殊进程：

    进程名 PID 创建函数 职责
    swapper/0（idle） 0 静态定义 启动链、CPU空闲时执行
    init 1 kernel_thread(kernel_init, ...) 用户空间祖宗，启动 systemd/init
    kthreadd 2 kernel_thread(kthreadd, ...) 所有内核线程的父进程

    kthreadd 的核心逻辑是一个无限循环，从 kthread_create_list 链表中取出创建请求（kernel/kthread.c，精简；注意链表操作由 kthread_create_lock 保护，这是文档摘录常被省略的细节）：

    /* kernel/kthread.c kthreadd()（v6.6，精简） */
int kthreadd(void *unused)
{
    struct task_struct *tsk = current;

    set_task_comm(tsk, "kthreadd");
    ignore_signals(tsk);            /* 内核线程不接收信号 */
    /* ... cpumask/mems 设置、PF_NOFREEZE 等 ... */

    for (;;) {
        set_current_state(TASK_INTERRUPTIBLE);
        if (list_empty(&kthread_create_list))
            schedule();           /* 无事可做，睡眠等待 */
        __set_current_state(TASK_RUNNING);

        spin_lock(&kthread_create_lock);
        while (!list_empty(&kthread_create_list)) {
            struct kthread_create_info *create;

            create = list_entry(kthread_create_list.next,
                        struct kthread_create_info, list);
            list_del_init(&create->list);
            spin_unlock(&kthread_create_lock);

            create_kthread(create);   /* 真正创建线程 */

            spin_lock(&kthread_create_lock);
        }
        spin_unlock(&kthread_create_lock);
    }
}

    create_kthread() 底层调用 kernel_thread()（kernel/fork.c:2958），后者打包 CLONE_VM | CLONE_UNTRACED 标志后走 v6.6 的统一创建入口 kernel_clone()（fork.c:2868）——旧读物中的 do_fork() 已不存在。

    kthread_create() 的完整调用链¶

    sequenceDiagram
    participant Caller as 调用者<br/>(驱动/子系统)
    participant API as kthread_create()
    participant List as kthread_create_list<br/>(全局链表)
    participant T as kthreadd<br/>(PID=2)
    participant CL as kernel_clone()
    participant Task as 新 kthread

    Caller->>API: kthread_create(fn, data, "name")
    API->>API: 分配并填充 kthread_create_info（含栈上 completion）
    API->>List: spin_lock + list_add_tail
    API->>T: wake_up_process(kthreadd_task)
    API->>API: wait_for_completion_killable()<br/>等待创建完成（可被致命信号打断）

    Note over T: kthreadd 被唤醒后
    T->>List: 取出 kthread_create_info
    T->>CL: create_kthread() → kernel_clone()
    CL->>Task: 分配 task_struct，共享内核地址空间
    Task->>Task: kthread() 入口：__set_current_state(TASK_UNINTERRUPTIBLE)
    Task->>API: create->result = current; complete(done)
    API-->>Caller: 返回 task_struct*（线程已存在，停在 UNINTERRUPTIBLE）

    Note over Caller,Task: 调用者随后调用 wake_up_process()<br/>线程才真正执行 threadfn(data)

    关键数据结构 kthread_create_info（kernel/kthread.c:38）：

    struct kthread_create_info
{
    /* Information passed to kthread() from kthreadd. */
    char *full_name;
    int (*threadfn)(void *data);
    void *data;
    int node;

    /* Result passed back to kthread_create() from kthreadd. */
    struct task_struct *result;
    struct completion *done;      /* 指向调用者栈上的 completion */

    struct list_head list;
};

    Trade-off：三种内核线程创建方式对比¶

    创建方式 API 适用场景 复杂度 睡眠能力 绑定 CPU
    内核线程（kthread） kthread_create() + wake_up_process() 长期运行的后台任务 中 ✅ 完整 kthread_bind()
    工作队列（workqueue） alloc_workqueue() + queue_work() 一次性/间歇性异步任务 低 ✅ 由 wq 类型决定 WQ_UNBOUND / WQ_CPU_INTENSIVE
    软中断/tasklet open_softirq() / tasklet_schedule() 极短、高频、不可睡眠 低 ❌ 不可 运行 CPU 即处理 CPU

    💡 选型建议：能用一个 work_struct 搞定，就不要创建专用 kthread——工作队列本质上是内核替你管理的 kthread 池（kworker）。只有当需要长期驻留、精细控制生命周期、特殊调度策略时，才直接创建 kthread。软中断/tasklet/workqueue 的完整选型对比见第 10 章底半部一节（10.3）。

    完整代码示例：驱动中创建内核线程¶

    /* my_driver.c — 内核线程创建与销毁的标准范式 */

struct task_struct *my_thread;
static atomic_t should_stop = ATOMIC_INIT(0);

static int my_kthread_fn(void *data)
{
    struct my_device *dev = data;

    set_freezable();            /* 支持系统休眠（suspend-to-ram） */

    while (!kthread_should_stop()) {
        if (kthread_freezable_should_stop(NULL))
            break;

        /* 核心业务逻辑 */
        do_periodic_work(dev);

        /* 睡眠等待，让出 CPU；可被 kthread_stop() 唤醒 */
        msleep_interruptible(1000);
    }

    pr_info("my_kthread: exiting\n");
    return 0;
}

static int __init my_driver_init(void)
{
    /* 第1步：创建（此时线程处于 stopped 状态） */
    my_thread = kthread_create(my_kthread_fn, my_dev,
                               "mydriver-%d", my_dev->id);
    if (IS_ERR(my_thread)) {
        pr_err("Failed to create kthread\n");
        return PTR_ERR(my_thread);
    }

    /* 第2步：绑定到特定 CPU（可选，NUMA/Affinity 场景） */
    kthread_bind(my_thread, 0);   /* 绑到 CPU0，按部署调整 */

    /* 第3步：唤醒，真正开始执行 */
    wake_up_process(my_thread);

    return 0;
}

static void __exit my_driver_exit(void)
{
    /* 优雅地停止线程：kthread_stop() 内部置 KTHREAD_SHOULD_STOP 标志、
     * kthread_unpark() 解除停放、wake_up_process() 唤醒（并用
     * TIF_NOTIFY_SIGNAL 确保可打断 interruptible 睡眠），
     * 最后 wait_for_completion() 等待线程完全退出后才返回 */
    kthread_stop(my_thread);
}

    停放机制：kthread_park() 与 TASK_PARKED¶

    8.1.2 的状态速查表里有一个 TASK_PARKED（ps 显示 P），它就来自 kthread 的停放机制。kthread_park() 置位 KTHREAD_SHOULD_PARK 并唤醒线程，线程在主循环里通过 kthread_parkme() 主动进入 TASK_PARKED 睡眠；kthread_unpark() 清除标志并再次唤醒。典型场景是 CPU 热插拔：smpboot 框架在 CPU 下线前把绑在该 CPU 上的 per-cpu 线程（ksoftirqd、kworker 等）停放，CPU 上线后再解除停放——线程不创建不销毁，只冻结在原地。v6.6 的 kthread() 入口在首次被唤醒后也会先过一道 __kthread_parkme()（kthread.c:386），保证"创建时就被 park"的边界情况不会漏执行 threadfn 之外的逻辑。

    🔴 忘记调用 kthread_stop() 就 rmmod 卸载模块，将导致线程仍在运行但代码页已被释放——这是高危的 use-after-free 场景。务必在 module_exit 中等待线程完全退出。

    ⚠️ kthread_create() 返回时新线程的初始状态是 TASK_UNINTERRUPTIBLE（自停放在 kthread() 入口），必须显式调用 wake_up_process() 才会开始执行 threadfn——这是最常见的新手错误。

    ⚠️ kthread_fn 里若长期卡在不可中断睡眠（如极端竞争下的 mutex_lock()），kthread_stop() 会一直等不到线程退出，模块卸载随之挂住。循环里保持 kthread_should_stop() 检查点、持锁路径尽量短。

    💡 kthread_run(fn, data, namefmt, ...) 宏（include/linux/kthread.h:51）是 kthread_create() + wake_up_process() 的组合，不需要绑核时一步到位：

    /* include/linux/kthread.h:51（v6.6 原文） */
#define kthread_run(threadfn, data, namefmt, ...)              \
({                                     \
    struct task_struct *__k                        \
        = kthread_create(threadfn, data, namefmt, ## __VA_ARGS__); \
    if (!IS_ERR(__k))                          \
        wake_up_process(__k);                      \
    __k;                                   \
})

    内核线程与用户线程的本质区别 [I]¶

    问题场景¶

    调试时发现：ps aux 里 kworker/0:1H 的 VSZ（虚拟内存大小）是 0。这正常吗？另一个问题：能在内核线程里调用 open() 或 read() 吗？

    核心差异¶

    属性 内核线程（Kernel Thread） 用户线程（User Thread）
    mm（内存描述符） tsk->mm = NULL，使用 active_mm 指向借用地址空间 指向独立的 mm_struct，包含完整用户页表
    虚拟地址空间 仅内核空间（0xFFFF... 以上，64位） 内核 + 用户空间完整 4/128TB
    用户空间访问 ❌ 不能直接访问用户空间 ✅ 可以
    入口地址 内核函数指针（如 my_kthread_fn） ELF 入口（如 _start → main()）
    创建路径 kernel_thread() → kernel_clone()（CLONE_VM | CLONE_UNTRACED），copy_mm() 直接返回 NULL mm clone()/fork() → kernel_clone() → copy_process()，完整复制或共享 mm
    系统调用 理论上在内核态，不通过 syscall 门 通过 int 0x80 / syscall / svc 陷入内核
    优先级范围 0~139（可进入 RT 调度类） 通常 100~139（用户可见 nice -20~19）
    /proc/<pid>/ 可见性 ✅ 可见，exe 指向空 ✅ 可见，exe 指向实际二进制

    关键代码路径¶

    内核线程 mm 为 NULL 的底层原因——copy_mm() 的提前返回（kernel/fork.c:1707，v6.6）：

    /* kernel/fork.c copy_mm()（v6.6，精简） */
static int copy_mm(unsigned long clone_flags, struct task_struct *tsk)
{
    struct mm_struct *mm, *oldmm;

    tsk->mm = NULL;
    tsk->active_mm = NULL;          /* 先默认置 NULL */

    /* Are we cloning a kernel thread? */
    oldmm = current->mm;
    if (!oldmm)
        return 0;               /* 父进程（kthreadd）无 mm：直接返回，
                       新内核线程的 mm/active_mm 保持 NULL */

    if (clone_flags & CLONE_VM) {
        mmget(oldmm);
        mm = oldmm;             /* 用户线程：共享父进程地址空间 */
    } else {
        mm = dup_mm(tsk, current->mm);   /* 独立进程：完整复制 */
        if (!mm)
            return -ENOMEM;
    }

    tsk->mm = mm;
    tsk->active_mm = mm;
    return 0;
}

    机制要点：内核线程的 mm == NULL 不是"走了 CLONE_VM 分支"，而是 copy_mm() 先把两个字段置 NULL、发现创建者（kthreadd）自己没有 mm 便直接返回。active_mm 的"借用"发生在运行时切换阶段（context_switch() 里内核线程借用前一个任务的 mm），与创建无关。

    🔴 内核线程 tsk->mm = NULL 意味着 access_ok() 检查会失败，任何试图在内核线程中直接访问用户空间指针的操作（如 copy_from_user()）都会导致 oops。确实需要在内核线程中操作用户空间数据时，必须先用 use_mm() 临时绑定一个地址空间（KVM、io_uring 等子系统即采用此法），用完 unuse_mm()。

    实践案例：嵌入式系统中的 watchdog kthread¶

    场景：某工业控制器要求在主 CPU 上运行一个 10ms 周期的 watchdog 喂狗任务，不能依赖用户空间进程（因为用户进程可能因 OOM 被杀）。

    方案：在平台驱动中创建一个 SCHED_FIFO 优先级的实时内核线程：

    static int __init watchdog_init(void)
{
    wdt_thread = kthread_create(watchdog_kthread_fn, NULL, "hw_wdt");
    if (IS_ERR(wdt_thread))
        return PTR_ERR(wdt_thread);

    /* 绑定到 CPU0，避免在 CPU 热插拔时漂移 */
    kthread_bind(wdt_thread, 0);

    /* 提升为实时调度，确保 10ms 周期不被普通任务抢占。
     * v6.6 推荐用 sched_set_fifo()（core.c:7935）——它把线程设为
     * SCHED_FIFO、优先级 MAX_RT_PRIO/2；旧的 sched_setscheduler()
     * 仍存在但源码注释已明确标注 "Use sched_set_fifo()"（core.c:7875） */
    sched_set_fifo(wdt_thread);

    wake_up_process(wdt_thread);
    return 0;
}

static int watchdog_kthread_fn(void *unused)
{
    while (!kthread_should_stop()) {
        pet_watchdog();                 /* 写硬件寄存器喂狗 */
        usleep_range(10000, 11000);     /* 10ms ± 1ms */
    }
    return 0;
}

    为什么不用用户空间进程？ 用户空间的实时进程（SCHED_FIFO + chrt）仍然是 OOM killer 的候选——内存耗尽时可能被杀，喂狗一停就是整机复位。内核线程没有 mm，根本不在 OOM killer 的候选名单里；且能直接访问 I/O 寄存器（iowrite32()），无需 mmap//dev/mem 等额外开销。

    💡 在 SMP 系统中，用 kthread_create_on_cpu() / kthread_bind() 将内核线程绑定到特定 CPU，配合 sched_set_fifo() 设置 RT 优先级，是构建确定性时延内核任务的常用组合。

    本节总结¶

    要点 一句话总结
    为什么需要 kthread 中断上下文不能睡眠，kthread 提供可阻塞的进程上下文
    kthread 如何创建 kthread_create() → 唤醒 kthreadd（PID=2）→ kernel_clone() 的工厂模式；调用者等 completion 到线程创建完成才返回
    停放与停止 kthread_park()/kthread_unpark() 对应 TASK_PARKED（CPU 热插拔场景）；kthread_stop() 置标志+唤醒+等退出
    kthread vs 用户线程 mm = NULL（copy_mm 提前返回）、仅内核态、无用户空间，但仍是完整调度实体
    选型原则 能用 workqueue 就不用 kthread；需要长期驻留/精确控制时才用 kthread
    生命周期安全 必须有 kthread_stop() 配对，模块卸载时等待线程退出
