            • 本节导读
            • main_loop 之前，串口和 MMC 怎么就绪了 [I]
            • 三要素：uclass、driver、udevice [I→E]
              • uclass：一类设备的公共接口
              • driver：具体 IP 的控制逻辑
              • udevice：一个实际存在的硬件实例
            • 与内核设备模型：长得像，骨子里不同 [I]
            • bind 与 probe：从 compatible 到可用设备的五步链路 [E]
              • 匹配：compatible 字符串是唯一桥梁
              • bind：建实例、挂 uclass、不碰硬件
              • probe：设备树参数在此兑现
            • probe 失败排查：log、dm tree、compatible 三板斧 [E]
              • 第一步：让 DM 自己说话
              • 第二步：逐字符比对 compatible
              • 第三步：验证并建立诊断习惯

    7.3.2 DM框架：U-Boot的设备模型¶

    所属章节：第7章 启动链深度解析 > 7.3 U-Boot

    难度：[I→E] | 预计阅读时间：40分钟

    本节导读¶

    7.3.1 的终点是 board_init_r 接手一个完整的 C 世界。接下来串口要能打印、MMC 要能读内核镜像、网口要能用 tftpboot——这些驱动必须在 main_loop 出现倒计时之前就绪。问题是：U-Boot 没有内核那样成熟的设备模型基础设施，没有模块加载，甚至没有真正的总线枚举，驱动是怎么被找到、被初始化、排好序跑起来的？答案是 2014.10 版本引入的 Driver Model（DM）框架。本节沿"驱动如何在 main_loop 之前就绪"这条主线，展开 DM 的三要素、bind 与 probe 的时机分野，以及它和内核设备模型长得像、骨子里不同的那几个关键点。
    本节覆盖：DM 之前的驱动组织方式及其痛点、uclass/driver/udevice 三要素、bind 与 probe 的触发时机、compatible 匹配到 probe 的完整链路、DM 与内核设备模型的异同、probe 失败的排查三板斧。

    main_loop 之前，串口和 MMC 怎么就绪了 [I]¶

    先看 DM 出现之前驱动是怎么组织的。一个老项目的 board 文件里，外设初始化是一串写死的函数调用：

    /* 老版本U-Boot（DM之前）的典型代码 */
extern struct mmc *find_mmc_device(int dev_num);
extern int eth_initialize(bd_t *bis);
extern int spi_init(void);

int board_init(void)
{
    /* 手动初始化每个外设，顺序写死 */
    mmc_initialize(gd->bd);
    eth_initialize(gd->bd);
    spi_init();
    /* 新加一个I2C传感器？在这里再插一行 */
    i2c_init(CONFIG_SYS_I2C_SPEED, CONFIG_SYS_I2C_SLAVE);
}

    每加一块板子就复制一套这样的代码，驱动注册函数散落在各处，设备实例是 board 文件里的全局变量。规模一大，问题集中爆发：

    问题维度 DM 之前 DM 之后
    驱动注册 全局链表手动挂接，*_register() 散落各处 U_BOOT_DRIVER() 宏由链接器收集到专用段
    设备发现 board 文件中硬编码设备实例 设备树节点自动实例化为 struct udevice
    资源管理 时钟、GPIO、pinmux 在驱动内直接写寄存器 经 clk_*、gpio_*、pinctrl_* 等 DM API 统一申请
    代码复用 同 IP 不同板卡复制粘贴整份驱动 通用驱动 + 设备树 compatible 绑定
    可测试性 依赖真实硬件 Sandbox 模式可在 x86 主机上跑 DM 驱动

    DM 的答案分两步：启动时扫描设备树，为每个节点创建设备实例（bind）；设备第一次被用到时才真正初始化硬件（probe）。board_init_r 的初始化序列里有一项 dm_init_and_scan()，它完成扫描与 bind；probe 则分散在后续各处——串口在 stdio_init 时被 probe，MMC 在第一次 mmc_init 时被 probe。到 main_loop 时，启动路径必需的设备已全部就绪，用不上的设备一个都没初始化。

    这种"先登记、后启用"的设计是 U-Boot 在资源约束下的取舍：bind 只花内存不碰硬件，probe 才付出时钟使能、寄存器映射的时间成本。启动慢的板子优化启动时间时，第一批候选削减项就是那些在 bootcmd 里根本没被用到的 probe。

    uclass：一类设备的公共接口¶

    不同厂商的 MMC 控制器寄存器千差万别，但"初始化卡、读写块"这类操作对上层应该长一个样。uclass 解决的就是这个问题：为一类设备定义统一的操作集合，上层代码只面对 uclass，不关心底下是哪家驱动。

    /* include/dm/uclass-id.h — 预定义的设备类ID（节选） */
enum uclass_id {
    UCLASS_ROOT = 0,
    UCLASS_MMC,         /* 块存储：eMMC/SD/SDIO */
    UCLASS_ETH,         /* 以太网 */
    UCLASS_SPI,         /* SPI主控 */
    UCLASS_I2C,         /* I2C总线 */
    UCLASS_PINCTRL,     /* 引脚控制器 */
    UCLASS_CLK,         /* 时钟 */
    UCLASS_BLOCK,       /* 块设备抽象 */
    /* ... 共80+个uclass ... */
};
    常见 uclass 职责 典型驱动 关键 API
    UCLASS_MMC SD/MMC/eMMC 协议层 sdhci、rockchip_dw_mmc mmc_init()、mmc_read_blocks()
    UCLASS_ETH 网络 MAC/PHY 抽象 eqos、gmac_rockchip eth_init()、eth_send()
    UCLASS_SPI SPI 主控制器 cadence_spi、rockchip_spi spi_claim_bus()、spi_xfer()
    UCLASS_I2C I2C 总线控制器 i2c_cdns、rk_i2c i2c_read()、i2c_write()
    UCLASS_PINCTRL 引脚复用配置 pinctrl-single、rockchip_pinctrl pinctrl_select_state()
    UCLASS_CLK 时钟树管理 clk_fixed_rate、各 SoC 时钟驱动 clk_enable()、clk_get_rate()
    UCLASS_BLOCK 块设备统一层（文件系统依赖它） 纯 uclass 层 blk_dread()、blk_dwrite()

    driver：具体 IP 的控制逻辑¶

    driver 是某个具体硬件 IP 的实现，通过 .id 声明所属 uclass，通过 .of_match 声明能兼容哪些设备树 compatible 字符串。注册不需要任何函数调用——U_BOOT_DRIVER() 宏把驱动结构体放进 .u_boot_driver_* 链接段，启动时由 DM 框架遍历这个段完成收集：

    /* drivers/mmc/sdhci.c — SDHCI 驱动定义 */
U_BOOT_DRIVER(sdhci) = {
    .name           = "sdhci",
    .id             = UCLASS_MMC,
    .of_match       = sdhci_ids,    /* compatible 匹配表 */
    .ops            = &sdhci_ops,
    .probe          = sdhci_probe,  /* 生命周期函数 */
    .remove         = sdhci_remove,
    .priv_auto      = sizeof(struct sdhci_host),   /* 自动分配priv空间 */
    .plat_auto      = sizeof(struct mmc_platdata), /* 自动分配plat空间 */
};

    .priv_auto 和 .plat_auto 两个字段引出 DM 最有 Bootloader 特色的一条纪律：platdata 与 privdata 强制分离。

    属性 platdata（平台数据） privdata（私有数据）
    来源 设备树属性解析，或静态 platdata 结构 驱动 probe() 中动态分配
    生命周期 与 udevice 同生共死 probe() 分配 → remove() 释放
    内容 寄存器基地址、时钟频率、总线宽度等硬件描述 控制器句柄、DMA 缓冲、运行时状态等软件上下文
    示例（MMC） bus_width、f_max、capability host 控制器指针、当前电压状态

    分离的意义在于启动时序：platdata 在 bind 阶段就要可用（此时连完整 malloc 都可能没就绪），privdata 只在 probe 之后存在。两者混在一个结构体里，bind 阶段就得为运行时才用的状态提前买单。

    udevice：一个实际存在的硬件实例¶

    每个 udevice 对应设备树里的一个节点，是 bind 阶段的产物：

    /* include/dm/device.h — struct udevice 的核心定义 */
struct udevice {
    const struct driver *driver;    /* 指向驱动操作函数表 */
    const char *name;
    void *plat_;                    /* 平台数据：设备树解析的硬件参数 */
    void *priv_;                    /* 私有数据：驱动运行时的状态缓存 */
    struct uclass *uclass;          /* 所属设备类 */
    u32 seq_;                       /* 同类设备中的序号（如 mmc0, mmc1） */
    ofnode node_;                   /* 对应的设备树节点 */
    /* ... 其他成员省略 ... */
};

    💡 驱动代码里访问这两块数据一律用 dev_get_plat() 和 dev_get_priv() 宏，不要直接碰 udevice->plat_。宏会在调试配置下附加空指针检查，probe 之前访问 priv（此时尚未分配）会被当场拦下，而不是带着野指针跑下去。

    与内核设备模型：长得像，骨子里不同 [I]¶

    写过内核驱动的人看 DM 会有强烈的既视感：compatible 匹配、device 实例化、probe 回调，词汇几乎一样。但三处本质差异决定了 DM 的行为模式和内核完全不同：

    维度 内核设备模型 U-Boot DM
    总线层级 struct bus_type 组织 platform/i2c/spi 等总线，支持热插拔与 uevent 通知 无 bus_type，设备树扫描一次性建齐，不考虑热插拔
    驱动来源 模块可运行时加载，module_init 带依赖解析 全部编译进镜像，链接段静态收集，无加载概念
    probe 时机 device 与 driver 匹配成功即 probe（注册时触发） bind 时只建实例，首次被使用时才 probe（惰性）

    第三条最值得停下来想一秒。内核里 probe 失败会留下明确的错误记录，因为 probe 是注册路径上的必经动作；U-Boot 里一个驱动可以全程绑好了却从没被 probe 过——只要启动路径没用到它。这带来两个实际后果：其一，dm tree 里看到的设备存在不代表它初始化成功，要看 Probed 列是否为 [ + ]；其二，probe 失败的报错时机不在启动扫描阶段，而在第一次使用设备的命令执行时，排错时不要被"启动日志很干净"误导。

    💡 SPL 里也能用 DM（CONFIG_SPL_DM），但那是精简版框架，部分 uclass 操作未实现，且 SRAM 预算紧张。SPL 场景放不下完整设备树时，CONFIG_SPL_OF_PLATDATA 可以在编译期把设备树节点转成静态 C 结构体，兼得声明式描述和零解析开销。

    bind 与 probe：从 compatible 到可用设备的五步链路 [E]¶

    移植新板卡时最常见的问题：mmc info 返回 "No MMC device found"。设备树里明明写了节点，驱动明明编进去了，链路断在哪一环？先看完整链路的五步：

    设备树节点
    ↓ (1) dm_extended_scan_dt() 遍历所有节点
    ↓ (2) lists_bind_fdt() 匹配 compatible 与 of_match 表
    ↓ (3) device_bind_with_driver_data() 创建 udevice 实例
    ↓ (4) uclass_bind_device() 将 udevice 挂接到对应 uclass
    ↓ (5) device_probe() 调用 driver->probe() 初始化硬件（首次使用时）
活跃 udevice（可使用）

    前四步在 dm_init_and_scan() 中完成，第五步要等设备首次被使用。逐步看关键代码。

    匹配：compatible 字符串是唯一桥梁¶

    驱动侧的匹配规则是一张 udevice_id 数组：

    /* drivers/mmc/rockchip_dw_mmc.c — of_match 表 */
static const struct udevice_id rockchip_dw_mmc_ids[] = {
    { .compatible = "rockchip,rk3568-dw-mshc" },
    { .compatible = "rockchip,rk3399-dw-mshc" },
    { .compatible = "rockchip,rk3288-dw-mshc" },
    { /* sentinel */ }
};

U_BOOT_DRIVER(rockchip_dw_mmc) = {
    .name           = "rockchip_dw_mmc",
    .id             = UCLASS_MMC,
    .of_match       = rockchip_dw_mmc_ids,
    .probe          = rockchip_dw_mmc_probe,
    .priv_auto      = sizeof(struct dwmci_host),
    .plat_auto      = sizeof(struct mmc_platdata),
};

    DM 框架遍历设备树节点，拿节点的 compatible 逐个比对链接段里所有驱动的 of_match 表。匹配是纯粹的字符串比较，没有模糊逻辑——这是后文排查案例的关键。

    bind：建实例、挂 uclass、不碰硬件¶

    /* drivers/core/device.c — 绑定核心逻辑（精简） */
int device_bind_with_driver_data(struct udevice *parent,
                                 const struct driver *drv,
                                 const char *name, void *driver_data,
                                 ofnode node, struct udevice **devp)
{
    struct udevice *dev;

    dev = calloc(1, sizeof(struct udevice));
    dev->driver = drv;
    dev->name = name;
    dev->node_ = node;

    /* 自动分配platdata和privdata空间 */
    if (drv->plat_auto)
        dev->plat_ = calloc(1, drv->plat_auto);
    if (drv->priv_auto)
        dev->priv_ = calloc(1, drv->priv_auto);

    /* 挂接到对应uclass */
    uclass_get(drv->id, &dev->uclass);
    uclass_bind_device(dev);

    /* 调用driver的bind()回调（如果有） */
    if (drv->bind)
        drv->bind(dev);

    *devp = dev;
    return 0;
}

    bind 阶段只做内存和关系，不碰硬件——寄存器没映射、时钟没使能。四个生命周期回调的分工由此确定：

    回调 调用时机 典型工作 失败后果
    bind() 设备实例创建时（启动扫描阶段） 分配空间、注册子设备 设备无法实例化
    probe() 设备首次被使用时 映射寄存器、使能时钟、初始化硬件 设备不可用，返回 -ENODEV
    remove() 设备显式卸载时 释放资源、关闭时钟 资源泄漏
    unbind() 设备实例销毁时 释放 platdata/privdata 内存泄漏

    probe：设备树参数在此兑现¶

    probe 里通过 dev_read_* 系列函数从设备树节点读取参数，填充 platdata 并初始化硬件。设备树一侧：

    /* arch/arm/dts/rk3568-evb.dtsi — eMMC 设备树节点（节选） */
&sdhci {
    compatible = "rockchip,rk3568-dw-mshc";
    reg = <0x0 0xfe310000 0x0 0x10000>;
    clocks = <&cru HCLK_EMMC>, <&cru CLK_EMMC>;
    resets = <&cru SRST_EMMC>;
    bus-width = <8>;              /* ← 解析为 plat->bus_width */
    max-frequency = <150000000>;  /* ← 解析为 plat->f_max */
    cap-mmc-highspeed;
    non-removable;
};

    驱动一侧：

    /* drivers/mmc/sdhci.c — probe中从设备树读取platdata（精简） */
static int sdhci_probe(struct udevice *dev)
{
    struct mmc_platdata *plat = dev_get_plat(dev);

    plat->f_max = dev_read_u32_default(dev, "max-frequency", 0);
    plat->bus_width = dev_read_u32_default(dev, "bus-width", 1);
    plat->removable = !dev_read_bool(dev, "non-removable");

    if (dev_read_bool(dev, "cap-mmc-highspeed"))
        plat->caps |= MMC_CAP(MMC_CAP_HS);

    return 0;
}

    一个完整的 probe 通常还包含时钟与复位的申请——这正是 DM 资源管理相对硬编码时代的核心价值：

    /* drivers/mmc/rockchip_dw_mmc.c — probe 典型流程（精简） */
static int rockchip_dw_mmc_probe(struct udevice *dev)
{
    struct dwmci_host *host = dev_get_priv(dev);
    struct clk clk;
    int ret;

    ret = clk_get_by_index(dev, 0, &clk);   /* 经CLK uclass申请时钟 */
    if (ret)
        return ret;
    clk_enable(&clk);

    ret = reset_get_by_index(dev, 0, &host->reset_ctl);
    if (!ret)
        reset_deassert(&host->reset_ctl);   /* 解除复位 */

    host->ioaddr = dev_read_addr_ptr(dev);  /* reg属性解析为寄存器基址 */

    return dwmci_probe(dev);                /* 交给通用驱动完成协议层初始化 */
}

    ⚠️ dev_read_u32() 在属性不存在时返回错误码但不打印任何信息，静默失败是它的默认行为。对影响功能的属性必须检查返回值并给出默认值或明确报错，否则设备树里少写一行，驱动就带着零值继续跑，症状出现在离根因很远的地方。

    ⚠️ 设备树里 status = "disabled" 的节点会被 DM 跳过，不创建 udevice；父节点 disabled 时所有子节点同样不被扫描。另外 of_match 表最后一项必须是空 sentinel { }，漏掉会导致遍历越界，匹配到内存垃圾或直接 data abort。

    probe 失败排查：log、dm tree、compatible 三板斧 [E]¶

    回到开头的故障：RK3568 板卡 U-Boot 启动后 mmc list 输出为空，mmc info 报 "No MMC device found"。

    第一步：让 DM 自己说话¶

    U-Boot 命令行执行 log level 7（或编译时开启 CONFIG_LOG_MAX_LEVEL=7）后重启，DM 框架会报告每个节点的绑定结果：

    DM: device 'mmc@fe310000' has no driver

    设备树节点存在但没有驱动认领——问题锁定在第 (2) 步 compatible 匹配。

    第二步：逐字符比对 compatible¶

    /* 设备树中写的（错误） */
compatible = "rockchip,rk3568-dwmmc";      /* 少了 "-mshc" */

/* 驱动中注册的（期望） */
{ .compatible = "rockchip,rk3568-dw-mshc" },

    🔴 这是 Rockchip 平台的历史遗留坑：旧版内核设备树用 dwmmc，主线统一为 dw-mshc。从旧项目直接复制设备树节点到 U-Boot，compatible 差几个字符，匹配静默失败，没有任何报错指向真正的原因。修复方向是改设备树与主线对齐；维护闭源老分支时也可以在驱动的 of_match 表里追加旧命名兼容。

    第三步：验证并建立诊断习惯¶

    修复后 log level 7 输出变为：

    DM: probe device mmc@fe310000 (rockchip_dw_mmc)
DM: probe ok
MMC:   mmc@fe310000: 1

    日常诊断 DM 问题的三个命令应当形成肌肉记忆：

    => dm tree                    # 查看完整的设备绑定树，Probed 列 [ + ] 表示已 probe
=> dm uclass                  # 按 uclass 分组列出所有设备实例
=> dm devres                  # 查看各设备申请的资源（clock/reset/regulator 等）

    dm tree 输出里设备存在但 Probed 列是 [ ]（未激活），说明 bind 成功、probe 未发生或失败——接着在该设备第一次被使用的命令处找报错，而不是回头查设备树。

    本节总结¶

    要点 内容
    DM 解决的问题 驱动注册散落、设备实例硬编码、资源直接写寄存器；改为链接段收集 + 设备树实例化 + DM API 统一管理
    bind vs probe bind 在启动扫描时创建 udevice（只花内存不碰硬件），probe 在设备首次被使用时初始化硬件（惰性）
    三要素 uclass 定义一类设备的公共接口，driver 是具体 IP 实现，udevice 是设备树节点的实例化身
    platdata / privdata plat 来自设备树描述硬件（bind 阶段可用），priv 来自 probe 分配描述运行时状态，两者强制分离
    与内核模型的差异 无 bus_type、无模块加载、probe 惰性触发；dm tree 里设备存在 ≠ 初始化成功，看 Probed 列
    compatible 匹配 纯字符串比较，无模糊逻辑；拼写不一致是移植新板卡最高频的 bind 失败原因
    排查三板斧 log level 7 看绑定报告 → dm tree/dm uclass 看实例与激活状态 → 逐字符比对 compatible
    SPL 场景 CONFIG_SPL_DM 为精简版；SRAM 紧张时用 CONFIG_SPL_OF_PLATDATA 编译期静态化设备树

    💡 DM 的惰性 probe 是理解 U-Boot 启动时间优化的钥匙：dm tree 里没被激活的设备就是没花启动时间的设备，反过来，启动慢的板子先看哪些不必要的设备在启动路径上被提前 probe 了。
