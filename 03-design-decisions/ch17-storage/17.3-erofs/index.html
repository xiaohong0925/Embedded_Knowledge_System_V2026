    17.3 文件系统决策：故障模式视角与 EROFS 时代¶

    所属章节：第17章 存储架构设计

    难度：[E] | 预计阅读时间：60分钟

    本节导读¶

    文件系统的机制层内容本书已经讲过：12.3.1~12.3.4 逐个子系统拆解了 ext4、F2FS、UBIFS 的内部工作原理，12.3.5 给了"介质定候选集、读写模式定选型"的框架和 fio 实测方法。机制与常规选型都已闭合，本节不再重复。本节立论：架构决策要比较的不是"怎么工作"，而是"怎么失败"——断电之后，每种文件系统坏成什么样、多久能回来、最坏情况丢什么。此外还有一条时间线：只读 rootfs 的最优解正在从 SquashFS 向 EROFS 迁移，12.3.5 的选型框架也需要补上两个时代维度。
    本节覆盖：

    • 故障模式视角的三个比较维度：恢复时间、损坏概率、最坏损失
    • 四条路线（ext4 / F2FS / UBIFS / 只读 FS）的断电故障模式卡与合成矩阵
    • EROFS vs SquashFS：结构差异、四个结构性优势、SquashFS 的保留场景、迁移清单
    • 选型维度的时代更新：dm-verity 与 OTA 形态并入，四维决策表
    • 工业网关的文件系统方案收口

    从"怎么工作"到"怎么失败"¶

    主要矛盾不在"好用"，在"坏相"¶

    正常工况下，主流文件系统的差异是"好"与"更好"：ext4 与 F2FS 在你的负载上差 20% 性能，这种事用 fio 一测就有数（12.3.5 的方法），而且多数嵌入式负载根本碰不到任何一方的性能边界。

    真正拉开差距的是失效工况。17.1 的第二波失效（断电损坏，量产半年后统计可见）打在文件系统层，每种 FS 的"坏相"完全不同：ext4 断电后走 journal replay，多数情况几秒恢复，但 journal 覆盖不到的元数据损坏要走 fsck，大分区 fsck 是分钟级；F2FS 用 checkpoint + roll-forward，恢复路径完全不同；UBIFS 日志结构天然抗断电，但背着 UBI attach 时间；只读 FS 根本没有"断电损坏"这个概念——没有写，就没有写一半。

    这些差异在 fio 报告里一行都没有。选型比较"坏相"，是因为失效工况的损失量级远大于正常工况的性能差异：20% 的性能差距用户无感，一次 fsck 卡死在客户现场就是售后工单。

    故障模式比较的三个维度¶

    维度 问法 为什么重要
    恢复时间 断电后多久能重新提供服务？ 无人值守设备的可用性指标；超过 watchdog 窗口就触发复位循环
    损坏概率 单次断电的损坏概率是多少？ × 现场断电次数 = 17.1 第二波的失效率
    最坏损失 运气最差时丢什么？ 丢最后一笔日志 ≠ 丢整个分区 ≠ 整卡变砖，恢复策略完全不同

    下面按这三个维度给四条路线各画一张故障模式卡。

    断电故障模式矩阵¶

    故障模式卡：ext4¶

    断电瞬间发生什么：data=ordered 模式下，数据先于元数据落盘，journal 里待提交的元数据事务丢失。机制见 12.3.1，挂载参数语义见 12.5.2。

    维度 表现
    恢复时间 journal replay 通常秒级；触发 fsck 则大分区分钟级
    损坏概率 低但非零——journal 只保元数据，barrier=1 + data=ordered 下文件内容仍可能丢尾
    最坏损失 元数据损坏穿透 journal（多次断电叠加、barrier 被关）→ 全分区 fsck；fsck 修不了的需人工介入——无人值守设备最怕这一格

    fsck 这一格值得展开，因为它是 ext4 在嵌入式场景的主要失分点。journal replay 只重做日志里已完成的事务，快；但损坏一旦落到 journal 覆盖范围之外（目录结构、inode 位图、超级块），只能走 fsck 全量校验。fsck 的时间随分区大小和文件数量增长，几百 GB 的分区跑几十分钟不稀奇。更麻烦的是交互性：经典 e2fsck 遇到某些损坏会停下来问"是否修复"——无人值守设备面前没有那个按 y 的人。

    工程上的应对是一套组合，不是单一开关：

    # 1. 让 fsck 自动修复而非交互询问（initramfs 或 systemd 集成处配置）
e2fsck -y /dev/mmcblk0p5

# 2. 给 fsck 加超时，超时即放弃并让系统带伤启动（带伤 > 卡死）
#    systemd 体系下由 systemd-fsck 的超时配置控制

# 3. 数据分区的设计配合：fsck 修不了的分区允许被 factory reset 重建
#    ——前提是该分区的数据持久化要求不是"不可丢失"（17.1 分类表）

    第 3 条把话题引回架构：ext4 数据分区的可接受性，取决于分区里数据的可重建性。这就是"故障模式决定选型"的完整逻辑链。12.5.3 的六大陷阱里还有三个是 ext4 挂载参数配错（barrier 被关、data=writeback 误用、atime 白写），参数纪律是前提。

    架构师视角的红线：ext4 用于无人值守设备的数据分区时，必须先回答"fsck 卡死怎么办"——自动修复策略、watchdog 联动、还是干脆换 FS。

    故障模式卡：F2FS¶

    断电瞬间发生什么：F2FS 以 checkpoint 为一致点，断电后回滚到最近一个 checkpoint，再做 roll-forward 恢复前滚日志中已确认的数据。

    维度 表现
    恢复时间 快——回滚到 checkpoint 是常数级操作，roll-forward 量取决于上次 checkpoint 以来的写入量；挂载速度本身就是 F2FS 的设计卖点
    损坏概率 低；checkpoint 双份（主/备）设计，单点损坏可切换
    最坏损失 两次 checkpoint 之间未落盘的写入（秒级窗口）；flash 友好布局意味着写放大可控，介质层损失也小

    checkpoint 双份值得多讲一句：F2FS 维护主备两份 checkpoint 区域，写新 checkpoint 时不覆盖旧的，断电最多损失"正在写的这份新 checkpoint"，回退到上一份仍是一致状态。这个设计和 17.4 里 A/B 分区、U-Boot 冗余环境变量是同一个思想——双份物理存在 + 写入不覆盖旧值，在文件系统内部、分区布局、bootloader 三层反复出现。识别出这个模式的重复出现，后面看任何存储设计都会先问"它的双份在哪"。

    架构师视角：高频写 + 需要快速断电恢复的数据分区（采集缓存、日志），F2FS 是块设备上的强候选。代价是生态与调优经验少于 ext4（GC 调优参数见 12.3.2），团队学习成本计入 TCO。

    故障模式卡：UBIFS¶

    断电瞬间发生什么：UBIFS 是日志结构文件系统，所有写入追加到日志，断电后从最后一致点重放。机制见 12.3.3。

    维度 表现
    恢复时间 挂载即恢复，秒级；但 UBI attach（扫描擦除块建映射）随容量增长，大分区可达秒级~十秒级，可用 UBI Fastmap 缓解
    损坏概率 极低——日志结构 + UBI 层磨损均衡 + 坏块管理三层都是为裸 NAND 的恶劣环境设计
    最坏损失 日志尾部未提交的数据；UBI 层处理坏块的能力是它存在的第一理由

    UBI attach 时间值得展开，因为它是 UBIFS 唯一的架构级代价。attach 是 UBI 层挂载前的初始化：扫描所有擦除块头、建立逻辑到物理的映射表。朴素实现要扫全片，时间随容量线性增长。Fastmap 的解法是把映射表在最近一次正常卸载时快照到固定块上，attach 时优先读快照、只增量校验——又是一次"双份 + 快照"思想的复用。代价是 Fastmap 本身占若干擦除块，且异常断电后快照失效要回退全扫。启动时间预算紧的产品（第 24 章的题材），UBI attach 是必须单独列项的预算条目。

    架构师视角：裸 NAND 路线上 UBIFS 几乎没有对手（12.3.5 的候选集结论），真正的代价是 attach 时间对启动预算的占用。

    故障模式卡：只读 FS（SquashFS / EROFS）¶

    断电瞬间发生什么：什么都不发生。没有写路径，就没有"写一半"的状态。

    维度 表现
    恢复时间 零——重新挂载即可，毫秒级
    损坏概率 仅取决于介质层位翻转（保持力问题，17.2 已折算），文件系统层免疫
    最坏损失 介质物理损坏 = 整分区失效 → 靠 A/B 分区的另一槽兜底（17.4 的布局配合）

    架构师视角：这就是"只读 rootfs 是产品化分水岭"在断电维度的理由——把系统盘放进故障模式最好的 FS 类型，第二波失效直接砍掉一半暴露面。

    合成矩阵¶

    维度 ext4 F2FS UBIFS 只读 FS
    适用介质 eMMC/UFS/SSD eMMC/UFS/SSD 裸 NAND 任意（含 ubiblock）
    恢复时间 秒级（fsck 时分钟级） 常数级 + 少量 roll-forward 秒级 + UBI attach 零
    单次断电损坏概率 低（参数正确时） 低 极低 免疫
    最坏损失 分区级 fsck，可能需人工 checkpoint 间窗口数据 日志尾部数据 介质损坏才失效，A/B 兜底
    无人值守适配 ⚠️ 需设计 fsck 策略 ✅ ✅ ✅
    配套成本 生态最成熟 团队学习成本 仅限裸 NAND 路线 需 overlayfs 配合可写需求

    矩阵的用法：采集缓存是决定性案例¶

    矩阵不是用来看的，是用来否决的。回到 17.1 工业网关的采集缓存需求——断网期间爆发式写入、业务必须保住、断电后从最后一致点续写：

    • ext4：fsck 分钟级 + 可能需人工 → 无人值守场景否决
    • F2FS：checkpoint 快速恢复 + 追加写友好 → 中标
    • UBIFS：介质是 eMMC 不是裸 NAND → 不在候选集
    • 只读 FS：缓存需要写 → 不适用

    三个维度里"恢复时间"一项就完成了否决——这就是故障模式视角的效率：正常工况下这四个选项的性能差异测半天，失效工况下一秒钟看出答案。

    💡 把矩阵应用到自己的产品：找出"业务必须 + 高频写 + 无人值守"三者交集的数据分区，逐个问它现在用的 FS 在矩阵哪一格、最坏损失是什么。多数存储架构的隐患都藏在这个交集里。

    EROFS vs SquashFS：只读 rootfs 的 2026 答案¶

    矩阵把系统盘的答案收敛到只读 FS。但只读 FS 内部有个正在进行的更迭：SquashFS 当了十几年嵌入式默认答案，EROFS（华为发起，内核 5.4 起主线化，Android 阵营大规模商用）在四个结构性点上完成了反超。

    结构差异：一切分歧的起点¶

    两者都是"只读 + 压缩"的文件系统，分歧在压缩数据的组织方式：

    SquashFS：压缩块按"未压缩数据"切分（默认 128KB 一块）
┌──────────128KB 未压缩──────────┐┌──────────128KB──────────┐
│  压缩后可能只有 40KB            ││  压缩后 45KB             │
└────────────────────────────────┘└─────────────────────────┘
  读其中一个 4KB 文件 → 整个 128KB 块解压 → 取出 4KB
  随机读小文件 = 大量浪费的解压工作

EROFS：压缩输出按页对齐（4KB 物理簇）
┌─4KB─┬─4KB─┬─4KB─┬─4KB─┬─4KB─┬─4KB─┐
│页对齐│页对齐│页对齐│页对齐│页对齐│页对齐│
└─────┴─────┴─────┴─────┴─────┴─────┘
  读一个 4KB 文件 → 只解压它所在的簇
  随机读 = 按需解压，没有浪费

    SquashFS 的设计重心是压缩率优先——128KB 大块给压缩算法更长的匹配窗口，压得狠；代价是随机读一个 4KB 文件要解压整个 128KB 块。EROFS 的设计重心是运行时性能优先——页对齐簇让随机读只解压需要的页，内存占用也更低。这个结构差异是下面所有优势的根源。

    EROFS 的四个结构性优势¶

    优势一：随机读性能。嵌入式 rootfs 的真实负载是大量小文件随机读——共享库加载、配置文件、locale 数据。页对齐解压对这类负载的增益是倍数级的（第三方在 Cortex-A53 + eMMC 5.1 + 内核 6.6 上的评测中，随机 4K 读 IOPS 达到 SquashFS lz4 的约 3 倍，挂载时间也更短）。应用启动速度、内存压力（缓存占用更低）都直接受益。

    优势二：块级去重（内核 6.1 起）。相同的 4KB 块只存一份。Yocto/Buildroot 构建出的多配置镜像、共享大量文件的容器层，去重能在压缩之外再省 5~15% 镜像体积。SquashFS 的 fragment 打包只做文件尾部的文件级合并，没有跨文件的块级去重。

    优势三：dm-verity 亲和。

    dm-verity：内核设备映射层的完整性校验机制，为块设备的每个数据块建哈希树，读取时逐块验哈希，篡改即拒绝。只读 rootfs + dm-verity 是产品防篡改的事实基线（第 19 章安全架构展开）。

    EROFS 的页对齐块与 dm-verity 的哈希树粒度天然对齐，随机读的校验开销低；SquashFS 的变长压缩块会跨 dm-verity 数据块，校验时多读多算。安全基线（19 章）与只读 rootfs（本章）在这里交汇——选型时这两个需求要一起算。

    优势四：OTA delta 更新友好。SquashFS 的 128KB 大块压缩意味着改一个小文件，其所在块及后续块的压缩输出全部变化，delta 更新能复用的内容很少。EROFS 的定长 4KB 簇让块级 diff（bsdiff 类工具）能精确定位变化块，delta 包显著更小。对带宽受限的 OTA（21 章的差分更新策略），这是实打实的下载量差异。

    SquashFS 的保留场景¶

    EROFS 不是全胜。SquashFS 在三个场景仍然是正确答案：

    场景 原因
    极致压缩率诉求 xz 压缩 + 大块窗口，压缩率仍高于 EROFS 的常用配置——存储空间卡死的超小容量设备
    顺序读为主 流式读取（媒体播放、日志回放）碰不到随机读劣势
    老内核（<5.4） EROFS 不在主线；存量产品的 BSP 内核没有升级计划时不动它

    外加一条非技术因素：构建流水线已围绕 mksquashfs 固化的团队，迁移有流程成本——但这属于 TCO 权衡，不是技术理由。

    迁移决策与操作清单¶

    决策：新设计的产品，只读 rootfs 默认选 EROFS（lz4hc 是常用甜点配置）；存量产品命中"随机读慢 / dm-verity 开销大 / OTA 包太大"任一痛点时启动迁移评估。

    迁移操作清单（文件系统内容不变，只换盘格式）：

    # 1. 构建侧：mksquashfs 换成 mkfs.erofs（erofs-utils，主流发行版 2023 年起已打包）
mkfs.erofs -zlz4hc rootfs.erofs rootfs/

# 2. 内核侧：确认 EROFS 内置（必须是 y，rootfs 不能用模块）
#    CONFIG_EROFS_FS=y
#    CONFIG_EROFS_FS_ZIP=y
#    CONFIG_EROFS_FS_ZIP_LZMA=y   /* 如需 micro-lzma */

# 3. 启动侧：fstab/initramfs 的挂载类型 squashfs → erofs

# 4. 安全侧：重新生成 dm-verity 哈希树（格式变化，旧哈希树作废）

# 5. 验证：文件权限、符号链接、设备节点、xattr 逐项抽查

    第 4 步最容易漏——哈希树不重新生成，设备会因校验失败拒绝挂载，表现为 OTA 后变砖。这也是"文件系统决策必须和 19 章安全、21 章 OTA 一起评审"的实证。

    ⚠️ EROFS 的镜像制作速度：高压缩级别（lz4hc 高级别）下 mkfs.erofs 显著慢于 mksquashfs。这只影响构建机，不影响设备运行时，但 CI 流水线时间预算要重估。

    选型维度的时代更新¶

    12.3.5 的选型框架是两个维度：介质定候选集、读写模式定选型。框架仍然正确，但它写于两个需求成为产品基线之前——完整性校验（dm-verity）和OTA 差分更新。2026 年，安全法规（欧盟 CRA）把防篡改从加分项变成入场券，OTA 从锦上添花变成标配。两个新维度正式并入。

    维度三：完整性校验成为基线¶

    dm-verity 要求的底层是只读块设备——它校验的是静态镜像的哈希树，镜像一旦可变，哈希树就失去意义。这条约束反向改写了选型逻辑：

    没有完整性校验需求时：
  rootfs 选什么 FS 都行，ext4 可写也挺好

有 dm-verity 需求时：
  rootfs 必须是只读 FS（或只读挂载的 ext4）
  → 可写需求全部下放到 overlayfs 上层或数据分区
  → 17.4 的"只读 rootfs 分水岭"从"推荐"升级为"前提"

    一旦产品把防篡改写进需求（车载、工业控制、任何要过 CRA 的设备），文件系统选型的一半已经被安全架构做完了——rootfs 位置只剩 SquashFS/EROFS 两个候选，选择焦点收缩到上一个二选一。这是"子系统关联"原则的活例：19 章的安全决策会反过来锁定本章的选型空间。

    维度四：OTA 形态的投射¶

    OTA 形态 对 FS 的要求 落点
    整分区替换（A/B 刷整镜像） FS 只读、镜像可整包校验 任意只读 FS 均可
    delta 差分更新 镜像格式要支持块级 diff——定长块结构是前提 EROFS 结构性占优，SquashFS 差
    包管理器式增量（dpkg/rpm 式） rootfs 必须可写 + 断电恢复能力强 与只读 rootfs 冲突，嵌入式设计一般不选这条路

    21 章会展开 OTA 方案的完整选型（RAUC/SWUpdate/Mender、灰度、防降级）。本章只要记住一个映射：选了 delta 更新，rootfs 的 FS 基本锁定 EROFS；选了整分区替换，EROFS/SquashFS 按前述判据正常比。

    2026 版选型决策表¶

    层级 问题 规则
    第一维：介质 介质定候选集 eMMC/UFS/SSD → ext4/F2FS/只读 FS；裸 NAND → UBIFS；只读镜像 → SquashFS/EROFS（12.3.5 原有，不变）
    第二维：读写模式 读写比例定细分 读多写少 → ext4/只读；写多 → F2FS；小文件高频 → F2FS/tmpfs 分流（12.3.5 原有，不变）
    第三维：故障模式 无人值守 + 业务必须的数据分区 恢复时间逐列否决（本节矩阵）；ext4 需先答 fsck 策略
    第四维：产品化需求 dm-verity？delta OTA？ 命中任一 → rootfs 锁只读 FS；命中 delta → 锁 EROFS

    四个维度的判断顺序就是表格顺序：介质砍一刀，读写模式砍一刀，故障模式砍一刀，产品化需求砍最后一刀。四刀下来还不收敛的场景，现实中极少。

    工业网关收口¶

    把四维框架用到 17.1 的需求清单上：

    rootfs（只读集合）：
  介质 eMMC → 候选 ext4/SquashFS/EROFS
  OTA 要可回滚（A/B 整分区替换）→ 只读 FS
  dm-verity（户外无人值守设备，防篡改应入需求）→ 锁只读
  结论：EROFS（新设计默认）；带宽若未来吃紧再评 delta

采集缓存（业务必须 + 高频写）：
  故障模式矩阵 → ext4 否决（fsck 风险）→ F2FS

日志（高频 + 可重建）：
  F2FS 或 ext4 均可；与缓存同区共用 F2FS 减少 FS 种类，
  独立分区 + 硬限容（17.4 展开）

配置（低频 + 业务必须）：
  数据分区 ext4 或随缓存区 F2FS；原子写保护（12.5.2）

    文件系统决策域收口：EROFS（rootfs）+ F2FS（缓存与日志）+ 原子写（配置）。注意这套组合里每个结论都能指回具体的推导——评审时不用辩护"我觉得"，只需展示链条。

    本节总结¶

    文件系统决策域闭环。比较"坏相"的三个维度（恢复时间、损坏概率、最坏损失）画出四张故障模式卡：ext4 的软肋是 fsck 的分钟级恢复与人工介入风险，F2FS 靠 checkpoint 双份拿到常数级恢复，UBIFS 在裸 NAND 上三层防护但背着 attach 时间，只读 FS 文件系统层免疫。EROFS 用页对齐压缩对 SquashFS 完成四个结构性反超（随机读/去重/dm-verity 亲和/delta 友好），新设计默认 EROFS，SquashFS 退守极致压缩、顺序读、老内核三个保留场景。选型框架最终升到四维——介质、读写模式、故障模式、产品化需求各砍一刀，网关收口为 EROFS + F2FS + 原子写，每个结论都有可回溯的推导链。
