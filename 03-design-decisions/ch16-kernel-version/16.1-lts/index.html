    16.1.1 Linux内核发布周期与版本生态基础¶

    开篇决策场景：为什么内核版本选择如此重要？¶

    你是某工业自动化公司的系统架构师，正在为一台工业网关产品设计软件平台。产品预计生命周期10年（2025年量产，2035年退役），目标出货量超过50万台。

    你的硬件团队已经选定了基于NXP i.MX93（Cortex-A55）的SoC方案。现在，你需要做出关键决策：使用哪个Linux内核版本？

    打开 kernel.org 的 releases 页面，你看到了这样的版本矩阵 ：

    版本 类型 维护者 发布日期 EOL
    6.18 longterm Greg K-H / Sasha Levin 2025-11 2028-12
    6.12 longterm Greg K-H / Sasha Levin 2024-11 2028-12
    6.6 longterm Greg K-H / Sasha Levin 2023-10 2027-12
    6.1 longterm Greg K-H / Sasha Levin 2022-12 2027-12
    5.15 longterm Greg K-H / Sasha Levin 2021-10 2026-12
    5.10 longterm Greg K-H / Sasha Levin 2020-12 2026-12

    你皱起眉头。6个活跃LTS版本，EOL从2026年底到2028年底不等。你的疑问包括：实时需求、BSP支持、10年生命周期如何保障、CIP SLTS是什么？

    本节将带你理解Linux内核的发布节奏和版本生态基础——这是做出正确选型决策的第一步。

    1.1 10–11周主线发布节奏：一台精密的分布式时钟¶

    Linux内核的开发遵循着世界上最高效的分布式协作模型之一。每年约发布5–6个主线版本，每个版本的开发周期严格控制在9–10周（约2–2.5个月）。这个节奏自2005年Git工具引入后逐渐稳定，至今已经运转了近20年 。

    理解这个节奏对嵌入式工程师至关重要，因为它直接决定了： - 新功能何时可用（某个驱动或子系统何时进入稳定版） - bug修复的backport路径（你的内核版本能否获得某个关键修复） - LTS版本的选择时机（每年只有一个版本会成为LTS，错过就要等下一年）

    1.1.1 Merge Window（2周）：新功能的大门¶

    每个开发周期以Merge Window（合并窗口）开始，持续约2周。这是新功能进入主线的唯一通道。

    [主线发布 v6.N] → Merge Window打开（2周） → rc1 → rc2 → ... → rc7 → [v6.N+1 稳定发布]
                     ↑
              子系统维护者向Linus提交pull request
              仅接受已 Review + Tested 的补丁集

    Merge Window的运作机制 ：

    Week 1（高强度合并期）： - Linus Torvalds每天合并数百个pull request，涵盖所有子系统（ARM架构、网络、文件系统、驱动等） - 每个pull request来自子系统维护者（如ARM SoC维护者Arnd Bergmann、网络维护者David Miller等） - 一个典型merge window处理约12,000–15,000个commits

    Week 2（收尾期）： - 合并速度放缓，处理延迟提交的请求和修复合并冲突 - 窗口关闭的标志：Linus发布 -rc1，同时宣布"Merge window is closed"

    ⚠️ Merge window关闭后再提交新功能？不可能。如果错过窗口，你的功能必须等待下一个周期（约9–10周后）。这就是为什么SoC厂商的驱动代码需要提前一个周期进入linux-next树，确保在merge window开启时能被顺利合并。

    1.1.2 RC阶段（6–8周）：只有修复，没有新功能¶

    Merge Window关闭后，进入Release Candidate（RC）阶段。这是内核走向稳定的关键期。

    RC 发布时间 主要工作 接受的内容
    rc1 第2周末 初始稳定性检查 仅回归修复
    rc2–rc3 第3–4周 主要bug修复 回归修复 + 重要bug修复
    rc4–rc6 第5–7周 细节打磨 仅回归修复
    rc7 第8周 最终验证 仅关键回归修复
    rc8（可选） 第9周 额外稳定化 仅在发现严重问题时发布
    Final 第8–10周 稳定发布 无

    RC阶段的核心规则：不接受任何新功能，只修复回归（regression）——即该版本引入的新bug。这个规则的严格执行是Linux内核质量的核心保障。

    实际案例：Linux 6.12的RC周期（2024年9月–11月）： 

    6.12-rc1  2024-09-29  Merge window关闭，PREEMPT_RT代码进入rc1
6.12-rc2  2024-10-06  ARM64 DTS修复、驱动稳定性调整
6.12-rc3  2024-10-13  网络子系统回归修复
6.12-rc4  2024-10-20  文件系统bug修复
6.12-rc5  2024-10-27  最后的驱动修复
6.12-rc6  2024-11-03  仅2个关键修复
6.12 Final 2024-11-17  v6.12稳定发布

    这个7周的RC周期是典型的"干净"发布——没有需要rc8的严重问题。

    1.1.3 LTS版本的诞生：每年一个幸运儿¶

    每年，Linux社区会从当年的主线版本中选择一个作为LTS（Long-Term Support）版本。选择规则 ：

    1. 通常选择当年最后一个稳定版本（即11月/12月发布的版本）
    2. 由Greg Kroah-Hartman（稳定版维护者）正式宣布
    3. 一经宣布，该版本将获得2–6年的维护期

    近年来的LTS选择历史：

    年份 LTS版本 发布时间 选择依据
    2020 5.10 2020-12 当年最后一个稳定版
    2021 5.15 2021-10 当年最后一个稳定版
    2022 6.1 2022-12 当年最后一个稳定版
    2023 6.6 2023-10 当年最后一个稳定版
    2024 6.12 2024-11 当年最后一个稳定版，含PREEMPT_RT
    2025 6.18 2025-11 当年最后一个稳定版

    💡 选择当年最后一个稳定版作为LTS，是因为经过一年的开发积累，该版本通常拥有最多的新功能和最好的硬件支持，同时又是"成熟的"——它后面的RC周期在冬季假期前完成，社区有足够时间进行测试。

    1.2 Stable Team的工作原理：Greg KH的"每周五补丁日"¶

    主线版本发布后，Stable Team接手维护工作。这个团队由Greg Kroah-Hartman和Sasha Levin领导，负责将主线中的bug修复和安全补丁backport（向后移植）到所有仍在维护的stable和LTS版本。

    1.2.1 每周发布流程¶

    Stable Team的工作节奏是每周一个发布 ：

    周一–周三：  Greg审查主线commits，选择适合backport的修复
周四：      生成stable-queue，构建发布候选
周五：      发布新的stable版本（如 v6.12.5）

    一个典型的stable发布包含20–100个补丁，涵盖： - 安全修复（CVE补丁） - 回归修复 - 驱动bug修复 - 文件系统稳定性修复

    1.2.2 Backport选择标准¶

    不是所有主线修复都会被backport到所有LTS版本。Greg KH有一套严格的选择标准 ：

    /* 理想情况下，我会将所有修复都backport到所有版本。但 */
/* 1. 有些修复依赖之前的重构（无法干净地cherry-pick）   */
/* 2. 有些修复"理论上"会影响老版本，但从未被报告          */
/* 3. 资源有限——6个LTS版本 × 每周 = 大量工作              */

/* 实际标准： */
/* - 有CVE编号的安全修复：必须backport                    */
/* - 有Reported-by标签的回归修复：优先backport            */
/* - 新硬件驱动修复：通常只backport到较新的LTS            */
/* - 内部重构清理：通常不backport                         */

    🔴 这意味着老版本LTS可能错过一些修复。特别是5.10/5.15这样的老版本，随着EOL临近，backport的优先级会越来越低。2026年仍基于5.10/5.15做新产品，意味着你可能在EOL之前就开始感受到补丁覆盖率的下降。

    1.4 为什么嵌入式工程师必须关注主线节奏¶

    一个常见的误解是："我选了一个LTS版本，主线开发跟我没关系。" 这个观念在嵌入式领域非常危险。

    1.4.1 主线→LTS的修复传导链¶
    [Bug在主线被发现] → [主线修复] → [Stable Team审查] → [Backport到LTS] → [你的设备获得修复]
        ↑                                                    ↑
   社区报告/开发者发现                              你的BSP供应商整合

    这个链条的延迟通常为1–4周（从主线修复到LTS版本发布）。但对于老版本LTS，如果修复无法干净cherry-pick，延迟可能延长到数月，甚至被跳过。

    1.4.2 硬件支持的上游优先原则¶

    新的SoC和外围设备的支持总是先进入主线，然后才可能被backport到LTS。这意味着：

    • 如果你使用的是最新SoC（如2025年发布的芯片），你可能需要较新的LTS版本才能获得完整的驱动支持
    • 老版本LTS（如5.10）可能永远无法获得新硬件的支持

    案例：NXP i.MX93于2023年发布，其完整Device Tree支持直到Linux 6.4才进入主线。这意味着6.1 LTS需要大量NXP的out-of-tree补丁才能支持i.MX93，而6.6 LTS和6.12 LTS的i.MX93支持则好得多。

    1.4.3 新功能vs稳定性的永恒平衡¶
    策略 优点 缺点 适用场景
    紧跟最新LTS 最新硬件支持、最新功能、最长维护期 可能存在未发现的bug 新产品开发、消费者设备
    选择成熟LTS 社区验证充分、补丁覆盖完善 硬件支持可能不足、EOL较早 保守的工业应用
    使用CIP SLTS 10年保障、工业级验证 版本较老、新硬件支持有限 关键基础设施、长生命周期产品

    2.2.2 关键特性¶

    Linux 6.18是2025年的年度LTS版本，引入了一系列重要的基础设施改进 ：

    Sheaves内存管理：6.18引入了名为"Sheaves"的新型per-CPU slab缓存层。传统的SLUB分配器在所有CPU之间共享slab缓存，高并发场景下产生显著的锁竞争。Sheaves为每个CPU核心分配独立的内存对象缓存，减少处理器争夺共享内存池的冲突，在高负载多线程场景下可提升10–20%的内存分配性能 。

    dm-pcache：Device-mapper新的持久缓存目标，允许使用NVDIMM/CXL等持久内存作为块设备的缓存层。这对需要高性能存储的工业边缘计算设备有潜在价值。

    XFS online fsck默认启用：XFS文件系统现在支持在线文件系统检查（fsck），无需卸载文件系统即可检测和修复问题。对于要求7×24运行的工业网关，这意味着可以在不中断服务的情况下进行文件系统健康检查。

    Signed BPF程序：内核现在支持加密签名的BPF（eBPF）程序。这一安全强化措施对使用eBPF进行网络过滤和监控的设备很重要——只有经过签名的BPF程序才能加载到内核。

    2.2.3 BSP支持状态¶

    作为最新LTS，6.18的BSP支持还在完善中：

    • NXP i.MX：Yocto walnascar分支提供linux-imx 6.18支持，但GPU/VPU驱动可能不如6.12成熟
    • TI：linux-ti-staging 树在 6.18 发布后持续跟进，具体外设驱动的成熟度需以实测为准
    • Rockchip：RK3588/RK3568的mainline支持在6.18中持续完善，GPU（Mali G610）的Panfrost驱动支持较好
    2.2.4 实时能力¶

    6.18继承了6.12的PREEMPT_RT主线化成果，支持CONFIG_PREEMPT_RT=y。但作为新版本，RT路径上的某些驱动（尤其是GPU和专用加速器）可能存在稳定性问题。

    2.3.2 关键特性：为什么6.12是嵌入式工程师的"梦中情核"¶

    Linux 6.12 LTS之所以被绝大多数嵌入式工程师视为当前的首选，不是因为某一项特性，而是因为它在多个关键维度上同时达到了里程碑 ：

    ① PREEMPT_RT主线化（最核心的特性）

    经过20年的开发，PREEMPT_RT实时补丁终于在Linux 6.12中完整合并到主线。这意味着： - 不再需要打外部RT补丁（以前每个内核升级都要重新适配RT补丁集） - 只需一个配置项即可启用实时：CONFIG_PREEMPT_RT=y - 所有内核驱动现在必须在RT环境下编译通过，RT兼容性成为上游标准 - 支持ARM64、x86_64、RISC-V架构

    我们将在第5节深入讨论PREEMPT_RT的技术细节。

    ② sched_ext：BPF可编程调度器

    6.12引入了sched_ext，一个基于BPF（Berkeley Packet Filter）的可编程调度类。这使得开发者可以用BPF程序定义自己的调度策略，而无需修改内核代码 。

    // sched_ext示例：一个简单的优先级提升调度器
#include <linux/bpf.h>
#include <bpf/bpf_helpers.h>

SEC("sched_ext/example")
int BPF_PROG(sched_init)
{
    // 自定义调度逻辑：为标记为RT的任务提供额外CPU时间
    return 0;
}

    对于工业设备，sched_ext的潜在应用包括： - 为Modbus/PLC通信线程创建专用调度策略 - 根据I/O负载动态调整任务优先级 - 实现"确定性的"任务执行时间片分配

    ③ ARM64 Permission Overlay Extension (POE)

    支持ARM的Permission Overlay Extension，允许用户空间对特定内存区域施加细粒度权限控制。这是实现更安全的用户空间内存管理的基础。

    ④ RISC-V架构扩展

    继续完善RISC-V架构支持，添加多个CPU ISA扩展。对于评估RISC-V SoC的嵌入式项目，6.12提供了比6.6更好的硬件兼容性。

    2.3.5 已知问题与限制¶

    1. PREEMPT_RT在某些SoC上的稳定性：虽然RT代码已主线化，但某些SoC的厂商驱动可能未在RT环境下充分测试。特别是GPU和VPU驱动，在RT内核上可能出现死锁。

    2. sched_ext的成熟度：BPF调度器是可编程的，但API可能在未来版本中变化。用于生产环境需要锁定API版本。

    3. Rust驱动的可用性：6.12支持Rust编写内核驱动，但实际可用的Rust驱动仍然很少。不要指望用Rust替代C编写设备驱动。

    2.4.2 关键特性¶

    EEVDF调度器：6.6最大的变革是用EEVDF（Earliest Eligible Virtual Deadline First）替代了服役16年的CFS（Completely Fair Scheduler）。

    EEVDF的核心改进在于延迟感知：CFS使用启发式方法猜测哪些进程需要更多关注，而EEVDF通过算法化的方式确保"被忽视"的进程自动获得下一次调度机会。实际效果： - 交互式任务（如UI响应）延迟降低15–30% - 批处理任务（如编译、数据处理）吞吐量保持或略有提升 - 去除了CFS中大量可调参数，调度行为更可预测

    ⚠️ EEVDF在某些特定工作负载下可能出现调度退化。2023年底6.6发布后，有用户报告在特定游戏场景下出现UI卡顿。虽然这些问题在后续stable更新中已修复，但如果你从5.15/6.1升级，建议进行全面性能回归测试。

    Intel Shadow Stack：支持Intel的Shadow Stack硬件特性，防止ROP（Return-Oriented Programming）攻击。对安全敏感的应用场景（如金融终端、安全网关）有价值。

    可配置unbound workqueue：改进无绑定workqueue的执行局部性，对多L3缓存的现代处理器（如AMD Zen 4、Intel Alder Lake）性能提升明显。

    2.4.3 BSP支持状态¶

    6.6的BSP生态非常成熟——它已经被多个Yocto和Buildroot版本采用：

    • NXP i.MX：scarthgap分支的linux-imx 6.6.23+git，经过充分验证
    • TI：linux-ti-staging 6.6支持AM62x/AM335x/AM437x全系
    • Rockchip：RK3588/RK3568支持良好，但不如6.12完善（部分GPU特性缺失）
    • Raspberry Pi：Raspberry Pi OS基于6.6内核
    2.4.4 实时能力¶

    6.6发布时PREEMPT_RT尚未完整主线化。要使用RT，需要打外部补丁（RT补丁集）。CIP项目维护6.6-cip分支，但不包含RT版本。

    16.1.3 LTS政策变迁与维护者危机¶

    上一节我们看到 6 个 LTS 版本并存、EOL 参差不齐的局面。这种局面并非一向如此——它是 2023 年 LTS 政策剧变和后续一系列妥协的产物。理解这段历史，才能判断"今天的 EOL 承诺明天还算不算数"，而这直接决定选型时对 EOL 日期的信任程度。

    3.1 历史背景：LTS政策是如何演变的¶

    理解当前LTS政策的混乱局面，需要回顾过去7年的历史。这不是一个突然的决定，而是一系列渐进变化的累积结果。

    3.1.1 黄金时代：2017–2023年的"6年LTS"¶

    2017年9月，Linux社区做出一个重要决定：将LTS支持周期从2年延长到6年 。这个决定的背景是：

    • 智能手机（Android）和物联网设备的爆发式增长
    • 这些设备的生命周期通常为4–6年，但之前LTS只覆盖2年
    • 设备厂商被迫自行维护老版本内核，导致安全补丁分散和重复劳动

    6年LTS政策的典型例子：

    版本 发布日期 原2年EOL 6年EOL 实际受益
    4.4 2016-01 2018-01 2022-01 Android 7/8设备
    4.9 2016-12 2018-12 2022-12 嵌入式设备
    4.14 2017-11 2019-11 2024-01 Android 9设备
    4.19 2018-10 2020-10 2024-12 工业设备
    5.4 2019-11 2021-11 2025-01 通用平台

    6年LTS政策被誉为嵌入式行业的"福音"——设备厂商可以放心选择 LTS 版本，产品的整个生命周期内都能获得安全补丁。

    3.1.2 地震来袭：2023年9月的"2年 shock"¶

    2023年9月，Linux内核维护者之一Sasha Levin在邮件列表中宣布：未来的LTS版本将只维护2年 。

    这个决定的核心原因是维护者burnout（职业倦怠）：

    "维护6个以上的LTS版本，每个版本每周处理数十个补丁，这是一份全职工作。但我们大多数人没有为此获得报酬。" —— 匿名维护者

    具体数据： - 2023年时，Stable Team同时维护6个LTS版本（4.14/4.19/5.4/5.10/5.15/6.1） - 每周review和backport约200–400个补丁 - 测试覆盖30+种架构和配置组合 - 只有Greg KH和Sasha Levin是全职维护者，其余依赖志愿者

    3.1.3 行业反击与政策妥协¶

    2年LTS的消息在嵌入式和Android行业引发了强烈反对 ：

    Google的应对（2024年7月）： Google宣布为Android ACK（Android Common Kernel）提供4年扩展支持——从6.6开始，ACK内核将维护4年（而非原来的2年）。这意味着Android设备厂商至少能获得4年的内核安全补丁 。

    CIP的表态（2023–2024年）： CIP项目明确表示不受上游LTS政策影响——CIP的SLTS版本将继续提供10年支持。这使得CIP成为长生命周期设备的"避风港"。

    Greg KH的妥协（2024–2025年）： 面对业界压力，Greg KH做出了一系列调整： - 2024年12月：意外延长6.1 LTS到2027年12月（从原计划的2026年底延长1年） - 2025年初：宣布6.6 LTS延长到2027年底 - 2025年中：宣布6.12和6.18延长到2028年底 - 2026年2月：6.6/6.12/6.18 的 EOL 再次集体后延，而 5.10/5.15 未获延期——这是"EOL 是地板不是合同"的最新实例：临近 EOL 的版本能否续命取决于维护者资源，选型时绝不能把"可能延期"当作依据

    16.1.4 CIP SLTS项目深度解析¶

    社区 LTS 的 2–4 年覆盖不了 10 年级的产品生命周期，这个缺口由谁来补？本节介绍的 CIP（Civil Infrastructure Platform）项目就是工业界给出的答案——它把"长期维护内核"从每个企业各自的负担，变成了行业共建的基础设施。

    4.1 CIP的诞生：工业巨头们的共同焦虑¶

    4.1.1 成立背景¶

    Civil Infrastructure Platform（CIP， civilinfrastructureplatform.org）项目成立于2016年4月，由Linux基金会托管 。它的诞生源于一群工业设备制造商的共同焦虑：

    "我们的工业控制系统设计寿命20–30年，但Linux内核只维护2–6年。这个缺口怎么办？"

    发起CIP的企业包括： - 西门子（Siemens）：工业自动化领域的全球领导者 - 东芝（Toshiba）：电力系统和基础设施设备 - 日立（Hitachi）：铁路信号和电力系统 - 瑞萨电子（Renesas）：嵌入式处理器和微控制器 - Plat'Home：日本嵌入式系统厂商 - Codethink：英国开源咨询公司

    这些企业认识到：维护长生命周期设备的Linux内核是共同的行业基础设施问题，不应该由每个企业单独解决。

    4.1.2 CIP的使命¶

    CIP的核心使命是 ：

    "为工业和基础设施应用建立一个开源的、工业级的软件基础层，实现能源、交通、智慧城市、制造、医疗和通信基础设施领域的软件构建块的实施和部署。"

    16.1.5 PREEMPT_RT主线化与实时Linux¶

    版本选型中最后一个高频变量是实时性。2024 年 11 月，PREEMPT_RT 在 6.12 中完整主线化，"实时 Linux"从补丁生态变成了内核原生能力——这直接改写了"要不要 RT、选哪个版本"的决策逻辑。本节回顾这段 20 年的历程，并给出 6.12+ 上启用和验证 RT 的完整方法。

    5.1 二十年征程：从2004年的一个补丁到2024年的历史性合并¶

    PREEMPT_RT（Real-Time Preemption）是Linux内核发展史上最持久、最雄心勃勃的项目之一。它的故事跨越了整整20年，涉及数十名内核开发者，改变了工业控制、医疗设备、机器人等领域对Linux的认知。

    5.1.1 起源：2004年，一个疯狂的想法¶

    2004年9月，Linux内核邮件列表上出现了一场激烈的讨论 。多个嵌入式Linux厂商的开发者发布了各自的实时补丁，但没有一个提供完整的解决方案。这些补丁主要解决了当时Linux内核在实时场景下的几个核心问题：

    • 不可抢占的内核代码路径：内核中有大量持有spinlock时禁用抢占的代码，导致高优先级任务被迫等待
    • 中断处理的原子性：中断处理程序运行在中断上下文，无法被抢占
    • 优先级反转：低优先级任务持有高优先级任务需要的锁，且没有优先级继承机制

    Ingo Molnar（当时Red Hat的内核开发者，Linux调度器维护者）开始收集这些补丁，重写不一致的部分，目标是创建一个完全集成在Linux内核中的实时解决方案——而不是像RTLinux或RTAI那样采用双内核架构 。

    5.1.2 关键里程碑时间线¶

    5.1.3 最后的拼图：printk()的RT兼容¶

    PREEMPT_RT合并到主线的最大障碍之一是printk()——内核中最古老的调试机制之一 。

    printk()的问题在于：它使用了大量不可抢占的代码路径和自旋锁。在实时内核中，printk()的调用可能阻塞高优先级任务长达数毫秒——这对实时应用是不可接受的。

    解决printk()的RT兼容性花费了超过5年的时间（2019–2024）： - 2020–2022年：逐步重构printk的核心数据结构和锁机制 - 2023年：引入atomic_printk()和deferred_printk()概念 - 2024年9月：Petr Mladek提交了最后的printk RT补丁 - 2024年9月19日：Thomas Gleixner在欧洲开源峰会（维也纳）上，将这份pull request用金色纸张打印、系上丝带，亲手交给Linus Torvalds

    Linus当天就合并了补丁，commit hash: baeb9a7d8b60b021d907127509c44507539c15e5

    💡 这个仪式感满满的提交标志着一个时代的结束：从此，实时Linux不再是"二等公民"，而是内核的一等公民。

    5.4 RT对内核其他子系统的影响¶

    启用CONFIG_PREEMPT_RT=y后，内核的行为发生以下关键变化 ：

    5.4.1 Spinlock → RT-Mutex转换¶
    // 标准内核（非RT）
spin_lock(&lock);      // 禁用抢占，忙等待
// ... critical section ...
spin_unlock(&lock);    // 启用抢占

// RT内核
// spin_lock() 被宏替换为：
rt_spin_lock(&lock);   // 可睡眠的锁，支持优先级继承
// ... critical section ...
rt_spin_unlock(&lock); // 唤醒等待者

    影响： - 中断处理程序不再禁用抢占（它们运行在内核线程中） - 优先级继承防止优先级反转 - 锁持有时间不再是硬实时边界

    5.4.2 中断线程化¶
    标准内核:    硬件中断 → 中断上下文（不可抢占）→ 返回
                ↓
RT内核:      硬件中断 → 快速ack → 唤醒中断线程（可抢占）→ 线程执行处理
                ↓
            高优先级任务可以抢占中断线程！

    这意味着：在RT内核上，一个高优先级的用户空间任务可以抢占正在执行的中断处理程序——这是标准内核绝对不可能的行为。

    5.4.3 延迟表现对比¶
    配置 调度延迟（典型） 调度延迟（最坏情况） 适用场景
    PREEMPT_NONE 10–100 ms 数秒 服务器吞吐量
    PREEMPT_VOLUNTARY 1–10 ms 100 ms 桌面系统
    PREEMPT (标准) 100 µs – 1 ms 10 ms 低延迟桌面
    PREEMPT_RT 5–30 µs 50–200 µs 工业/医疗/机器人

    5.5 当前限制和已知问题¶

    ⚠️ PREEMPT_RT主线化是里程碑，但不意味着"开箱即用"的硬实时。以下是当前的关键限制：

    5.5.1 不是"硬实时"¶

    PREEMPT_RT提供的是软实时（soft real-time），不是硬实时（hard real-time）：

    特性 PREEMPT_RT Linux 硬实时RTOS（QNX/VxWorks）
    最坏情况延迟 50–500 µs 1–10 µs
    延迟保证 统计性保证 确定性保证
    功能安全认证 无（IEC 61508 SIL 3不可用） 有（SIL 3/ASIL D）
    延迟失败后果 可接受偶发超时 不允许任何超时

    结论：PREEMPT_RT适用于"偶尔超时不会导致灾难"的场景——如工业协议网关、数据采集、非安全关键的控制系统。对于功能安全关键的应用（如汽车制动、飞机飞控、核反应堆控制），仍然需要认证的RTOS。

    5.5.2 GPU和加速器驱动的RT兼容性¶

    虽然RT代码已主线化，但某些驱动（尤其是GPU和AI加速器）在RT环境下可能表现不佳：

    • GPU驱动的调度依赖于非抢占的代码路径
    • DMA传输的同步原语可能与RT假设冲突
    • 固件加载（firmware loading）通常是同步阻塞的

    实际案例：在i.MX8M Plus上使用NPU（Ethos-U）进行AI推理时，如果同时运行RT任务，NPU驱动的中断处理可能导致RT任务延迟增加20–50µs。

    5.5.3 调试困难¶

    RT问题的调试比标准内核困难得多： - ftrace在RT路径上的开销影响实时性能 - printk的RT版本（atomic printk）可能丢失消息 - lockdep在RT下不可用（RT-Mutex的实现与lockdep假设冲突）

    5.5.4 性能开销¶

    RT功能有轻微的性能开销：

    指标 标准内核 RT内核 开销
    上下文切换 1.5 µs 2.0 µs +33%
    系统调用 80 ns 100 ns +25%
    吞吐量（网络） 100% 95–98% -2~5%

    对于绝大多数嵌入式设备，这个开销是可以接受的。但对于追求极致吞吐量的场景（如网络设备），需要进行评估。

# 在U-Boot环境变量中设置：

    本节总结¶

    内核版本生态的底层逻辑只有一条：维护承诺是有期限的，而产品生命周期往往比承诺更长。社区 LTS 提供 2–4 年的基础保障，CIP SLTS 把它延长到 10 年，PREEMPT_RT 主线化则消除了实时性带来的版本锁定——理解这三个机制，就掌握了版本选型的全部原料。
