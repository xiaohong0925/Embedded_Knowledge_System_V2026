# 速率与接口选择：怎样把调试证据用于决策

> 所属章节：第五部 B. 总线协议 > B-B.4 SPI 总线 > B-B.4.4 SPI 调试与选型
>
> 本组阅读：第 2 页，共 2 页

本页只回答一个问题：**完成分层调试后，怎样根据完整事务、控制器、器件和板级条件选择速率与接口？**

上一页已经用同一笔 JEDEC ID 读取建立正常基线，并区分了工具返回、内部回环、外部短接、数字帧和模拟波形的证据范围。现在不再增加故障清单，而是把这些证据变成选择约束：这笔操作到底需要多少拍，请求速率会怎样变成实际 SCLK，换一种接口又会改变哪些条件。

---

## <span class="blue"> 从恢复后的正常事务开始比较

贯穿实例仍是 RK3568 SPI1 与 W25Q128JV-IQ/JQ 之间的 Mode 0、8 位、MSB-first、低有效 CS 读取：

```text
MOSI：9F 00 00 00
MISO：?? EF 40 18
拍数：8 拍命令 + 24 拍响应 = 32 拍
```

恢复正常连接或参数后再次得到 `EF 40 18`，只说明这笔事务在当前条件下回到已知基线。它既不代表更高速率已经可用，也不代表 QSPI、OSPI 或另一块板卡已经验证。选择应从这份有限的证据出发，而不是从接口名称或器件类别出发。

### 先算完整事务，再讨论有效数据有多快

若一笔操作的命令、地址、dummy 和数据阶段分别需要 `N_cmd`、`N_addr`、`N_dummy`、`N_data` 个时钟，则总拍数为：

```text
N = N_cmd + N_addr + N_dummy + N_data
```

各阶段使用同一个实际 SCLK 频率 `f_actual` 时，纯时钟时间为：

```text
T_clock = N / f_actual
```

完整操作还要加上片选建立与保持、软件准备、调度、事务间隔等开销；编程或擦除命令另有器件内部忙时间：

```text
T_operation = T_clock + T_overhead + T_busy（仅在有内部忙过程时）
```

本例没有地址和 dummy，`N = 8 + 0 + 0 + 24 = 32`。如果实际 SCLK 恰好为 1 MHz，纯时钟时间是：

```text
T_clock = 32 / 1 MHz = 32 μs
```

若沿用上一页的 100 kHz 降速对照，且实际 SCLK 恰好为 100 kHz，同一笔读取就是 `32 / 100 kHz = 320 μs`。降速没有改变 32 拍，只把每拍拉长十倍；这两个数值都是给定频率下的算术结果，不是当前板卡的耗时测量。

`T_overhead` 不因公式省略而消失，`T_busy` 也不能塞进 dummy。dummy 是读取命令规定的固定等待拍数，BUSY 则反映编程或擦除是否仍在进行。比较不同命令时，必须重新读取手册并计算各阶段，不能把 32 拍或 32 μs 外推成所有 SPI 操作的固定成本。

### 把降速恢复转换成约束，而不是直接选定低速

上一页的降速对照只有在其他条件不变时才有比较意义。若较高速率异常、100 kHz 下恢复 `EF 40 18`，可以判断故障表现与频率或可用时间窗口相关；它不能区分控制器分频、器件输出有效、传播延迟、主机建立时间和信号质量中的哪一项超限。

| 调试证据 | 对选择的实际帮助 | 仍需补齐的条件 |
|---|---|---|
| 当前配置下工具成功返回，且 `RX[1]～RX[3]` 为 `EF 40 18` | 建立后续速率对照的基线 | 实际 SCLK、其他速率、长期稳定性和模拟裕量 |
| 高速异常，其他条件不变，降速后 ID 正确 | 把频率或时间窗口列为约束 | 用数字帧和接收端波形区分协议错误与时序、电气限制 |
| 数字帧仍完整，但接收端波形或采样窗口不合格 | 板级条件正在收窄可用速率 | 按手册代入最坏时序参数，并检查走线、门限、边沿和探测条件 |
| 数字帧本身不符合命令、拍数或位序 | 先排除协议与配置问题 | 不能用继续降速代替帧格式修正 |

因此，低速成功可以成为一个可复测的候选工作点，却不是永久配置答案。最终速率要同时满足功能需求和下面的控制器、器件、板级约束。

## <span class="blue"> 可用速率由控制器、器件和板级条件共同决定

### 控制器决定请求怎样落地

设备树中的 `spi-max-frequency` 和传输中的 `speed_hz` 都是速率上限或请求，不是对引脚频率的保证。Linux v6.6 的 [`spi_setup()`](code/B-B.4.3/kernel-v6.6/drivers/spi/spi.c){: data-code-viewer="true" data-code-title="spi.c" data-code-path="Linux v6.6 · drivers/spi/spi.c" data-code-lines="3695-3788"} 会把设备上限收窄到控制器已声明的上限；控制器驱动再根据自己的时钟和分频规则配置硬件。

当前 RK3568 驱动在 [`rockchip_spi_probe()`](code/B-B.4.3/kernel-v6.6/drivers/spi/spi-rockchip.c){: data-code-viewer="true" data-code-title="spi-rockchip.c" data-code-path="Linux v6.6 · drivers/spi/spi-rockchip.c" data-code-lines="854-880"} 中根据源时钟和硬件限制声明速率范围，又在 [`rockchip_spi_config()`](code/B-B.4.3/kernel-v6.6/drivers/spi/spi-rockchip.c){: data-code-viewer="true" data-code-title="spi-rockchip.c" data-code-path="Linux v6.6 · drivers/spi/spi-rockchip.c" data-code-lines="602-607"} 中把理想分频向上取到满足要求的偶数，使结果不超过本次请求速率。这个实现解释了为什么请求值与实际 SCLK 可以不同，但不能推广成所有 SoC 都使用偶数分频。

`spidev_test` 打印的 `max speed` 只是用户态读回的请求上限。Linux v6.6 的 spidev 文档明确说明，该接口不能报告实际移位位率；因此，本例的 1 MHz 不能仅凭这行输出写成仪器实测值。计算预算时应使用实际频率，必要时结合时钟配置、驱动实现和仪器测量交叉确认。

### 器件手册限制命令、速率和输出时间

同一颗器件的不同命令可以有不同的前导、数据路径和频率上限。选型时至少要核对：本例 Mode 0、8 位和 MSB-first 是否受支持，`0x9F` 的响应长度与有效位置是什么，目标命令允许的最高速率是多少，以及输出有效延迟是否随供电条件变化。

本例的预期身份还受具体后缀约束：IQ/JQ 对应 `EF 40 18`，不能把 IM/JM 的不同 Device ID 当成失败。上一页使用的 `tVSL` 则属于上电后到允许选中器件的就绪条件，它回答“何时可以开始访问”，不回答“访问可以用多快的 SCLK”。

### 板级条件决定标称上限能否真正使用

即使控制器和器件都允许某个频率，接收端仍可能没有及时得到稳定数据。B-B.4.2 已给出 MISO 从输出启动到主机采样的时间预算，本页把它直接作为速率约束：

```text
启动边沿到采样边沿的实际间隔
≥ tCLQV(max) + 走线传播 + 主机建立时间 + 设计裕量
```

`tCLQV(max)` 来自器件手册，走线传播取决于实际连接，主机建立时间来自控制器或 SoC 资料，设计裕量还要覆盖实际工作条件。提高频率会缩短可用间隔；降速之所以可能恢复，正是在为这几项让出时间，而不是修复了错误命令或错误 CS。

电平兼容、共地、过冲、下冲、振铃和缓慢边沿也会影响接收判决。多从机共享 MISO 时，还要确认未选中的器件已经释放数据线。逻辑分析仪解码正确不等于这些模拟条件合格，示波器波形良好也不等于命令和有效数据正确；速率定案需要两类证据各自覆盖自己的边界。

可以把选择结果写成：

```text
f_use ≤ min（控制器可用上限，当前命令的器件上限，板级可验证上限）
```

其中“板级可验证上限”不是手册里现成的一个数字，而是由最坏时序预算和实际测量共同确定。实际分频若低于请求值，还要用实际值重新计算完整事务时间。

## <span class="blue"> SPI 与 I2C 要比较同一件事：怎样完成并验证访问

SPI 和 I2C 都能连接串行外设，但它们分配总线、组织事务和提供应答的方式不同。SPI 用 CS 选中器件，主机提供 SCLK，MOSI 与 MISO 可同时移位；I2C 使用 SDA 和 SCL 两条线，以器件地址选择访问对象，并由接收方提供 ACK。比较必须落在这些实际差异上，不能简化成“SPI 快、I2C 省线”。

| 选择条件 | SPI 在本例中的具体表现 | I2C 需要同时满足的条件 |
|---|---|---|
| 如何选择器件 | 拉低目标 CS；多从机还要管理 MISO 驱动权 | 发送器件地址；地址分配不能与同总线其他器件冲突 |
| 一笔事务怎样组成 | 本例为 8 拍 `0x9F` 加 24 拍 ID，共 32 拍 | 按具体器件命令计算地址、控制、数据和应答，不套用 SPI 的 32 拍 |
| 数据路径与带宽 | MOSI、MISO 可全双工工作，适合需要较高串行带宽的访问 | SDA 双向传输，实际速率受所选模式、上拉和总线电容限制 |
| 引脚与共享 | SCLK、MOSI、MISO 之外通常还需独立 CS；增加器件时要检查片选和驱动权 | 两个总线信号可由多个器件共享，但地址、电平、上拉和负载必须共同设计 |
| 是否有低层应答 | 没有标准低层 ACK；32 拍完成和 `exit=0` 都不证明器件身份正确 | ACK 能提供接收应答证据，但仍要按器件协议检查完整操作和有效数据 |
| 本例怎样验证 | 同时检查工具返回、`EF 40 18`、完整数字帧和必要的模拟条件 | 按 I2C 帧检查地址、ACK、数据和总线状态，不能只凭一次无错误返回定案 |

如果需求需要较高串行带宽、独立全双工路径或明确的片选边界，并且候选器件和控制器都支持 SPI，SPI 更有优势，代价是片选、数据驱动权和板级时序需要单独验证。如果引脚受限、访问较短、多个器件适合共享两条线，并且需要接收方 ACK，I2C 更有吸引力，代价是要处理地址、模式、上拉、总线电容和相应带宽限制。

对本例 W25Q128JV-IQ/JQ，`0x9F` 是其 SPI 命令，不能把这笔事务直接改写为 I2C 地址帧。只有在比较“同样满足功能需求的不同候选器件”，且候选器件本身提供相应接口和命令时，SPI 与 I2C 才构成可执行的替代方案。I2C 的帧与电气机制见 B-B.3.1～B-B.3.2，本页不展开另一套协议细节。

## <span class="blue"> QSPI 与 OSPI 改变分阶段拍数，不抹去前导和忙时间

QSPI（四线 SPI）和 OSPI（八线 SPI）扩展了部分阶段可使用的数据线数。阅读命令时可用 `x-y-z` 依次记录命令、地址和数据阶段的线数；本例 `0x9F` 仍是单线命令、无地址、单线响应，不能因为没有单独的地址阶段就把它改写成“四线读取”。

B-B.4.2 的 [命令变体与协议验证](B-B.4.2_SPI协议层与时序_validation.md) 已给出同一颗 Flash 的具体对照：`0x0B` Fast Read 是 `1-1-1`，读取四字节共 72 拍；`0x6B` Fast Read Quad Output 是 `1-1-4`，命令、24 位地址和 8 拍 dummy 仍占 40 拍，只有数据阶段从 32 拍缩为 8 拍，总计 48 拍。

在各阶段使用同一实际频率的前提下，两者的纯时钟时间关系为：

```text
0x0B：T_clock = 72 / f_actual
0x6B：T_clock = 48 / f_actual
```

数据阶段的位数关系是四倍，整笔读取的理想纯时钟时间却只从 72 拍降到 48 拍。命令、地址、dummy、CS、软件调度和内部忙过程都没有被“四线”自动除以四。OSPI 同理，必须按目标命令逐阶段重新计数；若引入 DDR（Double Data Rate，双倍数据速率），每个时钟边界的位数和时序关系也会变化，不能沿用这里的 SDR 计算。

扩展线数还同时增加三个前提：控制器及其驱动声明并实际支持相应模式，器件命令和状态位满足要求，板级已经连接并验证新增数据线。`0x6B` 就要求 QE（Quad Enable，四线功能使能）位已置 1。Linux v6.6 的 [`spi_setup()`](code/B-B.4.3/kernel-v6.6/drivers/spi/spi.c){: data-code-viewer="true" data-code-title="spi.c" data-code-path="Linux v6.6 · drivers/spi/spi.c" data-code-lines="3719-3758"} 会检查 DUAL、QUAD、OCTAL 等模式组合；当前 Rockchip 驱动声明的 `mode_bits` 并不包含这些扩展，因此不能凭本例普通 SPI 的 JEDEC ID 成功，推断这条路径已经支持 QSPI 或 OSPI。

Flash 页编程、擦除和 BUSY 等待属于另一组命令与内部过程。增加数据线可能缩短写入数据的传输阶段，却不会自动缩短器件内部编程或擦除时间。读写选择应分别计算 `T_clock` 和 `T_busy`，W25Q 的正式产品接入与写路径归 B-B.4.5。

## <span class="blue"> 把候选配置收回同一套验证证据

速率和接口选择最后仍要落到可复测的事务，而不是停在参数表。对本例及后续候选命令，顺序如下：

1. **固定工作负载**：明确是 32 拍 JEDEC ID、其他读取，还是含内部忙过程的写入，分别列出命令、地址、dummy、数据和完成条件。
2. **计算完整时间**：先求各阶段拍数，再用实际 SCLK 计算 `T_clock`，另计 CS、软件、调度和适用的 `T_busy`。
3. **施加共同上限**：核对控制器能力及分频、当前命令的器件限制和板级时序、电气条件；选择 SPI、I2C、QSPI 或 OSPI 时，还要满足各自的接口前提。
4. **一次只改一个条件**：保留请求参数和实际条件，检查工具返回与有效 ID；速率或线数变化后，重新抓取完整数字帧，必要时在接收端测量模拟波形。
5. **按明确判据复测**：有限次数记录每次结果和测试条件。普通 `spidev_test -p` 不自动比较 TX/RX，也不向用户打印实际完成长度，不能只循环命令并统计 `exit=0` 来声称错误率。

若目标仍是本例正常读取，最小成功判据仍是工具正常返回、有效位置得到与器件后缀一致的 `EF 40 18`，并且 32 拍帧和当前速率下的采样条件成立。任何一项没有检查，就应留在未验证项中，而不是由“接口更高级”或“降速后曾成功”补全结论。

## <span class="blue"> 本节总结 [B→I]

SPI 调试从一笔已知答案的正常事务开始，再由软件返回、回环、数字帧和模拟波形逐层缩小范围；恢复接线与配置后重新得到正常 ID，才完成本次调试闭环。选型沿用同一条证据链：先算完整事务，再让控制器、器件和板级条件共同收窄可用速率，任何一次低速成功或高速解码都不能替代完整验证。

SPI 与 I2C 的选择取决于带宽、引脚、片选或地址、ACK、共享负载和器件实际支持，QSPI／OSPI 则必须逐阶段重算线数、拍数和时序。最值得保留的判别方法是：先问这笔操作由哪些阶段组成，再问每项证据究竟证明了其中哪一部分。

## <span class="blue"> 本节自查

??? details "Q1. 为什么本例不能只凭 `exit=0` 宣布 W25Q128JV-IQ/JQ 已正常识别？"
    SPI 没有低层 ACK，工具成功返回不等于器件身份正确。还要检查有效位置的 `RX[1]～RX[3]` 是否为 `EF 40 18`，并确认器件后缀。`RX[0]` 不参与判断，退出 0 也不能证明长期稳定或模拟裕量。

??? details "Q2. 内部回环与外部短接各自能排除什么，为什么都不能代替正常 JEDEC ID 读取？"
    内部回环检查控制器提供的回环配置和传输路径，不覆盖外部引脚与 Flash。外部短接把证据扩展到短接点，但不检查从设备应答。两者结束后都要恢复正常连接并重新读取 JEDEC ID，才能确认回到真实器件的已知事务。

??? details "Q3. 全 `FF` 为什么不能直接等同于 MISO 上拉且从设备未驱动？"
    固定高电平只是其中一种可能。错误 CS、器件未就绪、采样配置、接线、器件实际返回固定数据等也可能产生相同结果。应继续观察完整 CS、SCLK、MOSI、MISO 和软件交付位置，用下一项证据区分候选机制。

??? details "Q4. 线上已经解码出 `EF 40 18`，用户缓冲区却整体错位，应优先检查什么？"
    先检查软件接收长度、前导保留约定和缓冲区偏移，因为数字线上的数据已经正确。本例 JEDEC ID 只有 8 拍命令与 24 拍响应，不应机械套用 Fast Read 的 dummy 或 `RX[5]` 结论。

??? details "Q5. 为什么 `F7 02 18` 只能提示位序问题，不能直接定案？"
    它恰好是 `EF 40 18` 的逐字节位序反转，但普通通信中的数据还受其他机制影响。需要用已知发送数据的内部回环或隔离后的外部短接验证位序路径，再核对器件手册，不能靠一次模式切换后“看起来合理”来定案。

??? details "Q6. 降速后恢复 `EF 40 18`，下一步为什么还要看数字帧和模拟波形？"
    降速只证明故障与频率或时间窗口相关。逻辑分析仪用于确认 32 拍和有效数据是否仍正确，示波器用于检查接收端门限、边沿和采样窗口；两者结合后才能区分钟格式、输出有效、传播、建立时间和信号质量问题。

??? details "Q7. 为什么普通 `while true; do spidev_test -p ...; done` 不能直接统计错误率？"
    普通 `-p` 路径不会自动比较 TX/RX，工具也不向用户打印实际完成长度。没有逐次检查有效 ID、返回结果和测试条件，就无法区分成功与失败。统计必须使用有限次数和明确判据，并保留失败记录。

??? details "Q8. 本例在 1 MHz 请求下的 32 μs 是怎样得到的，为什么不能直接把它当成实测事务耗时？"
    `0x9F` 命令和三个 ID 字节共 32 拍；只有实际 SCLK 恰好为 1 MHz 时，`N/f_actual` 才等于 32 μs。用户态读回的 `max speed` 不是实际位率，完整操作还包括 CS、软件和调度等开销，因此 32 μs 只是算术结果，不是实测总耗时。

??? details "Q9. 选择 SPI 或 I2C 时，为什么不能只比较“速度”和“线数”？"
    还要比较器件是否实际支持、完整命令格式、CS 或地址分配、全双工需求、ACK、共享负载和板级限制。SPI 的 32 拍完成不提供低层 ACK，I2C 的地址与 ACK 也不免除完整数据验证；对本例 Flash 还不能把 SPI 命令直接换成 I2C 帧。

??? details "Q10. 为什么 `0x6B` 的四线数据阶段不能把整笔读取直接说成提速四倍，BUSY 又为什么要另算？"
    `0x6B` 只把四字节数据阶段从 32 拍缩为 8 拍，40 拍单线前导不变，所以整笔从 72 拍降为 48 拍，而不是全部除以四。dummy 是读取命令的固定前导，BUSY 是编程或擦除的内部完成状态，两者及各自耗时不能互相替代。
