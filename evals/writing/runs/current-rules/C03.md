# 组织传输请求

> 所属章节：第五部 B. 总线协议 > B-B.4 SPI 总线 > B-B.4.3 SPI Linux 驱动框架
>
> 本组阅读：第 3 页，共 6 页

上一页已经让匹配的 `spi_device` 进入 probe，但它只代表“这颗外设可以被驱动访问”，还没有描述一次具体读取。现在要从地址 `0x001234` 读出 4 字节：驱动需要先说明发送什么、在哪里接收，再把请求交给 SPI Core，并在结束后判断结果、释放资源。

本页只回答一个问题：**两个 `spi_transfer`、缓冲区和 `spi_message` 怎样组织一笔读取，并在成功或失败后正确返回？**

---

## <span class="blue"> 把 72 拍拆成 5＋4 字节

本例是受控 W25Q128JV 教学环境中的 Fast Read，不是所有 SPI 器件通用的读命令。外设协议驱动要完成的事务有明确输入和输出：输入是 24 位地址 `0x001234`，输出是从该地址开始的 4 个数据字节。

按 8 位字长计算，线上顺序如下：

1. 发送命令字节 `0x0b`，占 8 拍。
2. 发送 24 位地址，占 24 拍。
3. 发送 1 个 dummy 字节，提供器件要求的 8 个空位时钟。
4. 继续提供 32 拍，同时接收 4 个数据字节。

前 5 个字节是命令、地址和 dummy，后 4 个字节用于接收数据，总共交换 9 字节，也就是 **72 拍**。SPI 全双工意味着每个时钟都同时移出和移入一位；两段的区别不在于是否产生时钟，而在于驱动是否保存该方向的数据。

这个线上顺序可以直接映射为两个描述符：第一段持有 5 字节发送缓冲区，不保存同时移入的数据；第二段持有 4 字节接收缓冲区，发送侧由 Core 补零。它们必须属于同一笔事务，否则命令前导和数据阶段可能被拆成器件无法识别的两次访问。

> `spi_transfer`：一段具有独立缓冲区和长度的传输描述。`tx_buf` 非空而 `rx_buf` 为空时，同时移入的数据被丢弃；`tx_buf` 为空而 `rx_buf` 非空时，移出零并保存同时移入的数据。第二种情况仍会正常产生 SCLK。

<!-- -->

> `spi_message`：按顺序执行的一组 transfer。Core 把它作为一次总线事务调度，并记录总长度、实际完成长度和最终状态。未用 `cs_change` 主动改变片选时，CS 通常保持有效到最后一段结束，其他 message 不会插入这段序列。

这两个对象的接口约定可在 [`include/linux/spi/spi.h:901-916`](code/B-B.4.3/kernel-v6.6/include/linux/spi/spi.h){: data-code-viewer="true" data-code-title="spi.h" data-code-path="Linux v6.6 · include/linux/spi/spi.h" data-code-lines="901-916"}、[`include/linux/spi/spi.h:919-1071`](code/B-B.4.3/kernel-v6.6/include/linux/spi/spi.h){: data-code-viewer="true" data-code-title="spi.h" data-code-path="Linux v6.6 · include/linux/spi/spi.h" data-code-lines="919-1071"} 和 [`include/linux/spi/spi.h:1073-1148`](code/B-B.4.3/kernel-v6.6/include/linux/spi/spi.h){: data-code-viewer="true" data-code-title="spi.h" data-code-path="Linux v6.6 · include/linux/spi/spi.h" data-code-lines="1073-1148"} 回查。头文件还明确要求：message 排队使用期间，提交者必须保证 message、transfer 和数据缓冲区都持续有效。

## <span class="blue"> 按执行顺序建立请求

读取函数需要同时管理两类内存：`message` 和 `transfers` 是描述“怎样传”的栈上描述符，`tx_buf` 和 `rx_buf` 是保存“传什么、收到什么”的堆缓冲区。先用下面的骨架记住这条主线，随后每一段都按函数实际执行顺序展开；完整函数和完整模块在页末统一回查。

```c
// spi_frame_observer.c · spi_frame_observer_read() 的结构骨架，不是独立代码段
static int spi_frame_observer_read(struct spi_device *spi, u32 address,
                                   u8 *data)
{
    struct spi_transfer transfers[2] = { };
    struct spi_message message;
    u8 *tx_buf;
    u8 *rx_buf;
    int ret;

    // 检查地址，分配并填写缓冲区
    // 设置两个 transfer，按顺序加入 message
    // spi_sync() 同步提交
    // 检查返回值和 actual_length，正常时复制 4 字节
    // 成功与失败共用缓冲区释放出口
}
```

`transfers[2] = { }` 将两个描述符全部清零。这样，未显式设置的 `speed_hz`、`bits_per_word` 和 `cs_change` 都保持 0：速度和字长继承 `spi_device` 的配置，第一段结束后不主动切换 CS。`message` 则由专用的初始化函数处理，不能只声明后直接使用。

### 先分配数据缓冲区，失败时还不能提交

地址超过 24 位时，本例在分配前返回 `-EINVAL`。地址合法后才分配两个缓冲区：

```c
// spi_frame_observer.c · spi_frame_observer_read() 节选：参数检查与分配
if (address > 0xffffff)
    return -EINVAL;

/* kmalloc 族缓冲区可由 SPI Core 按控制器需要进行 DMA 映射。 */
tx_buf = kzalloc(OBSERVER_CMD_LEN, GFP_KERNEL);
rx_buf = kzalloc(OBSERVER_DATA_LEN, GFP_KERNEL);
if (!tx_buf || !rx_buf) {
    ret = -ENOMEM;
    goto out_free;
}
```

`kzalloc()` 分配并清零内核内存，`GFP_KERNEL` 表示分配过程允许睡眠，符合本例从 probe 同步调用的上下文。使用 `kmalloc` 族缓冲区，是为了满足 transfer 对可 DMA 映射内存的要求；不要把未说明这些约束的局部数组直接交给底层。

两个分配必须都成功。若其中一个失败，函数记录 `-ENOMEM` 并跳到 `out_free`；`kfree(NULL)` 是安全的，所以同一出口既能释放已经成功的那个缓冲区，也能处理另一个空指针。此时尚未调用 `spi_sync()`，Core 没有持有这些对象。

### 把 5＋4 字节分别写入两个 transfer

分配成功后，发送缓冲区先得到 Fast Read 的完整前导：

```c
// spi_frame_observer.c · spi_frame_observer_read() 节选：填写本例的 5＋4 字节
tx_buf[0] = 0x0b;
tx_buf[1] = (address >> 16) & 0xff;
tx_buf[2] = (address >> 8) & 0xff;
tx_buf[3] = address & 0xff;
tx_buf[4] = 0x00;              /* 8 个 dummy 时钟 */

transfers[0].tx_buf = tx_buf;
transfers[0].len = OBSERVER_CMD_LEN;
transfers[1].rx_buf = rx_buf;
transfers[1].len = OBSERVER_DATA_LEN;
```

当 `address` 为 `0x001234` 时，`tx_buf` 的 5 字节依次是 `0b 00 12 34 00`。移位和掩码把 24 位地址拆成线上需要的三个独立字节，最后一个零字节对应 dummy 阶段。

`transfers[0]` 只设置 `tx_buf` 和 `len = 5`，因此前 40 拍发送前导，同时移入的 5 字节被丢弃。`transfers[1]` 只设置 `rx_buf` 和 `len = 4`，因此后 32 拍由 Core 在发送侧补零，并把同时移入的 4 字节写入 `rx_buf`。两个 `len` 合起来仍是 9 字节，而不是只传输接收方向的 4 字节。

### 初始化 message，再按前导、数据的顺序追加

描述符和缓冲区就绪后，才把两段挂入同一 message：

```c
// spi_frame_observer.c · spi_frame_observer_read() 节选：组织并提交请求
spi_message_init(&message);
spi_message_add_tail(&transfers[0], &message);
spi_message_add_tail(&transfers[1], &message);

/* 同步返回前，栈上的 message 和 transfers 始终有效。 */
ret = spi_sync(spi, &message);
```

[`spi_message_init()`](code/B-B.4.3/kernel-v6.6/include/linux/spi/spi.h){: data-code-viewer="true" data-code-title="spi.h" data-code-path="Linux v6.6 · include/linux/spi/spi.h" data-code-lines="1150-1166"} 先清零整个 message，再初始化 transfer 链表和资源链表。`spi_message_add_tail()` 把 transfer 的 `transfer_list` 节点追加到 message 末尾，因此本例执行顺序固定为 5 字节前导、4 字节数据接收。

`spi_sync(spi, &message)` 的 `spi` 仍是上一页进入 probe 的同一个 `spi_device`，所以提交目标没有改变；新增的只是本次读取的描述符和缓冲区。同步提交会睡眠等待事务完成，返回前当前函数不会退出，栈上的 `message` 和 `transfers` 因而一直有效，两个堆缓冲区也尚未释放。若改用 `spi_async()`，就必须把这些对象的生命期延长到完成回调之后，不能沿用这里的栈上描述符和立即释放方式。

## <span class="blue"> 分别判断返回值、完成长度和数据

`spi_sync()` 返回只说明请求已经结束，还不能直接推出 4 字节结果有效。本例连续检查三个不同对象：

```c
// spi_frame_observer.c · spi_frame_observer_read() 节选：结果判断与统一释放
ret = spi_sync(spi, &message);
if (ret < 0)
    goto out_free;

if (message.actual_length != OBSERVER_CMD_LEN + OBSERVER_DATA_LEN) {
    ret = -EIO;
    goto out_free;
}

memcpy(data, rx_buf, OBSERVER_DATA_LEN);

out_free:
    kfree(rx_buf);
    kfree(tx_buf);
    return ret;
```

第一层是 `ret`。v6.6 的同步传输接口约定为 **0 表示成功，负值表示错误**，不是返回传输字节数。负错误出现时直接走释放出口，不复制接收缓冲区，也不能把其中内容当成有效读取结果。同步接口的睡眠语义和返回值说明见 [`include/linux/spi/spi.h:1341-1364`](code/B-B.4.3/kernel-v6.6/include/linux/spi/spi.h){: data-code-viewer="true" data-code-title="spi.h" data-code-path="Linux v6.6 · include/linux/spi/spi.h" data-code-lines="1341-1364"}。

第二层是 `message.actual_length`。头文件将它定义为所有成功段累计完成的字节数，本例完整成功时应为 `5 + 4 = 9`。若返回值为 0 但完成长度不是 9，教学代码把这种情况转换为 `-EIO`，避免把不完整事务当成完整数据。

第三层才是 `rx_buf` 中的数据。只有 `ret == 0` 且 `actual_length == 9`，函数才用 `memcpy()` 把 4 字节复制到调用者的 `data` 数组。这里的 9 是事务总长度，不是有效负载长度；最终交给调用者的仍然只有 4 字节。

无论在哪条路径离开，两个堆缓冲区都在返回前释放；栈上的 message 和 transfer 随函数返回自然失效，不需要也不能对它们调用 `kfree()`。释放不再被 Core 使用的内存，不等于撤销已经发生的总线传输：失败或短传输时，已执行到哪一段只能由返回值、完成长度和下层状态继续判断，不能凭缓冲区内容反推。

## <span class="blue"> 完整模块把读取接回 probe 和 remove

前面的片段都属于 `spi_frame_observer_read()`。下面的完整模块恢复它的调用上下文：probe 用同一地址发起读取，失败时把负错误码返回设备模型，成功时才打印 4 字节；remove 只记录解绑，因为传输缓冲区早已在读取函数出口释放。

这是本篇原创教学代码，面向 Linux v6.6 外设协议驱动模型，不是 Rockchip 控制器驱动或 spi-nor 源码节选，也不提供产品级 Flash 管理。模块加载后，设备匹配触发 probe，probe 在可睡眠上下文同步执行一次只读 Fast Read。

配套完整源码：[`spi_frame_observer.c`](code/B-B.4.3/spi_frame_observer.c){: data-code-viewer="true" data-code-title="spi_frame_observer.c" data-code-path="本篇教学配套 · code/B-B.4.3/spi_frame_observer.c"}。

```c
// SPDX-License-Identifier: GPL-2.0
/*
 * Linux v6.6 SPI framework teaching example.
 *
 * This is a read-only protocol observer for a controlled W25Q128JV setup.
 * It is not a replacement for the in-kernel spi-nor/MTD driver stack.
 */
#include <linux/errno.h>
#include <linux/module.h>
#include <linux/of.h>
#include <linux/slab.h>
#include <linux/spi/spi.h>
#include <linux/string.h>

#define OBSERVER_CMD_LEN  5
#define OBSERVER_DATA_LEN 4

static int spi_frame_observer_read(struct spi_device *spi, u32 address,
				   u8 *data)
{
	struct spi_transfer transfers[2] = { };
	struct spi_message message;
	u8 *tx_buf;
	u8 *rx_buf;
	int ret;

	if (address > 0xffffff)
		return -EINVAL;

	/* kmalloc-family buffers can be mapped by the SPI core if DMA is used. */
	tx_buf = kzalloc(OBSERVER_CMD_LEN, GFP_KERNEL);
	rx_buf = kzalloc(OBSERVER_DATA_LEN, GFP_KERNEL);
	if (!tx_buf || !rx_buf) {
		ret = -ENOMEM;
		goto out_free;
	}

	/* Fast Read: opcode, 24-bit address, then eight dummy clocks. */
	tx_buf[0] = 0x0b;
	tx_buf[1] = (address >> 16) & 0xff;
	tx_buf[2] = (address >> 8) & 0xff;
	tx_buf[3] = address & 0xff;
	tx_buf[4] = 0x00;

	/* Segment 0 sends the command and ignores simultaneous MISO data. */
	transfers[0].tx_buf = tx_buf;
	transfers[0].len = OBSERVER_CMD_LEN;

	/* Segment 1 shifts out zeroes and captures four simultaneous MISO bytes. */
	transfers[1].rx_buf = rx_buf;
	transfers[1].len = OBSERVER_DATA_LEN;

	spi_message_init(&message);
	spi_message_add_tail(&transfers[0], &message);
	spi_message_add_tail(&transfers[1], &message);

	/* Stack-held message/transfer descriptors live until spi_sync returns. */
	ret = spi_sync(spi, &message);
	if (ret < 0)
		goto out_free;

	if (message.actual_length != OBSERVER_CMD_LEN + OBSERVER_DATA_LEN) {
		ret = -EIO;
		goto out_free;
	}

	memcpy(data, rx_buf, OBSERVER_DATA_LEN);

out_free:
	kfree(rx_buf);
	kfree(tx_buf);
	return ret;
}

static int spi_frame_observer_probe(struct spi_device *spi)
{
	u8 data[OBSERVER_DATA_LEN] = { };
	int ret;

	dev_info(&spi->dev,
		 "matched: cs=%u, mode=0x%x, max_speed_hz=%u, bits_per_word=%u\n",
		 spi->chip_select, spi->mode, spi->max_speed_hz,
		 spi->bits_per_word);

	ret = spi_frame_observer_read(spi, 0x001234, data);
	if (ret < 0) {
		dev_err(&spi->dev, "fast_read failed: ret=%d\n", ret);
		return ret;
	}

	dev_info(&spi->dev,
		 "fast_read: ret=0, addr=0x001234, data=%02x %02x %02x %02x\n",
		 data[0], data[1], data[2], data[3]);

	return 0;
}

static void spi_frame_observer_remove(struct spi_device *spi)
{
	dev_info(&spi->dev, "unbound\n");
}

static const struct of_device_id spi_frame_observer_of_match[] = {
	{ .compatible = "kimi,spi-frame-observer" },
	{ }
};
MODULE_DEVICE_TABLE(of, spi_frame_observer_of_match);

static struct spi_driver spi_frame_observer_driver = {
	.driver = {
		.name = "spi_frame_observer",
		.of_match_table = spi_frame_observer_of_match,
	},
	.probe = spi_frame_observer_probe,
	.remove = spi_frame_observer_remove,
};
module_spi_driver(spi_frame_observer_driver);

MODULE_AUTHOR("Embedded Knowledge System V2026");
MODULE_DESCRIPTION("Read-only SPI framework teaching observer");
MODULE_LICENSE("GPL");
```

正常路径中，probe 得到 `ret = 0`，打印地址和实际收到的 4 字节，再返回 0 完成绑定。错误路径中，probe 打印 `fast_read failed: ret=<负错误码>` 并返回同一个错误，驱动绑定因此失败；它不会打印一次并未成功的数据结果。`module_spi_driver()` 只生成模块注册、注销所需的驱动生命周期样板，`MODULE_DEVICE_TABLE(of, ...)` 导出设备树匹配表，二者都不改变本例的 72 拍帧格式。

验证时要区分四类证据：本页已用指定 v6.6 头文件和配套源码核对字段、顺序与接口语义；模块编译、目标板运行和仪器测量是另外三项检查，不能由源码核对替代。目标运行时应看到成功返回、9 字节完成长度和 4 字节结果相互一致，但具体数据值由器件当前内容决定，不能预设成固定样本；若要确认 72 拍及 CS 连续有效，还需要逻辑分析仪等外部观测。

## <span class="blue"> 本页总结

一笔 SPI 读取的代码组织应与线上顺序一致：先用 transfer 描述各段方向和长度，再把它们按序加入 message，最后同步提交。`spi_sync()` 的返回值、`actual_length` 和接收数据必须分别检查，任何一个都不能替代另外两个。同步调用让栈上描述符可以安全使用到返回，但所有堆缓冲区仍需在成功、失败和短传输路径上统一释放。

## <span class="blue"> 本页自查

??? details "Q3. 为什么本例的第二段只设置 `rx_buf`，却仍会占用 32 拍？"

    SPI 每段始终同时移入和移出相同数量的数据。`tx_buf == NULL` 时，Core 的语义是移出零并填充 `rx_buf`，不是停止 SCLK。第二段长度是 4 字节，按 8 位字长计算就是 32 拍；加上第一段的 40 拍，整笔事务共 72 拍。

??? details "Q4. 一笔成功读取的返回值、`actual_length` 和有效数据长度分别是多少？"

    `spi_sync()` 成功返回 0，不返回 9。两段长度分别为 5 和 4，全部成功后 `message.actual_length` 为 9。教学代码只有在返回值为 0 且完成长度为 9 时才复制接收缓冲区，复制给调用者的有效数据长度是 4 字节。

??? details "Q5. 第二个缓冲区分配失败，或者同步提交返回负错误时，资源怎样释放？"

    两种情况都进入 `out_free`。分配失败时，`kfree()` 可以安全处理空指针，因此已成功的分配不会泄漏；提交失败时，同步调用已经结束，两个缓冲区同样可以释放。两条路径都不会把 `rx_buf` 复制成有效结果，栈上的 message 和 transfer 则随函数返回自然失效。
