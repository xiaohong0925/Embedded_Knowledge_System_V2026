# spi_sync 之后：Core 和 Rockchip 各做什么

## <span class="blue"> 沿同一笔双段事务进入源码

上一页构造的 message 保持不变：第一段发送 `0x0b 0x12 0x34 0x00`，长度 5 字节；第二段接收 4 字节。两段都没有单独设置 `speed_hz`、`bits_per_word` 和 `cs_change`，因此本页可以继续观察 Core 怎样补默认值、维持一次片选，并把两个分段收束成一次同步返回。

这条执行路同时经过通用框架和硬件适配层：

```text
spi_sync
└─ __spi_sync
   ├─ __spi_validate
   ├─ 直接执行：__spi_transfer_message_noqueue
   └─ 排队等待：spi_async_locked → 控制器消息队列
                  ↓
        __spi_pump_transfer_message
                  ↓
        spi_transfer_one_message（Core 默认实现）
                  ↓
        rockchip_spi_transfer_one（每个 transfer）
                  ↓
        中断或 DMA 完成 → spi_finalize_current_transfer
                  ↓
        spi_finalize_current_message → spi_sync 返回
```

这里的分工不能颠倒：Core 管理 message、分段顺序、默认 CS 策略和完成语义；Rockchip 驱动把当前 transfer 翻译成寄存器、FIFO、中断或 DMA 操作。`spi_sync()` 的返回值最终来自这条路的执行结果，不是传输字节数。

### 校验先补齐分段参数，不合法时不会进入硬件执行

`spi_sync()` 先获取控制器的 `bus_lock_mutex`。这是控制器级互斥锁，用于保护这次同步调用所经过的总线访问路径；随后进入 `__spi_sync()`，第一步调用 `__spi_validate()`。

`__spi_validate()` 不是只检查指针。它拒绝空 transfer 链表，检查半双工和收发方向限制，为未显式设置的 `bits_per_word`、`speed_hz` 填入设备默认值，再检查控制器字长能力、速度范围和传输长度是否为完整字。它还为未指定的 `tx_nbits`、`rx_nbits` 选择单线默认值，并在校验末尾把 `message->status` 置为 `-EINPROGRESS`，表示消息已经进入执行语义但尚未完成。

对本例而言，两段都没有逐段覆盖设备参数，所以真正生效的字长和速度来自 `spi_device`，并受控制器上下限约束。按本例的 8 位字长推演，一个字占 1 字节，5 和 4 都是完整字数；如果设备使用其他字长，仍须以同一条整除规则判断，不能只看字节数大小。

校验失败时，`__spi_sync()` 直接返回负错误码，尚未进入消息准备、CS 选中或 Rockchip 寄存器配置。此时也不能从一次提交失败推断接收缓冲区里出现了有效数据。

### 调度有直接执行和排队等待两条路

校验通过后，`__spi_sync()` 根据控制器队列状态选择路径。关键结构如下，代码为 `drivers/spi/spi.c` 中 `__spi_sync()` 的节选，省略号不参与执行：

```c
if (READ_ONCE(ctlr->queue_empty) && !ctlr->must_async) {
    message->actual_length = 0;
    message->status = -EINPROGRESS;

    __spi_transfer_message_noqueue(ctlr, message);
    return message->status;
}

message->complete = spi_complete;
message->context = &done;
status = spi_async_locked(spi, message);
if (status == 0) {
    wait_for_completion(&done);
    status = message->status;
}
message->context = NULL;
```

> noqueue：不先把当前 message 放入异步队列，而由当前调用路径直接驱动控制器执行。它只改变调度方式，不改变 `spi_sync()` 等待最终状态的语义。

队列为空且控制器没有强制异步要求时，直接路径把 `actual_length` 清零，再调用 `__spi_transfer_message_noqueue()`。该函数取得 `io_mutex`，把消息设为控制器当前消息，并进入共同的消息准备与执行函数。

队列中已有消息时，同步调用必须保持先前排队的访问顺序。Core 给 message 安装内部完成回调 `spi_complete`，通过 `spi_async_locked()` 排队；提交成功后，当前线程等待栈上的完成对象。排队路径同样在真正入队前把 `actual_length` 清零并设置 `-EINPROGRESS`。若排队提交本身失败，则不会进入这次等待，负错误直接成为同步调用的结果。

> ⚠️ `spi_sync()` 只能在可睡眠上下文使用。源码明确说明整体同步等待不可中断且没有超时；后文出现的单次 transfer 等待超时是 Core 默认逐段实现中的另一层保护，二者不能混为一谈。

### 共同入口准备资源，Core 默认实现逐段推进

两条调度路径最终都进入 `__spi_pump_transfer_message()`。它按控制器能力拆分过长的 transfer，执行可选的消息准备回调，并映射 DMA 缓冲区。随后调用 `ctlr->transfer_one_message()`；如果控制器驱动没有提供自己的整消息实现，Core 在初始化队列时安装默认的 `spi_transfer_one_message()`。

Rockchip 没有替换这个整消息遍历函数。它在 probe 中注册的是 `set_cs`、`transfer_one` 和 `handle_err`，入口见 [`drivers/spi/spi-rockchip.c:876-881`](code/B-B.4.3/kernel-v6.6/drivers/spi/spi-rockchip.c){: data-code-viewer="true" data-code-title="spi-rockchip.c" data-code-path="Linux v6.6 · drivers/spi/spi-rockchip.c" data-code-lines="876-881"}。因此，本例仍由 Core 决定先执行 5 字节前导段、再执行 4 字节接收段，Rockchip 每次只接到当前那一段。

默认 `spi_transfer_one_message()` 先选中目标设备，然后沿 transfer 链表执行。每个有缓冲区且长度非零的分段都遵循同一组判断：

```c
/* drivers/spi/spi.c：spi_transfer_one_message() 节选 */
reinit_completion(&ctlr->xfer_completion);
ret = ctlr->transfer_one(ctlr, msg->spi, xfer);
if (ret < 0) {
    /* 错误统计与日志从略。 */
    goto out;
}

if (ret > 0) {
    ret = spi_transfer_wait(ctlr, msg, xfer);
    if (ret < 0)
        msg->status = ret;
}

if (msg->status != -EINPROGRESS)
    goto out;

msg->actual_length += xfer->len;
```

`transfer_one()` 的返回值不是已传输长度。按照 `spi_controller` 的接口约定，0 表示该 transfer 已完成，1 表示硬件仍在执行；返回 1 的驱动必须在完成后调用 `spi_finalize_current_transfer()`。Core 看到正值时等待本次分段完成，只有消息仍为 `-EINPROGRESS` 才把当前 `xfer->len` 累加到 `actual_length`。

所以，本例第一段正常完成后 `actual_length` 为 5，第二段正常完成后才变为 9。若第一段失败，不会执行第二段；若第二段失败，已经记录的第一段长度仍是 5，但这不等于整笔 Fast Read 成功。

### Rockchip 把当前分段配置成真实硬件操作

`rockchip_spi_transfer_one()` 先处理当前 transfer 的边界条件，再决定硬件执行方式。它拒绝收发缓冲区同时为空的调用，拒绝超过控制器上限的长度，保存当前 transfer，并根据字长计算每个字占用的字节数。随后调用 `rockchip_spi_config()`，最后进入 DMA 或中断驱动路径：

```c
/* drivers/spi/spi-rockchip.c：rockchip_spi_transfer_one() 节选 */
rs->n_bytes = xfer->bits_per_word <= 8 ? 1 : 2;
rs->xfer = xfer;
use_dma = ctlr->can_dma ? ctlr->can_dma(ctlr, spi, xfer) : false;

ret = rockchip_spi_config(rs, spi, xfer, use_dma, ctlr->target);
if (ret)
    return ret;

if (use_dma)
    return rockchip_spi_prepare_dma(rs, ctlr, xfer);

return rockchip_spi_prepare_irq(rs, ctlr, xfer);
```

`rockchip_spi_config()` 把软件描述翻译成控制器设置：根据 `spi->mode` 配置时钟模式、位序和 CS 极性，根据收发缓冲区选择传输方向，根据 `bits_per_word` 设置字长，并用 `xfer->len` 得出本次传输字数。它还设置 FIFO 阈值和波特率寄存器。波特率除数向上取到偶数，使实际频率不高于请求频率；这说明设备或 transfer 中的 `speed_hz` 是配置输入，不是对引脚实测频率的证明。

> FIFO：控制器内部暂存收发数据的小容量硬件队列。CPU 可以往发送 FIFO 写字、从接收 FIFO 读字，不必为每个字都启动一次独立 message。

DMA 即直接内存访问，适合让硬件在内存与控制器之间搬运数据，但本驱动有明确启用条件。probe 只有在 TX、RX 两个 DMA 通道都请求成功时才注册 `can_dma`；`rockchip_spi_can_dma()` 再判断 `xfer->len / bytes_per_word >= rs->fifo_len`。因此选择依据是**字数、运行时 FIFO 深度和 DMA 通道可用性**，不是通用的“几十字节就用 DMA”规则。本页不预写本例上板时的实际选择结果。

中断驱动路径由 `rockchip_spi_prepare_irq()` 保存收发指针和剩余字数，使能控制器并打开接收 FIFO 中断，然后返回 1。中断服务函数 `rockchip_spi_isr()` 按需继续写发送 FIFO，并从接收 FIFO 取字：当前段没有 `rx_buf` 时，读出的字被丢弃；有 `rx_buf` 时，数据按字长写入接收缓冲区。`rx_left` 归零后，它关闭控制器、屏蔽并清除相关中断，再调用 `spi_finalize_current_transfer()`。

DMA 路径为收发方向准备描述符，先启动接收再启动发送。对应回调在所需方向结束后关闭控制器并通知 Core；发送侧完成时还会等待控制器退出忙状态。描述符准备失败会返回负错误，发送描述符失败时还会终止已经准备的接收通道。无论选择哪条硬件路径，**分段完成通知都不是整笔 message 已经完成**。

### CS 由 Core 按 message 边界和分段字段决定

CS 是片选信号，用来选中当前参与通信的从设备。本例两段的 `cs_change` 都保持零值，Core 的正常路径因此是：

1. 进入 transfer 循环前，按第一段的 `cs_off` 选中设备。
2. 第一段完成后，不主动撤销选中，直接推进第二段。
3. 第二段完成且没有末段保持选中要求时，在消息出口撤销选中。

Flash 因而把 5 字节前导和 4 字节接收看作同一笔命令。撤销选中是逻辑状态，不应固定写成“拉高”；实际电平还受 `SPI_CS_HIGH` 和 GPIO 描述符极性影响。Rockchip 的 `set_cs` 回调负责把 Core 的逻辑选择落实到硬件片选状态，见 [`drivers/spi/spi-rockchip.c:242-273`](code/B-B.4.3/kernel-v6.6/drivers/spi/spi-rockchip.c){: data-code-viewer="true" data-code-title="spi-rockchip.c" data-code-path="Linux v6.6 · drivers/spi/spi-rockchip.c" data-code-lines="242-273"}。

`cs_change = 1` 必须按分段位置解释：

- 在非末段设置时，Core 在段间短暂撤销选中，执行规定延时后再恢复选中。它会切断本例所需的连续命令边界，普通 Fast Read 不应这样设置。
- 在末段设置时，默认实现把 `keep_cs` 置为真。成功出口可以保留选中状态，供后续操作继续组成更大的器件事务，所以“message 结束必定撤销选中”不是不变量。
- 执行出错时，出口条件包含 `ret != 0`。即使末段要求保持选中，错误路径仍会撤销选中。

### 完成通知分两层，错误沿 message 状态返回

第一层是 transfer 完成。Rockchip 的中断或 DMA 路径调用 `spi_finalize_current_transfer()`，它只完成控制器的 `xfer_completion`，唤醒默认 Core 中等待当前分段的 `spi_transfer_wait()`。等待成功后，Core 才能累加本段长度并处理下一段。

对于控制器主模式，`spi_transfer_wait()` 还会根据分段长度和速度计算等待时间，并增加容差；超时返回 `-ETIMEDOUT`。这个负值写入 `message->status` 后，当前 message 停止推进。它只能说明 Core 没有在期限内收到分段完成通知，不能据此断言硬件已经完成或接收数据有效。

第二层是 message 收尾。`spi_finalize_current_message()` 解除缓冲区映射、释放传输拆分资源、执行可选的逆向准备回调，并清理当前消息状态。若 message 安装了 `complete`，它在收尾末尾调用该回调。排队同步路径的回调是 `spi_complete`，它唤醒 `__spi_sync()` 中的等待者；直接路径没有依赖这个外部回调，而是在直接执行结束后读取同一个 `message->status`。

正常与失败路径可以收束为以下结果：

| 本例到达的位置 | `spi_sync()` 结果 | `actual_length` | 后续动作与数据边界 |
|---|---:|---:|---|
| 两段都成功 | 0 | 9 | 默认撤销 CS；调用者检查长度后复制 4 字节接收结果 |
| 提交校验失败 | 负错误码 | 不能据此推断有效完成量 | 未进入本消息的硬件执行，不复制接收结果 |
| 第一段执行失败 | 负错误码 | 0 | 跳到消息出口，撤销 CS，不执行第二段 |
| 第二段执行失败或等待超时 | 负错误码 | 5 | 第一段长度保留，但整笔读取失败，不把 4 字节缓冲区当作有效结果 |

执行阶段的负错误进入默认消息出口时，Core 在仍为 `-EINPROGRESS` 的情况下把 `ret` 写入 `message->status`，随后撤销 CS；若控制器注册了 `handle_err`，还要执行控制器级错误处理。Rockchip 的处理函数关闭控制器、屏蔽并清除中断，并终止仍在活动的 DMA 通道，源码见 [`drivers/spi/spi-rockchip.c:275-294`](code/B-B.4.3/kernel-v6.6/drivers/spi/spi-rockchip.c){: data-code-viewer="true" data-code-title="spi-rockchip.c" data-code-path="Linux v6.6 · drivers/spi/spi-rockchip.c" data-code-lines="275-294"}。之后 Core 仍执行消息收尾和完成通知，让同步调用者拿到负错误，而不是永久停留在等待中。

上一页的教学代码因此同时检查两件事：`ret == 0` 表示框架报告事务成功，`actual_length == 9` 表示预期的两段都计入完成长度。长度不符由调用者转换成 `-EIO`；只有两项都满足，才把 `rx_buf` 复制为读取结果。失败路径不伪造数据，并照常释放两个堆缓冲区。

如果改用 `spi_async()`，返回 0 只表示请求已被接受，最终成败仍要看完成回调中的 `message->status`。v6.6 约定该回调在不能睡眠的上下文执行，不能直接等同为硬中断上下文；message、transfer 和缓冲区也必须一直有效到回调结束。

## <span class="blue"> 本页自查

??? details "Q5. 为什么不能把“message 结束 CS 必定拉高”当作不变量？"

    默认成功路径通常在 message 完成后撤销选中，但末段 `cs_change = 1` 会设置 `keep_cs`，允许设备保持选中到后续操作。非末段的 `cs_change = 1` 则用于段间短暂撤销并恢复选中。撤销选中也不等于固定拉高，实际电平取决于片选极性。

??? details "Q6. 第一段的 5 字节已经完成，为什么第二段失败后仍不能把整笔读取当作部分成功？"

    第一段成功时 `actual_length` 已累加为 5；第二段出错后，Core 停止推进并返回负错误，长度保持为 5。这个值只说明哪些分段被 Core 记为完成，不改变 Fast Read 需要完整前导和 4 字节数据的要求，因此调用者仍须放弃本次接收结果。

??? details "Q7. Rockchip 是否直接实现了默认 `transfer_one_message()`，DMA 又由什么条件决定？"

    v6.6 的 Rockchip 驱动设置的是 `ctlr->transfer_one = rockchip_spi_transfer_one`，默认 message 遍历仍由 Core 完成。只有 TX、RX DMA 通道都可用时才注册 `can_dma`，随后按传输字数与运行时 `fifo_len` 的关系判断是否使用 DMA，不能套用通用字节阈值。

??? details "Q8. `spi_finalize_current_transfer()` 和 `spi_finalize_current_message()` 分别唤醒哪一层？"

    前者表示当前 transfer 完成，使 Core 的逐段等待继续运行；它不代表后续分段已经执行。后者负责整笔 message 的解映射、资源释放和完成回调。排队同步路径由这个回调唤醒 `__spi_sync()`，调用者随后取得最终的 `message->status`。
