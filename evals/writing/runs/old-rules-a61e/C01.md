# B-B.4.3 SPI Linux 驱动框架

>
> 难度：[I] Intermediate

## <span class="blue"> 本节导读

B-B.4.2 已经把一笔 W25Q128JV Fast Read 拆成确定的线上字节：主机发送 `0B 00 12 34 00`，再提供读取 4 字节所需的时钟。本节继续追问同一笔操作在 Linux 中的完整路径：**设备树怎样变成一个可供驱动使用的设备对象，外设驱动怎样描述两段传输，SPI Core 和 RK3568 控制器驱动怎样执行它，结果或错误又怎样回到调用者。**

贯穿实例仍是 RK3568 SPI1、W25Q128JV-IQ/JQ、Mode 0、8 位、MSB-first、低有效 CS。事务固定为：

```text
地址 0x001234 的 Fast Read
第一段 TX：0B 00 12 34 00       长度 5 字节
第二段 RX：D0 D1 D2 D3           长度 4 字节
成功时 actual_length：9 字节
```

`D0～D3` 是 Flash 当前地址中的内容，不由 SPI 框架决定。后文用 `A7 5C 3F 19` 解释日志时，它只是**教学假设数据**，不是实测结果。`actual_length` 统计本 message 已执行的传输长度，因此本例成功时为 5＋4＝9 字节，不是只统计接收到的 4 字节。

这组页面的任务不是把一笔读取拆成互不相干的 API 介绍，而是让读者始终能回答三个问题：当前代码属于哪一层，它接收上一步的什么结果，它把什么交给下一步。对象创建、传输组装、控制器执行和结果观察分别展开，完整教学文件、真实源码与 Framework Lab 用于回查同一条路径。

本节覆盖：组内分页关系、SPI 各层的责任边界、一笔 5＋4 字节读取的完整调用路径、源码与交互资源入口，以及这些材料能够证明和不能证明的内容。<br>
spidev 工具排障归 B-B.4.4；`jedec,spi-nor → MTD` 的产品接入和烧录归 B-B.4.5。

## <span class="blue"> 这组短页面怎样合读成一条路径

首读按下列顺序推进。每一步都只放大完整路径中的一段，不更换事务，也不另起一套示例。

1. **本页：先建立全路与责任边界**：知道一笔读取会经过哪些角色，后续代码应放回哪一步理解。
2. **DTS 建链与对象生命周期**：从 SPI1 下的子节点出发，理解 `spi_device` 为什么先于外设驱动的 probe 存在，以及 `spi_driver` 怎样与它匹配。
3. **手工双段 message 基线**：先不用高级封装，直接组出 5 字节 TX 与 4 字节 RX，看清 `spi_message`、`spi_transfer`、缓冲区、返回值和释放路径。
4. **Core 与 Rockchip 执行路径**：沿同一 message 看调度、逐段执行、CS、DMA、完成通知与错误返回。
5. **便捷封装的边界**：在已经看懂双段基线后，再判断 `spi_write_then_read()` 隐藏了哪些步骤，哪些场景仍需要手工组装。
6. **构建观察与产品移交**：构建并观察教学模块，区分框架行为、教学假设与目标硬件结果，最后回到 `spi-nor → MTD` 的产品接入路径。

这样的顺序先给出完整地图，再逐段放大。读到某个函数、字段或错误分支时，都可以回到本页确认：它是在建立设备关系、描述传输、执行硬件动作，还是把结果交还调用者。

## <span class="blue"> 同一笔读取经过哪些层

B-B.4.2 关注的是 72 拍怎样出现在引脚上；本节关注的是谁组织这些时钟要传输的数据，谁真正操作 RK3568 控制器。两类问题不能混在一层代码里回答。

- **外设协议驱动**：本组教学模块所在的层。它理解 W25Q128JV 的 `0x0B`、24 位地址和 dummy 字节，把它们组装成 message 和 transfer，但不直接读写 RK3568 寄存器。
- **SPI Core**：提供设备、驱动和传输对象的公共模型，负责匹配、校验、排队或提交、逐段执行协调、完成通知和状态返回。它不理解 `0x0B` 的器件语义。
- **Rockchip 控制器驱动**：在 `spi-rockchip.c` 中适配具体硬件，配置并执行一个 transfer，处理控制器侧的数据交换。它不需要理解 Fast Read 命令的含义。
- **板级 DTS**：描述 W25Q128JV 或教学设备挂在哪个 SPI 控制器的哪个片选下，为设备创建和驱动匹配提供输入。DTS 本身不执行传输。

因此，协议驱动决定“要交换什么”，Core 决定“怎样把请求接到合适的控制器并协调完成”，控制器驱动决定“怎样让这一组硬件完成交换”。一次成功读取把三者串成下面的完整路径：

```text
板级 DTS 中的 spi-frame-observer@0
→ SPI Core 创建 spi_device（设备名 spi1.0）
→ compatible 匹配教学 spi_driver，进入 probe
→ probe 组出 5 字节 TX + 4 字节 RX 的 spi_message
→ spi_sync() 校验并提交
→ SPI Core 逐段调用 RK3568 的 transfer_one
→ 控制器产生 CS/SCLK 并交换 MOSI/MISO 位流
→ Core 完成缓冲区回收与完成通知
→ spi_sync() 返回 0，外设驱动取得 4 字节数据
```

这条链同时限定了错误归因的起点。设备没有出现，应先检查 DTS 建链与匹配；请求没有正确描述两段数据，应检查协议驱动；请求已进入控制器但在某段失败，则继续沿 Core 的返回路径和 Rockchip 的执行路径定位。这里的顺序用于组织源码阅读，不代替后文的实际错误推演。

## <span class="blue"> 本页自查

??? details "Q1. 为什么外设协议驱动不需要直接读写 RK3568 SPI 寄存器？"

    协议驱动的职责是把 W25Q128JV 的命令翻译成 message 和 transfer。Core 负责校验、调度与完成通知，Rockchip 控制器驱动通过 `transfer_one` 配置硬件并完成位移。分层后，同一颗 Flash 的协议代码不必随 SoC 寄存器变化而重写。

??? details "Q2. 为什么本例成功时 actual_length 是 9，而不是接收数据的 4？"

    本例 message 包含一段 5 字节 TX 和一段 4 字节 RX，`actual_length` 统计已执行的传输长度，所以完整成功时为 5＋4＝9。4 只是 RX 缓冲区的数据长度，`D0～D3` 的具体值仍由 Flash 当前内容决定。

??? details "Q3. 后续分页为什么先看 DTS，再看手工双段 message，最后才进入控制器路径？"

    DTS 建链先回答设备对象和 probe 从哪里来；手工双段基线再回答协议驱动向 Core 提交了什么；进入 Core 与 Rockchip 路径后，才能逐段追踪这个已明确的双段请求。这样每一页都在放大同一笔读取的下一步，而不是先陷入局部源码再拼接全路。
