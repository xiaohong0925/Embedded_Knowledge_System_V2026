# DTS 建链：spi_device 怎样进入 probe

> 所属章节：第五部 B. 总线协议 > B-B.4 SPI 总线 > B-B.4.3 SPI Linux 驱动框架
>
> 本组阅读：第 2 页，共 6 页

上一页把一笔 Fast Read 分成了设备树、SPI Core、控制器驱动和外设协议驱动四类角色。本页沿 RK3568 SPI1、CS0 上的教学节点，只回答一个问题：**静态设备树怎样变成 `spi_device`，这个对象又怎样经 `compatible` 匹配进入协议驱动的 `probe()`？**

这里会经过两次不同的驱动匹配：SPI1 控制器节点先匹配 Rockchip 的 platform 驱动，控制器下的外设节点再匹配 SPI 协议驱动。分清这两次匹配，就不会把控制器的 `probe()`、外设的 `probe()` 和 `spi_device` 的创建混成一件事。

DTS（Device Tree Source）是用节点和属性描述硬件连接关系的源文件，本身不执行创建对象的代码。DTSI 是可被板级 DTS 包含的源文件，用来复用同一颗 SoC 的公共描述；板级 DTS 再决定启用哪个控制器、接入了什么器件。

## <span class="blue"> 静态描述先分清控制器与外设

### SoC 节点提供 SPI1 的硬件事实

RK3568 的 SoC 级 DTSI 已经描述 SPI1。以下是 [`arch/arm64/boot/dts/rockchip/rk356x.dtsi:1291-1303`](code/B-B.4.3/kernel-v6.6/arch/arm64/boot/dts/rockchip/rk356x.dtsi){: data-code-viewer="true" data-code-title="rk356x.dtsi" data-code-path="Linux v6.6 · arch/arm64/boot/dts/rockchip/rk356x.dtsi" data-code-lines="1291-1303"} 的完整节点，属性值保持 v6.6 原文：

```dts
spi1: spi@fe620000 {
    compatible = "rockchip,rk3568-spi", "rockchip,rk3066-spi";
    reg = <0x0 0xfe620000 0x0 0x1000>;
    interrupts = <GIC_SPI 104 IRQ_TYPE_LEVEL_HIGH>;
    clocks = <&cru CLK_SPI1>, <&cru PCLK_SPI1>;
    clock-names = "spiclk", "apb_pclk";
    dmas = <&dmac0 22>, <&dmac0 23>;
    dma-names = "tx", "rx";
    pinctrl-names = "default";
    pinctrl-0 = <&spi1m0_cs0 &spi1m0_cs1 &spi1m0_pins>;
    #address-cells = <1>;
    #size-cells = <0>;
    status = "disabled";
};
```

这些属性分别回答控制器在哪里、需要哪些资源、怎样被驱动认领：

- `reg = <0x0 0xfe620000 0x0 0x1000>` 给出寄存器窗口的基址和长度。`0xfe620000` 来自 SoC 地址映射，不是外设协议驱动分配的地址。
- `interrupts` 声明 GIC 中断 104 及高电平触发方式；`clocks` 和 `clock-names` 给出控制器主时钟 `spiclk` 与 APB 接口时钟 `apb_pclk`。APB 是 SoC 内访问控制器寄存器所用的一类外设总线。
- `dmas` 和 `dma-names` 声明 DMAC0 的发送通道 22、接收通道 23。DMA（Direct Memory Access）由 DMA 控制器在内存与外设之间搬运数据，但声明通道不等于每笔传输都必须使用 DMA。
- `pinctrl-0` 选择 SPI1 的 m0 引脚复用组合。实际板卡必须与原理图一致；使用其他复用组时，应修改板级 pinctrl，不能沿用这组假设。
- `#address-cells = <1>` 与 `#size-cells = <0>` 规定子节点的 `reg` 只用一个单元表示片选号，不表示外设寄存器窗口。
- `status = "disabled"` 表示 SoC 文件只声明硬件能力，不替具体板卡启用 SPI1。

控制器的 `compatible` 同时列出 SoC 专用名和兼容回退名。本页保存的 [`rockchip_spi_dt_match`:1053-1067](code/B-B.4.3/kernel-v6.6/drivers/spi/spi-rockchip.c){: data-code-viewer="true" data-code-title="spi-rockchip.c" data-code-path="Linux v6.6 · drivers/spi/spi-rockchip.c" data-code-lines="1053-1067"} 不含 `rockchip,rk3568-spi`，但含 `rockchip,rk3066-spi`，因此这份 v6.6 快照实际由后者完成控制器驱动匹配。不能仅凭数组中的第一个字符串，就断定驱动表一定含有同名项。

### 板级节点说明 CS0 上接了什么

SoC 节点还没有说明哪块板启用了 SPI1、CS0 上接了什么。本篇使用一个只发起 Fast Read 的教学协议驱动，配套 [`spi-frame-observer.dts`](code/B-B.4.3/spi-frame-observer.dts){: data-code-viewer="true" data-code-title="spi-frame-observer.dts" data-code-path="本篇教学配套 · code/B-B.4.3/spi-frame-observer.dts"} 用下列板级片段补足这两项事实：

```dts
// 板级 DTS 片段；不是可独立编译的完整 DTS，也不是带 /plugin/ 的 overlay。
&spi1 {
    status = "okay";

    spi_frame_observer: spi-frame-observer@0 {
        compatible = "kimi,spi-frame-observer";
        reg = <0>;
        spi-max-frequency = <1000000>;
    };
};
```

`&spi1` 引用前面的 SoC 节点，`status = "okay"` 启用控制器。子节点中的 `reg = <0>` 选择 CS0，不是内存地址，也不是 I2C 从机地址；`spi-max-frequency = <1000000>` 把这块板上的外设速度上限设为 1 MHz，实际设置还会受控制器能力约束。

子节点没有写 `spi-cpol`、`spi-cpha`、`spi-lsb-first` 和 `spi-cs-high`。v6.6 的解析代码只在属性存在时设置对应模式位，因此本例保持 CPOL=0、CPHA=0 的 Mode 0、MSB-first 和低有效 CS。字长不在这里另设，注册阶段的 `spi_setup()` 会把默认值 0 落成 8 位。

到这里，DTS 仍只是静态描述。要得到可供协议驱动使用的对象，必须先让控制器注册成功。

## <span class="blue"> 控制器注册为子设备扫描提供入口

SPI 控制器通常由 platform 这类非 SPI 总线承载。`platform_device` 是平台总线中的设备对象；本例的 Rockchip 控制器驱动在它的 `probe()` 中创建 SPI 控制器对象，再把这个对象注册到 SPI Core。

> `spi_controller`：一个 SPI 主机控制器在内核中的对象。<BR>
> 它保存总线编号、片选数量、支持的模式与字长、速度范围和硬件操作回调。本例由 `rockchip_spi_probe()` 创建，协议驱动不创建也不释放它。

本例的正常调用顺序是：

```text
spi1 控制器节点经 compatible 匹配 Rockchip platform 驱动
→ rockchip_spi_probe(pdev)
→ spi_alloc_host() 分配 spi_controller
→ 获取寄存器、时钟和中断资源，设置 setup / set_cs / transfer_one 等回调
→ devm_spi_register_controller()
→ spi_register_controller()
→ of_register_spi_devices()
→ 遍历 SPI1 下的可用外设子节点
```

[`rockchip_spi_probe()`:752-948](code/B-B.4.3/kernel-v6.6/drivers/spi/spi-rockchip.c){: data-code-viewer="true" data-code-title="spi-rockchip.c" data-code-path="Linux v6.6 · drivers/spi/spi-rockchip.c" data-code-lines="752-948"} 不只是分配一个结构体。它还要映射寄存器、获取并使能时钟、申请中断、设置控制器能力与回调，并请求 TX/RX DMA 通道，最后才注册控制器。`transfer_one` 指向 `rockchip_spi_transfer_one()`，供以后的一笔传输使用；本页尚未提交 Fast Read。

这里的资源边界有两层：

- **probe 内的失败回滚**：控制器分配失败直接返回 `-ENOMEM`；寄存器、时钟、中断、FIFO 或控制器注册等步骤失败时，沿 `goto` 路径按已经进入的阶段回滚：释放已取得的 DMA 通道，关闭已经启用的运行时电源管理和时钟，并执行 `spi_controller_put()`。不能返回错误后把已使能的时钟和已申请的通道留在原处。
- **注册成功后的设备管理**：`devm_spi_register_controller()` 中的 `devm` 表示由设备模型管理资源。注册成功后，注销动作随设备资源释放路径执行；这不替代 probe 中途失败时的回滚，也不把控制器资源转交给外设协议驱动。

DMA 请求还有一个单独分支：返回 `-EPROBE_DEFER` 表示依赖尚未就绪，整个 probe 延后并重走清理；其他 DMA 请求错误只告警并把相应通道置为 `NULL`。只有 TX、RX 通道都取得成功时，驱动才设置 `can_dma` 回调。因此，DTS 声明了 DMA 资源，也不能推出每次传输都会走 DMA。

[`spi_register_controller()`:3103-3212](code/B-B.4.3/kernel-v6.6/drivers/spi/spi.c){: data-code-viewer="true" data-code-title="spi.c" data-code-path="Linux v6.6 · drivers/spi/spi.c" data-code-lines="3103-3212"} 检查回调、分配总线编号、注册控制器设备并初始化传输队列。完成这些步骤后，它才调用 `of_register_spi_devices()`。这就是控制器节点下的静态子节点进入 SPI 设备模型的入口。

## <span class="blue"> 一个可用子节点怎样变成 spi_device

> `spi_device`：SPI Core 为控制器一侧保存的外设代理对象。<BR>
> 它关联所属 `spi_controller`，保存片选、最高速度、传输模式、字长、中断和 `modalias` 等状态。协议驱动使用它发起传输，但不负责在 probe 中创建它。

Core 先遍历控制器节点的可用子节点。以下是 [`of_register_spi_devices()`:2377-2392](code/B-B.4.3/kernel-v6.6/drivers/spi/spi.c){: data-code-viewer="true" data-code-title="spi.c" data-code-path="Linux v6.6 · drivers/spi/spi.c" data-code-lines="2377-2392"} 的完整函数：

```c
// drivers/spi/spi.c · of_register_spi_devices()（Linux v6.6 完整函数）
static void of_register_spi_devices(struct spi_controller *ctlr)
{
    struct spi_device *spi;
    struct device_node *nc;

    for_each_available_child_of_node(ctlr->dev.of_node, nc) {
        if (of_node_test_and_set_flag(nc, OF_POPULATED))
            continue;
        spi = of_register_spi_device(ctlr, nc);
        if (IS_ERR(spi)) {
            dev_warn(&ctlr->dev,
                     "Failed to create SPI device for %pOF\n", nc);
            of_node_clear_flag(nc, OF_POPULATED);
        }
    }
}
```

`for_each_available_child_of_node()` 只遍历当前可用的子节点，跳过被禁用的节点。`OF_POPULATED` 是设备树节点的“已填充”标记：已设置的节点不重复创建；创建失败时清除标记，并记录警告。这个函数没有返回错误，一个子节点创建失败不会撤销已经注册成功的控制器，也不会阻止循环继续处理其他子节点。

每个节点实际经过的分配、解析和注册集中在 [`of_register_spi_device()`:2323-2368](code/B-B.4.3/kernel-v6.6/drivers/spi/spi.c){: data-code-viewer="true" data-code-title="spi.c" data-code-path="Linux v6.6 · drivers/spi/spi.c" data-code-lines="2323-2368"}。完整函数如下：

```c
// drivers/spi/spi.c · of_register_spi_device()（Linux v6.6 完整函数）
static struct spi_device *
of_register_spi_device(struct spi_controller *ctlr, struct device_node *nc)
{
    struct spi_device *spi;
    int rc;

    /* Alloc an spi_device */
    spi = spi_alloc_device(ctlr);
    if (!spi) {
        dev_err(&ctlr->dev, "spi_device alloc error for %pOF\n", nc);
        rc = -ENOMEM;
        goto err_out;
    }

    /* Select device driver */
    rc = of_alias_from_compatible(nc, spi->modalias,
                                  sizeof(spi->modalias));
    if (rc < 0) {
        dev_err(&ctlr->dev, "cannot find modalias for %pOF\n", nc);
        goto err_out;
    }

    rc = of_spi_parse_dt(ctlr, spi, nc);
    if (rc)
        goto err_out;

    /* Store a pointer to the node in the device structure */
    of_node_get(nc);

    device_set_node(&spi->dev, of_fwnode_handle(nc));

    /* Register the new device */
    rc = spi_add_device(spi);
    if (rc) {
        dev_err(&ctlr->dev, "spi_device register error %pOF\n", nc);
        goto err_of_node_put;
    }

    return spi;

err_of_node_put:
    of_node_put(nc);
err_out:
    spi_dev_put(spi);
    return ERR_PTR(rc);
}
```

把这段代码落到本例，顺序是四步：

1. **分配并关联控制器**。`spi_alloc_device()` 取得控制器引用，分配并清零 `spi_device`，把 `controller`、`dev.parent` 和 `dev.bus` 分别指向 SPI1 控制器、控制器设备和 `spi_bus_type`。分配失败时它返回 `NULL`，外层再转成 `-ENOMEM`。
2. **生成 `modalias` 并解析属性**。`modalias` 是设备用于模块别名和后续驱动匹配的名称或别名。`of_alias_from_compatible()` 根据节点的 `compatible` 生成它；`of_spi_parse_dt()` 再把模式属性、`reg` 和 `spi-max-frequency` 写入 `spi_device` 的相应字段。本例得到 CS0、1 MHz 上限和未额外置位的模式字段。
3. **保存设备树关联**。`of_node_get(nc)` 增加节点引用，`device_set_node()` 把节点句柄存入设备对象。此后 `spi_device` 不只是几个散落的模式字段，还保留它与静态 DTS 节点的关联。
4. **注册到 SPI 总线**。`spi_add_device()` 检查片选是否越界、是否已被占用，执行初始 `spi_setup()`，再调用 `device_add()`。设备名由控制器设备名和片选号组成，本例即 `spi1.0`；这个名字不是从 `@0` 单独推导出来的。

[`of_spi_parse_dt()`:2226-2320](code/B-B.4.3/kernel-v6.6/drivers/spi/spi.c){: data-code-viewer="true" data-code-title="spi.c" data-code-path="Linux v6.6 · drivers/spi/spi.c" data-code-lines="2226-2320"} 对缺失或无效的 `reg` 直接返回错误，所以本例不能省略 `reg = <0>`。`spi-max-frequency` 则是可选属性，只有读取成功时才覆盖 `max_speed_hz`。

[`__spi_add_device()`:628-688](code/B-B.4.3/kernel-v6.6/drivers/spi/spi.c){: data-code-viewer="true" data-code-title="spi.c" data-code-path="Linux v6.6 · drivers/spi/spi.c" data-code-lines="628-688"} 中的 `spi_setup()` 不是协议驱动在每次 probe 前必须重复执行的形式动作。注册阶段已经完成初始设置：[`spi_setup()`:3714-3838](code/B-B.4.3/kernel-v6.6/drivers/spi/spi.c){: data-code-viewer="true" data-code-title="spi.c" data-code-path="Linux v6.6 · drivers/spi/spi.c" data-code-lines="3714-3838"} 检查控制器是否支持请求的模式，把未指定的字长设为 8 位，将设备速度上限限制到控制器上限，再调用控制器的 `setup` 回调。协议驱动只有需要修改设备设置时才再次调用它，并处理负错误码。

失败清理与节点引用取得的先后一致：生成 `modalias` 或解析 DTS 失败时，尚未执行 `of_node_get()`，直接 `spi_dev_put(spi)`；`spi_add_device()` 失败时，先 `of_node_put(nc)` 归还节点引用，再 `spi_dev_put(spi)`。片选越界或重复、`spi_setup()` 失败、`device_add()` 失败都会使注册返回错误，不能把这些情况写成“设备已注册，只是还没匹配驱动”。

## <span class="blue"> compatible 匹配后才调用协议驱动 probe

`spi_device` 表示“控制器下有一颗这样连接的设备”，`spi_driver` 表示“这个驱动知道怎样使用某类设备”。后者保存匹配表以及 `probe`、`remove` 等回调，由协议驱动模块注册和注销。设备对象与驱动对象可以先后出现，匹配由 SPI 总线完成，不由 probe 自己解析 DTS 再创建设备。

> `spi_driver`：SPI 外设协议驱动对象。<BR>
> 它通过 `of_match_table`、`id_table` 或驱动名声明可支持的设备，并在匹配后收到已有的 `spi_device`。它的注册生命周期不等于某颗外设的生命周期。

[`spi_match_device()`:376-397](code/B-B.4.3/kernel-v6.6/drivers/spi/spi.c){: data-code-viewer="true" data-code-title="spi.c" data-code-path="Linux v6.6 · drivers/spi/spi.c" data-code-lines="376-397"} 的完整匹配顺序如下：

```c
// drivers/spi/spi.c · spi_match_device()（Linux v6.6 完整函数）
static int spi_match_device(struct device *dev, struct device_driver *drv)
{
    const struct spi_device    *spi = to_spi_device(dev);
    const struct spi_driver    *sdrv = to_spi_driver(drv);

    /* Check override first, and if set, only use the named driver */
    if (spi->driver_override)
        return strcmp(spi->driver_override, drv->name) == 0;

    /* Attempt an OF style match */
    if (of_driver_match_device(dev, drv))
        return 1;

    /* Then try ACPI */
    if (acpi_driver_match_device(dev, drv))
        return 1;

    if (sdrv->id_table)
        return !!spi_match_id(sdrv->id_table, spi->modalias);

    return strcmp(spi->modalias, drv->name) == 0;
}
```

OF（Open Firmware）在这里指设备树匹配路径。本例没有 `driver_override`，节点的 `compatible = "kimi,spi-frame-observer"` 与教学驱动 `of_match_table` 中的一项相符，因此 `of_driver_match_device()` 返回真。若未设置强制驱动名且 OF 未命中，代码还会尝试 ACPI、`id_table` 和驱动名，所以不能把 SPI 匹配概括成“永远只比较 compatible”。

匹配成功只说明设备和驱动可以绑定，还没有执行任何 SPI 数据传输。SPI 总线的 [`spi_probe()`:411-440](code/B-B.4.3/kernel-v6.6/drivers/spi/spi.c){: data-code-viewer="true" data-code-title="spi.c" data-code-path="Linux v6.6 · drivers/spi/spi.c" data-code-lines="411-440"} 在调用协议驱动前还要处理设备树时钟默认值、中断和电源域：

```c
// drivers/spi/spi.c · spi_probe()（Linux v6.6 完整函数）
static int spi_probe(struct device *dev)
{
    const struct spi_driver    *sdrv = to_spi_driver(dev->driver);
    struct spi_device          *spi = to_spi_device(dev);
    int ret;

    ret = of_clk_set_defaults(dev->of_node, false);
    if (ret)
        return ret;

    if (dev->of_node) {
        spi->irq = of_irq_get(dev->of_node, 0);
        if (spi->irq == -EPROBE_DEFER)
            return -EPROBE_DEFER;
        if (spi->irq < 0)
            spi->irq = 0;
    }

    ret = dev_pm_domain_attach(dev, true);
    if (ret)
        return ret;

    if (sdrv->probe) {
        ret = sdrv->probe(spi);
        if (ret)
            dev_pm_domain_detach(dev, true);
    }

    return ret;
}
```

`-EPROBE_DEFER` 表示某项依赖尚未就绪，需要延后 probe，不能当成设备已经绑定成功。其他中断获取错误在本路径中把 `spi->irq` 置为 0；电源域附加失败则直接返回。只有这些前置步骤成功后，`sdrv->probe(spi)` 才把**已经创建、解析并注册好的 `spi_device`** 交给教学协议驱动。

协议驱动的 probe 返回 0 才表示接受该设备。返回非零错误时，Core 分离刚才附加的电源域并把错误返回给设备模型；probe 内已经申请的其他资源仍须按该驱动自己的错误路径清理，不能由这段 Core 代码代为猜测和释放。解绑时，[`spi_remove()`:442-450](code/B-B.4.3/kernel-v6.6/drivers/spi/spi.c){: data-code-viewer="true" data-code-title="spi.c" data-code-path="Linux v6.6 · drivers/spi/spi.c" data-code-lines="442-450"} 先调用协议驱动的 `remove()`（若提供），再分离电源域。

至此，三个长期对象的责任已经分开：Rockchip 控制器驱动创建并注册 `spi_controller`，SPI Core 根据 DTS 创建并注册 `spi_device`，设备模型把该设备交给匹配的 `spi_driver`。一次 Fast Read 所需的 `spi_message` 和两个 `spi_transfer` 尚未出现，它们属于后续传输路径。

```mermaid
flowchart LR
    N[SPI1 控制器节点] -->|匹配 platform 驱动| R[rockchip_spi_probe]
    R -->|分配并注册| C[spi_controller]
    C -->|注册成功后交给 Core 扫描| K[of_register_spi_devices]
    N2[spi-frame-observer@0 子节点] -->|分配、解析、注册| D[spi_device：spi1.0]
    K --> D
    D -->|compatible 匹配| P[spi_probe]
    DRV[spi_driver：of_match_table] --> P
    P -->|传入已有 spi_device| CB[协议驱动 probe]
    CB -.下一页才创建.-> M[spi_message + 两个 spi_transfer]
```

读图时先分清两条入口：控制器节点进入 Rockchip probe，外设子节点进入 SPI Core 的设备创建路径。随后看 `spi_device` 与 `spi_driver` 在 `spi_probe` 处会合，probe 的参数来自前面的注册结果，而不是在回调里临时分配。去掉这张图，上文的调用顺序、错误路径和资源归属仍能独立说明同一过程。

[`struct spi_transfer` 与 `struct spi_message` 的内存约定](code/B-B.4.3/kernel-v6.6/include/linux/spi/spi.h){: data-code-viewer="true" data-code-title="spi.h" data-code-path="Linux v6.6 · include/linux/spi/spi.h" data-code-lines="1023-1104"} 明确规定：提交消息及其传输段的代码负责管理它们的内存。下一页组装双段 Fast Read 时，会沿这个边界分配、提交并释放缓冲区，不把一次传输的临时对象并入本页的控制器或设备生命周期。

## <span class="blue"> 本页总结

DTS 负责描述，Core 负责把描述变成设备对象，协议驱动负责在匹配后使用这个对象。只要记住 `rockchip_spi_probe()` 注册的是控制器、`of_register_spi_device()` 创建的是外设、`spi_probe()` 传入的是已有设备，就不会把两次 probe 和两类资源混为一谈。正常路径之外，还要保留分配、解析、注册和 probe 各自的错误返回与清理边界。

## <span class="blue"> 本页自查

??? details "Q2. `spi1.0` 这个设备对象是怎样出现的，probe 是否负责创建它？"

    Rockchip 控制器驱动注册 SPI1 后，Core 遍历其可用子节点，为 `spi-frame-observer@0` 分配 `spi_device`，生成 `modalias`，解析 CS0、速度和模式属性，保存设备树节点关联，再注册设备。compatible 匹配成功后，Core 才调用协议驱动的 probe，并把已经创建的 `spi_device` 作为参数传入。probe 不负责创建它；分配、解析或注册失败时，相应错误会沿 Core 的清理路径返回，不能进入正常绑定。
