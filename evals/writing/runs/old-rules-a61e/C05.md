# 同一笔 SPI 读取：手工 message 与 spi_write_then_read() 怎么选

> 所属章节：第五部 B. 总线协议 > B-B.4 SPI 总线 > B-B.4.3 SPI Linux 驱动框架
>
> 本组阅读：第 5 页，共 6 页

本页只回答一个问题：**面对同一笔“先写命令、再读数据”的 SPI 事务，手工 message 与 `spi_write_then_read()` 有什么实际差异，应当依据什么选择？**

---

## <span class="blue"> 两种写法描述的是同一笔事务

沿用手工基线中的受控 Fast Read 读取：先发送 `0x0b 00 12 34 00`，其中 `0x0b` 是命令，随后三字节是地址 `0x001234`，最后一字节提供 8 个 dummy 时钟；再读取 4 字节数据。dummy 时钟是器件在返回数据前要求的额外时钟，不是额外的数据字节。

两种调用方式都必须保留这份器件协议约定。它们的不同在于由谁分配缓冲区、组装传输描述符和处理完成后的数据，而不是线上换成了另一种传输。

> `spi_transfer`：一段具有独立缓冲区和长度的传输描述。只设置 `tx_buf` 时，同时移入的数据被丢弃；只设置 `rx_buf` 时，控制器继续提供时钟并移出零，同时保存移入的数据。

<!-- -->

> `spi_message`：按顺序执行的一组 transfer。SPI Core 把它作为一次总线事务调度，并记录实际完成长度和最终状态。默认情况下，同一 message 内的两段之间不撤销片选（Chip Select，CS）。

下面两个函数都是本篇原创教学代码中的完整函数，不是可以独立编译的模块。它们分别替代配套模块中的读取函数，实际调用时二选一；`spi` 是设备匹配后得到的外设对象，`data` 必须至少有 4 字节可写空间。完整模块及驱动注册上下文见 [`spi_frame_observer.c`](code/B-B.4.3/spi_frame_observer.c){: data-code-viewer="true" data-code-title="spi_frame_observer.c" data-code-path="本篇教学配套 · code/B-B.4.3/spi_frame_observer.c"}。

### 手工 message 保留每个环节的可见性

第一个函数沿用完整模块的手工基线。它来自 `spi_frame_observer.c` 的同一教学实例，使用其中已经定义的 `OBSERVER_CMD_LEN` 和 `OBSERVER_DATA_LEN`。

```c
static int spi_frame_observer_read_message(struct spi_device *spi, u8 *data)
{
    struct spi_transfer transfers[2] = { };
    struct spi_message message;
    u8 *tx_buf;
    u8 *rx_buf;
    int ret;

    tx_buf = kzalloc(OBSERVER_CMD_LEN, GFP_KERNEL);
    rx_buf = kzalloc(OBSERVER_DATA_LEN, GFP_KERNEL);
    if (!tx_buf || !rx_buf) {
        ret = -ENOMEM;
        goto out_free;
    }

    tx_buf[0] = 0x0b;
    tx_buf[1] = 0x00;
    tx_buf[2] = 0x12;
    tx_buf[3] = 0x34;
    tx_buf[4] = 0x00;              /* 8 个 dummy 时钟 */

    transfers[0].tx_buf = tx_buf;
    transfers[0].len = OBSERVER_CMD_LEN;
    transfers[1].rx_buf = rx_buf;
    transfers[1].len = OBSERVER_DATA_LEN;

    spi_message_init(&message);
    spi_message_add_tail(&transfers[0], &message);
    spi_message_add_tail(&transfers[1], &message);

    /* 同步返回前，栈上的描述符始终有效。 */
    ret = spi_sync(spi, &message);
    if (ret < 0)
        goto out_free;

    if (message.actual_length != OBSERVER_CMD_LEN + OBSERVER_DATA_LEN) {
        ret = -EIO;
        goto out_free;
    }

    memcpy(data, rx_buf, OBSERVER_DATA_LEN);

out_free:
    kfree(rx_buf);
    kfree(tx_buf);
    return ret;
}
```

`kzalloc()` 分配并清零内核内存，`GFP_KERNEL` 表示分配路径允许睡眠。本例使用 kmalloc 族缓冲区，使 SPI Core 能按控制器需要进行 DMA 映射。DMA（Direct Memory Access）是控制器不依赖 CPU 逐字节搬运数据的传输方式；这里的缓冲区要求只说明内存能否被映射和访问，不保证其中的数据内容正确。

`message` 和 `transfers` 是描述符，可以位于栈上，因为 `spi_sync()` 返回前函数不会退出。两个堆缓冲区则从分配一直保留到传输和结果复制结束，最后由同一个 `out_free` 出口释放。分配失败、同步传输失败和完成长度不符都不会把未确认的数据复制给调用者。

第一段发送 5 字节前导，第二段接收 4 字节。两段合计产生 9 字节的全双工位移，第二段并未因为只设置 `rx_buf` 而停止发送时钟。`spi_message_add_tail()` 的调用顺序就是 Core 处理两段的顺序，未设置的 `cs_change` 保持默认值，不在两段之间主动改变 CS。

### spi_write_then_read() 把同一结构收进 Core

第二个函数只替换调用方式，命令、地址、dummy 和读取长度都不变。

```c
static int spi_frame_observer_read_wrapper(struct spi_device *spi, u8 *data)
{
    u8 tx[5] = { 0x0b, 0x00, 0x12, 0x34, 0x00 };

    return spi_write_then_read(spi, tx, sizeof(tx), data, 4);
}
```

调用者不再分配接收缓冲区，也不显式初始化 message 和 transfer。v6.6 的 `spi_write_then_read()` 会在内部完成这些工作：准备小缓冲区，把发送数据复制进去，初始化一个 message 和最多两个 transfer，再调用 `spi_sync()`。返回成功后，它把内部接收区域中的 `n_rx` 字节复制到 `rxbuf`。

因此，封装减少的是**缓冲区管理、分段组装和结果复制的样板代码**。前导仍然是 5 字节，读取仍然是 4 字节，两段仍按同一顺序同步执行，SPI 线上仍是全双位移。器件要求多少地址字节和 dummy 时钟，仍由外设驱动依据器件手册决定。

## <span class="blue"> 实际差异落在缓冲区、可见信息和控制力

### 缓冲区由谁准备，决定了复制成本与内存要求

手工路径由调用者提供缓冲区。批量或性能敏感路径可以准备满足 DMA 要求的内存，直接交给 `spi_sync()`，并让这些缓冲区覆盖实际需要的传输周期，避免便捷封装内部的复制。

`spi_write_then_read()` 的传入和传出缓冲区不必是 DMA-safe，因为实现会复制到内部缓冲区。v6.6 优先使用静态预分配的小缓冲区，并用互斥锁保护它；传输总量超过内部容量或锁正被占用时，则临时分配内存。源码把 `SPI_BUFSIZ` 定义为 `max(32, SMP_CACHE_BYTES)`，并提示可移植代码不要传入超过 32 字节。这是实现的复制与分配策略，不是 SPI 协议或某个器件的通用事务上限。

### 返回值相同，完成长度的可见性不同

两种方式的返回语义一致：**0 表示成功，负值表示错误，都不返回传输字节数。** 两个函数都只能用于可睡眠上下文；底层 `spi_sync()` 的等待没有超时。

手工路径还能读取 `message.actual_length`。这个字段记录实际完成的传输长度，本例完整成功时应为 `5 + 4 = 9`。教学代码把长度不符转换为 `-EIO`，并且只在返回值为 0、长度也符合预期时复制接收数据。

`spi_write_then_read()` 不向调用者暴露内部 message，调用者因此无法通过这个接口检查同一笔事务的 `actual_length`。实现只在 `spi_sync()` 返回 0 时把接收数据复制给调用者，失败时返回负错误码。若调用方需要显式核验完成长度，手工 message 提供了直接入口。

### 是否需要逐段控制，是另一条选择边界

手工 message 可以按器件要求设置每段的 `speed_hz`、`bits_per_word` 和 `cs_change`，也可以组合不止两段传输。`spi_write_then_read()` 只表达“可选的一段写，随后可选的一段读”这一固定结构，不提供逐段配置入口。

本例两段使用默认配置，且不要求段间改变 CS，所以封装足以表达协议。若器件手册要求特殊的段间片选行为、不同字长或更复杂的传输序列，就应保留手工 message，而不能为了缩短代码牺牲这些控制条件。

Core 和 Rockchip 如何逐段执行、选择 DMA 或中断路径，以及 CS 在正常与错误路径上的收尾，属于[Core 与 Rockchip 执行](B-B.4.3_SPI Linux驱动框架_execution.md)的机制范围。本页只据此确定调用边界，不重复展开控制器实现。

## <span class="blue"> 按事务需求选择，而不是按代码长短选择

当前 5＋4 字节读取使用 `spi_write_then_read()` 更合适：结构固定、数据量小，调用者不需要逐段配置，也不必让内部 message 可见。它用内部复制换取更短的调用代码，并让栈上的普通收发数组也能作为参数。

以下情况应使用手工 message：

- 批量或性能敏感传输需要避免内部复制，并由调用者准备满足 DMA 要求的缓冲区；
- 需要检查 `actual_length`，或需要直接处理 message 的完成状态；
- 需要逐段设置字长、速度、CS 行为，或事务包含更复杂的传输序列。

这不是“手工方式一定更快”或“封装只能用于测试”的绝对划分。选择依据是实现中的复制成本、接口暴露的信息和器件协议所需的控制力。

本页只依据 Linux v6.6 源码和配套教学源码比较调用语义，**没有重新编译模块、上板读取器件或测量波形**。因此，本页不声称已经得到某个器件的 4 字节实测结果，也不预判 Rockchip 对这两段会选择哪条执行路径。模块构建、观察步骤和产品驱动移交由[构建观察与产品移交](B-B.4.3_SPI Linux驱动框架_practice.md)承担；受控只读示例不替代内核已有的 spi-nor/MTD 驱动栈。

## <span class="blue"> 本页总结

`spi_write_then_read()` 没有改变 Fast Read 的帧内容、全双工属性或默认事务边界，它把手工 message 的固定样板收进了 Core。小规模、结构固定的先写后读可以使用封装；需要避免复制、检查完成长度或逐段控制时，应直接管理 message 和缓冲区。两种接口都返回 0 或负错误码，返回值不能当作字节数。

## <span class="blue"> 本页自查

??? details "Q6. 为什么两种写法可以表达同一笔 5＋4 字节读取？"

    两种写法都按顺序描述一个 5 字节发送段和一个 4 字节接收段，并通过 `spi_sync()` 同步执行。第一段内容都是 `0x0b 00 12 34 00`，第二段都在继续提供时钟的同时接收 4 字节。封装只接管缓冲区、描述符和复制工作，不改变命令、地址、dummy 或读取长度。

??? details "Q7. 返回 0 后，两种写法对结果有效性的处理有什么不同？"

    两者的 0 都表示成功，不表示传输了 9 字节。手工路径还能检查 `message.actual_length` 是否等于 9，教学代码在长度不符时返回 `-EIO`，并且只在检查通过后复制数据。便捷封装不向调用者暴露 `actual_length`，其实现在内部同步调用返回 0 后复制 `n_rx` 字节，失败则返回负错误码。

??? details "Q8. 哪些需求会使手工 message 成为更合适的接口？"

    需要避免内部复制的批量或性能敏感传输、需要直接检查 `actual_length` 的调用方，以及需要逐段配置速度、字长、CS 行为或组织更复杂序列的器件，都应使用手工 message。判断依据是复制成本、可见信息和控制力，而不是代码行数。
