## 1. 核心判断

当前不舒服不是单纯由“代码太长”或“缺少双栏”造成的，而是两个问题叠加：

1. 一页同时承担子系统地图、对象创建、完整教学模块、运行传输、DTS 时序、用户态入口、GPIO 替换和实验室等任务，首读主线不够突出。
2. 当前中文正文的字号、行距、段距和页面长度形成的阅读节奏偏舒展；参考网站普遍更紧凑，并通过短页降低“看不到头”的压力。

改版目标不是减少内容，而是让读者能够分别完成四件事：

- 沿一笔 AT24C02 读取看懂主路径；
- 在每个片段中知道当前位置和上下文；
- 随时回查完整函数、完整文件与子系统地图；
- 在理解主线后再进入分支和实践。

## 2. 设计原则

1. **按阅读任务分页，不按字数机械切页。**一页只回答一个主问题。
2. **紧凑但不拥挤。**字号、行距、段距和栏宽共同试验，不为了双栏硬缩字。
3. **正文与源码双轨。**正文解释机制，完整源码负责恢复上下文和核验。
4. **重点与上下文同屏。**关键行正常显示，必要前后文灰显，完整函数可展开。
5. **先读懂，再实践。**Walk-through 与 Hands-on 分层，不让练习打断首次阅读。
6. **双栏只是可选增强。**不是全书默认版式，也不是本次改版的前置条件。

## 3. 分页方案

将当前长页重组为一个入口页和四个主题页。正式文件路径与导航编号在实施前另行确认，本稿不预设跨章链接变更。

| 页面 | 唯一主问题 | 保留内容 | 首读要求 |
|---|---|---|---|
| 0. 导读与源码地图 | 一笔读取会经过哪些角色、文件和对象？ | 贯穿实例、责任边界、源码目录、两条入口与共同后半路、阅读路线 | 必读 |
| 1. 启动建链 | DTS 怎样变成 adapter、client 和 `probe()` 参数？ | 必要结构体、控制器 probe、adapter 注册、client 创建、生命周期、`clock-frequency` 生效路径 | 必读 |
| 2. 运行传输 | 两条 `i2c_msg` 怎样穿过 Core 到达 RK3568，并把数据或错误返回？ | `demo_read_reg()`、完整教学模块入口、Core 加锁与回调、控制器状态机、返回值、正常与错误路径、构建验证 | 必读 |
| 3. 用户态入口 | `/dev/i2c-N` 怎样接到同一个 Core？ | i2c-dev、匿名 client、两个进程的共享与独立状态、完整用户程序、返回值边界 | 第二轮 |
| 4. 替换控制器 | 换成 GPIO 模拟后，为什么外设读取函数不变？ | GPIO DTS、algorithm 替换、位模拟、时钟延展、适用边界 | 第二轮 |

### 推荐阅读路线

- **首次阅读：0 → 1 → 2。**先获得一次完整走完的体验。
- **继续深入：3 → 4。**把用户入口和控制器替换视为主线的两个分支。
- **日后查阅：按页面问题直接进入。**不再要求读者先扫过整个长页。
- **实验室：分散到对应机制之后。**入口页只给简短入口，不在对象尚未建立时放一个高负担的大型 iframe。

分页以后，右侧本页目录只承担当前短页内部导航，因此暂不合并到左侧全局目录，也不全局删除。

## 4. 每页的内部结构

每页按同一阅读逻辑组织，但不增加模板化栏目：

1. 开头用具体实例说明本页要解决的问题，以及读完应能解释的结果。
2. 给一条短路径或局部地图，标出本页在全书主调用链中的位置。
3. 沿同一实例展开机制，不在中途引入另一套对象或示例数字。
4. 代码片段与解释相邻，完整函数和完整源码通过明确入口回查。
5. 页尾回到本页主问题，说明对象、状态或返回值发生了什么，并指向下一页。
6. 分支内容只在有助于理解本页主问题时进入，其余内容给准确指针。

## 5. 代码片段视图

每个关键片段统一回答以下问题：

- **位置**：文件、函数、Linux 版本、来源、完整或节选属性；
- **当前位置**：当前片段处于主调用链的哪一步；
- **任务**：这段代码只完成什么；
- **重点**：本次需要理解哪几行，为什么；
- **上下文**：前后有哪些必要代码，省略了哪些无关部分；
- **结果**：输入、输出、副作用、状态变化和返回值是什么；
- **回查**：完整函数、完整文件、复制和下载入口在哪里。

### 推荐呈现方式

```text
demo_read_reg() → i2c_transfer() → [__i2c_transfer()] → rk3x_i2c_xfer()

文件：drivers/i2c/i2c-core-base.c
任务：在已经持锁的前提下选择控制器回调

灰显：能力检查或相邻上下文，仅用于定位
正常：adap->algo->master_xfer(adap, msgs, num)
灰显：后续解锁与返回，用于说明错误也会经过同一路径

完整函数｜完整文件｜复制｜下载
```

要求：

- 灰显只降低视觉优先级，不表示代码可以忽略，也不能删掉理解错误路径所需的分支。
- 片段、完整函数和完整文件必须来自同一份原文，真实行号由提取结果生成，不手工拼接。
- 完整教学代码继续复用现有源码弹窗，不另造一套源码查看器。
- 固定版本的外部交叉索引可作为补充，但不替代仓库内的 v6.6 原文快照。

## 6. 紧凑排版 A/B 试验

先选一个包含连续解释、结构体、短代码和长代码的代表性页面，正文一字不改，只比较排版。

| 项目 | A：当前基线 | B：紧凑候选 |
|---|---|---|
| 正文字体 | 当前系统无衬线字体 | 不变，先排除字体族干扰 |
| 正文字号 | 17px | 16px |
| 正文行距 | 约 1.8～1.85 | 1.70 |
| 代码字号与行距 | 14px／1.75 | 13px／1.60 |
| 段落下间距 | 当前值 | 0.9em |
| 正文容器 | 当前最大 940px | 最大约 760px |
| 双栏 | 不启用 | 不启用 |

这些数值只是试验起点，不直接变成全书规范。先判断紧凑候选是否确实改善中文连续阅读，再决定是否单独比较中文衬线字体；第一轮不同时更换字体族。

评价重点不是“每屏显示更多字”，而是：

- 长段落是否更容易连续读完；
- 换行时是否更容易找到下一行；
- 代码与解释是否更容易保持同屏；
- 标题、正文、代码和提示框是否仍有清楚层级；
- 是否出现拥挤、扫读困难或代码辨识度下降。

## 7. 实践分层

实践放在对应 Walk-through 之后，每个任务必须给出环境前提、输入、操作、预期观察、恢复方式和验证状态。模型推演与实测结果继续严格区分。

候选任务：

1. **返回口径**：构造只完成一条消息的返回结果，解释教学驱动为什么把它转换为 `-EIO`。
2. **对象生命周期**：沿 DTS、adapter、client、`probe()` 和解绑路径指出每个对象由谁创建、谁持有、谁清理。
3. **共享与独立状态**：用两个进程打开 `/dev/i2c-1`，区分独立 file、匿名 client、消息缓冲与共享 adapter、总线锁。
4. **替换实现**：从硬件控制器切换到 GPIO 模拟，列出保持不变的外设消息、Core 调用与返回约定。
5. **源码核验**：从正文片段回到完整函数和完整文件，核对真实路径、行号及省略范围。

上述任务只是设计候选，实施时必须重新核对源码与环境；当前教学代码的交叉编译、目标运行和硬件测量仍不得写成已通过。

## 8. 非目标

本方案不做以下事情：

- 不为没有阅读负担的页面机械分页；公共 B2 排版另行按全书范围验收；
- 不合并或删除全站导航目录；
- 不把全书正文改成左右双栏；
- 不新增手机或窄屏适配与专项测试；
- 不重复实现源码弹窗或完整源码工作台；
- 不用视觉改造替代事实核验、连续阅读和代码跟随；
- 不因为分页而删除分支、错误路径、验证边界或既有资产。

## 9. 实施影响面与验收

本稿本身只是提案，不触发站点构建、浏览器检查或验收 JSON 更新。

若后续获批实施：

- 拆页、移动内容、调整前置链接按 **T3** 处理，检查相邻篇目重复、断层、链接和阅读顺序；
- 新增共享灰显代码组件或公共 CSS／JS 按 **T4** 处理，只检查直接受影响实例；
- 浏览器只验收指定桌面页面，不做窄屏或手机端专项检查；
- 文档构建、浏览器交互、教学代码编译、目标运行和硬件测量分别记录，不互相代替。

### 阅读验收的阻断条件

1. 首读只沿 0 → 1 → 2，就能说清一笔读取的完整路径，不必先读完全部分支。
2. 每个片段都能回答“在哪个函数、看哪几行、前后是什么、完整版本在哪里”。
3. 从片段回到完整函数后，能找回刚才的位置，不需要重新通读整个文件。
4. 去掉实验室后，正文仍能独立讲完机制；实验室只降低跟随成本。
5. 读者认为紧凑排版确实更舒服，而不是仅提高了每屏信息量。
6. 页面变短以后，原有事实、代码来源、正常与错误路径、验证状态没有漂移。

## 10. 推荐实施顺序

1. 先做局部排版 A/B，正文一字不改，由项目所有者选择阅读密度。
2. 再按 0 → 4 重组页面，先保证首读 0 → 1 → 2 连续成立。
3. 在“运行传输”页试做一种灰显上下文片段，验证定位与回查是否真正改善。
4. 最后调整实验室入口和实践任务，不同时改造其他章节。
5. 每一阶段经人工阅读确认后再进入下一阶段，不直接推广为全书模板。
