    B-B.4.4 SPI 调试与选型¶

    所属章节：第五部 B. 总线协议 > B-B.4 SPI 总线

    难度：[B→I] Beginner → Intermediate | 预计阅读时间：40 分钟

    本节导读¶

    B-B.4.1～B-B.4.3 已经分别建立 SPI 的位流、事务帧和 Linux 传输路径。本节追问一个调试问题：在 RK3568 SPI1 与 W25Q128JV-IQ/JQ 的受控实验环境中，怎样先完成一笔已知答案的 JEDEC ID 读取，再根据软件返回、回环、数字帧和模拟波形逐层定位异常？

    JEDEC ID 是器件按 JEDEC 标准返回的身份标识。贯穿实例固定为 Mode 0、8 位、MSB-first、低有效 CS 和 1 MHz 请求速率：

    MOSI：9F 00 00 00
MISO：?? EF 40 18
拍数：8 拍命令 + 24 拍响应 = 32 拍

    0x9F 是 Read JEDEC ID 命令，后三个 00 只用于继续提供时钟。?? 表示命令阶段的接收值不参与身份判断，不要求它等于 00 或 FF。EF 40 18 只适用于本例 IQ/JQ 后缀；IM/JM 后缀的 Device ID 不同，不能混用预期答案。

    本节覆盖：先走通一次 spidev_test 正常读取，再区分内部回环与外部短接的证据范围，用逻辑分析仪核对完整事务，用示波器检查时序和电气条件，最后把恢复验证与接口、速率选择收回同一笔事务。帧格式和时序细节归 B-B.4.2，设备创建与驱动匹配归 B-B.4.3，正式产品接入与烧录归 B-B.4.5。

    先建立可判定的正常基线¶

    受控实验的前置条件¶

    spidev：把 SPI 设备暴露为 /dev/spidevB.C 字符设备的内核驱动。B 是总线号，C 是片选号；用户态程序通过 open() 和 ioctl() 配置并发起传输。

    本节的正常路径是受控工具验证，不是正式 Flash（闪存）产品访问方式。开始前必须同时满足：

    1. 使用专用测试节点 spi1.0，其驱动已经绑定为 spidev，字符设备为 /dev/spidev1.0。
    2. 当前节点没有同时绑定 spi-nor（内核的 SPI NOR Flash 驱动）或其他协议驱动。不要在现场启动盘、已挂载根文件系统或其他业务正在访问的 Flash 上换绑驱动。
    3. 原理图确认 SPI1 CS0 确实连接本例 W25Q128JV-IQ/JQ，供电、共地、CS、MOSI、MISO 和必要的状态引脚符合器件手册。
    4. 当前账户有权读取 sysfs（内核导出设备对象与属性的文件系统）、打开字符设备并执行 spidev_test。工具取自 Linux v6.6 的 tools/spi/spidev_test.c，目标系统应使用与其内核 UAPI（用户态与内核之间的接口约定）兼容的构建版本。

    先检查绑定和字符设备。readlink 读取驱动符号链接，basename 去掉目录部分，test -c 检查路径是否为字符设备：

    basename "$(readlink /sys/bus/spi/devices/spi1.0/driver)"
test -c /dev/spidev1.0
printf 'char_device_check=%d\n' "$?"

    满足前提时，完整预期输出为：

    spidev
char_device_check=0

    spidev 证明当前绑定驱动名称，0 证明 test -c 成功。若 readlink 报错、名称不是 spidev 或字符设备不存在，应停止后续传输，按 B-B.4.3 检查控制器注册、设备创建和驱动匹配。设备存在与驱动绑定是两个阶段，不能用“没有 /dev”反推器件没有上电。

    用同一笔 0x9F 读取确认正常结果¶

    下面的 -D 选择设备，-s 1000000 把本次传输的请求上限设为 1 MHz，-p 给出四个发送字节，-v 打印收发缓冲区。TX 是发送缓冲区，RX 是接收缓冲区，RX[n] 表示从 0 开始编号的接收字节。工具会显式设置 Mode 0、8 位字长和 MSB-first；单条 SPI_IOC_MESSAGE(1) 让四字节处于同一笔全双工传输。

    spidev_test -D /dev/spidev1.0 -s 1000000 -p '\x9f\x00\x00\x00' -v
printf 'exit=%d\n' "$?"

    以下输出依据 v6.6 工具的打印逻辑和本器件手册推演，不是当前板卡实测。为展示完整格式，假设命令阶段的 RX[0] 恰好为 00；它不是身份判据，实际也可以是其他值。

    spi mode: 0x0
bits per word: 8
max speed: 1000000 Hz (1000 kHz)
TX | 9F 00 00 00 __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ |....|
RX | 00 EF 40 18 __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ |..@.|
exit=0

    逐段解读：

    • spi mode: 0x0 表示读回的模式为 Mode 0，未设置 CPOL、CPHA、LSB-first 等附加位。若控制器改写了请求模式，工具会先打印警告，不能把这里的值只当成用户输入。
    • bits per word: 8 表示每字 8 位，本例四字节对应 32 拍。
    • max speed 是用户态读回的请求上限，不是引脚实测频率。spidev 文档明确说明用户态无法通过该接口取得实际移位速率。
    • TX 是 9F 00 00 00。RX 中真正用于本例判断的是 RX[1]=EF、RX[2]=40、RX[3]=18。第一个 00 只是本示例对未知命令阶段接收值的占位。
    • 每行末尾的 __ 是工具把不足 32 字节的显示行补齐，竖线后是 ASCII 显示；不可打印字节显示为点，0x40 因而显示为 @。这些填充不是总线上额外的数据。
    • exit=0 由 shell 打印，表示工具正常返回。v6.6 工具在打开、配置或传输失败时通过 perror() 打印原因并调用 abort()，失败退出状态不应写成固定值，更不能解释成从设备返回了 NACK（Negative Acknowledgement，否定应答）。

    还要注意一个工具边界：spidev_test 对传输 ioctl 只检查返回值是否小于 1，没有向用户打印实际完成长度，也没有在普通 -p 路径中自动比较 TX/RX。因此，正常基线必须同时满足工具成功返回和有效位置的 ID 与器件后缀一致。SPI 没有低层 ACK，退出 0 本身不证明器件身份正确，更不证明其他速率、其他板卡或长期运行可靠。

    若打开设备失败，程序自身的典型错误行是：

    can't open device: No such file or directory

    这行只说明本次 open() 失败。应先检查节点、权限和绑定，不要继续改模式或短接引脚；shell 对 abort() 的附加诊断因环境而异，不把它拼进统一的工具输出。

    用回环缩小范围，但不夸大证据¶

    正常读取失败后，回环的作用是把外设协议答案暂时换成“发出什么，应收什么”。控制器内部回环与外部物理短接覆盖的路径不同，不能混为一个结论。

    内部回环：检查控制器提供的回环路径¶

    -l 设置 SPI_LOOP，-S 4 让工具生成四字节测试数据，-I 1 只执行一次。v6.6 在这条随机缓冲区路径中逐字节比较 TX/RX，不一致时打印 transfer error ! 并以 1 退出。RK3568 控制器驱动声明支持 SPI_LOOP。

    spidev_test -D /dev/spidev1.0 -s 1000000 -l -S 4 -I 1
printf 'exit=%d\n' "$?"

    若控制器接受回环模式、比较一致且本次执行未跨越工具的 5 秒统计间隔，完整预期输出为：

    spi mode: 0x20
bits per word: 8
max speed: 1000000 Hz (1000 kHz)
total: tx 0.0KB, rx 0.0KB
exit=0

    0x20 是 SPI_LOOP 模式位，CPOL/CPHA 仍为 0。0.0KB 是四字节除以 1024 后保留一位小数的结果，不表示没有传输。测试数据由 C 库的 random() 生成，本条命令没有 -v，所以不打印其内容；自动比较失败时打印的 TX/RX 也随数据而变，不能伪造一组固定失败输出。

    **内部回环成功只支持当前控制器回环配置和传输路径可工作，不证明外部引脚、焊接、连接线、CS 或 Flash 正常。**若出现模式不支持警告、传输失败或数据比较失败，先保留工具原始错误并检查控制器配置，不要把责任推给外设。

    外部短接：证据停在短接点¶

    外部回环需要在断电条件下，将指定测试点的 MOSI 与 MISO 短接，并隔离可能同时驱动 MISO 的 Flash。若保持 Flash 的数据输出引脚 DO 与主机 MOSI 对接，两个推挽输出可能争用，不能把这种接法当作无风险测试。短接点位于控制器测试焊盘、连接器还是器件引脚附近，决定了哪些线段被覆盖。

    恢复供电后，可沿用正常命令但不加 -l，此时预期 RX 与 TX 都是 9F 00 00 00。普通 -p 路径不会自动比较，必须人工或脚本逐字节核对。相等只说明短接点以内、当前配置下的收发路径一致，不能证明 Flash 会回答，也不能证明另一速率或其他 CS 正常。

    结束后必须断电、移除短接、恢复器件连接，再重新执行一次正常 JEDEC ID 读取。回环是隔离步骤，恢复正常事务才是收尾判据。

    让异常回到协议和电气机制¶

    全 00、全 FF：先确认线路是否静止，再列候选机制¶

    在本例有效响应位置，全 00 或全 FF 都不符合 IQ/JQ 后缀的 EF 40 18，但它们不指向唯一根因。MISO 可能因上拉、下拉或输入默认状态保持固定电平，也可能因 CS 未选中、器件未就绪、DO 高阻、接线错误、采样配置错误或器件实际返回固定数据而呈现相同结果。普通数据读取中的全 FF 甚至可能是擦除后的合法内容，不能脱离命令语义判断。

    下一项有区分度的观察是完整数字帧：

    • MOSI 上没有 9F 00 00 00，先查用户缓冲区、控制器、pinctrl（引脚复用配置）和片选路径。
    • MOSI 正确而 CS 未覆盖 32 拍，先查 CS 配置、映射和事务边界。
    • CS、SCLK、MOSI 都符合预期而 MISO 始终不动，再查器件供电、复位、DO 驱动权和输入门限。
    • 线上已经出现 EF 40 18 而用户缓冲区不同，应回查软件接收长度、偏移和交付路径。

    上电就绪也必须按具体器件判断。W25Q128JV Rev F 的 tVSL 是器件达到最低工作电压 VCC(min) 后到允许拉低 CS 的时间，最小 20 μs；写指令另有不同的上电约束。不能把一次全 00／全 FF 直接归成固定毫秒延时问题，更不能在未读手册前随意加 msleep()（内核毫秒级睡眠函数）。

    数据错位：分别检查采样位置、帧边界和软件偏移¶

    本例没有地址和 dummy（器件规定的额外等待时钟），正常结构只有 8 拍命令与 24 拍响应。若逻辑分析仪在正确采样边沿得到 EF 40 18，而用户态结果整体移动，应检查软件是否错误解释了 RX[0] 或遗漏前导。若线上位流本身错位，则检查 CPHA 是否改变采样边沿、CS 是否提前结束事务、SCLK 是否出现额外跳变。

    对于 B-B.4.2 的 Fast Read，还要多检查命令、地址和 dummy 的前导拍数；不能把那条命令的 RX[0]／RX[5] 结论机械搬到本例 JEDEC ID。两篇事务不同，判别依据始终是“哪一拍进入有效数据、接口保留哪些接收字节”。

    位序反转：用受控数据验证假设¶

    MSB-first 与 LSB-first 描述每个字内部哪一端先上线。若把预期的 EF 40 18 逐字节反转位序，会得到 F7 02 18；0x18 恰好正反相同，因此前两个字节更有区分度。这组值只能形成位序假设，不能单独证明根因。

    应回到已知发送数据的回环：内部回环检查当前控制器的位序路径，隔离后的外部短接再检查到短接点的线路。若受控 TX/RX 也呈逐位反转，才检查主从位序配置；若回环正确而器件响应异常，则继续检查器件手册要求的位序和实际帧。不要在普通通信中仅凭一个 0x80 就宣布 LSB/MSB 配错。

    降速恢复：说明与频率相关，不等于定位到信号完整性¶

    保持正常读取的其他前提不变，只把请求速率改为 100 kHz：

    spidev_test -D /dev/spidev1.0 -s 100000 -p '\x9f\x00\x00\x00' -v
printf 'exit=%d\n' "$?"

    若本次成功，完整预期输出如下。仍假设不参与判断的 RX[0] 为 00，它不是实测值：

    spi mode: 0x0
bits per word: 8
max speed: 100000 Hz (100 kHz)
TX | 9F 00 00 00 __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ |....|
RX | 00 EF 40 18 __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ __ |..@.|
exit=0

    除 max speed 变为 100 kHz 外，字段含义与正常基线相同。若高速时异常而这次恢复 EF 40 18，只能说明故障表现与频率或可用时间窗口相关。

    候选机制包括超过器件或控制器限制、Flash 输出有效延迟、走线传播、主机输入建立时间不足、边沿过慢、过冲和振铃。下一步应先用逻辑分析仪确认数字帧是否仍符合 32 拍，再用示波器在接收端附近检查真实电平和采样窗口；不能仅凭“低速能读”宣布走线或端接就是根因。

    对当前 RK3568 v6.6 驱动，分频实现选择不小于理想值的偶数分频，使结果不超过请求速率。这个控制器事实不能推广为所有 SoC（System on Chip，片上系统）控制器，也不能代替实测。对照结束后应恢复 1 MHz 请求并再次读取，确认结果变化确实跟参数修改同时出现，而不是一次偶然成功。

    升速或降速对照都遵守三条纪律：**一次只改一个参数；每项结果写明能支持什么、不能支持什么；结束后恢复原参数并复测正常 ID。**B-B.4.5 的提速验证沿用这三条纪律，不把一次低速成功当成永久修复。

    偶发故障需要有限次数、明确判据的记录：每次都检查 ioctl 结果、有效 ID 和实际测试条件，再统计失败数。普通 spidev_test -p 不会自动比较数据，单纯用 while true 循环它并不能得到错误率。

    数字帧与模拟波形各自回答什么¶

    逻辑分析仪用于核对数字关系。本例应从 CS 有效开始，确认 Mode 0 的空闲低、上升沿采样、32 个时钟、MOSI 的 9F 00 00 00，以及有效响应位置的 EF 40 18。解码器的 CPOL、CPHA 和位序应由这些可观察事实与手册确定，不能反复切换直到结果“看起来合理”。采样率、触发和存储深度按仪器带宽与需要捕获的完整事务设置，不使用统一倍数代替测量条件。

    示波器用于核对模拟条件。应在接收端附近观察 CS、SCLK 和相关数据线，按主从手册检查输入高低门限、过冲与下冲限制、边沿形态、输出有效到采样之间的窗口。0.9 VCC 或 0.5 VCC 在某些手册图中可能只是测量参考电平，不能直接当作所有器件的输入合格门限。

    B-B.4.2 已给出 MISO 的时间预算：

    启动边沿到采样边沿的间隔
≥ tCLQV(max) + 走线传播 + 主机建立时间 + 设计余量

    数字解码正确，说明分析仪在自己的门限和采样条件下识别出了预期位流，不证明接收端具有充分模拟裕量。反过来，波形边沿漂亮也不能证明命令、位序和器件应答正确。两类仪器各自提供一部分证据。

    多从机场景还要加入驱动权检查：只选中目标 CS，其他从机应按各自手册释放 MISO。若某从机未释放，或 reg 把访问引到另一 CS，主机同样可能读到固定值或争用后的无效电平。电气机制见 B-B.4.1，DTS 的 CS 与设备对象关系见 B-B.4.3。

    本文没有取得当前板卡的逻辑分析仪或示波器记录，以上均为验证方法和由手册推出的预期，不是实测波形。

    把调试证据用于速率和接口选择¶

    同一笔事务已经说明，速率不是设备树中的一个孤立数字。可用上限同时受控制器能力、外设手册、完整命令格式和板级时序约束。请求频率写入后，还要确认控制器实际分频和接收端采样窗口。

    比较接口时，先算完整事务而不只算有效载荷。若一笔操作需要 N 个时钟，频率为 f，纯时钟时间就是：

    T_clock = N / f

    本例在 1 MHz 下为 32 / 1 MHz = 32 μs，不包含 CS、软件调度和其他事务开销。数据量增大时，应按器件命令重新计算命令、地址、dummy、数据及内部忙时间，不能把某一笔 32 拍读取外推成所有 SPI 操作的固定成本。

    SPI 适合需要较高串行带宽、独立全双工数据路径或明确片选控制的器件；I2C 是带器件地址和接收确认的双线总线，在引脚受限、事务较短且需要 ACK 的场景更有吸引力。I2C 的实际设备数量、速率和功耗仍受地址、模式、上拉和总线电容约束，机制见 B-B.3.1～B-B.3.2。两种接口都不能只凭“某类器件通常使用它”决定。

    QSPI（四线 SPI）和 OSPI（八线 SPI）等扩展接口还要逐阶段重新数线数和拍数，不能把数据阶段的优势直接乘到整笔事务。Flash 的页编程、擦除和 BUSY（器件内部忙标志）等待属于器件内部过程，读写选择应分别计算；W25Q 的产品接入和写路径归 B-B.4.5。

    本节总结 [B→I]¶

    SPI 调试从一笔已知答案的正常事务开始。本例先确认 spidev 绑定，再用 9F 00 00 00 取得 EF 40 18，分别检查工具返回和有效身份数据。之后的每项观察都要回答它能缩小到哪一层、仍不能证明什么。

    内部回环、外部短接、逻辑分析仪和示波器不是可以互相替代的成功标志。全 00、全 FF、错位、位序反转和降速恢复都只是现象，必须回到采样、帧边界、软件偏移、驱动权和电气预算寻找具有区分度的下一项证据。恢复接线与配置后重新得到正常 ID，才完成本次调试闭环。

    选型沿用同一条证据链：先算完整事务，再比较控制器、器件和板级限制。SPI 与 I2C 各有适用条件，不存在脱离数据量、引脚、ACK、总线负载和写忙时间的通用器件分界。

    本节自查¶

    Q1. 为什么本例不能只凭 exit=0 宣布 W25Q128JV-IQ/JQ 已正常识别？

    SPI 没有低层 ACK，工具成功返回不等于器件身份正确。还要检查有效位置的 RX[1]～RX[3] 是否为 EF 40 18，并确认器件后缀。RX[0] 不参与判断，退出 0 也不能证明长期稳定或模拟裕量。

    Q2. 内部回环与外部短接各自能排除什么，为什么都不能代替正常 JEDEC ID 读取？

    内部回环检查控制器提供的回环配置和传输路径，不覆盖外部引脚与 Flash。外部短接把证据扩展到短接点，但不检查从设备应答。两者结束后都要恢复正常连接并重新读取 JEDEC ID，才能确认回到真实器件的已知事务。

    Q3. 全 FF 为什么不能直接等同于 MISO 上拉且从设备未驱动？

    固定高电平只是其中一种可能。错误 CS、器件未就绪、采样配置、接线、器件实际返回固定数据等也可能产生相同结果。应继续观察完整 CS、SCLK、MOSI、MISO 和软件交付位置，用下一项证据区分候选机制。

    Q4. 线上已经解码出 EF 40 18，用户缓冲区却整体错位，应优先检查什么？

    先检查软件接收长度、前导保留约定和缓冲区偏移，因为数字线上的数据已经正确。本例 JEDEC ID 只有 8 拍命令与 24 拍响应，不应机械套用 Fast Read 的 dummy 或 RX[5] 结论。

    Q5. 为什么 F7 02 18 只能提示位序问题，不能直接定案？

    它恰好是 EF 40 18 的逐字节位序反转，但普通通信中的数据还受其他机制影响。需要用已知发送数据的内部回环或隔离后的外部短接验证位序路径，再核对器件手册，不能靠一次模式切换后“看起来合理”来定案。

    Q6. 降速后恢复 EF 40 18，下一步为什么还要看数字帧和模拟波形？

    降速只证明故障与频率或时间窗口相关。逻辑分析仪用于确认 32 拍和有效数据是否仍正确，示波器用于检查接收端门限、边沿和采样窗口；两者结合后才能区分钟格式、输出有效、传播、建立时间和信号质量问题。

    Q7. 为什么普通 while true; do spidev_test -p ...; done 不能直接统计错误率？

    普通 -p 路径不会自动比较 TX/RX，工具也不向用户打印实际完成长度。没有逐次检查有效 ID、返回结果和测试条件，就无法区分成功与失败。统计必须使用有限次数和明确判据，并保留失败记录。

    Q8. 用 1 MHz 完成本例读取为什么只能算出 32 μs 的纯时钟时间，选型时还要补哪些条件？

    本例共 32 拍，所以 N/f=32 μs。完整操作还包括 CS、软件和调度开销；换命令要重新计算地址、dummy、数据和内部忙时间。接口与速率选择还要同时考虑控制器、器件、引脚、ACK、总线负载和板级时序。
