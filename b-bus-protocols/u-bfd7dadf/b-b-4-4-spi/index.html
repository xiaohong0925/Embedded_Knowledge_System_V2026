    B-B.4.4 SPI 调试与选型¶

    所属章节：第五部 B. 总线协议 > B. 低速外设接口 > SPI

    难度：[I] | 预计阅读时间：45 分钟

    本节导读¶

    SPI "用起来简单，调起来头疼"：没有 ACK 机制，任何配置错误都表现为静默的数据错乱——主机发了，从设备收了，双方都不觉得有错，只有数据对不上。但 SPI 故障的分布高度集中——模式、速率、CS、信号完整性四类占了绝大多数，排查路径因此可以收敛成固定流程。本篇前半是排障方法论，后半解决另一个工程问题：新方案设计时，这颗外设该选 SPI 还是 I2C。

    读本篇需要的背景：四种模式的 CPOL/CPHA 定义（4.1）、帧分段结构命令/地址/dummy/数据（4.2）、驱动框架（4.3）。本篇遇到这些概念只做最小回顾。

    本节覆盖：SPI 排查三原则与决策树（先软件后仪器的成本逻辑）、五类高频故障对照表、降速验证的三个操作入口与解读纪律、多从设备共享总线纪律、spidev_test 回环二分法与输出解读、内核侧观察手段、示波器四要点与逻辑分析仪设置、SPI vs I2C 九维选型对比、典型设备的接口选择、QSPI/OSPI 的读写不对称陷阱。按"坏了怎么查 → 查的工具怎么用 → 新设计怎么选"展开——这正是你实际遇到 SPI 问题的时间顺序：先救火，再复盘选型。

    读完你应该能独立完成三件事：面对一个"数据全错"的 SPI 故障，按决策树在十分钟内把故障域缩到一类；面对一个新外设选型，用九维对比表给出有理由的接口决策；面对多从设备总线设计，说清三条共享纪律与各自的故障形态。

    排查三原则与决策树¶

    SPI 没有 ACK 告诉你"收错了"，排查必须从最便宜的假设开始逐项排除。三条原则是：假设按命中率排序、手段按成本排序、每步必须缩小故障域——一步做完要么排除一类、要么指向下一类，不允许"试了一圈不知道排除了什么"。

    ① 核模式（成本 1 分钟）
   CPOL/CPHA/位序与从设备手册逐项对照——最高频故障
   ├─ 不一致 → 改 spi_mode 收工
   └─ 一致 ↓
② 降速验证（成本 5 分钟）
   SCLK 降到 1 MHz 甚至 100 kHz
   ├─ 降速后正常 → 信号完整性问题（走线/端接/飞线），回 4.1
   └─ 依旧异常 ↓
③ 抓波形对照（上仪器）
   按 4.2 的分段法：命令/地址/dummy/数据逐段对手册
   CS 是否全程稳定？SCLK 频率实测是否等于配置值？

    CPOL / CPHA（Clock Polarity / Phase，时钟极性/相位）：SPI 模式的两个布尔量——CPOL 决定 SCLK 空闲时停在高还是低，CPHA 决定数据在第一个还是第二个边沿采样。两两组合出 Mode 0~3 四种模式（4.1 有完整时序）。调试时只需记住：模式错=采样边沿错=数据整体错位，它是"数据全错但时序看着挺像"的第一嫌疑。

    先用软件手段（①②）排除八成的逻辑类故障，再上仪器（③）处理剩下两成的信号类故障。顺序反了是 SPI 调试最常见的浪费时间方式——仪器架起半小时，最后发现是模式写错，软件核对一分钟的事。

    为什么这个顺序是对的？因为三类检查的成本与命中率的乘积最优：核模式一分钟能排除最高频故障；降速五分钟把"逻辑错"与"信号错"一刀切分开；只有剩下两成才值得架仪器。这也是所有无 ACK 总线（SPI、1-Wire、自定义串行）通用的排障骨架——B.3.4 的 I2C 决策树是同一方法论的另一个实例。

    降速验证的操作入口有三个，按场景选：

    # 临时验证：spidev_test 直接指定速率，不碰任何配置
spidev_test -D /dev/spidev1.0 -s 1000000        # 降到 1 MHz

# 设备树固化：从设备的 max-frequency 属性
# spi@xxx { flash@0 { spi-max-frequency = <10000000>; }; };

# 驱动内逐事务：spi_transfer.speed_hz 覆盖本次传输

    注意"降速后正常"的解读纪律：它证明高速下有信号完整性问题，不证明低速就是正确答案——根因（走线/端接/飞线）还在，量产温度角会复发。降速是定位手段，不是修复手段。

    五类高频故障对照¶

    故障 症状 根因 定位 处理
    模式不匹配 数据错位、全 0x00/0xFF、位镜像 CPOL/CPHA/位序与手册不一致 ①核配置；波形看 SCLK 空闲电平 更正 mode/位序
    速率过高 偶发错误、温度相关、重试可恢复 超从设备上限或走线 SI 极限 ②降速二分 降速/缩线/串 22~47 Ω
    CS 异常 多收/少收字节、帧边界乱 CS 毛刺、GPIO 模拟时序不严、事务中途拉高 示波器单次触发抓 CS 硬件 CS、查驱动逻辑
    信号完整性 随机错、无响应、过冲振铃 走线长、无地回路、无端接 示波器看过冲/边沿 缩线/端接/降速
    上电时序 偶发启动失败、首笔超时 从设备未就绪主设备就发命令 电源与 CS 同屏观察 probe 加延时、查复位时序

    逐行展开三个值得说透的机理：

    • "全 0x00/0xFF"的指向性：读到全 0xFF 是 MISO 线被上拉且从设备没驱动（CS 没生效、从设备没上电、或 MISO 断线）；全 0x00 是 MISO 被钳到低。两个"全一样"的值其实是两种不同的硬件故障域——先别急着改模式，看一眼读到的是哪个"全"。
    • CS 毛刺为什么致命：从设备的帧边界判定完全依赖 CS——CS 拉高再拉低就是"上一帧结束、下一帧开始"。一个几十纳秒的毛刺，在从设备状态机里就是一次完整的帧结束+帧开始，后面的字节全部错位。GPIO 模拟 CS 在多线程环境被抢占，拉低到传数之间被调度出去，从设备看到的就是一个"超长事务"。

    • 上电时序的偶发性：从设备（尤其带内部固件的 RF 芯片、Flash）上电后需要 tPU（上电就绪时间，手册给出，ms 级）才能响应命令。主控 probe 跑得快，第一笔命令打在还没就绪的从设备上——冷启动偶发失败、热复位必现，是它的特征签名。以 W25Qxx 为例：手册给的 tPU 是上电到第一条命令的最小间隔，量产板上 VCC 爬升斜率受电源设计与温度影响，爬升慢的批次故障率就高——probe 里加 msleep() 兜底之前，先把手册的 tPU 与复位释放时序读出来。

    • 偶发错误要做统计，不要靠手感：速率类与 SI 类故障是概率事件，"试两次好了"不构成结论。用循环脚本压测（while true; do spidev_test ...; done）跑几千次统计错误率，再对比改前改后——偶发故障的修复验证必须是统计意义上的。

    💡 走线超 30 cm 且时钟超 10 MHz 时反射不可忽略：振铃让从设备在错误边沿采样，表现为"随机"错误。修复三选一：缩到 10 cm 内、源端串 22~47 Ω、降到 1 MHz 以下。飞线调试本身就是 SI 风险源——"飞线能跑通"不能证明设计没问题，"飞线跑不通"也不能证明代码有问题。

    多从设备共享总线的纪律¶

    SPI 总线挂多颗从设备是常态（Flash + 显示屏 + RF 芯片同挂 SPI1），共享带来三条纪律：

    • CS 一一对应，空闲必须全高：任一时刻只允许一颗设备的 CS 有效。两颗同时拉低，MISO 上两个驱动器对打，轻则数据错乱，重则烧 IO——设备树的 reg 属性就是 CS 号，填错等于选错设备。
    • 模式可以不同，但切换要干净：设备 A 用 Mode 0、设备 B 用 Mode 3 是合法的，控制器在选中不同设备时重新配置模式。Linux 侧由 spi_setup()/传输参数保证，每次选中设备前框架会重配——但自己用 GPIO+bitbang 玩 SPI 时，切设备忘切模式是经典 bug。
    • 速率按各设备上限分别配：spi-max-frequency 是每设备属性，框架自动在事务间切换。共享总线的实际吞吐受最慢设备与切换开销影响，别把最快设备的标称速率当总线能力。

    多设备场景的调试推论：故障只在挂某颗设备时出现，先怀疑那颗设备的 MISO 三态能力——CS 拉高后 MISO 必须释放为高阻，不支持三态的从设备会钳住总线，连累其他设备。

    工具链¶

    回环测试：一刀切成两半¶

    spidev_test 是内核自带的 SPI 测试工具（源码在 tools/spi/spidev_test.c），它最有价值的用法是回环：把 MOSI 和 MISO 物理短接，发出去什么就该收回来什么：

    spidev_test -D /dev/spidev1.0 -v

    一份典型输出：

    spi mode: 0x0
bits per word: 8
max speed: 500000 Hz (500 kHz)
TX | FF FF FF FF FF FF 40 00 00 00 00 95 FF ...
RX | FF FF FF FF FF FF 40 00 00 00 00 95 FF ...

    逐字段看三个要点：

    • TX 与 RX 完全一致 = 控制器侧无恙——pinctrl 复用、时钟分频、控制器驱动、DMA 这一整链都对了，故障域只剩从设备侧（接线、从设备本身、模式/时序）。一次短接把故障域砍掉一半，这就是二分的价值。
    • RX 全 0xFF 或全 0x00 = 短接没生效或 MISO 引脚复用错了——连回环都不通，先查 pinctrl 和接线，别碰从设备。
    • max speed 行只是请求值——实际频率受分频取整影响，要示波器实测（见下）。

    内核侧观察¶

    dmesg | grep -i spi            # 控制器注册、spi-nor 识别日志
ls /sys/bus/spi/devices/       # 设备实例化确认
cat /sys/bus/spi/devices/spi1.0/modalias    # 匹配的 compatible

    ls 里没有预期设备，是设备树没实例化（compatible 不匹配、reg 填错 CS 号）；有设备但驱动没绑上，看 modalias 与驱动 of_match_table 是否对上。这两条把"设备树问题"与"总线问题"分开——设备树问题在波形上是看不到任何东西的。

    需要用户态临时验证时，spidev 驱动把 SPI 控制器暴露成字符设备（/dev/spidevB.C，B=总线号 C=CS 号），open/ioctl 即可收发——内核文档 Documentation/spi/spidev.rst 有完整接口说明。它是 bring-up 阶段"先绕过正式驱动验证硬件通路"的标准做法，但量产代码不该依赖它（无并发仲裁、无电源管理）。

    示波器四要点¶

    1. SCLK 实测频率与占空比：分频取整可能让实际频率偏离配置值（配 50 MHz 实测可能 48 或 62.5 MHz）；占空比严重偏离 50% 说明驱动或负载问题。
    2. 数据边沿位置：CS 下降沿触发，对照手册确认采样边沿——判断模式匹配的最直观方法。
    3. CS 质量：单次触发抓 CS 全程，几十纳秒的毛刺也足以让从设备误判帧边界。
    4. 幅度与过冲：高电平应 ≥90% VCC；过冲超 10% 说明阻抗不匹配，需端接。

    读波形时记住两个"特征形状"：振铃（边沿后的衰减振荡，像敲了一下钟）说明走线电感与负载电容形成谐振，振铃穿过逻辑门限就会多触发一次采样；圆角沿（上升沿拖成斜坡）说明走线电容太大或驱动太弱，采样点落在斜坡上就是电平判决的抛硬币。两个形状分别对应"串阻阻尼"与"降速/换强驱动"的修复方向。

    逻辑分析仪¶

    接线：SCLK / MOSI / MISO / CS 四通道 + 共地
采样率：≥ SCLK × 4（8 MHz 总线用 32 MHz 以上）
触发：CS 下降沿，预触发 25~50%
解码器：SPI，Enable=CS Active Low，Bit Order=MSB First

    解码结果按 4.2 分段法对照手册：命令/地址/dummy/数据逐段核对。CPOL/CPHA 不确定时，解码器里切换组合直到数据合理——这是"仪器反推模式"的合法用法，比翻代码猜配置快。

    💡 示波器与逻辑分析仪是互补不是替代：示波器看模拟特性（过冲、振铃、边沿速率），逻辑分析仪看数字序列（命令对不对、数据错在哪字节）。"数据对不上"先上分析仪看序列对不对，序列对再出示波器看波形质量——这个顺序与决策树的"先逻辑后信号"同构。

    SPI vs I2C 选型对比¶

    维度 SPI I2C
    速率 1~50 MHz（QSPI 更高） 100k~1 MHz
    引脚 4 线起，每从机 +1 CS 恒定 2 线，挂百余设备
    双工 全双工 半双工
    寻址 无地址，靠 CS 7/10 位地址帧
    应答/流控 无 ACK、无流控 ACK 握手 + 时钟延展
    多主 不支持 原生仲裁
    标准规范 无统一标准，时序因厂而异 NXP UM10204 严格规范
    故障可见性 静默错乱（无 ACK） NACK 可直接观测
    功耗 推挽，静态功耗低 上拉电阻持续耗电

    决策一句话：要速度、要全双工、点对点——SPI；要省引脚、多设备、多主、低速控制——I2C。

    两个表格之外的实战推论：

    • "无统一标准"是 SPI 的隐形成本：每接一颗新芯片都要重新核对模式、位序、CS 极性、最大速率——I2C 设备手册大同小异，SPI 设备手册各有各的怪癖。维护多器件 SPI 总线的长期成本比引脚数看起来更贵。
    • 故障可见性差异决定调试成本：I2C 的 NACK 让"从设备没收到"直接可见；SPI 的一切错误都要靠数据内容反推。本章前半的整套决策树，本质上就是在补偿 SPI 没有 ACK 这件事。
    • I3C 正在侵蚀 I2C 的低功耗领地：电池产品里 I2C 上拉电阻的持续耗电曾是选 SPI 的理由之一，I3C 推挽化后这条优势被抹平（B.6 板块）。新设计的低速传感器选型，把 I3C 加进候选名单再决策。

    典型设备的接口选择¶

    设备类型 主流接口 速率 选择理由
    NOR Flash SPI/QSPI 20~80 MHz 吞吐决定烧录与启动时间
    OLED/LCD 小屏 SPI 10~40 MHz 帧数据量大；大屏视频用 RGB/MIPI（C.9 板块）
    ADC/DAC SPI 为主 1~20 MHz 采样率与时钟直接相关
    RF 收发器 SPI 为主 1~10 MHz 寄存器配置 + FIFO 数据
    温湿度传感器 I2C 为主 100~400 kHz 数据量小，省引脚
    加速度计/陀螺仪 两者皆有 高采样选 SPI >1 kHz 采样率 I2C 吃力
    触摸屏 I2C 为主 100~400 kHz 坐标数据量小
    EEPROM 小容量 I2C / 大容量 SPI — 分界线约 64 KB

    QSPI/OSPI 的选型决策¶

    机制已在 4.2 讲过，这里只给选型视角：

    • XIP 就地执行（代码直接跑在 Flash 上）：QSPI 是事实标准；
    • 大容量固件/资源存储（64 MB+）：OSPI 读速接近 SD 卡；
    • 成本敏感小系统：标准 SPI Flash 兼容性最好。

    一个把选型落到数字的例子：4 MB 固件用 40 MHz 单线 SPI 读出约 0.8 s，QSPI 四线缩到约 0.2 s——对"开机先等 Flash"的产品（仪表、家电），这 0.6 s 就是用户能感知的开机速度；而对数据记录器，写入瓶颈在 Flash 内部页编程时间（典型 0.6~3 ms/页），总线多宽都帮不上忙。

    ⚠️ QSPI/OSPI 的带宽优势几乎只在读路径：写入（页编程）多数仍走单线模式，且受 Flash 内部编程时间限制（ms 级）。频繁写入的场景（数据记录器），多线模式帮不上忙——选型时看的是写速，别被读速宣传误导。

    方案对比（Trade-off）¶

    维度 评价
    硬件 CS 时序精确无毛刺；代价是占用控制器片选资源
    GPIO 模拟 CS 片选数量不受限；代价是时序受调度影响、毛刺风险
    示波器 信号质量金标准；代价是贵、长时捕获弱
    逻辑分析仪 长时捕获+协议解码便宜；代价是看不到模拟特性
    高速 QSPI 读吞吐 ×4；代价是引脚、布线、写路径无收益

    本节总结¶

    SPI 调试的全部方法论收束成一句话：它没有 ACK，所以你要自己制造可见性。决策树"核模式 → 降速 → 抓波形"是按成本×命中率排序的固定流程，先软件后仪器是铁律；spidev_test 回环一次短接把故障域切成控制器侧/从设备侧两半，是性价比最高的一刀；五类故障（模式、速率、CS、信号完整性、上电时序）各有特征签名——全 0xFF 与全 0x00 指向不同硬件故障域，CS 毛刺几十纳秒就够毁掉帧边界，偶发冷启动失败先查从设备就绪时间，偶发错误的修复验证必须落到统计意义上。多从设备共享总线时，CS 纪律、模式切换、MISO 三态是三个独立故障源。选型侧，SPI vs I2C 九维对比的一句话决策之外，记住两条隐形成本：SPI 无统一标准导致每颗新芯片都要重核时序，无 ACK 导致调试成本结构性地高于 I2C。QSPI/OSPI 的带宽宣传只覆盖读路径，写密集场景按页编程时间选型。

    关键结论 一句话记忆
    决策树 核模式（1min）→ 降速（5min）→ 抓波形（半小时），别反着来
    回环二分 MOSI 短接 MISO 跑 spidev_test，TX=RX 则控制器侧无恙
    全 0xFF/0x00 不是模式问题：MISO 没被驱动/被钳低，先查接线与供电
    CS 毛刺 几十 ns 即毁帧边界；GPIO 模拟 CS 要防调度抢占
    实测频率 分频取整会让 50 MHz 变 62.5 MHz；示波器量，别信配置值
    选型一句话 速度/全双工选 SPI，省引脚/多设备/多主选 I2C
    QSPI 陷阱 读速×4 写速不变；写密集场景按页编程时间选型
    多从设备 CS 空闲全高；切设备框架自动重配模式/速率；查从设备 MISO 三态
    降速纪律 降速正常=高速有 SI 问题；降速是定位手段不是修复手段
    振铃/圆角沿 振铃→串阻阻尼；圆角沿→降速或换强驱动
    偶发故障 循环压测统计错误率，"试两次好了"不构成结论
    设备树分层 dmesg/sysfs 区分"没实例化"与"没绑定"；设备树问题波形上看不到东西
